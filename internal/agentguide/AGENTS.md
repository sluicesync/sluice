# AGENTS.md — driving sluice as an AI agent

sluice is a single-binary CLI that migrates and continuously syncs databases (MySQL ↔ Postgres in all four directions, plus SQLite / Cloudflare D1 import and sync). It is built for you: **no command ever blocks on a prompt when you drive it** (flags, environment variables, optional YAML config). A destructive command asks for confirmation only when stdin is a real terminal and `--yes` is absent; on a pipe, a CI runner, or any other non-terminal stdin it refuses with `SLUICE-E-CONFIRMATION-REQUIRED` (exit 3) before touching anything — pass `--yes` to proceed. Destructive operations require explicit opt-in flags, and ambiguous states refuse loudly with a named remedy instead of proceeding. This file is the operating guide for agents *using* the CLI; contributor/development guidance lives in `CLAUDE.md` and `CONTRIBUTING.md`.

## Command taxonomy

**Read-only — safe to run without approval.** These never modify either database: `sluice schema preview`, `sluice schema diff`, `sluice verify`, `sluice sync health`, `sluice sync status`, `sluice engines`, `sluice backup verify`, `sluice control-tables ddl` (prints the control tables' CREATE statements — on `--engine postgres` also the ADD COLUMN / CREATE INDEX / UTC-DEFAULT follow-ups; opens no connection), `sluice backfill --verify-only` (counts rows matching `--where`; no UPDATEs, no control-table writes), and **any command with `--dry-run`** (`expand-contract --dry-run` and `deploy-ddl --dry-run` additionally make zero control-plane calls).

**State-changing — run only as part of an approved task.** These write to the target (and create bookkeeping objects — see `docs/database-objects` on the docs site): `sluice migrate`, `sluice sync start`, `sluice sync run`, `sluice backup *` (writes to the backup store; `backup export-as-parquet` is read-only against the chain but writes Parquet files to its destination), `sluice restore`, `sluice cutover`, `sluice schema add-table`, `sluice trigger setup/teardown/prune`.

**Production-mutating schema-change commands — treat like state-changing, but the writes hit a PRODUCTION database in place**, not a migration target:

- `sluice backfill` — issues real `UPDATE`s against the one database named by `--dsn` (keyset-chunked, resumable; `--dry-run` and `--verify-only` are the read-only forms)
- `sluice deploy-ddl` — ships one DDL statement to a PlanetScale **production branch** via a deploy request
- `sluice expand-contract` — deploy-requests an `ADD COLUMN`, runs the backfill, and (only with `--yes`) deploy-requests the `DROP COLUMN` contract step

**Destructive flags — NEVER pass without explicit human approval for that specific invocation.** Approval to migrate is not approval to destroy:

- `--reset-target-data` — drops/truncates target tables before copy. On a `sync` stream it also discards the tables `sluice schema add-table` brought in (a WARN names each; they receive no changes afterwards — name them in `--include-table` or add them again). Added tables otherwise stay in the stream's scope whatever `--include-table` says
- `--restart-from-scratch` (`sync start`) — re-copies every table the stream applies, the added tables included, onto the populated target
- `sluice schema add-table --abandon <table> --yes` — takes a table out of a stream (marks a dead add abandoned, or removes a completed add's table from the live-added set, after which the next start stops applying it and records it as dropped); the only way a table `schema add-table` brought in leaves the stream's scope
- `--force-cold-start` — bypasses the populated-target safety preflight
- `--yes` — the destructive-confirmation opt-in on `--reset-target-data`, `schema add-table`, `trigger teardown`, `slot drop` and `sync decommission`; without it these refuse with `SLUICE-E-CONFIRMATION-REQUIRED` (exit 3) unless a human is at a terminal to answer the prompt. **On `expand-contract` it confirms the contract leg — a `DROP COLUMN` deploy request against the production branch** (without it the run stops after verify and prints the resume command)
- `backup prune` / `backup compact` without `--dry-run` — irreversibly drop backup history
- `sync decommission --yes` — drops a finished stream's replication slot + per-stream publication on the source and clears its control row on the target; the stream can never warm-resume after (preview with `--dry-run`, which needs no `--yes`)
- `--accept-unforwarded-schema-change=<fingerprint>` (`sync start`, `backup stream run`) — acknowledges a recorded `UNFORWARDED-SCHEMA-CHANGE` refusal. It accepts a source/target schema difference permanently unless the change was applied to the target first (for `backup stream`, unless a new full backup was taken first). A human applies the change; only then pass the fingerprint the replayed refusal prints, once. When the message also contains `ADD-COLUMN-BACKFILL-INCOMPLETE`, the column already exists on the target: the human repair is to copy the added column's values from the source for the rows that predate the `ADD COLUMN` (or re-copy with `--restart-from-scratch`), not to apply a change. This refusal exits **1 with no error code**, not 3, but it is still a decision point: every restart refuses again until it is acknowledged, so do not retry it
- `--accept-table-rename=<old>=<new>` (`sync start`) — acknowledges, for the `INCLUDE-TABLE-SCOPE-DRIFT` door, that `<new>` is the stream's table `<old>` renamed while the stream was stopped, where no engine-stable table id proves it (a PlanetScale/Vitess source, an encoded InnoDB name, a record without ids); the stream's record then follows the rename. A human decision: if `<new>` is in fact a different table, its target copy is wrong from then on. The record follows only when the target holds `<new>` and no longer `<old>`, and the target table under `<new>` is trusted as-is (sluice cannot check its content). Confirm the rename, and that the target table was renamed too.
- `--accept-slot-acked-past-position=<LSN>` (`sync start`) — acknowledges a `SLOT-ACKED-PAST-TARGET-POSITION` refusal (Postgres source): the replication slot was acknowledged past the position the target persisted, so resuming skips every change committed in between. The remedy is a re-copy with `--restart-from-scratch`, which is itself destructive and needs approval. Pass the flag only after a human has verified that the target already holds every change up to the LSN the refusal prints; it accepts the gap as skipped. An LSN that does not match the slot is refused

## The standard workflow

1. **Preview first**: `sluice migrate --dry-run --format json ...` — emits the full plan as JSON. Show it to the human before proceeding. To see the target DDL alone, `sluice schema preview` renders it with cross-engine translation notes.
2. **Run**: `sluice migrate --format json ...` — one JSON result envelope on stdout (see below).
3. **Verify**: `sluice verify --format json ...` — never report a migration done without it.
4. For continuous sync: `sync start --dry-run` → `sync start` → poll `sync health --format json` (exits 1 on breached thresholds, on durably skipped tables, on `CONTROL-TIMESTAMP-IN-FUTURE` — a stream row dated more than 60s ahead, whatever `--max-stale-seconds` says — on an add-table that stopped without completing (`ADD-TABLE INCOMPLETE`), or on one `--abandon` retired (`ADD-TABLE ABANDONED`: restart the stream); a `schema add-table` still running is exit 0 — cron/agent-friendly).

## Credentials: env-first, never in argv

Pass DSNs and secrets via environment variables, not flags — flags leak into process listings and shell history (crash-bundle redaction masks them, but env is the documented path):

| Variable | Holds |
|---|---|
| `SLUICE_SOURCE` / `SLUICE_TARGET` | source / target DSN (equivalent to `--source` / `--target`) |
| `CLOUDFLARE_API_TOKEN` | Cloudflare D1 API token (env-only; there is no flag) |
| `PLANETSCALE_METRICS_TOKEN_ID` / `PLANETSCALE_METRICS_TOKEN` | PlanetScale telemetry token |
| `PLANETSCALE_SERVICE_TOKEN_ID` / `PLANETSCALE_SERVICE_TOKEN` | PlanetScale service token (branch + deploy-request scopes) for `expand-contract`, `deploy-ddl`, and `migrate`'s index-build fallback — the pscale CLI convention; the `--service-token*` flags exist but the env vars are the documented path |
| `SLUICE_NOTIFY_WEBHOOK` / `SLUICE_NOTIFY_SLACK` | notification sink URLs (the URL path is the credential) |
| `SLUICE_NOTIFY_SMTP_PASSWORD` | SMTP auth secret (env-only by policy) |
| `--encryption-passphrase-env NAME` | names the env var holding the backup passphrase |

## Machine-readable output

- **`--format json`** on the primary verbs — `migrate`, `sync start`, `backup full`, `restore` — emits exactly one JSON result envelope as the last write to stdout on every exit path: `{"command","status":"completed|refused|failed","elapsed_seconds","source_engine","target_engine","tables":[...],"resume":{...},"error":{"message","code","hint"},"next_steps":[...]}`. `status:"refused"` means sluice declined by policy (loud-failure) — read `error.hint` for the remedy; `"failed"` means something broke mid-run. With `--dry-run` the same flag emits the plan instead: `{"command","dry_run":true,"plan":{...}}`.
- **`--format json`** also on: `verify`, `schema diff`, `schema preview`, `cutover`, `sync health`, `sync status`, `matview refresh`.
- **`--log-format json`** (global) — one JSON slog object per line on stderr; terminal coded errors carry `code` and `hint` attributes.
- Envelopes and logs never contain credentials; DSNs render as credential-free locators.

## Error codes and exit codes

Stable machine-parsable error codes (`SLUICE-E-*`) with remedy hints ride on the JSON envelope's `error` object and the JSON log stream — branch on `code`, show `hint` to the human. The full table: `docs/operator/error-codes.md`.

| Exit | Meaning |
|---|---|
| 0 | success |
| 1 | runtime failure (also: verify/diff drift found) |
| 2 | config-file error (verify-family: could not run) |
| 3 | named refusal — sluice declined by policy; the error names the remedy |
| 80 | CLI usage/parse error (kong) |

`!= 0` always means not-success. On exit 3, do not retry unchanged — surface `error.hint` to the human and wait for a decision (the remedy is often a destructive flag that needs approval). <!-- restart-refusal-roster --> One refusal has no code yet and exits 1: a message containing `UNFORWARDED-SCHEMA-CHANGE` from `sync start` / `sync run` / `backup stream run`. Treat it exactly like exit 3. Do not retry, surface the message, and wait (see the `--accept-unforwarded-schema-change` entry above). The same holds for these uncoded exit-1 refusals: `APPLY-MARK-MISMATCH` (a restart's re-delivered change contradicts its apply mark; the remedy, `--restart-from-scratch`, is destructive), `CHARSET-NOT-DECODABLE` (a value in a column's declared charset has no faithful conversion), `DSN-TIME-ZONE-NOT-UTC` (a MySQL DSN `time_zone` that is not UTC; remove it or set `'+00:00'`), `CHANGE-LOG-WATERMARK-STALLED` (a `postgres-trigger` stream read change-log rows its watermark did not advance past; a sluice bug, nothing was skipped — surface the message, which carries the query to include in a bug report), `HEARTBEAT-TABLE-NOT-SLUICES` (`--source-heartbeat-table-name` names an existing source table that is not sluice's heartbeat table; nothing was written to it — pick an unused name or turn the heartbeat off, and never drop or alter the named table to make it pass), `RESUME-SCHEMA-DIVERGENCE` (a table's first schema boundary after a `sync` (re)started disagrees with the target table in a way sluice cannot forward — a possible rename, more than one changed column, a type change across families the target does not already hold, a decimal widened on one axis and narrowed on the other; nothing after the boundary was applied, though rows read before it may already have been — surface the columns it names; the remedy is to make the target match the source by the drained model, and every start repeats the check until it does), `SCHEMA-CHANGE-REFUSED` (a `sync` that forwards no source DDL — `--schema-changes=refuse`, a multi-database stream, or `--inject-shard-column` with `--no-coordinate-live-ddl` — met a schema change the target table cannot hold: a source column the target lacks, or a type the target's column cannot take; nothing after it was applied and nothing was recorded — surface the columns it names; the remedy is to apply the change on the target (`sync stop --wait` first if the stream still runs) and start again with the same `--stream-id`, or, for a single-database stream under `--schema-changes=refuse`, to switch to `--schema-changes=forward`; an `ADD COLUMN` run on the target is not backfilled by the stream, so existing rows keep that ALTER's DEFAULT; if the message ALSO contains `AMBIGUOUS-SCHEMA-BOUNDARY`, do NOT apply the change: on a Postgres source it may be a replayed transaction, and narrowing or dropping the target column would destroy values the source still has — surface it; the human compares the source's current table definition with the target's AND confirms nobody ran DDL on that table on the source while the stream was stopped — a match alone does not prove a replay — and only then starts once with the `--accept-unforwarded-schema-change` fingerprint the message prints; if in doubt, re-copying the table is the safe answer; a refusal that contains `PRE-ALTER-REPLAY-WEDGE` is not cleared by the drained model — surface the recovery it names, which is destructive except for a single-database type widening), `COLUMN-ORDER-CHANGED` (a source schema change flipped the declared order of two of a table's columns — a `RENAME COLUMN` swap or rotation, or a MySQL/MariaDB column reorder; the two look identical and only the swap leaves the target's rows under the wrong names, so sluice refuses until the target's own column order has moved to the source's; on a stream that forwards no DDL it arrives inside `SCHEMA-CHANGE-REFUSED`; nothing after the boundary was applied — surface the message and do NOT update values to make it pass; the remedy it names is either applying the same RENAMEs or reorder on the target and starting again, or, when sluice cannot prove the target moved (no `sluice_cdc_column_order` record for the table, as on a stream started before v0.158.0, or a record that already disagreed with the source), or when the source reordered columns and the target cannot reorder in place (Postgres), the destructive `sync start --reset-target-data --yes`, which needs approval), `DEFERRED-SCHEMA-CHANGE` (a MySQL-family binlog row carries a column type change that no schema boundary will describe before its rows are applied — under `binlog_row_metadata=FULL` a deferred shape, or the stream has no typed shape of the table to hold it to; under MINIMAL or FULL, marked `COLLATION-CHANGE-UNANNOUNCED`, a character column whose collation changed with no logged DDL of the table, e.g. an ALTER run with `sql_log_bin=0`; the remedy is destructive — `sync start --reset-target-data --yes` for a sync, a fresh `backup full` for a backup chain), `COLUMN-IDENTITY-CHANGED` (a MySQL-family source's ALTERs, read from the binlog, left a column name holding a different column — a `DROP COLUMN` and re-`ADD` of the name, a `RENAME` of another column onto it, or a rename swap whose declared order was then restored — which no comparison of the table's shape can show; nothing of the new shape was applied — do NOT update values to make it pass; the remedy is destructive — `sync start --reset-target-data --yes` for a sync, a fresh `backup full` for a backup chain; a message containing `COLUMN-IDENTITY-UNREAD` is the same refusal for an ALTER sluice could not parse that spells `DROP`, `CHANGE` or `RENAME` or follows one that vacated a column name, and the same marker at WARN with the stream still running is not a refusal), `KEY-COLLATION-MERGE` (an upsert, CDC or copy, matched an existing target row through a primary or unique key whose target collation equates the two key values — `'A'` and `'a'` under a `_ci` collation, `'a '` and `'a'` under a PAD SPACE one — while the source's own collation keeps them apart, so applying it would merge two source rows into one; the statement was rolled back — do NOT change key values to make it pass; the remedy it names is to give the target key column the collation the message names and start again, or, when the key that identifies the row is itself compared differently or the table has no primary key, a re-copy with `--restart-from-scratch`, which is destructive; for a key armed to compare bytes (a Postgres source collation on a MySQL-family target) the message says a re-copy does not converge and names a binary collation instead, so do not propose one; a message that also contains `KEY-COLLATION-GUARD-UNSUPPORTED` means the target lacks the collation the check compares under — for a MySQL 8 source on a MariaDB target, a MariaDB below 10.10, under the supported 10.11 floor — and was refused before any change to the table was applied; a message that contains `KEY-COLLATION-HISTORY-UNORDERED` comes from `sync from-backup`, or a chain restore that cannot place a backup window's schema versions between its changes, on a window that changes a key column's collation: neither restarting nor changing the target key converges — the remedy is a new full backup after the key change, then `sluice sync from-backup run --reset-target-data --yes` (destructive, approval-gated) against the new chain; and a `KEY-COLLATION-MERGE` from `sluice restore` whose message says the incremental changes a key column's collation inside its own window needs that fresh full backup too, since every restore re-applies the change ahead of the same rows), `UNIQUE-KEY-CONFLICT-OTHER-ROW` (an upsert, CDC or copy, matched an existing target row through a unique key other than the primary key, and that row is a different row — its primary key, or on a table without one another of its unique keys, differs from the incoming row's — so applying it would overwrite one source row with another; the probable cause is a unique key the target still has and the source dropped, a `DROP INDEX` or `DROP CONSTRAINT` sluice does not forward; the statement was rolled back — do NOT change key values to make it pass; the remedy it names is to drop that key on the target (approval-gated) and start again with the same `--stream-id`, or, when the source still declares the key, a re-copy — `--restart-from-scratch` with the same `--stream-id` for `sync start` (from a Postgres source, after the `sluice slot drop` the message names), `--reset-target-data --yes` for `sync from-backup run` (which has no `--restart-from-scratch`) — both destructive), `INCLUDE-TABLE-SCOPE-DRIFT` (a warm `sync start` whose table scope holds a table the stream never brought in — a table named literally in `--include-table` that it never copied, a table that left the scope and was re-admitted by any filter, a never-copied table whose changes would be applied anyway, an established table its publication no longer lists, an established table that is no longer the same table (`TABLE-IDENTITY-CHANGED`: swapped with another on either engine, or dropped and re-created under the same name on Postgres — the remedy is a re-copy of it), a table renamed while stopped whose target was not renamed (rename the target table too, moving any stale table under the new name away first), `LIVE-ADDED-TABLE-EXCLUDED` (an `--exclude-table` names a table `schema add-table` brought in — at a start, narrow the exclusion or `--abandon` the table; raised by a running stream, the table is recorded as dropped, so keeping it needs a fresh copy, while keeping the exclusion passes), or a `schema add-table` that died — so changes would land on a target copy missing rows; nothing was applied; a never-copied table whose changes are provably not applied does not refuse but is named in an `INCLUDE-TABLE-NOT-ESTABLISHED` WARN — surface the tables it names; the remedies, which need approval, are emptying the target table and running `sluice schema add-table` for it with the stream stopped, taking the table out of scope (for a table `schema add-table` brought in, `--include-table` cannot: `sluice schema add-table --abandon <table> --yes`, then a restart), or `--restart-from-scratch`, and for a dead add-table of a table since dropped or descoped, `sluice schema add-table --abandon <table> --yes` (it marks the record ABANDONED: restart the stream, whose start clears it — `sync health` exits 1 with `ADD-TABLE ABANDONED` until then); a message that also carries `COLD-START-INCOMPLETE` means a cold start stopped after it began changing the target — the remedy is to re-run that cold start, `--restart-from-scratch` or `--reset-target-data --yes` (destructive, approval-gated); `INCLUDE-TABLE-ADD-IN-PROGRESS` instead means every table it names has an add-table still running — not this list: wait for it, then start again; `INCLUDE-TABLE-NARROWING-UNRECORDED`, also not this list (the fleet restarts it), means a start that narrows the scope could not record the narrowing — restore the previous scope flags, or ship the ALTER it names), `SOURCE-UNIQUE-KEY-ABSENT` (the target has a unique key no source key implies — usually a source `DROP INDEX` the stream did not see, made while it was stopped or on a `postgres-trigger`, SQLite/D1 trigger or PlanetScale/Vitess source, whose change streams carry no DDL — so the source's next duplicate of it would overwrite a different target row; checked at every start and, on those sources, periodically mid-stream; nothing after the check was applied — do NOT drop the key or pass a flag without approval; the remedy it names is to drop that key on the target and start again with the same `--stream-id`, or, where the message says rows may already have merged (a mid-stream re-check, or a source whose change stream carries no DDL), a re-copy, which is destructive; a key the target is meant to have is accepted by name with `--accept-target-only-unique-key <table>.<key>=<fingerprint>` (the value the refusal prints) on every start, or the fleet spec's `accept-target-only-unique-key` — a human decision), `SLOT-ACKED-PAST-TARGET-POSITION` (a Postgres source slot was acknowledged past the position the target persisted, so a resume would skip the changes in between; the remedy, `--restart-from-scratch`, is destructive, and the `--accept-slot-acked-past-position` entry above needs approval; from `backup stream` or `backup incremental` the message names the backup chain instead, the remedy is a new chain from a full backup, and there is no acknowledgement) and `SHARDED-TARGET-VINDEX-UPDATE` (vtgate refused a change that assigns a vindex column on a sharded target; the change cannot be applied there as is; a table routed on a vindex outside its primary key is refused earlier, before anything is written, by `migrate` and a `sync` cold start with the exit-3 `SLUICE-E-TARGET-SHARD-KEY-NOT-IN-UPSERT-KEY`). The last two are loss or scope signals, not routine states: every restart refuses the same way. Under `sync run`, a fleet leg that hits any of these (a fleet spec has no source-heartbeat key, so not the heartbeat one today) is marked failed and not restarted. So is a leg that stops on the exit-3 refusal `SLUICE-E-CDC-KEY-MATCHED-MULTIPLE-ROWS` (a CDC UPDATE or DELETE that names its row by key matched more than one target row; the remedy, `--reset-target-data`, is destructive). <!-- /restart-refusal-roster --> Other exit-3 refusals stay under `max-consecutive-failures`, because some clear without a change to the leg. Three more uncoded exit-1 messages are outside `sync`, and only the first is retry-safe: `BACKUP-WINDOW-ABANDONED-OPEN-TRANSACTION` from a one-shot `backup incremental` (the source's change stream closed inside a source transaction, so no manifest was written and nothing acknowledged; re-run the same command, which re-reads the window from the parent's end), `SMART-COMPACTION-SOURCE-ENGINE-UNKNOWN` from `backup compact --smart-compaction` (the chain names a source engine this sluice does not know, so it cannot judge whether the rewrite would hide a re-delivered transaction; nothing was compacted — surface it; the remedy is `--smart-compaction-off` or a sluice that knows the engine) and `BARRIER-FOLD-NOT-TRANSACTIONAL` (an internal defect in the CDC apply path, refused before anything is written; do not retry or work around it — surface the message and report it as a sluice bug).

`sync from-backup run` has one exit 1 that is not a refusal: a message containing `BROKER-INCREMENTAL-PARTIAL` means the run was cancelled (SIGINT/SIGTERM, a supervisor timeout) while it was applying an incremental. The broker's position stands inside that incremental, so re-running the same command re-applies from the first source transaction not durably applied (the one in flight, or on the lane apply mode the few whose lanes had not all committed). When the message says the incremental records change identities, the re-run is exactly-once for every change that carries one, key changes and tables without a key included: re-run it (a change recorded without an identity, logged as `BROKER-UNIDENTIFIED-CHANGES`, converges by its key unless its transaction moved a key value onto another row). When it says the incremental records none (written by an older sluice, or smart-compacted), every table that incremental touches was judged to have a key the replayed rows carry and collide on, because a table without one (including a target table keyed only on a serial, identity or defaulted surrogate the rows do not supply) is refused before anything is applied with the exit-3 `SLUICE-E-BROKER-KEYLESS-TABLE`; a re-run then converges for inserts, and for updates and deletes that keep each row's key, but not when that transaction changed a row's key value: the re-run can fail on a duplicate key (MySQL 1062 / Postgres 23505) on every attempt, so do not retry it unchanged, and when a key value was moved off one row and onto another, it can apply a change to the wrong row with no error at all. In that case the recovery is `--reset-target-data`, which is destructive: surface the message and wait for a human. A message containing `BROKER-COLD-START-PARTIAL` is the same kind of exit 1: a `--reset-target-data` cold start was cancelled after it began dropping the target's tables, so the target holds a partial restore and no position; re-run the same command with `--reset-target-data`, and never start that target with `--at-chain-id`. `sync from-backup run` also has one uncoded exit-1 refusal: a message containing `BROKER-AT-CHAIN-ID-CONFLICT` means `--at-chain-id` was passed to a target that already holds a broker position for the stream and names anything other than its last fully applied incremental with nothing in progress. Nothing was applied, and every restart with the same flags refuses again. Treat it like exit 3: surface it and wait. The message names three ways out: drop `--at-chain-id` to resume from the recorded position; pass `--reset-target-data` to rebuild the target from the chain (destructive, approval needed); or, if a human restored the target to that link themselves, delete the stream's row from `sluice_cdc_state` and its rows from `sluice_cdc_apply_marks` and run again with `--at-chain-id` (a manual write to the target, approval needed). To stop a broker without interrupting an incremental, run `sluice sync from-backup stop`.
