# AGENTS.md — driving sluice as an AI agent

sluice is a single-binary CLI that migrates and continuously syncs databases (MySQL ↔ Postgres in all four directions, plus SQLite / Cloudflare D1 import and sync). It is built for you: **no command ever blocks on a prompt when you drive it** (flags, environment variables, optional YAML config). A destructive command asks for confirmation only when stdin is a real terminal and `--yes` is absent; on a pipe, a CI runner, or any other non-terminal stdin it refuses with `SLUICE-E-CONFIRMATION-REQUIRED` (exit 3) before touching anything — pass `--yes` to proceed. Destructive operations require explicit opt-in flags, and ambiguous states refuse loudly with a named remedy instead of proceeding. This file is the operating guide for agents *using* the CLI; contributor/development guidance lives in `CLAUDE.md` and `CONTRIBUTING.md`.

## Command taxonomy

**Read-only — safe to run without approval.** These never modify either database: `sluice schema preview`, `sluice schema diff`, `sluice verify`, `sluice sync health`, `sluice sync status`, `sluice engines`, `sluice backup verify`, `sluice control-tables ddl` (prints the control tables' CREATE statements — on `--engine postgres` also the ADD COLUMN / CREATE INDEX / UTC-DEFAULT follow-ups; opens no connection), `sluice backfill --verify-only` (counts rows matching `--where`; no UPDATEs, no control-table writes), and **any command with `--dry-run`** (`expand-contract --dry-run` and `deploy-ddl --dry-run` additionally make zero control-plane calls).

**State-changing — run only as part of an approved task.** These write to the target (and create bookkeeping objects — see `docs/database-objects` on the docs site): `sluice migrate`, `sluice sync start`, `sluice sync run`, `sluice backup *` (writes to the backup store; `backup export-as-parquet` is read-only against the chain but writes Parquet files to its destination), `sluice restore`, `sluice cutover`, `sluice schema add-table`, `sluice trigger setup/teardown/prune`.

**Production-mutating schema-change commands — treat like state-changing, but the writes hit a PRODUCTION database in place**, not a migration target:

- `sluice backfill` — issues real `UPDATE`s against the one database named by `--dsn` (keyset-chunked, resumable; `--dry-run` and `--verify-only` are the read-only forms)
- `sluice deploy-ddl` — ships one DDL statement to a PlanetScale **production branch** via a deploy request
- `sluice expand-contract` — deploy-requests an `ADD COLUMN`, runs the backfill, and (only with `--yes`) deploy-requests the `DROP COLUMN` contract step

**Destructive flags — NEVER pass without explicit human approval for that specific invocation.** Approval to migrate is not approval to destroy:

- `--reset-target-data` — drops/truncates target tables before copy
- `--force-cold-start` — bypasses the populated-target safety preflight
- `--yes` — the destructive-confirmation opt-in on `--reset-target-data`, `schema add-table`, `trigger teardown`, `slot drop` and `sync decommission`; without it these refuse with `SLUICE-E-CONFIRMATION-REQUIRED` (exit 3) unless a human is at a terminal to answer the prompt. **On `expand-contract` it confirms the contract leg — a `DROP COLUMN` deploy request against the production branch** (without it the run stops after verify and prints the resume command)
- `backup prune` / `backup compact` without `--dry-run` — irreversibly drop backup history
- `sync decommission --yes` — drops a finished stream's replication slot + per-stream publication on the source and clears its control row on the target; the stream can never warm-resume after (preview with `--dry-run`, which needs no `--yes`)
- `--accept-unforwarded-schema-change=<fingerprint>` (`sync start`, `backup stream run`) — acknowledges a recorded `UNFORWARDED-SCHEMA-CHANGE` refusal. It accepts a source/target schema difference permanently unless the change was applied to the target first (for `backup stream`, unless a new full backup was taken first). A human applies the change; only then pass the fingerprint the replayed refusal prints, once. When the message also contains `ADD-COLUMN-BACKFILL-INCOMPLETE`, the column already exists on the target: the human repair is to copy the added column's values from the source for the rows that predate the `ADD COLUMN` (or re-copy with `--restart-from-scratch`), not to apply a change. This refusal exits **1 with no error code**, not 3, but it is still a decision point: every restart refuses again until it is acknowledged, so do not retry it
- `--accept-slot-acked-past-position=<LSN>` (`sync start`) — acknowledges a `SLOT-ACKED-PAST-TARGET-POSITION` refusal (Postgres source): the replication slot was acknowledged past the position the target persisted, so resuming skips every change committed in between. The remedy is a re-copy with `--restart-from-scratch`, which is itself destructive and needs approval. Pass the flag only after a human has verified that the target already holds every change up to the LSN the refusal prints; it accepts the gap as skipped. An LSN that does not match the slot is refused

## The standard workflow

1. **Preview first**: `sluice migrate --dry-run --format json ...` — emits the full plan as JSON. Show it to the human before proceeding. To see the target DDL alone, `sluice schema preview` renders it with cross-engine translation notes.
2. **Run**: `sluice migrate --format json ...` — one JSON result envelope on stdout (see below).
3. **Verify**: `sluice verify --format json ...` — never report a migration done without it.
4. For continuous sync: `sync start --dry-run` → `sync start` → poll `sync health --format json` (exits 1 on breached thresholds, on durably skipped tables, or on `CONTROL-TIMESTAMP-IN-FUTURE` — a stream row dated more than 60s ahead, whatever `--max-stale-seconds` says — cron/agent-friendly).

## Credentials: env-first, never in argv

Pass DSNs and secrets via environment variables, not flags — flags leak into process listings and shell history (crash-bundle redaction masks them, but env is the documented path):

| Variable | Holds |
|---|---|
| `SLUICE_SOURCE` / `SLUICE_TARGET` | source / target DSN (equivalent to `--source` / `--target`) |
| `CLOUDFLARE_API_TOKEN` | Cloudflare D1 API token (env-only; there is no flag) |
| `PLANETSCALE_METRICS_TOKEN_ID` / `PLANETSCALE_METRICS_TOKEN` | PlanetScale telemetry token |
| `PLANETSCALE_SERVICE_TOKEN_ID` / `PLANETSCALE_SERVICE_TOKEN` | PlanetScale service token (branch + deploy-request scopes) for `expand-contract`, `deploy-ddl`, and `migrate`'s index-build fallback — the pscale CLI convention; the `--service-token*` flags exist but the env vars are the documented path |
| `SLUICE_NOTIFY_WEBHOOK` / `SLUICE_NOTIFY_SLACK` | notification sink URLs (the URL path is the credential) |
| `SLUICE_NOTIFY_SMTP_PASSWORD` | SMTP auth secret (env-only by policy) |
| `--encryption-passphrase-env NAME` | names the env var holding the backup passphrase |

## Machine-readable output

- **`--format json`** on the primary verbs — `migrate`, `sync start`, `backup full`, `restore` — emits exactly one JSON result envelope as the last write to stdout on every exit path: `{"command","status":"completed|refused|failed","elapsed_seconds","source_engine","target_engine","tables":[...],"resume":{...},"error":{"message","code","hint"},"next_steps":[...]}`. `status:"refused"` means sluice declined by policy (loud-failure) — read `error.hint` for the remedy; `"failed"` means something broke mid-run. With `--dry-run` the same flag emits the plan instead: `{"command","dry_run":true,"plan":{...}}`.
- **`--format json`** also on: `verify`, `schema diff`, `schema preview`, `cutover`, `sync health`, `sync status`, `matview refresh`.
- **`--log-format json`** (global) — one JSON slog object per line on stderr; terminal coded errors carry `code` and `hint` attributes.
- Envelopes and logs never contain credentials; DSNs render as credential-free locators.

## Error codes and exit codes

Stable machine-parsable error codes (`SLUICE-E-*`) with remedy hints ride on the JSON envelope's `error` object and the JSON log stream — branch on `code`, show `hint` to the human. The full table: `docs/operator/error-codes.md`.

| Exit | Meaning |
|---|---|
| 0 | success |
| 1 | runtime failure (also: verify/diff drift found) |
| 2 | config-file error (verify-family: could not run) |
| 3 | named refusal — sluice declined by policy; the error names the remedy |
| 80 | CLI usage/parse error (kong) |

`!= 0` always means not-success. On exit 3, do not retry unchanged — surface `error.hint` to the human and wait for a decision (the remedy is often a destructive flag that needs approval). One refusal has no code yet and exits 1: a message containing `UNFORWARDED-SCHEMA-CHANGE` from `sync start` / `sync run` / `backup stream run`. Treat it exactly like exit 3. Do not retry, surface the message, and wait (see the `--accept-unforwarded-schema-change` entry above). The same holds for nine more uncoded exit-1 refusals: `APPLY-MARK-MISMATCH` (a restart's re-delivered change contradicts its apply mark; the remedy, `--restart-from-scratch`, is destructive), `CHARSET-NOT-DECODABLE` (a value in a column's declared charset has no faithful conversion), `DSN-TIME-ZONE-NOT-UTC` (a MySQL DSN `time_zone` that is not UTC; remove it or set `'+00:00'`), `CHANGE-LOG-WATERMARK-STALLED` (a `postgres-trigger` stream read change-log rows its watermark did not advance past; a sluice bug, nothing was skipped — surface the message, which carries the query to include in a bug report), `HEARTBEAT-TABLE-NOT-SLUICES` (`--source-heartbeat-table-name` names an existing source table that is not sluice's heartbeat table; nothing was written to it — pick an unused name or turn the heartbeat off, and never drop or alter the named table to make it pass), `RESUME-SCHEMA-DIVERGENCE` (a table's first schema boundary after a `sync` (re)started disagrees with the target table in a way sluice cannot forward — a possible rename, more than one changed column, a type change across families the target does not already hold, a decimal widened on one axis and narrowed on the other; nothing was applied — surface the columns it names; the remedy is to make the target match the source by the drained model, and every start repeats the check until it does), `SCHEMA-CHANGE-REFUSED` (a `sync` that forwards no source DDL — `--schema-changes=refuse`, a multi-database stream, or `--inject-shard-column` with `--no-coordinate-live-ddl` — met a schema change the target table cannot hold: a source column the target lacks, or a type the target's column cannot take; nothing after it was applied and nothing was recorded — surface the columns it names; the remedy is to apply the change on the target (`sync stop --wait` first if the stream still runs) and start again with the same `--stream-id`, or, for a single-database stream under `--schema-changes=refuse`, to switch to `--schema-changes=forward`; an `ADD COLUMN` run on the target is not backfilled by the stream, so existing rows keep that ALTER's DEFAULT; if the message ALSO contains `AMBIGUOUS-SCHEMA-BOUNDARY`, do NOT apply the change: on a Postgres source it may be a replayed transaction, and narrowing or dropping the target column would destroy values the source still has — surface it; the human compares the source's current table definition with the target's AND confirms nobody ran DDL on that table on the source while the stream was stopped — a match alone does not prove a replay — and only then starts once with the `--accept-unforwarded-schema-change` fingerprint the message prints; if in doubt, re-copying the table is the safe answer; a refusal that contains `PRE-ALTER-REPLAY-WEDGE` is not cleared by the drained model — surface the recovery it names, which is destructive except for a single-database type widening), `SLOT-ACKED-PAST-TARGET-POSITION` (a Postgres source slot was acknowledged past the position the target persisted, so a resume would skip the changes in between; the remedy, `--restart-from-scratch`, is destructive, and the `--accept-slot-acked-past-position` entry above needs approval; from `backup stream` or `backup incremental` the message names the backup chain instead, the remedy is a new chain from a full backup, and there is no acknowledgement) and `SHARDED-TARGET-VINDEX-UPDATE` (vtgate refused a change that assigns a vindex column on a sharded target; the change cannot be applied there as is; a table routed on a vindex outside its primary key is refused earlier, before anything is written, by `migrate` and a `sync` cold start with the exit-3 `SLUICE-E-TARGET-SHARD-KEY-NOT-IN-UPSERT-KEY`). The last two are loss or scope signals, not routine states: every restart refuses the same way. Under `sync run`, a fleet leg that hits any of these ten (a fleet spec has no source-heartbeat key, so not the heartbeat one today) is marked failed and not restarted. So is a leg that stops on the exit-3 refusal `SLUICE-E-CDC-KEY-MATCHED-MULTIPLE-ROWS` (a CDC UPDATE or DELETE that names its row by key matched more than one target row; the remedy, `--reset-target-data`, is destructive). Other exit-3 refusals stay under `max-consecutive-failures`, because some clear without a change to the leg. Three more uncoded exit-1 messages are outside `sync`, and only the first is retry-safe: `BACKUP-WINDOW-ABANDONED-OPEN-TRANSACTION` from a one-shot `backup incremental` (the source's change stream closed inside a source transaction, so no manifest was written and nothing acknowledged; re-run the same command, which re-reads the window from the parent's end), `SMART-COMPACTION-SOURCE-ENGINE-UNKNOWN` from `backup compact --smart-compaction` (the chain names a source engine this sluice does not know, so it cannot judge whether the rewrite would hide a re-delivered transaction; nothing was compacted — surface it; the remedy is `--smart-compaction-off` or a sluice that knows the engine) and `BARRIER-FOLD-NOT-TRANSACTIONAL` (an internal defect in the CDC apply path, refused before anything is written; do not retry or work around it — surface the message and report it as a sluice bug).

`sync from-backup run` has one exit 1 that is not a refusal: a message containing `BROKER-INCREMENTAL-PARTIAL` means the run was cancelled (SIGINT/SIGTERM, a supervisor timeout) while it was applying an incremental. Re-running the same command re-applies that incremental, and every table the broker replays was judged, on the chain's recorded schema and on the target, to have a key that the replayed rows carry and collide on, because a table without one (including a target table keyed only on a serial, identity or defaulted surrogate the rows do not supply) is refused before anything is applied with the exit-3 `SLUICE-E-BROKER-KEYLESS-TABLE`. So a re-run converges for inserts, and for updates and deletes that keep each row's key. It is not safe when the incremental changed a row's key value: the re-run can then fail on a duplicate key (MySQL 1062 / Postgres 23505) on every attempt, so do not retry it unchanged, and when a key value was moved off one row and onto another, the re-run can apply a change to the wrong row with no error at all. If the source changes key values, the recovery is `--reset-target-data`, which is destructive: surface the message and wait for a human. A message containing `BROKER-COLD-START-PARTIAL` is the same kind of exit 1: a `--reset-target-data` cold start was cancelled after it began dropping the target's tables, so the target holds a partial restore and no position; re-run the same command with `--reset-target-data`, and never start that target with `--at-chain-id`. To stop a broker without interrupting an incremental, run `sluice sync from-backup stop`.
