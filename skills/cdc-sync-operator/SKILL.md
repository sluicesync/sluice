# cdc-sync-operator

Operate a sluice continuous-sync stream through its lifecycle. State-changing (writes to the target); the recovery/cutover steps are approval-gated.

## When to use
The user wants ongoing replication (not a one-shot migrate): a cold-start snapshot that hands off gap-free to CDC, kept healthy, and eventually cut over.

## Inputs you need
- Source + target DSNs (env: `SLUICE_SOURCE` / `SLUICE_TARGET`) and drivers. For PlanetScale VStream, `--source-driver planetscale` (see `planetscale-migration`).
- A `--stream-id` (the key position is persisted under; auto-derived from host info if omitted — set it explicitly so you can monitor/stop it later).

## Steps

1. **Preflight (read-only).** Run `migrate-preflight` first, or `sluice sync start --dry-run --format json …` — it shows cold-start-vs-warm-resume, the source schema summary or the persisted position, and the CDC/slot plan, without touching the target.

2. **Start the stream.** `sluice sync start --format json --source-driver <drv> --source "$SLUICE_SOURCE" --target-driver <drv> --target "$SLUICE_TARGET" --stream-id <id>`. It cold-start bulk-copies existing rows, then hands off to CDC automatically. On Postgres the slot name comes from `--slot-name` (default `sluice_slot`, `sluice_`-prefixed); set a distinct one to run multiple streams against one source.

3. **Confirm the cold-start.** After the snapshot completes, run `fidelity-verify` before trusting steady state.

4. **Monitor freshness (cron/agent-friendly).** `sluice sync health --format json --target-driver <drv> --target "$SLUICE_TARGET" --stream-id <id> [--max-stale-seconds N] [--max-lag-bytes N]`. **Exit 0** healthy, **exit 1** a threshold breached (stale/lag) OR the stream has durably skipped events for tables the target lacks (`skipped_tables` in the JSON; no threshold — resolves via `schema add-table`, an explicit table filter, or — when the cause is revoked privileges rather than a missing table (information_schema hides tables the apply role cannot see) — restoring the grant, after which the next change applies with no re-snapshot. No remedy removes the ledger row, so health stays at exit 1 until, with the cause fixed, the row is deleted on the target: `DELETE FROM sluice_cdc_skipped_tables WHERE stream_id='<stream>' AND table_name='<table>'` — **approval needed: YES**, it is a write; **except** when the skipped table is `sluice_heartbeat`, the table named by `--source-heartbeat-table-name`, or another `sluice_*` control table — that is sluice's own bookkeeping, recorded by a release before v0.156.9, and the fix is to upgrade, then delete the leftover ledger row on the target with `DELETE FROM sluice_cdc_skipped_tables WHERE stream_id='<stream>' AND table_name LIKE '%sluice_heartbeat'` (substitute the table shown) — **approval needed: YES**, it is a write; never `schema add-table` a control table) OR a `schema add-table` stopped without completing (`ADD-TABLE INCOMPLETE`) or was retired by `--abandon` (`ADD-TABLE ABANDONED: restart the stream` — restart the stream, whose start clears it; `pending_added_tables` in the JSON; a `schema add-table` still running is exit 0) OR the stream row's `updated_at` reads more than 60s in the future (state `UNKNOWN`, `CONTROL-TIMESTAMP-IN-FUTURE`, `control_timestamp_in_future` and `stale: true` in the JSON — whatever `--max-stale-seconds` says, including 0; a row a pre-v0.156.5 binary wrote on an east-of-UTC Postgres database, or clock skew; the stream's next position write heals it, a stalled stream needs a restart), **exit 2** operational (stream not found / connect). Add `--source-driver`/`--source` for source-position + byte-lag (PG only). For a human view use `sluice sync status [--watch 2s] [--all --config <fleet>]`.

5. **Resume semantics.** A stopped or crashed stream usually warm-resumes from its persisted position on the next `sync start`, re-streaming only the un-applied tail. **The exception is a stream that stopped with `UNFORWARDED-SCHEMA-CHANGE`** (Postgres and MySQL/MariaDB binlog sources). The source changed a constraint, policy, RLS, `NOT NULL`, default or similar that CDC cannot forward. The refusal is recorded on the target, so every later start refuses again, on every start path. It exits **1 with no error code**, not 3, so do not treat it as an ordinary codeless failure. The replayed refusal prints `fingerprint <12 hex>`. Recovery is a decision point that needs human approval:
   1. A human applies the same change to the target.
   2. Only then, start once with `--accept-unforwarded-schema-change=<that fingerprint>`.
   
   **Variant: the message also contains `ADD-COLUMN-BACKFILL-INCOMPLETE`.** A forwarded `ADD COLUMN`'s backfill of the rows the target already held did not provably finish (a stop, crash or error interrupted it). The column already exists on the target, so step 1 is different: a human copies the added column's values FROM THE SOURCE for the rows that predate the `ADD COLUMN` (or re-copies with `--restart-from-scratch` on the acknowledged start). Then acknowledge the fingerprint as above.
   
   The flag clears only that refusal and takes a fresh baseline, so passing it without step 1 accepts the source/target difference permanently. Never add it on your own, and never leave it on a standing command line. On PlanetScale, a resume from a purged binlog position auto-recovers with a fresh re-snapshot by default (see `planetscale-migration`; `--no-auto-resnapshot` makes that a loud decision instead).

   **Second exception (Postgres source): `SLOT-ACKED-PAST-TARGET-POSITION`.** A warm resume refuses when the source replication slot's `confirmed_flush_lsn` is past the position the target persisted: PostgreSQL would start decoding at the later of the two and skip every change committed in between, and the target does not hold them. Causes: a stop of a Postgres → MySQL-family sync on v0.156.6 or earlier, a target restored or failed over to an older state, or a slot recreated after the stream wrote its position. It exits **1 with no error code**, and every restart refuses again. Surface the message and stop. The remedy is a re-copy with `--restart-from-scratch`, which is destructive and needs human approval. Only if a human has verified that the target already holds every change up to the printed LSN, start once with `--accept-slot-acked-past-position=<that LSN>` (also approval-gated: it accepts the gap as skipped).

   **Third exception: `COLUMN-ORDER-CHANGED` (v0.158.0+, any source).** The source declares two of a table's columns in the opposite order — a `RENAME COLUMN` swap or rotation, or a MySQL/MariaDB `MODIFY … AFTER/FIRST` reorder. Only the swap leaves the target's rows under the wrong names, and the two look identical, so the stream refuses until the target's own column order has moved from the order sluice recorded (`sluice_cdc_column_order`) to the source's. It exits **1 with no error code** (on a `--schema-changes=refuse` or multi-database stream it arrives inside `SCHEMA-CHANGE-REFUSED`), every restart refuses again, and `sync run` does not restart the leg. Surface the message; its remedy is one of two:
   - **Apply the same change on the target** (the same `RENAME COLUMN` statements, or the same `MODIFY … AFTER` on a MySQL-family target), then start again with the same `--stream-id`. A human runs the DDL. Never update target values instead: the check reads the target's column order.
   - **Re-copy** with `sync start --reset-target-data --yes` and the stream's other flags unchanged (on a Postgres source, `sluice slot drop` first). This is the only remedy offered when sluice holds no record of the table's target order (a stream started before v0.158.0, or a target that could not create the record table — the start WARNed `COLUMN-ORDER-RECORD-UNAVAILABLE`), when the recorded order already disagreed with the source, or when the source reordered columns and the target cannot (Postgres). Destructive → human approval. `schema add-table` is deliberately not offered: it keeps the stream's position and would replay pre-change rows under the old names.

   **Fourth exception: `DEFERRED-SCHEMA-CHANGE` (v0.158.0+, MySQL/MariaDB binlog sources under `binlog_row_metadata=FULL`; marked `COLLATION-CHANGE-UNANNOUNCED` under `MINIMAL` or `FULL`).** A row event's recorded shape changes a column's type or (v0.159.0+) a character column's collation, but a later `DROP COLUMN` or retype means no schema boundary will describe it before its rows are applied (or, on a warm resume, the stream holds no typed shape of the table to compare with). Marked `COLLATION-CHANGE-UNANNOUNCED`, a character column's collation changed with no logged DDL of the table (an ALTER run with `sql_log_bin=0`). Exit **1**, no code, every restart repeats it. The remedy is the destructive re-copy `sync start --reset-target-data --yes` → human approval.

   **Fifth exception: `COLUMN-IDENTITY-CHANGED` (v0.159.0+, MySQL/MariaDB binlog sources, any `binlog_row_metadata`).** The source's `ALTER`s left a column name holding a different column: a `DROP COLUMN c` and re-`ADD` of `c`, `RENAME COLUMN c TO tmp, ADD COLUMN c`, `DROP COLUMN b, RENAME COLUMN c TO b`, or a rename swap whose declared order was then restored by a `MODIFY … AFTER`. No comparison of the table's shape can see it, so sluice reads the `ALTER` statements in the binlog and refuses at the statement itself, live or on a warm resume. Exit **1**, no code, every restart repeats it, and `sync run` does not restart the leg. A message that also says `COLUMN-IDENTITY-UNREAD` is the same refusal for an `ALTER` sluice could not parse. Surface it; do NOT update target values to make it pass. The only remedy is the destructive re-copy `sync start --reset-target-data --yes` with the stream's other flags unchanged → human approval. A plain rename swap in one statement is not this refusal: it is `COLUMN-ORDER-CHANGED`, above.

   **Sixth exception: `KEY-COLLATION-MERGE` and `KEY-COLLATION-CHANGED` (v0.159.0+).** `KEY-COLLATION-MERGE` (MySQL-family and Postgres targets): a CDC upsert — or, v0.159.1+, a cold start's VStream COPY upsert, serial or fanned out — matched an existing target row through a primary or unique key whose target collation equates the two key values while the source's collation keeps them apart, so it would have merged two source rows; the statement was rolled back. `KEY-COLLATION-CHANGED` arrives inside `RESUME-SCHEMA-DIVERGENCE` or `SCHEMA-CHANGE-REFUSED`: a key column's collation or character set changed on the source, and the stream runs under `--schema-changes=refuse` or holds no earlier shape of the table to judge it by. Both exit **1**, no code, every restart repeats them, and `sync run` does not restart the leg. Never change key values to make either pass. Remedy: a human gives the target key column the collation the message names — the source's, or for a MySQL 8 key on MariaDB the NO PAD `utf8mb4_uca1400_nopad_*` form that compares as it does (`ALTER TABLE … MODIFY …` / `ALTER COLUMN … TYPE … COLLATE …`) — then restart with the same `--stream-id`. Branch on what a `KEY-COLLATION-MERGE` message actually says, because the remedy differs: for an ordinary key it leads with that `ALTER` and offers a re-copy with `--restart-from-scratch` as the alternative; when it says the key that identifies a row is itself compared differently (or the table has no primary key), the remedy it leads with is the re-copy with `--restart-from-scratch` → destructive, human approval; and when the key is armed to compare bytes (a Postgres source collation on a MySQL-family target), it says a re-copy does **not** converge — sluice would recreate the target's default collation, which equates the values — and names a binary collation (for example `utf8mb4_bin`) instead, so never propose `--restart-from-scratch` for it. A message from the cold start's COPY says "These are two rows of the source the copy is reading": align the target key's collation and run the copy again (a re-copy, approval-gated), or exclude the table. A copy's `KEY-COLLATION-REPLAY-AMBIGUOUS` (v0.159.1+, MySQL-family targets, LOAD DATA only) is different: a segment replayed after a transient skipped rows as duplicate keys sluice could not attribute; nothing merged, and running again is the remedy — `sync run` restarts it by design. `KEY-COLLATION-GUARD-UNSUPPORTED` in the message means nothing of that table's changes was applied, and it has two causes, never fixed by an unguarded run. Usually the target lacks the collation the check needs: the fix is the target's collation (create it, or align the key on both sides). On a MySQL-family target it can instead name a functional unique-key part whose columns sluice cannot resolve, which no collation change fixes; follow the per-part remedy the message gives — a column it cannot find (a non-ASCII name: recreate the key over ASCII-named columns), a string literal it cannot scan (write the literal plainly, or key a stored generated column holding the expression), generated columns nested more than eight deep (key a shallower expression) — or exclude the table. Recreating a key is a human's schema change.

   **Seventh exception: `SOURCE-UNIQUE-KEY-ABSENT` and `UNIQUE-KEY-CONFLICT-OTHER-ROW` (any source; the apply-time `UNIQUE-KEY-CONFLICT-OTHER-ROW` since v0.161.1).** The target has a unique key no source key implies, usually a source `DROP INDEX` the stream did not see (made while it was stopped, or on a `postgres-trigger`, `sqlite-trigger`, `d1-trigger`, PlanetScale or Vitess source, whose change streams carry no DDL), so the source's next duplicate of it would overwrite a different target row. `SOURCE-UNIQUE-KEY-ABSENT` is checked at every `sync start` (and every `sync run` leg start), at a schema change that moves a table's columns or loses a unique key with a column, and, on those DDL-less sources, at a re-check every 15 seconds; `UNIQUE-KEY-CONFLICT-OTHER-ROW` fires at apply time when an upsert matches a different target row through such a key. Both exit **1 with no error code**, every restart repeats them, and `sync run` does not restart the leg. Surface the message and branch on what it says:
   - **The key was dropped while no stream was reading, or the target was built with it** (the message says nothing written after the drop has been applied): a human drops that key on the target (`DROP INDEX`, or `ALTER TABLE … DROP CONSTRAINT` for the constraint the message names), then start again with the same `--stream-id`. Approval-gated: it is a schema change on the target.
   - **Rows may already have merged** (the mid-stream re-check found it, among the other cases the message and `docs/operator/cdc-streaming.md` list): dropping the key alone keeps the merged rows, so the remedy is a re-copy with `--restart-from-scratch` or `--reset-target-data --yes` and the same `--stream-id` → destructive, human approval. From a Postgres (pgoutput) source, `sluice slot drop` first. Under `--inject-shard-column` never `--reset-target-data` (it drops every shard's rows): drop the key and re-copy this shard with `--restart-from-scratch`.
   - **The target is meant to have the key:** a human may accept it with `--accept-target-only-unique-key <table>.<key>=<fingerprint>`, the value the refusal prints beside the key (`<database>.<table>.<key>=…` on a multi-database stream). That is a human decision, never yours: the acceptance is standing (it belongs on every start, or in the fleet spec's `accept-target-only-unique-key` key), is bound to the key's definition, and refuses again with a new value whenever that definition changes; passing the new value accepts the new definition. A key whose definition cannot be read (a functional part on PlanetScale/Vitess, or a target other than MySQL-family or Postgres) cannot be accepted; dropping it is the remedy.

   A `UNIQUE-KEY-CONFLICT-OTHER-ROW` statement was rolled back before it was applied. Its remedy is to drop that key on the target and start again (approval-gated), or a re-copy: `--restart-from-scratch` for `sync start` (from a Postgres source, after dropping the stream's replication slot), `--reset-target-data --yes` for `sync from-backup run`, which has no `--restart-from-scratch`; both destructive → human approval. It has no acknowledgement flag.

   A WARN containing `SOURCE-UNIQUE-KEY-RECHECK-FAILED` means a periodic re-check could not read a catalog; the next due check retries, and four failures in a row stop the stream with that marker, an ordinary failure a restart retries (a schema-change check that cannot read a catalog stops the stream at once with it).

   **Eighth exception: `INCLUDE-TABLE-SCOPE-DRIFT` (any source's warm `sync start`).** The resume would apply a table's changes onto a target copy the stream never made or stopped keeping up: an `--include-table` entry names, literally, a table the stream never copied (its `established_tables` record — each cold start's copy plus every completed add-table — lacks it); a table left the scope on an earlier restart and is re-admitted by any filter (`dropped_tables`: its changes were discarded meanwhile); a never-copied table admitted by a glob or no filter would have its changes applied anyway (its publication delivers it, or its target table exists); an established table is no longer in a FOR TABLE publication (dropped and recreated on the source); an established table is no longer the same table (`TABLE-IDENTITY-CHANGED`: swapped with another on either engine, or dropped and re-created under the same name on Postgres — remedy a re-copy of it); a table renamed while stopped whose target was not renamed (rename the target too, moving any stale table under the new name away first; a rename is followed only if the new name is in scope); `LIVE-ADDED-TABLE-EXCLUDED`, an `--exclude-table` naming a table add-table brought in (at a start: narrow the exclusion, or `--abandon` the table; raised by a running stream: the table is recorded as dropped, so keeping it needs a fresh copy — narrow the exclusion, empty its target table and add-table it again — while keeping the exclusion passes); or an add-table died (its pending entry's heartbeat is over five minutes old). A warm resume copies nothing, so the table would stay wrong while the stream looked healthy. It is refused before the reader opens; nothing was applied. A never-copied table whose changes are provably not applied does not refuse: it is named in an `INCLUDE-TABLE-NOT-ESTABLISHED` WARN and stays out until added. **`INCLUDE-TABLE-ADD-IN-PROGRESS`** is the restartable variant: every table it names has an add-table still running; wait for it to finish, then start again (`sync run` retries it itself). `sync health` shows a running add as in progress (exit 0) and a dead one as `ADD-TABLE INCOMPLETE` (exit 1); for a dead add of a table since dropped on the source or taken out of scope, `sluice schema add-table --abandon <table> --yes` (approval-gated) marks the record abandoned — `sync health` then exits 1 with `ADD-TABLE ABANDONED: restart the stream` until a restart clears it, and the target table may hold a partial copy. On a multi-database stream only the re-copy works. A stream cold-started before this record existed logs `INCLUDE-TABLE-SCOPE-UNRECORDED` until its next cold start. Widening `--include-table` on a restart is never how a table joins a stream. Remedy, per table the message names, with the stream stopped: empty the target table, then `sluice schema add-table <table>` with the stream's `--source-driver`, `--source`, `--target-driver`, `--target` and `--stream-id`, then the same `sync start` again. add-table refuses a target table that already holds rows, so a partial copy has to be emptied first (approval-gated: it deletes target rows). Or take the table out of scope — for a table add-table brought in, `--include-table` cannot: that is `sluice schema add-table --abandon <table> --yes` (approval-gated), then a restart. Or re-copy every table with `--restart-from-scratch` (from a Postgres source, after `sluice slot drop` of the stream's slot) → destructive, human approval; it re-copies the added tables too. The one acknowledgement is `--accept-table-rename <old>=<new>`, for a rename sluice cannot prove by the table's id (a PlanetScale/Vitess source, an InnoDB name stored in filename encoding, a record written without ids) → approval-gated: rename the target first; the record follows only when the target holds the new name and no longer the old one, the new target table is trusted as-is, and a pair that matches no rename only WARNs. Every other shape has no acknowledgement. **Added tables:** a table `schema add-table` brought in stays in the stream's scope whatever `--include-table` says (only `--abandon` takes it out); `--restart-from-scratch` re-copies it; `--reset-target-data` discards it with a WARN per table, after which it receives no changes — name it in `--include-table` or add-table it again. `INCLUDE-TABLE-NARROWING-UNRECORDED` (codeless exit 1, restarted by the fleet): a start that narrows the scope could not record the narrowing — restore the previous scope flags, or ship the ALTER it names. `VSTREAM-COPY-RESUME-WITHDRAWN` (under `INCLUDE-TABLE-SCOPE-DRIFT`, not restarted by the fleet): a `planetscale`/`vitess` stream holds a mid-copy cursor saved by v0.163.2 or earlier; a stopped VStream copy is re-copied, never resumed, because a resume kept rows the source deleted while stopped. Remedy: the same command with `--restart-from-scratch` (destructive, approval-gated); never `--force-cold-start`, which upserts over the table and keeps those rows. `VSTREAM-COPY-COMPLETION-UNPROVEN` (same marker, not restarted): a `planetscale`/`vitess` warm resume where nothing on the target proves the cold-start copy finished (no `established_tables` record and no complete `sync-<stream-id>` row in `sluice_migrate_state`) — cold-started before v0.149.0, or stopped mid-copy on v0.163.1 or earlier, whose saved position looks like a finished copy's. Remedy: `--restart-from-scratch` (approval-gated); only if a human confirms the copy finished (row counts match), `--assert-copy-finished` once (also approval-gated: a copy that stopped midway keeps its missing rows missing).

   **Two or more columns changing type or nullability in one `ALTER`** now refuse under the default `--schema-changes=forward` (v0.158.0+; forward mode applies one column's change per boundary), naming every column. Treat it like `RESUME-SCHEMA-DIVERGENCE`: a human applies the changes on the target by the drained model in `docs/schema-change-runbook.md`, then restart.

   **Apply-mark signals (v0.156.5+, ADR-0190).** A restart after a crash mid source transaction skips changes a durable mark proves already applied. Marks are written by default on the serial apply paths and for keyless tables and primary-key changes on the lane path; changes the concurrent lanes apply to a table with a secondary UNIQUE index are marked only with `--exactly-once-lanes` (off by default because it drains the lanes once per such source transaction). Without it, a crash there can still stop the restart on a unique collision (`23505` / `Error 1062`), exactly as before v0.156.5. Recovery from that stop is the destructive `--restart-from-scratch`, which needs human approval; turning on `--exactly-once-lanes` (or `--apply-concurrency 1`) protects only against later crashes. Three markers can appear:
   - `APPLY-MARK-MISMATCH` — terminal: a re-delivered change contradicts its mark, or the `--where` scope changed. Do not retry. The remedy is re-running with the original `--where`, or the destructive `--restart-from-scratch`, which needs human approval.
   - `APPLY-MARK-UNTRUSTED` — a WARN; the change was applied, not skipped. Expected on a sharded PlanetScale/Vitess keyspace. On a keyless table it can duplicate a row, so compare that table against the source.
   - `APPLY-MARKS-UNAVAILABLE` — a WARN: the mark table can't be used, so the stream runs as it did before (a crash mid-transaction may stop the restart on a unique collision, and a table with no usable unique key may gain a duplicate of a replayed row, so compare such tables against the source after a crash). A transient failure probing the table is retried, not reported this way. To enable it, let sluice create `sluice_cdc_apply_marks` (or have a role that may create it run the statements `sluice control-tables ddl --engine <target engine>` prints — the default engine prints the MySQL dialect) and grant the apply role SELECT/INSERT/UPDATE/DELETE on it.

6. **Manage the PG replication slot** (recovery/diagnostics). `sluice slot list --source-driver postgres --source "$SLUICE_SOURCE"` shows every slot (name/active/wal_status/LSNs). `sluice slot drop <name> --source-driver postgres --source "$SLUICE_SOURCE" --yes` removes an abandoned slot (`--if-exists`, `--force` if a consumer is attached, `--yes` is REQUIRED — `slot drop` never prompts; without it the command refuses with `SLUICE-E-CONFIRMATION-REQUIRED`) — dropping an in-use slot breaks that stream, so treat it as gated.

7. **Cut over.** Sequence: `sluice sync stop --target-driver <drv> --target "$SLUICE_TARGET" --stream-id <id> --wait` (drains in-flight changes and clears the stop signal; `--timeout` bounds the wait) → flip application traffic to the target → `sluice cutover --format json --source-driver <drv> --source … --target-driver <drv> --target …` (re-reads source sequence/AUTO_INCREMENT state and applies it with `--sequence-margin` headroom, default 1000). Cutover is idempotent (re-run reports "noop"); it **refuses loudly (exit non-zero)** if the target sequence is already ahead — that means a re-snapshot decision, not a retry.

8. **Decommission a finished stream** (destructive — gated like `slot drop`). `sluice sync decommission --source-driver <drv> --source "$SLUICE_SOURCE" --target-driver <drv> --target "$SLUICE_TARGET" --stream-id <id> --yes` drops the stream's PG replication slot and its recorded per-stream publication on the source (never the shared `sluice_pub`) and clears its control row on the target — after this the stream can never warm-resume. A finished stream's slot otherwise pins WAL and (since v0.99.289) blocks later differently-scoped cold starts. Refuses with `SLUICE-E-DECOMMISSION-STREAM-ACTIVE` while the slot is active (run `sync stop --wait` first); `--dry-run` previews without `--yes`; MySQL-family sources have no source-side objects (control row only). Partial failures keep the control row; re-run to finish.

## What you return
- **Lifecycle state:** cold-start done? handed to CDC? current `sync health` verdict (+ exit code).
- **Freshness:** seconds-since-last-apply, byte-lag (PG), any breached threshold named.
- **Slot state (PG):** the stream's slot name + activity, any abandoned slot flagged.
- **Cutover result:** primed/noop/refused per the cutover report; any refusal surfaced as a decision point.
- **Destructive or approval-gated steps (if any):** `--reset-target-data --yes` / `--restart-from-scratch` / `--force-cold-start` / `slot drop` / `--accept-unforwarded-schema-change` / `--accept-slot-acked-past-position` / `--assert-copy-finished` / `--accept-target-only-unique-key`, `--accept-table-rename` / `schema add-table --abandon`, each named and flagged as needing explicit human approval. On a stream with tables `schema add-table` brought in, say that `--reset-target-data` discards them (a WARN per table; they then receive no changes until named in `--include-table` or added again) while `--restart-from-scratch` re-copies them.

Never pass `--reset-target-data --yes`, `--restart-from-scratch`, `--force-cold-start`, `--accept-unforwarded-schema-change`, `--accept-slot-acked-past-position`, `--assert-copy-finished`, `--accept-target-only-unique-key`, `--accept-table-rename` (a human's statement that a table was renamed, not deleted and re-created — confirm it, and that the target was renamed too: the target table under the new name is trusted as-is) or `schema add-table --abandon` without approval for that specific invocation. On any `status:"refused"` / exit 3, and on an exit-1 `UNFORWARDED-SCHEMA-CHANGE`, `SLOT-ACKED-PAST-TARGET-POSITION`, `SHARDED-TARGET-VINDEX-UPDATE`, `APPLY-MARK-MISMATCH`, `COLUMN-ORDER-CHANGED`, `DEFERRED-SCHEMA-CHANGE`, `COLUMN-IDENTITY-CHANGED`, `KEY-COLLATION-MERGE`, `SOURCE-UNIQUE-KEY-ABSENT`, `UNIQUE-KEY-CONFLICT-OTHER-ROW` or `INCLUDE-TABLE-SCOPE-DRIFT`, surface the message and stop.
