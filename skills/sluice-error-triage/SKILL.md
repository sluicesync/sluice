# sluice-error-triage

Map a sluice failure to its root cause and the correct next action. Entirely read-only: this skill reads codes and state, it never re-runs the failing command (and never adds a destructive flag on its own).

## When to use
Any `sluice` invocation exited non-zero, printed a `SLUICE-E-*` code, or emitted a `status:"refused"`/`"failed"` JSON envelope — and you need to know the cause, the fix, and whether the fix is safe to apply automatically.

## Inputs you need
- The **exit code** (the single most important branch — see step 1).
- The **`SLUICE-E-*` code** if present (on the envelope `error.code`, or in the `--log-format json` stream's `code` attribute).
- The envelope `error` object (`{"message","code","hint"}`) or the raw stderr text.

## Steps

1. **Branch on the exit code first** (`AGENTS.md` / `docs/operator/error-codes.md`):
   - **0** — success (`verify`/`diff`/`sync health`: success *and* clean). Nothing to triage.
   - **1** — runtime failure, OR a `verify`/`diff`/`sync health` **drift/stale** result, OR `sync health` reporting durably **skipped tables** (`skipped_tables_tripped` in the JSON — the target lacks a table the stream carries, or the apply role's privileges on it were revoked, which reads identically; `schema add-table` or an explicit filter resolves the missing-table cause, restoring the grant resolves the revoked cause — no threshold applies, and no remedy removes the ledger row: once the cause is fixed the row must be deleted on the target before health returns to 0, `DELETE FROM sluice_cdc_skipped_tables WHERE stream_id='<stream>' AND table_name='<table>'`, **approval needed: YES**; **but if the skipped table is `sluice_heartbeat`, the table named by `--source-heartbeat-table-name`, or another `sluice_*` control table, none of those applies**: it is sluice's own bookkeeping, left in the ledger by a release before v0.156.9, so the fix is to upgrade and then delete the leftover ledger row on the target, `DELETE FROM sluice_cdc_skipped_tables WHERE stream_id='<stream>' AND table_name LIKE '%sluice_heartbeat'` (substitute the table shown); **approval needed: YES**, it is a write to the target), OR `sync health` state `UNKNOWN` with `CONTROL-TIMESTAMP-IN-FUTURE` (the stream row's `updated_at` reads more than 60s in the future, so its age cannot be read — trips whatever `--max-stale-seconds` says, including 0; the next position write heals it, a stalled stream needs a restart). A real failure to fix, or a genuine data/lag difference to report (hand a drift to `fidelity-verify`). **Exception:** a `sync`/`backup stream` message containing `UNFORWARDED-SCHEMA-CHANGE` is a refusal that exits 1 because it has no code yet. Treat it as a decision point (step 4).
   - **2** — config error (`--config` unloadable/unparsable), or a read-side command that **could not run at all**.
   - **3** — **named refusal (a decision point).** sluice declined by policy and named the remedy — retrying unchanged fails identically. The remedy is often a **destructive** flag needing human approval. Do NOT retry; surface `error.hint` and stop.
   - **80** — kong usage/parse error (unknown flag, missing required arg). Fix the command line; no sluice code ran.

2. **Resolve the `SLUICE-E-*` code** against the table in `docs/operator/error-codes.md` — read off *class* (runtime vs refusal), *cause*, and *remedy*. The `class` drives the exit code (refusal → 3, runtime → 1). Common ones:
   - `SLUICE-E-CONNECT-REFUSED` / `SLUICE-E-CONNECT-AUTH-FAILED` / `SLUICE-E-CONNECT-DATABASE-MISSING` (runtime) — fix DSN host/port, credentials, or db name.
   - `SLUICE-E-COLDSTART-TARGET-NOT-EMPTY` (refusal) — target table has data. Remedy names a **destructive** flag (`--reset-target-data --yes` for sync, `--force-cold-start`) or `--resume` for migrate → approval-gated.
   - `SLUICE-E-SCHEMA-EXTENSION-NOT-ENABLED` (refusal) — `--enable-pg-extension <ext>`.
   - `SLUICE-E-BULKCOPY-TABLE-FAILED` (runtime) — a **generic wrapper** for any per-table copy failure, and the case where **`code` and `hint` mislead: the real cause and correct remedy are in the `message`, not the `code`.** A value-level failure at copy time — a MySQL zero-date, an out-of-range `BIGINT UNSIGNED`, a NUL byte — surfaces here as `SLUICE-E-BULKCOPY-TABLE-FAILED` with the actual fix in `message` (`--zero-date=null|epoch`, a `--type-override`, clean the data), while the `SLUICE-E-VALUE-*` names below **never appear in the envelope `code`**. So for this code, **match on `message`, not `code`** — and ignore the generic `hint`: `--resume` re-hits the same offending row identically, and `--exclude-table` silently drops the whole table's data. Apply the message's remedy instead.
   - `SLUICE-E-VALUE-ZERO-DATE` → `--zero-date=null|epoch`; `SLUICE-E-VALUE-NUL-BYTE` → clean the data or `--type-override COL=bytea`. **These are the underlying causes carried inside a `SLUICE-E-BULKCOPY-TABLE-FAILED` `message` at migrate time (above), not standalone envelope `code`s — read them out of `message`.**
   - `SLUICE-E-INDEX-STATEMENT-TIME-LIMIT` / `-INDEX-DIRECT-DDL-DISABLED` (runtime, PlanetScale) — `--resume` finishes indexes / disable safe-migrations for the run.
   - `SLUICE-E-RESUME-SOURCE-MISMATCH` (refusal, v0.154.0+) — `migrate --resume` refused before any copy: the recorded state was written by a run reading a **different source** (identity is source engine + database + schema, deliberately not the host). The refusal prints the recorded and live identity side by side. Remedy: re-run `--resume` against the source the id belongs to, or — to migrate the source you pointed at — **drop `--resume`** and pass a fresh `--migration-id` (both halves are needed; `--resume` under an unused id refuses separately). Not destructive, so no approval gate. A resume whose recorded state predates the column is not refused; it proceeds with a `RESUME-SOURCE-UNRECORDED` warning, which means identity could not be checked — confirm the source yourself before trusting that run.
   - `SLUICE-E-CDC-REPLICATION-PERMISSION` (runtime) — `ALTER ROLE x REPLICATION`.
   - `SLUICE-E-CDC-KEY-MATCHED-MULTIPLE-ROWS` (refusal, v0.156.8+) — a CDC `UPDATE`/`DELETE` that names its row by key matched more than one target row (typically a `DEFERRABLE` key a source transaction shifted or swapped). Nothing was written; every restart repeats it, and `sync run` does not restart the leg. Remedy is a re-copy (`sync start --reset-target-data`, **destructive** → approval-gated), plus making the source key immediate if the application keeps shifting keys.
   - `SLUICE-E-BROKER-KEYLESS-TABLE` (refusal) — `sync from-backup run` refused before applying anything of an incremental, because a table that incremental touches has no PRIMARY KEY and no NOT NULL UNIQUE index on the chain's recorded schema, or no key on the target made of columns the chain's rows carry (a target re-keyed on a serial, identity or defaulted surrogate counts as keyless), AND its replay cannot be made exactly-once. It is judged per incremental (v0.157.0+, ADR-0191): such a table is replayed when the incremental records change identities and the target's apply marks cover the table. The message says what is missing, and the remedy depends on it: (a) the incremental records no identities (written by an older sluice, or smart-compacted) — `--reset-target-data` restores the chain through its tail and the broker then judges only later incrementals (**destructive** → approval-gated); (b) the reason names the target's apply marks — make `sluice_cdc_apply_marks` usable for the broker's role (only Postgres and MySQL-family targets have apply marks, and a PlanetScale Neki target cannot use them); (c) `BROKER-KEYLESS-NO-IDENTITY` — a change to the table carries no identity (a VStream COPY row, an interleaved shard group, a MySQL transaction without a GTID or server identity, a synthesized fill row), so marks cannot cover it; otherwise, and for (c), add the key on the **source**, take a new full backup and start the broker on the new chain, or replicate those tables with `sync start`. Nothing to undo: nothing of the incremental was applied. v0.156.11 and v0.156.12 refused every keyless table in the chain; if a broker on v0.99.222–v0.156.10 was ever interrupted on this chain, tell the human to compare the table with the source.
   - `SLUICE-E-BROKER-INCREMENTAL-REWRITTEN` (refusal, exit 3, v0.157.0+) — `sync from-backup run` refused to resume inside an incremental it had applied part of, because that incremental is no longer the stream its position counted over: usually `backup compact --smart-compaction` rewrote it under a live broker, or a different incremental now follows the last one applied, or it decodes to fewer events than were applied. Nothing of it was applied by the refused run. Remedy: `sync from-backup run --reset-target-data` (**destructive** → approval-gated). To prevent it, do not smart-compact a segment a broker is still replaying; naive `backup compact` is safe.
   - `SLUICE-E-RESTORE-KEYLESS-TABLE-NOT-EMPTY` (refusal) — `restore` refused before writing because an in-scope keyless table already holds rows (typically a re-run after a failed restore, which would duplicate every row). Remedy: after a failed restore, empty (`TRUNCATE`) or drop every table that attempt loaded, not only the named ones (a keyed table it loaded fails the re-run on its key) — **destructive**, approval-gated — or re-run with `--exclude-table` for the named ones.
   - `SLUICE-E-BACKUP-ROTATED-KEYLESS-TABLE` (refusal, exit 3) — a backup chain that rotated (`backup stream run --retain-rotate-at*`) would re-write a table with no key a re-written row collides on: chain restore applies every later segment full over the earlier segments' rows. Raised by `restore` before anything is written (it also covers a pre-created target table keyed only on a surrogate the rows do not carry), by `backup verify`, by `backup stream run` at the start of a NEW chain when rotation is on (an existing chain gets a `ROTATION-KEYLESS-TABLE` WARN and continues with rotation suspended), and logged at each refused rotation (the stream stays on its open segment). The key judged is the table the target will hold (the chain's own schema history), not only the later full's recorded key. Remedy on restore: re-run with `--exclude-table` for each named table and copy those tables from the source another way. For the source: a NOT NULL UNIQUE index replays mid-chain; do NOT reach for `ADD PRIMARY KEY` on a running chain — that makes it unrestorable (`SLUICE-E-BACKUP-SCHEMA-DELTA-UNSUPPORTED`) and needs a new full in a new location. Nothing to undo: the refusal wrote nothing.
   - `SLUICE-E-BACKUP-CHAIN-SEVERED-TRANSACTION` (refusal, exit 3) — a backup chain an older `backup stream` wrote carries one source transaction across two incrementals, so replaying it would apply part of it twice (or skip part of it on MySQL file/pos). Raised by `restore` before anything is applied, by `backup verify`, by `sync from-backup` for a link it has not applied yet, and by `backup compact --smart-compaction` (chain left unchanged). Remedy: **a new full backup** and a new chain from it — not destructive, and there is no override flag; do not retry unchanged. A chain whose *final* incremental ends mid-transaction is not refused; `restore` WARNs `CHAIN-TAIL-OPEN-TRANSACTION` instead (same remedy).
   - `SLUICE-E-BACKUP-INCOMPLETE` (refusal) — a restore/replay/export decoded a different number of rows/changes than the manifest records, or (refused before anything is applied) an incremental's `EndPosition` is past its last stored change. **On a chain written by `backup stream` on v0.19.0–v0.156.11 that was ever cancelled (SIGTERM/SIGINT mid-transaction, or a failed final flush), the likely cause is that release's cancel-drain loss, not tampering:** the dropped changes are in no incremental and cannot be recovered from the chain — take a new full backup and compare anything already restored or replayed from it against the source. Otherwise treat it as truncation/tamper and restore from an untampered copy.
   - `CHAIN-APPLIED-SEVERED-TRANSACTION` (a WARN from `sync from-backup`, not an error) — a severed-transaction finding on a link the broker **already applied** (by an older binary, or a pre-v0.138.0 Postgres resume). It is logged once and the broker continues, because refusing cannot undo it. Report it: the tables those links touched should be compared against the source, or the target rebuilt from a new full backup.
   - `BARRIER-FOLD-NOT-TRANSACTIONAL` (uncoded exit 1) — an internal-defect refusal in the CDC apply path: an engine was handed a checkpoint to fold into a change it does not apply in one transaction. Nothing was written. Not an operator problem and not fixable by flags — surface the message and report it as a sluice bug.

3. **Classify the remedy's blast radius.** If the remedy is a plain re-run, a DSN fix, or a read-only follow-up → safe to propose running. If it names any **destructive flag** (`--reset-target-data`, `--force-cold-start`, `--yes`, `backup prune`/`compact` without `--dry-run`, `slot drop`) or an acknowledgement flag (`--accept-unforwarded-schema-change`, `--accept-slot-acked-past-position`), it is a decision point. Flag it as needing explicit human approval for that specific invocation (`skills/README.md` safety model). The acknowledgements are gated because each accepts a loss permanently: `--accept-unforwarded-schema-change` a source/target schema difference unless the change was applied to the target first, `--accept-slot-acked-past-position` a gap of skipped changes unless the target was verified to hold them.

4. **A codeless failure is usually a normal operator state, not a bug — read the `message` before escalating.** An exit-1 `status:"failed"` with **no `error.code` and no `hint`** is most often an ordinary decision point whose fix is stated in the `message`: re-running an already-complete migrate (`migration_id "…" is already complete; drop the target tables to redo, or use a different --migration-id`), a wrong restore/backup passphrase (`unwrap chain cek (wrong passphrase / KMS key?)`), and similar. Read the `message` and hand back its stated fix — do **not** jump to filing an issue. A `sync from-backup run` message containing `BROKER-INCREMENTAL-PARTIAL` is this kind: the run was cancelled while applying an incremental. Since v0.157.0 the position stands inside that incremental, so the next run re-applies only from the first source transaction not durably applied (the one in flight; on the lane apply mode, the few whose lanes had not all committed). Read which case the message states. **When it says the incremental records change identities**, re-running the same command is exactly-once for every change that carries one, key changes and keyless tables included, wherever the target holds usable apply marks (approval needed: NO; a run that logged `APPLY-MARKS-UNAVAILABLE` had none, so treat it as the second case below); a change recorded without one (logged as `BROKER-UNIDENTIFIED-CHANGES`) converges by its key unless its transaction moved a key value onto another row. **When it says the incremental records none** (an older sluice wrote it, or smart compaction rewrote it), the re-run converges only if that one transaction changed no row's key value (approval needed: NO in that case). If the source changes key values, a re-run can fail on a duplicate key (MySQL 1062 / Postgres 23505) on every attempt, or, when a key value moved from one row onto another, apply a change to the wrong row with no error; do not retry it unchanged. The recovery then is `--reset-target-data`, which is destructive (approval needed: YES). When the incremental records no identities and you cannot tell whether the source changes key values, treat it as the second case and ask. A clean stop that avoids this state is `sluice sync from-backup stop`, which takes effect between ticks. Also a decision point is `BROKER-COLD-START-PARTIAL`: a `--reset-target-data` cold start was cancelled after it began dropping the target's tables, and re-running with `--reset-target-data` is the recovery (it re-drops those tables, so approval needed: YES; never `--at-chain-id` against that target). **Since v0.154.0 the already-complete state has a CODED sibling that looks similar and means the opposite, so check the code before reaching for this branch:** a `migrate --resume` whose recorded state belongs to a different source is `SLUICE-E-RESUME-SOURCE-MISMATCH` at **exit 3**, not a codeless exit 1. "Already complete" says *this* source's work is done; the coded refusal says the run was about to adopt **someone else's** copy — which, before the door existed, is exactly what exited 0 having copied nothing. Never answer it with "drop the target tables to redo"; see the code in step 2. **This heuristic does NOT apply to `UNFORWARDED-SCHEMA-CHANGE` (v0.156.0+).** That refusal is also a codeless exit 1, with no `error.code` and no `hint`, but it is a decision point. The source (Postgres, or a MySQL/MariaDB binlog source) changed a constraint, policy, RLS, `NOT NULL`, default or similar that CDC cannot forward, so the target is weaker than the source. The refusal is recorded on the target (for `backup stream`, in `stream_state.json`), and every restart refuses again. The replayed refusal prints `fingerprint <12 hex>`. Recovery: a human applies the same change to the target (for `backup stream`, takes a new full backup), then starts once with `--accept-unforwarded-schema-change=<fingerprint>`. **Approval needed: YES.** Passing the flag without the target change accepts the difference permanently. Never propose it as a plain re-run, and never restart the stream in a loop hoping it clears. A fleet leg shows `failed` and is not restarted. **Two more codeless exit-1 refusals are loss or scope signals, not routine states** — every restart refuses the same way, and a fleet leg that hits one shows `failed` and is not restarted: `SLOT-ACKED-PAST-TARGET-POSITION` (Postgres source: the slot was acknowledged past the position the target persisted, so a resume would skip the changes in between; remedy a re-copy with `--restart-from-scratch`, or, only after a human verifies the target holds every change up to the printed LSN, `--accept-slot-acked-past-position=<LSN>`; **approval needed: YES** for either) and `SHARDED-TARGET-VINDEX-UPDATE` (a sharded PlanetScale/Vitess target: vtgate refused a change that assigns a vindex column, so the change cannot be applied there as is; the message names the table, and the supported scope is in `docs/managed-services.md`; a table routed on a vindex outside its primary key is refused before anything is written, by `migrate` and a `sync` cold start, as the coded exit-3 `SLUICE-E-TARGET-SHARD-KEY-NOT-IN-UPSERT-KEY` — see step 2). A codeless exit-1 `CHANGE-LOG-WATERMARK-STALLED` (a `postgres-trigger` source) is a sluice bug, not an operator state: nothing was skipped, every restart re-reads the same window, and a fleet leg that hits it shows `failed` and is not restarted — treat it as the suspected-bug case below and include the change-log query the message prints. **Two codeless exit-1 schema refusals (v0.156.10+) are not routine states either:** `RESUME-SCHEMA-DIVERGENCE` (a table's first schema boundary after a `sync` started disagrees with the target table in a way sluice cannot forward — a possible rename, more than one changed column, a type change across families the target does not already hold) and `SCHEMA-CHANGE-REFUSED` (a `sync` that forwards no source DDL — `--schema-changes=refuse`, a multi-database stream, or `--inject-shard-column` with `--no-coordinate-live-ddl` — met a schema change the target table cannot hold). Both name every differing column with its source and target type, and nothing after the boundary was applied. Every restart repeats them, because each start compares the source with the target again, and a fleet leg that hits one shows `failed` and is not restarted. Recovery: a human applies the change to the target table by the drained model (`docs/schema-change-runbook.md`; `sync stop --wait` first if the stream still runs), then starts again with the same `--stream-id`. There is no acknowledgement flag, so never propose a plain re-run. **Exception — a `SCHEMA-CHANGE-REFUSED` message that also says `AMBIGUOUS-SCHEMA-BOUNDARY`:** do NOT propose applying the change. On a Postgres source it may be a replayed transaction, and narrowing or dropping the target column would destroy values the source still has; the human compares the source's current table definition with the target's AND confirms nobody ran DDL on that table on the source while the stream was stopped — a match alone does not prove a replay, because a column narrowed and widened back, or dropped and added again, while stopped matches too — and only then starts once with the `--accept-unforwarded-schema-change` fingerprint the message prints (it is bound to the position the stream resumed from, so a value left in place stops matching once the stream has moved past that position; still remove it after the one start); if in doubt, re-copying the table is the safe answer. **A refusal that contains `PRE-ALTER-REPLAY-WEDGE`** (a Postgres transaction wrote the table, then dropped, renamed or retyped a column) is not cleared by the drained model: every restart replays it. Surface the recovery the message names (`docs/operator/cdc-streaming.md`, "The pre-ALTER replay wedge"); only a single-database type widening recovers without a re-copy, and under `--inject-shard-column` the re-copy first needs this shard's target rows deleted — never `--reset-target-data`, which drops every shard's rows. **Approval needed: YES.** For `SCHEMA-CHANGE-REFUSED` on a single-database stream under `--schema-changes=refuse`, switching to `--schema-changes=forward` is the alternative; it applies schema changes to the target, so it is the operator's call. Only when the cause is genuinely unexplained (a real suspected bug, an unexpected mid-run `"failed"`) assemble an operator-bundle: `sluice diagnose --target-driver <drv> --target "$SLUICE_TARGET" --stream-id <id> -o bundle.zip` (add `--source-driver`/`--source`; `--privacy basic|standard|verbose` controls inclusion). Note `diagnose` **requires `--stream-id`**, so it fits a *sync* failure — a failed one-shot `migrate` has no stream id, so triage it from its `message`, not a bundle.

## What you return
- **Root cause:** the `SLUICE-E-*` code (or exit-code class) restated as a one-line cause.
- **Recovery command:** the exact next command from the remedy, DSNs via env (`SLUICE_SOURCE`/`SLUICE_TARGET`), never in argv.
- **Approval needed?** YES if the recovery uses a destructive flag, `--restart-from-scratch`, `--accept-unforwarded-schema-change` or `--accept-slot-acked-past-position` (name it, and stop for human sign-off); NO for a safe re-run/config fix.
- **If unclear:** the `sluice diagnose` line to produce a bundle for an issue.

On exit 3 / `status:"refused"`: surface `error.hint` verbatim and wait — do not retry unchanged, and do not pre-authorize the destructive remedy. **Since v0.151.0 sluice already prints the hint** as a trailing `hint: <remedy>` line on stderr, so check before repeating it; the envelope `error.message` is unchanged (the append happens after the envelope is built), which is why the two can disagree.
