# fleet-operator

Run and monitor a fleet of syncs from a single `sluice sync run` process, each failure-isolated with bounded-backoff restart (ADR-0122). State-changing (every leg writes its target); per-leg destructive-flag rules from `cdc-sync-operator` still apply.

## When to use
The user has multiple source→target sync streams and wants one supervised process managing them, with fleet-wide monitoring — instead of one `sync start` per pair.

## Inputs you need
- A `syncs.yaml` **fleet config** (the global `--config` file): a `syncs:` list plus an optional `restart:` policy. Each entry is a curated subset of the `sync start` flags (kebab-case keys: `stream-id`, `source-driver`, `source`, `target-driver`, `target`, `slot-name`, `target-schema`, `control-keyspace` (MySQL/PlanetScale/Vitess target only — the unsharded sidecar keyspace for CDC control tables; omit to auto-detect on a sharded target), `include-table`, `type-override`, `apply-batch-size`, `poll-interval`, per-leg `notify-*`, optional per-leg `planetscale-*`, `zero-date`, …).
- Credentials via env, never committed to the YAML: DSNs' secrets, `SLUICE_NOTIFY_*`, `PLANETSCALE_METRICS_TOKEN_ID`/`_TOKEN`.

## Steps

1. **Validate the fleet config (dry-run first).** `sluice sync run --config syncs.yaml --dry-run` loads and validates every leg without starting them. Fix any config error (exit 2) before running for real.

2. **Run the fleet.** `sluice sync run --config syncs.yaml`. The supervisor starts each leg, isolates failures (one leg crashing doesn't take down the others), and restarts crashed legs with bounded backoff per the `restart:` policy (`backoff-base`, `backoff-cap`, `healthy-run-threshold`, `max-consecutive-failures`). <!-- restart-refusal-roster --> **One exception:** a leg that stopped with `UNFORWARDED-SCHEMA-CHANGE` (the source changed a constraint, policy, RLS or default that CDC cannot forward) is **not** restarted. It shows `failed`, with an ERROR log line, while the other legs keep running. Every other failure is restarted as usual. Do not try to un-fail it with a restart or a `SIGHUP`, because it refuses again. Route it to the acknowledgement flow in `cdc-sync-operator`. That flow needs human approval, because `--accept-unforwarded-schema-change` has no `syncs.yaml` key and runs as a one-off `sync start` outside the fleet. **The same holds for these codeless refusals, which every restart would repeat:** `SLOT-ACKED-PAST-TARGET-POSITION`, `SHARDED-TARGET-VINDEX-UPDATE`, `UNIQUE-KEY-CONFLICT-OTHER-ROW` (an upsert, CDC or copy, matched a DIFFERENT target row through a unique key the target has and the source evidently no longer does, so applying it would overwrite that row with the incoming one; the remedy is to drop that key on the target and start again, or a re-copy — `--restart-from-scratch` for `sync start` (from a Postgres source, after dropping the stream's replication slot), `--reset-target-data --yes` for `sync from-backup run`, which has no `--restart-from-scratch` — both destructive), `INCLUDE-TABLE-SCOPE-DRIFT` (the leg's table scope holds a table the stream never brought in — a table named literally in the leg's `include-table` that it never copied, or a `schema add-table` that started and did not complete — whose existing rows a warm resume would never copy (on a Postgres pgoutput source it would not be streamed at all); the remedy is `sluice schema add-table` for each named table with the leg stopped (approval-gated), taking the table out of the leg's scope, or a re-copy), `SOURCE-UNIQUE-KEY-ABSENT` (the target has a unique key no source key implies — usually a source `DROP INDEX` the leg did not see, made while it was stopped or on a source whose change stream carries no DDL — so the source's next duplicate of it would overwrite a different target row; checked at every start and, on a `postgres-trigger`, SQLite/D1 trigger or PlanetScale/Vitess source, periodically mid-stream; the remedy is to drop that key on the target (approval-gated) and reload, or a re-copy where the message says rows may already have merged; a key the target is meant to have is accepted by name in the leg's `accept-target-only-unique-key` list of `<table>.<key>=<fingerprint>` values the refusal prints — a standing key bound to the key's definition, refused again on any change to it, a human decision), `APPLY-MARK-MISMATCH`, `CHARSET-NOT-DECODABLE`, `DSN-TIME-ZONE-NOT-UTC`, `CHANGE-LOG-WATERMARK-STALLED` (a `postgres-trigger` source; a sluice bug, so the remedy is a bug report carrying the query its message prints), `HEARTBEAT-TABLE-NOT-SLUICES` (the source heartbeat's table name is taken by a table sluice did not create; a fleet spec has no source-heartbeat key, so no leg reaches it today), `RESUME-SCHEMA-DIVERGENCE` (a table's first schema boundary after the leg started disagrees with the target table in a way sluice cannot forward), `SCHEMA-CHANGE-REFUSED` (a leg that forwards no DDL — `schema-changes: refuse`, or `inject-shard-column` with `no-coordinate-live-ddl` — met a schema change the target table cannot hold), `COLUMN-ORDER-CHANGED` (the source flipped the declared order of two of a table's columns — a `RENAME COLUMN` swap or a column reorder — and sluice cannot yet prove the target's order moved to match), `DEFERRED-SCHEMA-CHANGE` (a MySQL-family `binlog_row_metadata=FULL` row carries a type or collation change no schema boundary will describe before its rows land; the remedy is a re-copy), `COLUMN-IDENTITY-CHANGED` (a MySQL-family source's ALTERs left a column name holding a different column — a drop and re-add of the name, or a rename onto it — which no shape comparison can see; also raised as `COLUMN-IDENTITY-UNREAD` for an ALTER sluice could not parse; the remedy is a re-copy) and `KEY-COLLATION-MERGE` (an upsert, CDC or copy, matched a target row through a key whose target collation equates two values the source's collation keeps apart, so it would merge two source rows; the remedy is to give the target key the collation the message names, or a re-copy — except for a key armed to compare bytes (a Postgres source collation on a MySQL-family target), whose message says a re-copy does not converge and names a binary collation instead; `KEY-COLLATION-GUARD-UNSUPPORTED` in the same message means the target lacks the collation the check needs; `KEY-COLLATION-HISTORY-UNORDERED` in it means a backup window changes a key collation that `sync from-backup` cannot place, so neither a restart nor a target collation change converges — the remedy is a new full backup after the key change, then `sluice sync from-backup run --reset-target-data --yes` against it, run by hand and approval-gated). None from `HEARTBEAT-TABLE-NOT-SLUICES` on takes an acknowledgement flag. One coded refusal, `SLUICE-E-CDC-KEY-MATCHED-MULTIPLE-ROWS`, is not restarted either. <!-- /restart-refusal-roster --> The leg shows `failed` with an ERROR line naming the marker (`marker=` attribute) and is not restarted, whatever `max-consecutive-failures` says. A `SIGHUP` reload starts every failed leg still in the config again, so reload only after the fix. Remedy: apply the fix the message names. When it is a DSN change (`DSN-TIME-ZONE-NOT-UTC`), edit `syncs.yaml`, then reload. For `RESUME-SCHEMA-DIVERGENCE`, `SCHEMA-CHANGE-REFUSED` and a `COLUMN-ORDER-CHANGED` whose message says to apply the change on the target, a human applies the change to the target table by the drained model (`docs/schema-change-runbook.md`), then you reload; nothing was recorded, so the next start checks the target again and passes once it holds the change. Never update values to make a `COLUMN-ORDER-CHANGED` pass — the check reads the target's column order. For a `KEY-COLLATION-MERGE` whose message names a collation to give the target key, a human alters that target column (approval-gated), then you reload; never change key values to make it pass. When it needs a flag the fleet config has no key for (`--restart-from-scratch`, `--reset-target-data`, `--accept-slot-acked-past-position`), take the leg out of the fleet (remove it from `syncs.yaml` and reload), start it once by hand with `sync start` and that flag (approval-gated), and once it is streaming stop it with `sync stop --wait` and put it back in `syncs.yaml`.

3. **(Optional) serve the read-only dashboard.** Add `--dashboard-listen :9300` to expose an HTML view + a `/api/fleet` JSON API. **NO AUTHENTICATION** — bind to localhost or a trusted network only. If the address can't bind, the fleet refuses to start (rather than silently running blind).

4. **Attach the terminal dashboard.** `sluice sync tui --connect :9300` (or a full `http://host:9300/api/fleet` URL) polls a running `sync run --dashboard-listen` server — works over an SSH tunnel to a remote fleet.

5. **Monitor per leg (cron/agent-friendly).** Fleet roll-up: `sluice sync status --all --config syncs.yaml --format json` (one table across every configured target; `--watch 2s` to live-refresh, `--summary` for an aggregate header). Per-stream freshness with cron exit codes: `sluice sync health --format json --target-driver <drv> --target <dsn> --stream-id <id> [--max-stale-seconds N]` (exit 0 healthy / 1 breached-or-skipped-tables-or-`CONTROL-TIMESTAMP-IN-FUTURE` / 2 operational; a stream row dated more than 60s in the future is state `UNKNOWN` and trips 1 whatever `--max-stale-seconds` says, including 0; a nonzero skipped-tables count trips 1 with no threshold — `schema add-table` or an explicit filter resolves it; if the table exists but the apply role's privileges were revoked, restore the grant instead; no remedy removes the ledger row, so once the cause is fixed delete it on the target, `DELETE FROM sluice_cdc_skipped_tables WHERE stream_id='<stream>' AND table_name='<table>'`, **approval needed: YES**, before health returns to 0) — one call per leg you gate on.

## What you return
- **Fleet composition:** N legs, each `stream-id` → source→target, and the restart policy in effect.
- **Startup result:** dry-run validation outcome; which legs came up; any leg refused/looping and why.
- **Monitoring surface:** the `sync status --all` roll-up and per-leg `sync health` verdicts (+ exit codes); the dashboard/TUI address if enabled (with the no-auth caveat).
- **Per-leg issues:** name any breached threshold, restart-looping leg, or `failed` leg, and route it to `sluice-error-triage` / `cdc-sync-operator`. For a `failed` leg, quote the message, and name `UNFORWARDED-SCHEMA-CHANGE` (or any of the markers in step 2) explicitly when it appears, and `ADD-COLUMN-BACKFILL-INCOMPLETE` too when present (its repair is to copy the added column's values from the source, not to apply a change to the target).

Per-leg recovery that needs a destructive flag (`--reset-target-data`, `--restart-from-scratch`, `slot drop`, …), `--accept-unforwarded-schema-change`, `--accept-slot-acked-past-position` or a leg's `accept-target-only-unique-key` acceptance (the fleet key for `--accept-target-only-unique-key`) is still approval-gated. Surface it; don't auto-apply it. Keep tokens/URLs in env, never in the committed YAML.
