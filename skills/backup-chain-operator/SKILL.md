# backup-chain-operator

Plan and operate a sluice backup chain safely. State-changing (writes to the backup store); the history-dropping commands are destructive and approval-gated.

## When to use
The user wants a logical backup, an incremental chained off a prior backup, an encrypted chain, or to restore/verify one. Also for chain hygiene (compact/prune) and for proving a chain is restorable.

## Inputs you need
- Source DSN + driver (backup reads the source; incrementals need a CDC-capable engine).
- Destination: a local dir (`--output-dir DIR`) OR a store URL (`--target s3://… | gs://… | azblob://… | file:///…`) — mutually exclusive. S3-compatible providers add `--backup-endpoint` / `--backup-region` / `--backup-path-style`.
- If encrypting: a passphrase source (`--encryption-passphrase-env VAR` or `--encryption-passphrase-file PATH` — prefer these over `--encryption-passphrase`, which leaks into shell history) or a KMS key (`--kms-key-arn` / `--gcp-kms-key-resource` / `--azure-key-vault-id`).

## Steps

1. **Take the full backup.** `sluice backup full --format json --source-driver <drv> --source "$SLUICE_SOURCE" --output-dir <DIR>` (or `--target <URL>`). To encrypt, add `--encrypt` + a key source and choose `--encrypt-mode per-chain` (one CEK/chain; one unwrap per restore) or `--encrypt-mode per-chunk` (one CEK/chunk; defense-in-depth). To chain incrementals off a Postgres full with zero gap, add `--chain-slot` (provisions the persistent slot named by `--slot-name`; costs source WAL retention until consumed). Tune with `--chunk-size`, `--compression none|gzip|zstd`, `--table-parallelism`, `--bulk-parallelism`.

2. **Take incrementals.** `sluice backup incremental --source-driver <drv> --source "$SLUICE_SOURCE" --output-dir <DIR> [--since <BACKUP-ID>] [--window 5m] [--max-changes N]`. `--since` empty chains off the most recent manifest. **OMIT `--encrypt-mode` on an incremental** so it INHERITS the chain's mode — passing an explicit mode that conflicts with the chain is refused at build (the v0.99.185 / Bug-180 rule; **one encryption mode per chain**). Supply the same `--encrypt` + key source the full used. **Note: `backup incremental` has NO `--format` flag** — unlike `backup full` (Step 1) and `restore` (Step 5), it is not a JSON-envelope verb, so passing `--format json` is a kong usage error (exit 80). Don't generalize the full's `--format json` onto it.

   **MySQL/MariaDB sources: an incremental may refuse a schema change made inside its window (v0.158.0+).** The binlog reader decodes each row by the shape it was recorded under. Under the default `binlog_row_metadata` (`MINIMAL` on MySQL, `NO_LOG` on MariaDB) most schema changes of a backed-up table between the window's start and the head refuse (an index, a table option, a `TRUNCATE` or an in-place redefinition do not), and so does a `DEFERRED-SCHEMA-CHANGE` or `COLUMN-ORDER-CHANGED` from the reader. Retrying unchanged refuses again. Surface it: the remedy is for a human to set `binlog_row_metadata=FULL` on the source and take a new `backup full` (see `docs/operator/cdc-streaming.md`). **`COLUMN-IDENTITY-CHANGED` (v0.159.0+) refuses under every metadata setting, `FULL` included:** an `ALTER` in the window left a column name holding a different column (a `DROP COLUMN c` and re-`ADD` of `c`, or a `RENAME` of another column onto it), which no comparison of the table's shape can see, so sluice refuses at the statement. `COLUMN-IDENTITY-UNREAD` beside it is the same refusal for an `ALTER` sluice could not parse. Setting `FULL` does not clear it; the remedy is a new `backup full` (a new chain), and retrying unchanged refuses again.

   **Chain restore applies a key column's collation-only change (v0.159.0+).** When an incremental's window changes only a key column's collation or character set, `restore` of the chain alters the target column before applying that window's rows, so rows the source keeps apart under the new collation are not merged on the target. Before that, such a restore merged them at exit 0. The stated residual is the other direction (`_bin` → `_ci`) when the same window wrote and then removed a pair the new collation equates; no measured case reaches it.

   **Such a segment is stamped manifest format version 13, so an older binary refuses it (v0.159.1+, Bug 304).** An incremental whose `schema_delta` changes a PRIMARY KEY or UNIQUE column's collation or character set is stamped `FormatVersion` 13 (`FormatVersionKeyCollationDelta`), because a binary older than v0.159.0 reads that delta as no change and would restore the table under the old collation, merging rows at exit 0 with its own `backup verify` passing. A pre-v0.159.1 binary now refuses the manifest at its ceiling (`newer than this build supports`): **that is the guard working, not corruption — upgrade that sluice, do not re-take the backup.** The stamp is proportional: a full, a segment with no schema change, and a collation change on a non-key column keep their version and stay readable everywhere. It is not retroactive: a segment v0.159.0 captured across such a change carries no stamp and still restores wrongly on v0.158.x and older, so restore those chains with v0.159.0 or later.

   **Postgres sources: a window whose key collation changed after a row refuses at capture with `KEY-COLLATION-SAME-ANCHOR` (v0.160.0+).** A Postgres change stream anchors every schema version at LSN 0/0, so a backup keeps one shape of a table per window; when two shapes recorded in one window disagree on a PRIMARY KEY or UNIQUE column's collation, the `backup incremental` or `backup stream` exits 1 (uncoded) with `KEY-COLLATION-MERGE: KEY-COLLATION-SAME-ANCHOR: <table>` and records nothing. Retrying from the same position refuses again. Remedy: take a new `backup full` after the key change and continue the chain from it. This is not a target problem: do not offer the target-`ALTER` remedy other `KEY-COLLATION-MERGE` messages carry. Under `REPLICA IDENTITY FULL`, a plain `ADD COLUMN` inside the window does not trigger it.

   **Such Postgres segments can be stamped manifest format version 14 (v0.160.0+).** When the Postgres reader cannot establish a key column's collation for the rows it describes (the column's catalog row was rewritten by, or after, the transaction that wrote them, under a nondeterministic collation), the segment records that key as compared byte for byte and is stamped `FormatVersion` 14 (`FormatVersionKeyCollationUnestablished`). A v0.159.x binary would arm nothing for that key and merge rows at exit 0, so it now refuses the manifest (`newer than this build supports`). As with 13: **the guard working, not corruption — upgrade that sluice, do not re-take the backup.** `sync from-backup` (the broker) refuses such a window with `KEY-COLLATION-HISTORY-UNORDERED` before applying anything; remedy is a new `backup full`.

   **A vanilla-MySQL backup with a collated functional key part is stamped manifest format version 15 (v0.161.0+).** A full or segment whose recorded schema or schema delta carries the collation a MySQL functional key part's hidden column compares under (`HiddenCollation`, FUNCTIONAL-CAST-HIDDEN-COLLATION) is stamped `FormatVersion` 15 (`FormatVersionHiddenCollation`): the expression text does not decide that collation, so an older binary would drop the field and could rebuild the key from the text and merge rows the source keeps apart. A pre-v0.161.0 binary refuses the manifest (`newer than this build supports`): **the guard working, not corruption — upgrade that sluice, do not re-take the backup.** A manifest recorded below 15 that carries the field is refused on read, since no binary writes that shape. Proportional: a schema with no MySQL functional key, one read through vtgate (Vitess/PlanetScale, which does not serve the hidden column), and every Postgres, SQLite and trigger-CDC backup keep their previous version. A chain begun before v0.161.0 stays at its version until a window's schema delta swaps in a freshly read schema. Residual: a functional key's hidden collation changed and changed back inside one window is not seen (FUNCTIONAL-HIDDEN-COLLATION-WINDOW-REVERT).

   **A rotated chain's restore can refuse `KEY-COLLATION-MERGE` (v0.159.1+).** A rotation segment re-applies its snapshot over the rows the previous segment restored through the idempotent upsert writer, which now carries the key-collation guard: when a target key's collation equates two values the source keeps apart, the upsert would have merged two source rows, so it rolls back and the restore exits 1 (uncoded) with a message saying "These are two rows of the source the copy is reading". Never change key values to pass it. Remedy: a human gives the target key column the source's collation (Postgres target: a deterministic collation, or the source's), then restore again. `KEY-COLLATION-GUARD-UNSUPPORTED` in the message means nothing of that table was written, and usually that the target has no collation that compares as the source's; the fix is the target's collation. On a MySQL-family target it can instead name a functional unique-key part whose columns sluice cannot resolve, which no collation change fixes: follow the per-part remedy the message gives (a column it cannot find, from a non-ASCII name: recreate the key over ASCII-named columns; a string literal it cannot scan: write it plainly, or key a stored generated column; generated columns nested more than eight deep: key a shallower expression), or exclude the table.

   **If the source's change stream closes mid-transaction, a one-shot `backup incremental` exits 1 (uncoded) with `BACKUP-WINDOW-ABANDONED-OPEN-TRANSACTION` in the message.** Committing that window would end the chain inside a source transaction, so nothing was written and nothing acknowledged. It is retry-safe: re-run the same command, which re-reads the window from the parent's end position.

   **A full that recorded no end position cannot root a chain, and both extenders refuse it (`POSITIONLESS-FULL-ROOT`, v0.153.1+).** An incremental resumes the source's change stream from the position its parent recorded; with no position there is nothing to resume from, and the pre-v0.153.1 behaviour — start from the source's *current* position after a WARN — silently omitted every change between the full's read and the incremental's open. The refusal fires before any replication connection is opened and before anything is written to the store, so nothing is half-done. Which fulls carry no position: one taken from a PlanetScale Neki router (no cluster-wide position to give), one from a MySQL server with `log_bin` OFF, one older than v0.17.2, and — from a trigger-CDC source — one taken before v0.154.0 or one whose snapshot-anchored open refused (the backup WARNs and names the cause). Such a full is a complete, restorable backup on its own; it just cannot be a chain root. **Do not work around it** — take a fresh `backup full` on a source that records a position and start a new chain, and if the source is MySQL confirm `log_bin` is ON *before* the full.

   **The artifact side of the same hazard, which matters when OLD binaries share the store (v0.154.0+):** a positionless full is now stamped manifest format version **11**, above every older binary's ceiling, so a pre-v0.154.0 sluice refuses the manifest outright instead of extending the chain "from now". If a colleague's older binary reports such a full as unreadable, that is the guard working, not corruption — the remedy is to upgrade their sluice, not to re-take the backup. One refusal comes with it: an encrypted `backup full` that RESUMED an attempt written before v0.104.0 and then finishes without a position refuses at finalize (its sealed chunks predate the AAD encoding version 11 implies). Start a fresh full with `--force-overwrite`.

3. **(Optional) run a rolling stream.** `sluice backup stream run` produces rolling incrementals at a cadence. A chain never ends inside a source transaction, and that shapes how the stream stops:

   - **`sluice backup stream stop`** closes the in-flight rollover at once when no source transaction is open. When one is open, the stream keeps reading to that transaction's commit (already committed at the source, only being delivered) and then commits the rollover — bounded at **60 s / 1,000,000 changes**. If the budget runs out, the rollover is **abandoned**: the stream still exits 0, no manifest is written, nothing is acknowledged, and a WARN carries `BACKUP-WINDOW-ABANDONED-OPEN-TRANSACTION`. Nothing is lost — the next run re-reads that window from the previous rollover's end. `backup stream stop` returns once it has written the request; it is the stream PROCESS that waits.
   - **SIGTERM / SIGINT** (and `q`/ctrl+c in the live panel on a TTY) does not drain: it commits the rollover only when it stands at a transaction boundary, and inside a transaction abandons it immediately (same WARN, exit 0).
   - **Supervisor guidance:** stop with `backup stream stop`, wait for the process to exit, and send SIGTERM only as the fallback, with a grace period over 60 s (systemd `TimeoutStopSec`, Kubernetes `terminationGracePeriodSeconds`). A supervisor that restarts the stream more often than the rollover window (`--rollover-window`, default 5m) means the chain **never advances** — every run exits 0 and only the WARN says so. When reporting a stream's health, grep for that marker rather than trusting exit 0. See `docs/operator/running-as-a-service.md` ("Stopping `backup stream run`").

   **Rotation (`--retain-rotate-at` / `--retain-rotate-at-chain-length`) needs every backed-up table to have a key (Bug 297, v0.157.0+).** Chain restore applies each later segment full over the rows the earlier segments restored, which only a table with a PRIMARY KEY or NOT NULL UNIQUE index can absorb. So a stream starting a NEW chain with rotation on refuses with `SLUICE-E-BACKUP-ROTATED-KEYLESS-TABLE` (exit 3, nothing written) while a table it backs up is keyless; an EXISTING chain logs a `ROTATION-KEYLESS-TABLE` WARN and keeps running with every rotation suspended (each is refused and the stream stays on its open segment, retrying at every rollover). When reporting a rotating stream's health, grep for that marker: exit 0 does not say rotation stopped. Remedy on the source: a NOT NULL UNIQUE index replays mid-chain and lets rotation resume; **do not suggest `ADD PRIMARY KEY` on a running chain** — that delta makes the chain unrestorable from that point (`SLUICE-E-BACKUP-SCHEMA-DELTA-UNSUPPORTED`) and needs a new full in a new location. Or run the stream without the rotation flags.

   **If Step 1 used `--redact`, Steps 2 and 3 do not apply — they will refuse.** Only `backup full` redacts; incrementals and the stream take change events off the CDC pump verbatim, so extending a redacted full would archive plaintext for every row touched after the snapshot. Since v0.144.0 the full records that it was redacted and both extenders refuse with `SLUICE-E-BACKUP-REDACTED-CHAIN`, as does `backup compact`. **A redacted chain is a series of FULLS**: take periodic redacted fulls instead, and use `backup prune` rather than `compact` to reclaim space. If you want incrementals, start an unredacted chain deliberately and accept plaintext in the change window. One more consequence worth knowing before Step 5: resuming CDC off a redacted chain with `sync start --position-from-manifest` refuses unless that sync carries the same `--redact` rules, because otherwise every replicated update would overwrite the restored redacted value with the plaintext one.

4. **Verify the chain — and SAY WHICH QUESTION your run answered.** `sluice backup verify --from-dir <DIR>` (or `--from <URL>`) is read-only and safe to run anytime, but a green exit means three different things depending on **two independent axes**: the `--depth` you passed, and whether you gave it the key. Never report "the chain verifies" without naming both.

   - **`--depth hash` (the DEFAULT), key-less — sha256 only.** It re-checksums every chunk's bytes against the manifest and reports mismatches. That proves the bytes have not rotted **and nothing more**: bytes that hash correctly can still be sealed under a key `restore` will not reproduce, and can still be unreadable by the chunk reader.
   - **`--depth hash` + `--encrypt` and the chain's key material.** Adds the real AES-GCM authenticated open of every encrypted chunk, under the same CEK and AAD binding `restore` uses (in the default per-chain mode too, not just per-chunk).
   - **`--depth read`** — the depth that PARSES. It streams every chunk through the chunk reader `restore` itself uses and discards the rows, so it catches a chunk whose bytes are perfectly intact and still unreadable: a row longer than the reader's 64 MiB line cap (`SLUICE-E-BACKUP-CHUNK-UNREADABLE` — the shape that made a backup verifiable and unrestorable), a mangled codec stream whose SHA was re-stamped, a segment whose recorded codec is not the one its chunks were written with, a value envelope this build cannot decode. It **subsumes** the other two (the reader hashes as it goes and decrypts at open). On an **encrypted** chain it REQUIRES the key and refuses once, up front, with `SLUICE-E-BACKUP-ENCRYPTION-MISMATCH` if you did not pass it — parsing is all it does, so unlike the hash depth it cannot degrade gracefully. Cost: a full read + decompress + decrypt + decode of every chunk, which is why it is not the default.

   Every depth walks the chain's lineage first, the way `restore` does, so a chain a `prune`/`compact` left un-walkable is refused regardless. **A DR-trust verify REQUIRES the key material** — do not report an encrypted chain healthy off a key-less run. **Assert the fields, not the exit status:** the summary reports `Chunks` / `Decrypted` / `Depth` and the INFO line carries `chunks=N decrypted=M depth=…`. On an encrypted chain `M` must equal `N`; `decrypted=0` means no key reached the command. `depth=hash` means you got the byte-level claim only — say so rather than calling the chain proven. A chunk `restore` cannot read fails as `SLUICE-E-BACKUP-CHUNK-AUTH-FAILED` (exit 3); a wrong key fails earlier at the CEK unwrap. (Through v0.104.2 the key-ed mode logged only `decrypt_probe=true` and decrypted nothing at all in per-chain mode — Bug 215. If you see `decrypt_probe` with no `decrypted=`, the binary predates the fix and its green is hollow. A binary with no `depth=` on that line predates `--depth read`.)

   **Verify also runs the severed-transaction check (every depth), and the key axis decides whether it ran.** It decodes the change chunks and refuses a chain an older `backup stream` wrote with one source transaction split across two incrementals — shape A, `SLUICE-E-BACKUP-CHAIN-SEVERED-TRANSACTION` — and an incremental whose `EndPosition` is past its last stored change — shape C, `SLUICE-E-BACKUP-INCOMPLETE`. It does not judge the Postgres-only shape B (that needs the target engine's position order; `restore` into Postgres judges it). On an **encrypted** chain verified **without** the key, it cannot decode the chunks, so it WARNs that the check was SKIPPED and exits green: that run does not answer "is this chain severed?". Pass the key, or let the test-restore in step 5 answer it.

   **What NO depth of `backup verify` proves:** that the VALUES are correct (only a comparison against the source does that — `sluice verify`'s job), or that the rows will APPLY to a target. Those still need step 5. In particular, no depth can see a chain a release before v0.158.0 captured from a MySQL/MariaDB binlog with values decoded under the wrong column names (Bug 301: a reorder, column-name swap or `ENUM` label reorder while the reader was behind the head), or a MariaDB `NO_LOG` chain with large `UNSIGNED` integers recorded as negatives (MARIADB-NOLOG-UNSIGNED, v0.99.271–v0.157.2): the chain is internally consistent. If the source matches either description, report the chain as unproven and recommend a new `backup full`.

   **A chain whose incremental recorded a change to a table's column order now fails (v0.158.0+).** A MySQL/MariaDB reorder and a `RENAME COLUMN` swap record the same schema delta, and only the swap would restore rows under the wrong names, so `backup verify`, chain restore and `sync from-backup` refuse that incremental with `SLUICE-E-BACKUP-SCHEMA-DELTA-UNSUPPORTED` before anything of it is applied. Such a chain cannot be restored past that link; the remedy is a new `backup full`. An `ENUM` label reorder is not a column-order change and still passes.

5. **Test-restore before trusting the chain.** `sluice restore --format json --from-dir <DIR> --target-driver <drv> --target "$SLUICE_TARGET"` (or `--from <URL>`), then run `fidelity-verify`. A chain you have never restored is unproven. Tune with `--table-parallelism` / `--bulk-parallelism` / `--apply-concurrency` (incremental-replay lanes). **`--depth read` partially substitutes for this and does not replace it**: it answers "can every chunk be read back", which is a materially stronger DR signal than a key-ed hash, but it has no target database, so type-retarget failures, constraint violations and every other restore-time semantic are invisible to it. Prefer `--depth read` on the cadence you can afford *and* a periodic real test-restore. Restore into an **empty** target each time: a restore re-run onto a target that already holds a keyless table's rows refuses with `SLUICE-E-RESTORE-KEYLESS-TABLE-NOT-EMPTY` (it would otherwise append a second copy of every row), and a keyed table's rows collide loudly (on a MySQL target's `LOAD DATA LOCAL` path, as `LOAD-DATA-ROWS-SKIPPED`).

   **Chain restore pre-checks the whole chain for severed transactions before applying anything.** It refuses shape A (a non-final incremental ending inside an open source transaction) and, on a Postgres→Postgres restore, shape B (an incremental re-delivering the previous one's last transaction — every resumed window on chains written before v0.138.0) with `SLUICE-E-BACKUP-CHAIN-SEVERED-TRANSACTION` (exit 3), and shape C (an `EndPosition` past the last stored change — the old cancel-drain loss) with `SLUICE-E-BACKUP-INCOMPLETE`. A chain whose FINAL incremental ends inside an open transaction is not refused (nothing follows it), but restore WARNs `CHAIN-TAIL-OPEN-TRANSACTION`: what it restores includes only that transaction's head, a state the source never had. For every one of these the remedy is **a new full backup** (and a new chain from it); there is no override flag, so do not hunt for one.

6. **Chain hygiene — DESTRUCTIVE, gate these.** `sluice backup compact` merges adjacent segments; `sluice backup prune` drops the oldest incrementals to bound disk/restore time. Both **irreversibly rewrite the catalog / drop history** when run without `--dry-run`. ALWAYS run `--dry-run` first, show the plan, and get explicit human approval for that specific invocation before running for real. **`prune` takes the encryption flags for TWO reasons, and the signed-chain one is only the first.** (a) Pruning renumbers link positions and must **re-sign the surviving links**, so a SIGNED chain refuses to prune without `--encrypt` + the key — expected, NOT a usage error. (b) On ANY encrypted chain the key also upgrades prune's chain-readability gate from "the chain's identity survived" to "the chain's CEK still unwraps"; without it the gate degrades to the identity-only check and logs which it did. Pass the key on an encrypted chain even when it is unsigned. An unsigned PLAINTEXT chain prunes without a key. **`compact` DOES take the encryption flags** (this line previously said it took none, which was wrong even before v0.104.2): pass `--encrypt` + the chain's key and compaction proves the chain's CEK still unwraps before it swaps the catalog and after it deletes anything; without them it degrades to an identity-only check and logs which it did. Prefer passing the key on an encrypted chain — that check is the guard against a compaction that reports success over a chain it has made unreadable. Match the flags to what the operation actually touches, and check `--help` rather than assuming.

   **`compact --smart-compaction` (opt-in; off by default) refuses severed inputs before it copies anything.** Collapsing an incremental that carries a severed transaction (shape A, or on a Postgres chain shape B, on any incremental it would rewrite) would hide the evidence restore refuses on, so it refuses with `SLUICE-E-BACKUP-CHAIN-SEVERED-TRANSACTION` (exit 3) and the chain is **unchanged**. Remedy: `--smart-compaction-off` (naive compaction moves the chunks verbatim, so restore still refuses the chain) or, to get a chain that replays, a new full backup. Three more signals from the same pass: (a) when it cannot judge shape B (no recorded source engine, or an engine with no position order) it says so at **INFO** and carries on — read that line before reporting the compaction as fully checked; (b) a chain naming a source engine this sluice does not know refuses with `SMART-COMPACTION-SOURCE-ENGINE-UNKNOWN`, an **uncoded exit 1** (remedy `--smart-compaction-off`, or a sluice that knows the engine); (c) after the rewrite, a verdict gate compares the severed-transaction findings before and after, and any difference refuses as `SLUICE-E-BACKUP-CHAIN-UNREADABLE` at the **pre-swap** stage — nothing swapped or deleted. That one is a sluice defect, not a chain problem: use `--smart-compaction-off` and report it.

   **Smart compaction strips the chain's apply identities, which matters if a `sync from-backup` broker replays this chain (v0.157.0+, ADR-0191).** It collapses changes across source transactions, so the incrementals it rewrites lose the per-change identities that make a broker's re-run exactly-once and their manifests' `apply_identity` is cleared. A broker that is partway through a rewritten incremental then refuses with `SLUICE-E-BROKER-INCREMENTAL-REWRITTEN` (recovery: `sync from-backup run --reset-target-data`, destructive), and a rewritten incremental that touches a keyless table is refused with `SLUICE-E-BROKER-KEYLESS-TABLE`. Before approving a smart compaction, ask whether a broker still replays that segment; if one does, use naive compaction (`--smart-compaction-off`), which moves the chunks verbatim and keeps the identities.

   **On a SIGNED chain, prune and compact can refuse because the chain's EXISTING signatures do not verify — and that refusal means something entirely different from the ones above it. Do not treat it as a flag problem.** Since v0.145.0 both commands verify a signed chain before restructuring and re-signing it, because re-signing whatever is on the store is indistinguishable from laundering a tampered chain: an attacker's edit currently fails verification at restore, and a maintenance run holding the chain's key would replace that failing signature with a valid one over their content. The refusal names laundering and points at `sluice backup verify --require-signature`. **Escalate it to the human as a possible integrity event**, do not retry with different flags, and do not assume the chain is merely stale — a chain whose signatures went stale after an interrupted maintenance run still HEALS through the no-op path, so reaching this refusal means the signatures failed to verify, not that they were absent. `--dry-run` still reports on such a chain, which is what to run while investigating.

   **On an ENCRYPTED chain, compaction can refuse up front, and that refusal is correct.** From v0.104.2 a passphrase-encrypted chain whose root `manifest.json` is already missing — compacted or pruned by an earlier version — is refused rather than merged further. Such a chain is ALREADY unrestorable: the root manifest is where the restore side reads the Argon2id salt, so without it sluice derives the wrong key and fails at `unwrap chain cek` while the passphrase is perfectly good. Recovery, which the refusal names: `cp <chain>/seg-merged-*/manifest.json <chain>/manifest.json`. Do not "work around" this refusal — verify the recovery restored the chain, then re-run.

   **`prune` retention is SEGMENT-granular: it rounds your request UP, and on a never-rotated chain it refuses.** A segment full is a restore base only together with the incrementals that continue from it, so trimming the LEADING incrementals *inside* a segment would sever the chain. Prune therefore retires only WHOLE segments and rounds `--keep-incrementals` up to the nearest segment boundary — it keeps **more** than asked, never fewer. It reports both the requested and the retained count at INFO; **read that line and report the retained number**, not the one you asked for, or you will tell the operator their disk was bounded more tightly than it was. A chain that has never rotated is a single segment with no boundary below its root, so nothing is droppable and prune refuses with `SLUICE-E-BACKUP-CHAIN-UNREADABLE`, exit 3, **nothing deleted and the catalog untouched**. That refusal is CORRECT and must not be worked around: the segment full is the only base those incrementals replay onto. Rotate the chain so retention has whole segments to retire, or use `--keep-duration` with a cutoff older than every incremental to retire them all.

## What you return
- **Plan:** full/incremental cadence, destination, encryption mode (one per chain), retention intent.
- **Commands run + results:** backup IDs, chunk counts, `backup verify` outcome, and the **test-restore + fidelity-verify** result (the trust signal).
- **Destructive steps (if any):** the exact `prune`/`compact` invocation, its `--dry-run` output, flagged as needing human approval before the non-dry-run.
- **Slot note (PG `--chain-slot`):** the retained slot is named **`sluice_<name>`** — sluice prefixes the `--slot-name` value. Abandoning the chain means dropping it with `sluice slot drop --source-driver postgres --source "$SLUICE_SOURCE" sluice_<name> --yes` — the slot name is a **positional argument, not `--slot-name`** (passing `--slot-name` is exit 80). Because dropping a slot is destructive, pass `--yes` (`-y`) to confirm it — without `--yes`, `slot drop` never prompts; it refuses with `SLUICE-E-CONFIRMATION-REQUIRED` (exit 3) and touches nothing.

Never run `prune`/`compact` for real, or overwrite a prior backup with `--force-overwrite`, without explicit approval for that invocation.
