# Schema-change runbook

The operator reference for schema changes with sluice — both halves of the problem:

1. **Executing a schema change safely** on a live database. sluice ships a family of schema-change commands for this: `sluice expand-contract` (the full expand→migrate→contract pattern), `sluice backfill` (the data-migration middle step on its own), and `sluice deploy-ddl` + `sluice control-tables ddl` (the governed DDL channel and bootstrap for PlanetScale safe-migrations branches).
2. **Coordinating a schema change with a running sync stream** so the stream stays continuous through it.

What sluice still deliberately is *not*: a versioned-migration tool. There is no migration history table, no multi-environment promotion, no down-migrations — Atlas / Flyway / sqitch / liquibase own that layer, and sluice's commands compose with them (your tool decides *what* changes; sluice's commands are one safe way to *execute* it).

## Which command do I want?

| You want to… | Run | Engines |
|---|---|---|
| Add a column, backfill it, then drop the old one — online, gated, one command | `sluice expand-contract` | PlanetScale (safe migrations ON) |
| Fill/transform a column's values in place — resumable, keyset-chunked, no long locks | `sluice backfill` | MySQL / PlanetScale / Vitess / Postgres |
| Ship one DDL statement to a PlanetScale safe-migrations branch via a deploy request | `sluice deploy-ddl` | PlanetScale |
| Bootstrap sluice's own control tables on a safe-migrations branch | `sluice control-tables ddl` → `sluice deploy-ddl` per statement | PlanetScale |
| Preview the DDL sluice would emit for a target | `sluice schema preview` | all |
| Check whether source and target schemas have drifted | `sluice schema diff` | all |
| Keep a running sync stream aligned through source DDL | see [Coordinating with a running stream](#coordinating-a-schema-change-with-a-running-stream) | all CDC engines |

## `sluice expand-contract` — the full pattern (PlanetScale)

The classic online schema change is expand→migrate→contract: add the new column (expand), backfill the data (migrate), drop the old column (contract). `sluice expand-contract` (ADR-0162) drives all three against a PlanetScale database — dev branch + deploy request for each DDL leg, the ADR-0159 backfill for the data leg, and a verify gate that must pass before the destructive contract leg is allowed:

```bash
export PLANETSCALE_SERVICE_TOKEN_ID='...'   # service token: branch + deploy-request scopes
export PLANETSCALE_SERVICE_TOKEN='...'      # env, never argv — these never land in shell history

sluice expand-contract \
    --org myorg --database mydb --branch main \
    --dsn "$PROD_BRANCH_DSN" --table users \
    --expand-ddl   'ALTER TABLE users ADD COLUMN full_name VARCHAR(255)' \
    --set          'full_name = CONCAT(first_name, " ", last_name)' \
    --where        'full_name IS NULL' \
    --contract-ddl 'ALTER TABLE users DROP COLUMN first_name' \
    --yes
```

Load-bearing details:

- **`--where` is required and doubles as the verify gate.** Make it self-describing (`new_col IS NULL`): after the backfill completes, sluice counts rows still matching it across the whole table — only a count of 0 authorizes the contract leg. A nonzero count fails with `SLUICE-E-BACKFILL-INCOMPLETE` (re-run to catch the stragglers).
- **`--yes` is the destructive confirmation.** The contract leg is a `DROP COLUMN` deploy request against your production branch; without `--yes` (or without `--contract-ddl`) the run stops after verify as a success and prints the exact resume command. `--dry-run` and `--yes` are mutually exclusive by construction — a plan can never confirm a drop.
- **`--dry-run` prints the full plan** — branches, deploy requests, the rendered backfill statement, the gates — with zero control-plane calls and zero writes.
- **Interrupted runs resume with `--resume-from expand|migrate|contract`.** The backfill leg is natively resumable via its persisted cursor; verify always re-runs before contract.
- **A deploy request that outwaits `--deploy-timeout` un-deployed (your org's review queue) keeps its dev branch.** Deleting the branch would close the still-open deploy request you were just told to approve, so on exactly that timeout the cleanup exempts it (as if `--keep-branches` were set) and the message names the kept branch; delete it yourself once the request closes. Every other failure path still cleans up.
- **Safe migrations must be ON** for the production branch (`SLUICE-E-PS-SAFE-MIGRATIONS-DISABLED` otherwise) — deploy requests are the mechanism the command ships DDL through. sluice **never toggles the setting for you**; see [Safe migrations posture](#planetscale-safe-migrations-posture) below.
- Every dev branch passes the **stale-base freshness gate** (`SLUICE-E-PS-BRANCH-STALE-BASE`): a fresh PlanetScale branch's schema can lag production, and a deploy request from a stale base silently proposes *reverting* the missing schema — on the contract leg that would drop the freshly backfilled column. sluice compares the branch schema against production before any DDL, self-heals once via an on-demand backup rebase, and refuses if still stale. Since v0.99.258 (ADR-0167) the deploy request's computed diff is also fetched and refused if it touches any object the leg never intended, and production's schema is re-verified after a long review wait.

## `sluice backfill` — the migrate step alone (MySQL family + Postgres)

When the schema change itself is already handled (or you're not on PlanetScale), the middle step — a batched, resumable, online-safe in-place data migration — is `sluice backfill` (ADR-0159). It is single-endpoint (reads and updates one database) and walks the table's primary key issuing one bounded `UPDATE` per chunk, so no statement approaches PlanetScale/Vitess's synchronous-transaction-time wall (errno 3024) or holds long locks on any engine:

```bash
sluice backfill \
    --driver postgres --dsn "$DSN" \
    --table users \
    --set   "full_name = first_name || ' ' || last_name" \
    --where 'full_name IS NULL' \
    --verify
```

- **`--driver`** is one of `mysql`, `mariadb`, `planetscale`, `vitess`, `postgres` (SQLite/D1 refuse with `SLUICE-E-BACKFILL-UNSUPPORTED-ENGINE`). `--set` / `--where` are native SQL for that engine, emitted verbatim; `--set` splits at the *first* `=`, so CASE arms pass through.
- **Resume is automatic.** The cursor persists in the same database's `sluice_migrate_state` control tables, keyed by a hash of the spec (`--set` + `--where`); a killed run resumes where it stopped, replaying at most one chunk — which is why `--where` should be self-describing (`new_col IS NULL`), so the replay is a no-op. `--restart` discards the cursor and re-walks; `--batch-size` is excluded from the spec hash, so retuning it never orphans a cursor.
- **`--verify`** runs a whole-table remaining-count on `--where` after the walk: 0, *over a run that actually moved rows*, prints the safe-to-contract signal; >0 exits with `SLUICE-E-BACKFILL-INCOMPLETE` (rows written behind the walk's cursor during the run — re-run to catch up, then verify again). Zero remaining over a run that moved **nothing** — this walk, the run whose cursor it resumed, and the completed run it no-ops over all at zero — exits with `SLUICE-E-BACKFILL-VERIFY-NO-EVIDENCE` instead of authorizing the contract step: the count and the UPDATE render the same `--where`, so a predicate that is valid SQL but selects nothing agrees with itself at every step and proves nothing. **Re-running the identical `--verify` command after a successful run is not that shape and exits 0** — the completed run's row count is persisted and carried into the no-op, so an idempotent cron/CI step stays idempotent. (The one exception is a spec a sluice at or below v0.108.0 marked `complete`: those state rows never recorded the count and it cannot be recovered, so such a spec re-verifies as no-evidence — use `--verify-only` for it.) **`--verify-only`** is the standalone scriptable gate for deploy pipelines: no walk, no UPDATEs, no control-table writes, no PK requirement, `--set` optional. It never raises the no-evidence refusal — with no walk it has nothing to have evidence about — and its report says so: it states the remaining count as a fact and that the count alone does not show a backfill ever ran.
- **`--dry-run`** prints the exact engine-rendered chunk UPDATE plus a remaining-row estimate without writing anything.
- **Session time zone.** `--set` and `--where` run in sluice's session: pinned to `time_zone='+00:00'` on the MySQL family, **not** pinned on Postgres (the server/database/role default `TimeZone`, or `PGTZ` where sluice runs). A zoneless timestamp literal or a `now()`/`CURRENT_TIMESTAMP` written into a naive `timestamp`/`DATETIME` column therefore takes that zone's wall clock. Spell literals with an explicit offset, and for a naive column write `timezone('utc', now())` (Postgres) or `UTC_TIMESTAMP()` (MySQL) when you mean UTC. `--verify` renders the same `--where` in the same kind of session, so it cannot catch a boundary shifted by a zone. See [filtered-subset migration](operator/filtered-subset-migration.md#temporal-literals-which-session-time-zone-the-predicate-runs-in).
- Refusals are loud and coded: a table with no (orderable) primary key refuses with `SLUICE-E-BACKFILL-NO-PRIMARY-KEY` (there is deliberately no force flag — an unbounded UPDATE is the exact shape the command exists to avoid); a `--set` column that doesn't exist refuses with `SLUICE-E-BACKFILL-UNKNOWN-COLUMN` before any UPDATE runs; a cursor written by an older sluice that provably mangled it refuses with `SLUICE-E-BACKFILL-CORRUPT-CURSOR` (re-run with `--restart`); a spec whose state row shows a heartbeat fresher than 5 minutes while still walking refuses with `SLUICE-E-BACKFILL-CONCURRENT-RUN` (another run — typically an overlapping cron invocation — looks live; wait for it to finish or for its heartbeat to go stale, then re-run).

## `sluice deploy-ddl` + `sluice control-tables ddl` — the safe-migrations bootstrap

A PlanetScale branch with **safe migrations enabled refuses every direct DDL statement** (Error 1105, "direct DDL is disabled") — including sluice's own `CREATE TABLE IF NOT EXISTS` for its control tables, and the user-table CREATEs a fresh `migrate` or `sync` cold-start issues. sluice surfaces this as the coded refusal `SLUICE-E-PS-DIRECT-DDL-BLOCKED`, naming the exact refused statement, and the way through is the governed channel:

```bash
# 1. Print the exact CREATE statements for sluice's control tables (read-only, no credentials).
#    The default engine prints the MySQL dialect; --engine postgres prints the Postgres set,
#    each CREATE followed by the ADD COLUMN / CREATE INDEX / UTC-DEFAULT statements later releases added.
sluice control-tables ddl

# 2. Ship each statement via a deploy request (dev branch → apply → deploy → cleanup, one command)
sluice deploy-ddl --org myorg --database mydb --ddl '<one statement from step 1>'

# 3a. For sync: pre-create the USER tables the same way, then skip schema-apply
sluice schema preview --source-driver mysql --source "$SRC" --target-driver planetscale --target "$DST"
sluice deploy-ddl --org myorg --database mydb --ddl '<one CREATE from the preview>'   # per table
sluice sync start ... --schema-already-applied

# 3b. For a one-time migrate: pre-create the user tables via deploy-ddl as in 3a, then just run it —
#     no flag needed. migrate's pre-create shape gate (ADR-0166, v0.99.258) detects each
#     pre-created table, verifies its column shape matches (names/types/nullability), and skips
#     the refused CREATE with an INFO. A shape MISMATCH refuses upfront with
#     SLUICE-E-TARGET-TABLE-SHAPE-MISMATCH before any data moves.
sluice migrate --source-driver mysql --source "$SRC" --target-driver planetscale --target "$DST"
```

`deploy-ddl` (ADR-0165) is the full ADR-0162 safety wrapper around ONE verbatim statement: safe-migrations preflight, dev branch with the stale-base freshness gate, apply, deploy request, deploy, skip-revert finalize, always-cleanup. `--dry-run` makes zero control-plane calls. It is also the general escape hatch for any ad-hoc schema change on a safe-migrations branch. The service token rides `PLANETSCALE_SERVICE_TOKEN_ID` / `PLANETSCALE_SERVICE_TOKEN` (env, never argv), same as `expand-contract`.

**After upgrading to v0.158.0, a branch bootstrapped earlier lacks `sluice_cdc_column_order`.** The table records each table's source and target column order, so a stream can accept a column-order change once you have applied it on the target (`COLUMN-ORDER-CHANGED`, below). sluice creates it where it can. A safe-migrations branch, or a Postgres role that cannot create tables, refuses the CREATE; the start then logs `COLUMN-ORDER-RECORD-UNAVAILABLE` and runs, but every column-order change on that stream refuses with the re-copy remedy, even after you apply it on the target. To enable it, ship the `sluice_cdc_column_order` statement `sluice control-tables ddl` prints, via `sluice deploy-ddl`. Records are written at a stream's cold start and at each accepted schema boundary that changes a table's column list, so a stream started before v0.158.0 has no record for a table until one of those happens.

**After upgrading to v0.156.5, a branch bootstrapped earlier lacks `sluice_cdc_apply_marks`.** The table (ADR-0190) lets a restart skip changes of an interrupted source transaction that already reached the target. sluice creates it where it can; a safe-migrations branch refuses the CREATE, so each apply run logs `APPLY-MARKS-UNAVAILABLE` and runs as before, without that protection. To enable it, ship the `sluice_cdc_apply_marks` statement `sluice control-tables ddl` prints, via `sluice deploy-ddl`.

**After upgrading to v0.156.0, an existing `sluice_cdc_state` needs one new column.** The `unforwarded_refusal` column holds a recorded `UNFORWARDED-SCHEMA-CHANGE` refusal. A fresh `control-tables ddl` bootstrap already includes it. On an existing table, sluice adds it with a detect-then-ALTER, which safe migrations refuses. A start without `--schema-already-applied` stops with `SLUICE-E-PS-DIRECT-DDL-BLOCKED`, naming the statement. With `--schema-already-applied`, the start fails too: every start first makes sure a refusal could be recorded, and a stream that could not record one would have it accepted silently by the next restart. Ship it once before restarting your streams:

```bash
sluice deploy-ddl --org myorg --database mydb \
    --ddl 'ALTER TABLE `sluice_cdc_state` ADD COLUMN `unforwarded_refusal` TEXT NULL'
```

The same applies on a Postgres target when sluice's role does not own the control table. That is usually the `--schema-already-applied` setup, with the table pre-created by another role. Postgres checks ownership before `IF NOT EXISTS`, so only the owner can add the column: `ALTER TABLE sluice_cdc_state ADD COLUMN unforwarded_refusal TEXT NULL` (schema-qualified if the control table is not in `public`). Once the column exists, a DML-only role records and clears refusals without any DDL. More generally, every Postgres control-table ensure now checks the catalog first and runs only the DDL whose table, column, index or UTC default is missing; when that DDL is needed and this role cannot run it, the start stops with **`CONTROL-TABLE-DDL-REQUIRED`**, naming the object and the exact statement. Have the owner run it, or run the whole idempotent set `sluice control-tables ddl --engine postgres` prints once.

Indexes: the deferred index build can also hit the safe-migrations block (or the ~900s statement-time wall) *after* the copy — on `migrate`, on `restore`, and on the `sync start` cold-start alike. Arm the automatic deploy-request index-build fallback (ADR-0148) with `--planetscale-org <org>` plus the service-token env vars (optionally `--planetscale-database` / `--planetscale-branch` / `--planetscale-deploy-timeout`) on whichever of those commands you are running, and the still-pending indexes build through a dev branch + deploy request on the already-copied data, no re-copy. Unarmed, the refusal is `SLUICE-E-INDEX-DIRECT-DDL-DISABLED`.

## PlanetScale safe-migrations posture

sluice **never enables or disables safe migrations** on your branch. It is a behavior change on production (direct DDL becomes blocked from then on), and the enable/disable propagation lag makes toggling it around a run unsafe — so:

- `expand-contract` / `deploy-ddl` **require it ON** and refuse with `SLUICE-E-PS-SAFE-MIGRATIONS-DISABLED` when it's off (with it off, direct DDL works and you don't need them).
- `migrate` / `sync` / `backfill` work either way: with it ON, bootstrap via the `control-tables ddl` → `deploy-ddl` flow above; with it OFF they issue DDL directly as on any MySQL.
- If you hit `SLUICE-E-PS-DIRECT-DDL-BLOCKED`, the remedy is the governed channel (or a deliberate operator decision to disable safe migrations for a migration window) — never sluice flipping the toggle for you.

## Coordinating a schema change with a running stream

Separately from executing the change, a schema change on a *source under continuous sync* has to reach the target without breaking the stream.

**Default behavior: unambiguous DDL forwards online.** Since v0.92 (`--schema-changes=forward`, the default), the streamer applies every unambiguous source schema change on the target through the live CDC apply path — `ADD`/`DROP COLUMN`, `ALTER COLUMN TYPE`, and on a MySQL source `ALTER` nullability — logging each applied DDL at INFO. The stream stays online through routine schema evolution; usually there is nothing to coordinate.

**A forwarded `ADD COLUMN` is backfilled from the source by default.** The target fills the rows it already holds with the DEFAULT the forward carried, which is read when the change reaches sluice — after Django's follow-up `ALTER COLUMN … DROP DEFAULT`, after a `SET DEFAULT`, and re-evaluated by the target for a `now()` or `gen_random_uuid()` default dropped in between (a non-constant DEFAULT still declared when the change reaches sluice is refused, not backfilled). So sluice then reads the new column's value for every row from the source and writes it to the target, ahead of every later change. It costs one pass over the table on the source, the stream waits behind it, and it logs its progress; `--no-backfill-added-column` opts out and leaves the target's fill in place with a WARN. A backfill that is interrupted does not resume, so it stops the stream with `ADD-COLUMN-BACKFILL-INCOMPLETE` until you repair and acknowledge it. The details, including how a hard crash is handled, are in [cdc-streaming](operator/cdc-streaming.md).

**What never forwards, on any source: `CREATE`/`DROP INDEX` and `ADD`/`DROP`/`MODIFY CHECK`.** A shape forwards only if the source CDC reader produces a boundary carrying it, and neither reader does — the MySQL reader's DDL-boundary projection carries columns and the primary key only, and pgoutput's relation message carries columns and the replica-identity flag only ([ADR-0091 §1d](adr/adr-0091-default-on-schema-change-forwarding.md) is the matrix, and the source of truth). On a Postgres source the same holds for nullability. Plain indexes are still a silent gap: a source `CREATE INDEX` leaves the target without that index, un-WARNed. Add it on the target out-of-band (`CREATE INDEX CONCURRENTLY` on PG; a deploy request on PlanetScale). A source `DROP INDEX` is not forwarded either, so the target keeps the index. For a plain index that is harmless, but a target unique key the source no longer enforces could turn the source's next duplicate into an overwrite of a different target row, so a dropped *unique* key now refuses: live, at the first upsert that would match a different target row through it (`UNIQUE-KEY-CONFLICT-OTHER-ROW`, v0.161.1), and at every `sync start` and, on a `postgres-trigger`, `sqlite-trigger`, `d1-trigger`, PlanetScale or Vitess source, at a re-check every 15 seconds (`SOURCE-UNIQUE-KEY-ABSENT`). Neither carries an error code, so both exit 1. The recovery (drop the key on the target, re-copy where rows may already have merged, or accept a key the target is meant to have by its fingerprint) and the windows neither check covers are in [cdc-streaming](operator/cdc-streaming.md#sync-a-target-unique-key-the-source-does-not-enforce-refuses-source-unique-key-absent).

**Constraint, RLS, policy and default changes stop the stream (`UNFORWARDED-SCHEMA-CHANGE`, v0.156.0+; Postgres and MySQL/MariaDB binlog sources).** The streamer does not forward these changes, so the target is left without them. The classes are constraint changes (primary key, `UNIQUE`, foreign key, `CHECK`, plus `EXCLUDE` on Postgres), RLS and policies, `NOT NULL` on Postgres, `DEFAULT`, and identity, `EXTRA` or generation changes. Through v0.155.1 they passed silently, an `ADD CHECK` or `CREATE POLICY` included. Since v0.156.0 the stream stops at the next write to the affected table, and the refusal is recorded so every restart refuses again. To recover, apply the change on the target, then start once with `--accept-unforwarded-schema-change=<fingerprint>`, using the fingerprint the replayed refusal prints. The full procedure is in [cdc-streaming](operator/cdc-streaming.md). To avoid the refusal altogether, use the drained model below. A change applied on both sides while the stream is stopped is part of the next start's baseline, so it does not refuse. PlanetScale and Vitess (VStream) sources are not covered by this check, so a constraint, policy or default change there still passes silently, with one exception: a dropped unique key is caught by the `SOURCE-UNIQUE-KEY-ABSENT` re-check above, at most 15 seconds later. Within that window a merge the apply-time check cannot tell from a re-delivery (a table with no primary key and one unique key, or two rows that differ only in a NULL or partial-index column) is applied before the re-check refuses and names a re-copy; a mid-stream primary-key change is caught only at the next start. The full list is under "What this does not catch" in [cdc-streaming](operator/cdc-streaming.md#sync-a-target-unique-key-the-source-does-not-enforce-refuses-source-unique-key-absent).

**What still refuses loudly:** `RENAME COLUMN` and multi-shape combos (a rename is indistinguishable from drop+add without a stable column id — forwarding the wrong guess risks silent data loss), a type or nullability change to two or more columns in one `ALTER` (see below), a change to a table's column order (`COLUMN-ORDER-CHANGED`, below), on a MySQL/MariaDB binlog source a change that leaves a column name holding a different column — a `DROP COLUMN c` and re-`ADD` of `c`, or a `RENAME` of another column onto `c` — read from the `ALTER` statements themselves because no comparison of the table's shape can see it (`COLUMN-IDENTITY-CHANGED`; the remedy is a re-copy, see [cdc-streaming](operator/cdc-streaming.md)), a key column's collation or character-set change met as the first schema boundary after a start, or on a `--schema-changes=refuse` stream, when the stream is under `refuse` or holds no earlier shape of the table to judge it by (`KEY-COLLATION-CHANGED`, inside `RESUME-SCHEMA-DIVERGENCE` or `SCHEMA-CHANGE-REFUSED`; apply the same change on the target and restart — under `forward` with an earlier shape on record it is forwarded), and an `ADD COLUMN` whose `DEFAULT` is computed/volatile (`NOW()`, `nextval()`, `gen_random_uuid()`, … — forwarding it would silently diverge already-shipped rows). The refusal carries the per-table drift diff (F11) naming every drifted column/index/constraint plus a recovery hint per category.

**Forward mode forwards one column's type or nullability change per boundary (v0.158.0+).** Two or more columns changing type or nullability in one `ALTER` — `ALTER TABLE t ALTER b TYPE numeric(12,4), ALTER c TYPE numeric(12,4)`, or two `MODIFY`s in one MySQL statement — now refuse, naming every column. That includes two widens within one family, such as two `VARCHAR` widens. Through v0.157.2 the classifier read such a change as no change at all: a Postgres target kept `numeric(10,2)` and rounded every later value at exit 0, while a MySQL target refused the first value that did not fit. Affected: the forward path from v0.99.45, and `--inject-shard-column` (Shape A) since v0.73.0. At the first boundary after a cold start, several nullability-only changes are skipped with a WARN, as a single one is. Recover with the drained model below, applying every change on the target, or issue the changes as separate `ALTER` statements.

**A change to a table's column order refuses until the target holds it (`COLUMN-ORDER-CHANGED`, v0.158.0+).** `RENAME COLUMN b TO c, RENAME COLUMN c TO b` (a swap; a three-way rotation is the same) and `MODIFY c … AFTER id` (a MySQL/MariaDB reorder) produce the same schema boundary: every column keeps its name and type, and only the declared order changes. A reorder needs nothing on the target; a swap leaves every row the target already holds under the wrong column names. Through v0.157.2 both were forwarded as no change, so a swap silently left those rows wrong (RENAME-SWAP-FORWARD, CRITICAL; every release of `sync start`). The stream now refuses such a boundary before recording it or applying any row after it, and accepts it only once the target's own column order has moved from the order sluice recorded for the table to the source's new one. The record is the new control table `sluice_cdc_column_order`, written at the cold start and in the transaction of every accepted boundary that changes the source's column list. The check runs on the forward path, on a restart's first boundary, under `--schema-changes=refuse` (as `SCHEMA-CHANGE-REFUSED`), and under `--inject-shard-column`. The refusal is codeless (exit 1), every restart repeats it, and `sync run` does not restart the leg. The message names the remedy:

- **Apply the same change on the target**, then restart with the same `--stream-id`: the same `RENAME COLUMN` statements for a swap or rotation, or the same `MODIFY … AFTER/FIRST` for a reorder on a MySQL-family target (MySQL rebuilds the table to do it). Do not update values instead; the check reads the target's column order.
- **Re-copy** with `sluice sync start --reset-target-data --yes` and the stream's other flags unchanged (on a Postgres source, drop the slot with `sluice slot drop` first). This is the only remedy when the source reordered columns and the target cannot reorder in place (Postgres), and when sluice cannot prove the target moved: the table has no record, or its recorded target order already disagreed with the source. `schema add-table` is deliberately not offered: it keeps the stream's position and would replay rows written before the change onto the re-copied table under the old names.

**The cost.** A plain MySQL/MariaDB column reorder, which forwarded as a no-op since v0.99.45 ([ADR-0091 §4](adr/adr-0091-default-on-schema-change-forwarding.md)), now stops the stream until the target is reordered too. A stream started before v0.158.0 has no record for a table until that table's next accepted boundary that changes its column list, so a column-order change before then refuses with the re-copy remedy.

**MySQL and MariaDB sources: set `binlog_row_metadata=FULL` before you change schemas under a stream (v0.158.0+).** A binlog reader behind the head (every `backup incremental`, a resumed or lagging `sync`) decodes each row by the shape it was recorded under. Under MySQL's default `MINIMAL` or MariaDB's default `NO_LOG` the binlog does not record column names, so most schema changes of a streamed table between the reader and the head now refuse instead of decoding; that includes gh-ost / pt-online-schema-change / LHM `RENAME TABLE` cutovers. `FULL` lets sluice decode across them by name. Details, and what `FULL` still refuses, are in [cdc-streaming](operator/cdc-streaming.md#mysql-family-binlog-sources-decoding-rows-behind-the-head-deferred-schema-change-sluice-e-cdc-binlog-lookahead-short).

**If your target went through a column swap on an earlier release,** run `sluice verify --depth=sample` with a binary newer than v0.158.0: it compares columns by name, so the swapped rows it samples mismatch. (v0.158.0 and older hashed each side's columns in its own declared order and read a swapped target as clean.) A sample samples — if only a small fraction of the table predates the swap, raise `--sample-rows-per-table` or compare the affected columns' values by primary key between source and target yourself — and re-copy the table where they differ.

**A cast to or from a session-normalised timestamp refuses, in either direction and at any precision.** The original shape is a MySQL `TIMESTAMP` ↔ `DATETIME` `MODIFY`, and since v0.139.0 the refusal covers the wider measured class: a cast between `TIMESTAMP` and `VARCHAR`, `DATE`, `TIME` or `BIGINT` (and Postgres `timestamptz` to text or date) resolves through the executing session's zone in exactly the same way. The `time` / `timetz` pair is MEASURED asymmetric, and since v0.142.0 the refusal matches the measurement rather than covering both halves. `time` → `timetz` refuses: an offset is invented, and Postgres takes it from the executing session. `timetz` → `time` FORWARDS: `timetz` stores its offset alongside each value, so dropping it consults no session zone at all, and the cast measured byte-identical under `UTC` and `Asia/Tokyo`. The array shapes follow the scalar ones (`time[]` → `timetz[]` refuses, `timetz[]` → `time[]` forwards). The `timestamp` family is unchanged and still refuses in both directions, because `timestamptz` is stored normalised to UTC and so re-renders through the session zone whichever way the cast runs. Measured on MySQL 8.0.46 and Postgres 16. `ALTER TABLE t MODIFY c DATETIME` on a `TIMESTAMP` column (or the reverse) makes MySQL convert every stored value using the *executing session's* `time_zone` — not the server's, and nothing the binlog or the VStream wire carries. The source operator's ALTER ran under their own session, whose shipped default is `time_zone=SYSTEM` (the host zone), while sluice pins `time_zone='+00:00'` on every connection it opens; so a forwarded ALTER would re-cast the target's pre-existing rows against a different zone whenever the source host is not UTC. Every pre-existing target row of that column would end up off by the host's UTC offset, every row applied after the ALTER would be correct, row counts would match, and the sync would exit 0 — which is why the shape refuses (the message names the column, both types and the mechanism) rather than forward. Since v0.138.0 the refusal also fires at a table's **first** DDL boundary after a cold start or a warm resume: it had compared each boundary against a prior shape that only the boundary emitter itself wrote, so the first `MODIFY` per table after any start went unchecked, and under `--inject-shard-column` was forwarded (observed on a `+09:00` source: every pre-existing target row read nine hours off at exit 0). The MySQL reader is now seeded with each in-scope table's shape at start — the source schema on cold start, and on warm resume the target's own current column types read back through the target engine (the independent witness of the last shape the stream committed under; a target you have already ALTERed to the new family therefore lets the replayed DDL through as the no-op it is, which is what makes the drained-model recovery below resumable), with the retained schema-history version as the fallback for a table the target does not hold, a `--type-override` on a temporal column, or a target whose read-back does not distinguish the pair — and keeps its last decoded shape across a DDL cache clear, on all three lanes (binlog, VStream, VStream snapshot stream); the pipeline's boundary routers carry the same door as a belt. Precision-only changes within one type (`DATETIME(3)` → `DATETIME(6)`), and casts with no zoned side at all (`DATETIME` → `VARCHAR`), carry no zone conversion and keep forwarding. The widened class is enforced at the pipeline door, which is reached when a boundary is FORWARDED — the mode that re-casts the target's existing rows; the reader-side checks that refuse at a table's first boundary still carry the original pair. The remedy is the drained-model workflow below: stop with `--wait`, run the same `MODIFY` on source **and** target from your own client so both casts happen under a session zone you chose, then restart with the same `--stream-id`. Stated residual: a fallback table with no retained history row cannot be checked at its first boundary after a warm resume, so a swap performed while the stream was stopped on such a table is primed rather than refused. A MySQL MULTI-DATABASE stream is no longer a second residual. v0.143.0–v0.144.x delivered that lane its seed but never armed the reader's refusal, so a swap there was not refused at all. Since v0.145.0 the fan-out arms the reader like the single-database lanes (`schemaDeltaAppliesToTarget` is true for every stream), so the reader refuses a swap on a table whose seed gave it a prior. Since v0.156.10 every boundary on a multi-database stream is also compared with the target table by the `SCHEMA-CHANGE-REFUSED` check, which refuses a `TIMESTAMP` ⇄ `DATETIME` pair in either direction. It does so twice over: it tests the pair with the same session-zone predicate as the forward path's door, and it never counts a pair whose zone kind differs as the target being "wider" (a change across zone kinds is not comparable, so it refuses). The refusal names the column with both types. The remedy is the same drained-model workflow, with the target-side `MODIFY` run in the target database that source database maps to. The first residual above still applies with a WARN: a table the target does not hold, with no retained history row, passes its first boundary unchecked. Neither multi-database door is measured end to end on a real server (the session-zone integration test covers single-database Shape A, forward and refuse modes); the `SCHEMA-CHANGE-REFUSED` judgement is unit-pinned for the target-`TIMESTAMP`, source-`DATETIME` direction only. The Postgres lane's twin of the first-boundary gap was closed in v0.139.0 — its reader now takes the same target-witness seed and checks a table's first relation message against it. The `postgres-trigger` lane has no zone-SPECIFIC door and does not need one: a Postgres event trigger fires whether or not sluice is running, so a swap made while the stream was stopped is recorded as a DDL marker at the moment it happens and the resume refuses on it. Its residual is narrower and not specific to this class — an `--allow-polled-fingerprint` install has no event triggers, so no source DDL is visible to it at all. **On the MySQL family the refusal honours the sync's table filter as of v0.148.3, on all three of its CDC lanes.** A `TIMESTAMP`⇄`DATETIME` `MODIFY` on a table you excluded with `--exclude-table` no longer kills the stream, because nothing this sync emits for that table reaches the target — the same posture the XA refusal has carried since Bug 246. Before that the two VStream lanes could not honour a filter under any circumstance, having never declared the interface the pipeline hands it over through, so `--exclude-table` is a working mitigation on PlanetScale and Vitess only from this release.

**A change the stream did not see happen is checked against the target (`RESUME-SCHEMA-DIVERGENCE`, v0.156.10+).** Each table's first schema boundary after a stream (re)starts — a warm resume, a restart, an automatic retry — has no earlier boundary to compare against, so sluice compares it against the target table itself, column names and types. If they match, nothing happens. If the source has columns the target lacks, they are added (and backfilled). If exactly one column was widened within its family (a temporal precision, a decimal's integer digits and/or scale, a `CHAR`/`VARCHAR` length, `FLOAT` → `DOUBLE`, an integer width), the change is applied; if the target already holds that column WIDER than the source — within its family, or across one whose type holds every source value (`TEXT` for `VARCHAR`, a wide enough `NUMERIC` for an integer; never `jsonb` for `json`) — it keeps its type with a WARN — a first boundary never narrows a column, so a narrowing made while the stream was stopped is yours to apply on the target. A column named by `--type-override` is compared by presence only. If the target has columns the source no longer has (a `DROP COLUMN` made while the stream was stopped), a WARN names them and the target keeps them. Anything else — a possible rename, more than one changed column, a type change across families the target does not already hold, a decimal widened on one axis and narrowed on the other — stops the stream with `RESUME-SCHEMA-DIVERGENCE`, naming every differing column with its source and target type, before anything after the boundary is applied. Recover with the drained model below: make the target match the source, then restart; the check runs again at the table's first boundary on every start, so once the two agree the stream resumes. Through v0.156.9 that first boundary was simply accepted: a `DATETIME` → `DATETIME(6)`, `DECIMAL(10,2)` → `DECIMAL(12,4)` or `FLOAT` → `DOUBLE` change made while the stream was stopped (or after a restart, before the table's next row) never reached the target, and every following value was rounded into the old column at exit 0. With `--inject-shard-column` (Shape A) a difference the check forwards goes through the shard-consolidation lease like a live boundary, so it is applied once however many shards reach it.

**`--schema-changes=refuse`** restores the conservative pre-v0.92 posture for shops that gate DDL through a separate change-management process: the streamer forwards nothing. Since v0.156.10 it checks every schema boundary against the target instead (`SCHEMA-CHANGE-REFUSED`; a multi-database stream, which never forwards, and `--inject-shard-column` with `--no-coordinate-live-ddl` get the same check): a change the target already holds passes, a target column changed ahead of the source that holds every value the source can send passes with a WARN, a column only the target has passes with a WARN, and anything else — a source column the target lacks, a type the target cannot hold — stops the stream before any row after it is applied. So apply each change on the target, before or after the source; once the target holds it, restart with the same `--stream-id` — except when the refusal says `AMBIGUOUS-SCHEMA-BOUNDARY` (a Postgres source, where a replayed transaction and a change made while stopped look the same): compare the source's current table definition with the target's first, because if it is a replay, applying the "change" would destroy values — but a match does not prove a replay (a column narrowed and widened back, or dropped and added again, while the stream was stopped matches too), so also confirm nobody ran DDL on the table while it was stopped, and re-copy the table if you cannot. On a Postgres source the reader also refuses a column type change, `DROP COLUMN` or `RENAME COLUMN` it sees mid-session, and a transaction that writes a table, alters it and writes it again refuses on every restart (`PRE-ALTER-REPLAY-WEDGE`): a type widening on a single-database stream passes with one start under `--schema-changes=forward`; anything else needs `sluice slot drop` followed by one start with `--restart-from-scratch` — under `--inject-shard-column`, after deleting that shard's rows from the target tables. The details are in [cdc-streaming](operator/cdc-streaming.md). Through v0.156.9 none of those modes refused a type widen within a family (`DATETIME` → `DATETIME(6)` on MySQL, `numeric(10,2)` → `numeric(10,4)` on Postgres): every following value was rounded into the target's old column at exit 0 (GC-44 F5).

**The drained-model workflow** (for refused shapes, or under `refuse` mode):

```bash
# 1. Drain and stop; --wait blocks until the streamer confirms clean drain
sluice sync stop --wait \
    --target-driver postgres --target "$TARGET_DSN" \
    --stream-id myapp-prod

# 2. Apply the change on source and target with your SQL client, e.g.:
psql "$TARGET_DSN" -c 'ALTER TABLE accounts RENAME COLUMN old_name TO new_name'
# (and the equivalent ALTER on the source side)

# 3. Restart with the SAME --stream-id — sluice warm-resumes from the persisted CDC position
sluice sync start \
    --source-driver mysql    --source "$SOURCE_DSN" \
    --target-driver postgres --target "$TARGET_DSN" \
    --stream-id myapp-prod
```

`sync stop --wait` guarantees the in-flight batch is committed and the CDC position is persisted past the last applied event — on a Postgres source that is the last transaction's end LSN, so the resumed stream starts at the *next* transaction rather than re-delivering the one it closed. Re-running `sync start` with the same `--stream-id` warm-resumes automatically (there is no `--resume` flag on `sync start`); the post-restart CDC schema cache rebuilds from the first event after that position, so the new shape is the anchor on both sides. The corollary is that a schema change applied to the source *only*, while the stream was stopped, is not classified at resume — this workflow applies it on both sides before restarting, which is why it works. (Before audit finding A2-1 was fixed, a Postgres resume re-delivered the last applied transaction with its pre-DDL relation shape, and every refusal re-fired on the restart the hint prescribed.)

**A table rename done this way resumes on its own.** Rename the table on both sides while the stream is stopped (`ALTER TABLE t RENAME TO t2` on Postgres, `RENAME TABLE t TO t2` on MySQL-family), then restart: the stream's record of the tables it copied keeps each table's engine-stable id (Postgres `pg_class.oid`, InnoDB `TABLE_ID`), recognises `t2` as `t` renamed, and follows it. If the target was not renamed, the restart refuses `INCLUDE-TABLE-SCOPE-DRIFT` saying so. A table dropped and re-created under the new name is a different table (a new id) and refuses as never copied. Where no id proves the rename — a PlanetScale/Vitess source, a table name InnoDB stores encoded, or a stream whose record has no ids — the refusal names `--accept-table-rename <old>=<new>`: pass it once on that restart, after renaming the target too, and the record follows the rename.

**Type widening + a value the target can't hold** stays fail-loud by design: sluice preserves the source value bit-for-bit and lets the target's stricter constraint reject (`SQLSTATE 22001` or analogous) — the alternative is silent truncation. Widen the *target* column first (drained-model above), then restart; `--type-override TABLE.COLUMN=TYPE` is the tool when you deliberately want the target type to differ from sluice's auto-emit choice.

## Planning ahead with `sluice schema diff`

`sluice schema diff` (ADR-0029) runs the source schema through sluice's translation pipeline and compares the result against the target's actual schema. Use it to:

1. **Pre-flight a planned ALTER** — apply it on the source, run the diff, and the missing-on-target columns / type mismatches surface with suggested `ALTER` statements as a starting point.
2. **Verify post-ALTER alignment** — expect "in sync" + exit 0; CI-gateable.
3. **Catch unintended drift** — hand-edits on the target that were never mirrored surface before they break CDC apply.

The suggested ALTER statements are starting points, not verified migration scripts — the diff doesn't know your data volume, lock duration, or downstream consumers.

## When to reach for Atlas / sqitch / liquibase instead

Use a dedicated migration tool when you need version-controlled migration history with an audit log, multi-environment promotion (dev → staging → prod), down-migrations, or schema-as-code in your application's build. sluice runs alongside those: your migration tool decides and versions the change; `sluice backfill` / `expand-contract` / `deploy-ddl` are safe executors for the online-change and safe-migrations cases; and the coordination workflow above keeps a running stream aligned while the change lands.
