# Production readiness

This page is the one-stop answer to "is sluice ready for my workload?" — the support matrix, the CDC modes per source, the honest list of what sluice does *not* do today, and a pre-production checklist. It is maintained against the code, not aspirations; every limitation below names its trigger condition and its workaround. Status as of v0.159.1 (the stamp is checked: `TestProductionReadinessStatusStampIsCurrent` in `internal/docsync` fails the build once it falls outside the five newest archived releases). At this stamp every claim below was re-read against the code and `docs/dev/audit-backlog.md`; a claim that could not be checked that way says **unverified** where it stands.

The posture behind this page: sluice has **two outside production migrations on the record and no install base** — v0.111.1 (2026-08-05), a 2.64 GB MariaDB → PlanetScale move whose `migrate` completed clean and whose `sync` failed every attempt, and v0.148.0 (2026-09-08), an AWS → GCP move of a PlanetScale MySQL database that succeeded; each operator's field report drove that release — and treats that as the reason to gate on correctness rather than a caveat to bury — the project's tenet is that the first migration that silently corrupts data ends its credibility permanently. What "battle-tested" means here is therefore specific and checkable: every silent-loss class ever caught has a permanent class-pin test (per-family × per-shape matrices ground-truthed on real servers, not representative pins); six required CI checks run real-database integration suites — including cross-engine migrate + sync + backup — on every PR; repeated full blind multi-agent audits of the codebase (three in July 2026 alone) each ran to remediated closure; the PlanetScale filtered-sync path was validated end-to-end against real PlanetScale at 5M rows; and a multi-week soak fleet ran continuous syncs against live managed services between releases until it was torn down on 2026-09-13 — there is no standing soak today. What it does *not* mean: an install base, or a stability guarantee — v0.x minor releases may still include opt-in behavior changes ([README § Project state](../README.md#project-state)).

## Supported engines and directions

Fourteen engines are registered (`sluice engines` lists them): `mysql`, `mariadb`, `planetscale`, `vitess`, `postgres`, `sqlite`, `d1`, `csv`, `tsv`, `ndjson`, `mydumper`, `postgres-trigger`, `sqlite-trigger`, `d1-trigger`.

### Live databases — migrate and continuous sync

| Source ↘ Target → | MySQL | MariaDB | PostgreSQL | PlanetScale MySQL | PlanetScale PG | PlanetScale Neki |
|---|---|---|---|---|---|---|
| **MySQL** | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| **MariaDB** | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| **PostgreSQL** | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| **PlanetScale MySQL** | ✓ (VStream CDC) | ✓ (VStream CDC) | ✓ (VStream CDC) | ✓ | ✓ | ✓ |
| **PlanetScale PG** | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| **PlanetScale Neki** | ✓ (migrate) | ✓ (migrate) | ✓ (migrate) | ✓ (migrate) | ✓ (migrate) | ✓ (migrate) |

Every cell supports one-shot `migrate`; every cell whose source has a CDC mode (next section) also supports continuous `sync` — with ONE exception, stated here rather than left to be discovered: **PlanetScale Neki is a migrate source only.** The router refuses a replication connection outright (`replication connections must target a specific shard`, SQLSTATE 0A000 — measured on an unsharded Neki too), so `sync` stops at the snapshot open; and even a per-shard replication connection, which can export a snapshot, leaves nothing to import it with (`SET TRANSACTION SNAPSHOT` and `pg_export_snapshot()` are unimplemented), so there is no cold-start-to-CDC handoff out of it. Neki as a TARGET supports both, including into a sharded database and across a live reshard. Neki is reached with the ordinary `postgres` driver — there is no `--source-driver neki`; sluice detects it from the server version. See [`docs/managed-services.md`](managed-services.md#planetscale-neki-sharded-postgres) and [`docs/operator/planetscale-postgres-to-neki.md`](operator/planetscale-postgres-to-neki.md). MySQL flavors (vanilla, MariaDB, PlanetScale, Vitess) share one engine implementation with per-flavor `Capabilities` declarations; MariaDB is first-class since v0.99.268 (native `uuid`/`inet6`/`inet4` carry, domain-GTID CDC, JSON-via-`json_valid`).

A PlanetScale MySQL host needs a VStream driver. `migrate` and `sync` **refuse** such a host under `--source-driver mysql` or `--source-driver mariadb` (and the `--target-driver` equivalents) with `SLUICE-E-DRIVER-HOST-MISMATCH`, from the DSN string alone and before any connection: those flavors drive binlog CDC and `LOAD DATA` cold-copy, both of which Vitess blocks, so the run would otherwise fail obscurely partway through. Use `--source-driver planetscale` — or `vitess` for a self-hosted Vitess — which gets VStream CDC with the Vitess `_vt_*` shadow tables auto-excluded. The DSN-based arm runs on `migrate` and `sync`; since v0.125.0 a connect-time VERSION() fingerprint backstops EVERY surface that opens a schema reader or writer — `schema diff`, `schema preview`, `backup`, `restore`, `verify` included — refusing a plain-`mysql` connection to any Vitess-reporting server rather than letting its full scans silently truncate under the OLTP workload.

Cross-engine type translation covers the common surfaces (PG `UUID`/`INET`/`MACADDR`/`ARRAY` ↔ MySQL equivalents, `TINYINT(1)` ↔ `BOOLEAN`, `ENUM`/`SET`, PostGIS geometry with SRID, generated-column and `CHECK` idioms — see [translator-catalog](translator-catalog.md)); anything it cannot translate refuses loudly, with `--type-override` and `--expr-override` as the per-column escape hatches.

### Which engines can be a target

Most of the fourteen are source-only. These are the engine names `--target-driver` accepts for a `migrate` or a `sync` cold-start copy:

`mariadb`, `mysql`, `planetscale`, `vitess`, `postgres`, `postgres-trigger`, `sqlite`. Every other registered engine — `d1`, `d1-trigger`, `sqlite-trigger`, `csv`, `tsv`, `ndjson`, `mydumper` — refuses `OpenSchemaWriter`/`OpenRowWriter` and cannot be selected as a target at all.

### Adjacent surfaces

Encrypted logical backups with restore: `backup full`, restore, and point-in-time chain replay work on every engine that migrates — the restore side reads the stored chain and never touches the source. **Creating** the incremental side of a chain needs a **CDC-capable source**: `backup incremental` and the continuous `backup stream` producer capture the changes since the parent, and capturing changes is what CDC is, so both refuse a CDC-less source at validate. That is the engine set below (the CDC table's rows with a mechanism). Since v0.157.0 a change chunk records each change's apply identity (an optional `aid` field, with an `apply_identity` flag on the manifest; the backup `FormatVersion` is unchanged and v0.156.12 still reads such a chain), which is what lets `sync from-backup` replay a chain exactly-once (ADR-0191; scope under *Known limitations*). The broker's own position token changed with it (`backup-broker-v2`): v0.156.12 refuses it, so a broker cannot be downgraded in place — the CHANGELOG's v0.157.0 Compatibility section has the procedure. Since v0.159.1 an incremental segment whose window changed a primary-key or UNIQUE-key column's collation is stamped backup `FormatVersion` 13, so v0.159.0 and older refuse it at their version ceiling instead of restoring it with rows merged; a full, a segment with no schema change, and a collation change outside every key keep their earlier version and stay readable by older binaries. A VStream segment is never stamped this way (KEY-COLLATION-VSTREAM-UNSTAMPED, under F17 below), and a chain v0.159.0 already wrote across such a change carries no stamp — restore it with v0.159.0 or later. `sluice backup export-as-parquet` transcodes any backup chain into Parquet for DuckDB / warehouse ingestion ([ADR-0164](adr/adr-0164-backup-export-as-parquet.md)).

## CDC modes per source engine

Continuous sync (`sluice sync start`) needs a change stream from the source. Which transport sluice uses — and what the source must provide — depends on the engine:

| Source engine | CDC transport | Source requirements | Notes |
|---|---|---|---|
| `mysql` | Row-based binary log (binlog) | `binlog_format=ROW` — anything else (STATEMENT, MIXED) is **refused up front** with `SLUICE-E-CDC-BINLOG-FORMAT-NOT-ROW`, because a non-ROW stream is a fully silent empty-stream mode (verified on a real server before the gate shipped, v0.99.292). Full row images are required too — `binlog_row_image=MINIMAL`/`NOBLOB` (Azure MySQL's platform default is MINIMAL) refuses at CDC start with `SLUICE-E-CDC-ROW-IMAGE-PARTIAL`. **`binlog_row_metadata=FULL` is recommended** (`SET PERSIST binlog_row_metadata = 'FULL'`): since v0.158.0 a reader behind the head decodes each row by the shape it was recorded under, and under the default `MINIMAL` most schema changes of a streamed table between the reader and the head refuse instead ([cdc-streaming](operator/cdc-streaming.md#mysql-family-binlog-sources-decoding-rows-behind-the-head-deferred-schema-change-sluice-e-cdc-binlog-lookahead-short)). The CDC account needs `SHOW BINLOG EVENTS`, which `REPLICATION SLAVE` grants; without it the reader refuses with `SLUICE-E-CDC-REPLICATION-PERMISSION`. | GTID-based resume; covers RDS / CloudSQL / Azure / Percona — anything wire-compatible with upstream MySQL. |
| `mariadb` | Binlog with MariaDB domain GTIDs ([ADR-0170](adr/adr-0170-mariadb-flavor-phase3-cdc.md)) | Same ROW-format gate — note MIXED is MariaDB's *platform default*, so an untuned MariaDB source hits the refusal out of the box; the fix is one `SET GLOBAL binlog_format=ROW`. MariaDB's `binlog_row_metadata` defaults to `NO_LOG`; set it to `FULL` (`SET GLOBAL` plus `binlog_row_metadata = FULL` under `[mariadbd]` in the option file, since MariaDB has no `SET PERSIST`) for the same reason as MySQL. `SHOW BINLOG EVENTS` needs `BINLOG MONITOR` on 10.5+, which `REPLICATION CLIENT` includes. | Native `uuid`/`inet6`/`inet4` values carry faithfully on both bulk copy and the binlog tail ([ADR-0171](adr/adr-0171-mariadb-native-uuid-inet-cdc-decode.md)). |
| `planetscale` / `vitess` | Vitess VStream gRPC via vtgate | A vtgate endpoint; no binlog access needed. | VGTID positions, multi-shard, reshard-aware. A source-side throttle (typically a co-tenant OnlineDDL/MoveTables migration) can pause delivery — sluice WARNs on the throttle/idle signature and names `SHOW VITESS_THROTTLED_APPS`; latency only, never loss — unverified end to end, see the throttle entry under *Known limitations* ([vitess-vstream-troubleshooting](vitess-vstream-troubleshooting.md)). |
| `postgres` | Logical replication (pgoutput) | `wal_level=logical`, a role with `REPLICATION`, headroom for one replication slot per stream — preflighted with an inventory refusal (`SLUICE-E-CDC-REPLICATION-HEADROOM`) rather than a mid-run failure. | Per-stream publications with a scope-conflict guard (`SLUICE-E-CDC-PUBLICATION-SCOPE-CONFLICT`) so concurrent differently-scoped streams can't silently de-scope each other; `--where` row filters push down into the publication on PG 15+; pre-emptive slot-retention warnings; `sluice sync decommission` retires a finished stream's slot + its own publication (the shared default is never dropped) + control row. Prep guide: [postgres-source-prep](postgres-source-prep.md). |
| `postgres-trigger` | Trigger-based change log on the source | Plain DDL privileges — **no replication slot, no `REPLICATION` role, no `wal_level` change**. | The path for managed Postgres that blocks logical replication (e.g. Heroku). `trigger setup` installs, `trigger teardown` removes every trace. |
| `sqlite-trigger` / `d1-trigger` | Trigger-based change log | Write access to the file / D1 database. | Exactly-once resume via a change-log watermark. |
| `sqlite`, `d1`, `csv`, `tsv`, `ndjson`, `mydumper` | none | — | Migrate-only sources. |

## Known limitations

The honest list. Every entry is loud, off-default, or a schema-object (not value) gap — with **three known exceptions: the trigger-CDC REPLACE blind spot below**, which is silent at loss time and is therefore WARNed at setup time, **the open silent-value gaps listed in the next entry, and the GC-44 schema-change residuals marked *silent* further down, among them three HIGH ones under F17: KEY-COLLATION-BROKER-UNARMED (`sync from-backup` applied every incremental with the key-collation guard unarmed, through v0.160.0; fixed in the next release), KEY-COLLATION-TRIGGER-CDC-NO-HISTORY (the same gap for a `pgtrigger` source at apply and in its chain restore; open), and KEY-COLLATION-REVERTED-WINDOW-RESTORE (fixed in the next release for MySQL and MariaDB binlog sources — for chains that release writes; a `backup incremental` chain written by v0.159.1 or earlier recorded no evidence of a reverted window and still restores merged on every release, Bug 307 — open for VStream and for trigger-CDC, and for a Postgres source read after the revert or observed live with a row of the table before the change until v0.160.0, which fixes both (KEY-COLLATION-PG-LOOSENED-REPLAY, KEY-COLLATION-PG-SAME-ANCHOR); its loosened twin KEY-COLLATION-LOOSENED-WINDOW likewise, though the next release's restore armed only when a row of the table followed the loosening inside the window, Bug 306, fixed in v0.159.3)** — and each is stated with its exact trigger so you can check it against your workload. Items marked *queued* have fixes scheduled. (Until v0.156.2 this paragraph named only the first exception, while the second list below was already open in the audit backlog — a claim nobody was checking. Through v0.157.0 it named two, while the GC-44 entry already listed silent residuals.)

**Open silent-value gaps (filed in `docs/dev/audit-backlog.md`: (1)–(5) as GC-37, (6)–(8) under F-E1; each narrow).** (1) Since v0.156.4, a value with more scale than a MySQL-family `DECIMAL` column holds (for example more than 30 fractional digits into the `DECIMAL(65,30)` an unconstrained Postgres `numeric` maps to) **refuses** with `DECIMAL-SCALE-EXCEEDED` instead of being rounded. The Postgres-target sibling is still open: PG `numeric(p,s)` rounds an over-scale input without notice, so a value past a target column's scale lands rounded at exit 0. That is reachable only when the target column is narrower than the source's (a `--type-override` or a hand-made target table). (2) A MySQL-source expression DEFAULT containing `'` or `\` is re-emitted as-is, and MySQL re-parses a stored expression default under the `sql_mode` of whichever session next opens the table, so a `NO_BACKSLASH_ESCAPES` session reads a backslash differently (`MYSQL-EXPRESSION-DEFAULT-BACKSLASH`). (3) `mydumper` dumps: a MariaDB dump taken under a utf8 results charset already holds `?` for binary-default bytes ≥ `0x80`, and a MySQL dump holds `????` for a character beyond the BMP inside an expression — neither is recoverable from the dump. (4) A SQLite-dialect DEFAULT that has no MySQL spelling is dropped (with a WARN) rather than refused on a forwarded `ADD COLUMN`. (5) Since v0.156.3 the MySQL-family change streams convert a non-UTF-8 column by the charset it was written in (`CHARSET-NOT-DECODABLE` refuses what cannot be converted faithfully), but on a source that records no written charset — MariaDB with its default `binlog_row_metadata=NO_LOG`, and PlanetScale/Vitess (VStream) — a few narrow windows around a column charset change toward a non-UTF-8 charset stay silent: a `sync` restart between the replayed rows and the `ALTER`, an implicit `MODIFY` that takes the table default, an online schema change (gh-ost, pt-osc, a PlanetScale deploy request) swapping in a shadow table, and a backup window that decodes replayed rows after an earlier window already recorded the change. For a utf8mb4 → non-UTF-8 change these are silent where v0.156.2 was exact. Details and the full list: [migrating-legacy-mysql](operator/migrating-legacy-mysql.md); on MariaDB, `binlog_row_metadata=MINIMAL` records charsets for events written after it is set. (6) Since v0.156.11 sluice keeps an `AUTO_INCREMENT` value of `0` on every MySQL-family target by forcing `NO_AUTO_VALUE_ON_ZERO` into the session (`NO-AUTO-VALUE-ON-ZERO-UNSET` refuses a server that will not take it), but on a **sharded** Vitess/PlanetScale keyspace whose column is filled by a vtgate sequence, vtgate itself replaces an explicit `0` with a sequence value whatever the session mode (measured on vttestserver: the `0` landed as `1000`; `VTGATE-SEQUENCE-ZERO`, unmeasured on hosted PlanetScale). (7) Sharded targets that enforce a key only within a shard — a multi-shard vtgate keyspace, and a multi-shard PlanetScale Neki database — have two filed, **unmeasured** candidates: a re-delivered insert that does not carry the routing column can land a second copy on another shard through the steady-state upsert (CDC apply, the idempotent cold copy; F-E1-SHARDED-ROUTING), and the cold copy's plain-INSERT retry treats a duplicate-key error as proof a whole batch landed, which a `transaction_mode=MULTI` batch committed on one shard but not another breaks (VTGATE-MULTI-1062-PREMISE; reachable by `restore` into a pre-created vindexed keyspace). The broker and restore doors and the copy retry gate already require every primary-vindex column to be supplied on a multi-shard vtgate keyspace; the Neki probe has no shard-key rule yet. (8) A target table you pre-create keyed only on a column the rows do not carry (an `AUTO_INCREMENT`/`bigserial`/identity surrogate, a defaulted key) can still take a re-written row twice inside one `restore` run where the run re-carries rows by design — a resumed full's re-streamed tables, a compacted chain's overlap, restore's reparent reconcile (filed HIGH candidate, unmeasured; the rotation case is refused since v0.157.0, below) — and a pre-created unique key coarser than the source's (a prefix index, a case-insensitive collation) merges distinct source rows on first apply (measured, LOW). Tables sluice creates carry the source's key and are unaffected by (8). If any of these matches your schema, check the affected columns against the source after the copy.

**`sync`: a forwarded `ADD COLUMN` is backfilled from the source, and the stream waits for it (v0.156.1+).** After the `ALTER` lands, sluice reads the new column's value for every pre-existing row from the source (the key and the added columns only, in primary-key pages) and writes it to the target, because the target's own fill is not what the source holds whenever the DEFAULT was dropped or changed afterwards (Django's `AddField`) or was non-constant. The cost is one pass over the table plus one `UPDATE` per row — pipelined on a Postgres target, **one round trip per row on a MySQL/MariaDB/PlanetScale target** (perf gap 36) — and every later change waits behind it. A table without a primary key refuses. `--no-backfill-added-column` opts out and leaves the target's fill with a WARN. **An interrupted backfill does not resume:** a stop, crash, kill or error before it is confirmed on the target ends the stream with `ADD-COLUMN-BACKFILL-INCOMPLETE`, recorded like `UNFORWARDED-SCHEMA-CHANGE` below, and its repair is different — copy the added column's values from the source for the rows that predate the `ADD COLUMN` (or re-copy), then acknowledge. Full detail: [operator/cdc-streaming](operator/cdc-streaming.md).

**`sync`: exactly-once across a crash mid source transaction has a stated scope (ADR-0190, v0.156.5+).** By default it covers the serial apply paths and the lane barrier (keyless tables and primary-key changes). On the default concurrent lanes, a table with a secondary UNIQUE index is covered only with `sync start --exactly-once-lanes`. On a workload made of such transactions it runs at 0.86–0.97× the throughput of `--apply-concurrency 1` on the measured pairs (MySQL → Postgres at 0 and 5 ms, Postgres → Postgres, MySQL → MySQL; about half before v0.156.8), which is still 97–99% below the default lanes ([`benchmarks/fencebench`](../benchmarks/fencebench/README.md), [ADR-0190 §D.9](adr/adr-0190-exactly-once-apply-marks.md)). Without it, a crash in the middle of such a transaction can stop every restart on a loud unique-key collision. On a Vitess/PlanetScale target with its control tables in a sidecar keyspace (`--control-keyspace`, or auto-detected on a sharded target), vtgate commits the keyspaces separately. sluice commits the rows before the marks and position, so a torn commit re-delivers the transaction rather than skipping it: the marked classes there are at-least-once or loud, never a silent skip. A tear between two data shards is not covered by that ordering. Since v0.156.12 a lane barrier commits once instead of twice (its checkpoint is folded into the barrier's own target transaction, ADR-0190 amendment E) with the same delivery guarantees; a MySQL-family `Truncate` keeps two commits because MySQL commits around DDL. Details: [operator/cdc-streaming](operator/cdc-streaming.md).

**Backup replay of keyless tables, and chains older binaries wrote, refuse rather than duplicate (loud; v0.156.11–v0.157.1).** A table with no `PRIMARY KEY` and no `NOT NULL UNIQUE` index — or a target table keyed only on a column the backup's rows do not carry — cannot absorb a row written twice, so the paths that re-write rows now judge it first, before anything is applied:
- `sync from-backup` replays an incremental exactly-once since v0.157.0 when the chain records apply identities (written by v0.157.0 or later, and not rewritten by `backup compact --smart-compaction`, which drops them) and the target's apply marks can cover the table. Otherwise an incremental touching such a table refuses with `SLUICE-E-BROKER-KEYLESS-TABLE` (exit 3), naming the reason: no identities, a change without one (`BROKER-KEYLESS-NO-IDENTITY`), or a target whose marks cannot cover it (a PlanetScale Neki target, SQLite, or a target keyed only on an unsupplied column). A broker upgraded from v0.156.12 or older refuses the one incremental the old run may have been inside (`BROKER-CLASSIC-RESUME`); `--reset-target-data` is always a remedy. A keyed table replayed from a chain without identities converges by key, except a key value moved onto another row inside an interrupted source transaction (`BROKER-INCREMENTAL-PARTIAL` says to recover such a source with `--reset-target-data`).
- `restore` refuses a keyless in-scope table that already holds rows (`SLUICE-E-RESTORE-KEYLESS-TABLE-NOT-EMPTY`), and a **rotated** chain (`backup stream run --retain-rotate-at…`) whose later segment full carries rows for a keyless table (`SLUICE-E-BACKUP-ROTATED-KEYLESS-TABLE`; `backup verify` reports it too). The rows are in the chain, but this release cannot restore those tables from it: `--exclude-table` them and carry them another way (restoring them is filed as BUG297-REAL-FIX). `backup stream run` with rotation refuses to start a new chain on such a source; on an existing chain it WARNs `ROTATION-KEYLESS-TABLE` and suspends rotation, so the open segment grows until the table has a key.
- A chain a `backup stream` on v0.19.0–v0.156.11 wrote while being stopped or signalled inside a source transaction is refused before anything is applied (`SLUICE-E-BACKUP-CHAIN-SEVERED-TRANSACTION`, or `SLUICE-E-BACKUP-INCOMPLETE` for the cancel-drain shape), by chain restore, `sync from-backup` and `backup verify`; there is no override, and the remedy is a new full backup. Since v0.156.12 a window ends only at a transaction boundary, so a SIGTERM/SIGINT inside a transaction exits 0 without committing that window (`BACKUP-WINDOW-ABANDONED-OPEN-TRANSACTION`) and the next run reads it again; stop with `sluice backup stream stop` first. This release refuses an affected chain but cannot tell whether a target an earlier release restored from it already holds the harm — compare such targets with their source.

Recovery details: [recipe-broker-replay](cookbook/recipe-broker-replay.md) and [operator/error-codes](operator/error-codes.md).

**Sharded Vitess/PlanetScale targets that are already vindexed need every vindex column in the primary key (loud).** vtgate refuses a write that assigns a vindex column. With every vindex column inside the primary key, inserts, updates and deletes apply on every apply path (since GC-41 (e) the per-change UPDATE leaves an unchanged key column out of its `SET` list). A table vindexed on a column outside its primary key, or with no primary key, has no write sluice can send: a sync cold start refuses it up front with `SLUICE-E-TARGET-SHARD-KEY-NOT-IN-UPSERT-KEY`, and a warm restart stops at the first refused write with `SHARDED-TARGET-VINDEX-UPDATE`. A change that moves a row's vindex value is refused the same way, as are two narrow all-key shapes. Scope: [managed-services](managed-services.md).

**MySQL-family binlog readers behind the head decoded earlier rows by the table's current definition (silent through v0.157.2; fixed in v0.158.0, Bug 301).** Every `backup incremental` window, every `backup stream` start, a warm-resumed or lagging `sync start` and the CDC phase after a cold copy read the table's column list from `information_schema` as of now, while decoding events recorded earlier. A change that kept the column count and each column's type family decoded at exit 0 with values under the wrong column names. That covers a reorder of two same-type columns, a column-name swap, a drop-and-add of the same type, and an `ENUM` label reorder, which mapped each earlier row's index to the other label. A change issued from a different default database mis-decoded even at the head. The silent mis-decode existed since v0.1.0. From v0.113.0 changes across type families or column counts refused loudly with `SLUICE-E-CDC-SCHEMA-REPLAY-MISMATCH`, but same-family changes stayed silent. Since v0.158.0 each row is decoded by the shape it was recorded under or refused; `binlog_row_metadata=FULL` is the setting that lets sluice decode across schema changes rather than refuse them ([cdc-streaming](operator/cdc-streaming.md#mysql-family-binlog-sources-decoding-rows-behind-the-head-deferred-schema-change-sluice-e-cdc-binlog-lookahead-short)). **Checking an existing chain or target: sluice cannot.** `backup verify` (both depths) and restore read an internally consistent chain. `sluice verify --depth=sample` rarely reaches the rows written before the change. If an affected release captured a table across one of those changes, rebuild the chain from a new `backup full` and re-snapshot the target.

**MariaDB sources at the default `binlog_row_metadata=NO_LOG` streamed large UNSIGNED integers as negative numbers (silent, v0.99.271–v0.157.2; fixed in v0.158.0, MARIADB-NOLOG-UNSIGNED).** Under `NO_LOG` the binlog does not record signedness, and the decoder read such integers as signed. Every lane that reads a MariaDB binlog was affected: `sync start`'s CDC phase, `backup incremental`, `backup stream`, and `sync from-backup` applying those chains. A `TINYINT`/`SMALLINT`/`MEDIUMINT`/`INT`/`BIGINT UNSIGNED` value above the signed maximum arrived negative, at exit 0. An UPDATE or DELETE keyed by such a value matched no target row and was lost. MySQL 8.0/8.4, MariaDB under `MINIMAL` or `FULL`, PlanetScale/Vitess, every cold copy and `migrate`, and `DECIMAL`/`FLOAT`/`DOUBLE`/`YEAR`/`BIT` columns were not affected. **Checking a Postgres target:** `SELECT count(*) FROM t WHERE col < 0` per column the source declares `UNSIGNED`; a negative value proves the defect, but a lost update or delete leaves no trace on the target alone. `sluice verify` cannot clear it: across engines it compares row counts, and `backup verify` reads the chain as written. Re-snapshot an affected target (`sync start --restart-from-scratch`) and rebuild an affected chain from a new `backup full`. On an affected release, `SET GLOBAL binlog_row_metadata = 'MINIMAL'` (plus the option file) fixes binlog written afterwards, not binlog already written.

**A column RENAME swap on the source left the target's existing rows under the wrong column names (silent through v0.157.2; fixed in v0.158.0, RENAME-SWAP-FORWARD).** `RENAME COLUMN b TO c, RENAME COLUMN c TO b` on a source `sync start` was following reached the target as no change, so every pre-swap row the source never touched again disagreed with it in both columns. Rotations, a swap with a retype, and a swap of two differently typed columns behaved the same way. This affected every release of `sync start`, `--inject-shard-column` since v0.73.0, and chain restore and `sync from-backup` in every release that replays a schema delta. A boundary that changes a table's column order now refuses with `COLUMN-ORDER-CHANGED` until the target's own order has moved to the source's; chain restore, `backup verify` and `sync from-backup` refuse such a delta with `SLUICE-E-BACKUP-SCHEMA-DELTA-UNSUPPORTED`. **The cost:** a plain MySQL/MariaDB column reorder, a no-op since v0.99.45, now stops the stream until the target is reordered too, or, on a Postgres target, re-copied; an existing chain that recorded a reorder cannot be restored past it. **Checking a target:** `sluice verify --depth=sample` from v0.158.1 or later compares columns by name, so a swapped target mismatches on every sampled row that predates the swap; v0.158.0 and older hashed each side's columns in its own declared order and read a swapped target as clean (VERIFY-SAMPLE-COLUMN-ORDER). A sample still samples: if the pre-swap rows are a small fraction of the table, raise `--sample-rows-per-table`, or compare the affected columns' values by primary key between source and target yourself. Re-copy the table where they differ ([schema-change-runbook](schema-change-runbook.md)).

**A MySQL-family schema change that left a column name holding a different column left the target's rows under the wrong column (silent through v0.158.1; fixed in v0.159.0, RENAME-SWAP-INVISIBLE).** A MySQL column has no stable id, so an `ALTER` sequence whose names and order end where they started was invisible to every by-name comparison: `DROP COLUMN c, ADD COLUMN c` of the same type, `RENAME COLUMN c TO tmp, ADD COLUMN c`, `DROP COLUMN b, RENAME COLUMN c TO b`, and a rename swap followed by a `MODIFY … AFTER` restoring the order. The target kept every existing row's old values under the reused name, at exit 0, under `binlog_row_metadata` MINIMAL and FULL alike — FULL is no mitigation, because consecutive table maps name the same columns before and after. Since v0.159.0 the binlog reader reads the `ALTER TABLE` text itself and refuses `COLUMN-IDENTITY-CHANGED` at the DDL event and again at the table's next row; every restart repeats it, and the fleet supervisor does not restart such a leg. A statement it cannot parse that names an in-scope table and spells `DROP`, `CHANGE` or `RENAME` refuses as `COLUMN-IDENTITY-UNREAD`. It reaches `sync start` (live and warm), `backup incremental`, `backup stream` and the broker. The remedy is a re-copy (`sluice sync start --reset-target-data --yes` with the stream's other flags unchanged, or a fresh `backup full`). Not covered: VStream sources; a Postgres `DROP b, RENAME c TO b` met at the first boundary after a cold start or a restart; a pure permutation, then a persisted position and a restart, then a `MODIFY … AFTER`; table identity (`RENAME TABLE` swaps, `DROP` + `CREATE`); and a source with case-insensitive table names whose `ALTER` spells the table in another case, which the DDL-time refusal judges out of scope (RENAME-SWAP-F1-LCTN, unmeasured). **Checking a target:** as for the RENAME swap above — compare the affected columns by primary key against the source, and re-copy where they differ.

**`sluice verify --depth sample` compared columns by position and could not tell some values apart (silent false clean through v0.158.0; fixed in v0.158.1, VERIFY-SAMPLE-COLUMN-ORDER).** Each side hashed its columns in its own declared order, so a target holding the source's values under swapped column names read clean, and a target that only declared the same columns in another order mismatched on every row. The row rendering also collapsed values: NULL and an empty string hashed alike on both engines, a value containing the `|` separator could borrow its neighbour's, and on MySQL a `GEOMETRY`, `BIT`, `BINARY`, `VARBINARY` or `BLOB` value whose bytes are not valid UTF-8 — nearly any real geometry — rendered as an empty string (the utf8mb4 cast returns NULL for it), so any two such values hashed alike; and on MySQL and MariaDB a `FLOAT` rendered at 6 significant digits, so 1234567 and 1234568 hashed alike. On Postgres, `--strict-hash` failed on any table with a `bytea` column and read a backslash escape such as `\101` as the character it encodes, and endpoints whose `DateStyle` defaults differed (`SQL, MDY` against `SQL, DMY`) read a day/month-swapped `DATE` as clean. Now the source's column names fix one order both sides read by name, a source column the target lacks is reported as `COLUMN-MISMATCH` (JSON `status: column-mismatch`), each value is hashed from its exact text (a `FLOAT` through `DOUBLE`, binary data from its bytes), and Postgres pins the session settings that change a value's text. **A clean sample from v0.158.0 or older does not clear any of these;** re-run `verify --depth sample` with v0.158.1 or later. Since v0.158.1 a MySQL 8 `JSON` value past `max_allowed_packet`, which the server renders as an empty string, refuses its table naming the row rather than hashing alike (since v0.159.0 the refusal names the larger-`max_allowed_packet` remedy), and since v0.159.0 a failing run's closing line counts each kind of drift it found (`column-mismatch`, `sample-mismatch`, …) rather than calling every one a row-count mismatch.

**Two or more columns changing type or nullability in one `ALTER` were forwarded as no change (silent on a Postgres target, v0.99.45–v0.157.2; fixed in v0.158.0).** The classifier forwards one column's change per boundary and read two as none. A Postgres target kept the old type and rounded every later value at exit 0 (`numeric(10,2)` kept for two columns widened to `numeric(12,4)`: `1.2345` landed as `1.23`). A MySQL target refused the first value that did not fit. The forward path was affected from v0.99.45, and `--inject-shard-column` since v0.73.0. Such an `ALTER` now refuses, naming every column, including two same-family widens. **Checking a target:** compare the target's column types with the source's for any table altered this way while a stream ran, and re-copy a table whose values were rounded.

**Postgres sources whose tables are idle: through v0.156.7 the slot did not follow the server's WAL (fixed in v0.156.8; GC-41 (j)).** On Postgres 15 and later, a stream whose own tables saw no writes never advanced its slot, however much WAL the server wrote elsewhere: `pgoutput` skips a transaction that touches no published table — the `--source-heartbeat-interval` heartbeat's included, since its table is outside the publication — so no position was decoded and the slot retained WAL until the next user-table change (measured: 5.69 MB after 135 s at ~40 KB/s of other WAL, PG 15 and PG 16, Postgres and MySQL targets). Postgres 14 and earlier advanced only when something wrote in the stream's own database, which the heartbeat does. Since the fix, while no source transaction of the stream is in flight the reader persists the walsender's read position as a boundary, so the slot follows the server's WAL on every version, apply path and target with or without the heartbeat (measured: it passed the WAL position read when the stream went idle within 10–21 s, on PG 14 and PG 16). A server that goes fully quiet still keeps the WAL written since its last activity — `restart_lsn` advances only at a running-transactions record — but no more. On v0.156.7 and earlier, run the heartbeat on Postgres 14 and size `max_slot_wal_keep_size` for the longest idle period you expect on 15+.

**`migrate --resume` after a run that failed on another table: v0.99.29–v0.156.7 could skip a table that was only partly copied (silent; fixed in v0.156.8, GC-41 (i)).** With table parallelism of 2 or more (the default is 4) and without `--upfront-indexes`, a failure on one table cancelled its peers' copies, and a peer's cut-short copy could still be recorded complete with its indexes built: the overlapped index phase wrote the table's progress on the run's live context. A later `migrate --resume` then skipped that table and exited 0 with only the rows it had copied (Postgres targets from v0.99.29, MySQL targets from v0.99.30). Exposure needs all three: a failed `migrate`, a peer table copied whole-table rather than in primary-key ranges, and a `--resume` of that run. A whole-run Ctrl-C, `--upfront-indexes` and `sync start` were not exposed. Since the fix a table counts as copied only when its source read reached a natural end while the run was live and the writer consumed everything it was handed. If you resumed such a run on an older binary, check it with `sluice verify --depth count` against the source.

**Postgres targets with a `DEFERRABLE` primary key: v0.103.1–v0.156.7 could delete or overwrite a row the source never touched (silent; fixed in v0.156.8, GC-42).** sluice carries a Postgres source's `DEFERRABLE` primary key since v0.103.1. When the change's before-image is narrowed to that key (a source table under `REPLICA IDENTITY FULL`, or `postgres-trigger --capture-payload minimal`), a source transaction that moves key values through each other (`UPDATE t SET id = id + 1`, a swap) can leave two target rows sharing a key mid-transaction. A `DELETE … WHERE id = 2` then deleted both, and the commit-time re-check passed on the final, unique state. Since v0.104.0 such a table also needs an immediate `NOT NULL UNIQUE` index on the target, or `SLUICE-E-TARGET-DEFERRABLE-KEY` refuses it; the same loss applies on any release to a target table that does not hold the key unique. Since the fix, a key-scoped `UPDATE` or `DELETE` that matches more than one target row rolls back and stops the stream with `SLUICE-E-CDC-KEY-MATCHED-MULTIPLE-ROWS`. Every restart repeats it, and `sluice sync run` does not restart that leg. The remedy is a re-copy (`sync start --reset-target-data`). If the application shifts keys, make the source key immediate, or the stop will recur. To check a stream that ran on an older binary, use `sluice verify --depth sample` against the source: a deleted row shows in the count, but an overwritten one only in the sample.

**MySQL-family catalog text that cannot be recovered faithfully refuses (v0.156.1–v0.156.2).** MySQL's and MariaDB's catalogs lose characters in ways sluice now recovers — a literal DEFAULT or an expression (DEFAULT, generated column, CHECK, functional index) holding non-ASCII text — but three shapes refuse the schema read, naming the object, rather than being guessed: an expression literal in a charset other than utf8/latin1/binary, a latin1 byte in 0x80–0x9F, or a non-ASCII literal with no introducer. And a CDC row whose `ENUM`/`SET` value uses a label holding a character beyond the BMP stops the stream with `ENUM-LABEL-NOT-RECOVERABLE` unless the binlog source runs `binlog_row_metadata=FULL` (VStream always refuses): MySQL's catalog stores such a label as `?`, and before v0.156.1 CDC landed `?b` at exit 0. See [type-mapping](type-mapping.md) and [migrating-legacy-mysql](operator/migrating-legacy-mysql.md).

**Trigger-CDC (`sqlite-trigger`/`d1-trigger`): OR-REPLACE implicit deletes across a non-PK UNIQUE conflict are not captured.** With SQLite's default `PRAGMA recursive_triggers=OFF` — a per-connection setting of *your application's* writing connections, which sluice cannot set for them — the row an `INSERT OR REPLACE`/`UPDATE OR REPLACE` implicitly deletes to satisfy a **non-PK UNIQUE** conflict fires no DELETE trigger: the delete is never captured and the target keeps the row, at exit 0. A PK-conflict REPLACE converges (the captured insert upserts the same key); a `UNIQUE ... ON CONFLICT REPLACE` clause gives even a plain INSERT the same blind spot. Since v0.122.0 `trigger setup` WARNs per affected table, and the SQLite behaviour itself is premise-pinned in both directions. Remedies: run every writing connection with `recursive_triggers=ON`, or write upserts as `INSERT ... ON CONFLICT DO UPDATE` (never implicitly deletes; on D1 prefer this — whether the pragma is settable through D1's bindings is unmeasured). pgtrigger and the log-based CDC engines are exempt (their capture sees the delete regardless). Details: [ADR-0135](adr/adr-0135-sqlite-trigger-cdc.md).

**PostGIS Z/M-dimensional columns toward MySQL refuse at preflight (v0.124.0).** MySQL 8 supports no Z/M geometry; a `geometry(POINTZ, …)` or Z/M-flagged `geography` column toward a MySQL-family target now refuses at the shared pre-DDL chokepoint (migrate, restore, chain restore), naming the dimension and the mid-run error 1416 the refusal prevents — previously it passed every preflight and the copy died mid-run on the raw 1416. Remedies: `ST_Force2D` the column on the source if losing the extra dimension is acceptable, `--exclude-table`, or `--type-override`. Plain 2D geometry and geography stay supportable.

**`postgres-trigger` sources with PostGIS columns: `trigger setup` refuses (v0.124.0).** The trigger capture renders a spatial value as GeoJSON, which the apply path cannot decode — before v0.124.0 setup and cold copy succeeded and the FIRST spatial DML wedged the stream mid-incident. Setup now refuses spatial columns up front (refusal reason `postgis-spatial-column`; detected at every wrapping — direct column, array element, DOMAIN over geometry, DOMAIN over a geometry array). Remedies: the native `postgres` engine where logical replication is available (it carries spatial values as EWKB faithfully), or `--exclude-table`. Existing installs: a setup re-run now refuses; an already-running stream's failure mode is unchanged-loud until then. An ST_AsEWKB capture that would carry spatial columns is the recorded, demand-gated alternative.

**MySQL XA (distributed) transactions on replicated tables refuse loudly mid-stream (`SLUICE-E-CDC-XA-UNSUPPORTED`).** sluice applies CDC rows at read time, but an XA body's rows are invisible on the source until a later `XA COMMIT` — applying them would fabricate rows on the target if the coordinator rolls back, and mid-body positions are not valid restart points. XA traffic touching only non-replicated tables streams past unaffected, so a filtered sync sharing a server with an XA-using application keeps working. PostgreSQL two-phase (`PREPARE TRANSACTION`) has no equivalent exposure: sluice's slots never opt into two-phase decoding, so PG delivers prepared transactions only at `COMMIT PREPARED`, as ordinary transactions. Remedy: keep XA off the replicated tables or exclude them; faithful XA replication (buffering prepared transactions) is demand-gated.

**Secondary/index-only DDL is not forwarded mid-sync (all CDC sources).** An `ALTER TABLE … ADD INDEX` executed on the source *during* continuous sync does not cross to the target — no CDC wire protocol carries secondary-index metadata, so sluice never sees the delta. Data is unaffected, and the cold-start copy carries all source indexes; only indexes added *after* the copy are missed, and today there is no WARN when it happens. Workaround: add the index on the target out-of-band (`CREATE INDEX CONCURRENTLY` on PG; a deploy request on PlanetScale). Design exists ([ADR-0103](adr/adr-0103-forward-index-ddl-during-cdc.md)); building per-source detection is demand-gated.

**Constraint, row-level-security, policy and `DEFAULT` changes made on the source mid-sync are not forwarded — the stream refuses (`UNFORWARDED-SCHEMA-CHANGE`; Postgres and MySQL/MariaDB binlog sources).** Neither change stream describes these objects, so they cannot be carried to the target. On Postgres that covers `ADD`/`DROP CONSTRAINT` (primary key, `UNIQUE`, foreign key, `EXCLUDE`, `CHECK`), `ENABLE`/`FORCE ROW LEVEL SECURITY`, `CREATE`/`ALTER`/`DROP POLICY`, `SET`/`DROP NOT NULL`, `SET`/`DROP DEFAULT` and identity changes. On MySQL and MariaDB it covers primary key, `UNIQUE`, foreign key and `CHECK` (including `NOT ENFORCED`) changes, plus `DEFAULT`/`EXTRA`/generation-expression changes on an existing column. Through v0.155.1 these were ignored silently, which left the target weaker than the source (for a policy, a security boundary). Since v0.156.0, `sync` and `backup stream` stop at the first change on the affected table after such a DDL and name the change. The refusal is recorded: on the target's `sluice_cdc_state` row for `sync`, in `stream_state.json` for `backup stream`. So any restart refuses again instead of taking a fresh baseline that already contains the change, whether it comes from you, systemd `Restart=on-failure`, a pod restart or the fleet supervisor. The fleet supervisor does not restart such a leg at all. The replayed refusal prints a fingerprint. To continue, apply the same change to the target yourself (for `backup stream`, take a new full backup instead), then start once with the same `--stream-id` and `--accept-unforwarded-schema-change=<fingerprint>`. The acknowledgement clears only the refusal whose fingerprint it names, so a flag left in a service definition cannot accept a later, different one. **The acknowledgement takes a fresh comparison baseline, so passing it without applying the change accepts the difference permanently.** The refusal has no error code and exits 1, not 3. If the record cannot be written, sluice logs an ERROR saying a restart will not refuse again. A control table that lacks the new `unforwarded_refusal` column when sluice cannot add it (a non-owner Postgres role, a PlanetScale safe-migrations branch) fails the start instead, before any change stream opens. A downgrade to an older binary ignores a recorded refusal. An automatic retry after a transient error keeps the baseline it had, so a dropped connection between the DDL and the next write still refuses. Other limits: a change made while the stream was stopped, or during the cold-start copy, is part of the baseline and is not detected; detection needs a later write to the same table; and plain (non-constraint) indexes are not compared (see the index-DDL entry above). Column changes that sluice forwards (ADD/DROP/ALTER COLUMN, per ADR-0091) are unaffected, including a constraint that disappears because its column was dropped. One MySQL-only false refusal: `DROP COLUMN b` shrinks a composite `UNIQUE (a, b)` to `UNIQUE (a)` on MySQL, and sluice refuses that because the reader cannot tell whether the target shrank it the same way. PlanetScale/Vitess (VStream) sources are not covered yet; their stream does carry DDL events, so the same door is buildable there.

**`sync`: a column change the target cannot hold stops the stream — two codeless refusals, `RESUME-SCHEMA-DIVERGENCE` and `SCHEMA-CHANGE-REFUSED` (v0.156.10+).** Each table's first schema boundary after a stream starts (a warm resume, a restart, a fleet leg restart, an automatic retry) is compared with the target table itself, column names and types. A stream that forwards schema changes applies what it can (an added column, with the backfill; one column widened within its family), keeps a target column that is already wider with a WARN, and otherwise stops with `RESUME-SCHEMA-DIVERGENCE`. A stream that forwards no DDL (`--schema-changes=refuse`, a multi-database stream, `--inject-shard-column` with `--no-coordinate-live-ddl`) compares every boundary with the target the same way and stops with `SCHEMA-CHANGE-REFUSED` when the target cannot hold what the source now sends. Through v0.156.9 a type widen within a family (`DATETIME` → `DATETIME(6)`, `numeric(10,2)` → `numeric(10,4)`) made while a stream was stopped, or made at any time on a stream of the second kind, left the target column narrow, and every following value was rounded into it at exit 0. Both refusals exit 1 with no error code and record nothing: every start compares again, so every restart repeats them, and the fleet supervisor does not restart such a leg. To recover, apply the change to the target table by the drained model, then start again with the same `--stream-id`; there is no acknowledgement flag — except for a `SCHEMA-CHANGE-REFUSED` that also says `AMBIGUOUS-SCHEMA-BOUNDARY` (a Postgres source, where a replayed transaction and a change made while stopped look the same): compare the source's current table definition with the target's first; a match is consistent with a replay but does not prove one (a column narrowed and widened back, or dropped and added again, while the stream was stopped matches too), so only if nobody ran DDL on the table while the stream was stopped change nothing and start once with the `--accept-unforwarded-schema-change` fingerprint it prints (bound to the position the stream resumed from) — otherwise re-copy the table. An `ADD COLUMN` you run on the target is not backfilled by a stream that forwards nothing. Stated residuals: at a forwarding stream's first boundary a `--type-override` column is compared by presence only; a table the target cannot witness (not held, or no storage-shape rendering for the engine pair) with no earlier shape passes its first boundary with a WARN; and a narrowing made while the stream was stopped is WARNed, not applied. Details: [cdc-streaming](operator/cdc-streaming.md).

**Open schema-change residuals from the GC-44 work (`docs/dev/audit-backlog.md`).** Six are silent — F23, F22, F16, F19, F20 and F17 (KEY-COLLATION-FIRST-BOUNDARY), the first five narrow, and all but F19 and F17 a change made while the stream was stopped; F17 is fixed except for named residuals, three of them HIGH and silent: KEY-COLLATION-BROKER-UNARMED and KEY-COLLATION-TRIGGER-CDC-NO-HISTORY (both below), and KEY-COLLATION-REVERTED-WINDOW-RESTORE ( a backup window that changes a key's collation and changes it back; fixed in the next release for MySQL and MariaDB binlog sources for the chains it writes, not for a `backup incremental` chain written by v0.159.1 or earlier, which recorded no evidence of the window (Bug 307), open for VStream and for trigger-CDC, and for a Postgres source read after the revert or observed live with a row of the table before the change until v0.160.0, which fixes both (KEY-COLLATION-PG-LOOSENED-REPLAY, KEY-COLLATION-PG-SAME-ANCHOR); its loosened twin KEY-COLLATION-LOOSENED-WINDOW likewise); the rest are loud or recover by a re-copy, except F8 and half of F12, which are unmeasured. (Through v0.157.0 this entry said two were silent and left F15–F21 and F27 out, although the backlog had them open.) **F23** (Postgres source, MEDIUM, silent): Postgres schema history is anchored at LSN 0/0 and keeps one shape per table, so on a stream that forwards schema changes a column the source NARROWED while the stream was stopped is kept at the target's wider type with a WARN, and the target keeps the values the source's ALTER rounded; on a stream that forwards no DDL the same case refuses as `AMBIGUOUS-SCHEMA-BOUNDARY` instead. If a stopped Postgres stream's source may have narrowed a column, re-copy the table. **F22** (MEDIUM, silent, narrow; Postgres and VStream sources only since v0.159.0): a column dropped and re-added with the same name and type while the stream was stopped matches the target and passes, and the target keeps the old values. On a MySQL/MariaDB binlog source the same change now refuses `COLUMN-IDENTITY-CHANGED` when the resume replays its `ALTER` from the binlog, which a warm resume and a `backup incremental` always do (a binlog purged past it means a re-copy instead), except where `lower_case_table_names` lets the `ALTER` spell the table in another case (RENAME-SWAP-F1-LCTN). **F2** (MySQL binlog, MEDIUM): a schema boundary inside a source transaction that then fails can leave the table's only history row anchored past the persisted position, and the next resume drops and re-copies every target table (ADR-0093). **F6** (Postgres → MySQL, MEDIUM, loud): a forwarded `ALTER COLUMN TYPE` emits `MODIFY COLUMN` as `NOT NULL` with no DEFAULT, so it fails on a column holding NULLs and drops the column's DEFAULT. **F7** (Postgres → MySQL, LOW, loud): a `timetz` value carrying an offset is refused by the MySQL `TIME` column at apply. **F8** (unmeasured): a DDL made while an interrupted cold copy was stopped is not compared, because the resumed cold start seeds from the post-DDL source. **F9** (MariaDB → MySQL, MEDIUM, loud): an `INT UNSIGNED` value above 2³¹−1 is refused by the MySQL target at CDC apply, though the cold copy carries it. **F10** (Postgres source, MEDIUM, loud): a PostGIS `geography` column stops the stream at the table's first relation message. **F11** (MySQL-family binlog, MEDIUM, loud): `--type-override` from `TINYINT(1)` to `smallint` copies, then the change stream still decodes the column as a boolean and refuses at the first changed row. **F12** (MySQL/MariaDB binlog): every start writes one schema-history row per touched table, which nothing compacts (LOW, growth), and that first-touch row is anchored at the stream start with the post-DDL shape when a DDL follows later in the replayed range (MEDIUM, consumer impact unmeasured). **F24** (Postgres source, MEDIUM, loud): on a stream that forwards no DDL, a transaction that writes a table, changes a column's type (or drops or renames it) and writes it again is refused by the reader on every restart, the drained model notwithstanding (`PRE-ALTER-REPLAY-WEDGE`); a type widening on a stream over a single database and schema without `--inject-shard-column` passes with one start under `--schema-changes=forward`, anything else (F26: a forward start cannot pass a DROP or RENAME) needs `sluice slot drop` plus `--restart-from-scratch` — under `--inject-shard-column`, after deleting that shard's rows from the target. **F25** (LOW, loud): a `char(n)[]` source column against a `text[]` target refuses every start (padding); `varchar(n)[]` against `text[]` passes. **F16** (MEDIUM, silent, narrow): a geometry SRID is compared only where both sides declare a positive one, so an SRID change made while a Postgres-source stream was stopped (or to or from a MySQL column with no declared SRID) is not seen, and new rows are labelled with the target's SRID. **F19** (Postgres source, MEDIUM, silent, measured): a `char(n)` → `varchar`/`text` change forwarded live inside a transaction that also wrote the table before the `ALTER` can land those earlier rows with their blank padding (`'updated '` where the source holds `'updated'`). **F20** (Postgres source, MEDIUM, silent, narrow): `interval(p)` precision is not modelled, so an `interval(6)` → `interval(0)` made while the stream was stopped is not seen (mid-stream it refuses). **F17** (KEY-COLLATION-FIRST-BOUNDARY, HIGH, silent, measured 2026-10-11; fixed in v0.159.0 and v0.159.1 except for the residuals named at its end): the comparison ignored charset and collation, so a key column's collation or character-set change (`_ci` → `_bin`, PAD SPACE → NO PAD, `utf8mb4` → `ascii_bin`) met as the first schema boundary of a run, or on a `--schema-changes=refuse` stream, left the target's key comparing under the old collation, and rows the source keeps apart merged at exit 0; a `backup incremental` chain restore merged the same way. On a MySQL-family source the change is now judged against the source's own earlier shape and forwarded (or, under `refuse` or with no earlier shape on record, refused with `KEY-COLLATION-CHANGED`), and chain restore applies the collation change before the window's rows. A Postgres source (whose change stream carries no collation, and which merged on every entry, the live one included) now has its collation read from the catalog at every Relation, and both appliers refuse an upsert that would merge two rows the source's current collation keeps apart (`KEY-COLLATION-MERGE`). A VStream source carries no collation on the wire and stays uncovered: after changing a key column's collation there, apply the same change on the target before any row distinct only under the new collation is written, or re-copy the table. Also uncovered: at CDC apply, a Postgres-source primary key on the database default collation, or on a nondeterministic collation (an ICU case- or accent-insensitive key, which the MySQL emitter cannot declare), landing on a MySQL-family target (the copy phase checks both; at apply, deliberately: arming it would refuse a re-delivered case-only change that converges today; a UNIQUE key beside a primary key on that pairing is checked — for a nondeterministic key only since v0.159.1, compared byte for byte; v0.159.0's guard left it unarmed, so 'e' and 'é' under a level-2 ICU key merged at exit 0); a Postgres key whose collation was tightened and loosened back while the stream lagged, with a row inserted and deleted in between (the reader reads the collation in force now; review F-D, KEY-COLLATION-PG-LOOSENED-REPLAY, regraded HIGH after a measured restore lost a primary-key row at exit 0; wider than filed, since a live sync merged too when the change and its rows shared one transaction; fixed in v0.160.0, where the reader marks a collation read from a catalog row newer than the rows, or written by their own transaction, as not established and both appliers compare that key byte for byte, so the merge refuses `KEY-COLLATION-MERGE`); a SQLite or D1 source key, whose reader records no collation, on the copy phase's idempotent writer (unmeasured); and, restoring a Postgres-source backup chain written before v0.159.0 (whose manifests record no collation determinism) into a MySQL-family target, a key on the database default collation, which such a manifest cannot tell from a source that records no collation at all (a key with a named collation is checked since v0.159.1, compared byte for byte in every key including the primary key — before, every Postgres key of such a chain went unchecked on that restore; the cost, if that named collation was in fact nondeterministic, is that a re-applied case-only change of such a primary key refuses `KEY-COLLATION-MERGE` loudly where it would have converged). And **KEY-COLLATION-REVERTED-WINDOW-RESTORE (HIGH, silent, open on v0.159.1):** a backup window that changes a key column's collation and changes it back before it ends restores merged even on the current release, at `restore` exit 0: chain restore arms the guard from the window's last recorded shape, which equals the target's, so the rows written under the intermediate collation replay unchecked — for a live `backup stream` window (stamped `FormatVersion` 13, so older binaries refuse it, but this one restores it wrongly) and for a `backup incremental` run made after the revert under MySQL's default `binlog_row_metadata=MINIMAL`, which records only the current shape and stays unstamped (measured on MySQL 8.0; a sync stream resumed across such a window is plausibly exposed too, unmeasured). If a key column's collation was changed and changed back inside a backup window, re-copy the table rather than restoring it. Fixed in the next release for MySQL and MariaDB binlog sources: chain restore guards each row under the version recorded at its position (refusing `KEY-COLLATION-MERGE`), `sync from-backup` refuses such a window (`KEY-COLLATION-HISTORY-UNORDERED`), and a `backup incremental` or resumed `sync start` that reads it after the revert reports each row under the collation its binlog event recorded, which also closes the resumed-sync exposure (measured silent on v0.159.1's code). Its twin **KEY-COLLATION-LOOSENED-WINDOW** (HIGH, silent, open on v0.159.1, measured): a key LOOSENED inside a window (`_bin` → `_ci` after `'A'` beside `'a'` moved apart) restored, broker-replayed and warm-resumed merged, because the window's delta loosens the target before its rows; fixed in the same release the same way, the restore arming the guard from the window's start shape — but only when a row of the table followed the loosening inside the window: with none, v0.159.2 filed the start shape under no namespace where the rows' lookup names the database, and restored merged at exit 0 (Bug 306, HIGH, fixed in v0.159.3). The next release's fix of the reverted window also reaches only chains that record it: a `backup incremental` chain written by v0.159.1 or earlier recorded only the reverted shape, so every release restores it merged (Bug 307); check such restores against the source and take a fresh full backup. VStream stays uncovered for both, its events carrying no collation. Still open for the trigger-CDC sources, which record no schema versions; for a Postgres source read after the revert (review F-D below, measured HIGH: a primary-key row lost at exit 0) open until v0.160.0, which fixes it (KEY-COLLATION-PG-LOOSENED-REPLAY). **KEY-COLLATION-PG-SAME-ANCHOR** (HIGH, silent, fixed in v0.160.0, measured 2026-10-13): a `backup stream` window over a Postgres source that observes a key column's collation changed and changed back live can still restore merged at exit 0 (measured in 1 of 3 runs, when the reader keeps up) if a row of the table was written before the change in the same window: every Postgres schema version is anchored at LSN 0/0 and the capture keeps one per table and anchor, so the window records only the shape its first Relation carried and the restore arms nothing for the rows written under the intermediate collation. If a Postgres key column's collation was changed inside a backup window, re-copy the table rather than restoring it. v0.160.0 refuses such a window at capture (`KEY-COLLATION-SAME-ANCHOR`, measured 12 of 12 runs), and with it a forward-only key collation change in a window that already holds a row of the table, which restored correctly before; for both, take a fresh full backup after the change. A chain written before v0.160.0 keeps no evidence of the dropped shape, so its restore cannot refuse. **KEY-COLLATION-BROKER-UNARMED** (HIGH, silent, measured 2026-10-15, fixed in the next release): `sync from-backup` applied every incremental with the guard unarmed, in steady state and not only across a collation change, because its replay carries no schema version for the guard to arm from. On the pairings the guard covers, a source row that differs from an existing one only by case therefore merged into it at exit 0, where live `sync start` refuses (measured: a Postgres UNIQUE key beside the primary key, replayed onto MySQL). The next release arms it from each incremental's recorded schema; check targets a broker fed on such a pairing with `sluice verify`. **KEY-COLLATION-TRIGGER-CDC-NO-HISTORY** (HIGH, silent when reached, by code-reading): a `pgtrigger` source records no schema version either, so its live sync into a MySQL-family target and its chain restore apply with the guard unarmed in steady state, and the same merge is open there. Two more open backup residuals: **KEY-COLLATION-DRAIN-NO-DELTA** (MEDIUM, loud) — a `backup stream` window drained by a stop that changed a key's collation commits no schema delta, so on every restore its rows meet the old key and refuse `KEY-COLLATION-MERGE` at that segment (a correct chain this release cannot restore past; the same lag affects any DDL in a drained window); and **KEY-COLLATION-VSTREAM-UNSTAMPED** (silent on a downgrade only) — a VStream segment is never stamped 13, because VStream records no collation, so a pre-v0.159.1 binary can restore a VStream window that changed a key's collation with rows merged, and this binary's guard is unarmed for it as well (the VStream residual above). The copy phase itself is guarded since v0.159.1 (KEY-COLLATION-ROWWRITER): the idempotent row writer on both engines (chunked and resumed copies, `--force-cold-start`, `add-table`, the VStream copy serial and fanned out, restore of a rotated chain) refuses the same merge with `KEY-COLLATION-MERGE`, arming a Postgres default-collation key inside the primary key too; on a table whose key is compared differently on the two sides, MySQL's plain batched core re-sends a retried batch that meets a duplicate key as the guarded upsert (a genuine lost-ack replay converges, a real merge refuses), and LOAD DATA, which has no upsert form, refuses a replayed segment that skipped rows with `KEY-COLLATION-REPLAY-AMBIGUOUS` — before v0.159.1 both cores accepted the retry's duplicate key as their own rows and dropped the merged row at exit 0. The cost is loud: a resumed copy over a live source can re-send a row whose key has since changed and refuse rather than converge (re-copy that table from scratch). Since v0.159.1 the guard also compares a MySQL-family prefix key (`UNIQUE KEY uk (k(5))`) on the prefix the server matches, where v0.159.0 compared whole values and let 'Apple-1' overwrite 'apple-2'. A MySQL 8 source into MariaDB is compared under the NO PAD `uca1400` collations, so MariaDB's UCA 14.0.0 weights stand in for MySQL's UCA 9.0.0 ones; since v0.159.1 the cold start also creates every such character column under them (`utf8mb4_uca1400_nopad_ai_ci` and its `as_ci`/`as_cs` siblings, where earlier releases created the PAD SPACE `utf8mb4_uca1400_ai_ci`), so a source holding `'a'` and `'a '` copies and a `KEY-COLLATION-MERGE` re-copy with `--restart-from-scratch` converges; a target an older sluice created keeps its PAD SPACE columns, which the guard still covers. Still open and unmeasured on the guard: a functional key part (`UNIQUE ((lower(k)), x)`), a Postgres unique index declaring its own `COLLATE` over a column of another, a pre-created MySQL key column whose name differs from the source's only in case, and (fixed in the next release) a mydumper column declared with `COLLATE` alone, or inheriting a MariaDB table's collation, created under the target's default collation (MYDUMPER-COLLATION-NO-CHARSET); and a MySQL 8 → MariaDB `migrate` re-run, or a sync cold start that meets tables sluice already created, can falsely refuse `SLUICE-E-TARGET-TABLE-SHAPE-MISMATCH` on a remapped collation (loud, by code-reading). **F15** (MEDIUM, loud): a MySQL `TEXT` → `MEDIUMTEXT` (or BLOB/BINARY size) change forwarded live and then replayed refuses on every start, because those sizes have no width order. **F18** (MEDIUM, loud on a strict MySQL target): a MySQL `DECIMAL UNSIGNED` is read as signed, so a cross-engine target accepts negatives the source refuses. **F21** (observability): a key-scoped `UPDATE`/`DELETE` that matches no target row is logged at DEBUG only. **F27** (LOW, loud): a `sync run` leg on the F24 wedge is restarted with backoff and refuses identically each time, because that refusal is not in the supervisor's do-not-restart roster. Two more were filed with v0.158.0's binlog work. **DEFERRED-KEY-COLLATION** (MySQL-family binlog under `binlog_row_metadata=FULL`) was fixed in v0.159.0: the binlog does record a character column's collation, as an ID, and a collation change folded behind a later retype of the same column now refuses `DEFERRED-SCHEMA-CHANGE` before its rows land; before the fix such rows merged on a key and the boundary refused after them. **CONTROL-READ-BADCONN** (LOW, loud): a `driver: bad connection` on a setup-phase control-table read is still treated as terminal, so it ends the run instead of being retried in-process.

**User-defined triggers and event triggers are not carried (any path, including PG→PG).** The IR has no trigger model; the PG reader never reads `pg_trigger`/`pg_event_trigger`, so triggers are silently absent on the target after migrate, backup-restore, and sync. This deserves a specific callout: **an event trigger installed as a guard against accidental `DROP`/`TRUNCATE` vanishes silently too** — a guard whose whole job is safety should not be assumed to have crossed. Workaround: script trigger re-creation into your cutover runbook (`pg_dump --section=post-data` extracts them). Same-engine carry is a designed-but-not-built follow-up (roadmap item 50).

**Other Postgres object classes outside the IR are not carried either, silently (any path, including PG→PG).** `RULE`s, `GRANT`s/ACLs and `ALTER DEFAULT PRIVILEGES`, object ownership, extended statistics (`CREATE STATISTICS`), `SECURITY LABEL`s, text-search configurations, tablespaces, and per-table storage parameters (`reloptions` such as `fillfactor`). The PG schema reader never reads the catalogs that hold them — `pg_rewrite`, `relacl`, `pg_default_acl`, `relowner`, `pg_statistic_ext`, `pg_seclabel`, `pg_ts_config`, `pg_tablespace`, `reloptions` have zero references under `internal/engines/postgres` — so none of them appears on the target and nothing WARNs; `sluice schema diff` does not see these classes either. Losing `GRANT`s is the most common post-migration Postgres incident (the application role connects and gets `permission denied`). Workaround: `pg_dump --schema-only` with its defaults (owners and privileges included) and apply the `GRANT` / `ALTER … OWNER TO` / `CREATE RULE` / `CREATE STATISTICS` statements to the target in your cutover runbook.

**MySQL object classes outside the IR are not carried, silently.** Triggers, stored procedures and functions, scheduled events, and table partitioning (`PARTITION BY`) are never read — `internal/engines/mysql` runs no `information_schema.triggers` / `routines` / `events` / `partitions` query; every table is emitted `ENGINE=InnoDB` whatever its source storage engine; a `CHECK … NOT ENFORCED` lands ENFORCED, because the reader does not select the `ENFORCED` flag (rows the source admitted can then refuse at copy — loud, but a surprise); and a view's `DEFINER`, `SQL SECURITY` and `CHECK OPTION` are dropped (only the `SELECT` body round-trips). Workaround: `mysqldump --no-data --routines --events --triggers` on the source and apply the objects you need after the copy; for partitioning, pre-create the partitioned table on the target (a fresh `migrate` recognises a pre-existing table whose column shape matches, ADR-0166).

**Relaxed `sql_mode`: silent coercion WARNs on every write path.** If you opt into `--mysql-sql-mode=''` on a MySQL-family *target*, out-of-range or over-long values are coerced by the server (300→127, `'toolong'`→`'too'`) instead of refused. Every write path detects this via the server's warning list and emits a loud one-time-per-table WARN — the three bulk-copy paths since v0.99.28, and the steady-state CDC apply path (serial, coalesced-batch, and concurrent lanes) since the v0.100.0 line. Not reachable on the default path — strict mode (the default) refuses these loudly. Remedy: keep strict `sql_mode`, or `--type-override` the column to a type that fits. See [migrating-legacy-mysql](operator/migrating-legacy-mysql.md).

**Postgres schema reads need PostgreSQL 12 or newer.** The schema reader references PG-12 catalog columns (`pg_collation.collisdeterministic`, `pg_attribute.attgenerated`) unconditionally, so `migrate`, `sync`, `backup`, `schema preview` and `schema diff` against a PG 10/11 source fail at the column read with SQLSTATE 42703 rather than degrading; the CDC lane's own floor (pgoutput, PG 10) is lower and does not help — nothing runs before the schema read. `cutover` is documented at 12–18 above for the same reason.

**`GENERATED ALWAYS AS IDENTITY` lands as `BY DEFAULT` on every path except `migrate` — with a loud WARN.** The Postgres writer creates every identity column `GENERATED BY DEFAULT AS IDENTITY` so the bulk copy can land the source's ids (an ALWAYS column refuses an explicit value with SQLSTATE 428C9). `migrate` restores `ALWAYS` after the copy and constraints (`IDENTITY-ALWAYS-RESTORED`) **on the tables it created itself** — a table that already existed on the target (the `schema preview` → apply-yourself flow) is never altered and stays `BY DEFAULT` — and carries the identity sequence's options (`START` / `INCREMENT` / `MINVALUE` / `MAXVALUE` / `CACHE` / `CYCLE`) exactly, in either direction (a descending identity is primed from `MIN`, not `MAX`, after the copy). **`sync` cold start, `restore` and chain restore keep `BY DEFAULT`** — each hands the target to a change applier that writes explicit ids (CDC rows, incremental links, a `sync` resumed from a restored position), which `ALWAYS` would refuse — as do a shard-consolidation or `--force-cold-start` migrate, which are not the last bulk load into the table. On those paths the target accepts application-supplied ids the source rejected; the writer says so once per run in a WARN marked `IDENTITY-ALWAYS-DOWNGRADED` naming every affected `table.column`. Remedy after the last explicit-id write: `ALTER TABLE … ALTER COLUMN … SET GENERATED ALWAYS` per named column. Toward MySQL and SQLite the axis and the options do not exist; the writer WARNs per column (`IDENTITY-OPTIONS-NOT-CARRIED`) and the column lands as a plain `AUTO_INCREMENT` / rowid alias.

**UNIQUE-constraint attributes land weaker — now with a loud WARN.** `DEFERRABLE`, PG-15 `UNIQUE NULLS NOT DISTINCT`, and PG-18 `WITHOUT OVERLAPS` constraints are created on the target in their default (weaker) form — a NULLS-NOT-DISTINCT source admits duplicate NULLs on the target going forward. Since the v0.100.0 line the PG schema reader detects all three and WARNs once per constraint at read time, naming the attribute and the weaker landing, on every path that reads the schema (migrate, sync, backup, preview/diff). Faithful same-engine carry is a filed follow-up, as is the sibling gap the fix uncovered (PG 15+ also allows NULLS NOT DISTINCT on a plain `CREATE UNIQUE INDEX`, which still lands weaker un-WARNed). Remedy: re-apply the attribute on the target after migrate and confirm with `sluice schema diff`. Re-adding `DEFERRABLE` to a Postgres target that `sync` still writes to is not a plain restoration: while the applier runs with `session_replication_role=replica` (an apply role allowed to set it), the deferred re-check does not run, so the constraint holds only what the source sends (logged once per table as `DEFERRED-KEY-CHECK-OFF-IN-REPLICA-MODE`). With a role that may not set it, the check runs, and a source transaction split across target transactions is refused at commit (`DEFERRED-KEY-CHECK-FAILED-AT-COMMIT`).

**Empty-but-drifted pre-existing target tables: one residual path.** The shape gate that refuses copying into a pre-existing target table whose schema drifted from what sluice would emit (`SLUICE-E-TARGET-TABLE-SHAPE-MISMATCH`) covers `migrate` (v0.99.258, [ADR-0166](adr/adr-0166-migrate-precreate-shape-gate.md)) and the single-database `sync` cold start (v0.99.292). The **multi-database (`--all-databases`) sync cold-start path still creates tables ungated** — filed. Workaround there: `--reset-target-data` for a clean re-create, or pre-verify with `sluice schema diff`.

**Five expression-translator rules stay deferred** (`GREATEST`/`LEAST`, `REGEXP_LIKE`, `FIND_IN_SET`, `CONVERT_TZ`, `INET_ATON`/`INET_NTOA`) — each has a semantic divergence that makes auto-rewrite a masking risk; each fails loudly and has an escape hatch: `--expr-override TABLE.COLUMN=EXPR` for generated columns, `--exclude-table` or a source-side rewrite for CHECK/DEFAULT sites (the override rewrites only generated-column bodies). Full per-rule analysis: [translator-catalog](translator-catalog.md).

**Cross-engine view bodies are emitted verbatim.** A view definition that doesn't parse on the target surfaces as a loud target-side rejection at apply time. There is no flag that supplies a translated body (an earlier version of this entry named a `--view-override` that was never built); the workarounds that exist are `--exclude-view <name>` (or `--skip-views` to leave every view to out-of-band tooling) and then creating the view on the target by hand, or rewriting the view body on the source into a form both engines parse. PG materialized views refresh via `sluice matview refresh` (PG-only).

**Multi-source MySQL fan-in has no per-table rename.** Aggregating N MySQL sources into one target database relies on DSN/database choice for namespacing; there is no `--rename-table SOURCE=TARGET` flag (PG multi-source uses `--target-schema`). Zero demand to date; tracked as roadmap item 9.

**No Arrow / columnar in-flight format.** The analytics exit is `backup export-as-parquet` (one Parquet file per table); Arrow as an IR row representation is deliberately deferred with zero current demand.

**PG 19 native sequence sync: the dedicated tests are not written yet (roadmap item 61).** sluice runs its own CDC and is unaffected by PG19's `FOR ALL SEQUENCES` publications; the weekly version matrix still runs `postgres:19beta1` as a non-blocking canary with the full PG suite (`scripts/pg-versions.txt`). The ~2026-09 GA date this entry used to wait on has passed and the pin has not been promoted to a GA `19`; whether PG 19 has reached GA is unverified here. `sluice cutover` is today's engine-neutral, any-version equivalent of PG19's sequence sync (works PG 12–18 and cross-engine). Two sequence-carry residuals, both loud-not-silent: a sequence whose `INCREMENT` exceeds the cutover margin can fail the prime with a raw PG bounds error, and mid-stream `ALTER SEQUENCE` option changes are recorded in backups but not re-applied on chain restore.

**Cloud KMS signing/wrapping is live-validated on all three providers.** AWS KMS runs as the `kmsverify` localstack leg of the weekly scheduled `extended-suites.yml` (not per-PR; the IAM access-denied case stays skipped because localstack community edition does not enforce IAM); GCP Cloud KMS and Azure Key Vault were live-validated against the real services on 2026-07-24 (sign/verify round-trips, tamper refusal, and — for Azure — the key-version-pinned rotate-then-restore-old-chain recovery). The GCP/Azure live runs are operator-dispatched rather than per-PR (no free local emulator). Failure modes throughout are loud, never silent.

**VStream throttle stalls are latency, not loss.** A Vitess-side throttle (most commonly a co-tenant online DDL on the same keyspace) pauses delivery with no error on the wire; sluice stays position-safe and converges on unthrottle, and WARNs on the throttle/idle signature. The WARN is unit-pinned; the latency-not-loss half rests on VStream resuming from its last delivered position and has no end-to-end throttled-stream test, so it is **unverified** at this stamp. Budget for it in cutover timing on busy shared keyspaces.

**`--force-cold-start` bypasses the populated-target preflight.** The default slot-loss recovery path refuses loudly on a populated target; the bypass flag's name announces what it does. Don't script it.

**PG large objects are not copied, and an `oid`/`lo` column is refused.** `pg_largeobject` contents live outside every user table, so sluice does not carry them — and the referencing `oid`/`lo` column is itself an unsupported column type, so a source with one in scope does not migrate: the census WARN fires first naming every suspect `table.column`, then the schema read refuses loudly (`postgres: unsupported data_type "oid"`), on both `migrate` and `sync start`. To proceed without the table, `--exclude-table` it; to carry the blobs, convert the columns to inline `bytea` on the source first (`ALTER TABLE t ALTER COLUMN c TYPE bytea USING lo_get(c)`) so the bytes copy like any other column, or export them separately (`lo_export` / `pg_dump --blobs`). Full detail: [type-mapping § Postgres large objects](type-mapping.md#postgres-large-objects-pg_largeobject--oid--lo).

**The Heroku migrator wrapper is Postgres-target only.** sluice's core supports Heroku PG → MySQL-family via `postgres-trigger` (integration-tested); the convenience wrapper hasn't grown the target switch. Drive the core commands directly for that direction.

Tag publishes additionally require a real-cluster filtered move-OUT gate.
- **The dump-parity oracle is the machine-checked version of this page's schema-fidelity claims:** sluice's PG→PG and MySQL→MySQL output is diffed against `pg_dump`/`mysqldump` on every PR, and every allowlisted divergence must cite the doc that declares it — "what do we knowingly not carry?" is a reviewable file, not tribal knowledge. It is narrower than its name where the not-carried classes above are concerned: the PG leg runs `pg_dump --schema-only --no-owner --no-privileges`, so ownership and ACL loss are invisible to it by construction; the MySQL leg runs `mysqldump --no-data` with mysqldump's defaults, which omit routines and events; and its allowlist records no divergence in triggers, rules, grants or extended statistics — those classes are unexercised by the oracle, not proven carried.

## Pre-production checklist

The suggested path from evaluation to a production cutover. Each step is cheap relative to discovering its failure mode mid-migration.

1. **Preview the schema translation:** `sluice schema preview` against your real source. Translator gaps, type-mapping decisions, and refusals are visible here, before anything runs. Diff a scratch target with `sluice schema diff`.
2. **Dry-run the migration:** `sluice migrate --dry-run` prints the full plan (tables, types, indexes, constraints, notices) without touching the target.
3. **Rehearse on a non-production target:** run the real `migrate`, then `sluice verify` (`--depth count`, then `--depth sample` for content-hash spot checks). Investigate any delta before going further. A clean `--depth sample` is not proof of every value: it compares a sample of rows (by column name, so a target whose columns were swapped by name mismatches — on v0.158.1 or later; v0.158.0 and older read it as clean), and a sample rarely reaches defects confined to a few rows (see *Known limitations*).
4. **Prep the source for CDC:** [postgres-source-prep](postgres-source-prep.md) (GUCs, slot lifecycle, failover survival) for PG sources; `binlog_format=ROW`, `binlog_row_image=FULL`, `binlog_row_metadata=FULL` (recommended, so a reader behind the head can decode across schema changes) + retention for MySQL/MariaDB, with an account holding `REPLICATION SLAVE, REPLICATION CLIENT` ([operator/cdc-streaming](operator/cdc-streaming.md)); [managed-services](managed-services.md) for provider-specific preconditions. The preflights will refuse loudly on what's missing, but reading first avoids the round-trips.
5. **Rehearse the sync:** `sync start` against the non-production target with `--metrics-listen` (scrape `/metrics`, gate on `/readyz` — see [running-as-a-service](operator/running-as-a-service.md)) and `--source-heartbeat-interval=30s` on quiet sources. Watch the slot-health warnings (automatic on PG sources) and `sluice sync health --max-stale-seconds N` as the cron-able freshness probe.
6. **Wire alerting before cutover, not after:** the `--notify-*` threshold rules page webhook/Slack/SMTP sinks on slot retention, sync lag, storage, and target vacuum health. Alert on `sluice_seconds_since_last_apply` and `sluice_sync_lag_seconds` at minimum.
7. **Know the failure surface:** every recognized refusal carries a stable `SLUICE-E-*` code with a remedy ([operator/error-codes](operator/error-codes.md) — the full table, CI-synced with the code); exit codes are contractual (0/1/2/3/80). First move on anything unexplained: `sluice diagnose --output bundle.zip` for a redacted, shareable state bundle.
8. **Cut over deliberately:** drain with `sync stop --wait`, prime sequences with `sluice cutover` (prevents PK collisions on the first post-cutover INSERT), verify once more, then move traffic.
9. **Decommission finished streams:** `sluice sync decommission` drops the stream's replication slot, per-stream publication, and control row. A leftover PG slot pins WAL on the source indefinitely and blocks later differently-scoped streams — this is the step multi-wave migrations forget ([operator/staged-wave-migration](operator/staged-wave-migration.md)).
