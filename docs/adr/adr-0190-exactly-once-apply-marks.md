## Context

A restart re-delivers every change after the persisted position, and every apply path relies on ADR-0010 to make that harmless: an UPSERT of a change onto a target that already holds it is a no-op. GC-38 (l) measured where that assumption breaks. When a crash leaves a **prefix** of a source transaction committed on the target, the restart replays the transaction from its first change onto rows that the transaction itself has already changed. Most shapes converge. Three do not, because the replayed change meets a uniqueness constraint that the transaction's own later changes have already moved:

- a transaction that frees a unique value and reuses it (`DELETE u='x'` … `INSERT u='x'`),
- a swap through a temporary (`a.u=tmp; b.u=a0; a.u=b0`),
- a primary-key change (`UPDATE k1 → k2`), whose replay finds `k1` gone and `k2` present.

The replayed change fails with `23505` / `Error 1062`. The persisted position never moved past the transaction, so **every** restart re-delivers the same prefix onto the same target and fails the same way. It is loud and never silent (the gate asserts the position never passes the transaction and no row outside it is damaged), but there is no configuration that avoids it and no recovery short of re-copying the table (`--restart-from-scratch`).

### What was measured (GC-38 (l), `TestStreamer_CrashMidTxn_*`)

Sources: MySQL 8.0 GTID, MySQL 8.0 file/pos, MariaDB 11.4. Targets: Postgres 16, MySQL 8.0. The kill is a cancel while a target row lock holds the applier mid-transaction; the gate asserts the persisted position did not move, so it is equivalent to a SIGKILL at that point.

| Apply path | Before the kill | After restart |
|---|---|---|
| per-change, serial (`--apply-batch-size 1`) | a prefix applied | stops on the collision, every restart |
| per-change, lanes | a prefix applied | same |
| lanes, batched — **the operator default** (`--apply-concurrency auto`) | a prefix applied (a lane flushes early at every PK-changing barrier and at its size cap) | same |
| serial batched, transaction fits one batch | nothing applied | converges exactly |
| serial batched, transaction larger than a batch | a prefix applied | same collision |

By code-reading, not measured: (1) the lane path's checkpoint is a separate write, so a crash after a transaction fully committed but before the next checkpoint replays the **whole** transaction onto its own end state — the same collision with no mid-transaction kill at all; (2) sluice's VStream reader discarded vtgate's BEGIN/COMMIT events, so no apply path had transaction cohesion on PlanetScale/Vitess (corrected 2026-09-29: an earlier wording of this sentence said VStream emits no transaction markers, which is false; phase 4 forwards them); (3) Postgres sources re-deliver whole transactions from the slot and share the same appliers.

### When rows commit and when the position is saved, per path

- **Serial batched** (`appliershared.runOneBatch`, `internal/appliershared/batch_loop.go:400`). Data and position are written in one target transaction (`commitBatch`, `:781`), but the batch flushes mid-source-transaction at the row cap (which the ADR-0052 controller can shrink far below the configured ceiling), the byte cap, a keyless row, and a 100 ms delivery gap. `CheckpointOnlyAtTxBoundary` (doc at `:120`, enforced at `:796`) then commits the data **without** the position, so a mid-transaction flush leaves a durable prefix with the position still before the transaction. Only a transaction that fits one batch gets ADR-0027 cohesion.
- **Per-change** (`postgres/change_applier.go:1354`, `mysql/change_applier.go:1090`). Each row commits in its own transaction with no position (`applyOneImpl(..., writePosition=false)`); the position is written separately at the `TxCommit` (`persistSourceTxCommit`, `postgres/change_applier.go:1437`, `mysql/change_applier.go:1330`). Every row of a transaction is a durable prefix point.
- **Lanes** (`internal/laneapply/laneapply.go`, the ADR-0104 relaxation documented at `:56`). Each lane commits its routed sub-batch in its own transaction (`ApplyLaneBatch`); the merged position is persisted by the coordinator in a **separate** transaction (`WriteCheckpoint`, `:172`) up to the contiguous frontier's last transaction boundary, every 2000 routed changes (`checkpointEveryChanges`, `:230`), every idle second (`checkpointIdlePeriod`, `:246`), and around each barrier (`barrier`, `:903`). A transaction's rows scatter across lanes and commit independently; the position can lag the data by up to a checkpoint interval but never lead it.
- **Barrier** (keyless rows, PK-changing updates, malformed rows, Truncate, SchemaSnapshot; `laneapply.go:903`). Applied alone on the coordinator in global order, position-free, followed by a checkpoint. A PK-changing update is therefore always its own committed prefix point.

The invariant that holds everywhere — *persisted position ≤ durably committed data* — is exactly what makes the prefix possible: the data can lead the position by a partial transaction on every path, and by whole transactions on the lane path.

## Decision

Record, **in the same target transaction as the rows**, a small per-key *apply mark* naming the last change of the current source transaction that reached that key. On a restart, compare each re-delivered change's identity against the mark for its key and **skip** it when the mark shows it was already applied. Marks are written only by the changes whose replay is not idempotent; the skip check consults them for every change.

The two pieces that make this correct are a **stable change identity** (§1) and the **per-key prefix property** the lane router already guarantees (§2). Everything else is bookkeeping.

### 1. Change identity: `(TxID, Seq)`, assigned by the reader

Every row change carries a new field `ApplyID{TxID string; Seq uint64}` (on `ir.Insert` / `ir.Update` / `ir.Delete`; `internal/ir/change.go:164` and siblings), assigned by the **reader** — never by the pipeline or the applier — so that pipeline-side filtering (`filterChanges`, `internal/pipeline/filter.go:205`), `--include-table` changes, and add-table scope changes cannot shift it. `TxID` identifies the source transaction; `Seq` orders the change within it **per table**: the index of this change among the transaction's changes to the same table, counted before any sluice-side filter. A per-table ordinal is chosen over a per-transaction one because it is unaffected by changes to *other* tables' scope (a publication that gains a table, an `--exclude-table` edit).

The identity is only useful if a re-delivery produces the **same** `(TxID, Seq)` for the same change. Per source:

| Source | `TxID` | Stable across re-delivery? |
|---|---|---|
| MySQL, GTID mode | the transaction's own GTID `uuid:n` — the reader already stages it (`stageGTID`, `mysql/cdc_reader.go:2169`) before the rows; note it is **not** the row's `Position` (rows carry the pre-transaction set, `positionFor`, `:2312`) | Yes by construction: a GTID names one transaction on every server that holds it, and a resume always restarts at a transaction boundary. `Seq` counts ROWS (not rows events), so a replica that re-encodes the same transaction into differently-split rows events yields the same ordinals — **UNVERIFIED PREMISE** (row-image identity across a failover); verified by a test that resumes the same transaction from a replica. |
| MariaDB, GTID | `domain-server-seqno` | Same argument; same premise. |
| MySQL, file/pos | `server_uuid` + binlog file + the transaction's `BEGIN` / GTID-event offset | Yes: the v0.137.2 `server_uuid` stamp already refuses a position on a different instance, and a resume restarts at a transaction boundary (`CheckpointOnlyAtTxBoundary`). |
| Postgres (pgoutput) | the transaction's `CommitLSN` (already every row's `Position`; `postgres/cdc_reader.go:1361`, `positionAt` `:1952`), plus the pinned system id and timeline | Yes: logical decoding re-emits a transaction's changes in WAL order; the timeline pin refuses a different history. `Seq` counts the transaction's changes to the table **within the publication**, so a publication row filter (`--where` on PG 15+) that changes between runs shifts it — bound by the drift check in §5. |
| PlanetScale / Vitess (VStream) | `keyspace/shard` + that shard's GTID **before** the transaction (the shard's component of `r.currentVgtid`, which the reader advances only on the trailing VGTID event, `mysql/cdc_vstream.go:1526`; the ROW event names its shard, `:1856`) | Yes for the per-shard component: a resume restarts each shard from its own GTID, so a shard transaction's pre-transaction component is the same on every delivery. The **merged** VGTID the rows carry today is NOT stable — shard interleaving can differ between deliveries — which is why `TxID` must be per shard. Requires a reader change: VStream currently drops `BEGIN`/`COMMIT` (`:1567`) and does not stamp the shard onto the IR. **UNVERIFIED PREMISE**: vtgate re-delivers a shard transaction's ROW events in the same order on resume; verified by `TestVStream_*` replaying a mid-transaction resume and comparing identities. |
| postgres-trigger, sqlite-trigger, d1-trigger | empty; `Seq` = the change-log id | Yes: the id is a persisted, unique, monotone column of the capture table (`laneapply.go`, `flushPendingBoundary` doc at `:785`). With an empty `TxID` the skip rule below degenerates to "skip if the mark's id ≥ this id". |

A new optional reader capability (`ir.ApplyIdentityProvider`) declares that a reader stamps `ApplyID`. A reader that does not — every reader before its phase lands — produces changes with a zero `ApplyID`, and the applier treats a zero identity as *never skippable* (today's behaviour exactly).

### 2. Why per-key marks, and which changes write them

The lane router guarantees that every change sharing a route lands on one lane in source order (`laneapply` package doc), so **for any single key, the changes applied before a crash are a prefix of that key's changes in the transaction** — on every path (serial is trivially in order; lanes by the router; the barrier by global ordering). That is the property a skip needs. A per-*table* high-water mark would need the same property for the whole table, which holds only for tables routed `RouteScopeTable` (`laneapply/router.go:61`) and not for PK-only tables spread across lanes. A per-*lane* mark would be cheaper, but it is valid only if the restart routes every change to the same lane — the lane count, the hash (which v0.156.4 changed), and the per-table scope probe can all differ after a restart, and a routing mismatch there would skip a change that was never applied: silent. Per-key marks are independent of routing, so they are the only one of the three that is safe across an upgrade or a changed `--apply-concurrency`.

**Which changes write marks.** Replay is idempotent for a primary-key-only table whose transaction changes no primary key, so marking every change would double the write volume for no benefit. A change writes a mark when it is one of:

1. a change to a table with any non-PK uniqueness constraint (the tables the router already scopes `RouteScopeTable` — the probe exists),
2. a primary-key-changing update (it marks **both** the before-key and the after-key),
3. a change to a keyless table (the key is the empty string, so the mark is per table; keyless tables are already barriered in global order, so a per-table mark is a prefix there too — this makes keyless CDC exactly-once across a crash, which ADR-0089 could not; scope: on a target whose commit is atomic — see the GC-41 (c) note under "Implementation status" (after the phase 4–5 review hardening) for a vtgate MULTI target with a `--control-keyspace` sidecar, where it is at-least-once).

**Every** change — marked class or not — consults the marks before it is applied. That is what closes the resurrection case: in `UPDATE k1 SET v=5; UPDATE k1→k2; UPDATE k2 SET v=7` fully applied and then replayed, the first update is on an idempotent PK-only path and writes no mark of its own, but the PK change marked `k1` at a higher `Seq`, so the replay skips it instead of re-inserting `k1`.

### 3. The mark table and the write protocol

A new control table, **`sluice_cdc_apply_marks`**, created by `ensureControlTable` (`postgres/control_table.go:81`, `mysql/control_table.go:289`) and added to `appliershared.ControlTableNames` so every schema reader excludes it:

| Column | Meaning |
|---|---|
| `stream_id` | the stream (a Shape A fan-in has one per shard stream, so shards never read each other's marks) |
| `table_name` | the target table, schema-qualified (multi-database routing marks the routed table) |
| `key_digest` | a digest of the target primary-key values, canonicalized the way `laneapply.WriteCanonicalKeyValue` already canonicalizes them (empty for a keyless table) |
| `tx_id` | `ApplyID.TxID` of the last applied change to this key |
| `seq` | `ApplyID.Seq` of that change |
| `change_digest` | a digest of that change (operation + key + after-image), the tripwire in §5 |
| `scope_digest` | the digest of the stream's row-filter and scope configuration at write time (§5) |

Primary key `(stream_id, table_name, key_digest)`; each write is an UPSERT, so the table holds one row per marked key, not one per change.

**Protocol.** On every apply path, a marked-class change's mark is written **inside the same target transaction** as the change's own row write:

- serial batched: inside `runOneBatch`'s batch transaction, coalesced to one UPSERT per key per batch (the last change wins);
- per-change: inside `applyOneImpl`'s transaction;
- lanes: inside `ApplyLaneBatch`'s transaction, coalesced per key per sub-batch;
- barrier: inside `ApplyBarrierChange`'s transaction.

Because the mark and the rows commit together, the target can never hold a row without its mark or a mark without its row. The mark does **not** need the position: `sluice_cdc_state` keeps its current semantics and cadence untouched. Moving the lane checkpoint into the lane transactions was considered and rejected — lanes commit independently, so no single lane transaction can own a merged position. The marks close the lane post-commit window instead: a fully-applied transaction replayed after a lost checkpoint finds every marked key already at its last `Seq` and skips the non-idempotent changes, while its idempotent changes re-apply harmlessly.

**The skip decision.** When `Apply` starts, the applier loads this stream's marks into memory (the table holds only keys touched by marked-class changes of transactions not yet garbage-collected, so it is small). For each delivered row change with a non-zero `ApplyID`, before dispatch: look up the marks for the change's keys (before-key and after-key for an update); if a mark has `tx_id == TxID` and `seq ≥ Seq`, skip the change. A skip counts toward neither `rows_applied` nor the skip ledger, and is logged at DEBUG with a per-run INFO total. The lookup is in memory; no per-change round trip.

**Garbage collection.** A mark is needed only while its transaction can be re-delivered, that is, until the persisted position passes the transaction's commit.

- Serial batched and per-change: the `TxCommit` position write deletes the marks whose `tx_id` is the committing transaction, in the same transaction as the position (`commitBatch` / `persistSourceTxCommit`).
- Lanes: the coordinator records the `TxID` of each transaction whose `TxCommit` it passes; `writeCheckpoint` (`laneapply.go:1227`) deletes the marks of every transaction at or below the boundary it persists, in the checkpoint's own transaction.
- After a crash, some marks can outlive their transaction (a checkpoint lost between the lane commit and the delete). They are harmless — a stale `tx_id` never equals the `TxID` of a change delivered after the persisted position (§5, identity uniqueness) — and are swept at the first checkpoint after a restart: any mark loaded at start whose transaction was not re-delivered before that checkpoint is stale and deleted.
- Trigger sources (empty `TxID`): delete marks with `seq` at or below the persisted change-log watermark.

| Path | Honours marks | Notes |
|---|---|---|
| `sync start` / `sync run`, serial batched | yes | Phase 1 |
| per-change (`--apply-batch-size 1`) | yes | Phase 1 |
| lanes / `auto:N`, including the barrier | yes | Phase 2 |
| fleet supervisor restarts | yes, by construction | the supervisor restarts the same stream; the applier loads the marks |
| Shape A fan-in (`--inject-shard-column`) | yes | marks are per `stream_id`; the injected shard column is part of the target key, so the digest covers it |
| multi-database routing | yes | `table_name` is the routed target table |
| sync cold start (bulk copy) | exempt | the copy is not a CDC replay; the cold start clears the stream's marks (§5) |
| `sync from-backup` broker | **out of scope, follow-up** | the broker replays chain records with their own identity (link, chunk, record ordinal), which is intrinsic and stable; the same mark table fits, but the broker is a separate phase with its own pins |
| chain restore | exempt | a restore applies a chain into a target it owns from the start and re-runs from the beginning on failure |
| `migrate` | exempt | no CDC |

### 5. Silent-loss analysis

The tenet decides this design: GC-38 (l) is loud today, and a skip that fires wrongly turns it into silent loss. The rule the implementation must hold is that **a mark lookup can only ever cause a skip of a change the target already holds; any doubt resolves to applying the change**, which is today's loud behaviour at worst.

| Failure mode | Why it cannot skip an unapplied change, or how it refuses |
|---|---|
| Mark written but the rows not | Impossible: the mark and the rows are one target transaction. |
| Rows written but the mark not | Impossible for the same reason; a marked-class change never commits without its mark. |
| Stale marks after `--restart-from-scratch`, `--reset-target-data`, a slot-loss re-snapshot, or any cold start | Every cold-start path deletes the stream's marks before its copy begins, in the same place it resets `sluice_cdc_state`. Pinned by a test that re-snapshots and asserts the marks table is empty for the stream. |
| Identity collision across unrelated transactions | `TxID` is unique per source transaction by construction for every source in §1 (a GTID, a server-pinned file/offset, a timeline-pinned CommitLSN, a per-shard GTID, a unique change-log id). A source that would reuse an identity (a rebuilt server, a new timeline) is already refused by the existing identity pins. |
| Ordinal drift (a re-delivery numbers the same change differently) | The **tripwire**: when a replayed change's `Seq` equals a mark's `seq`, the applier compares the change's digest with the mark's `change_digest`; a mismatch refuses loudly (`APPLY-MARK-MISMATCH`, terminal, naming the table, key and identities) instead of skipping. This is the independent expected value on the skip path. It also catches a reader bug that drops or reorders rows. |
| A changed `--where` row filter or scope between runs | `scope_digest` records the stream's row-filter and scope configuration at write time; a mark whose `scope_digest` differs from the current run's is never used to skip — the applier refuses loudly (the same drift class `rowFilterHashDriftAny` already guards, `internal/pipeline/streamer_publication_ratchet.go:220`). |
| Schema change mid-transaction (a changed primary key or key column type) | The key digest is computed from the target's current key columns. A changed key yields a different digest, so the lookup misses and the change applies — today's behaviour, never a skip. |
| Lane re-partitioning after an upgrade or a changed `--apply-concurrency` | Per-key marks do not depend on routing (§2), so a different lane layout neither invalidates nor misapplies them. |
| Clock drift | No clock is read anywhere in the protocol. |
| Upgrade with a transaction in flight | The in-flight transaction's prefix has no marks (written by the older binary), so its replay behaves exactly as today. |
| Downgrade to an older binary | An older binary does not know the table and replays as today: loud at worst, never silent. The table is inert to it. |
| A reader that does not stamp `ApplyID` | A zero identity is never skippable (§1). |
| Partial after-images (Postgres unchanged TOAST) | Marks do not change what a replayed change writes; they only suppress changes already applied. A partial image that is applied is applied exactly as today. |

**Independent expected value for the pins:** the source's own final table state (`SELECT … ORDER BY` key, or an md5 over it), compared against the target after the crash and restart, with the persisted position asserted not to have passed the transaction before the restart (the existing gate's contract).

### 6. Cost

- **Writes.** One extra UPSERT per distinct marked key per batch, and only for the marked classes of §2. A PK-only workload with no PK changes writes none. A table with a secondary UNIQUE index — already pinned to one lane by the router — writes roughly one mark per changed row, coalesced within a batch.
- **Deletes.** One `DELETE … WHERE stream_id = ? AND tx_id IN (…)` per position save or checkpoint, only when the committing transactions wrote marks.
- **Reads.** One `SELECT` of the stream's marks at `Apply` start. The skip check is in memory.
- **Growth.** Bounded by the marked keys of transactions not yet covered by a persisted position, which on the lane path is at most about one checkpoint interval (2000 changes) plus the in-flight transactions.
- **Migration for existing deployments.** `ensureControlTable` creates the table when absent, following the `unforwarded_refusal` pattern exactly (`ensureUnforwardedRefusalColumn`, `postgres/unforwarded_refusal_store.go:31`, `mysql/unforwarded_refusal_store.go:33`): detect first, because a DML-only role gets "must be owner" on an unconditional DDL even when the object exists; a `--schema-already-applied` run and a PlanetScale safe-migrations branch cannot create it, so the ADR proposes (open question 2) that sluice then logs a grep-stable WARN (`APPLY-MARKS-UNAVAILABLE`) and runs without marks — today's loud behaviour — rather than refusing to start.

### 7. Alternatives considered

- **(b) Net-effect replay of the first post-restart transaction** — delete every key it touches, then write each key's final image. Rejected. It converges from any prefix, but on a Postgres target whose sync role cannot bypass foreign keys the deletes fire `ON DELETE CASCADE` into rows the transaction never touched: silent loss, exactly the conversion the tenet forbids. It also needs complete after-images (Postgres omits unchanged TOAST), buffers a whole transaction in memory, and does not cover the lane post-commit window.
- **(c) One target transaction per source transaction, with the position** — true today of the serial batched path only while a transaction fits one batch. Rejected as the fix: making it hold for every transaction means never flushing mid-transaction, which bounds nothing for a large transaction (memory, lock time); it is impossible across lanes without giving up lane concurrency for every table with a secondary unique index; and it does nothing for VStream until that reader emits transaction boundaries. It remains a reasonable complement for small transactions and is not ruled out.
- **Per-table or per-lane marks** — cheaper, but correct only under table-scoped routing (per-table) or an identical lane layout on restart (per-lane). §2 explains why either can skip an unapplied change.

(a) is the only option that covers the mid-transaction crash, the lane post-commit window, every source including VStream, and every apply path, while keeping every uncertain case on the loud side.

### 8. Phased implementation and pins

1. **Identity.** `ApplyID` on the IR and `ir.ApplyIdentityProvider`; MySQL GTID and file/pos, MariaDB, and Postgres readers stamp it. Pins: for each reader, reopen the stream from the same transaction boundary twice and assert the delivered `(TxID, Seq)` sequences are identical, including from a replica for the GTID premise.
2. **Serial and per-change.** The mark table, its migration, the write in the serial batch and per-change transactions, the in-memory skip, the tripwire, the `scope_digest` check, the cold-start clear, and GC at the position save. Pins: flip `TestStreamer_CrashMidTxn_*`'s serial and per-change cells from "stops on every restart" to "converges exactly", graded against the source's own final state.
3. **Lanes and barrier.** Writes inside `ApplyLaneBatch` and `ApplyBarrierChange`, and GC at `writeCheckpoint`. Pins: the default-lane cells flip; a new post-commit/pre-checkpoint crash cell (kill after a transaction fully commits across lanes, before the checkpoint) converges; lane count changed between the crash and the restart converges.
4. **VStream.** Per-shard identity in the reader (stop dropping `BEGIN`/`COMMIT`, stamp the shard). Pins: the same mid-transaction and post-commit cells on vttestserver.
5. **Trigger sources.** Change-log-id identity. Pins: postgres-trigger mid-batch crash converges.
6. **Tripwire and drift pins, all phases.** A deliberately shifted ordinal refuses with `APPLY-MARK-MISMATCH`; a changed `--where` refuses; a re-snapshot clears marks; a zero identity never skips; a downgrade (marks present, older-binary behaviour simulated by disabling the skip) replays loudly. Mutation-run each branch in both directions.

The pin matrix is source (MySQL GTID, MySQL file/pos, MariaDB, Postgres, VStream, postgres-trigger) × target (Postgres, MySQL) × apply path (per-change, serial batched, lanes) × crash point (mid-transaction, post-commit before checkpoint).

**Out of scope:** the `sync from-backup` broker (a follow-up with chain-record identity), chain restore, keyless-table exactly-once beyond the crash-replay window (ADR-0089's other cases), and any change to the position's cadence or format.

## Amendments (2026-09-28, operator-approved)

Both were found while implementing phase 3, stopped on, and put to the operator; both are now part of the design and supersede §3 where they differ.

### Amendment A — a lane writes a transaction's marks only after a checkpoint-before-mark fence

**Why §3's lane protocol is unsound as written.** §2's per-key prefix property is stated for ONE transaction, and the skip rule trusts only a mark of the SAME transaction. The lane post-commit window can hold SEVERAL fully-applied transactions ahead of the persisted checkpoint, and a key's mark is overwritten by the LAST transaction that touched it. The counterexample, on a secondary-unique table (so both changes are marked, and both ride one table-scoped lane): `T1: UPDATE k` then `T2: DELETE k`, both committed by the lane with k's mark naming T2, and the process dies before any checkpoint passes T1. The restart re-delivers from before T1. T1's update finds k's mark naming T2 — which proves nothing about T1 — and re-applies; on a MySQL lane the update is an after-image upsert, so **k is re-created**. T2's delete then finds its own mark and is **skipped**. k survives on the target though the source deleted it, at exit 0. Before ADR-0190 the same replay re-applied T2 too and converged, so §3 as written turns a converging replay into silent divergence — exactly what §5's first sentence forbids.

**The fence.** Before the FIRST change of a source transaction that will write a mark reaches a lane, the coordinator drains every lane to that change's predecessor and persists the checkpoint (the barrier's own prefix), and only then clears the lanes to write that transaction's marks (`laneapply` `fenceApplyMarks`; the seam's `ApplyMarkTx` / `ApplyMarksFenced`; `applymarks.LaneFence`). The persisted position then sits at the transaction's start, so no earlier transaction can ever be re-delivered alongside its marks; the next transaction's fence drains this one and moves the position past it, deleting its marks in that checkpoint. A lane additionally writes only marks the fence admits — the coordinator decides at route time and the lane at apply time, from caches that could in principle have moved in between — and applies anything else unmarked (today's behaviour, never a skip). The barrier already had this shape, which is why it was sound from the start.

**Why A rather than B.** The alternative put to the operator — a cross-transaction rule, skipping when the mark's transaction has not yet been re-delivered on that key — converges without the drain, but is sound only if no mark is ever stale, and so needs its own staleness guard (a sentinel recording the position the marks were last consistent with). A keeps every argument in §5 as written, keeps the skip rule same-transaction, and is the smaller change.

**Cost.** One lane drain plus one position write per source transaction that sends a marked change (secondary-unique table, keyless or PK-changing — the last two already barrier) to a lane. None for a transaction touching only PK-only tables (the steady state the marked-classes decision protects), none on a stream whose reader stamps no identity (VStream, trigger sources), and none on the serial paths, which already write the position at every transaction commit. Such transactions are serialised at their boundaries, not per row.

### Amendment B — the restart sweep rests on an invariant, not on timing

§3 swept "any mark loaded at start whose transaction was not re-delivered before the first checkpoint". On the lane path that is unsafe: a crash in the post-commit window could leave marks of transactions AFTER the first re-delivered one that the first checkpoint had not reached. The implemented sweep instead retires EVERY loaded mark at the run's first transaction close (`applymarks` `sweepLocked`), which is correct because of this invariant: **marks only ever exist for the first transaction after the persisted position.** Proof sketch, per path: the serial per-change and serial batched paths write each transaction's marks in target transactions that precede, or are, the one writing that transaction's commit position, and that position write deletes them — so at any instant only the transaction in flight has marks — **provided nothing persists any other position inside a transaction**. As first written this premise was unstated and false on the serial batched path (a schema event persisted its own, earlier, position mid-transaction; see Finding 1 below); it now holds by `schemaEventAtBoundary`, and a violation is caught at runtime by `APPLY-MARK-UNTRUSTED`. The barrier and (by amendment A) the lanes write a transaction's marks only after a checkpoint has persisted the position at that transaction's start, and the next marked transaction's fence (or barrier, or the transaction's own commit checkpoint) persists a position past it and deletes its marks in the same transaction. So a restart's first re-delivered transaction is the only one any mark can name; once it closes, every loaded mark is either its own (now passed) or stale — left by a position that moved without this binary's bookkeeping: an older binary, a run with marks unavailable, an external write. A stale mark is harmless to the skip rule (a TxID never recurs, so it proves nothing about any re-delivered change) and the sweep keeps it from living forever. The crash gate asserts the invariant at every kill ("marks for at most one transaction"), and `stale_mark_swept` plants a stale mark on a key the replay applies (which must skip nothing) and one on a key nothing touches (which only the sweep can delete), and requires the restart to converge with no mark left.

### Finding 1 of the pre-land review (2026-09-28): amendment B's invariant was false on the serial batched path — fixed, and now checked at runtime

**The defect (CRITICAL, silent; reproduced on real containers by the reviewer).** A reader emits a table's `ir.SchemaSnapshot` lazily, at the table's first row after a DDL — inside whatever transaction T that row belongs to — and stamps it with the DDL's OWN position (MySQL: the DDL anchor, `pendingDDLAnchor`; Postgres: the RelationMessage's WAL start, `0/0`). The serial batched loop treated every schema event as a position boundary: the Postgres target committed it with `atBoundary=true`, the MySQL target applied it through `applyOne` (`writePosition=true`). So mid-T it persisted a position from BEFORE an earlier, fully-applied transaction T-1, while T's rows and marks were durable. The restart replayed T-1 first (its INSERT upserted, re-creating the row T deletes), then T's DELETE found its own mark and was SKIPPED: the row survived at exit 0 (MySQL GTID → Postgres position `…:1-17` → `…:1-16`; GTID → MySQL and PG → PG the same, PG to `0/0`). Amendment B's invariant — marks exist only for the first transaction after the persisted position — did not hold, because the position had moved *behind* the marks. Lanes (the frontier never records a SchemaSnapshot, Bug 158) and serial per-change (defers every in-transaction position to the TxCommit, CDCPOS-2) were unaffected.

**Fix (a): a schema event inside a source transaction never persists its own position** (`appliershared` `schemaEventAtBoundary`). Its data commits and the position stays at the last boundary — exactly a mid-transaction flush — and the transaction's TxCommit persists the next one. Outside a source transaction (a MySQL `TRUNCATE`, which implicit-commits; a marker-less source's snapshot) the event is a statement boundary and still persists. Every place that persists a schema event's position, by symbol:

| Path | Engine | Symbol | Inside a source transaction |
|---|---|---|---|
| serial per-change | MySQL, Postgres | `ChangeApplier.Apply` → `applyOneImpl(…, writePosition=false)` | no position (CDCPOS-2) — unchanged |
| serial batched, schema event first in a batch or mid-batch | MySQL (`TransactionalDDL=false`) | `RunBatchLoop` → `BatchConfig.ApplyOne` = `applySchemaEvent(…, schemaEventAtBoundary)` | **no position — FIXED** (was `applyOne`, `writePosition=true`) |
| serial batched, same two shapes | Postgres (`TransactionalDDL=true`) | `commitBatch(…, schemaEventAtBoundary, …)` | **no position — FIXED** (was `atBoundary=true`) |
| lanes, SchemaSnapshot | both | `Orchestrator.handle` (never recorded as a boundary) + barrier `ApplyBarrierChange` → `applyBarrierNoPosition` | no position (Bug 158) — unchanged |
| lanes, Truncate | both | `Orchestrator.handle` records it as a boundary on marker streams | its position is the transaction's OWN start (Postgres `currentTxnLSN`; a MySQL `TRUNCATE` is never inside a transaction), not an earlier one — no regression; unchanged |
| pgtrigger target | — | delegates to the Postgres applier | covered by the Postgres rows |

Every other engine's `OpenChangeApplier` refuses (SQLite, D1, the trigger-CDC sources, flatfile, mydumper). No position-never-regresses guard was added at the write: a target cannot order a source's tokens without engine knowledge, so it is not cheap. The same regression also produced a LOUD defect: a Postgres → Postgres serial batched stream that crashed after a `DROP COLUMN` resumed from `0/0`, replayed rows from before the DDL and crash-looped on the dropped column. Fix (a) closes it; `schema_drop_column_mid_txn_serial_batched` pins it.

**Fix (b), defence in depth: amendment B as a runtime check.** `applymarks` `consult` trusts a loaded mark only when its transaction is the FIRST identity-carrying transaction the apply run delivered (`Tracker.firstTx`, noted in stream order by every path — the lane coordinator at route time). A mark of the replayed change's own transaction when that transaction was not delivered first means the position moved behind the marks; the change is APPLIED (a loud collision at worst) and the run WARNs once with `APPLY-MARK-UNTRUSTED`. With (b) alone the reviewer's repro converges; the crash gate additionally asserts `APPLY-MARK-UNTRUSTED` never fires on a converging cell, so a position that moves behind the marks is a failure even when (b) saves the run.

**Residual found by the re-review (LOW, caught by (b)):** the "outside a source transaction is a statement boundary" rule has one gap — a MariaDB standalone (non-transactional) event group that carries rows gets no TxBegin, so `inSourceTx` is false, and a lazily emitted snapshot inside it still carries the DDL anchor, which can lie before already-applied transactions. Those rows carry no identity, but on a MySQL target the next marked transaction's mid-transaction flush keeps that regressed position while its marks become durable. (b) catches it (`APPLY-MARK-UNTRUSTED`, the change re-applies), so the harm is today's pre-ADR behaviour, never a silent skip. A second LOW: when every row of the first re-delivered transaction bypasses the coordinator's route-time consult (an absent target table, or a failed metadata probe at route time), `firstTx` can be set by the next transaction — a wrong DISTRUST only (a re-apply), never a wrong trust.

**Also hardened:** an anonymous GTID (go-mysql parses `ANONYMOUS_GTID_EVENT` as a GTID event with the all-zero source id, the SAME `00000000-…:0` for every anonymous transaction) now gets no identity rather than a shared one (`anonymousGTIDSource`). Not reached today only because the server refuses an anonymous transaction to a GTID auto-position dump — sluice itself accepts `ON_PERMISSIVE` — so the check removes the dependence on that premise.

**Pins.** `schema_event_mid_txn_{serial_batched,lanes_batched,serial_per_change}` on all six source × target pairs (the reviewer's shape: DDL, then T-1 inserting row 500, then T deleting it and writing the DDL'd table's first row, then blocking); `schema_drop_column_mid_txn_serial_batched` on the Postgres sources. The kill assertion is strengthened on every cell: the persisted position did not move in EITHER direction, and every mark names the interrupted transaction — the first a restart re-delivers — with the expected identity derived from the SOURCE's own state on the MySQL GTID (`gtid_executed`), MariaDB (`gtid_binlog_pos`) and file/pos (`SHOW BINLOG EVENTS`' last `BEGIN`) sources; on Postgres (no after-the-fact commit LSN) the position check plus "one transaction" plus "no `APPLY-MARK-UNTRUSTED`" stand in. ADR §8's lane-count change is pinned (`lane_count_changed_{4_to_2,lanes_to_serial,serial_to_lanes}`). Unit: `TestRunBatchLoop_SchemaEventInsideSourceTx_NeverPersistsItsPosition` (both DDL modes × both schema events × first/mid-batch × inside/outside a transaction), `TestConsult_TrustsOnlyTheFirstDeliveredTransaction`, `TestTransactionIdentity_AnonymousGTIDHasNone`.

### Amendment C (2026-09-29, operator): lane marks are opt-in (`--exactly-once-lanes`)

**Why.** A pre-release benchmark (180 cells, every one converged correctly) measured amendment A's fence on the DEFAULT lane path: MySQL → Postgres, a workload of small transactions on a secondary-unique table, v0.156.4's lanes ran 7,557 transactions/s, HEAD's 10.2, HEAD's `--apply-concurrency 1` 230.5; a 20%-secondary-unique mix fell from 18,868 to 42.5; primary-key-only work was unchanged. The root cause was a timer, not the fence's own work: `fenceApplyMarks` waits for the frontier to reach the marked change's predecessor, and the lane holding the previous transaction's partial batch committed it only when `readLaneBatch`'s idle grace (`defaultIdleFlushPeriod`, 100 ms) expired — ~100 ms per marked transaction, 10.2 transactions/s being exactly 1/100 ms. The barrier's drain (`barrier` → `WaitForFrontier`) had the same stall, in v0.156.4 too, unmeasured.

**Decision (operator).** Ship with (1) the lane marks OPT-IN and (2) the wake fix.

1. **`sync start --exactly-once-lanes`** (fleet key `exactly-once-lanes`; `Streamer.ExactlyOnceLanes`, zero value = off = the default, per the v0.99.51 trap; `ir.ExactlyOnceLanesSetter` on both lane engines; `laneapply.Config.ExactlyOnceLanes`). Off, `fenceApplyMarks` is a no-op — the coordinator never even asks `ApplyMarkTx` — the lane fence never opens, and the lanes write no marks (`laneApplyMarks` / the MySQL lane loop drop them before the fence is consulted). Every lane change still CHECKS the marks (`decideApplyMarks` runs unchanged), so it is still skipped on a mark that proves it applied. KEPT ON regardless: the serial per-change and serial batched paths (they already commit once per source transaction with its position, so their marks add a statement to a transaction that was happening anyway, and nothing waits — the same benchmark's serial path ran 230.5 transactions/s on the secondary-unique workload, which writes marks, and 233.2 on the primary-key-only one, which writes none, MySQL → Postgres; 78.4 vs 77.0 into MySQL) and the lane BARRIER (keyless changes, PK-changing updates), which already drains. Sync-only: `migrate` has no apply loop (`TestMigrateSyncFlagSurfaceParity`, `reasonCDCApply`); the broker and chain replay carry no identities.
2. **The wake fix** (correctness-neutral; it helps the barrier by default and the fence when opted in). `Orchestrator.drainLanes`, the shared prefix of `barrier` and `fenceApplyMarks`, first queues a flush sentinel (`LaneChange.flush`) on every lane behind what the coordinator has already routed to it; `readLaneBatch` returns the partial batch it holds when it reads one, instead of waiting out the idle grace. Why that cannot change what commits or what is persisted: a lane batch's extent was already arbitrary (row cap, byte cap, idle grace); the frontier advances per seq only after that seq's lane commit; a checkpoint reads only the frontier and the recorded boundaries; and the sentinel carries no seq and is never applied. Pinned by `TestOrchestrator_DrainDoesNotWaitOutTheIdleGrace` (a 5 s grace; a fence stream and a barrier stream must each finish well inside one grace, on 1 and 3 lanes), with every existing orchestrator test unchanged. **The barrier and the fence wake the lanes; the look-ahead cap deliberately does not** (busy-lane backpressure, not idle): `routeRow`'s cap wait fires because a lane is BUSY behind a hot table (perf-parity row 28), recurs about once per committed batch there, and a sentinel each time could cut the hot lane's batches below its AIMD size (unmeasured) — so it keeps v0.156.4's plain `WaitForFrontier`. `TestOrchestrator_FrontierWaitsGoThroughDrainLanes` holds that it is the ONE named exemption: it fails on any other direct `WaitForFrontier` caller and on an exemption whose function no longer calls it. The wake reaches every user of `laneapply.Orchestrator`: the sync apply lanes, and the broker's and chain replay's concurrent apply (`broker.go` and `backup/chain_restore.go` hand the same applier lanes via `ApplyApplyConcurrency`), whose keyless and PK-changing changes take the same barrier.

**Why the partial coverage is sound.** The skip rule is sound iff (i) a mark is evidence only for changes of ITS OWN transaction, (ii) a mark on key k at ordinal s is written only when every change of that transaction to k at an ordinal below s is durable (the per-key prefix property), and (iii) marks exist only for the first transaction after the persisted position (amendment B), because only then can no EARLIER transaction be replayed onto a key a mark says is settled. With the lanes writing no marks, each still holds:

- (i) is the skip rule itself: `consult` ignores a mark whose TxID differs, whatever path wrote it. No change is ever skipped on another path's mark of another transaction.
- (ii) for a BARRIER mark: the barrier drains every lane to its predecessor (`drainLanes(seq-1)`) before `ApplyBarrierChange`, so every earlier change of its transaction — lower seq, and so lower per-table ordinal — is durable when its mark commits. For a SERIAL mark: one applier in source order. The lane changes AFTER a barrier in the same transaction carry higher ordinals, so the barrier's mark never skips them (`m.Seq > id.Seq` only for earlier changes). A lane change EARLIER in the transaction on the barrier's key is skipped on the mark — correct, it is durable — and that is what stops a replayed unmarked lane change from resurrecting a key the barrier moved (the `pkchange_lanes_batched` cell).
- (iii) for a BARRIER mark: the barrier checkpoints after its drain, and the checkpoint is the highest recorded boundary at or below the frontier — on a marker stream the TxCommit of the transaction before the barrier's own (the barrier's transaction has not committed yet), on a marker-less stream the settled predecessor. So when a barrier's marks commit, the persisted position sits at its transaction's start: the fence's own prefix, for free. For a SERIAL mark: the serial paths never move the position inside a source transaction (ADR-0027 cohesion, CDCPOS-2, `schemaEventAtBoundary`). And whichever path wrote a transaction's marks, the checkpoint or position write that passes its commit deletes them in the same target transaction (`closedTx` → `CloseTxs`).
- **The mixed case** — a transaction T whose barrier writes marks, with unmarked secondary-unique lane changes around it, followed by unmarked lane transactions T+1…, crash, replay. The position is at T's start (iii); marks name only T. The replay delivers T first (so `firstTx` = T and T's marks are trusted): T's changes before the barrier on the barrier's key are skipped on its mark (durable by (ii)); the barrier is skipped; T's other changes and T+1… carry no mark and re-apply — idempotent upserts, or the pre-ADR loud unique collision on a secondary-unique table. No skip is possible on T+1… (no mark names them), and no change of T is skipped that is not durable. So the partial coverage can turn a convergence into the documented LOUD collision, never into a silent skip. Pinned: `lanes_batched` (default: the barrier marks — 2 at the kill — and the lanes do not; the restart stops on `23505` / `1062`, and a second restart stops the same way, on every marker source; on the marker-less trigger sources the cell accepts EITHER convergence or the loud collision, because each change is its own transaction and the lane checkpoint sits inside the source transaction, so the unmarked replay window — logged every run, measured at change-log ids 103..108 and 105..108 below the blocking statement 109 — decides it by timing; measured: converged on both pairs), `pkchange_lanes_batched` and `keyless_lanes_batched` (default: converge on the barrier's marks), `lane_count_changed_serial_to_lanes` (serial marks CHECKED by default lanes: converges), and `lane_post_commit_window_default` (no mark at the kill; the idempotent replay converges — without marks the amendment-A window cannot produce a skip).

**Follow-up plan (not in this change).** Fix #2: write the fence's checkpoint in the marked batch's OWN lane transaction, so the fence costs no separate synchronous position write and a secondary-unique table's lane runs at about serial parity — then reconsider the default. Fix #3: a per-KEY fence (drain only the lane that holds the key's predecessor) — which reopens amendment A's option B territory and needs its own soundness argument; future. (Both are worked through in amendment D below: #2 is sound with two conditions, #3 is not compatible with amendment A.)

### Amendment D (proposed 2026-09-30, accepted and implemented 2026-10-01): the fence's checkpoint rides the marked lane batch's own transaction

**Status: ACCEPTED and IMPLEMENTED (2026-10-01); ships in v0.156.8.** It changes amendment A's fence *mechanics* only; amendment A's invariant, amendment B's sweep and its runtime check, and amendment C's opt-in (`--exactly-once-lanes`) all stand. The operator answered D-Q1…D-Q4 (§D.8); the design below is as proposed, and §D.9 records what was re-validated against the v0.156.7 code before any was written, where the implementation diverged, and what was measured.

**Verdict.** Fix #2 — fold the fence's position write into the target transaction of the lane batch that carries the transaction's first marked change — is **sound only with two conditions**, and both are load-bearing:

1. **The drain stays.** The folded position must be the transaction's START (the anchor below), and the anchor is only a legal position once every change before the transaction's first marked change is durable on every lane. A fold that writes "whatever the frontier currently allows" instead is unsound (counterexample V1).
2. **No other lane may commit a mark of the transaction before the fold commits** (the *anchored* rule). A fold that clears every lane at once is unsound as an invariant (counterexample V2); the Finding-1 (b) runtime check (`APPLY-MARK-UNTRUSTED`) happens to rescue it, but this ADR's rule is that the invariant holds without the check.

**The key invariant** is amendment B's, made tighter: **the mark set moves from transaction T−1 to transaction T in the same target transaction that moves the persisted position from T−1's start to T's start.** Today those are two commits (the checkpoint deletes T−1's marks and moves the position, then a lane commits T's marks); each is safe alone. Under the fold they are one commit, so no crash can land between them.

**Expected cost.** On a stream made of marked transactions, the fold removes one of the two synchronous target commits the fence pays today, which leaves one target transaction per source transaction carrying the same statements as the serial path's `commitBatch` (data, mark upsert, closed-mark delete, position). The model estimate is ~0.9–1.0× `--apply-concurrency 1` on the fencebench workload A (today ~0.49×) and about twice today's flag-on figure on the 20% mix (workload C). Neither number has been measured; §D.6 gives the acceptance thresholds. Fix #3 is rejected (§D.5).

#### D.2 The algorithm

Terms. For a marked transaction T whose first marked lane change has sequence `s`: the **anchor** is the checkpoint boundary `CheckpointPosition()` returns once the frontier is at least `s−1` — the highest recorded boundary at or below `s−1`. On a marker stream that is the last recorded boundary before T: T−1's `TxCommit`, or a GC-41 (j) keepalive boundary (an empty `TxBegin`/`TxCommit` pair the Postgres reader emits at the walsender's keepalive position while no source transaction is open) that fell between T−1 and T (T's `TxBegin` is not a boundary, and T's own rows before `s` are never boundaries on a marker stream). On a marker-less stream it is the change at `s−1` (`handle` runs `noteBoundary(s)` before `routeRow(s)`, which settles it). Either way it is T's start. A **fold ticket** is `{Tx, Seq: s, Pos, RowsApplied, ClosedTxs}`. T is **anchored** once the persisted position is at T's start.

**Coordinator side, in `fenceApplyMarks(ctx, seq=s, c)`,** replacing today's drain-then-`writeCheckpoint`:

1. As today, it runs only with `ExactlyOnceLanes`, when `ApplyMarkTx(c)` names a transaction T.
2. If T is the transaction already fenced (`fencedTx == T`), go to step 8.
3. `drainLanes(ctx, s−1)`, unchanged — the wake sentinel on every lane, then the frontier wait. **Preserves:** every change with seq ≤ s−1 is durable on every lane, which is the precondition for the anchor to be a legal position (position ≤ durable data).
4. Flush the coalesced skip ledger (`flushSkippedTables`, through a new seam method), a no-op unless a target table was absent. **Preserves:** H-4 — the ledger is durable before any position that covers the skips it records. This is the only synchronous write left at the fence, and it is empty in the steady state.
5. Read the anchor with `frontier.CheckpointPosition()`.
   - **(5a) No boundary recorded yet in this run** (`ok == false`). Then T is the first transaction this run delivers, so the persisted run-start position is already T's start (the same fact today's no-op `writeCheckpoint` relies on). T is anchored with no ticket.
   - **(5b) Anchor already persisted** (`seq ≤ lastWrittenSeq`). This happens when T's own earlier barrier, or an idle or count checkpoint, already wrote it. T is anchored with no ticket.
   - **(5c) Otherwise** build the ticket: `Pos`; `RowsApplied = boundaryRowDML[anchor] − lastWrittenCum`, exactly as `writeCheckpoint` computes it; and `ClosedTxs = closedTxsUpTo(anchor)`. Then **claim** the anchor: set `lastWrittenSeq`, `lastWrittenCum`, and prune `boundaryRowDML` and `closedTx`, exactly as a successful `writeCheckpoint` does. **Preserves:** seq-monotonicity. Between the claim and the fold's commit, every coordinator `writeCheckpoint` (count cadence, idle tick, the next barrier's post-apply write) returns in memory before touching the engine, because the frontier cannot pass `s−1` until the fold commits and no boundary at or below `s−1` is above the claim.
6. `LaneFence.Open(T, anchored)`, where `anchored` is true in cases 5a and 5b and false in 5c. Then `fencedTx = T`, `foldSeq = s`, and `foldLane = LaneForRoute(route)`. Routing is decided before the fence, and the fence does not change it.
7. Push `s`'s envelope to `foldLane` **carrying the ticket** (`LaneChange.fold`). Go to step 9.
8. (A later marked change c of the same T.) If T is not yet anchored and c routes to a lane **other than** `foldLane`, wait for the fold first: `drainLanes(ctx, foldSeq, foldLane)`, which sends a wake sentinel to `foldLane` only. After step 3 the frontier is `foldSeq−1`, so `frontier ≥ foldSeq` means exactly that the fold committed. A change routed to `foldLane` itself needs no wait, because a lane commits its batches in order. **Preserves:** the anchored rule, on the coordinator side.
9. Route normally.

**Lane side, in `ApplyLaneBatch(ctx, lane, batch, fold)`,** a new parameter carrying the ticket of any envelope in `buf`:

- **At most one ticket per batch.** Ticket T+1 is issued only after a drain that requires ticket T's batch to have committed. The orchestrator asserts this rather than assuming it: a second ticket in one `buf` is a coordinator bug and fails the run loudly (`FOLD-TICKET-DUPLICATE`, a named check).
- **On an in-lane split** (`applyLaneBatch`'s halving), the ticket rides the sub-batch that contains the ticket's envelope. The algorithm does not rely on `s` being first in its batch, though it always is: the drain's sentinel ends every batch that holds a seq below `s`.
- **Mark admission:** `LaneFence.Admits(ms, fold)` accepts T's marks when this batch carries T's ticket **or** T is anchored. Otherwise the marks are dropped and the change applies unmarked, which is today's fallback (loud at worst, never a skip). **Preserves:** the anchored rule, on the lane side. It covers a route-time verdict that the apply-time verdict contradicts, which `LaneFence` already guards against for the same reason.
- **The fold's statements,** in the lane's own transaction and in this order:
  1. the data, as today (including MySQL's trailing `flushPending`);
  2. `marks.CloseTxs(fold.ClosedTxs)`, then `Plan(gc=true)`, executed as the admitted-mark upserts plus the closed-mark delete, which is the same plan `WriteCheckpoint` runs;
  3. the position write, **last**: `writePositionTx(..., fold.Pos.Token, ..., fold.RowsApplied)`. On Postgres this is `writePositionPipelined` in the same `SendBatch`, so it adds no round trip. On MySQL it is one more statement on the lane's `*sql.Tx`. The position comes last so that the stream's `sluice_cdc_state` row lock is held only across COMMIT.
  4. COMMIT.
  5. `Committed(plan)`, then `LaneFence.Anchor(T)`, both **before** the lane returns and so before the frontier advances past `s`.
- **In-place retry.** A fold batch retries in place on an error raised **before** COMMIT (serialization, deadlock, tx-killer — the existing split-and-retry). An error from the COMMIT step itself — the Bug-56 watchdog firing, or the connection dying mid-COMMIT — has an unknown outcome, and on a fold batch it is **fatal to the run**. The ADR-0038 re-entry then re-reads the position and the marks. This is the one retry-semantics change, and it is load-bearing: if a COMMIT that actually succeeded were retried in place, the retry would add `RowsApplied` a second time. It would also make the retry decide from a tracker whose `Committed` never ran for the durable plan. "Fatal, then the re-entry reads the truth" assumes the outcome has SETTLED by the time the re-entry reads it, and that is not guaranteed: a COMMIT the Bug-56 watchdog abandoned (`RunWithDeadline` returns while the driver call is still in flight; on the pipelined core pgx cancels the request, which the server may receive after it has committed) can land AFTER the re-entry's `ReadPosition` and mark `Load`, so the new run starts from the older position without the landed marks while the target then holds them, and its first checkpoint can write a position below the one that landed. This is pre-existing and not specific to the fold — every commit path that abandons a COMMIT on the watchdog has it (the serial batch, per-change, the lane checkpoint, every lane batch) — and the 2026-10-01 independent review could construct only a loud outcome from it (a re-applied change colliding, or the GC-41 (h) door refusing a slot acked past a regressed position), not a silent skip: the late-landed marks name a transaction the re-entry re-delivers from an earlier position, so `consult`'s first-transaction check distrusts them. UNVERIFIED beyond that construction; no test builds a late-landing COMMIT.

**What does not change.** The position format, the mark table, the skip rule, `consult`'s first-transaction check, the sweep, the barrier (see sibling D-S1), `WriteCheckpoint` itself (still used by the count cadence, the idle tick, the barrier and the end of a run), and every flag-off path. With `--exactly-once-lanes` off, `fenceApplyMarks` still returns before step 2, so no ticket is ever created.

#### D.3 Soundness, point by point

The skip rule is sound iff amendment C's (i)–(iii) hold. (i) is untouched. (ii), the per-key prefix: T's marks on lane L are written in the batch that applies the changes they cover, and lane FIFO keeps T's earlier changes to that key at lower seqs in the same batch or an earlier committed one. The fold adds nothing to either. Everything below is (iii): *marks exist only for the first transaction after the persisted position.*

- **The GC rule, "a position write passing a transaction deletes its marks".** The fold's position (the anchor) passes exactly `ClosedTxs = closedTxsUpTo(anchor)`, the same set `writeCheckpoint` would hand for the same anchor, and the fold deletes those transactions' marks in the same transaction. T itself is not in the set: its `TxCommit` seq is above `s`. On the first close of a run, the sweep adds every loaded transaction to `closed`, as it does today. A loaded stale mark that names T itself would mean invariant B was already broken (a pre-existing position regression). In that case `Plan(gc=true)` drops T's pending marks and deletes T's durable ones, so T's changes in the fold batch apply unmarked, and `consult`'s first-transaction check had already set those marks aside with `APPLY-MARK-UNTRUSTED`. That is loud at worst, never a skip.
- **The frontier and persisted-position monotonicity.** Two components now write the position: the coordinator (`WriteCheckpoint`, on the primary pool) and the fold (on a lane connection). Their writes are **totally ordered by the frontier**:
  - A fold for anchor `a` is issued only when the frontier is at least `a`.
  - That fold commits before the frontier can reach `s > a`.
  - A coordinator write of any boundary above `a` needs the frontier at or beyond that boundary, and every such boundary is at least `s`, so it happens after the fold commits.
  - The next fold (T+1) is issued only after a drain that includes `s`.
  - A write at or below `a` after the claim is refused in memory by the seq guard.

  So the sequence of persisted positions stays non-decreasing in seq, and position ≤ durable data still holds, because the anchor needs only seqs ≤ `s−1`, which step 3 made durable. The claim-before-commit window is safe because, if the fold never commits, the run fails (a lane error cancels it), and the next run rebuilds the orchestrator from the durable position.
- **A crash between the fold's commit and the other lanes' commits.** At that instant:
  - the position is T's start;
  - the only durable marks are T's, on lane L's keys (other lanes' T marks are gated until the fold commits, and T−1's marks were deleted by the fold);
  - other lanes may hold T's unmarked changes and later transactions' unmarked changes, committed or not.

  The restart delivers T first, so `firstTx = T` and T's marks are trusted. T's changes on L's keys are skipped up to their mark's ordinal (durable by (ii)). Everything else re-applies: idempotent, or the pre-ADR loud collision where a gated or dropped mark was never written. No mark names a later transaction, so nothing later can be skipped. This is the mixed case of amendment C with the fold's mark set in place of the barrier's.
- **A crash before the fold commits.** Nothing of the fold is durable. The position is T−1's start (from T−1's fold) or earlier, and the durable marks are T−1's only (T's are gated on every lane). That is exactly the state amendment A leaves between two fences.
- **Mixed barrier and lane marks.**
  - *Lane fold first, then a barrier of T at `q > s`.* The barrier's `drainLanes(q−1)` waits for the fold. Its pre-apply `writeCheckpoint` is a no-op (the anchor is claimed and nothing above it is durable-and-recorded). Its marks commit after the fold, with the position already at T's start.
  - *Barrier of T first, then a lane change of T.* The barrier's own pre-apply checkpoint persisted T's start synchronously, so the lane fence hits 5b: no ticket, anchored immediately.
  - *Barrier of T+1 while T's fold is in flight.* The barrier drains, which includes `s`, before it does anything.

  In every order, (iii) holds for the barrier's marks by amendment C's argument.
- **A lane batch holding changes from several transactions (a batch spanning the fence).**
  - *Below `s`:* impossible after step 3. Were it possible it would still be safe: those seqs would be in the fold's own transaction, and the drain covers the other lanes.
  - *Above `s`, the common case:* the fold batch may continue with T's later changes, T's commit, and whole unmarked transactions T+1… up to the next fence's sentinel. A later transaction's change whose apply-time verdict is "marked" is refused admission (`tx ≠ T`) and applies unmarked. T+1's first *route-time* marked change triggers T+1's fence, whose sentinel ends this batch.
- **A lane-count change between runs.** The fold persists nothing routing-dependent. The ticket is in-memory per run, marks are per key (§2), and the position format is unchanged. The runs before and after may be any mix of serial, flag-off lanes, today's fence and the fold. Each leaves the durable state inside the same invariant, "marks name only the first transaction after the position", so any successor starts from a legal state. `lane_count_changed_*` stays green by construction, and is re-run (§D.6).
- **Trigger sources (marker-less; every change is its own transaction).** T is one change at `s`. The anchor is the change at `s−1`, settled by `noteBoundary(s)` before `routeRow(s)`; `ClosedTxs` is `{T−1}` via `settlePrev` → `closedTx`. Each marked trigger change costs one lane commit plus the drain, instead of two commits. The idle tick may settle `s` itself as a boundary while the fold is in flight; its `writeCheckpoint` cannot choose it until the frontier reaches `s`, which is after the fold commits.
- **VStream, multi-shard.** Nothing shard-specific changes. The anchor is the merged VGTID at T−1's commit, the same token today's fence checkpoint writes. A sharded restart may still deliver another shard's transaction first, and T's marks are then set aside with `APPLY-MARK-UNTRUSTED` (review hardening (3), best-effort, loud at worst). The fold can neither widen nor close that gap. Interleaved shard groups still arrive as one bracket, which is one T.

**Must the position write move to the lane's connection? Yes.** Only the lane's own transaction makes "T's marks durable ⇔ position at T's start" atomic. The single-writer question for `sluice_cdc_state`, by writer:

| Writer of the stream's row | Where | Relation to the fold |
|---|---|---|
| Lane checkpoint `WriteCheckpoint` | coordinator, primary pool | totally ordered with every fold by the frontier (above); never concurrent in the database, because its in-memory guard short-circuits while a fold is in flight |
| **The fold** (new) | lane pool. It is opened from the SAME config as the primary applier pool (`pipelineCfg: cfg` in both engines' `OpenChangeApplier`; PG adds the same `roleApplier` tag), so the lane connection holds the same privileges on `sluice_cdc_state` the checkpoint uses. No new grant is needed. | at most one in flight per stream (a ticket is issued only after the previous one committed) |
| `requestStop` (`sluice sync stop`, another process) | single-statement UPDATE of `stop_requested_at` | row-lock serialisation only. The position upsert's `ON CONFLICT` / `ON DUPLICATE KEY` sets do not list `stop_requested_at`, so the flag survives either order, as it does against today's checkpoint. The fold holds the row lock only across COMMIT (position statement last), so a stop request waits at most that long. No cycle: a one-statement transaction waits on nothing else. |
| `clearStopRequested` | Streamer start, before any apply | not concurrent |
| unforwarded-refusal store UPDATE | stream exit path | not concurrent with a running orchestrator; row-lock serialisation at worst |
| `ClearStream` DELETE | `--reset-target-data` / decommission, with the stream stopped | not concurrent |
| "heartbeat" writers | none on this row: `WriteHeartbeat` writes the SOURCE heartbeat table, `heartbeatShardLease` the shard-consolidation lease table, and `pipeline/stream.go`'s heartbeat the backup stream state | n/a |

Deadlock analysis. The fold's lock order is data rows → mark rows → the `sluice_cdc_state` row, and nothing after the state row but COMMIT, so no cycle can close through that row. On the mark table, the fold is the *only* writer from the fence until its commit: other lanes' T marks are gated, no other transaction is fenced, and the coordinator writes none in that window. That rules out the upsert-versus-closed-delete deadlock two concurrent mark writers could otherwise hit, including MySQL next-key locks on the delete's scan. After the fold commits, the mark-table concurrency is exactly today's.

**Two things found while checking, both PRE-EXISTING and not introduced here, filed for triage:**

- **D-F1 (UNVERIFIED — needs a reproduction before any grade is trusted).** Under `--control-keyspace` on a sharded Vitess target, `writePositionTx`'s own comment says the control-keyspace write and the data write "span two keyspaces, so vtgate can only best-effort the cross-keyspace commit (no 2PC)". Marks live in the same sidecar keyspace (`controlTableRef(controlKeyspace, applyMarksTableName)`), and `applyMarksUsable` enables them there. §5's row "Mark written but the rows not — Impossible" therefore rests on a single-keyspace premise that the sidecar configuration does not meet. A torn commit that lands the marks but not the rows would skip an unapplied change on restart, which is **silent**. It already applies to the serial paths and to the barrier by default, not only to the lanes. The same question applies to a Neki target whose control tables are in the unsharded shard group while the data is in sharded groups (UNVERIFIED PREMISE: that Neki commits across shard groups atomically). The fold adds no new harm to this class: its position is T's START, which depends only on data made durable before the fold began, so a torn fold that lands the position without the rows loses nothing the position vouches for. But the fold must not ship with the class unexamined. A likely remedy is to treat marks as unavailable (`APPLY-MARKS-UNAVAILABLE`) whenever the mark table and the data cannot share one atomic commit.
- **D-F2 (UNVERIFIED, noticed in passing).** Neither lane adapter's `WriteCheckpoint` calls `reportAppliedToken`, the Postgres slot-ack feedback the serial paths call after a position commit (`change_applier_batch.go`'s `AfterCommit`; `persistSourceTxCommit`). If nothing else reports on the lane path, a PG → PG stream on lanes never advances `confirmed_flush_lsn` past its start, and WAL is retained. Whatever the checkpoint's post-commit hook turns out to be, the fold must run the same one. The gate below holds the two post-commit sequences identical.

#### D.4 Simpler variants that are NOT sound

- **V1 — fold without the drain** (write whatever `CheckpointPosition()` returns now, in the batch carrying T's first marked change). Take T−1 = {update `rs` row 7 on lane L; insert into `po`, a PK-only table on lane M} and T = {delete `rs` row 7}. Lane M is slow, so T−1's `po` insert is not durable, and the anchor lags to T−2's commit. L commits T−1's update of row 7, then T's delete with T's mark and the lagging position. Crash. The restart replays from T−1's start. T−1's update finds row 7's mark naming T, which proves nothing about T−1, so it re-applies and **re-creates row 7**. T's delete then finds its own mark and is skipped. Row 7 survives at exit 0. This is amendment A's counterexample with the position failing to advance. `consult`'s first-transaction check happens to catch it (T−1 was delivered first, so T's mark is untrusted and the delete re-applies), but that is defence in depth, and the invariant is broken.
- **V2 — fold, but open the fence to every lane at once** (no anchored rule). T = {update `rs` (lane L, carries the ticket); delete `rs2` row 9 (a second secondary-unique table, lane M)}, and T−1 updated `rs2` row 9. M commits T's delete with its mark before L's fold commits. Crash. The position is still T−1's start, T−1's marks are still durable, and T's mark on row 9 is durable too, so marks exist for two transactions, which violates (iii). The restart replays T−1's update of row 9, which finds T's mark and re-applies (re-creating the row), then skips T's delete. The same runtime check rescues it with an `APPLY-MARK-UNTRUSTED` WARN, which the crash gate treats as a failure on any converging cell. It is rejected for the same reason as V1.
- **V3 — fold T's COMMIT position** (write T's end rather than its start, in T's last lane batch). The coordinator cannot know at route time which batch is last, and T's changes on other lanes may not be durable. The position would lead the data, breaking the relaxation every lane checkpoint rests on (`persisted_position ≤ all-durably-committed-data`).
- **V4 — drain only since the last fence** (skip the drain when the transactions in between were unmarked). The anchor must be T's start, and the position is one scalar across every lane, so an in-flight unmarked transaction U on another lane holds it back. The fold would have to write U's start, and then a restart delivers U first, T's marks are untrusted, and exactly-once degrades to loud. A relaxed invariant ("marks only for the first *marked* transaction after the position") might make this sound. It would need its own argument, including a change to `consult`'s first-transaction check. It is not proposed (D-Q4).

#### D.5 Fix #3 (per-key fence): not compatible with amendment A

Two independent reasons. **First, it buys nothing under the current skip rule.** The router already sends every change to a marked key through one lane in source order — a secondary-unique table is table-scoped, and a PK change is a barrier — so "wait only for the lane holding the key's predecessor" waits on the lane's own FIFO, which already holds. **Second, amendment A's condition is global.** When T's mark on k becomes durable, no earlier transaction may be re-delivered. The persisted position is one scalar for the whole stream, so meeting that condition requires every earlier change on every lane to be durable: that is the full drain. A per-key fence that does not move the position reproduces amendment A's counterexample verbatim (T1 updates k, T2 deletes k, one lane, a crash before the position passes T1). Making it sound means giving up (iii) for a cross-transaction skip rule — amendment A's rejected option B. That needs:

- an order on TxIDs, which are opaque today;
- a staleness guard;
- a new sweep, because B's "first close retires everything" no longer holds;
- a replacement for `consult`'s first-transaction check, which would otherwise distrust every mark after the first transaction and degrade exactly-once to loud.

So #3 needs its own ADR. The rest of this amendment does not depend on it.

**Re-validation before writing code.** The design was written against `1a338f9f` (v0.156.6). v0.156.7 (GC-41) changed three things it leaned on, so each premise was re-checked against the v0.156.7 code first:

1. *Data before control, rostered.* GC-41 (c) made every write core send its rows before its first control statement (`mysqlBatchTx.writeApplyMarks`, the Postgres queue order), held by `TestWriteCoreStatementOrder` over the cores the AST roster `TestWriteCoreRoster_EveryControlWriterCallerIsClassified` derives. 2. *The slot-ack ceiling.* GC-41 (a)/(b) replaced the applier-fed slot-ack tracker (`reportAppliedToken`, `AfterCommit`) with a sidecar that reads the persisted position back from the target (`releaseDurableSlotAck` → `ChangeApplier.ReadPosition`). A position the fold persists is visible to that read only once the fold's transaction commits, and it vouches only for changes at or below the anchor, which the fence's drain made durable before the fold began — so the read-back can never release WAL for a change the target does not hold. Holds. D-F2 is moot: there is no post-commit hook left for the fold to forget, and `TestLanePositionWriterRoster` (both engines) requires any hook the checkpoint ever gains to be called by every fold core too.
3. *The warm-resume door* (`SLOT-ACKED-PAST-TARGET-POSITION`, `checkSlotNotAckedPast`). It is sound while a correctly-running stream never moves its persisted position backward (the ack side ratchets on read-back positions). A resume after a fold therefore starts at or after `confirmed_flush_lsn` and the door cannot false-positive. Holds; pinned by `TestOrchestrator_PositionWritesTotallyOrdered`.

D-F1 was largely overtaken by GC-41 (c): under a vtgate MULTI sidecar a torn commit now leaves rows without their marks or position (at-least-once), never marks without rows, and the fold keeps that order. ### Amendment E (proposed and design-accepted 2026-10-04; implemented 2026-10-06): the barrier's pre-apply checkpoint rides the barrier's own transaction (D-S1, perf-parity GAP #48)

**Status: design ACCEPTED (operator answered the open questions on 2026-10-04, §E.13); IMPLEMENTED 2026-10-06 on `ec5effd2`, after the F-E1 broker fix (E-Q5), default-on with no flag (E-Q1). §E.9 D acceptance met and §E.10 pins built and mutation-run — see §E.14. CI `-race` Integration must be green before it is tagged.** Proposed 2026-10-04 as design only. Written against `14106b4f` (v0.156.10 + Bug 296). It changes the lane BARRIER's position mechanics only. Amendment A's invariant, amendment B's sweep and its runtime check, amendment C's opt-in and amendment D's fold all stand unchanged. Operator decision D-Q3 asked for D-S1 as a separate follow-up; this is it.

**Verdict.** Fold the barrier's pre-apply checkpoint (the position `writeCheckpoint` persists after the barrier's drain) into the barrier's own target transaction, written LAST, for every barrier kind whose `ApplyBarrierChange` runs as one real target transaction: keyless, absent-target and malformed row changes, primary-key-changing updates, and `SchemaSnapshot` on both engines, plus `Truncate` on Postgres. Keep today's two commits for a MySQL-family `Truncate`, which implicitly commits. It is amendment D's argument with the hard parts removed. The barrier runs synchronously on the coordinator after a full drain, so it is the only position writer while it runs: there is no claim-before-commit, no anchored rule and no second connection. It changes no delivery guarantee. The barrier is exactly-once today wherever it writes marks, and at-least-once wherever it does not, and both stay true (§E.5). What changes is that one synchronous commit per barrier-bearing source transaction disappears.

#### E.1 The problem (GAP #48, measured)

`Orchestrator.barrier` (`internal/laneapply/laneapply.go:1217`) drains every lane to `seq−1` (`:1218`, `drainLanes`), persists a checkpoint (`:1223`, `writeCheckpoint` → `LaneApplier.WriteCheckpoint`, its own transaction on the primary pool), applies the change (`:1226`, `ApplyBarrierChange`, a second transaction on the same pool), then marks the barrier's seq and checkpoints again (`:1252`–`:1254`). That is two synchronous target commits per barrier, by default, with or without `--exactly-once-lanes`. A barrier is every keyless change, every primary-key-changing update, and every `Truncate` and `SchemaSnapshot` on the lane path (§E.3).

fencebench workload D: transactions of 1–3 rows on table `k`, each row a primary-key-changing update with probability ½. Medians of three reps, source transactions/s, 0 ms added latency, every cell `VERIFY OK`:

**The commit arithmetic.** In workload D a transaction carries E[barriers] = 1.0. P(at least one barrier) = 1 − E[½^rows] = 1 − (½ + ¼ + ⅛)/3 ≈ 0.71. The pre-apply checkpoint writes something only at the first barrier of a transaction, because that is the only point a new boundary (T−1's `TxCommit`) is durable and unwritten. Later barriers of the same transaction find nothing new, and the post-apply checkpoint is a no-op for a row barrier (§E.2). So per source transaction the lane path pays about 0.71 checkpoint commits + 1.0 barrier commits + the lane commits each drain forces (roughly 0.7: one per lane holding rows, waited on synchronously). That is about 2.4 synchronous commits against the serial path's 1, consistent with the measured 0.45×. The fold removes the 0.71, so the model predicts about 1.7 commits per transaction: **~0.55–0.65× serial, ~1.35–1.45× today's lanes**. The model is not a measurement, and §E.9 holds it to the harness. Closing the remaining gap to serial would mean not draining at a barrier. That breaks the global ordering the barrier exists for, so it is not proposed.

#### E.2 What the pre-apply checkpoint protects today (from the code)

**Which position it writes.** `writeCheckpoint` → `nextCheckpoint` (`:1600`) → `Frontier.CheckpointPosition` (`frontier.go:140`): the highest *recorded boundary* at or below the frontier, which the drain has just made `seq−1`. The barrier's own position is never written:

- On a marker stream, the recorded boundaries are `TxCommit`s (`handle`, `laneapply.go:786`–`793`), GC-41 (j) keepalive boundaries, and a `Truncate`'s own position (`:845`), never a row. So the pre-apply checkpoint writes T−1's `TxCommit` (or a later keepalive boundary), which is **T's start**. A row barrier's own position is a mid-transaction position: unresumable on MySQL file/pos ("no corresponding table map event"), and excluded by the marker rule.
- On a marker-less stream (the trigger sources), `noteBoundary(seq)` settles the change at `seq−1` as a boundary before the barrier runs (`handle` → `noteBoundary` → `settlePrev`), so the anchor is the change before. Each change is its own transaction, so that is again T's start.
- A `SchemaSnapshot`'s position is metadata-anchored (Bug 158; pgoutput's first-touch relation carries `0/0`) and is excluded from boundary tracking on both stream shapes (`:837`–`:851`, `isSchemaSnapshot`).

Its `closedTxs` are `closedTxsUpTo(anchor)`, every transaction whose commit the anchor passes (T−1 and earlier). Its `rowsApplied` is the route-time DML count up to the anchor (`boundaryRowDML`). The barrier's own row is counted at route time (`:819`) and realised by a LATER boundary, never by this checkpoint.

**The post-apply checkpoint** (`:1254`) writes something only when the barrier's own seq is itself a recorded boundary. On a marker stream that is a `Truncate` (recorded at `:845` before `barrier` runs), whose own position then persists in a third commit. For a row barrier or a `SchemaSnapshot`, `nextCheckpoint` returns the boundary just written and the seq guard makes it a no-op. On a marker-less stream the barrier's own seq becomes a boundary only when a successor with a different token arrives, so this checkpoint is a no-op there too.

**What the barrier transaction itself writes.** `ApplyBarrierChange` → `applyBarrierNoPosition` → `applyOneImpl(…, writePosition=false)`. On MySQL: `mysql/change_applier_concurrent.go:540`, `mysql/change_applier.go:1265`, `:1315`. On Postgres: `postgres/change_applier_concurrent.go:735`, `postgres/change_applier.go:1556`, `:1569`. It writes the data, then the change's apply marks (`Plan(&pending, gc=false)`: upserts only, no closed-transaction delete), and no position. Postgres pins `synchronous_commit` (`forceSynchronousCommitOn`) and the FK/trigger bypass. A change the marks prove already applied returns BEFORE any transaction opens (`decision.Skip`, MySQL `:1336`, Postgres `:1587`).

**What the separate checkpoint buys, listed.**

1. **Amendment C's (iii) for barrier marks.** When the barrier's marks commit, the persisted position already sits at T's start. Without it, the barrier's mark on a keyless table (key digest empty, so one mark row per table) would overwrite T−1's and could be durable while the position still sat at T−1's start. A replay of T−1's keyless insert then finds a mark naming T, which proves nothing, and re-inserts it. That is a duplicate, saved only by `consult`'s first-transaction check.
2. **GC.** It deletes T−1's marks (`CloseTxs` + `Plan(nil, gc=true)` in `WriteCheckpoint`, MySQL `:492`, Postgres `:683`).
3. **H-4.** It flushes the coalesced skip ledger before the position (`flushSkippedTables`).
4. **The replay distance.** A crash inside the barrier replays from T's start rather than from the last count or idle checkpoint.

It does **not** make the barrier itself durable or atomic. That is `ApplyBarrierChange`'s own commit.

**Crash outcomes today.** P_prev is the last persisted position before the barrier's transaction T, and "marks" means an identity-carrying source with `sluice_cdc_apply_marks` usable on an atomically-committing target.

| Crash point | Persisted position | Durable marks | Restart, with marks | Restart, without marks |
|---|---|---|---|---|
| before the pre-apply checkpoint commits | P_prev | those of the transaction at P_prev | converges | the barrier is not durable, so it applies once; the changes between P_prev and the barrier replay with the pre-ADR outcome (a keyless row duplicates, a secondary-unique or key change may collide loudly) — "converges" only for the barrier itself *(corrected 2026-10-06, review of §E.14)* |
| between the checkpoint and the barrier's commit | T's start | none of T's | the barrier re-applies once: converges | converges |
| after the barrier's commit, before a checkpoint passes T | T's start | T's barrier marks | the barrier is SKIPPED on its own mark (T is delivered first, so `consult` trusts it): **exactly-once** | the barrier re-applies: a **keyless row duplicates** (ADR-0089 at-least-once), a PK change collides loudly on its after-key |

**So the barrier is exactly-once today wherever it writes marks, and at-least-once (keyless) or loud (PK change) wherever it does not.** The no-marks cases are: `APPLY-MARKS-UNAVAILABLE`; a reader or change with no identity (VStream COPY rows and interleaved shard groups, the broker, chain replay); and a vtgate MULTI `--control-keyspace` tear, which by GC-41 (c)'s design leaves rows without their marks. The marks case is pinned on every source × target pair by `keyless_lanes_batched` and `pkchange_lanes_batched` (`internal/pipeline/streamer_crash_midtxn_integration_test.go:634`, `:640`). Both kill on a statement blocked after the barrier committed, which is the third row. The first two rows have no dedicated cell. Nothing of the barrier is durable there, so convergence there is by construction, and §E.10 adds the cell the fold needs anyway. The no-marks keyless duplicate is the documented ADR-0089 contract on the sync path (`marks_unavailable` pins the loud half). On the broker it is a finding in its own right (§E.12, F-E1).

#### E.3 Every barrier kind, enumerated from the code

A change reaches `barrier` by two doors. `handle`'s `default:` (`:837`) takes every change that is not `TxBegin`/`TxCommit`/`Insert`/`Update`/`Delete` (today `Truncate` and `SchemaSnapshot`; `ir.Change` is sealed, `ir/change.go:92`). `routeRow`'s `ok == false` (`:1015`) is the engine's `RouteForChange` (MySQL `change_applier_concurrent.go:259`, Postgres `:282`) returning not-routable, and `PKValuesFromRow` (`router.go:403`) says why.

**Correction to §D.7 and GAP #48.** Both say "a DDL-bearing SchemaSnapshot implicitly commits". At `ApplyBarrierChange` no SchemaSnapshot carries DDL on either engine, and the MySQL arm's rollback is already pinned. The only non-transactional barrier kind is a MySQL-family `Truncate`. The MySQL batch loop's own comment (`applySchemaEvent`: "it can never share the batch tx: DDL implicit-commits") overstates it the same way. It is conservative and harmless there.

**Why the MySQL `Truncate` stays OUT even though the fold's position would be safe in it.** After `TRUNCATE`'s implicit commit, the fold's closed-mark DELETE and its position UPSERT would each autocommit separately. A crash between them deletes T−1's marks while the position still sits at T−1's start. The replay then re-applies T−1 unmarked, and a keyless row in T−1 duplicates **silently**. Reordering the two statements would avoid that, but it would rest the argument on per-statement autocommit behaviour inside a `*sql.Tx` the server has already ended. That is a wart with no name, to save one commit on a rare event. Keep today's three commits.

#### E.4 The design

**Seam (engine-neutral, `laneapply.LaneApplier`):**

- `FoldsBarrierCheckpoint(c ir.Change) bool` is new, pure, with no side effect. It reports whether `ApplyBarrierChange` runs c as ONE target transaction that can carry the position. MySQL answers `!isTruncate(c)`; Postgres answers `true`. The zero answer (`false`) is today's behaviour exactly, so a seam that does not opt in keeps two commits. That is the v0.99.51 zero-value-safe direction: the fold is the opt-in, per engine and per kind, and there is no operator flag (E-Q1).
- `ApplyBarrierChange(ctx, c ir.Change, at *BarrierCheckpoint) error` gains `at`, which is `{Pos ir.Position; RowsApplied int64; ClosedTxs []string}`: the exact fields `WriteCheckpoint` takes. `nil` means "write no position", which is today's behaviour.

**Coordinator, in `barrier(ctx, seq, c)`:**

1. `drainLanes(ctx, seq−1)`, unchanged. **Preserves:** every change at or below seq−1 is durable on every lane, so the anchor is a legal position (position ≤ durable data). The drain also waits for any in-flight amendment-D fold whose ticket seq is below `seq`.
2. `partCommitted` bookkeeping (Bug 294), unchanged.
3. If `FoldsBarrierCheckpoint(c)` is false, run today's sequence verbatim (`writeCheckpoint`, `ApplyBarrierChange(ctx, c, nil)`) and continue at step 6.
4. Otherwise `ck, ok := nextCheckpoint()`, the function `writeCheckpoint` itself uses. There are three cases, the same as amendment D's 5a/5b/5c:
   - (a) No boundary has been recorded this run, so the run-start position is already T's start: `at = nil`.
   - (b) The anchor is already persisted (`seq ≤ lastWrittenSeq`: an earlier barrier of T, a lane fold of T, or an idle/count checkpoint wrote it): `at = nil`.
   - (c) Otherwise `at = &BarrierCheckpoint{ck.pos, ck.rowsApplied, ck.closedTxs}`.
5. `ApplyBarrierChange(ctx, c, at)`. On success, and only then, `checkpointWritten(ck)`. On error, nothing is claimed. The error ends the run as it does today (`NoteSourceTxSplit` wrapping unchanged), and the next run's orchestrator starts from the durable position. There is **no claim-before-commit**: the coordinator is blocked in this call, the lanes are drained and nothing at or above `seq` is routed, so no other position writer exists for the duration (§E.8).
6. `MarkCommitted(seq)`; post-apply `writeCheckpoint`, unchanged. It stays a no-op for every folded kind. A Postgres `Truncate` on a marker stream still writes its own boundary in a third commit; folding that too is E-Q3.

**Engine, the barrier transaction's statements, in order:**

1. Data, as today (`dispatch`, including the GC-42 multi-row refusal, which rolls everything back).
2. Marks: `marks.CloseTxs(at.ClosedTxs)` then `Plan(&pending, gc=true)`, executed as the barrier's own upserts plus the closed-transaction deletes. That is the plan `WriteCheckpoint` + `ApplyBarrierChange` run today in two transactions, now in one. T is never in `at.ClosedTxs`: its `TxCommit` seq is above `seq` on a marker stream, and `closedTxsUpTo(seq−1)` stops at T−1 on a marker-less one. So T's pending mark is never dropped.
3. `flushSkippedTables`. It is on the primary pool, its own autocommit, before the position, exactly where `applyOneImpl`'s `writePosition` branch puts it today. **Preserves:** H-4.
4. The position, LAST: `writePositionTx(…, at.Pos.Token, …, at.RowsApplied)`. The stream's `sluice_cdc_state` row is then locked only across COMMIT.
5. COMMIT (`commitWithTimeout`), then `marks.Committed(plan)`, then the `SchemaSnapshot` cache-after-commit as today.

**The skip path owes the checkpoint.** A barrier that the marks prove already applied returns today before opening a transaction. With `at != nil` it must still persist `at`: open the transaction, run steps 2–5 with no data, and commit. That is the `WriteCheckpoint` body, so share it rather than copy it. Otherwise the orchestrator's `checkpointWritten(ck)` would record a position that was never written: rows_applied would lose `ck.RowsApplied`, and `ck.ClosedTxs`' marks would never be deleted. The marks would not be deleted until the restart sweep, which is harmless but a leak. The position would also lag silently. It is reachable: a Postgres restart can record a GC-41 (j) keepalive boundary before the first re-delivered transaction's barrier, and that barrier is skipped on its own mark. The contract, stated on the interface: **a non-nil `at` is persisted whether or not c applies, or the call returns an error.**

**A non-foldable kind handed a checkpoint refuses.** MySQL's `ApplyBarrierChange` returns a named error, `BARRIER-FOLD-NOT-TRANSACTIONAL`, for a `Truncate` with `at != nil`, rather than writing a position after an implicit commit. It is a coordinator-bug tripwire, with the same shape as `FOLD-TICKET-DUPLICATE`.

**The tempting shortcut is three defects.** Implementing the fold as `applyOneImpl(…, writePosition=true)` (the per-change path, already in the same function) would:

- write the change's OWN token, `c.Pos()`. That is mid-transaction on a marker stream: file/pos crash-loops on resume. For a `SchemaSnapshot` it is `0/0` (Bug 158).
- write `RowsAppliedDelta(c)` instead of `at.RowsApplied`, so rows_applied double-counts the row at its later boundary.
- call `marks.CloseOpen()`, which on the lane path closes T itself, because `Decide` noted T open (`applymarks.go:276`). `Plan(gc=true)` would then **drop the barrier's own mark**, and a crash after the commit would duplicate a keyless row **silently**.

Each of the three is a mutation in §E.10.

**In-place retry.** The barrier path has none. An `ApplyBarrierChange` error ends the run and the ADR-0038 re-entry re-reads the position and the marks. The one write the coordinator makes after a failed fold is review F1's fallback (§E.14), which writes the fold's checkpoint on its own. That write would double-count `RowsApplied` on top of a COMMIT that landed, and an earlier cut of this paragraph said "cannot double-count" while F1's fallback made it false. It is skipped for exactly that case: the engines wrap a fold's COMMIT-step error with amendment D's `CommitOutcomeUnknown`, and `barrierFoldFailed` does not write after one (review 2, pinned by `TestLaneBarrier_FoldCommitStepErrorIsOutcomeUnknown`). So a COMMIT whose outcome is unknown cannot double-count `RowsApplied` here, for the same reason amendment D's lane batches cannot (M8 there): nothing is written again after it. The late-landing COMMIT residual §D.2 describes (a Bug-56 watchdog that abandons a COMMIT which then lands after the re-entry read) applies here exactly as it already applies to today's barrier and checkpoint commits. The fold neither widens nor closes it. UNVERIFIED as there.

#### E.5 Soundness, per crash point, and the delivery guarantee

The skip rule is sound iff amendment C's (i)–(iii) hold. (i) is untouched. (ii) is unchanged: the drain makes every earlier change of T durable before the barrier's mark commits. For (iii) the fold makes amendment D's key invariant hold for barriers too: **the mark set moves from T−1 to T in the same target transaction that moves the persisted position from T−1's start to T's start.**

| Crash point under the fold | Persisted position | Durable marks | Restart |
|---|---|---|---|
| before the barrier's transaction commits | P_prev (the last count, idle, fence or barrier write) | at most those of the first transaction after P_prev (amendment B's invariant): the closed-delete did not land either | (iii) holds, because every marking path (serial, barrier, fence, fold) persists its transaction's start before or with its marks, and every position write that passes a transaction deletes its marks. The replay delivers that transaction first, trusts its marks, and re-applies everything else. The barrier is not durable, so it applies once. **Converges where today converges.** On a KILL the replay starts at P_prev instead of T's start, the same distance every non-barrier lane crash point already has. That equivalence holds for kills (and stops) only: as first implemented, a fold that FAILED — including on a transient error, since a barrier has no in-place retry — also left P_prev, where the two-commit order had already persisted T's start, widening the replay of every barrier failure. Corrected 2026-10-06 (§E.14, review F1): a fold that fails while the run is not cancelled makes ONE best-effort attempt to write its checkpoint on its own before the run ends. That attempt runs on the pool that just failed, so after a reparent or a dead connection it usually fails too (a WARN, and the replay stays at P_prev); and it is skipped when the fold's COMMIT step failed, whose outcome is unknown (review 2). So the corrected distance is the usual case, not a guarantee. With `--exactly-once-lanes` off, that wider replay can meet more unmarked secondary-unique lane changes and hit amendment C's documented LOUD collision more often. It is never a skip (no mark names a later transaction). |
| after the barrier's transaction commits, before a checkpoint passes T | T's start | T's barrier marks (T−1's deleted in the same commit) | identical to today's third row: the barrier is skipped on its own mark, **exactly-once** |
| torn commit (vtgate MULTI sidecar, Neki) | see §E.6 | | |

**The delivery guarantee does not change, in either direction.** Exactly-once where marks are written, and at-least-once (keyless) or loud (PK change) where they are not. It cannot get BETTER for the no-marks cases. The only position the fold may legally write is T's start, which precedes the barrier, so a replay re-delivers the barrier whatever is folded. Making a no-marks barrier exactly-once would need the barrier's OWN position. On a marker stream that is a mid-transaction position and illegal. On the marker-less trigger sources it would be legal, but their keyless tables are refused at the source and their PK changes are marked, so there is nothing to gain. Not proposed. It does not get worse either: every state the fold can leave is a state today's code can leave (P_prev with its marks; T's start with T's marks). The intermediate state "position at T's start, barrier not applied" disappears, and it was harmless. *Correction (2026-10-06, review of §E.14):* as first implemented this paragraph was false in two places, both now fixed. A fold that was the run's FIRST close ran the restart sweep inside the barrier's own transaction, and the sweep closed the barrier's transaction whenever its loaded marks were untrusted — so the fold dropped the barrier's new mark, a state the two-commit order could not leave (F2). And a failed fold left P_prev on errors, not only on kills (F1). See §E.14's review section.

**Independent expected value.** For correctness, the source's own final table state (`SELECT … ORDER BY` key, or an md5 over it, read from the SOURCE) against the target after the kill and restart. At the kill, the persisted position is checked against the source-derived transaction boundary (`gtid_executed` / `@@gtid_binlog_pos` / the last `BEGIN` in `SHOW BINLOG EVENTS`, the existing `assertMarksNameTheInterruptedTx` helpers). On Postgres sources, the position check plus "marks for one transaction" plus "no `APPLY-MARK-UNTRUSTED`" stand in, as in amendment B's pins. For performance, fencebench's `fb verify`: a full-row SHA-256 of every table on both sides, read by the harness, not by sluice. Neither rides the code under test.

#### E.6 Torn commits: vtgate MULTI with `--control-keyspace`, and Neki

**The position component of the fold is tear-safe in BOTH orders.** The folded position is T's start, which vouches only for changes at or below seq−1, and the drain made those durable before the barrier's transaction began. If a tear lands the position without the barrier's data, the restart replays from T's start and re-applies the barrier, losing nothing. If a tear lands the data without the position, the replay starts earlier (the first row of §E.5).

**The marks component has the same tear-order premise it has today.** It is GC-41 (c)'s data-before-control rule: vtgate MULTI commits shards in first-touch order, which `TestVStream_ControlKeyspaceTornCommit_PositionStaysBehindData` (`mysql/control_keyspace_tear_vstream_integration_test.go:50`) pins for the serial batch hook. The fold keeps data first (§E.4 order), so it adds no exposure.

**One shape is new.** A barrier that writes NO control row today becomes a cross-keyspace transaction under the fold, because it now carries the position. This covers a no-identity or marks-unavailable keyless barrier and an absent-table skip. Today such a barrier is single-shard and its checkpoint is a separate single-shard commit; under the fold both ride one MULTI commit. By the two-order argument above it is harmless. It still gets its own real-tear pin (§E.10, P10), because "harmless by argument" on a commit protocol is exactly what GC-41 (c) found false once.

The Neki half (a Postgres target holding the control tables in an unsharded shard group and the data in sharded groups) is the **UNVERIFIED PREMISE** named in `postgres/apply_marks.go:20`, unchanged. The fold extends it to nothing new: the barrier transaction already carries marks to the control group today, and the position it adds is tear-safe by the argument above.

#### E.8 Interactions

- **Amendment D's fold and `--exactly-once-lanes`.** The two folds never coexist in flight. A barrier drains to seq−1, which includes any lane fold ticket below it, and a lane fence drains to its own seq−1, which includes any barrier. The two mixed orders keep today's outcomes. *Lane fold first, then a barrier of T*: the lane fold claimed T's start, so the barrier's `nextCheckpoint` finds nothing new (case b) and folds no position. That is the same "pre-apply checkpoint writes nothing" `TestOrchestrator_BarrierAndFoldInOneTransaction` asserts today. *Barrier of T first*: the barrier folds T's start and `checkpointWritten` runs before the coordinator routes anything, so the later fence hits 5b, anchored with no ticket. That is the same as today, except that the start is written inside the barrier's transaction rather than before it. The flag gates nothing here. Barriers mark by default (amendment C), so the barrier fold is default-on, on both settings of the flag.
- **GC-41 (c) rosters.**
  - `TestWriteCoreRoster_EveryControlWriterCallerIsClassified` (both engines) already lists `laneApplierAdapter.ApplyBarrierChange` as the `lane-barrier` core. Any new helper (the shared checkpoint body; a fold-aware `applyOneImpl` signature) must be classified, and the AST walk fails until it is.
  - `TestWriteCoreStatementOrder` (both engines) drives `lane-barrier` today with no position. It must drive it WITH a `BarrierCheckpoint` on every IN kind, and require data before control and the position LAST.
  - `TestLanePositionWriterRoster` (both engines) classifies `ApplyBarrierChange` as "position-free … reached only by bare-name matching". That becomes false, so it moves to a real class, `barrier-fold`, with the fold core's checks: `Committed` called, its COMMIT called, the checkpoint's post-commit trail matched, and on Postgres the `synchronous_commit` pin. Its direct-call checks must bind to the function that actually opens and commits the transaction (today `applyOneImpl`), not to the one-line adapter, or they would grade a method that calls neither.
- **Slot-ack read-back** (`releaseDurableSlotAck` → `ReadPosition`, `pipeline/streamer_slot_ack.go:102`). It releases only what the target has persisted. The folded position becomes visible only when the barrier's transaction commits, and it vouches only for drained changes, so the ack can never pass a change the target does not hold. Holds, for the reason §D.9 (2) gives for the lane fold.
- **The warm-resume door** (`checkSlotNotAckedPast`, `postgres/cdc_resume_ack.go:185`). It is sound while the persisted position never moves backward. The folded value is the one `writeCheckpoint` would have written (same `nextCheckpoint`, same seq guard, single writer), so monotonicity is unchanged. Pinned by extending `TestOrchestrator_PositionWritesTotallyOrdered` to barriers (§E.10, P5).
- **Skip ledger (H-4).** It is flushed in the barrier's fold before the position (§E.4 step 3), where today's pre-apply `WriteCheckpoint` flushes it. A barrier that itself skips for an absent table records its skip in the same call, so the flush covers it too, which is earlier than today and harmless: the ledger is a counter, and a crash before the position re-counts, exactly as H-4 accepts on the serial path.
- **GC-42 key-scoped guard.** It runs in `dispatch` on barrier changes too (Postgres `change_applier.go:1849`, MySQL `checkKeyScopedResult`). A refusal now rolls back the folded position with the data, so the restart replays from P_prev instead of T's start. `ErrKeyScopedWriteMatchedMultipleRows`'s premise ("a restart replays the same source changes in order onto the same committed rows, so the write matches them again", `ir/restart_refusals.go:48`) still holds. The extra replayed prefix is idempotent, or is skipped on its marks (the transaction at P_prev is delivered first), so it reaches the same rows.
- **Bug 294 / 295 (`partCommitted`).** Computed from the drain before the checkpoint, and unchanged.
- **The restart sweep.** `CloseTxs` runs the sweep at the run's first close. If that first close is now a barrier's fold, the sweep's deletes ride the barrier's transaction instead of a checkpoint's. The set is the same.

#### E.11 `-race`

There is no new goroutine and no new shared state. The fold's bookkeeping is coordinator-local, and the engine side touches only the already-locked `applymarks.Tracker`. #### E.12 Findings made while checking (pre-existing; none introduced or changed by this amendment)

- **F-E1, the broker duplicates keyless rows on a re-run. HIGH, silent, by code reading, NOT reproduced; the grade is a hypothesis until a repro.** The precondition is a keyless table in the chain and an incremental interrupted after part of it committed: a target error, a SIGKILL, or a context cancel mid-apply, which `Run` logs as "context cancelled; exiting" and returns nil (`broker.go:547`). The mechanism has four steps:
  - `applyIncremental` streams every change at the PARENT token (BRK-1, `broker.go:1170`). That comment calls the result a "safe re-apply on restart".
  - The keyless guard (ADR-0089) and the lane barrier each commit keyless rows mid-incremental.
  - The broker's changes carry no `ApplyID` (`TestReplayPathsNeverFold`), so no mark exists.
  - The next run re-applies the whole incremental from the parent and re-inserts every committed keyless row, at exit 0.

  This is the concrete harm of operator decision 4 (the broker is out of ADR-0190's scope), and it reaches the serial and lane paths alike. It is not a barrier-fold matter: the fold writes the same parent token. Remedy options: refuse a keyless table on the broker, as `refuseKeylessRestreamOnAnchoredResume` does for an anchored backup resume (`pipeline/backup/backup.go:1791`); or give the broker chain-record identities and marks (decision 4's separate ADR). Either way, BRK-1's "safe re-apply" comment is a written invariant that is false for keyless tables.
- **F-E2, the stale barrier docs. LOW, doc drift.** `LaneApplier.ApplyBarrierChange`'s interface doc (`laneapply.go:195`: "writing its position + data atomically per ADR-0007") and the Postgres adapter's doc (`postgres/change_applier_concurrent.go:722`: "via applyOne, which writes the barrier's position + data atomically") both describe the pre-Bug-158 behaviour. The barrier has been position-free since. The implementation of this amendment rewrites both, since it changes that contract again.
- **F-E3, the GAP #48 / §D.7 claim that a `SchemaSnapshot` barrier carries DDL. A graded hypothesis that is false.** See §E.3. It moved the `SchemaSnapshot` kind from OUT to IN.

#### E.14 Implementation (2026-10-06)

Built on `ec5effd2` (after the F-E1 broker fix, as E-Q5 sequenced it). Every §E.4 point was re-checked against that code first; the design held as written, and the places the code made it take a particular shape are listed under divergences.

**What was built.** `laneapply`: `BarrierCheckpoint`, `FoldsBarrierCheckpoint` and the `at` parameter on `LaneApplier`, `BarrierFoldNotTransactionalMarker` (`BARRIER-FOLD-NOT-TRANSACTIONAL`) with `BarrierFoldNotTransactional`, and `Orchestrator.applyBarrier`: after `barrier`'s drain it either computes `at` with `nextCheckpoint` (the same function `writeCheckpoint` uses; `nil` for §E.4's cases (a) and (b)) and calls `checkpointWritten` only after the call returned nil, or, for a declined kind, runs the two-commit sequence verbatim. The interface docs were rewritten (F-E2). Engines: `applyOneImpl`'s `writePosition bool` became a three-way `positionWrite` (`noPosition`, `ownPosition`, `foldedCheckpoint(at)`), so the per-change path's own-token write cannot be reached with a folded checkpoint by construction (§E.4's three defects). The checkpoint's body is `writeCheckpointTx` — `CloseTxs(at.ClosedTxs)`, `Plan(pending, gc=true)`, the marks, the skip-ledger flush, then the position LAST — shared by `WriteCheckpoint` (through `commitCheckpoint`), the barrier fold (inside the barrier's own transaction, after its data) and the skip path (`commitCheckpoint` again). MySQL answers `FoldsBarrierCheckpoint = !Truncate` and refuses a `Truncate` handed a checkpoint before writing anything; Postgres answers `true`.

**Divergences and shapes the code chose, flagged:**

- **`WriteCheckpoint`'s skip-ledger flush moved inside its transaction**, after the marks and before the position (the §E.4 order, and where `applyOneImpl`'s own-position branch already flushed). It is still its own autocommit on the primary pool, still durable before the position commits (H-4). On MySQL it now also runs under the checkpoint's exec-timeout context.
- **The own-position branch was factored out** as `writeOwnPositionTx`, so `applyOneImpl` reads as data → marks/position → COMMIT. The GC-41 rosters were reclassified to match: `writeCheckpointTx` and `writeOwnPositionTx` are `control` writers and helpers in `TestWriteCoreRoster_*`; `applyBarrier` and `commitCheckpoint` are helpers; `applyBarrierNoPosition` is gone. `TestPositionWritersFlushTheSkipLedger` now grades the two new bodies instead of `applyOneImpl` and `WriteCheckpoint`.
- **`TestLanePositionWriterRoster` had to rebind the CHECKPOINT too, not only the barrier.** §E.8 asked that the barrier's checks bind to the function that opens and commits its transaction; `WriteCheckpoint` became a one-line adapter in the same change, so its checks would have graded nothing as well. Both now go through `laneTxBody` (`WriteCheckpoint` → `commitCheckpoint`, `ApplyBarrierChange` → `applyOneImpl`), with a stale-entry check (since the review, `checkLaneTxBodies` also requires each body to be reachable from its lane method and to call `BeginTx`). The barrier is the new class `barrier-fold`, with a floor.
- **A test seam**, `barrierFoldCommitHookForTest` on each `ChangeApplier` (nil in production), fails the barrier's transaction after its position is written: P7's failure arm.
- **P9's `ClosedTxs` half is unreachable, so it is not built.** A barrier the marks skip is always the run's trusted FIRST transaction (amendment B), so the only boundary a run can have recorded before it is a GC-41 (j) keepalive, which closes nothing. P9 therefore folds a checkpoint with no `ClosedTxs` (and a non-zero `RowsApplied`, to grade the contract rather than the keepalive). The `ClosedTxs` deletes on the commit path are P7's. The same fact is why the restart sweep cannot delete a skipped barrier's own loaded mark: `CloseTxs` returns before the sweep on an empty list. That is pinned only by these two tests passing, not by a test of its own.
- **P7's absent-table row grades the skip ledger as NOT in the transaction.** The flush is its own autocommit, so the failed arm has already counted the skip once and the replay counts it again: the over-count §E.8 accepts, written into the row so it cannot read as atomicity.
- **P12 is made deterministic with a held lane row.** The first cut lost a `select` race: once T−1's barrier returned, the coordinator's idle tick and T's first change were both ready, and when the tick won it persisted T's start itself, leaving T's barrier nothing to fold (and a mutant restoring the old order writes the same position). It was seen on the postgres-trigger pairs. T−1 now also updates a `po` row the cell holds with a target lock and releases after T is queued, so T's drain and fold run inside one `handle` call. On the marker-less trigger sources T−1's barrier is its own transaction, so an idle tick can still persist it first. There the cell accepts exactly that outcome (position = T−1's own ordinal, logged as ungraded) and refuses anything past it. The fold is graded on the six marker pairs.
- **The P5 model's barrier rows carry a position past their transaction's start** (`c<n>`), standing in for the mid-transaction own position no write may persist. That is how M-E2 shows up there.
- **`TestReplayPathsNeverFold` → `TestReplayPathsNeverFoldAMarkFence`**, with its scope stated in the doc (E-Q6).

**Independent review (2026-10-06): two MEDIUMs, both fixed.** Neither loses data outright, but both made "no delivery guarantee changes" false as first landed.

- **F2 — the fold's restart sweep dropped the barrier's own new mark (silent duplicate; reproduced on real Postgres).**
  - *Mechanism.* `writeCheckpointTx` runs `CloseTxs(at.ClosedTxs)` then `Plan(pending, gc=true)`. When that is the run's FIRST close, `CloseTxs` runs the restart sweep (`sweepLocked`), which closed the TxID of every loaded mark. That included the barrier's own transaction T, whenever T's loaded marks were untrusted because another transaction was delivered first. That is the APPLY-MARK-UNTRUSTED path, expected on a sharded VStream source where lanes are the default. `Plan` then dropped T's pending upserts and deleted T's old marks in the commit that re-applies T. The two-commit order swept in its own transaction, before T's change, so T's new mark survived.
  - *Harm.* A crash before a later checkpoint passed T re-applied T unmarked: a third copy of a keyless row at exit 0. The second copy is pre-existing (the untrusted re-apply).
  - *Fix, in the tracker so it covers every fold.* `sweepLocked` no longer closes a transaction this run has decided a change for and not yet closed (`t.open`). Such a transaction was re-delivered, so it is not stale, and a later position write that passes it closes it explicitly. Its loaded marks stay dirty, so that write deletes them.
  - *Reach, enumerated.* Every gc plan goes through `Tracker.Plan` (`TxMarks.Plan` delegates to it), so the fix reaches:
    - the barrier fold, both engines;
    - amendment D's `queueFold`, `execFold` (Postgres) and `writeFold` (MySQL). Each decides its batch's changes before its fold closes, so the fenced transaction is open.
    - **Exempt:** the serial paths (`commitBatch`, the per-change `ownPosition`, `persistSourceTxCommit`). `CloseOpen` empties `t.open` into `t.closed` before it sweeps, so their first close still passes every loaded mark at once — unchanged, and correct, because their position passes the open transaction in the same commit. Why that holds, from the code: every `CloseOpen` is immediately followed by a gc position write. That write is `persistSourceTxCommit` on the per-change path; on the batch loop it is `writeBoundaryOnly` under `CheckpointOnlyAtTxBoundary` or `commitBatch`'s own position write, both reached through `OnSourceTxCommit = a.marks.CloseOpen`; and it is `writeOwnPositionTx` for a change outside a source transaction. That write's `Committed` clears `closed`, so no closed set outlives the write it was computed for.
  - *Pins.*
    - `TestTracker_SweepSparesAnOpenTransaction` (unit, with the stale-mark control arm);
    - `TestLaneBarrier_UntrustedReloadFoldKeepsOwnMark` (real Postgres and MySQL; the reviewer's repro, with the two-commit order as the control arm).
- **F1 — a failed fold replayed from P_prev instead of T's start, on transient errors too.**
  - *Mechanism.* The lanes absorb transients in place, but a barrier has no in-place retry. So a Vitess tx-killer, a reparent or an exec timeout during a fold became an ADR-0038 re-entry from the previous checkpoint. Where that prefix's marks are absent or untrusted, it re-applied the prefix's keyless barrier rows silently, or hit amendment C's loud collision.
  - *Fix.* `Orchestrator.barrierFoldFailed`: a fold that fails while the run is NOT cancelled writes its checkpoint on its own (the ordinary `writeCheckpoint`; legal, since the lanes are drained), then the run fails with the barrier's error. This restores the old replay distance in the usual case, at no steady-state cost. It is ONE best-effort attempt on the same pool, not a guarantee: the failures it exists for — a reparent, a dead connection — often fail it too, and then it WARNs and the replay stays at P_prev.
  - *Commit outcome unknown (review 2, LOW).* As first fixed, the fallback also ran after a COMMIT-step failure. Such a COMMIT can still land after the Bug-56 watchdog gives up, and the second write then added the checkpoint's rows_applied twice. This was reproduced on real Postgres, with a deferred `pg_sleep` trigger against a 700 ms exec timeout: rows_applied was 10 for a checkpoint carrying 5. Position, marks and rows were correct. Now the engines wrap a fold barrier's COMMIT-step error, and `commitCheckpoint`'s, with amendment D's `CommitOutcomeUnknown`, so the two classifications cannot drift. `barrierFoldFailed` skips the fallback for it, and the replay is then whichever of the fold's position or P_prev is durable. Pins:
    - `TestOrchestrator_BarrierFoldFailureClaimsNothing`'s third arm: a seam whose fold lands and then reports the error gets no second write;
    - `TestLaneBarrier_FoldCommitStepErrorIsOutcomeUnknown`, on real Postgres: the reviewer's repro is classified unknown, and the fold's one increment is read back; a pre-COMMIT failure is NOT classified unknown.

    No real-MySQL pin: a COMMIT-step failure that lands needs a semi-synchronous replica that never acknowledges, as in §D.9. The MySQL wrap is the same code shape.

    Mutants, each caught by the arm built for it:
    - the orchestrator ignoring the classification → the third arm;
    - the orchestrator never falling back → the transient arm;
    - the Postgres engine not wrapping the COMMIT-step error → the engine pin's COMMIT arm;
    - the Postgres engine wrapping a pre-COMMIT error → the engine pin's pre-COMMIT arm.
  - *A cancelled run* (an operator stop) writes nothing. A cancelled context cannot write, and detaching from it would add a target write after the stop was asked for. The replay a stop leaves is a kill's at the same instant, which the two-commit order also left whenever the stop beat its pre-apply checkpoint.
  - *P4,* `TestOrchestrator_BarrierFoldFailureClaimsNothing`, now pins both arms. Transient: the checkpoint is written and its bookkeeping advanced. Cancelled: nothing is written and nothing claimed.

## Implementation status (2026-09-28, phases 1–5; shipped in v0.156.5)

**Phase 1 — identity: implemented as written.** `ir.ApplyID{TxID, Seq}` on `ir.Insert` / `ir.Update` / `ir.Delete`, the declaration `ir.ApplyIdentityProvider`, and a shared per-transaction stamper (`applymarks.Sequencer`). The MySQL/MariaDB binlog reader stamps the transaction's own GTID (MySQL `uuid:n`, MariaDB `domain-server-seq`) or, in file/pos mode, `filepos:<server_uuid>:<file>:<offset of the opening event>` (no `server_uuid` → no identity); the pgoutput reader stamps `pg:<system id>:<timeline>:<commit LSN>`. `Seq` is the per-table ROW ordinal as the reader emits it, after the reader's own table-whole scope gate and before every pipeline filter; a `--where` move-in / move-out rewrite carries the identity. Pins (real servers): `TestCDCReader_ApplyIdentity_{GTID,FilePos,MariaDB}_StableAcrossRedelivery`, `TestPGCDC_ApplyIdentity_StableAcrossRedelivery` (re-delivery from the prior commit position reproduces every `(TxID, Seq)`; the transaction identity is checked against the server's own GTID / `@@gtid_binlog_pos` / `server_uuid` / system id). **The §1 GTID replica premise is now VERIFIED**, not labelled: `TestCDCReader_ApplyIdentity_GTID_StableFromReplica` re-delivers a transaction from a replica booted with the minimum `--binlog-row-event-max-size` (anti-vacuity: the replica's binlog provably holds more `Write_rows` events for it than the primary's) and requires identical identities. The vtgate premise belongs to phase 4 and is untouched. The stamp set is gated: `TestApplyIdentityEngineListMatchesTheCode` (docsync) derives the stamping files from the AST and the covered packages from the capability pins, and holds the operator doc's `apply-identity-engine-packages` marker to them — which also makes "VStream and the trigger sources are unchanged" a checked statement (they stamp nothing, so their changes are never skipped).

**Phase 2 — serial and per-change: implemented as written, with one refinement to §3 GC.** `sluice_cdc_apply_marks` (`appliershared.ApplyMarksTableName`, on the control-table roster, placed on Neki, in `sluice control-tables ddl` for MySQL targets — and, since GC-40 (a) (evolution note 2026-09-30 in ADR-0165), in `sluice control-tables ddl --engine postgres` for Postgres targets too, where the role-based causes of `APPLY-MARKS-UNAVAILABLE` now reach the WARN because the other control-table ensures no longer run DDL on a current target) is created best-effort by `EnsureControlTable` (detect first); at every apply run the applier checks the table exists and that the role holds SELECT/INSERT/UPDATE/DELETE (Postgres `has_table_privilege`; MySQL no-row probes), else logs `APPLY-MARKS-UNAVAILABLE` and runs without marks (operator decision 2). Marks ride the per-change transaction (`applyOneImpl`) and the serial batch transaction (pipelined `pgxBatchTx`, the serial fall-back, MySQL's coalescing `mysqlBatchTx`), coalesced per key; a change whose dispatch skipped it (C-11 absent table) writes none. The skip decision, the tripwire and the scope refusal (`APPLY-MARK-MISMATCH`, terminal) are engine-neutral in `internal/applymarks`; the scope digest is the stream's row-filter hash. GC: the batch loop notifies the engine at every consumed `TxCommit` (`BatchConfig.OnSourceTxCommit`) before the position write, which then deletes the committed transaction's marks — and drops any of its marks still pending — in the same target transaction; `persistSourceTxCommit` does the same on the per-change path. Every cold-start entry (`coldStart`, `coldStartMultiDatabase`, the stopped-cold-start resume) clears the stream's marks through `ir.ApplyMarksClearer`, and `ClearStream` (`--reset-target-data`, decommission) clears them first. **Refinement (the restart sweep):** §3's sweep rule as written — "any mark loaded at start whose transaction was not re-delivered before [the first checkpoint] is stale" — is unsafe on the lane path, where a crash in the post-commit window leaves marks of transactions AFTER the first re-delivered one that the first checkpoint has not yet reached. The implemented sweep rests on an invariant instead of on timing: marks only ever exist for the FIRST transaction after the persisted position (amendment B carries the proof), so at the run's first transaction close every loaded mark is either that transaction's or stale, and all are closed together (`applymarks` `sweepLocked`; the crash gate asserts the invariant at every kill — "marks for at most one transaction").

**Phase 3 — lanes and barrier: implemented, with amendment A; lane-batch marks OPT-IN since amendment C.** Every lane change CHECKS the marks and is skipped when proven applied (also at route time, so it does not advance `rows_applied`). The barrier (`ApplyBarrierChange`) writes marks in its own transaction after its pre-barrier checkpoint. Ordinary lane batches (`ApplyLaneBatch`, both engines, including PG's serial fall-back) write marks ONLY with `--exactly-once-lanes` (amendment C) — by default they check marks but write none, and the fence does not run; with the flag they write the marks of the transaction the coordinator's mark fence cleared, in the lane's own transaction, and record them durable before the lane returns — so before the frontier can advance past them and a checkpoint close their transaction (amendment A; the first cut of this chunk had stopped here, with lane batches checking but not writing, because §3's lane protocol does not survive the post-commit window). The coordinator records each closed transaction and hands them to `WriteCheckpoint`, which deletes their marks with the position (`TestOrchestrator_CheckpointHandsEveryClosedTransactionOnce`); the fence is pinned on the orchestrator by `TestOrchestrator_MarkFence` (once per marked transaction, after every earlier change committed and the checkpoint persisted at the transaction's start; never for an idempotent-only transaction) and its route-time question by `TestWouldMark_AgreesWithDecide` / `TestLaneFence`.

**Pins.** `TestStreamer_CrashMidTxn_{MySQLGTID,MariaDB,MySQLFilePos}_ToPostgres`, `..._MySQLGTID_ToMySQL`, `..._Postgres_{ToPostgres,ToMySQL}` (the Postgres-source cells are new): the serial per-change, serial batched (including the over-cap split), lanes-per-change and **lanes-batched** cells now CONVERGE on all six pairs — target equals the source's own final state, the position advances, the stream's marks are gone afterwards (GC), and a PK-only table in the transaction wrote no mark. `lane_post_commit_window` (all six pairs) builds amendment A's counterexample on purpose: T1 updates and T2 deletes one row of the secondary-unique table on the lane batch path while the stream's position row is held locked on the target, so every checkpoint blocks while the lanes keep committing; the kill lands in that window, and the restart must converge (row 7 gone). Keyless cells (`keyless_*`, serial per-change / serial batched / lanes batched via the barrier) converge where two identical keyless rows used to duplicate. `pkchange_*` converge on the barrier's marks and the lanes' check of them. Refusal cells: `tripwire_digest_mismatch` and `scope_change` refuse with `APPLY-MARK-MISMATCH`; `marks_unavailable` (the table dropped, restart under `--schema-already-applied`) logs `APPLY-MARKS-UNAVAILABLE` and stops on the pre-ADR-0190 collision; `stale_mark_swept` plants two marks of a never-re-delivered transaction (the digest first checked against a real mark's): one on a key the replay applies, which must skip nothing, and one on a key nothing touches, which only the restart sweep can delete — the restart must converge with no mark left; `cold_start_clears_marks` (a `--restart-from-scratch` with no further source traffic, so no GC can mask it) leaves no mark. `TestChangeApplier_ApplyMarks_SecondApplyAfterTheTableVanished` (both engines) pins the disable on a SECOND apply run of one applier whose first run loaded marks — the shape a fresh applier cannot show, because its tracker starts disabled. **Phase 4 — VStream: implemented as written; the §1 premise VERIFIED.** Both VStream dispatchers — the tail reader (`vstreamCDCReader.dispatch`) and the snapshot stream's post-COPY pump (`vstreamSnapshotStream.dispatchCDCEvent`), which must name a change alike because a cold start's first delivery is re-delivered by the tail reader after a restart — now emit each shard transaction's `BEGIN`/`COMMIT` as `ir.TxBegin`/`ir.TxCommit` and stamp every row through the shared `vstreamTxState` (`mysql/cdc_vstream_apply_identity.go`): `TxID` = `vstream:<keyspace>/<shard>:<that shard's GTID component at BEGIN>`, `Seq` = the per-table row ordinal. `TxBegin` carries the pre-transaction merged VGTID, as the rows do; `TxCommit` the post-transaction one (the shard's VGTID event precedes its COMMIT). No identity is stamped for COPY rows (a start position with an empty GTID or a TablePKs cursor, until the stream-wide `COPY_COMPLETED` — a copy group's shard component does not advance per group, so every group would share one "transaction"; the snapshot stream's COPY rows ride the bulk queues and never reach a dispatcher), for a non-GTID component (`""`, `current`), or for any row from a `BEGIN` that arrives inside another transaction until the last open one commits (interleaved groups break the premise; WARNed once, never skipped — see the hardening paragraph below for why WARN and not a refusal, and how the emission stays balanced). **The premise** — vtgate re-delivers a shard transaction's ROW events in the same order on resume — is verified by `TestVStream_ApplyIdentity_StableAcrossMidStreamResume` against a real TWO-shard vttestserver: cross-shard transactions over two tables, then a resume from a stored mid-stream COMMIT position and one from a ROW's (pre-transaction) position; every re-delivered row carries its original `(TxID, Seq)` with the same content, and every re-delivered transaction comes back whole and in order (anti-vacuity: both shards, ordinals above 1 on both tables). **Behaviour change beyond the marks:** VStream is now a MARKER stream everywhere the change channel goes — the serial batched path flushes at each shard transaction's commit (ADR-0027 cohesion, as on the binlog reader), the per-change path persists the position only at `TxCommit`, the lane path records checkpoint boundaries only at `TxCommit` (the marker-less position-run heuristic no longer applies to VStream). **Finding-1 class on VStream, by symbol:** `maybeSnapshotSchema` / `maybeSnapshotSchemaCDC` emit a table's `SchemaSnapshot` at its FIELD event, inside a transaction, stamped with the CURRENT merged VGTID — the position after every shard's last completed transaction, never an earlier one; and since VStream now has boundaries, `schemaEventAtBoundary` keeps the serial batched path from persisting it mid-transaction anyway, per-change defers it (CDCPOS-2) and the lane frontier never records it. `dispatchDDL` / `dispatchCDCDDL` emit `Truncate` OUTSIDE any transaction, a statement boundary — unchanged. Pinned end to end by `schema_event_mid_txn_*` in `TestStreamer_CrashMidTxn_VStream_{ToPostgres,ToMySQL}`.

**Phase 5 — trigger sources: implemented with a DIVERGENCE from §1.** §1 proposed an empty `TxID` with the change-log id as a cross-change ordinal ("skip if the mark's id ≥ this id"). That is the cross-transaction skip rule amendment A rejected — sound only while no mark is stale, needing its own staleness guard — and it conflicts with the implemented zero-identity rule (empty `TxID` = no identity). The change log gives a persisted, unique, monotone id per change and NO usable transaction boundaries (pgtrigger records a txid, but concurrent transactions interleave in id order; SQLite/D1 record none). So each change is its own transaction: `TxID` = `<engine>:<change-log id>:<stamp>`, `Seq` = 1 (`triggercdc.ChangeApplyID`; pgtrigger `postgres-trigger:<id>:<txid>`, sqlite-trigger and its d1-trigger sibling `sqlite-trigger:<id>:<captured_at>` — the stamp was added by the review hardening below). No new skip rule is needed, because every path already keeps a marked change's predecessors out of any replay: the serial paths persist the position WITH the data at every flush on a marker-less stream, so an applied change is never re-delivered — `commitBatch` and `applyOneImpl` now close the stream's open transactions at every position write outside a source transaction, so those marks are never even written; the lane path fences before every marked change (amendment A) and each marker-less boundary closes the change before it (`laneapply` `settlePrev` → `closedTx`), so the checkpoint deletes its marks. The identity is stable by construction (a persisted column; no premise), pinned by `TestCapture_ApplyIdentityIsTheChangeLogID` (sqlite-trigger, re-delivery from a mid position reproduces every identity) and by the source-derived identity in `TestStreamer_CrashMidTxn_PgTrigger_*`'s `lane_post_commit_window` (the mark names exactly `min(id) > persisted last_id` in `sluice_change_log`). Cost: with `--exactly-once-lanes` (amendment C), one drain + checkpoint per marked trigger change on the lane path (secondary-unique tables, which the lane path already applies on a single lane); by default the lanes write no marks and the fence does not run. The barrier's drain and mark writes (keyless, PK-changing) apply regardless of the flag. The kill contract for a marker-less source is "position never moves backwards" rather than "unmoved" (it legitimately advances inside a source transaction). postgres-trigger refuses a keyless table, so it has no keyless cells.

**Review hardening of phases 4–5 (2026-09-28).** Four items from the review of the phase 4–5 commit.
(1) **A reset change-log id sequence could re-issue a marked name — MEDIUM-LOW, silent, fixed.** `<engine>:<id>` is unique only while the id sequence is never reset, and two operator actions reset it: on SQLite/D1 the `SLUICE-E-CDC-CHANGELOG-ID-REUSE` remedy said "set `sqlite_sequence.seq` to the watermark or higher", and exactly the watermark W re-issues W+1 — which is precisely the change a crash on the fenced lane leaves a mark for; on pgtrigger an `ALTER SEQUENCE … RESTART` or a teardown / re-setup is invisible to `verifyChangeLogSequence` (it grades configuration, not history). On a keyless target, identical re-inserted content passes the digest tripwire and no key collision is loud, so the new change was skipped at exit 0. The TxID now carries a stamp the change log persists with the row and a later capture cannot repeat: pgtrigger's `txid` column (`pg_current_xact_id()`, 64-bit epoch-extended, never reissued within a cluster, untouched by a sequence reset) and SQLite/D1's `captured_at` TEXT exactly as stored (millisecond wall clock). Both are re-delivered byte-identically, so the crash suites still converge. An empty stamp yields no identity rather than a repeatable one. UNVERIFIED PREMISES, named in `triggercdc.ChangeApplyID`: the SQLite/D1 stamp assumes the wall clock does not step back onto the marked change's exact millisecond across the reset; the pgtrigger stamp assumes the same cluster (a physical-backup restore rewinds txids) — each needs a reset AND a coincidence. The SQLite/D1 remedy now says "strictly above the stream's watermark" (the gate still accepts seq = W, which is visible to the poll; the remedy no longer leans on the stamp). Pins: `TestApplyIdentity_LoweredSequenceCannotReissueAMarkedName` (sqlite-trigger, unit) and `TestApplyIdentity_SequenceRestartCannotReissueAMarkedName` (pgtrigger, real PG) — each re-issues the marked change's id with byte-identical content (premise asserted from the change log itself), requires a real tracker loaded with the marked change's durable mark NOT to skip it on a keyless target, and carries a control that the same tracker DOES skip a change bearing the old name. Both trigger engines refuse a keyless SOURCE table, so "keyless" here is always the target.
(2) **Per-change fence cost on trigger sources — LOW, documented.** Each trigger change is its own transaction, so amendment A's fence (full lane drain + synchronous position write) is paid per marked CHANGE — secondary-unique, keyless-target, PK-changing — not per transaction. Stated in perf-parity row 44 and the operator doc; not benchmarked.
(3) **Sharded VStream: exactly-once across a crash is best-effort — INFO, documented.** A restart resumes every shard at once and may deliver another shard's transaction before the interrupted one; marks are trusted only for the first transaction a run delivers (amendment B), so the interrupted transaction's marks are set aside with `APPLY-MARK-UNTRUSTED` and it replays with the pre-ADR outcome — a loud collision at worst, never a silent skip. The `UntrustedMarker` doc, its WARN and the operator doc now say this is expected on a sharded keyspace rather than reading as a defect report. Unsharded keyspaces are unaffected.
(4) **Interleaved shard transactions: WARN kept, emission balanced — INFO, decided.** The phase-4 branch emitted `TxBegin, TxBegin, TxCommit, TxCommit` for interleaved groups, so the applier saw a boundary after the first `COMMIT` while the second group was still open. `vstreamTxState` now counts open transactions: the nested `BEGIN` and every `COMMIT` but the one that leaves nothing open are not emitted, so the applier sees ONE source transaction spanning the interleaved groups and persists no position inside it (the conservative bracket); rows from the nested `BEGIN` until then carry no identity. Refusal was rejected: those rows lose only the exactly-once optimisation and apply exactly as before ADR-0190, so no value is at risk, and a refusal would turn a shape the stream handled correctly into an outage. The premise "vtgate does not interleave shard transactions" is named UNVERIFIED PREMISE in `vstreamTxState.begin` (the multi-shard premise test saw none across 15 transactions — evidence, not a guarantee across vtgate versions). Pinned on both dispatchers by `TestVStream_NoIdentityDuringCopyOrInterleaving`.

**GC-41 (c) note (2026-09-30, post-release): sidecar control keyspace under vtgate MULTI — the tear goes the tolerable way, by design.** The "rows and their mark in one target transaction" premise assumes the transaction commits atomically. With a `--control-keyspace` sidecar the marks and the position live on another shard than the rows, and vtgate's `transaction_mode=MULTI` commits shard by shard in first-touch order, stopping at the first failure. v0.156.5–v0.156.6 touched the control shard first on the serial batch path, so a tear could commit marks and a position past rows that never landed — the silent state. Every write core now sends its rows first (`mysqlBatchTx.writeApplyMarks`; pinned by `TestWriteCoreStatementOrder` on both engines and `TestVStream_ControlKeyspaceTornCommit_PositionStaysBehindData`), so a tear instead leaves ROWS WITHOUT THEIR MARKS and the position behind them. That is the chosen trade: the replay re-applies the committed rows with no mark to skip them, which for a secondary-unique or PK-changing change is the pre-ADR loud collision and for a keyless table is a duplicate — at-least-once, not the exactly-once this ADR gives an atomically-committing target. Never a silent skip. A tear between two DATA shards is a separate class, not addressed by ordering.

**Not done here:** the broker (a separate ADR, operator decision 4). sqlite-trigger / d1-trigger have the reader pin but no crash-suite pair (the harness's crash source is a server; the marker-less apply logic they share is the pgtrigger pairs'). `-race`: this chunk adds shared state reached from the lane goroutines (`applymarks.Tracker`, `applymarks.LaneFence`) and a coordinator-side drain in the lane router — it lands through CI's `-race` Integration job before any tag.

## Open questions for the operator (as proposed; answered above)

1. **Marked classes.** This ADR marks only non-idempotent classes (secondary-unique tables, PK changes, keyless tables) to avoid doubling writes for PK-only workloads. The alternative — mark every change — is simpler to prove and costs one extra write per changed row. Recommendation: the classes.
2. **Missing mark table** (safe-migrations branch, non-owner role, `--schema-already-applied`). Recommendation: WARN (`APPLY-MARKS-UNAVAILABLE`) and run without marks, which is today's behaviour; the alternative is to refuse to start.
3. **Keyless tables.** Including them makes keyless CDC exactly-once across a crash (on an atomically-committing target; see the GC-41 (c) note), which is new behaviour beyond GC-38 (l). Recommendation: include, in Phase 2.
4. **The broker.** In scope for a later phase, or left to a separate ADR?
5. **VStream reader change.** Phase 4 changes what the VStream reader emits (transaction boundaries, the shard). It is the only way to give VStream a stable identity; confirm it is acceptable before that phase.
