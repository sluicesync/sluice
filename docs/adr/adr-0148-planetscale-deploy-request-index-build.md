# ADR-0148: PlanetScale deploy-request index build (auto-adjust for the deferred-index statement-time wall)

- **Status:** Accepted — **REVIVED and IMPLEMENTED (2026-07-15, roadmap item 67)** on the ADR-0162 foundations; see §Implementation below. The 2026-07-02 deferral (retained below as history) was overturned because its costs shrank to near zero: the shared PS API client, tolerant DR poller, skip-revert finalization, and the stale-branch freshness gate all shipped with ADR-0162, and the safe-migrations posture question dissolved into REQUIRE-on / never-toggle. The original prototype ground truth (endpoints, lifecycle states, findings #1–#7) remains the spec this implementation codes.
- **Date:** 2026-07-02 (prototype + deferral) / 2026-07-15 (implementation)
- **Related:** roadmap item 67; ADR-0162 (the expand-contract orchestration whose client/poller/freshness gate this reuses); ADR-0165 (`sluice deploy-ddl` — whose `legRunner` extraction this composes); `--upfront-indexes` (`ef07c1da`, the opt-in escape hatch — still the pre-copy alternative); ADR-0147 (OLAP count — the count-side sibling of the same errno-3024 wall); ADR-0107 (the telemetry client whose no-SDK posture started this lineage).

## Context

sluice defers secondary-index creation to a post-copy `ALTER … ADD INDEX`. On a large PlanetScale-MySQL target that ALTER runs synchronously and is killed by PlanetScale's max-statement-execution-time limit (**errno 3024**, ~900 s; live-proven: a 49 GB table's `ADD INDEX` failed at ~901 s), leaving the data copied but indexes uncreated.

Two workarounds exist or were considered:
- **`--upfront-indexes` (SHIPPED)** — build indexes before the copy so the INSERTs maintain them; no post-copy ALTER, so the wall is never reached. But it's an opt-in **reliability escape hatch, not a speed option**: benchmarked ~11× slower load (deferred 29 s vs upfront 333 s on 3.2 M rows / 4 indexes), because per-row B-tree maintenance is far costlier than a post-copy sort-based build. And it requires the operator to *know* to set it (a too-low auto-threshold would pay the 11× needlessly; a too-high one would still fail — the tier-dependent guessing problem).
- **A size heuristic** to auto-select upfront — set aside: the threshold is tier-dependent and a wrong guess is expensive both ways.

The only approach that **auto-adjusts in a single run with no guessing and no re-copy** — keeping the *fast deferred copy* AND avoiding the wall — is to build the deferred index through PlanetScale's **deploy-request workflow**, which applies the schema change to the production branch's data via VReplication (async, not bound by the statement-time limit). Note `SET @@ddl_strategy='vitess'` does NOT work directly on PlanetScale (the direct ALTER runs synchronously and hits errno 3024); the deploy-request workflow is the supported async path.

## Prototype (validated 2026-07-02 on a real PS-10)

The full chain was driven end-to-end via the PlanetScale API (raw HTTP + service-token auth, no `planetscale-go` SDK — mirroring the telemetry client) and **confirmed working**: an index added on a dev branch was deployed onto main's data (index present, data intact, planner uses it). Endpoints exercised: `POST …/branches`, branch password create, `ALTER … ADD INDEX` on the branch DSN, `POST …/deploy-requests` (branch→main), `GET …/deploy-requests/{n}` (poll `deployable`/`deployment_state`), `GET …/deploy-requests/{n}/diff`, `POST …/deploy-requests/{n}/deploy`, `POST …/deploy-requests/{n}/skip-revert`.

**Findings that shape the design:**
1. **Safe-migrations must be enabled on the target (production) branch** — deploy-request creation fails otherwise (`"…must be a branch with safe migrations enabled"`). Enabling it is a **behavior change**: with safe-migrations on, *direct* DDL is blocked, so every schema change must go through a deploy request. This is the biggest design consideration (auto-enable vs require, and the side effect on the operator's DB).
2. **No human approval was required for the service token** — the request became `deployable` (~8 s, once the diff computed) and deployed without a review step. Good for automation; some orgs may require review.
3. **Deploy lifecycle:** `open`/`pending` → `ready` (`deployable=true`) → `deploy` → `queued` → `complete_pending_revert`. Terminal success is `complete_pending_revert` (applied, with a revert window).
4. **The revert window holds the deployment "in progress"** — PS refuses to delete the DB (and presumably other lifecycle ops) until `skip-revert` finalizes it (or the window closes). sluice must `skip-revert` to finalize.
5. **Two extra credentials** beyond the data-plane DSN: a PlanetScale **API service token** (control-plane, deploy-request + branch + password scopes) and a **branch password** for the ALTER-on-branch step.
6. Small-table deploy was near-instant; a large table's deploy runs the index build via VReplication — real wall-clock but **async and not subject to errno 3024**.
7. **Safe-migrations enable/disable has a large propagation lag, which kills the per-table-toggle design (2026-07-02 follow-up prototype).** With safe-migrations ON, direct DDL is cleanly rejected with `ERROR 1105: direct DDL is disabled` (a detectable trigger). But after `disable` — even with the control-plane API already reporting `safe_migrations: false` — direct DDL stayed *blocked* for 100 s+ (never recovered in the observed window), and rapid toggling can leave the branch laggy/stuck. A ~100 s+ settle per flip is worse-than-the-wall when amortized per table, so **automatically toggling safe-migrations on/off per table (option (i)) is not viable.** The only workable shapes keep safe-migrations ON once enabled: a **one-way escalation** (direct DDL until the first errno-3024, then enable once and route all remaining post-copy DDL — indexes AND constraints — through deploy requests) or a **whole-run safe-migrations mode**. Both leave the operator's production branch changed (safe-migrations on, direct DDL disabled) unless restored afterward (which pays the same disable lag).

## Decision (proposed)

Make the deploy-request workflow the **automatic fallback** when a deferred `ADD INDEX` fails with errno 3024 on a PlanetScale target — not merely an opt-in mode. This is possible, and strictly better than a re-run, precisely because the deploy-request path builds the index **post-copy, on the already-migrated data** (via VReplication) — *exactly like the direct `ALTER` it replaces*. So when the direct deferred `ALTER` hits the wall, the data is already copied; sluice transparently rebuilds that same index via a deploy request on the existing data, with **no re-copy, no operator action, and no `--upfront-indexes` recommendation.** (This is the key asymmetry with `--upfront-indexes`, a *pre*-copy strategy that cannot be applied retroactively to an already-copied table.)

**The flow:** fast deferred bulk copy (unchanged default) → deferred `ADD INDEX` (unchanged default — fast for small/moderate tables) → **on errno 3024, per failed index/table:** create a dev branch off the target branch, apply the `ADD INDEX` to it, open a deploy request into the target branch, deploy, poll to `complete_pending_revert`, `skip-revert`, delete the dev branch → proceed. Implemented as a **thin HTTP client** in a new `internal/planetscale/deploy` package (no `planetscale-go` dependency — the telemetry client is the precedent).

`--upfront-indexes` remains an explicit opt-in (it avoids even *attempting* the doomed direct `ALTER`). The auto-fallback makes it optional, not required; the fast deferred `ALTER` stays the default everywhere and is only replaced when it actually fails. No size heuristic / guessing is needed for correctness — try-then-fallback beats a tier-dependent threshold.

**Cost of the auto-fallback — the burned attempt.** The direct deferred `ALTER` runs for ~900 s and fails before the fallback engages, so a large table pays that ~900 s once. This is the price of not-guessing. An optional future optimization — a cheap `information_schema.DATA_LENGTH` probe — could let sluice skip the doomed direct `ALTER` for *clearly*-huge tables (well past the wall on any tier) and go straight to the deploy request, avoiding the ~900 s waste, while still using try-then-fallback for the ambiguous middle. Not required for correctness; a perf refinement, and it pairs with (not replaces) the fallback.

## Open design questions

- **Safe-migrations: auto-enable vs require.** Auto-enabling changes the operator's production branch (direct DDL becomes blocked thereafter). Safer to *require* it be enabled and fail loud with a clear message if not? Or auto-enable with an explicit warning? Needs an operator-facing decision.
- **Credential UX.** sluice's migrate takes only a data-plane DSN today. This mode needs a PS API token + branch-password creation. How is the API token supplied (flag/env, mirroring the metrics token), and scoped?
- **Per-table vs whole-schema.** One deploy request per table, or batch all tables' indexes into one deploy request (fewer branches/deploys, but a larger single migration)?
- **Failure & cleanup.** Orphaned dev branches / open deploy requests on mid-workflow failure must be cleaned up (or `auto_delete_branch` on create); the revert window must be finalized. Idempotent re-run / `--resume` semantics.
- **Gating.** Only worth it above some size (below it the direct ALTER is faster and simpler) — pairs with the size-estimate work.
- **Batching the copy.** The dev branch needs the target schema to ALTER; confirm the branch-off-production semantics for a freshly-migrated (large) table and the deploy's VReplication timing at scale (the prototype used a tiny table).

## Consequences

- The true one-run auto-adjust: fast deferred copy + (on failure) async index build on the already-copied data, no errno-3024 wall, no re-copy, no size guessing, no operator action.
- **Subsumes the "(B) error-guided" idea** — no need to fail loud and tell the operator to re-run with `--upfront-indexes`; the fallback recovers automatically because the deploy-request build is post-copy.
- New control-plane surface in sluice (HTTP client + async workflow + branch/credential lifecycle) — the largest PlanetScale-specific integration to date, flavor-gated and engaged only on an actual errno-3024 failure (or via explicit `--upfront-indexes` to skip the attempt).
- Depends on an additional PlanetScale API credential and the safe-migrations prerequisite — the main UX costs.

## Deferral rationale (2026-07-02)

The prototype confirmed it *works*, but four findings turned the cost/benefit against building it now:

1. **The toggle-lag finding (finding #7)** kills the appealing per-table auto-toggle (option (i)); only a one-way escalation or a whole-run safe-migrations mode is viable, and both leave the operator's production branch changed.
2. **Two extra credentials + the safe-migrations prerequisite** are real UX + setup costs on a path sluice's other flows don't require.
3. **The benchmark quantified the gain it buys:** `--upfront-indexes` is only ~8–11× slower than deferred (5 M rows / 4 indexes: deferred 44 s vs upfront 363 s) — and that penalty is paid *only* on the opt-in large-PlanetScale case where deferred would otherwise **fail outright**. So the practical comparison is "`--upfront-indexes` completes in minutes" vs "a heavy async control-plane integration to shave those minutes." The former is good enough.
4. **The (B) hint closes the UX gap cheaply:** an errno-3024 index-build failure now points the operator straight at `--upfront-indexes` (`hints.go`), so no one is stranded on a cryptic error.

Net: ship `--upfront-indexes` + the hint; keep this ADR as the recorded, validated design to revisit if real users want the fast-copy-*and*-no-wall combination enough to justify the control-plane integration.

## Implementation (2026-07-15, roadmap item 67)

Shipped as the automatic fallback the Decision section proposed, simplified by the ADR-0162 posture. The layering keeps every boundary the architecture demands: the engine-neutral pipeline threads an opaque `ir.IndexBuildFallback` onto the target SchemaWriter (`ir.IndexBuildFallbackSetter`, mirroring the index-budget/tuner setters); the MySQL engine owns error classification and DDL re-derivation but never imports the control plane; the control-plane half lives in `internal/planetscale/expandcontract` (`IndexFallback`, composing the shared ADR-0165 `legRunner` the expand-contract legs and `sluice deploy-ddl` also ride); and the CLI is the composer.

**Trigger classes and posture.** The fallback engages on a deferred index build failing with errno 3024 (statement-time wall) or errno 1105 carrying "direct DDL is disabled" (the safe-migrations block), on both deferred-build call sites a PlanetScale target takes (whole-schema `CreateIndexes` and the VStream serial build-as-copied overlap) — the writer-side coverage is engine-method-wide, so it holds wherever the writer is ARMED. Mode reach (corrected by audit 2026-07-15 MED-A1 — the first cut ARMED only `migrate`, so the original "resume/restore/upfront" claim was true for the writer but not for the modes): armed on `migrate` (incl. `--resume` and `--upfront-indexes`), `restore` (Phase-4 `CreateIndexes`; on a chain the segment-0 full), the `sync start` cold-start deferred index phase (single- and multi-database; warm-resume builds no indexes), and — closing the MED-A1 residue tracked as gap #12 (2026-07-17) — the fleet `sync run` per-sync YAML specs and the `sync from-backup` broker's `--reset-target-data` chain reset-leg. The fleet carries the same `planetscale-*` keys `sync start` does (service token resolved env-first from `PLANETSCALE_SERVICE_TOKEN_ID`/`_TOKEN`, never committed to the YAML; the shared `planetscale-org` key is reconciled with the ADR-0126 telemetry opt-in exactly as the CLI does — a fallback-only arming turns telemetry off with a WARN at build, and passes config-load validation instead of tripping the all-or-nothing metrics refusal). The broker carries restore's flag set but has NO telemetry surface, so its `--planetscale-org` means only this fallback — no shared-org reconciliation — and stays explicit-only (no `PLANETSCALE_ORG` env binding) so an ambient var never silently arms a long-running broker. No unarmed siblings remain. It REQUIRES safe migrations already ON: sluice never toggles it (findings #1/#7 — the propagation lag kills any toggle-around design, and flipping it changes how every future schema change on the operator's branch must ship; the ADR-0162 refuse-and-name posture, adopted verbatim). With safe migrations on, the direct DDL that "fails" is in practice the instant 1105, so no ~900 s burn even without the probe; the 3024 class remains handled for the transitional states where direct DDL still executes.

**Arming (credential UX, answering the open question).** New optional `migrate` flags: `--planetscale-org` (env `PLANETSCALE_ORG`), `--planetscale-service-token-id`/`--planetscale-service-token` (env `PLANETSCALE_SERVICE_TOKEN_ID`/`_TOKEN`, the pscale-CLI convention shared with `expand-contract`), `--planetscale-database` (defaults from the `--target` DSN's database — the `--planetscale-metrics-db` convention), `--planetscale-branch` (default `main`), `--planetscale-deploy-timeout` (originally default 1h; **default `0` = unbounded since the 2026-07-30 revision below**). The MED-A1 widening carries the same flag set (same defaults) onto `restore` and `sync start`, with ONE reconciliation: those commands already had a `--planetscale-org` with the ADR-0107/0115 TELEMETRY meaning, so the one flag now names the org for BOTH consumers — each arms on its own token pair (metrics tokens → telemetry, service tokens → this fallback), a fallback-only arming turns telemetry off with a WARN instead of tripping the telemetry all-or-nothing refusal (a bare org, or a PARTIAL metrics pair, keeps that refusal — the typo-catch), and on those two commands the org flag deliberately has NO `PLANETSCALE_ORG` env binding (an ambient var would trip the telemetry refusal in pscale-shaped shells), so arming there requires the explicit flag while the service tokens still resolve from the env. Deriving org/database from the ADR-0107 telemetry flags was rejected simply because those flags exist only on `sync start`; only the org and token are genuinely new inputs. Arming is opportunistic and never a refusal: a planetscale target + org + token arms it; anything missing (or a non-planetscale target, since the env vars are ambient in pscale-shaped shells) logs a WARN at most and leaves the migrate byte-identical — the fallback only ever ADDS a recovery. The branch-password step needs no separate credential (finding #5's second credential is minted via the API, exactly as expand-contract does).

**Never worse than the status quo.** The fallback preflights once per run (branch exists + safe migrations on); any preflight failure — safe migrations off, bad token — is the `ir.ErrIndexBuildFallbackUnavailable` sentinel, on which the writer surfaces the ORIGINAL direct error so the existing errno-3024 `--resume`/`--upfront-indexes` hint path fires unchanged (with a WARN naming why the recovery didn't engage). A real deploy-request failure surfaces loudly as the reused `SLUICE-E-PS-DEPLOY-REQUEST-FAILED`, naming the DR number/state/URL and the direct failure it was recovering from. No new error codes were needed.

**Per-table batching (answering the per-table-vs-whole-schema question).** One dev branch + one deploy request per TABLE, carrying every still-pending index DDL for it: the writer re-probes the catalog after the failure (the Bug-131 detect-then-skip machinery), so indexes that landed before the wall are never re-sent, and the statements are the writer's own combined-ALTER emission (`emitCreateIndexesCombined`) — byte-identical to what the direct path would have run. Whole-schema batching was rejected: the failure is discovered per table, and a per-table DR keeps the diff, the narration, and a mid-run crash's blast radius one table wide.

**The DATA_LENGTH probe (the recorded optional optimization — included).** When armed, a cheap per-table `information_schema.TABLES` DATA_LENGTH read routes a clearly-huge table straight to the deploy request, skipping the doomed direct attempt. Threshold: 64 GiB, deliberately conservative — the sole ground truth is a 49 GB table dying at ~901 s (barely over the wall) on a small tier, and larger tiers build faster, so only well past that is "doomed on any tier". A mis-route is harmless in both directions (below: the wall failure still engages the fallback after the burn; above: the DR builds the same index correctly), and if the fallback turns out unavailable after a probe-skip, the direct attempt runs after all. On a 1105-refused branch the probe saves nothing (the direct attempt fails instantly) — stated honestly; its value is confined to states where direct DDL still executes.

**Speed expectations (stated honestly, in the narration too).** The deploy is VReplication — real wall-clock on large tables, async, unbounded by errno 3024, polled with `--planetscale-deploy-timeout` and the tolerant ADR-0162 state classification. (**Superseded by the 2026-07-30 revision below:** the poll is unbounded by default and the classification now covers the whole documented state enum rather than being tolerance-by-default; "real wall-clock on large tables" turned out to be the understatement that made the old default wrong.) The fallback's value is UNBLOCKING: the index lands on the already-copied data with no re-copy and no `--upfront-indexes` ~11× load penalty — not speed.

**Failure & cleanup (answering the open question).** Dev branch names are deterministic (`sluice-index-<10-hex sha256(table, pending DDL)>`, the shared `legBranchName` scheme); a leftover from a crashed run is refused by name with inspect/delete guidance, and `--resume` converges regardless — the index phase re-probes and rebuilds only what is still missing, so an already-deployed DR's indexes are simply skipped. Branches are deleted on every exit path (best-effort, cancel-immune, WARN on failure); `skip-revert` finalizes the revert window (finding #4), with a failure there a WARN, not a run failure. The shared `legRunner` includes the ADR-0162 stale-branch freshness gate (create → schema-compare → rebase-via-backup → coded `SLUICE-E-PS-BRANCH-STALE-BASE`), which also answers the old "branch-off-a-freshly-migrated-table" open question: branches CAN come up stale, and the gate handles it — without it, a stale index branch's DR would silently revert newer production schema.

**Impl note — one leg machine, three consumers.** The fallback composes the ADR-0165 `legRunner` extraction (item 66) verbatim — its `name`/`errPrefix`/guidance-string parameterization carries the index-fallback's `--resume`-centric recovery wording, its optional post-DDL `stage` hook applies a multi-index table's second-and-later statements (each FULLTEXT/SPATIAL must be its own ALTER) on the same branch before the single deploy request opens, and `preflightSafeMigrations` is reused wrapped in the unavailability sentinel so the coded refusal is only ever logged, never this path's run error.

**Impl note — the UNARMED path now advertises itself (added after a 122 GB field run).** The decision tree's first branch (`indexBuildFallback == nil` — no PlanetScale credentials supplied) originally ran the direct build and said nothing, so an operator who hit the very wall this ADR exists for was never told the automatic recovery existed. It now emits ONE WARN when — and only when — the direct build comes back walled (`isIndexBuildWalled`), naming `--planetscale-org`, the `PLANETSCALE_SERVICE_TOKEN_ID`/`_TOKEN` pair, and the safe-migrations-ON precondition. Scoping it to the walled shapes is deliberate: a successful build (every non-PlanetScale target, every table under the wall) and an ordinary DDL fault stay silent, so this is not chatter on the common path. It is the nil-case sibling of the pre-existing "deploy-request index fallback unavailable" WARN, and both directions are pinned (`TestCreateIndexes_NilFallbackWarnsTheWallIsRecoverable` over BOTH walled errnos, `TestCreateIndexes_NilFallbackStaysQuietOffTheWalledPath`).

## Revision — wait for the build, report it, and stop advising the destructive fix (2026-07-30, after a 122 GB field run)

The fallback did its job on a real PS-160: a 106 GB / 153 M-row `events` table with four secondary indexes correctly took the pre-emptive DATA_LENGTH branch, created the dev branch, applied one combined `ALTER … ADD KEY ×4`, and opened deploy request #1 in ~52 s. Then everything downstream of "the deploy started" was wrong.

**What the field run showed.** sluice polled for the `--planetscale-deploy-timeout` default of 1 h and exited non-zero with `SLUICE-E-PS-DEPLOY-REQUEST-FAILED` — "still deploying after 1h0m0s". PlanetScale's UI showed **60 % complete at 2 h 03 m**, throttled by the replication lag the VReplication build itself generates, projecting ~3 h 25 m. So sluice gave up at roughly **29 %**, and at this scale the timeout branch was the DEFAULT outcome, not an edge case. On the way out it tried to delete the dev branch, got `HTTP 422 (unprocessable): cannot be deleted while a deployment is in progress`, and logged `could not delete dev branch; delete it manually` — advising the one action that would have broken its own `--resume` recovery. The 422 was PlanetScale correctly refusing something sluice should never have asked for. Four separate defects, all in the poller.

**1. The deploy wait is now unbounded by default, and terminal FAILURE states still fail fast.** `--planetscale-deploy-timeout` defaults to `0` = wait for a terminal `deployment_state`, however long it takes (the zero value is the safe default per the v0.99.51 trap — every non-CLI construction gets zero, so zero has to mean the common intent). The deployable/review wait keeps a finite cap (`legHumanWaitCap`, 1 h) even then, deliberately: an unbounded wait is authorized for **machine work with visible progress**, never for a **human gate**, where waiting forever and hanging are indistinguishable. `expand-contract` / `deploy-ddl` keep their `--deploy-timeout 1h` defaults; `0` means unbounded there too.

**The state machine, enumerated.** The old poller knew 8 states by name and treated every other value as "keep waiting until the deadline" — right while a deadline was the safety net, wrong the moment there isn't one, because an unrecognized *terminal* state becomes an infinite spin. `internal/planetscale/expandcontract/deploy_state.go` now classifies PlanetScale's **whole documented 20-value `deployment_state` enum**, with a coverage gate (`TestDrStates_ClassifiesTheWholeDocumentedEnum`) asserting the table and the documented enum match in both directions:

| class | states | poller behaviour |
| --- | --- | --- |
| **in-flight** | `pending`, `ready`, `no_changes`¹, `queued`, `submitting`, `in_progress`, `in_progress_vschema`, `in_progress_cutover`, `in_progress_cancel`, `in_progress_revert`, `in_progress_revert_vschema` | keep polling; narrate |
| **terminal success** | `complete`, `complete_pending_revert` | proceed (`skip-revert` finalizes the revert window) |
| **terminal failure** | `error`, `complete_error`, `cancelled`, `complete_cancel`, `complete_revert`, `complete_revert_error` | fail FAST, coded `SLUICE-E-PS-DEPLOY-REQUEST-FAILED`, branch cleaned up |
| **human gate** | `pending_cutover` | stop and name the gate — *unless* `deployment.auto_cutover` is true, in which case PlanetScale clears it itself and the wait continues² |
| **unknown** | anything PlanetScale adds later | keep polling (the one surviving piece of the old tolerance) |

¹ intercepted earlier by the deployable wait's already-deployed refusal. ² sluice's own deploy requests come back `auto_cutover=true` (live-verified), so the downgrade lives in the poller rather than the table — without it the gate detection would fail perfectly healthy deploys. `in_progress_revert*` are in-flight because they resolve to `complete_revert*`, which is terminal-failure.

**2. Progress is reported.** The GET response has always carried `deploy_operations[]` / `deploy_operation_summaries[]` with `progress_percentage`, `eta_seconds` and `throttled_at`, plus `deployment.{table_locked,cutover_expiring,queue_paused,queue_pause_reason,auto_cutover}` and the DR's `approved`. None of it was read. `api.DeployRequest.Progress()` aggregates the operation rows — **lowest** percent and **longest** ETA across them (a deployment is only as done as its slowest leg), latest throttle stamp — reading `deploy_operations` and falling back to the summaries, because the response carries the same values in both and reading one location would go blind if PlanetScale ever populates only the other. The poller narrates on **state change, percentage change, or a new throttle stamp**, with a 5-minute heartbeat ceiling — never one line per poll, which at a 10 s interval over a 3 h build would be a thousand lines.

**The `throttled_at` wart, named.** It is documented as "when the deploy operation was **last** throttled", and it is **not a live gauge**. Measured on the live request: PlanetScale stamped it once at `00:21:59` — two seconds *before* the deployment's own `started_at` — and it had not moved 2 h 25 m later, on the very run whose UI read "This deployment is being throttled due to replication lag on your database" throughout. So the narration says "throttled at least once, last stamp …, PlanetScale records only the LAST throttle, so this is not a live gauge", and points at the honest live signal instead: an ETA that stops converging (measured 4435 s → 4299 s of ETA burned over 353 s of wall clock).

**The approval gate is ADVISED, not inferred.** A database requiring administrator approval would leave sluice waiting on a human. But `approved` cannot detect that — the live mid-build request read `approved=false` while deploying fine — so after 90 s of a non-deployable wait sluice emits one WARN naming the possibility and the URL, and says plainly that it cannot tell an approval requirement from a slow diff computation. A paused deploy queue (`queue_paused`, with PlanetScale's `queue_pause_reason`) gets the same treatment: one WARN by name, then keep waiting, because a held deploy is not an abandoned one.

**3. The dev branch is LEFT ALONE while its deployment is in flight.** The generalized `keepBranchError` now exempts the branch from cleanup on **both** non-terminal paths — the pre-existing deployable-wait timeout (audit L-D0-10) and the new deploy-wait/human-gate exits. sluice does not even *send* the DELETE (pinned on `deleteAttempts`, not on whether a delete succeeded — a `deleted`-only assertion would pass on exactly the refused-but-attempted request that was the bug), and every message that mentions the branch says it must be left alone and why: the running deployment depends on it, PlanetScale refuses the delete, and the `--resume` recovery needs the deployment to finish.

**4. A non-terminal exit is no longer called FAILED.** New code `SLUICE-E-PS-DEPLOY-REQUEST-INCOMPLETE` (runtime class) covers the three "nothing failed" shapes: a bound hit on a healthy progressing deploy, a request that never became deployable, and `pending_cutover` awaiting a person. `SLUICE-E-PS-DEPLOY-REQUEST-FAILED` narrows to what actually went wrong — terminal failure state, closed without deploying, empty diff, blast-radius stranger. Both rows updated in `internal/sluicecode` + `docs/operator/error-codes.md` under the parity gate. Messages on the INCOMPLETE path carry the observed state, the progress/ETA/throttle summary, the exact flag to zero out (per-consumer: `--planetscale-deploy-timeout` vs `--deploy-timeout`), and the leave-the-branch-alone instruction.

**5. Multi-table queueing — INVESTIGATED, NOT BUILT.** The question was whether N tables each needing a deploy-request index build should all be submitted upfront rather than submit-wait-submit-wait (serially, N × ~3.5 h). Established against the real API and PlanetScale's docs:

- **A database CAN hold multiple queued deploy requests** — PROVED. `GET /organizations/{org}/databases/{db}/deploy-queue` exists and is documented as "the current list of deploy requests **in the order they will be deployed**"; the deployment object carries `queued_at` and a `preceding_deployments[]` array. Queried live against the field run's database it returned the one in-flight entry (`state=in_progress`, `into_branch=main`, `preceding_deployments=[]`, `queue_paused=false`, `strategy=serial`).
- **But PlanetScale SERIALISES them per target branch** — PROVED by that same contract ("the order they will be deployed"), by `queue_paused` being documented as "whether the deploy queue for the **target branch** is currently paused", by the live deployment's `strategy: "serial"`, and by the deploy-request docs' "the deployment will begin **or be queued if there are other pending deployments**". **Submitting all N upfront therefore does not parallelise a single one of the builds.** Total wall clock is unchanged.
- **So queueing buys only sluice's own submit latency** — field-measured at ~52 s per table (branch create → password → branch ALTER → open DR). Against a ~3.5 h per-table build that is **~0.4 %**. It would also make the total ETA knowable upfront, which is a real but small UX gain.
- **And it costs a documented pile-up risk.** PlanetScale's own discussion #165: a deploy request stuck in `complete_error` "is blocking all other deploy requests", and the maintainer's explanation was that closing a failed DR "wasn't initiating an extra action that's needed to coax things past the failed state" — **PlanetScale support had to clear the queue by hand**. A fix was said to be forthcoming; whether it landed is NOT verified. Fanning out would put N open deploy requests and N dev branches in flight simultaneously on a path whose entire purpose is unblocking a stuck migration.

**Decision: keep the serial submit-wait.** Trading an N-wide blast radius and a documented queue-wedge failure mode for a 0.4 % saving is a bad trade, and the bottleneck the field run actually hit was sluice giving up at 29 % — which items 1–4 remove. (`SchemaWriter.CreateIndexes` builds tables serially anyway, so there is no existing fan-out to preserve.) If the knowable-total-ETA gain is wanted later it can be had **without** queueing: sum the DATA_LENGTH probe across the tables routed to the fallback and report an expected serial total before the first deploy opens. Filed, not built.

**Validation (this revision).** The `deployment_state` enum is the dispatched *family* here, so the pins walk all twenty values rather than a representative (the Bug 74 lesson applied to a state machine): every terminal-success state proceeds, **every terminal-failure state fails fast under an UNBOUNDED wait** (a misclassification would hang, so each case runs with no deadline and a test-side ctx converts a hang into a legible failure), every in-flight state keeps waiting, `pending_cutover` is pinned in both `auto_cutover` directions, and the coverage gate refuses a state that is in the code but not the fixture (or vice versa). Plus: the unbounded/bounded boundary at `pollDeadline` (a zero timeout used to be a deadline already in the past — an instant timeout), the human-wait cap, the narration cadence and content including the throttle caveat appearing exactly once, progress read from *both* field locations and from neither, the queue-pause and approval WARNs in both directions, and `deleteAttempts == 0` on all three keep-the-branch paths. The `api` package gained a **verbatim live fixture** of the mid-build response (`liveInProgressDeployRequest`, captured 2026-07-30 02:47 UTC) — the one fixture in that package that is ground truth rather than derived — pinning every field the narration reads, including `queue_pause_reason: null` decoding to `""` and `approved: false` on a deploying request.

**Validation.** Unit-pinned end to end: the engine half against a scripted fake driver (classifier matrix, both call sites, re-probe exclusion, batching, probe routing, unavailable-reverts-to-hint), the control-plane half against the same fakePS harness the ADR-0162 tests drive (happy path, safe-migrations-off, cached preflight, leftover refusal, coded DR failure, stale-base rebase). A live `psverify` run remains recommended before relying on it in anger — ADR-0162's live findings are the precedent — though the fallback reuses exactly the client verbs, poller, and freshness gate those findings already hardened.
