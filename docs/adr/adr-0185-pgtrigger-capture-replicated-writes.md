# ADR-0185: `trigger setup --capture-replicated-writes` — opt-in ENABLE ALWAYS capture for replica-role writes

- **Status:** Accepted — implemented 2026-08-27 (audit 2026-08-26 F1 full fix; operator-greenlit same day). Unreleased at time of writing.
- **Date:** 2026-08-27
- **Related:** audit 2026-08-26 **F1** (the blindness this closes) and **F1-REFUSAL-OPTION** (the refusal design this supersedes — see Alternatives); `preflight_replica_role.go` (the shipped WARN half, now the default-posture arm); the **F2** capture-shape door (`cdc_capture_shape.go` — grows the posture match here); [ADR-0066](adr-0066-postgres-trigger-engine-variant.md) (the trigger engine); Bug 164 / `postgres/change_applier.go` `replicaRoleSQL` (why sluice's own applier writes under replica role); `docs/dev/capture-completeness-matrix.md` §pgtrigger (the F1 row this moves from WARNED to opt-in CAPTURED).

## Context

The pgtrigger engine's capture triggers are plain `CREATE TRIGGER`, so PostgreSQL fires them for **origin** writes only: any DML executed under `session_replication_role = 'replica'` bypasses them entirely (observed on real PG 16; pinned by `TestReplicaRoleWrites_InvisibleToCapture_AndPreflightWarns`). Two real configurations write under replica role, and on both the sync exits 0 with rows silently missing from the target — the F1 HIGH:

1. **The source is a native logical-replication subscriber.** `CREATE SUBSCRIPTION` apply workers run under replica role, so every subscription-applied row is invisible to the capture. This pairing is natural on exactly the managed tiers the trigger engine targets — databases that can *receive* logical replication but cannot *serve* it (no slot creation) — and it is the topology behind the supported scenario this ADR enables: **locked-down primary → native subscriber → sluice trigger-capture → elsewhere** (fan-out from a replica of a primary you cannot install anything on).
2. **The all-sluice relay (A→B→C).** sluice's own Postgres applier issues `SET LOCAL session_replication_role = replica` on every apply tx when privileged (Bug 164), so a B→C pgtrigger capture forwards nothing an A→B sluice sync applies.

The v0.131.5 remediation shipped **detection** (the `SILENT-CAPTURE-GAP RISK` WARN at setup and every stream open) and deliberately deferred the full fix, because the obvious mechanism — `ENABLE ALWAYS` triggers, which fire under replica role too — turns shape 2 into an **echo loop**: the capture would see sluice's own applied rows and forward them as new changes, unbounded in a cyclic topology.

## Ground truth (real engines, 2026-08-27)

- `ALTER TABLE … ENABLE ALWAYS TRIGGER` makes both the row trigger and the FOR EACH STATEMENT truncate trigger fire under replica role in an ordinary session: replica-role INSERT/UPDATE/DELETE/TRUNCATE all captured (`TestCaptureReplicatedWrites_PostureAndEchoDoors`, PG 16).
- Through a **real native subscription** (two PG 16 containers, `CREATE PUBLICATION` → `CREATE SUBSCRIPTION`): replicated INSERT/UPDATE/DELETE land in the subscriber's change log as I/U/D, and — the cell that had to be observed rather than assumed, since the subscriber applies TRUNCATE via a separate executor path (`apply_handle_truncate`) — **replicated TRUNCATE fires the ENABLE ALWAYS truncate trigger and is captured as op='T'** (`TestCaptureReplicatedWrites_NativeSubscriptionRig`, observed sequence `IUDIIT`). No TRUNCATE residual needs documenting: the full DML+TRUNCATE surface of the plain capture is preserved under the opt-in.
- PostgreSQL has no `ENABLE ALWAYS` clause on `CREATE TRIGGER` itself, so the posture is a separate `ALTER TABLE … ENABLE ALWAYS TRIGGER` per trigger after each create.

## Decision

**The default posture is unchanged.** Plain triggers, origin-only capture, the existing WARN on both replica-role shapes — no upgrade changes any existing install's behaviour (a setup re-run without the flag converges an opt-in install back to plain).

**New opt-in: `sluice trigger setup --capture-replicated-writes`** (postgres-trigger only; SQLite/D1 have no replication-role concept — their triggers fire for every write already).

1. **ENABLE ALWAYS pairs.** `renderSetupDDL` emits `ALTER TABLE … ENABLE ALWAYS TRIGGER` for the row **and** truncate trigger of every table, so replica-role DML and TRUNCATE are captured. ~~The DDL event trigger is untouched — logical replication does not replicate DDL, so the event-trigger tier has no replicated-writes analogue.~~ **CORRECTED (audit 2026-08-31 A-1, see the implementation note below): the event triggers get `ALTER EVENT TRIGGER … ENABLE ALWAYS` too.** The struck premise is true of a native apply worker and does not cover the write class this opt-in admits — `session_replication_role='replica'` is an ordinary operator/ETL idiom, PostgreSQL filters event triggers by `evtenabled` exactly as it filters row triggers, and leaving them plain made replica-role DML captured while replica-role DDL stayed invisible.
2. **The posture is recorded** in `sluice_change_log_meta` (`capture_replicated_writes BOOLEAN NOT NULL DEFAULT FALSE`, schema_version 3 — the same meta-upsert pattern that recorded v2). The column is added by `ADD COLUMN IF NOT EXISTS` (one statement migrates fresh and pre-v3 installs alike) and is deliberately **not** in the internal-table column floor: readers default an absent column to false via a `to_jsonb` projection, so a pre-v3 install that never re-runs setup reads as what it is — origin-only.
3. **Echo-loop safety (the reason the fix was deferred, now a coded refusal).** When the opt-in is active AND the source carries sluice's own apply bookkeeping (`sluice_cdc_state` **anywhere in the database** — the same relay evidence the WARN keys on), sluice **refuses** with `SLUICE-E-CDC-TRIGGER-ECHO-LOOP`, naming the mechanism (the upstream sync's replica-role applied rows would be re-captured and forwarded as new changes) and the remedies (capture from the origin; decommission the upstream sync and drop its control table; or install without the flag). Enforced at **both** chokepoints — `Setup` (dry-run included) and every CDC open via `openCDCReader`, the shared chokepoint of `OpenCDCReader` (warm resume) and `OpenSnapshotStream` (cold start) — because the relay shape can appear after setup. A probe failure under the opt-in **fails closed** (a refusal-gating probe must not degrade to a pass; the SL-1 lesson); under the default posture a probe failure keeps the WARN-degrade.
4. **The subscriber shape under the opt-in is the supported case**: no WARN — the write class the WARN names is now captured. Without the opt-in, the subscriber WARN gains a steer to the new flag; the relay WARN states that the flag deliberately refuses on that shape.
5. **The F2 capture-shape door grades the posture, both directions.** The door used to accept `tgenabled` `'O'` or `'A'` blindly ("`'A'` is strictly-more capture"); it now demands the enablement **match the recorded intent** on both per-table triggers: opt-in-recorded-but-plain refuses (replicated writes silently uncaptured — the exact loss the opt-in closes), and plain-recorded-but-ALWAYS refuses (someone hand-flipped enablement into capturing replica-role writes without the echo-loop vetting — hand-flipped drift is exactly what the door exists for). `'D'`/`'R'` refuse as before under either posture; ~~the event trigger keeps its previous `'O'`/`'A'` acceptance, with the scope stated at the door~~ **— corrected by A-1: both event triggers are posture-graded in the same two directions, so the door reaches all four capture triggers rather than three of four.** The posture read itself fails closed at open.

## Alternatives considered

- **F1-REFUSAL-OPTION's liveness-graded refusal** (refuse at open when `sluice_cdc_state` has a *recently-heartbeated, not-stop-requested* stream row; override via an `--allow-replica-role-source` flag). Superseded, deliberately: that design graded the **default** posture's relay WARN into a refusal on live evidence. This ADR scopes the refusal to the **opt-in** instead, where the hazard is concrete (ALWAYS triggers + an upstream applier = echoes) rather than probabilistic — and keys it on control-table **existence**, not heartbeat freshness: a *paused* upstream sync resumes into the echo loop, so liveness grading would under-refuse exactly the operational lull in which an operator runs setup. The default posture keeps the WARN (both shapes can be intentional), so no override flag is needed — the escape from the refusal is not enabling the opt-in on a relay, which the message says.
- **Origin filtering / echo tagging instead of refusing** (capture replicated writes but suppress the sluice-applied subset — replication origins, txid bookkeeping, applier session markers). The genuinely full fix for relay topologies, and out of proportion: the capture function would need per-row origin evidence PG does not expose to triggers cheaply (`pg_replication_origin_session_setup` state is not visible to a plpgsql trigger without superuser-ish probing), and the supported scenario (native subscriber fan-out) does not need it. Recorded as the future direction if a real relay-with-opt-in demand appears; the refusal keeps the door shut until then.
- **ENABLE ALWAYS by default** (no flag). Rejected outright — it converts the relay WARN shape into a live echo loop on every existing B→C topology at upgrade time. The default posture is unchanged by design.

## Consequences

- The locked-down-primary → native-subscriber → sluice fan-out topology becomes a supported, tested configuration; the F1 matrix row moves from WARNED to **opt-in CAPTURED** (default stays WARNED, stated in the row).
- One new coded refusal (`SLUICE-E-CDC-TRIGGER-ECHO-LOOP`, registry + docrows + error-codes.md), enforced at setup and every CDC open.
- `ChangeLogSchemaVer` 2 → 3. No reader gates on v3 (the posture read tolerates the column's absence), so old binaries keep streaming from new installs; a pre-v3 binary re-running `trigger setup` writes schema_version 2 back down and plain triggers — the same accepted downgrade path v1→v2 had.
- **Residuals, stated:** (a) the echo refusal keys on *sluice's* apply bookkeeping in the capture schema — a non-sluice replica-role applier (pglogical, a custom applier) leaves no such evidence, and its writes are captured under the opt-in *by design* (that is the subscriber scenario generalized); if such an applier is itself fed from this capture's output, the operator owns that loop. (b) An upstream sluice sync applying into a *different* schema of the same database carries its control table there and is not probed — but its writes land on tables outside this capture's trigger set, so nothing it applies is captured either; the shapes fail together. (c) A subscription created with `copy_data = true` runs its initial tablesync under replica role too, so the opt-in captures the initial copy as ordinary I rows — genuine rows, but a large burst; the rig pins the live-apply path (`copy_data = false`) and this is noted rather than tested.
- Test surface: unit pins for the render shape (`TestRenderSetupDDL_CaptureReplicatedWrites`), the posture-matched door in both directions (`TestGradeCaptureShape`), and the CLI flag through the real kong parser (`TestTriggerSetup_CaptureReplicatedWritesFlag`, the Bug-180 lesson); integration pins for the mechanism (session + real-subscription, incl. replicated TRUNCATE), the echo refusal at all chokepoints, the WARN-unchanged default, and both posture-door directions with the setup-re-run repair (`TestCaptureReplicatedWrites_*`, per-PR pgtrigger shard).

## Implementation note (Bug 257, 2026-08-27): setup's own DDL must not poison the stream

The first release of this ADR (v0.133.0) made every `trigger setup` **re-run** over an existing event-trigger install self-poisoning: the `ADD COLUMN IF NOT EXISTS` meta migration rides every render and fires `ddl_command_end` even as a no-op, and the opt-in's two `ENABLE ALWAYS` ALTERs per table carry the `ALTER TABLE` tag — so the install's own `sluice_capture_ddl_trg` recorded sluice's setup statements as op='X' rows and the next warm resume refused `observed source-side DDL`, steering a full re-copy for DDL no operator ran. Every documented re-setup remedy (the subscriber WARN's steer to this flag, the posture-door repair, the PK re-bake) executed against a live stream hit it. Fresh installs were unaffected (setup's ALTERs precede `CREATE EVENT TRIGGER`).

The fix was **session-scoped suppression**, closing the class rather than the statement list: the setup plan is bracketed by `SET sluice.setup_in_progress = 'on'` / `RESET`, executes on ONE pinned connection, and the DDL capture function returns early when that GUC is set — so any current or future setup-emitted DDL is unrecorded while operator DDL from every other session (including DDL against sluice's own tables) records exactly as before. Two ordering consequences, both pinned: the capture-DDL function's `CREATE OR REPLACE` is the plan's FIRST DDL statement, ahead of every TAG-watched statement, because on the first re-setup over an OLD-function install the old body ignores the GUC and must be replaced before the meta ALTER it would record; and the alternatives (an internal-relation exemption in the reader — cannot distinguish the opt-in's user-table ALTERs from operator DDL, and narrows a refusal; setup deleting its own X rows by watermark — a delete span cannot be told apart from concurrent operator DDL recorded inside it, so a genuine refusal could be silently swallowed, and the deleted committed ids read as a change-log hole the stream must settle-prove before skipping) were rejected for the stated defects. Pins: `TestRenderSetupDDL_SelfDDLSuppression` (bracket + body check + function-first ordering, tags derived from the rendered event trigger) and `TestSetup_ReRunOverStreamedInstall_WritesNoSelfDDL` (real-PG: zero X rows and a CONSUMED warm resume after plain/opt-in/converge/old-binary re-setups, plus the over-reach direction — operator DDL still records and refuses). Residual, stated: an install already poisoned by a v0.133.0 re-setup still carries its X rows — this fix prevents new poisoning but does not consume old markers; recovery remains `--restart-from-scratch` (or a support-guided delete of the specific self-DDL rows). A polled-fingerprint-tier source that somehow retains an event trigger bound to a pre-fix function (privilege lost between setups) keeps the old body — setup cannot `CREATE OR REPLACE` a function it may not own — and is out of scope.

## Implementation note (audit 2026-08-31 SEC-2 / C-1): the suppression marker is a PRIVILEGE BOUNDARY, not an annoyance filter

The Bug 257 fix above is correct about *what* to suppress and wrong about *who may ask for it*. `sluice.setup_in_progress` is an ordinary dotted placeholder GUC, and PostgreSQL imposes **no privilege at all** on `SET`ting one in your own session — placeholders are created at `PGC_USERSET`. So `current_setting(guc, true) = 'on'` handed an off-switch for the engine's ONLY DDL-detection tier to every writer on the source. Observed on PG 16.14 with the function installed verbatim: an unprivileged role SET the marker, ran `ADD COLUMN` + `DROP COLUMN` + `CREATE INDEX`, and recorded **zero** `op='X'` rows while identical control ALTERs immediately before and after recorded normally. There is no second tier to catch it — the polled-fingerprint fallback was never implemented — so the stream keeps applying, and a hidden `DROP COLUMN` leaves the target holding the pre-DDL value forever at exit 0. The invariant comment that said "operator DDL … keeps recording" was, in exactly CLAUDE.md's sense, a hypothesis with no test behind it. Severity is MEDIUM rather than HIGH for a reason worth recording: to *hide* DDL you must be able to *run* it on a replicated table, i.e. own it, and such an owner already holds a residue-free lever the door never covered (drop the row trigger, do the DML, re-create it identically). What the GUC uniquely added was the only **non-superuser** way to blind the DDL tier specifically. That is a genuine, non-redundant hole in a safety net against accidental schema drift, and the fix is a few lines.

Separately (C-1, also observed), the marker's off-state rode a **trailing `RESET` statement**, which three paths never reach: an in-process mid-plan error (the exec loop returns immediately), an operator who pastes the `--dry-run` plan into psql under `ON_ERROR_STOP=1` and stops on a failure, and one who reviews the plan statement-by-statement and stops early. After any of those, the operator's own next `ALTER TABLE` in that session is silently suppressed — the exact silent-mis-capture class the event trigger exists to close, re-opened by the fix meant to protect it.

**The design.** Suppression is now bound to evidence the firing session cannot manufacture, and its off-state is structural:

- **The plan is one transaction.** `BEGIN` … `SET LOCAL sluice.setup_in_progress = 'on'` … `COMMIT`. PostgreSQL reverts `SET LOCAL` at **both** commit and rollback, so no error, cancel or abandonment can leave it set. Every statement the plan emits is transaction-safe (PG DDL is transactional, `CREATE EVENT TRIGGER` included — verified; the plan emits no `CONCURRENTLY`), which also makes the install atomic rather than half-applied. `Setup` additionally issues an explicit `ROLLBACK` on its error path so a pinned connection is never returned to the pool mid-transaction (pgx-stdlib's `ResetSession` is a liveness check only).
- **Two evidence arms in the capture function, neither of which accepts the marker value alone.** The STRICT arm requires the meta row to be *armed for this backend*: `pg_backend_pid()` equals the PID setup recorded, the marker equals a `gen_random_uuid()` nonce setup recorded, and the arm is fresher than one hour. Writing that row needs UPDATE on `sluice_change_log_meta`, and setup renders **no GRANTs** — verified: an unprivileged role gets `permission denied for table` on both SELECT and UPDATE, so the nonce is not merely secret, it is unreadable. The BOOTSTRAP arm covers the migration window only — the evidence columns absent (a pre-v4 install) or present-but-never-armed (`setup_nonce IS NULL`, true only between this plan's own `ADD COLUMN` and its arm) — and additionally requires `session_user = current_user`, which inside a `SECURITY DEFINER` body means "the firing session is authenticated as the install's own role" (ground-truthed: `session_user=app current_user=postgres`); changing `session_user` needs `SET SESSION AUTHORIZATION`, i.e. superuser. The disarm deliberately writes an empty-string sentinel rather than NULL so that arm is unreachable once any v4-aware setup has completed.
- **Fail-safe direction: an unreadable evidence read RECORDS.** Suppression is the privilege, so failing closed means capturing. `SELECT … INTO` over zero rows yields NULL and the guard tests `IS TRUE`; `undefined_table`/`undefined_column` routes to the bootstrap arm (which still demands the session_user evidence); any other exception sets the flag FALSE explicitly. Without that last handler the exception would propagate and *block* the operator's DDL, which is why the pin asserts the ALTER both succeeded and recorded.

**(a) PID reuse is bounded three ways, independently.** (1) The arm and the disarm both live inside the plan's transaction, so a completed plan leaves the row disarmed and an aborted one rolls the arm back — there is normally nothing to reuse. (2) The marker must equal the random nonce; a later session in a recycled PID that merely sets `'on'` fails, and reading the nonce requires privileges on an owner-only table. (3) The freshness window caps the one residue an operator can still produce by hand — pasting the plan and typing their own `COMMIT` between the arm and the disarm.

**(b) Hand-applied `--dry-run` plans keep working, and that is a design constraint, not an accident.** Nothing in the plan text is baked at render time: `pg_backend_pid()`, `gen_random_uuid()` and `clock_timestamp()` are all evaluated in the *executing* session, so the operator's own psql backend arms its own PID. The privilege boundary is the UPDATE on the meta table, not knowledge of a secret in the plan — which is what lets the same text be safe to print and still work when a human runs it. `set_config(name, value, is_local => true)` inside a `DO` block was verified on PG 16.14 to persist to end-of-transaction and revert at COMMIT. The plan must be applied **whole, in one session** — that was already true and is now structural: it opens with `BEGIN`.

**Ordering, which is load-bearing and was re-derived from the server rather than assumed.** Ground truth on PG 16.14: a no-op `CREATE TABLE IF NOT EXISTS` and a no-op `DROP INDEX IF EXISTS` produce **zero** `pg_event_trigger_ddl_commands()` rows, but a no-op `ALTER TABLE … ADD COLUMN IF NOT EXISTS` produces **one**. So the meta ADD COLUMNs fire on every re-run, and the plan arms *before* them; on a pre-v4 install that arm is a no-op (the columns do not exist), which is exactly the window the bootstrap arm carries, and the plan arms a second time after the migration so everything from there on rides the strict arm on every install vintage. The capture-DDL function's `CREATE OR REPLACE` stays the plan's first statement for the original Bug 257 reason.

**`ChangeLogSchemaVer` 3 → 4** (the three evidence columns). No reader gates on v4 — the capture function's own read tolerates their absence — so the lift stays bookkeeping. The columns are deliberately **not** in `internalTableColumnFloor`, for the same reason the v3 posture column is not.

**Residuals, stated.** (a) The boundary does not constrain the role that OWNS the install: it can write the meta table and therefore arm its own evidence. That role is superuser (it had to be, to create the event trigger) and can drop the event trigger outright, so the door never constrained it — but say it rather than imply it. (b) An operator who hand-applies the plan and types their own `COMMIT` between the arm and the disarm leaves an armed row; the freshness window bounds it to an hour, and re-presenting it also requires re-setting the marker to a nonce only that owner can read. (c) Existing installs keep the v0.133.1 marker-only body until `sluice trigger setup` is re-run — the same "the binary upgrade alone does not repair the database" shape as SEC-1, and the same remedy.

**Pins.** Unit: `TestRenderSetupDDL_SelfDDLSuppression` (transaction wrap, `SET LOCAL` with no session-scoped `SET`/`RESET` surviving, function-first ordering, an ARM before every watched-tag statement, the DISARM immediately before COMMIT — tags derived from the rendered event trigger) and `TestCaptureDDLSuppressionCheck_BindsToUnforgeableEvidence` (every conjunct the body must demand, plus a regex that fails if the v0.133.1 marker-only early return returns). Integration, real PG: `TestSetup_UnprivilegedSessionCannotSuppressDDL` — the audit's repro inverted, including the owner-with-marker-only arm and the fail-safe arm — and `TestSetupPlan_AppliedByHand` (a plan pasted into one session, abandoned mid-way and applied to completion; both must leave the marker unset and the operator's next ALTER recorded). `TestSetup_ReRunOverStreamedInstall_WritesNoSelfDDL` is unchanged in intent and still pins Bug 257 across the vintage matrix. Mutation-run in both directions: reverting the body to the marker-only check reddens the SEC-2 pin; reverting `SET LOCAL` to `SET` reddens the leak pin.

## Implementation note (audit 2026-08-31 A-1): the opt-in is a POSTURE for the whole install, not for the row tier

The first cut of this ADR set the row and truncate triggers `ENABLE ALWAYS` and deliberately left the DDL event trigger plain, on the premise recorded in the Decision above: *"the DDL event trigger is untouched — logical replication does not replicate DDL, so the event-trigger tier has no replicated-writes analogue."* The premise is true of a **native subscription apply worker** and does not cover the write class the opt-in actually admits. `ENABLE ALWAYS` fires for every replica-role write from **any** session, and `SET session_replication_role = replica` is an ordinary operator/ETL idiom — it is precisely how people suppress FK and user triggers during a bulk load. PostgreSQL filters EVENT triggers by `evtenabled` exactly as it filters row triggers (observed on PG 16: with `evtenabled='O'`, an `ALTER TABLE` under `origin` and under `local` recorded, the same ALTER under `replica` did not; `ALTER EVENT TRIGGER … ENABLE ALWAYS` restored it).

So the opt-in produced the first configuration in which the two capture tiers could **disagree**: an ETL session doing `SET session_replication_role='replica'; ALTER TABLE orders DROP COLUMN legacy_note; INSERT INTO orders …` had its INSERT captured with the post-DDL row shape and its ALTER invisible, so the applier wrote that row into a target still carrying the dropped column and the stream never refused. Under the DEFAULT posture the tiers are consistently blind (that is F1, a different and stated gap); the opt-in is what made them inconsistent.

**The fix is the whole-install posture.** `renderSetupDDL` now emits `ALTER EVENT TRIGGER … ENABLE ALWAYS` for **both** event triggers (the `ddl_command_end` arm and the `sql_drop` arm added by D-1 in the same release) whenever the flag is set, and the F2 capture-shape door grades all four triggers against the recorded posture in both directions — `'O'` under a recorded opt-in refuses (replica-role DDL undetected while its DML is captured), `'A'` under a recorded plain install refuses (hand-flipped drift). The door's previous `'O' or 'A'` acceptance for the event trigger is gone; the scope note that justified it is corrected at the door.

**Compatibility, stated plainly:** an install created by v0.133.x–v0.134.x **with** `--capture-replicated-writes` has plain event triggers and a recorded posture of `true`, so after this upgrade its next CDC open **refuses** with the message naming `sluice_capture_ddl_trg` and the remedy `sluice trigger setup --capture-replicated-writes`. That is deliberate and is the same direction ADR-0185 already took for the per-table pair: the alternative is streaming on with a known tier disagreement. The re-run is seconds and preserves the change log, its watermark and the consumer registry. Default-posture installs are unaffected.

**Why a refusal here and a WARN for the D-1 arm's absence** (they look similar and are not): a posture MISMATCH is an install that claims a capture guarantee it is not delivering, and the operator explicitly asked for that guarantee. A missing `sql_drop` arm is an install that never claimed the guarantee at all — refusing it would strand every pre-v0.135 sync at the moment the binary is upgraded, for a gap that is bounded and static. Same reasoning as SEC-1's `INSECURE-CAPTURE-FUNCTION` WARN.

**Gate.** `TestCaptureTierRoster_EveryEmittedTrigger` (`internal/engines/pgtrigger/capture_tier_roster_test.go`) derives the roster from the statements `renderSetupDDL` emits: every created trigger must be classified, every classified trigger must be `ENABLE ALWAYS` under the opt-in (or carry a written exemption), the plain render must set nothing, and each event trigger's tags must be recordable by its own arm. A new capture trigger that nobody classifies fails the build. Its scope is the rendered SQL only — the server-behaviour halves are `TestCaptureReplicatedWrites_ReplicaRoleDDLIsCaptured` (plain 'O' records nothing under replica role while origin DDL does; opt-in records the ALTER *before* the INSERT it reshapes; a replica-role DROP of a captured table records too; both posture-door directions with the setup-re-run repair) and `TestCaptureDropTier_DDLCommandEndIsBlindToDrops`.

## Implementation note (audit 2026-08-31 SEC-4 + A-5): the echo-loop refusal probes the DATABASE, not one schema

The refusal's evidence probe scoped its existence check to pgtrigger's own capture schema (`AND n.nspname = <the DSN's schema>`). The evidence it looks for does not live there by construction: the upstream sluice applier pins `sluice_cdc_state` to the **target DSN's** schema at construction, and `--target-schema` (ADR-0031) deliberately moves the *user data* to another namespace **without** moving the control table — `internal/engines/postgres/change_applier.go` says so where it does it. So an A→B sync with `…?schema=public --target-schema customer_svc` lands rows in `customer_svc` and its bookkeeping in `public`, and a `trigger setup --dsn '…?schema=customer_svc' --capture-replicated-writes` on B probed the one schema that could not hold the evidence. The refusal did not fire and the `ENABLE ALWAYS` triggers went in on exactly the relay topology it exists to stop. The plain posture's `SILENT-CAPTURE-GAP RISK` WARN shares the probe and therefore shared the blind spot.

The hazard is a property of the **database**, not of a schema: any schema's applied rows are replica-role writes the `ENABLE ALWAYS` triggers capture. The existence half is now database-wide (system namespaces excluded — a `pg_temp_N` table dies with its session and can be nobody's durable bookkeeping) and the message **reports the schema(s) where the evidence was found**, so it stays actionable when that is not the capture schema. The per-hit `count(*)` stays schema-qualified: it is detail, and a failure there degrades the message rather than the signal.

The same change spends the count's validity, which both consumers had computed and discarded (audit A-5): a denied or lock-parked `count(*)` rendered *"0 registered stream(s)"* inside a refusal that fired precisely **because** the table is there — a zero indistinguishable from a genuinely empty control table, pointing the operator at the "decommissioned residue, drop it" remedy on evidence nobody read. It now says `stream count unavailable — the detail read failed`, and a real zero still reads as a real zero.

**Gates.** `TestCaptureReplicatedWrites_PostureAndEchoDoors/relay artifacts in ANOTHER schema…` plants the control table in a schema other than the capture schema on a real PG and requires the coded refusal at the open and at `Setup`, plus the plain posture's WARN naming that schema; `TestRelayControlTableRendering_HonoursCountValidity` pins the A-5 half (unread vs genuinely-zero must stay distinguishable) and `TestProbeRelayControlTable_ExistenceQueryIsDatabaseWide` fails if the schema predicate ever comes back. Mutation-run by restoring `AND n.nspname = $2`: the integration pin reports `CDC open succeeded` — the shipped pre-fix behaviour — and the query pin fails.
