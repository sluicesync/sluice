# sluice v0.156.7

**CRITICAL fix — two silent-loss paths in change streams (GC-41).** (1) Through v0.156.6, `sync` from a Postgres source to a MySQL, MariaDB, PlanetScale or Vitess target acknowledged the replication slot past changes the target had not yet written. A run that ended by Ctrl-C, crash, kill or an apply error while changes sat in an apply batch lost those changes, and the next start resumed past them at exit 0. (2) On v0.156.5 and v0.156.6, a Vitess or PlanetScale target with its control tables in a sidecar keyspace (`--control-keyspace`, or auto-detected on a sharded target) could, on the serial batch apply path, commit the stream's position ahead of rows that then failed to commit, losing them at exit 0. Also fixed: a HIGH crash loop (Bug 293) that left duplicate rows in keyless tables, and a HIGH Postgres → Postgres slot that never advanced on the default apply lanes (unbounded source WAL retention). A new warm-resume check, `SLOT-ACKED-PAST-TARGET-POSITION`, refuses a resume that would skip a gap instead of skipping it. **Upgrading does not repair data an older release already lost.** Operators of the affected configurations must check their targets; read **Who needs this — action required** first. **Not a silent drop-in:** a resume can now refuse, and `sluice sync run` no longer restarts a leg on five more refusals that every restart repeats. See **Compatibility**.

## Features

**`sync start --accept-slot-acked-past-position=<LSN>`: a one-shot acknowledgement of the new `SLOT-ACKED-PAST-TARGET-POSITION` refusal (Postgres source).** The value must be the exact `confirmed_flush_lsn` the refusal printed; any other LSN is refused. So the flag cannot pre-accept a later refusal if it is left in a service definition. It is not accepted as a `syncs.yaml` key. Use it only after verifying that the target already holds every change up to that LSN, for instance because every change in the gap was outside the stream's filter. The stream then resumes and the gap is skipped. The normal remedy is a re-copy with `--restart-from-scratch`. See the GC-41 (h) entry under **Fixed**.

## Fixed

**`sync` from a Postgres source to a MySQL, MariaDB, PlanetScale or Vitess target no longer acknowledges the replication slot past changes the target has not durably applied (CRITICAL, silent loss; GC-41 (a)).** The Postgres CDC reader tells the slot which WAL the server may release. Only the Postgres applier gave the reader an applied-position tracker. For every other target, the reader acknowledged the position it had streamed, which advances as it parses each commit, before the applier has written it. At the CLI defaults the MySQL-family applier batches up to 1,000 changes across concurrent lanes. So a stop, crash or Ctrl-C while changes sat in a batch left the slot acknowledged past them, and the next start resumed past them. They were never applied, at exit 0. Measured on Postgres → MySQL 8 with the target blocked by `LOCK TABLES`, 200 inserts behind the block and a cancel: with the fix removed, the resumed target held 22 rows against the source's 221; Postgres → Postgres, the control, held 221. The fix is one mechanism for every target. The reader now never acknowledges past the highest position its consumer has released, floored at the stream's start. A new apply-phase sidecar reads the stream's persisted position back from the target's `sluice_cdc_state` row every 5 s (`ChangeApplier.ReadPosition`) and releases that. That is the position a warm resume restarts from, so the slot is not released past anything the target holds, whatever the engine, batch size, lane count or `--apply-delay`. This rests on one premise: a control row the target committed stays committed. A target restored or failed over to an older state breaks it, and the GC-41 (h) check below catches that. Cost: one primary-key read of `sluice_cdc_state` per 5 s; the slot trails the target's durable position by at most that interval plus the reader's 10 s keepalive. The `backup incremental` / `backup stream` chain already released only committed window ends and now uses the same always-on clamp. Not affected: sources without a slot (MySQL binlog, VStream, `postgres-trigger` and the SQLite/D1 trigger sources). Postgres → SQLite and Postgres → D1 are not sync paths. A graceful `sync stop` that drained its batch did not lose changes. Pinned on real servers by `TestStreamer_PostgresToMySQL_SlotAckNeverPassesTheDurablePosition`, which blocks the target, writes 200 single-row transactions, samples `confirmed_flush_lsn` against the persisted position, cancels, resumes, and requires the target's row count to equal the source's. The same test now also requires the slot to advance once the block lifts. Also pinned by `TestAckLSN_NeverPastTheReleasedCeiling` and `TestReleaseSlotAckTo_PositionShapes`. `TestSlotAckReleaseRoster_EveryStreamChangesSiteReleases` walks every `StreamChanges` call in the pipeline and fails the build unless it hands its reader to a release mechanism. `TestSlotAckCeilingRoster_EveryRegisteredEngine` fails the build for a registered engine that nobody has classified. **Affected releases:** every release through v0.156.6, for Postgres → MySQL-family sync. Postgres → Postgres and `postgres-trigger` targets had the same exposure through v0.99.129; that was fixed and disclosed in v0.99.130 (`fb4f9bf6`).

**Vitess and PlanetScale targets with a sidecar control keyspace: a commit torn between the data keyspace and the control keyspace can no longer persist a position past rows that never committed (CRITICAL, silent loss; GC-41 (c)).** With the control tables in a sidecar keyspace, one apply transaction spans two keyspaces. Under vtgate's default `transaction_mode=MULTI` there is no two-phase commit: vtgate commits the shards one at a time, in the order the transaction first touched them, and stops at the first failure. v0.156.5 introduced the ADR-0190 apply marks. On the serial batch path (`--apply-batch-size` above 1 with `--apply-concurrency 1`, or a lane count the resolver reduced to 1), a transaction's apply-mark statements were sent before its coalesced rows were flushed, so the control keyspace was touched first. When the data shard then failed at commit (a lost connection, a reparent, a killed transaction), the control keyspace had already committed. The position moved past the source transaction, and the rows of its final batch never landed. Nothing re-delivers a transaction the position has passed. Reproduced on vttestserver: position past the transaction, 3 of its 5 rows on the target, the other 2 lost at exit 0. The same order on a mid-transaction batch flush could commit apply marks without their rows, and the restart then skipped those rows as already applied. Every write path now sends all of a transaction's rows before its first control-table statement. A torn commit now leaves the position and marks behind the rows, and the transaction is re-delivered. Because the rows that committed carry no mark, that replay behaves as it did before ADR-0190: idempotent on a primary-key-only table, a loud unique collision on a secondary-unique or primary-key-changing change, and a duplicate row on a keyless table. So on vtgate MULTI with a sidecar, the marked classes are at-least-once or loud, not exactly-once, but never a silent skip. This closes the data-versus-control tear only. A transaction whose rows span two data shards (a sharded target keyspace, or a primary-vindex change that vtgate runs as a delete on one shard and an insert on another) can still tear between them; that class is being triaged separately. The default concurrent lane path and the per-change path already sent data first. Postgres targets send data first on every path. On a single Postgres server the commit is atomic regardless; for a sharded Postgres target (Neki) with the control tables on another shard, see **Compatibility**. The `--control-keyspace` help, and a code comment that called a position committed without its data harmless, were wrong and are corrected. Pinned by `TestVStream_ControlKeyspaceTornCommit_PositionStaysBehindData`, a real tear on vttestserver that fails against the v0.156.5 order. Also pinned by `TestWriteCoreStatementOrder` on both engines, which records every write core statement by statement and fails on a row sent after a control statement in any committed transaction. `TestWriteCoreRoster_EveryControlWriterCallerIsClassified` walks the AST from every control-table writer to its write cores, so a new core cannot go undriven. **Affected releases:** v0.156.5 and v0.156.6 (introduced by `e8377af3`, ADR-0190 phases 1–3).

**`sync` on the default apply lanes no longer panics at its first checkpoint when the apply-mark table is unusable, and so no longer crash-loops (HIGH, loud crash loop that leaves silent keyless duplicates; GC-41 (d), Bug 293).** When `sluice_cdc_apply_marks` cannot be used (absent, or a role without DML on it), sluice WARNs `APPLY-MARKS-UNAVAILABLE` and is meant to apply as v0.156.4 did. On the default concurrent lane path (`--apply-concurrency` above 1, `--apply-batch-size` above 1), it instead applied the first source transaction and then panicked with `assignment to entry in nil map` in `applymarks.(*Tracker).CloseTxs`, exit 2, at the checkpoint that would have persisted it. A disabled tracker was never loaded, so its maps did not exist, and that method wrote to them without checking. The position never advanced, so every restart replayed from the same point and panicked again. Each replay re-applied every change delivered before that checkpoint, with no marks. On a primary-key-only table that is idempotent. On a table with a secondary unique key, a replay could stop loudly on a unique collision (1062 / 23505). A keyless table gained one duplicate of every replayed row per restart, and those duplicates remain after the mark table is fixed and the stream recovers. `--apply-concurrency 1` was not affected. Every tracker method that touches its bookkeeping now does nothing on a tracker that was never loaded. Pinned by `TestTracker_DisabledIsInertOnEveryMethod`, which walks every exported `Tracker` and `TxMarks` method by reflection, so a new method is covered without being listed. Also pinned end to end by `TestChangeApplier_ApplyMarksUnavailable_DefaultLanesCrossCheckpoints` (MySQL) and the `marks-missing-lanes` arm of `TestControlTables_DMLOnlyRole` (Postgres): default lanes, no mark table, three checkpoints, the position advancing at each, and the keyed and keyless tables converging exactly. **Affected releases:** v0.156.5 and v0.156.6.

**`sync` from Postgres to Postgres (and to `postgres-trigger` targets) on the concurrent lane path, including the `--apply-concurrency auto` default, now advances the source slot's `confirmed_flush_lsn` (HIGH, unbounded source WAL retention; GC-41 (b)).** The Postgres applier reported commits to the reader's applied-position tracker from its serial paths only. The lanes' checkpoint persisted the position but never reported it. So on a stream with more than one lane, every keepalive acknowledged the stream's start position while the persisted position advanced. Measured at 4 lanes and at the `auto` default with `--apply-batch-size 1000`: `confirmed_flush_lsn` stuck while the target advanced; 1 lane was fine. The source retained all WAL written since the stream started or last restarted, until the next restart. That can fill the source's disk, or get the slot invalidated by `max_slot_wal_keep_size`, which forces a re-snapshot. Nothing was lost. The tracker is removed rather than patched. GC-41 (a)'s read-back releases the slot from every position write (serial, lane checkpoint or lane barrier) without any write site having to report, so the reader has one acknowledgement input instead of two. Pinned on a real Postgres by `TestStreamer_PostgresToPostgres_SlotAckFollowsTheDurablePosition`, at 1, 4 and `auto` lanes with `--apply-batch-size 1000`: within three keepalives of a 300-transaction batch landing, `confirmed_flush_lsn` passes the WAL position taken before it and never passes the target's persisted position. `TestSlotAckInputsRoster_EveryInputIsDurableEvidence` fails the build if the slot acknowledgement gains an input that is not listed as durable evidence. **Affected releases:** v0.99.130 (`fb4f9bf6`, which first attached the tracker on the streamer path) through v0.156.6, on Postgres and `postgres-trigger` targets with `--apply-concurrency` above 1 or `auto`.

**A warm resume from a Postgres source whose replication slot was acknowledged past the target's position now refuses with `SLOT-ACKED-PAST-TARGET-POSITION` instead of silently skipping the gap (MEDIUM, silent loss; GC-41 (h)).** PostgreSQL decodes from the later of the requested position and the slot's `confirmed_flush_lsn`. A resume never compared the two, so a slot acknowledged past the target's persisted position skipped every change committed in between, at exit 0. Three ways to get there: a Postgres → MySQL-family stream stopped on v0.156.6 or earlier with changes in an apply batch (GC-41 (a); without this check, its first resume on this release would still lose them); a target restored from a backup, or failed over to a replica, holding an older `sluice_cdc_state` row; and a slot dropped and recreated after the stream wrote its position. Every warm resume (single-schema, multi-schema, and the resume that finishes a stopped cold start) now reads `confirmed_flush_lsn` and refuses when it is past the persisted position. The refusal names the slot, both LSNs and the remedy: re-copy with `--restart-from-scratch` (or re-copy the affected tables), or acknowledge with `--accept-slot-acked-past-position` (see **Features**). A stream written by this release does not trip the check, because the slot is released only to positions read back from the target. One upgrade shape can trip it without loss: a stream an older release left at a mid-transaction schema anchor. The acknowledgement is the answer there. **Measured: a cleanly stopped stream from v0.156.6 does not trip it.** With the released v0.156.6 binary on PostgreSQL 16 and 14 sources and a MySQL target, the heartbeat on, and 40 s of writes to another database on the same server and to an unpublished table, a draining `sync stop` left `confirmed_flush_lsn` at or behind the persisted position every time, and this release's resume went ahead. Separately, a slot-acknowledgement release naming a different slot than the reader's (two streams sharing one `sluice_cdc_state` row) now WARNs once per slot instead of being ignored. Pinned on real servers by `TestStreamer_PostgresToMySQL_WarmResumeRefusesASlotAckedPastTheTarget` (the old binary's acknowledgement simulated with `pg_replication_slot_advance` over five unapplied transactions: the resume refuses, refuses an acknowledgement of a different LSN, and resumes on the exact one) and `TestStreamer_PostgresToPostgres_WarmResumeRefusesASlotAckedPastTheTarget` (a recreated slot refuses; a stop inside a DDL transaction on the serial-batch, per-change and lane paths resumes without refusing and delivers every row). Also pinned by `TestStreamer_PostgresToMySQL_CleanStopWithForeignWALDoesNotRefuse` (the clean-stop workload above) and `TestCheckSlotNotAckedPast`. **Affected releases:** every release with Postgres-source sync lacked the check.

**`sluice sync run`: a fleet leg that stops on a refusal every restart would repeat is no longer restarted into it forever (MEDIUM, loud; GC-41 R6).** The fleet supervisor special-cased only `UNFORWARDED-SCHEMA-CHANGE`. A leg that stopped on any other such refusal was restarted after backoff and refused again, and under the default `max-consecutive-failures: 0` it did so indefinitely while the fleet looked healthy. A leg that stops on any of these five is now marked `failed` with an ERROR log line carrying a `marker=` attribute, and is not restarted, whatever `max-consecutive-failures` says; the other legs keep running:

- `SLOT-ACKED-PAST-TARGET-POSITION`: the slot and the persisted position are both durable, so a restart compares the same two values.
- `SHARDED-TARGET-VINDEX-UPDATE`: the refused change is after the persisted position, so a restart re-delivers it.
- `APPLY-MARK-MISMATCH`: the marks are durable and a restart re-delivers the same transaction onto them.
- `CHARSET-NOT-DECODABLE`: a restart reads the same value again.
- `DSN-TIME-ZONE-NOT-UTC`: a restart parses the same DSN.

Terminal errors in general and coded (`SLUICE-E-*`) refusals are still restarted under the failure cap, because some of them clear without any change to the leg (a dead snapshot-pinned copy connection; `SLUICE-E-CDC-REPLICATION-HEADROOM` once another slot is freed). The fleet config has no key for `--restart-from-scratch` or the acknowledgement flags, so a remedy that needs one is run by taking the leg out of the fleet and starting it once with `sync start`. A `SIGHUP` reload starts every failed leg still in the config, so reload only after the fix. Pinned by `TestSupervisor_RefusalsARestartRepeatsAreNotRestarted` (one subtest per listed refusal at the restart-forever default, plus a roster floor) and `TestRestartRefusalSentinelsAreTheMarkers`; both slot-acknowledgement integration tests assert the error carries the sentinel the supervisor keys on. **Affected releases:** pre-existing for the four older markers; `SLOT-ACKED-PAST-TARGET-POSITION` and `SHARDED-TARGET-VINDEX-UPDATE` are new in this release.

**Vitess and PlanetScale: a change vtgate refuses because it would assign a sharded table's primary-vindex column now fails as `SHARDED-TARGET-VINDEX-UPDATE`, and the docs no longer call sync into a pre-vindexed sharded keyspace simply "supported" (HIGH scope correction, loud; GC-41 (e), open).** On a sharded target, vtgate refuses (Error 1235, VT12001) an UPDATE or `ON DUPLICATE KEY UPDATE` that assigns a primary-vindex column. That keeps a row from being moved between shards, and nothing is written, but it also means two things. A table whose primary vindex is not its primary key cannot take any row write from sluice. And on a table vindexed by its primary key, the per-change apply path's UPDATE is refused even when the key does not change. `docs/managed-services.md` and the `SLUICE-E-SCHEMA-TARGET-KEYSPACE-SHARDED` row now state that scope; lifting it is open work. The error now carries the marker, the table and a remedy instead of a bare 1235. One `ON DUPLICATE KEY UPDATE` spelling, `col = VALUES(col)`, vtgate accepts and executes as an insert on the new shard, leaving the old row in place: a silent cross-shard duplicate, measured on vttestserver. sluice's Vitess-family upsert uses the row-alias spelling, which vtgate refuses loudly, and that is now pinned. Pinned by `TestVStream_ShardedTarget_VindexMoveRefusesLoudly` (real vtgate, two shards; every apply path refused, both shards unchanged, position unmoved), `TestUpsertSpelling_VitessFamilyNeverUsesValuesFunc` and `TestClassifyApplierError_VindexUpdateRefusalIsMarkedTerminal`.

**A transient failure while checking the apply-mark table no longer switches the apply marks off for the run (LOW–MEDIUM; GC-41 (f)).** Each apply run checks that `sluice_cdc_apply_marks` exists and is usable. Any error from that check, including a lost connection or a timeout, disabled the marks behind the `APPLY-MARKS-UNAVAILABLE` WARN. The restart right after a crash is exactly when a target flaps and exactly when the marks matter, so that run could replay the interrupted transaction without them: a loud collision, or a duplicate on a keyless table. A transient failure of the check is now retried like any other transient apply error. Only a definite answer (the table is absent, the role lacks a privilege on it, or it cannot be resolved) disables the marks and WARNs. Pinned by `TestStartApplyMarks_TransientProbeRetriesDefiniteVerdictDisables` on both engines. **Affected releases:** v0.156.5 and v0.156.6.

**The serial batch apply now retries a transient failure during a batch's position write instead of stopping the stream (MEDIUM, loud; GC-41 (g)).** A failure at a batch's COMMIT was classified as retriable or terminal. A failure while writing the batch's position was returned unclassified, and the retry loop treats that as terminal. On MySQL-family targets that is where most of a batch's rows are actually sent (coalesced inserts flush just before the position write), so a lost connection there ended the run instead of retrying. Both position-write sites in the shared batch loop are now classified like the commit, which also lets the `SHARDED-TARGET-VINDEX-UPDATE` marker reach the operator from there. Pinned by `TestRunBatchLoop_PositionWriteErrorIsClassified`. **Affected releases:** pre-existing; not bisected.

## Compatibility

**New loud refusal on a Postgres-source warm resume: `SLOT-ACKED-PAST-TARGET-POSITION` (exit 1, no error code).** A stream that resumed on v0.156.6 can refuse here. That is intended: it means the resume would have skipped changes the target does not hold. Remedy: re-copy with `--restart-from-scratch`, or, after verifying the target holds the gap, start once with `--accept-slot-acked-past-position=<the printed LSN>`. The flag is new and additive. It is not a `syncs.yaml` key. The same check runs on a `backup stream` / `backup incremental` resume, where the message wrongly says the position came from the target's `sluice_cdc_state`, and the acknowledgement flag does not exist; `PreflightChainResume` refuses the same shape earlier on that path (open item GC-41 (k)).

**`sluice sync run` fleet behaviour.** A leg that stops on `SLOT-ACKED-PAST-TARGET-POSITION`, `SHARDED-TARGET-VINDEX-UPDATE`, `APPLY-MARK-MISMATCH`, `CHARSET-NOT-DECODABLE` or `DSN-TIME-ZONE-NOT-UTC` is now `failed` and not restarted, where before it was restarted indefinitely under the default policy. Alert on `failed` legs.

**Postgres-source slot acknowledgement timing.** For Postgres → MySQL-family streams the slot now trails the target's durable position by up to about 15 s (the 5 s read-back plus the 10 s keepalive), where before it ran ahead of it; slightly more WAL is retained. For Postgres → Postgres lane streams it now advances, where before it did not. Each sync stream does one extra primary-key read of `sluice_cdc_state` every 5 s.

**Apply-mark availability check.** A transient error from the mark-table check now retries the apply instead of WARNing `APPLY-MARKS-UNAVAILABLE` and continuing without marks.

**Error text.** vtgate's primary-vindex refusal now carries `SHARDED-TARGET-VINDEX-UPDATE`, the table and a remedy instead of a bare Error 1235. Scripts that matched the bare message should be checked.

**Sidecar control keyspace guarantee, scoped.** On a Vitess or PlanetScale target with a sidecar control keyspace under vtgate MULTI, the ADR-0190 apply-mark classes are at-least-once or loud, not exactly-once. A transaction spanning two data shards can still tear between them; that class is under triage.

**UNVERIFIED PREMISE: Neki commit order.** Whether a sharded Postgres target (PlanetScale Neki) with the control tables on another shard commits atomically, or in first-touch order like vtgate, has not been verified. sluice now sends data before control on every Postgres path, so a first-touch tear would leave control behind the data, not ahead of it. The premise is named on the Postgres `writePositionTx`.

**Otherwise a drop-in.** No flag was removed or renamed, and no control-table schema changed.

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale, a billable cluster), `d1verify` (live Cloudflare D1) and `nekiverify` (a billable Neki cluster) suites were not dispatched, because each provisions billable or live infrastructure and runs only on the operator's call. The sidecar-keyspace ordering fix was measured on vttestserver, not on live PlanetScale, and the Neki commit order above was not measured.

**Known open items, not fixed here.** GC-41 (j), unverified: on a PostgreSQL 15+ source, `--source-heartbeat-interval` probably does not advance an idle stream's slot, because the heartbeat table is outside the stream's publication and pgoutput skips empty transactions there. The help text says it does. If this holds, an idle PG 15+ source keeps retaining WAL. v0.156.6 behaved the same. GC-41 (k): the backup-path wording of the slot-acknowledgement refusal, above.

## Who needs this — action required

**Check after upgrading.** Upgrading stops new loss; it does not restore rows an older release already lost or duplicated.

- **Postgres → MySQL, MariaDB, PlanetScale or Vitess `sync`, on any release through v0.156.6, whose runs ever ended by Ctrl-C, a crash or kill, or an apply error.** Those runs may have lost the changes that sat in an apply batch (GC-41 (a)). A graceful `sync stop` that drained was not exposed. *If the stream has not resumed since that stop:* start it on v0.156.7. If it refuses with `SLOT-ACKED-PAST-TARGET-POSITION`, re-copy with `--restart-from-scratch`. The same signal, before resuming: `pg_replication_slots.confirmed_flush_lsn` past the LSN in the target's `sluice_cdc_state.source_position`. *If the stream already resumed on v0.156.6 or earlier after such a stop:* the gap was skipped at that resume, and neither the refusal nor the LSN comparison can see it any more. Compare row counts per table or run `sluice verify` against the source, and re-copy what differs.
- **Vitess or PlanetScale targets with the control tables in a sidecar keyspace (`--control-keyspace`, or auto-detected on a sharded target), on v0.156.5 or v0.156.6, on the serial batch path** (`--apply-batch-size` above 1 with `--apply-concurrency 1`, or a lane count resolved to 1). Exposure also needs a source transaction that touched a marked-class table (a secondary unique key, no usable key, or a primary-key-changing update) and was split across more than one batch, or the first transaction after a restart that left marks behind. Do not rely on the run having failed: the tear's triggers are retriable, so the apply retried in-process and could carry on to exit 0. Search those releases' logs for the WARN `mysql: applier: batch commit error` (followed by `applier: transient error; retrying` at INFO). For each one, compare the tables that source transaction touched against the source (row counts per table, or `sluice verify`).
- **Any stream that crash-looped on v0.156.5 or v0.156.6 behind `APPLY-MARKS-UNAVAILABLE` (exit 2, `assignment to entry in nil map`) on the default apply lanes.** Its keyless tables may hold duplicate rows. Keyless means no primary key and no unique key over NOT NULL columns; a row whose unique key holds a NULL is also not deduplicated. Compare each such table against the source by counting identical rows on both sides, hashing the whole row: on Postgres `SELECT md5(t::text) AS h, count(*) FROM tbl t GROUP BY h HAVING count(*) > 1`; on MySQL group by `MD5(CONCAT_WS(',', QUOTE(CAST(c1 AS BINARY)), QUOTE(CAST(c2 AS BINARY)), …))` over every column. A hash count that differs between source and target is the finding; inspect those rows, then delete the surplus copies on the target.
- **Postgres → Postgres or `postgres-trigger` target `sync` on v0.99.130–v0.156.6 with `--apply-concurrency` above 1 or `auto`.** No data was lost, but the source slot has been retaining WAL since the stream last started. After upgrading and restarting, check that `pg_replication_slots.confirmed_flush_lsn` advances and that retained WAL (`pg_current_wal_lsn()` minus `restart_lsn`) falls. If a slot was invalidated by `max_slot_wal_keep_size` in the meantime, the stream needed or needs a re-snapshot.
- **Vitess or PlanetScale sharded targets whose tables are vindexed on a column other than the primary key.** sluice cannot write those tables; the apply now stops with `SHARDED-TARGET-VINDEX-UPDATE`. See `docs/managed-services.md` for the scope.
- **`sluice sync run` fleet operators.** Alert on `failed` legs: the five refusals listed under **Fixed** (like `UNFORWARDED-SCHEMA-CHANGE` before them) no longer restart-loop, and each needs the remedy it names.
- **Everyone else:** upgrade; nothing to check.
