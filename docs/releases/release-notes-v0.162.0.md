# sluice v0.162.0

**HIGH fix, silent — new refusal: `sync` no longer streams into a target that enforces a unique key the source does not (`SOURCE-UNIQUE-KEY-ABSENT`, UNIQUE-KEY-STOPPED-WINDOW-DOOR).** Such a key let two distinct source rows merge into one target row at exit 0, in the shapes v0.161.1's apply-time check cannot see. The check runs at stream open, at schema changes that move a table's columns, every 15 seconds on VStream and trigger sources, and in `schema add-table`. A key the target is meant to have is accepted with the new `--accept-target-only-unique-key <table>.<key>=<fingerprint>`. No backup format change. This is a MINOR: a stream whose target carries a unique key the source does not will refuse at its next start until that key is dropped or accepted.

## Fixed

- **A target unique key the source does not enforce now refuses with `SOURCE-UNIQUE-KEY-ABSENT` instead of merging rows (HIGH, silent; UNIQUE-KEY-STOPPED-WINDOW-DOOR, POSTGRES-TRIGGER-DROP-INDEX-MARKER, VSTREAM-UNIQUE-KEY-DDL).** Every insert reaches a sluice target as an upsert. On a MySQL-family target the upsert resolves a conflict through any unique key the table has; on Postgres, through the table's ON CONFLICT key. A target key the source does not enforce can therefore turn the source's next duplicate of it into an overwrite of a different row. The usual cause is a source `DROP INDEX` that no stream saw: one made while the stream was stopped, or one on a `postgres-trigger`, `sqlite-trigger`, `d1-trigger`, PlanetScale or Vitess source, none of whose change streams carry index DDL.
  - **What v0.161.1 left silent.** Its apply-time check, `UNIQUE-KEY-CONFLICT-OTHER-ROW`, refuses most such merges at the first colliding row. Two shapes look to it exactly like a re-delivery of the same row: a table with no primary key and exactly one unique key, and two rows that differ only in a NULL or partial-index unique-key column. Measured on real servers before this change: with the DROP made while the stream was stopped, a pgoutput or MySQL binlog source into a MySQL or Postgres target applied both shapes at exit 0.
  - **Affected releases for those two shapes.** These are the same ranges v0.161.1 established for the upsert itself. On a MySQL target without a primary key, v0.99.5 through v0.161.1 (v0.99.5 introduced the full-row upsert for keyless tables). On a Postgres target whose ON CONFLICT key is a unique index rather than the primary key, v0.99.13 through v0.161.1 (v0.99.13 keyed the CDC Insert on that index). For every other table the merge was silent through v0.161.0 and loud at the first colliding row in v0.161.1. A second route also gets the check for the first time in this release: a `DROP COLUMN` of a key column that the stream forwarded or skipped. A Postgres source drops the whole index with the column, while a forwarded `DROP COLUMN` only narrows a MySQL-family target key, so `UNIQUE (a, b)` becomes `UNIQUE (a)`. No release through v0.161.1 checked keys at a schema change. The exact release where that route opened depends on when `DROP COLUMN` forwarding was introduced, and it is not pinned here.
  - **At stream open.** Every `sync start` reads, for each table the stream applies to, the source's current unique keys and the target's (the primary key included). The read happens after the change stream opens and before the first change of the run is applied. That covers cold start, warm resume, `--restart-from-scratch`, `--reset-target-data`, each namespace of a multi-database stream, and every `sync run` leg start. A target key passes when a source key implies it: the same columns in any order or a subset of them, a shorter prefix, or the same expression or partial-index predicate in the same SQL dialect. Across dialects, it passes when it is a key of the same name, as the target spells it, and the same shape. Keys sluice creates itself pass: copied source keys, the `--inject-shard-column` composite, and `AUTO_INCREMENT` or identity surrogates. On a Postgres side, an index-level collation, NULLS NOT DISTINCT, an invalid index left by a failed concurrent build, and a partitioned table's keys are all read from the catalog. A key column whose target collation equates values the source's keeps apart (case-, accent- or trailing-space-insensitive where the source is not) does not count as implied. The refusal names that column, and an `ALTER` of it to a collation as strict as the source's is a measured remedy. Collation direction is judged between two MySQL-family servers, between two Postgres servers, and from either into a Postgres-family target. From a pgoutput or binlog source it is judged at a cold start only, because a collation change made while stopped belongs to `KEY-COLLATION-MERGE`. From a PlanetScale, Vitess or trigger source it is judged at every check.
  - **At a schema change.** The check also runs at every schema change that moves a table's columns, for that table, on every source, whether or not the change was forwarded. That covers a Postgres index dropped together with a column, a forwarded `DROP COLUMN` narrowing a MySQL-family key, and a `DROP COLUMN` at the first boundary after a cold start, which is not forwarded and so leaves the target's column and its key in place. The Postgres reader also reports a unique key lost with a column that logical replication cannot show: a dropped GENERATED column, or a column dropped and re-added under its name and type. Nothing after the change is applied before the check. A catalog read that fails at that point stops the stream at once with `SOURCE-UNIQUE-KEY-RECHECK-FAILED`, which is restartable.
  - **Periodically, on sources with no DDL in their change stream.** On a `postgres-trigger`, `sqlite-trigger`, `d1-trigger`, PlanetScale or Vitess source (the `CDCTriggers` and `CDCVStream` modes), the check re-runs every 15 seconds (`uniqueKeyRecheckInterval`), over the tables whose target has a unique key besides its primary key. It runs before the first change of a transaction that writes one of those tables, and not at all while no such transaction arrives. A failed re-check logs a WARN carrying `SOURCE-UNIQUE-KEY-RECHECK-FAILED`. Four consecutive failures stop the stream with that marker rather than leave it unwatched. pgoutput and binlog sources are not re-checked this way, because they already refuse a live `DROP INDEX` with `UNFORWARDED-SCHEMA-CHANGE`.
  - **In `schema add-table`.** A pre-created target table is checked the same way before it is copied, with the same catalog facts on both sides. The command refuses if it cannot read either catalog.
  - **The refusal.** It is codeless (exit 1, so match on the marker), terminal, and on the fleet supervisor's do-not-restart list (`supervisor_restart_refusals.go`). It names each key under its target table name. The remedy depends on what happened:
    - **The key was dropped while no stream was reading.** A pgoutput or binlog source says so in the message. Drop the key on the target (the message gives `ALTER TABLE … DROP CONSTRAINT` for a key a Postgres constraint owns) and start again with the same `--stream-id`.
    - **Rows may already have merged.** This is the case for a refusal from the mid-stream re-check, or when a source with no DDL in its change stream dropped the key while a stream ran. Re-copy with `sync start --restart-from-scratch` or `--reset-target-data --yes`, which both drop and re-create the target tables and the key with them. From a pgoutput source, drop the stream's replication slot first; the measurement found that `--reset-target-data` needs this too. Under `--inject-shard-column`, do not use `--reset-target-data`, because it drops the table every shard shares. Drop the key and use `--restart-from-scratch` instead; that path is unmeasured.
  - Pinned on real servers by `TestStreamer_UniqueKeyDoor_PostgresSource`, `TestStreamer_UniqueKeyDoor_MySQLSource`, `TestStreamer_UniqueKeyDoor_TriggerCDC`, `TestStreamer_UniqueKeyDoor_VStream` (vttestserver), `TestStreamer_UniqueKeyDoor_AddTable` and `TestStreamer_UniqueKeyDoor_WorkingConfigurations`. The last of these holds the controls that must stream without a refusal. Each remedy above marked measured was run end to end. The independent expected value is the source catalog read fresh by the source engine's own reader, never the stream's state. Integration cells grade the source's rows against the target's.

- **`sync start --restart-from-scratch --help` no longer says that some sources re-copy onto the existing target rows (Bug 320).** On every source (VStream/PlanetScale, native MySQL binlog and Postgres alike) the in-scope target tables are dropped and recreated first (`freshCopyOperatorRestart`). The one exception is `--inject-shard-column`, whose consolidated tables other shards share and which are kept. The behaviour is unchanged. Since v0.109.0 the help text had said a VStream/PlanetScale or Postgres source upserts onto the old rows without dropping them. That was wrong in every release from v0.109.0 through v0.161.1, because v0.109.0 is where the operator restart started clearing the target on an idempotent reader too (`TestColdStartGate_RestartFromScratch_Idempotent_DropsTarget`). The same error is corrected in the refusal message for a target that cannot drop tables and in several code comments. Only the automatic re-snapshot after a purged position re-copies onto existing rows, and only on a VStream source, as `--no-auto-resnapshot` says.

## Features

- **New flag: `--accept-target-only-unique-key <table>.<key>=<fingerprint>`.** It accepts a target unique key the target is meant to have. It is repeatable and available on `sync start` and `schema add-table`, and as the fleet spec key `accept-target-only-unique-key`. The acceptance is standing, so pass it on every start. Pass the exact value the refusal prints beside the key. A multi-database stream takes `<database>.<table>.<key>=<fingerprint>`, by the source or target database name spelled exactly. A `<table>.<key>` that matches the key in more than one database refuses at the start. A `--target-schema` stream takes `<schema>.<table>.<key>=<fingerprint>`, and every check honours that form. The apply-time check still refuses a merge through an accepted key wherever it can tell the rows apart.
  - **What the fingerprint hashes.** It is a short sha256 over the key's definition as the target engine itself reports it (`ir.UniqueKeyDefinitionReader`), together with the definition of every column the key depends on. Nothing is normalised.
    - **On Postgres:** `pg_get_indexdef` (parts, expressions, per-part collation and operator class, NULLS NOT DISTINCT, and the predicate with its literals verbatim). For each column the index, expression or predicate reads, it also hashes the attribute number, name, type with modifiers, a domain's base type, the collation by schema-qualified name and whether it is deterministic, NOT NULL, and any generated expression.
    - **On a MySQL-family target:** the database and table as the server reports them, the key's `SHOW CREATE TABLE` line and `information_schema.STATISTICS` rows, and each dependent column's `information_schema.COLUMNS` row and `SHOW CREATE TABLE` line (every column of the table, for a functional key). On vanilla MySQL it also hashes a functional part's hidden column. Because the database is part of the hash, a fingerprint accepts the key only in the database it was minted from.
  - **Not hashed**, so the fingerprint is not read as broader than it is: a collation's provider and ICU version (a collation is bound by name only), the body of a user function an expression or predicate calls, a Postgres column comment, and the columns behind a whole-row reference in a Postgres expression or predicate.
  - **The loud costs, by design.** Any change to an input refuses at that change and at every restart until the new printed value is passed. That includes a forwarded `DROP COLUMN` narrowing the key and a `MODIFY … COLLATE` loosening it. It also includes harmless changes: a size-only widening, a rename, a MySQL column comment, and a server upgrade that respells a type or collation (MySQL 8.0.30's `utf8` → `utf8mb3`). On Postgres, a predicate holding a temporal literal is rendered in the reading session's `TimeZone` / `DateStyle`, so two hosts with different settings can disagree on an unchanged key's fingerprint and refuse an accepted key. A key whose definition cannot be read refuses rather than passing. A value with no fingerprint, or a malformed one, refuses at the start.
  - **Cannot be accepted.**
    - A key with a functional part on a PlanetScale or Vitess target (`ErrUniqueKeyDefinitionUnsupported`). The part compares under a hidden column's collation that those servers do not expose, and that collation can come from the session at `CREATE` time. The refusal says so; drop the key.
    - Any target-only key on a target engine without a definition surface. Only the MySQL-family and Postgres schema readers implement one, so on a SQLite or D1 target such a key refuses as unacceptable.
  - Pinned by `TestUniqueKeyDefinition_EveryDimension` (real MySQL, including an identical key in two databases), `TestFunctionalPartSupported` (every MySQL flavor), `TestUniqueKeyDoor_DefinitionReadFailsClosed` and `TestUniqueKeyDoor_TargetQualifiedAcceptance`.

## Not closed, stated

- **Mid-stream on a source with no DDL in its change stream**, up to 15 seconds of transactions between the source's drop and the next due re-check are applied before the refusal. For the two shapes above, a merge in that window is silent. Of these sources, only a VStream source can stream a keyless table, because the trigger engines refuse a table without a primary key at setup. For VStream this is by code reading and unmeasured. The re-check's refusal then names a re-copy. A mid-stream primary-key change on these sources is caught at the next start.
- **A key dropped, a duplicate written and removed, and the key re-created**, all while no stream was reading, looks unchanged at start. The apply-time check refuses the replayed duplicate where it is armed; for the two shapes above it is silent.
- **A cross-dialect functional or partial key redefined under its old name passes.** This is pinned as a known miss.
- **Collation-direction limits:**
  - It is not judged from a Postgres or SQLite source into a MySQL-family target. The column sluice creates there takes the target's case-insensitive default, so judging it would refuse every such stream. `KEY-COLLATION-MERGE` refuses that merge at apply time for a unique key beside a primary key.
  - A Postgres nondeterministic collation counts as folding both case and accents.
  - Two collations with the same axes but different folding tables (`utf8mb4_general_ci` and `utf8mb4_0900_ai_ci`) count as equal.
  - On a VStream source, where `KEY-COLLATION-MERGE` is unarmed, a key column moved to a stricter collation mid-stream can merge up to one re-check interval of rows first.
- **Loud over-refusal, taken on purpose.** The source catalog is read when a check runs and can be ahead of the stream. So a `DROP COLUMN` of a unique-key column made while the stream was stopped refuses at the start, and one the source has already made while the stream lags refuses at the earlier schema change. Both refuse even though replaying the stream would have forwarded the change. The check cannot tell either case from a key the source dropped on its own before writing a duplicate. Dropping the named key on the target converges; this is measured into Postgres and MySQL. On a PlanetScale or Vitess source, a due re-check can also coincide with a forwarded `DROP COLUMN` and refuse a key that drop is about to remove; a restart clears it.
- **`sync from-backup run` and `sluice restore` do not run this check.** They apply a backup window's recorded `DROP INDEX` before the window's rows, measured for a MySQL source by `TestSyncFromBackup_UniqueKeyDroppedInsideTheWindow`. They do not judge a target pre-created with an extra key (BROKER-RESTORE-UNIQUE-KEY-DOOR).
- **The apply-time check does not stand down for keys the source still declares**, so its re-delivery trade (UNIQUE-KEY-GUARD-OVERLAP-REFUSAL) is unchanged. The declared set is fresh only as of stream open, while a run applies from a persisted position that can predate it.
- **Cost.** Only the Postgres reader scopes its catalog read to the watched tables. A MySQL-family re-check reads the whole schema, measured at 513 ms on a 300-table catalog. The D1 cost, where each catalog query is a Cloudflare API call, is unmeasured (UNIQUE-KEY-DOOR-READER-SCOPE).

## Maintenance

- **Test only (bf093243):** the severed-tail broker integration leg now waits until the tail is fully applied (`brokerTailFullyApplied`, pinned by `TestBrokerTailFullyApplied`) instead of matching a frontier inside it (SEVERED-TAIL-BROKER-SENTINEL-DIVERGES). This was a test-side race, not a product defect. The broker had exited loudly with its partial-incremental refusal, and a re-run applied the row.

## Compatibility

- **New terminal refusal, `SOURCE-UNIQUE-KEY-ABSENT`, on every source and target.** A target that previously streamed with a unique key the source does not enforce will now refuse at its next `sync start` (or `sync run` leg start, or `schema add-table`). That includes a key added to a pre-created target on purpose. The stream stays stopped until the key is dropped on the target or accepted with `--accept-target-only-unique-key`. The fleet supervisor does not restart a leg that hits it.
- **New restartable failure, `SOURCE-UNIQUE-KEY-RECHECK-FAILED`.** It stops the stream when a schema-change check cannot read a catalog, or after four consecutive failed periodic re-checks.
- **Accepted keys refuse again on any change to their definition**, including size-only widenings and server-upgrade respellings, until the newly printed fingerprint is passed. A functional key part on PlanetScale or Vitess, and any target-only key on a SQLite or D1 target, cannot be accepted at all.
- **New flag:** `--accept-target-only-unique-key` on `sync start` and `schema add-table`, plus the fleet spec key `accept-target-only-unique-key`. No existing flag or default changed. The `--restart-from-scratch` change is help text only.
- **Periodic catalog reads.** On VStream and trigger sources there is a catalog read of both sides at most every 15 seconds, and only while transactions write a table with a secondary unique key.
- **No backup format change.** Nothing under the backup package changed, and `BackupFormatVersion` stays 15.
- **Not run for this release:** the dispatch-only `psverify` (live PlanetScale) and `d1verify` (live Cloudflare D1) suites. They run on no schedule, and each needs billable live infrastructure, which was not provisioned for this release. Coverage is the CI integration matrix on real MySQL, MariaDB and Postgres containers, plus the Integration (vstream) job, which runs `TestStreamer_UniqueKeyDoor_VStream` against vttestserver. Behaviour against a real PlanetScale cluster and against live D1 (including the re-check's API-call cost there) is unmeasured.

## Who needs this — action required

- **Anyone streaming into a pre-created or hand-modified target.** Expect a `SOURCE-UNIQUE-KEY-ABSENT` refusal at the first start on v0.162.0 if the target carries a unique key the source does not enforce. For each key it names:
  1. If the key was dropped on the source and the refusal says nothing has been applied since, drop it on the target and start again with the same `--stream-id`.
  2. If the target is meant to have the key, pass the printed `--accept-target-only-unique-key` value on every start.
  3. If rows may have merged, re-copy as the refusal says.
- **Anyone whose source dropped a unique key, or a column in one, while a stream was stopped, or at any time on a `postgres-trigger`, PlanetScale or Vitess source, on any release in the ranges above.** Rows may already have merged at exit 0, especially on a keyless table with a single unique key or rows differing only in a NULL key column. Compare the target's rows against the source's by id (a row-count shortfall is the tell), then drop the stale key and re-copy with `--restart-from-scratch`.
- **Everyone else:** upgrade. No action is needed.
