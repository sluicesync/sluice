# sluice v0.148.3

> **Correction (2026-09-10, from the v0.148.3 regression cycle):** the "Who needs this" section below says that if a prior `--target-schema` run split your rows, "the fix is to re-run the copy on v0.148.3". **That is wrong, and the plain re-run is refused rather than silently wrong.** Measured against a split target: `rc=3`, `SLUICE-E-COLDSTART-TARGET-NOT-EMPTY`, "target table … already contains data", nothing recovered. It is refused *every* time in this defect's shape, because the primary writer always landed at least one table in the named schema, so the target is never empty. The refusal's own hint names the runnable escape: re-run with `--reset-target-data --yes`, which does recover the named schema completely. **And it leaves `public` holding the stranded rows** — a full duplicate copy of most of your data that the recovery does not remove and that nothing below mentions. Drop those tables yourself once you have verified the named schema. One further correction to the description: the split is per COPY LANE, not per table, so a single large table can be split *across both schemas* — the cycle measured one table at 751 rows in the named schema and 2,249 in `public`. "The named schema ends up holding one table's worth of data" understates it.

**HIGH fix — `--target-schema` never reached the parallel copy lanes on a PostgreSQL target, so on any multi-table or chunked copy nearly every writer addressed `public` instead of the schema you named; plus a MySQL-family stream that died over a schema change on a table you had EXCLUDED, and a `schema diff` that certified semantically different CHECK constraints as in sync. Drop-in binary, no flag or format change; the only compatibility note is for people who build from source.** The `--target-schema` defect has been present since the flag shipped in v0.25.0 and is loud in most configurations and SILENT in one — read the action-required section if you have ever run `migrate` or `sync start` with that flag against PostgreSQL. Everything else here comes from the 2026-09-09 blind audit's remaining tiers and from the v0.148.2 regression cycle.

## Fixed

**`--target-schema` now reaches the parallel copy lanes on a PostgreSQL target, instead of sending nearly every table to `public`** (silent in one shape, loud in the rest; present since the flag shipped in **v0.25.0**, so **v0.25.0 through v0.148.2** all carry it). The namespace override is threaded onto each freshly-opened writer through the capability-only setter `ApplyTargetSchema`, and the PostgreSQL writer qualifies every COPY and INSERT it builds with whatever schema it was told — so a writer that was never told addresses `public`. Six of the eight places in the pipeline that open a target row writer applied it. Of the two that did not, one is the backup broker's table-drop loop, which has no such flag to apply; the other, `openOneChunkConn`, is the opener behind all three parallel chunk cores and behind the cross-table worker pool, which is to say the path that opens a writer for every table not currently holding the orchestrator's own connection pair — and that pair is returned and reclaimed as tables finish, so which tables landed correctly is a matter of the run's timing rather than a fixed single one. In a run with more than one table copying at once, or any table large enough to be split into chunks, the primary writer wrote to the named schema and every peer wrote to `public`. The audit's filing scoped the harm to tables above the within-table chunk threshold; re-measuring corrected that, because the copy pool lets exactly one running table reuse the primary pair while every concurrent peer opens its own — so at the default parallelism, any table copying alongside another was affected at any row count, proven on real postgres:16 by a two-row table dying on `relation "public.customers" does not exist` with the fix removed. That is the loud shape: `SLUICE-E-BULKCOPY-TARGET-TABLE-MISSING` when `public.<table>` is absent, or a duplicate key on a sync cold start into a populated `public`. The silent shape is the one to check for — when `public.<table>` does exist and accepts the rows, which is exactly the case for anyone who once migrated without the flag and then re-ran into a schema: the named schema ends up holding one table's worth of data, `public` holds the rest, the run exits 0, and CDC afterwards applies against the qualified table. The chunk opener now applies the override alongside the buffer cap and the grow gate, and `TestOpenRowWriterSitesApplyTargetSchema` is an AST roster over every writer-opening site in the pipeline requiring each to reach `ApplyTargetSchema` or record at the site why it cannot, with floors so a green cannot be bought by exempting everything. The single recorded exemption is the backup broker's table-drop loop, which has no such flag to apply, and `TestBrokerHasNoTargetSchemaToApply` asserts that premise from the AST so the exemption cannot outlive its reason. `TestMigrate_PG_TargetSchema` — whose own doc-comment used to promise "public stays empty" over two rows in one table, data that could reach neither the chunk axis nor the pool axis — now carries a second, larger table at a lowered parallel threshold and asserts that neither table appears in `public`.

**A schema change on a table you excluded from the sync no longer kills a MySQL-family stream** (loud failure on a working configuration; audit A0909-AQ-M-2). Changing a column between `TIMESTAMP` and `DATETIME` rewrites every stored value against the executing session's time zone, which sluice cannot follow safely, so `sessionTZCastRefusal` stops the stream and says so. That refusal was not consulting the table filter. The readers decode every table in the bound database and the filter is applied one stage downstream, so a table under `--exclude-table` still reached the check and a stream would die over a table it sends nothing to the target for. This is the same defect that was fixed for distributed-transaction refusals in an earlier release, on a second refusal in the same file, with the predicate already sitting on the receiver and simply unconsulted — and the sweep widened it past the filing, which named only the binlog lane: both VStream lanes carry the same refusal and neither implemented `ir.CDCScopePredicateSetter`, so the pipeline's type-assert found nothing and their copy was ungated by construction. They were not exempt by server-side filtering, which was the tempting assumption; the VStream tail rules match every table in the keyspace and the filter is applied downstream exactly as on the binlog lane. All three lanes now ask, the XA-specific helper is renamed `tableInScope` because the question is not about XA, and a stream with no filter wired still refuses exactly as before — the fail-loud direction. Pinned by `TestSessionTZRefusalSitesAreScopeGated`, an AST roster over every refusal site in the package floored at the true count, and by `TestEveryMySQLCDCLaneTakesTheScopePredicate`, which asserts the three lanes as a set.

**`schema diff` no longer certifies a CHECK constraint as in sync when the two sides differ in arithmetic grouping or in the case of a quoted identifier** (silent all-clear from a verification command; audit RC-2, measured on real postgres:16.15). The comparison folds both renderings toward a common shape so one predicate written two ways matches, which is what stopped the phantom-drift reports of Bug 241 — but the fold drops every parenthesis and lowercases outside string literals, so `a-(b+c) > 0` and `(a-b)+c > 0` became the same text, as did `"Amount" > 0` and `amount > 0`, which on PostgreSQL name two different columns. A target someone had hand-edited into a different constraint read as clean. The fix deliberately does not narrow the fold, which must keep collapsing — refusing any expression carrying a cast would report drift on essentially every PostgreSQL CHECK that migrate itself created, since PG renders an authored `status = 'a'` as `(status)::text = 'a'::text`. Instead the new `checkExprComparable` asks a second question once the folded forms already match: did the two sides discard the *same* detail? One server's own two renderings of one predicate always did, so a PG-vs-PG or MySQL-vs-MySQL pair cannot trip it and only a genuine asymmetry withholds the match. Because it can only ever withhold, it cannot hide drift. Both graded dimensions were chosen to be symmetric under one server's rendering: case-bearing quoted identifiers in both quote styles, since MySQL renders with backticks and PostgreSQL with double quotes, and parentheses only in a re-associating position, which is `-` and `/`, because counting a group after an associative operator would flag a server's own redundant parens. A unary minus does not count either: MySQL renders a negative literal as `-(100000)` where PostgreSQL renders `'-100000'::integer`, and treating that group as a re-association reported six phantom CHECK mismatches on a MySQL-to-PostgreSQL migrate before the integration suite caught it. All three places in the tree that compare two CHECK expressions now route through the single door `sameCheckPredicate`. One collision is still open and is now pinned as such rather than left to be rediscovered: a cast around a column (`x::text < '5'` against `x < 5`, a lexicographic comparison against a numeric one) is still reported in sync, because telling that cast from the ones PostgreSQL adds to every rendering needs the operand's type and therefore a real expression parser — `TestCheckExprComparable_TheCastCollisionIsStillOpen` holds the gap. The rest is pinned by `TestSameCheckPredicate_TheMeasuredRC2CollisionsAreRefused` and, for the half that decides whether this is shippable at all, `TestSameCheckPredicate_OneServersOwnRenderingsStayComparable`.

**A MariaDB server addressed with the plain `mysql` driver now meets the warning that names the right driver before it meets sluice's own SQL failing** (loud failure with a misleading diagnosis, and a silent-loss guard whose coverage depended on call order; Bug 280, filed by the v0.148.2 regression cycle, bisected across eleven staged binaries as identical back to at least v0.131.0 — not a regression). The flavor probe carries two things: `warnMariaDBUnderMySQLDriver`, a steer toward `--source-driver`/`--target-driver mariadb`, and `refuseVitessUnderNonVStreamFlavor`, which is a silent-loss guard because the vanilla flavor's full scans run without `set workload=olap` and Vitess truncates them at its OLTP row cap. It ran at exactly two of the engine's eight `Open*` doors, the schema reader and the schema writer, and its coverage rested on an unwritten assumption — that every path reaching data opens one of those first. `migrate` does not: it opens the migration-state store at phase 1.75, and that store renders its upsert in the flavor's spelling, MySQL 8.0.20's row alias, which MariaDB rejects. The run died on `Error 1064 … near 'AS new ON DUPLICATE KEY UPDATE'`, sluice's own statement, with the steer never reached; the diagnosis was pre-empted by its own symptom. The probe now runs at every door that actually opens a pool — including the row reader, which is where the truncation the Vitess guard refuses actually happens, and the change applier, the sync twin of the state store. That is affordable because `flavorVerdict` is memoised per server and flavor, so the doors that open per worker on the parallel copy path pay one probe per server rather than one per pool, and only a verdict that was actually reached is cached, so one transient read cannot make a wrong answer sticky for the process. `TestFlavorDoorRoster_EveryConnectionOpenerIsClassified` derives its universe from the AST — every engine `Open*` that opens a pool must run the probe or carry a reason inside the function — with floors on both the door count and the probing count; it records no exemptions, because the only reason available was the assumption that had just failed. Pinned end to end on real MariaDB by `TestMariaDBUnderMySQLDriver_SteerPrecedesItsOwnSymptom`, which drives the two doors the pipelines open first and requires both the steer and a working control table, asserts the memo speaks once across three opens, and asserts the correct driver is not steered.

**`sync health` and the `diagnose` bundle now look up the replication slot your stream actually created, instead of one that does not exist** (a missing signal that reads as a clean one; audit A0909-AQ-M-1). The `--slot-name` flag is a suffix — sluice prepends `sluice_`, so `sync start --slot-name shard_a` creates `sluice_shard_a`. Both of those read-only probes filled in the engine's default name for a PostgreSQL source but skipped the prefix step, so anyone passing the flag had them querying `shard_a`. Nothing said so: a lookup against an absent slot returns not-found, and the caller treated that identically to a slot with nothing to report, so the spill counters were simply absent from the output with no reason given — indistinguishable from a healthy slot that has not spilled. Both surfaces now delegate to one resolver, `SlotNameForSource`, which does the prefix convention and the engine default together, because separating them is precisely what went wrong; the duplicated default constant that each surface carried is what let the prefix step go missing. The diagnose bundle additionally records a `spill_reason` when no slot name reached it, so this class of omission appears in the bundle rather than vanishing from it. Pinned by `TestSlotNameResolutionIsIdenticalAcrossSurfaces` and `TestDiagnoseRequestCarriesAResolvedSlotName`.

**When the multi-schema publication-exposure check cannot run, it now says so at warning level instead of staying quiet** (audit A0909-AQ-M-4). A multi-schema sync on PostgreSQL publishes every table in the database, which stops UPDATE and DELETE on any table lacking a replica identity, including in schemas you did not select. One warning is the only signal an operator gets for that. If the check itself failed, both failure paths logged at debug level and returned, so nothing appeared at the default level and a missing warning looked exactly like a clean result — and the operator most likely to hit it is the one whose role cannot read `pg_publication_tables`, which is an otherwise perfectly working sync. Both paths now warn under the same `UNSELECTED-NAMESPACE-EXPOSURE` marker, so one search reaches the same page either way, with wording that distinguishes exposure unknown from exposure absent. It remains advisory and does not refuse.

**The agent guide the binary itself prints no longer names a command that does not exist** (audit 2026-09-09). `sluice agent-guide` emits a workflow document for coding agents, and its first step offered `sluice preview` alongside the dry run; there is no such command, and the parser answers `unexpected argument preview`. It now points at `sluice schema preview`, which is real, and distinguishes the DDL render from the JSON dry-run plan rather than presenting them as interchangeable. `TestDocsNameOnlyRealCommands` already resolved every backticked invocation in the docs against the parser's own command model, but its list of roots did not include the one document the binary ships; adding that root makes it fail on `preview` immediately. Separately, two cookbook recipes offered `sluice verify --depth=full` as the strongest option — that value is refused by the parser and the depth is designed but not built, and both recipes now say so.

## Internal

Four gates were found to be narrower than their names and were widened, none of which changes the released binary. `scripts/vet-tags.sh` now lists packages under each tag combination it checks rather than once with no tags at all — Go does not report a package whose every file is excluded by a build constraint, so a package existing only under a tag was never in the list and never checked under any combination while the script reported success for each one (measured on a planted package with a real type error). `scripts/check-shard-coverage.sh` now recognises a build constraint that does not begin with the `integration` tag, so `linux && integration` is found rather than only `integration && vstream`; a package written the first way would have run in no shard while the check that exists to prevent exactly that reported success. `TestPublicationPrivilegeRoster_EveryDDLSiteIsClassified` now grades all ten places that execute a PostgreSQL publication statement rather than eight, keying on the executions themselves instead of on where the SQL string is built — the two it missed were in fact wired correctly, so no operator saw a bare `SQLSTATE 42501`, but the check could not have said so — and its floor is now the true count, since a floor set below the real total cannot fire. And `TestOperatorMarkersHaveADocHome` now also scans string literals for the marker convention, ignoring flag help text and design-document references and carrying its own separate floor, because it previously derived its universe from marker constants and so could not see a marker written straight into the log call; two were in that position and both are now documented — `CHANGE-LOG-PAGE-UNORDERED`, the refusal that stops a trigger-CDC poll when a page of the change log arrives out of order, and `CAPTURE-FUNCTION-PUBLIC-EXECUTE`, the warning that the Postgres trigger capture functions are still executable by `PUBLIC`. No package in the tree was written in either of the two shapes the CI scripts could not see, so nothing was going unchecked or untested; the fixes are so that the next one fails CI instead.

## Compatibility

**Building from source now needs Go 1.26.7 or newer**, up from 1.26.6, because the Vitess client library moved to v0.24.3 and requires it. That upgrade also closes the one open dependency alert on the repository, an authorization gap on a Vitess tablet's debug endpoint — and stated plainly, **sluice was not exposed by it**: the vulnerable code is an HTTP handler on the tablet *server*, and sluice only ever acts as a streaming client, never running a tablet. A reachability scan reported zero reachable vulnerabilities both before and after the change. Installing a released binary or the container image is unaffected, and every CI workflow reads its toolchain version from `go.mod`, so no build configuration changes.

Nothing else changes. No flag was added, renamed or removed, and no default moved. The only output-shape change is additive: a `diagnose` bundle now carries a `spill_reason` key when no replication-slot name could be resolved, where it previously carried nothing at all. No position, manifest or backup format change — the backup format stays at 10 and the `postgres-trigger` change-log schema version stays at 5 — so no `sluice trigger setup` re-run is required by this release. Engines touched: PostgreSQL as a bulk-copy target on the `--target-schema` path (which the validate gate has always refused on flat-namespace engines, so MySQL targets were never in scope), MySQL and its MariaDB, PlanetScale and Vitess flavors on the CDC scope predicate and the flavor probe, PostgreSQL as a CDC source for the slot-name probes and the publication-exposure warning, and the engine-neutral `schema diff` comparison. No engine-specific code path for SQLite, D1 or the trigger-CDC lanes changed — the `schema diff` fix is in the engine-neutral comparison, so it applies to whatever renderings those engines produce as well — and `backup`, `restore` and `verify` are untouched.

## Who needs this — action required

**Anyone who has run `sluice migrate` or `sluice sync start` with `--target-schema` against a PostgreSQL target, on any release from v0.25.0 through v0.148.2.** Most such runs failed loudly at the time and lost nothing — that is the case where `public.<table>` did not exist, or existed with colliding keys. The one to check for is the run that exited 0: if the target's `public` schema already held tables of the same names, from an earlier migration you ran without the flag, then only those tables that happened to be holding the orchestrator's own connection pair at the time landed in your named schema — that pair is returned and reclaimed as tables finish, so which ones they were depends on the run's timing rather than being a fixed single table and every other table's rows went into `public`, at exit 0, with nothing in the log saying so. Look at the named schema and at `public` on that target and compare their row counts per table against the source; a table sitting empty (or stale) in the named schema while `public` holds the rows is this defect, and the fix is to re-run the copy on v0.148.3. Note the consequence for continuous sync specifically: CDC applies against the qualified table, so a stream started that way has been applying changes to a table in the named schema that never received the initial copy — that target needs a fresh cold start, not a top-up. A single-table migration at default settings, and any run that never used `--target-schema`, were never exposed.

**Anyone who runs `sluice schema diff` against a PostgreSQL target and relied on an "in sync" verdict for CHECK constraints.** Two classes of real difference were reported as matching: a predicate re-associated across `-` or `/`, and a quoted identifier differing in case, which on PostgreSQL names a different column. If a `schema diff` clean bill is what told you a hand-edited or independently-created target matched your source, re-run it on v0.148.3. Nothing was written or lost by the diff itself — this is a verification that under-reported, so the action is to re-verify, not to re-copy. The cast collision named above is still open, so a cast around a column still compares as in sync.

**Everyone else: nothing to re-verify, and no re-run of `sluice trigger setup`.** The excluded-table stream death, the MariaDB driver diagnosis, the slot-name probes, the publication-exposure warning and the agent guide are all loud-failure or missing-signal fixes — an upgrade is enough, and none of them can have lost or altered data. Contributors building from source need Go 1.26.7.
