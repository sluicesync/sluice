# sluice v0.160.0

**HIGH fix, plus a backup FORMAT break, so this is a minor release. On v0.159.0 through v0.159.3 a Postgres primary-key or UNIQUE-key column using a nondeterministic (ICU) collation could end up with two source rows merged into one at exit 0, in two ways. (1) The key was tightened and loosened back while a `backup incremental` or a lagging stream had not yet read the rows in between (KEY-COLLATION-PG-LOOSENED-REPLAY). This is wider than first filed: when the tighten, the write and the loosen shared one transaction, a live Postgres → Postgres `sync start` merged too. (2) A `backup stream` window held a row of the table and then saw the key's collation change (KEY-COLLATION-PG-SAME-ANCHOR). Both now refuse, with `KEY-COLLATION-MERGE` and the new capture-time marker `KEY-COLLATION-SAME-ANCHOR`. A segment that records a key collation not established for its rows is stamped `FormatVersion` 14, so v0.159.x refuses it instead of merging. Restoring a chain that contains one needs v0.160.0 or later. This release also stops `backup stream`'s cancel drain hiding a schema-history refusal behind an exit-0 WARN, stops an unrelated session-`SET` statement making MySQL and MariaDB streams refuse every table (loud), and fixes a serial-apply WARN that printed the wrong remedy (Bug 309, loud). Drop-in for flags and defaults. Read Compatibility if you run mixed binaries over one backup chain.**

## Fixed

- **A Postgres key whose collation was tightened and loosened back no longer restores or applies with two source rows merged (HIGH, silent; KEY-COLLATION-PG-LOOSENED-REPLAY; v0.159.0 through v0.159.3, every release with the Postgres key-collation guard).** pgoutput carries no collation, so the reader reads a column's collation from the catalog when it meets the table's relation message, which gives the collation in force *now*. Take a nondeterministic key, tighten it (`ci` → `"C"`), write `'A'` beside `'a'`, move or delete it, and loosen the key back to `ci`. A reader replaying that sequence after the loosening read `ci` for every row of it, so the guard took `'A'` for a re-delivery of `'a'`, the upsert overwrote `'a'`, and the replayed UPDATE or DELETE took the merged row away. This was measured on Postgres 16 through a `backup incremental` started after the revert and chain-restored onto Postgres: row 1 was gone at exit 0. When the tighten, the write and the loosen shared one transaction, a live Postgres → Postgres `sync start` merged too, at every entry (cold start, live, warm resume and `--schema-changes=refuse`), because pgoutput decodes a transaction at its commit, when the catalog already says `ci`. The fix uses the column's `pg_attribute` row, which altering the column rewrites. If that row's `xmin` is newer than the transaction being decoded, or equal to it, the collation read now may not be the one the rows were written under. When that collation is nondeterministic, the reader records it as not established, and both appliers compare that key byte for byte, so a merge refuses `KEY-COLLATION-MERGE` with nothing applied. The Postgres applier's guard used to stay unarmed whenever the source's collation name matched the target's. It now compares a not-established collation as bytes, as the MySQL applier's guard already did. In a backup window, a later not-established version of a table now weakens the version the window keeps, so the whole window compares that key as bytes. `sync from-backup`, whose applier is never armed from a version, refuses a window with a not-established key (`KEY-COLLATION-HISTORY-UNORDERED`). The xid comparison has a lower bound, because a frozen catalog row keeps its raw xmin. Without the bound, a column's catalog row more than 2^31 xids old would have read as newer than every row for half of each xid cycle. That was measured with `pg_resetwal` by a manual script, not a CI test. Pinned by `TestPostgresCatalogNewerThanRowsPremise` (the premise on real Postgres 16, through the reader's own query, in both directions with an untouched-column control), the `backup-incremental`, `broker` and `one-tx` cells of `TestChainRestore_KeyCollationChangedAndRevertedInsideTheWindow_Postgres16` (with the reader's check disabled they restore at exit 0 with row 1 gone), the `pg-pk-collation-reverted` and `pg-pk-collation-reverted-separate` cells of `TestKeyCollationFirstBoundary_Postgres16` (every sync entry), `TestSchemaHistoryDrain_NotEstablishedWeakensTheKeptVersion`, `TestRefuseUnreplayableKeyCollationHistory_NotEstablishedKey` and `TestPlanPGKeyCollationGuard`. An independent value-fidelity review of the first cut found the drain, broker and wraparound gaps before release.
- **A Postgres `backup stream` or `backup incremental` window that sees a key column's collation change after a row of the table was written is now refused at capture instead of restoring merged (HIGH, silent, timing-dependent; KEY-COLLATION-PG-SAME-ANCHOR; v0.159.0 through v0.159.3).** A Postgres change stream anchors every schema version at LSN 0/0, and a backup keeps one version per table and position. So a window that wrote a row of the table, changed the key's collation (`ci` → `"C"`), wrote `'A'` beside `'a'` and changed it back kept only the first shape, `ci`. The restore then armed nothing for the rows written under `"C"`, and row 1 was gone at exit 0. This was measured on Postgres 16 in 1 run of 3, when the reader kept up; when it lagged, the restore refused. The capture now refuses with `KEY-COLLATION-SAME-ANCHOR` when two shapes of a table recorded at one position disagree on a key column's collation (12 of 12 runs). The remedy is a fresh full backup taken after the change, with the chain continued from it. **The cost:** a forward-only key collation change, in a window that already holds a row of the table, is refused too, where it used to restore correctly. Pinned by `TestSchemaHistoryDrain_SameAnchorKeyCollationRefuses` (with the check disabled, the refusing cells record silently) and the `backup-stream` cells of `TestChainRestore_KeyCollationChangedAndRevertedInsideTheWindow_Postgres16`, including the primary-key cell with an earlier row that the v0.159.3 pin had excluded.
- **`backup stream`'s stop-on-cancel drain no longer turns a schema-history refusal into an exit-0 WARN.** When a stream was cancelled, the drain turned any failure of the window's last flush into a `BACKUP-WINDOW-ABANDONED-OPEN-TRANSACTION` WARN and exited 0. That is right for a store write that fails under a cancelled context, which the next run's re-read may not repeat. But it hid a refusal behind a clean exit and a misleading headline. A refusal from the window's schema history is a verdict on what the window recorded, not a transport failure, so the drain now returns it as the stream's error.
- **Backup format: a Postgres-source segment whose schema history records a primary-key or UNIQUE-key column with a collation not established for its rows is now stamped `FormatVersion` 14 (`FormatVersionKeyCollationUnestablished`), so older binaries refuse it instead of restoring it merged (MEDIUM, silent on an older binary).** v0.159.0 through v0.159.3 read such a segment, armed no key-collation guard for a key whose collation name matches the target's, and replayed a row written under a stricter collation onto an equal-looking key. This was measured with the real v0.159.3 binary on Postgres 16: it restores its own equivalent chain with row 1 gone. Those binaries now refuse the segment at their version ceiling (`format version 14 is newer than this build supports (13)`), and so does their `backup verify`. Pinned by `TestBackup_CrossVersionKeyCollationUnestablished`, run against v0.159.3 and mutation-checked both ways. It checks three things: the stamped chain is refused with the target untouched; a DML-only chain still restores exactly on the old binary; and the old binary merges its own chain. The history-stamp unit matrices pin the rest.
- **A MySQL or MariaDB stream behind the binlog head no longer refuses every table because of an unrelated statement that starts with a session `SET` (LOW, loud; the schema look-ahead, v0.158.0 through v0.159.3).** The look-ahead classifies every DDL on the server to see which tables it can reshape, and a statement it could not parse was treated as reaching every table. A binlog text such as `set foreign_key_checks=0; CREATE TABLE IF NOT EXISTS ...` is two statements, which it could not parse. So one such statement anywhere on the server made every stream behind the head refuse `SLUICE-E-CDC-SCHEMA-REPLAY-MISMATCH` on every retry. CI measured this on MariaDB 11.4: a sync target sharing the source's server created sluice's own control table that way, and three streams refused at once. A leading run of plain session assignments, with no quotes, parentheses or comments before its `;`, is now skipped, and the statement after it is classified. Anything else stays as bounded as before. Pinned by new `TestClassifyDDLReach` cells (mutation-checked).
- **A serial-apply refusal no longer logs a remedy the running command cannot carry out ahead of the one it can (LOW, loud; Bug 309; v0.159.3, and in earlier releases the returned remedy was the stream one too, Bug 308).** With `--apply-concurrency=1`, the shared batch loop logged a WARN (`batch rollback on position-write error` or `batch rollback on error`) carrying the applier's raw error. For a chain restore's `KEY-COLLATION-MERGE`, that repeated the stream remedy (`sluice sync start --restart-from-scratch`, `sluice sync from-backup run --reset-target-data --yes`) ahead of the correct one that `restore` then printed: a fresh full backup. The returned refusal was right on every path, and the default lane path never logged the WARN. The batch loop's five failure arms now keep a transient error's text, because it is retried and the WARN is its only record, and leave out a terminal refusal's text, which the caller reports. Pinned by `TestBatchLoopRollbackWarn_WithholdsATerminalRefusal` and `TestBatchLoopRollbackWarn_EveryErrAttrIsGuarded`, which fails if a WARN in `batch_loop.go` logs a raw error. Both were mutation-checked in both directions.

## Corrected

- **The v0.159.3 notes** wrongly said `sync from-backup` was not affected by the Bug 306 fix. A `sync from-backup run --reset-target-data` cold start replays through chain restore and was affected (Bug 310). The published v0.159.3 notes and their archive already carry the correction.

## Compatibility

**Backup format: `BackupFormatVersion` is now 14, so this is a minor release.** The stamp is proportional. Only an **incremental (CDC) segment from a Postgres source** is stamped 14, and only when its window's schema history records a primary-key or UNIQUE-key column whose collation is nondeterministic and was not established for its rows. That happens when the column's catalog row was rewritten after the replayed rows, or in their own transaction. Full backups, segments with no schema change, segments whose key collations the change stream established, and every MySQL, MariaDB, VStream and trigger-CDC segment keep the version they had before. Two stated over-approximations: under `REPLICA IDENTITY FULL` a Postgres change stream reports every column as part of the key, so an altered nondeterministic non-key column also stamps 14; and a schema-history entry this binary cannot decode stamps 14 as well as 13. Either costs a refusal on an older binary, never a merge.
- **A chain containing a 14 segment needs v0.160.0 or later** for `restore`, chain replay, `backup verify` and `sync from-backup`. v0.159.x refuses it with `format version 14 is newer than this build supports (13)`, touching nothing on the target. Older binaries refuse at their own, lower ceilings.
- Chains written by earlier releases stay readable by this release. They carry no not-established marks, because only this release's reader writes them. **That also means this release cannot detect the merge in them:** a window that a v0.159.x `backup incremental` or `backup stream` captured across a tightened-and-loosened Postgres key still restores with the rows merged on v0.160.0, at exit 0 (measured by the v0.160.0 regression cycle). If such a change happened on a backed-up table, take a fresh `backup full` and base future restores on it, and check targets already restored with `sluice verify`.

**The behaviour changes (no flag or default changed):**
- **Postgres key-collation checks are stricter.** A key whose catalog row changed after the replayed rows, or in their transaction, compares byte for byte, so a byte-different conflict refuses `KEY-COLLATION-MERGE`. This applies to any change to that column's catalog row: a collation change, a rename, `SET NOT NULL`, a column-level `GRANT`, or a `CREATE TABLE` with its seed rows in one transaction. `sync from-backup` cannot compare bytes, so it refuses any such window outright with `KEY-COLLATION-HISTORY-UNORDERED`; take a new full backup to replay past it.
- **New capture refusal `KEY-COLLATION-SAME-ANCHOR`** for a Postgres `backup stream` or `backup incremental` window that holds a row of a table and then sees that table's key collation change, including a forward-only change that used to restore correctly. The remedy is a fresh full backup after the change.
- **A cancelled `backup stream`** whose last flush fails on a schema-history refusal now exits non-zero with that refusal, instead of a `BACKUP-WINDOW-ABANDONED-OPEN-TRANSACTION` WARN and exit 0. Store-write failures under the cancel keep the old WARN handling.
- **Serial-apply WARN text** (`--apply-concurrency=1`): a terminal refusal's text is no longer repeated in the batch-rollback WARN. Anything matching on that WARN's error text will see less.

**Not covered, stated:** a DDL whose transaction got its xid before the replayed one but committed after it reads as older, so it is not caught. A table or key column renamed or dropped after the replayed rows misses the catalog lookup (by name) and stays unguarded, as before. A chain written before this release kept no trace of a dropped same-anchor shape, so its restore cannot refuse.

**Not affected:** MySQL, MariaDB, Vitess (VStream) and trigger-CDC sources by the Postgres fixes (only the Postgres change-stream reader records a collation as not established). Postgres sources by the look-ahead fix, which is MySQL-family only.

**Dependencies:** `github.com/Azure/azure-sdk-for-go/sdk/storage/azblob` 1.6.4 → 1.8.2 (#350), `github.com/parquet-go/parquet-go` 0.30.1 → 0.32.0 (#329), and `actions/setup-go` 6.5.0 → 7.0.0 in CI only (#295).

## Known issues

- **KEY-COLLATION-ROLLOVER-SPLIT-DELTA-DUP (open, loud, timing-dependent).** When a `backup stream` rollover splits a reverted key-collation window so that the revert lands in a later window than the row it made legal, chain restore can fail with the target's own `Error 1062 Duplicate entry` instead of a named refusal. Nothing merges.
- **KEY-COLLATION-DRAIN-NO-DELTA (MEDIUM, loud; open, unchanged)** and **KEY-COLLATION-VSTREAM-UNSTAMPED (silent on a downgrade only; open, unchanged)**, as described in the v0.159.3 notes. VStream and trigger-CDC sources still record no collation.

## Who needs this — action required

- **Postgres-source backup operators whose primary-key or UNIQUE-key columns use a nondeterministic (ICU) collation, and who changed such a key's collation (especially tightened it and later loosened it back) on v0.159.0 through v0.159.3.** A restore through a window spanning that change may hold one row where the source holds two, at exit 0. **Check:** on a quiesced pair, run `sluice verify` (row counts); every merge shows as a mismatch. To find candidates directly, use the collision query from the v0.159.3 notes on the source, grouping the key under the collation the target key uses (`GROUP BY lower(k)` is an approximation for a case-insensitive key). **Action:** re-copy any table that differs, and take a fresh `backup full` after the key change as the base for future restores.
- **Postgres → Postgres `sync start` operators who changed a key's collation and changed it back inside one transaction on v0.159.0 through v0.159.3.** The live target may have merged rows. **Check and action:** as above, using `sluice verify`, and re-copy (`sync start --restart-from-scratch`) any table that mismatches.
- **Anyone who runs more than one sluice version over the same backup chain** (for example, a v0.160.0 writer with a v0.159.x restore host). Once a 14 segment exists, v0.159.x refuses the chain. **Action:** upgrade every binary that reads the chain to v0.160.0 or later.
- **Postgres `backup stream` and `backup incremental` operators** who change key collations on live tables: expect `KEY-COLLATION-SAME-ANCHOR` at capture, and take a fresh `backup full` after the change when it fires.
- **MySQL or MariaDB streams that refused `SLUICE-E-CDC-SCHEMA-REPLAY-MISMATCH` on every retry on a shared server, on v0.158.0 through v0.159.3:** upgrade and restart. Nothing was lost; the stream had stopped loudly.
- **Everyone else:** upgrade.
