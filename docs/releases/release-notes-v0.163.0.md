# sluice v0.163.0

**HIGH fix, silent — a warm `sync start` no longer applies a table's changes onto a target copy the stream never made or stopped keeping up (Bug 321, `INCLUDE-TABLE-SCOPE-DRIFT`); and a table brought in with `schema add-table` now stays in the stream across restarts.** A warm resume copies nothing, so a table widened into `--include-table`, re-admitted after a narrowing, left behind by a failed `schema add-table`, or swapped or re-created while the stream was stopped was streamed onto an empty, partial or wrong target copy (or not streamed at all) at exit 0. Each stream now keeps a record of the tables it actually copied, and a warm resume refuses before the reader opens when its scope disagrees with that record. No backup format change. This is a MINOR: some configurations that used to start now refuse at their next start, and `sluice schema add-table --abandon` and `sync start --accept-table-rename` are new; see Compatibility.

## Fixed

- **A warm resume whose scope holds a table the stream never brought in, or stopped keeping up, now refuses with `INCLUDE-TABLE-SCOPE-DRIFT` (Bug 321, HIGH, silent).** The shapes that exited 0 before this release:
  - **A table widened into `--include-table` on a restart.** On a Postgres pgoutput source only the cold start scopes the publication, so the table was neither copied nor streamed and stayed empty or absent on the target. On a MySQL-family, VStream or trigger-CDC source, or through a publication that delivers it anyway (shared with another stream, `FOR ALL TABLES`, a multi-schema stream's), it was streamed from the persisted position onto a target copy missing everything before it.
  - **A table narrowed out of scope and later re-admitted** had its changes for the narrowed window discarded (INCLUDE-TABLE-RE-WIDEN).
  - **A failed `schema add-table`** had already added its table to the publication, so a later restart streamed new changes into a table missing its original rows.
  - **A table dropped and recreated, or swapped with another, while the stream was stopped.** Under a `FOR TABLE` publication the stream carried on with no log line; a swap (`RENAME TABLE t8 TO tmp, t9 TO t8, tmp TO t9`) applied each table's changes onto the other's target copy. These now refuse as `TABLE-IDENTITY-CHANGED`.
  - **Affected releases.** Measured on v0.161.1 and v0.162.0. By code reading, the widened-include shape on a Postgres source is present from v0.5.0 (where the publication became a cold-start-scoped `FOR TABLE` list, ADR-0021) through v0.162.0, and the failed-add-table shape from v0.15.0 (where `schema add-table` shipped) through v0.162.0. The first release carrying each of the other shapes is not pinned here; treat every release through v0.162.0 as affected.
  - **The record.** Each stream's control row now carries `established_tables` (what each cold start copied, every lane and every namespace of a multi-database stream, plus each completed `schema add-table`), `dropped_tables` (established tables a later restart's scope left out) and `pending_added_tables` (each `schema add-table` in flight, with a 30-second heartbeat in the control-table server's clock). A cold start marks the record at its point of no return (just before `--restart-from-scratch` / `--reset-target-data` drops the target, or before the copy's first write) and replaces the mark with the copied set when it finishes; a warm resume after a cold start interrupted past that point refuses with `COLD-START-INCOMPLETE` until a cold start finishes. A stream's first cold start has no control row to mark until its CDC anchor, so the anchor write itself records the copied tables and their ids, in the same transaction (`TestIncludeTableScopeDrift_PgoutputStopAtTheAnchorRefuses`, `TestIncludeTableScopeDrift_BinlogStopAtTheAnchorRefuses`).
  - **What refuses at a warm resume.** A table named literally in `--include-table` (no glob characters, case-sensitive) that the stream never copied; a dropped table that any scope re-admits, literal, glob or unfiltered; a never-copied table admitted by a glob or an unfiltered stream whose changes would nevertheless be applied (its publication delivers it, or on a source with no publication its target table exists); an established table that a `FOR TABLE` publication no longer lists; and an in-scope table whose add-table is pending. A never-copied table whose changes are provably not applied keeps the old rule (it stays out until `schema add-table` brings it in) and is named in an `INCLUDE-TABLE-NOT-ESTABLISHED` WARN on every resume.
  - **The refusal** names each table, is codeless (exit 1, match on the marker), and is on the fleet supervisor's do-not-restart list (`supervisor_restart_refusals.go`). When every refused table has an add-table still running (heartbeat under five minutes old), the resume instead defers with `INCLUDE-TABLE-ADD-IN-PROGRESS`, which the supervisor does restart. An add-table whose entry was abandoned or taken over by another run stops with `PENDING-ADD-SUPERSEDED`, cancels its copy and records nothing. A failed add-table marks its entry as no longer running and, on a Postgres source, takes back its publication add.
  - **Renames are followed, not refused.** The record keeps each table's engine-stable id (Postgres `pg_class.oid`, InnoDB `TABLE_ID`) and follows a table renamed while stopped when the target was renamed too (it holds the new name and no longer the old one). Where no id proves the rename (a PlanetScale or Vitess source, an encoded InnoDB name), the refusal names the new `--accept-table-rename <old>=<new>`. On Postgres any same-name oid change refuses (`VACUUM FULL`, `CLUSTER`, `TRUNCATE` and rewriting `ALTER`s keep the oid, measured); on MySQL-family a bare id change is accepted and recorded, because InnoDB assigns a new id on `OPTIMIZE TABLE`, a copying `ALTER` and `TRUNCATE`.
  - **Related fixes in the same path.** A narrowing that cannot be recorded now refuses the start with `INCLUDE-TABLE-NARROWING-UNRECORDED` instead of warning and leaving the table recorded as established. Every refusal a single-database cold start makes from the schema alone (the array-bytes preflight against a MySQL-family target and the query-timeout raise's two configuration refusals) now runs before `--restart-from-scratch` or `--reset-target-data` drops the target; the array preflight used to run after the drop. A record value that does not decode no longer blocks its own recovery: `--restart-from-scratch` overwrites it. A record column of a shorter type (MySQL-family `TEXT`/`VARCHAR`, Postgres `VARCHAR`) refuses with the `ALTER` that fixes it. On a MySQL-family control table the add-table clock no longer reads an hour off during a DST fall-back (`TestMySQLServerNowMillis_DSTFallBack`).
  - Pinned on real servers by the Bug 321 integration family in `include_table_scope_drift_integration_test.go`, among them `TestIncludeTableScopeDrift_PgoutputWidenedTableRefusedThenAddTableConverges`, `TestIncludeTableScopeDrift_MySQLLiteralPrecreatedTableRefused`, `TestIncludeTableScopeDrift_PgoutputFailedAddTableRefused`, `TestIncludeTableScopeDrift_GlobRewidenRefuses`, `TestIncludeTableScopeDrift_SharedPublicationRefuses`, `TestIncludeTableScopeDrift_PgoutputSwapWhileStoppedRefuses`, `TestIncludeTableScopeDrift_BinlogSwapWhileStoppedRefuses`, `TestIncludeTableScopeDrift_PgoutputRewriteKeepsTheTable`, `TestIncludeTableScopeDrift_PgoutputRenameFollowed` and `TestIncludeTableScopeDrift_RestartFromScratchRefusesBeforeDropping`, plus unit cells including `TestScopeDriftDoor_EstablishedArm`, `TestScopeDriftDoor_DroppedArm`, `TestScopeDriftDoor_ColdStartInProgress` and `TestScopeDriftDoor_TableIdentity`. The independent expected value is the stream's own per-cold-start copy record compared with the restart's scope and the publication's membership, never the scope the restart was given.

- **A table `schema add-table` brought into a stream stays in it across restarts, on every source (Bug 321 follow-up, silent).** The add now records the table in the stream's live-added set (`live_added_tables`), which every later start admits whatever `--include-table` says; it used to be recorded only on MySQL's `--no-drain` path. The documented staged-wave flow on a Postgres source (an `--include-table 'orders,order_items'` stream, `schema add-table users`, the same `sync start` again) silently stopped applying `users` at the dispatch filter, as did any restart after a drained add on any source. By code reading this is present from v0.15.0, where `schema add-table` shipped and the stream already filtered changes by `--include-table`, through v0.162.0.
  - **A cold start now copies the live-added tables too.** `--restart-from-scratch`, an interrupted copy's resume, and the re-snapshot after an invalid position used to copy only what the flags named and then stream a live-added table from its new snapshot onto a target copy missing every change made while stopped (measured on pgoutput and MySQL binlog). `--reset-target-data` deletes the live-added set along with the control row; a WARN names each live-added table it discards.
  - **An `--exclude-table` naming a live-added table now refuses as `LIVE-ADDED-TABLE-EXCLUDED`** (terminal, carrying `INCLUDE-TABLE-SCOPE-DRIFT`) at every start, and in a running stream as soon as its live-added poll sees a `--no-drain` add of an excluded table. Through v0.162.0 a MySQL `--no-drain` add silently won over the exclusion. The running stream first records, in one locked transaction, that the table's changes in the poll window (at most 5 seconds, ADR-0034) were discarded: the add's entry is marked abandoned and the table moves to the dropped set, so a restart that only narrows the exclusion refuses rather than streaming onto a copy missing those changes.
  - **A table name the MySQL-family live-added set cannot hold now refuses before the add changes anything.** On a MySQL-family target `live_added_tables` is a comma list trimmed on read, so `schema add-table` used to record a table named `" t"` as `t`, after which the stream applied a different table and dropped this one's changes; a name holding a comma was refused only after the copy. Both now refuse at add-table's preflight, naming the glob route (`--include-table` with `?` for each such character, then `--restart-from-scratch`). Each warm resume also WARNs about live-added entries the source catalog does not hold, so `--abandon` can retire them (`LIVE-ADDED-TABLE-NOT-IN-CATALOG`); a name an older release recorded with a comma still reads back as several names. Pinned by `TestIncludeTableScopeDrift_BinlogUnholdableNameRefusesBeforeTheCopy`.
  - Pinned by `TestIncludeTableScopeDrift_PgoutputAddedTableStaysInScope`, `TestIncludeTableScopeDrift_BinlogDrainedAddedTableStaysInScope`, `TestIncludeTableScopeDrift_PgoutputRestartFromScratchCopiesTheAddedTable`, `TestIncludeTableScopeDrift_BinlogRestartFromScratchCopiesTheAddedTable`, `TestIncludeTableScopeDrift_PgoutputLiveAddOfAnExcludedTableStops`, `TestIncludeTableScopeDrift_BinlogLiveAddOfAnExcludedTableStops`, `TestLiveAddedExcluded_RunningStreamStops` and `TestLiveAddedExcluded_RetireFailureStillStops`.

- **Postgres publication guards no longer count another database's stream.** The ADR-0175 refusals to rescope a publication another stream may read (`SLUICE-E-CDC-PUBLICATION-SCOPE-CONFLICT`) now count only sluice slots on the publication's own database, because a slot on another database cannot read it. Before, any server that also hosted a stream on a second database refused the rescope. Pinned by `TestOtherSluiceSlots_OnlyThisDatabase` and `TestIncludeTableScopeDrift_LegacySlotOnAnotherDatabaseIsNotAPeer`.

## Features

- **`sluice schema add-table --abandon <table> --yes`** retires an add-table entry no add-table can clear (a failed or killed add, for a table since dropped on the source or taken out of scope), or takes a completed add's table out of the live-added set. It refuses while the add is still running, and refuses without changing anything when the stream's record cannot be read. It marks the entry abandoned rather than removing it, drops the dead add's inactive `sluice_addtable_<table>` snapshot slot (which otherwise pins source WAL), and tells you to restart: `sync health` exits 1 with `ADD-TABLE ABANDONED` until a start clears the entry.
- **`sync start --accept-table-rename <old>=<new>`** (repeatable) acknowledges a rename that no engine id proves. It is held to the same target rule as an id-proven rename, and the target table under the new name is then trusted as-is.
- **`sync health` reports pending add-tables.** A running one is in progress (exit 0); one whose heartbeat is more than five minutes old is `ADD-TABLE INCOMPLETE` (exit 1). A malformed entry is reported rather than failing the command. The text `sync status` lists them too.
- **`sluice control-tables ddl`** now prints all four record columns (including MySQL's long-missing `live_added_tables`), held to what sluice ensures by `TestControlTableDDLPrintsEveryEnsuredColumn` on both engines.

## Not closed, stated

- **The check runs when a stream starts; nothing re-checks a running stream.** An add-table killed mid-copy, an abandon of an add whose table the stream is still applying, and a later cold start stopped between its anchor write and its record write are caught at the next start. `sync health` is the running-stream signal. A process killed mid-`schema add-table` cannot take back its publication add, so a running stream keeps applying into the partial copy until `sync health` reports it stale or the stream restarts; the add's snapshot slot is persistent and survives the kill until `--abandon` drops it (ADD-TABLE-SNAPSHOT-SLOT-PERSISTENT).
- **Streams without a record.** A stream cold-started by an earlier release, or only ever cold-started on a control table this role cannot ALTER, has no record. It falls back to its publication's membership for literal includes, only when no other sluice slot exists on the same database, and otherwise logs `INCLUDE-TABLE-SCOPE-UNRECORDED` on each resume and has no evidence. sluice does not seed the record from the current scope, because that would record a never-copied table as copied.
- **A table dropped and re-created under the same name while stopped is still uncaught on MySQL-family** (TABLE-RECREATED-WHILE-STOPPED), since a bare InnoDB id change is accepted. On Postgres it refuses wherever the record carries ids. Whether a binlog source has a further equivalent is not yet established. MySQL-family ids are not recorded at all for a table whose name InnoDB stores filename-encoded, for every table of a database whose name it encodes (such as `my-db`), or for a partitioned table, so a swap made while stopped is not seen there either (MYSQL-TABLE-IDS-NAME-ENCODING-AND-PARTITIONS).
- **A Postgres table dropped and re-created while an interrupted cold start was stopped, before it resumed** (RESUMED-COLD-START-CERTIFIES-RECREATED-TABLE, HIGH, silent, measured on Postgres 16 under `FOR ALL TABLES` and `FOR TABLE`; present since v0.149.0, where the resume shipped; not fixed in this release). The resume tracks copy progress by table name, so it does not re-copy the new table. The ids it records are read after the stop, so they certify the new table. Under a `FOR TABLE` publication the resumed run applies none of the new table's changes until the next start refuses. Under `FOR ALL TABLES` or `FOR TABLES IN SCHEMA`, the new table's changes are applied onto the old table's copy and nothing refuses. Until it is fixed, re-copy a table re-created during an interrupted cold start with `--restart-from-scratch` (remedy not measured).
- **Multi-database streams.** `schema add-table` cannot extend their record, so the refusal names only the re-copy. Each database's cold-start refusals run after earlier databases were copied (and, under `--restart-from-scratch` or `--reset-target-data`, dropped), so such a refusal repeats after re-copying them (MULTIDB-COLDSTART-REFUSAL-AFTER-COPY).
- **A later cold start killed between its anchor write and its record write** (`--restart-from-scratch` or a re-snapshot; `--reset-target-data` deletes the control row, so its anchor records the copy like a first cold start) leaves the in-progress mark, so the next warm resume refuses `COLD-START-INCOMPLETE` although the copy finished. This is loud and cleared by a re-copy. A stream's first cold start writes the copied tables and their ids in the same transaction as its anchor, so it warm-resumes instead; if the record columns cannot be added there, it logs `COLD-START-ANCHOR-UNRECORDED` and has no record.
- **A `LIVE-ADDED-TABLE-EXCLUDED` stop that cannot record the table as dropped** — its control-row write fails, or the stream's record is a legacy one, a multi-database one or a cold start in progress — still stops, and its refusal names the reason and says that a restart which only narrows the exclusion is then not protected, so the copy must be redone.
- **SQLite and D1 targets keep no live-added set or established-table record.** `schema add-table` onto one WARNs at add time that the table must be named in `--include-table` on every restart; a restart that does not name it stops applying its changes, and nothing at that restart says so.
- `sync status --format json` does not carry the pending record yet (`sync health --format json` does). An in-scope table with no capture trigger on a trigger-CDC source captures nothing, at cold start as well; that is a separate class.

## Maintenance

- **Not run for this release: `d1verify` and `psverify`.** `scripts/prerelease-triggers.sh` raised its unscheduled-pin advisory for this delta: `d1verify` has no workflow at all, and `psverify` is dispatch-only, and the delta touches `internal/pipeline/`, `internal/engines/mysql/` and `internal/engines/postgres/`, which both suites cover. Neither was run, because each needs live infrastructure (Cloudflare D1 credentials and a billable PlanetScale database) that was not provisioned for this release. Coverage is the CI integration matrix on real MySQL, MariaDB and Postgres containers plus the Integration (vstream) job. Behaviour against a real PlanetScale cluster and live D1 is unmeasured for this release; on those sources a rename is followed only through `--accept-table-rename`, as above.

## Compatibility

- **No flag default changed and no backup format change** (`BackupFormatVersion` stays 15). New flags: `--abandon` on `schema add-table`, `--accept-table-rename` on `sync start`.
- **Some configurations that started on v0.162.0 now refuse at their next start.** A literal `--include-table` entry for a table the stream never copied refuses, including one shape that used to work by luck on a MySQL-family source: a table created on the source and pre-created on the target while stopped, then named on the restart. So does a never-copied table admitted by a glob or no filter whose changes would be applied, any table that left the scope and came back, a warm resume after an interrupted cold start (`COLD-START-INCOMPLETE`), an `--exclude-table` naming a live-added table (`LIVE-ADDED-TABLE-EXCLUDED`), and on Postgres a table re-created or swapped while stopped (`TABLE-IDENTITY-CHANGED`).
- **A table added with `schema add-table` is now in scope until you take it out**, whatever the restart's `--include-table` says. A stream that relied on a restart quietly dropping it must now run `schema add-table --abandon <table> --yes`. `--restart-from-scratch` re-copies the live-added tables; `--reset-target-data` discards the live-added set (WARN), so re-add or name those tables afterwards.
- **New control-row columns, added on first write:** `pending_added_tables` by `schema add-table`, `established_tables` and `dropped_tables` by a cold start (and by a restart that narrows the scope). On a control table pre-created by a role that cannot ALTER it (or a PlanetScale safe-migrations branch), add-table refuses before changing anything and names the statement to run, and a first cold start WARNs `INCLUDE-TABLE-SCOPE-UNRECORDED` and runs without the record. A warm resume issues no new DDL unless it narrows the scope. On a MySQL-family control table `live_added_tables` is now `LONGTEXT` in `utf8mb4` and is ensured together with the three new columns (v0.27.0–v0.162.0 created it as `TEXT`, and `sluice control-tables ddl` never printed it): an existing `TEXT` or non-`utf8mb4` column is widened in place where sluice can ALTER, and otherwise refused with one statement built from the columns the table actually has (`ADD` for a missing column, `MODIFY` for one of the wrong type), which runs as printed (`TestTableSetColumnsDDL_RunsOnEveryReleasedShape`); `docs/managed-services.md` gives it for safe-migrations branches.
- **Postgres publication guards are narrower:** a stream on another database of the same server no longer triggers `SLUICE-E-CDC-PUBLICATION-SCOPE-CONFLICT`.
- **`sync health`** stays exit 0 while an add-table is still copying, and exits 1 once its heartbeat is more than five minutes old or the entry was abandoned.

## Who needs this — action required

- **Anyone who, on any release through v0.162.0, restarted a stream with a wider `--include-table` (or a glob or no filter that newly admitted a table), re-admitted a table after narrowing it out, restarted after a failed `schema add-table`, or restarted after re-creating or swapping tables on the source while the stream was stopped.** Those tables may be empty, partial or holding another table's rows on the target, at exit 0. Compare each such table's target rows against the source's (a row-count shortfall or an empty table is the tell). To repair one: with the stream stopped, empty the target table and run `sluice schema add-table <table>`, then the same `sync start`; or re-copy with `sync start --restart-from-scratch` (on a Postgres source after `sluice slot drop`). On a multi-database stream, re-copy.
- **Anyone who ran `schema add-table` on a Postgres source and then restarted with the original `--include-table`, or restarted after a drained add on any source.** The added table stopped receiving changes at that restart. Compare it against the source and repair it as above. The table now stays in scope on v0.163.0.
- **Anyone who ran a MySQL `--no-drain` `schema add-table` for a table the stream's `--exclude-table` named.** The add won over the exclusion; decide which you meant. On v0.163.0 the start refuses with `LIVE-ADDED-TABLE-EXCLUDED` until you keep the exclusion (and `--abandon` the add) or remove it.
- **Streams cold-started before v0.163.0** have no record and are judged only by their publication, or not at all (`INCLUDE-TABLE-SCOPE-UNRECORDED`). To get full protection, run one `--restart-from-scratch` after upgrading.
- **Anyone on v0.149.0 or later whose Postgres cold start was interrupted, resumed (`COLD-START-RESUMED`), and had a table dropped and re-created on the source in between.** That table's target copy may hold the old table's rows with the new table's changes applied on top, at exit 0. Compare it against the source; re-copy it with `--restart-from-scratch` (remedy not measured).
- **Everyone else:** upgrade. If a start refuses with `INCLUDE-TABLE-SCOPE-DRIFT`, the refusal names each table and its remedy.
