# sluice v0.115.0

**CRITICAL fix — two source tables could silently become ONE table on the target, with the losing table's rows INSERTed into the winner and the run exiting 0. Two engines, two mechanisms: on a SQLite target `CREATE TABLE IF NOT EXISTS` writes a bare, case-folded name so a collision is a success that creates nothing, and on a MySQL-family target running `lower_case_table_names != 0` the colliding CREATE returns Note 1050 — a warning — and creates nothing. Both are refused before any data moves, from every copy entry point. Also fixed: a `bytea` value arriving SHORTER than it left on a MySQL CDC lane. Upgrading from v0.114.0 is drop-in in the mechanical sense — no flag added, renamed or removed, no on-disk format change, no backup chain repartitioned — but four new error codes exist and several runs that previously exited 0 will now refuse. Those are in Compatibility.**

This release is the table-name half of a family sluice has been closing one member at a time. v0.114.0 refused SQLite's silent index-name no-op; v0.113.0's audit produced the entries; this one closes the two members that lose ROWS rather than an object, plus the audit's remaining value-fidelity door. The provenance is the same as the last two releases and worth stating plainly: nothing here came from a user hitting it. Item 148 was found by item 147's own sibling sweep, item 149 by item 148's roster refusing to record an exemption it could not argue for, and the audit B-2 follow-ups by a value-fidelity review of B-2's own fix. Three items also correct claims sluice had already published — a perf-parity row asserting a test that never existed, an engine list that could not name three of the engines it covered, and sixteen runtime messages naming command lines that exit 80. Two findings surfaced during this work are OPEN and are named at the end rather than quietly carried.

## Fixed

**Two source tables landing on ONE table on a SQLite target: both tables' rows in one table, at exit 0, with no operator-visible signal during the run (item 148).** SQLite keeps tables and views in one flat, ASCII-case-folded namespace, and sluice emits `CREATE TABLE IF NOT EXISTS` with a bare, never-qualified name — load-bearing for an idempotent `--resume`. So a PostgreSQL source legitimately holding `public.orders` and `public."Orders"` hands SQLite one name twice: the second CREATE returns OK and creates nothing, and the copy then INSERTs the second table's rows under a name that folds to the first table. **This is the worst member of the `IF NOT EXISTS` silent-no-op family precisely because nothing goes missing.** A lost index or a lost view is an absent object; here every row the copy read is written, no statement fails, and the run reports success. Reproduced end to end before the fix on a real Postgres source and a real SQLite target, with the oracle being the target file's own catalog rather than anything sluice reports: `map[Orders:4]` where the source holds two tables of two rows each.

**The fix is one claim pass over SQLite's flat namespace, and the shape of it was decided by ground truth rather than by symmetry.** `scanSQLiteObjectNamespace` claims tables then views in target phase order — so the prior claimant a refusal names is the object that would actually have survived — and reports table losers under the new `SLUICE-E-SCHEMA-TABLE-NAME-COLLISION` and view losers under item 147's `SLUICE-E-SCHEMA-VIEW-NAME-COLLISION`. That deletes the drift seam item 147 left behind, which was a comment in the view walk saying a duplicate TABLE name was deliberately not that function's refusal — the defect written down inside the function that already had the data. **The walk deliberately does NOT claim index names, and that asymmetry is measured rather than assumed:** on the driver this engine uses, `CREATE TABLE IF NOT EXISTS "ix"` against an existing index is a LOUD error, with or without `IF NOT EXISTS`, as is `CREATE INDEX IF NOT EXISTS "a"` against an existing table. Only the table-versus-table-or-view pair is silent. A unified walk would have refused runs that already fail visibly. Two doors carry it: a new connection-free `ir.TableEmitPreflighter` wired at all six copy entry points, and the create-tables phase itself.

**A second route, and route 1's check provably does not catch it: the multi-namespace fan-out into a target that has no namespaces.** Both fan-out orchestrators branch on the target implementing `ir.DatabaseDSNDeriver`, and `migrate`'s `else` arm carried a comment asserting it "is unreachable with today's engines". That was FALSE from the moment SQLite landed — SQLite implements neither `ir.DatabaseDSNDeriver` nor `ir.SchemaSetter`, so the arm ran, set `TargetSchema`, and `ApplyTargetSchema` discarded it, and every source namespace wrote bare names into ONE file. `migcore.ValidateMultiNamespaceTarget` now refuses the CONFIGURATION up front under `SLUICE-E-CONFIG-MULTI-NAMESPACE-TARGET-FLAT`, at both fan-outs. **It refuses the configuration rather than the collision on purpose:** same-named tables are the case that loses data today, but a flat target given N namespaces produces a merged file that neither `verify`, a later `add-table`, nor CDC apply can route back to a source namespace even when no name collides. A fan-out resolving to exactly one namespace is allowed through — that is a rename or a single-namespace filter, which a flat target can serve losslessly. The wiring is held by a DERIVED AST roster rather than a hand-maintained one, because hand-maintenance is how this propagated: the sync fan-out was written by copying the migrate one.

**Affected releases: v0.99.146, when SQLite shipped as a migrate target, through v0.114.0** — that commit (`4c99e7a7`) introduced both the bare `CREATE TABLE IF NOT EXISTS` emit and the only flat target engine sluice has, and `git tag --contains` puts it first in v0.99.146. Route 1 needs a source that can carry two names differing only in ASCII case (a PostgreSQL source with quoted identifiers is the ordinary way); route 2 needs a multi-namespace fan-out, which has existed since v0.99.16 but had no flat target to fan out into until v0.99.146. Cloudflare D1 is NOT affected by either route, and the reason is stronger than "the `d1` engine is a migrate source only" — **there is no D1 target PATH at all.** `d1Engine` refuses all three writer doors, and the `sqlite` engine's DSN parser has no `d1://` case, so the routing that would carry a D1 target through the SQLite engine does not exist: such a DSN is read as a literal file path. That is the retraction described below, and it corrects v0.114.0's notes, which said the sibling index collision reached "D1 targets".

**The identical merge on a MySQL-family target, by a different mechanism, and item 148 filed it as a KNOWN GAP rather than an exemption because there was no safety argument to state (item 149).** MySQL's `ddl_emit.go` writes the same bare `CREATE TABLE IF NOT EXISTS`, and a server running `lower_case_table_names != 0` — the default on Windows and macOS servers, and a legitimate deliberate setting on Linux — answers the second CREATE with **Note 1050, a warning**, and creates nothing. The losing table's rows are then INSERTed into the table that won the name. Reproduced end to end before the fix: `map[orders:4]` read from the target's own catalog, where the source holds two tables of two rows each, at exit 0.

**What made this a fourth sibling rather than a weakening of the third is that the fold is a property of the SERVER, not of the schema.** Item 148's `ir.TableEmitPreflighter` is connection-free by contract, and a check that folded unconditionally would refuse `orders` + `Orders` on every stock Linux MySQL, where that pair is two ordinary tables. So this ships as a connection-BEARING surface — `ir.TableNameFoldPreflighter` + `migcore.PreflightTableNameFold`, wired at the same six copy entry points, with the existing roster extended by one string rather than forked — plus a second door in `SchemaWriter.CreateTablesWithoutConstraints`, which asks the same question on its own connection. Both doors are needed for the reason item 148 measured on the sibling engine: a run against a target whose tables already exist (`--resume`, a `sync` cold start onto a populated target, a restore) never reaches the create-tables phase and INSERTs straight into the folded name.

**Ground-truthed on real servers rather than cited, and one measurement changed the code.** On `mysql:8` and `mariadb:11.4`, identical on both: `lct=1` folds silently and merges the rows; `lct=0` does not fold and nothing is refused; `lct=2` requested on a case-sensitive filesystem is NOT honoured (mysqld logs MY-010160 and `@@global` reports 0, no fold) — which is why every predicate reads the EFFECTIVE global rather than the operator's configured intent, since a check keyed on intent would over-refuse every such server. And `lct=1` folds `é`/`É` too. **That last row corrected a comment already written the other way**, which had claimed Go's Unicode `strings.ToLower` folds a strict superset of the server's and that the residual was therefore over-refusal by construction; the doc now says UNVERIFIED PREMISE in those words about the general non-ASCII case and names both failure directions, since the under-refusal one is silent. Also measured, because the writer door runs on every flavor and a PlanetScale/Vitess connection terminates at vtgate rather than at mysqld: vtgate answers the variable with 0, so those flavors take the no-fold path and the door adds no failure mode. **Affected releases: v0.3.0, when MySQL's table emit gained `IF NOT EXISTS` (`29e18aa6`), through v0.114.0** — before that the second CREATE was a loud error. Only against a server whose effective `@@global.lower_case_table_names` is non-zero, and only where the source carries two tables whose names fold together.

**A `bytea` value arriving on a MySQL target SHORTER than it left the source, with the cold copy and CDC disagreeing about the same cell inside one run (audit finding B-2, MySQL half).** `\xdead` is both PostgreSQL's `bytea_output = hex` rendering of two bytes and six perfectly ordinary bytes. The MySQL writer's `prepareValue` hex-decoded any `\x`-prefixed string bound to a binary column, so a column an operator's `--type-override` had MADE binary — carrying its source's own bytes, not a rendering — was decoded as if it were one. Restoring the exact pre-fix code and running the real-server matrix reports `\xdead` stored at `OCTET_LENGTH=2` where the source held 6, and a bare `\x` stored as ZERO where it held 2. **The sharp part is the divergence WITHIN one run:** the cold-start copy stored six bytes and the first CDC update to the same cell stored two, with no error on either side and matching row counts.

**Closed in two pieces, because the two doors carry different evidence.** The RowWriter cores (batched INSERT and `LOAD DATA`) now decide on `ir.Column.SourceColumnType` through `columnIsNativelyBinary`: a natively binary column carries PostgreSQL's rendering, a column an override made binary carries its source's own bytes. That is the Bug 47 precedent from next door. The ChangeApplier cannot decide at all — its column descriptors come from the TARGET's `information_schema`, where an override leaves no trace, so `SourceColumnType` is nil for every column it ever sees and the natively-binary reading is the only one available to it. That half is closed by refusal instead. Separately, a `\x`-prefixed but unparseable rendering on a natively binary column is now REFUSED under the existing `SLUICE-E-VALUE-BYTEA-TEXT-UNRECOGNIZED` rather than stored as its ASCII, matching the discipline the array leaf already applied. **One named WART, resolved opposite to the array leaf's:** a string with NO `\x` prefix still passes through, because the applier lane cannot tell `--type-override col=binary_uuid` (ADR-0024, documented and recommended) from a rendering, and refusing it would break that documented override. **Affected releases: v0.86.0, when the `\x` hex-decode branch shipped with postgres-trigger Phase 2 (`c7cb3ac8`), through v0.114.0.** Before that a string on a binary column was stored as its own bytes and there was nothing to shorten.

**The refusal that closes the applier half reached `sync` and not `schema add-table`, and it was keyed on CONFIG where the hazard is SCHEMA.** Both were found by a value-fidelity review of the fix above, and both are HIGH. `schema add-table` carries its own `Mappings`, exposes `--type-override` on the CLI, creates the target column from the mapped type and then hands the table to the LIVE stream — the identical refused configuration, with add-table's own copy storing six bytes and the running applier storing two, at exit 0 with matching row counts. It now asks the preflight before any connection, held by `TestMappingsCDCLaneRoster`: a DERIVED roster over every struct in `internal/pipeline` carrying a `Mappings []config.Mapping` field, each enforced-or-exempt-with-a-reason (`Streamer` and `AddTable` enforced; `Migrator` exempt because it has no CDC lane and its reader decodes with the mapped type; `Differ` and `Previewer` exempt because `schema diff` and `schema preview` are read-only). **The config-keyed check is also structurally blind to the sequence that reproduces the hazard without any flag:** `migrate --type-override t.c=bytea` (honoured, the source's own bytes land) followed by a plain `sync` sees `len(mappings) == 0`, refuses nothing, and hex-decodes every later update — **and the refusal's own remedy prose opened by recommending exactly that sequence.** So a second, schema-keyed check now compares the source column's own type against the TARGET's own catalog type and refuses binary-target-with-non-binary-source whoever created it, and the remedy prose says `migrate` honours the override only as a one-shot and names both commands that must not later be pointed at the resulting column.

**A pre-existing foreign key on the target killed a `sync` cold start ~20 seconds in with nothing having warned first (item 140).** Reported from production: an operator branched their target from an existing database, so the foreign keys were already there. sluice's deferred-constraint discipline — create the tables bare, copy, then add indexes and constraints — governs only the constraints sluice CREATES, and the bulk copy is not parent-first ordered, so a child row reached the target before its parent and the run died on `Error 1452`. Their own read was right: it would not have been an issue on a brand-new database, which is exactly the problem — the failure is invisible until it happens and the remedy is obvious only to someone who already understands the design. This is a preflight gap rather than a copy bug: the target's foreign keys are readable before a single row moves, through the very SchemaReader the ADR-0166 shape gate already opens, so the check rides that one catalog read and costs no extra round trip. **Refuse versus warn splits on the PARENT's scope, not on posture:** parent in scope (a self-reference included) means the parent's rows arrive during this same copy with nothing ordering them first, so it REFUSES under `SLUICE-E-TARGET-PREEXISTING-FOREIGN-KEY` naming child, constraint and parent; parent out of scope means whatever that table holds predates this run and may well satisfy every child row, so it WARNs rather than refusing a configuration that works today. **`--skip-foreign-keys` is deliberately NOT an exemption:** it strips foreign keys from the IR so the constraints phase creates none, but it issues no DDL against the target, so a constraint already there survives it and still rejects the copy — exempting it would have waved a run through to the identical failure. The MySQL integration leg proves that on a real server by reading the constraint back off the target after the refusal.

**On this one the exemptions matter more than the coverage, and they are argued rather than assumed.** The check reaches `migrate`, single-database `sync` cold start, and — added in this same release after a perf-parity pass found the gap — the multi-database `sync` cold-start fan-out, which runs a first copy per database and would have failed identically N-1 databases in. `restore`, `chain restore` (and with it `sync from-backup`, whose reset leg IS a ChainRestore) and `schema add-table` are EXEMPT, and all three share one property: **the check cannot distinguish a foreign key the target was BRANCHED with from one an earlier sluice run CREATED.** On an entry point whose contract is "run me again and I converge", that ambiguity turns the refusal into a refusal for having worked. `ChainRestore` is the decisive case — `applyFull` re-enters `Restore.Run` once per segment with segment 0 establishing constraints, so every multi-segment chain restore would have been refused from segment 1 on. add-table is exempt for a different reason: its scoped schema holds tables not yet on the target, so the check is vacuous by construction while the catalog read it needs is not free. The residual is REAL and filed as gap 20 in the perf-parity matrix, not implied. Coverage is held by `TestPreExistingFKCheckNamesEveryCopyEntryPoint`, which derives the six entry points from the shared roster and is fail-by-default in both directions. The refusal is a no-op on SQLite targets, which declare `ir.Capabilities.BulkCopyBypassesForeignKeys` because `writePragmas` opens every writable connection with `foreign_keys(0)` — the zero value of that capability is the enforcing answer, so a future target engine is fail-closed.

**Sixteen runtime messages named command lines the binary does not have — two read mid-incident, and one piped verbatim into webhook, Slack and email.** `sluice sync start --resume` appeared in ten production string literals. `sync start` has no `--resume` and never had one: it warm-resumes by DEFAULT when re-invoked with the same `--stream-id`. Two of those are read while something is on fire — the Postgres CDC reader's `schemaRaceRecoveryHint`, and the schema-forward refusal whose message body ADR-0157 sends verbatim as the `Body` of a critical schema-drift notification to the same webhook/Slack/SMTP sinks the metrics alerter uses. **So sluice paged an operator and handed them a command line that exits 80 with `unknown flag --resume`.** The gate found sixteen where a docs sweep had found nine, and the extra seven were a second class: a flag real on a SIBLING command. **The sharpest of those is `sluice migrate --schema-already-applied`** in the partitioned-table refusal — that flag exists on `sync start` only, so an operator following the advice would have had `migrate` reject it outright. The rest: `restore --tables` (the flag is `--include-table`) in both `verify_read_depth.go` and the byte-equal error-code row it mirrors onto the site, `sync --where` (the command is `sync start --where`), and `sync --position-from-manifest`. Plus one flag real NOWHERE: `sluice sync start --reset-position`, which ADR-0022 explicitly records as having been considered and never built — corrected to `--restart-from-scratch`, the flag that actually discards a position, and the same phantom removed from ADR-0066's recovery step, where one ADR had been instructing operators to use what another ADR records as rejected. Separately, `schema preview` recommended `--type-override users.id=binary_uuid` with no hint that a `sync` run now REFUSES a binary `--type-override` — sluice's own advice walking an operator into sluice's own refusal — and the hint now derives its caveat from `translate.IsBinaryFamily`, the same predicate the refusal uses, so a second binary alias cannot silently diverge.

**The gate is `internal/climsggate`, an AST walker over Go STRING LITERALS with NO exemption list, and its scope is stated where it is defined rather than implied.** A runtime message has no business naming an unbuilt command, so there is no legitimate exemption — which is exactly why this one can be strict where a docs walk could not be. Truth is kong's command model directly, not the generated flag manifest, because the manifest records flags only and a command owning none leaves no line. The false-positive rule is what a no-exemption gate lives or dies on: a span is graded only when it starts at the word `sluice` and its first word resolves to a real command, and a delimited span ends at the author's own closing delimiter, so a flag named in prose OUTSIDE an invocation stays a reference rather than an instruction — which is how a message tells an operator that a flag was removed. Unknown SUBCOMMANDS are graded only inside a delimited span that also carries a flag. **That last rule is a real hole and it is named in the open list below, not glossed.** The sibling gate `scripts/check-skills-flags.sh` had the same defect from the other direction — it validated flags and subcommands in two separate name-only passes, so a skill saying `sluice sync start --resume` passed both — and now grades (command, flag) pairs with ancestor inheritance and a vacuous-pass floor. **Affected releases:** the phantom-flag class reaches back to **v0.15.0** for the oldest surviving production string (`c5268b20`, the add-table MVP); the ADR-0157-piped one dates to **v0.79.0** and the Postgres CDC one to **v0.93.0**; all through v0.114.0.

**Every engine list sluice publishes was derived from PACKAGE DIRECTORY names, so three of the five engines that can run a filtered continuous sync could never appear in one.** `internal/docsync`'s helper walked `internal/engines/` and returned directory names — but engine names are not directory names: `internal/engines/mysql` registers four engines (`mysql`, `mariadb`, `planetscale`, `vitess`) and `internal/engines/sqlite` registers two (`sqlite`, `d1`). So the derivation could only ever emit `mysql, postgres`, the marker it held the doc to was correct BY CONSTRUCTION, and the operator-facing prose beside it was bound to nothing. **This gate exists specifically because three consecutive releases shipped a wrong claim about which engines a filtered-sync behaviour applied to, and it could not have caught a fourth.** The live consequence: MariaDB can run a filtered continuous sync — its binlog `*CDCReader` carries the `ir.FullBeforeImageSetter` pin, and the pipeline gates on a plain type-assert with no flavor list — and it was absent from every engine list sluice published, including `docs/operator/filtered-subset-migration.md`. The derivation now keeps the AST pass to find which PACKAGES carry a pin and then maps package to registered engine names through the live registry, so markers name what an operator types into `--source-driver`; the marker reads `mariadb, mysql, planetscale, postgres, vitess`. One of the three users of the shared helper stays deliberately package-scoped and says so in its key name, because its pin is on `*vstreamSnapshotRows` and a package-to-names mapping would emit `mysql` and `mariadb` and state the OPPOSITE of the truth for both. A new gate holds the test binary's effective registry to `cmd/sluice/main.go`'s imports so a new engine package cannot silently shrink every derived list, and its doc records what mutation showed it does NOT reach. **Affected releases: v0.103.2, when the gate shipped, through v0.114.0.** No behaviour changed — this is a documentation defect — but the docs it governs are mirrored onto sluicesync.com from the same source.

**A `json[]` or `jsonb[]` column could not reach a Postgres target at all (item 145).** The array element dispatch had arms for boolean, integer, float, the string-leaf family, decimal, the temporal types and — as of v0.114.0 — the binary families, and none for `ir.JSON`, so a table carrying one aborted the copy. Loud and never silent; a PG→PG migration of such a table simply could not complete. It ships with a `[]byte` leaf, the shape `decodeBytes` produces on both read lanes, and the family × shape matrix is ground-truthed on real PG 16 for `json[]` AND `jsonb[]` — `array_dims`, per-element subscripts, `::text` src==dst — across 1-D, 2-D, NULL-element, empty, whole-column NULL, a JSON `null` beside a SQL NULL, and a document whose content spells the array-literal metacharacters. **The filing's own Bug-74 warning pointed at the wrong hazard and the mutations say so:** pgx's `JSONCodec.PlanEncode` is a TOTAL function, so `ArrayCodec` never declines for the `_json`/`_jsonb` element OIDs and the silent 2-D flatten is unreachable through the leaf — the exact mutation that reproduced the `bytea[]` flatten leaves the whole matrix green, recorded as an equivalent mutant. The real hazard is a silent `json.Marshal` re-encode, which the value pins catch. **The load-bearing decision is that the trigger-CDC door is REFUSED:** `to_jsonb` embeds a json element AS JSON, so after the payload decode a JSON `null` element is byte-identical to a SQL NULL element and an array-valued element is byte-identical to a nested dimension, both resolved before any leaf runs. Accepting those payload shapes would trade today's loud refusal for silent loss, so the leaf refuses them by name and `pgtrigger.Setup` gains a refusal that fires before a trigger is installed. **Affected releases: v0.1.0, when the Postgres row writer shipped with no JSON array arm (`b1206a20`), through v0.114.0.**

**SQLite's `CREATE VIEW IF NOT EXISTS` against an existing table or view returned OK and created nothing, so the view was simply absent at exit 0 (item 147).** Filed as OPEN in v0.114.0's notes and closed here, under its own `SLUICE-E-SCHEMA-VIEW-NAME-COLLISION` rather than the index code, because the object lost is a view, the namespace is the table/view one rather than the index one, and the remedy names a different rename. Note the asymmetry that hid it: the index-versus-table case is LOUD, so an operator who has seen sluice refuse a name collision reasonably assumes the class is covered. It is wired into `CreateTablesWithoutConstraints`, `CreateViews` and a new connection-free `Engine.PreflightViews`, and the sibling sweep records every other target engine as exempt with a reason — Postgres and postgres-trigger emit `CREATE OR REPLACE VIEW` and raise 42P07 on a base table; the MySQL flavors raise `ER_WRONG_OBJECT`; the rest are source-only. **Affected releases: v0.99.146 through v0.114.0.**

**And a Postgres sibling found in the same sweep: two source views sharing their first 63 bytes left one view carrying the other's body.** `validatePGIdentifier` — which refuses the >63-byte truncation collision at emit — had no VIEW call site. Views are the worst object kind for it: every other kind emits `IF NOT EXISTS` and no-ops on a collision, while `CREATE OR REPLACE VIEW` REPLACES. **Affected releases: v0.14.0, when PG view emit shipped (`a05cb989`), through v0.114.0** — the identifier check itself only arrived in v0.108.0 and never covered this call site.

**The cold-copy grow gate's trip claim is now DERIVED rather than asserted, and four false sentences are gone (item 143).** The crux question was whether sluice can distinguish a real storage-grow reparent from a plain transport drop at the point the ADR-0110 gate trips, and the answer is NO: a genuine grow's most common face on an in-flight write is the connection dying, which is byte-identical to a plain drop, and none of the three corroborating signals the filing proposed are available where the decision is made — the tier probe is a one-shot preflight capacity read that observes no storage quantity, `--min-storage` is not a sluice flag at all, and the telemetry sidecar is opt-in, absent on `migrate` and `restore`, lagging, never consulted at trip time, and documented as transiently vanishing across the very reparent it would corroborate. **So the trip set is UNCHANGED — narrowing it would trade a bounded, loud-safe false positive for the chance of missing the event the gate exists for — and what changes is the CLAIM.** `ir.GrowEvidence` is derived per trip by each engine from the SAME predicates its retry classifier uses and printed as `evidence=` on the gate's CLOSED/reopened lines and both engines' retry WARNs. Under-claiming is the rule: `QueryList.TerminateAll`, `code = Aborted`, 1205, 1213 and PG 53200/53000/class-08 all stay no-grow-evidence, a deliberate divergence from the filing's own list recorded in code, and the zero value under-claims. One of the retracted sentences was a source-read trip's comment calling a source drop "the READ-side face of a target storage-grow stall" on a path that observes the target not at all. **Affected releases: v0.99.92, when the cold-copy reparent retry shipped with that wording (`2e602f59`), through v0.114.0.** Log text and one new field only; no data was ever affected.

## Changed

**Four new error codes exist and several runs that previously exited 0 will now refuse.** `SLUICE-E-SCHEMA-TABLE-NAME-COLLISION` (SQLite targets by case fold, MySQL-family targets by server fold), `SLUICE-E-SCHEMA-VIEW-NAME-COLLISION` (SQLite targets), `SLUICE-E-CONFIG-MULTI-NAMESPACE-TARGET-FLAT` (a fan-out of two or more source namespaces into a target that can neither derive a per-namespace DSN nor accept a schema override) and `SLUICE-E-TARGET-PREEXISTING-FOREIGN-KEY`. Each fires before any data moves, at every copy entry point the fix reaches, and each names the objects involved and the rename or configuration change that clears it. **That is the loud half of a silent-loss defect, and it is intended.**

**A binary `--type-override` is now REFUSED on a continuous-sync run, and honoured on `migrate`.** `sluice sync start` and `sluice schema add-table` refuse an override that lands any column on a binary target type, on the mapping list alone — no schema, no connection — so it fires identically on cold start AND on warm resume. The known over-reach is stated rather than left implied: an override onto a binary type whose SOURCE column is already binary is a no-op and is refused too, because distinguishing it needs the source schema and therefore a connection, on a path that deliberately has none; the remedy is to drop the no-op override, and the message says so. `migrate` is deliberately not refused — it has no CDC lane, the reader decodes with the mapped type, and the value reaches the writer as `[]byte`, provenance-decided end to end. **The second, schema-keyed check refuses a run whose TARGET already holds a binary column for a non-binary source column, whoever created it**, comparing the source's own type against the target's own catalog. It runs on every single-database `sync` cold-start branch and on add-table, riding the ADR-0166 shape gate's existing catalog read (now memoized, so the cold start still makes one round trip), and it runs even under `--schema-already-applied` — that flag waives DDL on the operator's promise that the schema is compatible, and that promise is exactly what this checks. **Its reach is narrower than the config check's and this is stated at the function: it does NOT reach warm resume, which reads neither schema by design, and it does NOT reach the multi-database cold-start fan-out, which reads no target catalog of its own.** Both of those remain covered by the config-keyed refusal only, and the residual is filed rather than half-built.

**A MySQL-family-target `migrate --dry-run` now opens ONE target connection and reads ONE variable, where a single-database dry run previously touched no target at all.** The table-name-fold preflight must ask the server whether it folds, and a plan whose answer depends on a server setting cannot be produced without the server. It is skipped entirely for a schema with fewer than two tables, and it is the same trade the multi-namespace fan-out already made for the DATABASE axis of this same setting. The read is now memoised per SERVER (network identity, not DSN — the two callers pass different DSNs to the same server on purpose), successes only, so a 200-database fan-out that previously made roughly 400 connect/read/close cycles before any row moved now makes one per server. The environmental premise that holds up the memo gets a check rather than a sentence: an integration test asserts a real MySQL and a real MariaDB REFUSE `SET GLOBAL lower_case_table_names` as read-only.

**`schema preview`'s binary-override hint now carries its own caveat.** The `--type-override users.id=binary_uuid` suggestion is annotated "honoured by `migrate`; a continuous `sync` run REFUSES a binary `--type-override`", derived from the same predicate as the refusal.

**Two operator-facing help texts were corrected, and both were describing a gate that had moved.** `--backfill-added-column` said it was "only consulted when `--forward-schema-add-column` is also set" — that flag is DEPRECATED and now only logs a warning, so the sentence read as "this feature is dead" for a flag that is live under the default. The real gate is `--schema-changes != refuse`, and the default is `forward`, so backfill is reachable out of the box; two further silent no-op conditions the text omitted entirely are now named (`--inject-shard-column`, and multi-database mode, where ADR-0091 forwarding is single-database only). And `migrate --where`'s help pointed at `sync --where` for the continuous form; the command is `sync start --where`.

**`SLUICE-E-BACKUP-ENCRYPTION-MISMATCH`'s Meaning named `sync --backup-to`, a flag the binary has never accepted.** The chain-extending writer is `backup stream run`. That cell is mirrored byte-equal into the code's own doc-row registry and from there onto sluicesync.com, so the phantom flag was published in three places from one source; both homes are corrected together.

**The perf-parity matrix retracts a safety claim it had been making about a test that does not exist.** Row 17 asserted that the item-138 quiesce ceiling's safety argument "cites an environmental fact and that fact is CHECKED, not asserted" and named a test as the binding. **That test has never existed** — the only occurrence of its name in the tree is the comment recording its absence — and the argument is FALSE for four of the nine write cores, which a commit retracted in `migcore` and a later commit updated this file without picking up. It is retracted here in those words, with the four gates that DO exist named. The general lesson is worth stating because of where it landed: **an artifact whose job is to record what is checked is not exempt from the unverified-invariant rule, and is the worst place for it to fail.** The same pass gave items 137, 142 and 144 their cells, deleted row 11's now-closed "known limitation", added the first preflight/entry-cost row, filed the FK-check exemptions as gap 20, and re-derived roughly thirty drifted `file:line` citations from the code rather than offsetting them — several were wrong in DIFFERENT directions, so a uniform offset would have encoded the error.

**Two more false sentences about correct code, both found while ground-truthing these very notes.** The first was published: six places — including the two byte-equal homes that mirror onto sluicesync.com as `SLUICE-E-SCHEMA-TABLE-NAME-COLLISION`'s Meaning — claimed that after a table merge `verify` "compares that name against that name and agrees." It does not. `Verify` iterates SOURCE tables and compares each against the target, so with `orders`=2 and `Orders`=2 against a merged target of 4, both mismatch: **a later `verify --depth count` would CATCH the merge.** What is silent is the migration itself, which exits 0 with no failing statement and no warning — still worth a preflight, since an operator should not need a separate opt-in step to learn that two tables became one, but the stronger claim was never checked and was not true. The second was one release old: the partitioned-table refusal said the preflight "does not run" on the `sync` cold start, where it runs unconditionally and ahead of the `--schema-already-applied` branches. That message had been rewritten one commit earlier to remove a phantom flag, and replaced a wrong sentence with a different wrong one.

**"D1 targets" do not exist, and sluice has now published that claim in two separate releases.** `d1Engine` refuses all three writer doors, and — the part that makes it unambiguous — the `sqlite` engine's DSN parser has **no `d1://` case at all**, so such a DSN is read as a literal file path. The routing four exemption comments asserted ("a D1 TARGET goes through the `sqlite` engine") is not a mechanism that exists. Source-side D1 writes are real and unaffected: `d1-trigger` creates its change-log tables and triggers on D1 during CDC setup. **The reason this needed a gate rather than another correction is that the correction had already been made** — `CHANGELOG.md` carries it dated 2026-08-04, and v0.114.0 made the claim again one release later. `TestTargetEngineListMatchesTheCode` now holds a `<!-- target-engines: … -->` marker to the code through **two derivations that share no evidence** — an AST refusal-stub shape keyed on receiver type (required, since `sqlite` and `d1` live in one package with opposite answers) and actually calling both doors — and a mutation that reworded the error text while leaving the AST shape untouched made the two disagree, so the gate refused both rather than picking a winner. Its scope is stated where it is defined: it grades `OpenSchemaWriter` and `OpenRowWriter`, not `OpenChangeApplier`, so the neighbouring "CDC apply targets" claim is still bound to nothing and says so.

## Compatibility

**No flag was added, renamed or removed** — the generated flag manifest is byte-identical to v0.114.0's. **No on-disk format changed its version, no backup chain is repartitioned or crosses an epoch boundary, and no IR type gained a field that rides the chain schema fingerprint.** Upgrading from v0.114.0 is drop-in in that mechanical sense. Four error codes are new and several previously-succeeding runs will now refuse; that is the part that needs reading.

**A migration whose source carries two tables that fold to one target name now REFUSES at preflight instead of merging them.** On a SQLite target that is two names differing only in ASCII case; on a MySQL-family target it is the same pair on a server whose effective `@@global.lower_case_table_names` is non-zero. On the stock Linux MySQL default (`lower_case_table_names=0`) nothing is refused and behaviour is byte-identical to before. The refusal fires from `migrate`, both `sync` cold-start paths, `schema add-table` and both restore paths, and on MySQL again in the create-tables phase. The remedy is to rename one of the two source tables. **The fold sluice applies on SQLite is Go's `strings.ToLower`, which is Unicode-aware and therefore a strict SUPERSET of SQLite's ASCII-only fold** — so a pair differing only in NON-ASCII case is refused although SQLite would keep both. That residual runs in the loud direction and is documented at the call site; it is the same over-refusal v0.114.0's index check carries, tracked as item 150. **On MySQL the direction is not established and the code says so:** `é`/`É` was measured to fold on both `mysql:8` and `mariadb:11.4` under `lct=1`, matching Go, but the general non-ASCII case is marked UNVERIFIED PREMISE in those words, with both failure directions named — the under-refusal one being the silent one.

**A SQLite target whose source declares a view whose name collides with a table or another view now REFUSES**, where it previously created nothing and exited 0. Postgres, postgres-trigger and the MySQL flavors are unaffected — their view emit already fails loudly on that collision.

**A multi-namespace fan-out (`--all-databases` / `--include-schema` / `--map-database`, on `migrate` or `sync` cold start) aimed at a target engine with a flat namespace now REFUSES up front.** In practice that means a SQLite target: it is the only registered engine that is both a write target and unable to derive a per-namespace DSN or accept a schema override. A fan-out that resolves to exactly ONE source namespace is still allowed, and is byte-identical to before — with one residual stated rather than implied, which is that a `--map-database old:new` in that single-namespace case is COSMETIC on a flat target, since there is no target namespace for the new name to be. Nothing is lost; the rename is simply not honoured.

**A `migrate` or `sync` cold start into a target that already carries a foreign key on an in-scope table now REFUSES when that constraint's parent is also in scope, and WARNs when the parent is out of scope.** This is a new refusal on `migrate`, single-database `sync` cold start and the multi-database `sync` cold-start fan-out. `restore`, `chain restore`, `sync from-backup` and `schema add-table` are deliberately unchanged — the check cannot tell a foreign key the target was branched with from one an earlier run created, and on an idempotent entry point that ambiguity refuses a run for having worked. **`--skip-foreign-keys` does not clear this refusal** and is named in the remedy as part of a fix, never as the fix. SQLite targets are exempt because their copy path opens every writable connection with `foreign_keys(0)` and genuinely cannot fail this way; the post-copy `PRAGMA foreign_key_check` still reports a real violation there.

**A binary `--type-override` on `sync start` or `schema add-table` is now REFUSED where it previously ran.** `migrate` still honours it. **A `sync` cold start or `add-table` whose target already holds a binary column for a non-binary source column is also refused, with no override on the command line at all** — that is the `migrate --type-override` followed by plain `sync` sequence, and it is the one the previous remedy text recommended. Warm resume and the multi-database fan-out are reached by the config-keyed check only; if your stream's first cold start ran before this release, or the target column was made binary while the stream was stopped, neither check fires on resume unless an override is still on the command line.

**A MySQL-family-target `migrate --dry-run` now opens one target connection.** Previously a single-database dry run touched no target at all. Skipped for schemas with fewer than two tables. No other dry-run behaviour changes, and the plan output is otherwise unchanged.

**Log output changes on the cold-copy storage-grow gate: an `evidence=` field appears on the gate's CLOSED/reopened lines and on both engines' retry WARNs.** The set of conditions that trip the gate is UNCHANGED — this is descriptive only, and a test exists specifically to fail if the evidence value ever starts changing the hold.

**Open and NOT fixed here, named so they are not discovered as surprises.** A `json[]` or `bytea[]` column bound for a MySQL target still silently base64s its elements: the `[]any` array branch calls `json.Marshal` directly, and `encoding/json` renders a `[]byte` element as base64, so a PG `json[]` lands on a MySQL JSON column as an opaque string, at exit 0. It is pre-existing, it is item 145's unenumerated sibling — 145 swept the Postgres target and the pgtrigger door and did not look at the MySQL target — and no pin exists in any shape. **Two runtime messages still name `sluice schema migrate`, a command that does not exist** (`sluice schema` has exactly three subcommands: `preview`, `diff`, `add-table`), and one of them is the schema-forward refusal ADR-0157 pipes into webhook/Slack/email. The new gate does not catch them by its own documented rule — an unknown SUBCOMMAND is graded only inside a delimited span that also carries a flag — so the class is narrowed, not closed. The `bytea[]` × pgx-exec-mode matrix is pinned only on the 1-D, two-element, non-NULL cell; the 2-D, NULL-element and empty shapes are not, and Bug 74 originated in exactly that kind of driver-side difference. The hex-decode roster gate is narrower than its name in two ways, now stated at the gate rather than fixed. And the grow gate's trip SIGNAL remains an inference rather than reparent evidence — this release made the CLAIM honest, not the signal better.

## Who needs this — action required

- **Anyone who has migrated into SQLite where the source schema carries two tables whose names differ only in case — a PostgreSQL source with quoted identifiers is the ordinary way to have this. Open the target file's catalog and count its tables against the source's, and if one is missing, treat the surviving table as holding BOTH tables' rows.** The second table was never created and its rows were INSERTed into the first, at exit 0, with no error and no failed statement anywhere in the run. **A `sluice verify --depth count` run after the fact WOULD have caught it** — it compares each source table's count against the target's, so both colliding tables report a mismatch — which means a clean verify on that migration rules this out. `SELECT name FROM sqlite_master WHERE type='table'` against the source's table list is the direct check; a table present in the source and absent from that list is the loss, and the surviving sibling is where its rows went. There is no automatic repair — the rows of the two tables are interleaved in one table and only your own schema can tell them apart. **Affected from v0.99.146 through v0.114.0.** After upgrading, the run refuses up front instead, and the remedy is to rename one of the two source tables.
- **Anyone who has run a multi-database or multi-schema fan-out (`--all-databases`, `--include-schema`, `--map-database`) into a SQLite target. Assume every source namespace was written into one flat file under bare names, and that same-named tables across namespaces were MERGED.** Even without a name collision the result cannot be routed back to a source namespace, so a per-namespace verification is the only meaningful check and re-running one namespace per invocation into its own file is the remedy. **Affected from v0.99.146 through v0.114.0.** After upgrading the configuration is refused before any connection is opened.
- **Anyone who has migrated into a MySQL or MariaDB target whose server runs `lower_case_table_names != 0` — that is the DEFAULT on Windows and macOS servers, and a deliberate setting some Linux deployments use — where the source carries two tables whose names fold together. Re-check the target's table list against the source's, and treat the surviving table as holding both tables' rows.** The colliding CREATE returned Note 1050, a warning, and created nothing; the losing table's rows went into the winner. As on SQLite, **a `verify --depth count` run after the fact would have caught it** — both colliding source tables mismatch against the merged target — so a clean verify rules this out. `SELECT @@global.lower_case_table_names` on your target tells you in one query whether you were ever exposed — **a `0` means you were not, on any release.** **Affected from v0.3.0 through v0.114.0.** PlanetScale and Vitess targets are NOT affected: vtgate answers that variable with 0, measured on a real cluster.
- **Anyone running a `sync` or `schema add-table` with a `--type-override` onto a binary target type (`bytea`, `binary_uuid`, `varbinary`, `blob`) against a source column that is NOT binary — or whose target simply holds a binary column for a non-binary source column, however it got there. Re-verify the VALUES in that column, not the row count.** A value spelling `\x` followed by an even run of hex digits was stored SHORTER than the source holds — `\xdead` as 2 bytes instead of 6, a bare `\x` as ZERO — on every CDC apply, while the cold copy stored the bytes verbatim. **The same cell disagreed with itself with no error on either side and matching counts, so a count comparison will NOT catch it.** Compare `OCTET_LENGTH` (or PG's `octet_length`) on rows you know have been UPDATEd since the cold copy against the source's own length for the same rows. **Affected from v0.86.0 through v0.114.0.** A run with no `--type-override` onto a binary type, and no target column that is binary where its source column is not, was never affected.
- **Anyone whose `migrate` or `sync` cold start died on `Error 1452` (or PG's 23503) around twenty seconds in, against a target branched or restored from an existing database. Upgrade and re-run; there is nothing to re-verify.** That was a loud failure, not a loss — the copy stopped, it never claimed success. sluice now refuses before any row moves and names the child table, the constraint and the parent. Note that `--skip-foreign-keys` was never the fix and still is not: it strips constraints from the IR and issues no DDL, so a constraint already on the target survives it.
- **Anyone who acted on a recovery hint sluice printed, or on a schema-drift alert it sent to Slack, a webhook or email, and got `unknown flag` back. The command line was wrong, not your invocation.** Sixteen runtime messages named CLI surfaces the binary does not have. The two that matter most are read mid-incident: the correct recovery for a schema-race or a refused DDL is to re-run `sluice sync start` with the SAME `--stream-id` (a restart warm-resumes from the persisted position and skips the snapshot and bulk-copy phase — there has never been a `--resume` flag), and the flag that actually discards a position is `--restart-from-scratch`. **There is nothing to re-verify** — no data was affected — but if a partitioned-source refusal sent you to `migrate --schema-already-applied`, that flag exists on `sync start` only and `migrate` would have rejected it. Two messages still name `sluice schema migrate`, which is not a command; read that as "run your schema migration".
- **Anyone who read sluice's documentation to decide whether their engine could run a filtered continuous sync. If your source is MariaDB, it can, and every list we published omitted it.** The five `--source-driver` values whose change stream delivers the full before-images a `sync --where` needs are `mariadb`, `mysql`, `planetscale`, `postgres` and `vitess`; SQLite, D1 and the trigger-CDC engines refuse at preflight and can never have entered the mode. **Nothing to re-verify** — this was a doc defect, and the engine list is now derived from the compile-time capability pins through the live registry rather than from directory names.
- **Anyone blocked from migrating a table with a `json[]` or `jsonb[]` column into Postgres.** That migration could not complete before and can now. It was always loud, so there is nothing to re-verify — a run either refused or never started. Note the sibling that is still open: those same array types bound for a **MySQL** target silently base64 their elements, and that is tracked, not fixed here.
- **Everyone else: nothing to do.** A `migrate` or `sync` with no case-folding table-name pair, no fan-out into a flat target, no binary `--type-override` on a CDC lane, no `json[]` bound for Postgres, and no pre-existing foreign keys on the target is unaffected by every item on this list. The remaining changes here are loud failures made louder, one new preflight connection on a MySQL-target dry run, a log field, and documentation held to the code by gates instead of by memory.
