# sluice v0.114.0

**A batch our own reviews found, not our users — and the sharpest item is that sluice has been printing an operator-facing log line that was never true: the `sync` cold-start computed a copy-parallelism cap, ANNOUNCED it, and threw it away. Alongside it, a cold copy whose target socket died mid-`LOAD DATA` hung forever with no error, no exit code and zero rows, and every MySQL backup taken without `FLUSH TABLES WITH READ LOCK` — RDS is the shape — captured its binlog position on the LOSS side of its snapshot window. Upgrading from v0.113.0 is drop-in in the mechanical sense: no flag added, renamed or removed, no new error code, no on-disk format change, and no backup chain repartitioned. Four behaviour changes need reading before you upgrade; they are in Compatibility.**

v0.113.0 was the audit-and-field-report release. This one is the follow-through, and its provenance is worth stating plainly: almost everything here was found by re-deriving a claim we had already made, rather than by a user hitting it. Two items exist only because someone read a comment and checked whether it was still true. One exists because a gate we shipped a day earlier ran for the first time and found more than the item it was written for. That is the intended cost structure — it is much cheaper than the alternative — but it also means several of these defects had been live and unnoticed for a long time, and the entries below say how long rather than rounding it off. Two findings surfaced during this work are OPEN and are named at the end rather than quietly carried.

## Fixed

**The connection-budget preflight computed a copy-parallelism cap, logged it to the operator, and discarded the report — so the cap never bound anything, on any target, ever.** `sync`'s cold-start ran the preflight, passed the resolved write fan-out degree as `requested`, took the effective value back, emitted the INFO announcing it, and dropped the report on the floor; `runBulkCopyWithOpts` then took `resolveCopyFanoutDegree(opts.CopyFanoutDegree)` and nothing else. **The log line announced a cap that did not happen.** Two comments hid it jointly, and each was true when it was written. The first said "we run it for the refusal; the effective value is discarded" — correct while the preflight requested 1 lane, which is what it did until the ADR-0097 write fan-out started passing the fan-out degree instead. The second said the probe was "a no-op on engines without a connection-slot model (MySQL)" — correct until MySQL gained `ProbeTargetConnectionBudget` and the PlanetScale buffer-pool tier cap. Neither comment was wrong on the day it was written and neither was re-checked, which is the 2026-07-28 lesson in its narrowest form: the invariant a comment promised was a *log line*, and nothing anywhere compared the announcement to the behaviour.

**What shipped is a ceiling on a separate axis, and it is deliberately scoped to targets whose capacity sluice cannot establish.** `ir.ConnectionBudget` gains `CopyFanoutCeiling`, declared by the target engine and applied to the fan-out degree only — never folded into `CopyBudget`, because folding it in would re-open item 123 by putting a tight cap back on `migrate`'s whole table × within-table product. MySQL declares the ceiling on the PlanetScale flavor, and only when the buffer-pool reading is below the smallest tier sluice records, deriving that condition from `bufferPoolParallelismCap` itself so the two decisions cannot drift apart. A **known**-tier reading declares no ceiling at all, and that is a measurement result rather than a conservative default: on a production PS-10, degree 2 ran 89.0 s and 91.2 s against degree 4's 80.9 s and 87.0 s — **about 7% slower for no measured benefit**, so capping a production instance would have been a real throughput loss. On the unknown-tier branch the ceiling is free: 101.2 s and 103.2 s at degree 2 against 95.0 s and 115.8 s at degree 4, the same mean within noise with the run-to-run spread collapsing from ~21 s to ~2 s. A production PS-10 reading exactly 128 MiB is byte-identical to before and is pinned as its own case.

**Correcting a claim in v0.113.0's own notes: the dramatic 2.5× speedup we attributed to fewer lanes was the connection STORM, not the fan-out.** That release said "more lanes were strictly worse" and pointed operators at `--copy-fanout-degree 2` on a dev branch. The direction was right and the mechanism was not. Re-validated on fresh PlanetScale infrastructure on 2026-08-06 — a new PS-10 with a production `main` and an explicit dev branch, 1,704,288 rows / 787 MB across four tables, target row counts verified after every run — the drop storm **did not reproduce across nine runs**: zero drops and zero grow-gate windows on both branch classes at both degrees. The storm is a property of the branch's live routing and availability state, not something a workload can summon, so the original A/B/A remains the causal evidence for the storm and this validation establishes the fix's *choice* and the *cost* of that choice. **Fan-out is not intrinsically harmful.** "More lanes were strictly worse" holds while the target is shedding connections; it is not a general fact and it should not have been published as one. The tier-cap premise itself reproduced a third time (production 134217728 bytes, dev 33554432), and the fixed binary chose 2 on the dev branch — logging `requested=4 effective=2 target_fanout_ceiling=2` — while leaving production at 4 with no cap line at all.

**Affected releases.** The discard has been in the sync cold-start since **v0.99.65**, when the ADR-0097 write fan-out started passing the fan-out degree as the preflight's `requested` value; before that it requested 1 and the discard was genuinely inert, exactly as its comment said. The misleading INFO can appear from v0.99.65 on any target whose engine declares a connection budget (Postgres from v0.98.0), but the fan-out it claimed to bound only ever runs against a MySQL-family target — `ir.ParallelCopyWriter` has exactly one implementor — so the consequential window is **v0.99.121 (when MySQL gained the connection-budget prober and the PlanetScale tier cap) through v0.113.0**. Note for anyone reading the roadmap entry or the commit message: both say the MySQL prober landed in v0.100.0. That is wrong — `git tag --contains 9c042c10` gives **v0.99.121**, which is earlier, since the v0.99.x run went to v0.99.292. The sync cold-start's write fan-out has never been bound by the tier signal on any published release. Separately, **multi-database `sync` cold-start had no connection-budget preflight of any kind**, so it also gains the loud refusal it never had, placed ahead of the spanning `FLUSH TABLES WITH READ LOCK` so a target with no free slot refuses without briefly freezing the source.

**A cold copy whose target connection died mid-`LOAD DATA` hung forever: no error, no exit code, no log line, ~0.3s of CPU, zero rows.** The goroutine dump showed it parked in `net.(*conn).Write` under the driver's `handleInFileRequest`. Pre-existing rather than new — reproduced 3/3 on v0.113.0 and 1/1 on v0.112.0 — and not the keyless carve-out: a keyed table at `--bulk-parallelism=1` stalls identically. Two halves ship, and the second matters more than the first.

**Half one: a per-socket WRITE deadline on every database connection, 10 minutes, in the new `internal/netdeadline`.** It bounds how long ONE socket write may block on a peer that has stopped draining — never how long a statement may take. That distinction is what makes it safe: a legitimately slow but live target keeps its receive window opening, so every packet completes and the next one is re-armed fresh, and a four-hour `LOAD DATA` against a loaded server is untouched. **The value is deliberately NOT the 15 seconds the reproduction used.** ADR-0109's premise is that a PlanetScale storage auto-grow blocks the target's writes for seconds-to-minutes; during one, an in-flight write parks on a perfectly healthy connection, and a 15-second deadline would convert every storage grow into a copy abort — strictly worse than the hang it replaces. Ten minutes is roughly 10× the documented worst case, and it is deliberately the same number as `sourceReadSessionTimeoutSeconds` so the source-read and target-write halves of one stall are bounded on one clock, with a test that fails if the two ever drift apart. The premise the whole argument rests on is bound to a test rather than asserted: TCP keep-alive probes are only sent on an IDLE socket, and a connection with unacknowledged data in its send queue is governed by the retransmission timer instead — so keep-alive's ~60-second dead-peer bound is precisely blind to a blocked write, and a real-socket test requires the surfaced error to be a `net.Error` timeout.

**Half two, and the more important one: an idle-progress copy WATCHDOG that WARNs when a lane makes no forward progress for five minutes.** This was **the third silent hang in three regression cycles** — a cleared connection-slot transient deadlocking the copy, a grow gate quiescing 81% of the wall clock, and now a dead socket. Three different mechanisms, none caught by a gate, because **all three look like healthy slow progress from outside.** Progress is measured as rows handed to the writer (bytes on the raw byte-pipe lane) rather than chunks completed or checkpoints durably advanced, because those move at whole-chunk granularity and every one of the three incidents was a stall INSIDE a chunk. It WARNs and never aborts — a stalled copy and one merely slower than the threshold are indistinguishable from where the watchdog stands, which is the whole premise, so aborting would eventually kill a legitimate copy on a guess and the layers that CAN tell keep the loud-failure duty. It is silent during a deliberate ADR-0110 grow-gate quiesce, asking the gate directly through a new `ir.GrowGateQuiesceObserver` rather than inferring it, because a watchdog that cries wolf on every storage grow gets suppressed and a suppressed watchdog catches nothing. Its re-warn interval WIDENS — 5m, 15m, 35m, 75m, then hourly — for exactly the same reason: a line every five minutes overnight is the same suppression failure by another route. It rides inside the progress-ticker constructors, so all eight ticker lanes are covered by construction, plus the ADR-0078 raw byte-pipe lane, which has no ticker at all and would otherwise have been the hole.

**The residual is deliberate and is stated rather than implied: READS get no deadline.** A read deadline is a whole-query timeout in disguise — the client blocks in `Read` from the moment it sends a query until the first result packet, so any bound tight enough to catch a dead peer also kills a legitimate long `COUNT(*)`, `ALTER`, or index build. **The integration test found the consequence directly rather than us reasoning about it:** with a proxy-wide blackhole, the first flush failed on the write deadline in 5 seconds and the run then hung in the RETRY's fresh-connection handshake read. That observation is recorded in the test file's header instead of being discarded, the test's proxy was made per-connection so it measures the write hang it is about, and it is the sharpest argument for having built the watchdog and not only the deadline. Also stated at the watchdog's definition: it observes the COPY, so a stall in a phase with no row flow — index build, constraint add, schema apply, CDC apply — is outside it. **Affected releases: no connection sluice opens has ever carried a write deadline, so the class reaches back to v0.1.0 on every MySQL and Postgres path; the reported instance rides the MySQL `LOAD DATA` core, which has existed since v0.7.0. Through v0.113.0.**

**Every MySQL backup taken without a coordinated read lock captured its binlog position on the LOSS side of the snapshot window.** `openBackupSnapshotSerial` opened the consistent-snapshot transaction and *then* read the position, holding no lock — the one ordering where a commit inside that window is above the read view and below the recorded `EndPosition`, so it lands in **neither** the full nor any incremental chained off it. This is not an exotic path. It is the floor every coordinated-FTWRL failure falls back to, and AWS RDS blocks `FLUSH TABLES WITH READ LOCK` for the master user regardless of grants, so on RDS it is not a fallback — it is the path. The order is now flipped, so the full's sweep is a SUPERSET of everything at or below the recorded `EndPosition` and **the residual moves from loss to re-delivery.** A churn probe (`reportBackupCaptureWindow`) brackets the window with two binlog-tip reads and reports quiet / moved / UNKNOWN per run: equal tips PROVE the window was empty, a moved tip WARNs naming the exact range. The probe checks its own premise rather than assuming it — a position is only returned with binary logging on. And `captureBackupPositionInTx` is renamed `captureBackupPosition`, because the name *was* the argument: nothing it reads is transactional, so being inside the transaction never bound the anchor to the read view.

**This was deferred once, and the reason it was deferred is the reason it took a separate change.** The identical shape was fixed on the CDC snapshot's lock-free path in v0.113.0 and explicitly NOT flipped here at the same time, because the chain anchor is load-bearing for incremental lineage and replay-window invariants that change had not validated. Every anchor consumer was checked before the flip, not after, and the decisive fact is directional: **an earlier anchor only ever WIDENS the replay window, and widening replays where narrowing skips.** An incremental starts at its parent's `EndPosition`, so an earlier anchor replays more and never less; `assertDataWindowEndPositionInvariant` returns early on zero change chunks, so a full's anchor never reaches it; resume-anchor adoption, `BackupID` derivation and the ADR-0088 coordinated path are untouched; MySQL has no chain-ack retention slot to move; and chain restore replays change chunks through `ir.ChangeApplier.ApplyBatch`, which is idempotent per ADR-0010. **The residual, named: a table with neither a primary key nor a NOT NULL unique index has no key for the apply to collide on, so a replayed INSERT can duplicate a row** — the same at-least-once accounting the sibling fix left. The durable half is a fail-by-default AST roster over every function in the MySQL engine that both opens a consistent-snapshot transaction and captures a position, requiring capture-before-open unless exempt with a written reason; a per-site pin is exactly what let this survive the first fix, and both the roster and the general-log integration pin passed their first mutant because both graded the churn probe's tip read instead of the anchor, which is why each was fixed and re-verified. **Affected releases: v0.18.0, when the snapshot-anchored `EndPosition` shipped, through v0.113.0.** Before v0.99.43 the serial path was the ONLY backup snapshot path, so every MySQL backup carried the window; from v0.99.43 the coordinated FTWRL path exists and this is what a target without it falls back to.

**Connection ACQUISITION bypassed the transient-error classifier, so a dropped connection between batches killed a run on a path where the identical drop one line later would have been retried.** Reported from production: a cold copy absorbed 78 vtgate drops exactly as designed and then died on `mysql: batched insert into "audits": pin connection: Error 1105 (HY000): internal: vtgate connection error: read tcp …: read: connection reset by peer`. `pin connection` is the tell — the acquire wraps its failure there and returns it raw, while the whole retry apparatus is called *inside* the write, i.e. only once the connection is already in hand. Acquisition now rides the same policy as the flush: same classifier verdict, same 100 ms → 30 s ladder, same ~30-minute wall-clock bound, same grow-gate participation, read from the same package variables so the two loops cannot drift. It deliberately carries **no keyless carve-out** — an acquire writes nothing, so a re-acquire is idempotent by construction, and importing the flush's ambiguous-commit refusal would reject a keyless table's copy for a hazard it cannot have.

**The roster found eight sites where the report named five, and the eighth is the one worth reading.** The filing listed five `Conn()` call sites; the AST walk found eight. Both fan-out lanes acquire TWICE (the single-worker shortcut and the per-worker goroutine, in each of the plain and idempotent variants), the idempotent batched writer has its own — and, found by the pins rather than by reading, **`checkLocalInfile`'s `SELECT @@local_infile` probe runs BEFORE the pin on the `LOAD DATA` lane**, so a drop killed that lane one statement EARLIER than the reported symptom, invisible to any roster that looks only at connection-acquisition call sites. It now checks out through the same helper and probes on that session, which is also the more faithful read of a session variable. Postgres was swept too: the chunked COPY already acquires inside its retry closure, the monolithic COPY path has no retry apparatus and only runs without a grow gate, and `ImportRawCopy` DID carry the defect — its COPY error went through the transient reporter while the acquire one line above returned raw, so a drop a moment earlier told the sibling lanes nothing. That one now trips the gate without retrying, because it reads a one-shot stream. Out of scope and named rather than implied: schema-writer acquisition (DDL, index, foreign-key wall) is a different lane with its own retry and is not covered by the roster. **This got unplanned live corroboration during item 144's validation** — one production degree-4 run died at 84.8 s with `pin connection: invalid connection`, on real infrastructure, on the wider fan-out and on neither degree-2 run. **Affected releases: v0.99.92, when the cold-copy reparent retry shipped and created the asymmetry, through v0.113.0.** The specific vtgate framing became retriable at the flush in v0.111.1, which is when the asymmetry became visible in the field rather than when it began.

**A `--where` filter on an `inet` column froze a filtered sync at exit 0.** `ir.Inet` was an empty struct carrying no family discriminator, and MariaDB's `INET6` stores `'10.0.0.1'` as the IPv4-mapped `::ffff:10.0.0.1` and delivers it that way — while still matching the bare literal server-side. So `--where ip = '10.0.0.1'` matched during the cold copy (that leg is evaluated by the server, and it took the rows) and NEVER matched in the client-side CDC evaluator, which compared against the delivered `::ffff:10.0.0.1`. Every subsequent insert, update and delete to those rows was scored out of scope, permanently, with the stream reporting caught-up and exit 0. Ground-truthed on the server rather than reasoned: `HEX(ip)` on the stored row is `00000000000000000000FFFF0A000001`, and the server's own `WHERE ip = '10.0.0.1'` returns 2 of 2 rows. `ir.Inet` and `ir.Cidr` now carry an `InetFamily` — `Unspecified` refuses (the same posture a zero MAC width takes), `Any` for Postgres, which constrains nothing and DECLARES that rather than defaulting into it, and `IPv4`/`IPv6` for MariaDB's two native types, which the IR had collapsed onto one. The predicate compiler gained the second axis: the rendering answers "is a prefix length shown?", the family answers "was the address coerced into another family before it was rendered?", and the rendering alone could never have caught this, because MariaDB's `INET4` and `INET6` share one rendering and disagree only on the second question.

**The premise is version-dependent, and the integration run is what said so rather than a reading of the docs.** The silent widening is MariaDB **11.4-and-later** behaviour. On **MariaDB 10.11** an `INET6` column REJECTS a bare IPv4 literal on INSERT (errno 1292) and matches zero rows for one in a `WHERE`, so 10.11 has no silent divergence at all. sluice's answer is the same on both lines — on 11.4+ the refusal names the delivered spelling, on 10.11 it names the only spelling the column can hold — so the fix carries no version split, but the pin measures whichever shape the image in hand exhibits and carries a floor that fails if NO supported line still widens, rather than asserting one version's behaviour as universal. **Affected releases: v0.99.276, when `--where` on the CDC leg shipped, through v0.113.0** — and only where a MariaDB source (first-class since v0.99.270, which is when the native `inet6`/`inet4` mapping landed) carries a native `INET6` column named in the filter, on MariaDB 11.4 or later. A Postgres `inet` source was never affected: PG does not widen.

**Two SQLite tables' same-named indexes collided, and `IF NOT EXISTS` turned the collision into a SILENT no-op.** SQLite index names are SCHEMA-scoped, not table-scoped, and the emit used `CREATE INDEX IF NOT EXISTS` with a bare name and no collision check — so the second table simply did not get the index its source declared, exit 0. **When the loser is the UNIQUE one, the target accepts duplicate rows the source rejects.** This is the same class Postgres already refused; it landed on the engine that had no such check. `validateSQLiteIndexNamespace` now refuses the pair under the same `SLUICE-E-SCHEMA-INDEX-NAME-COLLISION` code, wired into the create-tables phase (pre-copy), the index phase (where the no-op would actually happen, and the one `--resume` reaches without the first) and the connection-free preflight, so restore and `sync` cold start reach it too. **The comparison folds case, which ground truth demanded and the filing did not anticipate:** `CREATE UNIQUE INDEX IF NOT EXISTS "IDX_V"` is the same silent no-op against an existing `idx_v`, because SQLite compares identifiers case-insensitively even inside double quotes. **Correcting this paragraph as first published, which said "folds ASCII case":** the check folds through Go's `strings.ToLower`, which is Unicode-aware, so it is a strict SUPERSET of SQLite's ASCII-only fold. The consequence is a narrow over-refusal — a pair differing only in NON-ASCII case, `idx_é` against `idx_É`, is refused although SQLite would keep both as distinct indexes. That is deliberate and documented at the call site: the residual runs in the loud direction (a rename prompt on a migration that would have worked) rather than the silent one this refusal exists to close. The bookkeeping is shared with Postgres in a new `namecollide` package; the wording stayed per-engine deliberately, since Postgres has to explain a name transform the operator never sees and SQLite has to explain schema-scoping plus case folding, and one message parameterised over both would say less than either. The durable half is a registry roster requiring every non-exempt target to refuse its OWN collision fixture through the preflight surface — a shared fixture would have passed on Postgres for a correct reason, since its `<table>_` prefix disambiguates exactly the pair that collides on SQLite. **Affected releases: v0.99.146, when SQLite shipped as a migrate target, through v0.113.0.** Cloudflare D1 targets carry it too, because a D1 target writes through the SQLite engine. **Correcting that last sentence as first published:** there is no D1 target, and nothing "writes through the SQLite engine" on a D1 DSN — `d1` is a migrate SOURCE only (`OpenSchemaWriter` and `OpenRowWriter` both return `ErrD1NotImplemented`), and the `sqlite` engine's DSN parser has no `d1://` case, so a `d1://` DSN handed to `--target-driver sqlite` is read as a literal file path. What is true is the workflow: a D1-bound migration is a **SQLite target** — a `.db` file you then load with `wrangler d1 import` — so a D1-bound `.db` produced on an affected release carries the defect and is reached by the fix, exactly as stated. The over-claim is the mechanism, not the impact. It is also the same over-claim the v0.110.1 notes already carry a correction for, repeated one release later, which is why the target-engine list is now derived from the registry and held to a marker in `docs/production-readiness.md`.

**A `bytea[]` column could not reach a Postgres target at all.** The array element dispatch had arms for boolean, integer, float, the string-leaf family, decimal and the temporal types, and none for `ir.Binary`/`ir.Varbinary`/`ir.Blob`, so a table carrying a `bytea[]` aborted the copy with `postgres: array of element type ir.Blob not supported`. Loud and never silent — nothing was corrupted — but a PG→PG migration of such a table simply could not complete, and the operator's only options were excluding the table or dropping the column. What made it survive is that the READ half works and had a full family × shape matrix behind it: **a family can be completely decodable and completely unwritable, and nothing in the repository compared the two rosters.** The leaf is `[]byte` rather than a pgx wrapper (there is no `pgtype.Bytea`), reaching the element codec by the same deref route the existing scalar arms take, and this is Bug-74 territory rather than a mechanical addition: **mutating the leaf to a hex string reproduces the silent flatten exactly** — 1-D rows still compared equal while `array_dims` went `[1:2][1:2]` → `[1:4]` on both 2-D rows. One named wart: a nil `[]byte` for a PRESENT element is normalised to an empty non-nil slice, because pgx encodes nil as SQL NULL and passing one through would silently turn a present empty `bytea` into a NULL. The gate is a fail-by-default divergence map derived from BOTH Postgres reader doors — the first draft derived it from one door and missed `timetz` entirely — and it found a family the filing did not predict, recorded below rather than guessed at. **Affected releases: v0.1.0, when the Postgres row writer shipped with no binary array arm, through v0.113.0.**

**The copy retry budget was keyed by chunk index alone, so two tables shared one chunk's budget.** The maps tracking attempts and accumulated wait were keyed by chunk index, justified by a comment reading "the gate is constructed per table, so the index is unique within a gate" — which the run-wide gate had falsified without touching it. Table A's chunk 3 and table B's chunk 3 drew on one budget, so the per-chunk bound could fire earlier than advertised. Bounded and **loud** — an early abort, never a stall — which is why it was documented in place rather than bundled into the release that found it. Both maps are now keyed by `(table, chunk)`, and **the uniqueness argument is a test rather than a comment**: one test burns one table's chunk 3 to its give-up and requires another table's chunk 3 to still hold the FULL retry budget, and a second pins the backoff exponent, since a shared key also let one table's waiting inflate another's delay. No behaviour change on a single-table run. **Affected releases: v0.112.0, v0.112.1 and v0.113.0** — the per-chunk key was introduced by v0.112.0's own fix, and the run-wide gate that makes it wrong has been in since v0.99.134.

**And a gate: both change-chunk write lanes are now held to their byte ceiling by a check, not by two enumerations that each missed the other.** A per-chunk byte ceiling was added to the change lane because it had been added to the data lane and stopped there — and that fix's own commit, plus the entry above it, both read as if the change lane were fully covered. Two fixes, two enumerations, two misses, and nothing in the tree compared the lanes. The new gate discovers lanes by CALL SITE rather than by a written list: every production construction of a chunk writer under the pipeline package is a lane, grouped by the receiver that owns the writer, and each must compare bytes written inside a roll condition. A marker read into a manifest field is a stamp, not a ceiling, and does not count. The byte half has no exemption; the count half has a fail-by-default map with a written reason per entry, and a stale entry fails the build. Four lanes, three of them change lanes, with anti-vacuity floors in both dimensions — a walker that stopped matching, or one that found only data lanes, would otherwise be green for exactly the defect it was built for. **The residual is recorded at the gate rather than left implied: this is a STRUCTURAL check, and only two of the four lanes have a BEHAVIOURAL pin behind it.** Nothing today writes a wide change and asserts the chunk rolled on bytes rather than on count. The gate closes the "one lane and not its sibling" class, not the "the threshold is wrong" class. No behaviour change ships with it — the ceiling itself landed on both lanes in v0.113.0.

## Compatibility

**No flag was added, renamed or removed. No new error code was minted. No on-disk format changed its version, and no backup chain is repartitioned or crosses an epoch boundary.** Upgrading from v0.113.0 is drop-in in the mechanical sense. The five behaviour changes below are the part that needs reading.

**Every MySQL and Postgres connection now carries a 10-minute per-socket-write deadline.** It bounds how long ONE write may block on a peer that has stopped draining, not how long a statement may take, so a slow-but-live target is unaffected — each packet that completes re-arms a fresh deadline, and a multi-hour `LOAD DATA` or index build is untouched. On MySQL it is operator-overridable and the override wins absolutely: `writeTimeout=` in the target DSN takes precedence, and `writeTimeout=8760h` is how you effectively disable it. `writeTimeout=0s` is indistinguishable from "absent" to the driver, so it takes the default rather than disabling the bound. **Postgres has no DSN spelling for it.** Reads deliberately get no deadline. SQLite and the trigger-CDC SQLite engines are exempt (a local file has no receive window), D1 is exempt (HTTP, already bounded whole-request), and the file-based sources are exempt. The MySQL binlog syncer is armed separately, since it does not read the driver config.

**The copy write fan-out is now held to a ceiling of 2 on a target whose plan tier sluice cannot read, which CHANGES effective parallelism on a PlanetScale dev branch.** A dev branch reports a small fixed buffer pool below every known tier, so this fires there; a production branch on the same plan reports its tier and declares no ceiling, so it is byte-identical to before. The ceiling only ever LOWERS the degree, never raises it, and it lowers an explicit `--copy-fanout-degree` too — the target's measured capacity is the authority and the operator's value is the request, which is how every other budget clamp in sluice behaves. The cold-start logs the transition, so an operator whose 4 became 2 is told, and by what. If some other target class ever reports sub-floor, the ceiling is conservative for it on no evidence; the cost of that error is a narrower copy, which is slower at worst and LOUD. **Separately, multi-database `sync` cold-start now runs a connection-budget preflight it never had**, once for the run and placed ahead of the spanning read lock — so a multi-database cold start against a target with no free slot for the fan-out (or one exceeding `--max-target-connections`) now REFUSES up front where it previously proceeded.

**MySQL connection acquisition now waits on the storage-grow gate before checking a connection out**, so a cold-copy lane no longer grabs a connection during a window its siblings are parked in, and an acquisition failure now trips the gate for those siblings instead of returning raw. A run that previously died on `pin connection` during a vtgate drop will now retry it on the flush's policy and budget.

**`ir.Inet` and `ir.Cidr` gain an address-family field that RIDES THE WIRE and is deliberately EXCLUDED from the chain schema fingerprint, so no existing backup chain is repartitioned.** This is the item-102/104 trap, and it is worth spelling out because it has bitten twice: adding a field to an IR type that participates in the fingerprint mints a new epoch, and a chain written before that epoch becomes unrestorable by every later binary while reporting as corruption. The family rides the type envelope — a manifest should record which MariaDB network type a column was, and the fail-by-default envelope gate requires it — but it is stripped for fingerprinting exactly as the MAC width and the enum type name are, because the Postgres reader sets a non-zero family on **every** inet/cidr column, so `omitempty` would not hold it back. The equality is pinned as `with-field == without-field` plus a byte-level absence check, never as a self-referential frozen golden. **The stated cost: neither the fingerprint nor `schema diff` can notice an `inet4` ⇄ `inet6` retype**, because the rendered type is deliberately the same for every family (the family changes no target DDL — Postgres `INET`, a MySQL-family target `VARCHAR(45)`), and a rendered-type diff that split them would flag drift on every MariaDB-source inet column with nothing to act on. That asymmetry with the MAC width is deliberate and pinned in both directions.

**Two `--where` behaviours on network columns change, both correcting a filter that could never match what it claimed to.** **Correcting this paragraph as first published, which said the IPv4 literal "now canonicalises UP … that is the fix":** it does not. Both spellings are now **REFUSED**, each with its own message, and the refusal is the fix. A bare IPv4 literal against a MariaDB `INET6` column is refused as *not the canonical spelling*, naming `::ffff:10.0.0.1` as the form to write — the coercion to the IPv4-mapped form is what happens internally, and it is precisely what makes the operator's spelling non-canonical, because a change stream delivers the mapped form while the literal says the bare one. An IPv6 literal (including an IPv4-mapped spelling) against a MariaDB `INET4` column is refused as *not a valid value* for the column, where it previously compiled into a filter matching nothing. The Fixed-section paragraph above is accurate; this one described a silent widening that the binary does not do. And a `--where` on an inet/cidr column whose source engine does not declare an address family is refused rather than compiled; the two engines that produce these types both declare one, so this fires only if a new producer appears without deciding.

**`sluice schema diff` and every SQLite/D1 target now refuse a colliding index namespace.** (See the correction above: there is no D1 target engine — read "SQLite targets", which is what a D1-bound migration writes.) `SLUICE-E-SCHEMA-INDEX-NAME-COLLISION` is not new, but it now fires on SQLite and D1 targets where it previously only fired on Postgres, including on a pair of index names differing only in case. A migration into SQLite that previously exited 0 while quietly dropping one of two same-named indexes will now refuse at schema-emit time, before any table is created or any row copied, naming both source indexes and the colliding effective name. **That is the loud half of a silent-loss defect, and it is intended.** Postgres's own namespace check moved into the preflight surface so the roster has one door to enumerate; it refuses nothing new there.

**One retry-budget change worth knowing about on multi-table runs.** The cold-copy retry budget is now keyed by `(table, chunk)` rather than by chunk index, so on a run copying several tables each chunk gets its own full budget where previously same-indexed chunks across tables shared one. A run that aborted early with the budget exhausted may now retry longer before giving up. Single-table runs are unchanged.

**Open and NOT fixed here, named so they are not discovered as surprises.** A `json[]` or `jsonb[]` column still cannot reach a Postgres target — the same shape as the `bytea[]` fix, LOUD rather than silent, surfaced by that fix's own gate on its first run and filed rather than bundled, because choosing the element leaf is a Bug-74-class decision that owes its own real-target dimension matrix. SQLite's `CREATE VIEW IF NOT EXISTS` against an existing table or view is a SILENT no-op, so a view whose name collides with a table is simply absent on the target at exit 0; note the asymmetry that hid it, which is that the index-versus-table case is LOUD, so an operator who has seen sluice refuse a name collision reasonably assumes the class is covered. It needs its own error code, since a view colliding with a table is not an index-namespace problem and the remedy differs. The grow gate's trip SIGNAL is still an inference rather than reparent evidence, filed in v0.113.0 and still open. And on the backup snapshot fix, the duplicate-replay residual on a table with neither a primary key nor a NOT NULL unique index stands.

## Who needs this — action required

- **Anyone taking MySQL or MariaDB backups from a source where `FLUSH TABLES WITH READ LOCK` is unavailable — RDS is the shape, and on RDS it is not a fallback but the only path. Treat any backup taken during write traffic on v0.113.0 or earlier as possibly missing a commit at its boundary, and re-verify or re-take it.** The full's `EndPosition` was recorded on the LOSS side of the snapshot window, so a commit inside that window was in neither the full nor any incremental chained off it — permanently, invisibly, with the backup reporting success and `backup verify` reporting clean at every depth, because the archive is internally consistent about a row it never captured. **The independent check is the source database, not the archive**: a `COUNT(*)` and a spot comparison of rows written around the backup's start time. After upgrading, every run logs which capture path it took and whether the window was quiet, so you no longer have to guess. **Affected from v0.18.0 through v0.113.0.** Before v0.99.43 this was the only backup snapshot path, so a pre-v0.99.43 MySQL backup carries the window regardless of whether the lock was available.
- **Anyone running a filtered `sync` (`--where`) against a MariaDB 11.4-or-later source where the filter names a native `INET6` column. Assume the filtered subset has been FROZEN since the cold copy, and re-verify those tables against the source.** The cold copy took the rows (the server evaluated that leg and matched), and the client-side CDC evaluator then dropped every subsequent insert, update and delete to them — forever, with `sync status` green and exit 0. This is stale target data, not missing rows, so a row count will NOT catch it: compare the actual column values on rows you know have changed since the copy. **Affected from v0.99.276 through v0.113.0.** MariaDB 10.11 is NOT affected — it rejects the bare IPv4 literal outright, so there is no silent divergence on that line. A Postgres `inet` source was never affected.
- **Anyone who has migrated into SQLite — including a `.db` bound for Cloudflare D1, which is how D1-bound data is written, since there is no D1 target engine — with a schema where two tables carry indexes of the same name, including names differing only in case. Re-check the target's indexes, and specifically re-check for duplicate rows if either index was UNIQUE.** The second index was silently never created, at exit 0. `PRAGMA index_list` per table against the source's index set is the direct check; if the missing one was UNIQUE, the target may already hold duplicate rows the source could not, and those must be resolved before the index can be added. **Affected from v0.99.146 through v0.113.0.** After upgrading, the run refuses up front instead, and the remedy is to rename one of the two source indexes.
- **Anyone whose cold copy has ever stopped with no error, no exit code and no log line. Upgrade and re-run it; there is nothing to re-verify.** This is a hang, not silent data loss — the copy never claims success, so no run has reported completion over a partial target, and the rows that landed before the hang are correct. After upgrading, a dead target socket fails loudly within the write deadline instead, and a copy that stops making forward progress for five minutes says so by name in the log even when the mechanism is one we have not seen yet.
- **Anyone whose `migrate` or `sync` cold copy against a PlanetScale or Vitess target died on `pin connection`. Upgrade and re-run; nothing to re-verify.** That was a loud failure, not a loss — a dropped connection during acquisition terminated the run where the identical drop a moment later would have been retried. It is now retried on the same policy and budget as the write itself.
- **Anyone copying into a PlanetScale dev branch. You no longer need `--copy-fanout-degree 2`, and the reason we recommended it was wrong.** v0.113.0's notes attributed a 2.5× speedup to fewer lanes; that speedup was the connection storm, which did not reproduce across nine runs on fresh infrastructure. sluice now picks the conservative degree itself when it cannot read the target's tier, and logs when it does. **Nothing to re-verify** — this is throughput and observability, not data.
- **Anyone who has read a copy-parallelism cap in sluice's INFO output on a `sync` cold-start and believed it. It was not true.** The cap was computed, printed, and discarded; the copy used the raw requested degree. **There is nothing to re-verify** — no data was affected and no run reported completion it had not reached — but if you sized a target, tuned `--copy-fanout-degree`, or filed a support question on the strength of that line on any release from v0.99.121 through v0.113.0, the number it gave you was not what ran.
- **Anyone with a table carrying a `bytea[]` column bound for a Postgres target.** That migration could not complete before and can now. It was always loud, so there is nothing to re-verify — a run either refused or never started. Note that `json[]` and `jsonb[]` still refuse, and that is tracked separately.
- **Everyone else: nothing to do.** A `migrate` or `sync` with no MariaDB inet filter, no SQLite target (there is no D1 target — see the correction above), no `bytea[]`, no lock-free MySQL backup snapshot, and no copy that ever hung is unaffected by every item on this list. The remaining changes here are a loud failure made louder, a fan-out bound on a target class sluice cannot size, and gates made harder to escape.
