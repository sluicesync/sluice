# sluice v0.154.0

**MINOR, not a patch — this release raises the backup format floor and lands six operator-confirmed behaviour decisions.** A `backup full` that finalizes with no usable end position is now stamped `FormatVersionPositionlessFull = 11`, and **every v0.153.x and older binary refuses that artifact outright** at the manifest version ceiling — that is the compatibility break, and it is deliberate: before it, an older binary read the empty position as a legacy full and extended the chain "from now", silently omitting every change between the full's read and the incremental's anchor. Alongside it: trigger-CDC full backups finally record the change log's anchor, so a `postgres-trigger` / `sqlite-trigger` / `d1-trigger` chain resumes where the full's sweep ended instead of from the current `MAX(id)` (roadmap item 163 — a HIGH silent-loss class the v0.153.1 regression cycle measured at 100 of 100 rows missing); `migrate --resume` now binds the source's identity and refuses a foreign one; a MySQL source rolled back behind a position it issued itself, and a MariaDB source with an empty `@@gtid_binlog_state`, now refuse terminally instead of auto re-copying over a target that is ahead of them; a promoted primary whose replication channels are all stopped is accepted as a CDC source; and a warm Postgres resume from a diverged systemid or timeline refuses instead of cold-starting an empty target from the abandoned timeline. The rest of the release is the 2026-09-15 Tier-3 audit's MEDIUM queue across CI gates, pgtrigger, the pipeline and MySQL. Read **Compatibility** before upgrading a fleet — several changes refuse where sluice used to proceed, and the pgtrigger capture bodies changed, so every existing install warns `STALE-CAPTURE-FUNCTION` until `trigger setup` is re-run.

## Fixed

**Trigger-CDC full backups record the change log's anchor, so a chain no longer skips the window between the full and its first incremental (roadmap item 163).** None of the three trigger-CDC engines recorded a usable `EndPosition` on a `backup full`: `sqlite-trigger` and `d1-trigger` returned readers with no position capturer, so the manifest stayed empty and the chain extenders anchored at the change log's CURRENT `MAX(id)` — every row written between the full's sweep and that anchor was in no link of the chain, at exit 0 behind a WARN (the v0.153.1 regression cycle measured 100 of 100 rows absent), while `postgres-trigger` delegated to the composed Postgres reader and recorded a pgoutput `{slot, lsn}` the trigger poller then refused, so no trigger chain could be built at all. Every trigger engine now implements the snapshot opener and takes its anchor at snapshot START: `openAnchoredSnapshot` (pgtrigger) reuses the settled anchor the sync cold start computes, inside the backup's own REPEATABLE READ view, so it is gap-free and overlap-free; `anchorChangeLog` (sqlite-trigger, and d1-trigger over the D1 backend) reads the change-log preflight, `MAX(id)` and watermark grade BEFORE the cold-start row reader opens, so the result is overlap rather than gap, and replay of the overlap is idempotent because setup requires a PRIMARY KEY and chain restore upserts. The token is the existing `{"last_id":N}` trigger codec under each engine's own tag — no new format. Both chain extenders also seat the chain in the source's change-log consumer registry as `backup-chain:<root backup id>`, at the resume position before streaming and at each committed link, so a peer sync's `--auto-prune-change-log` or a manual `trigger prune` can never cut past the chain's next resume point. Pinned end to end by `TestBackupChain_PGTrigger_PostFullRowsReachTheRestore` and `TestBackupChain_SQLiteTrigger_PostFullRowsReachTheRestore`, whose independent expected value is the SOURCE's own `COUNT(*)` read after the post-full writes rather than anything the chain reports, and gated by `TestEveryCDCEngineRecordsABackupPosition`, a registry walk requiring every CDC engine to implement the opener and declare the position-capturer pin, with an EMPTY exemption map. **Affected releases: I could not pin the earliest one confidently and am saying so rather than guessing** — the harm needs a trigger-CDC source whose full is extended by an incremental, which has been possible since well before `resumeStartFromParent` took its current shape in v0.138.0; what is certain is that it was present through v0.153.2, and that v0.153.1's `POSITIONLESS-FULL-ROOT` refusal explicitly exempted the trigger family, so that release named the gap without closing it. `postgres-trigger` operators were never silently affected (their chains failed loudly); the silent arm is `sqlite-trigger` and `d1-trigger`.

**A positionless full is stamped format 11, so an older binary refuses it instead of extending it from now.** `POSITIONLESS-FULL-ROOT` shipped in v0.153.1 as a READER-side refusal, and the artifact itself carried nothing an older reader would trip over: a v0.153.1-or-older binary reads an empty `EndPosition` as a v0.16.x legacy full and extends the chain from the current position after a WARN — measured on a real v0.148.0 build, which logs `chain will start from CDC's current position` and proceeds. The artifact now carries the refusal: `IsPositionlessFull` / `StampPositionlessFull` raise a FULL manifest that finalized with an empty end position to `FormatVersionPositionlessFull = 11`, with a `minimumReaderVersion` row of v0.154.0, and `raiseFinalVersion` keeps sidecar-mode finalize from restoring the pre-sweep version over the stamp. The producer enumeration is in the commit and covers every path that reaches finalize with an empty position — a PlanetScale Neki router, a MySQL/MariaDB source with `log_bin` OFF, an empty VStream VGTID, rotation-born segment fulls and resumed fulls are all stamped; CDC-less engines (`sqlite`, `mydumper`, `flatfile`) stay exempt because no change stream exists that any binary could extend them with. One NEW refusal came out of building it: the stamp is the only version raise applied after chunks are sealed, so for an encrypted run resumed from a pre-v0.104.0 attempt the raise would cross the chunk-AAD encoding boundary and leave every chunk undecryptable — that now refuses at finalize naming `POSITIONLESS-FULL-ROOT` and `--force-overwrite` rather than producing an unrestorable backup. Pinned cross-version by `TestBackup_CrossVersionPositionlessFull`, which writes a positionless full on a real binlog-OFF mysqld and requires the OLD binary to refuse with the version-ceiling TEXT (a door refusal is explicitly not accepted as ceiling evidence), plus a control proving an ordinary positioned full still extends on OLD. The pre-tag value-fidelity review then caught that the stamp exempted `ir.CDCTriggers` — the very family whose reader-side exemption this same release removed — so a trigger full whose snapshot open faulted could finalize unstamped, be refused by v0.154.0's own reader, and be silently mis-extended by an older one; `ir.CDCNone` is now the only exemption, pinned by `TestStampPositionlessFull_TheOnlyExemptionIsCDCNone`.

**`migrate --resume` records the source's identity and refuses a foreign source.** `migrate --resume` adopted recorded state by MIGRATION ID ALONE, so a resume pointed at a different source that shares the id read a copy it never performed as its own and exited 0 having copied nothing — at phase `complete` it logged "already complete; nothing to do" and stopped, and mid-phase it skipped every table the other run recorded complete. Both arms were measured on real servers two ways: an operator-supplied `--migration-id` reused across sources, and, with no typed id at all, two databases on ONE host colliding on the auto-derived id, which hashes the source and target HOSTS and deliberately not the database. The header row now records a SET-ONCE `source_identity` column — absent from every engine's on-conflict SET list, which is load-bearing, because were it updated a foreign resume would overwrite the very evidence that refuses it — and `--resume` refuses a disagreeing live source with `SLUICE-E-RESUME-SOURCE-MISMATCH` before anything moves. Identity is source engine plus database plus schema and deliberately NOT the host, so a DNS move, a failover or a replica of the same database still resumes; that exclusion is mutation-tested rather than asserted. Pinned by `TestMigrate_ResumeRefusesForeignSource` on real postgres:16 and mysql:8.0. The pre-tag value-fidelity review then found the door was VACUOUS for most engines: the orchestrator parsed the DSN itself and recognised only Postgres URI, libpq key/value and the `@tcp(`/`@unix(` forms, returning empty for everything else — and the auto-derived id hashes a redacted host that is empty for exactly the same shapes, so BOTH discriminators collapsed together. Two different SQLite files, two different D1 databases, and two MySQL DSNs spelled `root:pw@/db` each produced the same id AND the same identity, and any `@tcp(...)` DSN whose password contained a `?` did too. Fixed IR-first rather than by adding parsers: `ir.SourceIdentityDescriber` asks the ENGINE what a DSN names, the pipeline's DSN knowledge was DELETED, and 14 of 14 registered engines are graded by `TestEverySourceEngineDescribesItsIdentity` with an empty exemption map — each must render a different identity for a different dataset, the same identity for the same source reached another way, and must carry no host, port, account or credential. When the live identity names no dataset the door still compares but WARNs first under `RESUME-SOURCE-UNDISCRIMINATED`, so an absent refusal is never read as proof. Affected: the foreign-source adoption is as old as `migrate --resume` itself (the resolver dates to the v0.3.0 era) through v0.153.2; the specific `sync-` alias arm — `--migration-id sync-<x>` reading a sync cold start's finished copy — became possible when the sync recording id shipped in v0.148.0 and is refused outright now. The vacuous-door defect was introduced and fixed inside this release and **was never published**.

**Three lineage verdicts stop re-copying over a target that is ahead of the source.** A warm Postgres `sync start` whose persisted position's `(systemid, timeline)` pin disagrees with the live source — a PITR, a promotion, a DSN re-pointed at another instance — wrapped `ir.ErrPositionInvalid`, which is the sentinel that ROUTES the automatic re-copy; a populated target was saved by the populated-target gate, but an EMPTY target cold-started from the diverged instance at exit 0 with the abandoned timeline's changes simply absent. It now wraps `ir.ErrPositionForeignLineage` and stops under `FOREIGN-LINEAGE-REFUSED`, touching nothing, gated repo-wide by `TestForeignLineageVerdictsCarryTheSentinelInEveryEngine`, an AST walk over every engine that grades return statements whose own text claims a different lineage, server or instance. On MySQL, a source BEHIND a position issued under its OWN `@@server_uuid` — a same-server rollback, or an in-place restore that seeded `gtid_purged` from an older backup — now returns the foreign sentinel via `gtidLineageBehindItsOwnPosition` under `SLUICE-E-CDC-LINEAGE-MISMATCH`, because that source is behind a position it issued itself, so the target is AHEAD and re-copying would reduce the only copy still holding the difference. On MariaDB, an EMPTY `@@gtid_binlog_state` refuses the same way: MariaDB carries no instance identity, so a same-server `RESET MASTER` with intact data and a rebuilt node with stale data are indistinguishable from the server's own answers, and the message names both possibilities. EMPTY under a MySQL server's own uuid deliberately KEEPS the existing fall-through, because a plain `RESET MASTER` with data intact is exactly that shape; the residual — an in-place restore that seeded no `gtid_purged` reads identically and still re-copies — is stated at the function, in `docs/operator/cdc-streaming.md` and in ADR-0022's fourth amendment. Every consumer of the verdict is enumerated in the commit with a fixed-or-exempt verdict, including the multi-database warm resume, which is terminal but returns the verdict without the `FOREIGN-LINEAGE-REFUSED` framing and is FLAGGED rather than changed. Affected: the Postgres arm dates to the source-identity pin's introduction in v0.74.0 and ran through v0.153.2; the two MySQL-family arms are policy decisions, not regressions — they were the documented open questions v0.153.2 left, and are now decided.

**pgtrigger's DDL markers stop losing a moved captured table, and a failed captured-OID load refuses instead of degrading the scope check.** The `sql_drop` arm never wrote `captured_relid`, so `DROP TABLE other.t` on a captured table that had been moved with `SET SCHEMA` recorded a marker the reader decoded to relID 0 and discarded — the silent-DROP class, one schema over; it now records the dropped object's OID, gated by `TestDDLMarkerProducerRoster_EveryProducerRecordsCapturedRelID`, which derives every marker producer from `setup.go`'s AST and requires each to carry the column or an exemption with a reason (there are none). Because the foreign-schema escape is DDL-only, a moved captured table's ROW and TRUNCATE events were dropped behind one WARN that blamed an attacker and never mentioned `SET SCHEMA`; those rows now log `CAPTURE-RELATION-MOVED` naming the move and its remedy, distinguished from a genuine decoy under `CAPTURE-OUT-OF-SCOPE` by one catalog read per relation. The containment also evaporated whenever the captured-OID load failed, which merely warned and left the set nil — that now REFUSES the stream open, a stated trade-off: a transient catalog blip at open fails `sync start` loudly and re-runnably instead of silently degrading the scope check for the stream's life. Finally, `CREATE TABLE … PARTITION OF` and `… INHERITS` recorded NO marker while `ATTACH PARTITION` did, because the marker query walked downward from an object id that for a relation-ADDING statement is the new relation with an empty descendant set; it now also seeds the new relation's PARENTS, for table-creating command tags only, measured on PG 16 and 18 as exactly one marker per CREATE. Affected: v0.148.2 (which landed the escape on the other arm) through v0.153.2. Rows are still DROPPED rather than applied for an out-of-scope relation — the halt is the design; these WARNs fire only where the halt did not.

**MySQL: an excluded table can no longer halt a stream, and LOAD DATA classifies every rejection family.** The v0.148.x scope gating reached only the XA and session-time-zone refusals, so the table-map shape guard, the partial-row-image belt, the generated-PK belt and every decode refusal — including the `TINYINT(1)` range check, whose preflight is in-scope-only — still killed the stream over tables the sync had `--exclude-table`d, under a remedy that could not even name the flag. All three row dispatchers now ask the table scope ONCE, ahead of every per-row question, and an out-of-scope rows event is dropped whole; `TestStreamKillingRefusalsInDispatchAreScopeGated` grades every non-nil return of the three dispatchers (36 gated, exactly 1 exempt — the unknown-table_id floor, where the identity is unknown so the question is unaskable) and requires the gate to be a top-level early return so lexical order is dominance rather than a proxy for it. Separately, the LOAD DATA writer's skip-code set held only the two CHECK codes, so a FOREIGN KEY (1452) or PARTITION (1526) skip on a replayed segment reached the coercion policy and surfaced as a type-override remedy under strict mode or as "clamped values" at exit 0 under a relaxed `sql_mode`; the set is now DERIVED by `TestLoadDataLocal_RejectionFamilyCodesAreClassified`, which loads a violating row for four rejection families across mysql:8.0, mysql:8.4 and mariadb:11 in both strict and relaxed modes (24 cells) and fails if a landed-row shortfall carries a code the writer does not classify. Also: the flavor memo cached a silent-loss guard's verdict for the life of the process on the premise that the answer cannot change under a running process — true of a server, false of an ADDRESS a days-long sync keeps opening doors on — so it is now bounded by `flavorMemoTTL` and a 64-entry cap and is forgotten outright for a server whose verdict turns foreign. Affected: the LOAD DATA and memo defects date to v0.148.2 and v0.148.3 respectively; the scope-gating gap is a loud failure whose per-row refusals predate the v0.148.3 gating that covered only two of them.

**Postgres refuses an empty SET clause, and the diagnostic columns are always storable.** A Postgres target update with no settable after-image built a statement with an empty SET list; `RefuseEmptySetClause` now refuses it naming the row, instead of a silent no-op at exit 0. The `last_error` control column cut on a byte boundary and could carry invalid UTF-8 or a NUL, which PostgreSQL refuses with 22021 and MySQL refuses with 1366 — measured on both engines with the raw pre-fix values as controls — so the write that records WHY a run failed was itself failing; it now cuts on a rune boundary and is made storable first. The sibling sweep over byte truncations surfaced `ChangeLogConsumerID`, the TEXT PRIMARY KEY of the source's consumer registry, which the pre-tag review then corrected twice over: it was rune-cut but never made storable, so a pre-existing invalid byte survived, and the obvious fix — reusing the diagnostic helper — would have been WRONG, because that helper collapses distinct invalid bytes to one replacement rune, merging two peers onto one registry row and letting a prune cut above the slower one. A sibling `storableIdentity` returns an already-storable id verbatim (which keeps every registry row an older binary wrote addressable) and escapes an unstorable one injectively. The review had graded this as a silent-loss defect reaching the new backup-chain seat; that grading was wrong and the regrade is the finding — `chainConsumerID` composes `backup-chain:` plus an always-ASCII hex backup id, so the seat cannot reach the defect, and the harm is confined to the `sync` path where it fails CLOSED (the prune refuses). Pinned by `TestChangeLogConsumerID_CutsOnARuneBoundary` and, on a real server, by a pgtrigger cell proving postgres:16 genuinely refuses the raw form and accepts the escaped one as a working primary key.

**The multi-namespace fan-out and the stopped-cold-start resume now reach migrate's target preflights.** `sync start --include-schema` / `--all-schemas` ran its per-database copy without the target-side preflights migrate has, so a target whose tables force row-level security under a `NOBYPASSRLS` role created the schemas, opened the slot and died mid-copy on SQLSTATE 0A000 behind an unhelpful hint; it now refuses up front with the BYPASSRLS remedy, pinned on real PG by `TestStreamer_MultiSchema_PG_TargetRLSRefusedBeforeTheCopy` asserting zero target rows. Re-running a stopped cold start likewise adopted recorded progress without re-checking the target, so a target that gained RLS, safe migrations, sharding, a binary column or an orphan backend during the stop failed partway through the remaining DDL phases or in CDC; `resumeTargetPreflight` now runs the same set, with each entry WIRED or EXEMPT-with-a-reason in the commit. Both are held by rosters in `TestTargetPreflightRoster_StoppedColdStartResumeReachesMigrateSiblings` and its fan-out and cold-start siblings — and two DEFECTS IN THE GATE ITSELF were found by mutation and fixed on the way: the roster keyed by bare symbol, so deleting the TARGET-side RLS call left it green because the same symbol was still called for the SOURCE side, and a helper in a reached set counted as reached after its only call was deleted. A residual is stated and not closed: a source column added during the stop leaves the target column absent with no copy to trip over, which needs a schema compare rather than a preflight.

**CI and gate guards, where the audit found checks narrower than their names.** The private-refs scan claimed to grade the whole tracked tree and greped four directories with every grep ending in `|| true`, so a planted tracked-file hit passed at exit 0 and so did a run whose scan root had been renamed away; class 1 now derives its universe from `git ls-files` with a 1000-path floor and both classes refuse a scan that reached too little. `vet-tags.ps1` — what the pre-commit hook runs on the primary development machine — vetted everything straight with no scratch exclusion and no package-count floor, so a `go list` that silently matched nothing printed a green line; it now mirrors the shell version, held to parity in both directions so losing the property on the reference side is a regression rather than a licence. The nekiverify suite justified omitting `-race` with a suite fact that had stopped being true and now runs under it. A new `[unscheduled-pin]` prerelease-trigger category derives, from the run-filter coverage tables rather than a hand list, which build-tagged suites run in NO workflow without being asked, and names them plus their pins when a delta touches their packages; it ships with its own self-test, and a CI failure during this release exposed that the self-test graded the script under a condition CI never provides — Lint checks out shallow and tagless — so the base-tag resolution was restructured and the self-test now shims `git describe` to reproduce a tagless checkout. The changelog-heading gate gained a `--working-tree` form that fires pre-commit, BEFORE any tag exists, where the remedy is not a force-move. The audit-findings index gained a per-date floor requiring the newest dated backlog section to be indexed, after both existing floors were found high enough to pass while none of the newest pass's IDs were entered at all. And the MySQL flavor probe now reaches every pool-opening door in the package — the Bug 280 roster's delegation check was a literal no-op under a comment claiming it recorded delegation, leaving the two CDC doors invisible rather than exempt, with floors one below the true counts and a universe of one file; the widened roster grades 17 doors transitively and produced a sibling sweep in which six more doors gained the probe.

**The perf-parity matrix had been publishing a false claim since v0.152.0, and now has a structural gate.** Line 1 of `docs/dev/perf-parity-matrix.md` was not the title but a 3,976-byte blob concatenating fragments of three rows with the H1 stuck on the end, introduced by the v0.152.0 doc pass and byte-identical at v0.153.2 — which also means the v0.152.0 content never reached the rows it was meant for, leaving row 4 asserting that the raw copy lane "CANNOT retry" and was "the ONLY unretryable one-shot write lane left in the tree" while both legs had had bounded retry with terminal short-circuiting and a loud refusal on exhaustion since v0.152.0. Ground-truthed against the code rather than against the matrix's own gap entry, the fragments were moved into their rows and the row now reads resolved-first. Nothing caught it because the only existing gate grades whether cited FILES exist, and every file the blob named still existed — the rot was in the file's SHAPE. `TestPerfMatrixIsStructurallySound` now asserts that line 1 is exactly the H1, that every row carries the column count the HEADER declares (derived from the header, so widening the table cannot silently disarm it), and that every row number is unique, with a floor of 30 numbered rows so a parse that stops extracting fails loudly instead of passing vacuously. Its doc comment states the reach plainly: it grades STRUCTURE, never TRUTH — row 4's false assertion would pass this gate cleanly the moment the columns lined up. Repairing it surfaced four rows carrying seven columns against the eight-column header, a defect predating the blob and born in a single commit; the dropped column is the broker one in each, and each restored cell is an explicit reason the technique cannot reach the broker replay leg. Two of the four are derived and two are judged, and the commit says which are which.

## Changed

**Six operator-confirmed behaviour decisions, in the order their commits number them.** (1) `migrate --resume` binds the source's identity; (2) a positionless full is stamped format 11; (3) a promoted primary whose configured replication channels ALL have both threads stopped is accepted as a CDC source rather than refused; (4) trigger-CDC fulls record the change log's anchor rather than refusing — roadmap item 163, whose commit labels it by roadmap item rather than by decision number, which is the only reason it reads differently from its five siblings; (5) MariaDB's empty `@@gtid_binlog_state` refuses terminally; and (6) a MySQL source BEHIND its own position refuses terminally.

**Refusals where sluice used to proceed, beyond the lineage ones above.** `migrate --migration-id sync-…` is refused outright before anything moves, instead of reading a sync cold start's finished copy as its own and exiting 0 having copied nothing; the CLI's regex mirror of that prefix is retired in favour of importing `SyncMigrationIDPrefix`, so the two cannot drift. A `migrate --resume` whose recorded state predates this release resumes under a `RESUME-SOURCE-UNRECORDED` warning rather than refusing — refusing would strand every migration in flight at the moment an operator upgrades, and that population can only shrink — and it is deliberately never back-filled, because recording the resuming run's identity would be writing a guess as evidence. A cold start stopped under an older binary with several out-of-order type overrides refuses ONCE as `COLD-START-SHAPE-CHANGED` after upgrading, because the copy-shape hash now sorts each group; a run whose overrides were already sorted, which is every single-override run, still matches.

**Prose, docs and skills.** ADR-0022 gains a fourth amendment recording decisions 5 and 6; ADR-0170's 2026-09-02 amendment said anchor refusals wrap the invalid sentinel and take the cold-start route, both of which stopped being true at v0.148.2, and is corrected against the code rather than against the filing. ADR-0051's status, decision and verification sections are re-dated for the terminal Postgres verdict. One detector finding was CORRECTED rather than transcribed: Postgres does not implement the lineage-verifier interface, so its REACTIVE mid-stream door asks Postgres nothing, and the operator doc says the Postgres door is the resume open only instead of repeating the MySQL "it fires on both paths" claim. Roadmap item 164 is filed for the residual named below.

## Compatibility

**One deliberate format break, and it is the reason this is a minor.** A positionless full written by v0.154.0+ — which in practice means a PlanetScale Neki router, a MySQL/MariaDB source with `log_bin` OFF, or a trigger-CDC full whose snapshot open FAULTED — is stamped format 11 and is **refused by every v0.153.x and older binary** at the manifest version ceiling, for `backup incremental`, `backup stream`, `restore`, `verify` and `export-as-parquet` alike. v0.154.0+ restores and verifies it normally and refuses to CHAIN off it under `POSITIONLESS-FULL-ROOT`. Every other artifact this release writes — positioned fulls, all incrementals, and CDC-less fulls — keeps its version and reads exactly as before. Positionless fulls written by v0.153.x and older stay at their old version: still extendable "from now" by v0.153.0 and older, which is the gap this cannot reach retroactively, and already refused by v0.153.1+ at the reader door. An encrypted run resumed from a pre-v0.104.0 attempt now refuses at finalize rather than stamping itself into an unrestorable state.

**Trigger-CDC sources change shape in three ways.** A `backup full` on `postgres-trigger` / `sqlite-trigger` / `d1-trigger` now records an anchor, so chains built from this release forward cover the window that used to be skipped. A trigger full taken BEFORE this release, or one whose snapshot open refused, is refused as a chain root under `POSITIONLESS-FULL-ROOT` like every other positionless full — the exemption that used to let it through is gone, so an existing trigger chain must be re-rooted with a fresh `backup full` rather than extended. `--chain-slot` is refused on all three, because no replication slot exists or is needed. Trigger chains now hold a seat in the source's change-log consumer registry, so a peer's `--auto-prune-change-log` or a manual prune cuts at the minimum across consumers and cannot outrun the chain; the residual, filed as roadmap item 164 and stated in the code and in `docs/operator/cdc-streaming.md`, is the window between the full and its FIRST incremental, which is not registered because the chain identity does not exist until the snapshot does — in that window a peer can still prune above the full's anchor, after which `postgres-trigger` skips the range as aborted with an INFO line and the SQLite and D1 engines give no signal at all. A trigger snapshot carries no snapshot name and no extra readers, so the backup sweep stays serial on the one pinned reader.

**CDC resume behaviour, by engine, verified against the capability pins rather than inferred.** On MySQL, a source rolled back BEHIND a position under its own `@@server_uuid` now refuses terminally instead of re-copying; EMPTY under its own uuid still takes the automatic re-copy, deliberately. On MariaDB, a routine `RESET MASTER` now costs one deliberate `--restart-from-scratch`, because an empty binlog state refuses terminally and MariaDB carries no witness that could tell an intentional reset from a rebuilt node. On Postgres, a warm resume from a diverged systemid or timeline refuses terminally where it used to route into the automatic re-copy; a `backup incremental` from such a source now fails with the generic CDC-start error rather than the wrong "WAL pruned past it" diagnosis. The VStream lane is unchanged — BEHIND there is tablet lag through vtgate, not a same-server rollback, and proceeds by design. The multi-database warm resume is terminal for these verdicts but returns them without the `FOREIGN-LINEAGE-REFUSED` framing; that is pre-existing, flagged and not changed here.

**`migrate` and `sync` surfaces.** `migrate --resume` against a different source refuses with `SLUICE-E-RESUME-SOURCE-MISMATCH`; `--migration-id sync-…` is refused outright; state written by an older binary resumes under `RESUME-SOURCE-UNRECORDED`; and an engine whose identity names no dataset warns under `RESUME-SOURCE-UNDISCRIMINATED`. The identity excludes the host by design, so a DNS move, a failover or a replica of the same database still resumes, and a single MySQL source spelled two different accepted ways now renders ONE identity rather than two. `sync start --all-schemas` / `--include-schema` into an RLS-forced target refuses up front instead of dying mid-copy; that refusal is UNCODED, because the underlying preflight returns a wrapped error that carries no `SLUICE-E` row. A stopped cold start re-checks the target before resuming.

**The pgtrigger capture bodies changed, so every existing install warns until setup is re-run.** The capture functions' rendered bodies differ from what this binary renders, so the capture-body door raises `STALE-CAPTURE-FUNCTION` on every existing install at every CDC open, with `trigger setup` as the remedy. This is a WARN and not a refusal on purpose: the door runs at every CDC open, so refusing would convert a binary upgrade into an outage on every running sync. A body that disagrees with the digest recorded at setup — something replaced it AFTER setup — still refuses, unchanged. There is no control-table, resume-state or on-disk format change beyond the backup manifest version above; the migrate control table gains one nullable `source_identity` column, added idempotently to tables an older binary created, and a row written before the column reads back as no evidence rather than as a mismatch.

## Who needs this — action required

- **Anyone who has built a backup chain from a `sqlite-trigger` or `d1-trigger` source.** Every incremental extended off a full taken before this release anchored at the change log's current position when the incremental opened, not where the full's sweep ended, so every row written in that window is in NO link of the chain — a restore from that chain is missing them, at exit 0, and the upgrade does not repair the existing artifacts. Re-root: take a fresh `backup full` on v0.154.0 and build forward from it. Do not attempt to extend the old chain — this release refuses it as a chain root under `POSITIONLESS-FULL-ROOT`. If you need to know how much is missing, compare the restored row counts against the source's own `COUNT(*)` rather than against anything the chain reports. `postgres-trigger` chains were never silently affected; they failed loudly at the first incremental and could not be built at all.
- **Anyone whose fleet mixes v0.154.0 with older binaries against the same store.** A positionless full this release writes is REFUSED by every v0.153.x and older binary, including for `restore` and `verify` — that is intended, and it is the mechanism replacing a silent mis-extension. If you restore from older binaries as a matter of policy, upgrade the readers before the writers, or confirm your sources do not produce positionless fulls (they do on a Neki router, on a MySQL/MariaDB source with `log_bin` OFF, and on a trigger full whose snapshot open faults).
- **Anyone who has ever run `migrate --resume` with a reused `--migration-id`, or with no id at all against two databases on the same host.** Both shapes could adopt a DIFFERENT source's recorded copy and exit 0 having copied nothing — at phase `complete` it said "already complete; nothing to do". The upgrade refuses that going forward, but it cannot tell you which past runs were affected: re-verify row counts on any target whose `migrate` finished suspiciously fast, or whose migration id you know was reused across sources. A resume against state written before this release proceeds with a `RESUME-SOURCE-UNRECORDED` warning — that warning means there is no evidence either way, not that the source matched.
- **Anyone running continuous sync from MySQL, MariaDB or Postgres who relies on sluice's automatic recovery.** Three shapes that used to re-copy now refuse terminally and touch nothing: a MySQL source behind its own position, a MariaDB source with an empty binlog state, and a Postgres source whose systemid or timeline diverged. Nothing to re-verify — the change is in the safe direction — but a routine MariaDB `RESET MASTER`, and any MySQL rollback or in-place restore, now costs one deliberate `--restart-from-scratch`, so update any runbook that expected sluice to recover unattended. Conversely, if your CDC source is a promoted primary with leftover stopped replication channels, it is now ACCEPTED where it used to be refused; you will see an INFO under `REPLICA-CHANNELS-STOPPED` naming the channels and `RESET REPLICA ALL`.
- **Every pgtrigger operator.** Expect `STALE-CAPTURE-FUNCTION` on every existing install after upgrading. Run `trigger setup` to re-render the capture functions; until then the stream runs normally and the warning repeats at each CDC open. Operators who cleared a `SET SCHEMA` move-halt should also know that a moved captured table's rows are still dropped — now labelled `CAPTURE-RELATION-MOVED` with the move named — and that a captured table dropped from another schema is no longer missed.
- **Anyone syncing from MySQL with `--exclude-table`, or loading through LOAD DATA.** An excluded table could previously halt the whole stream at its first row through several refusal paths; it no longer can. On LOAD DATA, a foreign-key or partition rejection on a replayed segment previously surfaced as a type-override remedy or as "clamped values" at exit 0 — if you ran replays under a relaxed `sql_mode` on v0.148.2 through v0.153.2 and saw a row-count shortfall explained as clamping, re-check those tables against the source.
- **Everyone else.** Nothing to do. If you do not take backups from a Neki, binlog-off or trigger-CDC source, do not use `migrate --resume`, and are not on pgtrigger, this release is drop-in.

**Two things were deliberately NOT fixed, and are named here rather than left implied.** The Postgres key-value DSN parser on the CONNECTION path re-joins tokens it did not strip, so an exotic quoted DSN such as `password='s schema=x' dbname=real` has a token REMOVED from the string handed to the driver, corrupting the password — it fails LOUDLY at connect, it is pre-existing, and changing what reaches the driver between the release commit and the tag is exactly the shape the project's own rules warn about, so it is filed in `docs/dev/audit-backlog.md` for immediately after this release, with a pin per accepted DSN form. And the `d1verify` suite could not run under this release's zero-cloud posture: every test in it skips without live Cloudflare credentials, so the `d1-trigger` engine's new backup position capturer — built from the code `sqlite-trigger` uses and pinned against the local executor and the D1 mock — has live-D1 behaviour that is DERIVED rather than verified. It is scheduled for 2026-09-20 and recorded in the backlog rather than skipped silently.
