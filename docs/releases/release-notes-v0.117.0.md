# sluice v0.117.0

**CRITICAL fix — a PostgreSQL CDC source whose row identity includes a STORED generated column SILENTLY OVER-DELETED on the target. PostgreSQL accepts a `PRIMARY KEY` on a stored generated column and then never publishes that column, so sluice's before-image narrowed to a NON-UNIQUE prefix of the key and one source `DELETE` removed every target row sharing it — measured against the target's own `COUNT(*)`: three rows on each side, one source delete, source ends at 2 and target at 1, exit code 0. The stream is now refused loudly. Riding with it: the MySQL sibling of the same class, and the cold-copy grow gate that livelocked a real user's `sync` cold start — 81.1% of a 91-minute run spent quiesced, four chunks copied in its last hour, while every retry mechanism reported perfect health. This is a drop-in upgrade from v0.116.1 and from anything older: no flag added, renamed or removed, and no on-disk format — backup chunks, chain manifests, resume state, the schema wire — is touched. TWO new error codes and FOUR new refusals ride along; everything that previously ran and now stops is named in Compatibility.**

The framing worth stating up front, because it is what shaped this release. The project's goal is that every command works smoothly against any database and any dataset, and a real operator hit the opposite: `migrate` copied their whole database in 45 minutes, and `sync` failed five times out of five in cold-start bulk copy. Two items here come out of that gap. One of them — the generated-identity CRITICAL — genuinely has no `migrate` equivalent, because `migrate`'s bulk copy reads a generated column with an ordinary `SELECT` and never needs an identity carried on a wire; only CDC does. **The other one does NOT have that shape, and saying otherwise would be wrong:** the cold-copy grow gate is built by `migrate` and by `sync` cold start from the same constructor with the same timing envelope, and their measured difference in the field is explained mostly by the TARGET, not by the entry point (their successful `migrate` ran against a PS-160 production branch; every failing `sync` ran against a dev branch, which their own log confirms independently with `innodb_buffer_pool_size=33554432`, 32 MiB). The gate defect is real regardless, and the fix improves both entry points.

## Features

**The GHCR container image now carries build provenance, and the claim about what provenance covers is a roster rather than a sentence.** v0.110.1 added artifact attestations and the workflow described them as covering "everything a consumer downloads" — true of the thirteen files attached to the GitHub release, and false of the one artifact most likely to be running in production. `gh attestation verify sluice_0.116.1_Linux_x86_64.tar.gz --repo sluicesync/sluice` returned a green result naming all thirteen subjects; `gh attestation verify oci://ghcr.io/sluicesync/sluice:0.116.1 --repo sluicesync/sluice` returned `HTTP 404`. **A narrowed security claim is worse than an absent one**, because a reader who sees "everything" stops checking. The image is attested at **three** digests, not one: the multi-arch OCI index that `:<version>` and `:latest` resolve to — the digest a `docker pull` reaches and the one `gh attestation verify oci://` looks up — plus both per-architecture manifests, because `:<version>-amd64` and `:<version>-arm64` are published, pullable tags whose digests an attestation on the index does not cover. Digests come from GoReleaser's own `dist/artifacts.json`, which records what each push reported, rather than from re-inspecting the registry afterwards (that would attest whatever the tag points at *now*, a different question); a digest that cannot be resolved fails the job loudly rather than attesting nothing. What makes it durable is a roster rather than a promise: `TestEveryPublishedReleaseArtifactIsAttestedOrExempt` requires every top-level section of `.goreleaser.yaml` to be classified as producing a published artifact — with how it is attested, cited by a string that must really appear in `release.yml` — or producing none, with a reason, so adding `sboms:`, an `nfpms` format or a third `dockers:` entry fails the build until someone decides; `TestSecurityMDAttestationRosterMatchesTheCode` holds SECURITY.md's operator-facing markers to that same map, so the list a person reads before trusting a download cannot narrow independently of the list the workflow implements. **The full artifact roster, attested-or-not-with-a-reason, is in [SECURITY.md](https://github.com/sluicesync/sluice/blob/main/SECURITY.md)**: the homebrew formula and scoop manifest are commits in sibling repos referencing an archive that *is* attested; the winget manifest is never published by CI (`skip_upload`); GitHub's auto-generated source archives never pass through the build, so the workflow has nothing to hash and the commit SHA is their control. **v0.117.0 is the first release whose image is attested** — on any earlier tag the `oci://` verify returns `HTTP 404`, which means "no attestation was recorded", not "the image is wrong".

## Fixed

**CRITICAL — a PostgreSQL CDC source table whose replica identity includes a STORED generated column silently deleted MORE target rows than the source deleted, and exited 0.** PostgreSQL accepts `PRIMARY KEY (a, g)` with `g` declared `GENERATED ALWAYS AS (…) STORED`, and then does not publish `g`: before PostgreSQL 18 `pgoutput` has no way to carry a generated column at all, so `pg_publication_tables.attnames` omits the key column and the `RelationMessage` sluice receives does not mention it. `resolveIdentityKeyCols` reads the identity off the wire, so the identity SHRINKS — to `{a}`, a non-unique prefix — and the applier's `WHERE` becomes `a = $1`. **Reproduced end to end with both numbers read off the servers rather than off sluice's reporting: three rows on each side, one source `DELETE` takes the source to 2 and the target to 1**, with the emitted `ir.Delete.Before` being `{"a":1}` for a `PRIMARY KEY (a, g)`. **The decisive piece of evidence is that this is a publication filter and not a WAL gap:** `test_decoding` on the same WAL renders `DELETE: a[integer]:1 g[integer]:10`, so the value IS in the WAL and is dropped by pgoutput's column filter — which is precisely why no change to sluice's decoder could have recovered it, and why the fix is a refusal rather than carriage. **All four replica identities were graded on a real PostgreSQL 16.14 from the raw pgoutput stream, and `FULL` is NOT the rescue it usually is:** `DEFAULT` and `USING INDEX` are unsafe identically (a partly generated key gives the non-unique prefix above and over-deletes; a wholly generated one gives no key flag at all, so the narrowing falls back to the null-marker full row and the `DELETE` matches nothing while the position advances); `FULL` is unsafe and was already FAILING, because the old tuple carries every PUBLISHED column and still omits the generated one, so the narrowing refused — loudly, but naming nothing an operator could act on; `NOTHING` is unreachable, since PostgreSQL refuses the source's own write for that shape. **The refusal keys on the PUBLICATION and carries no version branch, deliberately.** PostgreSQL 18 added `publish_generated_columns`, and with it set the column IS on the wire flagged as a key (verified on 18.4) — but sluice never sets that option, so scoping the check by server version would wrongly un-refuse PG 18. Instead it fires on a generated identity column ABSENT from the `RelationMessage` just received, which is the wire's own account of what it will carry: it cannot over-refuse a publication that does carry the column, and it needs no knowledge of the server version. It sits in `resolveIdentityKeyCols`, so both `RelationMessage` arms inherit it and cold start, warm resume, `add-table` and mid-stream DDL are all covered by one placement. **Affected releases: v0.85.2 through v0.116.1** — the over-delete shape needs the key-column narrowing introduced by `dc6e6cc3` (Bug 92, "narrow UPDATE Before to key cols under REPLICA IDENTITY FULL"), first tagged v0.85.2. Before that the same table would have produced a full-old-tuple `WHERE` of null markers, which matches nothing — a silent no-op rather than an over-delete. **That pre-v0.85.2 characterisation is derived by reading the code at the introducing commit, not by running an old binary; treat it as such.**

**The MySQL sibling of the same class ships here too, and it is NOT a previously-released fix.** A `PRIMARY KEY` on a `STORED GENERATED` column silently loses `DELETE`s and `UPDATE`s on MySQL binlog CDC, and the mechanism is entirely sluice-side — which is why every `binlog_row_image` pin missed it: MySQL carries the generated column in the row image exactly as it carries any other key column, and **the cell fails under `FULL` too**, which is the tell that the loss is ours. `decodeBinlogRow` drops every generated column deliberately and correctly for the INSERT/SET side, because the target's own `GENERATED` clause recomputes the value; but the `DELETE` and `UPDATE` arms then narrow the before-image to the key columns, so the narrowing yields one entry with a nil value. **Two outcomes, and only one of them is the silent one** — on the faithful mirror every schema writer emits, the target column is generated too, `NonGeneratedRowKeys` strips it out of the `WHERE`, the clause renders EMPTY and `DELETE FROM t WHERE ` is a hard SQL error (loud, but naming nothing actionable); when the target column is a plain materialised column instead — a `--type-override`, or a target dialect that cannot express the expression — the `WHERE` renders `key IS NULL`, matches zero rows, ADR-0010 absorbs the miss for resume idempotency, and the position advances with nothing said. Refused loudly on both narrowing arms under the same code as the Postgres half, rather than carried: carriage would need three coordinated changes on the MySQL side and **the Postgres sibling cannot be carried at all**, so a refusal is the only contract that can be uniform across engines. **Affected releases: the DELETE arm from v0.78.3** (`78e65439`, the Bug 88 narrowing) **through v0.116.1; the UPDATE arm from v0.99.266** (`3f0fe1f6`, Bug 193) **through v0.116.1** — the decoder's generated-column drop that supplies the other half has been in place since v0.3.1 (`089120c9`).

**The engine-agnostic `--where` narrowing site had no guard at all, and now refuses a partial key.** `whereCDCFilter.narrowBefore` re-narrows a deliberately un-narrowed before-image at the one site that is not inside an engine — a filtered table is streamed un-narrowed so the predicate can read every OLD column, which means each reader's own guard is bypassed for exactly those tables. It now refuses when the narrowed key is a PROPER SUBSET of the primary key. **Keying on the EVIDENCE (a key column absent from the image) rather than on the shape (a generated column in the key) is what keeps the Vitess VStream readers, which DO transmit the value, from being over-refused** — and it catches any other producer of a partial key for free. **The sibling enumeration is in the code rather than promised:** `mysql` reaches this site (its binlog reader is refused by its own new guard, and both VStream readers reach `narrowBefore` and PASS, which is the over-refusal control); `postgres` reaches it, with the reader refusing first, so this is the floor behind it and the only guard on a warm resume attached to a stream an older build started; `pgtrigger` is EXEMPT because it refuses any table with a stored generated column before a trigger is installed; `sqlite-trigger` and `d1-trigger` are EXEMPT because SQLite rejects the DDL outright — now ground-truthed by a premise test over `STORED`/`VIRTUAL` × sole/composite rather than asserted. The roster is enforced by a fail-by-default AST gate over every `StreamChanges` declaration under `internal/engines/**`, each package refusing-by-code or exempt-with-a-reason, with an anti-vacuity floor; a stale exemption fails it too. **Its known limit is stated where it is defined: the roster is PACKAGE-keyed, so one refusal satisfies MySQL's three readers.**

**A cold copy against a target that drops connections chronically LIVELOCKED, while every retry mechanism reported perfect health.** The report is a real 2.64 GB / 16 M-row / 197-table MariaDB → PlanetScale move: `migrate` copied everything in 45 minutes with no errors, and `sync` failed five times out of five, always in cold-start bulk copy, always on the same wide-row table (1.7 M rows, ~890 MB, ~520-byte rows). Run 3 was killed after 91 minutes having **absorbed 2,687 vtgate drops with zero unhandled**, tolerated 9 duplicate-key collisions, reached retry attempt 36, and **copied four chunks in its last sixty minutes**. Every individual mechanism behaved exactly as designed; the GATE is what stalled the copy. **Measured from the field log rather than reasoned about: the gate was CLOSED 81.1% of the run — 4,369 s of 5,385 s across 246 windows — and 92–97% of every ten-minute bucket after the first hour.** The correlation is the whole diagnosis: the one bucket that ran at 42% duty completed 62 tables; the buckets at 92–97% completed three, and 165 of the run's 170 table completions happened before the storm's duty cycle saturated. All 2,687 drops classify `no-grow-evidence` — they are `vtgate connection error: {no endpoints, unexpected EOF}`, which is in the transport half of the evidence partition by construction — so the discriminator that already existed was correct, computed, and ignored. **The fix is `GrowGateEvidenceFreeHoldCap` (250 ms), which bounds a single window's hold during an episode in which no trip has yet carried positive storage-grow evidence.** An evidenced episode keeps the full 30-second ladder; the flag accumulates per episode, so one evidenced trip restores the deep ladder for the rest of it, which is the conservative direction. **What it deliberately does NOT do is the part of the earlier refusal that still stands: the TRIP SET is unchanged — every classified transient still trips and still quiesces — and the early rungs stay evidence-independent, so the first hold, which is what ADR-0110's coordinated grow shield actually rides on, is bit-identical for every evidence value** (production rungs are 100 ms and 200 ms, both under the cap). Only the deep escalation on an episode that has produced no evidence across many armed-held-reopened-refuted windows is clipped — at which point "this is a bounded serving transition that needs quiet" is not an unfalsified hypothesis but one refuted by the gate's own measurements, because a grow window resolves and that is what makes it a window. **Why the discriminator has to be the evidence:** the tempting evidence-free fix, de-escalating on a prompt re-trip since that hold demonstrably bought nothing, is wrong in the dangerous direction, because a real multi-minute grow produces immediate re-trips too and de-escalating on them would hammer the target during exactly the window the shield exists for. **The 250 ms is anchored rather than picked** — both engines' cold-copy reparent ladders start at 100 ms and double, so 250 ms covers the tripping lane's own first two rungs, which is precisely the overlap that "alignment" names; a first cut at 1 s was caught by the throughput gate at 49.7%, i.e. exactly what the run-level share ceiling already gave.

**Two corrections to how that finding was described, because both were published verbally before they were checked.** First, **the user's `migrate`-versus-`sync` comparison is CONFOUNDED and is not the diagnosis.** Their log shows `innodb_buffer_pool_size=33554432` — 32 MiB, the PlanetScale dev-branch signature — while the successful `migrate` ran against a PS-160 production branch, and a dev branch is by far the likelier source of a chronic drop storm. Structurally both entry points construct the same gate with the same envelope; the only difference is `migrate`'s nil recovery probe, which affects early release and not hold length. So the honest answer to "why does `migrate` survive" is **the target, not the code path** — and the defect is real independently, because the gate is what converts a degraded-but-progressing copy into a stalled one on *any* target dropping at that rate. Second, **the run-level quiesce ceiling did not fail; it did not exist.** The reporter ran v0.111.1, which predates the ceiling (shipped v0.113.0) and the evidence discriminator it uses (v0.115.0). On current `main` that ceiling already bounds this at 50%, and 81% is literally the population the ceiling was filed from. **This release goes further because a FRACTION is the wrong unit:** half the wall clock spent in 30-SECOND units quantises a lane to one chunk per hold — a lane that finishes a chunk one millisecond after the gate closes waits a full cap-length hold before it may start the next — so throughput collapses independently of the average. **On the projected numbers: worst-case duty is `H/(H+I)` against the field's ~2 s drop interval, which takes the measured 81.1% to about 11% at a 250 ms cap, versus the ~50% the ceiling alone still permits. That ~11% is ARITHMETIC from the hold and the drop interval, not a measurement, and the in-repo measurement that does exist is a SCALED MODEL and not a real PlanetScale run** — a gate that scores chunks landed against the same lanes, against the same target, with no gate at all, in the same run, requiring at least 50% of ungated throughput where the pre-fix code scored 9.1%, with an anti-vacuity half requiring an *evidenced* storm to still be quiesced to ≤25% so the cap cannot leak onto the evidenced path.

**A PostgreSQL array or `jsonb` PRIMARY KEY PANICKED the concurrent apply path, on a supported configuration.** `laneapply.valuesEqualForKey` compared two `any` values with Go's `==`, which panics at runtime whenever the interface's dynamic type is uncomparable. **Reachability was verified against a real PostgreSQL 16 rather than argued:** PostgreSQL permits a `PRIMARY KEY` on an array column (btree `array_ops`) and on `jsonb` (`jsonb_ops`); the native reader's `decodeArray` returns `[]any`, and pgtrigger's `to_jsonb` payload decodes to `[]any` / `map[string]any` — and pgtrigger's setup explicitly ACCEPTS `text[]` columns, only `json[]`/`jsonb[]` being refused. PostgreSQL's `Update` always carries a Before image, so **every** `UPDATE` on such a table reached the comparison, and because interface comparison panics on an uncomparable dynamic type unconditionally, even an identity-copied Before image panicked. The existing `[]byte` special case shows the author stopped one type short of the general problem — `[]byte` is itself uncomparable, so that special case was load-bearing for exactly one of the four kinds that reach a key. **Fixed with `reflect.DeepEqual`. Comparing the router's own canonical key BYTES was considered and REJECTED on evidence:** that encoder's `%v` fallback collides `[]any{"a b"}` with `[]any{"a","b"}`, which is harmless for lane routing (colliding keys hash to the same lane, so nothing commits out of order) but is **silent row loss** in MySQL's coalescing apply path, where the same predicate decides whether upserting the after-image would ORPHAN the old-primary-key row. The binding property — equality here must IMPLY same lane, because both callers use a false result to skip the barrier — is now a gate over both packages rather than a comment. **The sibling sweep found exactly ONE `any == any` site in the tree and this was it**, swept by four independent passes; the two nearest neighbours (smart compaction's PK-change barrier and the lane router itself) are exempt because both stringify before comparing, which is precisely why this site was unique. **Affected releases: v0.99.82 through v0.116.1 via the two concurrent appliers** (`0ab40d63`, ADR-0105 step 2), **and v0.99.157 through v0.116.1 via MySQL's coalescing apply path** (`c2869362`, ADR-0140). **This is on the DEFAULT path, not an opt-in one:** `--apply-concurrency` defaults to `0` = auto:N (a conservative 4), so the concurrent lane router is live unless you set `--apply-concurrency 1`. The pinned family matrix additionally covers `[]string` — a MySQL `SET` is indexable and therefore can sit in a key — but that cell was **not** reproduced end to end and is not claimed as reachable.

**A PostgreSQL column typed through a `CREATE DOMAIN` whose base type lands on a MySQL `JSON` column could not be migrated OR restored into MySQL at all (Bug 233).** The copy died with the server's own `Error 3144 (22032): Cannot create a JSON value from a string with CHARACTER SET 'binary'` and the table landed **zero rows**. It reached every array element family through a domain — `json[]`, `bytea[]`, and even `text[]`, which works perfectly bare — plus scalar `json`. Root cause, confirmed on real containers before any fix: `columnSetExpr` decides which columns need a `CONVERT(… USING utf8mb4)` re-tag by dispatching on the column's declared type, an `ir.Domain` matched no arm, and a JSON column took the bare fall-through under `CHARACTER SET binary`. **The defect was LOAD-DATA-ONLY** — the batched-INSERT core binds what `prepareValue` returns, and that has unwrapped domains since Bug 122 — which is why the first investigation reported the bug as absent: the test container defaults to `local_infile=OFF`. Every assertion in the new integration test now pins which core actually ran, off the server's own `Com_load` counter. **This is the THIRD AXIS of one class.** Element family and arrival shape were each closed earlier with matrices over VALUES, and neither could see this one, because the defect is in which BRANCH runs and not in what the branch computes. So the fix is a single named unwrap (`ir.UnwrapDomain` / `ir.DomainOf` — a DOMAIN is a constraint wrapper, not a storage one, and only its name and CHECKs belong to the wrapper) plus a check that reads BRANCHES: `internal/domaingate`, a shared AST walker instantiated once per target engine, under which every type dispatch must unwrap or carry a written reason, fail-by-default, with stale exemptions a finding and an anti-vacuity floor. **The sibling roster is the gate's exemption maps, in the code:** eleven sites fixed, including the `LOAD DATA` geometry fallback probe, the TSV `ir.Bit` branch (whose other half was mutation-proven to store 1 instead of 170 if only one half unwraps), the `DEFAULT`-forbidden check, the geometry SRID clause, the `AUTO_INCREMENT` supporting-index emit, sequence priming, and the array-likeness and native-binary predicates; twelve sites exempt with stated reasons, two of them unreachable because SQLite refuses an `ir.Domain` column loudly at emit, which is now DRIVEN rather than asserted. The gate for `internal/translate` then found two more live instances of the same class one release later — the wide-`varchar` and unconstrained-`numeric` advisories never fired for a domain-wrapped column while MySQL's emitter down-mapped it anyway, so the operator got the rewrite with no notice — plus seven dispatch sites hiding in package-level `var` registries that the walker could not see at all, because it visited only function bodies. **Affected releases: reproduced on v0.115.0, v0.116.0 and v0.116.1. The dispatch defect is older than that** — `ir.Domain` has existed since v0.95.1 (`25a1c252`) and PG→MySQL domain columns became migratable rather than loudly refused during the v0.96.x line — **but the earliest affected tag was NOT bisected, so treat the window before v0.115.0 as unpinned rather than as ruled in or out.**

**Re-running `migrate` PG→MySQL over an existing target FALSE-REFUSED on every plain `json` column, every `bit varying(N)` column, and every column declared through a `CREATE DOMAIN` (item 153).** `translate.retargetPGtoMySQL` had no `ir.JSON` arm and no domain handling, so the pre-create shape gate — and `sluice schema diff`, which shares the comparison — put an UN-retargeted expected side against MySQL's catalog read-back, and refused. Loud, no data loss, but it breaks the `--resume`-shaped workflow an operator reaches for precisely when something already went wrong. Two rule-table arms close the bare families (`json` → the binary JSON MySQL reads back, `bit varying` → the fixed `BIT` MySQL lands), both inert on the emit lanes because MySQL's emitter reads neither field; the `bit varying` family was found by ground-truthing the matrix on a real server and was not in the original report. **The DOMAIN half is a second ENTRY POINT rather than a rule arm, and the reason is a silent-loss trap that must not be missed by anyone re-reading this later.** Flattening the domain inside `RetargetForEngine` — the way the item was originally filed — was REJECTED on evidence: that function's other consumers (`restore`, `chain restore`, the broker's schema-delta replay, schema-forward) hand their output to a `SchemaWriter`, and MySQL's emitter translates a domain's translatable CHECKs into inline table-level CHECKs by reading the column's declared type. **Flattening there would have traded this item's LOUD false-refusal for a SILENT constraint drop on the restore lane.** So `RetargetForShapeCompare` is a separate entry point used only for comparison, `schema diff` builds two schemas (flattened for the comparison, wrapper-carrying for its `CREATE TABLE` suggestions), and the claim is a gate rather than prose — a test asserts the wrapper-keeping pass emits the CHECK *and* that the flattening pass does not. **A premise pin was re-derived rather than deleted:** the old "no retarget rule produces a binary type", load-bearing for MySQL's native-binary predicate, is made FALSE by a domain over a blob, so it is replaced by a pin on what that consumer actually needs — the retarget never MANUFACTURES binariness, so a binary output must come from an input whose own unwrapped storage type is already binary — and its doc states plainly what it no longer guarantees. **Affected releases: the `migrate` re-run refusal from v0.99.258** (`15b280e1`, the pre-create shape gate) **through v0.116.1; the `schema diff` phantom-drift half is much older, from v0.8.0** (`eeb15c46`, where diff first ran a cross-engine retarget) **through v0.116.1.**

**A `backup incremental` window whose last position-bearing event was a schema snapshot was REFUSED, loudly, with the writer blaming the reader for a bug it did not have.** The capture loop opens a chunk writer on the first change of any kind, and a schema snapshot is diverted out of the JSONL stream onto the manifest envelope without bumping the record count — so such a window committed a chunk carrying ZERO records, and the data-window invariant read that chunk ENTRY as "data-bearing" and refused, printing "a data-bearing incremental window (1 change chunks)". It reproduces with real rows in the window via the ordinary `rows → TxCommit → snapshot` shape. **Fixed at the writer so the property is true BY CONSTRUCTION** rather than being an observation about what today's readers happen to emit: only a change the chunk stream actually RECORDS may move a window's `EndPosition`, and "data-bearing" is now a RECORD count rather than a chunk-entry count. The cost of that choice is stated where it is made — a window whose last event is a schema snapshot does not advance the chain past it, so the next link re-reads from the previous position and re-emits the snapshot, which is idempotent and is the same trade the empty-rollover path already makes. **The premise this rested on was UNVERIFIED and wearing a citation:** it named two tests as ground truth, and those tests assert a different invariant. **Affected releases: v0.99.226 through v0.116.1** (`89f40152`, which introduced the invariant as a reader-invariant writer backstop).

**`backup stream`'s rollover lane never drained schema-history snapshots at all, so every mid-stream DDL on a continuous chain lost its position-anchored schema version — on the lane that writes most change chunks.** Found by the sibling sweep of the entry above: the change-chunk writer's snapshot accessor had exactly ONE production caller, in the incremental lane. Both lanes now share one drain. **What this cost, stated precisely and not inflated: the manifest still recorded the schema delta, so a restore targeted the right shape, and the only path that paid was a restore-THEN-RESUME across that boundary, which landed on the cold-start floor instead of a primed history. No rows were lost.** **Affected releases: v0.70.0 through v0.116.1** (`88f01776`, which introduced the schema-history drain on the incremental lane only).

**A `sqlite-trigger` or `d1-trigger` change log could hand a future change an id at or below the stream's resume watermark, making that change permanently invisible to the `id > watermark` poll — captured, never replayed, position still advancing.** The engine's whole gap-freedom argument rests on two sentences, and only the first is a property of SQLite. Writers are serialised, so the change-log id is allocated in commit order — now ground-truthed under four contending writers, 160 of 160 emitted exactly once with strictly increasing ids. The second sentence, "the id is AUTOINCREMENT and therefore never reused", **is not a property of SQLite at all — it is a property of two pieces of ordinary, writable state, and both are constructible.** `sluice trigger setup` emits `CREATE TABLE IF NOT EXISTS`, so a table already named `sluice_change_log` is accepted as-is; if its id column is a plain `INTEGER PRIMARY KEY`, SQLite reuses rowids and the first capture after the auto-prune drains the log is allocated id 1. And `sqlite_sequence` is an ordinary writable table: with AUTOINCREMENT the next id is `max(max(rowid), seq) + 1`, so lowering `seq` is inert while rows remain and becomes an id re-issue the moment the prune empties the log — which the engine does on a cadence, by design. Both are now refused at the CDC doors on both transports (local SQLite file and D1 over HTTP, since `sqlite_master` and `sqlite_sequence` are ordinary tables on D1 too), under the new `SLUICE-E-CDC-CHANGELOG-ID-REUSE`. **Door coverage is stated per state rather than assumed uniform:** the not-AUTOINCREMENT arm fires at every door, while the lowered-sequence arm bites only on a WARM RESUME, because the other doors re-read the watermark from `MAX(id)` and so resume at 0, where there is nothing to lose and nothing to refuse. **Its limit is written where it is defined, because the name reads broader than the truth: it grades the allocation state AT OPEN and cannot see a tamper performed mid-stream.** This is the SQLite counterpart of the Postgres change-log sequence preflight and it CLOSES the sibling v0.116.1 filed as ungated — **note that the pgtrigger half already shipped in v0.116.1 and is not new here.**

**`sqlitetrigger.CDCReader.Close` never joined its pump.** It cancelled the context and then closed and nil'd the executor the pump reads on every poll, so a `Close` in that window nil-dereferenced INSIDE the goroutine — an unrecovered panic, plus an unsynchronised cross-goroutine field access. The pump is now joined before the executor is torn down. Found while building the watermark gate above.

**Eight unverified invariants from the audit backlog were re-derived, taking the queue from 4 of 17 closed to 12 of 17, and every verdict was worked out from the code rather than taken from the filing.** The two that were FALSE are the two fixed above (the DDL-only-window premise and the MySQL generated-key carriage). Of the six that held, three held only in a narrower sense than they were written: the cold-copy gaplessness property was unpinned **by a gate that named it** — the gate discovered the site and then EXEMPTED it, with the claim under audit as the exemption's free-text reason, so moving the position capture below `UNLOCK TABLES` left the entire package's unit suite green; the lane-router decode-type premise is true across change KINDS and was resting on an unstated second premise about PROVENANCE, since chain-restore and the from-backup broker drive the same lanes from backup chunks where the round trip widens every sized integer, which was self-consistent only by stream composition and is now invisible-by-construction because the integer widths are aliased onto one tag per family; and the PostgreSQL replay-floor premise was true, with its evidence being a hand-run transcript in a comment for fourteen months and the branch that ACTS on it — the pass-through that is the `else` of a silent-loss refusal — carrying no server-touching test at all. **One environmental premise was measured on the surface where it actually runs:** the new `@@GLOBAL.log_bin` preflight shipped with a comment claiming the variable is readable by an ordinary connection on every supported line of both families, ground-truthed on MySQL 8.0.46 and MariaDB 11.4 — **neither of which is vtgate**, where two of the four MySQL-family flavors terminate. Measured on a real multi-process Vitess 24.0.1 cluster: vtgate does not answer it locally, it ROUTES the read to a tablet, and a Vitess tablet runs mysqld with binary logging because VReplication and VStream both ride it — so the premise HOLDS structurally and **no behaviour changes**; the production edits in that commit are comments only.

## Compatibility

**No breaking changes and no flags. No flag was added, renamed or removed; no default was changed. No on-disk format — backup chunks, chain manifests, resume state, the schema wire — is touched, and no backup chain is repartitioned. This is a drop-in upgrade from v0.116.1 and from anything older.** Two NEW error codes are added (`SLUICE-E-CDC-GENERATED-PRIMARY-KEY` and `SLUICE-E-CDC-CHANGELOG-ID-REUSE`), and the existing `SLUICE-E-SOURCE-REPLICA-IDENTITY` gains a fourth shape; none is removed or renamed. **Four things that previously ran now refuse, and they are limitations to state plainly rather than fixes to celebrate.**

**1. A CDC stream over a table whose row identity includes a STORED generated column now REFUSES, on both PostgreSQL and MySQL.** On PostgreSQL this fires in the CDC reader on the relation message, so it covers cold start, warm resume, `add-table` and mid-stream DDL, and it fires whether the replica identity is `DEFAULT`, `USING INDEX` or `FULL` — **`REPLICA IDENTITY FULL` is explicitly NOT a remedy**, because PostgreSQL leaves a generated column unpublished under `FULL` as well, and the refusal says so per table. On MySQL it fires on both narrowing arms of the binlog reader. The remedy in both cases is a row identity made of non-generated columns: a surrogate key, or promoting an existing `NOT NULL UNIQUE` column and demoting the generated column to an ordinary indexed one; on PostgreSQL you can instead point `ALTER TABLE … REPLICA IDENTITY USING INDEX` at an immediate `NOT NULL UNIQUE` index over non-generated columns, and the candidate-index query no longer offers an index containing a generated column. If the source cannot change, `sluice migrate` copies the table fine (its bulk copy reads the generated value with an ordinary `SELECT`) or `--exclude-table` drops it from the stream. **A table that previously ran and is now refused was NOT working before — it was over-deleting or silently skipping, which is the whole point of this release.** The Vitess VStream readers are NOT refused, because Vitess transmits the value; `pgtrigger` already refused such a table at setup; `sqlite-trigger` and `d1-trigger` cannot construct one, since SQLite rejects the DDL.

**2. `sync --where` now REFUSES an `UPDATE` or `DELETE` on a filtered table whose before-image omits any primary-key column.** This is a completeness guard at the one narrowing site that is not inside an engine, and it keys on the evidence rather than on the shape, so the VStream readers pass. If your filtered table has a generated primary-key column you will hit this refusal instead of the previous partial-key `WHERE`; the remedy is the same as (1), or dropping the `--where` entry for that table, or copying it with `sluice migrate --where` instead.

**3. A `sqlite-trigger` or `d1-trigger` CDC stream now REFUSES at open if the change-log id column is not `AUTOINCREMENT`, or if `sqlite_sequence` has been lowered below the stream's watermark.** A change log created by `sluice trigger setup` and never touched is unaffected and pays nothing. What is affected is a source where a table already named `sluice_change_log` existed and was adopted as-is by `CREATE TABLE IF NOT EXISTS` with a plain `INTEGER PRIMARY KEY` — that stream will stop at open rather than start, with an `ALTER`/re-setup remedy in the message. **The pgtrigger sequence-configuration refusal is NOT new in this release; it shipped in v0.116.1.** A routine auto-prune is explicitly not refused (the gate keys on `max(MAX(id), seq)`, not on `MAX(id)`, and carries a pruned-but-healthy control).

**4. A PostgreSQL `sync` cold start now refuses one more shape at the replica-identity preflight, ahead of scoping the publication.** This is deliberately more LENIENT than the reader's own check: it exempts a column some publication carries (via `pg_publication.pubgencols` on PG 18+), on the principle that an early check may miss but must never refuse something that works. **Its known limit is stated rather than implied: for `relreplident='f'` the preflight grades the PRIMARY KEY — what sluice actually narrows to — while PostgreSQL 18's own rule is wider, so a `REPLICA IDENTITY FULL` table whose only generated column sits OUTSIDE the primary key PASSES this preflight and would still break on PG 18. Widening it would over-refuse every earlier version, which is why it is a known limit rather than a bug.**

**PostgreSQL 18 deserves its own note, because upgrading to it changes behaviour independently of sluice.** On PostgreSQL 18 and later, PostgreSQL itself refuses the **source application's own** `UPDATE` and `DELETE` for this shape — `42P10`, with the detail "Replica identity must not contain unpublished generated columns" — the moment a publication that covers the table publishes update or delete. Measured on real servers (18.4, 17.10, 16.14, one fresh database per cell, because a leaked `FOR ALL TABLES` publication silently turns every "no publication" cell into a published one and made the first pass of this measurement read as "18 refuses unconditionally", which is wrong): it refuses **iff** a publication covers the table AND publishes update or delete, AND that publication lacks `publish_generated_columns = stored`, AND the EFFECTIVE replica identity holds a stored generated column — where under `FULL` the effective identity is EVERY column. `INSERT` is never refused. PostgreSQL 17 and 16 refuse nothing, anywhere. **The practical consequence for an operator: scoping a publication for `sync` on PG 18 can break your own application's writes to that table, and that is PostgreSQL's rule, not sluice's** — which is exactly why the preflight carries this check ahead of the publication being scoped, and why the reader's refusal keys on the publication rather than on the server version.

**Two advisory surfaces now say more than they used to, both additive.** A domain-wrapped `varchar` over MySQL's row limit and a domain-wrapped unconstrained `numeric` now produce the same advisory a bare column of the same base type does; previously they produced none while MySQL's emitter down-mapped the column anyway. And the `pgtrigger` refusal hint for a stored generated column no longer says logical replication "carries them", which was false as written — it now says the `postgres` engine's target keeps the `GENERATED` clause so the column is recomputed rather than carried, unless the column is part of the row identity, where that engine refuses too.

**One behavioural change on the backup side, in the safe direction.** A `backup incremental` or `backup stream` window whose last position-bearing event is a schema snapshot no longer advances `EndPosition` past that snapshot, so the next link re-reads from the previous position and re-emits it. The replay is idempotent, chains written by older binaries are read identically, and the artifact format is unchanged. The window that previously FAILED this invariant now succeeds.

**The grow-gate change adds two fields to one existing log line** (`episode_saw_grow_evidence` and `evidence_free_capped`, alongside the `hold` they explain) and adds no new line. Anything parsing that line by field name is unaffected; anything asserting an exact field set is not.

## Who needs this — action required

- **Anyone running `sluice sync` from a PostgreSQL source where an in-scope table's PRIMARY KEY (or `REPLICA IDENTITY` index) includes a `GENERATED … STORED` column. This is the silent-loss case and it is the one entry on this list that requires you to go look at data. RE-VERIFY that table's row counts and contents against the source for the entire period the stream ran, then upgrade and re-run.** The failure is silent in both directions and neither is reported: when only PART of a composite key is generated, one source `DELETE` deleted **every** target row sharing the non-generated prefix — target rows the source never touched, gone, exit code 0; when the WHOLE key is generated, the `WHERE` matched nothing, so the source's `DELETE` never happened on the target and the position advanced anyway. `REPLICA IDENTITY FULL` did not save you — it failed loudly but named nothing actionable, so if you saw an unexplained narrowing refusal on such a table, that was this. **Affected: v0.85.2 through v0.116.1.** A row count alone is not sufficient evidence in the over-delete direction, because the target can be short by rows the source still has; compare on the key. `sluice migrate` of the same table was never affected, and `sluice verify` on the same table is a reasonable first instrument — but the copy itself was fine, so the divergence is only in what CDC applied afterwards.
- **Anyone running `sluice sync` from a MySQL, MariaDB or PlanetScale binlog source with a PRIMARY KEY on a `GENERATED … STORED` column. Check whether the TARGET column is generated or materialised before deciding how much to re-verify.** If the target column is generated too — the faithful mirror every sluice schema writer emits — your stream was failing LOUDLY with an empty `WHERE`, and there is nothing silent to audit; upgrade and fix the source's identity. **If the target column is a plain materialised column, because you used `--type-override` or a target dialect that cannot express the expression, then `DELETE`s and key-migrating `UPDATE`s matched zero rows and the position advanced with nothing said — re-verify that table against the source.** **Affected: the DELETE arm from v0.78.3, the UPDATE arm from v0.99.266, both through v0.116.1.**
- **Anyone whose PostgreSQL `sync` uses `--apply-concurrency` at its default (or above 1) against a table with an array or `jsonb` PRIMARY KEY. Upgrade; there is nothing to re-verify.** This one CRASHED — a Go panic on the first `UPDATE` to such a table — so it is loud by construction and cannot have diverged data silently. It is on the default path (`--apply-concurrency` defaults to auto:N), and `--apply-concurrency 1` was the workaround for the concurrent routing site. **Affected: v0.99.82 through v0.116.1 on the concurrent appliers, v0.99.157 through v0.116.1 on MySQL's coalescing path.**
- **Anyone whose PlanetScale or Vitess `sync` cold start crawled or appeared to hang on a large table while the log showed absorbed drops and zero unhandled errors. Upgrade and re-run; nothing was lost and nothing needs re-verifying.** The copy was correct and merely not progressing — the gate held it, the retry machinery worked exactly as designed, and the numbers to look for in your own log are a high `hold` with `escalation_cycle` climbing and a steady stream of `vtgate connection error` drops. On this release such an episode is capped at 250 ms per window until something actually reports storage-grow evidence. **Two honest caveats before you attribute your run to this: if you are on a PlanetScale DEV branch, the drop storm itself is very likely the branch, and the projected improvement here (~11% duty, from 81.1%) is arithmetic plus a scaled in-repo model, not a measurement against real PlanetScale.** If you were on v0.113.0 or newer you already had the 50% run-level ceiling; this release replaces a bad unit (a fraction of wall clock spent in 30-second blocks) with a bounded one.
- **Anyone who migrates or restores a PostgreSQL source into MySQL, MariaDB, PlanetScale or Vitess where any column is declared through a `CREATE DOMAIN` over a base type that lands as MySQL `JSON` — every array element family, plus scalar `json`. Upgrade and re-run; there is nothing to repair.** This failed LOUDLY with the server's own `Error 3144 … CHARACTER SET 'binary'` and landed **zero** rows, so no partially-correct table exists. It only fired on the `LOAD DATA` core, so a target with `local_infile=OFF` took the batched-INSERT path and was never affected — which is why it may not have reproduced for you. **Reproduced on v0.115.0, v0.116.0 and v0.116.1; the dispatch defect is older and its earliest affected tag was not pinned.**
- **Anyone who re-runs `migrate` PG→MySQL over an existing target, or reads `sluice schema diff` between those engines, on a schema containing `json`/`jsonb`, `bit varying(N)` or DOMAIN columns. Upgrade; the refusal was a false one and there is nothing to re-verify.** Nothing was written and no data moved — the gate refuses before any data moves, which is what it is for. If you worked around it by dropping and re-creating the target, that was unnecessary. **Affected: the `migrate` re-run refusal from v0.99.258; the `schema diff` false-drift report from v0.8.0; both through v0.116.1.**
- **Anyone running `sluice trigger setup` against a SQLite or D1 source where a table named `sluice_change_log` already existed before setup ran, or where anyone has written to `sqlite_sequence`. Read Compatibility item 3 BEFORE upgrading: your stream will stop at open rather than start.** And if that change log has ever been able to re-issue a low id — a non-AUTOINCREMENT id column after an auto-prune drained the log, or a lowered `sqlite_sequence` — **then changes captured at or below the watermark were silently never emitted while it was in that state; those rows are missing from the target and nothing reported it.** Re-verify that table against the source for that period and treat the stream as needing a fresh cold start rather than a warm resume. A change log created by `sluice trigger setup` and never altered was never exposed.
- **Anyone taking `backup incremental` or `backup stream` on a source that runs DDL. Upgrade; no repair is needed and no existing archive is invalid.** The refusal you may have hit — "a data-bearing incremental window (1 change chunks)" blaming the CDC reader — was a false one on a window whose only event was a schema snapshot, and the backup simply did not complete. Separately, a `backup stream` chain that observed mid-stream DDL had its position-anchored schema versions dropped: **the data is complete and the manifest still recorded the schema delta, so a restore lands the right shape; the only cost is that a restore-THEN-RESUME across such a boundary falls back to a cold-start schema floor instead of a primed history.** Nothing to re-verify. **Affected: the false refusal from v0.99.226, the drain gap from v0.70.0, both through v0.116.1.**
- **Anyone planning to upgrade a PostgreSQL SOURCE to version 18 while running `sluice sync`. Read the PG 18 note in Compatibility first.** On 18, PostgreSQL refuses your own application's `UPDATE`/`DELETE` on a table whose effective replica identity holds an unpublished generated column, once a delete-publishing publication covers it — and under `REPLICA IDENTITY FULL` the effective identity is every column, so this reaches tables whose generated column is nowhere near the primary key. sluice's preflight deliberately does not grade that last cell, so **it will not warn you about it**; that is a stated limit, not an oversight.
- **Anyone who verifies what they run.** From this release the GHCR image carries attestations at three digests — the multi-arch index plus both per-architecture manifests — so `gh attestation verify oci://ghcr.io/sluicesync/sluice:0.117.0 --repo sluicesync/sluice` succeeds where it returned `HTTP 404` on every earlier tag. A 404 on an older tag means no attestation was recorded, not that the image is wrong. The full attested-or-exempt roster is in SECURITY.md.
- **Everyone else: nothing to do.** A run with no generated column in a CDC row identity, no array or `jsonb` primary key, no PostgreSQL DOMAIN column bound for a MySQL-family target, no `migrate` re-run over an existing target, no adopted SQLite change log and no PlanetScale drop storm is unaffected by every item on this list. The remainder of the release is eight audit-backlog invariants re-derived and pinned, corrected error and hint text, and CI gates.
