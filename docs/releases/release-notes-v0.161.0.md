# sluice v0.161.0

**HIGH fixes: two ways a MySQL target's key could silently merge two source rows into one at exit 0, plus a views-only namespace that was skipped at exit 0 (Bug 317). This is a minor release because it carries a backup FORMAT break (`FormatVersion` 15): a backup of a MySQL table with a collated functional key, taken by this release, can't be read by older binaries. Existing backups are unchanged.**

## Fixed

- **A `postgres-trigger` source now arms the key-collation guard on a MySQL target (HIGH, silent; KEY-COLLATION-TRIGGER-CDC-NO-HISTORY).** The guard compares an upsert's key under the source's own collation. It learns that collation from the schema version the change stream carries. The pgoutput reader emits one at every table's first change of a stream. The trigger-CDC reader emitted none. Take a Postgres UNIQUE key beside the primary key on a case-sensitive collation (the database default, or `"C"`). A MySQL target creates that key under `utf8mb4_0900_ai_ci`. An insert of `'A'` beside `'a'` became an `ON DUPLICATE KEY UPDATE` onto the `'a'` row, so the target held one row where the source held two, with no DDL anywhere. This was measured on postgres:16 → MySQL 8 for live `sync start` (cold start and warm resume), and for a chain restore of a `backup incremental` and of a `backup stream` window.
  - **The fix.** The reader now precedes each table's first change of a session with a schema version. It reads that version from the source catalog using the same schema reader that records the backup manifest, and stamps each column's collation as the pgoutput reader does. The version flows into the backup's schema history like a native Postgres one, and is anchored one change-log id below the change it precedes.
  - **New boundary check.** That version is read from the catalog as it stands, so a source change made while the stream was stopped could reach the target on the default `--schema-changes=forward` path (measured). A trigger-CDC source therefore now runs the boundary check that `--schema-changes=refuse` runs, whatever the flag says. A boundary the target cannot hold stops the stream with `SCHEMA-CHANGE-REFUSED`. The remedy is to drain the stream and re-run `sync start --restart-from-scratch`. Under `--inject-shard-column`, apply the change to the consolidated table and delete this shard's rows first. Under `--schema-already-applied`, apply the change and empty the stream's tables first. The reader's own observed-DDL refusal now gives the same remedies. It used to say to run `sluice migrate` first, which cannot run on a populated target.
  - **Sharded live DDL coordination.** Under `--inject-shard-column`, a `postgres-trigger` source now refuses live cross-shard DDL coordination at start (`TRIGGER-SOURCE-LIVE-DDL-COORDINATION`). Pass `--no-coordinate-live-ddl`. `sqlite-trigger` and `d1-trigger` are not refused.
  - **Two warm-resume wedges fixed before release.** An independent review found them, and both were measured on real servers. First, a narrowing `--type-override` refused `SCHEMA-CHANGE-REFUSED` on every warm resume. Second, a Postgres domain with no CHECK beside a `jsonb` column wedged every warm resume onto a Postgres target ("unknown type (OID 0)"). The cause of the second was that an empty list and a nil list in a column type compared as different types (TYPE-WIRE-EMPTY-SLICE-SIGNATURE). Without `jsonb`, the same false change silently moved the table onto the applier's slow path.
  - **Cost.** One schema read per schema per session, plus one collation query per table. Measured: 100 first touches beside 500 tables, views and sequences took 1.36 s in all.
  - **Visible effects.** `backup incremental --max-changes` now counts each table's version as a change, as it already did for native Postgres, so a window can close one row earlier.
  - **Not covered.** An `sqlite-trigger` or `d1-trigger` source records no collation, so there is nothing to arm from. That gap is filed as KEY-COLLATION-SQLITE-SOURCE-UNSTAMPED. A source `DROP INDEX` still leaves the key on the target. That hole predates this release, affects every CDC source, and is filed separately.
  - Pinned by `TestKeyCollationTriggerCDC_LiveSteadyState`, `TestKeyCollationTriggerCDC_ChainRestore`, `TestTriggerCDCFirstTouch_StoppedStreamDDLIsNeverForwarded` and `TestKeyCollationTriggerCDC_WarmResumeShapes`, among others. They are graded against the source's own rows by key bytes and were mutation-checked.

- **A MySQL target's functional unique key no longer lets one source row silently overwrite another.** This is MEDIUM, silent, for KEY-COLLATION-FUNCTIONAL-KEY-PART. It is HIGH, silent, for FUNCTIONAL-CAST-HIDDEN-COLLATION, a MySQL → MySQL key whose hidden-column collation its text does not record.
  - **KEY-COLLATION-FUNCTIONAL-KEY-PART.** A Postgres `UNIQUE (lower(email))` reaches MySQL as a functional key under `utf8mb4_0900_ai_ci`. There, `lower('e')` and `lower('é')`, two different values on Postgres, are one key. The key-collation guard skipped every functional key part. The second row replaced the first through `ON DUPLICATE KEY UPDATE` at exit 0. This was measured on MySQL 8.4 on CDC apply and on every idempotent copy path: add-table, resumed and chunk-resumed copies, the VStream COPY, and restore. A fresh migrate or sync cold start was already loud. The guard now compares every functional part per row, against the collation recorded on the target index's hidden column. If it cannot read that column (vtgate on Vitess and PlanetScale), it assumes the part may match, and refuses when the target matched two rows whose columns differ.
  - **FUNCTIONAL-CAST-HIDDEN-COLLATION.** A MySQL functional key part compares under a hidden column's collation, which the catalog's expression text does not record. A charset-less `CAST` and a string literal take the creating session's `collation_connection`. An `ALTER … MODIFY` of the column leaves the hidden column on its old collation. Three source keys each kept a pair of values apart on the source (`'a'`/`'A'`, `'ss'`/`'ß'`, `'e'`/`'é'`):
    - `((cast(k as char(10))))`, created from a `utf8mb4_bin` session;
    - `((trim(k)))`, whose column was later moved off `utf8mb4_bin`;
    - `((if(f, 'A', 'a')))`, created from a `utf8mb4_bin` session.
    
    sluice rebuilt each key from its text under `utf8mb4_0900_ai_ci`, and the second row replaced the first at exit 0 (measured on MySQL 8.4). Released versions are exposed too. sluice now reads each part's hidden-column collation from a vanilla MySQL source, and emits it on the keys it creates (`((expr) COLLATE <it>)`), so both rows land. Vitess and PlanetScale do not serve the hidden collation. The guard compares the read collation with the target key's own. It also arms where a column the part reads is compared differently on the target.
  - **Refusals.** A merge refuses `KEY-COLLATION-MERGE`. The remedy names the key to recreate comparing byte for byte, using `COLLATE utf8mb4_0900_bin` (or `utf8mb4_nopad_bin` on MariaDB). Some tables are refused before any row with `KEY-COLLATION-GUARD-UNSUPPORTED`:
    - a part naming a column the table does not have;
    - a generated column nested more than eight deep;
    - an armed key whose columns are still not all in the insert.
  - **The cost.** Where the guard arms, a conflict between byte-different values that the source would equate now refuses instead of converging. This mostly affects Vitess and PlanetScale, and MySQL → MySQL CDC apply.
  - **Not exposed:** a Postgres target. Its upsert never arbitrates on an expression index.
  - **Residual:** a plain key whose column has a Postgres default or nondeterministic collation is still not guarded on CDC apply, when it sits in a table with no primary key or in the primary key itself (pinned in `TestPlanKeyCollationGuard`).

- **Backup format: a manifest carrying a functional key part's hidden-column collation is now stamped `FormatVersion` 15, so older binaries refuse it (HIGH, silent on an older binary; a backup FORMAT break).** The collation (`IndexColumn.HiddenCollation`) decides which values the key counts as equal, so it is now folded into the schema fingerprint when set. An empty one marshals away, so no existing chain's fingerprint moves.
  - **Why the stamp.** An older binary drops the field. On a chain restore of a manifest that carries it, the old binary refuses `SLUICE-E-BACKUP-MANIFEST-INVALID` on an intact chain. On its own chain of the same source, it rebuilds the key from the text and restores at exit 0 with a row gone (measured with v0.160.4). v0.160.4 and older now refuse at their version ceiling ("format version 15 is newer than this build supports (14)"), and so does their `backup verify`.
  - **The reverse door.** A manifest recorded below 15 that carries the field was not written by any sluice. It is refused on read.
  - **Which backups get stamped.** Only backups whose schema carries the collation, and a chain only from its first fresh schema read. A schema with no collated functional key keeps its previous version, as does one read through vtgate and every Postgres, SQLite and trigger-CDC backup. A chain begun before this release keeps its version until a window's schema delta swaps in a freshly read schema, and that segment is stamped.
  - **Residuals.** A hidden collation changed and changed back inside one window is not seen (FUNCTIONAL-HIDDEN-COLLATION-WINDOW-REVERT). A target whose column character set differs from the source's can still meet `ERROR 1253` at the index build, loudly (FUNCTIONAL-HIDDEN-COLLATION-TARGET-CHARSET).
  - Pinned by `TestBackup_CrossVersionHiddenCollation` (against v0.160.4; mutation-checked), `TestBackupSegment_HiddenCollationStamp` and `TestReadManifest_RefusesAnUnstampedHiddenCollation`.

- **A database or schema that holds views but no tables now has its views created, instead of being skipped at exit 0 (MEDIUM, silent omission; Bug 317).**
  - **The bug.** `migrate` returned early from a namespace with "source schema has no tables; nothing to migrate", before its views phase. In an `--include-database`, `--include-schema` or `--all-*` fan-out, a reporting schema of views was silently left out. A single-namespace `migrate` of a views-only database did nothing. The `sync start` fan-out cold start skipped such a namespace the same way.
  - **Deferred views pass.** Only a namespace with neither tables nor views returns early now. In a fan-out, every namespace's views are created in a final pass after every namespace's tables exist. That pass keeps going while any view is still being created, and it fails loudly, naming every pending view, when a round creates none. A `migrate --resume` after that pass failed reruns it.
  - **Materialized views.** The Postgres writer now refreshes a materialized view that already exists with the same definition, instead of failing "already exists". It refuses one with a different definition and names it.
  - **`schema preview` and `schema diff`** now accept a views-only schema.
  - **New refusal: `SYNC-VIEWS-ONLY-NAMESPACE`.** A single-namespace `sync start` of a views-only schema has no table to stream. It used to exit 0 with an INFO line. It now refuses with `SYNC-VIEWS-ONLY-NAMESPACE`, and so does its `--dry-run`. Create the views with `sluice migrate`, or pass `--skip-views` to accept a run that streams nothing.
  - **Typo'd table filters now refuse.** A table filter no longer refuses a views-only namespace. A source that has tables and loses all of them to the filter still refuses, now on Postgres too. This closes a hole that predates this release: a typo'd `--include-table` on a Postgres source with no views used to exit 0. It now refuses on single-namespace `migrate`, `sync start`, `backup full` and `schema diff`. A Postgres `migrate` or `sync start` fan-out whose filter matched no table in any namespace also refuses now, where it used to exit 0 having copied nothing.
  - Pinned on real MySQL and Postgres servers by the views-only-namespace integration tests (`TestMigrate_ViewsOnlyNamespace_PostgresDeferredPassInterleaved`, `TestMigrate_ViewsOnlyNamespace_MySQLToMySQL_Fanout`, `TestStreamer_ViewsOnlyNamespace_PostgresSingle_RefusesViewsOnly` and others), graded by each target view's rows against the source view's. Also pinned by `TestMigrate_FanoutTypoIncludeTableRefuses_Postgres` and `TestStreamer_FanoutTypoIncludeTableRefuses_Postgres`, and by two roster gates: `TestViewCreationRoster_EveryCreatorNamesItsPreflight` and `TestTableScopePushDownCallersOweTheRefusal`.

## Compatibility

**Backup FORMAT break: `FormatVersion` 15.** A backup taken by v0.161.0 of a vanilla-MySQL table with a collated functional unique key part is stamped 15, and v0.160.4 and older refuse it. That covers fulls, and `backup incremental` / `backup stream` segments once a window's schema delta swaps in a fresh schema. Restore any chain containing a version-15 manifest with v0.161.0 or later. Existing backups are unchanged, with no fingerprint moved. Backups that don't carry the field are not stamped 15: Postgres, SQLite, trigger-CDC, Vitess/PlanetScale (vtgate) backups, and MySQL backups without such a key. (A `postgres-trigger` segment now records first-touch schema versions, so the existing `FormatVersion` 14 tier can stamp one whose key column has a nondeterministic collation changed after capture; v0.159.x refuses it.)

**Downgrading a `postgres-trigger` stream past this release:** an older binary refuses to warm-resume it once its target holds `postgres-trigger` rows in `sluice_cdc_schema_history`. Delete those rows first, or restart from scratch. `sync from-backup` already refused this shape (`KEY-COLLATION-BROKER-UNARMED`) and still does.

**New loud refusals.** Each one replaces either a silent exit 0 or a silent merge:
- `KEY-COLLATION-MERGE` now covers merges through a MySQL target's functional unique key. `KEY-COLLATION-GUARD-UNSUPPORTED` refuses the three unguardable functional-key shapes above, before any row. On Vitess, PlanetScale and MySQL → MySQL CDC apply especially, some conflicts that used to converge now refuse.
- A `postgres-trigger` source now runs the schema boundary check whatever `--schema-changes` says, and stops with `SCHEMA-CHANGE-REFUSED` at a boundary the target cannot hold. Under `--inject-shard-column`, it refuses live DDL coordination at start (`TRIGGER-SOURCE-LIVE-DDL-COORDINATION`); pass `--no-coordinate-live-ddl`.
- `SYNC-VIEWS-ONLY-NAMESPACE` refuses a single-namespace `sync start` (and its `--dry-run`) of a views-only schema.
- On Postgres, a typo'd `--include-table` that matches no table now refuses. That covers single-namespace `migrate`, `sync start`, `backup full` and `schema diff`, plus `migrate` and `sync start` fan-outs whose filter matched nothing anywhere.
- The Postgres writer refuses a pre-existing materialized view whose definition differs from the source's. One with the same definition is refreshed.

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale), `d1verify` (live Cloudflare D1) and `nekiverify` (live Neki) suites, which need live, billable infrastructure.

## Who needs this — action required

- **Anyone streaming or backing up a `postgres-trigger` source into a MySQL target, where a table has a UNIQUE key beside its primary key on a case-sensitive collation.** Before this release, a row differing from another only by case could have overwritten it at exit 0. Compare the target's rows against the source's for such tables, and re-run `sync start --restart-from-scratch` (or restore again on v0.161.0) where they differ.
- **Anyone with a MySQL target whose tables carry functional unique keys**, especially from a Postgres `UNIQUE (lower(...))` source or a MySQL → MySQL key over a `CAST`, a string literal, or a column altered after the key was created. Rows the source kept apart may have merged on CDC apply or on an idempotent copy path. Compare row counts and keys against the source, and re-copy the affected tables on v0.161.0. A `KEY-COLLATION-MERGE` refusal names the key to recreate.
- **Anyone who migrated or synced a multi-namespace fan-out containing a schema or database of views only**, or ran a single-namespace `migrate` of one. Those views were never created. Re-run `migrate` on v0.161.0, which creates them. A single-namespace `sync start` of such a schema now refuses; use `sluice migrate` for the views.
- **Anyone whose Postgres `--include-table` run ended "nothing to migrate" / "nothing to stream" or "multi-database migrate complete" without copying anything.** Check the filter for a typo. That run now refuses.
- **Anyone restoring backups across versions:** restore any chain containing a version-15 manifest with v0.161.0 or later. Older binaries refuse those manifests loudly; chains without one restore on older binaries as before.
- **Everyone else:** upgrade.

**Corrected 2026-10-16 (found by the site docs review and this release's regression cycle, which measured the remedy).** Three statements above were wrong.
- **The `postgres-trigger` remedy does not converge as written.** The damaged tables hold values the source keeps apart only by case, under a UNIQUE key the MySQL target compares `utf8mb4_0900_ai_ci`, so that key cannot hold both. Measured: `sync start --restart-from-scratch` recreates the table with the same key, copies both rows, then fails `Error 1062` at the index build, leaving both rows and no unique key. What converges (measured, including a later live case-only pair): create the target table yourself with the key comparing byte for byte (`COLLATE utf8mb4_0900_bin`), then run `sync start --restart-from-scratch --schema-already-applied`. A plain re-copy after recreating the key does not work, because the re-copy recreates the table.
- **`FormatVersion` 15 is not limited to unique keys.** Any collated functional key part, unique or not, on a vanilla-MySQL source table stamps the backup 15. So v0.160.4 and older also refuse a backup whose only functional index is non-unique.
- **The typo'd-filter holes were narrower than stated.** On v0.160.4, `backup full`, `schema diff` and a fan-out `migrate` already refused a Postgres `--include-table` that matched nothing. The exit-0 holes this release closes are single-namespace `migrate`, single-namespace `sync start` and fan-out `sync start`.
