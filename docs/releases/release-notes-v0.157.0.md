# sluice v0.157.0

> **Correction (v0.157.1):** the statement below that `--reset-target-data` "is honoured over any broker-owned row, decodable or not" was not true at v0.157.0. A broker row that did not decode (a wrong-typed field, invalid JSON or a truncated token) was mislabelled as a non-broker writer's and refused with or without the flag (Bug 299). v0.157.1 fixes it. No data was at risk: the row was refused, not discarded.

**New: exactly-once `sync from-backup` replay (ADR-0191). This closes a HIGH silent misapply on interrupted broker runs, and Bug 297 (HIGH) is fixed: rotated chains that no restore can apply whole are now refused before anything is written.** (1) `backup stream` and `backup incremental` now record each change's apply identity in the change chunk. The broker's position can now stand inside an incremental, so an interrupted `sync from-backup` resumes at the source transaction that was in flight. It no longer re-applies the whole incremental. Before this release, a re-run onto a source transaction that moved a key value onto another row emptied a table at exit 0 (F-E1-KEY-REUSE-REPLAY, v0.99.222 through v0.156.12). Keyless tables, which v0.156.11 and v0.156.12 refused outright, now replay wherever the replay is exactly-once. (2) Bug 297: a rotated chain (`--retain-rotate-at*`) carrying rows for a keyless table failed partway through `restore`. Restoring one into a MySQL table pre-created with a surrogate key duplicated rows silently: 355 rows for the source's 32. Both are now refused up front, and `backup stream` refuses to build a new chain of that shape. **This is a MINOR release with persisted-format additions:** chains it writes still restore on v0.156.12, but a broker cannot be downgraded in place. Change chunks grow by 12–25% compressed. **Chains written by older releases record no identities, so the keyless refusal still applies to their incrementals.** Read **Compatibility** and **Who needs this**.

## Features

**Exactly-once `sync from-backup` replay (ADR-0191).** Every row change that `backup stream` and `backup incremental` write now carries the source reader's apply identity: the source transaction id and the change's ordinal, as an optional `aid` field in the change chunk. The incremental's manifest sets an optional `apply_identity` flag. The broker passes the identities to the apply marks `sync start` already uses (ADR-0190). Its position token is now `backup-broker-v2`, which can record "applied through event e of incremental X". The token advances in the same target transaction as the work, at each source-transaction boundary. A re-run reads the token back from the target before every incremental, skips what landed, and re-delivers from the first source transaction not durably applied. On serial apply that is the transaction in flight. On the lane apply mode it is the transactions whose lanes had not all committed. The marks skip any re-delivered change that already landed. Readers that stamp identities are the Postgres, MySQL/MariaDB (GTID and file/pos), VStream, postgres-trigger, sqlite-trigger and D1 CDC readers. A change the reader cannot name is recorded without an identity. That covers a VStream COPY row or interleaved shard group, a MySQL transaction without a GTID or server identity, and a row the capture synthesizes, such as an ADD COLUMN fill. Pinned on real Postgres, MySQL GTID, MySQL file/pos and MariaDB by killing a broker after every statement of a 44-event incremental. The incremental carries a keyless table, a secondary-unique table and both key-reuse shapes, under serial and lanes. All 38 cells per engine converge to the source (`TestBroker_CrashMidIncremental_Postgres`, `_MySQLGTID`, `_MySQLFilePos`, `TestBroker_CrashMidIncremental_MariaDB`). Repeated abrupt cancels are pinned by `TestBroker_CancelStorm_Postgres` and `_MySQLGTID`. The codec round trip, including `Seq` above 2⁵³, is pinned by `TestChangeChunk_ApplyIDRoundTrip`, and the token by `TestBroker_FrontierTokenAtEveryBoundary`.

**Keyless tables replay through the broker where exactly-once holds (`SLUICE-E-BROKER-KEYLESS-TABLE`, narrowed).** v0.156.11 and v0.156.12 refused every keyless table in a chain, at start. The broker now judges each incremental before applying any of it, for the tables that incremental touches. It refuses only when a table has no key the replayed rows carry AND the replay cannot be made exactly-once. That happens in three cases, and the message says which: the incremental records no identities (written by an older sluice, or rewritten by `backup compact --smart-compaction`), a change to the table carries none (`BROKER-KEYLESS-NO-IDENTITY`), or the target's apply marks cannot cover the table. Marks cannot cover it when they are unusable by the role, on a PlanetScale Postgres (Neki) target, or when the target is keyed only on a column the rows do not carry. Only the Postgres and MySQL appliers answer the coverage question. While an incremental relies on marks for a keyless table, the applier is held to them: a mark table that becomes unusable between the check and the apply refuses the apply before any row is written. Pinned by `TestBrokerKeylessDoor_PerIncrementalMatrix`, `TestFE1_Broker_KeylessChain_ExactlyOnceOrRefused` and `TestChangeApplier_RequireApplyMarks` (real Postgres and MySQL, both apply entries).

**`BROKER-UNIDENTIFIED-CHANGES` (WARN).** A keyed change without an identity inside an incremental that records them is replayed without marks. It converges by key, except for a key moved onto another row inside the one interrupted transaction. The broker logs this marker once per such incremental, with the count. It is routine on VStream chains. Pinned in both directions by `TestBroker_UnidentifiedKeyedChangesWarn`.

**Resuming inside a rewritten incremental refuses (`SLUICE-E-BROKER-INCREMENTAL-REWRITTEN`, exit 3).** The position records a digest of the in-progress incremental's chunk list. If smart compaction rewrote that incremental in between, or a different incremental now follows, or the incremental decodes to fewer events than the position counted, the broker refuses before applying anything of it. The recovery is `--reset-target-data`. Naive `backup compact` moves the same chunk bytes and resumes normally. Pinned by `TestBroker_RewrittenIncrementalRefuses`.

**Cold starts and chain restore clear the stream's apply marks first.** `--reset-target-data`, `--at-chain-id` and chain restore delete the stream's rows from `sluice_cdc_apply_marks` before applying anything. A mark left by an earlier run under the same stream id could otherwise skip a change the fresh target never received. Pinned by `TestBroker_ColdStartsClearTheStreamsMarks` and `TestBroker_ColdStartClearsAStaleMarkThatWouldSkip`, which has a control arm proving the planted mark skips.

## Fixed

**An interrupted broker no longer misapplies a source transaction that moved a key value onto another row (HIGH, silent; F-E1-KEY-REUSE-REPLAY).** An interrupted `sync from-backup` re-applied its whole incremental onto the state it had already produced. Re-applying `[UPDATE 1→2, DELETE 2, UPDATE 3→1]` left the table empty against the source's one row, at exit 0. `[INSERT 1, UPDATE 1→2]` instead failed on a duplicate key on every re-run. On a chain this release writes, the re-run is exactly-once (above). On an incremental without identities, the frontier confines the re-delivery to the interrupted source transaction (on the lane apply mode, the transactions whose lanes had not all committed), and the `BROKER-INCREMENTAL-PARTIAL` advice stands. **Affected releases:** brokers on v0.99.222 (when the broker started re-applying an interrupted incremental whole) through v0.156.12. The precondition is an interrupted broker, an incremental that moved a key value off one row and onto another, and a re-run.

**`--reset-target-data` and `--at-chain-id` are no longer ignored when the target already holds a broker position (HIGH, silent for `--at-chain-id` on a narrow precondition: a target re-restored to an earlier link; loud for `--reset-target-data`).** The warm-resume branch ran before either flag was read. A `--reset-target-data` therefore warm-resumed. On v0.156.11 and v0.156.12 that re-hit the corrupt-position refusal whose own message prescribed the flag. It also turned the recovery `BROKER-INCREMENTAL-PARTIAL` prescribes for a key-changing source into the unmarked re-run it warns against. An `--at-chain-id` was ignored without a word, so a broker over a target re-restored to an earlier link resumed from the stale row and skipped the incrementals in between. Now `--reset-target-data` is honoured over any broker-owned row, decodable or not. It clears the position row and the stream's marks after the pre-drop checks and before the drop, so a crash mid-reset leaves no position to resume onto a half-restored target. An `--at-chain-id` that names the position's last fully applied link, with nothing in progress, resumes as before. Any other `--at-chain-id` refuses with `BROKER-AT-CHAIN-ID-CONFLICT` before anything is applied. A row owned by a non-broker writer is still refused with or without the flag. Pinned by `TestBroker_ResetOverAnExistingPosition`, `TestBroker_AtChainIDOverAnExistingPosition` and `TestBroker_ResetOverAPosition_Postgres`. **Affected releases:** v0.20.0 (the broker's first release) through v0.156.12.

**An apply mark's transaction key always fits the MySQL mark table (HIGH; found by this release's value-fidelity review before the tag).** A VStream source names a transaction by its shard's executed GTID set. That set takes about 46 characters per server UUID, and a long-lived shard gains a UUID at every reparent. Five or more exceed the `tx_id VARCHAR(255)` column of `sluice_cdc_apply_marks` on a MySQL or Vitess target. Under the strict sql_mode sluice sets, the apply failed with error 1406 at the first marked change. Under a relaxed `--mysql-sql-mode`, MySQL truncated the value, so the mark stopped matching its change and the change could be applied twice after a crash. Without the fix, this release's exactly-once broker replay would have turned that into a duplicate row in a keyless table, at exit 0. Marks are now stored and compared under `MarkTxKey`. A transaction id of 255 bytes or fewer is stored unchanged; every source except VStream produces those. A longer one becomes its first 128 bytes, `:sha256:` and the SHA-256 of the whole id. The key is applied at every point a transaction id enters the mark logic, so the write, the comparison and the delete cannot drift apart. No schema change is needed. A MySQL mark write that would still exceed its column now refuses rather than letting any sql_mode truncate it. Pinned on real MySQL under strict and relaxed sql_mode by `TestApplyMarks_LongTxIDRoundTrip`, and through chain restore and an interrupted broker by `TestLongTxID_ChainRestoreAndBrokerOntoMySQL`. **Affected releases:** the same latent defect has been in live VStream→MySQL `sync start` since v0.156.5. There it was loud under the default sql_mode. No pin covers that path against a real VStream source; it goes through the same keyed entry points.

**A rotated chain that would re-write a keyless table is refused before anything is written (Bug 297; HIGH; loud on a keyless source table, silent on a surrogate-keyed MySQL target).** Rotation (`backup stream run --retain-rotate-at` / `--retain-rotate-at-chain-length`) writes a full per segment. Chain restore applies every full after the first over the rows the earlier segments already restored. A table with no `PRIMARY KEY` and no `NOT NULL UNIQUE` index cannot take that. The idempotent writer refused it, so `restore` exited 1 at the second segment full after part-writing the target. The regression cycle measured 18 of 36 keyed rows on a 10-segment chain on v0.156.12, and the same failure on every release it tried back to v0.150.0. The remedy in that message was written for the VStream cold-start copy. A target table pre-created keyed only on a surrogate the rows do not carry (`AUTO_INCREMENT`, serial, identity or a defaulted key) never collides at all. On MySQL, restoring a 14-segment chain with the keyless table excluded exited 0 holding 355 rows for the source's 32. On Postgres the same shape failed partway with SQLSTATE 42P10. `restore`, chain restore and `backup verify` now refuse both shapes with the new `SLUICE-E-BACKUP-ROTATED-KEYLESS-TABLE` (exit 3). The refusal names each table and the segment fulls (backup id and directory) that carry its rows. A later full with no rows for the table is not refused. The key judged is the one the target's table will actually hold. A later full never creates or re-keys a table: it lands in the table that segment 0 or an AddTable delta created, as altered by the recorded deltas. So the check projects the chain's own schema history and judges that projection, before anything is written and in `backup verify`. It also probes the live target catalog up front and again right before each later full. Pinned by `TestBug297_RotatedKeylessChain_PG`, `TestBug297_RotatedKeylessChain_MySQL`, `TestRefuseRotatedKeylessRecorded_Matrix`, `TestRefuseRotatedKeylessTarget_SurrogateKeyedTarget`, `TestRefuseRotatedKeylessRecorded_JudgesTheTableTheChainCreates`, `TestBug297_KeyAddedInRotationGap_MySQL` and `TestBug297_KeyAddedWhileStopped_MySQL`. **Affected releases:** chains written with rotation on v0.67.0 (inline rotation's first release) through v0.156.12. The loud arm failed on releases whose idempotent writer refuses keyless tables: v0.99.4 and later on a MySQL target, v0.99.13 and later on a Postgres target. By code reading only (unmeasured), restores on releases before those wrote the later fulls' rows for a keyless table as plain INSERTs, a silent duplicate at exit 0. The surrogate-keyed MySQL arm was silent on v0.156.12 (measured) and, by code reading, on every release with rotation. The rows are in the chain, but this release cannot restore those tables from it. The remedy is `--exclude-table` for each named table, and another route for those tables, such as `sluice migrate --include-table`.

**`backup stream` no longer builds such a chain.** With rotation enabled, `backup stream run` refuses to start a new chain while a table in the rotation's scope has no `PRIMARY KEY` and no `NOT NULL UNIQUE` index (`SLUICE-E-BACKUP-ROTATED-KEYLESS-TABLE`, exit 3, nothing written). A stream continuing an existing chain is not stopped, so an upgrade does not take down a running backup or leave a Postgres slot pinning WAL. Instead it logs a `ROTATION-KEYLESS-TABLE` WARN carrying the code, names the tables and says whether the chain already holds a later full that restore will refuse. It then continues with rotation suspended. A table that appears or loses its key mid-stream makes each rotation refuse before its snapshot opens: the stream logs the code with the existing "rotation aborted; staying on the open segment" ERROR and retries at every rollover. Pinned by `TestBackupStream_RotationKeylessStartDoor_ExistingChainContinues` and `TestBug297_RotationRefusedForAKeylessTableAddedMidStream_PG`. The idempotent writer's keyless refusal now names both callers that reach it, instead of only the VStream cold-start copy.

**A chain carrying a schema change that replay cannot apply is refused before anything is written (MEDIUM, loud).** Such a change is an `ALTER TABLE … ADD PRIMARY KEY`, a dropped column, an added or redefined CHECK, a foreign-key change, or a change to or from a generated column. Recorded mid-chain, it made `restore` fail at that incremental after writing every earlier link (measured: 11 of 51 keyed rows), with `SLUICE-E-BACKUP-SCHEMA-DELTA-UNSUPPORTED`. `backup verify` passed such a chain. `restore`, `backup verify` and the broker's `--reset-target-data` cold start (before its drop) now refuse it up front with the same code. Replaying a single delta also refuses before emitting DDL for any part of it, where it used to apply the parts listed before the refused one. This shapes the keyless remedy: a `NOT NULL UNIQUE` index added mid-chain replays, an `ADD PRIMARY KEY` does not. Pinned by `TestRefuseUnreplayableDeltas` and `TestApplyAlterDelta_RefusedAspectEmitsNoDDLForTheOthers`. **Affected releases:** v0.108.0 (when replay began refusing those changes) through v0.156.12.

**A broker or restore stopped while its keyless-table check probed the target now stops cleanly instead of exiting with a network error (LOW, loud; v0.156.11–v0.156.12).** pgx cancels an in-flight call by moving the socket deadline into the past; on the write path that surfaces as `write failed: … i/o timeout`, and the next statement as `driver: bad connection`, neither of which unwraps to the context error. A broker stopped during the door therefore exited non-zero with a network-looking cause. Nothing was applied or lost: the door writes nothing, and interrupted applies were already classified by the context. `migcore.ErrOrCancel` now reports a door probe's failure as the cancellation once the context has ended, at every target probe the door makes — the broker's keyless door, the restore re-run door and both rotated-keyless judgments, on every engine. The broker also applies the same rule once at its single exit point (`migcore.ErrOrCancel`), so a stop that lands in any other target statement, such as the startup position write, is reported as the stop too. A coded refusal and the broker's partial-progress errors are never re-attributed. Pinned by `TestSyncFromBackup_CancelMidPositionWriteIsTheCancel`, `TestSyncFromBackup_CodedRefusalUnderCancelStaysCoded`, `TestBrokerKeylessDoor_CancelMidProbeIsTheCancel`, `TestFindReplayKeylessTables_ProbeFailureUnderCancelIsTheCancel` and on real Postgres by `TestFindReplayKeylessTables_RealPostgresCancelIsTheCancel`.

**Built with Go 1.26.9 and `golang.org/x/net` v0.60.0, picking up eleven upstream security fixes (published while this release was in its tag gate).** govulncheck reported them reachable from sluice's code: GO-2026-6617, GO-2026-6612, GO-2026-6611, GO-2026-6610 and GO-2026-6603 in `golang.org/x/net` (HTTP/2), and GO-2026-6613, GO-2026-6608, GO-2026-6607, GO-2026-6605, GO-2026-6600 and GO-2026-6599 in the Go 1.26.7 standard library (`net/http`, `net/textproto`, `crypto/tls`, `net/http/httputil`, `html/template`). Most are server-side. sluice serves HTTP only when an operator opts in, through `--pprof-listen`, the metrics endpoint, the dashboard or `metrics-watch`. An operator who exposes one of those beyond a trusted network should upgrade. sluice's HTTP and TLS clients (webhooks, KMS, cloud object stores, the PlanetScale API) take the client-side fixes. No sluice code changed. **Affected releases:** every release built with Go 1.26.7 or earlier, and `golang.org/x/net` v0.58.0 or earlier.

## Known residuals

These are filed in `docs/dev/audit-backlog.md` (the F-E1 section) and ADR-0191 §13–§15, and are open.

- **UNVERIFIED PREMISE for VStream and the trigger sources.** Exactly-once replay assumes that no reader re-delivers a completed transaction into the next incremental (ADR-0191 §13 R2). This is measured on Postgres, MySQL GTID, MySQL file/pos and MariaDB (single- and multi-domain GTID) by `TestBackupChain_NoTransactionInTwoIncrementals_MariaDB` and its siblings. It is argued by code reading only for VStream and the trigger sources (F-E1-ST-ENGINE-PINS). The keyless lift relies on it only where those sources can carry a keyless table. A proposed identity-based check that would turn the premise into a refusal is not built.
- **Keyed rows recorded without an identity** replay unmarked, with only the `BROKER-UNIDENTIFIED-CHANGES` WARN. A key moved onto another row inside the one interrupted transaction can still misapply there.
- **BUG297-REAL-FIX: restoring the keyless tables of a rotated chain.** This release refuses them. Restoring them needs a per-table reload at each later full with a per-table skip floor for the overlap.
- **The rotation door is wider than the restore door.** `backup stream` judges every table a rotation full would read. A rotation full has no table filter of its own, so that is every table the engine does not exclude by default, including empty keyless tables that the restore door would never refuse. A table that appears or loses its key mid-stream suspends rotation indefinitely. The open segment then grows without bound, and the per-rollover ERROR is the only signal: `backup stream status` does not show it. An `ADD PRIMARY KEY` recorded on a running chain gets no backup-time warning. Restore and verify refuse it up front.
- **F-E1-ROTATED-SEGMENT-OVERLAP, remaining sources.** A resumed single-segment full, and restore's reparent reconcile, onto a target keyed only on a surrogate are not reached by the Bug 297 check.
- **Broker coverage gaps.** Any PlanetScale Postgres (Neki) target refuses keyless replay, even an unsharded one, until the Neki Tier-3 pass. Secondary-unique lane marks are not written on the broker, because `--exactly-once-lanes` is not plumbed to it. An in-flight transaction's secondary-unique collision therefore stays loud. A smart compaction that rewrites an incremental between a crash inside its first transaction and the re-run is not detected (§13 R11), and the re-run replays the rewritten incremental from its start. The crash suite is same-engine only (PG→PG, MySQL→MySQL), with no cross-engine target and no VStream or trigger-CDC source. Identity capture is not pinned for VStream or D1.
- **The rotated-chain check's up-front projection is narrower than the live probe.** A key column the target generates is now judged unsupplied up front. Deferrable keys, the vtgate primary-vindex rule and cross-engine index drops depend on the target engine, and `backup verify` has no target. So the live probe right before each later full is what catches them: still loud, but after earlier links were written.
- **Performance (perf-parity GAPs 53–56).**
  - Once any table a chain records is keyless, the broker decodes every incremental twice, not only those touching that table. On a cloud store that doubles the reads.
  - The broker also reads the target position once per incremental, and walks the chain's recorded schemas once per incremental.
  - The rotated-chain check probes each table on the target once per later full.
  - None of this is measured.
- **SIGTERM inside a rotation** exits non-zero, because a cancelled lineage load is returned as fatal rather than as a stay-open abort. This is LOW, loud and pre-existing.
- **Still open from v0.156.12:** F-E1-COARSER-TARGET-KEY and the steady-state half of F-E1-SHARDED-ROUTING.

## Compatibility

**Persisted format: additive, `FormatVersion` unchanged.** The change chunk gains an optional `aid` field and the manifest an optional `apply_identity` flag. Older binaries ignore both. Measured on v0.156.12 reading a chain this release wrote: `backup verify` OK, and restore equal to the source. This release reads older chains unchanged. The flag is outside the manifest signature, so signed chains this release writes still verify on older binaries. A forged flag is caught change by change, in either direction, by the identity checks.

**Broker downgrade is not in place.** The broker's position token is now `backup-broker-v2`. This release reads v0.156.12's token. v0.156.12 and older refuse the new token, reporting the stream as owned by a non-broker writer, rather than misreading it. They refuse before reading `--at-chain-id`. To downgrade, delete the stream's row from `sluice_cdc_state` and its rows from `sluice_cdc_apply_marks`, or choose a new `--stream-id`. Then start the older binary with `--at-chain-id=<last fully applied backup id>`; the deleted row named that id in `last_applied_backup_id`. A broker that was partway through an incremental when you upgrade re-applies that one incremental whole, without marks, as v0.156.12 would have. If that incremental touches a keyless table, it refuses with `SLUICE-E-BROKER-KEYLESS-TABLE` naming `BROKER-CLASSIC-RESUME`, as v0.156.12 did, because the old token proves no marks were kept. The broker writes v2 tokens from then on.

**Accepted costs (operator decision, ADR-0191 §14):**
- Change chunks grow by about 12–25% compressed (+11.8% to +25.2% measured on Postgres and MySQL sources). This exceeds the ADR's own ≤10% acceptance line, and the overshoot was accepted.
- Broker replay of primary-key-changing transactions (workload D) on the lane apply mode is about 10.5–10.8% slower, because of the apply marks each key change's barrier now writes. Serial replay is within 1.4% on workloads A, B and D.
- Cold starts and chain restore issue one extra `DELETE` on `sluice_cdc_apply_marks`.

**New refusals:**
- `SLUICE-E-BACKUP-ROTATED-KEYLESS-TABLE` (exit 3). It refuses `restore` and `backup verify` on a rotated chain that re-writes a keyless table or a surrogate-keyed target table. It also stops `backup stream run` from starting a new chain with rotation when an in-scope table is keyless, and makes it refuse each rotation (staying on the open segment) for a table that appears or loses its key. An existing chain only WARNs, with rotation suspended.
- `SLUICE-E-BACKUP-SCHEMA-DELTA-UNSUPPORTED` now fires before anything is written, from `restore`, `backup verify` and a broker `--reset-target-data`. It used to fire mid-restore, and verify did not report it.
- `SLUICE-E-BROKER-INCREMENTAL-REWRITTEN` (exit 3, new), `BROKER-AT-CHAIN-ID-CONFLICT` (new), `BROKER-CLASSIC-RESUME` (new, on the first incremental after an upgrade mid-incremental), and `SLUICE-E-BROKER-KEYLESS-TABLE` when the apply marks a keyless table relies on become unusable after the check. Keyed tables keep the `APPLY-MARKS-UNAVAILABLE` WARN and apply without marks, as before.

**Relaxed:** `SLUICE-E-BROKER-KEYLESS-TABLE` now refuses fewer chains. A keyless table on an identity-recording chain replays. A keyless table is now judged only when an incremental touches it, so a chain whose keyless table sits idle is no longer refused at start.

**Flags:** none added, removed or renamed. `--reset-target-data` and `--at-chain-id` on `sync from-backup run` now act over an existing broker position (above).

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale, a billable cluster), `d1verify` (live Cloudflare D1) and `nekiverify` (a billable Neki cluster) suites. Each needs live infrastructure and runs only on the operator's call. What that leaves unmeasured live:
- **PlanetScale MySQL / Vitess:** apply marks and exactly-once broker replay through PlanetScale's vtgate, and identity capture from a live VStream source.
- **Neki:** keyless broker replay is refused on any Neki target, so no exactly-once behaviour there is relied on.
- **D1:** identity capture and the rotation check on a live D1 source are not exercised.

## Who needs this — action required

- **Anyone who re-ran an interrupted `sync from-backup` on v0.99.222 through v0.156.12 over a source that moves key values between rows** (a transaction that frees a key and gives it to another row, such as a slot or ordering column used as a key). Compare the affected tables with the source using `sluice verify --depth count` (or `--depth sample`). A count below the source's means a misapplied re-run. Rebuild with `sync from-backup run --reset-target-data` on this release.
- **Anyone who passed `--at-chain-id` to a broker whose target already held a position** (v0.20.0 through v0.156.12), especially after re-restoring the target to an earlier link. The flag was ignored, and the broker resumed from the recorded position. Compare the target with the source; incrementals between the asserted and the recorded link may be missing. Anyone who passed `--reset-target-data` over an existing position, including on the advice of `BROKER-INCREMENTAL-PARTIAL` or a corrupt-position error on v0.156.11 or v0.156.12, got a warm resume instead. Treat that as the re-run above.
- **Anyone who restored a rotated chain (`--retain-rotate-at*`, v0.67.0 or later) into a MySQL target whose tables were pre-created with a surrogate key** (`AUTO_INCREMENT` or a defaulted key the backup's rows do not carry). Compare row counts with the source; a count above the source's means duplicated rows. Also check restores of rotated chains with keyless tables on releases before v0.99.4 (MySQL target) or v0.99.13 (Postgres target), which by code reading duplicated silently.
- **Anyone running `backup stream` with rotation over a source with keyless tables.** Run `sluice backup verify` on the chain. If it reports `SLUICE-E-BACKUP-ROTATED-KEYLESS-TABLE`, the chain cannot restore those tables: plan another route for them. After upgrading, the running stream logs `ROTATION-KEYLESS-TABLE` and stops rotating. Give each named table a `NOT NULL UNIQUE` index on the source (not `ADD PRIMARY KEY`, which makes the chain unrestorable from that change on), or run without rotation. A new chain with rotation will not start until every in-scope table has a key.
- **Broker operators who want keyless tables replayed:** upgrade the writer (`backup stream` / `backup incremental`) as well as the broker. Only incrementals written by this release carry identities. A broker that still has to replay an older incremental touching a keyless table refuses it. Recover with `--reset-target-data`, which chain-restores through the tail, so the broker then judges only incrementals written by the upgraded writer. Or take a new full. A smart-compacted incremental loses its identities, so do not smart-compact a segment a broker still has to replay (naive `backup compact` is safe).
- **Anyone planning to roll a broker back:** read **Compatibility** first. A broker that has run this release cannot be restarted on an older one without deleting its position.
- **Everyone else:** upgrade, nothing to check.
