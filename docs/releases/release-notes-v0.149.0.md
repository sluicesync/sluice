# sluice v0.149.0

**Stopping a `sync` cold start after its copy no longer costs you the copy.** Ctrl-C during a long index build used to mean re-copying everything — v0.148.0 kept the replication slot for a resume that did not exist, and v0.148.2's notes had to say so. This release ships the resume. It also ends the cold-start blackout on every source that is not PostgreSQL, corrects a published piece of operator guidance that would get a healthy migration killed, and closes a foreign-key refusal that this release's own new code was arming and never running.

## Features

**A PostgreSQL cold start that was STOPPED after its bulk copy finished is resumed by re-running it** (`COLD-START-RESUMED`). The cold start now records its snapshot anchor when it starts, in a new NULLable `snapshot_anchor` column on `sluice_migrate_state`. Re-run `sluice sync start` with the same `--stream-id` and it skips the bulk copy, finishes the remaining phases, and starts CDC from that anchor. Every source change committed while you were stopped is still on the slot and is delivered. On the v0.148.2 regression cycle the old behaviour cost 2.5M rows of re-copying.

It refuses rather than guessing, on every one of a list of proofs [`cdc-streaming.md`](../operator/cdc-streaming.md) carries in full: a PostgreSQL source (the new `SnapshotAnchorVerifier` capability, whose engine list is held to the code by a doc-sync gate rather than described in prose); no `sluice_cdc_state` row yet, so an ordinary warm resume is never touched and `--reset-target-data` never reaches the gate; a single namespace, since the proofs key on bare table names; **every in-scope table** recorded complete, judged on the per-table progress rows rather than the phase; the same row-shaping flags the copy was made with; the rows still present on the target; and a slot that is inactive, bound to this database, and sitting at exactly the recorded `confirmed_flush_lsn`.

Three of those are their own refusal, because each is a distinct way to lose data silently. `COLD-START-SHAPE-CHANGED` — the drift doors that normally catch a changed `--where` all key on the `sluice_cdc_state` row, which does not exist in this window, so a re-run without the old predicate would have inherited a filtered copy as if it were complete, and CDC never backfills what the copy did not select. `COLD-START-TARGET-EMPTIED` — a `TRUNCATE` leaves the control rows, the phase, the anchor and even the indexes intact, so it passes every check that reads sluice's own bookkeeping; the resume asks the target itself. `COLD-START-ANCHOR-MOVED` — a slot consumed past the anchor has already discarded the changes in between, and the refusal names both positions. A replaced source is caught too: the snapshot's position now carries the source's `system_identifier` and timeline from the moment the slot is created.

The phase is deliberately **not** the proof, and that is a correction to the original design made against a real server rather than reasoned about. On the PostgreSQL path the copy and the index build run overlapped under one errgroup, so an index-axis failure records phase `indexes` over a possibly-mid-table copy — and, measured, an operator stop records nothing at all, because the failure mark's own write runs on the context the stop cancelled. A stop injected at the index build leaves the header at `bulk_copy`, which is the phase the original gate would have refused, in the exact window it exists for.

What the target-row floor does **not** catch is a partial deletion: one surviving row satisfies it, and catching less would need a full `COUNT(*)` per table.

**Every cold start reports its progress, not only the PostgreSQL fast parallel one** (audit A0909-P2b). Cold-start visibility shipped in v0.148.0 and the recording it depends on was built by exactly one code path. Every serial source recorded nothing, so `sync status` showed nothing at all for a MySQL, MariaDB, Vitess, PlanetScale, SQLite, D1 or trigger-engine cold start, for the whole time it ran — including the shape of the operator report the feature was built for, which was a PlanetScale move. The recording now reaches the serial copy too, covering those engines plus `--schema-already-applied`, an interrupted-copy resume, and the multi-database fan-out, where one recording covers the run and progress is keyed per database. The cost is bounded by the throttle the fast lane already used: at most one intermediate write per table every two seconds, plus each table's first and last. A recording that cannot be written warns and never fails the copy.

## Fixed

**`sync status` no longer tells you a healthy cold start is dead** (audit A0909-STATUS-1). v0.148.0's cold-start block said a `LAST PROGRESS WRITE` age that keeps climbing means the run is gone. That is wrong for the entire copy phase: the row it renders moves only when the PHASE moves, while per-table progress goes to a separate table the command does not read. A long copy of one large table holds that age perfectly still on a healthy run — and the guidance told the operator to conclude the opposite and kill it. **The phase advancing is the liveness signal;** a climbing age means something only once the phase has stopped moving too, and comparing the target's row counts against the source settles it. Corrected in the rendered output, in `sync health`'s error, in the comment beside the code that said the same thing, and in the cross-region migration guide. The v0.148.0 and v0.148.1 notes carry correction banners.

**The stopped-cold-start resume proves its metadata-only foreign keys clean, instead of arming the fast add and never running the scan.** Found by this release's pre-tag value-fidelity review, in this release's own new code. A MySQL-family target can have foreign keys added without InnoDB's O(rows) re-validation, which is what dodges PlanetScale's statement-time wall on a large child table; that is safe only because a bounded orphan scan afterwards proves each one clean, drops it, and refuses loudly with `SLUICE-E-FK-SOURCE-ORPHAN` when it is not. The resume was handed an identically-configured writer by the helper this release split out — arming included — ran the constraints phase through it, and went straight to the CDC anchor without ever calling the scan. On a PostgreSQL source to a MySQL or PlanetScale target with no `--where`, a resumed run could leave a foreign key on the target over data that violates it, at exit 0, where the sibling path refuses. The arm and the scan now have a gate holding them together: `TestForeignKeyOrphanScanRoster_EveryArmedPathScans` derives the call graph from the code and requires every arming path to reach the scan or to name the ancestor that does, with both halves of that claim machine-checked.

**A resumed cold start raises the PlanetScale query timeout for the phases it still has to run.** The ordinary cold start raises it before the copy and index build; the resume runs the index build and the constraints phase and nothing else, which is exactly the work that hits the wall — so the case the feature exists for, a stop during a slow index build followed by a re-run, was the one going back into it. The size gate that keeps a small copy from paying two rolling restarts now reads the interrupted run's recorded per-table row counts, which are measured rather than estimated.

**A finished table's progress row can no longer be overwritten by a stale one.** Two work-stealing pipelines finishing chunks of the same table each snapshot the row under a lock and write it outside that lock, so the slower write could land last and put a completed table back to `in_progress` — permanently, since nothing writes that table again. `sync status` would have shown it unfinished forever. The race detector cannot see it: both in-memory accesses are correctly synchronized, and only the durable writes race. Writes for one table are now ordered, and a snapshot that lost the race is dropped rather than written.

**A Cloudflare D1 read catches a text rewrite that preserves the byte count.** D1 stores invalid UTF-8 intact but replaces every invalid subpart with a replacement character in its query response, server-side, so the mangled value arrives looking valid. sluice compared the delivered byte total against the stored one, which catches three bytes replacing one — and misses the case where exactly three bytes are replaced by one three-byte replacement character, which is what severing a four-byte sequence at a byte boundary produces: a truncated emoji. The trigger lane has counted replacement characters as a second number since v0.140.0; the read path never did. Both lanes now share one expression and one verdict. Stated plainly because it is not verified: nothing here ran against live D1, so the assumption that D1 replaces per invalid *subpart* rather than per invalid *byte* is unmeasured. If it replaces per byte, the existing byte check already covers this case, so the read is safe either way.

**The `diagnose` bundle says why it found no spill counters, in the case that actually happens.** v0.148.3 added that reason on a branch neither command-line path can reach; the branch a wrong or absent `--slot-name` actually lands on still wrote nothing. It now names the slot it looked up, on every outcome, beside the stream's real slot name the same bundle already carried.

**A table whose name contains a dot is graded consistently.** The change readers and the dispatch filter derived a table's unqualified name in two different ways, so for a table named `a.b` they disagreed about whether it was in scope — and a stream-killing refusal one side skipped could have its schema change forwarded by the other. Both now use one shared function. No filter behaviour changes for any name without a dot in it.

**The resume's shape-drift refusal no longer blames flags for a source-side change.** Two of the things it fingerprints — the table and view sets — come from the source schema rather than from any flag, so a table dropped on the source between the stop and the re-run produced a refusal telling the operator to re-run with flags that nothing could satisfy.

## Compatibility

**One additive schema change, and it is NULLable.** `sluice_migrate_state` gains a `snapshot_anchor` column, added by the same `ADD COLUMN IF NOT EXISTS` / detect-then-ALTER path the table's other columns use. A row written by an older binary carries no anchor, and the resume declines an anchorless header rather than guessing — so a stream interrupted under v0.148.x and re-run under this release behaves exactly as it did before, including its refusal. No position or manifest format changes, and no new flags.

`sync status`, `sync health` and the `diagnose` bundle gain fields but no removals. `--reset-target-data`, `--restart-from-scratch` and `--force-cold-start` are unchanged and still take precedence over the resume: an operator who asks for a fresh copy gets one.

## Who needs this

Anyone who has ever stopped a `sluice sync start` mid-cold-start on a PostgreSQL source and paid for it in a full re-copy. Anyone running a cold start from MySQL, MariaDB, PlanetScale, Vitess, SQLite or D1 who has been staring at `sync status` reporting nothing. **And anyone who read v0.148.0's advice that a climbing progress age means the run is dead — it does not, and acting on it kills healthy migrations.**
