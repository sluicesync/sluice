# sluice v0.156.10

**HIGH silent-loss fixes: a column type change that `sync` missed is no longer rounded into the old target column at exit 0 (GC-44).** On v0.99.45 through v0.156.9, a type change could be made while a sync was stopped, or after it restarted and before the table's next row. Schema forwarding took that change as the new baseline and never applied it. A widened `DATETIME`, `DECIMAL`, `FLOAT` or Postgres `timestamp`/`numeric` precision therefore left the target's narrow column in place, and every later value was rounded into it. Each table's first schema boundary after a start is now checked against the target catalog. The check applies the difference, keeps a wider target with a WARN, or stops with `RESUME-SCHEMA-DIVERGENCE`. Streams that forward no DDL had the same loss for every schema change. These are `--schema-changes=refuse`, multi-database and multi-schema streams, and `--inject-shard-column` with `--no-coordinate-live-ddl`. They now check every boundary and stop with `SCHEMA-CHANGE-REFUSED` (GC-44 F5). Also fixed: a Postgres `timestamp(0)` → `timestamp(6)` (and `time`, `timestamptz`, `timetz`) on a running stream was never forwarded (GC-44 F3). **Upgrading does not repair rows that were already rounded.** Read **Who needs this** before you upgrade, because one check works only before the upgrade. **Not a silent drop-in:** streams that forward no DDL can now stop where they used to run on. See **Compatibility**.

## Fixed

**`sync`: a schema change made while the stream was stopped, or after a restart and before the table's next change, now reaches the target or stops the stream with `RESUME-SCHEMA-DIVERGENCE` (HIGH, silent loss; GC-44).** Schema-change forwarding classifies each schema boundary against the last shape it saw for the table. After a warm resume, a restart, a `sync run` leg restart or an automatic retry after a transient error, it had seen nothing. So the table's first boundary was cached as the new baseline, recorded as schema history, and never applied to the target. The same shape was also skipped by the ADR-0091 seed guard at the first boundary after a cold start. A type widen within its family left the target's narrow column in place, and every following value was rounded into it at exit 0: `DATETIME` → `DATETIME(6)`, `DECIMAL(10,2)` → `DECIMAL(12,4)`, `FLOAT` → `DOUBLE`, or a Postgres `timestamp` or `numeric` precision. This was measured on MySQL 8.0 in file/pos and GTID mode, MariaDB 11.4, Postgres 16 and vttestserver. A `VARCHAR` widen or an `ADD COLUMN` failed loudly at the next row instead.

That first boundary is now compared with the target table itself, column names and types only:
- A match changes nothing.
- Columns the target lacks are added and backfilled, with the same `ADD-COLUMN-BACKFILL-INCOMPLETE` guarantee as a live `ADD COLUMN`.
- One column the source widened within its family is altered.
- A column the target already holds wider is kept with a WARN. Wider means within the family, or across families where the target's type holds every source value: `TEXT` for `VARCHAR`, a wide-enough `NUMERIC` with a non-negative scale for an integer, a wider signed integer for an unsigned one, or an `ENUM`/`SET` label superset. `CHAR` across families and `jsonb` for `json` never count as wider.
- Columns only the target has are kept with a WARN.
- Anything else stops the stream with `RESUME-SCHEMA-DIVERGENCE`, naming each column with both types, before anything after the boundary is applied. That covers a possible rename, more than one changed column, a cross-family change the target does not hold, and a decimal widened on one axis and narrowed on the other.

A first boundary narrows the target only when the stream's retained schema history proves the source narrowed. That proof is possible only on a MySQL or MariaDB binlog source, where the boundary must lie strictly after that history version in the source's own position order. A narrowing back to a shape the table held before also counts. Without that proof, a target wider than the source is kept with a WARN, because it cannot be told apart from a target someone widened on purpose. With `--inject-shard-column` (Shape A), a difference the check forwards goes through the shard-consolidation lease, so a change made on every shard's source while the fleet was stopped is applied once. A column a peer shard added is backfilled on every shard's rows from that shard's own source.

On MySQL and MariaDB binlog sources, a sync now also produces a schema boundary at each table's first change after every start, as Postgres and VStream sources already did. Before this, a DDL whose position the stream had already persisted past was never checked at all. For example: the DDL ran, a write to an excluded table committed after it, then the stream restarted. A column named by `--type-override` is compared here by presence only, because its type is the operator's.

The check records nothing, so the next start checks again. Every new behaviour is pinned end to end:
- `TestTWFBFamilyMatrix_MySQLToPostgres` and its five sibling engine-pair matrices, plus the PostGIS arms: no phantom forward, refusal or WARN for any type each pair maps.
- `TestTWFB_OperatorWidenedTarget_PostgresToPostgres` and `TestTWFB_OperatorWidenedTarget_MySQLToPostgres`: a wider target is never narrowed.
- `TestTWFB_SourceNarrowedWhileStopped_MySQLToPostgres`: a proven narrowing is forwarded.
- `TestShapeAFirstBoundary_RoutesThroughTheLeaseOnce` and `TestPhase2e_PG_FirstBoundaryPeerAddedColumn_BackfillsEveryShard`: the Shape A behaviour.

**Affected releases:** v0.99.45 through v0.156.9 (schema forwarding on by default). The opt-in `--forward-schema-add-column` was affected from v0.79.0, and `--inject-shard-column` (coordinated Shape A) from v0.73.1.

**Streams that forward no source DDL now check every schema boundary against the target and stop with `SCHEMA-CHANGE-REFUSED` instead of passing it unchecked (HIGH, silent loss; GC-44 F5).** Four kinds of stream forward nothing:
- `--schema-changes=refuse`
- a MySQL multi-database stream (`--all-databases`, `--include-database`, `--map-database`)
- a Postgres multi-schema stream
- `--inject-shard-column` with `--no-coordinate-live-ddl` (Shape A's drained model)

None of them checked schema changes either. A boundary went straight to the applier, which recorded it as history and carried on. The Postgres reader's own mid-stream gate covers only a relation it has already seen in the same session. So a change made while the stream was stopped got through on every source, and on a binlog source any change at all. The help text said refuse mode refuses source DDL. In fact a `DATETIME` → `DATETIME(6)` or `numeric(10,2)` → `numeric(10,4)` was rounded into the target at exit 0. This was measured on MySQL 8 and Postgres 16 under `refuse`, and on a MySQL 8 multi-database stream. A Postgres multi-schema stream was worse: it produced schema boundaries only for the schema the source DSN names, so in every other selected schema even a change made while the stream ran went unchecked. It now produces boundaries for every selected schema.

Every boundary is now compared with the target, column names and types:
- A match passes.
- A target column that holds every value the source can send passes with a WARN. This is the drained model: the target was changed ahead of the source.
- A column only the target has passes with a WARN.
- A source column the target lacks, or a type the target's column cannot hold, stops the stream with `SCHEMA-CHANGE-REFUSED`. The refusal names each column with both types, and fires before the boundary is recorded or any row after it is applied.
- If the stream's own earlier shape of the table proves the source narrowed a column, the stream stops with `SCHEMA-CHANGE-REFUSED` and the type is marked `narrowed from …`. The source's `ALTER` rounded the rows it stores, but the target's copies were never rounded. The earlier shape comes from the table's last boundary in this run or from its retained schema history.
- The same evidence refuses a `DROP COLUMN` the target still holds, named as the likely `RENAME COLUMN` when a new column comes with it.
- A Postgres column replaced under the same name, which a changed `attnum` shows, is also refused.

A `--type-override` column is judged on width. A source type that outgrows the override refuses. The override's own deliberate narrowing passes while the source type is unchanged since the table's last accepted shape or the cold start.

Nothing is recorded. Every start compares the target again, so the stream resumes once the target holds the change. MySQL and MariaDB binlog sources on these streams also produce the first-touch boundary described above. Pinned by:
- `TestStreamer_RefusePinMatrix_MySQLToPostgres`, `TestStreamer_RefusePinMatrix_MariaDBToPostgres` and `TestStreamer_RefusePinMatrix_PostgresToPostgres`
- `TestStreamer_MultiDatabaseRefuse_MySQLToPostgres` and `TestStreamer_MultiDatabaseRefuse_PostgresToPostgres`
- `TestStreamer_RefuseSourceNarrowing_PostgresToPostgres`
- `TestStreamer_RefuseNarrowBack_MySQLToPostgres`
- `TestStreamer_RefuseOverride_MySQLToPostgres`
- `TestJudgeUnforwardedColumns_EveryFamilyBothDirections`

**Affected releases:**
- `--schema-changes=refuse`: v0.99.45 through v0.156.9.
- MySQL multi-database `sync`: v0.99.16 through v0.156.9.
- Postgres multi-schema `sync`: v0.99.24 through v0.156.9.
- Shape A's drained model: v0.72.0 through v0.156.9 (opt-in through `--no-coordinate-live-ddl` since v0.73.0).
- Every single-database `sync` before v0.99.45 that did not pass `--forward-schema-add-column`.

**Postgres sources on those streams: a boundary sluice cannot tell from a replay refuses as `AMBIGUOUS-SCHEMA-BOUNDARY`, and can be acknowledged once (part of GC-44 F5).** Postgres schema boundaries are anchored at LSN `0/0`, and their schema history keeps one shape per table (GC-44 F23). So consider a transaction that wrote rows, ran `ADD COLUMN` (or a widen) and wrote again, and that was re-delivered after a restart or an automatic retry. Its pre-`ALTER` relation looks exactly like a source narrowing or `DROP COLUMN` made while the stream was stopped. Accepting the second would be silent loss, so the stream still stops with `SCHEMA-CHANGE-REFUSED`. The refusal now also carries `AMBIGUOUS-SCHEMA-BOUNDARY`, names both readings, and does not offer a remedy that destroys data.

First compare the source's current table definition with the target's. A match is consistent with a replay but does not prove one: a column narrowed and widened back, or dropped and re-added, while the stream was stopped also matches. So also confirm that nobody ran DDL on that table while the stream was stopped. If both hold, start once with `--accept-unforwarded-schema-change=<fingerprint>`. If not, re-copy the table. The fingerprint covers the table, the refused columns and the position the stream resumed from. It therefore accepts only the replay re-delivered from that position. A later boundary of the same shape, such as a genuine narrowing after the stream applied past the replay, gets a different fingerprint and refuses even if the flag is left in a unit file. Within one process, the value is dropped as soon as a retry resumes from a later position. Pinned by `TestAmbiguousAck_BoundToTheResumePosition`, `TestStreamer_AmbiguousAckConsumedOncePastTheReplay` and `TestStreamer_RefuseCrashReplayAddColumn_PostgresToPostgres`. The last of these acknowledges a 50,000-row replay exact, then refuses a genuine `DROP COLUMN` made while stopped under the stale fingerprint.

**Postgres sources: the pre-`ALTER` replay wedge now names itself (`PRE-ALTER-REPLAY-WEDGE`) and prints a recovery that works (GC-44 F24, loud, no data loss).** This applies to the four kinds of stream above that forward no DDL, including Shape A under the coordinated router. On those streams the Postgres reader refuses an `ALTER COLUMN TYPE`, `DROP COLUMN` or `RENAME COLUMN` on a table it has already seen in the session, as it did through v0.156.9. Take a source transaction that writes a table, changes a column and writes the table again. It is refused on its first delivery and again on every restart, whatever the target holds, because each replay caches the pre-`ALTER` relation first. Nothing the transaction wrote after the `ALTER` reaches the target. Rows it wrote before the `ALTER` may already be there, and the recovery re-applies them. The reader's refusal now carries `PRE-ALTER-REPLAY-WEDGE` when the refused relation's transaction had already written the table. It names the recovery for each case, and no longer offers the deprecated `--forward-schema-add-column`. Recovery, after applying the change to the target:
- **A type widening on a stream over a single database and schema, without `--inject-shard-column`:** start once with `--schema-changes=forward`, then return to `refuse`.
- **Any other change, or a multi-database or multi-schema stream:** drop the replication slot with `sluice slot drop`, then start once with `--restart-from-scratch`.
- **`--inject-shard-column`:** first delete this shard's rows from each in-scope target table, then drop the slot, then start once with `--restart-from-scratch`. The shard preflight's hint now names the shard column, the value and the schema-qualified table rather than rendering a statement. Never use `--reset-target-data` here: it drops every sibling shard's rows.

Each recovery is pinned end to end, with rows read back exact and the stream resuming in its own mode. Pinned by `TestStreamer_WedgeRecovery_SingleDatabase_PostgresToPostgres`, `TestStreamer_WedgeRecovery_MultiSchema_PostgresToPostgres`, `TestStreamer_WedgeRecovery_ShapeA_PostgresToPostgres`, `TestStreamer_RefuseMidTransactionAlter_PostgresToPostgres` and `TestWithPreAlterReplayWedge`. The wedge itself is unchanged from v0.156.9 and stays open (see **Known residuals**). Only the marker and the recovery text are new.

**Postgres sources: `ALTER COLUMN … TYPE timestamp(6)` on a `timestamp(0)` column of a running stream is now forwarded (HIGH, silent loss; GC-44 F3).** The same fix covers `timestamptz`, `time` and `timetz`. The Postgres comparison lens put bare, `(0)` and `(6)` in one precision class. So the change classified as no change, the target kept `(0)`, and every following value was rounded to whole seconds at exit 0. This was measured on postgres:16 for all four types. Now only bare and `(6)`, which store the same values, share a class. Pinned by `TestNormalizeForCDCComparison_TemporalZeroIsNotInTheClass`. **Affected releases:** v0.99.176 through v0.156.9, the releases that create a declared `(0)` as `(0)` on the target. Before v0.99.176 a declared `(0)` was created bare on the target.

**`schema diff` and the `migrate` pre-create shape gate now predict what a MySQL-family target declares for some types (low).** That covers a bare Postgres `numeric` (`DECIMAL(65,30)`) and a MariaDB source's native `UUID`, `INET4` and `INET6` (`CHAR(36)`, `VARCHAR(45)`). The GC-44 family matrix found these. With the old prediction, the new first-boundary check would have forwarded a phantom `ALTER` (the numeric) or refused (the MariaDB types) on every resume of such a stream. Pinned by `TestMaterializedDecimalMatchesTheEmitter` and `TestMaterializedNetworkTypesMatchTheEmitter`.

**`KEY-SCOPED-WRITE-MATCHED-MULTIPLE-ROWS` no longer says the source transaction "WAS split" when nothing of it was committed (LOW, loud, no data loss; Bug 295).** On `--apply-concurrency 1`, a Postgres source emits a table's schema snapshot at the table's first row, inside that row's transaction, and the batch loop commits the snapshot on its own. v0.156.9 counted that commit as part of the transaction. So a refusal of the transaction's first statements said the transaction was split and the table held a state the source never had, while the target actually held the clean pre-transaction state. Every apply path now decides a split by one rule, `ir.WritesSourceStatement`. An applied row change or an applied Truncate of the transaction is a split. A schema snapshot, or a change skipped because its target table is absent, is not. A Truncate committed inside the transaction now counts as a split on the batch loop and on the per-change path (`--apply-batch-size 1`), as it already did on the lanes. The remedy, `--reset-target-data`, is unchanged. Pinned by `TestRunBatchLoop_KeyScopedRefusalNamesTheSplit`, `TestOrchestrator_KeyScopedRefusalNamesTheSplit`, `TestGC42_SchemaSnapshotInsideTheTransaction` and `TestGC42_TruncateInsideTheTransaction`. The last two run on real Postgres, across both privilege modes and all four apply paths. **Affected releases:** v0.156.9, which introduced the "WAS split" note.

## Known residuals

These GC-44 items are filed and open. Read them before relying on the new checks.

- **F23: on a Postgres forward-mode stream (`--schema-changes=forward`, the default), a column narrowed on the source while the stream was stopped is still kept with a WARN.** The target is not narrowed, and its existing rows keep values the source's `ALTER` rounded. Postgres schema history cannot prove that a boundary comes after its earlier shape, so the narrowing cannot be told from a crash replay. Pinned as the residual by `TestTWFB_SourceNarrowedWhileStopped_PostgresToPostgres`. If you see the WARN `the target column is WIDER than the source's`, narrow the target or re-copy the table.
- **F24 and F26: the pre-`ALTER` replay wedge is loud and stays open.** A forward start cannot pass a `DROP COLUMN` or `RENAME COLUMN` wedge (F26), so for those the re-copy is the only recovery.
- **F22: a `DROP` plus `ADD` of the same column name and type, both made while the stream was stopped, is not seen.** The target keeps the old column's values. Within one run it is caught.
- **F16, F17 and F20: some changes made while the stream was stopped are not seen.** These are a geometry SRID that only one side declares (F16), a column collation change (F17), and `interval(p)` precision (F20).
- **F19: a live Postgres `char(n)` → `varchar` change inside a transaction that also wrote rows before the `ALTER` can leave those rows padded on the target.** This is pre-existing and measured.
- **F25 and F15: some type pairs refuse on every start instead of passing (loud).** These are `char(n)[]` against a `text[]` target (F25), and a MySQL `TEXT` → `MEDIUMTEXT` that was forwarded and then replayed (F15).
- **Under `--schema-changes=forward`, a `--type-override` column is compared by presence only at the first boundary**, so an override changed between runs is not seen there.
- **Shape A: a column a peer shard added keeps the holder's fill on this shard's rows** when the stream retained no schema-history version of the table.
- **Also open:** F2, F6 through F12 (F12 is the schema-history growth listed under **Compatibility**), F18 and F21. They are listed in `docs/dev/audit-backlog.md`.

## Compatibility

**New stops on streams that forward no DDL.** `--schema-changes=refuse`, MySQL multi-database, Postgres multi-schema and `--inject-shard-column --no-coordinate-live-ddl` streams now stop with `SCHEMA-CHANGE-REFUSED` (codeless, exit 1) at a schema change the target cannot hold. Through v0.156.9 they ran on and rounded the values. A refusal can also carry `AMBIGUOUS-SCHEMA-BOUNDARY`. The first start after upgrading also checks each table's first change, so a change made long ago that the target never received refuses at that point. To recover, apply the change to the target and restart with the same `--stream-id`.

**New stop on forwarding streams.** A first boundary that the target cannot be reconciled with now stops with `RESUME-SCHEMA-DIVERGENCE` (codeless, exit 1). Before, it was accepted silently. A first boundary can now also apply an `ADD COLUMN` (with backfill) or an `ALTER` on the target at startup, logged at INFO as `forwarding the difference (target-witnessed, GC-44)`.

**The fleet supervisor does not restart the new refusals.** Under `sluice sync run`, a leg that stops on `RESUME-SCHEMA-DIVERGENCE` or `SCHEMA-CHANGE-REFUSED`, including the AMBIGUOUS case, is marked `failed` and the other legs keep running. A restart would read the same source and target and refuse again. The fleet spec has no acknowledgement key, so start an AMBIGUOUS leg once outside the fleet. The Postgres reader's mid-stream refusal that carries `PRE-ALTER-REPLAY-WEDGE` is not on that list, so a wedged leg is restarted and refuses again each time; that is unchanged from v0.156.9 and filed as GC-44 F27. Alert on a leg that keeps restarting with that marker and apply the recovery above.

**MySQL and MariaDB binlog `sync` streams now emit a first-touch schema boundary**, at each table's first change after every start. This applies in every schema-changes mode.

**Schema-history growth (GC-44 F12).** Each first-touch boundary writes an ADR-0049 schema-history row per touched table, per start at a new position. A Postgres multi-schema stream now writes history for every selected schema instead of only the DSN's own. Nothing compacts a sync stream's history. A long-lived, often-restarted stream can therefore pass the 10,000-row warm-resume read sooner, and that read logs a WARN that it may be incomplete. No value is lost.

**Message changes.** The Postgres reader's mid-stream schema refusal adds the `PRE-ALTER-REPLAY-WEDGE` text and drops the `--forward-schema-add-column` suggestion. The Shape A shard preflight's `sync` hint changes wording. `KEY-SCOPED-WRITE-MATCHED-MULTIPLE-ROWS` keeps its "may" wording where nothing of the transaction committed, and names the split after a committed Truncate. Markers and codes are unchanged.

**Otherwise a drop-in.** No flag was removed or renamed, and no control-table or backup-format schema changed. `--accept-unforwarded-schema-change` gains one meaning: it now also accepts an AMBIGUOUS fingerprint. VStream sources (PlanetScale, Vitess) were measured for the forward-path fix on vttestserver. Under the refuse and drained-model check they are covered by the same code but were not measured.

## Who needs this — action required

**Upgrading stops new rounding. It does not repair rows already rounded on the target.** One check below must run before the upgrade.

- **Every `sync` with schema forwarding on, on v0.99.45 through v0.156.9 (v0.79.0 with `--forward-schema-add-column`; v0.73.1 with `--inject-shard-column`), that resumed through a column type change.** A stream is exposed if it changed a column's type on a synced table while it was stopped, or between a restart and that table's next change. A restart includes a `sync run` leg restart and an automatic retry. Changes made right after a cold start are also exposed. **Before upgrading**, run `sluice schema diff` and compare each target column's declared type with the source's. Where the source's type is wider, the rows written since the change hold rounded values, and the remedy is to re-copy the table. **If you already upgraded**, the first start applies the difference itself, so a later diff is clean and proves nothing. Instead, grep that first post-upgrade start's log for `forwarding the difference (target-witnessed, GC-44)`. Every hit whose `difference=` names a type change marks a column whose earlier rows were rounded, and that table needs the same re-copy.
- **Every `--schema-changes=refuse`, MySQL multi-database, Postgres multi-schema or `--inject-shard-column --no-coordinate-live-ddl` stream, on any release before this one, that changed a column type on the source without first changing it on the target.** This also covers any single-database `sync` before v0.99.45 without `--forward-schema-add-column`. On a Postgres multi-schema stream it also covers changes made while the stream ran in any schema other than the DSN's own. Compare declared types with `sluice schema diff`, and re-copy any table where the source's type is wider. After the upgrade the stream refuses at the first such table until the target holds the change. Apply the change there, then restart.
- **Postgres-source streams that ran `ALTER COLUMN … TYPE timestamp(6)` (or `timestamptz`, `time`, `timetz`) on a `(0)` column, on v0.99.176 through v0.156.9.** The target column is still `(0)`, and every value since the change was rounded to whole seconds. Alter the target column, then re-copy the table or the affected rows.
- **Anyone who gets `AMBIGUOUS-SCHEMA-BOUNDARY`.** Do not change the target until you have compared the definitions and ruled out DDL made while the stream was stopped. Then acknowledge the printed fingerprint or re-copy the table, as the refusal says.
- **`sluice sync run` fleet operators.** Alert on `failed` legs. The new refusals do not restart-loop.
- **Bug 295 (v0.156.9 only).** A "WAS split" note on a refusal whose transaction's first statements were refused may have been false. The remedy is the same either way. Nothing to check.
- **Everyone else:** upgrade, nothing to check.
