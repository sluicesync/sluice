# sluice v0.160.1

**HIGH fix — on v0.159.0 through v0.160.0, `sync from-backup` replayed every incremental with the key-collation guard unarmed, so a key the target compares more loosely than the source (a Postgres key into a MySQL-family `_ci` column, or a target key loosened by hand) could merge two source rows into one at broker exit 0, where live `sync start` refuses the same row (KEY-COLLATION-BROKER-UNARMED). The broker now arms the guard from each incremental's recorded schema and refuses `KEY-COLLATION-MERGE` with the target untouched. This release also stops a mydumper or pscale-dump import creating a binary- or case-sensitive-collated column under the target's default collation (MEDIUM; MYDUMPER-COLLATION-NO-CHARSET), and stops MySQL and SQLite expressions that name an upper- or mixed-case column failing on a Postgres target with SQLSTATE 42703 (MEDIUM, loud; GitHub #356). Drop-in: no flag, default, error-code or backup-format change. If you run a broker into a MySQL-family target, read Who needs this.**

## Fixed

- **`sync from-backup` now checks key collations on every incremental it replays, instead of applying all of them unchecked (HIGH, silent; KEY-COLLATION-BROKER-UNARMED, wider than filed; v0.159.0 through v0.160.0, every release with the key-collation guard).** The appliers' `KEY-COLLATION-MERGE` guard arms from the source's schema, which reaches them as schema versions in the change stream. A live `sync start` and a chain restore deliver those versions; the broker replays a chain's incrementals as source events only, so its guard had nothing to arm from and stayed off for every incremental, not only one that changed a collation. The backlog had filed this as a narrow window case. Measured on Postgres 16 → MySQL 8.0, with a UNIQUE key beside the primary key on the Postgres default collation (case-sensitive), which MySQL creates under `utf8mb4_0900_ai_ci`: an incremental inserting `'A'` beside an existing `'a'` overwrote row 1's key and dropped the new row, at broker exit 0. Live `sync start` refuses the same row. The broker now hands the applier each incremental's recorded schema before replaying it, through a new optional applier surface, `ir.GuardSourceShapeSeeder`, held in memory and never persisted. That shape is sound for the whole window because the broker already refuses any window whose recorded versions disagree with it on a key collation (`KEY-COLLATION-HISTORY-UNORDERED`). A MySQL-family manifest records its tables without a namespace while its rows name the database, so a seeded shape with no namespace answers for its table under any namespace (the Bug 306 trap). A broker that would have merged now refuses `KEY-COLLATION-MERGE` with the target untouched; give the target's key column a binary collation, as the message says, and restart the broker. Pinned by `TestSyncFromBackup_PostgresToMySQL_SteadyStateKeyCollationMerge` and `TestSyncFromBackup_MySQLSteadyStateKeyCollationMerge` (real servers, with the source rows by `HEX(k)` as the expected value) and `TestSeededShapes_NamespaceRule`. Mutation-checked: with the broker's seeding disabled, both integration tests merge at exit 0; without the namespace-less fallback, only the MySQL one does. **Still open:** a `pgtrigger` source records no schema versions either, so its live sync and chain restore into a MySQL-family target are unguarded in the same way (KEY-COLLATION-TRIGGER-CDC-NO-HISTORY). **Affected releases:** v0.159.0 through v0.160.0. v0.159.0 introduced the key-collation guard; earlier releases have no guard on any path.
- **A mydumper or pscale-dump import no longer creates a binary- or case-sensitive-collated column under the target's default collation (MEDIUM; MYDUMPER-COLLATION-NO-CHARSET, wider than filed; every release with the mydumper reader).** A dump carries `SHOW CREATE TABLE`, which spells a column's collation two ways the parser did not resolve. MySQL 8 prints a column that inherits a `utf8mb4_bin` table default as `COLLATE utf8mb4_bin`, with no charset; the parser carried that collation without its charset, the MySQL writer took it for another engine's collation name and dropped it with a WARN, and the column was created under the target's default, typically `utf8mb4_0900_ai_ci`. MariaDB prints such a column with no collation at all and names it only on the table line, which the parser never applied to columns, so the column took the target's default silently, with no WARN. A key that was case-sensitive on the source became case-insensitive on the target: a fresh import of rows such as `'a'` and `'A'` refused with a duplicate key (measured through a real `mydumper` dump), and since v0.159.1 the copy writer's key-collation guard made a resumed import refuse rather than merge. Non-key columns compared and sorted under the wrong collation with no error at all. The parser now derives a column's charset from its collation, and gives a column that declares neither the table's charset and collation, as the server did. A table line with a charset and no collation (a `latin1` or `utf8mb3` table, or any MySQL 5.7 dump) leaves the collation to the target, because the charset's default collation depends on the source server. Pinned by `TestParseCreateTable_ColumnCollationsResolveLikeTheServer` (both measured server spellings), `TestParseCreateTable_CollationOnlyColumnFeedsTheCharsetGate`, and the `binary-collated-key-keeps-its-collation` leg of `TestMydumperIntegration_RealDumpEndToEnd` (a real mydumper 1.0.3 dump of a MySQL 8 `utf8mb4_bin` table into MySQL: the key keeps `utf8mb4_bin` and both rows land). Mutation-checked: without the charset derivation, that leg refuses with a duplicate key; without the inheritance step, the MariaDB cases fail.
- **A MySQL functional index, generated column or CHECK constraint, or a SQLite partial-index predicate, that names a column spelled in upper or mixed case no longer fails on a Postgres target with `column "…" does not exist` (MEDIUM, loud; GitHub #356; long-standing).** MySQL and SQLite resolve a column name inside a stored expression case-insensitively, and MySQL keeps a functional index's expression as typed, so `KEY (plant, (lower(status)))` over a column named `STATUS` is valid there. sluice strips the source's identifier quotes when it reads an expression, and Postgres folds every unquoted identifier to lower case, so the expression reached Postgres naming a column that does not exist and the CREATE failed with SQLSTATE 42703 — even when the case matched exactly (`Price * Qty` over `Price` and `Qty`). Only an all-lower-case column name worked. A generated column or CHECK failed at CREATE TABLE. A functional index failed at the index phase, after the whole copy, so a `sync start` cold start stopped holding every row with no CDC position (reported as `SLUICE-E-INDEX-TARGET-MISSING`). The Postgres writer now resolves every bare column reference in a cross-dialect expression against the table's columns, case-insensitively as the source does, and emits the column's real name, quoted when Postgres would otherwise fold it; a plain index key part spelled differently from its column resolves the same way. Words the grammar takes bare stay bare even when a column shares the name — including `LEADING`, `TRAILING` and `BOTH` inside `TRIM(…)`, where quoting would be valid Postgres that trims a column's characters and so silently changes a generated column's values. The pre-tag review found that case in this fix; the older reserved-word pass did the same to a lower-case column named `leading`, `trailing` or `both`, and both are closed (`TestRequotePGReservedIdents_TrimKeywordsStayGrammar`). `schema diff` translates a CHECK's expected side the same way, so it does not report the quoted form as drift. **Recovery:** a stream that already failed this way refuses a plain re-run with `SLUICE-E-COLDSTART-TARGET-NOT-EMPTY`; after upgrading, re-run it with `--reset-target-data --yes` (verified: the copy, the index and CDC all complete). Pinned by `TestMigrate_MySQLToPostgres_MixedCaseColumnExpressions` (real MySQL 8.0 and Postgres: the reported index shape, an exact-case functional index, a generated column, a CHECK and a lower-case control), `TestCrossDialectExpressions_ResolveColumnCase` (all four expression sites, MySQL and SQLite dialects), `TestEmitCreateIndex_FunctionalKeyPartResolvesColumnCase` and `TestRequoteIdentifiers_ResolvesColumnReferences`. Mutation-checked: with the column binding removed, the integration test fails at CREATE TABLE; with only the index site unbound, it fails at the index phase with the reported error.
- **Internal, no operator impact:** CI's `pipeline-rest-other` integration shard was split (the `TestRenameSwap*` and `TestChain*` families moved to their own shard) to stay inside its time budget, and a timing flake in the backup-stream severed-tail test fixture was fixed by waiting for delivery instead of sleeping.

## Compatibility

**Drop-in.** No flag, default or error-code change, and no backup format change (`BackupFormatVersion` stays 14). **The behaviour changes:**
- **`sync from-backup` may now refuse `KEY-COLLATION-MERGE`** where it previously merged silently, on a pairing the guard covers. The target is untouched when it does; give the target's key column a binary collation and restart the broker.
- **A mydumper `COLLATE latin1_bin` column in a `utf8mb4` table is now recognised as latin1,** so the mydumper charset gate refuses it as it refuses every non-UTF-8 column. It was imported as utf8mb4 before. Columns that inherit a binary or case-sensitive table collation now keep it on the target, so a key that was case-sensitive on the source stays case-sensitive.
- **Cross-dialect expressions on a Postgres target now carry quoted column names** where the column's real name is not all lower case. `schema diff` accounts for this, so it is not reported as drift.

**Not affected:** live `sync start` and chain restore by the broker fix (they already armed the guard), and broker pairings whose target key compares as the source's does; non-mydumper sources by the mydumper fix; MySQL and SQLite targets by the #356 fix (both match column names case-insensitively).

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale), `d1verify` (live Cloudflare D1) and `nekiverify` (live Neki) suites, which need live, billable infrastructure.

## Who needs this — action required

- **Anyone who ran `sync from-backup` on v0.159.0 through v0.160.0 into a MySQL-family target from a Postgres source, or into a target whose key columns were loosened by hand.** The target may hold one row where the source holds two, at broker exit 0. **Check:** on a quiesced pair, run `sluice verify` (row counts); every merge shows as a mismatch. **Action:** upgrading does not repair rows that already merged. A merged table needs a target key whose collation keeps the two values apart (a binary collation such as `utf8mb4_bin`, which the refusal message names) before it can hold both rows again, and then its rows copied from the source. A plain `--reset-target-data` re-copy is not enough on its own: it recreates the key under the target's default collation, so the copy refuses `KEY-COLLATION-MERGE` again rather than merge. From this release the broker refuses instead of merging.
- **`pgtrigger`-source operators syncing or chain-restoring into a MySQL-family target:** still unguarded (KEY-COLLATION-TRIGGER-CDC-NO-HISTORY, open). Check such targets with `sluice verify` until it is fixed.
- **Anyone who imported a mydumper or pscale-dump dump of a MySQL 8 table with a binary or case-sensitive collation (`utf8mb4_bin` and similar), or any MariaDB dump whose table line names a collation.** The target columns may carry the target's default collation instead. **Check:** compare the target columns' collations (`information_schema.COLUMNS.COLLATION_NAME`) with the source's. **Action:** re-import the affected tables with this release, or alter the target columns to the source collation (a case-insensitive key may refuse that `ALTER` if it already holds rows that differ only by case; re-import then).
- **MySQL or SQLite → Postgres users with an upper- or mixed-case column named in a functional index, generated column, CHECK constraint or partial-index predicate.** Those migrations and cold starts failed loudly; nothing was lost. **Action:** upgrade and re-run; a `sync start` that stopped at the index phase needs `--reset-target-data --yes`.
- **Everyone else:** upgrade.
