# sluice v0.156.1

> **Corrections (found by the post-release regression cycle, 2026-09-25).** (1) **Bug 288 (HIGH, silent):** "a character DEFAULT holding a character outside the BMP now reaches the target intact" holds for **literal** defaults only. A MySQL 8.0/8.4 source's **expression** default (`DEFAULT ('…')`) holding **any** non-ASCII character is read double-encoded from `information_schema` (`é` lands as `Ã©`) on `migrate`, cold start and forwarded `ADD COLUMN`, to MySQL and Postgres targets. v0.156.1 also newly carries such a default onto `TEXT`/`JSON`/`BLOB` columns of MySQL targets, where earlier releases dropped it. Copied and backfilled rows are byte-exact; the harm is the target's DEFAULT for inserts made there after cutover (and pre-existing rows under `--no-backfill-added-column`). MariaDB and Postgres sources are unaffected. Until the fix ships, compare `HEX(DEFAULT(col))`/`pg_get_expr` on the target against the source for expression defaults with non-ASCII text. (2) **Bug 289:** a restart refused on `ADD-COLUMN-BACKFILL-INCOMPLETE` printed "apply the same change to the target" as step (1); for this refusal the repair is to copy the added column's values from the source, as the Compatibility section below says. If you acknowledged it after applying only a target change, repair those rows from the source. Both are fixed on `main` for the next release.

**CRITICAL fix — a forwarded `ADD COLUMN` no longer leaves the rows already on the target holding the wrong value.** On a Postgres or PlanetScale/Vitess source, `sync` added the column without its DEFAULT, so every pre-existing target row held NULL (`NOT NULL` columns included) where the source held the default, at exit 0. On every source, a DEFAULT that was dropped or changed after the `ADD COLUMN` — which is what Django's `AddField` does every time — or a non-constant one left those rows with the target's fill instead of the source's values. This release carries the DEFAULT, turns the ADR-0058 backfill **on by default** so the target's pre-existing rows are filled from the source's own values, makes backup chains capture the same fill, and closes five further silent DEFAULT/label losses on MySQL-family paths. It also corrects the notes of v0.155.1 and v0.156.0 (Bug 287). **Not quite drop-in:** the backfill costs one pass over each altered table and the stream waits behind it, and several shapes that used to pass silently now refuse loudly — read **Compatibility**. Upgrading does not repair rows written wrong by an earlier release; read the repair notice below.

## Repair notice — if you were affected

Upgrading stops the loss; it does not find or fix rows an earlier release already wrote. The target cannot tell you which rows are wrong by looking at them — the wrong value is also what a legitimately defaulted row would hold — so every repair below compares against the **source**. In each case, "repair the column" means: update that column, on the target rows that existed when the column was added, from the source's values (key by primary key), or re-copy the table.

1. **`sync` from a Postgres or PlanetScale/Vitess source that forwarded an `ADD COLUMN … DEFAULT`, on v0.156.0 or earlier (CRITICAL, silent).** Every row the target held when the column was added holds NULL instead of the default. Affected: v0.99.45 through v0.156.0 (forwarding is on by default since ADR-0091), and the opt-in `--forward-schema-add-column` of v0.79.0–v0.99.44 when run without `--backfill-added-column`. Set the target column's DEFAULT to the source's (`ALTER TABLE … ALTER COLUMN … SET DEFAULT …`) and repair the column.
2. **`sync` from ANY source (Postgres, MySQL, MariaDB, PlanetScale/Vitess) that forwarded an `ADD COLUMN` whose DEFAULT was dropped or changed afterwards, or was non-constant, on v0.156.0 or earlier (CRITICAL, silent).** This is Django's `AddField` with a default (`ADD COLUMN … DEFAULT 'v'` then `DROP DEFAULT`), a later `SET DEFAULT`, or a `now()`/`gen_random_uuid()`/`CURRENT_TIMESTAMP` default dropped or changed before sluice reached the `ADD COLUMN`. The pre-existing target rows hold the target's fill (NULL, the newer default, or the target's own evaluation) instead of the values the source filled them with. Same release range as item 1. Repair the column.
3. **`sync --inject-shard-column` (Shape A fan-in).** Items 1 and 2 apply to every shard's pre-existing rows on the consolidated target, on every release with the Shape A router (first shipped v0.73.0) through v0.156.0. Additionally, on a MySQL-family source the router forwarded a volatile DEFAULT (`CURRENT_TIMESTAMP`, `JSON_OBJECT()`, …) that the single-stream path refuses, so every pre-existing row got the target's own evaluation of it. Repair the column for every row of every shard that was on the target when the column was added.
4. **Backup chains (`backup incremental`, `backup stream`) that captured an `ADD COLUMN` window, restored by chain restore or `sync from-backup`.** Restored rows that predate the `ALTER` hold the window-end DEFAULT rather than what the source filled them with: NULL after Django's dropped DEFAULT, the new value after a changed one, the restore's clock for `now()`. A chain captured by v0.156.0 or earlier does not contain the fill, and this release cannot reconstruct it from that chain (it names the non-constant cases under `ADD-COLUMN-FILL-NOT-REPRODUCIBLE` on restore; a Django-style dropped DEFAULT is invisible to it). **Take a fresh full backup after upgrading**, and repair any target already restored from such a chain against the source.
5. **MySQL-family targets and MySQL-family sources — five narrower silent losses, each fixed here:**
   - **A `TEXT`, `BLOB`, `JSON` or `GEOMETRY` column with a DEFAULT, written to a MySQL, MariaDB or PlanetScale/Vitess target.** The DEFAULT was dropped. On `migrate`, `sync` cold start and `restore`, later inserts that omit the column got NULL; on a forwarded `ADD COLUMN`, every pre-existing target row got NULL. Set the DEFAULT on the target and repair the column where it was forwarded.
   - **A MariaDB source with a `BINARY`/`VARBINARY` DEFAULT containing a byte at or above `0x80`** (every release reading MariaDB sources, v0.99.268 onward). Each such byte landed as `0x3F` (`?`). Correct the target DEFAULT and repair the column where it was forwarded.
   - **Any MySQL, MariaDB or PlanetScale/Vitess source with a character DEFAULT holding a character outside the Basic Multilingual Plane** (an emoji, a CJK extension ideograph). The character landed as `?` (MariaDB `TEXT`: `????`) in the target DEFAULT on `migrate`, cold start, restore and forwarded `ADD COLUMN`. Check with `SELECT HEX(DEFAULT(col))` against the source, correct the DEFAULT, and repair rows that took it.
   - **A Postgres unconstrained `numeric` column added mid-stream, forwarded to a MySQL target.** It was created as `DECIMAL(0,0)`, so its DEFAULT and every value carried into it afterwards were truncated to an integer. Re-copy the table or copy the column from the source (and widen the column: this release forwards it as `DECIMAL(65,30)`).
   - **An `ENUM`/`SET` value whose label holds a character outside the BMP, streamed by CDC from MySQL, MariaDB or PlanetScale/Vitess.** A row holding `'😀b'` landed as `'?b'`. Compare the column against the source and repair the rows.
6. **The Bug 287 correction** (below): a MariaDB binlog source that forwarded an `ADD COLUMN … DEFAULT` on v0.99.271–v0.155.0, or a MySQL binlog source that forwarded an `ADD COLUMN` with a `BINARY`/`VARBINARY` default containing a NUL byte on v0.155.1 or earlier, left the rows already on the target with the wrong default — the notes for those fixes said the rows were intact. Correct the DEFAULT and repair the column.

## Changed

**`sync`: after a forwarded `ADD COLUMN`, the rows the target already held are now filled from the SOURCE's values by default (CRITICAL, silent).** The forward reads the column's DEFAULT when the boundary reaches it — after a Django `DROP DEFAULT` — so for every dropped, changed or non-constant default the target filled its existing rows with something the source never held. The ADR-0058 §1c backfill, opt-in since v0.79.0, now runs after every forwarded `ADD COLUMN`: it pages the table on the source by primary key, reading only the key and the added columns, and writes each row's value ahead of every change that follows the boundary, so a row updated after the `ALTER` still ends at its updated value. It covers single-stream forwarding from Postgres, MySQL, MariaDB and PlanetScale/Vitess sources and the Shape A fan-in, where each shard's stream fills only its own shard's rows. The trigger-CDC sources (postgres-, sqlite- and d1-trigger) emit no schema snapshot, so they forward no `ADD COLUMN` and have nothing to backfill; a multi-database stream does not forward DDL. A non-constant DEFAULT the source still declares when the `ADD COLUMN` reaches sluice is still refused (ADR-0058 §2a), not backfilled. The stream waits behind the backfill, which logs its start, a progress line every 30 seconds, and its row count. Opt out with `--no-backfill-added-column` (fleet key `no-backfill-added-column`; the rows keep the target's fill and a WARN names each column). `--backfill-added-column` is now a deprecated no-op that logs a notice.

Four defects in the backfill itself are fixed with it, and they affected anyone who opted in on an earlier release: on a Postgres table with `REPLICA IDENTITY FULL` — required for every filtered `--where` sync — it keyed each `UPDATE` on the replica identity, which under FULL includes the column being filled, so every `UPDATE` matched nothing and the rows stayed NULL at exit 0 (it now keys on the source catalog's primary key, `TestRunBackfill_ReplicaIdentityFullKeyIsNotTheKey`); a page whose read failed part-way was taken for the end of the table; its rows were encoded against the pre-`ALTER` table (a refused array on Postgres, `BIT(8)` written as text on MySQL); and on a PlanetScale/Vitess source it refused every table as keyless, because the VStream field event carries no key.

**An interrupted backfill now refuses on every restart under `ADD-COLUMN-BACKFILL-INCOMPLETE`, instead of resuming past it with the rest of the table unfilled.** A restarted stream never sees the `ADD COLUMN` again, and the resume ADR-0058 described was never built (measured: stopped 12 rows into a 60,000-row backfill, the restart left 59,989 rows NULL at exit 0). So a run that ends before the backfill provably reached the target — a stop or Ctrl-C during it, a failed read, an apply error — ends with `ADD-COLUMN-BACKFILL-INCOMPLETE`, recorded like `UNFORWARDED-SCHEMA-CHANGE` in `sluice_cdc_state.unforwarded_refusal`, and every restart refuses until you repair the rows and start once with `--accept-unforwarded-schema-change=<fingerprint>`. A hard kill (SIGKILL, OOM, power loss) is covered too: the owed backfill is written to that record **before** the `ALTER` is applied (`schema_forward_backfill_ledger.go`), and cleared only by a compare-and-clear once the backfill is proven durable on the target — checked every 10 seconds while running (`watchAddedColumnBackfillDurability`) and again at stop. A record that cannot be written refuses the `ADD COLUMN`. The record is conservative, so a hard kill in the seconds after a backfill completes, or after an `ALTER` that failed, also refuses on restart. Not covered: on the Shape A fan-in, a hard kill after a peer shard's `ALTER` has filled this shard's rows and before this stream has seen its own `ADD COLUMN`. Pinned by `TestStreamer_AddColumnBackfill_InterruptedRefusesOnRestart_PostgresToPostgres` and `TestStreamer_AddColumnBackfill_HardKillRefusesOnRestart_PostgresToPostgres`, plus per-lane backfill pins for Postgres, MySQL, MariaDB, VStream, Postgres → MySQL and a two-shard Shape A.

## Corrected

**Correction (Bug 287): the wrong-DEFAULT fixes in v0.155.1 (Bug 286) and v0.156.0 (GC-29) also left rows ALREADY ON THE TARGET silently wrong, and their notes said those rows were intact.** When the forwarded `ADD COLUMN` ran on a Postgres target, Postgres filled every existing row with the column's DEFAULT — the wrong one. The source filled its own existing rows with the declared DEFAULT, but that fill writes no binlog row event, so CDC never corrected the target's copy. Measured by the v0.156.0 regression cycle: on v0.155.1 a forwarded `VARBINARY(4) DEFAULT 0xFF00` / `BINARY(3) DEFAULT 0xFF00AA` left the pre-existing target rows at `ff` / `ff0000` against the source's `ff00` / `ff00aa`; on v0.155.0 a MariaDB source left them holding the four-character string `NULL` and `'abc'` with its quotes. Rows written after the `ADD COLUMN` carry explicit values and were correct, as stated; the sentences "Rows are intact" and "Replicated rows were always correct" were wrong about the rows that already existed. The v0.155.1 and v0.156.0 archived notes carry this banner. v0.156.0 lands the declared DEFAULT, so the existing rows are filled correctly from there on; the repair for earlier runs is item 6 above.

## Fixed

**`sync` from a Postgres or PlanetScale/Vitess source: a forwarded `ADD COLUMN … DEFAULT` now lands the default (CRITICAL, silent).** Neither change stream carries a column's DEFAULT — pgoutput's relation message and the VStream field event have no field for it — and the forward added the column without one, logging only a WARN. The forward now reads the default through the source schema reader, the same value a cold-start `migrate` emits (`carrySourceDefaults`), and refuses if that read fails. MySQL and MariaDB binlog sources were already carrying the default in-band and are unchanged. Found by a new gate that grades every pre-existing target row against the source across every default family and seven lanes (`TestStreamer_AddColumnForward_PreexistingRowDefaults_*`), with `TestCarrySourceDefaults` as the unit pin.

**`sync --inject-shard-column` (Shape A) from a Postgres or PlanetScale/Vitess source: the same fix on the fan-in router (CRITICAL, silent).** The router built its `ADD COLUMN` from the change stream's projection. It now reads the default through the stream's own source schema reader, and refuses if that read fails or if the reader will not open at start. The router also gains the ADR-0058 §2a volatile-DEFAULT refusal it never had, and the carried default is folded into the lease checksum the shards compare (`leaseDDLTextWithCarriedDefaults`), so shards whose sources declare different defaults for the same added column refuse with a checksum mismatch instead of the first shard's default filling every shard. Pinned by `TestRouteBoundary_AddColumn_CarriesTheSourceDefault`, `TestRouteBoundary_AddColumn_VolatileDefaultRefuses`, `TestRouteBoundary_AddColumn_PeerWithADifferentDefaultRefuses` and `TestRouteBoundary_NothingCarriedKeepsTheLeaseText`.

**Backup chains now capture the `ADD COLUMN` fill (CRITICAL, silent).** An `ADD COLUMN … DEFAULT` fills every source row without writing a row event, so no link carried it and replay let the target fill the rows from the window-end schema. Both capture lanes (`backup incremental`, `backup stream`) now, once a window that added a column closes, read the added columns back from the source keyed by primary key and write them into the same incremental as ordinary updates that replay after every event of the window (`captureAddColumnFill`, `incremental_add_column_fill.go`; logged per table as `recorded the ADD COLUMN fill`). No format change: schema hash, backup ids and format version are unchanged, and a v0.156.0 binary was measured restoring such a chain to the same rows on Postgres and MySQL. A table with no primary key is logged at capture under `ADD-COLUMN-FILL-NOT-CAPTURED`. The restore-side WARN `ADD-COLUMN-FILL-NOT-REPRODUCIBLE` now fires only where the fill is genuinely missing: a skipped table, or a chain captured by an older sluice whose added column has a DEFAULT sluice cannot prove constant. Values are read when the window closes, so a row changed after the window's end carries its newer value one link early; a whole-chain restore is exact. Pinned by `TestIncrementalBackup_ChainRestore_AddColumnDefaults` on Postgres and MySQL, each through `backup incremental` and `backup stream`, plus `TestSmart_AddColumnFill_SurvivesCollapse` for smart compaction.

**MySQL 8.0.13+, MariaDB and PlanetScale/Vitess targets: a DEFAULT on a `TEXT`, `BLOB`, `JSON` or `GEOMETRY` column now lands, instead of being dropped (CRITICAL, silent on a forwarded `ADD COLUMN`).** The writer now reads the server version and emits the parenthesised `DEFAULT (…)` form, translated per value family; a string holding a quote, backslash or control character is spelled `CONVERT(UNHEX('…') USING utf8mb4)` on MySQL, because MySQL re-parses a stored expression default under the next session's `sql_mode` (`MYSQL-EXPRESSION-DEFAULT-BACKSLASH`). A default that still cannot be carried (older MySQL, a geometry literal, an array of an unsupported element family) is dropped from `CREATE TABLE` with the WARN `LOB-DEFAULT-NOT-CARRIED`, and on a forwarded `ADD COLUMN` now **refuses** with `SLUICE-E-VALUE-UNREPRESENTABLE` before the `ALTER`. Pinned by `TestAlterAddColumn_LOBDefault_FillsPreexistingRows` and `TestAlterAddColumn_LOBDefault_RefusedWhenTheServerCannotHoldIt`.

**MariaDB sources: a `BINARY`/`VARBINARY` DEFAULT keeps its bytes at or above `0x80` (CRITICAL, silent).** MariaDB 10.6–11.4 stores a quoted binary default in utf8mb3 catalog text with every non-UTF-8 byte replaced by `0x3F`, so `DEFAULT 0x00AB00` landed as `0x003F00` on `CREATE TABLE` and on a forwarded `ADD COLUMN`. Both MariaDB catalog readers now re-read such a default through a `DEFAULT()` probe and refuse loudly on any disagreement with the catalog text; the unforwarded-schema-change door compares on the same true bytes. MariaDB 11.8+'s lossless `x'…'` literal is recognised too.

**MySQL, MariaDB, PlanetScale and Vitess sources: a character DEFAULT holding a character outside the BMP now reaches the target intact, instead of as `?` (silent).** `information_schema.COLUMN_DEFAULT` is utf8mb3 on both servers. A default that reads back with a `?` is now re-read — `SELECT HEX(CONVERT(DEFAULT(col) USING utf8mb4))` on MySQL and MariaDB, `SHOW CREATE TABLE` on PlanetScale and Vitess — and must agree with the catalog text or the schema read refuses, naming the column; a genuine `?` stays `?`. A mydumper dump of a MySQL source spells such defaults as `0x…` literals, which now decode (`TestParseCreateTable_HexTextDefault`). Refused rather than guessed: such a default on a non-UTF-8 column charset on PlanetScale/Vitess, and an `ENUM`/`SET` default using such a label. Not recoverable: a mydumper dump of a MariaDB source, whose `SHOW CREATE TABLE` already holds the `?`.

**`sync` and `backup stream` from MySQL, MariaDB, PlanetScale or Vitess: a row whose `ENUM`/`SET` value uses a label containing a character outside the BMP now stops the stream with `ENUM-LABEL-NOT-RECOVERABLE`, instead of landing as `?` (silent).** The binlog identifies an ENUM value by position and a SET by bitmask, and sluice named them through the catalog, which writes such characters as `?`; VStream does the same mapping inside vttablet. On a binlog source running `binlog_row_metadata=FULL`, sluice now reads the true labels from each row event and applies them (measured faithful on MySQL 8.0 and MariaDB 11.4); otherwise, and always on VStream, a row using such a label stops the stream naming the table, column and label. Only rows that use such a label are affected. A label that genuinely is `'?'` on a `utf8mb4`/`utf16`/`utf32` column cannot be told apart and is refused the same way unless the source runs `binlog_row_metadata=FULL`. Pinned by `TestEnumLabelLoss_MySQL_FullMetadataRecovers`, `TestEnumLabelLoss_MariaDB_MinimalMetadataRefuses` and siblings, and `TestRefuseVStreamLostLabel`. See `docs/operator/migrating-legacy-mysql.md`.

**`sync` from a Postgres source: an unconstrained `numeric` column added mid-stream forwards as `NUMERIC` (MySQL: `DECIMAL(65,30)`), not precision 0 (silent on a MySQL target).** The change stream carries a bare `numeric` with no type modifier, and the reader decoded it as `NUMERIC(0,0)`; a Postgres target refused the `ADD COLUMN`, a MySQL target accepted `DECIMAL(0,0)` and truncated every value to an integer. The forward now emits exactly what a cold start emits. The same change fixes a bare `bpchar` (forwarded as `CHAR(0)`), and stops a `numeric(10,2)[]`/`varchar(n)[]`/`char(n)[]`/`timestamp(3)[]` array column from reading as altered at every boundary, which halted the stream at the first forwarded column on such a table.

**`sync` from a Postgres or PlanetScale/Vitess source: a change stream held back by a slow consumer no longer loses its connection (HIGH, loud).** On Postgres the reader sent standby status only from the loop that hands changes on, so a reader waiting on a full channel went silent and `wal_sender_timeout` dropped it; it now sends status every second while it waits, reporting the same applier-confirmed position it always reports (`TestCDCReader_BlockedConsumerKeepsTheWalsenderAlive`). On PlanetScale/Vitess, sluice's own stall watchdog ended a stream waiting on its consumer after 45 s; the reader now tells the watchdog it is waiting (`sendHeld`, `TestVStream_VTTestServer_BlockedConsumerIsNotAHungStream`). The reconnect was harmless before this release; with the default-on backfill it would have ended every large table's backfill as `ADD-COLUMN-BACKFILL-INCOMPLETE`.

**`sync` from a MySQL or MariaDB binlog source in GTID mode: a transaction the source re-sends after a reconnect is no longer applied twice (HIGH, loud).** When the binlog connection drops — a consumer held past `net_write_timeout`, or any network break — the MySQL client library reconnects on its own and, in GTID mode, resumes from before the newest transaction it had seen, so that transaction arrives again from its first row (measured: 101,936 of 150,000 rows of one transaction delivered twice). The repeat collided with rows the same transaction had already changed and stopped the stream on a duplicate key, and every restart stopped the same way. The reader now recognises a re-sent transaction by exact GTID and drops what it already delivered (`cdc_reader_resend.go`), logging `the binlog connection was re-established and the source re-sent …`. Measured end to end on MySQL → Postgres (serial and concurrent apply) and MySQL → MySQL: every row applied once (`TestStreamer_MySQLBinlogResend_GTID_MySQLToPostgres`, `TestStreamer_MySQLBinlogResend_GTID_MySQLToMySQL`, with `TestStreamer_MySQLBinlogResend_FilePos_MySQLToPostgres` as the unchanged control). File/pos mode (`gtid_mode=OFF`) repeated nothing and is unchanged; VStream, Postgres and the trigger-CDC readers do not reconnect this way. Not changed: a CRASH inside such a transaction still re-delivers it onto a target that applied its first rows (filed as GC-38).

**Two defects in this release's own backfill and chain fill, found by the pre-release value-fidelity review and fixed before it shipped (no earlier release affected).** The backfill's durability proof accepted a persisted position "at or after" the first change following the backfill; on a MySQL GTID or VStream source that position could already be durable while backfilled rows were uncommitted, so a kill in that window could restart past the boundary with rows unfilled. The proof is now strictly past the backfill (`TestStreamer_AddColumnBackfill_GTIDRecordHeldUntilTheBackfillCommits`); on a VStream source it waits for the next position-bearing change, and a stop with none refuses rather than completes. And chain restore at an apply concurrency above 1 could route a MySQL `UNSIGNED` `TINYINT`/`SMALLINT`/`MEDIUMINT`/`INT`-keyed row's window INSERT and its fill UPDATE to different lanes; the lane hash now encodes a key by value (`TestLaneKey_CopyReadAndBinlogRouteAlike`).

## Compatibility

**Behaviour changes an operator will hit — this is a patch, but it is not a silent drop-in for a stream that forwards `ADD COLUMN`:**

- **The added-column backfill is on by default.** Each forwarded `ADD COLUMN` now costs one pass over the table on the source (key plus added columns only) and one `UPDATE` per pre-existing row on the target — one round trip per row on a MySQL, MariaDB or PlanetScale target, where the updates are not yet batched. The stream applies nothing else while it runs; expect lag to grow on a large table and watch the 30-second progress lines. Opt out with `--no-backfill-added-column` (fleet key `no-backfill-added-column`) only if the target's fill is acceptable. `--backfill-added-column` still parses and does nothing.
- **`ADD-COLUMN-BACKFILL-INCOMPLETE` is a new recorded refusal.** Stopping a stream (Ctrl-C, `sync stop`, a supervisor restart) while a backfill runs, or a hard kill shortly after one, now makes every restart refuse until you repair the column and acknowledge with `--accept-unforwarded-schema-change=<fingerprint>`. A target `ALTER` that fails — even transiently — now stops the stream loudly: the record was written before the `ALTER`, so the automatic retry and every restart refuse until you check the column against the source and acknowledge. Plan schema changes so a stream is not stopped mid-backfill. `sluice sync run` treats it as it treats `UNFORWARDED-SCHEMA-CHANGE` and does not restart the leg.
- **Shape A (`--inject-shard-column`) refuses a volatile or unrecognised expression DEFAULT on a forwarded `ADD COLUMN`**, as single-stream sync always has, and now refuses at start if it cannot open a source schema reader.
- **Shape A shards must be upgraded together.** The carried DEFAULT is part of the lease checksum, so a fleet mixing v0.156.1 with an older binary refuses with a checksum mismatch on an `ADD COLUMN` whose default is carried. So do shards whose sources declare different defaults for the same column — deliberately.
- **A forwarded `ADD COLUMN` to a MySQL-family target whose `TEXT`/`BLOB`/`JSON`/`GEOMETRY` DEFAULT cannot be carried now refuses** with `SLUICE-E-VALUE-UNREPRESENTABLE` (`LOB-DEFAULT-NOT-CARRIED`) instead of forwarding without it. On `CREATE TABLE` it is still dropped with that WARN.
- **`ENUM-LABEL-NOT-RECOVERABLE` stops a MySQL-family stream** at the first row using an `ENUM`/`SET` label with a character outside the BMP, unless the binlog source runs `binlog_row_metadata=FULL`; VStream always refuses. Set `binlog_row_metadata=FULL` on the source to stream such rows faithfully.
- **Schema reads can refuse where they used to proceed**: a character DEFAULT whose re-read disagrees with the catalog, a MariaDB binary DEFAULT whose `DEFAULT()` probe disagrees, and on PlanetScale/Vitess a non-BMP DEFAULT on a non-UTF-8 charset or an `ENUM`/`SET` default using such a label.
- **MySQL/MariaDB GTID-mode streams** now drop a re-sent transaction after a silent reconnect and log it; nothing to configure.

**No format or control-table change.** The write-ahead record reuses v0.156.0's `sluice_cdc_state.unforwarded_refusal` column. The chain fill is ordinary change events; chains written by this release restore on v0.156.0 (measured), and the manifest's new optional fill record is ignored by older readers. An older binary compacting a new chain drops that record, which can only produce a spurious `ADD-COLUMN-FILL-NOT-REPRODUCIBLE` WARN for a column that restores correctly. Downgrading: v0.156.0 reads the same column and replays a recorded `ADD-COLUMN-BACKFILL-INCOMPLETE` like any other recorded refusal; a binary older than v0.156.0 ignores it and resumes past the owed backfill silently, so repair and acknowledge it before downgrading that far.

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale, billable cluster) and `d1verify` (live Cloudflare D1) suites were not dispatched; each provisions billable or live infrastructure and runs only on the operator's call. What that leaves unverified live: the VStream arms of this release — the carried DEFAULT, the backfill keyed from the source catalog, the watchdog's consumer-held signal, the `ENUM` lost-label refusal and the `SHOW CREATE TABLE` non-BMP re-read — were measured on vttestserver in the per-PR vstream integration job, not against PlanetScale; and the backfill ledger's reliance on a later VGTID advancing after the last `ADD COLUMN` is stated in the code as an UNVERIFIED PREMISE for PlanetScale deployments (if none arrives, a stop refuses rather than completes, so the failure mode is loud). No D1 path changed beyond the backfill's source reader opening lazily, so a d1-trigger source (which forwards no `ADD COLUMN`) is not refused at start. PlanetScale Postgres is a plain Postgres source, covered by the per-PR real-Postgres suites.

## Who needs this — action required

- **Anyone who ran `sync` (including Shape A) that forwarded an `ADD COLUMN` from a Postgres or PlanetScale/Vitess source on v0.156.0 or earlier**, or **from any source where that column's DEFAULT was later dropped or changed, or was non-constant** — every Django project adding a field with a default is in this set. Upgrade, then follow items 1–3 of the repair notice: compare each column added mid-stream against the source for the rows that existed when it was added, and repair. Anyone who opted into `--backfill-added-column` on an earlier release against a Postgres table with `REPLICA IDENTITY FULL` (every filtered `--where` sync) is in this set too: that backfill silently matched no rows.
- **Anyone with backup chains that span an `ADD COLUMN`.** Take a fresh full backup after upgrading; repair any target restored from such a chain (item 4).
- **MySQL-family targets that received a `TEXT`/`BLOB`/`JSON`/`GEOMETRY` column with a DEFAULT; MariaDB sources with `BINARY`/`VARBINARY` DEFAULTs holding bytes ≥ `0x80`; MySQL-family sources with a text DEFAULT holding a character outside the BMP; Postgres unconstrained `numeric` columns added mid-stream to a MySQL target; `ENUM`/`SET` labels with characters outside the BMP streamed by CDC.** Check and repair per item 5. For the last, also set `binlog_row_metadata=FULL` on the source, or streams will now stop at the first such row.
- **MariaDB binlog sources on v0.99.271–v0.155.0, and MySQL binlog sources with NUL-bearing binary defaults on v0.155.1 or earlier, that forwarded an `ADD COLUMN … DEFAULT`** (Bug 287): repair the pre-existing rows as well as the DEFAULT (item 6).
- **Anyone running Shape A**: upgrade every shard together.
- **Anyone with runbooks that stop streams during schema changes**: a stop mid-backfill now needs a repair plus an acknowledgement; wait for the backfill's completion line before stopping.
- **MySQL/MariaDB GTID-mode streams that stopped on a duplicate key after a connection drop**: this release prevents the re-send, but a stream already stuck that way restarts into the same collision (the unfixed crash shape above) and needs the affected table re-copied.
- **Everyone else**: nothing to do beyond upgrading.
