# sluice v0.159.1

**HIGH fixes: the copy phase's upserts could merge two source rows into one target row at exit 0, and v0.159.0's key-collation guard left two kinds of Postgres key unchecked. The release also adds new refusals, a new backup format tier and an open HIGH known issue in chain restore. Drop-in for streams and copies whose key collations agree on both sides; everyone else should read Compatibility, Known issues and Who needs this before upgrading.** (1) **KEY-COLLATION-ROWWRITER (HIGH, silent):** v0.159.0 guarded the CDC appliers, but the idempotent copy writer still upserted unchecked. It serves `schema add-table`, a resumed or chunk-resumed copy, `--force-cold-start`, the VStream COPY and restore of a rotated chain. Where the target key's collation equates two values the source keeps apart, the second row replaced the first, on MySQL-family and Postgres targets alike. The same class also reached MySQL's batched and LOAD DATA retry arms. (2) **Postgres keys left unarmed (HIGH, silent):** on a MySQL-family target, a key on a Postgres nondeterministic (ICU) collation merged at CDC apply and on every copy that upserts. So did any named Postgres key from a backup chain written before v0.159.0. (3) **Prefix keys (MEDIUM, silent):** the guard compared whole values where the server matches a prefix key (`UNIQUE KEY uk (k(5))`) on the prefix. (4) **Bug 304:** a backup segment that changes a key's collation is now stamped `FormatVersion` 13, so older binaries refuse it instead of merging rows. (5) **Bug 305:** MySQL 8 → MariaDB now creates NO PAD collations, so a `KEY-COLLATION-MERGE` re-copy converges. **Known issue, open:** this release's own chain restore can still merge rows from a window that changed a key's collation and changed it back (KEY-COLLATION-REVERTED-WINDOW-RESTORE). See Known issues.

## Fixed

**A copy that upserts no longer merges two source rows whose keys the target's collation equates (HIGH, silent; KEY-COLLATION-ROWWRITER).** The idempotent row writer is the copy path that tolerates a row already on the target. It serves `schema add-table`, a resumed or chunk-resumed copy, a `--force-cold-start` copy into a populated target, the VStream COPY (serial and fanned out) and restore of a rotated chain. A fresh first-pass copy uses the plain bulk path, which was already loud on a collision. Take a target key whose collation equates two values the source keeps apart: `'A'` and `'a'` on a `_ci` key from a `_bin` source, or a Postgres default-collation key on the `utf8mb4_0900_ai_ci` column sluice itself creates on MySQL, or a Postgres `"C"` key onto a nondeterministic ICU key on Postgres. There, the second row's upsert overwrote the first at exit 0. On a table whose every column is the key, the second row vanished instead. This was measured on MySQL 8.4, MariaDB 11.4 and Postgres 16, across a primary key, a UNIQUE key beside one, an all-key table and a UNIQUE key with no primary key, and both MySQL write cores: two source rows became one target row.

Both engines' idempotent writers now carry the appliers' in-statement guard, armed from the source's collation. A merge refuses with `KEY-COLLATION-MERGE` and the statement is rolled back. A re-sent row with the same source key, such as a resumed chunk, still converges. Unlike the applier, the copy also arms a Postgres default-collation or nondeterministic key inside the primary key. The guard is rendered once per table and the server evaluates it only on a conflict. On a 100k-row chunk the measured cost was within run-to-run noise on both engines, whether the rows were fresh or all conflicting.

The sibling sweep found the same class in the retry arms of MySQL's two plain write cores (the ADR-0108 reparent/storage-grow ride-out). After a transient, the batched core accepted a retry's duplicate-key error as its own lost-ack rows, and the LOAD DATA core counted a replay's duplicate-key skips the same way. So a retried batch holding `'A'` and `'a'` was dropped whole (batched) or lost `'a'` (LOAD DATA), at exit 0. Now, on a table whose key is compared differently on the two sides:
- **Batched core:** a retry that meets a duplicate key re-sends the batch as the guarded upsert (`replayArmedBatchAsGuardedUpsert`). A genuine lost-ack replay still converges on its own rows, and only a real merge refuses, with `KEY-COLLATION-MERGE`.
- **LOAD DATA core:** LOAD DATA has no upsert form. A replayed segment that skipped rows (rows inserted short of the segment, or a duplicate-key warning) refuses with the new marker `KEY-COLLATION-REPLAY-AMBIGUOUS`. A replay whose only warnings are something else, such as a clamp under `--mysql-sql-mode=''`, skipped nothing and passes.

Postgres's plain cores never tolerated a duplicate on replay and are unchanged. Pinned by `TestRowWriterKeyCollationGuard_MySQLFamily` (every source collation × key shape × serial and fan-out × MySQL 8.0 and MariaDB 11.4), `TestRowWriterKeyCollationGuard_Postgres` and `TestRowWriterKeyCollationGuard_PlainCoresWithholdTheReplayTolerance`. `TestKeyCollationRowWriter_CopyPaths` drives the orchestrator's copy paths with the real source readers, every cell graded by key bytes against the source. **Affected releases:** the idempotent writer every release from v0.4.0 through v0.159.0. The batched retry arm from v0.99.92 (where the ADR-0108 ride-out landed), and the LOAD DATA replay from v0.113.0 (segmented LOAD DATA), both through v0.159.0.

**A Postgres key on a nondeterministic collation is now checked on a MySQL-family target (HIGH, silent).** MySQL cannot declare an ICU nondeterministic key such as `und-u-ks-level2`, which keeps `'e'` and `'é'` apart, or a level-3 one, which keeps `'a'` and `'A'` apart. The cold start therefore creates the key under the target's default `utf8mb4_0900_ai_ci`, which equates both pairs. v0.159.0's guard armed every other Postgres key on such a target but left this one unarmed. The second row then reached an `ON DUPLICATE KEY UPDATE` onto the first and the two became one at exit 0, at CDC apply and on every copy that upserts. Such a key is now compared byte for byte. A nondeterministic collation equates more byte strings than byte equality does, never fewer, so two rows of a source unique key are always byte-distinct. A merge refuses with `KEY-COLLATION-MERGE`. The copy arms such a key in any key. CDC apply arms it in a UNIQUE key beside a primary key, and leaves the primary key itself unarmed, because arming it would refuse a re-delivered case-only change that converges today. A copy-time refusal on such a key names both readings of the conflict:
- if the source equates the two values, the target holds a stale row whose key changed between the copy's attempts, and a re-copy from scratch converges (a resume repeats the refusal);
- if the source keeps them apart, the target key needs a binary collation.

This was measured on Postgres 16 ICU → MySQL 8.0 at both levels, through `add-table`, the resumed and chunk-resumed copy and CDC apply; the writer was also measured on MariaDB 11.4. Pinned by `TestKeyCollationFirstBoundary_PostgresNondeterministicUniqueToMySQL`, the nondeterministic cells of `TestKeyCollationRowWriter_CopyPaths`, and the writer and applier matrices. **Affected releases:** CDC apply through v0.159.0. The copy phase from v0.4.0 through v0.159.0. On a Postgres target this arm does not apply: the Postgres applier already compared a nondeterministic source key under its own collation, and its copy is covered by the KEY-COLLATION-ROWWRITER fix above.

**A named Postgres key whose determinism nothing recorded is now checked in every key (HIGH, silent).** A manifest written before v0.159.0 carries no collation determinism. So every key of a Postgres-source backup chain from that era went unchecked on a cross-engine restore into MySQL, both on its rotated-segment copy and on its replay. A mydumper column declared with `COLLATE` alone was unchecked too. Such a key is now compared byte for byte in every key, including the primary key at apply. For example, a `COLLATE "C"` primary key holding `'A'` in the full and receiving `'a'` from an incremental now refuses instead of merging. The cost is loud and is the same known class as a stamped deterministic key: a re-delivered window in which a primary-key value meets a case or accent variant of itself on the target refuses `KEY-COLLATION-MERGE` where it would have converged. That covers a re-applied case-only change, or a delete and re-insert of a variant. Pinned by `TestPlanKeyCollationGuard` and the "determinism unknown" cells of `TestKeyCollationGuard_MySQLFamily` and `TestRowWriterKeyCollationGuard_MySQLFamily`. **Affected releases:** restore of a pre-v0.159.0 Postgres chain into a MySQL-family target, through v0.159.0. A key on the database default collation in such a chain still cannot be told apart from a source that records no collation, and stays unchecked (see Not covered).

**The key-collation guard now compares a prefix key part the way the server matches it (MEDIUM, silent).** On a MySQL-family target a UNIQUE or primary key can index only a column's first characters (`UNIQUE KEY uk (k(5))`), which sluice reproduces from the source. The server matches an upsert through such a key on the prefix alone, but v0.159.0's guard compared whole values. So `'Apple-1'` meeting `'apple-2'` on a `_ci` target key from a `_bin` source looked like two different keys, and the upsert overwrote the existing row at exit 0. The guard now reads each key part's prefix length from the catalog (`uniqueKeyColumns`) and compares that prefix on both sides, in characters, as MySQL and MariaDB define it. The merge now refuses with `KEY-COLLATION-MERGE`. This was measured on MySQL 8.0 and MariaDB 11.4, at CDC apply (both doors) and on the copy writer (both cores). Pinned by `TestKeyCollationGuard_PrefixKeyPartsCompareThePrefix` and by the prefix-key cells of `TestKeyCollationGuard_MySQLFamily` and `TestRowWriterKeyCollationGuard_MySQLFamily`. **Affected releases:** the v0.159.0 guard. Before v0.159.0 there was no guard at all, so the same merge falls under v0.159.0's KEY-COLLATION-FIRST-BOUNDARY entry. Postgres has no prefix keys.

**A backup segment whose window changed a key column's collation is now stamped so older binaries refuse it, instead of restoring it with rows merged (HIGH, silent on a downgrade; Bug 304).** v0.159.0 records a collation-only change to a primary-key or UNIQUE-key column in an incremental's schema delta, and restores it correctly. Examples are `MODIFY k … COLLATE utf8mb4_bin` on MySQL and `ALTER COLUMN k TYPE text COLLATE "C"` on Postgres. But the manifest kept its ordinary format version. A binary older than v0.159.0 read that delta as no change: it restored the table under the old collation and replayed the window onto it. A row the new collation keeps apart was merged at exit 0, and that binary's own `backup verify` passed. This was measured with v0.158.1 against v0.159.0 chains from MySQL 8.4 and Postgres 16. Such a segment is now stamped `FormatVersion` 13 (`FormatVersionKeyCollationDelta`), and every older binary refuses it at its version ceiling (`newer than this build supports`) before touching the target. The stamp is proportional. A full, a segment with no schema change, and a collation change outside every key keep their previous version.

Every `backup stream` and `backup incremental` commit now also stamps from the schema history the change stream recorded in its window (`stampKeyCollationHistory`). That reaches two segments that carry no delta:
- a `backup stream` stopped mid-window, whose drain commit skips the schema refresh;
- a window that changed a key's collation and changed it back before its end, observed live on MySQL 8.0.

It does not reach a VStream (Vitess/PlanetScale) segment, because VStream records no collation (KEY-COLLATION-VSTREAM-UNSTAMPED, below). The fix is not retroactive: a chain v0.159.0 already captured across a key-collation change carries no stamp. Restore such chains with v0.159.0 or later. Pinned cross-version against a real older binary by `TestBackup_CrossVersionKeyCollationDelta`, now a fourth suite in the `crossversion` leg. `TestSchemaDeltaWritersStampKeyCollation` and `TestCDCSegmentCommitsStampFromHistory` are AST rosters that fail any future commit path that does not stamp. Also pinned by `TestStampKeyCollationHistory`, `TestBackupStream_DrainCommit_StampsAKeyCollationWindow` and `TestBackupStream_KeyCollationChangedAndRevertedInsideTheWindowIsStamped`. **Affected releases:** chains captured by v0.159.0 that are restored with v0.158.1 or older.

**MySQL 8 → MariaDB now creates character columns under the NO PAD collation the source's means (MEDIUM, loud; Bug 305).** The MariaDB flavor used to create a MySQL 8 `utf8mb4_0900_ai_ci` column, and likewise `as_ci` and `as_cs`, as `utf8mb4_uca1400_ai_ci`. That collation is PAD SPACE: it equates `'a'` and `'a '`, which every 0900 collation keeps apart. v0.159.0's guard correctly refused the second row with `KEY-COLLATION-MERGE`. But its re-copy remedy rebuilt the same PAD SPACE key and failed on a duplicate entry, leaving a primary-key table empty and a UNIQUE-key table without its index. A cold copy of a source already holding both values failed the same way. The cold start now creates `utf8mb4_uca1400_nopad_ai_ci` and its `as_ci`/`as_cs` siblings (`0900_bin` was already `utf8mb4_nopad_bin`). These exist on every supported MariaDB. The change applies to every character column, not only keys, because a column can become a key later. MariaDB → MySQL maps the NO PAD forms back onto the 0900 set. A target an older sluice created keeps its PAD SPACE columns. The guard still refuses a merge into such a column, and its remedy now names the collation the key needs (`COLLATE utf8mb4_uca1400_nopad_ai_ci`, not the 0900 name, which MariaDB 10.11 lacks). `--restart-from-scratch` now recreates the key NO PAD and converges. This was measured on MySQL 8.4 → MariaDB 10.11 and 11.4, with PK and UNIQUE keys, under MINIMAL and FULL row metadata. Pinned by `TestKeyCollationFirstBoundary_MySQL84ToMariaDB_PadSpace`, `TestKeyCollation_MySQL84ToMariaDB_NoPadColdStart`, `TestEmitterRemapCreatesWhatTheGuardComparesUnder` and `TestKeyCollationMergeRemedy_NamesTheCollationThatConverges`. **Affected releases:** the remedy in v0.159.0. The cold-copy failure on a source holding `'a'` and `'a '` dates from the MariaDB flavor's collation remap (v0.99.268).

**`KEY-COLLATION-MERGE` remedies name the collation the key needs (MEDIUM, loud).** The copy writer's refusal said "a deterministic collation, or the source's". On MySQL that could name a collation the target cannot declare. Each refusal now names, per armed column, the collation the guard compared under, and says when a re-copy would not converge. That case is a key armed to compare bytes, where a re-copy recreates the target's equating default. Pinned by `TestCopyKeyCollationMergeRemedy_NamesTheCollationTheKeyNeeds` (MySQL) and `TestCopyKeyCollationMergeRemedy_NamesTheCollation` (Postgres).

## Compatibility

**Drop-in for streams, copies and chains whose key collations agree on both sides.** Those carry no check and render byte-identical statements. **The behaviour changes:**
- **A copy through the idempotent writer** (`schema add-table`, a resumed or chunk-resumed copy, `--force-cold-start`, the VStream COPY, restore of a rotated chain) now refuses with `KEY-COLLATION-MERGE`, before the merge is written, where it used to merge. If the target cannot express the source collation for the comparison, it refuses with `KEY-COLLATION-GUARD-UNSUPPORTED` before any row of the table is written. A copy resumed over a source whose key value changed case or accent between attempts can also refuse; the refusal names both readings.
- **LOAD DATA retries on a vanilla MySQL or MariaDB target:** on a table whose key is compared differently on the two sides, a replayed segment that skipped rows now refuses with `KEY-COLLATION-REPLAY-AMBIGUOUS`. That includes a genuine committed-but-unacked transient, which used to ride through. This is deliberate, because LOAD DATA cannot tell its own re-sent row from a second source row. Nearly every Postgres → MySQL text-keyed table is such a table. The batched path (PlanetScale/Vitess, and any target without LOAD DATA) still rides through, by re-sending as the guarded upsert.
- **A named Postgres key of unknown determinism** (a pre-v0.159.0 chain, or a mydumper `COLLATE`-only column) is now compared byte for byte in every key. A re-delivered window in which a primary-key value meets a case or accent variant of itself refuses where it used to converge.
- **A Postgres nondeterministic UNIQUE key beside a primary key**, on a MySQL-family target, is now checked at CDC apply.
- **MySQL 8 → MariaDB:** newly created character columns are NO PAD `uca1400` collations rather than PAD SPACE. On the target, `'a'` and `'a '` now compare as distinct, as they do on the source. Tables an older sluice created keep their PAD SPACE columns until re-created.

**Backup format: `BackupFormatVersion` is now 13.** A CDC segment whose window changes a key column's collation is written at `FormatVersion` 13. **Every older binary, v0.159.0 included, refuses such a segment** with `newer than this build supports; upgrade sluice`. Other segments and every full keep their previous version and stay readable by older binaries. So downgrading below v0.159.1 cuts off only chains that crossed a key-collation change. v0.159.1 reads every older chain.

**Markers, no new error codes:** `KEY-COLLATION-REPLAY-AMBIGUOUS` is new. `KEY-COLLATION-MERGE` and `KEY-COLLATION-GUARD-UNSUPPORTED` now also fire on the copy phase.

**Not affected:** SQLite and D1 targets, which use plain INSERTs and fail loudly on a collision. Postgres's plain write cores, which never tolerated a duplicate on replay. The fresh first-pass bulk copy, which is plain and was already loud.

## Known issues

- **KEY-COLLATION-REVERTED-WINDOW-RESTORE (HIGH, silent; open, fix in progress).** Chain restore can merge rows from a window that changed a key's collation and changed it back. This release's chain restore can land a merged row from such a window at exit 0. Measured on MySQL 8.0: a UNIQUE key `utf8mb4_0900_ai_ci` → `utf8mb4_bin`, a row `'A'` inserted beside `'a'`, then its key moved and the collation reverted. The restore left target row 1 holding `'A'` where the source holds `'a'`. That happened both for a live `backup stream` window (stamped 13) and for a `backup incremental` run made after the DDL (unstamped, since under the default `binlog_row_metadata=MINIMAL` the replay records only the current shape). The cause is that restore arms the guard from the window's last recorded shape, which equals the target's again. The same exposure is plausible for a `sync` stream resumed across such a window; that is unmeasured. **Affected releases:** v0.159.0 and v0.159.1. Before v0.159.0, chain restore had no key-collation handling at all; see v0.159.0's KEY-COLLATION-FIRST-BOUNDARY.
- **KEY-COLLATION-DRAIN-NO-DELTA (MEDIUM, loud; open).** A `backup stream` stopped mid-window whose window changed a key's collation produces a correct chain that this release cannot restore. The drain commit writes no schema delta, so the collation change reaches the target only with the next segment. The drain segment's rows replay onto the old key, and the guard refuses `KEY-COLLATION-MERGE` at that segment on every restore. Nothing merges. Older binaries refuse the segment at its stamp. The same lag affects any DDL in a drained window.
- **KEY-COLLATION-VSTREAM-UNSTAMPED (LOW to MEDIUM, silent on a downgrade only; open).** A VStream (Vitess/PlanetScale) segment is never stamped from its window's history, because VStream records no collation and a collation-only DDL changes nothing it does record. A VStream window that changed a key's collation and back therefore stays readable by older binaries, which can merge. This release does not guard it either: VStream sources carry no collation, so no key-collation check arms for them (unchanged from v0.159.0). A broader stamp was tried during review and withdrawn before release. It would have stamped virtually every VStream segment of a string-keyed table and cut older binaries off nearly every Vitess/PlanetScale chain.

**Not covered (filed in `docs/dev/audit-backlog.md`):**
- A Postgres-source chain written before v0.159.0 with a key on the database default collation, restored into MySQL, stays unchecked.
- A SQLite or D1 source key records no collation and is not armed.
- A functional key part (`UNIQUE ((lower(k)), x)`) is skipped by the guard (KEY-COLLATION-FUNCTIONAL-KEY-PART).
- A Postgres unique index that declares its own `COLLATE` over a column of another collation is not seen.
- A pre-created MySQL target key column whose name differs from the source's only in case is left unarmed.
- A target key re-collated by hand mid-run is compared under the cached plan until the writer or applier is reopened.
- A LOAD DATA segment that skipped rows can pass the replay gate when `@@warning_count` cannot be read and `max_error_count = 0`.
- A mydumper `COLLATE`-only key column is created under the target's default collation (MYDUMPER-COLLATION-NO-CHARSET). Its copy is now guarded.
- Restore of a rotated chain and the broker cold start have no end-to-end key-collation pin; the writer they call is pinned directly.

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale), `d1verify` (live Cloudflare D1) and `nekiverify` (live Neki) suites, which need live, billable infrastructure.

## Who needs this — action required

- **Anyone who copied a table through the idempotent writer where the target key's collation equates values the source keeps apart, on any release through v0.159.0.** That means `schema add-table`, a resumed or chunk-resumed `migrate` or `sync` cold start, `--force-cold-start`, a VStream COPY, or restore of a rotated chain. The commonest shape is **Postgres → MySQL/MariaDB/PlanetScale/Vitess with a text primary or unique key**, because sluice creates that key under `utf8mb4_0900_ai_ci`. Others are a MySQL `_bin` source onto a `_ci` target key, a Postgres nondeterministic key onto MySQL, and a Postgres key onto a nondeterministic Postgres target key. A retried batch after a reparent or storage-grow transient on such a table is affected too (batched from v0.99.92, LOAD DATA from v0.113.0). **Check:** the target is a row short for every merge, so `sluice verify` (row counts) on a quiesced pair reports a count mismatch. To find candidate collisions directly, group each key column on the source under the target's collation. On MySQL: `SELECT k COLLATE utf8mb4_0900_ai_ci AS kk, COUNT(*) FROM t GROUP BY kk HAVING COUNT(*) > 1`. On Postgres: `GROUP BY lower(k)`, as an approximation for a case-insensitive MySQL target. **Action:** re-copy each table that mismatches. Upgrading does not repair rows that already merged.
- **Anyone streaming a Postgres source with a nondeterministic-collation UNIQUE key into a MySQL-family target, on any release through v0.159.0.** Check and act as above.
- **Anyone who restored a pre-v0.159.0 Postgres-source chain into a MySQL-family target whose keys use a named collation** (for example `COLLATE "C"`). Check and act as above.
- **Anyone on v0.159.0 streaming into a MySQL-family target whose UNIQUE or primary key is a prefix key** (`k(N)`) with a collation that differs from the source's. Check and act as above, grouping on `LEFT(k, N)`.
- **Anyone who restored, with v0.158.1 or older, a chain that v0.159.0 captured across a key column's collation change.** That restore may have merged rows, and its `backup verify` would have passed. **Action:** re-restore with v0.159.1, or check as above. Do not restore such chains with older binaries; v0.159.1-captured ones now refuse there.
- **Anyone relying on a chain restore whose windows changed a key's collation and changed it back** (KEY-COLLATION-REVERTED-WINDOW-RESTORE, open). **Action until it is fixed:** after any such DDL sequence on a key, take a fresh `backup full`, and verify any restore spanning that window against the source (`sluice verify` row counts, or the collision query above).
- **MySQL 8 → MariaDB operators whose target tables an older sluice created** (PAD SPACE `uca1400` columns). Merges into them already refuse since v0.159.0. To adopt the NO PAD collations, re-copy with `--restart-from-scratch`, which now converges.
- **Operators who roll back binaries:** a chain that v0.159.1 stamped `FormatVersion` 13 is readable only by v0.159.1 and later.
- **Everyone else:** upgrade. Tables whose key collations agree on both sides need no action.
