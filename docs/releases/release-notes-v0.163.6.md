# sluice v0.163.6

**HIGH fix, silent: after a transient fault during a PlanetScale/Vitess cold start's copy, the target no longer keeps rows the source deleted while the copy reconnected (`VSTREAM-COPY-RECONNECT-STALE-ROWS`).** Since v0.99.5, a retriable error mid-copy (a dropped vtgate connection, a reparent) re-opened the VStream in place from the position the copy had reached. Vitess then replays the source's changes since the old snapshot as row events inside the copy phase, and sluice's copy keeps only after-images, so every DELETE in the reconnect window was dropped while updates landed, at exit 0. Measured through a fault proxy: 20 of 20 window deletes stale in every run of every affected cell. The in-place reconnect is removed: a fault now ends the copy and the stream's outer retry restarts it, clearing and re-copying on a first cold start and refusing loudly where it cannot clear. This changes a guard and ships alone. No flag change and no backup format change, but a mid-copy fault now costs a full re-copy and enough of them end the run (see Compatibility).

## Fixed

- **A mid-copy VStream fault restarts the cold start instead of reconnecting in place (`VSTREAM-COPY-RECONNECT-STALE-ROWS`, HIGH, silent).** The mechanism was confirmed with temporary debug logging: after the re-open, vtgate ran catch-up from the old snapshot GTID and sent the window's changes (60 deletes and 30 updates in the fault cell) to the copy dispatcher, none to the CDC pump, then copied the rest under a new snapshot. `bufferCopyRow` decodes only after-images, so each catch-up DELETE was dropped, and the CDC tail started at the later GTID. An uninterrupted copy has one snapshot per table and no copy-phase catch-up, and its CDC tail replayed all 80 deletes, which is why a copy without a fault was exact. Measured on vttestserver (MySQL 8.0 source, Postgres 16 target, one and two shards, a window of about 2.2 seconds): the `vstream_copy_single_stream` opt-out lost the deletes both in the table it had already finished, which it also copied again from its first row, and in the table the fault hit. The default per-table copy and a one-table scope lost them when the fault hit the first or only table, in the in-progress table's rows below the cursor and at its frontier. With a finished table first, the default path was exact only because the stitched-minimum CDC start reached back to that table's earlier snapshot. The three copy loops (`copyPump`, `pumpOneTableCopy`, `copyStream.pumpTable`) now return the classified Recv error, and `reconnectCopy` and `reconnectStream` are deleted. What happens next was measured with the reconnect disabled before the change was made. A first cold start's fault reaches the retry, which finds no position, clears the in-scope target tables and copies again from a new snapshot: exact in 8 of 8 cells (default, fault in the first table, one-table scope, single-stream; one and two shards). A re-copy of a stream that already reached CDC refuses `COLD-START-INCOMPLETE` instead, with `--restart-from-scratch` as the remedy: 6 of 6. Where the tables cannot be cleared the retry refuses: under `--schema-already-applied` with `RESTART-FROM-SCRATCH-TARGET-NOT-CLEARED`, now worded as "a fault during the copy made this run restart the copy" rather than naming a `--restart-from-scratch` you never passed; under `--inject-shard-column` the shard preflight refuses until this shard's rows are deleted. Pinned by `TestStreamer_VStreamCopyReconnectStaleRows` (vstream tag, no skips): every faulted first cold start must retry and land exact, including the concurrent copy at `vstream_copy_table_parallelism=2`; every faulted re-copy must refuse `COLD-START-INCOMPLETE` and then land exact under `--restart-from-scratch`; the no-fault controls must be exact. Also pinned by `TestVStreamSnapshot_MidCopyRecvErrorEndsTheCopy`: all three loops, retriable and non-retriable, end the copy, keep the retriability and never re-open the faulted table. A mutation that put the reconnect back turned both red, the integration cell with 20 of 20 stale rows.
- **A fault-restarted copy under `--schema-already-applied` refuses a partial target (`SAA-COLD-COPY-RETRY-UNCLEARED`, MEDIUM, silent before this release).** Found by this release's pre-tag review, because the fix above sends every mid-copy fault into this path. The case is a first cold start under `--schema-already-applied` from a PlanetScale/Vitess source whose copy faulted while the target's position read also failed. The retry deliberately does not latch a restart on a failed read, so it ran as a plain cold start, the schema-already-applied branch checked nothing, and the re-copy upserted over the interrupted copy, keeping the source's deletes in between, at exit 0. The retry now records that it restarted a copy it could not place past the cold copy (`coldCopyFaultRetried`), and the schema-already-applied branch then requires every in-scope target table to be empty: a populated table or a failed emptiness probe refuses. A run with no retry behaves as before. Pinned by `TestSAAColdCopyRetry_RefusesAPartialCopy`, `TestSAAColdStart_NoRetryIsUnchanged`, and the vttestserver cell `OneShard/SchemaAlreadyApplied`: a real mid-copy fault refuses with the fault wording, and emptying the tables and re-running lands exact. Disabling the check in that cell gave 20 of 20 stale rows: the silent upsert this prevents.
- **`schema add-table` and `backup full` from a PlanetScale/Vitess source now fail on a mid-copy fault instead of continuing the copy in place.** They read through the same copy loops. A failed `schema add-table` leaves its pending record, which refuses the next warm resume, and its re-run refuses the populated table: empty it and run the command again. A failed `backup full` fails; run it again. The backup had the same harm before this release: a reconnected snapshot held re-copied rows, lacked the window's deletes, and recorded a later end position. `migrate` never used this copy and is unaffected. The multi-database streamer refuses VStream sources and never reached it.

## Not closed, stated

- **`VSTREAM-SINGLE-STREAM-CATCHUP-DELETE-DROPPED` (OPEN, HIGH, silent, no fault needed).** It was found while measuring this fix and is filed in `docs/dev/audit-backlog.md`. With the `vstream_copy_single_stream=true` opt-out and more than one table, Vitess runs a catch-up before each table after the first, inside the copy phase, and the same after-image-only buffering drops a DELETE made on an earlier table while it was being copied. Measured with no fault: 60 of 60 deletes stale. Until its fix ships in its own release, use the default per-table copy.
- **The `--slot-name` copy-scope defect (OPEN, HIGH, silent).** Found by the review that follows this release and not yet fixed at this tag. A `planetscale` or `vitess` `sync start --slot-name X` opens a keyspace-wide copy that ignores `--include-table` and `--where` for the copied tables. Do not pass `--slot-name` to a PlanetScale/Vitess source; it has no meaning there. The fix ships in its own release.
- **`schema add-table` from a PlanetScale/Vitess source opens a keyspace-wide copy (severity ungraded, not measured).** The same review read this from the code. The add streams every other table of the keyspace while it drains only the new one. A large keyspace can refuse at `--max-buffer-bytes`, and a delete on the new table during the copy may meet the catch-up drop above. Whether that delete reaches the target depends on the mode, and it has not been measured.
- **`backup full` falls back to the non-snapshot copy, with a WARN and exit 0, on any snapshot-open error (OPEN, MEDIUM).** On PlanetScale/Vitess such a fallback has no consistent view and records an end position after the sweep. This is separate from the mid-copy fault above, which fails the backup.
- **A first cold copy never gets a fresh retry budget (`VSTREAM-COLD-COPY-RETRY-BUDGET-NEVER-CREDITS`, OPEN, LOW/MEDIUM, loud).** The cost is described under Compatibility. There is a proposal to credit a fresh budget when a restarted copy demonstrably makes progress. This release deliberately makes no retry-semantics change.
- **A new process re-run under `--schema-already-applied` after a stopped copy cannot know the tables hold a partial copy.** That flag is your statement that they are empty, so empty them before re-running. This is in the operator guide.
- **Not run for this release: `psverify` and `d1verify`.** Every measurement was on a local vttestserver cluster, not on PlanetScale itself. The cell that grades the `--inject-shard-column` refusal end to end, and a fault cell under `--where`, were not built.

## Compatibility

- **No flag change and no backup format change** (`BackupFormatVersion` stays 15). It is not drop-in in one respect: a PlanetScale/Vitess cold copy that meets a transient fault behaves differently.
- **Each mid-copy fault costs a full re-copy** of the in-scope tables, where before it cost a few seconds of reconnect.
- **During a first cold copy the retry budget never refills.** So after `--apply-retry-attempts` faults (8 by default, counted over the whole copy) the run exits with `apply retry budget exhausted` and the last fault in the message. At the default backoff (100 ms doubling), a vtgate outage longer than about 13 seconds uses all 8, and so do 8 separate blips over one long copy. The interrupted copy stays on the target, so a plain re-run refuses `SLUICE-E-COLDSTART-TARGET-NOT-EMPTY`. The remedy is the same command with `--restart-from-scratch`, or a higher `--apply-retry-attempts` to ride out more faults. Under `--schema-already-applied`, empty the in-scope tables first.
- **A PlanetScale reparent during the copy now restarts it**, and one that keeps vtgate unavailable for longer than the budget covers ends a first cold start.
- **Only `planetscale` and `vitess` sources are affected,** and only while copying: a first cold start, a re-copy, `schema add-table` and `backup full`. A stream that has reached CDC is unchanged, because its change stream has its own reconnect, which is not a copy reconnect. MySQL binlog, Postgres, SQLite/D1 and trigger-CDC sources are unaffected.

## Who needs this — action required

- **Anyone whose PlanetScale or Vitess cold start, on v0.99.5 through v0.163.5, logged `mysql/vstream: snapshot: COPY stream dropped; reconnecting in place from cursor`** (or its concurrent-copy form, `concurrent COPY stream dropped; reconnecting in place from cursor`). The in-place reconnect first shipped in v0.99.5 (ADR-0072 Phase C, commit `a00c217f`); the concurrent-copy loop carried it from v0.99.67. Every reconnect logged that WARN before re-opening, so a cold start that never logged it was not affected by this defect. One that did may hold rows the source deleted during the reconnect. To check, pause writes on the source, let the stream catch up, and run `sluice verify --depth count` against the same source and target (`--depth sample` refuses a PlanetScale/Vitess source). Stale deletes show up as a target count above the source's. Or skip the check and re-copy with `--restart-from-scratch`. Only current code was measured; earlier releases carried the same reconnect, but none was measured on its own.
- **Anyone whose `backup full` from a PlanetScale/Vitess source logged the same WARN:** that full may hold re-copied rows and lack the window's deletes, and its end position is later than the deletes. Take a new full.
- **Anyone whose `schema add-table` from a PlanetScale/Vitess source logged the same WARN:** it read the same copy loop, though that path was not measured. Compare the added table against the source or re-add it.
- **Anyone using `vstream_copy_single_stream=true` with more than one table:** switch to the default per-table copy until `VSTREAM-SINGLE-STREAM-CATCHUP-DELETE-DROPPED` ships its fix. That defect needs no fault.
- **Everyone else:** nothing to do.
