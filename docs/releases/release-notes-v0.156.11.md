# sluice v0.156.11

**HIGH and CRITICAL-class silent-data fixes: an interrupted `sync from-backup` no longer duplicates keyless rows, and a MySQL-family target no longer renumbers an `AUTO_INCREMENT` value of `0`.** (1) Audit F-E1: on v0.99.222 through v0.156.10, a `sync from-backup` broker interrupted partway through an incremental re-applied the whole incremental on its next run. Every row it had already committed to a keyless table, or to a table keyed only on a surrogate the rows do not carry, was written a second time at exit 0. On v0.20.0 through v0.99.221 the same interruption skipped the rest of the incremental instead. A `restore` re-run after a failed attempt duplicated the same way, on every release. Both now refuse before writing (`SLUICE-E-BROKER-KEYLESS-TABLE`, `SLUICE-E-RESTORE-KEYLESS-TABLE-NOT-EMPTY`), and a cancel mid-incremental now exits 1. (2) On every release through v0.156.10, a source row whose `AUTO_INCREMENT`-mapped column held `0` landed on a MySQL, MariaDB or Vitess target under the next generated value, at exit 0. sluice now forces `NO_AUTO_VALUE_ON_ZERO` on every MySQL session. **Upgrading does not repair rows already duplicated, skipped or renumbered.** Read **Who needs this**. **Not a silent drop-in:** keyless tables can no longer be replayed by `sync from-backup`, and several new refusals can fire on configurations that used to run. See **Compatibility**.

## Fixed

**`sync from-backup`: an interrupted incremental no longer duplicates the rows of a keyless table, and a cancel that interrupts one no longer exits 0 (HIGH, silent loss; audit F-E1).** The broker stamps every change of an incremental with the position of the incremental before it, and advances its position only once the whole incremental has applied. Those changes carry no apply identity, so ADR-0190's apply marks cannot skip any of them. Any interruption partway through an incremental (an apply error, a chunk that failed to fetch, a crash, a SIGINT or SIGTERM) therefore re-applies the whole incremental on the next run. A table with a PRIMARY KEY or NOT NULL UNIQUE index made of columns the replayed rows carry absorbs that, because the re-applied INSERT upserts on the key. A table with neither falls back to a plain INSERT, and gained a duplicate of every row the interrupted run had committed: measured on Postgres at 2,001 target rows for 1,001 source rows, in both the serial and lane apply modes, and 1,989 when every row was its own source transaction, so the window is the whole incremental. A target table keyed only on a column the rows do not carry (a `bigserial`, identity, `DEFAULT gen_random_uuid()`, MySQL `AUTO_INCREMENT` or `DEFAULT`-expression surrogate) duplicated the same way, because every re-applied row draws a fresh key value and collides with nothing (measured at 2,000 for 1,001). A SIGINT or SIGTERM, or `q`/ctrl+c on the live panel, made it worse: the broker treated the cancel as a clean stop and exited 0 even mid-incremental.

The broker now refuses with `SLUICE-E-BROKER-KEYLESS-TABLE` (exit 3) before it applies anything when any table the chain records has no such key. It checks on warm resume, before an `--at-chain-id` position write, before a `--reset-target-data` drop, and before each tick that brings a table not yet judged. A table already judged is judged again before any incremental whose schema change alters its definition. Each table is judged twice, and the message says which judgment failed:
- On the chain's recorded schema (`irbackup.TableReplayIdempotent`), which no longer counts a partial UNIQUE index, since a replayed row outside its predicate collides with nothing.
- On the live target (the new `ir.ReplayKeyProber`), which asks whether a re-written row actually collides. On Postgres, the `ON CONFLICT` arbiter the applier itself picks must be made entirely of columns the rows supply. On the MySQL family, some PRIMARY KEY or UNIQUE index of NOT NULL, non-generated columns must be fully supplied. On a multi-shard Vitess or PlanetScale keyspace, every primary-vindex column must also be supplied, because a key there is enforced per shard and a re-sent row without its routing column lands on another shard (measured on a 2-shard vttestserver: 7 of 16 re-sent rows landed as duplicates at no error). A generated key column never counts as supplied.

A cancel that lands while an incremental is being applied now returns an error carrying `BROKER-INCREMENTAL-PARTIAL` (exit 1). The message names the incremental and says the next run re-applies it. It also says when a re-run is the wrong recovery: an incremental that changed key values does not converge on a re-run, so a source that changes key values recovers with `--reset-target-data`. A cancel during a `--reset-target-data` cold start, once its drop has begun, returns `BROKER-COLD-START-PARTIAL` (exit 1), because the target then holds a partial restore and no position. A cancel between incrementals or between ticks, and `sync from-backup stop`, still exit 0. Pinned by `TestFE1_Broker_KeylessChain_RefusedBeforeAnything`, `TestFE1_Broker_SurrogateKeyedTarget_RefusedBeforeAnything`, `TestFE1_Broker_MySQLTarget_KeylessDoor`, `TestRowWriter_ProbeReplayKey_ShapeMatrix` (one per target engine, each shape graded against that engine's own measured re-write), `TestVStream_ProbeReplayKey_UnsuppliedPrimaryVindex`, `TestSyncFromBackup_ClearedTableLosesKeyLater_RefusedAtTick`, `TestSyncFromBackup_CancelMidIncremental_ExitsWithPartialMarker` and `TestSyncFromBackup_CancelDuringResetColdStart_ExitsWithPartialMarker`. **Affected releases:** duplication on v0.99.222 through v0.156.10, the releases that stream each incremental at its parent's position (audit BRK-1). On v0.20.0 through v0.99.221 an interrupted incremental was instead recorded as applied, and its un-applied rest was skipped, in any table.

**`restore` refuses to re-load a keyless target table that already holds rows (HIGH, silent loss; audit F-E1, the restore sibling).** Re-running a `restore` (a single full or a chain) onto a target an earlier attempt had already written re-wrote everything that attempt wrote. A keyed table failed loudly on its key. A keyless table, or one the target keyed only on a surrogate the backup's rows do not carry, silently held two copies of every row: measured at 2,001 for 1,001 on a Postgres chain re-run and 200 for 100 on SQLite. The new refusal `SLUICE-E-RESTORE-KEYLESS-TABLE-NOT-EMPTY` (exit 3) fires before anything is written when an in-scope table (after `--include-table` / `--exclude-table`) is keyless on either judgment above and already holds rows. It applies on every target engine: Postgres, the MySQL family and SQLite. The door fails closed: a target whose row writer cannot answer either question is refused, not skipped. A view or foreign table holding rows under a backup table's name is also refused, rather than cleared as an absent table that restore will create with its key (measured: a view made writable by an `INSTEAD OF` trigger received the same row twice). The Postgres and SQLite probes now count views, and on Postgres also foreign tables and materialized views, as existing. Restoring into a database that holds other data, or into empty tables you pre-created, is unaffected. Pinned by `TestRestoreRerun_SQLiteTarget`, `TestRowWriter_ProbeReplayKey_InsteadOfView` and `TestReplayDoorSurfaceRoster_EveryTargetWriter`, which derives every target engine from the registry and requires both probe surfaces on each one's row writer. **Affected releases:** every release through v0.156.10.

**A cold copy no longer re-sends a batch into a target keyed only on a surrogate the rows do not carry (HIGH, silent loss; audit F-E1, the in-run sibling).** Both engines' cold-copy writers ride a transient target error (a reparent, a storage grow, a dropped connection) by re-sending the same batch on a fresh connection. That is safe only when a batch that committed before its acknowledgement was lost collides on a key the second time. The retry gate (`SLUICE-E-COPY-RETRY-AMBIGUOUS-KEYLESS`) judged only the source table. A target created before the copy and keyed only on an `AUTO_INCREMENT`, `bigserial`, identity or defaulted surrogate passed the gate, and the re-sent batch landed twice at exit 0. This was measured on real servers with an injected committed-then-acknowledgement-lost failure, on MySQL's `LOAD DATA`, batched-INSERT and idempotent cores and Postgres's chunked COPY. It reaches `restore` into such a target, and a cross-engine `migrate` or `sync` cold start that warns about a pre-existing table and proceeds. The gate now asks the same question as the restore and broker doors, through one shared predicate (`irbackup.JudgeReplayKey`). It probes the target once per table per writer, only at the first retry decision, and a probe that cannot answer never licenses a re-send. A table sluice creates itself is unaffected: a PK-less source keyed by a NOT NULL UNIQUE index has that key created inline at `CREATE TABLE`, so it is keyed while it copies (`TestColdCopyCreate_PKLessNotNullUnique_IsKeyedWhileItCopies`). Pinned by `TestColdCopyRetry_SurrogateKeyedTarget_AckLostRefuses` on both engines. **Affected releases:** MySQL-family targets v0.99.92 through v0.156.10, Postgres targets v0.99.111 through v0.156.10, the releases with an in-run cold-copy retry.

**An `AUTO_INCREMENT` value of `0` is no longer renumbered on a MySQL-family target (CRITICAL class, silent alteration).** MySQL treats an explicit `0` written into an `AUTO_INCREMENT` column as "generate the next value" unless the session's `sql_mode` carries `NO_AUTO_VALUE_ON_ZERO`. sluice declares `AUTO_INCREMENT` at `CREATE TABLE` for a MySQL source's `AUTO_INCREMENT` column, and for a Postgres `bigserial` or identity column. Through v0.92.0 sluice inherited the server's `sql_mode`, whose stock default lacks the flag. From v0.92.1 it forced its own strict mode, which also lacked it. So a source row keyed `0` landed under the next free value at exit 0: `{0,'zero'},{5,'five'},{100,'hundred'}` landed as `{1,'zero'},{5,'five'},{100,'hundred'}`. This was measured on every write path into a MySQL target: `migrate` (both the `LOAD DATA` and batched-INSERT cores), Postgres `bigserial` and identity → MySQL, the idempotent `ON DUPLICATE KEY UPDATE` core, the `sync` cold start, CDC apply (serial and lanes), `restore` and the `sync from-backup` broker. Where the source also held the value the `0` was renumbered to, the copy failed loudly instead.

sluice now adds `NO_AUTO_VALUE_ON_ZERO` to every MySQL session it opens. It is appended to the mode sluice injects, including any `--mysql-sql-mode` list. When sluice injects no mode (a DSN `sql_mode=` parameter in any key spelling, or `--mysql-sql-mode=''`), it adds the flag to the live session after connecting and reads it back, keeping the strictness you chose. A server that will not take it is refused with `NO-AUTO-VALUE-ON-ZERO-UNSET`. `TestMySQLConnectionRoster_EveryPoolGoesThroughOpenDB` holds every MySQL pool in the tree to that one connection chokepoint. Measured fixed on MySQL 8.0 and 8.4, MariaDB 11.4 and Vitess through vtgate on an unsharded keyspace. It does **not** cover a sharded Vitess or PlanetScale keyspace whose column is filled by a vtgate sequence (see **Known residuals**). **Affected releases:** every release through v0.156.10.

**Postgres slot-drop recovery hints now print the full `sluice slot drop` command (LOW, loud, no data loss; Bug 296).** The `PRE-ALTER-REPLAY-WEDGE` recovery added in v0.156.10 printed `sluice slot drop <slot> --yes`: a placeholder instead of the slot name, and no `--source-driver` or `--source`, so it exited 80 as printed. The slot-usability (`wal_status` unreserved and lost), foreign-lineage and `--chain-slot` hints left out `--yes`, which `slot drop` has required since v0.99.189. Every slot-drop hint in the Postgres engine now renders one form: the resolved slot name, `--source-driver=postgres`, `--source <source DSN>` and `--yes`. Only the DSN is left to fill in. Pinned by `TestSlotDropCommand_RunnableAsPrinted`. **Affected releases:** the wedge hint on v0.156.10; the missing `--yes` on v0.99.189 through v0.156.10.

**Design only:** ADR-0190 Amendment E, which folds the lane barrier's pre-apply checkpoint into the barrier's own transaction, is design-accepted. This release ships no code for it.

## Known residuals

These are filed in `docs/dev/audit-backlog.md` under F-E1, and open.

- **F-E1-KEY-REUSE-REPLAY (HIGH candidate, silent, measured on both engines).** Re-running a broker incremental in which a key value moved off one row and onto another can apply a change to the wrong row at exit 0. A key-changing incremental that does not reuse a key fails loudly on every re-run instead (in the lane apply mode, after committing part of it). After a `BROKER-INCREMENTAL-PARTIAL` on a source that changes key values, recover with `--reset-target-data`, not a re-run.
- **F-E1-ROTATED-SEGMENT-OVERLAP (HIGH candidate, silent, unmeasured end to end).** Within a single run, rows are re-carried by design in several places. The restore door checks only tables that already hold rows, so an empty pre-created surrogate-keyed target is not covered.
- **F-E1-COARSER-TARGET-KEY (LOW, measured on MySQL 8).** A target unique key coarser than the source's identity (a prefix index, or a case-insensitive collation over a case-sensitive column) merges distinct source rows on first apply. This is not a replay defect, and neither F-E1 judgment sees it.
- **F-E1-SHARDED-ROUTING (HIGH candidate, silent, unmeasured).** The replay probe half is fixed in this release. Steady-state `ON DUPLICATE KEY UPDATE` writes (CDC apply inserts and the idempotent cold copy) into a multi-shard keyspace whose primary vindex the rows do not carry can still duplicate a re-delivered row. A multi-shard PlanetScale Postgres (Neki) target's equivalent is an UNVERIFIED PREMISE.
- **VTGATE-SEQUENCE-ZERO (CRITICAL class, measured on vttestserver).** On a sharded Vitess or PlanetScale keyspace whose column is filled by a vtgate sequence, vtgate replaces an explicit `0` with a sequence value whatever the session's `sql_mode` (the `0` landed as `1000`).
- **VTGATE-MULTI-1062-PREMISE (HIGH candidate, silent loss, reachable by code reading, unmeasured).** The batched INSERT's retry treats a duplicate-key error as proof the whole batch landed. A `restore` into a pre-created, vindexed multi-shard keyspace can commit one shard's part of a batch and not the other's.
- **F-E1-MYSQL-REPLAY-DUP-ATTRIBUTION (narrow, unmeasured).** A `LOAD DATA` segment replayed after a transient accepts a duplicate-key skip as the earlier attempt's row, and cannot tell it from a different row the target already held.

**Next:** exactly-once replay for broker changes, an apply identity per change so the marks can skip what already landed. It will lift the keyless refusal and close F-E1-KEY-REUSE-REPLAY with the rest of the class.

## Compatibility

**New refusals:**
- **`sync from-backup` refuses keyless tables (`SLUICE-E-BROKER-KEYLESS-TABLE`, exit 3), with no override.** A chain carrying a table with no PRIMARY KEY or NOT NULL UNIQUE index, or a target table keyed only on a surrogate the rows do not carry, now stops the broker at start, warm resume included. Give the table a key on the source and take a new full backup, or replicate it with `sluice sync start`. A view, foreign table or materialized view under a chain table's name on a Postgres target now refuses here too. Before, the applier skipped every change into it as an unknown table and recorded the skip.
- **`restore` refuses to load an in-scope keyless table that already holds rows (`SLUICE-E-RESTORE-KEYLESS-TABLE-NOT-EMPTY`, exit 3), with no override.** That includes a deliberate append. After a failed attempt, empty or drop every table it loaded, since a keyed one fails the re-run on its key. Or exclude the named tables. A table holding rows under a name the key probe cannot judge (a view or foreign table) refuses the same way.
- **A cold copy into a pre-created target keyed only on a surrogate now refuses on a transient target error (`SLUICE-E-COPY-RETRY-AMBIGUOUS-KEYLESS`) instead of retrying.** On Postgres, a pre-created target with a surrogate PRIMARY KEY beside a UNIQUE index on the source's key refuses too, because the applier's arbiter is the surrogate.
- **`migrate` into a SQLite file whose tables already hold rows now refuses with `SLUICE-E-COLDSTART-TARGET-NOT-EMPTY`** (override with `--force-cold-start`), as it already did on Postgres and MySQL targets. Before, it appended to them. The SQLite row writer gained the emptiness check the pre-flight needs.
- **A MySQL server or proxy that will not accept `NO_AUTO_VALUE_ON_ZERO` in the session `sql_mode` now refuses the connection** with `NO-AUTO-VALUE-ON-ZERO-UNSET`. This applies to source connections as well as targets, because every MySQL pool shares one connection path. MySQL 8.0/8.4, MariaDB 11.4 and vtgate were measured to accept it.
- **Vitess and PlanetScale MySQL targets: the replay key probe now enumerates the keyspace's shards, and on a multi-shard keyspace reads the table's primary vindex with `SHOW VSCHEMA VINDEXES ON`. Both fail closed.** If the target credentials cannot run them, the broker door refuses, the restore door refuses a table that already holds rows, and the cold-copy retry gate refuses instead of retrying. Whether PlanetScale's restricted roles allow these reads is **UNVERIFIED**: they were measured on vttestserver only.

**Exit-code change:** a cancel (SIGINT, SIGTERM, or `q`/ctrl+c on the live panel) that lands mid-incremental now exits 1 with `BROKER-INCREMENTAL-PARTIAL`, and one during a `--reset-target-data` cold start after its drop began exits 1 with `BROKER-COLD-START-PARTIAL`. Both used to exit 0, and the panel printed "stopped.". Supervisors that treat a cancel's exit status as success should expect this. `sync from-backup stop`, and a cancel between incrementals or ticks, still exit 0.

**`--mysql-sql-mode` no longer sets exactly the listed modes:** `NO_AUTO_VALUE_ON_ZERO` is always added. The same goes for a DSN `sql_mode` and for `--mysql-sql-mode=''`.

**Otherwise a drop-in.** No flag was added, removed or renamed, and no control-table or backup-format schema changed. The broker and restore doors do not apply to `sync start`, which has its own apply marks.

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale, a billable cluster), `d1verify` (live Cloudflare D1) and `nekiverify` (a billable Neki cluster) suites were not dispatched, because each needs live PlanetScale, D1 or Neki infrastructure and runs only on the operator's call. What that leaves unmeasured live:
- On PlanetScale MySQL: the sharded primary-vindex rule and the `SHOW VSCHEMA VINDEXES ON` / shard-enumeration permissions under PlanetScale roles, the `NO_AUTO_VALUE_ON_ZERO` injection and read-back through PlanetScale's vtgate, and VTGATE-SEQUENCE-ZERO's behaviour there. All were measured on vttestserver.
- On Neki: the Postgres probe's arbiter judgment on a multi-shard target (the F-E1-SHARDED-ROUTING premise) and the Postgres cold-copy retry gate against real Neki transients.
- On D1: D1 is a source only and has no row writer, so none of this release's doors reaches it. `d1verify` would only have re-exercised the SQLite engine package the SQLite target changes live in.

## Who needs this — action required

**Upgrading stops new duplication and renumbering. It does not repair rows already affected.**

- **`sync from-backup` brokers on v0.99.222 through v0.156.10 that were ever interrupted** (an error, a crash, a supervisor restart, a SIGINT or SIGTERM, `q`/ctrl+c), over a chain carrying a table with no PRIMARY KEY and no NOT NULL UNIQUE index, or into a target table keyed only on a surrogate. Run `sluice verify --depth count` against the backup's source database and the target. A target count above the source's on such a table is duplicated rows. After the upgrade the broker refuses those tables, so key them on the source and take a new full backup, or move them to `sluice sync start`. Then rebuild or de-duplicate the target table.
- **`sync from-backup` brokers on v0.20.0 through v0.99.221 that were ever interrupted mid-incremental.** Rows from the interrupted incremental may be missing, in any table. Run `sluice verify --depth count` and re-copy any table whose target count is below the source's.
- **Anyone who re-ran a `restore` onto the same target after a failed attempt, on any release through v0.156.10,** where the backup carried a keyless table or the target table was keyed only on a surrogate. Compare those tables' row counts with the source using `sluice verify --depth count`.
- **Cold copies into a pre-created, surrogate-keyed target** (MySQL family on v0.99.92+, Postgres on v0.99.111+) whose log contains `hit a transient target error`. Compare that table's row count with the source.
- **Anyone who migrated, synced or restored into a MySQL, MariaDB, Vitess or PlanetScale MySQL target, on any release through v0.156.10, a table whose `AUTO_INCREMENT`-mapped column holds `0` on the source** (a MySQL `AUTO_INCREMENT` column, or a Postgres `bigserial` or identity column). On the source, list the rows with `0` in that column. If the target has no row with `0` there, the row landed under a generated value: find it by its other columns and correct its key. A sharded keyspace with a vtgate sequence on the column is still affected after the upgrade (VTGATE-SEQUENCE-ZERO), so avoid carrying `0` into one.
- **Operators who copied a Postgres slot-drop hint and saw it fail (Bug 296).** Nothing to check. Use the new printed command, filling in the source DSN.
- **Everyone else:** upgrade, nothing to check. Expect the new refusals in **Compatibility** if a broker chain carries keyless tables.
