# sluice v0.163.4

> **Correction (2026-10-22).** The remedy below for a stream refused once though healthy is wrong as written, and the list of such streams is incomplete. The fix shipped in v0.163.4 is unchanged; v0.163.5 corrects the flag's help and the refusal's message.
>
> **"after you have compared the target's row count with the source's, table by table, and they match"** cannot work on a source that kept taking writes while the stream was stopped. A refused stream has applied none of those writes, so its counts differ even when its copy finished (measured on a complete stream: 4,992 on the target, 4,989 on the source), and an operator following it would re-copy a healthy stream. Use this order instead: pass `--assert-copy-finished` once, let the stream catch up, pause writes on the source, and run `sluice verify --depth count` against the same source and target (`--depth sample` refuses a PlanetScale/Vitess source); re-copy with `--restart-from-scratch` any table it reports short. That check is mandatory, because the flag records the tables at once and nothing refuses the stream afterwards: measured on an incomplete copy, `verify` reported `t2_big MISMATCH source=299500 target=149000` and the re-copy then matched, while on complete copies it reported every table `OK`. The list of streams refused once also leaves out a PlanetScale/Vitess stream handed off with `--position-from-manifest` on v0.163.3 or earlier, which has neither a record nor a progress row; the same order applies. Found by the v0.163.4 regression cycle (sluice-testing Bug 328).

**HIGH fix, silent: a PlanetScale/Vitess cold start stopped mid-copy by v0.163.1 or earlier no longer warm-resumes as if its copy had finished (Bug 327, `VSTREAM-COPY-COMPLETION-UNPROVEN`).** Those releases often saved only the copy's first checkpoint, which carries no copy cursor and looks exactly like a finished copy's CDC anchor. v0.163.2 and v0.163.3 warm-resumed from it, logged only an `INCLUDE-TABLE-SCOPE-UNRECORDED` warning, and never copied the rest. Measured on v0.163.3: 40,000 to 49,000 of 300,000 rows missing, exit 0, in 3 of 3 runs. This is the fix the v0.163.3 known-issue banner promised. A PlanetScale/Vitess warm resume now refuses unless the target proves the copy finished. The cost is a one-time false refusal for some healthy older streams, which the new `sync start --assert-copy-finished` flag clears after you compare row counts (see Compatibility). This release changes a guard and ships alone. One new flag, no backup format change.

## Fixed

- **A VStream warm resume needs proof that its copy finished (Bug 327, HIGH, silent; `VSTREAM-COPY-COMPLETION-UNPROVEN`).** v0.163.3 already refused a saved mid-copy position that carries a cursor (`VSTREAM-COPY-RESUME-WITHDRAWN`). A cursor-less one went on to the warm resume, which copies nothing. The new door runs on every warm resume from a `planetscale` or `vitess` source, before the scope-drift door and before the change stream opens. It asks the target for proof. **The established-tables record is proof on its own.** The cold start has written it in the same transaction as its CDC anchor since v0.163.0, after the copy, and a mid-copy checkpoint never wrote it. **The cold-start progress header (`sync-<stream-id>` in `sluice_migrate_state`, written since v0.149.0) at phase `complete` is not proof on its own.** It goes `complete` as soon as the bulk copy returns, before the FLOAT re-read, the FK check and the anchor. And an interrupted `--restart-from-scratch` can leave an old one beside an emptied target. So it counts only with target evidence. First, every table it records as having copied rows must still hold rows on the target, or be empty on the source too: a drained table, checked by a one-row source probe through the source's own row reader. Second, the stream's position row must have been written after the header. That comparison is made only on a Postgres target whose session zone has a UTC offset of 0 on both 1 January and 1 July. A MySQL-family target's `sluice_cdc_state.updated_at` also moves on stop requests and table-set writes, so there the header alone never proves the copy. A pass on the header records the established tables (only tables the header covers that exist on the target), so the header is judged once and later starts pass on the record. The door fails closed: a record, header, position row, clock or target table it cannot read refuses rather than passes. The refusal is a codeless exit 1 carrying `INCLUDE-TABLE-SCOPE-DRIFT`, which the `sync run` fleet supervisor does not restart, and it has applied no change. Pinned by `TestVStreamCopyDoor_DrainedTable`, `TestVStreamCopyDoor_HeaderProofRecordsOnlyCoveredTables`, `TestVStreamCopyDoor_FilteredTableNotProbed`, `TestVStreamCopyDoor_FilteredTableDoesNotMaskALostCopy`, `TestControlTimestampsComparable_NeverOnMySQL`, `TestControlTimestampsComparable_FollowsTheSessionZone` (real Postgres, including Europe/London and Europe/Lisbon for the summer-time arm), and the `CursorlessCheckpoint` cells of `TestStreamer_VStreamCopyResume`. Those cells use a real Vitess cluster with a Postgres target and with a MySQL target. A planted cursor-less position refuses with the target unchanged, and `--restart-from-scratch` lands exact.
- **New flag `sync start --assert-copy-finished` lets a stream the door cannot prove through, once (`COPY-FINISHED-ASSERTED`).** It records as established the in-scope tables that exist on the target and hold rows; an absent or empty table is not recorded and is named in a warning. Later resumes pass on the record without the flag. It is refused when the target shows the copy did not finish: a progress header short of `complete`, a complete header whose copied table is now empty on the target while the source table holds rows, or a position row written before the header. Missing evidence (no header, clocks that cannot be compared) does not block it. A table under a `--where` filter is never probed on the source, because an unfiltered probe would find the rows the filter excludes. It answers "unproven", never "contradicted", and it cannot mask a contradiction on another table. The flag is rejected together with `--restart-from-scratch` or `--reset-target-data`, and it does nothing on any non-VStream source. The fleet spec has no key for it: take a `sync run` leg out of the fleet and run `sluice sync start` with the flag once.
- **A PlanetScale/Vitess `sync start --position-from-manifest` handoff now records the tables it restored.** Without a record, every later plain restart of a handed-off stream would have met the new door. Once the handoff's change stream opens, it writes the chain's position as the anchor and records the stream's scope, narrowed to the chain's tables (`LoadChainTerminalTables`) and to the tables present on the target, in one write. A table in scope that the backup never held is not recorded, so the scope-drift door still judges it at the next start. A stream that already has a record keeps it. If the chain's table list cannot be read, the write fails, or the target writes the anchor without the record (`COLD-START-ANCHOR-UNRECORDED`), the handoff refuses `MANIFEST-HANDOFF-UNRECORDED` and has applied no change. Handoffs from every other source are unchanged. Pinned by `TestRecordManifestHandoff_TargetIntersection` and `TestRecordManifestHandoff_AnchorUnrecordedRefuses`.
- **A control table that needs DDL this role cannot run is now a terminal refusal naming the right remedy, not a restart loop.** A new sentinel, `ErrControlTableDDLRequired` (carried as `ControlTableDDLRequiredError` with the engine's remedy), is raised by the Postgres control-table paths (an absent table on a never-create path, or SQLSTATE 42501) and by the MySQL safe-migrations classifier. The door, the flag's record write and the handoff all treat it as terminal. On Postgres the remedy is `sluice control-tables ddl --engine postgres`. On a MySQL-family target (PlanetScale safe migrations) it is `sluice deploy-ddl --ddl '<ALTER>'` with the failing ALTER itself, because `sluice control-tables ddl` prints CREATE statements only. A re-run names the next ALTER the same way, so expect one round per statement. Pinned by `TestVStreamCopyDoor_ControlTableDDLRefusal`, `TestControlTableBootstrapRemedy_AlterNamesTheAlter` and `TestStreamer_VStreamCopyDoor_ControlTablesDMLOnlyRole` (real Postgres, DML-only role).

## Not closed, stated

- **The drained-table pass is pinned by unit tests only.** No real-store cell drains a source table. The source probe itself is exercised against a real Vitess source in the contradicted arm.
- **A MySQL privilege error outside safe migrations (errno 1142) is not classified as `ErrControlTableDDLRequired`.** The MySQL engine does not mark it, so it takes the ordinary control-table failure path instead of the terminal refusal with a DDL remedy. This is documented on the sentinel.
- **`sync start --dry-run` still prints "warm resume" for a VStream stream whose real run refuses (DRY-RUN-PREDICTS-REFUSED-VSTREAM-RESUME, LOW, filed).** This is not a loss, because the real run refuses loudly. It was already true of `VSTREAM-COPY-RESUME-WITHDRAWN` in v0.163.3.
- **Three residual premises are written into the door's doc comment as unverified.** (1) Take a stream stopped by v0.163.1 or earlier after its header went `complete` but before its anchor, and already warm-resumed by v0.163.2 or v0.163.3. Its position row has been rewritten since, so on a UTC Postgres target the clock check reads it as finished. The header-only pass then records it, making that verdict permanent for the stream. The rows the stopped copy never reached were already lost by the earlier warm resume, and a re-copy is the remedy either way. (2) A re-copy on v0.163.1 or earlier, with progress recording inert, that stopped after writing some rows to every copied table passes the emptiness check. (3) On Postgres, the clock answer uses this session's UTC offset in place of the offset of the session that wrote an older row.
- **Not run for this release: `psverify` and `d1verify`.** Every VStream measurement was on a local Vitess cluster, not on PlanetScale itself.

## Compatibility

- **One new flag (`sync start --assert-copy-finished`), no flag removed, no backup format change** (`BackupFormatVersion` stays 15). Not drop-in for every PlanetScale/Vitess stream: some refuse their next warm resume once, as below.
- **Who is refused, and whether that is correct.** These are warm resumes from a `planetscale` or `vitess` source only. MySQL binlog, Postgres, SQLite/D1 and trigger-CDC sources are unaffected.
  - **Refused correctly:** a stream stopped mid-copy on v0.163.1 or earlier, whether or not it has been resumed since. Re-copy it with `--restart-from-scratch`.
  - **Refused once though healthy:** a stream whose last cold start finished on v0.148.x or earlier (no progress header, no record).
  - **Refused once though healthy:** a stream whose last cold start finished on v0.149.0 through v0.162.x (header but no record) when its target is MySQL-family, or Postgres with a session zone that is not UTC all year.
  - **Refused once though healthy:** a stream whose progress recording was disabled, or whose evidence does not hold up as described above.
  - **Pass without action:** streams cold-started on v0.163.0 or later, which carry the record. Streams cold-started on v0.149.0 through v0.162.x into a Postgres target whose session is on UTC all year, provided the evidence holds; the first pass records them.
- **Two ways out of a refusal.** The safe one is `--restart-from-scratch`, which drops the in-scope target tables and copies them again. With `--schema-already-applied` it cannot drop them, so it refuses `RESTART-FROM-SCRATCH-TARGET-NOT-CLEARED` while they hold rows; with `--inject-shard-column` it refuses until this shard's rows are deleted by hand. The other is `--assert-copy-finished`, once, after you have compared the target's row count with the source's, table by table, and they match. That the stream has been streaming changes is no evidence: every stream this refusal protects has been.
- **`sync run` fleets:** a refused leg stops and is not restarted by the supervisor. Take it out of the fleet, run it with `sluice sync start` (and the flag, if the counts match), then return it.
- **`--position-from-manifest` handoffs from a PlanetScale/Vitess source** now write an anchor and an established-tables record when they start, and refuse `MANIFEST-HANDOFF-UNRECORDED` if they cannot.

## Who needs this — action required

- **Anyone who stopped a PlanetScale or Vitess `sync start` cold start during its copy on v0.163.1 or earlier.** The saved cursor-less position was a silent warm resume on every release through v0.163.3. That is the v0.163.2 CRITICAL for releases before it, and Bug 327 on v0.163.2 and v0.163.3. If such a stream is still stopped, upgrade and re-run with `--restart-from-scratch`. If it has already been re-run on any release through v0.163.3, and particularly if a v0.163.2 or v0.163.3 run logged `INCLUDE-TABLE-SCOPE-UNRECORDED`, compare each table's row count against the source and re-copy with `--restart-from-scratch`. On this release such a stream refuses `VSTREAM-COPY-COMPLETION-UNPROVEN`, and usually the flag is refused too. Treat the refusal as the signal: do not reach for `--assert-copy-finished` without counting.
- **Anyone running a healthy PlanetScale/Vitess stream last cold-started before v0.163.0:** expect the one-time refusal described in Compatibility. Compare row counts table by table, then either pass `--assert-copy-finished` once or re-copy.
- **Everyone else:** nothing to do.
