# sluice v0.107.0

**Nine silent-failure fixes found by a systematic sweep, not by a bug report.** Every one of them exited 0 while doing something wrong, and four of them lost data. This release is the remediation half of a project-wide audit of the places where sluice could fail quietly — and it ships the permanent gates that make each class fail the build from now on, rather than relying on someone finding it again.

If you use mydumper/pscale dumps as a source, take encrypted or chained backups, run a supervised `sync run` fleet, migrate Postgres arrays, or run any MySQL-target migration whose tables differ only by letter case, there is something here for you.

## Fixed

**A stray `/*` in a mydumper dump silently dropped every row after it, and `migrate` exited 0.** A block comment with no closing `*/` — a hand-edited dump, a truncated upload, a chunk severed mid-comment — put the reader's lexer into comment state for the rest of the file, which is correct; what was not correct is that the classifier then treated the whole remainder as a comment and skipped it. Every `INSERT` after the stray `/*` vanished, the table arrived short, and the migration reported success. `sluice verify --depth count` could not catch it either: it reads the dump through the same path, so it counted the same truncated file and agreed. The versioned `/*!…*/` form was already handled correctly; the plain form was the one branch the earlier fix for severed fragments and mid-file byte-order marks did not close. An unterminated comment of either flavour now refuses, naming the chunk file.

**`backup verify` reported an interrupted backup healthy, and `restore` restored it to exit 0 with tables missing.** A `backup full` that is killed leaves a manifest marked `partial_state: in_progress` listing only the tables it had finished. Every chunk that manifest names is real and correctly hashed — so `backup verify` rehashed them all and reported the backup intact, and `restore` created every table in the embedded schema, loaded the ones the manifest listed, logged the remainder at INFO, and exited 0. An operator following the documented DR drill got green signals over a backup that was never finished, and the missing tables arrived **empty rather than absent**, which is the harder failure to notice. One qualification worth stating: on some chain shapes an unrelated pre-existing guard does stop the restore — but it diagnoses an interrupted backup as a *tampered* one, which sends the operator to rotate keys instead of to finish the backup, so the signal was wrong even where it fired. Restore (single-manifest and every link of a chain), `backup verify`, and `export-as-parquet` now refuse such a manifest before reading any data, with the new `SLUICE-E-BACKUP-INTERRUPTED` (exit 3). The remedy is to finish the backup — re-running the same command resumes it, keeping the tables already complete. A manifest with no `partial_state` field is a pre-v0.16.x backup, not an interrupted one, and still reads normally.

**A non-rectangular array bound for a Postgres array column silently dropped elements — or crashed the writer.** The row writer derived each array dimension by walking only the first element at that depth, then flattened every leaf with no length check against those dimensions. A jagged array — from a JSON-decoded change stream, say — lost the overflow silently when a later row was longer, lost more when the first row was shorter than its siblings, and panicked outright when a trailing row was short. Ragged arrays now refuse with `SLUICE-E-VALUE-RAGGED-ARRAY` (exit 3) naming the depth and the mismatched lengths. Rectangular arrays of every element family are unaffected and are now pinned across 16 families × 12 shapes.

**MySQL control tables keyed source identifiers case- and accent-INSENSITIVELY, so `Foo` and `foo` silently overwrote each other.** Every MySQL control table declared `DEFAULT CHARSET=utf8mb4` with no `COLLATE`, inheriting a case- and accent-insensitive collation on the columns holding table names, stream ids, and migration ids. Two source tables differing only by letter case (or by an accent) collided on the primary key, the upsert made one overwrite the other's cursor, and on `--resume` the second table restarted from the first's position — **every row below it never copied**, exit 0. The Postgres equivalents were always correct, so this was a MySQL-only divergence. Twelve key columns across eight control tables are now binary-collated. Existing control tables keep their old collation — an automatic `ALTER` is not safe on a PlanetScale safe-migrations branch and is a full rebuild on a large table — so sluice now WARNs at every startup naming the table, the columns, and the exact statement to run.

**VStream decoded `BIT` columns differently from every other MySQL path.** The Vitess/PlanetScale CDC reader grouped `BIT` with the byte families and handed up raw bytes, where every other path yields the canonical bit-string — a representation that exists precisely because the raw form was silently corrupted by the Postgres writer once before. A Postgres target refused loudly. A MySQL or PlanetScale target bound the raw bytes, which under sluice's default strict `sql_mode` also fails loudly — the silent-acceptance risk was confined to a target running a relaxed `sql_mode` that coerces them. Reached on both CDC and the cold-start copy.

**A value-preparation refusal lost its error code on the way through `COPY`, exiting 1 instead of 3.** When a copy source refuses a value, pgx aborts the `COPY` by handing the refusal's message *text* to the server and returns the server's echo — so the words survived but the error chain did not. This affected `SLUICE-E-VALUE-NUL-BYTE` too: a MySQL→Postgres copy hitting an embedded NUL exited 1, and any automation matching the documented code or on exit 3 could not see it. Pre-existing; surfaced by the array work.

**A fleet `sync run` config silently ran the opposite cross-shard DDL posture from a byte-identical `sync start`.** Live cross-shard DDL coordination is documented as on by default when `--inject-shard-column` is set, but the field carrying it was named for its on-behaviour and assigned in exactly one place — the `sync start` CLI. Every other construction, the supervised fleet included, got Go's zero value and quietly took the suppressed branch, which also made the loud refusal for a target engine that cannot satisfy the coordination contract unreachable there. The field is now an opt-out, so the safe default is what an unset field means, and the fleet spec gained a matching `no-coordinate-live-ddl:` key.

**`sync start --upfront-indexes` and `--analyze-after` reach the default Postgres cold-start path.** Both flags are new to `sync start` in this release. The sync cold-start has three copy paths, and the one that runs by default whenever a Postgres source can export a shareable snapshot — the fast parallel lane — was initially wired to pass a hardcoded "off" for both, under a comment describing each as a migrate-only flag. They are not: the serial cold-start path honours them. That gap was found and closed inside this same release, so no published binary ever accepted the flag and ignored it — on v0.106.0 and earlier `sync start` rejects both as unknown flags. Recorded here because the *shape* of the defect (a knob wired on one sibling path and silently inert on another) is the class the new parity gates below exist to catch.

**`--copy-fanout-degree` was inert on the multi-database sync cold-copy.** Same one-sided-knob shape as the two above, and found by the new gate rather than by a report.

## Added

**`sync start --strict-float`: demand exact single-precision FLOAT on a PlanetScale/Vitess cold-start, or refuse.** A VStream COPY renders `FLOAT` at MySQL's six-significant-digit display precision, and sluice repairs that afterwards by re-reading the affected columns exactly. Some tables can never be repaired — no primary key to target the re-read, or a `FLOAT` inside the primary key — and until now the sync cold-start only warned and proceeded with rounded values. `backup full` has had the exact-or-refuse posture for the same reader since the repair landed; `sync start` now has it too, refusing upfront with `SLUICE-E-VSTREAM-FLOAT-LOSSY` (exit 3) before any row moves. Off by default.

## Changed

**The migrate/sync copy-phase parity gate now fails by default instead of asking a human to remember.** The previous gate iterated a hand-curated list of seven flag names and checked only that a struct field of that name existed — so a new one-sided flag passed silently, and a field that was never assigned, or assigned a constant at the call site, passed too. Both failure modes had live instances in this release. The replacement diffs the real flag sets of `migrate` and `sync start` and requires every difference to carry a written architectural reason, so a flag added to one command and not the other fails the build until someone wires it or records why not. Two static gates then verify the shared-phase fields are actually assigned at every production construction site and reach the orchestrator from a field rather than a constant, each with an anti-vacuity floor that fails when its walk stops matching the code.

## Compatibility

**Three new refusals where sluice previously proceeded.** An unterminated block comment in a dump, an interrupted backup manifest, and a ragged array bound for a Postgres array column now all fail loudly instead of silently losing data. Each is a case that was producing a wrong result before, so a run that starts failing here was already failing — it just was not saying so. New codes: `SLUICE-E-BACKUP-INTERRUPTED`, `SLUICE-E-VALUE-RAGGED-ARRAY`.

**One behaviour change worth reading if you script against exit codes.** A value refusal travelling through a Postgres `COPY` now exits 3 with its documented `SLUICE-E-*` code. Previously the refusal's own code was lost — pgx aborts the copy by handing the message text to the server and returning the server's echo — so the error surfaced under a generic phase code and exit 1 rather than the documented value code. If you have automation matching on exit 1 for this case, it needs updating; it was matching a bug.

**The MySQL control-table collation change applies to newly created tables only.** Existing control tables are left alone and warned about, with the exact `ALTER` statement printed. One caveat, stated plainly: `utf8mb4_bin` is the only binary utf8mb4 collation portable across MySQL 5.7/8.x, MariaDB and Vitess, and it is PAD SPACE — so two keys differing only by a trailing space now compare equal where the previous collation held them apart. That is strictly narrower than the case- and accent-folding it replaces, and MySQL forbids trailing spaces in identifiers.

## Who needs this

- **mydumper / pscale-dump sources** — the comment fix is a silent-loss class that `verify` could not catch.
- **Anyone relying on `backup verify` as a DR signal** — it was green over interrupted backups.
- **MySQL-family targets** with tables differing only by case or accent, and anyone on Vitess/PlanetScale carrying `BIT` columns.
- **Postgres targets receiving arrays** from a change stream.
- **Supervised `sync run` fleets** using `--inject-shard-column`.
- **Postgres sync cold-starts** where `--upfront-indexes` was being passed and ignored.
