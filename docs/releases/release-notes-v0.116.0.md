# sluice v0.116.0

**CRITICAL fix — a PostgreSQL `json[]` or `jsonb[]` column landed on a MySQL-family target as an opaque base64 token instead of the document it holds: `{"a":1}` stored as `"eyJhIjoxfQ=="`, at exit 0, with matching row counts and nothing in the log. Reproduced end to end on a real MySQL 8 with PostgreSQL's own `json_out` as the oracle. Upgrading from v0.115.0 is drop-in in the mechanical sense — no flag added, renamed or removed, no on-disk format change, no backup chain repartitioned — but ONE new error code exists, a continuous `sync` carrying such a column is now REFUSED where it previously ran, some MySQL-target array values change their stored form, and a SQLite name pair that v0.114.0 and v0.115.0 refused is now ACCEPTED. Those are in Compatibility.**

This release is unusual in two ways worth naming up front: it RELAXES a refusal sluice shipped two releases ago, and it retracts five written claims rather than fixing five bugs — one of them a sentence written inside this very release, three days old at retraction. The provenance is again not "a user hit it". Item 152 was filed by the pass that rescued the audit's work queue out of a gitignored file, and it is item 145's unenumerated sibling: 145 closed exactly this family for the Postgres target one release ago and never enumerated the MySQL one. **Item 152's own first cut was then found incomplete by a `value-fidelity-reviewer` pass run before the tag** — correct on the axis it enumerated, blind to a second one — so the fix ships in two passes and the second is described here as its own finding rather than folded in silently. Item 150 was caught by v0.115.0's post-release regression cycle against real SQLite. Item 108 came from a live PlanetScale incident on 2026-07-30 where sluice told an operator to delete something that was working. Bug 230 came out of a bare-flag census of every string literal in the tree.

## Fixed

**A PostgreSQL `json[]` / `jsonb[]` column silently became an array of opaque base64 tokens on a MySQL, MariaDB, PlanetScale or Vitess target (item 152).** MySQL has no array type, so sluice renders an `ir.Array` column as a `JSON` column and serialised the value through `convertArrayLikeToJSON`, which handed the IR's `[]any` straight to `json.Marshal`. Both PostgreSQL read lanes decode a `json`/`jsonb` array element to `[]byte` and a `bytea` element to `[]byte`, and **Go renders a `[]byte` as base64** — so a document became a token, a queryable column became an unqueryable one, and every JSON function, index and downstream consumer pointed at that column had been reading the token. **Row counts do not change when a value is re-encoded, and `sluice verify` cannot catch this class at any depth:** `--depth count` compares counts, and `--depth sample` REFUSES a cross-engine pair outright (server-side hashing renders values engine-specifically, so a cross-engine sample would produce false mismatches), which leaves no depth that inspects the value.

**The fix is a per-element-family leaf policy — `arrayLeafForJSON` — and the decision that matters is what a `json`/`jsonb` element becomes.** It is now the document's **exact text inside a JSON string**, reached with `JSON_UNQUOTE`. Nesting the document as a JSON value reads better and was deliberately rejected for the reason item 145 rejected the same shape on the trigger door: nesting makes a JSON `null` DOCUMENT byte-identical to a SQL NULL element, and an array-valued document (`[1,2]`) byte-identical to a nested array dimension. Both are real, both are unrecoverable, and both would be silent — so the lossless option is taken instead of trading one silent loss for two. A `bytea` element is **base64, now DECLARED**: no stored value changes on the lane it already governed, what is added is a name in `docs/type-mapping.md`, a test, and the one-way WART note that no MySQL reader ever reconstructs an `ir.Array`, so neither encoding round-trips back through a later MySQL-sourced migration. Every other family passes through untouched because Go's rendering is already faithful for it — but a `[]byte` leaf on such a family, or on a column whose element type cannot be resolved, is now REFUSED by name under the existing `SLUICE-E-VALUE-UNREPRESENTABLE` rather than base64'd on a guess, and a `NaN`/`±Infinity` element is refused too where it used to be a swallowed marshal error that surfaced as the `LOAD DATA` serializer's `unsupported value type []interface {}`.

**And then the review found the second dispatch axis: the policy keyed on the element FAMILY and not on the shape the value ARRIVES in.** `convertArrayLikeToJSON` recognises the same array three ways — the decoded `[]any` the scan and pgoutput lanes hand it, the PostgreSQL array TEXT LITERAL that a `--type-override <col>=jsonb` leaves as a string, and that same literal as `[]byte` — **and only one of the three reached the new policy.** So a `bytea[]` rendered `["3q0="]` down one lane and `["\\xdead"]` down the other two: same declared family, same source bytes, two encodings decided by which lane the row came down, on the very family the policy exists to make deterministic. All three arms now end at one `marshalArrayLeaves`, so `pgArrayLiteralTokens` is a PARSE and every fidelity verdict belongs to `arrayLeafForJSON`. **The split also separates two failure modes the old function had conflated:** a parse failure is a SHAPE verdict — "this value is not an array literal", fall through to the next branch — while a leaf refusal means "it is one and it cannot be carried faithfully", and is loud. A `bytea[]` literal token that is not the `\x`+even-hex form now refuses instead of storing its own ASCII. **`json[]` is where this matters most for reading the affected range: the two lanes already AGREED for that family**, because the literal arm emitted each token as a JSON string, which is the document's text — the same answer the new policy gives. That row is kept in the parity matrix specifically so a change that fixes `bytea` by breaking `json` reports as itself.

**A third instance of the same class, found while writing the pin.** The empty-`{}` disambiguation — which decides whether the two bytes `{}` are an empty JSON OBJECT (Bug 47) or an empty PG array (Bug 14) — consulted `SourceColumnType` alone, so an empty array on a plain `ir.Array` column landed as the JSON object `{}` through the bytes arm and as `[]` through the other two. It now asks the same pair `arrayElementType` reads.

**The CDC applier lane cannot resolve the element family at all, so it is closed by REFUSAL, and the over-reach is stated rather than implied.** A `ChangeApplier` reads its column descriptors from the TARGET's `information_schema`, where MySQL renders both `json[]` and `bytea[]` as the same `JSON` column — so the element type is simply not there, while the CDC reader types its values from the SOURCE. The content cannot decide it either: a `bytea` whose bytes happen to spell a JSON document is an ordinary `bytea`. Guessing would make the cold copy encode one way and every later apply the other, disagreeing about the same column with no error on either side. So the leaf refuses, and `preflightArrayBytesLeafOnCDC` turns that late refusal into an early one at `sync` cold start and `schema add-table`. **`bytea[]` is refused too although its two lanes would in fact have agreed** — the honest scope is the family SET whose leaf is byte-shaped, not the one member of it whose answer happens to be stable. Two corrections landed here in the review pass: the preflight keys on the target ENGINE rather than on a target catalog read (its first cut rode the sibling refusal's catalog read and silently no-opped on a fresh target, which is exactly the run that matters), and it now sees through an `ir.Domain` — `CREATE DOMAIN d AS json[]` is a real Postgres shape that a bare `src.(ir.Array)` walked straight past, so the column skipped the cold-start refusal and failed mid-stream instead. **The value path had been unwrapping domains since v0.95.3 and the preflight had not, so the two were asking different questions about the same column.**

**The sentence the whole preflight-scope argument rested on was FALSE, and it is corrected rather than closed.** `arrayLeafForJSON` claimed to be "the backstop that keeps the halves that preflight does NOT reach loud rather than silent". It fires on a `[]byte` leaf, so it reaches the doors that PRODUCE one — and the `postgres-trigger` door does not: that reader decodes its capture payload with a `UseNumber` `encoding/json` unmarshal and no column types, so its leaves are drawn from `{string, json.Number, bool, nil, []any, map[string]any}` and can never be a `[]byte`. Measured on the applier lane, a trigger-sourced `bytea[]` element arrives as PostgreSQL's `\x`-hex string and lands as `["\\xdead"]` where the cold copy stored `["3q0="]`, and a `json[]` element arrives as a nested map and lands as `[{"a":1}]` — silent divergence, not loss, since nothing is destroyed and the two halves of one column simply disagree. **Refusing there was considered and rejected on evidence**, which is why it is scoped rather than closed: on that door the offending value is byte-identical to values that are correct today and common — a `jsonb` column whose DOCUMENT is an array decodes to the same top-level `[]any` of the same leaf types, and a `text[]`/`int[]` change arrives as `[]any` of strings or `json.Number` on both doors and renders exactly as the cold copy does — so a blanket refusal would break every jsonb array document over pgtrigger→MySQL and every string- and native-leaf array over CDC. Sniffing the CONTENT to tell them apart is precisely what item 135 forbids one layer up. **So the claim is retracted in both homes, the residual is scoped (cold start IS covered, because the preflight reads the SOURCE schema whatever the source engine), and it is pinned as an ENUMERATION of what passes rather than asserted as a guarantee.** It predates this release; it is in the residual list below, not presented as new.

**The other two blind halves are still loud, and that is checked rather than assumed.** Warm resume and a mid-stream `ALTER TABLE … ADD COLUMN` over the `postgres` (pgoutput) or scan doors still fail at the applier's leaf, naming the column. The multi-database cold-start fan-out is not wired to the preflight, but its source can only be one of the two `ir.MultiDatabaseSnapshotOpener` implementors — MySQL, whose schema reader never produces an `ir.Array` at all, or Postgres, whose door decodes both byte-shaped families to `[]byte` and so trips the refusal — so it stays loud by construction rather than by luck. **And the mid-flight refusal no longer strands the operator:** it now carries the preflight's own remedies and states that the family is sync-unsupported, in both the prose and the coded `Hint`, instead of reading as a bare per-value type complaint. The text is duplicated rather than shared because engines must not import the pipeline package, and a test on each side holds the two together.

**Sibling sweep, every target that can receive an `ir.Array`, since this defect exists because the previous sweep stopped at one target.** `mysql` — fixed, and `mariadb`, `planetscale` and `vitess` register from the same package and share the same three write cores through one `prepareValue`. `postgres` — already correct from items 141/145, untouched. `pgtrigger` — delegates its writer to postgres. `sqlite` / `d1` — exempt, a SQLite target refuses `ir.Array` at schema emit and a value never arrives. `sqlite-trigger`, `d1-trigger`, `flatfile`, `mydumper` — exempt, source-only. `blobcodec` — exempt, it tags a `[]byte` element and recurses. `parquetexport` — exempt, it routes each leaf through the element's own encoder and refuses multi-dim loudly. A second sweep covers every ARM of `convertArrayLikeToJSON`, with the `map[string]any` arm the one deliberate exception because its leaves are a jsonb document's rather than an array's. The roster gate is derived from the Postgres reader's own element map — **now including the VALUES, which the first cut hand-wrote and bound to nothing**, so repointing an entry fails the build; what stays unbound is the `data_type` → IR mapping itself, and the header says so rather than letting the two derived halves imply otherwise.

**Two claims made about this fix's own test coverage were wrong and are corrected in the same delta.** The item-152 commit said the real-server matrix covered 3-D arrays; the seed DDL stopped at 2-D. There is now a ragged 1×2×2 row — ragged so a flatten and a transpose read differently — with a full `array_dims` comparison. And that integration test ran through ONE MySQL bulk-write core without asserting which: **the engine defaults to `LOAD DATA` and falls back silently to batched INSERT when `local_infile` is off, so a single unasserted run pinned whichever core the container happened to allow and left the other — including the TSV escaper, against exactly the backslash and quote payloads at issue — covered by nothing.** It now runs both, with the core that executed asserted from the server's own `Com_load` counter. That is the same silent fallback that made an earlier "three write cores" gate actually grade two.

**Affected releases: v0.69.0 through v0.115.0**, and the route is narrower than "any `json[]` column". `612095a0` is where an un-overridden `ir.Array` column first routed into `prepareValue`'s JSON arm — before that the same value crashed the `LOAD DATA` serializer loudly — and that decoded-`[]any` lane is the one that base64'd. **A `--type-override <col>=jsonb` on a `json[]`/`jsonb[]` column took the array-literal lane and was CORRECT on every release**, storing the document's text, so those columns were never affected. **The source has to be the `postgres` engine:** `postgres-trigger` refuses a `json[]`/`jsonb[]` table at `trigger setup`, before any trigger is installed. The `bytea[]` arrival-shape divergence (`["3q0="]` versus `["\\xdead"]` depending on the lane) has the same v0.69.0 lower bound, since it needs both arms reachable. **And the `json[]` loss is REVERSIBLE from the target alone** — base64 is a faithful, decodable projection and the array's structure, NULL elements and nesting all survived — which is what makes the action item below concrete rather than "re-migrate and hope".

**The SQLite name-collision fold was Unicode where SQLite's is ASCII-only, so `café` and `CAFÉ` were refused as a collision although they are two objects on a real SQLite target (item 150).** SQLite's identifier comparison folds `A`-`Z` and nothing else — a stock build carries a 256-entry table that leaves every byte of every multi-byte UTF-8 sequence alone. The three collision walks keyed on Go's `strings.ToLower`, which is Unicode-aware and therefore a strict SUPERSET, and the difference was operator-visible in the over-refusal direction: `idx_é` and `idx_É` are two indexes on a real SQLite target and migrated fine through v0.113.0. **Both call sites' comments already SAID the fold should be ASCII-only, so the code and its own documentation had been disagreeing since they were written**, and one of the two was a separate `ToLower` used only to RENDER the refusal message — a display fold that does not match the check names an effective identifier nothing ever computed. `foldSQLiteIdentifier` is now SQLite's rule in one place, used by the table walk, the view walk, the index walk and the message. It walks BYTES rather than runes on purpose: SQLite does not require an identifier to be valid UTF-8, and a rune-wise fold would map each bad byte to U+FFFD and hand the collision map one key for two different broken names.

**MySQL's fold is deliberately NOT shared, and that is the half where sharing would have been silent.** `foldMySQLIdentifier` imitates a SERVER rule that DOES fold non-ASCII case under `lower_case_table_names != 0` — `é`/`É` was measured as ONE table on both `mysql:8` and `mariadb:11.4` during item 149 — so handing MySQL SQLite's ASCII-only fold would be an UNDER-refusal, which is the direction that loses rows. Postgres passes no fold at all, because sluice's quoted identifiers compare byte-exactly. The seam is now enforced rather than requested: an AST roster requires every `namecollide.New` call under `internal/engines` to pass `nil` or a fold declared in the CALLING engine's own package, so a fold borrowed from anywhere both engines can reach — the standard library included — fails the build. Completeness is structural rather than argued: the seam package sits under `engines/internal`, so Go's own internal rule makes `internal/engines` the entire set of possible callers. The pin is a 12-pair matrix ground-truthed against real SQLite as tables, as views AND as indexes, with the expectation read out of `sqlite_schema` rather than written by hand, covering the three Unicode special-casings Go gets differently — U+212A KELVIN SIGN folding to ASCII `k`, U+1E9E, and U+0130, which `ToLower` expands to two runes and would change an identifier's LENGTH. **Affected releases: v0.114.0 (`37cc7ef0`) for index names and v0.115.0 (`5c8c699a`) for table and view names, both through v0.115.0.**

**`--resume` refused a PlanetScale dev branch whose deploy request was still healthily building, and told the operator to delete it (item 108).** The ADR-0148 index-build fallback names its dev branch deterministically from its own DDL, so a re-run finds its own leftovers — and finding one was an unconditional refusal reading "inspect its deploy request; otherwise delete the branch and re-run". **The operators that line reached most often were exactly the ones the unbounded-wait behaviour was written FOR:** holding a branch whose VReplication index build was still running. Observed live on 2026-07-30 with deploy request #1 at 78%, `deployment_state=in_progress` and PlanetScale's own ETA at ~52 minutes, a `--resume` refused, and the remedy it printed would have discarded roughly three hours of completed build. The PlanetScale API refuses that delete outright, which is the platform being right and sluice being wrong. It also carried no `SLUICE-E-*` code, so no automation could branch on it.

**`legRunner.run` now hands a leftover branch to `adoptLeftoverBranch`, which looks up the deploy request opened from it and JOINS the same `waitDeployed` poller a fresh run uses** — no second branch, no second deploy request, no DDL re-execution, and the identical finalize/cleanup/keep-the-branch tail, now shared by both paths rather than duplicated. **The line adoption will not cross is that it joins a deploy already ISSUED, never one merely deployable**, and that boundary is argued rather than chosen: the fresh path makes two promises immediately before `Deploy` — that the dev branch's schema base still matches current production, and that the request's diff touches nothing outside the leg's intended tables — and neither can be re-established for a branch this run did not provision. Deploying from a stale base silently reverts newer production schema, so a never-deployed leftover is REFUSED even though the filing did not ask for that case; the re-run costs only a re-provision, and the pre-deploy gates are then absent from the adopt path by construction rather than by omission. The adoptable-state set is derived rather than re-guessed: `classifyAdoption` reuses the poller's existing 20-value `deployment_state` enum and a test asserts its graded set is EXACTLY that enum in both directions with a 20-state floor. **Two INDEPENDENT pre-deploy signals are required**, because a state name sluice has never seen that is still awaiting its `Deploy` call would otherwise be handed to a poller that waits on it forever. Identity rests on the branch name being `sha256(scope, ddl)[:10]`, which is also why "verify the DDL matches" needs no DDL comparison — a changed index set hashes to a different name and is never found — plus the request being opened from that branch, merging into THIS run's production branch, and being the only one; a human creating a branch at that exact name and a 40-bit hash collision are named as NOT ruled out. The new `api.ListDeployRequests` returns a truncation error rather than a short list and stops on an EMPTY page rather than a short one, because truncation here reads as "there is no deploy request", whose old remedy was a branch delete. **The refusal residue is the new `SLUICE-E-PS-DEV-BRANCH-NOT-ADOPTABLE`, and its message says "delete it" only in the shapes where nothing is deploying.** Sibling sweep: the leftover path lives in the shared `legRunner`, so all three of its users are covered — the index fallback, both expand-contract legs, and `deploy-ddl`. **Affected releases: v0.99.248 (`a0b8849a`, the expand-contract leg) through v0.115.0**; `sluice deploy-ddl` inherited the same refusal in v0.99.254 and the ADR-0148 index-build fallback in v0.99.255.

**A shared bulk-copy failure hint named `--resume` and `--exclude-table` to commands that have neither, so following it mid-incident exited 80 (Bug 230).** The hint registry is phase-scoped and a phase is shared: the bulk-copy catch-all said "use `--resume` to continue after fixing the offending table, or `--exclude-table=<name>` to skip it" and reached `migrate`, both `sync` cold starts (`sync start` and the fleet `sync run`) and `schema add-table`. Only `migrate` has `--resume`; `sync start` warm-resumes by default on re-invocation with the same `--stream-id`; `sync run` has neither flag because its table scope is a fleet-config key; and `schema add-table` has neither AND copies exactly one table, so the hint's "any earlier tables" premise was false there too — **while add-table's own `--help` says in as many words that there is no resume flag.** Loud, zero data loss, and byte-identical since the hint shipped.

**A hint's text is now resolved against the command the process is running, and the zero value is the safe one.** `migcore.SetRunningCommand` takes kong's own selected-node path at the composition root — derived from the model, not a roster, so it covers commands that do not exist yet — and a per-command override replaces the neutral text. The neutral text is the ZERO VALUE and names no command-specific flag, so a forgotten override costs precision, never correctness. Sibling sweep across the whole registry: the bulk-copy catch-all, the PlanetScale errno-3024 index wall, the errno-1105 direct-DDL block, the constraints foreign-key wall and the connect "database missing" hint are all fixed; the remaining entries are exempt because they name no flag at all. The gate grades every bare `--flag` in every text the registry can emit — per-command text against that command, neutral text against ALL commands — fail-by-default, no exemption list, three anti-vacuity floors, derived from the registry so a new hint is graded the moment it is added. **Why it is scoped to the registry rather than the whole tree is measured rather than asserted:** a census of every non-test Go string literal under `cmd/sluice` and `internal/` found 2100 bare `--flag` tokens, of which 58 occurrences name nothing on any sluice command — and nearly all of those are OTHER tools' flags (`pg_dump --blobs`, `az --resource-group`, `docker run --name`, `mysqld --local-infile`), so a union-level gate would need an exemption list about as long as its finding list. The genuine phantoms the census surfaced are fixed anyway and recorded as ungated. **Affected releases: v0.96.1 (`dc8c4e63`) through v0.115.0** for the bulk-copy hint; the PlanetScale index-fallback guidance strings carry the same defect from v0.99.255.

**And a gate written this cycle immediately caught itself under-covering.** A mutation swapping `selectedCommandPath` for kong's own `Node.Path()` stayed GREEN — the mutant applied, and the gate could not see it, because sluice's CLI has no branch-argument node and no command alias so the two renderings agree on all 47 selectable nodes. The doc comment justifying the hand-rolled version was an unverified premise about a dependency: true of kong in general, false of every command sluice has. Both halves are fixed — the gate now walks the whole model with an anti-vacuity floor instead of a five-argv list, and the actual difference is pinned against a synthetic alias-bearing model, so the mutant now fails and the comment says which of the two properties is load-bearing today.

**Four written invariants retracted, each with the test that now fails.** They were re-derived from the code rather than taken from the audit that flagged them; all four survived. **`restore`'s `DataOnly` dispatch was false twice over.** Its comment said "no-PK tables fall back to plain `WriteRows`", describing a branch that does not exist — the dispatch is a single `ir.IdempotentRowWriter` type assertion, a no-PK table upserts on a non-null UNIQUE, and a truly keyless one is refused by the engine. And the safety argument for the missing-surface branch — "a plain insert only collides on a PK the upsert would have updated to the same value" — **silently assumes a PK exists**: on a rotation-segment restore, a KEYLESS table has nothing to collide on, so a plain INSERT of segment N's snapshot over segment N-1's restored rows would double every row it re-carries, at exit 0. That branch is now a loud refusal resolved before a single goroutine or channel exists. **No registered engine reaches it today and the reason is structural rather than lucky** — `ChainRestore.Run` opens `OpenChangeApplier` before the segment walk, so only a CDC-apply target gets there, and every engine implementing that door also implements the idempotent writer while `sqlite`, the one target-capable engine without one, refuses that door — which is a premise about the engine REGISTRY that the backup package cannot import, so it is now checked by a docsync gate deriving both sets rather than asserted in a comment.

**The schema-anchor completeness claim named a consumer that does not exist.** `SchemaHistoryAnchors` has exactly one non-test caller in the tree and it is the writer-side assertion that cites it; the restore net rests on `lastApplied == end` and documents at its own definition that it does not trust the anchor. The sibling sweep found `Manifest.CDCPositionCommitsAfterRows` making the same false claim in its field doc, with no restore-side reader either. Both comments now say BELT, and a fail-by-default AST roster over every read of the two anchor symbols holds it. **"Newer sluice always reads older" is FALSE unqualified**, and it is a compatibility claim, so it gets the honest form rather than a softening: `verifySchemaHashes` recomputes an older link's fingerprint with THIS build's `ComputeSchemaHash`, which keys off no recorded algorithm version, so an untagged `ir.Index`/`ir.Column` addition partitions the corpus — two boundaries inside format v8 and one at v0.104.3. The behavioural evidence already existed in the cross-version cells and nothing was bound to it; it is deliberately NOT pinned with a golden hash, which is the self-referential shape item 104 already got wrong. **And ADR-0067 said "no code written yet" in the same squashed commit that shipped the code** (v0.88.0). The reusable half is WHY both ADR-status gates were blind to it: the status scan read only the first non-blank line of `## Status`, which there is an amendment blockquote, so the file parsed as declaring no status and fell out of scope entirely. The scan now skips blockquote lines with a parsed-file floor — **and the new gate immediately found the sibling: ADR-0071, the bounded-memory VStream pump, shipped in v0.99.3, cited by ten non-test files across five packages, with ADR-0095 built on top of it, still marked `Proposed.` for the whole of its shipped life.** Corrected in the same pass.

**Item 130's compaction memory bound was resting on a premise that had already rotted.** The emitted-side sink's bound is `max(B, I)` — the per-slot output budget and the largest input chunk — and it is the ADVERTISED budget only while `I <= B`. Its doc argued that at length and concluded that the degraded case was the normal one, on two cited facts: that the change-chunk byte ceiling was unreleased and that it had reached only one of the two production lanes. **Item 142 falsified BOTH in v0.114.0, one release later, and nothing failed** — two facts each pinned, the argument between them unpinned, which is the premise-naming rule's exact shape. The doc now states the true position in its two halves (a chain written by v0.114.0 or later gets the tight bound; one written by v0.113.x or earlier gets its largest-chunk bound, and the degraded branch stays live code because nothing rewrites an existing chunk), and a gate binds both change-chunk production lanes and the compaction budget to ONE symbol — over the symbol, not the value, so replacing the constant with a different symbol of the same value fails the binding while every behavioural pin and the pre-existing structural gate stay green. The behavioural gap item 142's own gate NAMED out loud is closed with four pins driving the real roll paths of both lanes. Separately, `PeakChunkBufferBytes` and `ChainsEvicted` now reach the operator's report: the arithmetic had always been computed and then dropped on the floor, so the field's own doc calling it "reported" was true only of a log line.

**Documentation and gate work, the phantom-command class closed on the docs side.** `sluice sync start --resume` is gone from 18 documentation files, deleted rather than substituted; the two worst were copy-pasteable blocks in `docs/use-cases.md` and `docs/cutover.md`. Instances that merely NAME the phantom in order to say it does not exist are left standing, because a notice is the legitimate way to reference an absent flag and rewriting those would delete the warning. **Found in the record itself:** ADR-0030's own 2026-08-06 correction note, and the audit backlog, both said `--resume` is real on "migrate and restore" — `restore` has no `--resume`, it is not among its 41 flags. A correction note carrying its own factual error is this whole class one level up. **Three more phantoms nobody had listed:** `docs/use-cases.md` carried a procedure block in which three of four commands do not exist — `backup start`, `backup retain --rotate-at`, and `backup restore --from-chain-id` (`restore` is top-level, not a `backup` child) — and a phase-3 design doc positively ASSERTED the phantom's existence by declaring a real flag "mutually exclusive with `--resume`". The two runtime strings naming `sluice schema migrate`, a command that does not exist, are corrected in place; the v0.115.0 CLI-surface gate still cannot see them by its own documented rule, so that blind spot is narrowed rather than closed. And the pgtrigger `json[]` refusal told the operator to use `--exclude-column`, which sluice has never had — ADR-0177 records that it filters at namespace, table, row and value granularity and has no column surface at all — with the integration test asserting the phantom, so the flag was pinned rather than caught. `docs/type-mapping.md`'s `array_strategy: json | concat` override went the same way: **a config key that exists nowhere in the tree**, deleted and replaced with the per-path preflight scope.

**The "which driver can drive a PlanetScale MySQL host" claim now has a gate, because this was its THIRD correction.** `mysql.Engine.ValidateDSN` has refused a `*.connect.psdb.cloud` / `*.private-connect.psdb.cloud` host under any non-VStream flavor since v0.99.192 (`26212de5`) — the guard is `!usesVStream()`, so `mariadb` is refused too, which the code's own comment did not say. `docs/production-readiness.md` said the OPPOSITE outright; the README and the error-code table were true but partial in the same way; and the engine's `DefaultExcludePatterns` comment called the refused pairing "a legitimate configuration", which was true when written and which `ValidateDSN` falsified without anything re-checking. The new gate reads the suffix list out of the engine by AST, builds a DSN from each suffix, asks every registered DSN validator what it actually returns, and holds two markers in all three prose homes — the suffix list, and the FULL graded verdict map rather than a works-list, which would read as broader than it is. A second gate keeps the three-home list from becoming the next narrow gate: any non-archival markdown naming an endpoint suffix must be a gated home or exempt with a written reason, and a stale exemption fails too — it fired for real during the change.

**And a `perf-parity-checker` pass before the tag retracted two more claims the code had already retracted.** The matrix said a `backup compact`'s degraded peak bound "is TODAY'S NORMAL case" — the same doc rewritten inside this very release says it is the LEGACY-chain case, so an operator pricing a compaction on a modern chain was being told the worst case was the normal one. And it carried "D1-as-target ABSENT (stage-local instead)", wrong twice over: there is no D1 target at all, and `--stage-local` is a D1 SOURCE mechanism that was never a write path. **That was the FOURTH home of a sentence v0.115.0 already retracted, and row 32 of the same file already said "there is no D1 target" — the file contradicted itself.** The target-engine gate now states, where it is defined, that its marker lives in exactly one file, because a gate whose coverage is narrower than its claim's SPREAD does not merely miss a home, it stops anyone from checking the others. The same pass priced item 140's real entry cost, which the matrix understated two ways, and re-derived five drifted `file:line` citations by symbol lookup rather than by offset — they had moved in different directions and by different amounts, so a uniform shift would have encoded the error. That recurrence is now filed as its own gap: **no gate reads the `file:line` cites in `docs/` at all**, since the existing code-pointer test walks `internal/` only.

**And the roadmap's own record was repaired.** The 2026-08-05 audit's invariant sweep — 17 unverified claims and 5 suspect-false ones, each with a proposed sub-20-line check — existed ONLY in a gitignored scratch file, while the tracked backlog carried the three COUNTS and nothing else. A count cannot be worked and cannot say which items are already closed, which is the same durability failure the tracked file exists to prevent, reproduced one level down. It is now enumerated in tracked content, and enumerating it surfaced three corrections that summarising had hidden — including that of the five suspect-false claims ONE was closed and FOUR were open, where the summary read as two of five. Stale status markers were ground-truthed with `git tag --contains` rather than read off a header: item 82 shipped in v0.102.1 and had read OPEN for THIRTEEN releases, and item 142's behaviour shipped in v0.113.0 on both change lanes with only its gate in v0.114.0 — a single v0.114.0 stamp told a reader on v0.113.x they were exposed when they were not. Structurally, an orphaned `<details>` wrapper left by an earlier heading cleanup was swallowing two whole roadmap items inside a third's collapsed disclosure on GitHub; that is the SECOND instance of the same shape in three days, so the standing check is recorded with the fix and the whole file swept. And one test fixed itself: item 150's door walk ranged over a MAP while its own comment said "every door, in phase order", so it passed or failed on Go's randomised map iteration — and its failure mode was worse than the flake, because the loop reported ANY error as the item-150 refusal regressing, which is exactly the shape that gets written down as a real finding.

## Changed

**One new error code: `SLUICE-E-PS-DEV-BRANCH-NOT-ADOPTABLE`.** It is the RESIDUE of the item-108 fix, not its main effect — adoption is the normal outcome and raises no error. The code fires when a re-run finds its own deterministic PlanetScale dev branch and cannot adopt the deploy request on it: there is none, there is more than one, it merges into a different production branch, it was never deployed, or it ended in a terminal failure. It is registered, carries a Meaning/Remedy row in `docs/operator/error-codes.md` and its byte-equal mirror in the code, and its message tells you to delete the branch only in the shapes where nothing is in flight.

**A `json[]`, `jsonb[]` or `bytea[]` source column bound for a MySQL-family target is now `migrate`-only.** A continuous `sync` cold start and `schema add-table` REFUSE it up front, naming the column, before any data moves — including when the column is declared as a DOMAIN over the array. Every other array element family — text, numeric, temporal, uuid, network, and the native scalars — syncs normally. The refusal is a plain preflight error rather than a coded one; the leaf refusal that backstops it is `SLUICE-E-VALUE-UNREPRESENTABLE`, and it now carries the preflight's own remedies so a mid-flight arrival reads the same as a cold-start one.

**The value a MySQL-family target stores changes on three lanes.** A `json[]`/`jsonb[]` element arriving as a decoded array is now the document's own text inside a JSON string where it was previously base64 — the headline fix. A `bytea[]` element arriving as a PostgreSQL array TEXT LITERAL (the `--type-override <col>=jsonb` lane) is now base64 where it was previously the `\x`-hex rendering, which is what puts all three arrival shapes on one encoding. And an empty array on a plain `ir.Array` column arriving as bytes now lands as `[]` where it landed as the JSON object `{}`. A `json[]` element on the literal lane is UNCHANGED — it was already the document's text — and every other element family is byte-identical to before.

**Two array values that previously reached a MySQL-family target now refuse.** A `[]byte` leaf on an element family that has no byte-shaped leaf, and a `NaN`/`±Infinity` element, both under `SLUICE-E-VALUE-UNREPRESENTABLE` naming the column. So does a `bytea[]` literal token that is not the `\x`+even-hex form `bytea_output = hex` produces, where it previously stored its own ASCII.

**A SQLite target now ACCEPTS a name pair that differs only in NON-ASCII case**, where v0.114.0 (indexes) and v0.115.0 (tables and views) refused it. ASCII case pairs are still refused on all three object kinds — that is the silent-no-op class those releases closed and it is unchanged.

**A re-run that finds a leftover PlanetScale dev branch now ADOPTS its deploy request instead of refusing.** It joins the same poller a fresh run uses, with the same progress narration, the same fast-fail on a terminal state, the same keep-the-branch rule and the same finalize/cleanup tail. A deploy request that already deployed is finalized and its branch cleaned up. A never-deployed one is still refused, and that refusal is deliberately new: sluice adopts only an already-issued deploy, because the pre-deploy freshness and blast-radius promises cannot be re-established for a branch it did not provision this run.

**Runtime hint text now varies by the command you invoked.** The bulk-copy, index-wall, direct-DDL, constraint-wall and connect hints name only flags the running command accepts; commands without a sharper text get command-neutral prose that names no command-specific flag at all. `sluice backup compact` gains two fields on its report (`chains_evicted`, `peak_chunk_buffer_bytes`), printed unconditionally so an operator diffing two runs can see one of them hit its ceiling.

**A rotation-segment (`DataOnly`) restore into a target whose row writer has no idempotent form now REFUSES.** No registered engine reaches it — every CDC-apply target implements the idempotent writer, and `sqlite`, the one target-capable engine without one, refuses the change-applier door and so cannot reach a data-only segment at all — so this is a belt for the day that stops being true, held by a gate that derives both engine sets independently.

## Compatibility

**No flag was added, renamed or removed, no on-disk format changed its version, no backup chain is repartitioned or crosses an epoch boundary, and no IR type gained a field that rides the chain schema fingerprint.** Upgrading from v0.115.0 is drop-in in that mechanical sense. One error code is new, one previously-working configuration is now refused, one previously-refused configuration is now accepted, and several MySQL-target array values change their stored form — those are the parts that need reading.

**`bytea[]` over CDC into a MySQL-family target is now REFUSED, and this is a LIMITATION rather than a fix.** It worked before and it worked consistently: base64 on the cold copy and base64 on every pgoutput apply, both lanes agreeing. It is refused now because the change applier cannot tell a `bytea[]` from a `json[]` — both are the same `JSON` column in the target's catalog — and letting `bytea[]` through would mean the applier deciding "these bytes are bytes, not a document", which is a guess with no evidence behind it. The refusal fires at `sync` cold start and `schema add-table`. **A stream started on v0.115.0 or earlier carrying such a column will stop on its first warm resume after upgrading** — that is the upgrade break, and the message now names the family as sync-unsupported and carries the same remedies the preflight does, so the operator is not left with a bare per-value type complaint. `sluice migrate` carries the column faithfully and is the documented remedy, along with `--exclude-table`.

**`json[]` / `jsonb[]` over CDC into a MySQL-family target is also now refused, and that direction is a fix** — it previously ran to completion while storing base64 tokens.

**A `migrate` into a MySQL-family target stores a different value than v0.115.0 did, on three specific lanes.** A `json[]`/`jsonb[]` column with no `--type-override` changes from base64 tokens to the documents' text. A `bytea[]` column WITH a `--type-override <col>=jsonb` changes from `["\\xdead"]` to `["3q0="]`. An empty array on a plain `ir.Array` column arriving as bytes changes from `{}` to `[]`. **A `json[]` column with a `--type-override <col>=jsonb` is UNCHANGED** — that lane already stored the document's text and was never affected. If you re-run a migration over a target you already populated, expect the first two to differ; if you have a downstream consumer parsing the `\x`-hex form out of an overridden `bytea[]` column, it needs updating. Every other array element family is byte-identical to before.

**Postgres targets, SQLite targets and the backup/parquet encoders are untouched by all of this** — the Postgres writer already had a per-family arm from items 141/145, a SQLite target refuses `ir.Array` at schema emit so no value ever arrives, and the backup and parquet encoders route each leaf through its own encoder.

**A SQLite target no longer refuses a name pair differing only in non-ASCII case.** `café` and `CAFÉ`, `idx_é` and `idx_É`, `Café_Order` and `CAFÉ_ORDER` are two objects on a real SQLite target and are now allowed through — where v0.114.0 refused the index case and v0.115.0 refused the table and view cases. ASCII case pairs are still refused on all three object kinds, and MySQL-family targets are UNCHANGED: their fold imitates a server that does fold non-ASCII case under `lower_case_table_names != 0`, measured on `mysql:8` and `mariadb:11.4`, and sharing SQLite's narrower rule there would be an under-refusal in the silent direction.

**A `migrate --resume` (or any re-run) against a leftover PlanetScale dev branch now adopts instead of refusing.** So does a re-run of `sluice deploy-ddl` and of either expand-contract leg. The case that is NEWLY refused rather than newly accepted is a leftover branch whose deploy request was never issued: nothing is building there, the re-run costs only a re-provision, and the two pre-deploy guarantees cannot be re-established for a branch this run did not provision. Both outcomes are loud and named; neither can lose data.

**A `sync` cold start whose source carries a DOMAIN over `json[]`/`jsonb[]`/`bytea[]` now refuses at preflight** where it previously started and failed mid-stream at the writer. Same verdict, earlier and cheaper.

**Runtime hint and message text changed in several places.** No behaviour rides on it, but if you have automation matching on hint prose rather than on `SLUICE-E-*` codes, the bulk-copy, index-wall, direct-DDL, constraint-wall and connect hints now differ per command. `sluice backup compact` emits two additional log fields. The cold-copy and restore paths are otherwise byte-identical.

**Open and NOT fixed here, named so they are not discovered as surprises.** **The largest one is a residual this release scoped rather than closed, and it predates the release:** over a `postgres-trigger` source, a `bytea[]` or `json[]` array reaching the CDC applier on WARM RESUME or via a mid-stream `ALTER TABLE … ADD COLUMN` is **silently divergent** rather than refused — that reader's payload decode produces no `[]byte` leaves, so the writer's refusal cannot fire, and a `bytea[]` element lands as `["\\xdead"]` where the cold copy stored `["3q0="]`. Nothing is destroyed and the two halves of one column simply disagree. It is not closed because on that door the value is byte-identical to a `jsonb` column holding an array DOCUMENT and to an ordinary `text[]`/`int[]` change, both of which are correct today, and sniffing the content to separate them is what item 135 forbids. Cold start IS covered, because the preflight reads the SOURCE schema whatever the source engine and `sluice trigger setup` refuses `json[]`/`jsonb[]` outright, so the exposure is a stream started before v0.116.0 or a column added to a live one. The `postgres` (pgoutput) and scan doors are loud on the same paths, and the multi-database fan-out is loud by construction because both of its possible source engines trip the refusal. **The rest:** the `sluice schema migrate` phantom is corrected in both string literals but the CLI-surface gate still cannot see that class by its own documented rule, so it is narrowed, not closed; the bare-flag gate is scoped to the hint registry rather than the whole tree, and the eight genuine phantoms the tree-wide census found are fixed but ungated; no gate reads the `file:line` citations in `docs/` at all, which is why two consecutive passes each re-derived a batch of them by hand; item 130's degraded compaction bound stays live code for chains written by v0.113.x or earlier, because nothing rewrites an existing chunk; `backup.SourceEngineCommitsAfterRows` is a phantom SYMBOL cited in `manifest.go` and existing nowhere, filed with a gate proposal rather than fixed; and the `json[]`/`bytea[]` encodings onto a MySQL target remain ONE-WAY, so a later MySQL → Postgres migration of such a column lands a `jsonb` document holding those strings, not the original array type — a consequence of MySQL having no array type, now written down in `docs/type-mapping.md`.

## Who needs this — action required

- **Anyone who has migrated a PostgreSQL `json[]` or `jsonb[]` column into a MySQL, MariaDB, PlanetScale or Vitess target WITHOUT a `--type-override` on that column. Go look at the values; do not trust a row count and do not trust `verify`.** Every element was stored as base64 of the document rather than the document, at exit 0, with no failed statement anywhere in the run. **`sluice verify` cannot catch this on any depth** — `--depth count` compares counts, which did not change, and `--depth sample` REFUSES a cross-engine pair outright, so there is no depth that would have looked at the value. The one-query check on the target is `SELECT JSON_EXTRACT(<col>, '$[0]') FROM <table> LIMIT 1`: an affected column returns a base64 token like `"eyJhIjoxfQ=="` where a correct one returns the document's text. **The good news, and it is load-bearing: the loss is fully REVERSIBLE from the target alone.** Base64 is a faithful projection and the array's nesting, NULL elements and empty arrays all survived it, so `FROM_BASE64()` on each element recovers the exact document — or re-run `sluice migrate` for those tables on v0.116.0, which lands the text form directly. **Affected from v0.69.0 through v0.115.0.** **A column you migrated WITH `--type-override <col>=jsonb` was never affected** — that lane stored the document's text on every release — so it needs no audit. A `postgres-trigger` source was never exposed either: it refuses a `json[]`/`jsonb[]` table at `trigger setup`, before any trigger is installed.
- **Anyone running a continuous `sync` from PostgreSQL into a MySQL-family target with a `json[]`, `jsonb[]` or `bytea[]` column in scope. That stream will now refuse rather than run — read this before you upgrade.** A cold start or `schema add-table` refuses at preflight, naming the column, before any data moves. A stream you warm-resume will instead stop at the first change touching that column, with a message that now names the family as sync-unsupported and carries the same remedies. For `json[]`/`jsonb[]` this is a fix — it was storing base64 on both lanes, so re-verify the already-applied rows as above. **For `bytea[]` it is a genuine capability loss:** that column synced correctly, consistently base64 on both lanes, and sluice now refuses it because the applier cannot distinguish it from a `json[]`. The remedies are `sluice migrate` for a one-shot copy of that table, or `--exclude-table` to keep the stream running without it.
- **Anyone running a continuous `sync` from a `postgres-trigger` source into a MySQL-family target where a `bytea[]` column was added to a live stream, or the stream was started before v0.116.0. Compare that column's elements between source and target; nothing will have told you.** This is the residual named above and it PREDATES this release: over the trigger door the element arrives as PostgreSQL's `\x`-hex text and lands as `["\\xdead"]` where the cold copy stored `["3q0="]`. Nothing is destroyed — both forms decode to the same bytes — so the repair is to normalise the column downstream or re-run `sluice migrate` for that table. sluice does not refuse it, and the reason is written down: on that door the value is byte-identical to values that are correct and common, so a refusal would break them. A cold start on v0.116.0 refuses the configuration up front.
- **Anyone who migrated a `bytea[]` column into a MySQL-family target using `--type-override <col>=jsonb`, and has a downstream consumer parsing the `\x`-hex form. That column's elements are now base64.** No data is lost in either direction and both forms are reversible, but the stored text changes, so update the consumer or re-run the migration and re-point it. A `json[]` column overridden the same way is unchanged.
- **Anyone who migrated into SQLite and was refused for a name collision on a pair that differs only in NON-ASCII case — `café` vs `CAFÉ`, `idx_é` vs `idx_É`. Upgrade and re-run; there is nothing to verify.** The refusal was wrong: those are two distinct objects on a real SQLite target, and sluice was applying Go's Unicode fold where SQLite folds ASCII only. It was a loud refusal naming a rename, never a silent loss, so no data was ever affected — if you renamed a source object to get past it, you can rename it back. Affected from v0.114.0 for index names and v0.115.0 for table and view names. ASCII case pairs are still refused, correctly.
- **Anyone whose PlanetScale run refused with "dev branch already exists — a previous run left it behind" while a deploy request on that branch was still building. Do NOT delete the branch; upgrade and re-run.** sluice now finds that deploy request and joins the same poller, so a multi-hour VReplication index build that is 78% done is resumed rather than discarded. Following the old advice would have thrown that work away — and the PlanetScale API refuses the delete outright while the deployment runs, which is the platform being right. If the re-run instead reports `SLUICE-E-PS-DEV-BRANCH-NOT-ADOPTABLE`, read which shape the message names: it tells you to delete the branch only when nothing is in flight. Affected from v0.99.248 through v0.115.0. **Nothing to re-verify** — this was a refusal, not a data path.
- **Anyone who followed a recovery hint sluice printed during a failed bulk copy, or a PlanetScale index-wall message, and got `unknown flag` back. The command line was wrong, not your invocation.** There has never been a `--resume` on `sluice sync start` — it warm-resumes by default when re-invoked with the same `--stream-id` — and `sync run` and `schema add-table` have neither `--resume` nor `--exclude-table`. **Nothing to re-verify; no data was affected**, this was always a loud failure whose printed remedy was unrunnable. Two runtime messages still name `sluice schema migrate`, which is not a command; read that as "run your schema migration".
- **Anyone who read `docs/production-readiness.md` and concluded that `--source-driver mysql` can drive a `*.connect.psdb.cloud` host. It cannot, and has not been able to since v0.99.192.** That doc said the opposite; the refusal is `SLUICE-E-DRIVER-HOST-MISMATCH` and it covers both non-VStream flavors, `mysql` and `mariadb`. Pass `--source-driver planetscale` / `--target-driver planetscale` (or `vitess` for self-hosted Vitess). **Nothing to re-verify** — the refusal fires from the DSN string alone before any connection, so a run that started was always on a correct driver.
- **Anyone who priced a `sluice backup compact` off the perf-parity matrix, or read that sluice supports a D1 target, or configured `array_strategy` in a config file.** The compaction peak-memory row described the legacy-chain worst case as the normal one; a chain written by v0.114.0 or later gets the tight bound. There is no D1 target and never was — `d1` is a migrate SOURCE, and a D1-bound migration produces a SQLite `.db` file you then load with `wrangler d1 import`. And `array_strategy` was never implemented, so a config carrying it was doing nothing; use `--type-override` to land the column as text instead.
- **Anyone relying on ADR-0067 or ADR-0071's status line to decide whether a design is built. Both were wrong; both are corrected.** ADR-0067 shipped its code in v0.88.0, in the same squashed commit as the ADR that said no code was written; ADR-0071's bounded-memory VStream pump shipped in v0.99.3 and read `Proposed.` for its entire life while ten non-test files cited it and a later Accepted ADR was built on top of it. Nothing changed in the code, and a gate now fails when a Proposed ADR is cited by non-test code.
- **Everyone else: nothing to do.** A run with no PostgreSQL array column bound for a MySQL-family target, no SQLite non-ASCII name pair, and no PlanetScale deploy-request leg is unaffected by every item on this list. The rest of this release is a relaxed refusal, corrected runtime and documentation text, two new log fields, and five written claims replaced by tests that fail when they break.
