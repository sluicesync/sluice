# sluice v0.156.3

**CRITICAL fix — MySQL, MariaDB, PlanetScale and Vitess change streams now carry text in non-UTF-8 charset columns (`latin1`, `cp1251`, `sjis`, `gbk`, `utf16`, …) as the same text the bulk copy carries, and backups refuse a text value that is not valid UTF-8 instead of writing it as `�`.** Through v0.156.2, `backup stream` and `backup incremental` of such a column stored every non-ASCII changed value as `�` (U+FFFD) or as a different character, silently, and restored it that way; `sync` landed some values as a different character at exit 0 and missed rows keyed on them. Separately, any backup (`backup full` included) of a source holding bytes that are not valid text in a text column sealed them as `�`. This release converts change-stream values by the charset they were written in, adds loud refusals (`CHARSET-NOT-DECODABLE`, `BACKUP-VALUE-NOT-UTF8`, a charset-DDL replay guard) where a value cannot be carried faithfully, and fixes the remedy printed on a failed added-column backfill (Bug 290). **Not a silent drop-in:** streams and backups that used to pass can now refuse loudly, and one narrow set of windows is silent where v0.156.2 was exact — read **Compatibility**. Upgrading does not repair rows or chains an earlier release already wrote; read the repair notice below.

## Repair notice — if you were affected

Upgrading stops the loss; it does not find or fix what an earlier release already wrote. The bulk copy (`migrate`, a `sync` cold start, the rows a `backup full` copied from a MySQL-family source) was always exact — the damage is in change-stream values and in backups of invalid text.

1. **Backup chains (`backup stream`, `backup incremental`) of a MySQL, MariaDB, PlanetScale or Vitess source with a text column declared in a non-UTF-8 charset, captured by v0.156.2 or earlier (CRITICAL, silent).** Every non-ASCII value such an incremental recorded in such a column is stored as `�` or as a different character, and the chain cannot give it back. **Take a fresh full backup with v0.156.3**, and compare the affected columns of any target restored or `sync from-backup`-seeded from the old chain against the source, repairing from the source. To find the chains: chain restore, `sync from-backup` and `backup verify` now WARN with `LEGACY-CHARSET-INCREMENT` for each such incremental, naming the table and columns. Restoring a bare full and `export-as-parquet` read no incremental and do not WARN.
2. **`sync` from such a source, on v0.156.2 or earlier (silent for part of the value space).** A change-stream value whose raw stored bytes happened to be valid UTF-8 landed as a different character at exit 0 (a `latin1` `Ã©` as `é`, a `cp1251` `Г©` likewise; every non-ASCII `swe7` value, because `swe7` is not ASCII-compatible), and a later UPDATE or DELETE keyed on such a value never found its row. Values whose bytes were invalid UTF-8 failed loudly at the target. Compare those columns against the source for rows changed after cutover and repair from the source, or re-copy the table (`--restart-from-scratch`).
3. **Any backup (`backup full`, `backup incremental`, `backup stream`) of a source whose text columns hold bytes that are not valid UTF-8** — a SQLite `TEXT` value written from raw bytes (measured: `backup full` of `CAST(x'636166e9' AS TEXT)` sealed `caf�` at exit 0), a Postgres `SQL_ASCII` database, legacy invalid bytes in a MySQL `utf8mb4` column. Those values were written as `�`; `backup verify` agreed with the chunk and a restore landed `�` at exit 0. Compare the affected text columns of anything restored from such a backup against the source — a `�` there is a lost value — and repair the source value (or store it as `BLOB`/`bytea`) before taking a new backup, which will now refuse on it.

## Fixed

**MySQL, MariaDB, PlanetScale and Vitess sources: change-stream values of non-UTF-8 charset columns are converted by the charset they were written in (CRITICAL for backup chains, silent; HIGH for `sync`; GC-37 (j)).** The bulk copy reads over a `utf8mb4` connection, so the server converts every value first; the binlog row image (MySQL 8.0, MariaDB 11.4) and vttablet's VStream row event carry a character column's stored bytes instead — measured for every non-UTF-8 charset MySQL ships, on all three lanes — and every decoder passed those bytes on as a Go string. The binlog and VStream decoders now convert every character value, before-images and keys included, by the column's charset: a binlog value by the TABLE_MAP event's per-column collation (what it was *written* in), named through the source server's own collation table, and a VStream value by the field's collation. Conversion tables cover every 8-bit charset, `latin1` as MySQL's cp1252 variant, the Japanese, Korean and GB charsets, `tis620` and the UTF-16/UTF-32/UCS-2 family, each graded against the server's own `CONVERT(… USING utf8mb4)` over its whole code space on MySQL 8.0 and MariaDB 11.4 (`TestColumnCharsetDecode_MatchesTheServer_MySQL`, `TestColumnCharsetDecode_MatchesTheServer_MariaDB`). What cannot be converted faithfully refuses with `CHARSET-NOT-DECODABLE`, naming the table, column and charset: a non-ASCII `big5` value (no available table matches MySQL's; the common one disagrees in 267 places), on PlanetScale/Vitess any non-ASCII value in a `gbk`/`big5`/`tis620`/`gb18030` column (vttablet sends those with collation 0, so the stream cannot tell the charset — measured), and the `tis620` bytes MySQL itself converts to U+FFFD. Pure-ASCII values in those columns stream normally. The remedy is convert-then-re-snapshot (`--restart-from-scratch`), never convert-and-resume, and the refusal does not print the value.

**PlanetScale/Vitess `ENUM`/`SET` and `_bin` collations.** vttablet sends a non-UTF-8 `ENUM`/`SET` cell as UTF-8 label text in CDC but as its stored bytes in the COPY phase, with identical field metadata, so a COPY cell holding `Ã©` in a latin1 `ENUM('é','Ã©')` landed as the other member `é`, silently. Each such cell is now resolved against the column's own label list; a cell that is a member under both readings refuses as ambiguous, and the empty string MySQL stores for an invalid ENUM value (index 0) is a member of every ENUM. vttablet also types a `CHAR`/`VARCHAR`/`TEXT` column collated `latin1_bin`, `cp1251_bin`, `utf8mb4_bin`, … as `BINARY`/`VARBINARY`/`BLOB`, and sluice carried every such cell as bytes; it is now decoded as text by that collation (the declared column type decides, so a true binary column stays bytes), and a `_bin` `ENUM`/`SET` goes through the label resolver too. This also brings a `latin1_bin` primary key's lane routing in line with the bulk copy. On the binlog an ENUM/SET cell is an index or bitmask and was unaffected.

**Replays across a charset change.** On MySQL 8 (default `binlog_row_metadata=MINIMAL`) and on MariaDB under `MINIMAL` or `FULL`, a stream replaying history recorded before an `ALTER … CHARACTER SET` — a warm resume, a lagging stream, a cold-start handoff whose copy spanned the DDL — decodes the old bytes by the old charset, value-exact (`TestCDCReplay_AcrossCharsetDDL_DecodesWritten_MySQL`); only a collation ID neither the source nor sluice can name refuses with `SLUICE-E-CDC-SCHEMA-REPLAY-MISMATCH`. Two sources record no written charset: MariaDB under its default `binlog_row_metadata=NO_LOG`, and PlanetScale/Vitess, whose vttablet reports a replayed row's *current* collation. There each table with non-UTF-8 text columns logs `CHARSET-HISTORY-UNRECORDED` once, and a new charset-DDL guard refuses a replay across a change INTO a non-UTF-8 charset: when the stream reaches an `ALTER` that sets one (`CONVERT TO CHARACTER SET`, or `MODIFY`/`CHANGE` with an explicit `CHARACTER SET` or `COLLATE`, parsed after MariaDB-only prefix syntax such as `ALTER ONLINE`, `IF EXISTS`, `WAIT n` is normalised), it compares the charset and collation the `ALTER` sets with the shape it has been decoding the table by, and a shape that already matches means the stream is replaying — `SLUICE-E-CDC-SCHEMA-REPLAY-MISMATCH`. The rows replayed before that `ALTER` were already emitted, so the refusal's hint depends on the command: `sync` re-snapshots the table (`--restart-from-scratch`); `backup stream` and `backup incremental` take a fresh full backup. A backup window that ends *before* the stream reaches the `ALTER` is refused before it commits: both capture lanes read the source schema at the start and end of every window, and when a column's charset changed into a non-UTF-8 charset between the two while the reader decoded that table by the new charset, the window refuses with `CHARSET-HISTORY-UNRECORDED` and the fresh-full remedy (measured on MariaDB NO_LOG: a two-run `backup incremental` that committed misdecoded rows at exit 0 now refuses on the first run, and a `backup stream` that committed 9 replayed change records commits none). A change into `utf8mb4`/`utf8mb3`/`utf8` is not guarded, so routine UTF-8 DDL (a collation change, an ORM restating a column) never refuses a live stream (`TestCDCLive_CharsetDDL_NoGuardRefusal_MariaDBNoLog`, `TestVStream_CDCCharsetDDLLive_RoutineDDLNoRefusal`); its replay carries old bytes as v0.156.2 did.

Pinned per charset × {`CHAR`, `VARCHAR`, `TEXT`, `ENUM`, `SET`} × {insert, NULL, update and delete by a non-ASCII text key} on the binlog (MySQL, MariaDB) and VStream lanes (`TestCDCCharsetDecode_Binlog_MySQL`, `TestVStream_CDCCharsetDecode`, `TestVStream_CopyCharsetDecode_FourStreams`), the replay guard on both no-record sources (`TestCDCReplay_AcrossCharsetDDL_GuardRefuses_MariaDBNoLog`, `TestVStream_CDCCharsetDDLReplay_GuardRefuses`, `TestBackupStream_CharsetDDLReplay_RefusesBeforeCommit_MariaDBNoLog`, `TestIncrementalBackup_CharsetDDLReplay_WindowEndsBeforeALTER_Refuses_MariaDBNoLog`), and end to end through `sync` and a `backup incremental` chain restore (`TestSync_LegacyCharsetColumns_MySQLToPostgres`, `TestIncrementalBackup_LegacyCharsetColumns_ChainRestore_ToPostgres`).

**Backups (`backup full`, `backup incremental`, `backup stream`): a text value that is not valid UTF-8 refuses the capture with `BACKUP-VALUE-NOT-UTF8` instead of being written as `�` (CRITICAL, silent).** Every backup chunk is JSON, and Go's JSON encoder writes each invalid-UTF-8 byte as U+FFFD without an error. Both chunk write cores — the data-chunk writer behind `backup full` and the change-chunk writer behind incrementals, streams, the `ADD COLUMN` fill and smart compaction — now check every string before encoding (a text value, strings inside lists and maps including map keys, and any string another Go type would serialise) and refuse naming the table, column, change image and nested position. A `backup stream` stops on the refusal rather than retrying, and no manifest is committed for the refused window. Binary values (carried as base64) and a JSON column arriving as raw bytes are not inspected; a literal `�` that is really in the source's text is valid and is carried as before. The refusal is deliberately not byte-exact carriage: no target except SQLite can store such a value (Postgres refuses it with 22021, strict utf8mb4 MySQL with 3988), and a new value encoding would fail an older binary only mid-restore. Pinned by `TestChunkWriter_RefusesNonUTF8String`, `TestChangeChunkWriter_RefusesNonUTF8String`, `TestBackupCodec_ValidUTF8RoundTrips` and `TestIncrementalBackup_NonUTF8StringRefusesTheWindow`.

**`sync`: a failed added-column backfill's own ERROR line names the source-values repair (Bug 290, loud but misleading).** v0.156.2 fixed the startup refusal and the fleet supervisor's log for Bug 289, but the backfill failure itself still appended the generic hint "apply the schema change yourself, then resume". The `ALTER` has already landed by then and the attempt ends as `ADD-COLUMN-BACKFILL-INCOMPLETE`, so following that line left the rows that predate the `ADD COLUMN` holding the target's fill. It now says the run ends with that refusal and gives the refusal's repair — copy the added column's values from the source (or re-copy), then acknowledge the fingerprint — on single-stream forwarding and on the Shape A fan-in alike. The two siblings on the same path that refuse *before* the `ALTER` (an unclassifiable shape, a write-ahead record that cannot be written) keep the generic hint deliberately. The next restart already refused with the right repair on v0.156.2, so no rows were lost to this line alone. Found by the v0.156.2 regression cycle.

## Compatibility

**New loud refusals, on purpose — a stream or backup that ran on v0.156.2 can stop on this release:**

- **`CHARSET-NOT-DECODABLE`** stops a MySQL-family change stream on a non-ASCII `big5` value; on PlanetScale/Vitess on a non-ASCII value in a `gbk`, `big5`, `tis620` or `gb18030` column (collation 0); on the `tis620` bytes MySQL maps to U+FFFD; and on a PlanetScale/Vitess `ENUM`/`SET` cell that is a member under both readings (rename one label, or exclude the table). To proceed, convert the column to `utf8mb4` on the source **and** re-snapshot (`--restart-from-scratch`), or exclude the table.
- **`SLUICE-E-CDC-SCHEMA-REPLAY-MISMATCH`** stops a stream on MariaDB NO_LOG or PlanetScale/Vitess replaying across a change into a non-UTF-8 charset, and a backup window that decoded rows by the new charset before reaching the `ALTER`. False positives, loud: an `ALTER` setting a non-UTF-8 column to the charset and collation it already has, a replayed collation-only change on such a column, and a charset `ALTER` the parser cannot classify on a table with non-UTF-8 columns all refuse, live or not.
- **`BACKUP-VALUE-NOT-UTF8`** stops any backup that meets a text value that is not valid UTF-8 — including a SQLite `TEXT` column holding raw bytes. `backup full` can skip it meanwhile with `--exclude-table` or `--redact <table>.<column>=null`; `backup incremental` and `backup stream` have no such option and stop until the source value is repaired or the column is stored as `BLOB`/`bytea`.

**Windows that remain, on MariaDB under `binlog_row_metadata=NO_LOG` and on PlanetScale/Vitess only.** For a change from `utf8mb4` into a non-UTF-8 charset these windows are **silent where v0.156.2 was exact** (it carried a `utf8mb4` value's stored bytes, which are its UTF-8); for a change between two non-UTF-8 charsets they are silent where v0.156.2 was loud or silent by the bytes. If a stream was behind such a change, re-snapshot (or take a fresh full backup) yourself:

- a `sync` restart between the replayed rows and the `ALTER` — the next run reaches the `ALTER` with no decoded rows to compare, and the backup window check does not reach `sync`;
- a backup window that decoded the replayed rows after an earlier window had already recorded the charset change (its start and end schema agree);
- a second charset change to a table the same reader session already crossed an `ALTER` on;
- a `MODIFY`/`CHANGE` that changes a column's charset implicitly (no `CHARACTER SET`/`COLLATE`, taking the table default), and a table-default change (`ALTER TABLE … DEFAULT CHARSET`);
- an online schema change — gh-ost, pt-online-schema-change, PlanetScale deploy requests and Vitess online DDL — which swaps in a shadow table with a `RENAME` and never streams an `ALTER … CHARACTER SET` on the table;
- an unclassifiable statement that names no charset keyword at all.

**On MariaDB, set `binlog_row_metadata=MINIMAL` (or `FULL`)** so each row event records the charset it was written in and replays across a charset change are exact. It applies only to binlog events written after the change; history already written stays unrecorded. MySQL 8 records it by default. See `docs/operator/migrating-legacy-mysql.md`.

**No backup format, control-table or flag change.** The `LEGACY-CHARSET-INCREMENT` WARN is new on chain restore, `sync from-backup` and `backup verify` of pre-v0.156.3 MySQL-family incrementals with non-UTF-8 text columns; it does not fail the command. A failed load of the source's collation table is retried after 30 s rather than cached for the reader's life.

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale, billable cluster) and `d1verify` (live Cloudflare D1) suites were not dispatched; each provisions billable or live infrastructure and runs only on the operator's call. The VStream arms of this release — collation-driven decoding, the collation-0 refusal, the COPY/CDC `ENUM`/`SET` label resolution, `_bin` decoding and the replay guard — were measured on vttestserver in the per-PR vstream integration job, not against PlanetScale. The SQLite/D1 impact of this release is the new `BACKUP-VALUE-NOT-UTF8` refusal on the backup write path, pinned locally.

## Who needs this — action required

- **Anyone with `backup stream` / `backup incremental` chains of a MySQL, MariaDB, PlanetScale or Vitess source that has text columns in a non-UTF-8 charset.** Take a fresh full backup with v0.156.3; repair any target restored from the old chain against the source. `LEGACY-CHARSET-INCREMENT` names the affected chains and columns on restore or `backup verify` (repair notice item 1).
- **Anyone who ran `sync` from such a source.** Compare the non-UTF-8 text columns against the source for rows changed after cutover, and repair or re-copy (item 2).
- **Anyone who backed up a source whose text columns can hold invalid UTF-8** (SQLite `TEXT` from raw bytes, Postgres `SQL_ASCII`, legacy bytes in MySQL `utf8mb4`). Check restored text for `�` against the source (item 3); expect `BACKUP-VALUE-NOT-UTF8` until the source is repaired.
- **MariaDB sources on the default `binlog_row_metadata=NO_LOG`, and PlanetScale/Vitess sources, that change a column's charset while a stream or backup is behind.** Read the remaining windows under **Compatibility**, and on MariaDB switch to `MINIMAL` or `FULL`.
- **Anyone who followed a failed backfill's ERROR line on v0.156.2** and applied only a target change: repair the added column from the source for the rows that predate the `ADD COLUMN` (the restart's own refusal already gave the right repair).
- **Everyone else:** nothing to do beyond upgrading.
