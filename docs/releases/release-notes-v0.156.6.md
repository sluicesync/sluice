# sluice v0.156.6

**Fix — `sync health` no longer reports a stalled stream healthy because its control-table row is dated in the future, and a Postgres sync role that holds only DML on the control tables now starts (GC-40).** Through v0.156.5, a `sluice_cdc_state` row written by v0.156.4 or earlier on a Postgres target whose database zone is east of UTC read hours in the future. A negative age is below every `--max-stale-seconds` threshold, so a stream that had stalled before the upgrade read `healthy` at exit 0. Such a row now reads UNKNOWN under `CONTROL-TIMESTAMP-IN-FUTURE` (exit 1), and `sluice_seconds_since_last_apply` emits `+Inf`. Separately, every Postgres control-table ensure now reads the catalog first and runs only the DDL that is missing. A role without `CREATE` on the schema, or one that does not own the tables, therefore starts against a current target instead of stopping at `permission denied for schema public`. `sluice control-tables ddl --engine postgres` is new and prints the set for an owner to run. Also fixed: "does not exist" errors are classified by SQLSTATE / errno, not by text. **Not a silent drop-in:** a Postgres target whose `sluice_migrate_state` tables predate v0.99.263 can now be refused with `CONTROL-TABLE-DDL-REQUIRED` on a non-UTC session, and `sync health` / the metric change output for future-dated rows. Read **Compatibility** and **Who needs this**. No confirmed data loss is fixed in this release; the headline fix is a monitoring check that failed open. One pre-existing guard gap could have let overlapping `backfill` walks run west of UTC; see **Fixed** and **Who needs this**.

## Features

**`sluice control-tables ddl --engine postgres` (and `--engine postgres-trigger`).** Before this release the command printed only the MySQL family's set. It now prints the Postgres migrate-state + cdc-state set for an owner to run once. That set is `sluice_migrate_state`, `sluice_migrate_table_progress`, `sluice_cdc_state`, `sluice_cdc_schema_history`, `sluice_shard_consolidation_lease`, `sluice_cdc_skipped_tables` and `sluice_cdc_apply_marks`. Each table gets its `CREATE`, then the `ADD COLUMN`, `CREATE INDEX` and UTC `ALTER COLUMN … SET DEFAULT` statements that later releases added. Every statement is idempotent. The statements are generated from the same values the runtime ensure executes, so the printed set and what sluice checks cannot drift apart. After an owner runs them, the sync role needs only `SELECT`, `INSERT`, `UPDATE` and `DELETE` on those tables. `postgres-trigger` prints the same set, because that engine's target-side tables are the Postgres applier's own. Three tables are not printed, on the MySQL family's terms: `sluice_keysets`, `sluice_target_metrics_history` and the source-side heartbeat table. Each is ensured only by the feature that uses it, and that feature's refusal names its own statement. The statements name schema `public`; if your target DSN sets `schema=`, edit the qualifier. Any other engine is refused, and the error lists the supported engines read from the engine registry. The old list left out `mariadb`. Pinned by `TestControlTablesDDLCmd_PostgresPrintsTheFullShape`.

## Fixed

**`sync health`, `sync status`, `sluice_seconds_since_last_apply` and the live panel no longer read a stream row dated in the future as fresh (LOW, fail-open monitoring; GC-40 (c)).** Before v0.156.5, sluice wrote Postgres control-table timestamps in the database's session zone and read them as UTC. On a zone east of UTC, a row those binaries wrote reads hours in the future: the v0.156.5 regression cycle measured −32,395 s on `Asia/Tokyo`. v0.156.5's first position write corrects such a row. A stream that stalled before the upgrade never writes one, and that is exactly the stream a stall probe exists to catch. Every reader that turns `updated_at` into a freshness reading now goes through one helper, `ControlTimestampAge`. Up to 60 s in the future counts as clock skew and is aged normally. Anything further is unknown and marked **`CONTROL-TIMESTAMP-IN-FUTURE`**, with the cause and the remedy. What each surface now does with such a row:

- **`sync health`** exits 1 in state `UNKNOWN`, whatever `--max-stale-seconds` says, including 0. In JSON both `control_timestamp_in_future: true` and `stale: true` are set, so a consumer that reads only `.stale` fails closed. The raw negative `seconds_since_last_apply` stays visible.
- **`sync status` and the `--all` fleet view** show the marker in the AGE column, with a remedy line in text and the same `control_timestamp_in_future` flag in JSON.
- **The status summary fails closed.** A future-dated row is left out of `most-recent` / `newest_seconds` and makes the oldest age unknown. The text says `oldest=unknown (N CONTROL-TIMESTAMP-IN-FUTURE)`. In JSON, `oldest_seconds` is the maximum value instead of a negative number, and the rows are counted in `control_timestamp_in_future_count`.
- **`sluice_seconds_since_last_apply`** emits `+Inf` under a `# CONTROL-TIMESTAMP-IN-FUTURE` comment line, so a `> N` alert fires. Omitting the series or emitting `NaN` would have failed open, as the negative number did. Skew inside 60 s now emits `0` instead of a negative number.
- **The live panel** shows freshness as unknown.
- **Cold-start ages** (in `sync status`, and in the `sync health` message for a stream that is still cold-starting) go through the same helper.

The remedy on every surface is the same. The stream's next position write heals the row, so restart a stalled or stopped stream with `sync start` and check NTP on both hosts. Pinned on a real Postgres by `TestControlTimestampAge_PreV01565RowOnATokyoDatabase`, which runs `ALTER DATABASE … SET timezone = 'Asia/Tokyo'` and writes a row the pre-v0.156.5 way. The same test binds the premise that such a row lands hours past the tolerance and that a current position write heals it. Also pinned by `TestEvaluateHealth_FutureDatedRowIsNotHealthy`, `TestRenderStatus_FutureDatedRowIsFlagged`, `TestEmitMetrics_FutureDatedRowFailsClosed` and `TestControlTimestampAge_Boundary`. `TestControlTimestampAge_EveryAgeConsumerRoutesThroughIt` walks `cmd/` and `internal/` and fails the build on a new direct `.Sub(x.UpdatedAt)`, `x.UpdatedAt.Sub(…)`, `time.Since(x.UpdatedAt)` or `time.Until(x.UpdatedAt)` that is not listed with a reason. Its exemption list is empty, and it does not reach `Before` / `After` comparisons. **Accepted residual (RESIDUAL-1), stated exactly:** take a row an older binary wrote at time 0 on a database zone `O` ahead of UTC, probed at elapsed time `d` with `--max-stale-seconds N` > 0. It reads `d − O` old, so for `d` from `O − 60 s` to `O + N` the probe reports healthy. Before that window it reads UNKNOWN (exit 1), and after it STALE (exit 1). With `N = 0` the staleness threshold is disabled as always, so from `O − 60 s` on such a row reads healthy. Nothing in the row tells a pre-v0.156.5 write from a current one: there is no per-row version stamp, and a legacy table DEFAULT is no evidence, because every current write names `updated_at`. The window therefore matters only for a stream that stalled before the upgrade. `TestEvaluateHealth_LegacyRowWindow` pins its edges on `Asia/Tokyo` at `O − 61 s`, `O − 30 s` and `O + N + 1 s`: exit 1, exit 0 and exit 1. **Affected releases:** every release through v0.156.5 aged the row without a future-date check. The zone-shifted rows themselves come from v0.156.4 and earlier binaries on east-of-UTC Postgres targets. A target clock more than 60 s ahead of the probing host gave the same fail-open reading on any engine.

**Postgres targets: a sync role that holds only `SELECT`, `INSERT`, `UPDATE` and `DELETE` on control tables another role created now starts and streams (LOW, loud, zero loss; GC-40 (a), Bug 291).** Every start ran `CREATE TABLE IF NOT EXISTS` and a series of `ALTER TABLE … ADD COLUMN IF NOT EXISTS` against every Postgres control table. PostgreSQL checks `CREATE` on the schema before it evaluates `IF NOT EXISTS`, and checks table ownership before an `ALTER`. So every sync role had to own the control tables and hold `CREATE` on their schema, even when every table and column was already present. Measured on v0.156.5 and v0.156.4: `permission denied for schema public (SQLSTATE 42501)` for a role without `CREATE`, and `must be owner of table sluice_cdc_state` for a non-owner that had it. This is also why v0.156.5's documented role causes of `APPLY-MARKS-UNAVAILABLE` could not reach that WARN on Postgres. The following Postgres ensures now probe the catalog first and run only the missing `CREATE`, `ADD COLUMN` or `CREATE INDEX`, so a current target sees no DDL at all:

- `sluice_cdc_state`, `sluice_cdc_skipped_tables`, `sluice_shard_consolidation_lease` and `sluice_cdc_schema_history`
- the migrate-state header and progress tables
- `sluice_keysets` and `sluice_target_metrics_history`
- the source-side heartbeat table

`sluice_cdc_apply_marks` and the `unforwarded_refusal` column already detected first. The MySQL family's ensures already detected first too, except for three unconditional creates: `sluice_keysets`, `sluice_target_metrics_history` and the heartbeat table. Those now detect first as well, because MySQL also checks the `CREATE` privilege before `IF NOT EXISTS`. That also lets them run on a PlanetScale safe-migrations branch once the table exists. Needed DDL that cannot run still stops the start, now marked **`CONTROL-TABLE-DDL-REQUIRED`**. The error names the missing table, column or index and the exact statement, and it is worded from the actual cause:

- **A table absent on a path that never creates control tables** (the `--schema-already-applied` refusal-record door) says to have the owner create it.
- **`42501`** gives the privilege remedy.
- **`3F000`** says the control schema does not exist and points at the DSN's `schema=`.
- **Any other failure** (a lock timeout, say) reports the raw cause and makes no claim about privileges.
- **A role without `USAGE` on the control schema** is told exactly that, with the `GRANT USAGE ON SCHEMA`.

The `APPLY-MARKS-UNAVAILABLE` WARN's remedy no longer says the printed DDL is MySQL-only. Pinned on a real Postgres by `TestControlTables_DMLOnlyRole`. It uses a login role with no `CREATE` on the schema, against tables an owner created from the printed set. The role ensures, applies a row and does not WARN. With the mark table dropped, it starts, WARNs `APPLY-MARKS-UNAVAILABLE` and applies. With a column or a table dropped, it is refused with that object named. Also pinned by `TestControlTableEnsure_IssuesZeroDDLWhenCurrent` over every Postgres ensure door and `TestEnsurePathsIssueZeroDDLWhenCurrent` on MySQL, and by `TestControlTableEnsure_RefusalNamesTheMissingObject` and `TestControlTableEnsure_RefusalWordsTheCause` (one case per cause). `TestControlTableDDLLiterals_OnlyInDetectFirstBuilders` fails the build on any Postgres `IF NOT EXISTS` DDL literal outside a detect-first builder or an exempted user-schema emitter. Measured end to end with the built binary: a superuser cold-started a Postgres → Postgres stream, which was then resumed with a target DSN for a DML-only role. It applied 50 inserts, 10 updates and 10 deletes. v0.156.5 on the same target refused with `permission denied for schema public`. **Affected releases:** every release through v0.156.5, on Postgres targets whose sync role does not own the control tables with `CREATE` on their schema. The unconditional `ADD COLUMN IF NOT EXISTS` ensure is present at least since v0.3.0; the first affected version was not bisected further. Nothing was lost: the start refused.

**Postgres source heartbeat: a DML-only source role on a pre-created heartbeat table now writes heartbeats, and a missing sequence grant is named at startup (LOW, degraded protection; GC-40 (a) review L4).** For the same `CREATE`-before-`IF NOT EXISTS` reason, a source role with only `INSERT`/`DELETE` on a heartbeat table an owner had pre-created used to take the permission-degrade path. It WARNed and wrote no heartbeats, so idle-source slot/binlog protection (ADR-0061) was off for that stream. The ensure now detects the table first. The table's `id` is `BIGSERIAL`, so every heartbeat `INSERT` also draws from its sequence. The ensure therefore checks `USAGE` on that sequence. When the grant is missing, it takes the same degrade path, and the WARN's error names the `GRANT USAGE ON SEQUENCE` to run, instead of every heartbeat `INSERT` failing later. The MySQL heartbeat ensure detects first too. Pinned on a real Postgres by `TestEnsureHeartbeatTable_DMLOnlyRole`, with and without the sequence grant. **Affected releases:** every release through v0.156.5 that has the source heartbeat; the first version was not bisected.

**Postgres targets: `sluice_migrate_state` / `sluice_migrate_table_progress` tables created before v0.99.263 no longer store their timestamps in the session's local time (LOW; GC-40 LOW-1/2).** Those tables were created with `DEFAULT CURRENT_TIMESTAMP` on `started_at` / `updated_at`. Since v0.150.0 the migrate-state writes leave both columns to the DEFAULT, to work around a PlanetScale Neki router rewrite. `CURRENT_TIMESTAMP` into a naive column stores the session zone's wall-clock digits. East of UTC, every migrate-state write was therefore dated hours in the future. The `backfill` concurrent-run guard then refused the spec as "live on another runner" for hours, and cold-start progress ages read negative. West of UTC, writes were dated hours in the past. There the guard could read a live walk's heartbeat as stale and let a second, overlapping walk of the same spec through, which is the case the guard exists to stop. The Postgres migrate-state ensure now reads each column's DEFAULT and re-points a session-clock one at `timezone('utc', now())`. `sluice control-tables ddl --engine postgres` prints the same `ALTER COLUMN … SET DEFAULT`. A role that may not ALTER the table is handled by its session zone (see **Compatibility**):

- **Session zone not UTC all year:** refused with `CONTROL-TABLE-DDL-REQUIRED`. A zone such as `Europe/London`, which matches UTC only in winter, counts as not UTC.
- **UTC session:** only WARNed, because there the legacy default is harmless.

The other Postgres control tables are left alone. `sluice_cdc_state`, the skip ledger, the shard lease and schema history write every timestamp explicitly. `sluice_keysets` and the heartbeat table use `timestamptz`, and `sluice_target_metrics_history` binds its value. Their legacy defaults are never evaluated. The `backfill` guard and the cold-start ages now read migrate-state timestamps through `ControlTimestampAge`. A heartbeat dated past the skew tolerance still refuses, so the guard fails closed. The refusal is now marked `CONTROL-TIMESTAMP-IN-FUTURE` and names the legacy-default and clock-skew causes instead of claiming a live run. Pinned on a real Postgres by `TestMigrateState_LegacySessionClockDefault_UnderTokyo`, under `Asia/Tokyo` with the legacy default. The test covers the premise that such a write lands about +9 h, that the owner's ensure re-points the defaults so the next write ages ≈0, and that a non-owner is refused on the Tokyo session and only WARNed on a UTC one. Also pinned by `TestControlTableEnsure_LegacySessionClockDefault` and the future-dated arm of `TestBackfill_ConcurrentRunHeartbeatGuard`. **Affected releases:** v0.150.0 through v0.156.5, on Postgres targets whose migrate-state tables were created before v0.99.263 and whose database zone is not UTC. The UTC DEFAULT arrived in v0.99.263, and the writes began relying on it in v0.150.0 (`8e27ee68`).

**"Does not exist" errors are classified by SQLSTATE / errno instead of by text (LOW, loud, misleading remedy; GC-40 (b), Bug 292).** The connect-phase hint coded any error containing "does not exist" as `SLUICE-E-CONNECT-DATABASE-MISSING`, with the remedy "verify the database name in the target DSN". Because of that, `sync start --schema-already-applied` against a Postgres target without `sluice_cdc_state` was told the database was missing while the database was there: `relation "public.sluice_cdc_state" does not exist (SQLSTATE 42P01)`. MySQL's own wording, `Unknown database`, never matched, so a DSN naming a missing MySQL-family database carried no code. The connect hint now matches on structure:

- **Postgres:** SQLSTATE `3D000`, read through the driver error's `SQLState()` method. A new engine-neutral `ir.SQLStater` interface is pinned against `*pgconn.PgError` in the Postgres engine, so a driver change cannot silently blind it. `nettransient` now reads SQLSTATEs through the same helper instead of its own copy.
- **MySQL family:** errno `1049`. The MySQL connect chokepoint marks it `ir.ErrDatabaseNotFound`, because that driver exposes only the generic SQLSTATE `42000`. That database-missing case is now coded.

With the detect-first ensure above, the `--schema-already-applied` case now says `"public"."sluice_cdc_state" does not exist` under `CONTROL-TABLE-DDL-REQUIRED`. The hint is also side-neutral now. The same connect phase opens the source too: `backup` (which has no target) and `schema add-table`'s source reader. So the hint now says the database this connection's DSN names does not exist, and points at "that DSN", which the wrapped error identifies. The sibling "does not exist" entries were narrowed the same way when the error carries a SQLSTATE:

- **Bulk copy:** `SLUICE-E-BULKCOPY-TARGET-TABLE-MISSING` now requires a missing relation or schema (`42P01`/`3F000`). A missing column or type falls through to the generic copy-table hint.
- **Index and constraint builds:** the `…-TARGET-MISSING` hints now require a missing relation, schema or column (`42P01`/`3F000`/`42703`). A missing operator class, collation, type or function (`42704`/`42883`) is no longer told it was "dropped between the copy and the index build".

Errors without a SQLSTATE (MySQL, or a message flattened on the way up) keep the substring match. The other entries match text unique to their class and are unchanged. Pinned by `TestDoesNotExistClassification_EveryObjectKind`, which covers every "does not exist" object kind × phase × engine through real `*pgconn.PgError` and `*mysql.MySQLError` values. Also pinned by `TestMarkDatabaseNotFound`, and on real servers by `TestConnectHint_DoesNotExist_RealServers`. There, Postgres `--schema-already-applied` without `sluice_cdc_state` is not coded database-missing. A genuinely missing Postgres target, Postgres source or MySQL target database is, and the source case's hint does not name the target. **Affected releases:** the connect-phase substring match has been in every release from v0.2.0 through v0.156.5; the MySQL 1049 gap is as old. The bulk-copy entry dates from v0.2.0. The index/constraint entries are later; not bisected.

**Docs: v0.156.5 post-publish corrections.** The v0.156.5 notes said `APPLY-MARKS-UNAVAILABLE` covered a role without `CREATE` and a DML-only role. On a Postgres target those causes did not reach that WARN, because the start stopped earlier while ensuring `sluice_cdc_state` (Bug 291, fixed above). The archived v0.156.5 notes, its CHANGELOG entry and `docs/operator/cdc-streaming.md` now say so. Also corrected: the go-sql-driver sends a DSN's session parameters as a single `SET`. VStream's BEGIN/COMMIT events were discarded before v0.156.5, not absent. The `--exactly-once-lanes` help now quotes the post-drain-fix cost (97–99% of lane throughput) instead of the pre-fix ~99.9%.

## Compatibility

**New loud refusal: legacy migrate-state DEFAULTs on a non-UTC Postgres session.** A `sluice_migrate_state` / `sluice_migrate_table_progress` table created before v0.99.263 still defaults `started_at` / `updated_at` to `CURRENT_TIMESTAMP`. sluice now re-points those defaults at UTC with `ALTER TABLE … ALTER COLUMN … SET DEFAULT (pg_catalog.timezone('utc', pg_catalog.now()))`. If the connecting role may not ALTER the table (it is not the owner) and its session `TimeZone` is not UTC all year, sluice refuses with `CONTROL-TABLE-DDL-REQUIRED`, naming the column and the statement. What that refusal stops depends on the command:

- **`migrate` and `backfill`:** they stop.
- **`sync` cold start:** only cold-start progress recording is disabled, with a WARN. The copy proceeds, but `sync status` shows the stream as absent until the CDC anchor is written.

On a UTC session the same role gets a WARN and runs. A configuration that ran on v0.156.5 can stop here. **Remedy:** have the table owner run the printed statements once (`sluice control-tables ddl --engine postgres`, or just the `ALTER COLUMN … SET DEFAULT` lines). Alternatively, run once as the owner, which applies them automatically.

**`sync health` exit code and JSON.** A stream row dated more than 60 s in the future now exits 1 (`UNKNOWN`, `CONTROL-TIMESTAMP-IN-FUTURE`) regardless of `--max-stale-seconds`, including 0, and sets `stale: true` plus the new `control_timestamp_in_future` field. A probe that exited 0 on v0.156.5 can exit 1 here. That is intended: it is the stall the probe exists to catch, or a clock that needs NTP.

**`sluice_seconds_since_last_apply` values.** A future-dated row now emits `+Inf` under a comment line, and skew inside 60 s emits `0` instead of a negative number. The metric never goes negative any more. A dashboard or recording rule that assumed a finite value should handle `+Inf`.

**`sync status` JSON and text.** Additive fields: `control_timestamp_in_future` per row, and `control_timestamp_in_future_count` in the summary. When any row is future-dated, `oldest_seconds` is the maximum value and the text summary reads `oldest=unknown (…)`.

**Error codes and hints.** A missing MySQL-family database at connect now carries `SLUICE-E-CONNECT-DATABASE-MISSING`, where before it carried no code. A missing control table on a Postgres target is no longer coded database-missing. Some Postgres column / type / operator-class errors in bulk copy and index/constraint builds no longer carry the `…TARGET-TABLE-MISSING` / `…-TARGET-MISSING` codes. The connect hint's wording changed; it no longer names the target. Scripts that key on those codes or on the hint text should be checked.

**`control-tables ddl`.** The default engine is unchanged (`planetscale`), so existing invocations print what they did. `--engine postgres` and `--engine postgres-trigger` are new. The refusal for an unsupported engine now lists the supported set from the registry.

**Otherwise a drop-in.** No flag was removed or renamed, and no column type changed. On a current Postgres target the ensure issues no DDL. On a target missing a column it issues the same statements as before, but only those. The detect-first change applies to Postgres and `postgres-trigger` targets, the Postgres source heartbeat, and the MySQL family's keysets, metrics-history and heartbeat ensures. SQLite/D1 targets are unaffected.

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale, a billable cluster), `d1verify` (live Cloudflare D1) and `nekiverify` (a billable Neki cluster) suites were not dispatched, because each provisions billable or live infrastructure and runs only on the operator's call. The detect-first ensures on MySQL-family targets, including the newly detect-first keysets / metrics-history / heartbeat ensures on a PlanetScale safe-migrations branch, and the migrate-state DEFAULT re-point on a Neki target, were therefore not measured against live PlanetScale or Neki.

## Who needs this — action required

- **Anyone who alerts on `sync health` or `sluice_seconds_since_last_apply` for a Postgres target whose database zone is east of UTC and that ran v0.156.4 or earlier.** Upgrade and run the probe. An exit 1 with `CONTROL-TIMESTAMP-IN-FUTURE` means that stream has not written a position since the upgrade that fixed its row, which usually means it is stalled or stopped. Restart it with `sync start` and check again. Treat any past `healthy` reading from such a target as unverified. See the RESIDUAL-1 window above for the one interval in which a stalled pre-upgrade row still reads healthy.
- **Anyone who sees `CONTROL-TIMESTAMP-IN-FUTURE` on any engine after upgrading, with no pre-v0.156.5 history.** The target's clock is more than 60 s ahead of the probing host; fix NTP.
- **Postgres targets whose migrate-state tables were created before v0.99.263, on a database zone that is not UTC, run by a role that does not own them.** `migrate` and `backfill` now refuse with `CONTROL-TABLE-DDL-REQUIRED` until the owner runs the `ALTER COLUMN … SET DEFAULT` statements that `sluice control-tables ddl --engine postgres` prints. If you ran `backfill` west of UTC on v0.150.0–v0.156.5 with overlapping invocations (cron), check that the backfilled column is complete, because the concurrent-run guard could have let two walks overlap there.
- **Postgres CDC targets that you want to run with a DML-only sync role.** Have the owner run `sluice control-tables ddl --engine postgres` once, then grant the sync role `SELECT`, `INSERT`, `UPDATE` and `DELETE` on those tables and `USAGE` on the control schema. For a Postgres source heartbeat under a DML-only source role, also grant `USAGE` on the heartbeat table's id sequence. Nothing needs re-verifying: the old behaviour was a refusal, never a loss.
- **Scripts or runbooks that key on `SLUICE-E-CONNECT-DATABASE-MISSING`, `SLUICE-E-BULKCOPY-TARGET-TABLE-MISSING`, the index/constraint `…-TARGET-MISSING` codes, or the connect hint's text.** Review them against the narrowed classification above.
- **Everyone else:** nothing to do beyond upgrading.
