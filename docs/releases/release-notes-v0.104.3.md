# sluice v0.104.3

**`backup verify` on an encrypted chain was not meaningfully verifying decryptability, and had not been for as long as the check has existed.** Its `decrypt_probe=true` meant only "an envelope was supplied": the probe unwrapped each chunk's own `WrappedCEK`, a field that only `--encrypt-mode=per-chunk` populates, so on a default per-chain chain it returned nil for every chunk without touching a byte of ciphertext. The total decryption performed by an entire `backup verify --encrypt` run was one chain-root key unwrap. Everything else was a SHA-256 of bytes that were on disk and hashed correctly regardless of whether any key in the world could open them. That is not a small gap in a nice-to-have — it is the check operators are told to run on a schedule precisely so they never learn about a bad backup during a recovery, and it was answering a different question than the one being asked. Verify now performs a real AES-GCM authenticated open of every encrypted chunk, under the same key and the same binding `restore` uses, and reports `decrypted=N` alongside the chunk count. **Assert that count, not the exit status** — a green verify with `decrypted=0` on a chain you believe is encrypted is the shape this release exists to make visible. It also walks the chain's lineage the way restore does before it starts, so a chain whose links no longer stitch together is refused by verify rather than discovered during a restore. This costs real time on a large chain, and that cost is the honest price of the check.

The rest of the release is largely what that hollow signal was hiding: three separate ways a backup chain could be written, maintained, or pruned into a state `restore` refuses, all of them exiting 0 at the time and surfacing only at recovery.

### Fixed

**`backup verify --encrypt` now authenticates every encrypted chunk.** It performs the real decryption under the same key and binding the restore path uses, in the default per-chain mode as well as per-chunk, and reports `decrypted=N` beside `chunks=N`. **Read that count, not the exit status:** on an encrypted chain `decrypted` must equal `chunks`, and `decrypted=0` means no key reached the command and you got the checksum-only depth. Verify also walks the chain's lineage the way restore does before it begins, so a chain whose links no longer stitch together is refused here rather than discovered during a recovery. It is slower and there is no opt-out. If an earlier release told you an encrypted chain was healthy, re-run this and treat `decrypted=N` as the answer.

**Encrypted chains written after a `backup stream` rotation could not be restored.** Every rotation-born segment full runs the ordinary full-backup orchestrator against an empty directory, so it mints its own fresh chain key — and the restore path knows this, reading a segment's bulk-copy chunks with that segment's key while reading every incremental's change chunks with the chain root's. The writer did not agree: it resolved the key owner through the currently-open segment store. A long-running `backup stream` matched the read path only by accident, because it resolves its key once at startup when the open segment still *is* the lineage root and carries that key across every subsequent rotation. Anything that arrived later resolved through the segment instead and sealed its chunks under a key nothing would ever use to read them. The restore applied everything up to the last rollover and then stopped at `chunk failed authenticated decryption`, exit 3, with the correct passphrase in hand. **The trigger is not "rotation" — it is "the open segment is not the lineage root"**, so an ordinary `backup stream` restart on a rotated encrypted chain reached it just as readily as a one-shot `backup incremental` did, and the `sync from-backup` broker's replay was affected identically. Both extending writers now resolve the key at the lineage root, which is where the read path has always looked. Nothing was lost from the source and every byte is still on disk; those chunks are still decryptable, but only under the segment key they were sealed with, and sluice will not do that for you.

**`backup prune` destroyed an encrypted chain's identity.** Retiring whole leading segments swept the lineage-root `manifest.json` along with segment 0's data — the same root-manifest defect `backup compact` had in v0.104.2, on a path that runs on a retention schedule rather than as occasional maintenance, which is what makes it the more dangerous of the two. That file is where a passphrase chain's Argon2id salt is recorded, so deleting it made every *surviving* segment fail to restore at `unwrap chain cek` as though the passphrase were wrong. The root manifest is now kept unconditionally, whether or not the chain is encrypted; the retired segment's own chunks and incrementals still go. Both maintenance commands additionally re-read the chain the way a restore would — before the destructive sweep, so a refusal has deleted nothing, and again after it, so a run can never exit 0 over a chain it just made unreadable.

**Chain restore and `backup verify` both read a chain's encryption identity from the wrong manifest once its root segment had been retired.** Keeping the root manifest was necessary but not sufficient. Both paths took the chain's encryption identity from the first *catalogued* segment, which is segment 0 right up until a whole-segment prune retires it — after which it is a later segment full whose freshly-minted key never sealed a change chunk. Restore was fixed first; `backup verify` had the same skew and it surfaced as the inverse of the bug above, a red verify (`aes-gcm open: message authentication failed` on every change chunk) over a chain that restored row-exact in the same run. Both now resolve the chain root by absolute path, with the same fallbacks so a chain with no root manifest and a plaintext chain keep behaving exactly as before.

**`backup compact --smart-compaction` produced chains that `restore` refuses.** Smart compaction buffers row events into per-primary-key accumulators and flushes them at end-of-incremental, and it flushed them *after* the stream's closing transaction commit — while a collapsed event deliberately carries the *first* position of the events it collapsed. So any incremental that touched one row in more than one transaction ended below its own recorded end position, and the restore path's tail-truncation backstop reads exactly that as a truncated change list and refuses the whole chain with `SLUICE-E-BACKUP-INCOMPLETE`. Loud rather than silent, but it is still a compacted backup that will not restore. The trigger needed no rotation, no resume, no encryption and no stream — two transactions touching one row inside a single incremental was enough. The closing commit is now held back so the collapsed rows land *inside* the last transaction, which tightens the envelope rather than loosening it, and the chain once again ends on its own recorded position. This is pre-existing, not a regression: it was proven against the base tree, and it had been masked by the `--max-changes` defect below.

**`--max-changes` and `--rollover-max-changes` / `--rollover-max-bytes` could close a window that captured nothing new.** A resumed CDC stream re-delivers the transaction its parent ended on — PostgreSQL's logical decoding begins at the requested LSN and skips only transactions whose commit record is strictly *before* it, so resuming at a parent's end position, which is exactly a commit LSN, replays that entire transaction. Every event of that replay carries the same commit LSN, so a tight bound could be satisfied by the replay alone and commit a manifest with `start_position == end_position` that contained none of the delta the operator had just written — while logging a non-zero change count. It was not silent loss: the replication slot had not advanced past the missed changes, so a later unbounded or time-bounded window picked them up. What it cost was trust in the per-run summary, and an operator building a chain with tight bounds could accumulate empty segments believing each captured their writes. Both bounds — and, on the streaming path, the byte bound as well, which had the identical defect and was not in the original report — now additionally require that the window has advanced past its own start position before they may close it. The wall-clock deadline is deliberately exempt, so a quiet source still closes its window on schedule; a window that ends without advancing now logs a warning naming the shape. The replayed events are kept rather than filtered, because when a parent's own window ended mid-transaction the replay is the only thing carrying its severed tail, and dropping it would turn a benign duplicate into real loss. Ground-truthed on real PostgreSQL 16 with an instrumented capture loop; the guard itself is engine-neutral and applies to every source.

**A Postgres CDC reader could panic and take the process down when it was closed while still streaming.** `Close` set the reader's database handle to nil with no join against its own pump goroutine, and that pump is not merely decoding buffered bytes — every relation message it sees runs live catalog queries on that same pool. A pump that passed the handle's nil check and then reached the query dereferenced a nil pool and panicked on a goroutine with no recover anywhere on its path. This was reachable in production, not only from the `-race` CI run that reported it: `sluice sync`'s per-attempt teardown and `backup stream`'s transient-retry reopen both close a reader whose pump is live, and both already documented the reader as joining its streaming goroutine deterministically — the contract was right and the implementation was not. `Close` now cancels and joins before releasing anything the pump owns. Fixing it also closed a second defect it had been hiding: pgx reports an already-cancelled context as a *timeout*, so the pump's keepalive branch spun forever instead of unwinding, leaking a hot goroutine for every torn-down stream. The receive path now tests for cancellation before it treats an error as a timeout. This is the `postgres` engine's logical-replication reader specifically; see the note on the MySQL sibling under **Who needs this**.

**An explicitly-named `PRIMARY KEY` constraint now survives a Postgres → Postgres migration.** sluice emitted `PRIMARY KEY (cols)` inline, so Postgres auto-named the target's constraint `<table>_pkey` and a source that had named its own key `CONSTRAINT orders_pk PRIMARY KEY (id)` lost that name. Enforcement was never affected — same columns, same uniqueness — but every *reference* to the name broke at cutover, and `INSERT … ON CONFLICT ON CONSTRAINT orders_pk` is the one that bites an application in production. The name is now carried when the source engine names primary keys as first-class constraints, which today means Postgres only. The dispatch is on an explicit IR flag and never on the name text, deliberately: a MySQL primary-key index is literally named `PRIMARY`, and a text-level rule was ground-truthed to emit `CONSTRAINT "PRIMARY" PRIMARY KEY (…)` and fail hard with `relation "PRIMARY" already exists` on the second table of the migration. **MySQL and SQLite sources therefore still emit an inline, unnamed primary key, on purpose**, and a Postgres → MySQL migration still drops the name because MySQL parses `CONSTRAINT x PRIMARY KEY` and discards `x` — it is not representable there.

**A backup manifest written by a different sluice release no longer tells the operator their backup is corrupt.** Every manifest records a fingerprint of the schema it was written with, and a chain restore recomputes that fingerprint on every link and refuses the whole chain on a mismatch. That check has two possible causes and cannot tell them apart — a manifest written by a release whose internal schema representation differs, in which case the chain is *intact* and merely unreadable by this binary, or genuine corruption — and it named only the second, in as many words: *"corrupted or partially-rewritten manifest"*, remedied by *"restore from an untampered copy"*. That is a false accusation of tampering delivered to someone mid-recovery, and it sends them hunting a fault in their storage that is not there. The refusal now names both causes, release skew first, and identifies the release that wrote the manifest from the manifest's own recorded version rather than from a hardcoded table. `backup verify` and `export-as-parquet`, which have no such preflight, append the same possibility when a manifest's own recorded fingerprint fails to reproduce. **The refusal still refuses — only its honesty changed.** See the epoch section under **Who needs this**; this is the part of the release that most deserves reading before you need it.

**A field added in the previous release would have partitioned every backup chain again, and was caught before release.** The primary-key-name fix above added a field to the internal schema representation, which is marshalled without JSON tags into the fingerprint above — so it silently re-fingerprinted every schema that had not changed, on every index of every table. The field now carries `omitempty`, which restores the fingerprint byte-identically (verified by hashing the same schema through v0.104.2 and this tree from tag worktrees), so **v0.104.3 shares its fingerprint epoch with v0.103.0 through v0.104.2 and adds no new boundary.** A frozen-golden unit test now fails CI on any change to that fingerprint, so the next one can only happen deliberately.

**The chain-maintenance readability refusal now carries a machine-readable code.** `backup compact` and `backup prune` refuse when they re-read a chain and cannot walk it, or when its identity/key material is missing — that refusal was a bare error with exit 1, so a script branching on `SLUICE-E-*` (which is what the error-codes table instructs) could not detect it. It is now `SLUICE-E-BACKUP-CHAIN-UNREADABLE` with refusal exit status 3, naming which operation refused and which leg it refused at, so `pre-swap`/`pre-commit` (nothing deleted) is distinguishable from `post-sweep` (already deleted, recovery named). The code is applied inside the guard rather than at its call sites, so a future caller cannot acquire the check without acquiring its refusal class.

### Changed

**`backup prune` retention is now segment-granular: `--keep-incrementals` and `--keep-duration` are rounded UP to a segment boundary.** Prune had two retention shapes, and only one of them was safe. Retiring whole leading segments is restore-safe because the next segment's full is a self-contained base; trimming leading incrementals *inside* the floor segment left that segment's full anchored at one position with its first surviving incremental starting at a later one, and the changes in between simply gone — a chain that restore refuses, correctly, on the severed parent link and again on the forward position gap. That was reproduced on a real rotated Postgres chain in **plaintext**, on the pre-fix binary: prune deleted an incremental, exited 0, and the subsequent restore failed. Encryption was never involved. Prune therefore now only ever retires whole leading segments. **Your number becomes approximate in the safe direction — never fewer incrementals than you asked for, sometimes more** — and every run reports both `incrementals_requested` and `incrementals_retained`, logging an explicit rounding line with its reason when they differ, because silent over-retention is how "my disk did not shrink" starts. `--dry-run` reports the rounded plan rather than the requested one.

**`backup prune --keep-incrementals` on a never-rotated (single-segment) chain now refuses, actionably, where it previously destroyed the chain.** Rounding up can only reach a boundary that exists at or above the request, and a chain that has never rotated has no boundary at all — so honouring the request segment-granularly would mean retaining everything and deleting nothing, and reporting *that* as a successful prune is exactly the silent no-op this contract exists to prevent. That one case gets a purpose-built refusal instead: `SLUICE-E-BACKUP-CHAIN-UNREADABLE`, exit 3, naming the shape, promising inertness (nothing was deleted), and computing the retention counts that *are* safe on that particular chain. It fires for `--dry-run` too — a dry run that promises a prune the real run refuses is worse than no dry run. Use `--keep-duration` past every incremental, or let the chain rotate, or accept the boundary counts the refusal names.

**`backup verify --encrypt` is meaningfully slower on encrypted chains.** It now decrypts and authenticates every encrypted chunk instead of hashing bytes. That is the point, and there is no flag to opt out of it.

## Who needs this

- **Anyone who has ever run `backup verify` against an encrypted chain and taken the result as assurance.** You got less than you were told: on the default `per-chain` mode the run decrypted nothing, and even on `per-chunk` it proved only that a key wrap opened, never that any ciphertext authenticated under it. Re-run verify with this release against every encrypted chain you rely on, and **assert `decrypted=N` is non-zero and matches your chunk count** — the exit status alone is what was misleading you before.
- **Anyone with an encrypted chain that has rotated and was then extended by a `backup incremental`, a `backup stream` restart, or a supervisor-driven restart of any kind.** Those chunks were sealed under the wrong key and are unreadable by `restore`. Verify the chain now rather than during a recovery. The data is not lost — every byte is on disk and is decryptable under the segment key it was sealed with — but sluice will not resolve that for you, and re-taking the backup with this release is the clean path.
- **Anyone who has run `backup prune` on an encrypted chain in v0.104.2 or earlier.** If the prune retired the root segment, that chain is unrestorable right now, and it exited 0 when you ran it. It is repairable without a re-backup: every rotation-born segment full carries the same chain salt, so `cp <chain>/seg-*/manifest.json <chain>/manifest.json` from any surviving segment restores the chain's identity. From this release on, prune keeps the root manifest and proves the chain still reads before and after it deletes anything.
- **Anyone who has run `backup compact --smart-compaction`.** Test-restore those chains. A compacted incremental that touched one row in more than one transaction will be refused with `SLUICE-E-BACKUP-INCOMPLETE`; re-compacting the chain with this release, or restoring from an uncompacted copy, is the way out.
- **Anyone using `backup prune --keep-incrementals` or `--keep-duration` on a schedule.** Read the Changed section before upgrading. Your retention numbers are now rounded up to a segment boundary, and on a never-rotated chain `--keep-incrementals` refuses rather than proceeding. Both are strictly safer than what they replace, and both are visible behaviour changes to a scheduled job.
- **Anyone holding a backup chain written by v0.102.2 or earlier — read this carefully, because it is not fixed in this release.** Backup chains are partitioned into three incompatible fingerprint epochs: **v0.99.292 and earlier**, **v0.100.0 through v0.102.2**, and **v0.103.0 onward (which includes this release)**. A chain cannot be restored across a boundary **in either direction** — a newer binary cannot read an older chain and an older binary cannot read a newer one. This release does **not** repair that. What it fixes is the message: until now the refusal told you your manifest was *"corrupted or partially-rewritten"* and advised you to restore from an untampered copy, about a chain that was byte-for-byte intact. It now names both possible causes and prints the release that wrote the manifest, and the epoch table is documented at `docs/operator/error-codes.md` under "Schema-fingerprint epochs". **The one genuinely reassuring thing is that it fails in the safe direction**: a loud refusal in preflight, before a single row lands on your target — never a silent partial restore. Your options today are to restore such a chain with a sluice release from its own epoch, or to re-take the backup with a current binary; there is no flag that skips the check, and the compatibility shim that would recompute a fingerprint at the writing release's field set is deliberately unbuilt — with no production install base there is no stranded chain in the field to rescue, and building it now would be complexity bought for nobody. If that stops being true for you, say so. Two things narrow the blast radius: a **bare full** backup (one segment, no incrementals) is unaffected, because the single-manifest restore path never walks a chain or runs the check; and the boundary is now pinned by a cross-version CI cell so it cannot move unnoticed. Note the same check runs in the `sluice sync from-backup` broker, so this is not restore-only.
- **Anyone building chains with a tight `--max-changes`, `--rollover-max-changes` or `--rollover-max-bytes`.** Segments you believed captured a delta may have captured only the parent's replayed boundary transaction. Nothing was lost — the slot never advanced past the missed changes, so a subsequent unbounded window swept them up — but if you have been reading per-run change counts as "N of my writes are in here", re-check the chain rather than the summaries. Those bounds now count change *events* including transaction framing (a one-row transaction is three), which the `--max-changes` help text now says.
- **Anyone syncing from Postgres under a supervisor, or running `backup stream` against a Postgres source.** The shutdown panic and the leaked pump goroutine were both reachable from ordinary teardown and retry paths. No action beyond upgrading.
- **MySQL sources: the same close-vs-pump defect exists in the MySQL CDC reader and is NOT fixed in this release.** It was found by code-reading while fixing the Postgres one and deliberately not bundled with it — MySQL's pump has a different lifecycle, so transplanting the Postgres patch without its own ground truth and its own pins is exactly the "fix the representative, not the class" mistake this project has paid for before. No CI run has reported it, so the risk today is theoretical rather than observed; but if you are tearing down MySQL CDC readers under load, do not read the Postgres fix as covering you. Tracked as roadmap item 103.
- **Anyone migrating Postgres → Postgres whose application uses `ON CONFLICT ON CONSTRAINT`.** Named primary-key constraints now survive the migration. If you previously worked around this by renaming the target's constraint by hand after a migration, that workaround is no longer needed — and re-running a migration will now produce the source's name rather than `<table>_pkey`.
- Everyone else: no action needed beyond upgrading.
