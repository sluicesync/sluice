# sluice v0.163.8

> **Correction (2026-10-23).** These notes present `--no-drain` on a Postgres source as the working live path. It is not safe either. The refusals this release ships are unchanged and correct; only the statement that the Postgres path is the one to use was wrong.
>
> **"`--no-drain` now works only on a Postgres source"** (and the CHANGELOG's "The Postgres live path is unchanged", read as safe) does not hold: the v0.163.8 regression cycle measured `schema add-table --no-drain` from a Postgres source losing changes made to the new table during the add, at exit 0, with the success line claiming the table is covered (sluice-testing Bug 332, CRITICAL, silent; measured back to v0.150.0). On a stream with `--include-table`, every change between the add's snapshot and the stream's next poll of its live-added tables is dropped (PG→PG: 25 deleted rows kept, 24 inserts missing, 25 stale values). On an unfiltered stream, a delete applied before the copy wrote its row is undone by the copy (PG→PG: 12 deleted rows kept). **Do not use `--no-drain` on any source.** Use the drained flow on Postgres too: `sluice sync stop --wait`, then `sluice schema add-table` without `--no-drain`, then restart the stream, keeping it stopped until add-table returns. That flow was measured exact from MySQL, MariaDB and Vitess sources; from a Postgres source it is not yet measured. A table added with `--no-drain` from a Postgres source on an earlier release may hold rows the source deleted or changed, or miss rows it inserted; `sluice verify --depth count` cannot rule that out, so compare the table against the source and re-copy it the way this release's entries describe, including the foreign-key caveat. A refusal of `--no-drain` on every source ships in its own release.

**HIGH fixes, silent: `sluice schema add-table --no-drain` lost changes to the new table on every MySQL-family source, and is now refused there (`NO-DRAIN-BINLOG-SOURCE` for MySQL/MariaDB, `NO-DRAIN-VSTREAM-SOURCE` for PlanetScale/Vitess).** A live add from those sources lost the changes made to the added table between the add's snapshot and the running stream admitting it, at exit 0 with no WARN; on a binlog source that window is the whole copy, not the few seconds of poll lag ADR-0034 described. `--no-drain` now works only on a Postgres source. The remedy is the drained flow, and the stream must stay stopped until `schema add-table` returns, because add-table does not yet check that it is (a known open gap, fixed in a later release). No backup format change. Not drop-in for `--no-drain` from a non-Postgres source, which now exits 1 (see Compatibility).

## Fixed

- **`--no-drain` refuses on a MySQL or MariaDB binlog source (`NO-DRAIN-BINLOG-SOURCE`, HIGH, silent; the `mysql` driver since v0.27.0, a MariaDB server run under it included, and the `mariadb` driver since its CDC arrived in v0.99.271).** ADR-0034's filter-flip live path (commit `4381688d`, v0.27.0) copies the table from a snapshot fixed when the copy opens, records the table in the running stream's live-added set only after the copy finishes, and the stream drops every change to the table until its next poll admits it, while its position moves past those changes. Measured against a running stream adding a 20,000-row table (`TestAddTableNoDrainWindow_Binlog_MySQLToMySQL_Live`, at the commit before the refusal), with changes made right after the snapshot opened, mid-copy, and after the add returned but before admission: every one was lost, 60 deleted rows kept, 30 rows at their old value and 30 inserted rows missing, on MySQL into MySQL and on MariaDB into MariaDB; a 200ms poll still lost everything made during the copy, as the default 5s poll did. The add exited 0, logged no WARN, and its success line said the stream would pick the table up. MySQL into a Postgres target already refused. The drained flow against a stopped stream was exact in every phase of the same measurement, on MySQL into MySQL, MySQL into Postgres and MariaDB into MariaDB (`TestAddTableNoDrainWindow_Binlog_MariaDBToMariaDB_DrainedStoppedControl` among them).
- **`--no-drain` refuses on a PlanetScale or Vitess source (`NO-DRAIN-VSTREAM-SOURCE`, HIGH, silent).** The help listed the live paths as a Postgres source and a MySQL-family binlog source writing to a MySQL-family target, but the check looked only at the target, so a VStream source writing to a MySQL-family target took the filter-flip path too. On VStream the add's copy is one keyspace-wide snapshot that also drops the deletes made to the table while it runs. Measured on a local vttestserver (Vitess 24, one shard, three runs per cell) with a MySQL 8.0 target, adding a 100,000-row table while the source deleted and updated rows (`TestStreamer_VStreamAddTableKeyspaceWideCopy`): 80 deleted rows stayed on the target and 10 updated rows kept their old values, in every run, at exit 0, and stayed so across later restarts; on a stream cold-started in the same process the added table received no changes at all afterwards. The drained flow was exact, because the restarted stream replays the add's window from its position: measured on one shard, three runs into Postgres 16 and one into MySQL 8.0. Whether the source is VStream is judged from `--source-driver` and from the stream's recorded position (the new `PositionCDCMethod` on the MySQL engine, reached through `positionCDCClassifier`), so a stream started as `planetscale` or `vitess` and then handed `--source-driver mysql` (self-hosted Vitess's underlying mysqld, for example) also refuses; a declared VStream driver refuses whatever the position says.
- **How the door works and what pins it.** `noDrainLivePathRefusal` takes the live path only for a source that implements the publication surface, and by the code only the Postgres engine does (`AddPublicationTables` has one production implementor). Every other source refuses in `preflightStream`, before the schema read, the dry-run report, the snapshot, any pending or live-added record and any target write; `--dry-run` reaches the same door. Both markers' messages carry `drainedAddTableFlow`: `sluice sync stop --wait`, then `sluice schema add-table` without `--no-drain`, then restart with `sluice sync start` and the same `--stream-id`, or for a `sluice sync run` fleet leg through the fleet, which restarts a leg from its config. The CLI is the only constructor of the add (no fleet, supervisor, broker or API path reaches it). Pinned by `TestNoDrainLivePath_EngineMatrix` (every registered engine, fail-by-default classification, anti-vacuity floor, calling the same function production calls), `TestAddTable_LiveMode_BinlogSourceRefusesBeforeAnyWrite`, `TestAddTable_LiveMode_VStreamSourceRefusesBeforeAnyWrite`, `TestAddTable_LiveMode_RecordedPositionPicksTheRefusal`, `TestPositionCDCMethod`, the window file's live arms (now requiring the refusal with no snapshot, no target table and the running stream still applying its own table) and the vttestserver `NoDrain` cells. A fix-aimed review before the tag measured the drained and re-copy claims below, added the foreign-key caveat to the remedy, and stopped the in-flight-stop error from offering `--no-drain` on a source that refuses it (`TestAddTable_InFlightStopHintOffersNoDrainOnlyOnPublicationSource`).

## Not closed, stated

- **A drained add against a stream that was never stopped loses the same changes (`DRAINED-ADD-TABLE-RUNNING-STREAM-UNCHECKED`, OPEN, HIGH, silent).** `schema add-table` without `--no-drain` refuses a stop that is still in progress but does not detect a stream that is running. Measured on the vttestserver rig, MySQL 8.0 target: an add without `--no-drain` against a running PlanetScale/Vitess stream lost the same 80 deletes and 10 updates. By the code a running MySQL binlog stream takes the same window (not measured). It needs a design decision on what "stopped" means for a crashed stream and a fleet leg, and will be fixed in a later release. Until then the stop is not optional: keep the stream stopped, with no fleet reload and no supervisor or systemd restart, until `schema add-table` returns; a fleet reload restarts a stopped leg that is still in its config.
- **`schema add-table` from a PlanetScale/Vitess source still copies the whole keyspace in drained mode (`VSTREAM-ADD-TABLE-KEYSPACE-WIDE-COPY`, OPEN, loud).** Measured: beside a 150,000-row unrelated table the add read every row of it (40.3 MB); beside an 80 MB unrelated table it refuses loudly at the 64 MiB snapshot buffer, and `schema add-table` has no `--max-buffer-bytes`.
- **A `postgres-trigger` stream handed `schema add-table --no-drain --source-driver postgres` takes the publication path (`PGTRIGGER-SOURCE-DRIVER-NODRAIN-BYPASS`, OPEN, MEDIUM provisional, not measured).** By the code it is loud unless another logical-replication stream's default `sluice_slot` and `sluice_pub` exist on the same database. Do not pass a different `--source-driver` to add-table than the stream runs.
- **Not run for this release: `psverify` and `d1verify`.** Every VStream measurement was on a local vttestserver, not on PlanetScale itself. The dispatch-only Extended suites ran on this release's code (`fb0dff1a`): the pipeline vstream suite, 31 tests including `TestStreamer_VStreamAddTableKeyspaceWideCopy`, passed, as did the reshard, NOBLOB, cross-version backup, corpus and KMS suites. The Vitess chaos suite failed on `TestVitessChaos_ErrantGTID_PositionAndLineage` (no position carried by any change), which failed the same way on `main` on 2026-10-18 before this release's changes.

## Compatibility

- **Not drop-in for `--no-drain` from a non-Postgres source:** `sluice schema add-table --no-drain` from a `mysql`, `mariadb`, `planetscale` or `vitess` source now exits 1 (codeless, `NO-DRAIN-BINLOG-SOURCE` or `NO-DRAIN-VSTREAM-SOURCE`) instead of adding the table. Use the drained flow the message names.
- **Behaviour change for the trigger-CDC sources** (`postgres-trigger`, `sqlite-trigger`, `d1-trigger`): writing to a MySQL-family target they also reached the filter-flip path (never listed in the help, never measured; add-table installs no capture triggers, so it almost certainly never worked). They now take the generic refusal. The drained flow it names is not measured for them either.
- **The refusal lives in the binary that runs `schema add-table`.** An `add-table --no-drain` run by v0.163.7 or older against a stream this release runs still takes the old path and loses the same window, so upgrade the binary that runs add-table, not only the one that runs the stream.
- **Postgres sources are unchanged:** the publication live path (ADR-0030, strict zero-loss since v0.32.0) still works with `--no-drain`. No flag added or removed; `--no-drain`'s help now says it is available on a Postgres source. `BackupFormatVersion` stays 15.

## Who needs this — action required

- **Anyone who ran `schema add-table --no-drain` from a MySQL source on v0.27.0 through v0.163.7, or from a MariaDB source** (the `mariadb` driver since its CDC arrived in v0.99.271; a MariaDB server run under the `mysql` driver before that took the same code path, not measured), **into a MySQL-family target.** The added table may hold rows the source deleted, rows with old values, and be missing rows the source inserted, for every change made to it during that add. `sluice verify --depth count` cannot rule that out: a stale value does not change a count, and kept deletes and missing inserts offset each other. Re-copy any such table: with the stream stopped (`sluice sync stop --wait`), empty the target table, run `sluice schema add-table` for it without `--no-drain`, then restart the stream, keeping it stopped until add-table returns. **Empty it without firing the foreign keys that reference it:** sluice creates the source's foreign keys on the target, so a plain `DELETE` cascades into, or nulls, the rows of every table that references it with `ON DELETE CASCADE` or `SET NULL`, and the restarted stream never puts them back (measured: a plain `DELETE` left 0 of 200 rows of a cascading child, on MySQL, MariaDB and Postgres targets). Check the target for foreign keys that reference the table; then empty it on MySQL or MariaDB in one session with `SET FOREIGN_KEY_CHECKS = 0` before the `DELETE`, and on Postgres in one transaction with `SET LOCAL session_replication_role = replica` before the `DELETE` (it needs a superuser, or on Postgres 15 and later a role granted SET on that parameter; a `TRUNCATE` without `CASCADE` refuses while a foreign key references the table, and `TRUNCATE ... CASCADE` empties the children too), or re-copy the referencing tables as well. That re-copy, with the child kept, was measured exact for the table and its child on MySQL into MySQL, MariaDB into MariaDB and MySQL into Postgres, against all three kinds of damage (`TestAddTableNoDrainWindow_Binlog_RecopyRemedy`, `TestAddTableNoDrainWindow_Binlog_RecopyRemedyMariaDB`, `TestAddTableNoDrainWindow_Binlog_RecopyRemedyPostgresTarget`). `--restart-from-scratch` also works but re-copies every table in the stream's scope.
- **Anyone who ran `schema add-table --no-drain` from a PlanetScale source on v0.27.0 through v0.163.7, or from a Vitess source on v0.99.15 through v0.163.7, into a MySQL-family target.** The path was reachable by the code from those releases (the filter-flip dispatch checked only the target from `4381688d` on; the `vitess` driver arrived in v0.99.15); the loss was measured only on this release's code, so older releases are presumed affected, not proven. The table may hold rows the source deleted or changed during the add. `sluice verify --depth count` finds kept deletes but not changed values, so compare the table's rows against the source. To repair, re-copy the stream with `--restart-from-scratch`, which re-copies every table in the stream's scope (under `--schema-already-applied` it refuses while the tables hold rows, `RESTART-FROM-SCRATCH-TARGET-NOT-CLEARED`: empty them yourself first, with the same foreign-key caveat as above for any referencing table outside the stream's scope). The single-table re-copy above was measured on MySQL and MariaDB binlog sources, not on VStream.
- **Anyone using the drained `schema add-table` on any source:** stop the stream and keep it stopped until add-table returns. Nothing checks this yet.
- **`--no-drain` from a Postgres source, or into a Postgres target:** nothing to do. The Postgres live path is unchanged, and every MySQL-family source into a Postgres target already refused `--no-drain`.
- **Everyone else:** nothing to do.
