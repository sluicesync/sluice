# sluice v0.156.5

**New: exactly-once CDC apply across a crash in the middle of a source transaction (GC-38 (l), ADR-0190) — and a HIGH silent fix: a MySQL-family DSN `time_zone=` other than UTC shifted every `TIMESTAMP` sluice read or wrote, and is now refused.** Through v0.156.4, a `sync` killed partway through applying a source transaction left part of it on the target, and the restart replayed the whole transaction on top of that part. A transaction that freed a unique value and reused it, swapped values through a temporary, or changed a primary key then stopped on a duplicate key (`23505` / `Error 1062`) on every restart, recoverable only by re-copying the table. This hit MySQL/MariaDB (GTID and file/position), Postgres, PlanetScale/Vitess and trigger-CDC sources on every apply path. sluice now writes apply marks in the same target transaction as the rows, into a new control table `sluice_cdc_apply_marks`, so a restart skips what already landed and converges. This is on by default for the serial apply paths and for the lane path's barrier (keyless tables, primary-key changes). For secondary-unique tables on the default concurrent lane path it is opt-in with `--exactly-once-lanes`, because it costs a lane drain per marked transaction. Also fixed: Postgres control-table timestamps were written in the database's session zone and read as UTC, so `sync health` could fail open east of UTC; SQLite/D1 "now" DEFAULTs landed in the target session's zone. **Not a silent drop-in:** a non-UTC `time_zone=` in a MySQL-family DSN now refuses to start, sluice creates a new control table on CDC targets, and VStream sources change their position cadence. Read **Compatibility** and **Who needs this**.

## Features

**Exactly-once apply across a crash mid source transaction (GC-38 (l), ADR-0190).** Before this release, a restart re-delivered the interrupted source transaction onto a target that already held part of it. Most changes replay harmlessly because the apply is an idempotent upsert, but three shapes do not: a transaction that frees a unique value and reuses it, one that swaps values through a temporary, and one that changes a primary key. Those collided on every restart. The lane path (the `--apply-concurrency auto` default) could also replay a fully committed transaction after a crash in the window before its next checkpoint. In that window the marks cover the barrier's keyless and primary-key changes by default, and secondary-unique lane changes only with `--exactly-once-lanes`. Now every source reader gives each change a stable identity that a re-delivery reproduces exactly:

- MySQL/MariaDB binlog: the transaction's GTID, or `server_uuid` + binlog file + start offset in file/position mode.
- Postgres logical replication: the commit LSN.
- PlanetScale/Vitess VStream: keyspace, shard and that shard's GTID before the transaction.
- Trigger CDC: the change-log id, stamped with the capturing transaction's id on `postgres-trigger`, or with the row's `captured_at` on `sqlite-trigger` / `d1-trigger`.

Each identity also carries the change's position within its transaction. The applier writes a mark for every **non-idempotent** change (a table with a secondary UNIQUE index, a primary-key change, a table with no key) in the same target transaction as the row. **Every** change checks the marks on replay, and a change that a mark proves already landed is skipped. A primary-key-only table writes no marks and pays nothing.

What is covered by default, and what needs the flag:

- **Covered by default:** per-change apply (`--apply-batch-size 1`), serial batched apply (`--apply-concurrency 1`), and the lane path's barrier. The barrier applies every change to a keyless table and every primary-key change.
- **Opt-in with `sync start --exactly-once-lanes`** (fleet key `exactly-once-lanes`): changes that the lanes apply to a table with a secondary UNIQUE index, on the default `--apply-concurrency auto` path. Before a lane writes a mark, the lanes must drain and the position must be saved at the transaction's start. Without that, a lane's mark written ahead of a pending checkpoint could let a replayed earlier update re-create a row whose later delete is then skipped (ADR-0190 amendment A). That drain, once per such transaction, is expensive. Before the drain fix below, a pre-release benchmark measured it at ~99.9% of lane throughput on a workload made of such transactions (MySQL → Postgres, 7,557 → 10 transactions/s). With the fix it still costs 97–99%: 7,282 → 112 transactions/s, about half of what `--apply-concurrency 1` reaches on the same workload. So it is off by default (amendment C). It pays off only when marked transactions are a minority: with 20% of them, the flag ran 1.7–2.1× faster than `--apply-concurrency 1`.
- **Without the flag:** a crash in the middle of such a transaction on the lane path can still stop every restart on the unique collision, exactly as in v0.156.4. That outcome is loud, never silent. Every lane change still checks the marks that the serial and barrier paths write.

Keyless tables on MySQL/MariaDB binlog and Postgres logical sources are now exactly-once across such a crash; before, they duplicated rows. VStream and the trigger engines refuse keyless source tables, so the question does not arise there. A transaction's marks are deleted by the same target transaction that persists a position past it, and every cold start clears the stream's marks. Gated by `TestStreamer_CrashMidTxn_*` (`internal/pipeline/streamer_crash_midtxn_integration_test.go`), which kills a stream mid-transaction on MySQL GTID, MySQL file/position, MariaDB, Postgres, VStream and `postgres-trigger` sources into Postgres and MySQL targets. Its cells cover every apply path, keyless tables, primary-key changes, the lane post-commit window and the refusal cases. The secondary-unique lane cells run with `--exactly-once-lanes` both off and on. Each cell is graded against the source's own final state. With the flag off, the secondary-unique lane cells are pinned to the v0.156.4 loud collision on the binlog, logical-replication and VStream sources. On `postgres-trigger` they are pinned to either convergence or that collision, and to nothing else.

**Lane drains no longer wait out the idle-flush grace.** When the lane path drains its lanes (for a barrier, and for the `--exactly-once-lanes` fence), a lane holding a partial batch used to commit it only after the 100 ms idle-flush grace. The coordinator now tells each lane to commit its partial batch at once. This changes when a batch commits, never what commits or which position is saved. It applies to the `sync`, `sync from-backup` broker and chain-restore lane paths, which share the barrier. The look-ahead cap's wait is unchanged, because it waits on busy lanes, not idle ones. On a workload of primary-key-changing transactions, which all take the barrier, default-lane throughput rose from 16 to 104–107 transactions/s at 0 ms (MySQL → Postgres, Postgres → Postgres), 13 to 36 on MySQL → MySQL, and 8.6 to 12.2 against a target 5 ms away. All 192 benchmark cells ended with target equal to source. Even so, a stream made mostly of barrier changes (keyless tables, primary-key changes) still runs at about 0.45× `--apply-concurrency 1`, as it did, more slowly, before this release. Pinned by `TestOrchestrator_DrainDoesNotWaitOutTheIdleGrace` and `TestOrchestrator_FrontierWaitsGoThroughDrainLanes`.

Scope and new signals, stated exactly:

- **`APPLY-MARK-MISMATCH`** (terminal): a mark contradicts the replayed change, for example a renumbered transaction or a `--where` changed since the mark was written. sluice refuses instead of skipping on doubtful evidence.
- **`APPLY-MARKS-UNAVAILABLE`** (WARN): the mark table cannot be created or used. Causes are a PlanetScale safe-migrations branch, a role without `CREATE`, `--schema-already-applied` without the table, or missing `SELECT`/`INSERT`/`UPDATE`/`DELETE` on it. The stream then runs exactly as v0.156.4 did: nothing is lost, and a crash mid-transaction can still stop the restart on a collision. *(Corrected after publish, Bug 291.)* On a Postgres target the role-based causes mostly do not reach this WARN. A role without `CREATE` on the control schema, or one that does not own `sluice_cdc_state`, stops the start loudly while sluice ensures `sluice_cdc_state`, exactly as in v0.156.4. On Postgres the WARN is in practice the `--schema-already-applied`-without-the-table case.
- **`APPLY-MARK-UNTRUSTED`** (WARN, at most once per apply run): a restart met a mark of a transaction that was not the first one it re-delivered. sluice applies the change instead of trusting the mark. That is loud on a unique collision, but on a keyless table it can add a duplicate row, so compare that table against the source.
- **Sharded VStream keyspaces: exactly-once across a crash is best-effort.** A restart resumes every shard at once and may deliver another shard's transaction first. The interrupted transaction then replays as before, logging `APPLY-MARK-UNTRUSTED`; the worst outcome is a loud collision, never a silent skip. Unsharded keyspaces are unaffected. Rows from VStream's COPY phase carry no identity.
- **Not covered:** the `sync from-backup` broker (a separate ADR), and chain restore.

See the operator guide section "A crash in the middle of a source transaction" in `docs/operator/cdc-streaming.md`.

## Fixed

**A MySQL, MariaDB, PlanetScale or Vitess DSN `time_zone=` naming anything but UTC is refused with `DSN-TIME-ZONE-NOT-UTC` (HIGH, silent; GC-39 item 1).** sluice reads and writes a MySQL `TIMESTAMP` as a UTC instant, so it sets `time_zone='+00:00'` on every connection. It skipped that when the DSN already carried a `time_zone=`, but still read the session's digits as UTC. Measured on MySQL 8.0 under `'+09:00'`: a stored 12:00Z read back as 21:00Z, and a 12:00Z written by sluice was stored as 03:00Z, both at exit 0. The shift reached every `TIMESTAMP` that a `migrate` or `sync` cold copy read from such a source, and every one written into such a target (bulk copy, `LOAD DATA`, the CDC applier, restore). Three cases were not affected: `DATETIME` columns hold no zone, the binlog change stream carries `TIMESTAMP` as an epoch, and a named zone on a server without time-zone tables already failed loudly at connect. Every spelling of UTC is accepted. The variable name is matched the way MySQL reads it (any case, with or without `@@`, with `session.`/`local.` or `SESSION`/`LOCAL`), and a `GLOBAL` spelling is refused whatever its value. Beyond the DSN check, every new connection now reads back its own `@@session.time_zone` and refuses unless it is UTC. If that read itself fails, it WARNs and relies on the DSN check. The post-connect check exists because a pre-release cut let `@@local.time_zone` through to a random 1–7 of 30 pooled connections. `docs/operator/migrating-legacy-mysql.md`, which said sluice respects DSN session parameters, is corrected. Pinned by `TestFinishParseDSN_TimeZoneSpellings` and, on a real server, by `TestSessionTimeZone_NonUTCShiftsTimestamp_AndTheDSNDoorRefusesIt`. **Affected releases:** every release from v0.8.0 through v0.156.4. The skip-if-present injection dates from `deef403d` (v0.8.0); releases before that set no session zone at all.

**Postgres targets: `sync health`, `sluice_seconds_since_last_apply` and `sync status` age a stream correctly on a database whose default time zone is not UTC (MEDIUM, silent; GC-39 item 2).** The control tables keep timestamps in naive `TIMESTAMP` columns and read them back as UTC, but wrote them with `CURRENT_TIMESTAMP`, which stores the session zone's wall-clock digits. Measured: on `America/Los_Angeles` every stream read about 7 hours stale, so a `--max-stale-seconds` health check failed on a healthy stream. On `Asia/Tokyo` streams read 9 hours in the future, so a stalled stream looked fresh and the stall alarm failed open. Every write and DDL default into `sluice_cdc_state`, `sluice_cdc_skipped_tables`, the shard-consolidation lease table and `sluice_cdc_schema_history` now stores UTC. Column types do not change, and an existing stream's row is corrected by its next position write. Pinned by `TestControlTables_TimestampsAreUTC_UnderANonUTCDatabaseZone` in both skew directions. Gated by `TestControlTableSQL_WritesUTCIntoNaiveTimestamps`, which fails the build on any session-clock SQL literal in the Postgres and `postgres-trigger` engines. **Affected releases:** long-standing; the first affected version was not bisected.

**SQLite and D1 sources: current-time column DEFAULTs land on a Postgres or MySQL target as UTC for the column's type (MEDIUM, silent; GC-39 item 3).** SQLite evaluates `'now'` in UTC, but sluice mapped `CURRENT_TIMESTAMP`, `datetime('now')`, `date('now')`, `time('now')` and `strftime(…, 'now')` onto the target's session-zone `CURRENT_*`. Every row inserted after the migration without the column therefore got local wall-clock digits, beside migrated rows that held UTC. Measured 9 hours ahead on an `Asia/Tokyo` Postgres and a `+09:00` MySQL session, across `DATETIME`, `TIMESTAMP`, `DATE`, `TIME` and `TEXT` columns. On MySQL, `DATE DEFAULT CURRENT_DATE` and `TIME DEFAULT CURRENT_TIME` failed `CREATE TABLE` with Error 1064. Each default is now rendered for its column type on the UTC clock (`timezone('utc', now())`, `UTC_TIMESTAMP()`, `UTC_DATE()`, `UTC_TIME()`, or SQLite's exact text shape on a text column). A zoned column (`timestamptz`, MySQL `TIMESTAMP`) keeps `now()` / `CURRENT_TIMESTAMP`, which is already correct there. On Postgres, the epoch form `strftime('%s','now')` keeps its numeric default on a numeric or text column. On any other column type it is dropped with a WARN, rather than failing `CREATE TABLE` for the whole migration. A default with no faithful spelling on its column type is dropped with a WARN naming the column, and so is every one on a MySQL server older than 8.0.13, which cannot evaluate an expression DEFAULT. Also fixed, and also silent: the matcher lowercased the format string, so `strftime('%S','now')` (seconds) became the epoch and `strftime('%Y-%M-%d','now')` (minutes) became today's date. The documented `'%Y-%m-%d %H:%M:%S'` form never matched and was dropped. Pinned by `TestMigrate_SQLiteNowDefaults_AreUTC_OnANonUTCTarget` (every shape × column type × both targets × a zone on either side of UTC), `TestSQLiteNowDefaultPG_ShapeByColumnType` and `TestSQLiteNowDefaultMySQL_ShapeByColumnType`. **Affected releases:** long-standing; the first affected version was not bisected.

**Serial batched apply: a schema event inside a source transaction no longer persists its own, earlier position (pre-existing LOUD Postgres crash-loop).** A reader emits a table's schema snapshot lazily, at the table's first row after a DDL. That can fall inside a later transaction, and the snapshot carries the DDL's own position. The serial batched path (`--apply-concurrency 1`) treated it as a position boundary, so it could save a resume point behind a transaction it had already applied. On released versions this surfaced loudly: a Postgres source stream killed after a `DROP COLUMN` resumed from the snapshot's `0/0`, replayed rows from before the DDL, and crash-looped on "column … does not exist". With the new marks, the same regression would have been a silent skip. The pre-land review caught that, so it never shipped. Schema events now persist a position only outside a source transaction. As defence in depth, a mark is trusted only for the first transaction a restart re-delivers (`APPLY-MARK-UNTRUSTED` otherwise). Pinned by `schema_event_mid_txn_*` on every source × target pair of `TestStreamer_CrashMidTxn_*`, by `schema_drop_column_mid_txn_serial_batched` on the Postgres sources, and by `TestRunBatchLoop_SchemaEventInsideSourceTx_NeverPersistsItsPosition`. **Affected releases (the loud crash-loop):** pre-existing; the first affected version was not bisected.

**Docs: the `CONVERT_TZ` advisory and the session zone of `--where` / `--set` (GC-39 items 4 and 5).** The translation advisory's two-step `(ts AT TIME ZONE 'from') AT TIME ZONE 'to'` is right only on a naive `timestamp`. On a `timestamptz` the right form is `ts AT TIME ZONE 'to'`, and Postgres reads `'+05:00'` as UTC−5 (POSIX), so spell it `AT TIME ZONE INTERVAL '+05:00'`. Measured on Postgres 16 and corrected in `internal/translate/gaps.go` and `docs/translator-catalog.md`. `migrate --where`, `verify --where`, and `backfill` / `expand-contract` `--set` and `--where` run in sluice's session. That session is UTC on the MySQL family but not pinned on Postgres, so a zoneless literal against a `timestamptz` means local midnight there. `docs/operator/filtered-subset-migration.md`, `docs/schema-change-runbook.md` and those flags' `--help` now say so. They also note that `verify --where` cannot catch a zone-shifted boundary, because it renders the same predicate in the same kind of session.

**Error-code docs.** The `SLUICE-E-CDC-CHANGELOG-ID-REUSE` remedy now says to set `sqlite_sequence.seq` strictly **above** the stream's watermark. Setting it to exactly the watermark re-issues the next id.

## Compatibility

**New loud refusal:** a MySQL, MariaDB, PlanetScale or Vitess DSN carrying a `time_zone=` that is not UTC, or any `GLOBAL` `time_zone` spelling, now refuses at connect with `DSN-TIME-ZONE-NOT-UTC`. This applies to every command that opens that DSN, including CDC-only streams whose binlog values were never shifted. A configuration that ran on v0.156.4 can stop here. Remedy: remove the parameter or set it to `'+00:00'`. A new connection whose session zone reads back as anything but UTC is refused with the same marker.

**New control table `sluice_cdc_apply_marks`** on every `sync` target. sluice creates it when absent, which needs create privilege. On a MySQL-family target, `sluice control-tables ddl` prints its statement. Where it cannot be created or used (safe migrations, a non-owner or DML-only role, `--schema-already-applied` without it), sluice WARNs `APPLY-MARKS-UNAVAILABLE` and runs exactly as v0.156.4 did. On a Postgres target a non-owner or DML-only role stops earlier, as in v0.156.4 (see above). An older sluice binary ignores the table.

**Behaviour changes:**

- **PlanetScale/Vitess (VStream) sources** are now a transaction-marker stream. The reader passes each shard transaction's BEGIN/COMMIT to the applier, so the stream saves its position at transaction commits. The serial batched path (`--apply-concurrency 1`, not the PlanetScale default) now commits once per source transaction, as it does for a MySQL binlog source. Position-write cadence and batch shapes on PlanetScale sources therefore change.
- **Lane-path cost.** By default the lane path adds no drain: keyless and primary-key-changing work already drained at the barrier, and that drain is now faster (see Features). With `--exactly-once-lanes`, a source transaction that writes marks on a lane is preceded by one lane drain and one position write. Trigger sources (`postgres-trigger`, `sqlite-trigger`, `d1-trigger`) pay that per marked change, because each change is its own transaction. Primary-key-only work pays nothing either way.
- **SQLite/D1 → MySQL older than 8.0.13:** current-time DEFAULTs are now dropped with a WARN instead of being carried in the session zone.

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale, a billable cluster), `d1verify` (live Cloudflare D1) and `nekiverify` (a billable Neki cluster) suites were not dispatched, because each provisions billable or live infrastructure and runs only on the operator's call. The VStream apply identity and transaction boundaries are verified against vttestserver (unsharded, plus a two-shard resume check), not against live PlanetScale. The new post-connect `@@session.time_zone` read and the `sluice_cdc_apply_marks` create path were likewise not measured against PlanetScale or live D1.

## Who needs this — action required

- **Anyone whose MySQL, MariaDB, PlanetScale or Vitess source or target DSN carries a `time_zone=` other than UTC.** Remove the parameter; this release refuses to start until you do. Then re-copy the affected tables' `TIMESTAMP` columns, or correct them by the zone's offset with `CONVERT_TZ`, because every `TIMESTAMP` that a cold copy read from such a source or wrote into such a target was shifted. `DATETIME` columns and values that arrived through the binlog change stream were not shifted. Applies to every release from v0.8.0 through v0.156.4.
- **SQLite/D1 → Postgres or MySQL migrations and syncs whose target session zone is not UTC, where the application relies on current-time column DEFAULTs, or used `strftime('%S','now')` / `'%M'` defaults.** Upgrading changes only newly created tables. On existing targets, re-declare the DEFAULT, for example `ALTER TABLE t ALTER COLUMN c SET DEFAULT (timezone('utc', now()))` on Postgres, or `ALTER TABLE t MODIFY c DATETIME DEFAULT (UTC_TIMESTAMP())` with the column's own type on MySQL 8.0.13+. Then correct the rows inserted since the migration by the zone's offset.
- **Postgres CDC targets whose database default time zone is not UTC.** No action is needed: each stream's row self-heals on its next position write. Past `sync health` / `sluice_seconds_since_last_apply` readings on such a target were hours off in either direction, and east of UTC a stalled stream read as fresh, so treat a past "healthy" reading there as unverified.
- **Anyone whose `sync` is stopped on a duplicate key after a crash (a GC-38 (l) collision).** Upgrading does not unstick a stream that is already stuck: its interrupted transaction has no marks, so recovery is still `sync start --restart-from-scratch`. The marks protect crashes that happen after the upgrade.
- **Default-lane (`--apply-concurrency auto`) streams into tables with a secondary UNIQUE index, where a restart that stops on a collision is not acceptable.** If most transactions touch such a table, use `--apply-concurrency 1`: it is exactly-once by default and measured about twice as fast as `--exactly-once-lanes` there. If they are a minority, `--exactly-once-lanes` is faster; measure it on your workload first. Streams made mostly of primary-key changes or keyless-table writes also run faster on `--apply-concurrency 1`.
- **Operators on safe-migrations branches, DML-only roles (MySQL-family targets), or `--schema-already-applied`.** Watch for `APPLY-MARKS-UNAVAILABLE`. To get exactly-once apply, create the table (on MySQL targets, `sluice control-tables ddl` prints it) and grant the apply role `SELECT`, `INSERT`, `UPDATE` and `DELETE` on it.
- **Everyone else:** nothing to do beyond upgrading.
