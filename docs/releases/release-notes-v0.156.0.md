# sluice v0.156.0

**MINOR: silent schema loss closed on the change stream. A source schema change that `sync` or `backup stream` cannot carry now STOPS the stream under `UNFORWARDED-SCHEMA-CHANGE` instead of being ignored at exit 0 (GC-2), and the stop is recorded so a restart cannot quietly accept it.** On Postgres and MySQL/MariaDB binlog sources, a constraint, row-level-security, policy or `DEFAULT` change made on the source mid-stream never reached the target, and nothing said so. The target stayed weaker than the source; for a policy, that is a security boundary. The sharpest shape was one statement: `ALTER TABLE t ADD COLUMN x int, ADD CONSTRAINT fk FOREIGN KEY (x) REFERENCES p(id)` forwarded the column and silently dropped the foreign key, on both engines. The refusal is persisted on the target (or in the backup destination), replayed on every later start, and cleared only by `--accept-unforwarded-schema-change=<fingerprint>` naming that exact refusal. The fleet supervisor no longer restarts a leg that stopped this way. This is a minor because a stream that used to run straight through such a DDL now ends, and because the control table gains a column; read **Compatibility** before upgrading a live stream, especially on a PlanetScale safe-migrations target or with a Postgres role that does not own the control table. Also fixed: a forwarded MySQL `ADD COLUMN` whose BINARY/VARBINARY default contains a NUL byte landed the wrong default on the target (GC-29, silent).

## Changed

**`sync` and `backup stream` refuse a source schema change the change stream cannot carry, naming it (GC-2; Postgres and MySQL/MariaDB binlog sources).** Neither change stream describes these objects. pgoutput's relation message carries column names, type OIDs and key flags only. On a binlog source, a DDL clears the reader's schema cache, and the next row rebuilds the table from `information_schema` as columns plus primary key only. So the forwarding classifier had nothing to compare, and the change was dropped with no log line. Covered on Postgres: `ADD`/`DROP CONSTRAINT` (primary key, `UNIQUE`, foreign key, `EXCLUDE`, `CHECK`), `ENABLE`/`FORCE ROW LEVEL SECURITY`, `CREATE`/`ALTER`/`DROP POLICY`, `SET`/`DROP NOT NULL`, `SET`/`DROP DEFAULT` and identity or generated-column changes. Covered on MySQL and MariaDB: primary key and `UNIQUE` changes (including a prefix-length change), foreign key changes (columns, referenced table and columns, `ON UPDATE`/`ON DELETE`), and `CHECK` changes (including `NOT ENFORCED` on MySQL). Also covered there: `DEFAULT`, `EXTRA` (`AUTO_INCREMENT`, `ON UPDATE`) or generation-expression changes on an existing column, with BINARY/VARBINARY defaults compared on their true bytes re-read from `SHOW CREATE TABLE`. Nullability is not compared there, because the column forward already carries it. The mechanism: when the stream starts, the reader fingerprints these objects for every table in scope. That fingerprint is the baseline. On Postgres, each of these DDLs makes the server re-send the relation description before the next change it decodes for that table; on MySQL, the next row on the table rebuilds it. At that point the reader re-reads that one table from the catalog and diffs. On any difference it ends the stream with `UNFORWARDED-SCHEMA-CHANGE`, naming each change, before the boundary or the row is emitted, so the post-DDL row does not land. The refusal is terminal (`terminalPGError` / the new `terminalMySQLError`) and is never retried automatically. On MySQL, `classifyReaderError` now returns any terminal error untouched before its text heuristics. That is load-bearing, because the refusal quotes catalog text: a `DEFAULT 'connection reset by peer'` was otherwise re-wrapped as retriable.

What is NOT refused, because the pipeline already handles it (ADR-0091): the attributes of a column added in the same boundary, and a constraint that disappears because its column was dropped. A constraint added WITH a new column is not exempt; that is the foreign-key shape above. Two other shapes pass on Postgres: a `PRIMARY KEY`/`UNIQUE`/`EXCLUDE` whose definition text changed because a column it keys on was renamed (a retype does not change that text, so it excuses nothing), and a generation expression re-rendered by a retype. A retype does NOT excuse a new DEFAULT value, because the forwarded type change carries no DEFAULT to a Postgres target. Only a re-spelling of the same value is exempt, such as MySQL rendering `0` as `0.00` after a move to `DECIMAL`. Postgres CHECKs and policies compare on their stored expression tree with positions stripped. That tree names columns by number, so a rename leaves them equal while a real edit made in the same window is still seen. Foreign keys compare on their structured catalog tuple, not their definition text, so renaming the referenced table is not a false refusal. Constraint validity is not compared, so `ADD … NOT VALID` then `VALIDATE` does not refuse. Each exemption rests on a measurement on a real server, pinned by `TestRelationFacts_DiffPremisesOnARealServer` (Postgres) and `TestTableFacts_DiffPremisesOnARealServer` (MySQL), rather than on an assumed catalog rendering. The code is `cdc_unforwarded_classes.go` in each engine: `readRelationFacts` on Postgres, and on MySQL `readTableFacts`, graded in `dispatchRows`. Pinned by `TestDiffRelationFacts_RefusesEveryUncarriedClass`, `TestDiffRelationFacts_ExemptsConsequencesOfHandledColumnChanges`, `TestDiffRelationFacts_ForeignKeyComparesStructureNotText`, `TestDiffTableFacts_RefusesEveryUncarriedClass`, `TestUnforwardedDoor_BothProtocolArmsCallIt` (both the protocol-v1 and v2 relation-message arms must call the door), `TestUnforwardedChangeError_IsTerminalAndCarriesMarker`. End to end, `TestStreamer_PGSource_UnforwardedSchemaChange_Refuses` (real PG → PG), `TestStreamer_MySQLSource_UnforwardedSchemaChange_Refuses` (MySQL 8 → PG) and `TestStreamer_MariaDBSource_UnforwardedSchemaChange_Refuses` (MariaDB 11.4 → PG) each require the stream to end naming the change, the target's catalog not to have it, and the post-DDL row not to land. Each also carries a forwarded-column control that must keep applying.

**An automatic retry keeps the baseline instead of re-reading it (GC-32).** An ADR-0038 in-process retry after a transient error opens a fresh reader. A fresh catalog read would already contain any change made before the error, so a dropped connection between the source DDL and the next write would have accepted the change silently. Both readers now expose the baseline through `UnforwardedBaseline` / `SetUnforwardedBaseline`. The pipeline hands the previous reader's baseline to the next one within a run, through `wireReaderSchemaSeed` for `sync` and through `carryUnforwardedBaseline` on `backup stream`'s transient reopen (`unforwarded_baseline_carry.go`). A reader that failed before it ever started streaming passes on the baseline it was handed rather than nothing, so two failures in a row cannot drop it. The carry is reset at both cold-start sites, where a cold start has just rebuilt the target from the current source schema. Pinned by `TestUnforwardedBaseline_CarriedAcrossReaders`, `TestUnforwardedBaseline_PassesOnWhatItWasHandedWhenNeverStarted`, `TestWireUnforwardedBaseline_CarriesAcrossAttemptsAndResetsPerRun`, `TestUnforwardedBaselineCarry_WiringSites`. On real servers, `TestStreamer_PGSource_UnforwardedSchemaChange_SurvivesTransientRetry` and `TestStreamer_MySQLSource_UnforwardedSchemaChange_SurvivesTransientRetry` pin the same behaviour.

**The refusal is persisted, and every later start refuses before any change stream opens.** A new process has no in-memory baseline to carry. A systemd `Restart=on-failure` unit, a pod restart or a supervisor would start a fresh reader that baselined the catalog already holding the refused change, and accepted it silently, forever. So a run that ends with the refusal records it. For `sync`, it goes on the stream's row of the target's `sluice_cdc_state`, in the new column `unforwarded_refusal`. For `backup stream`, it goes in the destination's `stream_state.json`, under the new key `unforwarded_schema_change_refusal`. The record is written on a context the run's own cancellation cannot abort. If it cannot be written, sluice logs an ERROR saying a restart will NOT refuse again. The startup door (`phaseRefuseRecordedUnforwardedChange` for `sync`, `refuseRecordedUnforwardedChange` for `backup stream`) runs before any CDC reader opens, on every start path. That includes warm resume, multi-database resume, `--restart-from-scratch` and `--reset-target-data`, and every automatic retry. It replays the recorded refusal together with its fingerprint. The classification rides `ir.ErrUnforwardedSchemaChange` through every pipeline wrap, and the persistence contract is `ir.UnforwardedRefusalStore`, implemented by both engines' appliers (the postgres-trigger engine delegates to the Postgres one) over a shared skeleton in `appliershared`. Pinned by `TestStreamer_PGSource_UnforwardedRefusal_SurvivesRestart`, `TestStreamer_MySQLSource_UnforwardedRefusal_SurvivesRestart` and `TestBackupStream_UnforwardedRefusalSurvivesARestart`. With the door disabled, both integration cells go red from their own "restart did not refuse" assertion, which reproduces the defect. Also pinned by `TestUnforwardedRefusalStore_RoundTrip`, `TestUnforwardedRefusal_SentinelSurvivesThePipelineWrapping` and `TestStreamStateHeartbeat_PreservesTheRecordedRefusal`.

**The acknowledgement is fingerprint-bound: `--accept-unforwarded-schema-change=<FINGERPRINT>` on `sluice sync start` and `sluice backup stream run`.** The replayed refusal prints `fingerprint <12 hex>`, the first 12 hex digits of the SHA-256 of the recorded refusal; the record-time log line carries it too. The stored refusal is prefixed with the moment it was recorded, so the same change recurring later gets a new fingerprint. Only that value clears THAT record. A different value is refused, and the message says the acknowledgement "names a different refusal than the one recorded". An empty value keeps refusing. On `sync`, the flag is consumed once it clears the record, so a later refusal in the same process is not pre-accepted. A flag left in a systemd `ExecStart` line or a wrapper script therefore cannot accept a later refusal on the next automatic restart — not even a recurrence of the same change. It is deliberately not a `syncs.yaml` key, because standing config would pre-accept refusals. Remedy: apply the same change to the target first (for `backup stream`, take a new full backup first, since a chain restored from the old full would lack the change), then start once with the flag. **The flag takes a fresh baseline, so passing it without the first step accepts the difference permanently**, and nothing reports it again. Pinned by `TestStreamerUnforwardedDoor_MismatchedFingerprintRefuses`, `TestRecordedUnforwardedRefusalText_IdenticalRefusalsGetDistinctFingerprints`, `TestStreamerUnforwardedDoor_ZeroValueRefuses`, `TestStreamerUnforwardedDoor_AckClearsAndIsConsumed` and `TestStreamerUnforwardedDoor_NothingRecorded`.

**`sluice sync run` does not restart a leg that stopped with `UNFORWARDED-SCHEMA-CHANGE`.** `superviseOne` marks that leg `failed` at once and logs it at ERROR, naming the acknowledgement route. Under the default policy it used to restart the leg on backoff forever. A restart can only refuse again, and it is the one refusal where a restart that somehow skipped the record would accept the change. The exception is scoped to this sentinel on purpose. Every other failure is restarted exactly as before, including other terminal errors: several are terminal only to the in-process retry, and a fresh run is what recovers them. To bring the leg back, apply the change to the target and run `sluice sync start` for that stream once outside the fleet with the flag. Then stop it with `sluice sync stop --wait` and restart the fleet. Off Windows, a `SIGHUP` also works, since its reload starts a failed leg that is still configured. Pinned by `TestSupervisor_UnforwardedRefusalIsNotRestarted` and `TestSupervisor_OtherTerminalFailuresAreStillRestarted`, with `TestSupervisor_DefaultPolicyRestartsForever` unchanged as the control.

**What the door does not catch, stated so it is not read as broader.** A change made after the last acknowledged position and before the stream started is already in the baseline. That covers a change made while the stream was stopped, one made during the cold-start copy, a DDL a lagging stream had not reached when it stopped, and anything made before you upgrade and restart onto this release. Upgrading does not find an old gap. Detection needs a later write to the same table; a change on a table nobody writes to again is not seen until someone does. On MySQL, a DDL whose statement runs under an out-of-scope default database (`USE other; ALTER TABLE db.t …`) does not clear the schema cache and is not seen. The catalog read is current, not position-anchored, so a change reverted before the read is missed (net no change). Several things are not compared: plain (non-constraint) indexes (the documented index-DDL gap), Postgres column collation, and policies or RLS on a partitioned Postgres root. `backup incremental` opens a fresh reader every run, so a change between two incrementals is in the next run's baseline. PlanetScale and Vitess (VStream) sources are not covered: that reader never runs this path, though the VStream wire does carry DDL events, so the same door is buildable there (filed GC-31). The postgres-trigger, sqlite-trigger and d1-trigger engines use their own readers and are not reached. There are known false refusals, each costing one acknowledgement. On MySQL, `DROP COLUMN b` shrinks a composite `UNIQUE (a, b)` to `UNIQUE (a)` while Postgres drops the whole index, and the reader cannot see which the target did. On Postgres, a constraint rename refuses as a drop plus an add. A periodic source-to-target comparison that would close the stopped-stream gap is filed separately (GC-30). The operator section is `UNFORWARDED-SCHEMA-CHANGE` in `docs/operator/cdc-streaming.md`, and the honest-list entry is in `docs/production-readiness.md`.

## Fixed

**MySQL binlog `sync`: a forwarded `ADD COLUMN` with a BINARY/VARBINARY default containing a NUL byte now lands the declared bytes on the target (GC-29, silent).** MySQL's `information_schema.columns.COLUMN_DEFAULT` cuts such a default off at its first NUL byte. The cold-start schema read has recovered the true bytes from `SHOW CREATE TABLE` since v0.99.187. But `loadTableSchema`, the CDC reader's per-table re-read at a DDL boundary, did not. Its defaults are what the ADR-0091 forward intercept re-emits as the target column's DEFAULT. Measured on a real MySQL → Postgres run with the recovery removed, all at exit 0:

- A leading NUL (`BINARY(1) DEFAULT 0x00`) landed as the two ASCII bytes `0x`.
- Any VARBINARY with a NUL (`VARBINARY(4) DEFAULT 0xFF00`) landed as `0xFF`.
- A mid-value NUL on BINARY (`BINARY(3) DEFAULT 0xFF00AA`) landed as `0xFF0000`.

A BINARY default whose only NULs are trailing was not wrong end to end, because the target DEFAULT is padded to the column's width. The boundary re-read now runs the same predicate (`binaryLiteralDefaultNeedsRecovery`) and the same recovery (`recoverFromShowCreate`) as the seed: one `SHOW CREATE TABLE`, only for a table carrying such a default. Replicated rows were always correct, because CDC rows carry explicit values. The harm is the default that every later target-side write omitting the column receives. MariaDB was unaffected, because it escapes NULs in `COLUMN_DEFAULT` rather than truncating. So were PlanetScale/Vitess, whose VStream lane takes defaults from the seed reader. Pinned by `TestLoadTableSchema_DefaultAgreesWithSeed_EveryBinlogFlavor` and on real MySQL → Postgres by `TestStreamer_AddColumnForward_MySQLToPostgres_BinaryDefaultNUL`. The latter reads back a target-side INSERT omitting every forwarded column as hex and compares it against the declared DDL bytes, including VARBINARY in `SHOW CREATE`'s quoted form and BINARY with leading and interleaved NULs. **Affected: vanilla MySQL binlog sources only.** Certainly affected: v0.99.45 (default-on forwarding, ADR-0091) through v0.155.1 on a table without secondary indexes, and v0.155.0–v0.155.1 on an indexed one (before v0.155.0 an indexed table's boundary halted instead, GC-1). The opt-in `--forward-schema-add-column` path of v0.79.0–v0.99.44 carried the same projection but was not re-derived.

## Compatibility

**Behaviour change: a Postgres or MySQL/MariaDB binlog `sync` or `backup stream` that used to run straight through such DDL now stops.** That covers a constraint, RLS, policy, `NOT NULL`, `DEFAULT`, identity, `EXTRA` or generation-expression DDL on the source. The stream ends with `UNFORWARDED-SCHEMA-CHANGE` at the next write to that table and stays stopped until acknowledged. If your source takes such DDL routinely during a sync, plan for it: a deploy that adds a `CHECK`, a migration tool that adds foreign keys, a tenant onboarding that creates policies. The cheapest path is the drained model in `docs/schema-change-runbook.md`: stop the stream, apply the change on both sides, and restart. A change made while stopped is in the next baseline, so it does not refuse. Column DDL that sluice forwards is unaffected, as is every source on the VStream and trigger-CDC lanes.

**The refusal exits 1, not 3.** It carries no `SLUICE-E-*` code yet, so there is no `code` or `hint` in the JSON log or envelope. Match on the marker `UNFORWARDED-SCHEMA-CHANGE`. Automation that treats a codeless exit 1 as "retry" will simply see it refuse again, since it is recorded, but alert on the marker rather than letting it loop.

**New control-table column and state key.** `sluice_cdc_state` gains `unforwarded_refusal` (`TEXT NULL`). `EnsureControlTable` adds it on the next start after upgrading, and a fresh CREATE and `sluice control-tables ddl` already include it. `stream_state.json` gains the key `unforwarded_schema_change_refusal`, which is written only when a refusal is recorded. Two setups cannot add the column themselves; in both, add it by hand after upgrading and before restarting streams.

- **PlanetScale safe-migrations branch.** The direct ALTER is refused. Without `--schema-already-applied`, startup fails with `SLUICE-E-PS-DIRECT-DDL-BLOCKED`, naming the statement. With it, the usual safe-migrations setup, the start fails too: every start first makes sure a refusal could be recorded, and refuses to stream when the column is missing and cannot be added, or exists but this role cannot write it, because a stream that could not record a refusal would have it accepted silently by the next restart. Ship ``ALTER TABLE `sluice_cdc_state` ADD COLUMN `unforwarded_refusal` TEXT NULL`` through `sluice deploy-ddl`.
- **A Postgres role that does not own an existing control table.** Postgres checks ownership before `IF NOT EXISTS`, so this is typically the `--schema-already-applied` setup. The store detects the column before it ALTERs, so a DML-only role records and clears refusals once the column exists (`TestUnforwardedRefusalStore_NonOwnerRoleRecords`). But only the owner can add it: `ALTER TABLE sluice_cdc_state ADD COLUMN unforwarded_refusal TEXT NULL`.

The startup door checks the column on every start, before any change stream opens: a column that is missing and cannot be added stops the start with a message naming the statement to run, and a read error stops it too, rather than streaming unchecked.

**New flag: `--accept-unforwarded-schema-change=<FINGERPRINT>`** on `sync start` and `backup stream run`. It takes a value. The refusal that first stops the stream names the flag without one, and the replayed refusal on the next start prints the fingerprint to pass. It is not a `syncs.yaml` key.

**Downgrade.** An older binary ignores a recorded refusal: it neither reads the column nor keeps the state-file key. A downgrade followed by a restart therefore takes a fresh baseline and accepts the refused change silently. Apply any recorded change to the target before downgrading.

**One new way for a stream to fail to START.** The baseline is read from the source catalog when the stream opens; if that read fails, the stream fails to start loudly rather than running unguarded. The reads touch only standard catalogs. On Postgres those are `pg_class`, `pg_constraint`, `pg_policy`, `pg_attribute` and `pg_attrdef`. On MySQL/MariaDB they are the `information_schema` tables `columns`, `statistics`, `table_constraints`, `key_column_usage`, `referential_constraints` and `check_constraints`, plus `SHOW CREATE TABLE` for a table with a BINARY/VARBINARY literal default. A role that can already run sluice's schema read should be able to run them.

**Not run for this release:** the `psverify` (billable PlanetScale) and `d1verify` (live Cloudflare D1) tagged suites were not dispatched. The new door is inert on the trigger-CDC, VStream and D1 lanes, so the PlanetScale MySQL and D1 paths are untouched. PlanetScale Postgres is a plain Postgres source and DOES run the Postgres door and its persistence. That path is covered by the per-PR real-Postgres suites, not by a live PlanetScale Postgres run.

## Who needs this — action required

- **Anyone who has run `sync` or `backup stream` from a Postgres or MySQL/MariaDB binlog source, on any release through v0.155.1, while the source took a constraint, RLS, policy, `NOT NULL`, `DEFAULT`, identity or generation-expression DDL.** The target, or the chain restored from that stream, does not have the change. Upgrading will NOT find it, because the baseline this release takes at start already includes it. Audit the tables that took DDL mid-stream, before or right after upgrading, and apply any difference to the target by hand:
  - On Postgres, compare `pg_constraint`, `pg_policy`, `pg_class.relrowsecurity`/`relforcerowsecurity`, `pg_attribute.attnotnull` and `pg_attrdef` source against target.
  - On MySQL/MariaDB, compare `information_schema.table_constraints`, `check_constraints`, `referential_constraints` and `columns.COLUMN_DEFAULT`/`EXTRA`.

  Pay particular attention to row-level security and policies (a tenant-isolation boundary), and to any `ADD COLUMN … ADD CONSTRAINT … FOREIGN KEY` statement, whose foreign key was dropped. For `backup stream`, take a new full backup. This is a never-carried gap, not a regression. It has existed as long as the Postgres and MySQL binlog CDC lanes have (MariaDB since v0.99.271).
- **PlanetScale safe-migrations targets, and Postgres targets where sluice's role does not own `sluice_cdc_state`.** Add the `unforwarded_refusal` column as described under Compatibility before restarting your streams. Otherwise a refusal cannot be recorded, and a restart would accept it.
- **Anyone running `sync` from a vanilla MySQL source that forwarded an `ADD COLUMN` whose BINARY/VARBINARY default contains a NUL byte.** That means a leading NUL, a mid-value NUL, or any NUL on VARBINARY. Check the target's `column_default` for each such column and correct it with `ALTER TABLE … ALTER COLUMN … SET DEFAULT`. Rows are intact.
- **Anyone operating a long-running Postgres or MySQL binlog stream under systemd, Kubernetes, a wrapper script or `sync run`.** Expect `UNFORWARDED-SCHEMA-CHANGE` (exit 1) if the source takes the DDL above. Teach runbooks the apply-then-acknowledge remedy, and keep the flag out of service definitions: it belongs on one manual start.
- **PlanetScale / Vitess (VStream) sources.** Nothing changes. The gap remains there (GC-31), so audit the target by hand after any such DDL.
- **Everyone else.** Nothing to do.

## Contributors

The bash pre-commit hook (`.githooks/pre-commit`) no longer aborts silently on nearly every commit. Under `set -e`, its NUL-byte and merge-conflict-marker guards assigned from a `while` loop whose exit status was that of its last body command, so a clean last file killed the hook with no message. Separately, the NUL match (grep with -qP) never matched a NUL without -a, so the NUL guard could not fire. Both are fixed (done || true on both loops, and -qaP) and verified in both directions. `scripts/pre-commit.ps1` was unaffected. No effect on the shipped binary.
