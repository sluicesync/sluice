# sluice v0.159.0

**CRITICAL fixes: three silent-data defects in CDC, each independently reviewed before release, and new refusals that change behaviour. This is a MINOR release, not a drop-in: read Compatibility and Who needs this before upgrading.** (1) **RENAME-SWAP-INVISIBLE (CRITICAL):** on a MySQL or MariaDB binlog source, a sequence of ALTERs that leaves a column name holding a different column (`DROP COLUMN c, ADD COLUMN c`, `DROP COLUMN b, RENAME COLUMN c TO b`, a swap whose order is then restored) produced no schema boundary at all. The target kept every existing row's old values under the reused name, at exit 0, at the head and on a warm resume, under `MINIMAL` and `FULL` alike. These changes now refuse with `COLUMN-IDENTITY-CHANGED`. The refusal fires at the DDL itself, so a restart cannot skip it. (2) **DEFERRED-KEY-COLLATION (HIGH):** a `FULL`-metadata row held to an earlier shape was never compared on collation, so a key's collation change folded behind a later retype merged a row before the stream refused. (3) **KEY-COLLATION-FIRST-BOUNDARY (HIGH):** a key column's collation or character-set change merged distinct source rows into one target row at exit 0 when a stream met the change as the first schema boundary of a run (a warm resume, or a live stream's first boundary after its cold start), on MySQL and on Postgres to Postgres. It also merged on every `--schema-changes=refuse` stream and in every chain restore. **Existing targets that crossed these changes may already hold merged or misplaced rows, and upgrading does not repair them.**

## Fixed

**A MySQL-family schema change that leaves a column name holding a different column now refuses instead of leaving the target's rows under the wrong column (CRITICAL, silent; RENAME-SWAP-INVISIBLE).** A MySQL column has no stable id, so every comparison sluice made was by name. Some ALTER sequences end with the same names and order they started with, and no shape comparison can see them:
- `DROP COLUMN c, ADD COLUMN c` of the same type, in one ALTER or two;
- `RENAME COLUMN c TO tmp, ADD COLUMN c`;
- `DROP COLUMN b, RENAME COLUMN c TO b`, in one ALTER or two;
- a rename swap (`RENAME COLUMN b TO c, RENAME COLUMN c TO b`, or the `CHANGE` spelling) followed, before the table's next row, by a `MODIFY … AFTER` that restores the order.

These were measured on MySQL 8.4 before the fix. Under `MINIMAL`, every shape was silent live at the head, on a warm resume, and in a `backup incremental` + restore. Behind the head, v0.158.0's look-ahead refused them first, but only when a row of the table sat between the stream and the change. Under `FULL`, every shape was silent on every entry, behind the head included. `FULL` metadata is no mitigation here, because consecutive TABLE_MAPs name the same columns before and after the change.

sluice now reads the `ALTER TABLE` text in the binlog. Every statement reaches the reader in binlog order, whatever the metadata setting or lag. A per-table ledger records what each statement did to column identity. When a name now holds another column, the stream refuses with `COLUMN-IDENTITY-CHANGED`, a refusal that repeats on every restart. It refuses at the DDL event itself, so a position persisted past the ALTER followed by a restart cannot skip it, and again at the table's next row. The remedy is a re-copy: `sluice sync start --reset-target-data --yes` with the stream's other flags unchanged, or a fresh `backup full` for a chain. A pure permutation in one statement, such as a plain swap or rotation, is still left to `COLUMN-ORDER-CHANGED`, whose remedy is to apply the same renames on the target.

Review found three silent gaps in the first cut, and all were fixed before release:
- the refusal at the DDL itself, described above;
- a no-op `CREATE TABLE IF NOT EXISTS` (which MySQL binlogs, and ORMs issue routinely) or a `DROP TEMPORARY TABLE` reset the ledger, and no longer does;
- MariaDB statements the parser could not read only logged a WARN.

On MariaDB, `IF [NOT] EXISTS` on a column clause is now read as taking effect. A statement that still cannot be parsed refuses, marked `COLUMN-IDENTITY-UNREAD`, when it names an in-scope table and either spells `DROP`, `CHANGE` or `RENAME` or follows a statement that vacated a name of that table. Otherwise it logs a WARN and the stream continues, so a routine `ADD COLUMN u UUID` keeps flowing.

The refusal reaches every lane that reads the binlog: `sync start` (live and warm), `backup incremental`, `backup stream` and the broker. Pinned by `TestRenameSwapInvisible_MySQL80`, `TestRenameSwapInvisible_MySQL84` and `TestRenameSwapInvisible_MariaDB` (each with a `_FullMetadata` twin): 434 cells, every one graded by column name against the source, plus `TestColumnIdentity_DDLSequences`. **Affected releases:** not bisected to a first release. The cause has been present in every release with MySQL-family binlog CDC, so treat every release through v0.158.1 as affected. In v0.158.0 and v0.158.1, the look-ahead refused a `MINIMAL`/`NO_LOG` case behind the head only when a row of the table sat between the stream and the change.

**A `FULL`-metadata row held to an earlier shape is now compared on its character columns' collation (HIGH, silent; DEFERRED-KEY-COLLATION).** Since v0.158.0, under `binlog_row_metadata=FULL`, sluice holds a row whose recorded shape includes a column dropped or retyped later in the binlog to the table's previous shape. The TABLE_MAP records a character column's collation as an ID, but sluice named that ID only by character set and then cleared the collation. A collation change folded behind a later retype was therefore never compared. This was measured on MySQL 8.0 and 8.4 under `FULL`, on a warm resume with an earlier row:
1. Key `k` is `utf8mb4_0900_ai_ci` and holds `'a'`.
2. `MODIFY k … COLLATE utf8mb4_bin`, then row 99 `'A'`.
3. `MODIFY k VARBINARY(80)`.

Row 99 reached the target's `_ci` key ahead of the folded boundary and merged into row 1: row 1 was gone, and row 99 was kept with `k = 'a'`. Only then did the boundary refuse with `RESUME-SCHEMA-DIVERGENCE`, and that refusal's remedy leaves the merge in place.

sluice now names the recorded ID from the source's own collation table: MariaDB's `FULL_COLLATION_NAME`, otherwise `information_schema.COLLATIONS`. It never uses a static table, because MySQL and MariaDB give the same high IDs to different collations. A name that differs from the earlier shape's refuses with `DEFERRED-SCHEMA-CHANGE`. An ID the source's table cannot name also refuses, where the first cut had skipped the comparison (review finding, fixed before release). Pinned by `TestHoldDecodedOrder_DeferredShapeMatrix` (`VARCHAR`/`CHAR`/`TEXT` collation changes, PAD SPACE → NO PAD, unnamed IDs) and by key-collation cells added to the double-retype matrix on MySQL 8.0, 8.4 and MariaDB 11.4. `TestCDCRecordedColumnTypes_EveryFamily` is the no-false-refusal half. **Affected releases:** v0.158.0 and v0.158.1. The deferred-shape hold first shipped in v0.158.0. Before it, the same row was decoded through the catalog, and its merge falls under KEY-COLLATION-FIRST-BOUNDARY below.

**A key column's collation or character-set change no longer merges rows on the target (HIGH, silent; KEY-COLLATION-FIRST-BOUNDARY).** Take a key that was `utf8mb4_0900_ai_ci` and becomes `utf8mb4_bin` through `MODIFY k … COLLATE utf8mb4_bin`. PAD SPACE → NO PAD, or `utf8mb4` → `ascii_bin` in place, behave the same way. A new row distinct from an existing one only under the new collation (`'A'` beside `'a'`, `'a '` beside `'a'`) was merged into the existing row at exit 0. On a PRIMARY KEY the existing row vanished; on a UNIQUE column it was overwritten. It happened whenever the stream met the change in one of these ways:
- as the first schema boundary of a run: a warm resume, or a live stream's first boundary after its cold start;
- on any `--schema-changes=refuse` stream;
- in any `backup incremental` + chain restore, whose schema diff did not compare collations at all;
- on a Postgres source, on every entry including the live one, because `pgoutput` carries no collation.

This was measured on MySQL 8.0 and 8.4 under `FULL` and `MINIMAL`, and on Postgres 16. It is fixed in three layers:
- **At the boundary (`KEY-COLLATION-CHANGED`).** A key column's change is judged against the source's own earlier shape of the table: the cold-start read, or the stream's retained schema history. Under `--schema-changes=forward` it is forwarded to the target column, as the same change seen live always was. Under `refuse` it stops the stream with `SCHEMA-CHANGE-REFUSED`. With no earlier shape on record, a key whose collation differs from the target's stops the stream with `RESUME-SCHEMA-DIVERGENCE`. Each refusal names the column and both collations. Applying the change on the target and restarting converges.
- **In the applier (`KEY-COLLATION-MERGE`, `KEY-COLLATION-GUARD-UNSUPPORTED`).** This backstop covers whatever no boundary shows. Each upsert now runs a check inside the statement, which adds no round trip. If the key matched an existing target row that the target's collation treats as equal but the source's current collation treats as different, the upsert refuses with `KEY-COLLATION-MERGE` before anything is written. The check is armed only where the source key's current collation distinguishes values the target's collation equates. A table whose source and target key collations agree carries no check, and a `_ci` source re-delivering a case-only change still converges. It covers MySQL, MariaDB, Vitess/PlanetScale and Postgres targets on every change-apply path: serial, batched and lanes, and through them the broker and chain restore. If the target cannot express the source collation for the comparison, the stream refuses with `KEY-COLLATION-GUARD-UNSUPPORTED` at the table's first upsert. The Postgres CDC reader now reads each column's collation from the catalog at every Relation message.
- **In chain restore.** `backup incremental` now records a collation-only change to a key column as a `column-collation` delta. Chain restore and the broker apply that delta to the target before the window's rows.

Review fixes before release:
- A MySQL 8 → MariaDB stream merged with no schema change at all. The cold start created a `utf8mb4_0900_ai_ci` key as MariaDB's PAD SPACE `utf8mb4_uca1400_ai_ci`, so a source row `'a '` overwrote `'a'` (measured on MariaDB 10.11 and 11.4). The key is now compared under `utf8mb4_uca1400_nopad_ai_ci`.
- The guard's error expression no longer fails MariaDB's type check on `UUID`, `INET6` and `GEOMETRY` columns. It is byte-exact across 20 column types on four servers.
- Collation determinism now survives a backup manifest, so a chain restore from Postgres to MySQL arms the guard.
- The Postgres readers record the database default collation as deterministic. This closes a case where a key moved to the default while the stream lagged replayed earlier rows unguarded.
- A Postgres default-collation UNIQUE key beside a primary key, landing on a MySQL-family target, is now guarded.
- When the key that identifies a row is itself compared differently, or the table has no primary key, the refusal leads with the remedy that converges: a re-copy.

Pinned by `TestJudgeKeyCollation_Matrix`, `TestKeyCollationFirstBoundary_MySQL80_Full`, `_MySQL84_Minimal`, `_MySQL84_Full`, `_Postgres16`, `_ChainRestore`, `_ChainRestore_PGCollateCToMySQL`, `_MySQL84ToMariaDB_PadSpace` and `_PostgresDefaultUniqueToMySQL`. Engine-level pins are `TestKeyCollationGuard_MySQLFamily`, `TestKeyCollationGuard_Postgres`, `TestKeyCollationGuard_HangTypeFamilies` and `TestVStream_KeyCollationGuard_ShardedTarget`. Every integration cell is graded by key bytes against the source. **Affected releases:** not bisected to a first release; treat every release through v0.158.1 as affected. The causes are long-standing: `pgoutput` has never carried a collation, the incremental schema diff never compared one, and the first-boundary and refuse-mode comparisons ignored collation. The MySQL 8 → MariaDB arm dates from the MariaDB flavor's collation remap (v0.99.268).

**A failing `sluice verify` names the kinds of drift it found (LOW, message; Bug 303).** The closing line said `drift detected: N table(s) with row-count mismatch` whatever had failed the run, including a `SAMPLE-MISMATCH` or `COLUMN-MISMATCH` whose counts matched. It now counts each table's verdict, the same word as its JSON `status`. For example: `drift detected: 2 table(s) mismatched (1 column-mismatch, 1 sample-mismatch)`. The per-table rows and the exit codes are unchanged. Pinned by `TestVerifyExitError`. **Affected releases:** the wording dates from v0.12.0.

**MySQL 8 sample verify's oversized-`JSON` refusal names its remedy (LOW, message).** v0.158.1's refusal for a `JSON` value past `max_allowed_packet` named the row but not a way forward. It now names the likely cause and the fix: `SET GLOBAL max_allowed_packet = …`, which reaches new connections, then `sluice verify --include-table <table>`. Pinned by `TestNullHashInputRefusal_NamesTheRemedy`, and live by `TestSampleRowHashes_ValueLargerThanMaxAllowedPacket`, which checks that the remedy works. **Affected releases:** v0.158.1.

**Test-only:** `TestGrowGate_EpisodeLadderClimbsPerWindowAndResetsAfterAHealthyStretch`, which failed on the v0.158.0 tag's Windows leg, now runs on a fake clock. The failure was a stale hold the test read under CPU contention, not a missed reset in the gate. No product change.

## Compatibility

**This is not a drop-in for streams whose sources change key collations or recycle column names.** Streams that make neither kind of change behave as before. **The behaviour changes:**
- **A column swap spelled as three separate renames through a temporary name** (`RENAME COLUMN b TO tmp; RENAME COLUMN c TO b; RENAME COLUMN tmp TO c`) now refuses with `COLUMN-IDENTITY-CHANGED` at its second statement, where it cannot be told from `DROP b; RENAME c TO b`. The remedy is a re-copy. The same swap in one statement is still `COLUMN-ORDER-CHANGED`, which accepts applying the same renames on the target.
- **`DROP COLUMN c, ADD COLUMN c`, `RENAME COLUMN c TO tmp, ADD COLUMN c` and `DROP COLUMN b, RENAME COLUMN c TO b` on a streamed MySQL/MariaDB table now refuse**, including in `backup incremental` and `backup stream`, which then need a fresh `backup full`.
- **On MariaDB, a no-op `DROP COLUMN IF EXISTS c, ADD COLUMN c` now refuses**, because the clause is read as taking effect.
- **On MariaDB, a statement sluice cannot parse now refuses** (`COLUMN-IDENTITY-UNREAD`) when it names an in-scope table and either spells `DROP`, `CHANGE` or `RENAME` or follows a statement that vacated a name of that table. Other unparsed statements still WARN and flow.
- **A key column's collation or character-set change now refuses on a `--schema-changes=refuse` stream**, and is forwarded under `forward`. Under `forward`, a key-collation change together with any other difference in the same boundary refuses.
- **When there is no earlier shape on record**, a stream between two engines of the same name whose target key column has a different collation from the source's now refuses its first boundary for that table with `RESUME-SCHEMA-DIVERGENCE`. That includes a target deliberately created with a different collation.
- **An upsert that would merge two source keys** the target's collation treats as equal now refuses with `KEY-COLLATION-MERGE` rather than merge. For a table with no primary key, or whose identifying key is itself compared differently, a re-delivered case-only change also refuses on every start, and the remedy is a re-copy.
- **A source collation the target cannot compare under** refuses with `KEY-COLLATION-GUARD-UNSUPPORTED` at the table's first upsert. So does a MySQL-family source key on a Postgres target column with a nondeterministic collation, and a MySQL 8 source into MariaDB older than 10.10 (not measured; below the supported 10.11 floor).
- **A `FULL`-metadata backup window** in which a key's collation change is folded behind a later retype now refuses with `DEFERRED-SCHEMA-CHANGE`. Measured cases of this had restored exact.

**Postgres reader:** the CDC reader now reads `pg_attribute.attcollation` (joined to `pg_collation`) at every Relation message. That is one catalog query per table per session and per schema change, and it needs no new privilege. Both Postgres readers now record the database default collation as deterministic.

**Backup format:** unchanged. `BackupFormatVersion` stays 12. Manifests gain an optional per-type `collation_determinism` field. It is additive, and older binaries ignore it (read from the code; not run against an older binary). It is excluded from the chain fingerprint (`fingerprintType`, pinned by `TestSchemaHash_ExcludesCollationDeterminism` as equality with the field absent), so no existing chain is repartitioned. An incremental captured by this release can record a `column-collation` delta. An older binary restoring such a chain reads that delta as no change and does not apply it, so restore chains captured by v0.159.0 with v0.159.0 or later.

**Markers, no new error codes:** `COLUMN-IDENTITY-CHANGED`, `COLUMN-IDENTITY-UNREAD`, `KEY-COLLATION-CHANGED`, `KEY-COLLATION-MERGE` and `KEY-COLLATION-GUARD-UNSUPPORTED` are new. `DEFERRED-SCHEMA-CHANGE`, `SCHEMA-CHANGE-REFUSED` and `RESUME-SCHEMA-DIVERGENCE` are existing refusals with wider scope. **Verify output:** the closing line of a failing `sluice verify` has new wording, so a CI step that greps for `with row-count mismatch` needs updating. Exit codes are unchanged.

**Not covered (filed in `docs/dev/audit-backlog.md`):**
- **VStream sources (Vitess/PlanetScale).** The stream carries no collation, so none of the key-collation checks arm. The column-identity ledger reads only the binlog, so the VStream reader is not covered either (unmeasured).
- **A Postgres-source PRIMARY KEY (or a UNIQUE key on a table without one) on the database default collation, landing on a MySQL-family target.** That key is created under the target's default collation, usually case-insensitive, and a second source row distinct only in case merges. This is deliberately not armed, because it would also refuse a re-delivered case-only change of that key, which converges today. A UNIQUE key beside a primary key on the same pairing is checked.
- **The copy phase's idempotent row writer** (a chunked cold copy of a large table, a resumed copy, `add-table`, the VStream copy) upserts unguarded (KEY-COLLATION-ROWWRITER).
- **A Postgres key made stricter and then looser again while the stream lagged**, with a row inserted and deleted in between. The reader reads the collation in force now, so the replayed delete can remove the existing row (KEY-COLLATION-PG-LOOSENED-REPLAY).
- **`lower_case_table_names` 1 or 2.** An `ALTER` that spells an in-scope table in another case is judged out of scope at the DDL, so the refusal that holds across a restart does not fire for it. The row path still judges the table (RENAME-SWAP-F1-LCTN; not measured).
- **UCA weight residuals.** A MySQL ↔ MariaDB key is compared by MariaDB's UCA 14.0.0 weights where MySQL sorts by UCA 9.0.0.
- **Stream shapes still uncovered:** a non-key column's collation-only change, which chain restore does not apply (no merge is possible); a chain whose incremental was captured before this release; a pure permutation followed by a persisted position, a restart and a `MODIFY … AFTER`; table identity (`RENAME TABLE` swaps, or DROP + CREATE of one name); and Postgres's `DROP b, RENAME c TO b` at a first boundary after a cold start or a restart.

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale), `d1verify` (live Cloudflare D1) and `nekiverify` (live Neki) suites, which need live, billable infrastructure.

## Who needs this — action required

- **Anyone whose MySQL or MariaDB binlog source ran one of the column-recycling shapes on a streamed table on any release through v0.158.1.** Those shapes are: `DROP COLUMN c, ADD COLUMN c` of the same type, `RENAME COLUMN c TO tmp, ADD COLUMN c`, `DROP COLUMN b, RENAME COLUMN c TO b`, or a rename swap followed by a `MODIFY … AFTER`. It applies to `sync start`, `backup incremental`/`backup stream` chains and `sync from-backup`. Every row the target held before the change may carry the old column's values under the reused name. `sluice verify` at the default `--depth count` cannot see it, because the row count is unchanged.

  **Check:** run `sluice verify --depth sample` on this release; since v0.158.1 it compares columns by name. A target that lacks a source column (the `tmp` shape) fails as `COLUMN-MISMATCH` deterministically. For the other shapes, each sampled row that predates the change and whose value in the reused column differs is a mismatch. The default 100-row sample gives about 99% confidence when at least 5% of the table's rows differ (the flag's documented math). Raise `--sample-rows-per-table`, or vary `--sample-seed`, for a table where few rows predate the change. A clean sample is evidence, not proof.

  **Action:** re-copy each affected table: `sluice sync start --reset-target-data --yes` (or `--restart-from-scratch`) with the stream's other flags unchanged. Rebuild affected chains from a new `backup full`.
- **Anyone whose source changed a key column's collation or character set while sluice followed it, on any release through v0.158.1.** That is any change to a PRIMARY KEY or UNIQUE column on MySQL, MariaDB or Postgres, through `sync start`, a `--schema-changes=refuse` stream, or a backup chain restore and `sync from-backup`. Also affected, with no schema change at all:
  - a MySQL 8 → MariaDB stream whose key column is `utf8mb4_0900_*` and whose source holds keys that differ only by trailing spaces;
  - a Postgres → MySQL-family stream with a UNIQUE key (beside the primary key) on the database default collation whose source holds values that differ only in case.

  The target may be missing rows that merged into another row. **Upgrading does not repair rows that already merged;** it only stops new merges. **Check:** in the cases measured, each merge left the target one row short, so `sluice verify` (row counts, the default depth) on a quiesced stream reports a count mismatch for the table. `--depth sample` adds the per-row comparison by name, at the odds above. To find candidate collisions directly, group each key column on the source under the target's collation and look for groups larger than one. On MySQL, for example: `SELECT k COLLATE utf8mb4_0900_ai_ci AS kk, COUNT(*) FROM t GROUP BY kk HAVING COUNT(*) > 1`. On Postgres, use `GROUP BY k COLLATE "<target collation>"`, or `lower(k)` as an approximation for a case-insensitive MySQL target. **Action:** re-copy each table that mismatches.
- **Anyone on v0.158.0 or v0.158.1 with a `binlog_row_metadata=FULL` source whose key column's collation was changed and the column then retyped or dropped before the stream caught up** (DEFERRED-KEY-COLLATION). If the stream then stopped with `RESUME-SCHEMA-DIVERGENCE` and you followed its remedy, the merged row is still on the target. **Action:** check and re-copy as in the previous item.
- **Operators who deliberately give a target key a different collation from the source, or who recycle column names, or swap columns through a temporary name:** expect the new refusals in Compatibility. Each refusal names its remedy.
- **CI that greps `sluice verify` output for `with row-count mismatch`:** update the pattern.
- **Everyone else:** upgrade. Streams with no key-collation changes and no column-name recycling need no action.
