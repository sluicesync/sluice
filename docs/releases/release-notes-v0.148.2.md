# sluice v0.148.2

**HIGH fix — a MySQL-family source that is NOT the lineage your persisted position came from is now refused instead of being automatically re-copied over a correct target; plus a MySQL row `LOAD DATA` silently dropped and reported as a coercion, and a `postgres-trigger` stream that stalled silently when a captured table was moved with `ALTER TABLE … SET SCHEMA`. Drop-in binary, with one deliberate behaviour change: a sync that used to recover unattended from a replaced source now stops and asks.** All three come from the remaining tiers of the 2026-09-09 blind audit, filed after v0.148.1 shipped, and every one was measured on a real server before it was fixed. Take this release if you run continuous sync from MySQL, MariaDB, PlanetScale or Vitess, if you migrate into MySQL from a source carrying CHECK constraints, or if you run `postgres-trigger` CDC.

## Fixed

**A MySQL-family source that is a different lineage from the persisted position is refused on every lane and on both paths, instead of being re-copied over the target** (silent destruction at exit 0; the binlog GTID, MariaDB and VStream arms affect v0.138.0 through v0.148.1). A persisted position stops being usable for two reasons that arrive at the orchestrator as the same thing — an error. Either the *same* source moved past it (binlogs purged, a `RESET MASTER`), or a *different* source now answers the DSN: an instance replaced, a node restored from the wrong backup, a DNS or load-balancer failover, a keyspace that is simply another database. The automatic recovery for the first drops the target's in-scope tables and re-copies from whatever now answers the DSN, which is precisely the wrong thing for the second, and the audit measured it end to end on real MySQL: source A's four rows sitting correctly on the target, instance B carrying one row brought up at the same host:port, then `sync start` logging "warm resume: persisted position is no longer valid; falling through to cold start", dropping the table, and leaving the target holding the wrong database's single row — at exit 0, with every signal green. v0.146.0's SLM-6 fix had made a replaced instance terminal on the binlog file/pos arm and declared the GTID arm covered "by construction"; it was caught by construction and routed, by construction, into the destructive recovery, because the enumeration asked which flavours call the identity check rather than which arms turn a different-server diagnosis into the automatic re-snapshot. The fix is one sentinel, `ir.ErrPositionForeignLineage`, which deliberately does **not** satisfy `errors.Is(err, ir.ErrPositionInvalid)` — the sentinel every fall-through keys on — and which is now carried, under the existing `SLUICE-E-CDC-LINEAGE-MISMATCH` code, by every "different lineage" verdict in the engine: binlog GTID (a non-empty `@@global.gtid_executed` that shares no UUID with the resume set), binlog file/pos (`@@server_uuid`), MariaDB (both the lineage anchor and the replication-domain check in `mariadb_lineage.go`), and VStream (a foreign keyspace or shard). The pre-flight warm-resume path refuses under the grep-stable marker `FOREIGN-LINEAGE-REFUSED`, states that nothing on the target was touched, and names the deliberate ways to re-copy; the reactive path — a position that goes invalid mid-stream, which restarts from scratch with no pre-flight of its own — now asks the reader first, through the new optional `ir.LineageVerifier` capability, whose `VerifyLineage` runs exactly the same verification without opening a stream, and refuses before it drops anything. What still recovers automatically, on purpose: an EMPTY executed set (a same-server `RESET MASTER`, where there is no other lineage to re-copy from), a purged position, a probe that could not run, and a VStream errant GTID, whose remedy is executable on the source and which keeps its existing route. Pinned per lane on a fake server by `TestLineageVerdicts_ForeignIsTerminalResetIsNot`; by an AST roster over every return site in the engine whose text says "different lineage" or "different server", with a reasoned exempt map and anti-vacuity floors, in `TestForeignLineageVerdictsCarryTheSentinel`; at the reactive door by `TestReactiveResnapshot_RefusesAForeignLineageBeforeTheDrop`; on real MySQL and MariaDB across instances; and end to end on real MySQL by `TestStreamer_MySQLForeignLineage_RefusesTheAutomaticRecopy`, where the target must keep its four rows after the source becomes a foreign lineage and must still be re-copied after a plain reset. Both readers `OpenCDCReader` can return implement the capability — the binlog one and the VStream one — and a roster derived from the code, not from a list, fails the build if a third reader type ever appears without it. That roster is in the release because the first cut of this fix did not have it: only the binlog reader answered, every PlanetScale and Vitess flavor routes to the other one, and so the reactive door took its no-capability branch and re-copied over the target on exactly the lane the fix claimed to cover — while a roster exemption, keyed by file rather than by site, asserted the opposite. The pre-tag review caught it.

**A row the MySQL target dropped during `LOAD DATA` is refused as a lost row in every sql_mode, never reported as a coerced value** (silent short copy at exit 0 under `--mysql-sql-mode=''`; the relaxed-mode WARN has read that way since v0.99.28, and the population it can bite widened in v0.141.4). `LOAD DATA LOCAL` carries IGNORE semantics: a row that violates a target CHECK constraint becomes a warning and is SKIPPED, in strict and relaxed sql_mode alike — measured on `mysql:8.0.46`, where `(1,-5),(2,7),(3,-1)` lands `{2}` with two warnings and no error at all, and on `mariadb:11.4.13`, which does the same thing under a different code (`4025 CONSTRAINT … failed`, not MySQL's 3819). Taking one engine's code as the class was the first cut's mistake, caught before the tag: the skip-class set now holds both, with a real-MariaDB pin that quotes the server's own warning so a renumber fails it. Under `--mysql-sql-mode=''` the writer's warning gate WARNed once per table that values "were clamped or truncated on write" and returned nil, so row loss was described as coercion and the migration exited 0 short of rows; under strict mode it did refuse, but diagnosed per-row type-conversion errors and prescribed `--type-override`, which cannot address a CHECK. `showWarnings` now counts skip-class codes as `Skipped`, and `decideBulkWriteWarnings` refuses on any skip BEFORE the sql_mode policy is consulted, with a dedicated refusal marked `LOAD-DATA-ROWS-SKIPPED` that names the constraint, the count, and the three real ways out: fix or exclude the offending source rows, drop the target CHECK, or set `local_infile=OFF` on the target server (it is a global variable, not a session or DSN one) so the copy takes the batched-INSERT path, where the same violation is errno 3819 as an error and the statement fails. Behind that sits an independent witness no warning SAMPLE can hide — the 2026-08-01 rule, name the number the check does not derive from the artifact it grades: on a first attempt `reportLoadDataWarnings` refuses any shortfall between the rows sluice sent and the rows the driver reports inserted, whenever the server warned at all, which catches a skip even on a server tuned to `max_error_count=0` where the warning list comes back empty while `@@warning_count` stays accurate. Replays are exempt, because their shortfall is the duplicate accounting's business. On the population, stated precisely because the mechanism matters: a source CHECK has always landed on a MySQL target as an ENFORCED CHECK, since MySQL has no created-but-unvalidated state — what changed in **v0.141.4** is that an unvalidated PostgreSQL DOMAIN CHECK, whose body the Postgres reader used to mangle so the translation failed and the constraint was dropped with a WARN, now parses and translates successfully, so it lands enforced too and the drop-warn no longer fires. Both code comments beside that translation claimed the mismatch "fails LOUDLY at errno 3819"; that was true of the batched-INSERT path only, and both now say which path they mean. Pinned by `TestDecideBulkWriteWarnings_ASkippedRowRefusesInEverySQLMode` (relaxed, strict and default, plus a coercion-still-WARNs control), `TestRowsSkippedError_NamesTheShortfall`, and on real MySQL by `TestRowWriter_LoadData_CheckViolationIsASkippedRowNotACoercion`, whose relaxed `max_error_count=0` cell only the witness can catch and whose expected value is the target's own row count.

**`ALTER TABLE … SET SCHEMA` on a captured table halts a `postgres-trigger` stream loudly again instead of stalling it silently** (silent stall with a frozen target at exit 0; affects v0.145.0 through v0.148.1). `pg_event_trigger_ddl_commands().schema_name` reports the DESTINATION schema and the capture trigger moves with the table, so the move's DDL marker is written under the new schema — and the reader's `rowInCaptureScope` schema check, which exists so a decoy relation in a schema another role controls cannot halt your stream, discarded that marker before `refuseObservedDDL` could ever see it. The trigger kept writing change rows the reader then dropped after a single `CAPTURE-OUT-OF-SCOPE` WARN, and the stream ran on at exit 0 with the target frozen; measured on real PG 16. Before v0.145.0 the marker went straight to the refusal and the stream halted with the drain/restart remedy — the schema check arrived with the S-2 capture-scoping work in v0.145.0 and narrowed past this case, so this is a delta regression with a three-release window. The precise discriminator is a relation's OID, which survives both a rename and a `SET SCHEMA` while the name does not — but it has to be the OID of the CAPTURED relation the command concerns, not of the command's own object. Those differ in two shapes the first cut of this fix got wrong: for a `CREATE INDEX` the object is the index, and for an `ALTER` on a partitioned parent it is the parent while the capture triggers sit on the partitions, so both recorded an identity the reader could never match and stayed exactly as broken as before. The `ddl_command_end` capture function now records `captured_relid` (as text, so the reader's string-map decode still keeps every field and a reader from an earlier release still decodes the whole payload), read straight out of the recursive lookup that already resolves index-to-table and parent-to-partitions rather than from a second copy that could drift from it; `loadCapturedRelIDs` loads the relations carrying this install's capture trigger — identified by that trigger's FUNCTION namespace, so a table that has already moved out of the reader's schema is still found, which is what lets a reader opened AFTER the move re-read the pending marker and halt rather than letting the halt fire once and go quiet; and a foreign-schema marker is in scope exactly when its recorded relation is in that set, graded BEFORE the schema check. The security half holds by construction rather than by promise: a decoy relation was never captured here, so its OID is absent from the set and it still cannot halt the stream; a marker carrying no OID (an install running an older capture function) decodes as 0 and matches nothing, so it can only ever narrow; the row and TRUNCATE arms are untouched; and a failed OID load WARNs and leaves the pre-fix behaviour rather than failing open. Pinned by `TestRowInCaptureScope_AMovedCapturedTableStaysInScopeByOID` (moved, decoy, no-OID, row-arm and no-set cells) and `TestDecodeDDLMarker_ReadsTheRelationOID`, and on real PostgreSQL by `TestCDCReader_DDLRefusal_ForeignSchemaMarkers`, which asserts the OID set actually loaded and then requires the halt within 10 s of the move plus a write through the moved table; disabling the OID arm turns that cell into its own 10-second silent-stall timeout. The `objid` field comes from the capture function installed on your source, so this one needs an action — see below.

## Compatibility

**One behaviour change, and it is the reason to read this section before upgrading.** A MySQL, MariaDB, PlanetScale or Vitess sync whose source is a DIFFERENT lineage from the persisted position — a replaced instance, a node restored from the wrong backup, a DNS or load-balancer failover onto another database, a different keyspace — used to be diagnosed correctly and then routed into the automatic cold-start re-snapshot, which drops the target's in-scope tables and re-copies from whatever now answers the DSN. From v0.148.2 that is a terminal refusal on every lane and on both the warm-resume and the reactive paths. Concretely: a sync that previously recovered unattended in the replaced-source case now stops and asks, and if the replacement IS what you intend you re-copy from it deliberately with `sluice sync start --restart-from-scratch` (which keeps the cdc-state row) or `--reset-target-data` (which clears it too). Both flags bypass the position read entirely, so neither is blocked by the new refusal. Nothing else about the recovery narrows: a same-server `RESET MASTER` with an empty executed set, a purged position, a probe that could not run, an engine without the capability, and a VStream errant GTID all proceed exactly as they did in v0.148.1.

No flag was added, renamed or removed, and no CLI surface changed. No position, manifest or backup format change — the backup format stays at 10, and the `postgres-trigger` change-log schema version stays at 5. The `postgres-trigger` DDL marker's `pk_jsonb` payload gains one key, `captured_relid`, written as text so an older reader's string-map decode is unaffected; the marker is otherwise byte-identical, and the change-log table's own shape is untouched. Because the capture function's body changed, its recorded provenance digest changes with it: an existing install keeps the old body, and every CDC open WARNs under `STALE-CAPTURE-FUNCTION`, until `sluice trigger setup` is re-run — the binary is safe to take without that step, it simply does not yet carry the `SET SCHEMA` fix (see below). Engines touched: MySQL and its flavors as CDC sources on the lineage doors (binlog and VStream both reach the pre-flight refusal and both answer the reactive door), MySQL as a bulk-copy target on the `LOAD DATA` path, and `postgres-trigger` on the DDL tier. The native PostgreSQL logical-replication engine, SQLite, D1 and the SQLite/D1 trigger-CDC lanes are unaffected, as are `backup`, `restore` and `verify`.

## Who needs this — action required

**`postgres-trigger` operators, on v0.145.0 through v0.148.1 — upgrading the binary is NOT enough.** The fix depends on the `captured_relid` field the `ddl_command_end` capture function writes into the DDL marker, and that function lives on your source, so re-run `sluice trigger setup` with the same `--tables` to install the fixed body; until you do, every CDC open WARNs `STALE-CAPTURE-FUNCTION` and an `ALTER TABLE … SET SCHEMA` on a captured table still stalls the stream silently exactly as it did before. Then audit the window: if any captured table was moved between schemas while you were on v0.145.0–v0.148.1, the stream did not halt, its later changes were discarded, and the target has been frozen for that table since the move — compare the moved table's source rows against the target and re-copy it. Streams where no captured table was ever moved between schemas are unaffected and need nothing beyond the `trigger setup` re-run.

**Anyone running continuous sync from MySQL, MariaDB, PlanetScale or Vitess whose source was ever replaced, restored from a backup, or reached through a failover-capable endpoint, on v0.138.0 through v0.148.1.** If a sync in that window logged a fall-through to cold start and re-copied the target, and the source at that moment might not have been the same instance or keyspace the position came from, the target was repopulated from whatever answered the DSN — silently, at exit 0. Re-verify that target's row counts and contents against the database you actually intend to be syncing, not merely against the current DSN; a target that was filled from the wrong source needs a deliberate fresh copy from the right one. A sync whose source has never been replaced, and one whose only recoveries were routine binlog purges or a same-server `RESET MASTER`, was never exposed. Whether releases BEFORE v0.138.0 could reach the same destructive outcome by a different route is **not pinned** — the lineage checks that produce this diagnosis landed in v0.138.0, and I did not measure how an older binary classified a replaced instance — so treat v0.138.0 as the start of the *proven* range rather than of the possible one.

**Operators who migrate into MySQL from a source carrying CHECK constraints — including any PostgreSQL source with an unvalidated (`NOT VALID`) DOMAIN CHECK, from v0.141.4 on — and who ran with `--mysql-sql-mode=''`.** Those runs could complete at exit 0 having silently dropped every row the target CHECK rejected, with the log calling it a clamp. Re-verify the affected tables' row counts against the source (`sluice verify` in count mode, or a direct `COUNT(*)` on both sides); any shortfall is real rows that were never written and needs a re-copy after you fix or exclude the offending rows, or relax the target CHECK. Runs under strict sql_mode failed loudly at the time, so they lost nothing — the diagnosis was wrong, not the outcome — and targets with no CHECK constraints were never exposed.

**Everyone else: nothing to re-verify.** No data path outside the three above changed, and the upgrade is a straight binary swap.
