# sluice v0.123.0

**CRITICAL fix — the per-change CDC apply path could silently skip the tail of a source transaction on crash-resume, and XA transactions on replicated tables were silently mis-replicated; both are closed, a latent GTID-set race on every GTID-mode stream is fixed, and unknown-target-table CDC events now skip-and-count durably instead of halting.** This is the audit's CDC-position arc: two silent-loss defects in how positions relate to applied data, the concurrency bug the new tests flushed out, and the operator-approved C-11 decision on what a stream should do when the target lacks a table. Drop-in upgrade from v0.122.0 and older — no flag or default changed; one error code is added and one MySQL behaviour deliberately changes (halt → skip, see Compatibility).

## Fixed

**The per-change apply path (`--apply-batch-size=1`) persisted a position with every row, so a crash between rows of one source transaction resumed past the un-applied tail — silent skip (audit CDCPOS-2).** In file/pos mode — which `gtid_mode=OFF`, MySQL's default, auto-selects — every row of one RowsEvent carries the event's END LogPos, so persisting row K's position and crashing before row K+1 of a transaction-final multi-row event resumed at the persisted position and silently skipped rows K+1..N. The item-132 work closed this for the batched paths (v0.99.89's tx-boundary checkpointing) and honestly scoped the per-change path out of its gate — which is exactly where the defect lived. Both appliers now defer mid-source-transaction position persistence to the delivered TxCommit: rows between TxBegin/TxCommit apply through the position-free seam with their rows_applied deltas accumulated, and the TxCommit — the post-commit point in every source's position scheme — is the only mid-stream persist. The Postgres applier gets the same rule, not an exemption: the tempting "PG slots re-deliver whole transactions" argument was refused as the one-source-justification trap item 132 recorded, because that applier is fed by MySQL file/pos sources too. ADR-0007 is amended accordingly — the surviving invariant is directional: **a persisted position never covers un-applied data**; the reachable divergence is data-ahead-of-position, which a resume replays idempotently (ADR-0010). Changes outside any source transaction keep the original atomic position-with-data write, and GTID mode's per-change path was already safe since v0.113.0's staging fix. A new G-2 extension gate (`TestPerChangeApplyMidTxPositionPins`) walks `internal/engines/**` for every per-change Apply implementor and requires each to name its pin test — exactly two exist (mysql, postgres; pgtrigger inherits the postgres applier), both fixed, both pinned on real servers, mutation-run in all three directions. Affected releases: the per-change path has written a position with every row since per-change position persistence shipped in v0.1.0 (`0c34f38b`), through v0.122.0; the silent-skip window is the file/pos-mode shape, with GTID mode covered since v0.113.0 and the batched paths since v0.99.89.

**XA (distributed) transactions on replicated tables are now refused loudly with the new `SLUICE-E-CDC-XA-UNSUPPORTED` instead of being silently mis-replicated (audit CDCPOS-1).** Two defects closed in one. First, `XA START` arrives as a QueryEvent that is neither BEGIN nor COMMIT, so it fell into the generic-DDL arm, whose fold ran before any of the body's rows — every mid-XA position already contained its own transaction, and a crash between applier flushes resumed past the un-applied tail: the exact item-132 shape, re-opened through a different door. Second, and unfixable by staging alone: sluice applies rows at read time, but an XA body's rows are invisible on the source until a later `XA COMMIT` — so a coordinator rollback leaves rows on the target the source never showed anyone. Phantom rows, permanent, exit 0. Faithful XA replication requires buffering prepared transactions the way a real replica does; that is demand-gated, and a staging-only fix would have looked fixed while leaving the rollback half silently open — hence the refusal. It is scoped: the refusal fires only for an in-scope row inside an XA window, strictly after the scope drop, so XA traffic on non-replicated tables of a shared server streams past untouched (the body's GTID folds one group late via the documented non-lossy staging degradation), and filtered syncs keep working. Sibling enumeration: Postgres two-phase is unconstructible (sluice never requests `two_phase` at slot creation, so PG delivers prepared transactions only at COMMIT PREPARED as ordinary transactions); VStream-based streams (vitess/planetscale) ride a separate carrier whose dispatch never sees binlog XA verbs; the trigger-CDC engines capture only committed rows, so an XA rollback rolls the capture back too. Pinned by four synthetic dispatch pins plus a real-server binlog pin covering both the stream-past and refuse directions; mutation-run. Affected releases: every MySQL binlog CDC stream (GTID or file/pos mode) whose source uses XA on replicated tables, since the reader shipped in v0.1.0 (`32f1b3ec`), through v0.122.0.

**A latent cross-goroutine map race on every GTID-mode stream: the reader handed its GTID set to go-mysql's syncer, which mutates it from its own goroutine while sluice's fold mutates the same map from the pump.** `startStreamer` assigned one parsed GTID set to both `r.gtidSet` and `StartSyncGTID`; go-mysql's BinlogSyncer keeps the object and runs its own per-event AddGTID bookkeeping on it from its goroutine — an unsynchronized concurrent Go-map write whose failure modes are a runtime crash ("concurrent map read and map write") or silent corruption of the running set, which IS the resume position, making this silent-loss-adjacent rather than merely a crash risk. First observed by the `-race` Integration gate on the CDCPOS-1 push — the new XA test's dense group traffic widened the overlap window enough for TSan to see the pair; the race predates the XA change, which only made it visible. Fixed by cloning: each side bookkeeps its own object, and sluice's position reads only its own copy. Verified under the local DooD `-race` harness with the exact test that reproduced it, and re-gated by CI's full `-race` run. Affected releases: every GTID-mode stream since the reader shipped in v0.1.0 (`32f1b3ec`, which introduced both the aliasing and the go-mysql version that bookkeeps), through v0.122.0.

**A graceful `sync stop` no longer surfaces a spurious apply error when it lands mid-position-write** (the fix the tag's own gate run caught — added to these notes 2026-08-12 shortly after publish; the published binaries always contained it). `database/sql` auto-rolls-back a `BeginTx(ctx)` transaction the moment the context cancels, so a stop landing between BeginTx and Commit surfaced as `sql.ErrTxDone`, which the streamer's clean-stop check does not match — an ordinary stop reported as an apply failure. Apply-transaction failures now map to the stream's own cancellation when the context is terminated (nothing persisted is the safe direction; resume re-delivers), at all six sibling sites across both engines. Pinned in both directions; the exact failing test passes 3/3 on real containers.

## Added

**When a stream carries changes for a table the target lacks, every applier now skips-and-counts instead of halting (MySQL) or WARNing per event (Postgres) — operator-approved audit C-11.** The rationale is that halting had the blast radius inverted: the source still holds every skipped row (recoverable with `sluice schema add-table`, a fresh table snapshot), while a halted stream lags every table and, past binlog/slot retention, loses the position itself. The new behaviour: WARN once per table, and count every skip durably in the new `sluice_cdc_skipped_tables` control table — one row per (stream, table) carrying the cumulative count and the first/last skipped position tokens verbatim — surfaced in `sync status`, the `sync stop` summary, the streamer's settle log, and `sync health`, which exits 1 while any count is nonzero, so a skip is never log-only (a failed ledger upsert fails the apply loudly rather than dropping the count). Classification is structural on both engines — catalog probes, never error text — and the skip resolves at metadata-resolution time on every arm including TRUNCATE; a table dropped mid-stream after applies landed stays a loud exec-time failure, deliberately, and converges to a clean skip on retry. Every apply path is enumerated fixed-or-exempt in the commit: both engines' serial, batched, pipelined, and concurrent-lane paths funnel through the fixed dispatchers; pgtrigger inherits the PG applier; the engines with no ChangeApplier are exempt. The removal of PG's old exec-time TRUNCATE 42P01 swallow is part of this: it was unsound all along, since absorbing the error left the open transaction aborted so the position write behind it failed with 25P02 — a poison-pill retry loop dressed as a benign skip. CDCPOS-2 is not perturbed: a skip still defers positions to the delivered TxCommit, and the ledger records the skipped events' own tokens. Pinned by four real-container integration tests across both engines and both apply shapes with hostile identifiers and byte-exact token round-trips, plus health/status/stop rendering pins; mutation-run in both directions.

## Compatibility

No CLI flag or default changed (the delta in `cmd/sluice` only extends `sync status`, `sync stop`, and `sync health` output), and no on-disk format changed shape. **Drop-in upgrade from v0.122.0 and older**, with these behaviour notes. One error code is added: `SLUICE-E-CDC-XA-UNSUPPORTED` — a stream whose source writes replicated tables inside XA transactions now refuses loudly where it previously mis-replicated; keep XA off the replicated tables or exclude them. One deliberate MySQL behaviour change: an unknown-target-table CDC event now skips-and-counts where it previously halted the stream — **operators who relied on that halt as a schema-drift alarm must watch `sync health` instead**, which now exits 1 while any skip count is nonzero (also new for scripts wrapping `sync health`); Postgres moves from a per-event WARN to once-per-table plus the durable ledger, and its unsound exec-time TRUNCATE swallow is removed. The new `sluice_cdc_skipped_tables` control table is additive and auto-created by the existing control-table bootstrap (`sluice control-tables ddl` now prints 7 tables; on PlanetScale with safe migrations the pre-existing `SLUICE-E-PS-DIRECT-DDL-BLOCKED` pre-create flow applies). Position-persistence cadence on the per-change apply path changes shape, not safety direction: inside a source transaction, positions now persist only at the TxCommit, so a crash mid-transaction re-delivers the whole transaction and idempotent apply absorbs the replay — re-delivery, never loss; changes outside any source transaction persist exactly as before, and PG→PG slot feedback now advances at commit granularity, which is the granularity `confirmed_flush` advances at server-side anyway. The batched apply paths, GTID-mode staging, and all non-CDC paths (migrate, backup, restore, verify) are unaffected.

## Who needs this — action required

**Anyone running continuous sync with `--apply-batch-size=1` (the per-change apply path) whose stream ever crashed or was killed mid-flight** — on any release v0.1.0 through v0.122.0, and especially against a `gtid_mode=OFF` (file/pos) MySQL source: a resume after a mid-transaction crash may have silently skipped the tail rows of one source transaction. Re-verify the target (`sluice verify`) for those streams; the source retains every row, so a divergent table re-syncs cleanly. The default batched path has been safe since v0.99.89 and GTID-mode per-change since v0.113.0. **Anyone whose source application uses XA (distributed) transactions on replicated tables** (any release since v0.1.0): the target may hold phantom rows from coordinator rollbacks and may be missing transaction tails — re-verify affected tables, and before upgrading note that such a stream will now refuse loudly with `SLUICE-E-CDC-XA-UNSUPPORTED` until XA is moved off the replicated tables or they are excluded. **Anyone running GTID-mode MySQL CDC**: the map race's crash form is loud, but the corruption form silently alters the resume position — if a stream has shown unexplained resume divergence, re-verify; otherwise upgrading is the whole action. **Anyone who relied on the MySQL halt as an unknown-table drift alarm**: switch that alerting to `sync health` (nonzero exit while any skip count is nonzero); `sync status` and the `sync stop` summary show the per-table ledger. If none of these describe your setup, the upgrade is a no-op.
