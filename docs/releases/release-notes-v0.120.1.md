# sluice v0.120.1

**HIGH fix — `backup verify` no longer passes a chain that cannot restore.** A chain recorded by a pre-v0.120.0 MySQL-family reader carrying a mangled apostrophe expression failed `restore` mid-run with the target's raw parser error, while `backup verify` returned exit 0 over the same chain and `backup incremental` kept extending it silently (Bug 243). Every door now refuses — or, for `incremental`, warns — with the new `SLUICE-E-BACKUP-RECORDED-SCHEMA-MALFORMED` code and a working salvage path. Also here: the MySQL→PostgreSQL expression gate now recognizes MariaDB's infix `REGEXP` operator, so a MariaDB-source CHECK gets the designed pre-DDL refusal instead of dying in PostgreSQL's parser after partially creating the target (Bug 242). Drop-in upgrade with one addition to know about: this release ADDS one error code; no flag, default, or on-disk format changed. If you hold backup chains recorded from a MySQL or MariaDB source before v0.120.0, see "Who needs this".

## Fixed

**A backup chain whose recorded schema cannot be emitted as valid SQL is now refused at every door, instead of `verify` passing it, `incremental` extending it, and `restore` dying mid-run (Bug 243).** A chain recorded by a pre-v0.120.0 MySQL-family reader can carry a mangled expression — the escaping defect v0.120.0 fixed recorded any apostrophe-carrying CHECK, generated column, expression default or functional index as text whose string literal never closes. Restoring such a chain died in the target's parser (raw MySQL Error 1064, no code, no remedy, earlier tables already created), `backup verify` returned rc=0 over the same chain because every data chunk really was intact and no depth ever read the recorded schema, and `backup incremental` kept appending at exit 0 — an un-restorable chain that kept accepting backups in silence. The detector is structural, not a parser and deliberately not a repair: under the IR's portable literal spelling every mangle of this family ends inside an open string literal, and a recording the current binary cannot prove the intent of gets a loud refusal with the remedy, never a guessed rewrite. Four doors, one shared (code, hint) pair: `restore` refuses pre-DDL, first of the schema refusals and deliberately FILTER-AWARE — `restore --exclude-table=<the named table>` is the documented salvage when the source is gone, and a filter-blind gate would make its own remedy impossible (pinned: excluding the affected table releases the gate); chain restore's schema deltas refuse unconditionally, since delta tables apply unfiltered; `backup verify` refuses chain-level at any depth (the schema rides in the manifest, no chunk read needed), so verify can no longer pass a chain a plain restore refuses; and `backup incremental` WARNs rather than refuses — the incremental's own data is valid — naming the code so a chain stops being extended in silence. **The stated blind spot, filed in `docs/dev/audit-backlog.md` and NOT covered here: a structurally-valid recording from the same era can still spell a literal backslash in MySQL's doubled form, which lexes cleanly, restores correctly to a MySQL target, and names a DIFFERENT predicate on a PostgreSQL target — silent, pre-existing, and not detectable from the artifact's structure alone.** **Affected releases: the mangled recordings come from the reader defect pinned live since v0.97.0 (with the blind un-escape it replaced byte-identical back to v0.3.2, so treat earlier recordings as suspect rather than cleared); the missing doors are as old as backup itself — `backup verify` has passed this class since it shipped in v0.15.0 (`5550c230`) and `backup incremental` has extended it silently since v0.17.0 (`4b22bacf`), through v0.120.0. The catalog's differential run pins both halves: the same chain copy fails restore byte-identically under v0.119.0, and v0.120.0's verify and incremental both exited 0 over it.** Pinned with the catalog's measured mangle bytes at all four doors — the restore pin runs against a panic-on-use stub target, which is the pre-DDL proof — and mutation-run: disabling the detector fails all five door pins.

**A MariaDB-source CHECK spelled with the infix `REGEXP` operator now gets the designed pre-DDL refusal instead of dying in PostgreSQL's parser after partially creating the target (Bug 242).** MariaDB's `information_schema` renders `c REGEXP '...'` as the infix operator, where MySQL 8 normalizes it to the `regexp_like()` call — and the untranslatable-expression gate scanned function-call idents only, so the operator sailed through and `migrate` died with PostgreSQL's raw `syntax error at or near "regexp"` (SQLSTATE 42601) with the control tables and earlier tables already created, while the byte-identical source CHECK on MySQL 8 was refused cleanly pre-DDL. A flavor-sibling gap of exactly the sweep-discipline class. The new arm is a string-literal-aware, word-bounded token scan for the two MEASURED spellings — infix `REGEXP` and its `RLIKE` synonym; `SOUNDS LIKE` is deliberately not listed, because no catalog rendering of it has been measured and this gate adds spellings from measurements, not from the manual. The refusal names the operator, its MariaDB provenance, and the `x ~ 'pattern'` PostgreSQL equivalent with the ICU-vs-POSIX regex-flavour caveat; both consumers — the pre-DDL refusal and the schema-preview advisory — ride the one scanner so they cannot drift. The guard directions are pinned: `regexp_like` stays the call arm's business, the word `regexp` inside a string literal is data, and an identifier merely containing the word does not match; a column literally NAMED `regexp` or `rlike` would false-trip the gate — the loud direction, vanishingly rare, with `--expr-override` as its escape hatch. **Affected releases: the gate has scanned call-form spellings only since it was introduced in v0.68.3 (`68c0defb`), and MariaDB became a supported source in v0.99.268 (`38de856a`) — so v0.99.268 through v0.120.0, measured byte-identical on v0.119.0 by the catalog's differential run. The failure was loud in every affected release: nothing landed in the offending table and the source was untouched.** Mutation-run: disabling the shared scanner fails all three pins across both gates.

**The v0.120.0 release notes' backup-chain compatibility claim was corrected, and the correction ships in this release's history (`d947b5f2`).** The published note claimed a chain whose recorded schema carried an affected MySQL expression re-fingerprints with one forced full backup on its next incremental; the post-release regression cycle measured that it does not — the spelling change lands as an ordinary recorded schema delta at exit 0. The published v0.120.0 notes and CHANGELOG were corrected in place hours after publish; the Bug 243 fix above is the substantive half.

## Compatibility

No breaking changes. No flag was added, renamed or removed; no default changed; no on-disk format — backup chunks, chain manifests, resume state, the schema wire — changed shape. This is a drop-in upgrade from v0.120.0 and anything older. **One error code was ADDED** — `SLUICE-E-BACKUP-RECORDED-SCHEMA-MALFORMED` — where v0.120.0 could say none was; none was removed and no existing code changed meaning. Three behaviour notes:

- **`backup verify` now exits non-zero on a chain it previously passed, when that chain's recorded schema is malformed.** This is the correct direction — such a chain could never restore, and the old rc=0 was verify confirming only the chunks. A scripted verify that starts failing after upgrade found a chain that was already broken, not a new problem.
- **`backup incremental` over such a chain now prints a WARN naming the code; it still succeeds**, because the incremental's own data is valid — but the chain will not restore until a fresh `backup full` re-records it.
- **A MariaDB→PostgreSQL `migrate` that previously died mid-DDL with a raw SQLSTATE 42601 now refuses pre-DDL with the coded message and remedies, leaving the target empty.** A column literally named `regexp` or `rlike` would now false-trip that refusal — loud, and `--expr-override` is the escape hatch.

## Who needs this — action required

- **Anyone holding backup chains recorded from a MySQL or MariaDB source before v0.120.0 whose schema carries apostrophe-bearing expression literals: run `backup verify` on this release against every chain you rely on.** A passing verify from ANY earlier release did not check this class — verify confirmed the chunks and never read the recorded schema. If verify refuses: the chain cannot restore; take a fresh `backup full` of the live source on v0.120.0 or newer, and if the source is gone, `restore --exclude-table=<the named table>` recovers every other table — the data chunks are intact, and the refusal names each affected table and field.
- **The blind spot is yours to track if you restore MySQL-recorded chains onto PostgreSQL targets: a pre-v0.120.0 recording carrying literal BACKSLASHES in an expression is structurally valid, passes this new gate, restores correctly to MySQL — and names a different predicate on a PostgreSQL target, silently.** That class is not detectable from the chain alone and is filed, not fixed. Treat such chains as suspect for PG restore until re-recorded by a v0.120.0+ full.
- **MariaDB sources with `REGEXP`/`RLIKE` CHECK constraints migrating to PostgreSQL: upgrade and re-run.** The old failure was loud and lost nothing, but it left partially created tables on the target — clean those up from any prior failed attempt. The refusal now arrives before any DDL, names the constraint, and offers `--expr-override` / `--exclude-table`.
- **Everyone else: nothing to do.**
