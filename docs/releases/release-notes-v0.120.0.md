# sluice v0.120.0

**PostGIS `geography` is now first-class, and MySQL expression escaping is rebuilt on a literal-aware scanner — one arc of which was silent.** A single bare `geography` column killed every schema-reading command for the whole database, and geography could not be written over `sync`/CDC at all; both are fixed and driven end to end. On the MySQL side, an expression literal carrying an apostrophe was mangled at schema read, and a backslash-carrying expression was SILENTLY mis-valued on PostgreSQL targets — if you carried one, see "Who needs this". Also here: `schema diff` stops reporting phantom drift when the two servers render one CHECK predicate differently, and a malformed VStream row event now refuses loudly instead of decoding as an empty row. Drop-in upgrade — no flag, error code or on-disk format changed — with one planning note for backup chains whose recorded schema carried an affected MySQL expression.

## Fixed

**A single bare `geography` column made every schema-reading command fail for the whole database (Bug 240).** `migrate`, `sync`, `schema diff`, backup — anything reading a PostgreSQL schema died with a raw driver scan error, because PostGIS's `geography_columns` view exposes the raw `postgis_typmod_*` accessors with no null-handling (unlike `geometry_columns`, which coalesces internally — both view definitions were measured), so a typmod-less column reports `coord_dimension = NULL` and the int scan failed. Every query that reads the spatial registration views now COALESCEs, with the sibling enumeration in the commit: the schema reader's geography and geometry lookups, its no-view-row geography fallback, the change applier's loader, and the CDC SRID catalog read are fixed; the domain-geometry reader was exempt because it already coalesced — the precedent this fix follows. **Affected releases: v0.33.3 (`20d25095`, which added `coord_dimension` to the geography query) through v0.119.0.** Pinned by `TestSchemaReader_PostGIS_BareGeographyColumn` over a real bare column on PostGIS 16-3.4, mutation-run: reverting either COALESCE fails its own subtest with the verbatim Bug 240 error.

**`geography` values now write through the parameter-binding cores, so `sync` and CDC into a PostGIS `geography` column work at all (audit GAP 1).** The EWKB codec was registered for the `geometry` OID only, so a parameter-bound geography value fell back to TEXT and died in `geography_in` with the same raw `parse error - invalid geometry` (SQLSTATE XX000) that Bug 239 fixed for geometry — with no codec AND no refusal, exactly the gap v0.119.0 filed as known. `afterConnectRegisterGeometry` now registers the binary codec for BOTH spatial OIDs on every parameter-binding pool in the package (the v0.119.0 roster gate holds each pool to its classification); `geography_recv` reads the same EWKB framing the COPY core has always shipped, which is why `migrate` of a typed geography column already worked. **No prior release could write geography through a batch or idempotent core, and the failure was always loud — there is no silent window here.** Mutation-run: dropping geography from the registration list fails exactly the 28 parameter-bind geography cells of the extended family matrix with the verbatim field error. End to end on the Bug 240 repro database: `migrate` exits 0, the bare geography value lands byte-identical at SRID 4326 on the target, and `schema diff` reports in sync.

**A bare geography column's declared SRID was recorded as the view's raw 0 while every value it stores carries 4326, so the row-level SRID guard refused every row and `schema diff` saw phantom drift (unfiled, surfaced by the end-to-end run).** The readers took `geography_columns.srid = 0` at face value, but geography stamps 4326 on every value it ingests and PostGIS normalizes an emitted `geography(X, 0)` typmod to 4326 — both environmental premises are pinned against the real server in the new test's premise leg rather than asserted. `effectiveGeographySRID` (0 → 4326, geography only — geometry is deliberately untouched, because 0 is a legitimate declared SRID there) now applies at every catalog-read site. The row-refusal half is the v0.118.0 C-14 guard doing exactly what it says against a mis-read declaration; the whole defect was masked behind Bug 240 on every schema-reading path, which is why it was never filed — it surfaced the moment the crash was fixed and the first end-to-end run reached rows.

**A MySQL or MariaDB expression whose string literal carries an apostrophe was mangled at schema read, and an expression carrying a backslash was SILENTLY mis-valued on PostgreSQL targets (escaping-matrix chunk).** MySQL's `information_schema` renders a stored expression — `CHECK_CLAUSE`, `GENERATION_EXPRESSION`, `STATISTICS.EXPRESSION` (functional indexes), `COLUMN_DEFAULT`, all four measured to share the rendering — as its `SHOW CREATE` spelling plus one extra escaping layer, and the reader un-did that with three blind text replaces, each wrong inside literal VALUES: an interior apostrophe arrives double-escaped and the blind un-escape consumed the wrong pair, carrying a malformed literal into the IR for every apostrophe-bearing CHECK, generated column, functional index and expression default; backticks inside literal values were stripped as identifier quoting; and introducer-looking value text (a literal `'_utf8mb4'`) was partially deleted. The silent sibling found by the consumer sweep is the one that matters most: the old spelling kept literal backslashes MySQL-doubled, which PostgreSQL under `standard_conforming_strings` reads as TWO backslashes — so a pattern like `'a\d'` landed on a PG target as a different predicate, enforced silently, at exit 0. The reader is now a two-stage literal-aware scanner (decode the measured I_S layer, then walk the `SHOW CREATE` spelling with the package's full ADR-0161 literal decoder; structural strips apply outside literals only), emitting SQL-standard spelling, and the MySQL emit boundary re-escapes literal backslashes per the writer's resolved `sql_mode` on all four expression positions — byte-identical on every previously-correct shape, held by the pre-existing unit pins. Measured before implementing on real MySQL 8.0 AND MariaDB 11, whose I_S carries NO extra layer, so the normalizer is flavor-dispatched and threaded to every consumer: the schema reader's four sites, both CDC lanes' schema loader, the MariaDB default hook, and the mydumper shim (whose dump-file input is already `SHOW CREATE`-form and now enters at stage two); the shard-consolidation probe, which compared its RAW observed clause against the IR spelling — always a false divergence for literal-carrying CHECKs — now decodes its observed side first. **Affected releases: the 2026-08-10 filing pins the mangle live since v0.97.0, but the blind un-escape it replaces is byte-identical back to v0.3.2 (`bf389c33`), so treat any earlier release that read these expressions as suspect rather than cleared.** Pinned by unit matrices carrying the measured server bytes verbatim on both halves, an emit-side matrix with a reader–emitter round-trip property, and a real-server integration matrix whose oracle is the target server's own CHECK enforcement — an INSERT the server accepts or rejects — plus a second read hop pinning that the spelling does not drift per hop; both cores mutation-run with grep-verified mutants.

**`schema diff` reported phantom drift on a name-matched user CHECK whenever the target server re-renders the predicate at DDL time (Bug 241).** A numeric literal wearing a cast — PostgreSQL stores `(0)::numeric`, MySQL `cast(0 as decimal(10,0))` — or `length()` spelled back as `char_length()` was compared byte-for-byte, so a target `migrate` itself had just created diffed dirty, in both directions. `canonicalCheckExpr` now folds the two servers' renderings before comparing: `cast(X as T)` → `(X)` via a literal-aware balanced scan (recursive for nested casts, symmetric with the `::T` strip it already performed), and call-form `char_length(` → `length(` — a COLUMN named `char_length` is not folded, and a shape that does not complete is copied verbatim, spurious difference at worst, never a spurious match. Every real-drift direction keeps reporting — widened range, changed literal, changed column, and a predicate WEAKENED under the same name — pinned at the canonicalizer, at the comparison, and on real servers in both diff-after-migrate directions with the filing's repro fixtures. The deliberately ACCEPTED false-match window — a hand-edit of ONLY the cast type or ONLY the length-function spelling on a name-matched constraint — was weighed in a decision memo, chosen by the operator, and is pinned as documentation rather than left to be discovered. The other byte-exact CHECK comparisons (CDC drift, the incremental delta shape, the shard-consolidation probe) are enumerated exempt: each compares two reads of the SAME server, where DDL-time re-rendering cannot diverge. **Affected releases: cross-engine CHECK diffing has compared this way since v0.8.0 (`eeb15c46`), through v0.119.0 — advisory-only, a false report and exit 1, no data path.**

**Two latent traps in the CHECK canonicalizer, both phantom-drift direction (audit GAP 5, plus a same-day red-CI correction).** The `= ANY (ARRAY[...])` → `IN (...)` fold was a greedy regex: an expression carrying TWO such terms canonicalized by spanning from the first `array[` to the LAST `])`, folding both terms and the AND joining them into one fictitious member list — replaced by a balanced scan tracking bracket depth and skipping literal spans, with an unbalanced term left unfolded. And the emitted-check matcher walked every actual-side constraint in name order, so an emitted prediction could steal a source-declared constraint's target twin and orphan its name-keyed expected pair — one missing plus one extra on a target holding both. The first cut of that filter was itself too broad — on a PG target, where the writer's synthesized check names round-trip, it starved the emitted match and made every MySQL→PG migrate's SET-emulation and enum CHECKs report as mismatched; CI caught it on `main` within one commit, it never reached a release, and the corrected filter (the exclusion applies only when the name-claimer is SOURCE-declared) is pinned without a container so the class fails in 0.4 s instead of needing the integration shard. **Affected releases: both traps live in the emitted-check matching v0.119.0 introduced, so v0.119.0 only; no emitted shape is known to reach the greedy fold.** Both fixes mutation-run in both directions with grep-verified mutants.

**A VStream row event with mismatched length and field counts decoded as an EMPTY row — and on the snapshot path every missing column reached the writer as NULL, at exit 0 (invariant queue).** The malformed-event branch returned an empty row with `ok=true`, commented "so the caller surfaces the issue" — a premise nothing checked: all five production callers treated the empty row as a normal one. It now refuses on the error channel every caller already propagates — verified at all five sites: the CDC dispatcher's Before/After pair, the concurrency pump, and the snapshot path's three — naming the table and both counts. The sibling in the same function, which the filing did not name: a Values buffer SHORTER than its own Lengths claim panicked on the slice expression (mutation-confirmed), killing the reader goroutine instead of erroring the stream; same class, same refusal shape, now guarded. **Affected releases: both shapes date to the original VStream spine, v0.1.0 through v0.119.0, on the Vitess/PlanetScale source only. Both require the server to emit a malformed event and neither has a known field occurrence — this closes the audit's silent-loss shape defensively, it does not respond to an observed loss.** Pinned by `TestDecodeVStreamRow_MalformedEventRefusesLoudly` over both malformed shapes plus the nil-row and well-formed controls.

**A short geometry cell whose SRID word is complete and non-zero now refuses with the actionable C-14 message — "this SRID cannot be carried on this path; declare it on the column" — instead of the framing-floor message (audit GAP 3).** For a malformed cell of 4–8 bytes the SRID word is readable, and v0.119.0's framing floor checked length first, demoting that window to the less useful of two true messages. Both are loud and neither loses data; only the refusal text an operator sees changes. Affects v0.119.0 only.

## Changed

**The PostGIS write-core family matrix grew its SRID, M and ZM axes (audit GAP 2): 3 cores × 28 family/dimension cases × {geometry, geography} × {bare + SRID 0, typmod + 4326} = 336 cells, all byte-exact on real PostGIS — and every cell now also asserts the LANDED SRID**, the silent-re-stamp direction the old matrix could not observe at all. Mutation-run: a mis-stamped SRID word in `wkbToEWKB` fails every arm, the bare-column cells via the new SRID leg (the silent direction) and the typed cells via the server's own refusal. Alongside it, the domain-CHECK reconciliation matrix now tampers its REGEX arm — the delicate half of the canonicalizer, where a false match is most plausible — not only the range arm (audit GAP 4). Both are test-only; no production code changed.

**Item 157's evidence-free hold cap got its `docs/dev/perf-parity-matrix.md` row, with the MEASURED figures rather than the projection** — the v0.117.0 regression cycle's replication: v0.116.1 dead at 105 s with 309,212 of 1.8 M rows landed versus v0.117.0 complete at 95 s, 5.96× throughput, gate duty 92.6% → 36.4%. The roadmap's ~11% duty projection is annotated as a FLOOR with the reason it under-predicts (a fleet-wide sever opens one window per tripped lane), and the previously-unwritten mode parity note is recorded: `migrate`/`restore` construct the grow gate with no telemetry seam, so the 250 ms cap binds more readily there — the conservative direction. Docs-only.

## Compatibility

No breaking changes. No flag was added, renamed or removed; no default changed; no error code was added or removed; no on-disk format — backup chunks, chain manifests, resume state, the schema wire — changed shape. This is a drop-in upgrade from v0.119.0 and anything older. Four behaviour notes worth knowing:

- **A backup chain whose recorded schema carried a previously-mangled or backslash-carrying MySQL expression re-fingerprints on its next incremental — one forced full backup.** The recorded spelling was malformed or PG-corrupting, so the repartition is correct; plan for one full-backup's worth of time and storage on affected chains.
- **A bare `geography` column's declared SRID now reads as 4326 rather than the view's raw 0**, matching what the server actually enforces on every stored value, so schema read-back, `schema diff`, and the row-level SRID guard all see 4326.
- **A malformed VStream row event now errors the stream instead of decoding as an empty row.** The prior behaviour on that shape was silent NULLs or a reader panic, not success — a stream that starts refusing after upgrade was losing data before, not working.
- **`schema diff` no longer reports a hand-edit of ONLY the cast type or ONLY the `length`/`char_length` spelling on a name-matched CHECK** — the accepted false-match window of the Bug 241 fold, chosen deliberately and pinned as documentation. Any other tamper on the same constraint still reports.

## Who needs this — action required

- **MySQL or MariaDB source with backslash-carrying expression literals on a PostgreSQL target — re-verify; this was silent.** Any CHECK, generated column, functional index or expression default whose literal carries a backslash (e.g. a `REGEXP 'a\\d'` pattern) landed on PG with every backslash doubled — a different predicate, enforced silently, exit 0, in every release that carried it. Action: upgrade, run `sluice schema diff` against each PG target (it now compares the two servers' renderings canonically), and re-create anything it reports; or re-run `migrate` for the schema.
- **Apostrophe-carrying expression literals read from a MySQL or MariaDB source — re-verify the target's spelling.** The read carried a malformed literal into the IR, so every consumer of it — target DDL, `schema diff`, the backup chain's recorded schema — worked from a wrong expression. Same action: `schema diff` after upgrading.
- **Anyone with PostGIS `geography` columns: upgrade — a bare column blocked every schema-reading command outright, a typed column could `migrate` but never `sync`.** Every failure in this arc was loud; there is nothing to re-verify and no silent loss.
- **Anyone whose `schema diff` reported CHECK drift on a target sluice itself created:** re-run on this release — cast-rendering and `char_length` reports were phantom, and a genuinely weakened or dropped constraint still reports.
- **Vitess/PlanetScale VStream users: nothing to do.** The malformed-event shapes have no known field occurrence; from this release they refuse loudly, naming the table, instead of landing NULLs or killing the reader.
- **Everyone else: nothing to do.**
