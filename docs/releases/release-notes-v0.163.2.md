# sluice v0.163.2

**CRITICAL fix, silent — a PlanetScale/Vitess cold start stopped early in its copy no longer resumes as if the copy had finished (VSTREAM-COPY-CURSORLESS-CHECKPOINT-WARM-RESUMES, measured on Vitess 24, present since v0.99.5).** A VStream cold start saves a checkpoint of its copy while it runs, so a stopped copy can continue where it left off. Some of those checkpoints carried no copy cursor, and the next `sync start` reads a position without one as a copy that finished: it went straight to streaming changes, and the rest of the table was never copied. Measured: 294,500 of 300,000 rows missing, with the stream running, applying new changes, and reporting no error. **Also: a failed re-read of a copy's table ids now refuses instead of passing (ANCHOR-ID-REREAD-FAILURE-PASSES, MEDIUM, Postgres and postgres-trigger sources).** No flag change and no backup format change.

## Fixed

- **A VStream copy checkpoint is saved only when the next start can resume from it (VSTREAM-COPY-CURSORLESS-CHECKPOINT-WARM-RESUMES, CRITICAL, silent).** The copy checkpoint saved every durable position, including ones with no cursor: the first checkpoint of a copy, taken at roughly 1,500–2,500 rows before any cursor exists; one taken between two tables; and, as observed on a one-shard keyspace, the checkpoints of a multi-table copy on the single-stream path (`vstream_copy_single_stream=true`). On a multi-shard keyspace there was a second shape: Vitess resumes each shard on its own, and a checkpoint in which one shard carried a cursor while another had started without one was saved too, so that shard skipped the rest of its copy. On a stream's first cold start that checkpoint is also what creates the stream's state row, so nothing recorded that a copy was in progress: a stop while such a checkpoint was the saved one left the next start with what looks exactly like a finished copy. It logged only an `INCLUDE-TABLE-SCOPE-UNRECORDED` warning and streamed changes from then on. Measured on a local Vitess 24 cluster with a Postgres target, each with the stream live and applying traffic: a two-table copy on the default path, 300,000 source rows against 2,000 on the target; a one-table copy, 300,133 against 2,133; a two-table single-stream copy, 300,000 against 1,000. A checkpoint is now saved only when its resume copies every shard: each shard either has not started or carries a copy cursor (`everyShardResumesItsCopy`). A stop now leaves either an earlier cursor, from which the resume re-copies, or no state row at all, in which case the re-run refuses on the populated target. With the fix, the same stops either resumed exactly (300,019 = 300,019) or refused loudly. Pinned by `TestApplyCopyCheckpoint_PersistsOnlyAPositionTheNextStartResumes`, `TestEveryShardResumesItsCopy`, `TestVStreamSnapshot_CheckpointWithholdsAShardThatWouldSkipItsCopy`, and the real-cluster cells in `TestStreamer_VStreamCopyResume` (one shard) and `TestStreamer_VStreamCopyResume_TwoShards`, which stop past the first checkpoint and hold the per-shard rule throughout the copy. With the check removed, two of the one-shard cells lose 294,500 rows silently. The multi-shard shape was found by this release's pre-tag review and then measured on a two-shard Vitess 24 cluster: with only the any-shard check, a stop mid-copy left 152,960 of 300,000 rows on the target, one shard's share never copied, with the stream live and no error; with the per-shard rule, both stops refused loudly.
- **Who was exposed, by case.** A stream's first cold start, on every release since v0.99.5, when the copy checkpoint shipped. A re-copy of an existing stream (`--restart-from-scratch`, or the automatic re-snapshot after an invalid position) through v0.162.x; since v0.163.0 its in-progress mark refuses the resume with `COLD-START-INCOMPLETE`. MySQL binlog, Postgres and the trigger-CDC sources have no copy checkpoint and were never affected.
- **A failed id re-read refuses `TABLE-IDENTITY-UNREAD` (ANCHOR-ID-REREAD-FAILURE-PASSES, MEDIUM, silent for one run).** v0.163.1 made every cold start's CDC anchor, and `schema add-table` before it records an add complete, re-read each table's `pg_class.oid` (on Postgres and postgres-trigger sources) and refuse `TABLE-IDENTITY-CHANGED` on one that moved since the copy. A re-read that *failed*, for example on a connection error or a namespace that could not be resolved, returned no id. The check treated that like a table the source no longer holds and passed. If a table had also been dropped and re-created under its name in the same window, CDC applied the new table's changes onto the old table's rows for the rest of that run, at exit 0. The resumed cold start's anchor runs after the index and constraint phases, possibly hours after the copy. The next start refused `TABLE-IDENTITY-CHANGED`. The read now reports its failure (`readEstablishedIDs`), and the anchor or the add refuses before writing anything. A table the source genuinely no longer holds still passes. A stop landing during the re-read does not count as a failure: the read runs on the same uncancellable, time-bounded context as the anchor write, so stopping a cold start in its handoff still keeps the slot. On the refusal, once the source can be queried, re-copy as for `TABLE-IDENTITY-CHANGED`: `sluice slot drop` if the slot is left, then the same `sync start` with `--restart-from-scratch`. For `schema add-table`, empty the target table and run the add again. These are the existing remedies of the same check, not measured end to end for this refusal. Pinned by new cells in `TestAnchorTableIDs` and `TestAddTableVerifiedTableIdentity`, mutation-run in both directions. MySQL-family sources, whose table ids are not verified, keep their best-effort read.

## Measured, no change needed

- **A table added to `--include-table` before a VStream copy resume is copied (VSTREAM-COPY-RESUME-SCOPE-WIDEN refuted).** This was measured on the default path, on a single-stream resume and on a resume narrowed to a table the first run never reached. In each case the target matched the source exactly.

## Not closed, stated

- **A VStream copy resume keeps rows the source deleted while the stream was stopped (VSTREAM-COPY-RESUME-RECREATED-TABLE, HIGH, silent, measured, open).** A resumed copy re-copies the tables before the cursor's table by upsert, which never removes a row. A row deleted on the source while the stream was stopped therefore stays on the target, and so does every old row of a table dropped and re-created under its name. Measured: a re-created table holding 6,701 rows on the target against 701 on the source, and a plain stopped-window `DELETE` of 20 rows that survived. No new row was found missing. This release does not fix it. Until it does, re-copy a VStream stream whose copy was stopped and resumed with `--restart-from-scratch`, if the source deleted rows (or re-created a table) while it was stopped.
- **A multi-table single-stream VStream copy may now save no checkpoint**, since none of its checkpoints carried a cursor in the one-shard measurement, so a stop mid-copy refuses on the populated target rather than resuming (loud). Why is not yet investigated.
- **Not run for this release: `d1verify` and `psverify`.** `scripts/prerelease-triggers.sh` raised its unscheduled-pin advisory because the delta touches `internal/pipeline/`. Neither suite exercises these changes. The VStream fix was measured on a local Vitess 24 cluster, not against PlanetScale itself. Coverage otherwise is the CI integration matrix on real MySQL, MariaDB and Postgres containers, including the `-race` Integration job, and the weekly pipeline vstream suite, which now carries the new cells.

## Compatibility

- **No flag change and no backup format change** (`BackupFormatVersion` stays 15).

## Who needs this

- **Anyone who ran a PlanetScale or Vitess `sync start` cold start that was stopped or crashed during its copy and then re-run.** If the re-run did not refuse and did not log a copy resume, it may have skipped the rest of the copy; check for the `INCLUDE-TABLE-SCOPE-UNRECORDED` warning in its output. Compare each table's row count against the source. If they differ, re-copy with `--restart-from-scratch` (remedy not measured on an affected stream).
- **Anyone on v0.163.1 with a Postgres source whose cold start or `schema add-table` logged `could not read the source's table ids`, `could not resolve the source namespaces to read table ids` or `could not read the table's id`.** If a table was also re-created in that window, the next start refused `TABLE-IDENTITY-CHANGED` and named it; follow that refusal's remedy.
- **Everyone else:** upgrade; nothing to do.
