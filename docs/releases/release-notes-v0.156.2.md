# sluice v0.156.2

**HIGH fix — non-ASCII text in a MySQL or MariaDB expression (DEFAULT, generated column, CHECK, functional index) now reaches the target intact, instead of garbled (Bug 288).** On a MySQL source, an expression default such as `DEFAULT ('é')` was read back from `information_schema` double-encoded and created on the target as `'Ã©'` — on `migrate`, `sync` cold start, `restore` and a forwarded `ADD COLUMN`, to MySQL and Postgres targets, at exit 0. On MariaDB, a character outside the Basic Multilingual Plane in an expression became `????`. The damaged text reached the target's DEFAULT, its generated-column expressions (so the target computed wrong values for every row), CHECKs and functional indexes. Copied and backfilled row values were never affected. This release also corrects v0.156.1's claim that a non-BMP DEFAULT "reaches the target intact" — that held for **literal** defaults only — and fixes a misleading remedy on the `ADD-COLUMN-BACKFILL-INCOMPLETE` refusal (Bug 289). Both were found by the v0.156.1 post-release regression cycle; the fix went through two pre-tag value-fidelity reviews, the first of which caught a regression in its own first cut.

## Repair notice — if you were affected

Upgrading stops the damage; it does not re-declare objects an earlier release already created wrong.

1. **A MySQL, PlanetScale or Vitess source with a non-ASCII character in an expression DEFAULT, a generated column, a CHECK or a functional index** (every release through v0.156.1), or **a MariaDB source with a character outside the BMP in one**. Compare each such object on the target against the source's `SHOW CREATE TABLE`, re-declare those that differ, and for a generated column whose expression was wrong, recompute its rows — a `STORED` column keeps its wrong values until it is re-declared. Rows inserted on the target after cutover that took a wrong DEFAULT need repairing from the source.
2. **v0.156.1 only: an `ADD-COLUMN-BACKFILL-INCOMPLETE` refusal acknowledged after applying only a target change.** The restart told you to "apply the same change to the target"; the right repair was to copy the added column's values from the source. Compare the added column against the source for the rows that predate the `ADD COLUMN` and repair them.

## Fixed

**MySQL, MariaDB, PlanetScale and Vitess sources: non-ASCII text in an expression DEFAULT, a generated column, a CHECK or a functional index (HIGH, silent; Bug 288 / GC-37 (a)).** The two engines' catalogs lose this text in opposite places. MySQL stores each string literal in its charset introducer's encoding and its `information_schema` renders every stored byte as a separate character (`é` reads back as `Ã©`), measured on MySQL 8.0.46 and 8.4 and through vtgate; MariaDB's `information_schema` is faithful for the BMP but writes one `?` per byte beyond it, on every LTS line from 10.11 to 12.3. The readers now recover each such expression (`internal/engines/mysql/expr_text_recovery.go`). On MySQL the byte widening is undone and each literal is decoded by its own introducer: utf8mb4/utf8mb3/binary as UTF-8, latin1 as latin1 characters — so a table created from a latin1 client session keeps exactly what it declared. A latin1 byte in 0x80–0x9F (MySQL's latin1 is cp1252 there), a literal in any other charset (`gbk`, …), or a non-ASCII literal with no introducer **refuses the schema read**, naming the object, rather than being guessed. The recovered text must also appear on that object's own `SHOW CREATE TABLE` line, or the read refuses. On MariaDB the `SHOW CREATE TABLE` text that the catalog's `?`s match is taken, searched only within the object's own clause. Pinned on real servers by `TestExprText_NonASCII_OnARealServer`, `TestExprText_NonUTF8LiteralCharsets_MySQL`, `TestMigrate_NonASCIIExpressionDefaults_MySQLToMySQL`/`_MySQLToPostgres`/`_MariaDBToMariaDB` and `TestMigrate_Latin1SessionExpressions_MySQLToMySQL`/`_MySQLToPostgres`, each graded against the source's own evaluation, and mutation-run in both directions.

**The unforwarded-schema-change door, on both flavors (found while fixing Bug 288).** MariaDB's door compared the lossy text and so never saw a change between two such expressions; it now reads the recovered text. Its start-time baseline now reads base tables only — a view over such a table broke every `sync start` on the server — and only the stream's own databases, and skips a table dropped mid-read with a WARN. MySQL's door compared the raw widened text, and MySQL re-spells a CHECK's literals on **any** later `ALTER TABLE` (a CHECK created from a latin1 session reads `_latin1'…'` before an unrelated `ADD COLUMN` and `_utf8mb4'…'` after, even when pure ASCII), so a stream halted with `UNFORWARDED-SCHEMA-CHANGE` on a change nobody made, and the refusal displayed the clause as mojibake that an operator following "apply the same change to the target" would have copied onto the target. The door now compares and displays each expression's value-level text, falling back to the raw text only where the decode refuses — detection stays exact, and no new refusal path is added (`TestUnforwardedDoor_MySQLExpressionText_ValueLevel`, which asserts MySQL really re-spelled the clause).

**`sync`: a restart refused on `ADD-COLUMN-BACKFILL-INCOMPLETE` now leads with the right repair (Bug 289, loud but misleading).** The startup refusal (`internal/pipeline/unforwarded_refusal_persist.go`) and the fleet supervisor's log both printed the generic step (1), "apply the same change to the target". For this refusal the column is already on the target and the rows that predate the `ADD COLUMN` need the source's values; following the generic step and then acknowledging left those rows wrong permanently. Both surfaces now pick step (1) from the refusal itself through one shared helper (`TestStreamerUnforwardedDoor_BackfillIncompleteNamesTheSourceRepair`, `TestSupervisor_UnforwardedRefusalLogNamesTheRightRepair`).

**Docs.** `docs/operator/error-codes.md` now lists the forwarded-`ADD COLUMN` LOB-DEFAULT case of `SLUICE-E-VALUE-UNREPRESENTABLE` (`LOB-DEFAULT-NOT-CARRIED`), introduced in v0.156.1. `docs/operator/cdc-streaming.md` no longer says the MySQL GTID re-send's effect is unmeasured; v0.156.1 fixed and measured it. The v0.156.1 notes carry a correction banner for Bugs 288 and 289.

## Compatibility

- **New loud refusals, on purpose.** A MySQL expression holding a latin1 byte in 0x80–0x9F, a non-ASCII literal in a charset other than utf8/latin1/binary, a non-ASCII literal with no introducer, or a `_binary` literal whose bytes are not UTF-8, now refuses the schema read naming the object. Earlier releases carried most of these wrong at exit 0 (the non-UTF-8 `_binary` and `gbk` cases are measured; a plain latin1 expression such as `DEFAULT ('café')`, which v0.156.1 carried correctly, still migrates). The whole-expression refusal for a mixed-charset expression is filed as GC-37 (l).
- **One extra `SHOW CREATE TABLE`** per table that holds a non-ASCII expression, on each schema read and CDC boundary rebuild.
- **Not covered:** `mydumper` dumps of a MySQL source already carry a non-BMP character inside an expression as `????`, and it cannot be recovered from the dump (GC-37 (k)).
- No backup format, control-table or flag change. The dispatch-only PlanetScale/D1 live-verification suites (`psverify`, `d1verify`) provision billable infrastructure and were not run for this release; the delta is reader-side catalog decoding, pinned against real MySQL, MariaDB and vtgate.

## Who needs this

Anyone migrating or syncing from MySQL, PlanetScale or Vitess with non-ASCII text in an expression DEFAULT, generated column, CHECK or functional index; anyone on MariaDB with emoji (or other non-BMP characters) in one; anyone who created tables from a latin1 client session and keeps CHECK constraints (the false `UNFORWARDED-SCHEMA-CHANGE` after any `ALTER TABLE`); and anyone who acknowledged an `ADD-COLUMN-BACKFILL-INCOMPLETE` on v0.156.1.
