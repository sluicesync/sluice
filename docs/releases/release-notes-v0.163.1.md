# sluice v0.163.1

**HIGH fix, silent — a resumed cold start, and every cold start's CDC anchor, now prove each table is the one the copy made (RESUMED-COLD-START-CERTIFIES-RECREATED-TABLE, measured on Postgres 16, present since v0.149.0).** On a Postgres source, a table dropped and re-created under the same name while a stopped cold start waited was treated by the re-run (`COLD-START-RESUMED`) as already copied, and the ids it then recorded were read after the stop, so they certified the new table. Under a `FOR ALL TABLES` publication the target kept the old table's rows, missed the new one's, and took the new table's later changes onto the old copy, at exit 0, with nothing refusing afterwards. Such a resume now refuses with `TABLE-IDENTITY-CHANGED`, naming the table and both ids. **Also HIGH, silent — a table brought in with `schema add-table` now receives the changes made to it while the stream was stopped (Bug 322, measured on MySQL 8.4, regression since v0.154.0).** No backup format change.

## Fixed

- **A stopped cold start's resume refuses a table that is no longer the one it copied (RESUMED-COLD-START-CERTIFIES-RECREATED-TABLE, HIGH, silent).** Each table's `pg_class.oid` is now read when its copy starts and carried in the recorded copy (the copy-shape fingerprint's `table_ids` aspect). The resume compares them table by table before it skips anything, and a difference refuses with `TABLE-IDENTITY-CHANGED`. A copy recorded without ids (by v0.163.0 or earlier) cannot prove anything, so its resume stands down to the existing slot refusal rather than trusting the names; see Compatibility. Pinned on real Postgres by `TestResumeTableIdentity_PgoutputRecreatedWhileStoppedRefuses` and `TestResumeTableIdentity_PgoutputRenameSwapWhileStoppedRefuses`; `TestResumeTableIdentity_PgoutputTruncateWhileStoppedConverges` and `TestResumeTableIdentity_PgoutputVacuumFullWhileStoppedResumes` pin that `TRUNCATE` and `VACUUM FULL`, which keep the oid, still resume.
- **Every cold start's CDC anchor checks the ids against the copy's.** A table re-created between any cold start's copy and its CDC anchor used to be recorded under the new table's id, so the scope record certified a table the copy never saw. The anchor now re-reads the ids and refuses with `TABLE-IDENTITY-CHANGED` on any table whose id moved since its copy started, and the record written after the anchor takes the anchor's verified ids, never a fresh read (`TestCopyIdentity_PgoutputRecreatedBeforeTheAnchorRefuses`, `TestCopyIdentity_PgoutputRecreatedBeforeTheResumeAnchorRefuses`). A Postgres multi-schema stream's anchor does the same for each schema's tables (`TestCopyIdentity_PgoutputMultiSchemaRecreatedBeforeTheAnchorRefuses`, `TestCopyIdentity_PgoutputMultiSchemaStopAtTheAnchorRecords`). `sluice schema add-table` checks its one table the same way before recording the add complete.
- **A live-added table's stopped-window changes reach the target (Bug 322, HIGH, silent).** On a MySQL binlog source, every INSERT, UPDATE and DELETE made to a table in the stream's live-added set while the stream was stopped was discarded at the restart, at every restart, with the stream green and `sync health` healthy, while the table's later changes still applied. The binlog reader drops a rows event whose table is out of the stream's scope, and it judged scope against a live-added set that was loaded only after the reader had started, so the stopped-window events at the front of the binlog were read and dropped first. The set is now loaded before any reader opens (`phaseReadLiveAddedScope`). Affected: `--no-drain` adds since v0.154.0, and every drained add since v0.163.0, which first kept a drained add's table in scope across restarts. The VStream (Vitess, PlanetScale) and trigger-CDC readers drop rows by the same scope check and had the same window, fixed by the same change. The postgres-trigger arm was measured after release by the v0.163.1 regression cycle (lossy on v0.163.0, exact on v0.163.1). VStream was not measured end to end. The same gap also reached a cold start that copies a live-added table (`--restart-from-scratch`, the re-snapshot after an invalid position, an interrupted copy's resume, each of which copies live-added tables since v0.163.0): changes made to that table just after the copy's snapshot were dropped the same way. Measured after release: v0.163.0 dropped the 5 inserts made between the snapshot and the live-added merge, and v0.163.1 was exact. Postgres pgoutput sources were not affected. Pinned by `TestIncludeTableScopeDrift_BinlogStoppedWindowReachesTheAddedTable`, `TestIncludeTableScopeDrift_BinlogStoppedWindowReachesTheNoDrainAddedTable`, `TestIncludeTableScopeDrift_PgoutputStoppedWindowReachesTheAddedTable` and the unit `TestWireCDCScopePredicate_PersistedLiveAddInScopeBeforeTheReaderOpens`.
- **Sources whose ids do not survive a rebuild are unchanged.** InnoDB's `TABLE_ID` changes on `OPTIMIZE TABLE`, a copying `ALTER` and `TRUNCATE`, so on a MySQL-family source a changed id is as likely routine maintenance as a re-creation: the anchor and record keep the fresh read they always had. Only a Postgres source can reach the cold-start resume today.

## Not closed, stated

- **The copy-time ids are read just after the copy's snapshot opens**, so a table re-created between those two statements is recorded with its new id. That window is a few statements inside the run, not the stop or the copy this release closes.
- **Not run for this release: `d1verify` and `psverify`.** `scripts/prerelease-triggers.sh` raised its unscheduled-pin advisory because the delta touches `internal/pipeline/`. Both suites need live infrastructure that was not provisioned. The table-id change is confined to Postgres; the Bug 322 change reaches the PlanetScale/Vitess reader's scope check, whose end-to-end behaviour against a real cluster is therefore unmeasured for this release. Coverage is the CI integration matrix on real MySQL, MariaDB and Postgres containers, including the `-race` Integration job.

## Compatibility

- **No flag change and no backup format change** (`BackupFormatVersion` stays 15).
- **A stopped cold start recorded by v0.163.0 or earlier does not resume on this release.** Its recorded copy carries no table ids, so the re-run cannot prove the tables are the ones it copied; it refuses on the existing slot instead, as before v0.149.0. Re-copy it (`sluice slot drop`, then `sync start --restart-from-scratch`).
- **Downgrading loses the check.** A cold start stopped under this release and re-run on v0.163.0 or earlier resumes without comparing table ids, because the older binary ignores them. Re-run a stopped cold start on this release or later.

## Who needs this

- **Anyone on v0.149.0 or later whose Postgres cold start was interrupted, resumed (`COLD-START-RESUMED`), and had a table dropped and re-created on the source in between.** That table's target copy may hold the old table's rows with the new table's changes applied on top, at exit 0. Compare it against the source and re-copy it with `--restart-from-scratch` (remedy not measured).
- **Anyone who ran `schema add-table` on a MySQL-family, Vitess/PlanetScale or trigger-CDC source and later restarted the stream** (a `--no-drain` add on v0.154.0 or later, any add on v0.163.0). Changes made to that table while the stream was stopped never reached the target. They are still on the source: with the stream stopped, empty the target table, run `sluice schema add-table <table> --yes` again, then the same `sync start` (measured against a by-hand reproduction of the lost state), or re-copy the stream with `--restart-from-scratch` (measured after release on streams v0.163.0 had diverged, drained and `--no-drain`).
- **Everyone else:** upgrade; nothing to do.
