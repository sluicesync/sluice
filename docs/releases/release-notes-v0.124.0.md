# sluice v0.124.0

**Security fix plus the 2026-08-13 audit burn-down: a tampered or corrupted backup manifest can no longer execute arbitrary SQL during restore — emitted DDL now refuses to be more than one statement on both lanes that could run it (new code `SLUICE-E-DDL-EMIT-MULTI-STATEMENT`); the MySQL-family→PG CHECK operator gate is rebuilt from a fresh real-flavor measurement; and a broker cold start refuses a bad chain BEFORE dropping the target's tables.** Also in this batch: spatial preflights for the pgtrigger lane and Z/M geometry toward MySQL, the schema-preview geography flatten note, `--max-buffer-bytes` reaching the VStream concurrent COPY, loud validation of `--notify-*` fractions, a runnable recovery for the trigger-lane UTF-8 halt, and three false operator claims corrected under new marker gates. Drop-in upgrade from v0.123.1 and older — no flag or default changed; one error code added; several previously-late or silently-inert failures now refuse loudly at preflight (see Compatibility).

## Fixed

**Emitted DDL now refuses to be more than one statement before the server sees it — the restore-injection door, closed on both lanes that could execute it (audit C1-1, new code `SLUICE-E-DDL-EMIT-MULTI-STATEMENT`).** sluice's emitters only ever produce one SQL statement, but the restore path inlines recorded expression bodies (CHECK constraints, generated columns, defaults) from a backup manifest verbatim into that DDL — and Postgres's pgx simple protocol and SQLite's modernc driver both execute multi-statement strings, so a tampered or corrupted manifest whose body closed the surrounding syntax and appended `; DROP TABLE …; --` executed arbitrary SQL as the restore role, at exit 0, with `backup verify` green (signature verification catches tampering when enabled; this door holds regardless, on the structural invariant the emitters already guarantee). A per-lane validator that understands the quoting exactly as it is produced — dollar-quoted bodies on PG; all three self-doubling quote forms, `[bracketed]` identifiers, and line/block comments on SQLite, whose `--stage-local` path executes user-authored dump DDL — refuses any top-level second statement, unbalanced paren, or unterminated quote with the new code, and an AST-roster gate requires every emitted-DDL exec site to route through the one door (all 24 sites in the PG schema writer; the SQLite schema writer and `--stage-local`), with each exemption named. End-to-end pins drive the audit's exact hostile CHECK body against a real Postgres and the embedded SQLite and require both halves — the coded refusal AND the canary table still standing; under the validator-disabled mutant the SQLite injection actually executed and took the canary, which is the teeth check. MySQL-family targets are structurally immune (go-sql-driver refuses multi-statement Exec and sluice never sets `multiStatements=true`, grep-verified — a premise now pinned, not assumed); the D1 HTTP transport is the one filed open sibling. Affected releases: the Postgres restore surface has executed recorded-manifest DDL through the simple protocol since restore shipped in v0.15.0 (`5550c230`); the SQLite lane since the SQLite target shipped in v0.99.146 (`4c99e7a7`), with the `--stage-local` consumer since v0.99.167 (`d53b9e2c`); both through v0.123.1.

**The MySQL-family→PG CHECK-constraint operator gate now covers the measured operator table, not the two spellings its founding incident happened to render (audit ARCH-1).** Bug 242's gate (v0.120.1) listed REGEXP/RLIKE and nothing else, so sibling operators that render into real catalogs the same way still died in PostgreSQL's parser mid-migrate, after earlier tables were created: infix `DIV`/`XOR` on both flavors, MariaDB's infix `MOD` (rendered for BOTH source spellings, `a MOD b` and `a % 3` — MySQL 8 renders both as `%`, which PG parses), MariaDB's preserved prefix `!`, `MEMBER OF` (MySQL 8 only — MariaDB rejects it at CREATE), bare `INTERVAL n unit`, and column-level `COLLATE`. The gate is rebuilt from a fresh measurement (one CHECK per operator in the MySQL grammar's operator table, read back from information_schema on mysql:8.0/8.4 and mariadb 10.11/11.4/11.8/12.3), with call-shaped `mod()`/`div()` and translator-rewritten `date_add`/`cast` shapes deliberately not refused, and every refusal carrying a runnable remedy. *[Correction 2026-08-13: the "runnable remedy" half of that sentence was wrong as shipped — the CHECK-site refusals recommended `--expr-override`, which rewrites only generated-column bodies and errors on a CHECK constraint target (Bug 247). v0.124.1 makes every remedy site-aware: generated columns keep `--expr-override`; CHECK/DEFAULT sites get `--exclude-table` or fix-on-source.]* It is held by a real-flavor matrix (`TestCheckOperatorFamilyMatrix_{MySQLToPG,MariaDBToPG}`) that classifies every reader-rendered expression against both pre-DDL gates with a per-flavor verdict map, then runs the real Migrator and requires each surviving CHECK present in the real target's catalog — the independent oracle — plus a loud-late pin for the one documented escape (a bare `!a` alone, whose refusal would need a real parser). All five MySQL-family source engines route through the one gate: `mysql`, `mariadb`, `planetscale`, `vitess`, `mydumper` (the `IsMySQLFamily` dispatch; vitess/planetscale are MySQL-8-lineage catalogs). Loud-late→loud-early: nothing was silently lost, but a mid-migrate abort becomes a preflight refusal with a remedy.

**A broker (`sync from-backup`) cold start with `--reset-target-data` now refuses a bad chain BEFORE dropping the target's tables (audit BRK-1).** Bug 243's door sweep (v0.120.1) covered restore, chain-restore deltas, verify, and the maintenance WARNs — and missed the broker: its reset path drops every table named in the cached manifest before `ChainRestore` runs its own refusals, so a chain carrying a malformed recorded schema had the target's tables destroyed and THEN refused, with nothing restored in their place. The malformed-recorded-schema door is now exported from the backup package — the same detector and the same coded renderer as every other door, so the doors cannot disagree — and runs over the whole chain's manifests before any drop (deliberately unfiltered: the broker restores whole chains). The ordering itself is pinned: a stub whose row writer always errors proves the refusal arrives before any drop attempt, and the door-blinded mutant reproduces the exact pre-fix behaviour. Affected releases: the drop-before-refusal ordering has existed since the broker's reset drop shipped in v0.20.1 (`3742c954`), through v0.123.1; the refusal it now front-runs became refusable when the Bug 243 doors shipped in v0.120.1. Loud either way — the cost was the destroyed target, not silent loss.

**`postgres-trigger` setup now refuses PostGIS geometry/geography columns instead of wedging the stream at the first spatial DML (audit SPAT-4).** The delegated postgres reader carries spatial columns (ADR-0035), so pgtrigger setup and the cold copy succeeded on a spatial table — and then the trigger capture (`to_jsonb`) renders a spatial value as a GeoJSON object the shared apply path cannot decode, so the first spatial change after cold start failed the apply and wedged the stream mid-incident; the engine's own doc used to claim a refusal that did not exist. Setup now refuses at the preflight roster (reason `postgis-spatial-column`) with runnable remedies: the `postgres` engine (logical replication carries spatial values as EWKB faithfully) or `--exclude-table`. Detection covers every wrapping the capture can meet — direct column, array element, DOMAIN base, and DOMAIN-over-array (the domain case is the subtle one: geometry's `typtype` is `'b'`, so the existing unrecognised-domain gate never caught it) — pinned on real PostGIS including the negative half (an ordinary table in a PostGIS-enabled database must NOT refuse). Engine scope, from the sibling enumeration: `postgres-trigger` only — SQLite/D1 have no spatial column type, MySQL binlog CDC carries geometry bytes natively, and the `postgres` slot engine is the refusal's named remedy. A full spatial-carry capability for the trigger lane is recorded as the deliberate alternative in the backlog, not foreclosed. Affected releases: pgtrigger has accepted spatial tables at setup since the engine shipped in v0.85.0 (`9f220c47`), through v0.123.1; the failure was loud (a wedged stream), never silent.

**A PostGIS Z/M-dimensional column toward a MySQL-family target now refuses at preflight instead of aborting mid-copy on the server's raw error 1416 (audit SPAT-2).** MySQL 8 supports no Z/M geometry at all, and the MySQL writer's type emission silently drops the dimensional suffix — so the DDL created a 2D column, every preflight passed, and the copy then aborted mid-run on an error that names nothing about dimensionality. The shared pre-DDL chokepoint (migrate, restore, chain restore) now refuses Z/M-flagged geometry and geography toward the MySQL-family targets (`mariadb`, `mysql`, `planetscale`, `vitess`), naming the dimension, the mid-run failure it prevents, and the `ST_Force2D` landing for operators who accept losing the extra dimension, with the `--exclude-table`/`--type-override` recovery riding as before; 2D geometry and geography stay supportable (ADR-0035's direction must not regress to a blanket refusal — pinned as the negative half). Loud-late→loud-early; no data was silently altered.

**`schema preview` now surfaces the geography→geometry computational flatten toward MySQL-family targets (audit SPAT-3).** A PG geography column toward MySQL lands as planar geometry with the value bytes and SRID carried exactly — nothing refuses and nothing should — but geography computes distance/area/containment geodesically (meters on the spheroid) while MySQL geometry computes them planar in coordinate units, so queries moved verbatim silently change meaning; preview reported this flatten as "0 translations; 0 hints" because both sides rendered as "geometry" and the equal-rendering short-circuit suppressed even the bare note. The PG-family side (`postgres` and `postgres-trigger`, which delegates its schema read) now renders "geography" and the notes registry carries the geodesic→planar caveat; a PG→PG move keeps the type and stays silent, and the reverse direction gains no note (MySQL geometry is already planar). Pinned in both directions.

**`--max-buffer-bytes` now reaches the VStream concurrent cross-table COPY's per-stream sub-budgets (audit VST-1).** The ADR-0099 concurrent COPY on VStream sources (`vitess`/`planetscale`) gates its K producers on per-stream budgets derived once when the pump starts, and the pipeline applies `--max-buffer-bytes` after the reader is open — so the operator's cap updated only a field the concurrent producers never consult, and the sub-budgets stayed at the default (16 MiB per stream at K=4) whatever was asked for. A memory bound still existed; it just wasn't the operator's. The setter now re-derives the sub-budget under the same lock with the pump's own formula, floored at one byte so a tiny cap degrades to one-row-at-a-time rather than wedging, and both call orders are correct; the sequential VStream path always honoured the cap and is untouched, and every VStream caller (sync cold start, migrate, the backup snapshot) routes through the one setter. Affected releases: since the concurrent COPY shipped in v0.99.67 (`a658c064`), through v0.123.1.

**Out-of-range `--notify-*` fractions now refuse loudly at start instead of arming an alert that can never fire (audit PROG-NOTIFY-1).** The utilisation thresholds (`--notify-storage-util`/`--notify-cpu-util`/`--notify-mem-util`) and `--notify-storage-growth-per-min` are fractions (0–1), and any positive value was accepted — an operator typing `--notify-storage-util 85` (meaning 85%) armed a rule that could never fire, the exact quiet failure an alert threshold exists to prevent; negative and NaN values were likewise silent. One validator now refuses fractions outside 0–1 with the corrected-value hint ("if you meant 85%, pass 0.85"), and NaN/negative everywhere; 0 stays the documented disable and `--notify-lag-seconds` keeps its seconds unit. It is wired at every entry that arms the rules, before anything starts: `sync start` and the standalone `metrics-watch` (whose fleet mode is reachable only through the same door, grep-verified). Affected releases: the sync-scoped thresholds have accepted inert values since they shipped in v0.99.108 (`e583713a`), the standalone watcher since v0.99.115, through v0.123.1.

**The invalid-UTF-8 halt's printed remedy is now runnable on the sqlite-trigger lane (Bug 245, filed by the v0.123.0 regression cycle).** v0.122.0's SQT-1 refusal printed "repair the value at the source" on every lane, but on the trigger lane the poison also lives in the captured change-log before/after images the refusal names — and the repairing base-row UPDATE itself captures a NEW change whose before-image carries the poison — so an operator following the hint exactly re-halted on every restart, and the lane's real recovery was undocumented (loud, zero silent loss; the halt is the guard working as designed). The refusal is now a typed error and the trigger lane's wrap sites append the runnable recovery — `sluice trigger teardown` + repair + `sluice trigger setup` + a fresh sync, with the byte-level image scrub as the advanced alternative — documented in the operator CDC docs; the d1-trigger transport gets the same extension through the shared typed error, and a negative pin ensures the teardown recovery attaches to nothing else (a corruption error carrying "run trigger teardown" would send an operator to tear down a healthy capture set). The end-to-end pin drives the filing's repro as printed: halt, source-only repair, re-halt, then the recovery, ending in a clean delivered change. Affected releases: the incomplete remedy text shipped with the SQT-1 refusal in v0.122.0, through v0.123.1.

**Three false operator claims corrected, each now held true by a marker gate derived from the code (audit D-1/D-2/D-3).** `migrate --where` claimed to work "on every engine that supports migrate" — the pushdown set is actually `mariadb`, `mysql`, `planetscale`, `postgres`, `postgres-trigger`, `vitess` (postgres-trigger's bulk-copy reader delegates to postgres; that delegation is now pinned at compile time and verified with a real predicate against a real Postgres), while the flat-file (`csv`/`tsv`/`ndjson`), SQLite/D1, and mydumper readers migrate but refuse `--where` at preflight rather than silently copying every row. Production-readiness claimed backup chains and the continuous broker "work on every engine that migrates" — only `backup full` and the restore/replay side are engine-neutral; creating the incremental side (`backup incremental`, `backup stream`) needs a CDC-capable source, and that set is `d1-trigger`, `mariadb`, `mysql`, `planetscale`, `postgres`, `postgres-trigger`, `sqlite-trigger`, `vitess`. And the online schema-change family was claimed whole for MySQL-family + Postgres — `backfill` covers that wider set, but `expand-contract` and `deploy-ddl` are PlanetScale-only and refuse without a PlanetScale service token. Each corrected sentence now sits over an `internal/docsync` marker derived from the code (compile-time capability pins, the engine registry, the command hardcodes), with anti-vacuity floors, all mutation-run — the same machinery that already holds the filtered-sync and target-engine lists.

## Compatibility

No CLI flag or default changed, no on-disk format changed shape, and one error code is added: `SLUICE-E-DDL-EMIT-MULTI-STATEMENT` (a restore or SQLite `--stage-local` run whose recorded/dump DDL contains a top-level statement boundary now refuses before the server sees it; genuine emitter output never does). **Drop-in upgrade from v0.123.1 and older**, with these behaviour notes — every one a loud-at-preflight (or loud-at-start) conversion of a previously late, destructive, or silently-inert failure. A `postgres-trigger` setup on a table with PostGIS spatial columns now refuses where it previously succeeded and wedged the stream at the first spatial DML — remedy: the `postgres` engine or `--exclude-table`. A PostGIS Z/M-dimensional column toward a `mariadb`/`mysql`/`planetscale`/`vitess` target now refuses at preflight where the copy previously aborted mid-run on a raw 1416 — remedy: `ST_Force2D` at the source, `--exclude-table`, or `--type-override`. A migrate from a MySQL-family source (`mysql`, `mariadb`, `planetscale`, `vitess`, `mydumper`) to Postgres whose CHECK constraints render infix `DIV`/`MOD`/`XOR`, prefix `!`, `MEMBER OF`, bare `INTERVAL`, or column-level `COLLATE` now refuses pre-DDL with a runnable remedy where it previously died in PG's parser mid-migrate after earlier tables were created — note that MariaDB renders infix `MOD` even for `%`-spelled source constraints, so a `%` CHECK that passes from MySQL 8 refuses from MariaDB: the rendering is the server's, and it is exactly what would have died. An out-of-range `--notify-*` fraction now refuses at `sync start`/`metrics-watch` start where a config carrying e.g. `85` was previously accepted and the alert silently never fired — pass `0.85`. A broker `--reset-target-data` cold start on a chain with a malformed recorded schema now refuses with the target's tables intact where it previously dropped them first. Also in this release: the C-11 skip-ledger residuals are closed test-side (the MariaDB `VALUES()` upsert arm and a >64 KB position token pinned on real servers, no production code changed) and the skip WARN's operator doc now distinguishes the privilege-revoked cause (restore the grant and the skip clears on the next change — no re-snapshot). All CDC delivery semantics, positions, and the batched/concurrent apply paths are otherwise untouched.

## Who needs this — action required

**Anyone with `--notify-storage-util`/`--notify-cpu-util`/`--notify-mem-util`/`--notify-storage-growth-per-min` in a config or wrapper script: check the values now.** If any is above 1 (e.g. `85` meaning 85%), that alert has NEVER been able to fire on any release since v0.99.108 — the run was healthy-looking with a dead alarm. On v0.124.0 such a config refuses at start with the corrected value in the message; fix it to the fraction (`0.85`) and confirm the alert arms. **Anyone restoring encrypted backups to a Postgres or SQLite target from storage a third party could write to, with signature verification off**: upgrade before the next restore — a tampered manifest could previously execute arbitrary SQL as the restore role at exit 0; if that exposure applies retroactively, review restore-role activity and prefer enabling signature verification as well. **Anyone running the broker with `--reset-target-data`**: upgrade before pointing it at a chain you have not verified — a refusable chain no longer costs the target its tables first; if a past cold start refused after the drop, that target was left empty and needs a restore from a good chain. **Anyone running VStream (`vitess`/`planetscale`) cold copies with `--max-buffer-bytes` and the concurrent COPY**: the cap now actually reaches the per-stream budgets, so memory use will follow what you asked for — if you tuned the flag downward and saw no effect, expect the lower (correct) footprint now. **pgtrigger operators with PostGIS tables, and MySQL-family→PG migrations with the named CHECK operators**: your next setup/migrate may refuse where it previously failed later — the refusal text carries the remedy in each case. No fix in this release involves silent row loss in an ordinary configuration, so no data re-verification is owed.
