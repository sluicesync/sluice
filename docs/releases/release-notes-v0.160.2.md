# sluice v0.160.2

**HIGH fix — v0.160.1 could change the values of a MySQL or MariaDB generated column or CHECK on a Postgres target, at exit 0, when the expression used a column named `both`, `leading` or `trailing` inside `TRIM(…)` (Bug 311). That release's own fix for GitHub #356 introduced it, and its regression cycle caught it against real servers. Only v0.160.1 is affected. The pre-tag review of the fix found two older shapes of the same class on MySQL-family targets, also closed: a Postgres table using `trim(x)` in a generated column, CHECK or index could not be migrated to MySQL at all, and could compute a wrong trim when the table had a column named `both`. This release also makes three key-collation refusals and warnings name a remedy that works. Drop-in: no flag, default, error-code or backup-format change. If you ran v0.160.1 from a MySQL-family source into Postgres, read Who needs this.**

## Fixed

- **A MySQL or MariaDB expression that uses a column named `both`, `leading` or `trailing` inside `TRIM(…)` keeps its meaning on a Postgres target again (HIGH, silent; Bug 311; v0.160.1 only).** MySQL's stored text tells the column (backticked) from the `TRIM` keyword (bare), but sluice strips the backticks when it reads an expression, so the Postgres writer has to tell them apart by position. v0.160.1's pre-tag review found that quoting the keyword as a column is valid Postgres that trims different characters, and its fix kept those three words bare anywhere inside `TRIM`. That broke the opposite case: MySQL stores ``trim(`both` from `code`)`` (trim the characters held in column `both`), and v0.160.1 emitted `TRIM(BOTH FROM code)`, which trims spaces. Measured by the regression cycle: a generated column held `bbabb` and `bab` where the source computed `a` and `  bab  `, through `migrate`, `sync start` and later CDC rows, with `verify --depth count` clean; a CHECK over the same shape silently became a different constraint, and `concat(trim(`trailing`),'!')` failed with SQLSTATE 42601. The writer now keeps the word bare only as the first token of `TRIM`'s arguments with a remove-string and then FROM after it (`TRIM(BOTH 'x' FROM s)`, and `TRIM(BOTH -(1) FROM s)`, which is how MySQL stores a unary-minus remove-string); right before FROM, or with no FROM in the call, it is the column. That rests on measured server behaviour, not the grammar: on MySQL 8.0.46 and MariaDB 11.4 neither server stores the keyword without a remove-string after it (MySQL cannot store `TRIM(LEADING FROM s)` at all; MariaDB stores it as `ltrim(s)`), so the earlier rule's comment, which said MySQL stores exactly that form, was wrong. The MySQL writer had the opposite half of the same defect, long-standing and loud: a MySQL → MySQL generated column `trim(both 'x' from code)` failed with `Error 1064` because the keyword was quoted as a column, and it now uses the same rule. The pre-tag value-fidelity review of this fix found two more shapes, both long-standing on MySQL-family targets and both closed here. A unary-minus remove-string (`trim(both -1 from code)`) was read as the column `both` minus 1, silently, when the table had an integer column of that name. And Postgres prints `trim(x)` as `TRIM(BOTH FROM x)`, a form MySQL accepts in a statement but cannot store (its own re-print fails with ERROR 1064, measured on 8.0.46), so every Postgres → MySQL table with `trim(x)` in a generated column, CHECK or functional index was refused, and with a `both` column the keyword could be read as that column, silently; the Postgres → MySQL translator now rewrites the keyword-only forms to `TRIM(x)`, `LTRIM(x)` and `RTRIM(x)`, which trim the same spaces. Pinned by `TestMigrate_MySQLSource_TrimKeywordColumns` (real MySQL 8.0 source into Postgres and into MySQL, each generated value compared with the value the source server computed, including the unary-minus remove-string), `TestMigrate_PostgresToMySQL_TrimKeywordForms` (real Postgres source into MySQL: generated columns, a CHECK and a functional index, compared with what Postgres computed), `TestRequotePGReservedIdents_TrimKeywordsStayGrammar` and `TestRequoteMySQLReservedIdents_TrimKeywords` (the measured stored shapes). Mutation-checked, each with its loud cells removed so the value comparison alone had to catch it: v0.160.1's rule restored (`bbabb` where the source computed `a`); the unary-minus case misread (`-1a-1` where the source computed `a`); the Postgres `TRIM` rewrite disabled (`b` where Postgres computed `aba`). With the MySQL rule removed, the MySQL leg fails with 1064.
- **Chain restore and `sync from-backup` now WARN for every MySQL or MariaDB incremental captured before v0.159.2 that has a character column in a primary or unique key (MEDIUM; Bug 307, KEY-COLLATION-PRE0159-2-UNDETECTABLE).** `backup verify` does too. Such a capture recorded a key's collation only as of its window's end, so a key changed and changed back inside the window left no evidence, and every release restores it with the two source rows merged at exit 0. No release can refuse it, because nothing in the chain says it happened; v0.159.2's notes asked operators to check such restores against the source. The WARN, marked `KEY-COLLATION-PRE0159-2-UNVERIFIABLE`, names the table and its character key columns, and says to run `sluice verify` against the source and take a fresh full backup with v0.159.2 or later. Pinned by `TestWarnUnverifiableKeyCollationIncrement` and `TestSluiceVersionBefore`.
- **A chain restore whose incremental changes a key column's collation, where the target refuses that change, now says so with a remedy instead of the target's raw duplicate-key error (LOW to MEDIUM, loud; KEY-COLLATION-ROLLOVER-SPLIT-DELTA-DUP).** Chain restore applies an incremental's schema changes ahead of its rows, so a later incremental that loosens a key back can reach the target while two values the source had already reconciled are both still there, and MySQL refuses the ALTER with `Error 1062`. An hourly `backup incremental` splits a change from its revert this way by construction. Nothing merged, but the error named no remedy. It is now `KEY-COLLATION-MERGE`, marked `KEY-COLLATION-DELTA-FAILED`, keeps the target's error, and gives the remedy the other refusals of such a window give. Applying such a change at the end of the incremental instead, so the restore converges, is still open. Pinned by `TestApplySchemaDeltas_KeyCollationDeltaFailureIsNamed`.
- **A Postgres-target CDC `KEY-COLLATION-MERGE` now names the table and a remedy that can work (LOW, loud; KEY-COLLATION-PG-UNESTABLISHED-REMEDY, wider than filed).** On the pipelined batch apply path, the default, the refusal named no table at all. On the serial path it said to give the target's key the source's collation, which cannot converge for a key compared byte for byte because its collation was not established for the rows being replayed: the target already carries that collation. Both paths now name the table and the collation sluice compared the key under (`"k" COLLATE "C"`), with the `ALTER TABLE` and the re-copy for `sync start` and `sync from-backup`; where the target already has the source's collation, the remedy offers the re-copy alone and says why. Pinned by `TestApplyKeyCollationMergeRemedy` and `TestPipelinedInsert_KeyCollationMergeNamesTheTable`.
- **Internal, no operator impact:** the seeded-boundary integration test for a loosened key-collation window now requires each case's exact outcome rather than a count of graded cases.

## Compatibility

**Drop-in.** No flag, default or error-code change, and no backup format change (`BackupFormatVersion` stays 14). **The behaviour changes:**
- **Postgres → MySQL:** `trim(x)`, `trim(leading from x)` and `trim(trailing from x)` now arrive as `TRIM(x)`, `LTRIM(x)` and `RTRIM(x)`.
- **Cross-dialect expressions on a Postgres or MySQL target** spell a column named `both`, `leading` or `trailing` inside `TRIM(…)` as a quoted column wherever it is not the leading keyword.
- **Restore, `sync from-backup` and `backup verify` may WARN `KEY-COLLATION-PRE0159-2-UNVERIFIABLE`** on older MySQL-family chains. It is a warning; nothing refuses.

**Not affected by Bug 311:** Postgres targets fed by a Postgres or SQLite source (a Postgres source's expressions are copied verbatim; SQLite has no `TRIM(… FROM …)` form), and expressions with no column named `both`, `leading` or `trailing` inside `TRIM`.

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale), `d1verify` (live Cloudflare D1) and `nekiverify` (live Neki) suites, which need live, billable infrastructure.

## Who needs this — action required

- **Anyone who ran v0.160.1 from a MySQL or MariaDB source into Postgres where a generated column or CHECK uses a column named `both`, `leading` or `trailing` inside `TRIM(…)`.** The generated values may differ from the source's, and a CHECK may enforce a different condition. **Check:** compare the generated column with the source's (`verify --depth count` does not see it). **Action:** upgrade, then re-copy the affected tables; for a `sync start` stream, re-run it with `--reset-target-data --yes`. A stored generated column recomputes only when its row is written, so upgrading alone does not repair existing rows.
- **Postgres → MySQL users with a column named `both` and a generated column using `trim(x)` (long-standing, every release).** The keyword could be read as that column, so the target computed a different trim at exit 0. **Check:** compare the generated column with the source's. **Action:** upgrade and re-copy the table. Without such a column the same tables were refused loudly, and now migrate.
- **MySQL or MariaDB → MySQL users with an integer column named `both`, `leading` or `trailing` and an expression such as `trim(both -1 from …)` (long-standing, rare).** It was read as a subtraction, at exit 0. **Check and action** as above.
- **Operators restoring or replaying MySQL-family backup chains taken before v0.159.2:** read the new WARN when it appears and check those tables with `sluice verify`.
- **Everyone else:** upgrade.
