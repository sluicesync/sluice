# sluice v0.148.1

**HIGH fixes — the cold-start visibility v0.148.0 announced was absent on every MySQL-family target and a no-op on an ordinary `sync start` target; this release makes it true where it can, says where it still is not, and closes two silent-empty-tail defects on MySQL sources plus one on `postgres-trigger` partitions.** The 2026-09-09 blind audit measured v0.148.0's headline feature rather than reading its notes, and found `sync status` erroring on every MySQL target and creating no progress tables on any target that had never run `migrate`. The same audit found two MySQL CDC doors comparing database names under a rule the server does not use — one of them since the binlog reader first shipped — and a `postgres-trigger` DDL filter that stopped seeing DDL issued through a partitioned parent. Drop-in: no flag, schema, position or manifest format changes.

## Fixed

**DDL issued through a partitioned parent was invisible to `postgres-trigger` when the capture triggers sit on the partitions** (silent divergence, exit 0; affects v0.140.0 through v0.148.0). The `ddl_command_end` capture recorded only commands whose own relation carried a capture trigger. Measured on PG 16: an `ALTER TABLE <partitioned parent> ALTER COLUMN … TYPE` produces exactly one `pg_event_trigger_ddl_commands()` row, and its object is the parent — so with the triggers on the partitions the predicate matched nothing, no DDL row was recorded, and the stream ran green while the target kept its pre-ALTER values (the audit's run had source 100/200/300 against target 1/2/3). This is the common configuration, not a corner: `sync start` and `migrate` refuse a declaratively partitioned parent at preflight, so capturing the partitions is the supported route. It is a delta regression — before v0.140.0 the DDL tier recorded every DDL and halted loudly; the SLP-2 narrowing that cut the false halts narrowed past the parent case. The predicate now walks `pg_inherits` recursively downward from the command's relation, which covers declarative partitioning and classic INHERITS with one mechanism and nests, so a trigger on a sub-partition still makes the root's ALTER visible; only downward is needed, because PostgreSQL clones a parent's row trigger onto every partition. Pinned on a real server by `TestCaptureDDL_ThroughParentWithTriggersOnChildren`, mutation-run in both directions. Note that the predicate lives in the `sluice_capture_ddl` function body installed on the source — see the action section below.

**`sync status` failed outright on every MySQL-family target** (v0.148.0 only). The new cold-start lister rendered `ESCAPE '\'`; MySQL treats a backslash as a string escape by default, so that is an unterminated literal and `Error 1064` — a parse error, so it fired whether or not the control table existed, and the whole command errored instead of rendering anything. `sync health` swallowed the same error. PostgreSQL's `standard_conforming_strings` makes the byte-identical statement valid, which is exactly how it shipped: the two engines' SQL was reviewed as the same string and one dialect disagreed. Both engines now render `ESCAPE '#'` and the shared escaper (`likeEscapeChar`) escapes `#`, `%` and `_` — a character neither dialect treats specially removes the divergence instead of quoting around it. Neither engine had a test touching the lister; `TestMigrationStateStore_ListAgainstRealMySQL` now runs the real statement against a real server, including a prefix-collision case that proves the ESCAPE clause is in effect.

**Cold-start visibility was a no-op on any target that had never run `migrate`** (v0.148.0 only). The control tables were created from exactly one place, the resume read that the sync recording context refuses by construction — so on the ordinary `sync start` target every progress write failed (twelve SQLSTATE 42P01 warnings on the audit's real-PG run) and `sync status` showed nothing for the whole copy, precisely the blackout the feature exists to end. The recording context now ensures its own tables; if it cannot, recording degrades to inert with a WARN and the migration proceeds, because refusing to migrate over a progress table would be the wrong trade. Pinned by `TestSyncRecordingContextEnsuresItsTables`.

**A finished cold start's progress row is now marked terminal.** `markComplete` was called from `migrate`'s driver, not from the shared copy phases, so the sync path recorded a run that never ended and `sync health` reported "cold start in progress" indefinitely — worse than cosmetic, because the release's own operator rule is that a progress age which keeps climbing means the run is dead, and a permanent phantom teaches operators to distrust the one signal the feature provides. The row now transitions to `complete` when the copy phases return; `sync health` treats a `complete` row as "no cold start" and falls through to its normal not-found answer, and `sync status` drops it from the in-progress section (`filterColdStarts`) rather than listing a finished copy with a climbing age — the pre-tag review caught the first cut of this fix reaching health and not status, and both are pinned. A cold start that finished under v0.148.0 was never marked and keeps its last live phase until the row is removed by hand (see below).

**Correction to v0.148.0: a cold start stopped before its CDC anchor cannot be resumed, and `STOPPED-SLOT-KEPT` now says so.** v0.148.0 kept the replication slot when a stop landed after the copy and told you to re-run with the same `--stream-id` to resume. The kept-slot door only ever fires before the anchor is written (the copy and index phases), so no position exists for a re-run to find: it cold-starts and refuses on the existing slot. Only a stop during the anchor write itself resumes, and that window was protected before v0.148.0. Found when the release commit's CI caught the pin `TestStreamer_ColdStartStopInHandoff_PG_KeepsSlotAndResumes` landing a stop in `create indexes` — it had passed for two releases only when its 1 ms poll raced past the anchor. The WARN now states the real way out (`sluice slot drop … --yes`, then `sync start --reset-target-data`), the pin grades each stop by the window it landed in, `docs/operator/cdc-streaming.md` and the v0.148.0 notes carry the correction, and the handoff resume that would make the kept slot useful is tracked as A0909-STOP-1.

**`sync status` says when it could not open the target's migration-state store.** Before, an open failure silently left the cold-start section empty, which reads exactly like "nothing running" — the reading this whole surface exists to prevent. It now WARNs and tells you to treat an absent stream as unknown. The PostgreSQL lister gained the real-server pin its MySQL twin got (`TestMigrationStateStore_ListAgainstRealPostgres`), including the escape character escaping itself.

**The visibility block reaches PostgreSQL sources on the fast copy path only, and the docs now say so.** Only the shareable-snapshot parallel cold start (the default fresh cold start from a PostgreSQL source) builds the recording context; a resumed copy, `--schema-already-applied`, and every non-PostgreSQL source — MySQL, MariaDB, PlanetScale and Vitess, including the source whose field report prompted the feature — take the serial copy path, which still records nothing. This is not fixed in v0.148.1; threading recording through the serial path is a real chunk, and shipping half of it under the original broad claim would repeat the mistake being corrected. `cross-region-migration.md` carries the correction and points at the `FLOAT-EXACT-REREAD` log line that remains the signal on those sources. Tracked as audit A0909-P2b.

**A case-mismatched `--binlog-do-db` no longer passes the binlog-filter door on a case-sensitive MySQL or MariaDB source** (`SLUICE-E-CDC-BINLOG-DB-FILTERED`; affects v0.132.0 through v0.148.0). The door compared filter entries to synced database names case-insensitively on every server, and its own comment argued the fold erred in the silent-loss direction's favour — true of the ignore arm, inverted on the do arm. On the Linux default (`lower_case_table_names=0`) the server compares byte-exactly, so `--binlog-do-db=T` with database `t` passed the door while the server logged nothing for `t`: the cold copy completed, the stream entered CDC and heartbeated green, and every later write stayed on the source at exit 0 (observed end to end on real `mysql:8.0.46`). The comparison is now the server's own rule (`binlogFilterCaseRule`), read at preflight only when a filter is present, and measured per engine on real servers: MySQL follows `lower_case_table_names`; MariaDB compares the entry as typed against the stored name at every setting, so a mixed-case MariaDB entry matches nothing. One function serves both arms so they cannot disagree about one server; the refusal names the rule it compared under; the ignore arm names the synced database as sluice spells it; and the same change stops the door over-refusing a case-mismatched `--binlog-ignore-db` that a case-sensitive server does not apply. The startup-grace WARN's hint now names binlog filters. Pinned at both levels — `TestBinlogFilterCaseRule_MeasuredMatrix` and `TestPreflightBinlogDBFilter` on the rule, `TestCDCReader_BinlogDBFilterPreflight_CaseRule_MySQL` and `TestMariaDB_CDCReader_BinlogDBFilterPreflight_CaseRule` on real servers, where every cell derives its expected value from `SHOW BINLOG EVENTS` after a probe INSERT rather than from the rule table. MariaDB at `lower_case_table_names=2` is written as an unverified premise in the file comment; no Linux container can measure it.

**A MySQL source DSN whose database is spelled in a different case than the server stores no longer produces an empty CDC tail on a folding server** (`lower_case_table_names` ≠ 0, the Windows/macOS default; affects every release since the MySQL CDC reader first shipped, v0.1.0 through v0.148.0). The server resolves `/SOURCE_DB` to the stored `source_db` for every query, so the cold copy completed normally, while every binlog event carried the stored lowercase name and the reader's single-database scope (`databaseInScope`) compared it byte-exactly against the DSN's spelling: zero changes delivered, heartbeat green, exit 0. Measured before it was changed: a reader opened on the uppercase DSN emitted zero inserts for the same write the lowercase-DSN reader emitted. The reader now reads the server's fold setting at stream open (`foldScopeNames`, loud on failure like the preflights beside it) and compares the way the server does; the truncate and statement-DML arms reach the same compare. The multi-database and `--include-table` predicates are deliberately unfolded — their selected sets are computed from the catalog listing, so they only ever hold stored spellings — and the VStream lane filters server-side and has no client compare. Pinned at the reader (`TestDatabaseInScope_FollowsTheServersFold`, `TestCDCReader_ScopeFollowsTheServersFold` on a real folding server) and end to end (`TestStreamer_MySQLFoldingSource_UppercaseDSNDeliversPostCopyWrites`, where the target's row count is the expected value).

**Docs:** the `cdc-streaming.md` claim that `CREATE_REPLICATION_SLOT` waits on prepared transactions anywhere on the cluster is now measured rather than reasoned (PG 16: a prepared transaction stranded in another database blocked slot creation past 40 s; rolling it back let the identical creation finish in 123 ms), with one operational detail from the same run — an interrupted slot creation leaves an inactive slot behind, already pinning WAL.

## Compatibility

No breaking changes; drop-in. No flag added, renamed or removed; no schema, position, manifest or backup format change (backup format stays at 10). The LIKE escape character used by the migrate-state lister changed from `\` to `#` — this is internal to one read statement and affects no stored data. The binlog-filter door reads two more server variables at preflight, only when a `--binlog-do-db` / `--binlog-ignore-db` filter is present; the MySQL CDC reader reads `lower_case_table_names` once at stream open, and a failure there is loud rather than a silent fallback. Engines touched: `postgres-trigger` (DDL tier), the MySQL engine and its flavors as CDC sources (binlog lane; the VStream lane is untouched), and MySQL/PostgreSQL as `sync` targets (the status lister). SQLite, D1, the trigger-CDC SQLite engines and plain `migrate` are unaffected. `sync status --format json` is shape-identical to v0.148.0.

## Who needs this — action required

**`postgres-trigger` operators with capture triggers on partitions or INHERITS children, on v0.140.0–v0.148.0.** Upgrading the binary is not enough: the DDL predicate is the body of `sluice_capture_ddl` installed on the source, so re-run `sluice trigger setup` with the same `--tables` to install the fixed definition; until you do, an install with recorded provenance gets the `STALE-CAPTURE-FUNCTION` WARN at every open. Then audit: any `ALTER TABLE` issued against a parent during that window was never recorded and the stream did not halt, so compare each captured child's current source definition and values against the target, and re-copy any table the DDL rewrote. A stream that halted loudly on parent DDL before v0.140.0, or one where all DDL was issued against the children directly, is not affected.

**MySQL / MariaDB CDC sources started with `--binlog-do-db`, v0.132.0–v0.148.0.** If the filter entry's case differs from the synced database's name on a byte-exact server (`lower_case_table_names=0`, the Linux default — or MariaDB at any setting with a mixed-case entry), every post-copy write was left on the source at exit 0. Re-verify the target's row counts against the source; a divergent target needs a fresh start, because writes made while the filter excluded the database are not in the binlog. After upgrading, the door refuses at `sync start` with the rule it compared under.

**MySQL CDC sources on a folding server (`lower_case_table_names` ≠ 0) whose DSN spelled the database in a different case, any release through v0.148.0.** Same shape: complete cold copy, empty tail, green heartbeat. Check whether the target ever advanced past the snapshot; if not, re-verify counts and re-run. Sources on the Linux default, or with the DSN spelled as stored, were never affected.

**Anyone who ran `sync status` or `sync health` against a MySQL-family target on v0.148.0**, or a `sync start` whose target had never run `migrate`: nothing to re-verify — no data path was touched — upgrade and the feature works where the section above says it does. If a cold start **finished** under v0.148.0 on a target where the progress tables existed, its row was never marked complete and `sync status` will keep listing it under "cold start in progress" with its last live phase; delete that row from `sluice_migrate_state` (`migration_id = 'sync-<stream-id>'`) to clear it.

**Operators counting on the cold-start block for a MySQL, MariaDB, PlanetScale or Vitess source:** it does not appear there yet (A0909-P2b); the `FLOAT-EXACT-REREAD` and per-table copy log lines remain the signal.
