# sluice v0.120.2

**Fix — `restore` with a table filter now works on chains that carry incrementals (Bug 244).** `restore --exclude-table`/`--include-table` on any backup chain with an incremental died mid-restore with `table X has no columns (does it exist?)`: the base full honoured the filter, but the chain's post-full walk consulted it nowhere, so an excluded table's change events and schema deltas were replayed against a table the filter deliberately never created. Loud in every affected release — v0.17.0 through v0.120.1 — and it broke v0.120.1's own documented `--exclude-table` salvage for malformed-schema chains the moment the chain carried an incremental. Also here, the two follow-ups filed by the v0.120.1 cycle: `backup compact` and `backup prune` now WARN over a chain whose recorded schema cannot restore (they were the last doors still silent), and the infix `REGEXP`/`RLIKE` refusal message now describes the operator the way the operator wrote it and names its MariaDB catalog provenance. Drop-in upgrade: no flag, default, error code, or on-disk format changed.

## Fixed

**Chain restore's post-full walk now honours `--exclude-table`/`--include-table`, so a filtered restore of a chain carrying incrementals completes instead of dying mid-restore (Bug 244).** The base full's restore has always received the filter, but everything after it did not: an excluded table's Insert/Update/Delete/Truncate events reached the change applier, which died loudly against the table the filter deliberately never created (`table X has no columns (does it exist?)`); an `AlterTable` schema delta on an excluded table died the same way; an `AddTable` delta RESURRECTED a table the operator excluded; and the sequence re-prime tail — create-if-missing by design — resurrected sequences owned by excluded tables. All four doors are now filter-aware, enumerated fixed-or-exempt in the commit, keyed on the same table-name space the base full's filter matches so the doors cannot disagree about what "excluded" means. Excluded events and deltas are skipped at the producer with INFO-logged counts; transaction boundaries pass (an emptied transaction is a harmless begin/commit pair); the schema-history stream is deliberately unfiltered because it writes only sluice's own CDC stream-state table, never user tables. One subtlety the pin proved by mutation: the skip runs AFTER the tail-truncation backstop's bookkeeping, because that backstop grades the recorded chunk stream — the window's end-position-bearing tail change may itself belong to a filtered table, and skipping it first would turn a legitimate filtered restore into a false `SLUICE-E-BACKUP-INCOMPLETE`. Consequence of fixing this: v0.120.1's Bug 243 delta door is now filter-aware BY CONSTRUCTION — its documented "unconditional because deltas apply unfiltered" premise is superseded, and `restore --exclude-table=<affected>` releases the delta door exactly as it releases the restore door, so the Bug 243 salvage now works on full+incremental chains, which is precisely how the v0.120.1 regression cycle found this bug. One behavioural note: when the filter drops an incremental's tail changes, the applier's durable position can end short of the manifest's EndPosition; chain replay is idempotent (the applier path upserts, per ADR-0010), so a subsequent resume re-applies rather than loses. One derived sibling deliberately NOT fixed and filed in `docs/dev/audit-backlog.md`: the unrepresentable-target-shape emit preflights are filter-blind on both restore paths — loud, one phase earlier, same salvage-defeating shape. **Affected releases: chain restore shipped with the filter field in v0.17.0 (`d48769dc`) and the post-full walk has never consulted it — v0.17.0 through v0.120.1, byte-identical measured on v0.119.0 and v0.120.0, loud in every one; general to every filtered chain restore, not specific to malformed-schema salvage.** Pinned container-free through the real methods, including a sealed-set roster over all seven change variants × filter shapes; all four arms mutation-run in both directions with grep-verified mutants, and the pre-tag value-fidelity pass added the one remaining matrix cell — a genuinely truncated chain still refuses with the filter active, mutation-proved against the forge-the-position regression (catalog Bug 244, fixture `chainD`).

**`backup compact` and `backup prune` now WARN when the chain's restorable window carries a recorded schema that cannot restore — closing the last silent-maintenance doors of the Bug 243 class.** Both are chain-rewriting operations that exited 0 in silence over a chain `verify` and `restore` refuse: as of v0.120.1, restore and verify refused, `backup incremental` WARNed, and the two maintenance doors said nothing. One shared helper now scans every RESTORABLE segment's full and incremental manifests and WARNs once — naming `SLUICE-E-BACKUP-RECORDED-SCHEMA-MALFORMED`, the first offending field, and the fresh-`backup full` remedy. Deliberately a WARN and not a refusal: the maintenance operation's own work is valid, and restore/verify hold the refusal. Coverage is stated at the helper per the gate rule: retired segments sit outside the restore path and are unscanned, and a manifest the scan cannot read is skipped — the skip suppresses at most this advisory, never a refusal, because an unreadable manifest is refused loudly by restore/verify, which hold the real gate. **Affected releases: `backup prune` has been silent over this class since it shipped in v0.50.0 (`fb998774`) and `backup compact` since v0.77.0 (`845fa7e7`), through v0.120.1 — the silence only matters for chains recorded by a pre-v0.120.0 MySQL-family reader carrying the Bug 243 mangle class.** Pinned through the real `CompactChain`/`PruneChain` (removing either call site fails the wiring pin), mutation-run both, plus helper-level coverage pins for the incremental-delta arm and the retired-segment boundary.

**The infix `REGEXP`/`RLIKE` refusal now says what the operator wrote — "the infix REGEXP operator" instead of the call-form "REGEXP()" — and names the MariaDB catalog provenance.** v0.120.1's Bug 242 fix caught the operator spellings but rendered them through the call-form template, and its note never named the MariaDB provenance — which is how the v0.120.1 release notes came to claim provenance-naming that the rendered message lacked (that claim was corrected in place, dated, on 2026-08-11; this change is the code half that makes it true going forward). The gap record now carries an infix marker threaded from the pattern registry, the refusal renders "the infix REGEXP operator has no PostgreSQL equivalent", and both infix notes name the MariaDB catalog spelling while keeping the `x ~ 'pattern'` remedy and the ICU-vs-POSIX regex-flavour caveat. **Affected releases: v0.120.1 only — the infix arm shipped there — and the delta is message content, not code, exit status, or reach.** Pinned by `TestRefuseOnLoudGaps_InfixRegexpRendering`, which asserts the message operators actually see — the curated gate that shadows the backstop for these spellings — including the MariaDB naming and the refusal of call-parens; mutation-run in both directions.

## Compatibility

No breaking changes. No flag was added, renamed or removed; no default changed; no error code was added, removed, or changed meaning; no on-disk format — backup chunks, chain manifests, resume state, the schema wire — changed shape. This is a drop-in upgrade from v0.120.1 and anything older. Three behaviour notes:

- **`restore` with a table filter on a chain carrying incrementals now completes where it previously died mid-restore.** Excluded tables' change events and schema deltas are skipped, with INFO-logged counts. If the filter drops an incremental's tail changes, the applier's durable position can end short of the manifest's EndPosition — chain replay is idempotent, so a resume re-applies rather than loses.
- **`backup compact` and `backup prune` on a chain whose recorded schema cannot restore now emit one WARN naming `SLUICE-E-BACKUP-RECORDED-SCHEMA-MALFORMED` where they were previously silent.** Both operations still succeed — their own work is valid — and the chain still will not restore until a fresh `backup full` re-records it.
- **The MySQL→PostgreSQL infix-`REGEXP`/`RLIKE` refusal message wording changed** — it now reads "the infix REGEXP operator" and names the MariaDB catalog provenance. Content only; the refusal fires at the same point with the same exit status.

## Who needs this — action required

- **Anyone whose filtered chain restore died with `table X has no columns (does it exist?)` — including anyone who tried v0.120.1's `restore --exclude-table` salvage on a full+incremental chain and hit that crash: upgrade and re-run the restore.** The old failure was loud and lost nothing on the source or the chain; the same command now completes, and the salvage works as documented.
- **Operators running `backup compact` or `backup prune` against chains recorded from a MySQL or MariaDB source before v0.120.0: watch for the new WARN.** A warned chain cannot restore until a fresh `backup full` re-records it — the same v0.120.1 guidance, now surfaced at the maintenance doors instead of only at verify/restore.
- **Everyone else: nothing to do.** The rendering change is cosmetic and the restore fix only changes runs that previously crashed.
