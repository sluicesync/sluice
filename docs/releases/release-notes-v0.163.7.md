# sluice v0.163.7

<!-- notes-claims-exempt: VSTREAM-ADD-TABLE-KEYSPACE-WIDE-COPY BACKUP-SNAPSHOT-OPEN-ERROR-FALLS-BACK -->
<!-- Both are OPEN filings in docs/dev/audit-backlog.md, outside the gate evidence scope; this release does not fix them and names them so operators can follow them. -->

**HIGH fixes, silent: two ways a PlanetScale/Vitess cold start's copy left rows on the target that the source had deleted or filtered out, at exit 0.** `vstream_copy_single_stream=true` with more than one table in the copy scope is now refused before anything is written (`VSTREAM-SINGLE-STREAM-MULTI-TABLE`), and `--slot-name` on a `planetscale` or `vitess` source no longer turns the copy into one unscoped, unfiltered keyspace-wide stream (`VSTREAM-SLOT-NAME-UNSCOPED-COPY`). The two ship together because they are one defect reached two ways: the first fix's remedy (remove the parameter) still left a `--slot-name` stream on the keyspace-wide single stream that loses the same deletes. No backup format change. Not drop-in for a multi-table `vstream_copy_single_stream=true` cold start, which now refuses (see Compatibility).

## Fixed

- **`vstream_copy_single_stream=true` is refused when more than one table is in the copy scope (`VSTREAM-SINGLE-STREAM-CATCHUP-DELETE-DROPPED`, HIGH, silent; marker `VSTREAM-SINGLE-STREAM-MULTI-TABLE`).** The parameter copies every table in one VStream instead of one per table (ADR-0095's opt-out). One VStream copying several tables does not stay at one snapshot: before each table after the first, vttablet replays the changes made to the tables it has already copied, as row events inside the copy phase. sluice's copy keeps only the after images of that replay and the change stream starts after it, so a row deleted from an already-copied table while a later table was copying stayed on the target. No fault is needed. Measured on a local vttestserver (`vitess/vttestserver:mysql80`): 60 of 60 such deletes stayed, updates were exact, and the default per-table copy was exact under the same changes. The refusal (`refuseSingleStreamMultiTable`, sentinel `ErrVStreamSingleStreamMultiTable`) fires only for a VStream flavor, the exact value `true`, and more than one listed table. It is raised at the VStream snapshot door before the dial, and earlier through the new `PreflightSnapshotScope` check: `sync start` refuses after reading the source schema and before it writes to the stream's tables, clears its apply marks or saves a position. That covers a first cold start, `--restart-from-scratch`, `--reset-target-data` and the automatic re-snapshot. A cold-start `--dry-run` refuses the same scope, and `backup full` refuses before its snapshot opens instead of falling back to its non-snapshot copy. The cold start now clears its apply marks after the source read rather than before it, so an established stream refused this way keeps its marks and warm-resumes as it was. The refusal is not retriable, and a `sync run` leg that hits it is not restarted. A one-table scope keeps the parameter, since there is no later table to catch up before. The resume refusals that used to advise setting the parameter now name `--restart-from-scratch`. Pinned by `TestCheckSnapshotScope_SingleStreamMultiTable` (scope size × parameter spelling × all four MySQL-family flavors), `TestColdStart_SingleStreamMultiTable_RefusesBeforeAnyWrite`, `TestDryRun_SingleStreamMultiTable_Refuses`, `TestBackup_SingleStreamMultiTable_RefusesBeforeTheSnapshot`, and the vttestserver cells in `TestStreamer_VStreamCopyReconnectStaleRows`. Those cells require the refusal with the target and position untouched, including the cell that measured the loss, and then require the remedy (the parameter removed) to land exact under the same in-copy changes on one and two shards. Mutations that disabled the refusal, refused a single table, ignored the parameter or the flavor, removed the cold-start, dry-run or backup check, or moved the mark clear back each turned a pin red with its own assertion.
- **`--slot-name` on a PlanetScale/Vitess `sync start` keeps the copy scoped to `--include-table` and `--where` (`VSTREAM-SLOT-NAME-UNSCOPED-COPY`, HIGH, silent).** VStream has no replication slot and the flag was documented as ignored. But `openSnapshotStreamScoped` checked for a slot name before the table scope and, on a source without a slot-aware open, returned the open with no table list. On VStream that is one stream over the whole keyspace. The copy streamed every table regardless of `--include-table` (tables outside the scope were not created on the target). It skipped the `--where` push-down, and the post-open filter is a no-op on VStream, so rows outside the filter were copied. It also lost deletes made during the copy through the multi-table catch-up above. That last harm needed only more than one table in the keyspace, not in the scope. Measured with the fix reverted on a local vttestserver (`vitess/vttestserver@sha256:02ac88d0af259656b8152cda60b5bf262a2b7a46cc51871c817a7f3facaafec1`, Postgres 16 target). The setup was two tables under `id > 100`, an out-of-scope table copied after them, and deletes and updates during the copy. The result was 100 rows outside the filter on each table and 20 of 20 in-copy deletes kept on the first table, at exit 0. With the fix both tables matched the filtered source exactly. The slot branch is now taken only when the engine implements the slot-aware open, which only Postgres does. Every other source ignores the name and takes the same open it takes without the flag. Only the MySQL engine has a table-scoped open, so the change reaches MySQL-family sources only; SQLite/D1 and trigger-CDC sources took the same open either way. The `--slot-name` help now says what MySQL/MariaDB and PlanetScale/Vitess do with the flag instead of "silently ignores". Pinned by `TestOpenSnapshotStreamScoped_SlotNameOnASlotlessSourceKeepsTheScope` (slot unset/set × no filter/filter, never the no-table open), the existing `TestOpenSnapshotStreamScoped` slot cases, and `TestStreamer_VStreamSlotNameKeepsTheCopyScope`. That cell asserts the per-table copy opened over exactly the two in-scope tables and that both land exact. Restoring the old early return turned the unit pin and the vttestserver cell red, the latter with 100 rows outside the filter on each table. In that mutation run the in-copy delete arm did not reproduce (0 kept, against 20 of 20 in the first run), so the delete loss on the old path depends on timing; the scope and `--where` leaks do not.

## Not closed, stated

- **`schema add-table` from a PlanetScale/Vitess source still opens a keyspace-wide copy (`VSTREAM-ADD-TABLE-KEYSPACE-WIDE-COPY`, OPEN, not measured).** Its open never reads `vstream_copy_single_stream` or `--slot-name`, so neither fix changes it. The open is itself a multi-table single stream, so a delete on the new table during its copy may meet the catch-up drop above. It is filed and will be fixed in a release of its own.
- **`backup full` falls back to its non-snapshot copy, with a WARN and exit 0, on any other snapshot-open error (`BACKUP-SNAPSHOT-OPEN-ERROR-FALLS-BACK`, OPEN, MEDIUM).** Examples are a dial failure, a buffer-cap refusal or a bad `vstream_*` value. This release closes that fallback only for the single-stream refusal, by checking the scope before the open.
- **Not run for this release: `psverify` and `d1verify`.** Every measurement was on a local vttestserver, not on PlanetScale itself. The check-and-re-copy procedure under "Who needs this" was not itself measured against either defect.

## Compatibility

- **Not drop-in for one configuration:** a PlanetScale/Vitess cold start, cold-start `--dry-run` or `backup full` with `vstream_copy_single_stream=true` and more than one table in the copy scope now exits 1 (codeless, `VSTREAM-SINGLE-STREAM-MULTI-TABLE`) instead of copying. Remove the parameter from the source DSN and re-run the same command. For a `sync run` leg, edit the leg's source DSN and reload. The scope that counts is the one after `--include-table`, `--exclude-table` and the default exclusions. An established stream with a saved position still warm-resumes with the parameter set; the refusal comes at its next cold start.
- **`--slot-name` on a `planetscale` or `vitess` source now does nothing,** as documented. A cold start that used to stream the whole keyspace now copies only the in-scope tables, filtered by `--where`.
- **Behaviour change for a MySQL binlog source with `--slot-name`:** its cold start now gets ADR-0101's concurrent cold-copy readers, which it got without the flag and lost with it. This is not a fix for data loss. Its `--where` was applied after the open, so it filtered correctly before this release too.
- **Postgres keeps its slot-aware open unchanged.** SQLite/D1 and trigger-CDC sources are unaffected. `migrate` never used either path. No flag added or removed, and `BackupFormatVersion` stays 15.

## Who needs this — action required

- **Anyone who cold-started a PlanetScale/Vitess stream, or ran `backup full`, over more than one table with `vstream_copy_single_stream=true` on v0.99.63 through v0.163.6.** The parameter arrived with the per-table copy in v0.99.63 (ADR-0095, commit `b3357220`). Rows the source deleted during the copy may still be on the target, or missing from the backup's deletes. The same applies to every multi-table PlanetScale/Vitess cold start before v0.99.63, when the single stream was the default (not measured). To check a stream, let it catch up, pause writes on the source, and run `sluice verify --depth count` against the same source and target, passing the stream's own `--where` values (without them every filtered table mismatches by design). A table with more rows on the target than on the source kept rows it should not have. To repair, re-copy without the parameter using `--restart-from-scratch`. Under `--schema-already-applied` it refuses while the tables hold rows (`RESTART-FROM-SCRATCH-TARGET-NOT-CLEARED`): empty them yourself, for example with `TRUNCATE`, then re-run. Re-take a backup taken that way, without the parameter.
- **Anyone who cold-started a PlanetScale/Vitess `sync start` with `--slot-name` (or a fleet leg with `slot-name`) on v0.99.12 through v0.163.6.** v0.99.12 (commit `71a9245b`) is when the copy began honoring `--include-table` and the slot branch began skipping it; before that every VStream copy was keyspace-wide. Since v0.99.278 (commit `9d89cd7c`, the `--where` push-down) a `--where` on such a stream was also not applied to the copy, so rows outside the filter may be on the target. Deletes made during the copy may have been kept whenever the keyspace held more than one table, even with a one-table `--include-table`. A table under a `--where` is the likeliest to be affected. Check and repair exactly as above: `sluice verify --depth count` with the stream's `--where` values, then `--restart-from-scratch` (emptying the tables yourself first under `--schema-already-applied`). Do not pass `--slot-name` to a PlanetScale/Vitess source; it has no meaning there.
- **A MySQL binlog source with `--slot-name`:** nothing to do. Its data was correct; its cold copy is now faster.
- **Everyone else:** nothing to do.
