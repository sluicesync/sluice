# sluice v0.144.0

**`backup full --redact` produced a PII-clean archive, and every incremental taken on top of it restored plaintext.** Only `backup full` redacts. `backup incremental` and `backup stream run` have no `--redact` flag and apply none — their change events come off the source's CDC pump verbatim — so a redacted full extended with incrementals restored unredacted PII for every row touched after the snapshot, at exit 0, while the `--redact` help text promised the restored shape would match. This release records the redaction in the manifest and refuses every operation that would mix postures.

**If you have ever run `backup full --redact` and taken an incremental or a `backup stream` against that chain, treat the restored data as holding plaintext PII for every row the change window touched, and re-take the chain.** Chains written before v0.144.0 carry no marker, so nothing can detect the mix retroactively.

## Fixed

**A redacted backup chain can no longer be extended with plaintext.** `backup full --redact` applies redaction at chunk-write time, so the archive it writes is clean; the incremental and stream paths never learned to. The full's manifest now records a redaction marker — a rule count plus a fingerprint of the policy, never the rules or the columns themselves — and every door that could change or hide the chain's posture refuses on it: `backup incremental` and `backup stream` refuse to extend it, a resumed `backup full` refuses under different `--redact` rules, and `restore`, chain restore, `backup verify`, `export-as-parquet` and the from-backup broker refuse a chain whose links disagree. Reproduced and closed on real Postgres, old binary against new: the v0.143.0 binary restores the fifth row as `erin-SECRET@example.com` in plaintext; v0.144.0 refuses before the change window opens.

**`backup compact` could launder a mixed chain into one that looks clean.** Found while grinding the sibling list rather than reading the fix: the first sweep enumerated the write doors and the read doors and missed the door that *rewrites*. Compaction merges a group of segments by byte-copying the oldest segment's full manifest into the merged segment and folding every later link's changes on top, so the manifest is re-attributed to data it did not originally cover. Compact a chain an older binary had already mixed and the result is a segment claiming to be redacted over plaintext chunks — at which point the read door sees links that all agree and passes it. Compaction turned a chain that restore correctly refuses into one it accepts. It now refuses a chain carrying the marker at all, which costs nothing because a redacted chain is a series of fulls with no incrementals to collapse. `backup prune` is deliberately exempt, with the reason recorded at the gate: it deletes whole segments and never re-attributes a manifest.

**`sync start --position-from-manifest` resumed CDC off a redacted chain and wrote plaintext to a live target.** This was the one redaction-posture door in the product reaching no guard, and its harm is worse than the archive bug above. The flag's own help names the workflow: `restore --from=<chain>` to seed a target, then resume CDC from the chain's tail without re-bulking. Off a redacted chain the restore lands hashed values correctly, and then every replicated `UPDATE` overwrote the hashed value with the plaintext one — on a live downstream database, at exit 0, with nothing reported. The function that loads the position built the whole lineage and read the terminal manifest, so it *held* the marker and returned only the position; it now returns both, and a mismatch between the chain's policy and the sync's refuses before the stream opens. The check is agreement in both directions — a redacting sync resumed off an unredacted chain refuses too, because redacting only the tail leaves a target nobody can audit.

**Every entry point that emits rows now runs the source-shape preflights.** `PreflightRLS`, `PreflightPartitionedTables` and `PreflightInheritanceTables` ran on `migrate` and single-stream `sync` cold start and nowhere else. RLS is the one that bites: a table with row-level security enabled, read by a role without `BYPASSRLS`, returns only the rows the policy admits — so a `backup full` writes an archive that is silently short, and every restore taken from it inherits the loss with nothing recording why. They now also run on `backup full`, `schema add-table` and the multi-database fan-out. Widening the roster that enforces this found a fourth gap on its own: the roster matched a lowercase symbol prefix, and the preflights had just been exported, so it would have gone green having silently stopped collecting all three — fixing the matcher immediately surfaced `PreflightTableReads`, an already-exported preflight the fan-out never ran and no gate had ever looked for.

**The Cloudflare D1 change-log poll no longer trusts what D1 delivers.** D1 stores invalid UTF-8 verbatim but rewrites it to U+FFFD server-side in its HTTP response, so by the time sluice's existing guard sees the payload it is valid UTF-8 and structurally cannot fire. The poll now brackets each captured image against the byte length D1 reports for the *stored* value — and, since that check has a blind spot, against the stored count of replacement characters too. D1 substitutes one U+FFFD per maximal invalid subpart, and a subpart of exactly three bytes rewrites to a three-byte replacement with the length unchanged; a four-byte emoji severed at a byte boundary is exactly that shape. Between the two numbers no rewrite passes. A value that legitimately contains U+FFFD still does.

## Compatibility

**Backup format version 9 → 10, and this bump is load-bearing rather than tidy.** A manifest written by `backup full --redact` is stamped version 10, so a pre-v0.144.0 binary refuses it outright instead of ignoring the unknown marker and cheerfully extending the chain. A backup taken *without* `--redact` records no marker and keeps the version it always had, so unredacted chains are byte-identical to what v0.143.0 wrote and remain readable by older binaries. Verified with a real two-binary run: v0.143.0 writes a chain, v0.144.0 verifies, restores and extends it.

**New refusals can fire on configurations that previously exited 0.** `backup full` now refuses on Postgres sources with declaratively-partitioned or `INHERITS` tables in scope, and on RLS-enabled tables read by a role without `BYPASSRLS`. Those are correct — they are the checks `migrate` and `sync` have always run — but if you have a permissive `USING (true)` policy on a table you back up, this will surprise you. `--exclude-table` is the documented route. Likewise `backup compact` refuses on a redacted chain, and `sync start --position-from-manifest` refuses when its `--redact` rules do not match the chain's.

**Chains taken before v0.144.0 carry no redaction marker.** Nothing can detect a pre-existing mix retroactively: a pre-v0.144.0 chain rooted in a redacted full still restores its incrementals' rows unredacted, silently. There is no way around this from inside the tool — re-take those chains.

Error code `SLUICE-E-BACKUP-REDACTED-CHAIN` is new. No CLI flag was added, renamed or removed.

## Who needs this

- **Anyone who has run `backup full --redact`** — read the second paragraph above before anything else.
- **Anyone running `backup full` against a Postgres source with RLS**, especially under a role without `BYPASSRLS`, where the archive may already be short.
- **Anyone using `sync start --position-from-manifest`** after restoring from a redacted chain.
- **Cloudflare D1 trigger-CDC users** whose source may hold invalid UTF-8 or truncated multi-byte text.

## Development notes

Two things about how this release was built are worth recording, because both are recurring shapes rather than one-offs.

**The pre-tag value-fidelity review found a HIGH in the release's own new code for the sixth consecutive release.** It was the `--position-from-manifest` door above — the fix for a PII leak having shipped with a second, worse instance of the same leak still open one function away. The review derives the door matrix itself rather than reading the commit message, which is exactly why it found a door the commit message's own enumeration had missed.

**Four gates caught this release's work, three of them pre-existing.** The doc byte-equality gate refused a door list that said "three doors" when there were four. The manifest-consumer roster noticed that a manifest read had *moved* out of the function its exemption named, into a helper extracted to satisfy a complexity limit — the third instance in one session of a gate going red because guarded calls were extracted, which is the failure mode the cold-start roster was written to document. And the release's own new compaction gate caught two of its author's errors: an assertion grepping the wrong string for a remedy, and an ordering anchor that matched a doc comment four hundred lines above the call it meant to anchor on. An anti-vacuity anchor guessed from prose is precisely the defect the anchor exists to catch.
