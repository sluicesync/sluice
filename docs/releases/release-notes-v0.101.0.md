# sluice v0.101.0

**Two ways an unattended continuous sync could stop on a routine, recoverable source event — a graceful connection drain and a schema change on the keyspace — are now reconnects instead of exits. Plus Postgres target telemetry that was silently inert: a storage alert that could never fire on PG, and replica lag that was unobserved on *both* engines whenever a branch had more than one replica.** Drop-in upgrade, no breaking changes, no flag changes. Everyone running continuous sync against PlanetScale/Vitess should take this one; anyone relying on `--notify-storage-util` or `--notify-lag-seconds` against a Postgres target was not being alerted and should read the telemetry section.

## Fixed

**A graceful HTTP/2 GOAWAY no longer kills a VStream CDC stream.** A PlanetScale edge pod rotating — routine platform maintenance — sends `GOAWAY` with `ErrCode=NO_ERROR`, HTTP/2's polite "reconnect" signal. grpc-go delivers it wrapped as `codes.InvalidArgument`, because the code describes the envelope-parse failure rather than the operator's request, and sluice's reader classifier treats `InvalidArgument` as terminal — correctly, for a genuinely malformed request. The result was a stream that exited on maintenance and stayed down until a human restarted it. Loud and zero-loss (the position was intact and a warm resume lost nothing), but continuous replication that stops on routine maintenance is not continuous. The drain is now recognised and retried at both call sites it can reach: the VStream reader, and the MySQL applier's Error-1105 path, where Vitess wraps the vtgate→vttablet gRPC status inside a MySQL error and the same drain surfaces on the *apply* side. The check is a conjunction — a GOAWAY **and** a no-error code — never the bare word, because the same frame carrying `PROTOCOL_ERROR` or `ENHANCE_YOUR_CALM` means the peer is rejecting how we speak to it and must stay terminal. It lives in one shared matcher so the two sites cannot drift on what "graceful" means.

**A schema change on the keyspace no longer kills the stream either.** With a keyspace-wide sync running — the default shape, since `--include-table` is opt-in — a `CREATE TABLE` on *any* table could exit the stream with `row event for … without preceding FIELD event`, and the error would name a **different, long-established table** than the one the DDL touched. The mechanism: after a DDL, sluice invalidates its column-shape cache with a blanket clear across every table, which is deliberately conservative because decoding rows against a stale column list after an `ALTER` is silent corruption — but vtgate only re-announces the table whose shape actually changed, so the next row on any *other* table found an empty cache and hit a hard floor. That floor is now a reconnect: nothing decodes with guessed or stale metadata, and re-opening the stream at the last position re-learns every table's current shape, because the protocol emits a field event ahead of the first row event per table. A field announcement that genuinely never arrives still fails loudly rather than looping.

**Postgres storage alerts could never fire, and replica lag was unobserved on both engines.** sluice picks the write-target's series out of a per-pod metric fan using a selection cascade. Postgres emits its per-*pod* metrics — the volume pair — with no `tablet_type` and no `container` label, carrying only `planetscale_role`, which nothing in the cascade read. So a three-pod Postgres branch fell through every tier to the refuse-to-guess arm: honest (no wrong number was ever reported) but silent, and `--notify-storage-util` was permanently inert on Postgres. `planetscale_role` is now a recognised selector. Replica lag was worse than engine-specific: **neither** surface emits a primary lag series — because a primary has no replication lag — so primary-selection found nothing and refused on any branch with two or more replicas, leaving `--notify-lag-seconds` inert on Postgres *and* Vitess. Lag now reduces by worst-replica, which is both the semantically right answer for an alert and a no-op where lag already resolved. Postgres connection metrics are wired for the first time, and two code comments asserting these series did not exist are corrected — they do; the probe behind them had gone stale.

**A new worst-pod storage signal, separate from the primary's.** On live PlanetScale Postgres the replicas run consistently fuller than the primary, so an alert watching only the primary is blind to the pod that reaches its ceiling first. `sluice_target_storage_util_worst` and its two companions describe the fullest pod of the branch and are never folded into the existing primary figures — the storage *alert* now reads the worst pod, while write-rate adaptivity deliberately stays on the primary, since that is the volume sluice's own writes land on. Keeping them separate also preserves the meaning of already-persisted metrics history. The reduction joins available and capacity **per pod** rather than minimising and maximising independently, which would pair a small pod's free bytes with a large pod's capacity and manufacture a utilisation no pod has.

**Postgres internal partition foreign-key clones are now excluded from schema reads.** Unreachable today — partitioned Postgres sources are refused up front — so this is insurance for when partition support ships, and it is version-gated: `conparentid` exists only on PG 11+, while this query runs against every Postgres source, so an unconditional reference would have failed the entire foreign-key read on a PG 10 server.

## Features

**A WARN when the change stream cannot carry a column DEFAULT.** Forwarding an `ADD COLUMN … DEFAULT` mid-sync lands the column on the target *without* the default whenever the CDC projection cannot report one — the vtgate field event never carries a default, and Postgres's relation message does not either. The target's pre-existing rows then hold NULL where the source's hold the default, and no row event ever reconciles them, because adding a column with a default writes no per-row changes. Rows changed afterwards are unaffected, so the divergence is confined to rows that existed at that moment: invisible to a row-count check, visible only to a value-comparing `verify`. sluice now names the table, the column, the source's default, and two remedies. It stays quiet when nothing is lost — a column with no default, or one whose default the projection *did* carry (the MySQL binlog path, which re-reads the catalog) — so it does not become noise on every forwarded `ADD COLUMN`.

## Corrected

**The v0.100.0 managed-Postgres 55006 entry told the wrong causal story.** The five-minute "replication slot is active" retry budget shipped on the stated grounds that PlanetScale-Postgres, having moved to Postgres 18, holds a just-closed reader's walsender active for ten-plus minutes. A controlled measurement afterwards — PG 17.10 versus 18.4 on the same tier, with a harness whose clean close is byte-identical to sluice's own — disproved it: **the two major versions are indistinguishable, and reap latency is governed by disconnect observability, not the version.** A clean graceful close is reaped in under two seconds; an abrupt socket or TCP-FIN close, sub-second; only a truly silent vanish waits the full `wal_sender_timeout`, measured at 60 seconds across every PlanetScale-Postgres tier checked. So a routine stop-and-restart against managed Postgres essentially cannot hit a loud 55006 at default settings — which was the practical question behind the original fix. **The five-minute budget stays**, and the raise from the old fixed ~31.5 seconds was still warranted, but the justification is that 60-second timeout rather than a PG18-specific hold. The one >90-second hold seen in CI and the >12-minute one seen in v0.100.0's own validation run were never reproduced and are both inconsistent with the 60-second ceiling, so neither is the walsender-reap path. No behaviour changed and no user action follows; this is a causal-accuracy correction, not a data or correctness banner.

## Compatibility

No breaking changes, no flag changes, drop-in upgrade. The two CDC fixes only convert previously-fatal conditions into reconnects, so a stream that never met them behaves identically. The telemetry changes are additive: `sluice_target_storage_util` keeps its exact meaning (the primary's), and the three `*_worst` series are new names rather than a relabelling, so existing dashboards and alert rules are unaffected — though operators alerting on Postgres storage or replica lag should note those alerts were previously never firing and will now begin to. The `ADD COLUMN` WARN is advisory and changes no data path or exit code.

## Who needs this — action required

- **Anyone running continuous sync from PlanetScale or Vitess** — both fixes are in this path, and both turn an unattended-stream outage into a reconnect. This is the release to take.
- **Anyone alerting on `--notify-storage-util` against a Postgres target, or `--notify-lag-seconds` against any target with more than one replica** — those alerts were silently inert. They now work. Re-check your thresholds before assuming quiet meant healthy.
- **Operators forwarding `ADD COLUMN … DEFAULT` on a Vitess source** — you will now see a WARN naming rows that need a backfill. The divergence it describes predates this release.
- Everyone else: no action needed beyond upgrading.
