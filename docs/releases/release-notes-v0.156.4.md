# sluice v0.156.4

**CRITICAL fix — backup chains from a `postgres-trigger` source now restore `numeric`, `numeric(p,s)`, `numeric[]` and `jsonb` numbers exactly instead of rounding them through a 64-bit float, and MySQL, MariaDB and PlanetScale/Vitess targets now refuse a DECIMAL value (or literal DEFAULT) past the target column's scale instead of rounding it (HIGH, silent).** Through v0.156.3, chain restore, `sync from-backup` and smart compaction of a `postgres-trigger` chain turned `10.50` into `10.5`, a 20-digit `numeric` into a rounded one and `jsonb` `1e-400` into `0`, at exit 0; and a CDC applier writing a Postgres `numeric` with more than 30 decimal places into MySQL's `DECIMAL(65,30)` stored it rounded, at exit 0. Existing `postgres-trigger` chains restore exactly with this release without being re-taken (except a chain an affected release smart-compacted). This release introduces **backup format version 12** for `postgres-trigger` change segments that carry an exact number, so older binaries refuse such a chain instead of rounding it. **Not a silent drop-in:** a stream that ran on v0.156.3 can now stop on `DECIMAL-SCALE-EXCEEDED` — read **Compatibility**. Upgrading does not repair values an earlier release already wrote; read the repair notice below.

## Repair notice — if you were affected

Upgrading stops the rounding. It does not find or fix values an earlier release already wrote to a target.

1. **MySQL, MariaDB or PlanetScale/Vitess targets fed by the CDC applier from a Postgres source or chain (HIGH, silent).** Covers `sync` (log-based or `postgres-trigger`), chain restore and `sync from-backup` into a MySQL-family target. Any `numeric` value with more fractional digits than the target DECIMAL's scale was stored rounded at exit 0. For an unconstrained Postgres `numeric`, which lands as `DECIMAL(65,30)`, that means more than 30 decimal places (measured: `0.1234567890123456789012345678901` landed as `0.123456789012345678901234567890`, and `-0.99999999999999999999999999999999` as `-1.000000000000000000000000000000`). The same applies to `sync` with a float column retyped by `--type-override` to a DECIMAL narrower than its values. **Repair:** compare those columns against the source and re-copy the affected rows. Separately, a DECIMAL column's literal DEFAULT past the scale was stored rounded on `CREATE TABLE` (`migrate` and a `sync` cold start alike) and on a forwarded `ADD COLUMN`, so every row later inserted on the target without that column took the rounded default. Re-declare such a DEFAULT from the source. The bulk copy (`LOAD DATA` and the batched INSERT path) already refused over-scale values and wrote no rounded row.
2. **`postgres-trigger` backup chains restored or brokered by v0.154.0–v0.156.3 (CRITICAL, silent).** This covers `backup incremental` or `backup stream` chains restored with chain restore or used to seed `sync from-backup` by those releases. v0.154.0 is the first release that could build a trigger chain; earlier releases refused to extend a trigger full. The following values were altered at exit 0 if their source text was not the shortest `float64` rendering of the value:
   - an unconstrained `numeric` value or any number inside a `jsonb` document with a trailing-zero scale, at any digit count (`numeric` `10.50` → `10.5`, `jsonb` `1.500` → `1.5`);
   - such a value with more than about 15 significant digits (`123456789012345678.123456789012` → `123456789012345680`);
   - a magnitude below about `1e-308` (`1e-400` → `0`);
   - a subnormal-range magnitude (`1.234567e-320` → `1.2347e-320`);
   - every `numeric(p,s)` value past 15 significant digits (a scale-constrained column re-pads the trailing zeros, so only the long values changed).

   `numeric[]` elements failed loudly on a Postgres target (measured). Toward a MySQL target they were most likely rounded silently like scalars (from reading v0.156.3's code; not measured), so audit `numeric[]` columns restored to MySQL too. `double precision`, `real`, `NaN` and integers restored with the right value. **Repair:** re-run the restore (or re-seed the `sync from-backup` target) with v0.156.4, then compare those columns against the source. A target restored by an affected release keeps the rounded values until you do. **A chain that an affected release smart-compacted cannot be repaired from the chain.** Compaction decodes and re-encodes the chunk, so the rounded digits are in its bytes. Take a fresh full backup.

## Fixed

**`postgres-trigger` backup chains restore every number exactly (CRITICAL, silent).** The trigger CDC reader hands every non-integer number to its consumers as the exact source text (a `json.Number`), and the backup change-chunk writer always stored that text faithfully. The bug was on the read side: chain restore, the broker and smart compaction decoded every bare JSON number back as a `float64`. The change-chunk reader now keeps each bare number as its exact text when the owning manifest's source engine is `postgres-trigger`. That is the same type the engine's live change stream hands those consumers. Chains from other engines keep the previous decode, because their change streams never produce these values. The fix keys on the chain's source engine, not its format version, so chains written by v0.154.0–v0.156.3 restore exactly with this release and need no rewrite. The exception is a chain an affected release already smart-compacted (see the repair notice). Pinned on real servers through chain restore to Postgres and to MySQL and through `sync from-backup` (`TestBackupChain_PGTrigger_NumericValuesRestoreExactly`, `TestSyncFromBackup_PGTriggerChain_NumericValuesExact`). Also pinned through smart compaction at unit level (`TestSmartCompaction_PGTriggerChunks_KeepNumericDigits`) and by a premise test that the trigger reader produces no floats (`TestNumbersArePreserved_PGTriggerCarriesNoFloats`).

**Backup format version 12 — older binaries refuse a trigger chain instead of rounding it.** The fix did not change any chunk bytes, so an older binary restoring a chain written by this release would round it the same way. This release therefore stamps `FormatVersion` 12 on a `postgres-trigger` incremental or `backup stream` segment, including the ADD COLUMN fill segment it carries, when its change chunks held an exact number. The stamp is proportional:
- Fulls, segments from other source engines, and trigger segments whose changes carried only integers, text and other non-numeric families keep their previous version and stay readable by older binaries. Plain integers of up to 15 digits inside a `jsonb` document count as integers, because a float carries them exactly.
- A segment that touched a `numeric(p,s)` column with a scale is stamped, because the capture carries the scale digits.

v0.156.3 and older now refuse a stamped chain ("newer than this build supports"), so upgrade the binary that restores. Gated by `TestBackup_CrossVersionExactNumbers`, which builds a real v0.156.3 and checks four things: it refuses a stamped chain, still restores an integer-only chain, and silently rounds its own chain, while this release restores both exactly. Also gated by `TestStampExactNumbersOnSeal_StreamAndFillLane`. See `docs/backup-format-versioning.md`.

**MySQL, MariaDB and PlanetScale/Vitess targets: a DECIMAL value or literal DEFAULT past the target scale is refused, not rounded (HIGH, silent; GC-37 (c)).** Past a DECIMAL's fractional digits, MySQL and MariaDB round the value and report only Note 1265, which even strict `sql_mode` accepts. The bulk-copy writers already refused on it, because they fail a strict-mode write with a non-empty warning list. The CDC applier never reads that list, so it stored rounded values at exit 0 on serial and concurrent lanes alike. That path covers `sync`, the added-column backfill, chain restore and `sync from-backup`. sluice now checks every value and every literal DEFAULT before the driver sees them. It checks each value through the one value funnel every MySQL write lane shares, and each DEFAULT through the one emit every `CREATE TABLE` and `ADD COLUMN` shares. An over-scale value refuses with `SLUICE-E-VALUE-UNREPRESENTABLE`, marked `DECIMAL-SCALE-EXCEEDED`, naming the column and the digits lost. The check applies whatever Go type the reader delivered:
- a string, from the Postgres, MySQL/VStream, SQLite/D1, mydumper and flat-file readers;
- a `json.Number`, from the `postgres-trigger` reader (the managed-Postgres lane, reproduced silent end to end before the fix);
- raw bytes;
- a float, from a float column retyped to DECIMAL with `--type-override`.

A pre-existing target column whose name differs from the source's only in case is now typed rather than written with no descriptor, so it gets the check too; MySQL matches column names case-insensitively. Extreme exponents are counted arithmetically, so a pathological literal cannot panic or allocate out of proportion. Trailing zeros past the scale lose nothing and are not refused. NaN, ±Infinity and integer overflow were already refused by the server and are unchanged. `numeric[]` values land in a JSON column as strings and were already exact. Pinned on real MySQL 8.0 and MariaDB 11.4 targets through `migrate`, `sync` (serial and lanes), the DEFAULT arm and the `postgres-trigger` lane, with the source's own `v::text` as the expected value. Remaining: a value for a column the applier's descriptor map does not know at all (a cold cache) is not checked.

**Concurrent CDC apply routes a float or exact-number primary key to one lane in whatever form it arrives (LOW, silent).** The key-hash router built the lane key for a `float64` key and a `json.Number` key from their Go spelling. As a result, the same row could reach two lanes and apply out of order, for example an ADD COLUMN fill and a later update of that row. Two examples: a `double precision` key of `1.5e-7` reads as `1.5e-07` in the fill and as `0.00000015` in the `postgres-trigger` stream; a `numeric` key read as the string `"1.50"` differed from the stream's `json.Number` `1.50`. Both forms now encode as the plain decimal Postgres renders, and an integral float, including a `json.Number` `-0`, shares the integer's encoding. Integers, strings and bytes keep exactly the encoding they had, and the encoding is never persisted. Bound to a real server by `TestLaneKey_FloatKeyFromTheStreamMatchesTheCopyRead`. Pinned by `TestCanonicalKeyValue_OneValueOneEncodingAcrossKinds`, `TestCanonicalKeyValue_SurvivesThePreservedNumberRoundTrip`, `TestCanonicalKey_NegativeZeroNumberIsTheIntegralZero` and `TestPlainDecimal`. Two known residuals remain:
- A `real` key widened to `float64` before routing still splits from the stream's `float4` rendering.
- A `NaN`/`±Infinity` float key still splits between the copy read and the stream's string spelling.

**Error-code docs.** The `SLUICE-E-CDC-SCHEMA-REPLAY-MISMATCH` row now describes v0.156.3's charset-replay case and its backup remedy, in `docs/operator/error-codes.md` and the in-binary registry mirror alike. `SLUICE-E-VALUE-UNREPRESENTABLE` gains the new `DECIMAL-SCALE-EXCEEDED` case.

## Compatibility

**New loud refusals, on purpose — a stream or restore that ran on v0.156.3 can stop on this release:**

- **`DECIMAL-SCALE-EXCEEDED`** (`SLUICE-E-VALUE-UNREPRESENTABLE`) stops the CDC applier on a MySQL-family target when a value has more fractional digits than the target DECIMAL's scale, where v0.156.3 rounded it silently. It also stops `CREATE TABLE` / forwarded `ADD COLUMN` on a DECIMAL literal DEFAULT past the scale. To proceed, widen the target column (for example with `--type-override`) or exclude the table. The bulk copy's behaviour is unchanged, because it was already loud; the refusal now names the column instead of the server warning.
- **A MySQL `FLOAT` (single-precision) source column retyped with `--type-override …=decimal(p,s)`** now refuses in CDC while its cold copy lands (GC-37 (u), filed). The binlog delivers the value as a float32 widened to float64, so `0.1` arrives as `0.10000000149011612`, which is over-scale for `DECIMAL(10,2)`. The cold copy reads the server's own text and lands `0.10`. v0.156.3 landed `0.10` on both paths. This is loud, not silent. It is niche, and a proper fix, carrying the source float width to the decode, is filed.
- **Format version 12:** v0.156.3 and older refuse a `postgres-trigger` chain segment written by v0.156.4 that carried an exact number. Every other chain, including every full and every chain from other engines, stays readable by older binaries. This release reads every older chain. Verified cross-version by `TestBackup_CrossVersionExactNumbers` against a real v0.156.3 build, in the dispatched extended-suites run 36210086066.

**Exempt, stated:** a Postgres target's `numeric(p,s)` also rounds over-scale input without notice. It is reachable only through a narrowing `--type-override` or a pre-existing narrower target column, because sluice's own emit carries the source precision and scale. It is filed as GC-37 (t) and not changed here.

**No flag, default or control-table change.** No new CLI flag was added, and no existing invocation changes shape.

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale, billable cluster) and `d1verify` (live Cloudflare D1) suites were not dispatched; each provisions billable or live infrastructure and runs only on the operator's call. This release's PlanetScale/Vitess reach is the shared MySQL value funnel and DEFAULT emit, and it was not measured against PlanetScale.

## Who needs this — action required

- **Anyone who restored a `postgres-trigger` chain, or seeded `sync from-backup` from one, with v0.154.0–v0.156.3.** Re-run the restore (or re-seed) with v0.156.4 and compare `numeric`, `numeric[]` (on MySQL targets too) and `jsonb` columns against the source. If an affected release smart-compacted the chain, take a fresh full backup instead (repair notice item 2).
- **Anyone running `sync`, chain restore or `sync from-backup` from a Postgres source into a MySQL, MariaDB or PlanetScale/Vitess target where a `numeric` value can exceed the target DECIMAL's scale.** In practice that means more than 30 decimal places in an unconstrained `numeric`, or a float column retyped by `--type-override` to a narrow DECIMAL. Compare those columns against the source and re-copy affected rows; re-declare any DECIMAL DEFAULT taken from such a source (repair notice item 1). Expect `DECIMAL-SCALE-EXCEEDED` on those values from now on.
- **Anyone who restores `postgres-trigger` chains with more than one sluice version.** Upgrade the restoring binary to v0.156.4, because older binaries refuse new stamped segments.
- **Everyone else:** nothing to do beyond upgrading.
