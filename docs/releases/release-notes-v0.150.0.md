# sluice v0.150.0

### Added

**PlanetScale Neki support — sharded Postgres as a migrate and sync target, and as a migrate source.** Neki is PlanetScale's horizontally-sharded PostgreSQL: a router speaking the PostgreSQL wire protocol in front of real PostgreSQL clusters. sluice reaches it with the ordinary `postgres` driver — there is no `neki` engine, no `--target-driver neki`, and nothing to configure. It detects Neki from the server's own `version()` string and adapts the handful of behaviours that differ ([ADR-0186](docs/adr/adr-0186-neki-is-a-postgres-flavor.md)). Measured against live clusters: `migrate` and `sync` into it including CDC insert/update/delete, `migrate --resume`, a live reshard underneath a running stream with no loss or duplication, and `migrate` **out of** it including from a sharded database. Value fidelity is byte-identical across every column family through nine different router read shapes, including two router-level hash joins. Operator reference in [`docs/managed-services.md`](docs/managed-services.md), and a tested step-by-step procedure for moving an existing PlanetScale Postgres database across in [`docs/operator/planetscale-postgres-to-neki.md`](docs/operator/planetscale-postgres-to-neki.md).

**Neki is a migrate source but not a continuous-sync source, and that is a platform limitation rather than missing work.** A Neki replication connection can export a snapshot but nothing can import one — `pg_export_snapshot()` and `SET TRANSACTION SNAPSHOT` are unimplemented on the router — so there is no consistent handoff from the bulk copy to the change stream. `migrate` out works; plan a cutover window rather than a continuous tail.

**Four new refusals for states a sharded target cannot make safe, each replacing a silent outcome.** `SLUICE-E-TARGET-SHARD-KEY-NOT-IN-UPSERT-KEY` refuses a sharded target whose routing columns are not in the key sluice's idempotent write conflicts on — on such a table `ON CONFLICT` is evaluated only on the shard the incoming row routes to, so an upsert inserts a duplicate of the primary key instead of updating, silently. `SLUICE-E-TARGET-SHARD-KEY-UPDATE-UNSUPPORTED` refuses a change that would move a row between shards rather than applying every other column and leaving the routing column behind. `SLUICE-E-TARGET-SHARD-PLACEMENT-MISMATCH` refuses a table whose routing and physical row placement disagree. `SLUICE-E-MIGRATE-PROGRESS-UNRECORDABLE` refuses before a table's first row when the migrate-state store cannot record that the table is being copied.

**An endpoint can now decline the raw-copy passthrough lane at runtime.** Lane eligibility used to be a compile-time question about types; it is now also a question about the server behind a DSN. A Neki source declines, because its router does not implement the `COPY (SELECT …) TO` form the exporter's projection invariant requires — so a Neki source reaches a PostgreSQL target through the IR path instead of failing. Detected from the server version, logged with the reason, no flag involved.

### Fixed

**A table copy sluice could not RECORD silently duplicated the table on the next `--resume`.** The resume classifier reads a missing per-table progress row as "this table was never copied" and starts it fresh **without truncating**, which is sound only while a missing row really does mean never-copied. The in-progress breadcrumb — the one per-table write made before any of the table's rows move — was best-effort, so a run whose store rejected it copied the table anyway, and a later `--resume` copied it a second time. With a primary key the upsert heals; with no primary key there is nothing to conflict on and the rows are appended. Measured on a live sharded target whose control tables refused every INSERT: a 40-row keyless table came out of the resume holding 80. The breadcrumb write is now fatal at all four sites while every later per-table write stays best-effort by design, and a resumed table classified fresh whose target already holds rows is refused (`SLUICE-E-RESUME-FRESH-TABLE-NOT-EMPTY`) rather than copied over.

**`sluice schema diff` and `sluice verify` failed outright on any PostgreSQL database holding a range type.** The verbatim-carry tier for types with no rich cross-engine IR shape — range types, `tsvector`, `tsquery`, uncatalogued user-defined types — reached the five source-read sites and none of the others, so `schema diff` between two ordinary PostgreSQL databases died with `unsupported data_type "int4range"`. The same gap silently degraded `migrate`'s pre-create shape compare **and** its pre-existing-foreign-key check on such a target, which is the quieter half: that refusal exists because a field report died seconds into a cold start on exactly the constraint it detects. Fixed at all four target-read sites and both diff/verify source reads.

**A missing operator-class extension failed with PostgreSQL's words rather than ours.** A schema using `btree_gist` — an `EXCLUDE USING gist (a WITH =, b WITH &&)` constraint, or an index mixing a scalar column into a GiST index — copied to a target without the extension died with `data type integer has no default operator class for access method "gist"`, which names neither the extension nor a remedy. sluice already refused properly when an extension owns a column *type*; an extension-owned *operator class* fell through to the driver. Now refused with the extension named and the exact `CREATE EXTENSION` command.

**Five statements and catalog reads a Neki router refuses, all fixed portably.** Three correlated subqueries in `JOIN … ON` clauses (the column read, the CDC applier's column-type read, and a shard-consolidation probe) blocked schema reads and CDC apply against a sharded database; each is now a plain `LEFT JOIN` that is simpler on every engine. The idempotent `CREATE TYPE` idiom no longer needs a plpgsql `EXCEPTION` handler. Standalone sequences are created and primed without a transaction on Neki, where DDL inside a transaction is invisible to the rest of that transaction. A sequence's position is read from `pg_sequences` when the router refuses to read the sequence as a relation, which unblocked every re-run into a Neki target that already had sequences.

### Compatibility

No flag, default, or on-disk format changed. Every behaviour above is either additive or a new refusal on a state that previously produced a silent wrong result. Targets that are not PlanetScale Neki render byte-identical SQL to v0.149.0 on every path this release touched, and pay nothing for the detection beyond one `SELECT version()` per server.

### Who needs this

Anyone evaluating or running **PlanetScale Neki**. Anyone running `sluice schema diff` or `sluice verify` against a PostgreSQL database with a **range, `tsvector` or `tsquery` column** — those commands failed outright. Anyone whose `migrate` target is a PostgreSQL database holding one of those types, which silently lost two preflight checks. And anyone who has ever seen `per-table state write failed; continuing` in a migrate log: that warning could precede a duplicated keyless table on the next `--resume`.
