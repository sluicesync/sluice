# sluice v0.113.0

**Three silent-loss CRITICALs, a field-reported copy that could not finish, and two behaviour changes that will stop things which previously "succeeded" — read Compatibility before upgrading. No flags were renamed or removed and nothing on disk is repartitioned, but a backup chain whose window carried an `ADD CHECK` or any foreign-key DDL now REFUSES at replay, and a table carrying a non-PK unique index now applies CDC on a single lane.**

This is the largest batch in the project's history: a full-depth audit landed on 2026-08-05 and a production field report arrived the same day, and this release is what came out of both. Most of what follows was found by reading, not by a failing test — which is the recurring shape worth naming, because in nearly every case a green signal was sitting on top of the defect. A concurrent CDC apply that reported success on both lanes while a row vanished. A compacted backup that verified clean and resurrected a deleted row. A cold copy whose every log line read healthy while it spent 81% of its wall clock doing nothing. Two of the changes here will make things fail that used to exit 0; both are the loud half of a silent-loss defect, and both are explained below rather than announced.

This release also carries everything in v0.112.1, which was cut on a release branch. Upgrading from v0.112.0 or v0.112.1 is drop-in.

## Features

**`sluice backup verify --depth read` — the depth that actually parses a row.** `backup verify` has always rehashed each chunk's stored bytes against the SHA-256 the manifest records, and never parsed a row. Its evidence was therefore the same artifact it was checking: it could tell you the bytes had not rotted while saying nothing about whether they could be read back. That is precisely how Bug 226 shipped — `backup full` rc=0, **`backup verify` rc=0**, `restore` rc=1 with 0 rows and `token too long`. v0.112.0 stopped new backups from carrying such a row; artifacts already written were untouched, and the reason they were possible was still live. `--depth read` streams every chunk — data chunks **and** change chunks — through the real `ChunkReader` / `ChangeChunkReader` with the exact (CEK, AAD, codec, segment store) quadruple `restore` resolves, and discards the rows. A byte-intact chunk its own reader cannot decode raises the new `SLUICE-E-BACKUP-CHUNK-UNREADABLE`. `hash` remains the default and is byte-identical to before, so a cron probe against object storage stays cheap; the depth's zero value is `hash`, so only the CLI can turn the cost on.

**What it covers, and what no depth covers — stated in the code and the operator docs rather than implied.** Covered, each verified as passing the hash depth and failing the read depth: an over-long row or change line (Bug 226's shape on artifacts written at or below v0.111.1), a truncated codec stream with a re-stamped SHA, a segment whose recorded codec is not the one its chunks were written with, a value envelope this build's decoder rejects, and — on an encrypted chain with key material — a wrong CEK or AAD. **Not covered by any depth: whether the VALUES are correct.** A parse proves the chunk decodes; it says nothing about fidelity, and no depth of `verify` can ever prove fidelity, because a backup is not independent evidence about itself. That is `sluice verify`'s job (source against target), or a post-restore comparison against the source. Also not covered: whether the rows will APPLY to a target, a change chunk's decoded event count against its recorded `RowCount` (chain restore does not check it either, and verify must never refuse a chain `restore` would accept), and the chunk-header ↔ manifest-schema column pairing, which stays restore-only. Row chunks DO get the count cross-check, from the same predicate `Restore.streamChunkRows` uses — one predicate, two callers, so they cannot drift apart the way the manifest-preflight lists did in Bugs 217/218.

On an encrypted chain the read depth REQUIRES key material and refuses without it, rather than degrading to the hash depth: parsing is the whole of what it does, and reporting every chunk of a healthy chain unreadable because a passphrase was missing would send an operator hunting a corrupt backup that does not exist.

## Fixed

**A chain whose window carried an `ADD CHECK` or any foreign-key DDL restored a target missing that constraint, and exited 0.** This one changes behaviour you will notice, so it leads. The incremental schema-delta comparison never compared `CheckConstraints` or foreign keys at all — so a mid-window `ALTER TABLE … ADD CONSTRAINT … CHECK (…)` produced **no delta to dispose of**, and the restore's whole contract ("the target matches the source at the window's end") quietly did not hold. Observed rather than reasoned: the item-60 integration ground truth printed `scenario="ADD CHECK CONSTRAINT only (no DML)" schemaDelta=0`. A target missing a CHECK or an FK accepts rows the source would reject, which is the same silent constraint-weakening class this project refuses at migration time — and no surface anywhere would have told an operator, since `schema diff` could not see FK drift either until v0.112.0.

Six aspects are now compared. A DROPPED check APPLIES, because dropping a constraint only ever widens what is legal and so cannot reject a replayed event. A check that was ADDED or REDEFINED REFUSES with `SLUICE-E-BACKUP-SCHEMA-DELTA-UNSUPPORTED`, remedy: take a fresh full and start a new chain — the source's own `ADD CHECK` landed partway through the window and validated only the rows present at that instant, so an earlier event in the same window can legally carry a value the constraint forbids, and neither replay ordering is faithful. All three foreign-key aspects REFUSE, because the IR exposes no FK applier surface on any engine; foreign-key-dropped is the one that would be safely applicable if it did, and that is written down rather than left implied.

**So chains that used to "work" will start failing, and that is correct.** The refusal is the loud half of a defect that previously exited 0 over a target missing a constraint — the same posture the column-dropped and narrowing-retype dispositions already took. It is not a regression, and the remedy is named in the message. **Affected releases: every release from v0.17.0 (when `backup incremental` and the schema-delta diff shipped) through v0.112.1.** v0.108.0 closed the *disposition* hole — no delta shape can reach a silent `continue` — but it did not close this *coverage* hole one level up, because these two aspects produced no delta in the first place.

**CRITICAL — the concurrent CDC apply could silently lose a row when two different primary keys collide on a secondary unique index.** The key-hash apply is default-on (`--apply-concurrency 0` → W=4) and is engaged by `sync`, by the broker, and by chain-restore. It guaranteed ordering per (table, PRIMARY KEY), and its own doc claimed the dependent-row hazard "cannot occur" — true for one row, false across two. Source order `DELETE(pk=1, uniq='x')` then `INSERT(pk=2, uniq='x')` — an ordinary natural-key reassignment on the wire — hashes to two lanes with unconstrained commit order. On a MySQL-family target the lane INSERT carries `ON DUPLICATE KEY UPDATE`, which fires on ANY unique index: it conflicts on `uniq` against the surviving row pk=1 and **mutates pk=1 in place** (the PK is excluded from its SET list) instead of inserting pk=2; the DELETE lane then removes pk=1. Zero rows where the source has one, both lanes green, `ApplyBatch` returning nil, and the checkpoint advanced past the loss. On a Postgres target the same routing raises 23505 and takes the run down loudly, so the *silent* form is MySQL-family-specific. The ODKU mechanism was observed on real MySQL 8.0, and both halves of the gate were written first and confirmed red at HEAD.

The fix is a routing SCOPE rather than a barrier per row: a table carrying a non-PK uniqueness constraint routes wholly to one lane, which orders that table's changes against each other while keeping cross-table concurrency. `RouteScope`'s zero value is whole-table, so an engine earns per-key routing only by PROVING the target table carries no non-PK uniqueness constraint — a failed catalog probe is not a proof, fails closed, is not cached, and WARNs once per table so the throughput change is visible rather than silent. Postgres's probe deliberately covers more than "a unique index": non-primary UNIQUE constraints, bare unique indexes, PARTIAL and EXPRESSION unique indexes, and EXCLUSION constraints, which are the same cross-key conflict with a different operator.

**The honest throughput number, in both directions.** Measured on local MySQL 8.0 at W=4: a single hot unique-carrying table, 8,000 inserts, is **3.9s per-key against 10.2–11.1s whole-table — about 2.6× slower**. That is the pathological cell and anyone whose workload is one big natural-keyed table will feel it. It **reverses with table count**, because whole-table routing improves coalescing locality: 4 tables × 500 rows measured 23.8s per-key against 3.9s whole-table — about **6× faster** — with 8 and 32 tables within ±10%, and a lane histogram at 32 tables of {3500, 3500, 4500, 4500} against {4004, 4000, 3996, 4000}, i.e. 1.29× skew. Unique-value-aware sequencing (a barrier only on an observed value collision) stays the named, unbuilt follow-up if a single hot unique-heavy table becomes the binding constraint. **Affected releases: v0.99.77 onward with `--apply-concurrency` set explicitly, and v0.99.91 onward by default (when concurrent apply became fast-by-default), through v0.112.1 — plus the broker's from-backup replay from v0.99.123 and chain-restore.**

**A `sync` cold copy against a busy Vitess target spent 81.1% of its wall clock quiesced, and could not finish, while every layer reported success.** This is a real user's second report, and the numbers are the story. They ran a cold start for 91 minutes against a PlanetScale target. The v0.111.1 retry work behaved exactly as designed — **2,687 vtgate drops absorbed, zero unhandled, 9 duplicate-key collisions tolerated** — and the table still never finished: four chunks in the last sixty minutes. Measured from their log, not inferred: 246 `grow-gate CLOSED` / `reopened` pairs, **4369.3s closed against 1015.8s open**.

The ADR-0110 coordinated grow pause holds every cold-copy lane still while a target rides out a storage-grow reparent, escalating its hold each time the trouble persists. **The escalation advanced once per trip token, and every lane mid-flush posts one.** Every lane parks in `Await` while the gate is closed, so the only trips that can arrive during a window come from the lanes that were mid-flush when it closed — all reporting the *same* target event, carrying no new information. Across the 246 windows the hold matched `backoff(tripCount)` to the millisecond (0.100s at 1 trip, 0.81s at 4, 12.87s at 8, 30.0s at ≥14), so with the default 16-lane fan-out on sync cold-start (up to 32 on `migrate`) one dropped connection burned the ladder to its 30-second cap in about **4 milliseconds**. **The 30 seconds was never a design choice — it is the cap of a ladder consumed by concurrency, escalation driven by fan-out width rather than by elapsed time.**

Three coupled parts of one mechanism. In-window trips now coalesce without advancing the ladder, and a window is one hold that nothing can lengthen — the `extend` channel is deleted rather than guarded, which makes the defect inexpressible instead of merely absent. The ladder becomes episode-scoped: one rung per window while trouble persists, reset after a healthy stretch of open time, which is the first time the long-standing "the exponential backoff grows across windows" comment has actually been true (it did not — `finishWindow` cleared all state and every window restarted at rung 1, which is exactly why the growth had to come from trip count). And a run-level ceiling bounds the share of any recent stretch of wall clock the pause may consume, which the existing max-hold never could: max-hold bounds ONE window, no window in the field run came near it, and the gate still accumulated 73 minutes of quiesce — a gate whose scope was narrower than its name. Past the ceiling the gate declines to close and the per-lane retry budgets carry the run.

**Validated on real PlanetScale, at the reporter's scale** — a PS-10 database, 1.7M rows / 918 MB, A/B against the previous release. The clean signal is the hold distribution rather than the percentage: before, every hold across twenty windows was either about 0.2s or exactly 30.0s with nothing in between, which is what a ladder consumed by fan-out looks like; after, the ladder ran its full course twice under the same storm, 0.105s through 30.005s across ten cycles with the idle reset firing between them. Quiesce per absorbed drop fell from 1.38 and 1.61 seconds to 0.50 and 0.50 — and post-fix the total quiesce was identical across two runs that absorbed 302 and 300 drops, where before it tracked drop volume directly. That is the fix's thesis measured on real infrastructure rather than argued. **The 81% did not reproduce — the worst observed was 46.2%**, because the drop rate was lower and less clustered, and that is reported rather than extrapolated. No wall-clock improvement is claimed: the before and after ranges overlap.

**The trigger is a separate defect and it is NOT fixed here.** The same validation established why a dev branch stalls where a production branch does not, and the cause is sluice's own tier heuristic rather than anything unknown about the platform. A production branch reports a buffer pool matching its plan tier, so the parallelism cap applies and the copy runs eight lanes; a dev branch reports a small fixed pool below every known tier, so the cap correctly declines to throttle — and the copy runs sixteen. Twice the write fan-out, against the weaker branch. The control is decisive: on the previous release, on the dev branch, halving the fan-out and changing nothing else produced **zero connection drops, zero gate windows, and a copy 2.5× faster**. **If you are copying into a PlanetScale dev branch, `--copy-fanout-degree 2` is worth trying today** — more lanes were strictly worse. Tracked separately; this release fixes the amplifier, not the trigger.

Sizing is unchanged in intent: the ladder tracks the per-lane reparent-retry ladder, so the gate's hold overlaps the backoff each lane would have taken anyway — the pause buys lane alignment, not extra waiting. A genuine sustained grow event still quiesces exactly as it did. **Not fixed here, deliberately, and filed separately: the trip SIGNAL is still an inference.** The gate trips on whatever the engine classifier calls retriable, and 244 of the 246 windows in the field log were opened by `vtgate connection error: no endpoints` — a routing error carrying no reparent evidence at all. That is real, but it is not what produced the 81%, and bundling it would have obscured the measured fix. **Affected releases: v0.99.100 (`migrate`) and v0.99.102 (sync cold-start, when the gate was wired there) through v0.112.1.** The diagnostic premise in the original report — that `migrate` survives this — did not survive contact: `migrate` engages the same gate with *more* lanes, and the successful comparison run was against a production branch on a paid tier while the stalled runs were against a development branch.

**CRITICAL — a MySQL GTID-mode row position contained its own in-flight transaction, so a crash mid-transaction could skip that transaction's tail on resume.** `gtidSet.Update` ran on the GTID event that OPENS a transaction and `positionFor` stamps the running set on every emitted change, so a row's recorded position was a GTID set that already contained the transaction that row belongs to. `StartSyncGTID` with a set containing transaction N skips transaction N entirely. Any consumer that persisted a row's position mid-transaction therefore silently dropped the rest of it. **Scope, not overstated: the default concurrent apply path was immune** — it checkpoints only at `TxCommit`. The serial apply loop does exactly this on a row-cap, byte-cap, idle or channel-close flush, and it is reachable on `--apply-concurrency 1`, on the budget-probe degrade-to-serial, and under the ADR-0107 headroom clamp — the constrained-target case where the batcher also shrinks, i.e. where a large transaction is most likely to straddle a flush. The MySQL target applier has refused mid-transaction checkpoints since v0.99.89; **the exposed combination was a GTID-mode MySQL/MariaDB source into a non-MySQL target on the serial apply path.**

The reader now stages a group's GTID and folds it at the group's COMMIT, so rows carry the pre-transaction set — a legal restart point at every row — and only the commit carries the post-transaction set. Ground-truthed on a real `gtid_mode=ON` MySQL with the source's own `GTID_SUBSET` as the oracle: the three rows of one transaction carry `…:1` and their `TxCommit` carries `…:1-2`. The implicit-commit shapes are the part that would have been missed — a MySQL DDL `QueryEvent`, a `TRUNCATE`, and a MariaDB STANDALONE group each end without an XID and must fold somewhere else or their GTID stays staged forever; a mid-transaction `SAVEPOINT` reaches the same arm and must NOT fold; and a group whose terminator sluice does not model (XA PREPARE) folds at the next group's GTID event, so an unrecognised shape degrades to the old behaviour rather than to a dropped GTID. The Postgres applier took `CheckpointOnlyAtTxBoundary=true` rather than an exemption, because no honest exemption could be written: a MySQL file/pos source into a Postgres target has no valid mid-transaction restart point either. Marker-less sources — VStream and every trigger-CDC engine — are unaffected, verified by which readers emit transaction markers at all rather than assumed. **Affected releases: reachable in principle since the MySQL CDC reader shipped in v0.1.0; the serial-apply exposure narrowed to non-MySQL targets from v0.99.89 onward, and persisted through v0.112.1.**

**CRITICAL — a compacted backup could RESURRECT a deleted row.** Smart compaction's Update arm routed on the After image alone, justified by a comment claiming "key-only changes are represented as DELETE+INSERT in MySQL and as a separate event in PG". **Both halves are false of sluice's own readers**: the MySQL CDC reader emits one `ir.Update` whose narrowed Before carries the OLD key, and Postgres emits one `UpdateMessage` with an `OldTuple`. So on `INSERT(1)` / `UPDATE(1→2)` / `DELETE(2)`, the INSERT bucketed under key 1 while the UPDATE and DELETE both bucketed under key 2; key 2 collapsed to the DELETE and key 1 still emitted its INSERT. The compacted stream is `INSERT(1) + DELETE(2)`, and replaying it leaves row 1 alive where the source has no rows. `backup verify` could not see it, because compaction re-stamps the very hashes verify checks. A PK-changing UPDATE is now a barrier over the two keys it moves between, scoped to those keys rather than the whole table so one re-keyed row does not stop every unrelated row collapsing.

Alongside it, a HIGH: **the compactor's accumulator keys were non-injective.** The PK-value key rendered `%v` joined by a NUL byte, so `("a\x00","b")` and `("a","\x00b")` collided, and type-blindly, so `(int64(1),"2")` and `("1",int64(2))` collided — two different rows sharing one accumulator, where an INSERT of one and a DELETE of the other net to nothing and the row is silently gone. The table key had the Postgres-side twin: `schema + "." + table` is ambiguous for quoted identifiers containing a dot, which collapsed two tables into one namespace and poisoned the PK-lookup cache so the second inherited the first's primary key. Both are now length-prefixed and type-tagged, and the type tag errs SAFE — if a column's decode ever varies it SPLITS a chain (less collapse, still correct) rather than MERGING two rows. The convergence oracle is independent: every test replays the UNCOMPACTED stream through the same replay function to derive the expected row state, so nothing rests on the compactor's own arithmetic. **Affected releases: v0.85.0 (when `backup compact --smart-compaction` shipped) through v0.112.1, on chains that were smart-compacted.** Note that MySQL-family sources could not reach smart compaction at all until v0.111.1 fixed a separate defect that made it a no-op there.

**Postgres `bytea` decided text-versus-binary by SNIFFING the content, so genuine binary that spells `\x` + hex was silently shrunk.** `decodeBytea` decided whether its input was PostgreSQL's `bytea_output = hex` TEXT rendering by looking at it: a `\x` prefix plus an even-length run of valid hex meant "decode". Raw binary that happens to spell that shape was silently shortened. Measured on real PG 16 with pgx v5.10.0: `convert_to('\xdead','UTF8')` is **6 bytes on the server and decoded to 2**, and the 2-byte `convert_to('\x','UTF8')` **decoded to zero bytes**. Every lane using the row reader was affected — `migrate` bulk copy, `sync` cold-start, and **backup**, where the shrunken value is durable in the chain and `restore` reproduces it faithfully. The existing unit pin asserted that zero-length result as CORRECT, which it is for the CDC tuple path and destructive for the scan path: one test blessing both readings of the same bytes is the sharpest possible statement of the defect.

The audit's proposed fix — "hex-decode only in `decodeTuple`, never on the scan path" — was NOT what landed, because it would have been a regression: a `bytea[]` scanned into `*any` comes back as a string in PostgreSQL array-text form with every element already hex-rendered, in all five pgx exec modes, so the array lane is correct today *precisely because* it hex-decodes on the scan path. What landed is PROVENANCE. There are now two entry points rather than a bool, so each call site names its lane at the call and a new caller cannot default into one; the binary lane copies verbatim and never inspects, and the text lane hex-decodes and REFUSES a rendering that is not `\x` + even-hex with the new `SLUICE-E-VALUE-BYTEA-TEXT-UNRECOGNIZED` rather than falling through to a verbatim copy that stored the ASCII of the rendering as the value. An undeclared provenance refuses for `bytea` specifically, because there is no safe default: one lane silently shrinks binary and the other silently stores ASCII. Every other value family is provenance-inert, which the family table now pins by running through both entry points. `bytea[]` had zero value-level coverage in the repo before this — only an OID-parity pin. **Affected releases: v0.1.0 through v0.112.1.** Cross-engine `verify` cannot catch this class at all: it refuses `--depth sample` across engines, so a PG→MySQL run gets a `COUNT(*)` that a shrunken value does not change.

**Three more Postgres lanes rendered `bytea` as text with no pinned output format, so a legacy `bytea_output = escape` server corrupted values on every one of them.** pgoutput renders `bytea` using the walsender's GUC, inherited from the server, database or role default; sluice's decoder recognised the `\x` hex default and copied anything else verbatim, so on such a server every streamed `bytea` row stored the escape-format ASCII text as the target's bytes. Fixed at the WIRE — pinning the session's format removes the ambiguity instead of teaching the decoder to guess. A review then re-derived the reachability matrix against real PG 16 and found two more lanes: the **ordinary pgx pool**, where a scalar `bytea` is immune (pgx decodes it to raw bytes either way) but a `bytea[]` is not — measured under `bytea_output = escape`, a genuine 2-byte `0xDEAD` element arrives as `\336\255` and is stored as 8 bytes, on `migrate`, on `sync` cold-start, and into the backup archive — and the **pgtrigger capture function**, whose `to_jsonb()` renders through the same output function honouring the *firing application's* session, which sluice can only pin on the function itself. A roster gate now derives the lane list from the source: any session that pins `extra_float_digits` is by construction a session that renders values as text, and must pin `bytea_output` too, so the next lane fails until it copies both. **Affected releases: v0.1.0 through v0.112.1, on any Postgres source whose `bytea_output` is not the `hex` default.**

**A shared trigger-CDC change log was pruned against ONE stream's frontier, so a slower peer silently lost rows.** A source change log is shared by every sync reading that database, and the auto-prune cut at THIS stream's durably-applied frontier by change-log id — so on the staged/wave shape the documentation recommends (several syncs off one source, disjoint table sets, necessarily different speeds), the faster sync reaped everything between the two frontiers before the slower one read it. Silent, permanent, and undiscoverable from the slow side: it simply never sees those changes. v0.110.0 added a warning; this fixes it. `sluice trigger setup` now installs a `sluice_change_log_consumers` table on the source and moves the change-log `schema_version` from 1 to 2; every trigger-CDC stream publishes its durably-applied frontier there once a minute — **whether or not that stream enabled `--auto-prune-change-log`**, because the sync that loses rows is usually the one *without* the flag — and the prune cuts at the MIN across every registered consumer, clamped to the pruning stream's own freshly-read frontier. Registration starts at the cold-start snapshot open rather than at first apply, so a peer's multi-hour bulk copy holds the log for its whole duration.

Two things fail CLOSED rather than guessing. A source engine that can be pruned but does not implement the new consumer-registry surface is **not pruned at all** (logged at ERROR) — falling back to the old cut would recreate the bug for exactly the engine someone forgot to migrate. And an EMPTY registry is refused rather than read as "no consumers, prune everything", because empty and "nobody has registered yet" are the same observable state and the other reading would be a worse silent-loss bug than the original. All three trigger-CDC engines (pgtrigger, sqlite-trigger, d1-trigger) are fixed; the one sibling deliberately not gated is the operator-run `sluice trigger prune`, which is clamped to the registry MIN and prints when its cut was lowered but does not refuse when there is no registry to consult — refusing an explicit operator action that has been safe for a single stream since the feature shipped would be a regression. **What this does NOT close, and it is in the flag's help text and a startup WARN: a peer running a sluice older than the registry never registers and leaves no trace on the source, so it cannot be detected.** Upgrade every sync on a shared source before enabling the flag. A peer that ran an *older* `sluice trigger setup` IS caught, because that rewrites the schema version below the floor. **Affected releases: v0.99.174 (when auto-prune shipped) through v0.112.1, with `--auto-prune-change-log` enabled on a source shared by more than one stream.**

**A cold copy into a table with no primary key could silently DOUBLE the table when a transient error was retried.** The reparent-retry's ambiguous-commit proof is entirely an argument about a duplicate-key collision — and a collision needs something to collide with. On a table with no PRIMARY KEY and no all-NOT-NULL UNIQUE index the committed-but-unacknowledged branch produces no collision at all, so the retry re-inserts every row and the copy exits 0 with the table doubled. v0.111.1's widening of the vtgate error class armed this on exactly the PlanetScale path the field report came from. Fixed by REFUSAL (`SLUICE-E-COPY-RETRY-AMBIGUOUS-KEYLESS`) rather than by post-table reconciliation: reconciliation cannot be made honest at this layer, because it needs a baseline the writer does not have (N parallel workers over one table; resume and restore paths deliberately write into a non-empty target), the count would be a full scan issued when the target is least able to serve it, and comparing against "rows I sent" is the writer's own bookkeeping, i.e. no independent evidence. The gate lives in the one place the retry policy lives, so a third caller inherits it — which is exactly what happened later in this same release when `LOAD DATA` became the third core. The sibling sweep is enumerated in the commit, with a verdict for each of eleven write paths across four engines; the Postgres chunked-COPY retry carried the same hole and got the same gate. **Affected releases: v0.99.92 (when cold-copy reparent-retry shipped) through v0.112.1, on keyless tables only.**

**A `backup prune` that retires every earlier segment sent `restore` to the retired root manifest while `backup verify` walked the catalog floor.** `prune --keep-duration` past a rotated chain retires each earlier segment WHOLE and leaves the newest segment holding only its full. On that shape the restore dispatch predicate answered "one segment, no incrementals" and took the single-manifest path, which resolves `manifest.json` at the lineage ROOT by convention — and after such a prune that file is the RETIRED segment-0 full, kept deliberately for the chain's identity. Two commands, one directory, different manifests: either verify-green and restore-chunk-missing on an intact chain, or **a silent stale restore of older data** where the retired segment's chunk deletes had failed. The predicate now also asks WHERE the surviving segment lives, and it is the one predicate `restore`, `backup verify` and `export-as-parquet` share, so all three move together. The "safe by construction" comments each enumerated ONE reader of the retired root and there were two; the enumeration is now derived by an AST roster requiring every by-convention root-manifest read to be classified with a reason.

Two siblings fixed with it. **Maintenance retired manifests but never their detached `.sig` files**, so a stale artifact still cryptographically verified — the retired chain-identity `manifest.json` kept a valid signature asserting it is link 0 of a chain it had left. And **prune discarded every delete error**, which is precisely how a loud "missing chunk" becomes a silent stale read: a store that refuses deletes (expired credentials, object-lock/WORM, a read-only mount) leaves the retired chunks in place for the mis-dispatched reader to find. Delete failures are now collected and named at WARN. **Affected releases: the silent-stale-restore shape requires the retired root manifest to be kept, which began in v0.104.3 — so v0.104.3 through v0.112.1. The `.sig` orphan half is reachable wherever detached signatures exist, i.e. from v0.99.208.** Before v0.104.3 the retired root was removed outright, so the failure was loud rather than silent; if you want to be careful, treat the whole prune-to-floor shape as suspect on any pre-v0.113.0 release rather than trusting that boundary.

**`sluice schema diff` was structurally blind to sequences and to row-level security.** It walked tables and views only, so `ir.Schema.Sequences` and each table's RLS enable/force flags and policies — all carried in the IR specifically to close named silent-loss items — were never compared. A target-side `DISABLE ROW LEVEL SECURITY` read as "in sync", exit 0, and every tenant read every tenant's rows. Sequences now compare on what decides the values they PRODUCE (data type, start, increment, min/max, cache, cycle, owned-by); the sequence POSITION is deliberately not compared and says so in its doc, because it moves under write load and a check that fires on every run of a healthy pair gets suppressed. RLS compares enable and force as one unit (force without enable enforces nothing) plus each policy's command, permissive flag, roles, `USING` and `WITH CHECK`, with role lists compared sorted because PostgreSQL does not guarantee their ordering and a reorder must not read as drift.

**And v0.112.0's own foreign-key comparison was invisible in the output.** It wired the comparison and the has-changes flag but neither the text render nor the JSON summary counts, so `schema diff` exited 1 printing nothing and a CI consumer keying off the summary read zeros. That is fixed, along with a rendering defect the comparison shipped with — converting a uint8-backed action type with `string()` yields the raw code point (`"\x02"` for `CASCADE`), and `go vet` is silent on it *precisely because* the type implements `Stringer`. The completeness rosters that forced these out also surfaced two more: EXCLUDE constraints had the same comparison-without-render defect since they were added, and the unnamed-foreign-key count could only ever be seen on a table that had OTHER drift. **Affected releases: sequences and RLS have never been compared since `sluice schema diff` shipped in v0.8.0 (RLS became representable in v0.84.0, sequences in v0.99.175); the FK render and count defect is v0.112.0 and v0.112.1 only.**

**MySQL binlog CDC could not decode `BIT(N>1)` at all, and a warm resume could decode old events against the current catalog.** The BIT decoder accepted only byte-slice and string forms, while go-mysql's own row-event code documents that it hands `MYSQL_TYPE_BIT` back as an int64 — so the first change touching a `BIT(2)` or wider column killed the sync. Loud and deterministic, but only after the cold copy had already succeeded. `BIT(1)` escaped because the type mapper renders it as a boolean: the one width everybody tests was the one width immune. Separately, warm resume decoded buffered history against the CURRENT catalog: the contract cited a real server property — MySQL serialises DDL against DML — but that property is about the binlog HEAD, not about replaying history, so a DDL during downtime that preserved the column COUNT (a type change) silently remapped every replayed value. Column-count changes already failed on arity; this is the case that did not. A new guard compares the `TABLE_MAP` event's type vector against the shape about to decode it, before any row is decoded, and refuses with the new `SLUICE-E-CDC-SCHEMA-REPLAY-MISMATCH`. Comparison is by DECODE FAMILY, not exact type code, so `INT`→`BIGINT` and `VARCHAR`→`TEXT` do not halt a stream while `DECIMAL`→`DOUBLE`, `ENUM`→`INT` and `TIMESTAMP`→`DATETIME` do. **Residuals stated in the code rather than implied: a pure column RENAME and an ENUM/SET label-list reorder are same-family and are NOT caught — both need `binlog_row_metadata=FULL`, which is not the default.** Both defects date from v0.1.0.

**The MySQL lock-free snapshot fallback captured its binlog position on the wrong side of the snapshot.** The path that every FTWRL-less environment lands on — RDS is the shape — opened the consistent-snapshot transaction and *then* read the position, which is the one ordering where a commit in that window is above the read view and below the recorded position, so it lands in NEITHER the snapshot nor the CDC stream. The order is flipped, which moves the residual from **loss** to **re-delivery**. This SHRINKS the window; it does not close it, and the code says so. What was added instead of a lock is a churn probe: the far edge of the window is read too, and equal binlog tips PROVE the window was empty. A moved tip gets a WARN naming the exact range, including the caveat that the duplicate side is only free for keyed tables, and every run now logs which capture path it took. **The same shape is still unfixed on the BACKUP snapshot's serial path** — it is filed with a comment at the site, and was not flipped in the same change because the chain anchor is load-bearing for incremental lineage and replay-window invariants that this change did not validate. Do not read this fix as covering it. **Affected releases: v0.99.16 through v0.112.1 for the CDC snapshot; the backup-snapshot sibling remains open in v0.113.0.**

**Binlog file ordering answered backwards across the suffix widening.** The comparison was a plain string compare, justified by "the fixed zero-padded width makes string comparison correct". The width is not fixed: `mysql-bin.999999` is followed by `mysql-bin.1000000`, and lexically `"1000000" < "999999"`. A position-ordering predicate that answers backwards is how a resume concludes that a newer position is older. Now basename plus numeric suffix, falling back to lexical for anything that does not split that way, pinned with an antisymmetry property test because a hand-rolled comparator reporting both directions true would make "at or after" incoherent. Affected from v0.70.0, and only on a server that has rotated past a million binlog files.

**MySQL's `LOAD DATA` cold copy was one monolithic statement per table, so a transient had no resume point.** The whole table streamed through one exec, consuming the row channel as it went; when the statement failed the rows were gone — no replay, no cursor, and a multi-hour copy discarded entirely. Every other cold-copy write core rides a transient by re-driving a BUFFERED unit, and this one had nothing buffered. It now loads a table as a sequence of bounded statements (16 MiB of encoded TSV each, lowered by `--max-buffer-bytes`), each driven through the same retry helper the batched cores use, so the retry policy, the grow-gate participation, the wall-clock bound and the keyless carve-out are inherited rather than re-derived.

The premise was verified rather than assumed, and it makes the guarantee STRONGER than planned: `LOAD DATA LOCAL INFILE` downgrades a duplicate-key error to a warning and skips the row — the server cannot stop a transfer already in flight, so it behaves as if `IGNORE` were given — ground-truthed against a real MySQL 8.0. That makes a byte-identical replay convergent on a keyed table whether the prior attempt rolled back, committed fully, or committed a prefix. The wart it costs is that a replay legitimately produces one duplicate warning per already-landed row, and the strict-mode probe refuses on ANY warning; tolerating them wholesale would let a real coercion hide among them, and it genuinely can, because the server caps `SHOW WARNINGS` at 1024 rows so a single truncation on a large replay sits entirely outside the visible window. The tolerance is therefore bought with an INDEPENDENT number — duplicates-skipped derived from the driver's affected-rows, total from the server's uncapped `@@warning_count` — and any remainder refuses. **Throughput: an extra segment costs exactly one extra transaction commit and nothing else, and the cost prices in linearly with segment count (8 MiB budget 0.99×, 4 MiB 1.09×, 2 MiB 1.19×, 1 MiB 1.46×, 256 KiB 2.59×), so at the shipping 16 MiB budget the copy is within measurement noise of the old form.** The binding constraint turned out to be memory, not throughput: one segment's bytes are held per concurrent writer where the streaming form held 64 KiB. Affected from v0.7.0; note this core is declared only by vanilla MySQL (including RDS, CloudSQL and Azure) and MariaDB — the PlanetScale and Vitess flavors use the batched insert core and were never on this path.

**Smart compaction retained every event it read, and then held every event it emitted.** The compactor's only accumulator barriers were TRUNCATE, schema snapshots and end-of-incremental, so an incremental carrying none of those held its whole input: measured at 100k events → 261 MiB, and a 100:1-*collapsing* corpus → 248 MiB, i.e. no relief from collapsing at all, extrapolating to roughly 2.6 GiB at a million events. A byte ceiling with early eviction bounds the retained half; single-event chains are evicted first in insertion order because their flush emits exactly what finalize would have emitted, so the workload with the worst retention is also the one where the cap changes nothing observable. The emitted half is now bounded too: the compactor streams into a sink with a one-slot lookahead that holds a trailing transaction commit back, and output distributes across the incremental's existing chunk slots under a byte budget instead of packing everything into slot 0 — which is what makes it work on an ENCRYPTED chain at all, since that writer buffers a whole compressed chunk for its authentication tag. Measured ceiling 65,890 bytes against an unbounded 1,378,986 bytes on the same corpus, plaintext and encrypted. What remains unbounded, logged at INFO rather than assumed away: when an input chunk exceeds the budget the peak is that chain's LARGEST CHUNK — still O(one chunk), never O(the incremental).

That work found and fixed **two live position-ordering holes nobody had filed** (the PK-change barrier and the DDL barrier both appended collapsed events after a trailing transaction commit, which the restore side's tail-truncation backstop refuses), and it found that **`backup incremental`'s change-chunk lane had no byte ceiling at all** — a previous change had added one to the data-chunk lane and its commit message enumerated this lane as covered, which was false. Worse, the first fix for *that* reached the `backup incremental` capture loop and not `backup stream run`'s rollover, which writes most change chunks; both now roll on bytes against the same constant. Three enumerations narrower than the claim made for them, in one day.

**Smaller fixes in the same batch.** A gate this project shipped a day earlier was ESCAPABLE and the audit proved it by executed mutation: it discovered chunk write cores by matching a field NAME, so a fourth core spelling its buffer differently stayed green — it is now dual-signal, unioned with the *shape* of emitting a line, which is what makes renaming useless. Compaction stamped each rewritten chunk's SHA and row count from its own writer's in-memory accounting and never read the object back, so every later consumer compared the store's bytes against a number the writer asserted; it now re-reads each rewritten chunk through the store with the real reader. A blank line inside the error-codes table ended it, so 48 of 74 codes rendered as raw pipe-delimited text on the published docs, and both existing doc gates stayed green because each parses the file line by line and never asks whether the lines form one table. The README prescribed a path that is refused unconditionally, for roughly thirteen releases. And the pre-commit NUL-byte and merge-conflict-marker guards sat after the "no Go files staged" early return, disarming them for exactly the commit class every incident they cite came from — a Markdown file, on a path where CI skips too.

## Compatibility

**No flags were renamed or removed, no on-disk format changed its version, and no backup chain is repartitioned or crosses an epoch boundary.** Upgrading from v0.112.0 or v0.112.1 is drop-in in the mechanical sense. The behaviour changes below are the part that needs reading.

**One new flag: `--depth` on `sluice backup verify`, `hash` (default) or `read`.** The default is byte-identical to the previous behaviour. On an encrypted chain, `--depth read` requires `--encrypt` plus key material and refuses with `SLUICE-E-BACKUP-ENCRYPTION-MISMATCH` without it.

**Four new error codes**, all refusals on paths that previously continued: `SLUICE-E-BACKUP-CHUNK-UNREADABLE` (raised only by `backup verify --depth read`), `SLUICE-E-VALUE-BYTEA-TEXT-UNRECOGNIZED` (a Postgres `bytea` text rendering that is not `\x` + even-length hex — in practice, a source running `bytea_output = escape`), `SLUICE-E-COPY-RETRY-AMBIGUOUS-KEYLESS` (a cold-copy transient on a table with no primary key and no NOT NULL unique index), and `SLUICE-E-CDC-SCHEMA-REPLAY-MISMATCH` (a binlog `TABLE_MAP` shape that disagrees with the current catalog, i.e. a DDL that ran during downtime). The existing `SLUICE-E-BACKUP-SCHEMA-DELTA-UNSUPPORTED` now also fires on an added or redefined CHECK constraint and on any foreign-key add, drop or redefine.

**Chain replay refuses on more schema deltas than it did.** A chain whose incremental window carries an `ADD CHECK` or any foreign-key DDL now refuses at replay where it previously exited 0 having restored a target missing the constraint. The remedy is a fresh full and a new chain, and it is named in the message. A DROPPED check still applies. This will stop chains that used to appear to work; that is the intent.

**A source-side schema migration is required for `--auto-prune-change-log`.** `sluice trigger setup` installs a `sluice_change_log_consumers` table and moves the change-log `schema_version` from 1 to 2. A new binary meeting an un-migrated change log refuses to auto-prune and names `sluice trigger setup`, which is idempotent — **re-running it IS the migration**. Do it with the syncs stopped: setup drops and recreates the capture triggers, and on Postgres the migration's own `CREATE TABLE` is captured as a DDL marker that a live reader refuses on. A source engine exposing the pruner without the new registry surface is not pruned at all rather than pruned wrongly. **The honest residual: a peer running a sluice older than the registry never registers and leaves no trace on the source, so it cannot be detected.** Upgrade every sync on a shared source before enabling the flag. A peer that ran an older `trigger setup` IS caught, because that rewrites the schema version below the floor.

**A table carrying a non-PK unique index now applies CDC changes on a single lane.** This is a throughput change and it goes both ways: about 2.6× slower on a single hot unique-carrying table, and about 6× faster at four tables, with 8 and 32 tables within ±10%. If your workload is one large natural-keyed table under heavy CDC, you will see this; if it is many tables, you will likely see the opposite. A failed catalog probe fails closed to whole-table routing and WARNs once per table, so a degrade is visible rather than silent. Postgres targets also route whole-table for EXCLUSION constraints and for partial and expression unique indexes.

**MySQL's `LOAD DATA` cold copy is now segmented, which changes two things.** A failed table copy can now leave PARTIAL rows where it previously left none, because each segment is its own transaction — the same shape the batched cores have always had, and which the resume and empty-target preflight paths already handle. And a keyless table that hits a transient now refuses with `SLUICE-E-COPY-RETRY-AMBIGUOUS-KEYLESS` rather than the old `LOAD DATA`-specific message, which is the same disposition the batched cores already took in that situation. This affects vanilla MySQL and MariaDB targets only; PlanetScale and Vitess use the batched insert core.

**`sluice schema diff` will report drift it previously called in sync, and it exits 1 when it finds any.** Sequences and row-level security are now compared, and v0.112.0's foreign-key comparison now actually renders and counts. As with v0.112.0's index and FK work, a CI gate that has been green may go red on the **first** run against an unchanged pair of databases, because the difference was always there and could not be seen. Read the report before assuming a false positive. Sequence POSITION is deliberately not compared, so an advanced sequence does not report drift. The JSON summary gains additive fields only — `sequences_missing` / `_extra` / `_mismatched`, `views_missing` / `_extra` / `_mismatched`, `rls_mismatched`, `policies_missing` / `_extra` / `_mismatched`, `excludes_missing` / `_extra` / `_mismatched`, and `foreign_keys_unnamed` hoisted to a schema-level total that survives when a table carries no other drift; existing consumers that read only the fields they already knew about are unaffected.

**Chunk boundaries in NEW backups can differ from earlier releases**, because the change-chunk lane now rolls on bytes as well as event count, on both the `backup incremental` and `backup stream run` writers. Existing chunks are untouched, restore is unaffected, and nothing keys on a boundary. `backup compact --smart-compaction` also distributes its output across the incremental's chunk slots instead of packing slot 0, so a compacted chain's chunk shapes will differ; content is unchanged.

**One narrow new false-positive is named rather than left to be found.** A GTID position is a set, and a row now carries the set as of BEFORE its own transaction — so a DDL's anchor and the rows of the next transaction carry the same set by construction. The backup reader's data-window end-position assertion refuses a data-bearing window whose end position coincides with a schema anchor, so it can now false-positive. It needs a MySQL GTID source, a DDL inside the window, AND one of two documented mid-transaction window exits. It is loud, never silent, and the restore side rests completeness on the change-chunk tail rather than on this property, so the cost is a refused backup whose message blames the reader for behaviour that is now correct. It was not relaxed here because narrowing a safety backstop deserves its own change.

**Postgres sessions now pin `bytea_output = hex` on the replication connection, the ordinary pgx pool, and the pgtrigger capture function.** If you deliberately run a source on `bytea_output = escape`, sluice now reads it correctly on every lane instead of storing the escape rendering's ASCII; a text rendering it cannot read refuses rather than falling through.

## Who needs this — action required

- **Anyone running `sync`, the broker, or chain-restore with concurrent CDC apply into a MySQL, MariaDB, PlanetScale or Vitess target, on a table with a UNIQUE index that is not the primary key. Re-verify that table.** This is a silent loss: a natural-key reassignment (`DELETE` then `INSERT` on the same unique value, different primary keys) could leave zero rows where the source has one, with both lanes reporting success and the checkpoint advanced past it. Row counts on the affected table will be short, so `sluice verify --depth count` against the source is a genuine independent check and is the cheapest place to start; `--depth sample` on a same-engine pair is stronger. Affected from v0.99.77 with `--apply-concurrency` set, and from v0.99.91 by default, through v0.112.1. **A Postgres target was never silently affected** — the same routing raised a duplicate-key error and took the run down loudly.
- **Anyone who has restored, or is relying on, a chain that was smart-compacted. Re-verify against the source, or take a fresh full.** A primary-key-changing UPDATE inside the compacted window could leave a deleted row ALIVE in the restored target, and `backup verify` could not see it at any depth because compaction re-stamped the very hashes verify checks. Two rows whose primary-key values collided under the old non-injective key rendering could also net to nothing. Affected on chains compacted by v0.85.0 through v0.112.1. The independent check is the source database, not the archive — a `COUNT(*)` and a spot comparison of recently re-keyed rows.
- **Anyone migrating, syncing or backing up a Postgres source with `bytea` or `bytea[]` columns. Re-verify those columns, and check `bytea_output`.** Two separate defects: genuine binary that spells `\x` + hex was silently shortened on every cold-copy and backup lane (measured 6 bytes → 2, and a bare 2-byte `\x` → 0), and on a server whose `bytea_output` is `escape` the CDC stream, the `bytea[]` scan path and the pgtrigger capture function all stored the ASCII of the rendering as the value. Both are durable in a backup chain, and `restore` reproduces them faithfully. Cross-engine `verify` cannot see either — it refuses `--depth sample` across engines, so PG→MySQL gets a `COUNT(*)` that a shrunken value does not change. **The independent check is `octet_length()` / `encode(col,'hex')` on the source against the same on the target.** Affected from v0.1.0 through v0.112.1.
- **Anyone running more than one trigger-CDC sync against a shared source with `--auto-prune-change-log` enabled. Assume the slower stream lost rows, and re-verify the tables it owns.** The prune cut at the enabling stream's frontier, so anything between the two frontiers was deleted before the slower peer read it — silently, permanently, and invisibly from the slow side. Affected from v0.99.174 through v0.112.1. Before enabling the flag again: upgrade **every** sync on that source (a pre-registry peer is undetectable), then re-run `sluice trigger setup` with the syncs stopped to install the consumer registry.
- **Anyone who took a MySQL/MariaDB backup or CDC snapshot on a target where `FLUSH TABLES WITH READ LOCK` is unavailable — RDS is the shape.** The CDC snapshot's position was captured on the loss side of its window; it is now on the duplicate side, with a churn probe that reports whether the window caught anything at all. **The identical shape is still unfixed on the backup snapshot's serial path in v0.113.0** — a commit in that window is in neither the full nor an incremental taken from it. If you take backups from an RDS-like MySQL source without the coordinated lock, treat a backup taken during heavy write traffic as possibly missing a commit at its boundary, and prefer a quiet window until that fix ships.
- **Anyone running `sync` with `--apply-concurrency 1`, or on a target constrained enough to degrade to serial apply, from a MySQL or MariaDB GTID-mode source into a non-MySQL target. Re-verify after any crash or restart.** A checkpoint taken mid-transaction recorded a position that already contained that transaction, so resuming from it skipped the transaction's remaining rows. The default concurrent apply path was immune. If a stream in that configuration ever crashed or was killed mid-transaction, re-verify the affected tables against the source.
- **Anyone whose cold copy against a PlanetScale, Vitess or auto-growing Postgres target has been crawling or never finishing.** There is nothing to re-verify — this was a throughput collapse, not data loss — but a copy that could not finish is now expected to finish. If you have a run that has been quiesced for hours while the logs report drops absorbed and nothing lost, upgrade and re-run it.
- **Anyone doing `backup prune --keep-duration` on a rotated chain, or relying on detached signatures.** A prune to the floor could send `restore` to the retired root manifest — either a loud missing chunk, or a **silent restore of older data** where the retired chunks' deletes had failed. Re-run `backup verify` and a test `restore` on any chain you have pruned to a single segment, and sweep the store for orphaned `.sig` files, which previously outlived the manifests they signed and would still verify.
- **Anyone using `sluice schema diff` to gate a deploy.** Sequences and row-level security were never compared, and v0.112.0's foreign-key comparison printed nothing and counted zero. Re-run it against a pair you believe is in sync, and expect a first run to go red on drift that was always there.
- **Anyone with backups older than v0.112.0 holding wide rows.** Run `sluice backup verify --depth read` against them. A row above the format's 64 MiB per-line limit was writable by any sluice at or below v0.111.1, verified clean at the hash depth, and fails at restore. The read depth is the first thing that can tell you before you need the backup. It cannot tell you whether the values are right — nothing that reads only the archive can.
- **Everyone else: nothing to do.** The remaining fixes here are loud failures made louder, gates made harder to escape, and memory bounds. A `migrate` or `sync` with no unique-index CDC apply, no trigger-CDC sharing, no `bytea`, no compacted chain and no pruned-to-floor backup is unaffected by every item on this list.
