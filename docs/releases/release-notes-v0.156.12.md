# sluice v0.156.12

**HIGH silent-data fix — a `backup stream` window no longer ends inside a source transaction, and chains older releases wrote that way are now refused instead of restored wrong.** (1) F-E1-SEVERED-TAIL-REPLAY: on v0.19.0 through v0.156.11, a `backup stream` stop, stop file, cancel or source close that landed mid-transaction committed the window anyway. Chain `restore` and `sync from-backup` then applied that transaction twice at exit 0 (a keyless table restored at 6 rows against the source's 3; a key-reusing transaction lost a row). On MySQL file/pos the cut instead lost the rest of a ROWS event (40,000 rows restored as 39,996). The old cancel drain could also drop whole committed transactions from the chain. On Postgres chains written before v0.138.0, `backup compact --smart-compaction` could hide the re-delivered transaction from every check, including a lost DELETE that leaves a row the source deleted on a keyed table. (2) The lane apply barrier now commits once instead of twice, about 1.3× faster on keyless and primary-key-changing workloads, with no change to the delivery guarantees. **Upgrading does not repair a target an earlier release already restored or brokered from an affected chain, and it does not make an affected chain replayable: the remedy is a new full backup.** Read **Who needs this**. **Not a silent drop-in:** affected chains are now refused with no override, `backup stream stop` can wait up to 60 s, and a SIGTERM inside a transaction discards the in-flight window. See **Compatibility**.

## Fixed

**`backup stream` no longer writes a window that ends inside a source transaction (HIGH, silent; F-E1-SEVERED-TAIL-REPLAY).** Every exit of a `backup stream` window committed it whatever its position: `backup stream stop`, the stop file, SIGTERM/SIGINT and the source stream closing. A window cut inside a transaction ended after that transaction's first rows, and the next incremental resumed from a position inside it. On Postgres, MySQL/MariaDB GTID and VStream, every row of a transaction carries a position from which a resume re-reads the whole transaction. So the next incremental re-delivered it, and chain restore and `sync from-backup` applied its first rows twice. That is harmless only for primary-key inserts and same-key updates. Measured at exit 0: a keyless table restored at 6 rows against the source's 3, and a key-reusing transaction (`UPDATE 1→2, DELETE 2, UPDATE 3→1`) lost a row. On MySQL file/pos every row of a multi-row ROWS event shares the event's end position, so the next incremental started after the interrupted event and the rest of it was missing (40,000 rows restored as 39,996). A cut between two statements instead stopped the next `backup stream` with `rows event for unknown table_id`. MySQL GTID chains written before v0.113.0 lost the rest of the transaction instead of duplicating its start.

The cancel drain (SIGTERM/SIGINT) had a second, worse defect. Inside a transaction, or when its final flush failed, it skipped storing its last chunk but still committed the chunks already stored, with EndPosition already advanced to the last change it had read. Every change in the unstored chunk was in no incremental, and the next run resumed after them, so those changes were LOST. The failed-flush case reaches every engine, the trigger-CDC ones included. Since v0.99.222, restore and `sync from-backup` refuse such a link with `SLUICE-E-BACKUP-INCOMPLETE`, but only after applying everything before it. Earlier releases replayed the chain without those changes at exit 0.

A window now ends only at a transaction boundary. A stop inside a transaction keeps reading until that transaction commits, for at most 60 s or 1,000,000 changes. If that budget runs out, or the context is cancelled or the source closes first, the window is abandoned. No manifest is written and the replication position is not acknowledged, so the next run reads the window again from the parent's end. This is logged at WARN as `BACKUP-WINDOW-ABANDONED-OPEN-TRANSACTION`. EndPosition now moves only once the chunk carrying a change is stored, and a failed drain flush also abandons the window. One-shot `backup incremental` fails (exit 1) with the same marker when its source stream closes inside a transaction, and writes no manifest. Pinned by `TestSeveredTail_PG`, `TestSeveredTail_MySQLGTID` and `TestSeveredTail_MySQLFilePos` (stop, stop file, cancel and spent budget, each landing inside a transaction carrying a keyless insert, the key-reuse sequence and a multi-row event, graded against the source on chain restore and, for keyed tables, the broker), `TestBackupStream_CancelDrainFlushFails_Abandons` and `TestChangeChunkBuffer_EndPosMovesOnlyWhenStored`. **Affected releases:** chains written by `backup stream` on v0.19.0 through v0.156.11, for the duplication, file/pos loss and drain loss alike. One-shot `backup incremental` had the same channel-close exit, which committed mid-transaction on every release before this one. Trigger-CDC sources (pgtrigger, SQLite, D1) record no transactions and resume strictly after the last change id, so they can carry only the failed-flush loss.

**Chain restore, `sync from-backup` and `backup verify` now refuse chains that older releases wrote this way (`SLUICE-E-BACKUP-CHAIN-SEVERED-TRANSACTION`, `SLUICE-E-BACKUP-INCOMPLETE`, exit 3, no override).** A new check, `SeveredTransactionDoor`, decodes the first and last change chunks of every incremental before anything is applied. It reads the transaction markers and row positions the source stamped, not the manifest's own position fields. It refuses three shapes:
- **Shape A:** an incremental that is not the chain's last ends inside an open transaction. An incremental ending on a bare transaction begin, with no row of that transaction after it, carries none of it and is not refused.
- **Shape B, Postgres only:** an incremental opens with rows at or before the previous incremental's last rows. This is the transaction the previous window ended on, re-delivered by the resume. Every resumed window had this shape on chains written before v0.138.0, and a current binary extending such a chain writes one more.
- **Shape C (`SLUICE-E-BACKUP-INCOMPLETE`):** an incremental whose EndPosition is past the last change its chunks record. This is the cancel-drain loss above. Restore's existing tail check made the same comparison, but only mid-apply. Shape C runs before anything is applied, and its message names the cause instead of blaming tampering.

The two consumers apply the next incremental after a segment full too, so A and B are judged across segment fulls. A chain whose final incremental ends inside a transaction is not refused, because nothing follows it yet. Chain restore logs `CHAIN-TAIL-OPEN-TRANSACTION` at WARN for it. Chain restore judges every link before it applies anything. The broker runs the check on every tick that brings new work, and refuses only findings on a link it has not applied yet. A finding on a link it already applied is logged once as `CHAIN-APPLIED-SEVERED-TRANSACTION` at WARN, naming the links to compare with the source, and the broker continues. Otherwise an upgraded broker over a pre-v0.138.0 Postgres chain would halt forever on history it can no longer undo. A chunk the check cannot read refuses with the fetch's own error before anything is applied. The exception is a broker that already applied both that link and the next incremental, where it WARNs and leaves the link unjudged. `backup verify` runs the same check for shapes A and C and reports every refusal. It judges past a link it cannot decode, and on an encrypted chain it needs the key material, WARNing that it skipped the check without it. Chain restore's and the broker's tail checks, the zero-chunk guards and shape C now share one predicate, `EndPositionUnreached`, so none refuses what another accepts. Pinned by `TestSeveredTransactionDoor_ShapeC_AgreementTable` and `TestShapeCAgreement_BrokerTailBackstop` (each shape through the check, chain restore, the broker and verify), `TestSeveredTransactionDoor_PairsAcrossASegmentFull`, `TestSeveredTransactionDoor_CheckFrom_UnreadableAppliedLinkDoesNotHideTheNextLink`, `TestVerifyBackup_RefusesShapeC_AtHashAndReadDepth`, `TestVerifySeveredTransactions_JudgesPastAnUndecodableLink` and `TestBrokerReplayRunsTheSeveredDoorBeforeApplying`. The check was also run against real chains written by the producer with its fix reverted, and refused them on all three engines (A on Postgres and GTID, C on file/pos).

**`backup compact --smart-compaction` no longer hides a re-delivered transaction on a Postgres chain (HIGH, silent).** Smart compaction is opt-in. It collapses repeated changes to a row, and a collapsed event carries the row's first position. On a chain carrying shape B, that can hide the shape from the check above in two ways. If the first incremental touched a row twice, its last row position drops below the re-delivered transaction, and a restore or broker replay then applied that transaction twice (measured: a keyless table restored at 4 rows against the source's 2). If the second incremental re-delivered a keyed INSERT that a later change in it DELETEd, the pair collapses to nothing and the second incremental's first row moves past the boundary. The result is a lost DELETE: the target keeps a row the source deleted (measured, at exit 0). The uncompacted chain was correct there, because the re-delivered INSERT upserts and the DELETE then applies. Smart compaction now resolves the chain's source-engine position order from the engine its catalog records. Before copying anything, it refuses (`SLUICE-E-BACKUP-CHAIN-SEVERED-TRANSACTION`) a chain where shape A or B involves an incremental it would rewrite, and leaves the store as it was. When it cannot judge shape B (any engine but Postgres, or none recorded), it says so at INFO and in its result (`shape_b_judged`). It refuses an engine it does not know with `SMART-COMPACTION-SOURCE-ENGINE-UNKNOWN`. The refusals name `--smart-compaction-off` (plain compaction moves the evidence verbatim) and a new full backup. As a backstop, before swapping the catalog compaction compares the check's findings on each rewritten incremental, before and after. It refuses the swap (`SLUICE-E-BACKUP-CHAIN-UNREADABLE`, nothing deleted) if any finding was gained or lost. A refused run now removes the merged copy it wrote. Pinned by `TestSmartCompaction_RefusesToHideShapeB`, `TestSmartCompaction_CrossGroupPairShapeB`, `TestSmartCompaction_BeltSeesShapeBLost`, `TestCompactChain_VerdictChangeGate`, `TestSmartCompaction_RefusesASeveredFramedIncremental`, `TestSmartCompaction_ResolvesThePositionOrder` and `TestBackupCompactPassesThePositionOrder`. **Affected releases:** v0.85.0 (smart compaction's first release) through v0.156.11, on Postgres chains that carry shape B, which means chains spanning a resume written before v0.138.0.

**`backup compact --smart-compaction` no longer writes an incremental that restore refuses (MEDIUM, loud, no data loss).** Whenever an incremental's last event was not a commit the compactor could hold back, collapsed rows landed last at their first positions. The rewritten incremental then ended below its own EndPosition. Restore and `sync from-backup` refused it as truncated (`SLUICE-E-BACKUP-INCOMPLETE`) although nothing was lost. Two inputs reach that: every trigger-CDC chain, which carries no transaction markers, and a MySQL/MariaDB window ending on a TRUNCATE, which the binlog reader emits outside any transaction. The rewrite now closes such an output with an empty begin/commit pair at the original stream's last position. It is never stamped past what the original recorded, so an input that was already short is still refused, and an input ending inside an open transaction never gets it. A window ending on a bare transaction begin is now compacted with the begin held back, so it stays restorable. Chains an earlier release compacted stay refused, because the chain cannot show whether a collapsed tail was dropped or not. The refusal names compaction as the likely cause, and the remedy is a new full backup. Pinned by `TestSmartCompaction_HealthyFramedTailsStayRestorable` and `TestSmartCompaction_RefusedRunLeavesNoMergedCopy`. **Affected releases:** written on v0.85.0 through v0.156.11. Refused by restore since v0.99.222.

**`sync from-backup` no longer refuses a DDL-only `backup stream` rollover (LOW, loud, no data loss).** Such a rollover writes one change chunk with no records and records its StartPosition as its EndPosition. Chain restore accepted it, but the broker's tail check lacked restore's EndPosition = StartPosition exemption and refused it as truncated (`SLUICE-E-BACKUP-INCOMPLETE`). Fixed by the shared `EndPositionUnreached` predicate. Pinned by `TestRolloverWindow_SchemaSnapshotDoesNotMoveEndPosition`, through the broker. **Affected releases:** v0.117.0 through v0.156.11.

## Changed

**Performance: on the default lane apply path, a barrier now commits once instead of twice (ADR-0190 Amendment E; perf-parity GAP #48).** A barrier is every keyless change, every primary-key-changing update, a schema snapshot, and a `Truncate` on a Postgres target. The coordinator used to persist the barrier's checkpoint (its source transaction's start) in a transaction of its own before applying it. That checkpoint is now written inside the barrier's own target transaction, after its data and apply marks, as the last statement. It reaches `sync start`, `sync from-backup` and chain restore's incremental replay, all of which run lanes by default. There is no flag. `--apply-concurrency 1` (serial apply) is unchanged. Measured with `benchmarks/fencebench` on workload D (half the rows primary-key-changing), medians of three, every cell verified against the source by an independent full-row hash. Figures are source transactions per second:

| Pair | before (lanes) | after (lanes) | speed-up | after ÷ serial |
|---|---|---|---|---|
| MySQL → Postgres | 103.4 | 134.5 | 1.30× | 0.58× |
| Postgres → Postgres | 105.2 | 135.3 | 1.29× | 0.57× |
| MySQL → MySQL | 35.4 | 48.9 | 1.38× | 0.63× |
| MySQL → Postgres, 5 ms added latency | 12.4 | 14.8 | 1.19× | 0.55× |

Workloads without barriers, and the serial path, are unchanged within the harness's noise. **The delivery guarantees are the two-commit order's.** Barriers that write apply marks are applied exactly once. Barriers that cannot write them are at-least-once (keyless) or fail loudly (a key change). Two behaviours keep that true. When a barrier's checkpoint is the run's first position write, its restart sweep no longer drops the apply mark of a transaction the run is re-applying. Without that, a crash before the next checkpoint would duplicate a keyless row, on the untrusted-mark path (`APPLY-MARK-UNTRUSTED`, expected on a sharded VStream source). This also covers `--exactly-once-lanes`' folds. And a barrier that fails while the run is still live, transient errors included (a tx-killer, a reparent, a statement timeout), now makes one best-effort attempt to persist its transaction's start before the run stops, so the retry replays from there rather than from the previous checkpoint. The attempt uses the same connection pool, so after a reparent or a dead connection it usually fails too: that is logged at WARN and the retry replays from the previous checkpoint, as a kill would. It is skipped when the failure was in the barrier's COMMIT step, whose outcome is unknown, so a commit that lands late is not counted twice. A cancelled run writes nothing, which leaves the same replay as a kill at that instant. A MySQL-family `Truncate` keeps the two commits, because MySQL commits implicitly around DDL. Pinned by `TestLaneBarrier_FoldIsOneTransaction` (both engines, every barrier kind), `TestLaneBarrier_MySQLTruncateDeclines`, `TestLaneBarrier_UntrustedReloadFoldKeepsOwnMark` (real Postgres and MySQL, with the two-commit order as control), `TestTracker_SweepSparesAnOpenTransaction`, `TestOrchestrator_BarrierFoldFailureClaimsNothing`, `TestOrchestrator_BarrierIssuesNoSynchronousCheckpoint` and `TestBroker_BarrierFoldKeepsTheParentToken`, plus two new cells in the crash-mid-transaction suite, registered on every pair.

## Known residuals

These are filed in `docs/dev/audit-backlog.md` (the F-E1 section) and ADR-0190 §E.14, and open.

- **Shape B is judged only on a Postgres-to-Postgres chain restore or broker.** Ordering positions needs the source engine's order, and only Postgres declares one. A Postgres chain restored or replayed into MySQL is not checked for shape B, and neither is `backup verify` on any chain. Smart compaction judges B only when the chain's catalog records Postgres as its source.
- **No repair of a refused chain.** Dropping the duplicated transaction could repair shape A on re-delivering sources and shape B exactly. This release does not implement it, and a MySQL file/pos chain with a severed tail cannot be repaired. The remedy is a new full backup.
- **`sync start --position-from-manifest` on a chain whose final incremental ends inside a transaction** (old binaries only) resumes mid-transaction and re-delivers that transaction onto a restore that already holds its start. Chain restore WARNs, but the resume does not refuse.
- **SIGTERM inside a transaction abandons the window rather than draining it.** Draining on SIGTERM would need the CDC pump and every in-window store write moved off the cancelled context. It is not implemented. See **Compatibility** for the cost.
- **Unverified premises.** The 60 s stop drain assumes an open transaction the stream is receiving has already committed at the source. That is pinned for Postgres and unverified for the MySQL/MariaDB binlog and VStream. If it is wrong, a stop waits out the budget and abandons the window, which costs a re-read and never commits a severed window. Shape B's no-false-refusal argument assumes Postgres logical decoding emits in commit order. If it does not, the check refuses loudly. Whether VStream frames the TRUNCATE it emits from a DDL event was not verified. The compaction backstop covers it either way.
- **Neki.** The barrier fold on a PlanetScale Postgres (Neki) target is recorded against the Neki Tier-3 pass and was not measured. The F-E1-SHARDED-ROUTING Neki premise was corrected in this range: a multi-shard Neki target accepts a unique constraint that omits the shard key and enforces it only within a shard. So the Postgres replay-key probe needs a shard-key rule it does not have yet. This is unmeasured through sluice.
- **Still open from v0.156.11:** F-E1-KEY-REUSE-REPLAY, F-E1-ROTATED-SEGMENT-OVERLAP, F-E1-COARSER-TARGET-KEY and the steady-state half of F-E1-SHARDED-ROUTING. **Next:** exactly-once broker replay (ADR-0191, design accepted), which gives every broker change an apply identity.

## Compatibility

**New refusals of existing chains, with no override:**
- Chain `restore` and `sync from-backup` refuse a chain carrying shape A or C, or B on a Postgres-to-Postgres restore or broker. Shapes A and B refuse with `SLUICE-E-BACKUP-CHAIN-SEVERED-TRANSACTION`, shape C with `SLUICE-E-BACKUP-INCOMPLETE`, both exit 3, before anything is applied. Chain restore refuses on a finding anywhere in the chain. The broker refuses only on a link it has not applied yet. **Any Postgres chain that spans a resume written before v0.138.0 carries shape B** and will be refused by a Postgres chain restore, and by a broker that has not applied the affected link yet. The remedy is a new full backup.
- `backup verify` now reports a chain carrying shape A or C as failed, where it used to report it healthy.
- `backup compact --smart-compaction` refuses a chain carrying shape A, or B on a Postgres source, on an incremental it would rewrite. It also refuses a chain whose recorded source engine it does not know (`SMART-COMPACTION-SOURCE-ENGINE-UNKNOWN`). `--smart-compaction-off` compacts either chain without rewriting it.

**`backup stream` stop and cancel semantics:**
- `backup stream stop` (the command and the stop file) no longer stops the stream the moment it is seen while a source transaction is open. It waits for that transaction's commit, for up to 60 s or 1,000,000 changes (fixed defaults, no CLI flag). If the budget runs out, the stream still exits 0, and that window is not committed but read again by the next run. `backup stream stop` itself returns once it has written the request, so a supervisor must wait for the stream process to exit (up to about 60 s plus the commit) before signalling it.
- SIGTERM/SIGINT inside a source transaction exits 0 without committing the in-flight window. It used to commit the chunks stored so far. On a busy source, where a cancel almost always lands inside a transaction, that discards up to a full window of work (`--rollover-window`, default 5 minutes or 100,000 changes) to be read again. A supervisor that restarts the stream more often than one window never advances the chain: every run exits 0 with only the `BACKUP-WINDOW-ABANDONED-OPEN-TRANSACTION` WARN. To stop cleanly, run `sluice backup stream stop` first, and signal the process only once it has exited (for example as the unit's `ExecStop`).
- One-shot `backup incremental` now exits 1 with `BACKUP-WINDOW-ABANDONED-OPEN-TRANSACTION`, writing no manifest, when its source stream closes inside a transaction. It used to exit 0 with a severed incremental. Re-run it.

**Lane barrier:** the folded checkpoint is default-on with no flag. An engine handed a checkpoint for a barrier kind it does not fold refuses with `BARRIER-FOLD-NOT-TRANSACTIONAL`. That is a coordinator-defect tripwire, and a MySQL-family `Truncate` is declined before it can fire.

**Otherwise a drop-in.** No flag was added, removed or renamed, and no backup-format, manifest or control-table schema changed.

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale, a billable cluster), `d1verify` (live Cloudflare D1) and `nekiverify` (a billable Neki cluster) suites were not dispatched, because each needs live infrastructure and runs only on the operator's call. What that leaves unmeasured live:
- **PlanetScale MySQL / Vitess:** the barrier fold through PlanetScale's vtgate (measured on vttestserver, including the control-keyspace torn-commit case), and the stop drain's "already committed" premise on a VStream source.
- **Neki:** the barrier fold on a Neki target (§E.14 defers it to the Neki Tier-3 pass), and the shard-key exposure of the Postgres replay probe.
- **D1:** D1 is a source only, and this release changes no D1 code. A trigger-CDC `backup stream` from live D1 is exposed here only to the failed-flush drain loss and the marker-less smart-compaction tail fix. Both are pinned on local fixtures, not against live D1.

## Who needs this — action required

**Upgrading stops new severed chains and refuses affected old ones. It does not repair a target an earlier release already restored or replayed from one, and it does not make an affected chain replayable.**

- **Anyone who ran `backup stream` and ever stopped or restarted it** (`backup stream stop`, the stop file, SIGTERM/SIGINT, a supervisor restart), or whose source stream ended while transactions were being captured, on v0.19.0 through v0.156.11, and then restored that chain or replayed it with `sync from-backup`. First run `sluice backup verify` on the chain with this release (with the key material if it is encrypted). A shape A or C refusal means the chain is affected. Then compare each target with its source using `sluice verify --depth count` (or `--depth sample`). A target count above the source's on a keyless table means duplicated rows. A cancel that logged `drain-flush failed` is the cancel-drain loss on any engine. A count below the source's on any table means lost changes: a key-reusing transaction, the MySQL file/pos ROWS-event loss, or the cancel drain's lost transactions, which can reach any table on any engine, trigger-CDC included. Replace an affected chain with a new full backup, and rebuild or correct the affected target tables.
- **Postgres chains written before v0.138.0 that span a resume** carry shape B, which `backup verify` does not judge. Compare any keyless table, and any table touched by a key-reusing transaction, with the source.
- **Anyone who ran `backup compact --smart-compaction` on such a Postgres chain and then restored or replayed it** (v0.85.0 or later). Compare keyless tables and key-reusing transactions with the source for rows applied twice. Also compare keyed tables whose rows are deleted soon after insert, such as queue tables, for rows the source deleted that the target still holds. Take a new full backup.
- **Brokers (`sync from-backup`) running over an affected chain:** after the upgrade they WARN `CHAIN-APPLIED-SEVERED-TRANSACTION` on links already applied, naming the links to compare with the source, and refuse when they reach an affected link they have not applied. Grep the broker log for that marker, then compare the named tables as above.
- **Supervised `backup stream` deployments:** switch the stop path to `sluice backup stream stop`, waiting for the process to exit, before any signal. Otherwise frequent restarts can stop the chain advancing (see **Compatibility**).
- **Everyone else:** upgrade, nothing to check. Lane-apply users get the barrier speed-up with no action.
