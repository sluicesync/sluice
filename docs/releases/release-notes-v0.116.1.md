# sluice v0.116.1

**CRITICAL fix — a regression sluice shipped in v0.116.0. `sluice restore` of a PostgreSQL-sourced backup into a MySQL-family target refused EVERY `json[]`, `jsonb[]` and `bytea[]` column with `SLUICE-E-VALUE-UNREPRESENTABLE`, exited non-zero and left the table created and EMPTY — including for chains taken by EARLIER releases, so operators who upgraded found backups they already held stopped restoring. v0.116.0 is the only affected release, the archives are intact and nothing was lost. Drop-in upgrade from v0.116.0 and from anything older: no flag added, renamed or removed, no error code added or removed, no change to the archive, manifest or resume-state formats. Three behaviour changes ride along and are named in Compatibility — a NEW pgtrigger change-log-sequence refusal, a MySQL `backup full` against a binlog-less source that now records an empty position instead of a plausible-looking one, and a cross-engine retarget that now populates `ir.Column.SourceColumnType`.**

The restore regression is the reason this release exists, and the way it was missed is the transferable part. v0.116.0's leaf policy for MySQL array elements is correct and stays: it dispatches on the element FAMILY and refuses rather than guessing when it cannot resolve one. What nobody checked was whether every lane still HAD an element family to hand it. `migrate` does, because the schema its row writer holds is the source's own. `restore` did not, because it puts the manifest's schema through `translate.RetargetForEngine` first — and that pass rewrote `ir.Array{Element: X}` to the MySQL-shaped `ir.JSON{Binary: true}` and recorded nothing, dropping X one step before the writer asked for it. Identical columns, identical values, identical writer, opposite outcomes, decided by a schema pass one lane runs and the other does not. The rest of the release is four invariant closures worked out of the audit backlog — three of which turned out to differ from how they were filed, in both directions — and one new CI gate.

## Fixed

**`sluice restore` and `chain restore` of a PostgreSQL-sourced chain into MySQL, MariaDB, PlanetScale or Vitess refused every `json[]`, `jsonb[]` and `bytea[]` column and restored zero rows (Bug 232).** Restore runs the manifest's schema through `translate.RetargetForEngine` before handing it to the row writer; MySQL has no array type, so `retargetTable` rewrote the column's `ir.Array{Element: X}` to `ir.JSON{Binary: true}` and kept no record of X. v0.116.0's `arrayLeafForJSON` resolves the element family from the column's `Type` **or** its `SourceColumnType`, found neither, and correctly took the "cannot resolve, will not guess" refusal. The element type was in the manifest the whole time (`"kind":"Array","element":{"kind":"JSON"}`); only the retarget had thrown it away. **Only the two `[]byte`-leaf element families dispatch on the element type at all**, which is why the string- and native-leaf array families in the same table restored fine and nothing looked broken until an operator hit a document or a blob array. The fix parks the pre-rewrite type in `ir.Column.SourceColumnType` — the field that already carries exactly this ("what did sluice replace here?") for `--type-override`, and the pair the MySQL writer already consults — and an override that fired first is never clobbered, because it recorded the operator's true source type and the retarget's would be one step nearer. **Fixing it in the translate pass rather than inside restore is what makes `restore`, `chain restore`'s full leg and the from-backup broker's initial full load agree with `migrate` in one place** instead of three. **Affected releases: v0.116.0 only** — `arrayLeafForJSON` was introduced by `f67dd126`, first tagged v0.116.0, and v0.115.0 restored all of these columns (with the base64 rendering that release still had). **The manifest wire has never carried `SourceColumnType` and the archive format is unchanged**, so a chain written by any older binary is shape-identical here and the restore lane re-derives the provenance locally rather than trusting what an old binary happened to record; verified out of band by restoring a real v0.115.0-written chain with the fixed binary, which is Bug 232's reported population.

**The refusal's TEXT was wrong too, and that is fixed as a separate defect rather than being made moot by the value fix.** It asserted "this is the continuous-sync lane, where the applier reads column types from the TARGET" and prescribed `sluice migrate` — printed during a `restore`, which has no CDC lane at all and cannot be replaced by a command that cannot read an archive. Which lane it is, is now DERIVED instead of asserted: a column that is (or started as) an `ir.Array` came from a lane holding a real source schema and gets its own refusal naming a sluice defect, while a column with no array provenance is the applier's, whose target-derived descriptors MySQL's schema reader never gives an `ir.Array`. The applier text now says CHANGE-APPLIER lane and names all three of them — continuous sync, a chain restore's incremental replay, and the from-backup broker's — instead of claiming to be `sync`, and its remedy names the PROPERTY that decides the answer (a lane that reads the SOURCE schema: `migrate`, a `sync` cold copy, a `restore` bulk load) rather than one command.

**The sibling sweep is carried in the commit, lane by lane, with where each one's column descriptor comes from.** Every source-schema lane — migrate bulk copy including the parallel and chunked writers, `sync` cold start single-DB and multi-DB, `schema add-table` — was already correct and is unchanged. `restore`, `chain restore`'s full leg and the from-backup broker's cold start were the bug and are fixed by the one change. The two REPLAY appliers (a chain restore's incremental leg and the broker's) read descriptors from the target and genuinely cannot resolve the family, so they still refuse loudly by design — and they are now NAMED in the preflight's scope section, which listed neither. What pins it is a parity gate that builds its restore-lane column by running the REAL retarget and compares it against the migrate lane for every element family in a roster derived from the Postgres reader × {1-D, 2-D, NULL element, empty}, plus an integration test that goes PG → backup → restore → MySQL through the migrate sibling's fixture and its assertion helper unchanged — so the independent expected value is PostgreSQL's own `::text`, `encode(…,'base64')` and `array_dims`, never sluice's reporting and never the archive's own recorded count.

**v0.116.0's item 108 refused the exact case it shipped to adopt: a leftover PlanetScale dev branch whose deploy request was MID-DEPLOY (Bug 231).** `classifyAdoption` ORed PlanetScale's `deployable` flag into the adoption verdict as a second, "independent" refusal signal, on the premise that a request the API would still accept a `Deploy` call for cannot be one it is already deploying. **The premise is false — the live API reports `deployable=true` for the whole duration of a running deployment** — so a leftover whose deploy was in flight was graded "never deployed" and refused, which is the one shape item 108 exists to join. Measured by the v0.116.0 regression cycle on live PlanetScale: deploy request #3 read `deployment_state "in_progress", deployable=true` and was refused at `20:31:07`, strictly between PlanetScale's own `started_at 20:31:03.962Z` and `deployed_at 20:31:11.393Z`. The other two leftover shapes behaved correctly — an already-deployed leftover adopts and finalizes, a never-issued one refuses — which is why the release's own live validation passed. **LOUD, zero data loss:** nothing was written and no schema reverted; the cost is that the in-flight deploy is not joined, and on a real build that is the multi-hour VReplication index build item 108 exists to rescue. For a `deployment_state` sluice documents, the state table is now the whole verdict; `deployable` is consulted only where the table has nothing to say — an UNDOCUMENTED state — and that case gets its own verdict rather than borrowing the never-deployed one. **Affected releases: v0.116.0 only** — `classifyAdoption` was introduced by `2f28d4ab`, first tagged v0.116.0.

**The refusal's message was the worse half of Bug 231, and it is fixed as its own defect.** It printed `deployment_state "in_progress"` and, in the same sentence, *"Nothing is deploying, so the branch is safe to delete"* with the `pscale branch delete` spelled out — advice which, believed, discards a healthy in-flight deploy. **A message must not assert a condition the evidence it just printed denies.** The delete-is-safe claim now has exactly one renderer, and a gate greps for that literal phrase across every state × every `deployable` response shape × `open`/`closed`, failing when a refusal makes the claim from a state that does not establish it. The refusal for a state sluice does not recognize says so and names no branch delete at all. Swept in the same pass: the closed-but-unrecognized-state refusal no longer asserts "its schema change is NOT applied" either, since an unknown state does not establish that. **Why the 20-state matrix did not catch it is the transferable part** — it graded all twenty states and asserted its key set equalled the enum in both directions, and every row carried a hard-coded `deployable` value taken from a comment about the live API. The fake control plane encoded the same premise. **The matrix was complete along the axis it enumerated and blind along the axis it assumed.** `deployable` is now an enumerated shape axis (absent / nested / top-level / both) with the verdict required to be invariant across it for every documented state, and the fake serves the live shape with a pin that fails if it stops.

**A tampered `postgres-trigger` change-log id sequence could allocate an id the poller silently never emits, and is now refused at both CDC doors.** The gap-free poll consumes ids strictly ABOVE a watermark, and that watermark floors at 0 — an empty change log starts the stream at 0, and a negative cold-start anchor is clamped to 0 — so any id at or below the floor is skipped on the first poll and never comes back. The clamp's own comment asserted this could not happen because "BIGSERIAL never allocates 0 (it starts at 1)". **Ground-truthed on PostgreSQL 16, that is false of a sequence anyone can `ALTER`:** `MINVALUE 0 RESTART WITH 0` really does allocate id 0 and `MINVALUE -100` really does allocate negatives. Re-deriving the class found the already-refused `CACHE > 1` was one of FOUR settings that admit such an id, so the preflight now grades all four — `CACHE`, `MINVALUE`, `INCREMENT`, `CYCLE` — at `openCDCReader` and at `OpenSnapshotStream`, each with its own message and its own `ALTER SEQUENCE` remedy. **The scope is stated where the check is defined, because the name reads broader than the truth:** this grades the sequence's CONFIGURATION at open, and it cannot see a mid-stream `ALTER SEQUENCE … RESTART WITH <low>`, which re-issues low ids under a perfectly legal configuration. **A sibling is filed rather than fixed and is named here:** `sqlite_sequence` is writable, so the same tamper is constructible on the `sqlite-trigger` and `d1-trigger` engines and is ungated there.

**A MySQL or MariaDB source with binary logging OFF recorded a well-formed, resumable-LOOKING, empty GTID cursor on its backup manifest.** `CaptureBackupPosition`'s doc closed with "the binlog stream is always available to a privileged connection" — never checked, and false. The two arms disagreed about it: the file/pos arm already refused loudly, because `SHOW MASTER STATUS` returns zero rows on such a source, while the GTID arm read an EMPTY `@@global.gtid_executed` and encoded it into a perfectly well-formed position token, producing a backup that verifies clean and resumes nothing. **Both spellings of that shape are reachable and both were booted and read live: MySQL 8.0.46 ACCEPTS `--skip-log-bin --gtid-mode=ON --enforce-gtid-consistency=ON` and reports `gtid_mode=ON` with `log_bin=0`; and MariaDB needs no contrivance at all, because `gtidModeOnFor` returns true for that flavor UNCONDITIONALLY, so every binlog-less MariaDB took the GTID arm.** A `@@GLOBAL.log_bin` preflight now runs before either arm at BOTH capturers — the schema-reader one and the conn-scoped snapshot-anchored one, which had the identical defect — and a binlog-less source records the empty `ir.Position` plus a WARN naming the consequence and the remedy. Refusing was considered and rejected: a standalone `backup full` of a binlog-less source (a reporting replica, a restored dev copy) is a legitimate thing to want, and the empty position already has meaning downstream — `backup incremental` WARNs that the chain will start from CDC's current position, and `sync start --position-from-manifest` refuses the manifest outright. **Affected releases: the MariaDB half from v0.99.271 (`0eaf1573`, which introduced the unconditional-GTID arm) through v0.116.0; the MySQL half — which needs the deliberate `--skip-log-bin --gtid-mode=ON` pairing — from v0.17.2 (`1ad2168c`, where `backup full` first recorded an `EndPosition`) and v0.18.0 (`c0e19a4b`, the snapshot-anchored capturer) through v0.116.0.**

**Two more premises were re-derived and both survived, which is worth recording because one of them was filed as a gap that had already been closed.** The mydumper metadata-count tripwire — "real mydumper writes a row count this parser recognises, and it is exact" — is TRUE, and is now ground-truthed against a real mydumper v1.0.3 dump with `COUNT(*)` on the live source as the independent number, rather than against the hand-written fixtures every previous pin used. That distinction is the whole point: a changed key or section spelling would have left the tripwire inert everywhere with every unit pin still green. The D1 replica-routing premise — that the CDC poll never reaches a lagging read replica, whose exactly-once `id > watermark` invariant would wobble against one — is TRUE and structurally unreachable, but it rested on ABSENCE, which is exactly where an attractive latency change would land unnoticed. It is now pinned rather than asserted (the single request builder's path, its two headers, and the fact that no DSN parameter can re-point the endpoint), **and the one residual is stated at the site in those words: that Cloudflare serves the D1 REST `/query` endpoint from the primary is THEIR contract, an UNVERIFIED PREMISE no test here can hold them to.**

**Roadmap status markers said "unreleased" long after the code shipped, and CI now fails when they do.** Nothing in the release flow ever updated them — the flow writes `CHANGELOG.md` and `docs/releases/`, and the staleness sweep runs when a human asks — while `git` has known the answer for free the whole time. A post-release sweep found five stale markers on 2026-08-07: items 152, 150 and 108 read unreleased minutes after v0.116.0 shipped, item 75 had read unreleased across fourteen minor versions since v0.102.0, and item 82 across thirteen. **The new gate then immediately found four more nobody had listed** — items 103, 104, 106 and 107 still read "ships in v0.104.x" twelve minor versions after those tags — and all of them are corrected here. It fires on either of two independent signals: a commit SHA cited inside the status marker, or the blame commit of the marker's own line, and **the second is the load-bearing one** (only one of the original four cited a SHA, so a SHA-only gate would have caught one in four while being named for all of it). Blame is an upper bound rather than the release, so the failure text says "no later than" and points at `CHANGELOG.md`. Its own hazards are handled rather than assumed: `ci.yml`'s Test job now checks out full history and tags, because under the default depth-1 tagless checkout `git tag --contains` answers empty for every commit and the gate would pass everything forever — **and the gate REFUSES loudly when tags are invisible rather than skipping**, so the missing checkout depth goes red by design instead of going quiet. "Unreleased" is still a legitimate state and zero pending items is a legitimate result; the marker vocabulary was derived by grepping every heading line in the roadmap's whole history rather than from the spellings anyone remembers; and the classifier fixture is built from PRE-fix marker text out of `git log -p`, so it cannot go self-referential the way item 104's frozen golden did.

## Compatibility

**No breaking changes. No flag was added, renamed or removed. No error code was added or removed. Nothing about the on-disk formats — backup chunks, chain manifests, resume state, the schema wire — is touched, and no backup chain is repartitioned.** This is a drop-in upgrade from v0.116.0 and from anything older, and a v0.116.0-written chain and a v0.115.0-written chain both restore identically on it.

**A `postgres-trigger` CDC stream now REFUSES at open if its change-log id sequence has `MINVALUE` below 1, a non-positive `INCREMENT`, or `CYCLE`. This is new in this release and it is a limitation, not only a fix.** `sluice trigger setup` creates the column as `BIGSERIAL` — `CACHE 1`, `MINVALUE 1`, `INCREMENT 1`, `NO CYCLE` — so a correctly-provisioned source is unaffected and pays nothing, but a source where someone deliberately configured the sequence with `CYCLE`, a descending step or a low `MINVALUE` will now stop at `openCDCReader` or `OpenSnapshotStream` with an `ALTER SEQUENCE` remedy where it previously ran. **The `CACHE > 1` arm is NOT new — it has refused since v0.108.0** (`79e469e7`); only the `MINVALUE`, `INCREMENT` and `CYCLE` arms are added here. The check is configuration-only and cannot see a mid-stream `ALTER SEQUENCE … RESTART WITH <low>`, and it does not reach the `sqlite-trigger` / `d1-trigger` engines, whose ids come from SQLite's own rowid machinery; both limits are stated where the check is defined.

**A MySQL-family `backup full` against a source with `log_bin=OFF` behaves differently, in two directions depending on which arm it used to take, and the recorded artifact changes.** On the GTID arm (any binlog-less MariaDB, or a MySQL configured `--skip-log-bin --gtid-mode=ON`) the backup used to SUCCEED and record a well-formed-looking `{"mode":"gtid"}` token that resumes nothing; it now succeeds and records an EMPTY `EndPosition` plus a WARN. That is the fix, and it means a manifest taken on this release carries a different value for that source than one taken on v0.116.0 — an empty position is the truthful one, and it is what makes `sync start --position-from-manifest` refuse the manifest instead of silently resuming from nowhere. On the file/pos arm (`gtid_mode=OFF` and `log_bin=OFF`) the backup used to FAIL outright with "master status returned no rows (binlog disabled?)" and now SUCCEEDS with the same empty position and WARN. **Refusing was considered and deliberately rejected** — a standalone full of a binlog-less source is legitimate — so if you were relying on that failure as a guard that your source had binlogs on, the WARN is now what carries that signal.

**A cross-engine retarget now populates `ir.Column.SourceColumnType` where it previously left it nil, and every consumer of that field was checked.** The field does NOT ride the wire — `columnWire` has no slot for it and gains none — so no persisted artifact changes and a chain written by an older binary arrives with it nil exactly as before; the restore lane re-derives it locally from the manifest's source-native IR. The one consumer that a newly non-nil value could have flipped is MySQL's `columnIsNativelyBinary`, which reads nil as "natively binary" — it only asks about a column whose post-rewrite `Type` is already binary, and **no retarget rule produces a binary type**, which is a fact about that rule table and is therefore pinned with an anti-vacuity floor rather than asserted. The two schema-comparison consumers (`ir/diff`'s drift compare and the shard-consolidation probe) already nil the field before comparing. The lanes that only DDL-emit a retargeted table — the broker's and chain replay's schema-delta apply, schema-forward — are unaffected because schema writers emit from `Type` and ignore this field. **The one user-visible effect is the intended one:** array element values that v0.116.0 refused on the restore lane now land, byte-identical to what `migrate` produces for the same source column.

**One thing the fix does not change, stated so it is not read as broader than it is:** a chain restore's INCREMENTAL replay leg and the from-backup broker's incremental replay still refuse a `json[]`/`jsonb[]`/`bytea[]` value, because those lanes read column descriptors from the TARGET and genuinely cannot resolve the element family. The FULL leg of both is fixed, so a restore reaches its data; what remains is a late, loud error on an incremental, never a silent one, and it is now named in the preflight's scope section instead of being left implied.

## Who needs this — action required

- **Anyone who upgraded to v0.116.0 and holds a PostgreSQL-sourced backup chain containing a `json[]`, `jsonb[]` or `bytea[]` column, intending to restore it into MySQL, MariaDB, PlanetScale or Vitess. Upgrade and re-run the restore. There is nothing to re-verify and nothing to repair.** This was a LOUD refusal, not silent loss: the run exits non-zero with `SLUICE-E-VALUE-UNREPRESENTABLE`, the target table is created and left EMPTY, and **the archive was never read past the refusal and is completely intact**. No restore has ever reported success over a partially-restored table on this defect. It applies to chains taken by ANY release, including ones written before v0.116.0, because the loss happened at restore time and not at backup time — which is exactly why upgrading appeared to break backups that had worked for months. Restoring the same chain into a PostgreSQL target was never affected, and `sluice migrate` on the same columns was never affected.
- **Anyone who worked around it by restoring into PostgreSQL and migrating onward, or by excluding those tables: you can go back to a direct restore, and the values you already landed are fine.** The restored values on this release are byte-identical to what `migrate` produces for the same source column, ground-truthed against PostgreSQL's own rendering across every element family × {1-D, 2-D, NULL element, empty}. If you restored into PostgreSQL and then migrated to MySQL on v0.116.0, that path was correct and needs no audit.
- **Anyone whose PlanetScale run on v0.116.0 refused a leftover dev branch as "never deployed" while its deploy request was actually still deploying. Do NOT delete that branch on the strength of the message you got; upgrade and re-run.** The refusal printed `deployment_state "in_progress"` and told you the branch was safe to delete in the same sentence; following it would discard an in-flight build (PlanetScale's own API refuses that delete while a deployment runs, which is the platform covering for sluice). The re-run adopts the running deploy request and joins the same poller. **Nothing to re-verify — no data was written and no schema was reverted.** Affected: v0.116.0 only.
- **Anyone running `postgres-trigger` CDC whose change-log id sequence has been `ALTER`ed away from `BIGSERIAL` defaults. Read the Compatibility note BEFORE upgrading: your stream will stop at open rather than start.** The refusal names the setting and the exact `ALTER SEQUENCE` to run. **If your sequence has ever carried `MINVALUE` at or below 0, a non-positive `INCREMENT`, or `CYCLE`, then changes captured at or below the watermark floor were silently never emitted while it did — those rows are missing from the target and nothing reported it.** Re-verify that table's contents against the source for the period the sequence was in that state, and treat the stream as needing a fresh cold start rather than a warm resume. A source provisioned by `sluice trigger setup` and never altered was never exposed and needs nothing.
- **Anyone who took a `backup full` of a MariaDB source, or of a MySQL source configured `--skip-log-bin --gtid-mode=ON`, and intends to chain an incremental off it or resume `sync` from it. Check `@@GLOBAL.log_bin` on that source; if it is 0, the manifest's recorded `EndPosition` is a cursor that resumes nothing.** The manifest LOOKS resumable — a well-formed GTID token — and `backup verify` has nothing to say about it, because the position was never wrong in a way a checksum can see. **The full backup's DATA is complete and correct; what is worthless is the resume anchor.** On this release the same source records an empty position and warns, `backup incremental` tells you the chain will start from CDC's current position, and `sync start --position-from-manifest` refuses the manifest outright. To get a chainable full, enable binary logging on the source (`log_bin=ON`, `binlog_format=ROW`, `binlog_row_image=FULL`) and take the full again. **Affected: MariaDB from v0.99.271 with no unusual configuration; MySQL from v0.17.2 only under the deliberate `--skip-log-bin --gtid-mode=ON` pairing.**
- **Anyone who read a roadmap item's status marker to decide whether something is built. Eight of them were wrong and are corrected here.** Items 152, 150 and 108 read "unreleased" after shipping in v0.116.0; item 75 had read unreleased across fourteen minor versions and item 82 across thirteen; items 103, 104, 106 and 107 read "ships in v0.104.x" twelve minor versions after those tags. Nothing in the code changed for any of them — the markers lagged. CI now fails on a marker that claims unreleased once a tag contains its commit.
- **Everyone else: nothing to do.** A run with no PostgreSQL array column bound for a MySQL-family target through a `restore`, no PlanetScale deploy-request leg, no `ALTER`ed pgtrigger change-log sequence and no binlog-less MySQL-family backup source is unaffected by every item on this list. The rest of this release is two premises confirmed and pinned, one residual stated as an UNVERIFIED PREMISE, corrected error text, and a CI gate that holds documentation to git.
