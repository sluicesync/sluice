# sluice v0.122.0

The second correctness batch from the 2026-08-11 blind audit, plus the follow-up its post-release sweep owed. Two silent value alterations are closed: the SQLite/D1 JSON decode silently rewrote invalid-UTF-8 text to U+FFFD before delivering it, and a PG→MySQL geometry carrying NaN/Inf coordinates stored silently as a poison value MySQL cannot read back. Also here: the trigger-CDC REPLACE implicit-delete capture blind spot is now named at setup with remedies, and v0.121.0's `max_error_count=0` clamp fix reaches its third and last consumer.

## Fixed

**SQLite and D1 text the JSON decode cannot represent faithfully is now refused loudly instead of being silently rewritten to U+FFFD (audit SQT-1).** `encoding/json.Unmarshal` never errors on invalid UTF-8 inside a string token or on a lone-surrogate `\u` escape — it silently substitutes U+FFFD per byte. SQLite TEXT is byte-agnostic and legally carries invalid UTF-8, the capture trigger and the D1 API pass those bytes through verbatim, and the local-file cold-start snapshot (a direct scan, no JSON) carries them faithfully — so the same logical row diverged between the snapshot and CDC phases at exit 0, in a form (valid UTF-8) no downstream check or target could refuse. The decode now refuses both vectors before Unmarshal, naming the remedy (store raw bytes as BLOB rather than TEXT, or repair the value at the source), and the refusal is batch-atomic on the CDC path: the poisoned poll batch is withheld and the watermark does not advance, so a repaired source resumes with nothing skipped — halted, never lost. One guarded extraction serves the sqlite-trigger CDC decode, D1 live rows, D1 staging, the D1 catalog scalars whose DEFAULT text feeds emitted DDL — and, after the pre-tag value-fidelity review caught a one-layer-up sibling, the d1-trigger transport's own change-log payload extraction, where an unguarded decode would have mangled the captured row images before the inner guard could see them. pgtrigger is exempt (Postgres text cannot hold invalid UTF-8 — the server validates) and the MySQL/Postgres engines are exempt (binary wire protocols, no JSON row decode). One premise is stated rather than claimed: whether Cloudflare's D1 API returns invalid-UTF-8 bytes verbatim is UNMEASURED against real D1 (marked UNVERIFIED PREMISE in the code, live-D1 pin filed) — if D1 mangles server-side, that loss happens upstream of any client guard. Affected releases: v0.99.143 (the D1 reader) through v0.121.0, with the sqlite-trigger and d1-trigger CDC lanes affected since v0.99.148/v0.99.149. Pinned at four layers including an end-to-end refusal on a real capture, every arm mutation-run with grep-verified mutants.

**PG→MySQL geometry with NaN or Infinity coordinates — including PostGIS `POINT EMPTY`, whose WKB representation IS a NaN/NaN point — is now refused loudly client-side instead of storing silently as a value MySQL cannot itself produce (audit SPAT-1).** sluice carries geometry byte-verbatim and MySQL performs no coordinate validation on raw internal-format inserts, so the poison landed at exit 0 and only surfaced on later access: `ST_AsText` returns NULL, coordinate accessors raise error 3037. Empty LINESTRING/POLYGON/MULTI* draw the server's own loud error 1416, so NaN/Inf coordinates were exactly the silent residue; PostGIS legitimately holds both, so any PG→MySQL run can feed one in (a PG round trip preserves the bytes, which is why the audit graded this HIGH rather than CRITICAL). A WKB scanner now walks every coordinate double across all 7 WKB families — nested collections included, honouring both the ISO Z/M/ZM and PostGIS EWKB dimensional spellings and both endiannesses — and refuses a non-finite coordinate with the existing `SLUICE-E-VALUE-UNREPRESENTABLE` code at the single write choke point serving all three paths: the batched INSERT core, the LOAD DATA geometry fallback, and the CDC applier. Structurally unparseable WKB refuses too rather than passing unscanned. Postgres targets are exempt by policy (PostGIS holds NaN/Inf/EMPTY natively) and SQLite targets store geometry as a byte-faithful BLOB with no server interpretation to poison. Affected releases: PG→MySQL geometry has written this way since it first shipped in v0.28.0, through v0.121.0. Pinned by a unit matrix over all families/dims/endiannesses, a 7-family real-server matrix, and a premise pin that MySQL still accepts the raw poison bytes when inserted directly (the fact that makes the client-side scan load-bearing); mutation-run.

**The REPLACE implicit-delete capture blind spot on the trigger-CDC engines is now named at setup, documented, and premise-pinned (audit SQT-2).** With `PRAGMA recursive_triggers` OFF — SQLite's default, per-connection on the application's own writers, outside sluice's control — the rows an `INSERT OR REPLACE`/`UPDATE OR REPLACE` implicitly deletes to satisfy a non-PK UNIQUE conflict fire no AFTER DELETE trigger: the delete is never captured and the target keeps the row forever, at exit 0. A PK-conflict REPLACE converges anyway (the captured insert upserts the same key), so the divergent class is exactly non-PK UNIQUE constraints — including inline UNIQUE columns and `UNIQUE ... ON CONFLICT REPLACE` clauses, under which even a plain INSERT takes REPLACE semantics. Trigger setup now emits one WARN per table carrying a non-PK UNIQUE index, naming the blind spot, the affected indexes, and both remedies: `recursive_triggers=ON` on every writing connection, or `ON CONFLICT DO UPDATE` upserts, which never implicitly delete (on D1 prefer the upserts — whether the pragma is settable through D1's bindings is unmeasured). This is deliberately a WARN and not a refusal, because every non-OR-REPLACE write replicates perfectly. It reaches sqlite-trigger and, through the shared installer, d1-trigger; pgtrigger is exempt (Postgres row-level triggers always fire) and the log-based CDC engines see the delete in the binlog/WAL/VStream regardless. The blind spot itself is an environmental property of SQLite present since the engines shipped (v0.99.148/v0.99.149) and it remains — what changes is that it is now loud at setup, documented in ADR-0135 and the operator CDC docs, and the environmental premise is pinned in both directions against the real engine so a SQLite behaviour change fails the build instead of silently orphaning the docs.

**The v0.121.0 `max_error_count=0` clamp-detection fix (COLD-1) now reaches its third and last consumer: the CDC-apply clamp WARN.** v0.121.0 moved the silent-clamp trigger to the uncapped `@@warning_count` in the two bulk write cores but its sweep missed the third SHOW WARNINGS consumer — the CDC apply path's clamp WARN still decided on the visible row count, so a server tuned with `max_error_count=0` silenced it entirely. Impact is bounded: WARN-only, reachable only under the explicit `--mysql-sql-mode=''` opt-in (strict mode refuses at the statement) — but it is exactly the sibling shape the sweep discipline exists to catch, and the enumeration is now complete in the commit: all three production consumers of the warnings read gate on `@@warning_count`, with the remaining visible-count reads documented as the fallback when that read itself fails. Found by the post-release learnings sweep the same day. Affected releases: the apply-path WARN has been suppressible this way since it shipped in v0.100.0, through v0.121.0. Pinned on a real server with `GLOBAL max_error_count=0` and the applier pool opened under the suppressed buffer; mutation-run in both directions.

## Compatibility

No error code, flag, or default changed, and no on-disk format changed shape — the geometry refusal reuses the existing `SLUICE-E-VALUE-UNREPRESENTABLE` code, and the SQLite/D1 refusal is a decode error carrying table/column/row context. **Drop-in upgrade from v0.121.0 and older.** Four behaviour notes: a write of a NaN/Inf-coordinate geometry (including PostGIS `POINT EMPTY`) into a MySQL-family target now refuses client-side where it previously stored a poison value, and structurally unparseable WKB refuses instead of passing unscanned; a sqlite-trigger/d1-trigger CDC batch or D1 read carrying invalid-UTF-8 TEXT or a lone-surrogate escape now halts loudly with the watermark unmoved, where it previously delivered rewritten text; trigger-CDC setup on a table with a non-PK UNIQUE constraint now emits one WARN naming the REPLACE blind spot and its remedies; and a MySQL CDC apply under `--mysql-sql-mode=''` against a `max_error_count=0` server now surfaces the clamp WARN it previously suppressed.

## Who needs this — action required

**Anyone who has migrated, synced, or restored PostGIS spatial data into a MySQL-family target** (any release since v0.28.0): if the source could hold `POINT EMPTY` or NaN/Inf coordinates, audit the target — poison rows are non-NULL geometry values where `ST_AsText(col)` returns NULL — and re-copy affected rows after upgrading; the source values are intact. **Anyone syncing from a sqlite-trigger or d1-trigger source, or reading from D1** (since v0.99.143), whose TEXT columns can carry invalid UTF-8: rows delivered through the CDC or D1 read path may hold U+FFFD-rewritten text diverging from the source (the local-file snapshot phase was always faithful; D1 API reads were affected on every path) — re-verify text values against the source. **Trigger-CDC operators whose applications use OR REPLACE writes on tables with non-PK UNIQUE constraints**: the target may retain rows the source implicitly deleted, for as long as the sync has run — re-verify row counts on the tables the new setup WARN names, and adopt one of its remedies. **Anyone running MySQL CDC apply under `--mysql-sql-mode=''` against a `max_error_count=0` server** (since v0.100.0): value clamps may have applied without their WARN — re-verify. If none of these describe your setup, the upgrade is a no-op.
