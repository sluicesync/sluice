# sluice v0.127.0

**The audit-close release — the entire 2026-08-14 repository audit is fixed and gated.** Every finding across silent-loss/security, architecture, testing/CI, and performance is resolved, and each one exits into a permanent gate rather than a promise, which is why this is a minor bump. The user-facing shape: MySQL's restore-injection immunity is now enforced by the driver instead of resting on the operator's DSN; a MySQL sync misrouted to a database or schema that does not exist now halts loudly instead of skipping every table at exit 0; `schema diff` stops both certifying a gutted `NOT IN` constraint as in-sync and phantom-reporting drift on constraints a migrate itself created (both directions now); warm-resumed sync into a pre-vindexed sharded Vitess/PlanetScale keyspace is no longer wrongly refused; and two VStream-source backup corner cases (a float-repair key collision and a dropped verbatim marker across compaction) that could silently write or blind the wrong record are closed. **Drop-in upgrade from v0.126.x — no operator action required, no schema/format/flag change.**

## Fixed

**MySQL's immunity to the restore-injection class is now ENFORCED, not left resting on the operator's DSN (audit H-3).** sluice's emitters produce one statement, and the restore path inlines recorded expression bodies (CHECK constraints, generated columns, defaults) verbatim into that DDL. go-sql-driver refuses a multi-statement `Exec` unless the DSN carries `multiStatements=true` — which sluice never sets, but which an operator's target DSN can carry and which sluice's `cfg.Clone()` otherwise preserved. So on a target whose DSN happened to set the flag, a tampered or corrupt manifest whose CHECK body appended `; DROP TABLE …` would execute as the restore role — the MySQL counterpart of the PostgreSQL C-1 bypass, one DSN parameter away. `openDB` now force-clears `MultiStatements` on every connection sluice opens, making the driver itself the door (Error 1064 on any second statement) regardless of the DSN; sluice has no code path that needs multi-statement execution on its own connections. Pinned by a cfg-mutation unit test and a live integration test that hands `openDB` a `multiStatements=true` DSN and proves the injected second statement is refused with the canary intact (anti-vacuity control: a raw connection on the same DSN does execute it). The backwards doc claim that "the pipeline appends `&multiStatements=true`" is corrected. The C-1 differential-lexer oracle was also widened to run its injection corpus through the INLINE `CREATE TABLE (… CHECK (<body>))` restore-emission template — the shape the restore path actually uses — not just the `ALTER TABLE ADD CONSTRAINT` wrapper it first pinned, with a per-template anti-vacuity floor.

**A multi-database sync misrouted to a non-existent target database/schema now halts loudly instead of silently skipping every table (audit M-2, silent-loss).** The C-11 unknown-target-table skip classifies a load failure by probing `information_schema` for the table — but an empty result is ambiguous: the table is missing, or the whole database/schema is. A namespace mapping that routes a source database to a target that does not exist therefore made every event for every table skip, WARN once per table, count in the ledger, and the stream exit 0 with positions advanced — the loud halt C-11 replaced, turned silent. Both engines now probe schema existence first: a present schema keeps the recoverable per-table skip; a missing one halts with a routing-fault error naming the database/schema and the mapping to fix. Pinned live on both engines (a routed-to-a-ghost-database event refuses loudly and records no skip), sibling-swept across MySQL and PostgreSQL, and mutation-run.

**`schema diff` no longer certifies a semantically gutted `NOT IN` CHECK as in sync (audit H-1, silent-loss).** The DIFF-2 NOT-pushdown fold (v0.126.0) normalized `NOT (v = 5)` onto `v <> 5` by negating the operator — correct for a scalar comparison, but INVALID across a quantifier. PostgreSQL renders `CHECK (i NOT IN (1,2))` as `CHECK (NOT (i = ANY (ARRAY[1,2])))`, and operator negation there yields `i <> ANY (ARRAY[1,2])` — a materially different predicate that *accepts* the very rows the source rejects (`i=1`, `i=2`). Both canonicalized equal through the fold, so a drifted or hand-gutted target constraint reported no drift. The pushdown now bails when either operand leads with a quantifier (`ANY`/`ALL`/`SOME`), leaving the `NOT` verbatim so the two constraints compare as the different things they are. Pinned with the exact measured PG rendering in both directions (the gutted pair reports drift; a scalar `NOT (v = 5)` still folds; a column merely named like a quantifier still folds), mutation-run, and grounded by an end-to-end migrate-then-diff gate that gut-edits a real `NOT IN` constraint and asserts the drift is reported.

**Continuous sync into a pre-vindexed sharded Vitess/PlanetScale keyspace is no longer over-refused (audit H-2).** v0.126.0's sharded-target door sat at `OpenSchemaWriter` — but that open is reached by many table-FREE paths, and critically by the continuous-sync schema-forward writer, which opens the target schema writer (to be ready to forward source `ALTER`s) even on warm resume and with `--schema-already-applied`. So a sync into a sharded keyspace whose tables the operator had already created and vindexed — an operator-confirmed supported flow — refused at stream start with `SLUICE-E-SCHEMA-TARGET-KEYSPACE-SHARDED`, a regression against a working configuration. The actual hazard is sluice CREATING a new vindex-less table (whose rows cannot route, Error 1173), so the door moved to the true chokepoint, `CreateTablesWithoutConstraints`: on a sharded keyspace it now refuses only when at least one table in the schema does NOT already exist on the target — naming the shards and the specific new table(s) — and passes when every table already exists, letting the `CREATE TABLE IF NOT EXISTS` phase no-op and sluice stream rows into the correctly-routed tables. This one chokepoint covers migrate's create phase, `add-table`, and broker reset uniformly; a shard-discovery failure still WARNs and proceeds. The state-store door (Bug 250) stays at `OpenMigrationStateStore` unconditionally, and `schema diff`/`preview` are read-only and no longer refuse a sharded target at all. A new AST roster gate (`TestShardedTargetDoorRoster_EveryCallSiteClassified`) enumerates every pipeline `OpenSchemaWriter` and `CreateTablesWithoutConstraints` call site and fails the build on an unclassified new one. Pinned live on a real 2-shard cluster and mutation-run.

**`schema diff` no longer phantom-reports drift on the `NOT IN` / `NOT BETWEEN` negation siblings a migrate itself created (audit M-1).** The DIFF-2 canonicalization folded `IN` / `BETWEEN` / `NOT`-over-a-single-comparison, but not their negation siblings, so a target migrate itself created reported drift on constraints that were byte-for-byte what sluice wrote. Measured on real MySQL 8.0 + PostgreSQL 16, the two catalogs store a negated CHECK differently: `x NOT IN (1,2)` reads back as PG's `<> ALL (ARRAY[1,2])`, and `x NOT BETWEEN a AND b` as PG's `(x < a) OR (x > b)`. The fold now covers both — the `<> ALL` → `not in (` arm (semantics-exact for the NULL-free list a CHECK carries) and a `NOT BETWEEN` → `x < a OR x > b` expansion matching PG's own stored form. The remaining De Morgan siblings stay LOUD phantom drift rather than risk the H-1 quantifier hazard, and are exempt with a written reason. Pinned with the measured rendering pairs verbatim and mutation-run.

**MySQL now exposes its CHECK-expression translator to `schema diff`, closing the PG→MySQL phantom-drift direction (audit M-5).** `ir.CheckExprDialectTranslator` — the optional surface that lets `schema diff` compare a foreign-source CHECK against the target catalog's read-back like-against-like — was implemented only by PostgreSQL's `SchemaWriter`. MySQL had the symmetric rewrite and applied it at DDL-emit time but never exposed it, so a PG→MySQL migrate reached the diff untranslated and phantom-reported drift in the MySQL-target direction (the architecture-side cousin of M-1). The MySQL `SchemaWriter` now exposes the same rewrite the emitter applies (declining a non-PG dialect; best-effort passthrough for untranslatable constructs), pinned at compile time and by unit test. The durable half is a sibling-roster Lint guard (`scripts/check-dialect-translator-roster.sh`) that derives its universe from the tree — every engine package with a `translateExprFor*` — and fails the build if one lacks the `ir.CheckExprDialectTranslator` pin, so no future translating engine can forget the exposure; it carries an anti-vacuity floor and was mutation-run (which caught a real vacuity hole in the first cut).

**A VStream float-repair key collision can no longer write one row's exact floats into another row's archived record (audit M-4, silent-loss).** `floatPatchKey` rendered a row's composite primary key as `%v` joined with a bare NUL byte — non-injective on a boundary shift: a NUL carried inside a PK value (which `utf8mb4_bin` and MySQL `VARCHAR` both admit) shifts the component boundary so `("a\x00","b")` and `("a","\x00b")` render identically. A collision merged two distinct rows' exact-re-read entries, and the patch then wrote one row's exact float values into the other's archived record — a silent wrong value in a backup that verifies green. The key now length-prefixes each PK component (`<len>\x1e<value>`, B-5's `writeLengthPrefixed`), so every boundary is unambiguous and distinct composite PKs never collide. Deliberately WITHOUT the `%T` type tag B-5's single-reader `pkValueKey` carries: `floatPatchKey` bridges two readers — the exact-scan `RowReader` and the VStream COPY decode — that render the same unsigned-integer PK to different Go types (int64 vs uint64), so a type tag would miss the patch for every unsigned-integer PK, the MySQL autoincrement norm; the pre-release value-fidelity review caught exactly that regression in the first cut, and the final fix is length-prefix only. VStream-source only, but default-on there. Pinned by the NUL-boundary-shift case and the cross-reader int64==uint64 equality — at the key level and end-to-end through the patch reader — mutation-verified both directions; the sibling `redact.DeriveRowSeed` was swept and deliberately left unchanged (a seed collision is a uniqueness loss, never a wrong value written to the wrong row, and the seed must stay replay-stable).

**Cross-segment backup compaction now carries the UNION of verbatim markers, so it can't blind the cross-engine restore refusal (audit M-3, silent-loss).** A merged segment's data span runs oldest-start..newest-end and carries every source's incrementals, but `mergedSegmentFromGroup` carried forward only the OLDEST source segment's verbatim-extension markers. So when a NEWER source's full first declared a PG-only verbatim column (the Bug 251 mid-chain verbatim-arrival shape, reachable since v0.126.1), that column's data lived in the merged segment while its marker was dropped — and the cross-engine restore refusal, which sums each segment's markers, then found nothing and would let a cross-engine restore of PG-only verbatim columns proceed silently. The merge now unions the markers across every segment in the group (sorted, deduped); additive is safe because a column dropped mid-chain still has data in the earlier incrementals. Pinned by a non-oldest-segment-introduces-the-marker case, mutation-verified that oldest-only carry-forward drops it. The broader "non-verbatim schema object introduced in a crash-recovery gap" case is narrower and surfaces LOUDLY at restore (missing object), and is documented as a noted limitation rather than blanket-refused.

## Hardening

Internal CI/gate work that closes the audit's testing and performance findings, with no operator-facing behavior change: the scheduled-red consumer now files a standing issue for EVERY scheduled correctness workflow (H-5); every filtered integration leg now carries a vacuous-green guard so a boot failure that skips the crux family fails rather than passes (H-6); the LOAD DATA skip allowlist is anchored to the tests that actually skip (T-4); every CI Lint guard now also runs in the local pre-commit hooks with a parity ratchet (T-7); and the perf-parity matrix arrears are reconciled. One throughput fix rides here too (audit H-4): the unknown-target-table skip ledger write is now coalesced to one UPSERT per table at each position-write boundary instead of a per-event autocommit — a new source table whose CREATE was never forwarded no longer turns the ordered CDC apply into a per-event-fsync crawl (which could let other tables' lag outrun binlog/slot retention and lose the very resume position the skip exists to protect).

## Compatibility

No flag, capability, on-disk format, or error-code change. Every fix here is a behavioral correction toward loud-failure and away from phantom drift: a misrouted MySQL sync now halts instead of exiting 0 empty; a warm-resumed sync into a pre-vindexed sharded keyspace now proceeds where v0.126.0 wrongly refused it (a narrowed refusal, never a new one on a working setup); `schema diff` reports fewer phantom differences and no longer mis-certifies a gutted `NOT IN`; and two VStream-source backup paths stop a silent wrong-value / silent-blinding corner case. The `SLUICE-E-SCHEMA-TARGET-KEYSPACE-SHARDED` refusal still fires — only later and only when sluice would actually CREATE a vindex-less table. **Drop-in upgrade from v0.126.x.** No data was at risk on any working configuration from these changes, and nothing here requires re-verifying past runs — except the two narrow, named cases in the next section.

## Who needs this — action required

**Anyone running MySQL sync or migrate**: upgrade. The `multiStatements=false` enforcement (H-3) is defense-in-depth — it only mattered if your target DSN set `multiStatements=true` AND a manifest was tampered/corrupt, so no past run needs re-verifying, but the surface is now closed by construction. If you run a **multi-database sync with namespace mappings**, upgrade specifically for M-2: on v0.123.0 through v0.126.2 a mapping pointing at a target database/schema that does not exist made the stream exit 0 while skipping every table — if you suspect a routed target namespace may have been wrong, re-verify that those runs actually landed rows; from this release such a misroute halts loudly and cannot be missed.

**Anyone who runs `schema diff` after a cross-engine migrate**: re-run it on v0.127.0. Under v0.126.0–v0.126.2 the NOT-pushdown fold could certify a genuinely gutted `NOT IN` constraint as in-sync (H-1) — if a `schema diff` on those versions reported CLEAN and you rely on it to gate a cutover, re-run here; the fold now compares those constraints correctly. The same release also removes phantom drift reports on `NOT IN` / `NOT BETWEEN` (M-1) and in the PG→MySQL direction (M-5), so drift reports you previously dismissed as noise will now be genuinely absent.

**Anyone using encrypted backup chains with VStream (PlanetScale/Vitess) sources**: upgrade. Two silent corner cases are closed — a float-repair key collision that could write one row's floats into another row's archived record (M-4; the trigger is a composite PK carrying a NUL byte or type-ambiguous components, latent since v0.99.207), and a compaction that dropped a mid-chain verbatim marker and could let a cross-engine restore of PG-only columns proceed silently (M-3; reachable since v0.126.1). Both verify green, so a routine `backup verify` would not have caught them. If you compacted a VStream-source chain whose schema evolved mid-chain, or backed up a table with a NUL-bearing composite key, re-take or re-verify against a real restore on this version. **Everyone else: no action — this is a drop-in upgrade.**
