# sluice v0.159.2

**CORRECTION (2026-10-13).** Two statements in these notes are wrong. First, the KEY-COLLATION-LOOSENED-WINDOW fix is inert when no row of the table follows the loosening `ALTER` inside the window: chain restore by v0.159.2 still merges two source rows into one at exit 0 there, on both the `backup incremental` and `backup stream` lanes, with `backup verify` passing (Bug 306, HIGH, fixed in the next release, v0.159.3). Second, "Anyone holding a chain that spans such a window: v0.159.2's restore of it now refuses `KEY-COLLATION-MERGE`" is false for a window that changed a key's collation and changed it back when the chain was written by `backup incremental` on v0.159.1 or earlier: that chain recorded only the reverted shape, so no release can see that the key was ever stricter, and v0.159.2 restores it, or replays it through `sync from-backup`, with the rows merged at exit 0 (Bug 307). The same is true of a `backup stream` window whose reader was behind the source when it read past the revert, and of any collation change made with `sql_log_bin=0` before v0.159.2. A `backup stream` window captured live, and a loosened window written by v0.159.0 or v0.159.1, do carry the evidence; the next release, v0.159.3, will refuse such a merge in both. If you restored, or will restore, a MySQL or MariaDB chain across a window in which a key column's collation changed, check each such table against the source (`sluice verify`, or `SELECT k COLLATE <the target key's collation> AS kk, COUNT(*) FROM t GROUP BY kk HAVING COUNT(*) > 1` on the source) and re-copy it on a mismatch, and take a fresh `backup full` to restore from in future.

**HIGH fixes: a backup window that changed a MySQL or MariaDB key column's collation and changed it back, or loosened it, could restore or replay with two source rows merged into one at exit 0 — on v0.159.0 and v0.159.1 despite their key-collation guard, and on every earlier release, which has no guard. The release also adds new refusals and leaves two HIGH Postgres known issues open. Drop-in for streams and chains whose windows never change a key column's collation; everyone else should read Compatibility, Known issues and Who needs this before upgrading.** (1) **KEY-COLLATION-REVERTED-WINDOW-RESTORE (HIGH, silent):** a key changed `utf8mb4_0900_ai_ci` → `utf8mb4_bin` and back inside one window carries no schema delta, and the restore armed its guard from the reverted shape, so a row the `_bin` key had kept apart replayed onto an existing one. (2) **KEY-COLLATION-LOOSENED-WINDOW (HIGH, silent):** a key loosened `utf8mb4_bin` → `utf8mb4_0900_ai_ci` inside a window had its delta applied to the target ahead of rows written under `_bin`, with nothing guarding them. Both are fixed in chain restore, refused by `sync from-backup`, and exact on a warm-resumed `sync start`, because the MySQL and MariaDB binlog reader now decodes each row under the collation its event recorded. (3) **BINLOG-SERVER-ID-COLLISION (loud):** two binlog readers opened by one process could register the same replica server id, which MariaDB refuses with `ERROR 4052`; on MySQL 8 it was measured harmless.

## Fixed

**A key column whose collation was changed and changed back inside one backup window no longer restores with two source rows merged (HIGH, silent; KEY-COLLATION-REVERTED-WINDOW-RESTORE).** Take a key `utf8mb4_0900_ai_ci` changed to `utf8mb4_bin`, a row `'A'` written beside an existing `'a'` (distinct under `_bin`), `'A'` moved out of the way, and the key changed back. The window ends with its original shape, so it carries no schema delta and the restored key compares under `_ci` throughout. Measured on MySQL 8.0 (MINIMAL and FULL row metadata, UNIQUE and primary keys): the target held `'A'` where the source holds `'a'`, or with the key as the primary key row 1 was gone, at exit 0. Three paths reached it, each fixed differently:
- **Chain restore** pushed every schema version a window recorded onto the applier before the window's first row, so the guard armed from the last, reverted shape — equal to the target's. It now releases each version immediately before the first change recorded at or after its anchor, at a transaction boundary, by the recorded source engine's own position order (`historyReplay` in `chain_restore_history_order.go`; the CLI injects the engine through `SourceEngine`, since the orchestrator imports no engine). The rows written under `_bin` are guarded under `_bin`, and the restore refuses `KEY-COLLATION-MERGE` with nothing of the colliding row applied. A point-in-time restore takes the same path.
- **`sync from-backup`** places no schema version between a window's changes at all, so its guard was never armed from the source. It now refuses, before applying any of it, a window that changes a key column's collation (`KEY-COLLATION-HISTORY-UNORDERED`; see Compatibility for what else that refuses).
- **A `backup incremental` or a warm-resumed `sync start` reading the window after the revert** recorded only the catalog's current `_ci` shape, although every row event's TABLE_MAP records the collation it was written under — under MySQL's default `binlog_row_metadata=MINIMAL` as well as FULL. The MySQL and MariaDB binlog reader now decodes and reports each row under its recorded collation and character set (`stampRecordedCollations`), so the schema boundary it emits at the change carries `_bin`: a sync forwards it before the rows written under it, and a backup records it for chain restore to guard them under.

A MySQL source restored onto Postgres lands byte-exact, the Postgres key being case-sensitive. Pinned by `TestChainRestore_KeyCollationChangedAndRevertedInsideTheWindow` (and its `_MySQLToPostgres` variant, with the CLI's engine wiring), `TestSyncFromBackup_KeyCollationChangedAndRevertedInsideTheWindow`, `TestHistoryReplay_VersionsInterleaveByPosition`, `TestPositionAtOrAfter_PlacesASchemaVersionBetweenTransactions` (the real MySQL orderer: GTID, file/position, across a rotation, and MariaDB GTID) and `TestStampRecordedCollations`. **Affected releases:** v0.159.0 and v0.159.1, by code-reading at both tags (each prepends every recorded version ahead of the window's rows, has no `sync from-backup` refusal and no recorded-collation decoding). Earlier releases have no key-collation guard at all and merge the same way (v0.159.0's KEY-COLLATION-FIRST-BOUNDARY entry).

**A key column whose collation was LOOSENED inside one backup window no longer restores or replays with two source rows merged (HIGH, silent; KEY-COLLATION-LOOSENED-WINDOW).** A key `utf8mb4_bin` at the start of a window holding `'a'`, a row `'A'` written beside it, moved out of the way, and the key loosened to `utf8mb4_0900_ai_ci`. The window's schema delta loosened the target key before any of its rows replayed, and no schema version armed the guard for the rows written before the change, so `'A'` met `'a'` on a `_ci` key. Measured on MySQL 8.0 (MINIMAL and FULL, UNIQUE and primary keys), at exit 0, by chain restore of a `backup stream` rollover window and of a `backup incremental`, by `sync from-backup` over a rollover window, and by a warm-resumed `sync start`, whose first boundary after the resume carried the catalog's `_ci` shape. Now:
- **Chain restore** releases, ahead of a window that changes a table's key collation, the shape the previous link recorded for that table (`windowStartVersions`), so the rows written before the change are guarded under `_bin` and the restore refuses `KEY-COLLATION-MERGE`. Restarting re-applies the loosening ahead of the same rows, so the refusal now says so and names the remedy: a fresh full backup taken after the key change.
- **`sync from-backup`** refuses the window (`KEY-COLLATION-HISTORY-UNORDERED`).
- **A warm-resumed `sync start`** replays exactly: the recorded-collation decoding above makes its first boundary carry `_bin`.

Pinned by `TestChainRestore_KeyCollationLoosenedInsideTheWindow`, `TestWindowStartVersions`, `TestRefuseKeyCollationHistory_ComparesConsecutiveVersions` and `TestRefuseKeyCollationHistory_DeltaAndRecordedSchema`. **Affected releases:** v0.159.0 and v0.159.1, by code-reading at both tags and measured on this release's base; earlier releases, with no key-collation guard, merge the same way.

**The binlog reader now checks the premise both fixes rest on: a collation change is a logged DDL.** The boundary that carries a recorded collation is placed at the first row after a DDL. A collation change with no statement in the binlog — an `ALTER` run with `sql_log_bin=0` — changes the catalog and the row images and writes nothing a boundary could follow. The reader now refuses a row whose recorded collation differs from the shape this stream last decoded the table with when no DDL that can reach that table was logged in between (`DEFERRED-SCHEMA-CHANGE`, marked `COLLATION-CHANGE-UNANNOUNCED`), before any row of it is decoded. The check is scoped per table: a logged `ALTER` of another table does not silence it. And it refuses, on any character column, a row carrying a collation ID the source's `information_schema.COLLATIONS` could not be read to name or does not list (`COLLATION-NAMES-UNAVAILABLE`); a restart retries the read. Every character column, not only the primary key, because the reader does not know a table's UNIQUE keys. Pinned by `TestHoldUnannouncedCollation`, `TestBackupStream_UnloggedKeyCollationChangeRefuses` (the unlogged change alone, and after a logged `ALTER` of an unrelated table) and `TestRefuseUnnamedCollations`.

**A first row whose recorded collation differs from a seeded basis becomes a schema boundary, not a refusal.** Every binlog stream that starts from a typed basis handed to it rather than one it observed — `backup incremental` and `backup stream` (seeded from the parent manifest's schema) and `sync start`'s warm resume and cold start (seeded from the schema the stream starts with) — compares its first row of each table against that seeded shape. A parent manifest's schema is read when its window closes, so it can already show a logged `ALTER … COLLATE` the next window has not reached. A first cut of the check above refused those rows on every restart (measured, and fixed before release). A seeded mismatch now owes a schema boundary at the stream's start, as a table's first touch does, so the row's recorded shape reaches the schema history and a later logged DDL is its own boundary. On the `sync start` wirings the table's first-touch boundary already fires first and carries the recorded shape. A shape that can never be a boundary, or a stream whose start position did not resolve, still refuses. This also covers an unlogged change reverted before a table's first row of a window: the version records the collation the rows were written under, and chain restore refuses `KEY-COLLATION-MERGE` rather than merging. Pinned by `TestBackupIncremental_CollationAlteredAfterTheWindowEnds` and `TestChainRestore_UnloggedRevertedKeyCollationBeforeTheWindowsFirstRow`.

**Two binlog readers opened by one sluice process no longer register the same replica server id (loud; BINLOG-SERVER-ID-COLLISION).** The id was a hash of the host, the pid and one clock read per reader. On Windows, two readers opened within one clock tick got the same id; measured, two consecutive calls collided. On MariaDB the second registration failed with `ERROR 4052 (HY000): A slave with the same server_uuid/server_id is already connected`, ending that stream loudly — for example one leg of several opened together against one MariaDB source. On MySQL 8 the collision was harmless, measured: both readers kept receiving every row and both dump connections stayed up, because MySQL tells dump threads apart by the replica UUID the binlog library sets per connection (a behaviour of MySQL and of that library, pinned by that test rather than guaranteed). No silent stall was observed on either engine. The id is now a per-process base plus a process-wide sequence, kept at or above 65536 so it stays clear of 0 and of the small ids operators often assign by hand, and checked at stream start against the source's own `@@server_id` (managed services assign large ids), taking a fresh one on a match. A sibling replica's id is not visible to sluice and is not checked. There is no server-id option to configure. Pinned by `TestGenerateServerIDIsDistinctWithinAProcess` (1,000 rapid calls, red on the old code), `TestCDCReader_SameServerIDOnMySQL_BothStreamsKeepReading`, `TestCDCReader_ServerIDEqualToTheSourcesIsReplaced` and `TestKeyCollationFirstBoundary_MariaDB114_Minimal`/`_Full`, which hit the collision in 4 of 24 cells before the fix and 0 of 36 after. **Affected releases:** the id scheme dates from the first MySQL binlog reader (v0.1.0) and is unchanged through v0.159.1; the loud MariaDB failure is reachable from v0.99.271, the first release with MariaDB CDC. The collision was measured on Windows only; on other platforms a finer clock makes it less likely, unmeasured.

## Compatibility

**Drop-in for streams and chains whose windows never change a key column's collation**, and for every non-MySQL-family source except as noted below. **The behaviour changes:**
- **`sync from-backup` refuses any window that changes a key column's collation** — a schema delta that does, two consecutive recorded versions of a table that disagree, or a version that disagrees with the segment's recorded schema (which reaches a drain-committed window) — with `KEY-COLLATION-HISTORY-UNORDERED`. **This includes a forward change it used to replay correctly**: it cannot tell a forward change from a reverted or loosened one. Restarting refuses again and changing the target key does not help. **Remedy:** take a new full backup after the key change, then `sluice sync from-backup run --reset-target-data --yes` against the new chain (destructive). A VStream (Vitess/PlanetScale) window still replays as before: a VStream schema version records no collation and is not read as a change (a first cut did, and refused every VStream incremental of a character-keyed table; pinned by `TestSyncFromBackup_VStreamCharacterKey_NoKeyChange_ReplaysExactly` and `TestKeyCollationHistory_AVersionRecordingNoCollationIsNoEvidence`).
- **Chain restore from a trigger-CDC source** (pgtrigger, sqlite-trigger, d1-trigger), which records no schema versions and has no position order, now refuses `KEY-COLLATION-HISTORY-UNORDERED` for any window whose schema delta changes a key column's collation — including a forward, tightening change it used to restore correctly. Same remedy: a fresh full backup after the key change, restored on its own.
- **Chain restore of a MySQL-family window that loosens, or changes and reverts, a key's collation** now refuses `KEY-COLLATION-MERGE` where it used to merge, and restarting refuses again; the message says the remedy is a fresh full backup after the key change.
- **The MySQL and MariaDB binlog reader** now refuses `DEFERRED-SCHEMA-CHANGE` marked `COLLATION-CHANGE-UNANNOUNCED` on a collation change it observes with no logged DDL of the table (remedy, destructive: `sync start --reset-target-data --yes` for a sync, a fresh `backup full` for a backup chain), and refuses `COLLATION-NAMES-UNAVAILABLE` when it cannot name a recorded collation ID (a restart retries).
- **Schema boundaries now carry the recorded collation**, so a `sync start` resumed behind a key-collation change sees that change at the table's first boundary. Under `--schema-changes=forward` it is forwarded ahead of the rows written under it; under `--schema-changes=refuse` it is judged like any other schema change the target does not hold, and refused.
- **More backup segments are stamped `FormatVersion` 13.** A `backup incremental` read behind the head across a key-collation change now records the collation its rows were written under, so its schema history shows the change and the segment is stamped as v0.159.1 stamps a live window — where v0.159.1 recorded only the catalog's current shape and left it unstamped. v0.159.1 and later read it; v0.159.0 and older refuse it at their version ceiling. `BackupFormatVersion` stays 13; there is no new format tier.
- **Generated replica server ids** are now at or above 65536, and every binlog stream start runs one `SELECT @@server_id` against the source.

**Markers, no new error codes:** `KEY-COLLATION-HISTORY-UNORDERED` arrives inside a `KEY-COLLATION-MERGE` refusal; `COLLATION-CHANGE-UNANNOUNCED` arrives inside `DEFERRED-SCHEMA-CHANGE`; `COLLATION-NAMES-UNAVAILABLE` is a new uncoded refusal.

**Recorded-collation decoding needs a TABLE_MAP that records collations:** `binlog_row_metadata` MINIMAL or FULL. MySQL's default is MINIMAL. MariaDB's default, NO_LOG, records none, so on such a MariaDB source nothing is stamped: chain restore's version ordering and window-start seeding and the `sync from-backup` refusal still apply, but a `backup incremental` or warm-resumed `sync start` reading a reverted window behind the head has no recorded collation to carry. That MariaDB NO_LOG case is not measured in this release; set `binlog_row_metadata=MINIMAL` or FULL on a MariaDB source to get the fix.

**Not affected:** MySQL → Postgres restores (byte-exact, the Postgres key being case-sensitive); windows whose only collation change is a logged change to a non-key column, which do not refuse except under `--schema-changes=refuse`.

## Known issues

- **KEY-COLLATION-PG-SAME-ANCHOR (HIGH, silent, timing-dependent; open).** A Postgres window observed live by `backup stream`, with a row of the table written before a key-collation change, can still restore merged. Every Postgres schema version is anchored at the same position, so a window keeps only the shape its first Relation carried; when the reader keeps up that is the pre-change shape, the restore arms nothing for the rows written under the stricter collation, and with the key as the primary key target row 1 is gone at exit 0 (measured on Postgres 16, 1 of 3 runs; when the reader lags, the restore refuses instead). The affected cell of `TestChainRestore_KeyCollationChangedAndRevertedInsideTheWindow_Postgres16` is excluded from the pin with a pointer to this entry.
- **KEY-COLLATION-PG-LOOSENED-REPLAY (HIGH, silent; open).** The Postgres twin of both fixes above, read after the change: a Postgres key tightened (`ci` → `"C"`), given a row distinct only under the tighter collation, that row moved or deleted, and the key loosened back — replayed by a `backup incremental` or a lagging stream started after the change — replays under the loose collation, because pgoutput carries no collation and the reader stamps the catalog's current one. Measured on Postgres 16 restored onto Postgres with the primary key on the column: target row 1 gone, exit 0. Regraded from MEDIUM. No cheap fix exists: it needs collation history the stream does not carry.
- **VStream, trigger-CDC and Postgres change streams record no collation.** VStream events carry none, so no key-collation check arms for a VStream source and a VStream window that changes a key's collation is not guarded on restore. The trigger-CDC sources (pgtrigger, sqlite-trigger, d1-trigger) record no schema versions, so a key collation changed and changed back inside one of their windows leaves nothing to arm the restore guard from (unmeasured). Postgres is covered by the two entries above.
- **KEY-COLLATION-DRAIN-NO-DELTA (MEDIUM, loud; open, unchanged).** A `backup stream` stopped mid-window whose window changed a key's collation produces a correct chain that this release's chain restore refuses (`KEY-COLLATION-MERGE`) at that segment on every run, because the drain commit writes no schema delta. Nothing merges. `sync from-backup` refuses it with `KEY-COLLATION-HISTORY-UNORDERED`.
- **KEY-COLLATION-VSTREAM-UNSTAMPED (LOW to MEDIUM, silent on a downgrade only; open, unchanged).** A VStream segment is never stamped from its window's history, because VStream records no collation, so a VStream window that changed a key's collation and back stays readable by older binaries, which can merge.

**Also filed in `docs/dev/audit-backlog.md`:** `sync from-backup` still applies a window whose key-collation change nothing records (a VStream window), or onto a target key whose collation was set by hand to differ from the source's, unguarded; and a `COLLATION-CHANGE-UNANNOUNCED` refusal can fire on an unlogged change after another table's logged DDL that an owed boundary would in fact have carried (availability, not safety).

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale), `d1verify` (live Cloudflare D1) and `nekiverify` (live Neki) suites, which need live, billable infrastructure.

## Who needs this — action required

- **Anyone who restored a MySQL- or MariaDB-source backup chain, ran `sync from-backup`, or warm-resumed `sync start`, across a window in which a primary-key or UNIQUE-key column's collation was changed and changed back, or loosened** — on v0.159.0 or v0.159.1 by the paths above, and on any earlier release, which has no key-collation guard. The target may hold one row where the source holds two, at exit 0. **Check:** on a quiesced pair, `sluice verify` (row counts) reports a mismatch for every merge; to find candidates directly, group the key on the source under the collation the target key uses: `SELECT k COLLATE utf8mb4_0900_ai_ci AS kk, COUNT(*) FROM t GROUP BY kk HAVING COUNT(*) > 1`. **Action:** re-copy each table that mismatches. Upgrading does not repair rows that already merged.
- **Anyone holding a chain that spans such a window.** v0.159.2's restore of it now refuses `KEY-COLLATION-MERGE` rather than merging. **Action:** take a fresh `backup full` after the key change and restore from it.
- **`sync from-backup` operators whose source changes a key column's collation at all** — even a forward change, and on a trigger-CDC chain restore a forward delta too. The replay now stops with `KEY-COLLATION-HISTORY-UNORDERED`. **Action:** take a new full backup after the key change, then `sluice sync from-backup run --reset-target-data --yes` against the new chain.
- **Anyone who runs collation DDL on a MySQL or MariaDB source with `sql_log_bin=0`.** Streams and backups now stop with `COLLATION-CHANGE-UNANNOUNCED` rather than decode rows under a shape nothing announced. **Action:** run such DDL with binary logging on; to recover a stopped stream, re-copy (`sync start --reset-target-data --yes`) or take a fresh `backup full`.
- **Postgres-source backup operators** (KEY-COLLATION-PG-SAME-ANCHOR, KEY-COLLATION-PG-LOOSENED-REPLAY, both open). **Action until fixed:** after any change to a key column's collation, take a fresh `backup full`, and verify any restore spanning that window against the source (`sluice verify` row counts, or the collision query above with `GROUP BY lower(k)` as an approximation).
- **MariaDB CDC users who saw `ERROR 4052` on a stream's first read**, typically with several streams opened together by one process. **Action:** upgrade; nothing to repair, since the failure was loud and was observed at the stream's first read. MySQL users: nothing to do.
- **Everyone else:** upgrade. Streams and chains whose windows never change a key column's collation need no action.
