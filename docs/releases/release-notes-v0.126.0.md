# sluice v0.126.0

**The operator-honesty release.** No silent-loss fixes this time — every change in this batch makes sluice's own signals tell the truth. A wedged stream's sync-lag alert now stays latched instead of clearing itself the moment changes stop flowing; two Vitess/PlanetScale guards now probe reality before refusing (one of them un-breaking a v0.125.0 regression whose printed remedy could never release it, the other refusing a sharded target keyspace up front instead of letting a doomed migrate fail late, dirty and nondeterministically); the cross-engine restore gate stops refusing over tables you explicitly excluded; `schema diff` stops crying wolf on 13 measured CHECK-rendering families; and the D1 invalid-UTF-8 caveat now covers the export path with a live measurement rather than an assumption. **Drop-in upgrade from v0.125.0.**

## Fixed

**A wedged stream's sync-lag alert stays latched instead of clearing itself (PROG-LAG-1).** The engine-neutral sync-lag reading reported sustained idle as "0, caught up" — but the apply seam cannot distinguish a genuinely quiet source from a wedged pipeline, so a fired lag alert on a stuck stream cleared and re-armed as soon as changes stopped flowing, exactly when the operator most needed it to persist. Idle now reads as UNKNOWN (carrying the last frozen lag as context): the `sluice_sync_lag_seconds` gauge goes unobserved rather than fabricating a zero, and the alerter neither fires nor re-arms until changes flow again and demonstrate low lag. The complementary "not applying at all" signal remains `sluice_seconds_since_last_apply`, which ages. This was the documented behavior since the sync-lag reading shipped, not a regression; the pin is the inverted idle test, which names the pre-fix clear-and-re-arm consequence and was mutation-run.

**The multi-database fan-out's Vitess/PlanetScale refusal probes keyspace existence first, so its printed remedy actually runs (Bug 249 — affects v0.125.0 only).** v0.125.0's fan-out guard refused unconditionally, so a fully pre-provisioned fan-out re-refused byte-identically, making "create the keyspace first" an unrunnable hint — and the refusal carried no error code. `EnsureDatabase` on a VStream flavor now probes `SHOW DATABASES` on a server-level connection first: an existing keyspace satisfies the ensure step and the fan-out proceeds; only a missing one refuses, as the new `SLUICE-E-SCHEMA-KEYSPACE-MISSING` with a remedy that genuinely releases the gate on re-run. Pinned against a real vtgate in both directions and mutation-run.

**A sharded Vitess/PlanetScale keyspace as a write target refuses at schema-writer open, before any DDL (`SLUICE-E-SCHEMA-TARGET-KEYSPACE-SHARDED`).** *(Correction, 2026-08-14: as shipped in this release, the door protected sync cold-start, `preview`, and `schema diff` — but NOT `migrate`, whose migration-state bootstrap opens the target first and still materialized state tables per-shard before dying on the raced errors (Bug 250, found by this release's regression cycle). Fixed in the next release by dooring the state-store open identically.)* Every table sluice creates carries no vindex, so nothing sluice writes into a sharded keyspace can route — and a live measurement on a real 2-shard cluster falsified the code's own "fails loudly at CREATE TABLE" comment: `CREATE TABLE` *succeeds* and materializes the table on every shard, the vindex refusal waits for the first row write, and the error a real migrate actually surfaced was a nondeterministic vtgate schema-tracker race, leaving per-shard debris vtgate cannot route to. The new preflight enumerates the target keyspace's shards at schema-writer open (VStream flavors only): an unsharded keyspace passes untouched, a sharded one refuses naming its shards and the runnable remedies, and a probe failure WARNs and proceeds so a transient discovery error cannot break a working unsharded target. This was never a working configuration, so no working setup is newly refused — the failure just moved from late-and-dirty to a clean preflight. Stated boundary: the door refuses sluice-created tables — every write shape sluice has today; a future vschema-aware mode would lift it for its own writes. Pinned live on the real 2-shard cluster and mutation-run.

**The cross-engine restore supportability gate honours the table filter on both restore paths — the last sibling of the filter-blind-door class.** The Bug 134 gate (PG-only constructs refused before a cross-engine restore) graded the unfiltered manifest schema, so a Z-dimensional geometry or EXCLUDE constraint in an *excluded* table refused the whole restore — while the refusal's own message recommends `--exclude-table` on exactly that table. Both restore paths now grade the filtered view (the chain path filters its schema deltas identically). An over-refusal only, never a data risk; present since the gates' introduction (the chain path since v0.21.0, the single-manifest path since v0.99.33). Pinned in both directions, with the mutation run reproducing the self-defeating shape verbatim.

**`schema diff` no longer phantom-reports 13 measured CHECK-rendering families on a cross-engine target migrate itself created (DIFF-2).** A bounded measurement pass — a 30-family portable CHECK corpus applied identically to a real MySQL 8 and PostgreSQL 16 — found 13 families beyond the two Bug 241 folded where the two catalogs re-render the same predicate differently, every one previously reported as CHECK drift the operator could not act on. The fold set now covers all of them: the `substring`/`substr` and `ceiling`/`ceil` spelling renames, PostgreSQL's `TRIM(BOTH FROM x)` and `~~`/`!~~` LIKE spellings, MySQL's `round(x, 0)` default-scale materialization and `mod(a,b)` → `%` rewrite, PostgreSQL's quoted-negative-literal decoration, NOT-pushdown of a single comparison, and BETWEEN folded to its own `>=`/`<=` expansion. Each fold carries its measured rendering pair verbatim as a pin plus a guard direction proving the meaning axis still reports (a widened bound, a changed pattern, LIKE vs NOT LIKE, a non-zero round scale all remain drift), the corpus rides the migrate-then-diff integration gate end to end, and the folds were mutation-run in both directions. The three translated-predicate families (`json_extract`, `json_unquote`, `date_format`) still phantom-report and are filed with a recommended fix shape rather than folded — folding them would duplicate the translator.

**The D1 invalid-UTF-8 caveat now covers the export path, measured rather than assumed.** An open question from the SQT-1 measurement — does the server-side dump behind `wrangler d1 export` preserve invalid-UTF-8 TEXT where the `/query` API mangles it? — is now measured on real D1: it does not. Storage holds the raw bytes (`hex(x)` proves it), but the export dump carries U+FFFD replacement characters exactly like the query API, so export is not a rescue path for this vector (it remains one for BLOBs, rendered faithfully as `x'…'` literals) and a server-side `hex(x)` stays the only faithful readout. The import-guide caveat states the export half explicitly, and a second live `d1verify` pin drives the real `/export` polling protocol so a Cloudflare serialization change fails a named test instead of silently invalidating the doc.

## Compatibility

No flag or on-disk format changed. Two error codes added (`SLUICE-E-SCHEMA-KEYSPACE-MISSING`, `SLUICE-E-SCHEMA-TARGET-KEYSPACE-SHARDED`). Two refusals narrowed to their intended scope (a pre-provisioned fan-out keyspace now proceeds; a PG-only construct in an excluded table no longer blocks a cross-engine restore) and one moved earlier (a sharded target keyspace now refuses at preflight instead of failing nondeterministically mid-run — it was never a working target, so no working configuration is newly refused). The sharded-target door sits at schema-writer open, which `schema diff` and `preview` also pass through for their DDL suggestions: against a sharded keyspace, `preview` now reports the same refusal the real migrate would hit, and `schema diff` still runs and reports — only its missing-table DDL suggestions refuse, where the suggested `CREATE TABLE` genuinely could not run. Sharded-target sync with platform-created vindexed tables and `--schema-already-applied` is unaffected (that path never opens the schema writer). One observable metrics change: during sustained idle, `sluice_sync_lag_seconds` is now absent from `/metrics` instead of reporting `0` — a dashboard or alert rule that relied on a zero-during-idle sample will see the series go unobserved between changes. **Drop-in upgrade from v0.125.0.** No data was at risk from any of these — nothing in this release requires re-verifying past runs.

## Who needs this — action required

**Anyone alerting on sync lag**: upgrade — before this release a wedged stream's fired alert silently cleared as soon as changes stopped; also check dashboards that assumed the lag gauge emits 0 while idle (see Compatibility). **Anyone whose v0.125.0 multi-database fan-out refused despite pre-provisioned keyspaces**: upgrade and re-run — the refusal was the bug, your setup was fine. **Anyone whose cross-engine restore refused on a construct in a table they had excluded**: upgrade; the filter now releases that gate. **Anyone who diffed a MySQL→PostgreSQL migrate and saw CHECK drift**: re-run `schema diff` on v0.126.0 — drift reports matching the 13 folded families were phantom (reports on `json_extract`/`json_unquote`/`date_format` predicates still are, until the translator-aware fix lands). **Anyone extracting from live D1 with possibly-invalid UTF-8 in TEXT columns**: `wrangler d1 export` is now confirmed not to be a workaround — plan around `hex(x)` per the import guide. No one needs to re-verify previously migrated data.
