# sluice v0.158.0

**CRITICAL fixes — three silent-data defects in CDC, and new refusals that change behaviour. This is a MINOR release, not a drop-in: read Compatibility and Who needs this before upgrading.** (1) **Bug 301:** a MySQL/MariaDB binlog stream that was behind the binlog head when a schema change landed decoded the earlier rows under the wrong column names at exit 0 for a same-type column reorder, a column-name swap or a same-type drop-and-add. That covers every `backup incremental` and `backup stream` window, every warm-resumed `sync start`, the CDC phase after a cold copy, and a live sync that lags. (2) **MARIADB-NOLOG-UNSIGNED:** on MariaDB's default `binlog_row_metadata=NO_LOG`, UNSIGNED integers above the signed maximum streamed as negative numbers, and updates and deletes keyed by them were dropped. (3) **RENAME-SWAP-FORWARD:** a column RENAME swap, and a multi-column type change in one ALTER, were forwarded to the target as nothing. **Existing MySQL-family chains and synced targets that crossed such a change may hold wrong values, and no sluice check can clear them.** The fixes refuse where sluice cannot prove the shape, so some DDL that used to stream through now stops the stream until the target is reconciled or `binlog_row_metadata=FULL` is set.

## Fixed

**A MySQL-family stream behind the binlog head no longer decodes earlier rows under the wrong column names (CRITICAL, silent; Bug 301).** The binlog reader took a table's column list from `information_schema` whenever its decode cache was cold, and the catalog answers as of now while a stream behind the head reads events recorded earlier. A change that moved the column count or a column's type family refused (`SLUICE-E-CDC-SCHEMA-REPLAY-MISMATCH`). A change that did neither decoded cleanly with every value under the wrong name, at exit 0. This was measured on MySQL 8.4 with `MODIFY c … AFTER id` over two `VARCHAR` columns: `backup incremental`, a warm-resumed `sync start` and a live `sync start` a few hundred rows behind all swapped `b` and `c` in the earlier rows. A column-name swap and a same-type drop-and-add are the same shape, and an `ENUM` whose labels were reordered in place decoded each earlier row to the other label. The same mis-decode happened even at the head for a change issued from another default database (`USE other; ALTER TABLE app.t …`). The reader now reads each statement's own table references with a SQL parser.

Each event is now decoded by the shape it was recorded under, or refused before any row of the table is decoded:
- **Under `binlog_row_metadata=FULL`**, events carry column names and sluice decodes by them. A column it cannot type from a read definition or from the binlog alone refuses. That covers a dropped signed `TINYINT`, a spatial column, and a binary column on MariaDB. So does a schema change, between the stream and the head, of a table that holds a GENERATED column or a MariaDB `UUID`/`INET4`/`INET6` column. A row whose shape includes a column dropped or retyped later never becomes a schema boundary. The reader therefore holds that row to the table's previous row, or to the shape the run started from. It refuses `COLUMN-ORDER-CHANGED` if two shared columns reversed order, and `DEFERRED-SCHEMA-CHANGE` if a shared column's type changed. That includes a column retyped twice, and a character column widened past what the earlier shape could hold.
- **Without names** (MySQL's default `MINIMAL`, MariaDB's default `NO_LOG`), sluice proves the catalog shape by reading the schema changes logged between the stream's position and the catalog read (`SHOW BINLOG EVENTS`). It refuses a table that one of them reshapes. A binlog event type not known to be schema-free counts as reshaping every table. A look-ahead that cannot read up to the position the source reported retries for about ten seconds, then refuses with the new `SLUICE-E-CDC-BINLOG-LOOKAHEAD-SHORT`.

The `FULL` deferred-shape checks (`BUG301-FULL-DEFERRED-SWAP`, `BUG301-DEFERRED-RETYPE`, the length widen, a column retyped twice) were regressions in this fix's own `FULL` decoding. They were found by review and the regression matrix and fixed before release, so no published release carries them. Pinned by `TestCDCShapeAtPosition_Matrix` (every shape × MINIMAL/FULL × GTID/file-pos), `TestCDCShapeAtPosition_MariaDB`, `TestCDCShapeAtPosition_ForeignDefaultDatabaseDDL`, `TestHoldDecodedOrder_DeferredShapeMatrix`, and end to end through `backup incremental`, `backup stream` and a warm-resumed `sync start` by `TestShapeAtPosition_MySQLPaths`. **Affected releases:** the silent mis-decode has existed since v0.1.0 for every shape that keeps the column count. From v0.113.0 the TABLE_MAP type-family guard made the cross-family and count-changing shapes refuse loudly, and the same-family shapes stayed silent through v0.157.2.

**A MariaDB source on its default `NO_LOG` binlog no longer streams UNSIGNED integers above the signed maximum as negative numbers (CRITICAL, silent; MARIADB-NOLOG-UNSIGNED).** Whether a binlog integer is signed or unsigned is recorded only in the TABLE_MAP's optional signedness field. MariaDB writes that field under `MINIMAL` and `FULL`, but not under `NO_LOG`, and the decoder read an integer without it as signed. On every lane that reads a MariaDB binlog, an UNSIGNED `TINYINT`, `SMALLINT`, `MEDIUMINT`, `INT` or `BIGINT` above the signed maximum arrived negative at exit 0. Those lanes are `sync start` (after the cold copy, live, and warm resume), `backup incremental`, `backup stream`, and `sync from-backup` applying those chains. For example, `BIGINT UNSIGNED` 18446744073709551615 arrived as -1. On a Postgres target, an INSERT stored the negative value. An UPDATE or DELETE keyed by such a value matched no row and was dropped as an already-applied replay. A chain restore into MariaDB refused with `Error 1264`. Where an event records no signedness, the decoder now takes it from the table's definition, which the Bug 301 look-ahead has proven to hold at that event. A signedness change between the stream and the head refuses (`SLUICE-E-CDC-SCHEMA-REPLAY-MISMATCH`). Pinned by `TestCDCSignedness_EveryNumericFamily` on MariaDB 11.4 and 10.11 under `NO_LOG`, `MINIMAL` and `FULL`, and on MySQL 8.0 and 8.4. End to end it is pinned by `TestSync_MariaDBNoLogUnsigned_ToPostgres`, `TestSync_MariaDBNoLogUnsigned_BigintAboveInt64_RefusesOnPostgres` and `TestBackup_MariaDBNoLogUnsigned_ChainRestore`. **Not affected:** MySQL 8.0 and 8.4 (`MINIMAL` records signedness), MariaDB under `MINIMAL` or `FULL`, PlanetScale and Vitess, every cold copy and `migrate`, and `DECIMAL`/`FLOAT`/`DOUBLE`/`YEAR`/`BIT` columns. **Affected releases:** v0.99.271 (MariaDB CDC) through v0.157.2.

**A column RENAME swap on the source no longer leaves the target's existing rows under the wrong column names (CRITICAL, silent; RENAME-SWAP-FORWARD).** `ALTER TABLE kd RENAME COLUMN b TO c, RENAME COLUMN c TO b` reached the target of `sync start` as nothing, at exit 0. This was measured on MySQL 8.0 and Postgres 16. Every row the source never touched again stayed swapped, permanently. `sluice verify --depth sample` read the target as clean, because it hashes each side's columns in its own declared order. sluice compares schemas by name, and a swap keeps every name and type in place. Only the declared order changes, and a MySQL `MODIFY c … AFTER id` reorder changes it identically. A boundary across which two columns' order flipped now refuses with `COLUMN-ORDER-CHANGED` before anything after it is applied. It is accepted only once the target's own column order has moved from the order sluice recorded to the source's new order, which proves the operator applied the same change there. That record is the new per-table control table `sluice_cdc_column_order`. A table with no record refuses with the only safe remedy, `sluice sync start --reset-target-data --yes`. That covers a stream started before this release, and a target whose role cannot create the table (`COLUMN-ORDER-RECORD-UNAVAILABLE` is logged as a WARN at start). On a target that cannot reorder in place (Postgres, per the new `ReorderColumns` engine capability), a source reorder goes to the same re-copy. The check covers the live forward path, a restart's first boundary, `--schema-changes=refuse` and the other streams that forward no DDL (as `SCHEMA-CHANGE-REFUSED`), and Shape A (`--inject-shard-column`). It also covers chain restore and `sync from-backup`, which now refuse an incremental whose schema delta changed a table's column order. On a Postgres source, `DROP COLUMN b, RENAME COLUMN c TO b` now refuses rather than reading as a plain drop. Pinned on MySQL 8.0, MySQL 8.4, MariaDB 11.4 and Postgres 16 by `TestRenameSwapForward_*` and `TestRenameSwapForward_ChainRestore`. A column-order record answers only for its own namespace in a multi-database or multi-schema stream. That was found by review before release and is pinned by `TestColumnOrderRecords_LookupNeverCrossesNamespaces`. **Affected releases:** every release of `sync start` (no boundary was checked before v0.79.0; from v0.79.0 opt-in and v0.99.45 default, the forward path read the swap as no change), Shape A since v0.73.0, and chain restore and `sync from-backup` in every release that replays a schema delta.

**More than one column changing type or nullability in one ALTER is no longer forwarded as no change (HIGH, silent on a Postgres target; RENAME-SWAP-FORWARD sibling).** `ALTER TABLE t ALTER b TYPE numeric(12,4), ALTER c TYPE numeric(12,4)`, or two `MODIFY`s in one MySQL statement, reached the target as nothing. A Postgres target kept `numeric(10,2)` and rounded every later value (`1.2345` landed as `1.23`, at exit 0, measured). A MySQL target refused the first such value with `DECIMAL-SCALE-EXCEEDED`. sluice now refuses such a boundary and names each column. Against the cold-start seed, the target decides, as it does for one column. Two pure widens in one statement (`MODIFY a VARCHAR(20), MODIFY b VARCHAR(20)`) now refuse too. **Affected releases:** the forward path from v0.99.45, and Shape A since v0.73.0.

**A refused schema boundary no longer says "nothing has been written" (LOW, message).** `RESUME-SCHEMA-DIVERGENCE`, `SCHEMA-CHANGE-REFUSED` and `COLUMN-ORDER-CHANGED` ended with that claim, which was never wholly true: rows the source wrote before the change are applied before its boundary is judged. The refusals now say only that nothing after the boundary was applied, and that rows read before it may already have been. A change only to a column's collation is not recorded by the binlog and can still land ahead of its boundary (filed as DEFERRED-KEY-COLLATION for a key column). `TestBoundaryRefusals_ClaimNothingWritten` keeps the old phrase out of `internal/pipeline`. It pins the wording, not the truth of the replacement sentence.

## Compatibility

**This is not a drop-in for MySQL-family CDC across schema changes.** Streams that do no DDL behind the binlog head, and Postgres sources that do no column swap, behave as before. **The behaviour changes:**
- **A genuine MySQL/MariaDB column reorder now refuses with `COLUMN-ORDER-CHANGED`** until the target is reordered the same way (a table rebuild on MySQL), or, on a Postgres target, re-copied. It had forwarded as a no-op since v0.99.45 (ADR-0091 §4).
- **More than one column's type or nullability changed in one ALTER now refuses**, including two same-family widens.
- **Behind the head under `MINIMAL`/`NO_LOG`, schema changes of a streamed table now refuse** where they used to decode. Exempt are an index change, a table option, a `TRUNCATE`, and an in-place redefinition that the event still decodes the same way. The changes that now refuse include:
  - an `ENUM`/`SET` label append via `MODIFY`;
  - the `RENAME TABLE` cutover of gh-ost, pt-online-schema-change and LHM, even for an index-only migration;
  - a no-op `CREATE TABLE IF NOT EXISTS` of a streamed table;
  - `CONVERT TO CHARACTER SET` on a table with `ENUM`/`SET` columns;
  - an in-place `MODIFY` of a `YEAR` column;
  - on MariaDB `NO_LOG`, any in-place redefinition, because that format records no charset or signedness.

  The CHANGELOG entry has the full list. The remedy is `binlog_row_metadata=FULL`.
- **Under `FULL`, a type change folded behind a later `DROP COLUMN` now refuses** (`DEFERRED-SCHEMA-CHANGE`), even where the target could have held the rows. The same change on its own still forwards.
- **An existing backup chain with an incremental that recorded a MySQL/MariaDB column reorder or swap now fails `backup verify`.** It cannot be restored or broker-replayed past that incremental, which refuses (`SLUICE-E-BACKUP-SCHEMA-DELTA-UNSUPPORTED`) before writing anything. An `ENUM` label reorder is not a column-order change and still passes.

**New control table:** `sluice_cdc_column_order`, kept on MySQL-family and Postgres targets (the appliers that implement `ColumnOrderStore`; other targets keep no record and refuse a column-order change as unprovable). A record is written at the cold start, and in the same transaction as each accepted boundary that changes a table's order. A role that cannot create it gets a `COLUMN-ORDER-RECORD-UNAVAILABLE` WARN, and every column-order change on that stream then refuses as unprovable. Streams started before this release have no record, so their first column-order change sends them to `--reset-target-data`.

**New error code and markers:** `SLUICE-E-CDC-BINLOG-LOOKAHEAD-SHORT` (new); `COLUMN-ORDER-CHANGED`, `DEFERRED-SCHEMA-CHANGE`, `COLUMN-ORDER-RECORD-UNAVAILABLE` (new markers). `SLUICE-E-CDC-SCHEMA-REPLAY-MISMATCH` and `SLUICE-E-CDC-REPLICATION-PERMISSION` are existing codes with wider scope. New engine capability: `ReorderColumns` (MySQL flavors).

**Privileges:** the look-ahead runs `SHOW BINLOG EVENTS` on MySQL-family sources behind the head. MySQL needs `REPLICATION SLAVE`, which CDC already requires. MariaDB 10.5+ needs `BINLOG MONITOR`, which the CDC account already holds because `REPLICATION CLIENT` is its alias there. An account without it refuses with `SLUICE-E-CDC-REPLICATION-PERMISSION`, naming the grant. **Cost:** the look-ahead reads the binlog between the stream and the head at most once per window, and nothing for a stream at the head.

**Backup format:** unchanged. `BackupFormatVersion` stays 12, and no file under `internal/ir/backup` changed. Chains written by v0.157.2 and v0.158.0 are mutually readable, subject to the new column-order refusal above.

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale), `d1verify` (live Cloudflare D1) and `nekiverify` (live Neki) suites, which need live, billable infrastructure. **VStream (PlanetScale and Vitess) sources are unverified for Bug 301:** their lanes were not changed, on the premise that each row is decoded against the FIELD event Vitess emits for it, and that premise is not measured (BUG301-VSTREAM-PREMISE). With Vitess schema tracking off, the vttablet may answer a historical event's fields from the current schema.

**Known residuals (filed in `docs/dev/audit-backlog.md`):**
- BUG301-LEGACY-CHAIN-DETECTOR: a `backup verify` warning that flags old windows that could hold mis-decoded rows is not built.
- BUG301-WARM-RESUME-SYNTH-BOUNDARY: under `FULL`, a warm resume's first boundary can land at the DDL rather than the stream start. That outcome is loud or a WARN, never silent.
- COLUMN-ORDER-RECORDS-LIFECYCLE: column-order records are not deleted on reset, `remove-table` or `add-table` (LOW).
- DEFERRED-KEY-COLLATION: as above.

## Who needs this — action required

- **Anyone with a MySQL or MariaDB CDC source (`sync start`, `backup incremental`/`stream`, `sync from-backup`) whose source saw a column reorder, a column-name swap, a same-type drop-and-add, or an `ENUM` label reorder:** your target or chain may hold earlier rows with values under the wrong columns or labels. This applies while the stream was behind the head, which is every backup window and every resume, or at the head when the DDL was issued from another default database. **No sluice check can clear it.** `backup verify` (both depths) and restore cannot see it, because the chain is internally consistent. `sluice verify --depth=sample` hashes a sample per table, while Bug 301 alters only the rows written before the change. A full row comparison is not implemented. **Action:** set `binlog_row_metadata=FULL` on the source first, so that later schema changes decode by name instead of refusing:
  - MySQL: `SET PERSIST binlog_row_metadata = 'FULL'`.
  - MariaDB, which has no `SET PERSIST`: `SET GLOBAL binlog_row_metadata = 'FULL'`, plus `binlog_row_metadata = FULL` under `[mariadbd]` in the option file.

  Then re-snapshot each such sync target (`sync start --restart-from-scratch`) and rebuild each such chain from a new `backup full`. Events written before the setting cannot be decoded by name.
- **Anyone whose source (MySQL, MariaDB or Postgres) applied a column RENAME swap or rotation while `sync start` followed it:** every pre-swap row the source never updated again is swapped on the target. No sluice check finds it, and `verify --depth sample` reads it as clean. **Action:** compare the affected columns' values by primary key between source and target yourself, and re-copy the table where they differ.
- **Anyone whose source applied two or more column type changes in one ALTER while syncing to a Postgres target:** later values may have been rounded or narrowed to the old type. **Action:** check the target's column types against the source, and re-copy the table if they differ.
- **Anyone with a MariaDB source on `NO_LOG` (MariaDB's default) and UNSIGNED integer columns holding values above the signed maximum:** the target or chain may hold negative values, rows under a negative key, and lost updates and deletes. **Detection:** on a Postgres target, `SELECT count(*) FROM t WHERE col < 0` for each column the source declares UNSIGNED; any hit is proof. A lost update or delete leaves no trace on the target. Across engines, `sluice verify` compares row counts only, which catches a lost DELETE and nothing else. On a MySQL-family target an INSERT of such a value refused loudly, but a keyed UPDATE or DELETE was still dropped. **Action:** re-snapshot the target (`sync start --restart-from-scratch`) and rebuild chains from a new `backup full`. If you cannot upgrade yet, `SET GLOBAL binlog_row_metadata = 'MINIMAL'` (and in the option file) makes binlog written afterwards decode correctly on older releases. Binlog already written is not fixed.
- **Operators who reorder MySQL columns, run gh-ost/pt-osc/LHM cutovers, or run multi-column ALTERs on a streamed table:** expect the new refusals in Compatibility. Set `binlog_row_metadata=FULL` to keep streams decoding across most of them, and reconcile the target's column order (or `--reset-target-data`) when `COLUMN-ORDER-CHANGED` fires.
- **Anyone holding a backup chain with a recorded MySQL/MariaDB column reorder:** it now fails `backup verify` and cannot be restored past that incremental. **Action:** take a fresh `backup full`.
- **CDC accounts on MySQL-family sources without `REPLICATION SLAVE` (MySQL) or `BINLOG MONITOR` (MariaDB 10.5+):** grant it, or the stream refuses with `SLUICE-E-CDC-REPLICATION-PERMISSION`.
- **Postgres-to-Postgres or Postgres-to-MySQL streams with no column swaps, and VStream sources:** nothing to do beyond upgrading. VStream is not verified for Bug 301 (see above).
