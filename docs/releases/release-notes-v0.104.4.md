# sluice v0.104.4

**v0.104.3 added a fourth backup-chain fingerprint epoch, and its notes said it did not. This release puts the fingerprint back.** Every backup manifest records a fingerprint of the schema it was written with; a chain restore recomputes it on every link and refuses the whole chain on a mismatch. So a field added to sluice's internal schema representation partitions chains by release. v0.104.3 added one — the flag that carries a Postgres source's primary-key constraint name — and gave it `omitempty` believing that made it invisible to chains that do not use it. It does, but only when the field is **false**, and the Postgres reader sets it **true** for every primary key, which Postgres names automatically. So on any real Postgres chain the field was present and the fingerprint moved. The field is now excluded from the fingerprint outright, which returns the bytes to exactly what v0.103.0 through v0.104.2 hashed.

The more useful half of this release is why nothing caught it. v0.104.3 shipped a frozen-golden test *specifically* to make a fingerprint change impossible to miss, and it could not see this one: its fixture carried the new field at its new value — a value no older binary could ever have written — so it only ever proved the current binary agrees with itself. **A golden fixture built from post-change values is self-referential by construction.** What found the defect was a post-release regression cycle asking the boring question, "does the new release's output still read on the old one?" That question is now a permanent CI cell, and the frozen constant is now a number a real v0.104.2 build was made to print rather than one this build computed for itself.

### Fixed

**A chain written by v0.104.3 from a Postgres source with primary keys could not be restored by any earlier release.** The fingerprint now excludes the primary-key-name flag entirely, so a chain written by this release is an ordinary E3 chain again and restores on v0.103.0 through v0.104.2. The fourth epoch does not vanish — it remains a permanent one-release detour for the chains v0.104.3 already wrote — but no release adds to it. **A chain v0.104.3 already wrote from a primary-keyed Postgres source remains readable only by v0.104.3** — its manifest records a fingerprint computed *with* the field, and nothing re-derives it, so that one release is its own epoch for restore purposes. Re-take that backup with this release, or restore it with v0.104.3. Chains v0.104.3 wrote from a MySQL source, or from a Postgres source with no primary key, were never affected. The primary-key names themselves still carry exactly as they did: the flag still rides the wire and a restore still re-emits the source constraint name. It simply no longer participates in a fingerprint, where its only effect was to move a number.

**A MySQL CDC reader could panic and take the process down when it was closed while still streaming.** The defect fixed for Postgres in v0.104.3, in the engine next door — found by looking for the class rather than by a crash. `Close` released the reader's database pool with no join against its own pump goroutine, and that pump is not merely decoding buffered bytes: the first row event for a table it has not cached sends it into a live `information_schema` query on that very pool. Unlike its Postgres sibling it did not even test the handle for nil first, so losing the race meant a method call on a nil pool and a panic on a goroutine nothing recovers. Two ordinary paths close a reader whose pump is live — `sluice sync`'s per-attempt teardown and `backup stream`'s transient-retry reopen — and both already documented the reader as joining its streaming goroutine deterministically. `Close` now cancels, joins, and only then closes the syncer and releases the pool, so by the time it returns the change channel is already closed and nothing is left reading what it just released. Unlike the Postgres fix this needed only one half: go-mysql returns a cancelled read as a plain cancellation, so there was no timeout-dressed context error for the pump to swallow — checked against the dependency's source rather than assumed, and pinned by a real-server test that hangs rather than fails if it ever stops being true. Separately, a deliberate stop no longer surfaces through `Err()` as the stream's terminating failure: a dispatch cancelled by the teardown is the teardown, not a fault.

### Compatibility

- **Chains written by this release restore on v0.103.0 – v0.104.2**, which was true before v0.104.3 and is true again. The epoch table in `docs/operator/error-codes.md` now lists v0.104.3 as the one-release detour it is, including which of its chains are affected.
- **The epoch boundaries at v0.100.0 and v0.103.0 are unchanged and still unrepaired.** A chain from an older epoch is still refused, still loudly, still before any data lands. The compatibility shim that would recompute a fingerprint at the writing release's field set remains deliberately unbuilt.
- **No format-version bump**, no flag changes, no behaviour change to any command's interface.

### Who needs this

- **Anyone who took a backup with v0.104.3 from a Postgres source.** If those tables have primary keys — which is to say, if they are ordinary tables — that chain reads only on v0.104.3. Nothing is corrupt and nothing was lost: the refusal is a fingerprint mismatch in preflight, not damage. Re-take the backup with this release and the chain is ordinary again. If you would rather not, keep a v0.104.3 binary alongside it, because no later release will read it.
- **Anyone who read v0.104.3's release notes and concluded their chains were fine.** That claim was corrected in place on the published release the same day, and this release is the fix behind the correction. If you took backups on v0.104.3 believing they were cross-compatible, this is the paragraph to act on.
- **Anyone syncing from a `mysql` or `mariadb` source under a supervisor, or running `backup stream` against one.** The shutdown panic was reachable from ordinary teardown and retry paths, the same way the Postgres one was. No CI run ever reported it — it was found by asking whether the Postgres fix had a sibling — so treat this as closing a hazard rather than as a crash you would have noticed. No action beyond upgrading. **PlanetScale and Vitess sources are not affected and are not covered**: those flavors stream through VStream, a different reader that never routes through the binlog path, and whose own `Close` was checked while here — it has the outline but not the defect, because its pump never reads the field `Close` clears. That check is recorded in roadmap item 103 rather than left as an assumption.
- Everyone else: no action needed beyond upgrading.
