# sluice v0.159.3

**HIGH fix — cancelling a `backup stream` (Ctrl-C, SIGTERM) on v0.156.12 through v0.159.2 could commit a window that ends inside a source transaction. A `sync from-backup` broker could then apply that transaction twice at exit 0, and chain restore refused the chain with `SLUICE-E-BACKUP-CHAIN-SEVERED-TRANSACTION` once a later link existed, or only WARNed `CHAIN-TAIL-OPEN-TRANSACTION` on the final link. Second, v0.159.2's fix for a key column LOOSENED inside a MySQL or MariaDB backup window did nothing when no row of the table followed the loosening `ALTER` in that window, so chain restore still merged two source rows into one at exit 0, with `backup verify` passing (Bug 306, HIGH, silent). This release also stops a busy MySQL source's CDC stream dying on a torn look-ahead read (v0.158.0 through v0.159.2, loud). It rewrites the chain-restore `KEY-COLLATION-MERGE` remedy so that `restore` can carry it out (Bug 308), corrects what the v0.159.2 notes claimed about existing chains (Bug 307), and moves sluice to pgx 5.11 (#348), with the `postgres://` DSN rewrites fixed to be safe on it. Drop-in, except that pgx 5.11 reads backslashes in key/value Postgres DSNs and multi-host port lists the way libpq does (see Compatibility). If you stop `backup stream` by cancelling it, hold a chain spanning a window that changed a key column's collation, or use a key/value Postgres DSN with a backslash or several hosts, read Who needs this.**

## Fixed

**A cancelled `backup stream` no longer commits a window that ends inside a source transaction (HIGH, silent; v0.156.12 through v0.159.2).** A cancel (Ctrl-C, SIGTERM) ends the window's context and, through the same context, closes the CDC reader's change channel, and the capture loop could observe either first. If it saw the cancel, it stored the window's last change chunk under a fresh deadline and the stop drain committed the whole window. If it saw the closed channel, it tried to store that chunk under the already-cancelled context. The store refused the write, nothing marked the window abandoned, and the drain committed every chunk stored before the cancel. Change chunks roll on a change count (`--chunk-size`, 100,000 by default) or 64 MiB, not at transaction boundaries. So when the window's last transaction spanned a chunk roll, the committed incremental held that transaction's head and ended inside it, because its commit lay in the chunk that was never stored. The pgtrigger and sqlite-trigger readers, and a failed Postgres standby-status send, record the cancel as their own error, which reached the same commit by a second path. The next window re-delivers the whole transaction. On a chain already written, `sluice restore` refuses before applying anything with `SLUICE-E-BACKUP-CHAIN-SEVERED-TRANSACTION` once a later incremental exists. If the severed incremental is the chain's last link, the restore only logs `CHAIN-TAIL-OPEN-TRANSACTION` and applies the transaction's head, a state the source never had. A `sync from-backup` broker that applied the severed incremental while it was the chain's tip only WARNs (`CHAIN-APPLIED-SEVERED-TRANSACTION`) when the next link arrives, and applies the transaction again at exit 0: a keyless row lands twice, and a key-reusing transaction is misapplied. When the window's last transaction did not span a roll, the same race committed nothing of the window instead, and the next run re-read it, so nothing was lost. By code-reading, the sources that can produce a severed transaction are those whose change stream carries transaction boundaries: MySQL and MariaDB binlog, Vitess VStream and Postgres. The trigger-CDC sources (pgtrigger, sqlite-trigger, d1-trigger) carry no transaction markers and cannot. Now both arms take the same drain. A structural backstop also abandons the window whenever the capture ends on a context-class error with changes it read still unstored, so no exit can commit the stored chunks short of them. The abandoned window is logged at WARN as `BACKUP-WINDOW-ABANDONED-OPEN-TRANSACTION`, and the next run re-reads it from the parent's end. A window cut inside a transaction is still abandoned, as before. Pinned by `TestBackupStream_CancelDrainNeverCommitsASeveredTail` (a transaction spanning a roll), `TestBackupStream_CancelDrainTakesAReaderThatRecordedTheCancel`, `TestBackupStream_UnstoredTailAbandonsOnAnyContextError`, `TestBackupStream_CancelDrainCommitsWhicheverArmSeesTheCancel` and `TestBackupStream_CancelInsideATransactionStillAbandons`. **Affected releases:** v0.156.12 through v0.159.2. v0.156.12 introduced the drain-commit that this arm reaches. Severed windows written by v0.19.0 through v0.156.11 are the earlier F-E1-SEVERED-TAIL-REPLAY class, disclosed in the v0.156.12 notes.

**A key column loosened inside one backup window no longer restores with two source rows merged when no row of the table follows the loosening in that window (HIGH, silent; Bug 306).** v0.159.2's KEY-COLLATION-LOOSENED-WINDOW fix released, ahead of the window, the key shape the previous link recorded (`utf8mb4_bin`), so that the rows written under it would be guarded. A MySQL or MariaDB full manifest records its tables with no namespace, while every row the binlog recorded names its database. The applier files a schema version, and looks one up for a row, by namespace and table. The window-start version borrowed the database name only from a version the window itself recorded of the same table, and a window whose last event for the table is the loosening `ALTER` records none. In that window the version was filed under `kd` while the rows looked up `<db>.kd`. The guard never armed, and `'A'` replayed onto `'a'` through the loosened key. This was measured on MySQL 8.4 under MINIMAL and FULL row metadata, with PRIMARY and UNIQUE keys, restoring both a `backup incremental` window and a `backup stream` rollover window, and with `--apply-concurrency=1` too. `restore` exited 0, `backup verify` passed, and the target's `sluice_cdc_schema_history` held the version under `schema_name = ''`. Now `historyReplay` gives a version that names no namespace the namespace the window's first row of a table names. The boundary at which that version is due waits for that row, and an empty transaction passes ahead of it. A later named row of that table that names a different namespace, or that arrives after the version has already gone out naming none, refuses `KEY-COLLATION-VERSION-NAMESPACE` rather than letting the lookup miss again. A row that itself names no namespace is exempt and neither sets the namespace nor contradicts it. This matters for the `ADD COLUMN` fill that both capture lanes record at the end of a window (one update per row, by primary key), which names what the manifest names, that is, none. An early version of this fix refused that fill, so a window that loosened a key and added a column failed to restore, although v0.159.2 restores it exactly. Review caught this before release. When a window with a schema delta does not itself end on the shape it recorded for such a table, the restore also releases that recorded shape at the window's end (`windowEndVersions`), so the restore's later windows of that table start from the shape this window ended on. This exists in memory only, for later windows of the same restore, and no real-server chain that reaches that state has been found. Two comparisons that keyed on a version's literal namespace (the refusal for a window the restore cannot order, and the stranded-version check) now treat a version naming no namespace as the same-named table. A window-start version is now seeded only for the table the schema delta names, and no longer for a same-named table in another database. `sync from-backup` was not affected, because it refuses such a window (`KEY-COLLATION-HISTORY-UNORDERED`) from the delta alone. Pinned by the no-trailing-row cells of `TestChainRestore_KeyCollationLoosenedInsideTheWindow` (both capture lanes, MINIMAL and FULL, PRIMARY and UNIQUE key; these cells also read the namespace from the target's schema history), `TestChainRestore_KeyCollationLoosenedPlusAddColumnWindow` (the Bug 306 window with an `ADD COLUMN` refuses with nothing merged, and the quiet window restores exactly), `TestChainRestore_KeyCollationLoosenedWindowEndsOnItsRecordedShape`, `TestChainRestore_PGKeyTightenedAsTheTablesLastEventToMySQL`, `TestWindowEndVersions`, `TestHistoryReplay_VersionTakesTheRowsNamespace`, `TestHistoryReplay_VersionNamespaceIsChecked` and `TestKeyCollationHistory_ANamespacelessVersionIsTheSameTable`. **Affected releases:** v0.159.2 (measured), where the window-start version was introduced. v0.159.0 and v0.159.1 merge the same window for the reason the v0.159.2 notes gave (KEY-COLLATION-LOOSENED-WINDOW). Earlier releases have no key-collation guard at all.

**A MySQL CDC stream (`sync start`, `backup stream`, `backup incremental`) no longer dies on a busy source with `look-ahead SHOW BINLOG EVENTS … Error 1220 … binlog truncated in the middle of event; consider out of disk` (loud, transient, nothing lost; v0.158.0 through v0.159.2).** The binlog reader's schema look-ahead, added for Bug 301 in v0.158.0, runs `SHOW BINLOG EVENTS … LIMIT 5000` when the reader is behind the binlog head and has to prove a table's catalog shape. That happens on a source with `binlog_row_metadata` MINIMAL or NOBLOB (MySQL's default), on FULL for a table holding a generated column or a type the binlog does not describe, and at the rotation settle for a table that owes a schema boundary. On the file the server is still writing, the row-count limit carries the read past the position it needs into the live tail, where a transaction being flushed can be only partly on disk. MySQL then fails the whole statement with error 1220, and the stream stopped with it. Measured on mysql:8.4 and 8.0 under eight concurrent writers: about one read in a hundred tore, every tear lay at or past the `SHOW BINARY LOG STATUS` position read just before the query, and every row before the tear reached the client intact. **MariaDB is not affected:** mariadb:11.4 serves only whole events and never raised it. Vitess sources read through VStream and do not run this look-ahead. The look-ahead now reads a page that tore at the active file's tail as one that ended where the server stopped. It is complete when it covers the position it needed, and is re-read like any short page when it does not, so it never marks a byte it did not read as checked. It still refuses `SLUICE-E-CDC-BINLOG-LOOKAHEAD-SHORT` when it cannot get past the tear, and that refusal now carries the server's own 1220 rather than pointing at `sync_binlog`. A tear in a binlog file the server has already rotated away from is not a live tail and still fails as before. Pinned by `TestDDLLookahead_TornTailPastTheEndIsEnough`, `TestDDLLookahead_TornTailRefusals` and, against a real server under write load, `TestDDLLookahead_TornActiveTail_RealServer`. **Affected releases:** v0.158.0 through v0.159.2, only when the look-ahead runs as described above.

**A chain restore's `KEY-COLLATION-MERGE` refusal now leads with a remedy that `restore` can run (LOW, loud; Bug 308).** The refusal reused the applier's remedy, which was written for a stream: give the target key the source's collation and restart, or re-copy the table with `--restart-from-scratch`. `restore` has no such flag and does not resume. A re-run after altering the key starts over from the full backup and fails with `LOAD-DATA-ROWS-SKIPPED` (measured on MySQL 8.4). v0.159.2 added the right remedy after the two wrong ones. The restore's remedy now replaces the applier's and depends on the command and the key:
- **Inside a window that itself changes a key column's collation:** take a fresh full backup after the key change and restore it into an empty target. For the `sync from-backup run --reset-target-data` cold start, which runs the same chain restore, the remedy is `sluice sync from-backup run --reset-target-data --yes` against the new chain. Before this release, that cold start was shown `sluice restore` advice.
- **Outside such a window, when sluice creates the key under a target default collation that treats the two values as equal** (for example, a byte-compared Postgres key restored onto a MySQL-family target): the table cannot be restored onto that target as it is. Leave it out with `sluice restore --exclude-table`, or use a target that keeps the source's comparison.
- **Outside such a window, for a key sluice would create correctly:** the table most likely existed before the restore, because the restore's `CREATE TABLE` is `IF NOT EXISTS`. Drop the restored tables and restore again, or leave the table out.
- **Where the engine cannot say what the key needs** (the Postgres applier): both of the previous two remedies, each with the condition under which it applies.

The applier's own remedy, which `sync start` and `sync from-backup run` still show, now names the re-copy command for each: `sluice sync start --restart-from-scratch`, or `sluice sync from-backup run --reset-target-data --yes` for a backup replay. Before, it named `--restart-from-scratch` alone, and `sync from-backup run` does not accept that flag either. Pinned by `TestRestoreKeyCollationRemedy` (each command × each key kind), `TestSyncFromBackup_ColdStartChainRestoreNamesTheBroker`, `TestKeyCollationMergeRemedy_NamesTheCollationThatConverges`, the CLI-surface gate over every invocation named, and the restore cells of `TestChainRestore_KeyCollationLoosenedInsideTheWindow` and `TestChainRestore_KeyCollationChangedAndRevertedInsideTheWindow`. **Affected releases:** v0.159.0 through v0.159.2, by code-reading: the stream-only `--restart-from-scratch` remedy dates from the MySQL applier's key-collation guard in v0.159.0, and chain restore can raise `KEY-COLLATION-MERGE` there. Nothing was lost in any of these releases, because the refusal was loud.

**A `postgres://` DSN whose query string carries a space now reaches the driver with the space intact under every pgx version (required by the pgx 5.11 this release ships; no release shipped without it).** Examples are `options=-c%20search_path%3Dapp` and the Neki `options=-c __neki.shard=<uid>` recipe. Five places re-encode a URI DSN's query before handing it to pgx: the connect path's `schema` strip in the Postgres and pgtrigger engines, the `application_name` stamp, the replication-connection rewrite, and `WithDatabase`. All five used Go's form encoder, which writes a space as `+`. pgx up to 5.10, the version every earlier release shipped, reads `+` back as a space, so no released binary was affected. pgx 5.11, which this release ships, adopts libpq's URI grammar, where `+` is a literal plus. On pgx 5.11 without this fix, the rewritten DSN reached the server as `-c+…`: `options=-c%20search_path%3Dapp` failed loudly with `FATAL: unrecognized configuration parameter "+search_path"`. Worse, `options=-csearch_path%3Dapp%20-cstatement_timeout%3D5` connected silently with search_path `app+-cstatement_timeout=5` and statement_timeout 0, losing the second option. The fix landed before the pgx bump, so no release paired the two. All five sites now share one encoder, `EncodeURIQuery`, which writes a space as `%20`. Every pgx version and libpq read that as a space, and a real `+` is still sent as `%2B`. Key/value DSNs (`host=… options='-c …'`) are passed to the driver verbatim and were never affected. One reading is deliberately unchanged: a bare `+` you write yourself in a `postgres://` query is still read as a space, because sluice's rewrite decodes the query with Go's URL parser first, even though psql, and pgx 5.11 given the DSN directly, read it as a literal plus. To mean the same thing to every tool, write `%20` for a space and `%2B` for a plus. Pinned by `TestURIRewriters_KeepOptionsSpacesForPgx` (five DSN shapes across every rewriter and the replication and pool connect chains, each asserting the exact `options` value pgx parses and that the rewritten DSN carries no `+`), `TestParseURIDSN_KeepsOptionsSpacesForPgx` (the pgtrigger copy) and `TestEncodeURIQuery_PlusIsOnlyEverASpace` (checked against an independent libpq-grammar decoder); the first two run against the pgx 5.11 this release ships. **Affected releases:** none; the defect would only have reached a binary built with pgx 5.11, and the fix landed before the bump.

## Corrected

**The v0.159.2 notes overstated which existing chains v0.159.2 protects (Bug 307).** They said anyone holding a chain that spans a key-collation window gets a restore that "now refuses `KEY-COLLATION-MERGE` rather than merging". That is true only for chains that recorded the evidence. The published v0.159.2 release body now opens with a CORRECTION banner. For a MySQL or MariaDB source, by lane:
- **A window that changed a key's collation and changed it back, captured by `backup incremental` on v0.159.1 or earlier: not detected by any release.** The incremental read the window after the revert and recorded only the catalog's reverted shape, with no schema delta, so nothing in the chain shows the key was ever `utf8mb4_bin`. v0.159.2 restores it, and replays it through `sync from-backup`, with the rows merged at exit 0, exactly as v0.159.1 did. This was measured on MySQL 8.4 (MINIMAL and FULL, PRIMARY and UNIQUE key). By code-reading, the same holds for a `backup stream` window whose reader was behind the source when it read past the revert, and for a collation change made with `sql_log_bin=0` in any chain written before v0.159.2.
- **The same window captured live by `backup stream`, with the reader keeping up: detected.** Its schema history recorded the intermediate shape, and v0.159.2 refuses `KEY-COLLATION-MERGE` (measured on a chain written by v0.159.1).
- **A window that loosened a key, written by v0.159.0 or v0.159.1 on either lane: detected from its schema delta.** v0.159.2 detects it only when a row of the table follows the loosening inside the window (Bug 306 above); this release detects it either way. Such a window written by v0.158.x or earlier records no collation change at all. By code-reading, its restore keeps the target key at the stricter collation, so nothing merges, but the target's key then compares values differently from the source's.

**Remedy for a chain that cannot be checked:** take a fresh `backup full` and use it as the base for every restore from now on. Check any table already restored from such a chain against the source and re-copy it where they differ. Use `sluice verify` on a quiesced pair, or run this collision query on the source: `SELECT k COLLATE <the target key's collation> AS kk, COUNT(*) FROM t GROUP BY kk HAVING COUNT(*) > 1`.

## Compatibility

**Drop-in.** No flags, defaults or backup format change (`BackupFormatVersion` stays 13). **The behaviour changes:**
- **A cancelled `backup stream`** now drains and commits its window whichever way the capture observes the cancel, where before it sometimes committed nothing (re-read on the next run) or a window cut inside a transaction. A window that cannot be committed whole is abandoned and logged at WARN as `BACKUP-WINDOW-ABANDONED-OPEN-TRANSACTION`; the next run re-reads it.
- **Chain restore of a MySQL- or MariaDB-source window that loosens a key's collation, where the table's last event in the window is the `ALTER`,** now refuses `KEY-COLLATION-MERGE` where v0.159.2 merged at exit 0. Restarting refuses again. The remedy is a fresh full backup taken after the key change.
- **New refusal marker `KEY-COLLATION-VERSION-NAMESPACE`,** carried inside a `KEY-COLLATION-MERGE` refusal (no new error code). It fires only when a named row of a table contradicts the namespace its schema version was filed under. The fix assumes a flat manifest is a single-namespace stream; this marker turns that assumption into a check. No real chain is known to reach it.
- **The MySQL binlog look-ahead** tolerates a page torn at the active binlog's tail instead of stopping the stream. When it still refuses `SLUICE-E-CDC-BINLOG-LOOKAHEAD-SHORT` after such a tear, the message carries the server's 1220 and no longer suggests `sync_binlog`.
- **The chain-restore `KEY-COLLATION-MERGE` message text changed** (Bug 308). Anything that matches on the old stream-oriented remedy wording will see different text. The marker and error code are unchanged.
- **`postgres://` DSNs that sluice rewrites now encode a space as `%20` instead of `+`,** which the pgx 5.11 this release ships reads as a space, so connections behave exactly as they did on earlier releases.

**Not affected by the Bug 306 fix:** `sync from-backup` (it already refused such windows), `sync start`, Postgres-source chains (a Postgres manifest names `public`), key/value Postgres DSNs, and MySQL DSNs. **Not affected by the look-ahead fix:** MariaDB sources and Vitess (VStream) sources.

**Dependencies:** the `aws-sdk-go-v2` group was bumped (#351): core 1.47.0→1.47.1, `config` 1.33.4→1.33.6, `credentials` 1.20.4→1.20.6, `service/kms` 1.60.0→1.61.1, `service/s3` 1.113.1→1.114.0. Upstream rewrote the KMS request serializers. Before landing, their output was checked byte-identical against a probe and by the `kmsverify` suite. S3 checksum defaults are unchanged.

**pgx 5.11 is in this release** (`github.com/jackc/pgx/v5` 5.10.0 → 5.11.0, #348). Two connection-string changes are operator-visible; both match libpq and were measured against both pgx versions' `ParseConfig`:
- **Backslashes in key/value DSNs.** A backslash now escapes the next character outside quotes as well as inside, so an unquoted `sslrootcert=C:\certs\root.pem` reads as `C:certsroot.pem`. Write `C:\\certs\\root.pem` (quoted or not), or use forward slashes. pgx 5.10 kept an unquoted `\c` as written.
- **Multi-host ports.** Ports pair with hosts by position. In a URI, a host written without a port gets 5432 instead of borrowing another host's: `postgres://u@a,b:5433/db` connected to `a` on 5433 under 5.10 and now connects to `a` on 5432. In a key/value DSN, a single `port` still applies to every host, but a port list whose length is neither one nor the number of hosts is refused with `could not match 2 port numbers to 3 hosts`, where 5.10 silently gave the extra host the first port.

pgx 5.11's codec changes are hardening: binary decodes are bounds-checked and refuse trailing bytes; numeric binary encode refuses a value whose 16-bit wire fields would overflow instead of silently wrapping; `timestamptz` values scanned in TEXT result format now come back in `time.Local` rather than the server's offset (the same instant; sluice's default binary lane and its pgoutput CDC lane, which has its own parser, are unaffected); and BC February 29 and years above 9999 are handled correctly.

## Known issues

- **KEY-COLLATION-PG-SAME-ANCHOR (HIGH, silent, timing-dependent; open).** A Postgres window observed live by `backup stream`, in which a row of the table was written before a key-collation change, can still restore merged. Every Postgres schema version is anchored at the same position, so a window keeps only the shape its first Relation carried. When the reader keeps up, that is the pre-change shape, and the restore arms nothing for the rows written under the stricter collation. Measured on Postgres 16 in 1 of 3 runs: with the key as the primary key, target row 1 was gone at exit 0. When the reader lags, the restore refuses instead.
- **KEY-COLLATION-PG-LOOSENED-REPLAY (HIGH, silent; open).** A Postgres key tightened (`ci` → `"C"`), given a row distinct only under the tighter collation, with that row then moved or deleted and the key loosened back, replays under the loose collation when read after the change by a `backup incremental` or a lagging stream. pgoutput carries no collation, so the reader stamps the catalog's current one. Measured on Postgres 16: target row 1 gone, exit 0.
- **KEY-COLLATION-ROLLOVER-SPLIT-DELTA-DUP (LOW to MEDIUM, loud, timing-dependent; open).** When a `backup stream` rollover splits a reverted key-collation window so that the revert lands in a later window than the row it made legal, chain restore applies that window's delta before its rows. The target's own `ALTER` then fails with `Error 1062 Duplicate entry`. Nothing merges, but the failure carries no named refusal and no remedy. Seen once in four runs under load. By code-reading, v0.159.2 does the same.
- **VStream, trigger-CDC and Postgres change streams record no collation.** No key-collation check arms for a VStream source, and a VStream window that changes a key's collation is not guarded on restore. The trigger-CDC sources (pgtrigger, sqlite-trigger, d1-trigger) record no schema versions, so a key collation changed and changed back inside one of their windows leaves nothing to arm the restore guard from (unmeasured). Postgres is covered by the first two entries.
- **KEY-COLLATION-DRAIN-NO-DELTA (MEDIUM, loud; open, unchanged).** A `backup stream` stopped mid-window, in a window that changed a key's collation, produces a correct chain that chain restore refuses (`KEY-COLLATION-MERGE`) at that segment on every run. Nothing merges.
- **KEY-COLLATION-VSTREAM-UNSTAMPED (LOW to MEDIUM, silent on a downgrade only; open, unchanged).** A VStream segment is never stamped from its window's history, so a VStream window that changed a key's collation and changed it back stays readable by older binaries, which can merge.

## Who needs this — action required

- **Anyone who ran `backup stream` on v0.156.12 through v0.159.2 and stopped it by cancelling it (Ctrl-C, SIGTERM, a supervisor stop), on a MySQL, MariaDB, Vitess or Postgres source.** A window committed at that cancel may end inside a source transaction. **Check:** run a chain restore with this release and look for `SLUICE-E-BACKUP-CHAIN-SEVERED-TRANSACTION` (a refusal) or `CHAIN-TAIL-OPEN-TRANSACTION` (a WARN on the final link) in its output. For a `sync from-backup` broker fed by such a chain, grep its log for `CHAIN-APPLIED-SEVERED-TRANSACTION` and compare its target with the source using `sluice verify --depth sample`; a keyless table holding more rows than the source is the duplicated transaction. **Action:** a chain that refuses or warns needs a fresh `backup full`; re-copy any broker or restore target that differs from the source. Upgrading stops new severed windows but does not repair a chain already written or a target already applied from one. Trigger-CDC sources (pgtrigger, sqlite-trigger, d1-trigger) cannot carry a severed transaction.
- **Anyone who restored a MySQL- or MariaDB-source backup chain with v0.159.2 (or any earlier release) across a window in which a primary-key or UNIQUE-key column's collation was loosened.** On v0.159.2 this matters most where the `ALTER` was the table's last event in that window (Bug 306). The target may hold one row where the source holds two, at exit 0, and `backup verify` would not have flagged it. **Check:** on a quiesced pair, `sluice verify` (row counts) reports a mismatch for every merge. To find candidates directly, group the key on the source under the collation the target key uses: `SELECT k COLLATE utf8mb4_0900_ai_ci AS kk, COUNT(*) FROM t GROUP BY kk HAVING COUNT(*) > 1`. **Action:** re-copy each table that mismatches. Upgrading does not repair rows that already merged.
- **Anyone holding a chain that spans such a window.** This release's restore refuses `KEY-COLLATION-MERGE` instead of merging. **Action:** take a fresh `backup full` after the key change and restore from it.
- **Anyone who relied on the v0.159.2 notes' statement that existing chains are protected (Bug 307),** especially chains written by `backup incremental` on v0.159.1 or earlier across a window that changed a key's collation and changed it back. **No release can detect those. Action:** check restored tables against the source as above, re-copy any that differ, and take a fresh `backup full` as the base for future restores.
- **Postgres-source backup operators** (KEY-COLLATION-PG-SAME-ANCHOR and KEY-COLLATION-PG-LOOSENED-REPLAY, both still open). **Action until fixed:** after any change to a key column's collation, take a fresh `backup full`. Verify any restore spanning that window against the source with `sluice verify` row counts, or with the collision query above using `GROUP BY lower(k)` as an approximation.
- **Anyone whose MySQL CDC stream stopped with `Error 1220 … binlog truncated in the middle of event` on v0.158.0 through v0.159.2:** upgrade and restart it. Nothing was lost; the stream had stopped loudly.
- **Anyone with a key/value Postgres DSN that carries a backslash (typically a Windows certificate or key path), or with a multi-host Postgres DSN:** review it before upgrading, because pgx 5.11 now reads both the way libpq does (see Compatibility). Double each backslash or use forward slashes, and give each host its own port or one port for all. A `postgres://` DSN whose `options=` carries a space needs nothing; it connects as before.
- **Everyone else:** upgrade.
