# sluice v0.156.9

**HIGH fixes — a `postgres-trigger` stream with a table filter that stalled for good while `sync health` read healthy, and a source heartbeat that could write into and delete rows from a user table on the SOURCE.** (1) v0.145.0 through v0.156.8: a `postgres-trigger` sync with `--include-table` / `--exclude-table` stopped applying anything once 10,000 consecutive change-log rows belonged to tables it excludes, and a restart did not help; nothing was lost, and a restart on this release recovers it. (2) v0.82.0 through v0.156.8: `--source-heartbeat-interval` used any existing table under the heartbeat's name as it found it, INSERTing into it and pruning its older rows on the source; it is now refused with `HEARTBEAT-TABLE-NOT-SLUICES`. Also fixed: per-change UPDATEs into a pre-vindexed sharded Vitess/PlanetScale keyspace (HIGH, loud), an idle MySQL/MariaDB binlog stream that dropped and re-copied its target after a binlog purge (MEDIUM, loud and destructive), and `sync health` exiting 1 on the MySQL heartbeat's own rows (MEDIUM). **Not a silent drop-in:** three new stops (see **Compatibility**). **Known open issue:** after a warm resume, the first schema change per table is not forwarded to the target (GC-44); read **Known open issue** if your sources change schema while a sync is running.

## Fixed

**`postgres-trigger` sources: a stream with `--include-table` or `--exclude-table` no longer stalls forever behind a burst of changes to a captured table it excludes (HIGH, silent stall, no data loss; GC-43 (a)).** The reader drops a change-log row for a table the sync excludes, and since v0.145.0 it did so without moving its watermark past the row; only a row it applied moved it. While excluded and synced tables interleaved, the next applied row carried the watermark past the dropped ones and nothing showed. Once one full poll window (10,000 rows) of consecutive change-log rows belonged to excluded tables, every poll re-read and re-dropped the same window: nothing was applied again, the persisted `last_id` stopped, a restart resumed from the same id and stopped again, and `sync health` exited 0. Measured: 10,101 rows into an excluded table, then one row into a synced table; five minutes later the target held only the rows from before the burst. The only signal was a once-per-table `CAPTURE-RELATION-MOVED` WARN that wrongly said the excluded table had moved schemas and pointed at `--restart-from-scratch`; an excluded table in the stream's own schema now logs one DEBUG line instead, and that WARN is kept for rows from another schema (GC-43 (c)). A dropped row now moves the watermark like an applied one. As a backstop, a poll that reads rows with no gap but leaves the watermark behind them now halts the stream with `CHANGE-LOG-WATERMARK-STALLED` instead of re-polling the same window (GC-43 (d)); that halt is a codeless exit 1 and means a sluice bug. Nothing was lost: the change log keeps every row above the stuck position, and the trigger auto-prune cuts only below the lowest consumer's frontier. Pinned by `TestPGTriggerStreamer_ExcludedTableBurstDoesNotStall` (a live stream across a 10,101-row burst, then a restart from below a further 10,050-row burst, the shape of an already-stuck stream after an upgrade). **Affected releases:** v0.145.0 (which introduced the scope drop) through v0.156.8.

**`sync --source-heartbeat-interval` no longer writes into, or deletes from, an existing source table that is not sluice's heartbeat table (HIGH, destructive on misconfiguration, source-side).** The heartbeat writer creates its table only when no table of that name exists, and through v0.156.8 it used any table it found under the name as it was. It INSERTs a row every interval and, once a minute, DELETEs the rows whose `ts` is older than `--source-heartbeat-prune-window` (default 1h), on the source. So if `--source-heartbeat-table-name` (or the default `sluice_heartbeat`) named an existing user table, the INSERTs landed when `stream_id` was its only required column, and when it had a `ts` column the prune deleted that table's older rows, at exit 0. Now an existing table must have exactly the shape sluice creates (`id` bigint, `ts` timestamp / timestamptz, `stream_id` varchar / text, no other column, and an ordinary table, not a view), or `sync start` stops before writing anything with `HEARTBEAT-TABLE-NOT-SLUICES`, naming the table, the columns it found and the expected shape. That shape has not changed since v0.82.0, so a table any release created still passes. A user table with exactly those three columns and types would still be accepted; there is no marker on sluice's table to key on. Applies to MySQL, MariaDB, PlanetScale, Vitess, Postgres and `postgres-trigger` sources; SQLite and D1 sources have no heartbeat. Pinned by `TestEnsureHeartbeatTable_RefusesATableThatIsNotSluices` on real MySQL and real Postgres (an extra column, the right names with the wrong types, and on Postgres a view are refused with their rows untouched; a table built with the v0.82.0 DDL is accepted) and `TestAttachSourceHeartbeat_ForeignTableStopsTheStream`. **Affected releases:** v0.82.0 (where the flag first appears) through v0.156.8.

**Sharded Vitess/PlanetScale targets vindexed on the primary key: an UPDATE sent by the per-change path no longer stops the stream (HIGH, loud, no data loss; GC-41 (e)).** vtgate refuses any assignment to a primary-vindex column, even one that assigns the column its own value, and the MySQL applier's per-change UPDATE set every column of the after-image, the unchanged vindex column included. So on a pre-vindexed sharded keyspace every UPDATE through that path stopped with `SHARDED-TARGET-VINDEX-UPDATE`: `--apply-batch-size 1`, the broker and chain restore, a partial after-image (including the default-on `ADD COLUMN` backfill) and any primary-key change. The per-change UPDATE now leaves a primary-key column out of its `SET` list when its after value is identical to its before value; the `WHERE` already pins that column to that value, and the batched path has always sent this shape. It applies on every MySQL-family flavor. "Identical" is compared by `appliershared.SameBoundValue`, floats by bit pattern, so a `DOUBLE`/`FLOAT` key moving between `0` and `-0` is still sent. A real change to a vindexed key column is still refused by vtgate with the same marker; a primary-key change that keeps the vindex value (a new `id` on a table keyed `(tenant, id)` and vindexed on `tenant`) now applies as an in-shard update. Pinned by `TestDropUnchangedKeyColumns_EveryKeyFamily`, `TestBuildUpdateSQL_LeavesUnchangedKeyOutOfSET` and `TestVStream_ShardedTarget_VindexMoveRefusesLoudly` (real vtgate, two shards). **Affected releases:** v0.127.0 through v0.156.8, per the CHANGELOG; v0.127.0 is the release that stopped refusing a sync into a pre-vindexed sharded keyspace at open. Releases from v0.99.193 (sharded targets via `--control-keyspace`) to v0.125.x that reached such a keyspace would have met the same vtgate refusal; not re-measured.

**Sharded Vitess/PlanetScale targets with a vindex column outside the primary key are refused before anything is written, instead of at the first row (HIGH, loud; GC-41 (e)).** No write sluice can send works there: vtgate refuses an `ON DUPLICATE KEY UPDATE` that assigns a vindex column, and the spellings it accepts duplicate a moved row across two shards. A sync cold start, and its stopped-copy resume, now read each in-scope table's vindexes (`SHOW VSCHEMA VINDEXES ON`) and refuse with `SLUICE-E-TARGET-SHARD-KEY-NOT-IN-UPSERT-KEY`, naming the table and the column, the refusal PlanetScale Neki already gets for a shard key outside the primary key. A table with no primary key is refused the same way. A warm restart of an existing stream runs no such preflight and still stops at the first refused write; a vschema the role cannot read gives a WARN and the same write-time refusal. Two narrow shapes are still refused only at write time, and are filed: an insert into a table whose every column is in the primary key when the first key column is a vindex column, and an update whose after-image holds only unchanged key columns. Pinned by `TestVindexUpsertMismatch_EveryShape`, `TestShardKeyUpsertMismatch_NoOpOffVtgate` and the preflight arm of `TestVStream_ShardedTarget_VindexMoveRefusesLoudly`.

**`sync` and `backup stream` from a MySQL or MariaDB binlog source: an idle source now persists its position at every binlog rotation, so a restart after binlog retention purges the old files resumes instead of dropping and re-copying the target (MEDIUM, loud and destructive, no data loss; GC-43 (r)).** The applier persists a position only at a source transaction's commit, and three kinds of binlog traffic produce none: a rotation, a heartbeat event, and a standalone GTID group (a DDL, `CREATE USER` / `GRANT`, `OPTIMIZE TABLE`). A stream that saw only those kept its persisted position in a binlog file the source then rotated past and purged, though it had read every event and missed nothing. Measured on mysql:8.0 (file/pos and GTID) and mariadb:11.4: the next `sync start` failed the resume check, and the ADR-0093 auto-resnapshot dropped the target's tables and copied them again. In file/pos mode a fully idle source was enough; in GTID mode it took standalone groups as the last GTIDs before the purge. A source that kept committing transactions (any transaction, since an out-of-scope one still persists a position) was not affected. The binlog reader now emits a row-less boundary transaction at each rotation read from the binlog when no transaction is open: the next file's start in file/pos mode, the executed GTID set in GTID mode, and on MariaDB the re-anchored lineage. A file can only be purged after the server rotates past it, so a connected stream always persists past it first. Before persisting, the boundary settles every table an earlier DDL left owing a schema change, exactly as that table's next row would; if any cannot be rebuilt at that moment, no boundary is persisted at that rotation. (Without that step, caught before release, the boundary could persist past `ALTER TABLE t MODIFY ts DATETIME(6)` and a restart then lost the forward: measured mysql:8.0 → Postgres 16, the target stayed `timestamp(0)` and microseconds were rounded.) Residuals, named in the code: a source restart switches files without a rotation event, a MySQL `XA PREPARE` that is the last group of a file waits for the next group, and VStream sources (PlanetScale, Vitess) are not covered by this change (filed). Pinned by `TestStreamer_IdleBinlogRotation_MySQLFilePos`, `TestStreamer_IdleBinlogRotation_MySQLGTIDStandaloneGroups`, `TestStreamer_IdleBinlogRotation_MariaDBStandaloneGroups`, `TestStreamer_IdleBinlogRotationOwedDDL_MySQLFilePos`, `TestStreamer_IdleBinlogRotationOwedDDL_MySQLGTID` and `TestStreamer_IdleBinlogRotationOwedDDL_MariaDB`. **Affected releases:** the drop-and-re-copy since v0.99.71 (which made the auto-resnapshot clean a populated native-MySQL target before re-copying); every release before that failed the same restart loudly.

**MariaDB sources: the lineage anchor is no longer moved to the start of the stream's first binlog file when the stream connects (LOW, weakens a refusal; GC-43 (r)).** The rotate event a replication connection opens with names the file the stream is already in, and the reader treated it as a rotation: the capture door's anchor (a mid-file offset and the GTID state at it) was replaced by offset 4 of the same file and that file's start state. On a server's first binlog the start state is empty, so the anchor became `(file, 4, "")`, which every fresh MariaDB instance reproduces, letting a rebuilt instance pass the lineage door. The anchor now moves only at a rotation read from the binlog. Separately, the idle-stream defect above meant the re-anchored lineage was never persisted, so a restart after a purge could only proceed under `UNVERIFIED-INSTANCE-IDENTITY`. Pinned by `TestStreamer_IdleBinlogRotation_MariaDBLineageAnchor`. **Affected releases:** v0.138.0 (which introduced the anchor) through v0.156.8.

**`sync --source-heartbeat-interval` on a MySQL source no longer makes `sync health` exit 1, and sluice's control tables are never part of a sync's scope (MEDIUM, loud, no data loss; GC-43 (e)).** On a MySQL source the heartbeat's rows are in the binlog, and they reached the applier, which found no such table on the target and counted every heartbeat in `sluice_cdc_skipped_tables`; `sync health` reported `SKIPPING`, exited 1, and told the operator to `sluice schema add-table` sluice's own bookkeeping table. `sluice_heartbeat` was already on sluice's control-table list, but that list was applied only when reading schemas. Now every control table is outside every sync's scope whatever `--include-table` says: the MySQL and MariaDB binlog, VStream and `postgres-trigger` readers drop such changes as they read them, and the dispatch filter in front of the applier drops them for every source. The heartbeat's transaction boundary still passes, so the persisted position still moves on heartbeats alone. This also keeps a source that is itself a sluice target from streaming its own `sluice_cdc_state` rows onward. A heartbeat table renamed with `--source-heartbeat-table-name` is now excluded too, from the cold copy as well as the stream. Before, the heartbeat created it on the source before the cold copy read the schema, so the copy created it on the target and copied it (measured on MySQL), and on a MySQL source whose heartbeat was turned on after the cold start its rows went into the skip ledger. A target that already holds a copied custom-named heartbeat table keeps it. `migrate`, `backup` and `schema diff` run no heartbeat and still read a renamed heartbeat table as user data; `--exclude-table` covers them. A Postgres source's heartbeat table is outside the stream's publication and did not reach the applier, except under a `FOR ALL TABLES` publication. Pinned by `TestStreamer_MySQLSourceHeartbeat_AdvancesPositionWithoutSkips`, `TestCDCScope_ControlTablesNeverPass`, `TestStreamer_MySQLCustomHeartbeatTable_StaysOutOfScope` and `TestCDCScope_CustomHeartbeatTableNeverPasses`. **Affected releases:** v0.123.0 (the skip ledger that trips `sync health`) through v0.156.8; earlier releases handled an unknown target table differently and were not re-measured. The custom-name copy: through v0.156.8.

**PlanetScale Neki targets: a float shard key updated from `0` to `-0` is refused as a shard-key change, instead of being dropped from the `UPDATE` while the target kept `0` (LOW, silent).** The Neki shard-key trim compared before and after with `reflect.DeepEqual`, which calls `-0.0` and `+0.0` equal, though `float8` stores them distinctly; its own comment claimed the opposite. It now uses `appliershared.SameBoundValue`, the bit-exact comparison the new MySQL trim above uses (whose first cut had the same flaw and was caught before release). Reaching it needs a `real` / `double precision` shard-key column and a source update between the two zeros. Pinned by `TestDropUnchangedShardKeysSignedZeroIsAChange` and `TestSameBoundValue_EveryFamily`. **Affected releases:** v0.150.0 (which introduced the Neki trim) through v0.156.8.

**`SLUICE-E-CDC-KEY-MATCHED-MULTIPLE-ROWS` no longer says "nothing was written" when part of the source transaction already was (LOW, loud, no data loss; Bug 294).** The message and its hint said the apply transaction was rolled back and nothing was written. That holds for the target transaction holding the refused change, but not for the source transaction when an apply batch boundary, a lane, a key change applied alone as a lane barrier, or `--apply-batch-size 1` split it across target transactions. In the filed repro the key-shifting `UPDATE` had committed and the target held two rows on one deferrable key, a state the source never had. The refusal now says this target transaction was rolled back and earlier parts of the same source transaction may already be committed, and adds "this source transaction WAS split" wherever the apply loop knows an earlier target transaction committed part of it. The remedy is unchanged: `sync start --reset-target-data`. The shard-placement refusal's "Nothing has been written" now reads "This run has written no rows yet", since a resumed cold start may hold an earlier attempt's rows. Pinned by `TestRefuseKeyScopedMultiMatch_RollbackAccount`, `TestRunBatchLoop_KeyScopedRefusalNamesTheSplit`, `TestOrchestrator_KeyScopedRefusalNamesTheSplit` and `TestGC42_TriageRepro`. **Affected releases:** v0.156.8 (where the refusal was introduced).

**`backup stream` / `backup incremental` from a Postgres source: a `SLOT-ACKED-PAST-TARGET-POSITION` refusal now names the backup chain and its remedy, instead of a sync target's `sluice_cdc_state` and a `sync start` flag (LOW, loud; GC-41 (k)).** The door runs inside the Postgres CDC reader, so every caller reaches it, but its message assumed a `sync` warm resume. On the backup path it now says the position is the end of the chain's last committed manifest, that no link of the chain holds the skipped changes, and that the remedy is a new chain from a full backup (`backup full --chain-slot`). There is deliberately no acknowledgement there: a chain that skipped the gap would restore without it on every restore that crossed it. `backup stream`'s reopen after a transient error runs no chain preflight, so there this door is the only guard. `sync start --position-from-manifest` now names that chain and offers restoring from a fresh full backup alongside the re-copy; `--accept-slot-acked-past-position` still applies there. The `sync` warm-resume message is unchanged. Pinned by `TestCheckSlotNotAckedPast_WordedByResumeOrigin`. **Affected releases:** v0.156.7 (where the door was introduced) through v0.156.8.

**`sluice sync run`: a fleet leg that stops on `CHANGE-LOG-WATERMARK-STALLED` or `HEARTBEAT-TABLE-NOT-SLUICES` is not restarted (MEDIUM, loud).** Both join the supervisor's list of refusals a restart repeats, beside `SLOT-ACKED-PAST-TARGET-POSITION`: the leg is marked `failed` and the other legs keep running, where under the default `max-consecutive-failures: 0` it would have restarted forever behind backoff. A restart after the watermark halt re-reads the same immutable change-log window through the same code; whether every possible cause repeats is UNVERIFIED (the halt means an unknown sluice bug), and it is listed because restarting forever would turn the halt back into the silent stall it exists to end. A fleet spec has no heartbeat key today, so no fleet leg reaches the heartbeat refusal yet. Pinned by `TestRefuseStalledWatermark_CarriesTheSupervisorSentinel` and `TestSupervisor_RefusalsARestartRepeatsAreNotRestarted`. **Affected releases:** none released; both refusals are new in this release.

**Docs: the skip ledger is never cleared by sluice.** The operator docs and the `cdc-sync-operator` and `fleet-operator` skills said a restored grant clears a skipped table "on the next change", and the ledger's code comment said a stream reset clears it. Nothing in sluice deletes a `sluice_cdc_skipped_tables` row: not `schema add-table`, a filter change, a restored grant, or a stream reset. A fixed cause stops new skips, and `sync health` keeps exiting 1 until the row is deleted on the target. The docs and skills now say so and give the `DELETE`. That a correct remedy leaves `sync health` red is a product gap, not fixed in this release.

**Docs: the v0.156.8 release notes overstated how few change records an idle `backup stream` window can hold.** They gave 2 × window / 10 s; the bound is 2 × ⌈window / 10 s⌉ (a 15 s window was measured holding 4), plus one more pair when a boundary emitted while the previous window was committing lands at the start of the next. The archived notes (marked corrected after publish), the published GitHub release body and the perf-parity matrix now say so.

## Known open issue

**After a warm resume, the first schema change per table is not forwarded to the target (GC-44, open, silent-loss priority; being worked on next).** With online schema forwarding on (`--schema-changes=forward`, the default), the forward step classifies each source schema change against the shape it last saw for the table. Its only starting point besides earlier changes in the same run is the cold start's own read of the source schema. After any warm resume (a `sync start` that resumes a persisted position) it has none, so the first schema change per table is taken as the new baseline and never applied to the target. Measured on MySQL file/pos → Postgres 16: stop, restart, then `ALTER TABLE fsp MODIFY ts DATETIME(6)` and a row with `10:11:12.345678`: the target stayed `timestamp(0)` and held `10:11:12.000000`, at exit 0. The same happened when the restart fell between the DDL and the table's next row, and in GTID and MariaDB mode when the resume replayed the DDL. Harm by kind: a column type widen (fractional seconds, numeric scale, varchar length) silently changes or truncates values; an `ADD COLUMN` stops the next insert loudly with a schema-drift error (measured); nullability changes are not applied by the same code path (not measured). Separately and by design (ADR-0091 §3), a type change or drop that is the first schema change on a table after a cold start is also not forwarded, logged at INFO as "schema-forward: skipping a destructive/mutating shape at the first post-cold-start boundary". A follow-up investigation measured the same loss on a Postgres source (numeric scale and timestamp precision rounded on the target), for a schema change made while the stream was stopped, and after sluice's own in-process retry of a transient error (no process restart needed). By code reading, MariaDB, VStream and `--inject-shard-column` (Shape A) streams are exposed too; `postgres-trigger`, `sqlite-trigger` and `d1-trigger` sources are not (their DDL handling refuses loudly). Also found, and also open: on a Postgres source, `timestamp(0)` → `timestamp(6)` (and the same for `time` / `timestamptz`) is classified as no change and never forwarded, even without a restart. **Affected releases:** every release since v0.99.45, when schema forwarding became the default (since v0.79.0 for the opt-in form).

- **Who is exposed:** any `sync` (or `sync run` leg) with schema forwarding on whose source tables had a schema change since the stream last started, or as the first change after its cold start. A long-running stream that has restarted even once is in scope.
- **How to check:** for every table whose schema changed on the source since the stream last restarted, compare the source and target column types and lengths (`information_schema.COLUMNS` on MySQL, `\d table` or `information_schema.columns` on Postgres). A target column narrower than the source's, or a column missing on the target, is this issue.
- **Until it is fixed:** for a column type change, apply the same change to the target yourself, in the target's dialect, before running it on the source; sluice's forwarded `ALTER COLUMN ... TYPE` (Postgres) or `MODIFY COLUMN` (MySQL) is a no-op on a column already at that type, so a later forward does not conflict. An `ADD COLUMN` that is not forwarded stops the stream loudly at the next insert; follow the remedy that stop prints. Where a column has already diverged, apply the change on the target and re-copy the affected data: values already narrowed on the target cannot be recovered from it. `sync start --restart-from-scratch` re-copies the whole stream (on a native MySQL binlog source it drops and recreates the in-scope target tables first).

## Compatibility

**New stop: `HEARTBEAT-TABLE-NOT-SLUICES` (codeless, exit 1).** A sync whose heartbeat table name matches an existing table that is not exactly sluice's shape used to run, writing into that table; it now stops at start, before writing. Pick an unused `--source-heartbeat-table-name` (sluice creates it) or turn the heartbeat off.

**New stop: `CHANGE-LOG-WATERMARK-STALLED` (codeless, exit 1, `postgres-trigger` only).** Only a sluice bug produces it; report it. Under `sync run` the leg is `failed` and not restarted.

**Earlier stop: `SLUICE-E-TARGET-SHARD-KEY-NOT-IN-UPSERT-KEY` on Vitess/PlanetScale sharded targets.** A sync cold start into a keyspace with a vindex column outside a table's primary key, or a table with no primary key, now refuses before copying instead of at the first row. Every such stream already failed. Remedy: put every vindex column in the primary key.

**Control tables and the custom heartbeat table are out of every sync's scope.** A `--include-table` that names a control table no longer admits it. A sync whose source is itself a sluice target no longer forwards that source's `sluice_cdc_state` rows. A custom-named heartbeat table is no longer created on the target or copied; one an earlier release already copied stays until you drop it.

**MySQL-family per-change UPDATE shape.** On every MySQL-family target, the per-change UPDATE now leaves an unchanged primary-key column out of its `SET` list, matching the batched path. On a target whose key value is collation-equal but byte-different from the source's, the stored bytes are now left as they are, as the batched path always did.

**Idle MySQL/MariaDB binlog streams write at rotations.** An idle binlog-source `sync` now commits one position-only target transaction per binlog rotation. An idle `backup stream` from such a source records the rotation's boundary pair, so a rollover window that spans a rotation commits instead of being skipped as empty (code-read from the backup stream's capture path, not measured). In GTID mode on an otherwise idle source, a stop after a settled `ADD COLUMN` and before the next source transaction ends with `ADD-COLUMN-BACKFILL-INCOMPLETE` although the backfill landed; acknowledge with `--accept-unforwarded-schema-change`, or avoid it with any later source transaction, including `--source-heartbeat-interval`'s.

**Message changes.** `SLUICE-E-CDC-KEY-MATCHED-MULTIPLE-ROWS`, `SLOT-ACKED-PAST-TARGET-POSITION` on the backup and manifest-handoff paths, and the shard-placement refusal have new wording; the codes and markers are unchanged. Alerting that matched the old text should key on the marker.

**Otherwise a drop-in.** No flag was removed or renamed, and no control-table or backup-format schema changed.

**Not run for this release:** the dispatch-only `psverify` (live PlanetScale, a billable cluster), `d1verify` (live Cloudflare D1) and `nekiverify` (a billable Neki cluster) suites were not dispatched, because each provisions billable or live infrastructure and runs only on the operator's call. The new Vitess vindex preflight and per-change UPDATE trim are pinned on vttestserver, not on live PlanetScale; the Neki signed-zero fix is unit-pinned only.

## Who needs this — action required

**Check after upgrading.** Upgrading stops new harm; it does not repair a source table the heartbeat already wrote into, or a target column a schema change was not forwarded to.

- **`postgres-trigger` syncs on v0.145.0–v0.156.8 whose `sluice trigger setup` captured tables the sync's table filter excludes.** Compare the source's `SELECT max(id) FROM <schema>.sluice_change_log WHERE table_name IN (<the synced tables>)` with the `last_id` in the target's `SELECT source_position FROM sluice_cdc_state WHERE stream_id = '<stream>'`. A `last_id` that stays below that maximum while the source writes to the synced tables is this stall, and so is a `CAPTURE-RELATION-MOVED` WARN naming a table you excluded and did not move. Upgrade and restart the stream with `sluice sync start`; it resumes from the persisted position, reads past the excluded rows and applies everything behind them. Do not use `--restart-from-scratch`; the resume is enough. Nothing was lost.
- **Anyone who ran a sync with `--source-heartbeat-interval` on v0.82.0–v0.156.8 whose heartbeat table name is, or might be, the name of a real table (including a user table literally named `sluice_heartbeat`).** On the source, look in that table for rows whose `stream_id` names the sync stream (the heartbeat's INSERTs), and for rows older than the prune window (default 1h) that are missing (the prune's DELETEs); restore those from a backup. Then pick an unused `--source-heartbeat-table-name`, or turn the heartbeat off; this release refuses the collision at start.
- **Anyone syncing into a pre-vindexed sharded Vitess/PlanetScale keyspace.** Put every vindex column in each table's primary key; a cold start now refuses a table where it is not. Streams that stopped on `SHARDED-TARGET-VINDEX-UPDATE` for an UPDATE that did not change the key can be restarted on this release.
- **MySQL or MariaDB binlog-source `sync` or `backup stream` with long idle periods and binlog retention short enough to purge files during them.** No data was lost, but on an affected release the next restart could drop and re-copy the target. Upgrade; on a release you cannot upgrade yet, `--source-heartbeat-interval` keeps the position moving, and `--no-auto-resnapshot` turns the drop into a loud refusal.
- **Anyone using `--source-heartbeat-interval` with a MySQL-family source.** If `sluice sync status` shows `sluice_heartbeat` under `SKIPPED TABLES`, upgrade, then delete the leftover row on the target (it is never cleared automatically): `DELETE FROM sluice_cdc_skipped_tables WHERE stream_id = '<stream>' AND table_name LIKE '%sluice_heartbeat'`. Nothing was lost; the skipped rows were heartbeats. If you use a custom heartbeat table name, drop any copy of it on the target you do not want.
- **Anyone whose `sync health` is red on a `sluice_cdc_skipped_tables` row whose cause is already fixed.** Delete that row on the target; sluice never clears it.
- **PlanetScale Neki targets with a `real` / `double precision` shard key, on v0.150.0–v0.156.8.** Only a source update between `0` and `-0` on that key is affected; if your source can produce one, compare the key's sign on source and target.
- **Every sync with schema forwarding on (the default) whose source tables change schema while it runs:** see **Known open issue**. Apply schema changes to the target yourself first until it is fixed, and check columns changed since the stream last restarted.
- **`sluice sync run` fleet operators.** Alert on `failed` legs; `CHANGE-LOG-WATERMARK-STALLED` no longer restart-loops.
