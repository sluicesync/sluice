# sluice v0.132.0

**CRITICAL fix — MariaDB `log_bin_compress=ON` sources silently dropped every row event ≥ 256 bytes from CDC (and backup incrementals) on every prior release; they are now fully captured.** This is the M2 capture-completeness release: a systematic per-lane sweep of "which write classes are invisible to each CDC capture mechanism" (45 cells, ground-truthed on real engines) found nine verified gaps, all remediated here — the MariaDB compression fix, four new coded refusals on configurations that silently lose writes, a Postgres typmod-rewrite detection fix, three new detector WARNs, and honest documentation of the two provably-undetectable cells. Drop-in from v0.131.5 — no schema, format, flag, or command change; but read the Who-needs-this section if you sync from MariaDB or your upgrade is greeted by a new refusal.

## Fixed

**CRITICAL silent data-loss: a MariaDB source with `log_bin_compress=ON` dropped every row ≥ 256 bytes from CDC — now captured identically to uncompressed events.** With that setting ON, MariaDB writes every row image ≥ `log_bin_compress_min_len` (256 B default) as a `MARIADB_*_ROWS_COMPRESSED_EVENT_V1` — all three DML verbs, including a large row's DELETE via its before-image. sluice's event dispatch never enumerated those types, so they fell through to a silent skip while the GTID/XID fold advanced the resume position past the loss: small rows kept, big rows gone, exit 0, restart-safe skip — and backup incrementals ride the same reader, so chains from a compressing source carry the same hole. The library layer decompresses these events into row images shape-identical to their uncompressed twins before any column is decoded, so the three compressed types now route through the exact same dispatch arms — every existing safety belt applies unchanged. Pinned by a family × verb × shape matrix against a real compressing MariaDB 11.4 (with an anti-vacuity floor proving the compressed events were actually on the wire, plus the size-conditional compressed/uncompressed interleave on one stream) and a dispatch-equivalence unit pin. **Affected releases: v0.99.271 (where MariaDB CDC shipped, ADR-0170) through v0.131.5 — every release that could sync a MariaDB source.** The VStream (Vitess/PlanetScale) lane is not affected — Vitess tablets run MySQL, which has no such setting.

**Postgres typmod-only column rewrites (e.g. `numeric(10,4)` → `numeric(10,1)`) are now detected and ride the standard schema-change policy.** That ALTER rewrites the table — rounding every stored value — while decoding zero messages on the wire, and the relation-change classifier compared only type OIDs, never typmods, so it classified as no change at all. Under `--schema-changes=refuse` there was no door for this shape: silent divergence at exit 0. The classifier now compares typmods, so refuse mode refuses loudly with honest text, and the default forward mode's convergence (which already held via the schema-signature path — established by a mutation probe against the real pipeline) is now integration-pinned; a family matrix covers numeric/varchar/timestamp/bit × shrink/widen/identical-resend. The same-type `USING <expr>` rewrite is content-identical on the wire and permanently undetectable — now documented honestly in ADR-0091 rather than left implied covered, alongside two typmod families that are detected-but-not-forwarded (`interval(p)` and array-element typmods refuse loudly under refuse mode but cannot be forwarded — the projected schema signature doesn't move; use the drained model for those ALTERs). **Affected releases: v0.99.45 (ADR-0091's classifier) through v0.131.5, `--schema-changes=refuse` mode only for the detected families** — default forward mode converged throughout for the families it forwards.

**Concurrent same-key backup-store writes could install a torn local file.** The local store's atomic tmp+sync+rename used a fixed temp sibling, so two incremental extenders racing through the ADR-0160 claim→Put residual window shared one temp file and could install a blend of both writers (observed once on CI as an unreadable lineage catalog). Each write now gets a unique temp file, so the rename installs exactly one writer's complete bytes. This was always loud when hit — an unreadable catalog, caught by `verify` and the chain-readability gate — never a silent value loss; present since the local backup store's introduction (v0.15.0). Cloud blob stores were never affected (object-store uploads are all-or-nothing).

## Features

**Four new coded refusals on configurations that silently lose writes.** All are wired through bundled per-lane CDC-open preflights that reach every open chokepoint at once (cold start, warm resume, backup incremental/stream, mid-sync `add-table` — AST-roster-gated so no open path can adopt a subset), and all are scoped to the operator's actual sync filter per the Bug 246 discipline, so an out-of-scope table or database never trips them:

- **`SLUICE-E-CDC-REPLICA-NO-LOG-UPDATES`** (MySQL-family binlog lane) — the source is itself a replica with `log_replica_updates=OFF`, so replicated writes never enter its binlog; observed on a real linked pair as a quietly-empty CDC tail plus perpetual resnapshot churn. Refuses only the proven conjunction (replica status non-empty AND log updates off, both variable spellings); a chained replica with log updates ON passes, and a privilege-blocked status probe warns-and-passes rather than refusing a working config on a failed read.
- **`SLUICE-E-CDC-BINLOG-DB-FILTERED`** (MySQL-family binlog lane) — server-side `--binlog-ignore-db`/`--binlog-do-db` filters silently exclude a synced database from the binlog; sluice already fetched the evidence columns and discarded them. The check proves the synced set is actually logged (do-list subset proof; ignore-arm consulted only when the do-list is empty, matching the server's own precedence), and a filter on an unrelated database passes.
- **`SLUICE-E-CDC-UNLOGGED-TABLE`** (Postgres pgoutput lane) — an UNLOGGED table in a CDC scope is cold-copied and then silently frozen forever: PG excludes it from a `FOR ALL TABLES` publication without error, and unlogged writes produce no WAL. The census runs at spanning cold start AND warm resume (because `SET UNLOGGED` succeeds mid-sync under FOR ALL TABLES and silently drops the table), at backup `--chain-slot`, and on the scoped single-schema lane (upgrading PG's raw error to a coded, pre-DDL refusal). An `--exclude-table`d unlogged table never trips it.
- **`SLUICE-E-CDC-STATEMENT-DML`** (MySQL-family binlog lane) — a privileged session's `SET SESSION binlog_format=STATEMENT` slips the existing GLOBAL-format gate, and its DML arrived as query text the generic-DDL arm silently dropped. A dispatch-time belt now refuses statement-format INSERT/UPDATE/DELETE/REPLACE, with the false-positive analysis for ROW-mode traffic stated in code (CTAS, `INSERT…SELECT`, trigger bodies, and MariaDB's `DELETE HISTORY` are all correctly exempt) and out-of-scope sessions surviving.

**Three new detector WARNs where a refusal would be wrong**, each also warning (never silently skipping) on a probe error:

- **`FK-REFERENTIAL-ACTION-CAPTURE-GAP`** — on MySQL/MariaDB binlog and Vitess/PlanetScale VStream CDC sources, cascaded child changes (`ON DELETE/UPDATE CASCADE`, `SET NULL`, `SET DEFAULT`) never enter the binlog — the server expects the replica to re-run the cascade, which sluice's appliers deliberately suppress (the Bug 164 posture) — so child rows silently diverge on most target postures. A census of the in-scope tables' FKs now warns with the remedy at every CDC open, on both lanes, bound by a cross-lane roster test. The Postgres, pgtrigger, SQLite and D1 capture lanes are exempt because they demonstrably capture cascaded changes (WAL decode / row triggers fire on cascades — matrix-verified); `RESTRICT`/`NO ACTION` FKs stay silent because they cascade nothing.
- **`DDL-DETECTION-ABSENT`** — the `postgres-trigger` engine's `--allow-polled-fingerprint` tier promised a DDL-detection loop that was never implemented, so on that tier any source DDL (including value-rewriting `ALTER … TYPE USING`) is invisible to capture. Every CDC open on that tier now warns, and every claim surface that promised the detection (the Heroku recipe, the setup-mode string, the flag help, the comparison and operator docs) now states the truth. The full fingerprint loop remains filed, not built.
- **`PREPARED-XACT-BLOCKS-SLOT-CREATE`** — a pending prepared transaction (2PC) blocks Postgres replication-slot creation with no message, so a cold start hung silently until the transaction resolved. The single slot-creation chokepoint now warns, naming the gid, database, and age plus the `COMMIT/ROLLBACK PREPARED` remedy; healthy 2PC resolves on its own, so no refusal.

**The provably-undetectable write classes are now documented for operators.** `SET SESSION sql_log_bin=0` writes (zero after-the-fact server trace) and self-hosted Vitess `ExecuteFetchAsDBA --disable-binlogs` writes cannot be detected by any CDC reader; a new section in the CDC streaming operator doc names each class, the point-in-time live-session probe that exists for the first, and `sluice verify` as the only independent catch (reading `@primary` on Vitess). A documented gap is still a gap — the matrix keeps their verdicts honest — but you can now plan around them.

## Internal

The capture-completeness matrix itself (`docs/dev/capture-completeness-matrix.md`) lands as a standing gate: 45 verdicted cells with inline evidence, and a standing rule that any new CDC lane or newly discovered write class owes a row in the same PR. The per-lane CDC-open preflights are bundled behind single openers with AST-derived roster gates (anti-vacuity-floored, mutation-verified both directions) so no open path can run a subset. Also: a freeze-window test-matcher fix (the ordering pin now tolerates the preflight bundle's legitimate pre-lock position scan while still failing if the real anchor read leaves the lock window — a matcher fix, product ordering was correct throughout), and an ADR-0135 doc correction re-scoping the D1 `recursive_triggers` caveat to what is actually unmeasured.

## Compatibility

Drop-in from v0.131.5 — no schema, format, flag, or command change; the four new error codes and three WARN markers are additive. **The new refusals can fire on a configuration that previously appeared to work:** a replica source without log updates, a server-side binlog filter covering a synced database, an UNLOGGED table in scope, or mid-sync statement-format DML were all silently losing writes on every prior release — the refusal you may now see at upgrade names a loss that was already happening, it does not create one. Lane scope is as stated per door above: the binlog-lane refusals cover the MySQL and MariaDB flavors (the VStream lane is exempt with per-cell reasons — tablet mysqld config is Vitess-owned, and the vstreamer already kills statement-format DML upstream); the UNLOGGED census is pgoutput-lane (pgtrigger's setup-time refusal was the pre-existing sibling; the MySQL family has no unlogged concept). MariaDB `log_bin_compress` goes the opposite direction: previously silent loss, now full support, no configuration change needed.

## Who needs this — action required

- **Anyone syncing or backing up from a MariaDB source: check `SHOW GLOBAL VARIABLES LIKE 'log_bin_compress'`.** If it is ON — or ever was while a sync or backup chain was running — upgrade, then run `sluice verify` against every target: rows ≥ 256 bytes written during CDC on v0.99.271–v0.131.5 are missing or stale on the target and the resume position advanced past them, so only an independent verify will surface it; a divergence needs a resnapshot. Backup chains extended from a compressing source carry the same hole in their incrementals — cut a fresh full backup to re-found the chain. If the variable was always OFF, upgrading is sufficient.
- **Postgres sources running `--schema-changes=refuse`**: if a column's precision/scale/length was ALTERed mid-sync on a prior release, that rewrite silently diverged the table — verify and resnapshot it. Default forward-mode operators converged and need nothing.
- **Anyone whose upgrade is greeted by one of the four new refusals**: your sync was silently losing writes under that configuration; the error message names the specific fix (enable log updates, remove or accommodate the binlog filter, `SET LOGGED` or exclude the table, restore ROW format).
- **`postgres-trigger` operators on the `--allow-polled-fingerprint` tier**: the DDL detection the docs promised does not exist — treat source DDL as invisible on that tier and plan migrations accordingly (the WARN now says this at every open).
- Everyone else: upgrade normally; no action.
