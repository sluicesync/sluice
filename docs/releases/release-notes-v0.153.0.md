# sluice v0.153.0

**New: sluice can now write its own control tables on a SHARDED PlanetScale Neki target.** The CDC position, the migrate breadcrumbs, the skipped-table ledger and their siblings are placed in the target's authoritative shard group automatically, at control-table creation, with no flag and no operator step. Before this, both CDC apply lanes died at their first position write with a bare `NK306`, and a `migrate` into a sharded Neki refused at its first breadcrumb; a chain `restore` creates the CDC control tables through the same applier door and met the same `NK306`. Drop-in: nothing changes on any target that is not a Neki router, and the control tables keep their names and shapes, so state written by an older binary is found unchanged and placed on the first post-upgrade start. Two error codes are added (`SLUICE-E-TARGET-CONTROL-TABLE-PLACEMENT`, `SLUICE-E-TARGET-SHARD-KEY-MISSING`); no flags.

## Features

**sluice's control tables are placed in Neki's authoritative shard group (ADR-0187, the control-table half of NEKI-NK306).** sluice's bookkeeping tables — `sluice_cdc_state`, `sluice_cdc_schema_history`, `sluice_shard_consolidation_lease`, `sluice_cdc_skipped_tables`, `sluice_target_metrics_history`, `sluice_migrate_state`, `sluice_migrate_table_progress` and `sluice_keysets` — carry no shard key, because on every other engine there is no reason for one. On a sharded Neki the database's default shard group covers `public`, and a table `CREATE TABLE` creates is absent from the operator-declared data topology by construction, so it falls to that default and every write to it is refused: `shard-key column "…" of primary index 0 is required but missing from INSERT (SQLSTATE NK306)`. Measured 2026-09-10 and bisected 2026-09-14 on live 2- and 3-shard clusters, it blocked both CDC apply lanes at the position write (the serial lane's data `INSERT` had already succeeded; only sluice's own bookkeeping failed), and on a pre-v0.150.0 tree it turned a 40-row keyless table into 80 rows across a `--resume`, because the breadcrumb that would have said *already copied* could not be written. sluice cannot fix this by creating the table differently — Neki declares a `shard_group` per table in a document that DDL does not touch. So `ensureNekiControlTablePlacement` now runs at each of the four doors that create control tables: it reads `__neki.get_data_topology()`, asks whether a shard index currently routes each table (the exact condition under which the router demands a shard key), and if one does, assigns those tables to the topology's `authoritative_shard_group` — the group PlanetScale's own guidance sizes for metadata, catalog work and sequences — writes the document back with `__neki.set_data_topology`, and waits on `__neki.wait_for_data_topology` so the write that follows cannot land on a router still routing the table by shard key. The decision half is the pure `planNekiControlPlacement`, graded against measured topology documents without a cluster.

**What it deliberately does and does not do, because a topology write is a heavier side effect than a `CREATE TABLE`.** It is a no-op off Neki, and a no-op on a Neki that routes none of the tables — an unsharded database never sees a topology revision from sluice. It happens at most once: the plan compares before it writes, and this is load-bearing rather than tidy, because writing an *unchanged* document still mints a new revision (measured 36469 then 36472 across two writes of the same bytes, nekiverify run `34910229846`) and `EnsureControlTable` runs on every start. It is attributable: the write carries the comment `sluice: place control tables in the authoritative shard group`, so `SELECT * FROM __neki.list_data_topology_changes()` shows exactly when sluice touched the topology and `__neki.get_data_topology()` shows each control table listed with its `shard_group`. The document is edited as generic JSON with `UseNumber()`, so a preview-era field sluice has never heard of round-trips through a sluice write intact. Concurrency is read-modify-write with `expected_revision` (read via `__neki.get_data_topology_revision()`, which is not on the vendor's topology page and was found by enumerating `pg_proc`), bounded to four attempts, re-reading and re-planning on conflict — a second sluice process normally finds the first's placement already in the document and writes nothing.

**A topology READ failure warns and continues; a topology WRITE failure refuses.** The two are deliberately asymmetric. Skipping the placement fails loudly later (`NK306`, never silently), and refusing on a read failure would take down an *unsharded* cluster whose role merely lacks `SELECT` on the topology — a configuration that works today — so the read failure is a warning. A write failure is the governance door: `SLUICE-E-TARGET-CONTROL-TABLE-PLACEMENT` fires at control-table creation, before any data moves, naming the database, schema, tables and the group to place them in so an operator can make the placement by hand, and it says when the cause is that sluice's role may not call `set_data_topology` (SQLSTATE `42501`). It also covers a topology with no `authoritative_shard_group`, an authoritative group that itself declares a `default_shard_index` (a table placed there would still be routed), and a control table an operator has pinned to a shard index, which sluice will not overwrite. There is deliberately no flag to proceed without the placement — the next write to a control table would be refused anyway, and the refusal carries the recipe. The manual procedure and the role requirement are in `docs/operator/planetscale-postgres-to-neki.md` under "Sharded targets and sluice's control tables".

**Every control table this engine creates is enumerated, and the enumeration is a gate.** Eight table-name constants across four doors: `ChangeApplier.EnsureControlTable` (the CDC state, schema-history, consolidation-lease and skipped-table tables), `EnsureTargetMetricsHistory`, `MigrationStateStore.EnsureControlTable` (migrate's door, which `sync` cold-start progress recording also shares) and `pgKeysetStore.EnsureKeysetTable`. Exempt with reasons: the source-side heartbeat table (a Neki cannot be a continuous-sync source, ADR-0186 probe R-1), the migrate breadcrumb's own `NK306` (already the more specific `SLUICE-E-MIGRATE-PROGRESS-UNRECORDABLE`), the bulk `COPY` writer (does not route through the applier's classifier; filed for the preflight's topology check), and pgtrigger capture tables on a Neki *source* (never run; filed, not claimed). `TestEveryPostgresControlTableIsPlacedOnNeki` derives that roster from the package's own `*TableName` constants off the AST, grades both directions, cross-checks each placed name against `appliershared.IsControlTable` so placement and the schema readers' exclusion roster cannot diverge, and carries a floor of eight constants and four call sites. Mutation-run in both directions. `TestPostgresSuite_NekiFlavorForced` pins the warn-not-refuse decision at all four doors against a vanilla server.

## Fixed

**`NK306` is classified.** Neki's missing-shard-key refusal appeared in this repository only as prose until now: the engine graded `NK013`, `NK205` and `NK213` and nothing else in the NK3xx range, so a refusal the live suite had measured twice carried no verdict — the same class as the unclassified `NK205` that killed a full-volume copy in v0.152.1. It is now `SLUICE-E-TARGET-SHARD-KEY-MISSING`, terminal, because the statement's *shape* is what the router refuses and the same shape is refused identically on retry. Reached from the applier's classifier for a user-table `INSERT`, and annotated at the wrap on both position-write lanes (serial and pipelined), which do not route through the classifier. With the placement in front of it, what remains for a control table is the path where the topology could not be read and the database turned out to be sharded after all; for a user table it means the `INSERT` sluice emitted carries no column by the target's shard-key name, and the remedy names `--exclude-table` or a routing column the source rows actually have.

**Test infrastructure, not shipped behaviour.** `TestMigrate_FastLoader_CrashMidFastChunk_ResumeIsIdempotent/postgres` blew a fixed three-minute budget on two consecutive release tags (v0.152.1, v0.152.2) at ~181 s each, passing on rerun, always as `create indexes: context deadline exceeded` — a tag run is the most contended CI this project does, so a fixed budget blows exactly when it gates publish. It is now bounded by IDLE time rather than wall clock: `progressWatchdog` rides the existing progress sink and cancels only after a window with no phase or table event, carrying a cause that says STALL rather than a bare `context canceled`, and it has its own gate because the first mutation run (idle bound of 1 ns) did not fail the test at all — the tick floor meant the watchdog had never looked. The weekly live-Neki suite gained the `set_data_topology` write-semantics probe that the placement above was designed from, the three control-table placement probes (separate schema: refused identically; constant shard key: works, kept as the fallback; authoritative group: works under sluice's own role), and an adversarial shard-key corpus for the one slice — the platform's routing of a key value — that nothing outside a live sharded cluster can exercise.

## Compatibility

No breaking changes. No flags, no config, and no change to any control table's name, schema or column shape — only the topology group the router uses to route it, and only on a Neki. A binary that wrote these tables before this release finds them unchanged afterwards, and a pre-fix cluster's control tables are placed on the first post-upgrade start, in one revision, once. Resume, backup and restore state formats are unaffected.

The engine set, exactly: this reaches **Postgres-engine targets that are PlanetScale Neki routers** (the flavor is detected at runtime per ADR-0186), and on those only when a shard index would route a control table. Every other Postgres target, and every other engine, is byte-identical to v0.152.2. An *unsharded* Neki never has its topology written. A Neki as a continuous-sync source is not possible (ADR-0186), and a Neki source under the pgtrigger engine is out of scope and filed.

Two new error codes join the operator-facing surface; none change meaning and no existing message is reworded. `NK306` on the migrate breadcrumb keeps surfacing as `SLUICE-E-MIGRATE-PROGRESS-UNRECORDABLE`.

## Who needs this

- **Anyone running `migrate`, `sync` or `restore` into a SHARDED PlanetScale Neki.** In v0.150.0 through v0.152.2 — every published release that recognises a Neki target — a sharded target could not be used: `sync` died at its first position write on both apply lanes with an unclassified `NK306`, `migrate` refused at the first breadcrumb with `SLUICE-E-MIGRATE-PROGRESS-UNRECORDABLE`, and a chain `restore` — which creates the CDC control tables through the same applier door — met the same `NK306`. All loud; nothing to re-verify. The silent `--resume` doubling of a keyless table was measured only on a pre-v0.150.0 tree and was already refused loudly from v0.150.0 on. The action is to upgrade and start: sluice makes the placement itself. Check the role it connects as can call `__neki.set_data_topology` (the default role a Neki database hands out could when this was measured); if it cannot, the run refuses at control-table creation with `SLUICE-E-TARGET-CONTROL-TABLE-PLACEMENT` and the exact entries to add by hand, before any data moves.
- **Anyone auditing topology changes on a Neki cluster.** Expect one entry in `__neki.list_data_topology_changes()` with the comment `sluice: place control tables in the authoritative shard group`, naming only `sluice_*` tables, on the first start after upgrading — and none after that.
- **Anyone on an unsharded Neki, or any non-Neki target.** Nothing to do; nothing changes.
