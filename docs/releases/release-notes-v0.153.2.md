# sluice v0.153.2

**HIGH fixes — three silent-loss defects in long-shipped code, each reproduced on a real server through the shipped binary by the 2026-09-15 Tier-3 audit's refuters, plus one credential leak in an error message.** A YAML `redactions:` rule missing a required numeric key ran with the Go zero value at exit 0 — for `mask` / `outer` that meant the source value shipped UNCHANGED under a rule that declared it masked — while the identical `--redact` spec was refused (every release since v0.54.0). The MySQL binlog CDC lane emitted a `TRUNCATE` with the statement's own spelling on a `lower_case_table_names` source while every row event carried the stored name, so the truncate was skipped against a case-sensitive target (target kept every row the source dropped) or landed on an `--exclude-table`d table on a folding one, both at exit 0 (every release). And a REBUILT MySQL source presenting an empty or behind GTID set was auto re-copied OVER a populated target, losing every row CDC had written since the source's backup, stream green, exit 0 (v0.138.0 through v0.153.1). Three behaviour changes, all in the direction of refusing where sluice used to proceed; no flags, no config keys, no state or on-disk format changes. Read **Who needs this** — two of the three have retroactive consequences an upgrade cannot repair.

## Fixed

**A YAML redaction rule with a required numeric option omitted is refused at config load, exactly like the option-less CLI spec (A0915-CFG-HIGH-1).** `config.Redaction` (`internal/config/config.go`) held `length`, `m1`, `m2`, `min` and `max` as flat integers, so an omitted key decoded to `0` and the YAML arms in `cmd/sluice/redact_flag.go` — which checked only `Length<0`, `M1,M2<0` and `Min>Max` — built the strategy and ran. Measured on real Postgres through the shipped binary: `strategy: truncate` with no `length:` emptied every row; `strategy: randomize` / `form: int` with no bounds wrote `0` to every row; `mask` / `inner` masked the whole value; and `mask` / `outer` masked NOTHING — the source PAN shipped unchanged under a rule that declared it masked — all at exit 0, no WARN, while the four identical `--redact` specs were refused. The doc comment on the struct asserted a missing-bounds refusal no code performed. The fix makes omission representable (`Length`, `M1`, `M2` are now `*int`; `Min`, `Max` are `*int64` — the zero-value-safe-defaults rule applied to config) and refuses `nil` with the SAME error values the CLI parser returns (`errTruncateRequiresLength`, `errRandomizeIntRequiresBounds`, `errMaskGenericFormNoMargins`), so the two surfaces cannot drift. A key that is present with the value `0` is still honoured (`length: 0`, `m1: 0`, `min: 0`), exactly as `truncate:0` / `mask:inner:0,4` / `randomize:int:0,9` are on the CLI. The spurious-option check is now presence-based: `m1: 0` on a preset mask form, or `min: 0` on `form: email`, is refused as a field that form does not take (previously tolerated silently). Sibling sweep across every optional option × strategy × form on the YAML surface is in the commit; `value` (static), `char`, `brand`, `country_code` and `key` are exempt because their empty value is a documented default on both surfaces, and `algo`, `form`, `dict` and `table` were already refused on both. Pinned by `TestRedactCLIAndYAMLAgreeOnRequiredOptions` (derives its case list from `strategyFromSpec`'s own supported-spec refusals — 19 option-less shapes today, floor 10 — feeds each to BOTH parsers and requires the same verdict and, for the refusals this fix added, the same error value), `TestMergeYAMLRedactions_OmittedRequiredOptionIsRefused` (the four shapes plus the explicit-0 and presence-based-spurious halves), `TestRedactYAML_MaskOuterWithoutMarginsRefusedThroughConfigLoad` (the compliance-shaped arm through a real YAML file and `config.Load`) and `TestLoadYAML_RedactionOptionPresence` (each of the five keys × omitted → nil, 0, non-zero, -1, and 2^53+1 for the int64 pair). Mutation-run in both directions with each red read as the graded assertion's own. `docs/redaction.md` gains a "YAML field reference" table — the keys `length`, `m1`, `m2`, `min`, `max` appeared in no operator doc before this release. Affected: every release since each arm shipped — `truncate` since v0.54.0, `mask` inner/outer since v0.56.0, `randomize` int since v0.59.0 — through v0.153.1, on `migrate`, `sync`, `backup` and `preview` (the four commands that merge `redactions:` from config). The CLI `--redact` path was never affected. The pre-tag value-fidelity review then found the same substitution through another spelling: YAML's weak typing decoded `length: ""` as a present `0`, wrapped `min: 9223372036854775808` to `-2^63`, and coerced `5.7` and `true` to integers, where the CLI refuses all of them. `optionalIntegerHook` (`internal/config/optional_integer_hook.go`) now refuses an empty string, a non-integral or boolean value, and any magnitude at or above 2^53 for these keys — yaml.v3 routes an out-of-range literal through float64, so a plain range check accepted `-9223372036854775809` as exactly `-2^63` — while `"5"`, `-0`, `1e3`, `0x10` and `null` decode exactly as before; pinned in `TestLoadYAML_RedactionOptionPresence` and as eleven CLI/YAML refusal pairs in `TestRedactCLIAndYAMLAgreeOnRequiredOptions`.

**The MySQL binlog CDC lane emits a `TRUNCATE` under the server's stored spelling on a folding source (A0915-MYSQL-HIGH-1).** On a `lower_case_table_names=1` server the row events for a table carry the stored lower-case name from the Table_map, but the `TRUNCATE` arm of `CDCReader.dispatch` in `internal/engines/mysql/cdc_reader.go` emitted `ir.Truncate` with whatever the operator typed — `TRUNCATE TABLE T1` went out as `T1`. v0.148.1's RC-1b fix folded the ADMISSION compare (`databaseInScope`) and left the PAYLOAD raw, and the pipeline's dispatch filter matches byte-exactly. Measured through a real `sync start` on mysql:8.0 at lct=1: into Postgres, the truncate was skipped as "target lacks this table" and the target kept every row the source had dropped, behind a WARN whose every clause was wrong (it said the source still held the rows, and pointed at `schema add-table`); into a folding MySQL target with `--exclude-table=t1`, the EXCLUDED table was truncated, with no WARN, no ledger row and no health signal, because the filter did not match `T1`. The fix is `CDCReader.truncateEmitNames`: the parser's raw spelling, defaulted to the QueryEvent's USE-context schema, then RESOLVED to the stored spelling rather than folded by imitation: on a case-sensitive server nothing is consulted; otherwise the reader's own Table_map record and schema cache answer first, then a case-insensitive `information_schema` lookup under the server's own `LOWER()`, and only when neither knows the table does it fall back to the lower-case fold on `lower_case_table_names=1` (where the stored name is lower-case by definition) and to the statement's own spelling on `lower_case_table_names=2` (where the store keeps the as-created case and a lower-case fold would have DIVERGED from the row events; the pre-tag value-fidelity review's catch against the first cut, and unmeasurable in a Linux container, so marked UNVERIFIED PREMISE at the function) — the same server setting `databaseInScope` folds under, so the two cannot disagree about it. The resolution lives at the emit site, not in `parseTruncateTable`, whose contract is the statement's own spelling. On a case-sensitive server (lct=0) names stay byte-exact, because there `t1` and `T1` are two tables. The skip WARN is now op-aware: `ir.SkippedTableRemedyFor` names `ir.SkippedTableTruncateRemedy` for a skipped TRUNCATE ("the source does NOT still hold the rows it dropped; if the target holds this table under another spelling it is now AHEAD"), and the shared `ir.SkippedTableRemedy` printed by the op-blind CLI surfaces scopes its "source still holds every row" claim to row changes so it is true for every op. Sibling sweep: every `ir.Change` construction site in the MySQL engine whose name does not come from a Table_map is graded by `TestEmittedChangeNamesFollowTheServersFold` (an AST roster, fail-by-default, 15 sites today, floors ≥1 folded / ≥4 Table_map / ≥10 total); the two VStream `ir.Truncate` sites are EXEMPT by design — that lane never reads `lower_case_table_names` and its keyspace scope compare is byte-exact too, so a folding vttablet is a stated, unmeasured gap. Pinned on a real server by `TestCDCReader_EmittedTruncateNameFollowsTheServersFold` (mysql:8.0 at lct=1 AND lct=0; the expected value is the Table_map-sourced `ir.Insert`'s name for the same table, independent of the code under test; the lct=0 cell pins mixed case so a fold-always mutant reds), and in unit by `TestTruncateEmitNames_FollowsTheServersFold` and `TestWarnSkippedTable_HintIsOpAware`. Affected: every published release — the binlog lane has emitted the statement's own spelling since it first recognised `TRUNCATE` in v0.1.0, and v0.148.1 through v0.153.1 folded the scope compare without folding the payload. It fires only on a folding MySQL source (`lower_case_table_names` non-zero; measured at 1) when the `TRUNCATE` statement's spelling differs from the stored name. Postgres, SQLite/D1, the trigger-CDC engines and the VStream lane are not touched.

**A rebuilt MySQL source presenting an empty or behind GTID set is refused (`FOREIGN-LINEAGE-REFUSED`) instead of auto re-copied over the target (A0915-MYSQL-HIGH-2).** `verifyGTIDLineageContinuity` classified an EMPTY `@@global.gtid_executed` as `ir.ErrPositionInvalid` unconditionally, on the premise "a same-server RESET MASTER — there is no other lineage here to re-copy from", and that sentinel routes the streamer's automatic recovery: drop the target's in-scope tables, re-copy from whatever now answers the DSN. Measured false with a real `sync start` on mysql:8.0: a REBUILT instance at the same address — a restore followed by the documented `RESET MASTER`, or a logical load under `sql_log_bin=0` — presents an empty set with its stale rows intact, and the target was reduced to those stale rows; every row CDC had written since the source's backup was gone, `tables_dropped=1` in the WARN, stream green, exit 0. The BEHIND arm (every resume UUID present, sequence numbers short) had the same harm from a restore that seeds `gtid_purged` under the OLD uuid (`mysqldump --set-gtid-purged=ON`, the xtrabackup restore step). In both, sluice had the witness in hand — it stamped the replacement's `@@server_uuid` into the position it wrote after destroying the target. The fix, MySQL only: on the EMPTY and BEHIND arms (only those two, so the contained path stays a single round trip) read `@@global.server_uuid`; if the resume set does not name that uuid, `gtidLineageForeignByIdentity` returns `ir.ErrPositionForeignLineage` under `SLUICE-E-CDC-LINEAGE-MISMATCH`, naming the uuid and saying to wait for a lagging replica to catch up or `--restart-from-scratch` for an intended replacement; if it does, the existing `ir.ErrPositionInvalid` stands (a same-server `RESET MASTER` or rollback — the v0.148.2 decision, now scoped to the instance it was made for). A witness that cannot be read is a plain error carrying neither sentinel. `VerifyLineage`, the reactive mid-stream door, reaches the same function and is pinned. What the uuid witness cannot tell apart is stated at the function: a physical restore that carries `auto.cnf` (same uuid) onto another host reads as same-server and still takes the re-copy; a replica promoted and then RESET is refused and costs one `--restart-from-scratch` — the safe direction. Sibling sweep of every arm that reaches the automatic re-copy from a lineage verdict: the non-empty-disjoint arm was already foreign (v0.148.2); file/pos was already foreign via `verifySourceInstanceIdentity`; `backup incremental` (`internal/pipeline/incremental.go`) reaches the same function and returns terminally, its diagnosis for the rebuilt shape now the foreign one; VStream unchanged; **MariaDB NOT CHANGED — a known gap**: MariaDB has no `@@server_uuid` and its GTIDs are domain-server-seq, so a same-server reset and a rebuilt node are indistinguishable from the server's answers, and refusing every empty `@@gtid_binlog_state` would refuse every legitimate reset; that is an operator policy call filed in `docs/dev/audit-backlog.md`, and `TestGTIDResumeMariaDBBindsLineage` measures the verdict on a real rebuilt mariadb:11.4 every run, skips with the reason while the gap stands, and fails the day the verdict turns foreign so the cell gets promoted. Pinned by `TestLineageVerdicts_ForeignIsTerminalResetIsNot` (fake server, the full {empty, behind} × {uuid named, uuid foreign} matrix plus case-insensitive uuid, a promoted-replica multi-uuid set and an unreadable witness), `TestVerifyLineage_AnswersOnlyTheForeignQuestion` (the reactive door, rebuilt shape), `TestGTIDResumeBindsLineageAcrossInstances` (real mysql:8.0 — its old "SAME instance after RESET MASTER" cell had booted a DIFFERENT container and pinned the destructive route; it is now the rebuilt-EMPTY and rebuilt-BEHIND cells, which must be foreign, plus the real same-server EMPTY and BEHIND cells, which must keep `ir.ErrPositionInvalid`), and `TestStreamer_MySQLForeignLineage_RefusesTheAutomaticRecopy` (real MySQL end to end: a persisted position re-stamped under a uuid the server never had plus `RESET MASTER` → `FOREIGN-LINEAGE-REFUSED` with the target still holding its 4 rows where the re-copy would leave 1; the same-server `RESET MASTER` cell still re-copies). `docs/operator/cdc-streaming.md` no longer claims an empty executed set is always a same-server reset. Affected: v0.138.0 through v0.153.1 — v0.138.0 introduced the `GTID_SUBSET` lineage binding that routed every not-contained set, empty ones included, to the automatic re-copy; v0.148.2 carved the non-empty-disjoint arm out as foreign and explicitly labelled the empty arm same-server. Releases before v0.138.0 had no lineage binding at all, and what they did with a rebuilt instance was not re-derived for these notes. MySQL binlog GTID mode only. Two follow-ups from the pre-tag review: the executed-set probe and the `@@server_uuid` witness are now ONE statement, so a load-balancing proxy cannot answer them from two different backends — with the stated cost that a source which answers `GTID_SUBSET` but refuses `@@global.server_uuid` now fails loudly on every arm; and `VerifyLineage` with an unreadable witness is pinned to its documented fail-open answer. What the witness cannot see, stated at the function and in the operator doc: an in-place same-server restore (`RESET MASTER` then the dump reloaded on the same box, `auto.cnf` untouched) presents EMPTY or BEHIND under the position's own uuid and still takes the automatic re-copy, reducing a target that is ahead of the source. That is a residual, and whether the BEHIND-with-own-uuid arm should be terminal is an open policy question, not decided here.

**A blob-store URL that fails to parse no longer carries the credential it redacted into the error (A0915-SEC-MEDIUM-1).** `annotateBlobURL` and `extractBlobPrefix` in `internal/pipeline/blobcodec/blob_store.go` printed `redactBlobURL(urlStr)` and then `%w`-wrapped the raw `*url.Error`, whose `Error()` embeds the verbatim input, userinfo included — undoing the redaction one argument earlier — and the no-scheme branch (`//KEY:SECRET@bucket/p`, a dropped `s3:`) echoed `urlStr` with no redactor at all. Reachable from every `backup` subcommand that takes a store URL, `sync … --backup-target` and `--position-from-manifest`, with no prior validation. All three sites are fixed: the two wraps go through `safeerr.SafeParseError` (the leaf helper the six PG/pgtrigger DSN sites already use, which keeps only the reason), the echo goes through `redactBlobURL`. Sibling sweep across all 16 non-test `url.Parse` / `url.ParseRequestURI` sites under `cmd/` and `internal/` is in the commit — seven already routed through `SafeParseError`, the rest compare the error to nil or discard it, and `parseAzureKeyID` is exempt with its reason because a Key Vault key ID is a public locator with no credential position. Gated repo-wide by `TestEveryURLParseErrorIsWrappedThroughSafeParseError` (`internal/docsync`: an AST walk that follows each `url.Parse` error to the end of its scope and classifies every use, fail-by-default exemption map with a stale-entry check, floors 10 sites / 3 routed; it reaches the ERROR only — the raw-string echo shape has no repo-wide gate and is pinned per-site) and `TestBlobStore_ParseFailureErrorsDoNotLeakCredentials` (both leak shapes × `annotateBlobURL`, `extractBlobPrefix`, `OpenBlobStore`; secret and access key asserted absent, locator asserted present). Affected: every release with a URL-addressed blob store, v0.16.0 through v0.153.1 — the redaction added in v0.99.214 and the userinfo stripping added in v0.110.1 covered the printed URL and never the wrapped error. The pre-tag review found a fourth site the enumeration had missed: the cloud driver's OWN error from `blob.OpenBucket` prints the URL with its userinfo — `s3://KEY:SECRET@bucket/p?bogus=1` came back as `unknown query parameter "bogus"` carrying the secret, and a typo'd scheme likewise — so `scrubBlobDriverErr` now replaces the raw URL, both userinfo segments and every escaping of the password in that error's text before it is wrapped, pinned by driver-refusal cells on s3, gs, file and an unknown scheme. Not a data-loss defect: it reaches error output and logs, and only when the URL is malformed or refused by the driver.

## Compatibility

No flags, no config keys, no control-table, resume, backup or restore format changes. Three behaviour changes, each a refusal where sluice used to proceed:

1. **A YAML `redactions:` rule with a required numeric key omitted now refuses at config load** — `strategy: truncate` without `length`, `strategy: mask` with `form: inner` or `form: outer` without both `m1` and `m2`, and `strategy: randomize` with `form: int` without both `min` and `max` — with the same error the CLI gives for the option-less spec. In v0.54.0 through v0.153.1 those rules loaded and ran with the zero value: every row `0` (randomize int), empty (truncate), fully masked (mask inner), and for `mask` / `outer` the source value UNCHANGED. An explicit `0` is still honoured. A numeric key that is present — even as `0` — on a form that takes none (`m1: 0` on a preset mask, `min: 0` on `form: email`) is now refused as spurious; before, it was silently ignored. If a config that loaded on v0.153.1 refuses on v0.153.2, the rule it names was never doing what it said.
2. **A MySQL source whose executed GTID set is EMPTY or BEHIND the resume position, AND whose `@@server_uuid` is absent from that position's set, is refused as `FOREIGN-LINEAGE-REFUSED` (`SLUICE-E-CDC-LINEAGE-MISMATCH`, terminal, target untouched) instead of being auto re-copied.** This includes a genuinely lagging replica behind a failover or load-balanced endpoint, which in v0.138.0 through v0.153.1 was re-copied FROM — dropping the target's in-scope tables and refilling them from the lagging node. Wait for it to catch up and retry (the resume proceeds once the position is contained, with the target intact), or `--restart-from-scratch` if the replacement is intended. A same-server `RESET MASTER` — the instance whose uuid the position names — keeps the automatic re-copy exactly as before. MariaDB is unchanged: it carries no instance identity, so a rebuilt MariaDB node with an empty `@@gtid_binlog_state` still takes the automatic re-copy — a KNOWN GAP, stated in the operator doc and measured every run by a skipping cell that promotes itself the day a witness exists. VStream, file/pos and the non-empty-disjoint GTID arm are unchanged (already terminal since v0.148.2).
3. **`ir.SkippedTableRemedy` — the remedy text the skipped-table WARN, `sluice sync health` and the stop summary print — is reworded**, and the applier's WARN for a skipped TRUNCATE now names `ir.SkippedTableTruncateRemedy` instead. Anything matching on the old sentence "the source still holds every skipped row" needs updating; the log line's message and the `sluice_cdc_skipped_tables` ledger are unchanged.

The TRUNCATE name resolution reaches only the MySQL binlog lane on a folding source (`lower_case_table_names` non-zero) and changes nothing on a case-sensitive server, where names stay byte-exact; a stored-name lookup that fails now stops the stream like a schema-load failure would. A YAML redaction value that is an empty string, a non-integer, a boolean, or beyond ±2^53 for `length`, `m1`, `m2`, `min` or `max` is refused at load too. A MySQL source that answers `GTID_SUBSET` but refuses `@@global.server_uuid` now fails the resume loudly on every arm, where before only the empty and behind arms read it. The VStream lane emits TRUNCATE names unfolded, as before. Postgres, SQLite/D1 and the trigger-CDC engines are byte-identical to v0.153.1 on every path this release touches; the blob-store change alters error text only.

## Who needs this — action required

- **Anyone with a YAML `redactions:` rule that omits `length` (truncate), `m1`/`m2` (mask inner/outer) or `min`/`max` (randomize int).** The config now refuses at load; add the key. Then look back: every `migrate`, `sync`, `backup` or `preview` run under that rule since v0.54.0 / v0.56.0 / v0.59.0 respectively produced wrong output at exit 0. Under `mask` / `outer` the column was NOT redacted — the source value shipped verbatim — so any target or backup written under that rule holds the PII it claimed to mask and needs the same treatment as an unredacted copy. Under `truncate`, `mask` / `inner` and `randomize` / `int` the column is destroyed (empty / fully masked / all `0`) rather than leaked; re-run once the rule is fixed. `--redact` on the CLI was never affected.
- **Anyone syncing FROM a MySQL source with `lower_case_table_names=1` (or 2) whose operators issue `TRUNCATE` in a spelling that differs from the stored name.** Upgrade, then check both harms. Into a case-sensitive target (Postgres, or MySQL at lct=0): query `sluice_cdc_skipped_tables` and your logs for the "target lacks this table" WARN with `op=truncate` — each one is a table the source truncated and the target still holds in full; the target is AHEAD of the source and needs the truncate applied by hand before anything is re-attached (the WARN now says so). Into a folding MySQL target with `--exclude-table`: an excluded table whose name the source truncated in another case was truncated on the target with no WARN — compare row counts against what you expected the exclusion to preserve. Nothing to do on a case-sensitive source, or on any other engine.
- **Anyone whose MySQL GTID-mode sync, on v0.138.0 through v0.153.1, logged the "names transactions this source no longer records (RESET MASTER, or a fresh instance)" refusal followed by the automatic re-copy after the source had been restored or rebuilt.** The target was reduced to the rebuilt instance's rows; every row CDC had written between the source's backup and the rebuild is gone from the target, and the upgrade does not bring it back — recover from a target backup or from the original source, then `--restart-from-scratch`. Going forward the same shape refuses with `FOREIGN-LINEAGE-REFUSED` and the target is untouched. If your endpoint fronts a replica set, expect the refusal on a lagging node where you used to see a re-copy: wait and retry. MariaDB operators: the rebuilt-node shape is still auto re-copied there — treat a `RESET MASTER`-shaped WARN on a MariaDB source that was restored as this finding until the gap closes.
- **Anyone who has pasted a failed `backup … --target` error, or a `sync --backup-target` / `--position-from-manifest` error, into a ticket or log aggregator.** If the URL had embedded `KEY:SECRET@` userinfo and failed to parse (or lost its scheme), the message carried the credential verbatim; rotate it and scrub the record. A URL that parsed was never affected.
- **Everyone else.** Nothing to do; nothing changes.
