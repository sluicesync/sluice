# CDC streaming: the applier retry policy

`sluice sync start` opens a change-data-capture stream and applies
source changes to the target indefinitely. On a managed database
(PlanetScale-Vitess, managed Postgres / Patroni), the apply path will
periodically hit a **transient** infrastructure error — a Vitess
transaction-killer rollback, a vtgate restart, a tablet failover, a
throttler engagement, a Postgres serialization failure, a standby
promotion, or a connection reset. None of these mean the operator's
data or configuration is wrong; they are normal operational events on
a managed deployment.

Sluice absorbs these with a **bounded, observable retry policy** on
the applier's batch loop. The full design rationale lives in
[ADR-0038](../adr/adr-0038-applier-retry-on-transient-errors.md); this
page is the operator-facing summary.

## What gets retried (and what does not)

The retry is **default-deny**: an error is retried only if it matches
a documented transient shape. Anything else exits the stream loudly so
a real problem surfaces immediately rather than being masked by a
retry loop.

**MySQL / Vitess — retriable:**

- `Error 1213` (InnoDB deadlock victim) — the idempotent replay
  succeeds against the new lock order.
- `Error 1105 (HY000)` whose message contains `vttablet` **and** one
  of `code = Aborted` / `code = Unknown` / `code = Unavailable` /
  `code = ResourceExhausted` — the Vitess transient class (tx-killer,
  vttablet not ready, failover in flight, throttler engaged).
- Connection lost / EOF / bad-connection / per-exec timeout — the
  driver reconnects on the next attempt.

**PostgreSQL — retriable:**

- `40001` (serialization failure), `40P01` (deadlock detected).
- `57P01` / `57P02` / `57P03` (admin / crash shutdown, cannot connect
  now) — standby promotion or restart.
- The entire `08*` class (connection exception).
- Connection lost / EOF / per-exec timeout.

**Trigger-CDC transports (pgtrigger / sqlite-trigger / d1-trigger) —
retriable (v0.99.286):** transient transport shapes on the change-log
poll — connection reset/refused, timeouts, TLS handshake timeout, and
(D1) HTTP 408/429/5xx. Since v0.99.289 the `postgres-trigger` poll
also retries PG's connection-availability SQLSTATEs — `57P01`/`57P02`/
`57P03` (admin/crash shutdown, cannot connect now — a managed-PG
maintenance restart or standby promotion) and the class-08 connection
exceptions. Wrong DSN, bad token, a missing change-log table (`42P01`),
and decode faults stay terminal.

**Connect-phase transients — retriable (v0.99.288):** each retry
attempt first has to re-establish its connections (reopen the target
applier and source readers), and a transient network failure there —
a dead pool connection (`invalid connection`), reset/refused,
timeouts, TLS handshake timeout — now rides the same bounded budget
instead of exiting the stream. Positively-matched shapes only: DSN
parse errors, bad credentials, unknown-host, and coded refusals stay
terminal, and a target that can never be reached still exhausts the
budget loudly.

**Explicitly NOT retriable (both engines):** duplicate-key
(`1062` / `23505`). A duplicate key during continuous sync is either
an operator data issue (a non-PK uniqueness violation) or a sluice
idempotency gap — both deserve a hard, loud failure, never a
retry-and-mask. This is a deliberate fence (see ADR-0038 and GitHub
issue #14); it is not a gap.

## The retry shape

When a retriable error fires, the streamer waits and re-applies the
batch:

- **Exponential backoff**, starting at `--apply-retry-backoff-base`
  (default `100ms`), doubling each attempt, capped at
  `--apply-retry-backoff-cap` (default `30s`). With defaults the
  per-attempt sequence is `100ms → 200ms → 400ms → 800ms → 1.6s →
  3.2s → 6.4s` — seven sleeps, not eight: the final failure exhausts
  the budget and returns without waiting, so the 12.8s term this list
  used to end with was never reached.
- **Bounded attempts.** After `--apply-retry-attempts` (default `8`)
  *consecutive* failures of the same un-progressed position, the
  stream exits with a terminal `apply retry budget exhausted` error
  that preserves the most recent transient. Eight attempts at the
  default schedule is **12.7 seconds** of deliberate backoff
  (100ms → 200ms → 400ms → 800ms → 1.6s → 3.2s → 6.4s; the eighth
  failure exhausts the budget without sleeping). The observed wall
  clock is longer and varies by failure shape — a half-open target
  can burn up to `--apply-exec-timeout` (60s by default) per attempt
  before the error even arrives — but the *deliberate* wait is those
  12.7 seconds.

  That is short. It absorbs a tx-killer or a momentary blip; it does
  **not** ride out a Patroni failover or a vtgate restart, which take
  longer than the whole budget. If you need that, widen it — see
  `--apply-retry-attempts` below. Until v0.141.4 this paragraph, the
  ADR and the CLI help all claimed "roughly four minutes", arrived at
  by multiplying the 30s cap by the attempt count; the schedule
  exponentiates from 100ms and never reaches that cap at eight
  attempts.
- **Counter resets on progress.** If the persisted CDC position
  advanced between attempts (a partial batch committed before the
  failure), the consecutive-failure counter resets to 1. A stream
  surviving for days does not accumulate retry debt from unrelated,
  widely-spaced transients.
- **Idempotent by construction.** A retried Insert is absorbed by the
  PK-keyed UPSERT; a retried Update/Delete is a no-op against the
  already-applied state (ADR-0010). On the batched path, position and
  data are written in the same target transaction, so a rolled-back
  attempt rolls back both. On the per-change path, rows inside a
  source transaction commit position-free and the position lands with
  the delivered TxCommit (ADR-0007's 2026-08-12 amendment) — the
  invariant either way is directional: a persisted position never
  covers un-applied data, and the reachable divergence
  (data-ahead-of-position) replays idempotently on resume. The retry
  adds no new correctness requirement.

## Observability

Every retry logs at INFO:

```
level=INFO msg="applier: transient error; retrying"
  stream_id=… engine=… attempt=3 max_attempts=8
  backoff=400ms err="<the wrapped driver error>"
```

Budget exhaustion logs/returns a terminal error at the stream's exit:

```
pipeline: apply retry budget exhausted after 8 consecutive
failures at position "<token>": <last transient>
```

Same transient eight times means the dependency is genuinely down
(e.g. vtgate is not coming back); different transients across the
eight means intermittent infrastructure.

## Configuration

| Flag | Default | Range | Notes |
|---|---|---|---|
| `--apply-retry-attempts N` | `8` | `1`–`64` | `1` = no retry; exit on the first transient (the pre-v0.42.0 behaviour). |
| `--apply-retry-backoff-base DUR` | `100ms` | `10ms`–`10s` | Starting backoff before exponential doubling. |
| `--apply-retry-backoff-cap DUR` | `30s` | `1s`–`300s` | Per-attempt upper bound. |

Out-of-range values are **rejected at startup** with a precise error
(not silently clamped) so the worst-case envelope an operator computes
from the docs is always the one the policy actually uses.

Operators on bare-metal MySQL with an unbounded transaction lifetime,
or anyone who wants the strict fail-fast behaviour, can opt out with
`--apply-retry-attempts=1`. Operators expecting a slow Patroni
failover under throttler load should widen the envelope — and at the
default of 8 they need to, because 12.7 seconds does not cover a
failover. `--apply-retry-attempts=20` gives 5m51s of deliberate backoff
(measured, not derived), because attempts 10 onward do reach the 30s
cap and each contributes a full 30 seconds.

## Tables the target lacks: skip-and-count, never halt

When the stream carries changes for a table the **target** doesn't have — a drifted publication scope, a table the operator dropped on the target, a keyspace-wide binlog stream whose target was migrated with `--include-table` — every engine's applier **skips those events** instead of halting the stream. The choice is deliberate, because the blast radius is inverted: for a skipped INSERT, UPDATE or DELETE the source still holds every row, so the table is recoverable with `sluice schema add-table` (a fresh table snapshot) — a skipped TRUNCATE is the one event for which that is not true, see below — while a halted stream lags *every* table and — if the halt outlives binlog/slot retention — loses the resume position itself, converting one table's drift into a whole-database re-snapshot.

A skip is never log-only:

- The applier **WARNs once per table** (not once per event) with the remedy.
- **Every skipped event is counted durably** in the per-target `sluice_cdc_skipped_tables` control table: one row per (stream, table) with the cumulative count and the first/last skipped source position tokens, surviving restarts.
- `sluice sync status` renders the ledger (`SKIPPED TABLES` block; `skipped_tables` in `--format json`), the `sync stop` summary and the stream's exit log repeat it, and **`sluice sync health` exits 1 while any skip count is nonzero** — there is no threshold flag, because skipped tables only resolve through operator action.

sluice's own control tables (`sluice_heartbeat`, `sluice_cdc_state`, the trigger change-log tables, and the rest of the list the schema readers exclude) never reach this path. Since v0.156.9 no stream carries their changes, whatever `--include-table` says. Through v0.156.8 a MySQL source's `--source-heartbeat-interval` rows did, and `sync health` exited 1 on a `sluice_heartbeat` skip. The same holds for a heartbeat table renamed with `--source-heartbeat-table-name`: since v0.156.9 a `sync` that writes heartbeats under that name keeps it out of both the cold copy and the stream. Through v0.156.8 the cold copy created and copied it on the target as an ordinary table (the heartbeat creates it before the copy reads the source schema; measured on MySQL), and a MySQL source whose heartbeat was turned on after the cold start skipped its rows into the ledger like `sluice_heartbeat`'s. A ledger row left by such a release stays until it is deleted on the target: `DELETE FROM sluice_cdc_skipped_tables WHERE stream_id = '<stream>' AND table_name LIKE '%sluice_heartbeat'`.

The remedy is always one of two explicit choices: re-attach the table with `sluice schema add-table` (fresh table snapshot — for skipped INSERT/UPDATE/DELETE events nothing was lost; the source still holds every row), or make the exclusion explicit with a table filter so the stream no longer carries the table at all. One cause needs a different first step: a table whose **privileges were revoked** from the apply role reads as absent too (`information_schema` hides tables the role cannot see), and there `add-table` is the wrong remedy — restore the grant and the next change for that table applies, no re-snapshot needed.

Whichever remedy applies, it stops new skips; it does not remove the ledger row. Nothing in sluice deletes ledger rows (not `schema add-table`, a filter change, a restored grant, or a stream reset), so `sync health` keeps exiting 1 until the row is deleted on the target once the cause is fixed: `DELETE FROM sluice_cdc_skipped_tables WHERE stream_id = '<stream>' AND table_name = '<table as the ledger shows it>'`.

One *event* inverts the "nothing was lost" reading: a skipped **TRUNCATE**. The source has already dropped the rows, so if the target holds the table under another spelling, the target is now **AHEAD** of the source — the shape the 2026-09-15 fix (v0.153.2) closed on `lower_case_table_names=1` MySQL sources, where `TRUNCATE TABLE T1` was emitted under the statement's spelling while every row event for the same table carried the stored `t1`, so the truncate was skipped as "target lacks this table" and the target kept every row the source dropped, behind a WARN that said the source still held them. The once-per-table WARN carries the first skipped op, and for a TRUNCATE it names the TRUNCATE-specific remedy instead: truncate the target table deliberately, or re-attach it with `sluice schema add-table`, or make the exclusion explicit. The ledger and the `sync status` / `sync health` surfaces do not know the op, so their shared remedy text scopes its "source still holds every row" claim to row changes.

The skip resolves when the applier looks the table up (metadata resolution). A table that vanishes *mid-stream after rows were already applied to it* is a different condition and still fails loudly at execution time — destroying replicated state out from under a running stream deserves a halt, and on the batched apply paths a failed statement aborts the whole batch transaction anyway.

## Foreign keys during CDC apply

A CDC change stream is **not foreign-key-dependency-ordered**, so the
applier deliberately bypasses target FK enforcement for the duration of
each apply transaction. This is the standard logical-replication
technique (it is what Postgres's own logical replication does):
constraint integrity is the **source's** responsibility — it has already
validated every change — so the target faithfully mirrors the source,
including any FK-inconsistency the source itself permits.

The two engines differ in what else the bypass suppresses. On Postgres,
`session_replication_role = replica` also disables **user triggers**
during replay, so replicated rows do not double-fire target triggers
(again matching Postgres logical replication). On MySQL,
`foreign_key_checks = 0` disables **FK constraints and FK cascades
only** — target user triggers still fire on replayed rows.

Why this is necessary: a source that does not enforce FKs (SQLite with
the default `PRAGMA foreign_keys=OFF`, MySQL MyISAM, or any application
that deletes a parent row that still has children) emits orphaning
changes, and sluice's concurrent key-hash apply lanes
(`--apply-concurrency`) can commit a child INSERT before its parent in a
different lane. Enforcing the target FK against such a stream would
reject a routine source operation and halt replication. The applier
therefore:

- **Postgres** — sets `SET session_replication_role = replica` on each
  apply transaction.
- **MySQL** — sets `foreign_key_checks = 0` on each apply session.

The bypass is scoped to sluice's own apply work; the constraints remain
on the target schema and are enforced for every other client. (A bulk
migrate, separately, defers and re-validates constraints after the copy
— this section is specifically about continuous CDC apply.)

### Managed-Postgres privilege caveat

`SET session_replication_role` requires elevated privilege — superuser,
`rds_superuser`, or a role explicitly granted it. On a managed Postgres
where the apply role lacks it, sluice cannot bypass FK/trigger
enforcement; rather than failing cryptically it emits a **one-time
WARN** at the first apply and continues. The sync still works for
FK-consistent streams, but an FK-violating or out-of-order change will
then fail the apply loudly. To get the full bypass on such a target,
grant the apply role the privilege to set `session_replication_role`,
or make the target FK constraints `DEFERRABLE`. MySQL's
`foreign_key_checks` needs no special privilege.

### Deferrable keys (`KEY-SCOPED-WRITE-MATCHED-MULTIPLE-ROWS`, `DEFERRED-KEY-CHECK-OFF-IN-REPLICA-MODE`, `DEFERRED-KEY-CHECK-FAILED-AT-COMMIT`)

Every `UPDATE` and `DELETE` the applier issues names its row by the change's before-image. When a source sends only the row's key there — a table under `REPLICA IDENTITY FULL` (sluice narrows it to the primary key), or a `postgres-trigger` source set up with `--capture-payload minimal` — and the target's primary key is `DEFERRABLE`, a source transaction that moves key values through each other (`UPDATE t SET id = id + 1`, a swap) can leave two target rows sharing a key value until it commits, and the next change for that key names both. Any `UPDATE` or `DELETE` that matches more than one row is refused with `KEY-SCOPED-WRITE-MATCHED-MULTIPLE-ROWS` (`SLUICE-E-CDC-KEY-MATCHED-MULTIPLE-ROWS`) and its target transaction rolled back, instead of changing rows the source never touched (where the source transaction was split across target transactions, its earlier statements are already committed, and the message says so when the apply path knows it); before this guard, `UPDATE s SET id = 2 WHERE id = 1; DELETE FROM s WHERE u = 'b'` on the source deleted both rows with key 2 on the target, at exit 0. The same refusal catches a before-image narrowed to columns the target does not hold unique, and a key-narrowed before-image against a target table without a key; a write to a table without a key whose before-image is the whole row is addressed to exactly one of its identical copies. A key change in an order that makes keys collide cannot be applied from a key-only stream; recover with `sluice sync start --reset-target-data` and keep such transactions off a replicated table. A source under `REPLICA IDENTITY USING INDEX` names rows by that index, which stays unique, so its key shifts apply. See [error-codes.md](error-codes.md#error-codes) for the full remedy.

Postgres implements the deferred check of a `DEFERRABLE` primary key, unique constraint or exclusion constraint as an internal trigger, so `session_replication_role = replica` switches it off too. sluice keeps replica mode — leaving it for such a table would fire the target's own triggers on replicated rows — so during apply such a constraint holds only what the source sends. The applied rows still match the source; what can go wrong is a target constraint **stricter** than the source's (one the source does not have), which can end up holding rows it forbids. The first time a run touches such a table it logs `DEFERRED-KEY-CHECK-OFF-IN-REPLICA-MODE` once, naming the table and constraint. `REINDEX TABLE <table>` fails if a violating row has landed. The remedy is to give the target the source's constraint: drop one the source does not have, or make it `NOT DEFERRABLE` so a violating row is refused at its statement.

With an apply role that may not set replica mode, the deferred check runs at the end of each target transaction. A source transaction that is valid only as a whole — a swap of two unique values — then applies when it lands in one target transaction and is refused when it is split across two, with `DEFERRED-KEY-CHECK-FAILED-AT-COMMIT` naming the constraint; nothing in that target transaction is written. A split happens on the per-change path (`--apply-batch-size 1`), when a key change is applied alone as a lane barrier, and wherever the batch loop flushes mid-transaction — its row cap, its byte cap, its 100 ms idle timer, a keyless-table change — so no batch size guarantees one target transaction.

## MariaDB sources

MariaDB is a first-class MySQL-family flavor (`--source-driver mariadb`,
since v0.99.268), not "MySQL with a different banner": `sluice sync start`
reads its binlog the same way it does vanilla MySQL's, through the same
snapshot→CDC handoff and the same retry policy above. Four
flavor-specific behaviors are worth knowing as an operator:

- **`binlog_row_metadata` defaults to `NO_LOG`.** Under `NO_LOG` the
  binlog records neither column names nor integer signedness. Through
  v0.157.2 that made every `UNSIGNED` integer above its type's signed
  maximum arrive negative on every lane that reads a MariaDB binlog
  (`sync start`'s CDC phase, `backup incremental`, `backup stream`, and
  `sync from-backup` applying those chains), at exit 0
  (MARIADB-NOLOG-UNSIGNED, CRITICAL, affected v0.99.271–v0.157.2). An
  UPDATE or DELETE keyed by such a value matched no target row and was
  lost. Since v0.158.0 the decoder takes signedness from the table's
  proven definition. To check a Postgres target fed by an affected
  release, run `SELECT count(*) FROM t WHERE col < 0` for each column the
  source declares `UNSIGNED`; a lost update or delete leaves no trace on
  the target alone, and `sluice verify` cannot clear it. Re-snapshot such
  a target (`sync start --restart-from-scratch`) and rebuild such a chain
  from a new `backup full`. Without column names, most schema changes
  made while a reader is behind the head now refuse; set
  `binlog_row_metadata = FULL` (`SET GLOBAL` plus `[mariadbd]` in the
  option file) to decode across them — see
  [decoding rows behind the head](#mysql-family-binlog-sources-decoding-rows-behind-the-head-deferred-schema-change-sluice-e-cdc-binlog-lookahead-short).

- **Domain GTIDs.** MariaDB replicates with domain GTIDs
  (`domain-server-sequence`, e.g. `0-1-38`), not MySQL's UUID-set GTIDs.
  sluice's CDC position, warm resume, and cold-start anchor
  (`@@gtid_binlog_pos`) all speak the MariaDB shape natively
  ([ADR-0170](../adr/adr-0170-mariadb-flavor-phase3-cdc.md)); a restart
  resumes exactly-once from the persisted domain-GTID position, and a
  source that has purged the binlog past that position refuses loudly
  (errno 1236) instead of silently restreaming from the wrong point.
  Since v0.138.0 a MariaDB position also carries a lineage anchor — the
  binlog `(file, offset)` it was captured at and `BINLOG_GTID_POS` of
  that byte — so a resume against a rebuilt or foreign instance whose
  GTIDs happen to collide refuses instead of replaying that instance's
  whole history; see the resume-signals section below for the
  `UNVERIFIED-INSTANCE-IDENTITY` warning an anchorless (pre-v0.138.0)
  position logs.
- **Native `uuid` / `inet6` / `inet4` columns** decode faithfully off the
  binlog
  ([ADR-0171](../adr/adr-0171-mariadb-native-uuid-inet-cdc-decode.md)).
  The wire format is subtle — MariaDB strips trailing `0x00` bytes from
  these fixed-width values, and its `inet6` text rendering differs from
  most languages' — so the decode was ground-truthed byte-exact against
  live 11.4 and 10.11 and pinned per type × shape. CDC values converge
  byte-for-byte with what a bulk copy of the same rows produces, on both
  same-engine and cross-engine (e.g. MariaDB → Postgres `uuid`/`inet`)
  targets.
- **Version-dependent collation catalog.** MariaDB's
  `information_schema.COLLATIONS.PAD_ATTRIBUTE` column is absent through
  the 11.x LTS line and 12.0 (added in 12.1), so sluice keys trailing-
  space `=` semantics off the version-independent `_nopad_` collation
  name token and the server's own behavior — relevant when a filtered
  `--where` predicate compares string columns. Details in the
  [field note](https://sluicesync.com/field-notes/mariadb-no-pad-attribute-column/)
  and in
  [migrating-legacy-mysql.md](migrating-legacy-mysql.md#mariadb-sources-and-targets).

## Trigger-based CDC sources: `sqlite-trigger` and `d1-trigger`

Most CDC sources read a native change stream — Postgres logical
replication, MySQL binlog, Vitess VStream. SQLite and Cloudflare D1 have
no such stream: SQLite's WAL is a *physical* page-log, not a logical
record of row changes. So sluice captures their changes with **triggers**,
the same technique the `postgres-trigger` engine uses for managed Postgres
that blocks logical replication ([ADR-0066](../adr/adr-0066-postgres-trigger-engine-variant.md)).

`sluice trigger setup --source-driver sqlite-trigger` (a local file) or
`--source-driver d1-trigger` (a live D1 over the HTTP query API) installs:

- **Per-table AFTER INSERT / UPDATE / DELETE triggers** that write the
  before/after row image into a `sluice_change_log` table. The image is
  encoded as the same `(typeof, text/hex)` pairs the lossless `d1` reader
  uses (NOT `json_object()`, which would round integers above 2⁵³ to
  float64 and can't represent BLOBs) — so capture is value-exact
  ([ADR-0135](../adr/adr-0135-sqlite-trigger-cdc.md) /
  [ADR-0136](../adr/adr-0136-d1-trigger-cdc.md)).
- A **monotonic-`id` watermark** on `sluice_change_log`: the polling
  reader emits changes in `id` order and persists the last applied `id`,
  so a restart resumes **exactly-once** from the durable position.
- A **`MAX(id)` snapshot anchor** captured at snapshot start, so the
  cold-start → CDC handoff is gap-free (every change after the anchor is
  streamed; everything at or before it is already in the snapshot).
- A **captured-column fingerprint** (`sluice_change_log_columns`) that
  **refuses loudly on schema drift** rather than silently dropping a
  column added after setup (SQLite has no DDL triggers, so an added
  column is otherwise invisible to the capture path).

**Known limitation — `OR REPLACE` across a UNIQUE conflict.** With SQLite's
default `PRAGMA recursive_triggers` OFF (a per-connection setting of *your
application's* writing connections), the row an `INSERT OR REPLACE` /
`UPDATE OR REPLACE` implicitly deletes to satisfy a **non-PK UNIQUE**
conflict fires no DELETE trigger, so that delete is never captured and the
target keeps the row — a silent divergence. `trigger setup` WARNs on every
table with a non-PK UNIQUE constraint. Mitigate by running writers with
`PRAGMA recursive_triggers = ON`, or by writing upserts as
`INSERT ... ON CONFLICT DO UPDATE` (which never implicitly deletes); on D1
prefer the latter. Details in
[ADR-0135](../adr/adr-0135-sqlite-trigger-cdc.md).

**`CHANGE-LOG-PAGE-UNORDERED` (refusal, at every poll).** The reader
refuses a page of `sluice_change_log` whose rows do not arrive in
strictly ascending `id` order, naming the two ids it saw out of
sequence. This is a bug in the poll query or the transport, never in
your data, and there is nothing to repair on your side — report it. The
reason it refuses rather than carrying on is that the resume watermark
is the page's MAXIMUM id: an out-of-order page advances that watermark
past rows the poll never returned, and a keyset resume then starts above
them, so those rows are captured, undelivered, and unreachable. That is
not hypothetical. It is what Bug 266 was, on the `d1-trigger` lane,
where an output alias made SQLite sort the page lexicographically; the
query is fixed and pinned, but the pin grades the QUERY, while this
check grades what the pump was actually handed. A future transport or a
server-side ordering change becomes a loud stop instead of missing rows.

**Recovering from an invalid-UTF-8 / lone-surrogate halt (the local
`sqlite-trigger` lane).** The reader refuses loudly (batch withheld
atomically, watermark unmoved — nothing is skipped or duplicated) when a
captured TEXT value carries bytes JSON cannot represent faithfully, e.g.
`CAST(x'FFFE61' AS TEXT)`. On this lane **repairing the source row alone
does not unblock the stream**: the refusal's `id=N` names a row of
`sluice_change_log` whose captured image already holds the poison, and
the repairing `UPDATE` captures a *new* change whose before-image
carries it again, so a restart halts again. The runnable recovery —
which the refusal message also prints — is `sluice trigger teardown`,
repair the source row, `sluice trigger setup`, then a fresh sync.
(Advanced alternative: scrub the affected `before`/`after` images in
`sluice_change_log` directly; SQLite's JSON functions cannot locate
invalid UTF-8, so the scrub is byte-level, e.g. matching on
`hex(before)`.) For the local file's non-capturing consumers of the same
guard — catalog scalars, the snapshot phase — repairing the source value
is sufficient as written. (Bug 245.)

**The `d1-trigger` lane never halts on invalid UTF-8 — the value
arrives pre-mangled. The bulk `d1` read DOES halt since v0.140.0, by a
different route (see below).** Measured on real D1 (2026-08-13): the
`/query` API replaces invalid bytes with U+FFFD *server-side*, for
direct reads and change-log images alike, so the invalid-UTF-8 arm of
this guard cannot fire on live-D1 sources — there is no halt to recover
from, and the substituted value is indistinguishable from a genuine
U+FFFD. See the caveat in
[the D1 import guide](sqlite-d1-import.md) for what is and is not
recoverable. (The lone-surrogate arm on D1 is unmeasured; this
paragraph scopes only the invalid-UTF-8 vector.)

`d1-trigger` polls D1's **primary** (strongly-consistent) query path, not
a read replica, so commit order equals `id` order. Because every change
appends a `sluice_change_log` row that is never auto-reaped, run
`sluice trigger prune` periodically to bound source growth — it deletes
only rows strictly below the target's durable applied watermark (see
[trigger-changelog-retention.md](trigger-changelog-retention.md)). The
full operator walkthrough, including teardown, is in
[sqlite-d1-import.md](sqlite-d1-import.md).

## `postgres-trigger` sources: replica-role writes are not captured by default

The `postgres-trigger` engine's capture triggers are plain `CREATE TRIGGER` by default, so Postgres fires them for **origin** writes only: any DML executed under `session_replication_role = 'replica'` bypasses them entirely. Two real configurations write under replica role, and on both the sync **exits 0 with rows silently missing from the target**:

- **The source is itself a logical-replication subscriber.** A native `CREATE SUBSCRIPTION` apply worker runs under replica role, so every row a subscription applies to a subscribed table is invisible to the capture triggers. Only rows written directly on the source database are captured. This pairing is natural on exactly the managed tiers the trigger engine targets (slot-blocked databases that *receive* logical replication but cannot *serve* it), which is why it deserves this callout.
- **The all-sluice relay (A→B→C).** sluice's own Postgres change applier sets `SET LOCAL session_replication_role = replica` on every apply transaction when the apply role is privileged (see [Foreign keys during CDC apply](#foreign-keys-during-cdc-apply)). So if database B is the target of an A→B sluice sync and simultaneously the `postgres-trigger` source of a B→C sync, the B→C capture sees **nothing** the A→B sync applies. The failure is shaped to pass testing: an unprivileged dev applier's rows *are* captured (the privilege probe fails and the bypass is skipped), while the privileged production applier's are not.

`sluice trigger setup` and every stream open probe for both shapes — `pg_subscription` rows for the subscriber shape, sluice's own `sluice_cdc_state` apply bookkeeping for the relay shape — and emit a loud `SILENT-CAPTURE-GAP RISK` WARN naming the loss scenario. It is a WARN rather than a refusal because both shapes can be intentional and safe (a subscription feeding tables outside the replication set; a decommissioned relay's leftover control table). If the WARN fires on your topology: for the subscriber shape, opt in to replicated-write capture (below); otherwise sync from the origin database directly, keep subscribed tables out of the replication set, or stop the upstream sync before trusting the capture.

### Capturing replicated writes: `trigger setup --capture-replicated-writes` (ADR-0185)

For the subscriber shape there is a supported opt-in: re-run `sluice trigger setup --capture-replicated-writes` and the per-table capture triggers (row **and** truncate) are set `ENABLE ALWAYS`, so writes applied under `session_replication_role = 'replica'` **are** captured. This is the topology it exists for: a locked-down primary you cannot install anything on → a native `CREATE SUBSCRIPTION` subscriber → sluice trigger-capture → elsewhere. Replicated INSERT/UPDATE/DELETE **and replicated TRUNCATE** are captured — ground-truthed through a real publication→subscription pair on PG 16, including the subscriber's separate TRUNCATE apply path — and with the opt-in active the subscriber-shape WARN no longer fires (it is the supported case). Re-running `trigger setup` without the flag reverts to plain origin-only triggers, provided the run names every captured table (see below). Four things to know:

- **The relay shape refuses under the opt-in** (`SLUICE-E-CDC-TRIGGER-ECHO-LOOP`, at setup and at every stream open): if the source also carries sluice's own apply bookkeeping (`sluice_cdc_state`, looked for in **every schema of the database** — an upstream sync run with `--target-schema` keeps its control table in the target DSN's schema while its rows land elsewhere, so the bookkeeping and the capture schema routinely differ; the message names where it was found), another sluice sync applies into this database, and `ENABLE ALWAYS` triggers would re-capture its applied rows as new changes — an echo loop. Capture from the origin database instead, or decommission the upstream sync (and drop its control table), or stay on the default posture. A subscription whose `copy_data = true` initial sync runs after setup is captured too — the initial copy arrives as ordinary insert rows.
- **Adding a table to an opt-in install: keep the flag on.** The posture is recorded once per install and enforced per trigger, so `sluice trigger setup --tables=<the new table>` **without** the flag would leave the tables it does not name at `ENABLE ALWAYS` while recording origin-only. Since v0.137 that run **refuses** and prints both runnable commands (re-run with `--capture-replicated-writes` to keep the opt-in, or re-run with `--tables=<every captured table>` to convert the whole install back to origin-only); an opt-in run naming a subset instead **widens** the tables it did not name, so the install can never end up half-converted. Before v0.137 the half-converted state was reachable and wedged the next stream open with a message blaming a hand-flip; if you have one, the refusal at open now prints the full `--tables=` list that repairs it.
- **The flag sets one posture for the whole install, including DDL capture.** Since v0.135 the opt-in also sets both DDL event triggers `ENABLE ALWAYS`. PostgreSQL filters event triggers by their enablement exactly as it filters row triggers, so through v0.134.x the opt-in captured replica-role *DML* while replica-role *DDL* stayed invisible — an ETL session running `SET session_replication_role='replica'; ALTER TABLE t DROP COLUMN c; INSERT INTO t …` had the INSERT captured in its post-DDL shape and the ALTER not, and the applier wrote that row into an unchanged target with no refusal. **If you have an existing `--capture-replicated-writes` install, its next stream open will refuse** naming `sluice_capture_ddl_trg`: re-run `sluice trigger setup --capture-replicated-writes` (seconds; the change log, watermark and consumer registry are preserved). Default-posture installs are unaffected.
- **The enablement posture is recorded and verified.** Setup records the opt-in in `sluice_change_log_meta`, and every stream open checks the installed triggers — the per-table pair *and* both event triggers — against it: an opt-in install whose trigger was hand-flipped back to plain refuses (its replicated writes, or replica-role DDL, would be silently missed), and a default install whose trigger was hand-flipped to `ENABLE ALWAYS` refuses too (replica-role capture without the echo-loop vetting). Re-running `sluice trigger setup` with the matching flag repairs either — **name every captured table in `--tables`**, which is what the refusal message prints for you: the posture is recorded once for the whole install, so a re-run that names fewer tables cannot converge it.

Separately, every `postgres-trigger` stream open now verifies the installed capture artifacts themselves (the same capture-shape door the `sqlite-trigger`/`d1-trigger` engines got in v0.131.2): a manually dropped or `DISABLE TRIGGER`-d capture trigger, a trigger set `ENABLE REPLICA`, a trigger rewired to a foreign function, or a dropped/disabled `sluice_capture_ddl_trg` / `sluice_capture_drop_trg` event trigger **refuses loudly at open** — re-running `sluice trigger setup` reinstalls everything and preserves the change-log and resume watermark. Without the door, a dropped trigger is invisible to both drift tiers (the DDL event triggers only watch table DDL and drops of captured tables; the `--allow-polled-fingerprint` tier watches nothing — its fingerprint loop is not yet implemented, and every stream open on that tier logs a `DDL-DETECTION-ABSENT` warning) and every subsequent change on that table would be silently uncaptured.

### Which DDL halts the stream (scoped to captured tables since v0.140.0)

A Postgres event trigger is DATABASE-wide — it cannot be attached to a schema — so through v0.139.0 the DDL tier recorded a marker for any `ALTER TABLE`, `CREATE TABLE` or `CREATE INDEX` anywhere in the database, and the stream halted on it. A colleague creating an unrelated table in a schema sluice never touches stopped your sync, with a restart-from-scratch remedy.

Since v0.140.0 the tier records only commands whose RELATION carries this install’s capture trigger. In practice:

- **Still halts** (these change a captured table’s shape): `ALTER TABLE` on a captured table, including `ADD COLUMN`, `ALTER COLUMN TYPE`, `DROP COLUMN`, `ADD CONSTRAINT` and `RENAME COLUMN`; and `CREATE INDEX` on one.
- **No longer halts**: anything on a table this install does not capture — another schema entirely, an uncaptured neighbour in the same schema, or a brand-new table. A table with no capture trigger emits no change rows, so it cannot make the applier write a wrong one; `sluice schema add-table` is how it joins the stream.

Upgrading changes the capture function bodies, so an install created by an earlier release warns `STALE-CAPTURE-FUNCTION` until `sluice trigger setup` is re-run once. **v0.154.0 is such an upgrade**: the `sql_drop` marker now carries `captured_relid`, and `CREATE TABLE … PARTITION OF` / `… INHERITS` under a captured parent now record a marker of their own — so every install made before it warns until setup is re-run.

**One reason to re-run setup carries NO warning, and it is worth knowing about explicitly.** v0.145.0 takes sluice-created capture functions off PostgreSQL's default `PUBLIC` EXECUTE grant, because they are `SECURITY DEFINER`: without that revoke, any source role able to create a table and a trigger could attach the capture function to a table of its own, named after a synced table, and have every row it wrote applied to the target's real table. An install created BEFORE v0.145.0 keeps that grant until `sluice trigger setup` re-runs — and unlike the signalled reasons above, nothing reports it at stream open, because the capture-shape door grades the function's body, config and security flag and never reads its ACL. The reader-side scope check covers the window by dropping any captured row whose schema is not this stream's (a `CAPTURE-OUT-OF-SCOPE` warning, once per relation), so an unrevoked install is not exposed to the write primitive — but re-running setup is what actually closes it. Check with:

```sql
SELECT proname, proacl FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
 WHERE n.nspname = current_schema() AND proname LIKE 'sluice_capture%';
```

A `NULL` `proacl` is PostgreSQL's default, which means PUBLIC still holds EXECUTE.

**`CAPTURE-OUT-OF-SCOPE`** is the warning that fires when a change-log row names a relation in a schema this stream does not read. Two causes: a capture trigger left on a table outside the sync (a stale install, or the attack above), or a misconfiguration. The row is never applied and the stream continues; the log line carries the `REVOKE` remedy. A row for a captured table that the sync's own `--include-table` / `--exclude-table` leaves out is not warned about: it is skipped with one DEBUG line per table, the same as every other engine's table filter. Through v0.156.8 such a row was reported as `CAPTURE-RELATION-MOVED` (below), wrongly.

**`CHANGE-LOG-WATERMARK-STALLED`** halts a `postgres-trigger` stream when a poll read change-log rows with no gap but the stream's watermark did not move past them. Nothing could change on the next poll, so the stream would otherwise re-read the same rows forever without applying anything. That has no legitimate cause and means a sluice bug; the persisted position is unchanged and no row was skipped. It exists because v0.145.0–v0.156.8 had exactly that stall: a skipped row for a table the sync excludes did not move the watermark, so 10,000 of them in a row (one poll window) stopped the stream silently. Upgrading and restarting the stream resumes it from the persisted position.

**`CAPTURE-RELATION-MOVED`** is the same drop with a different cause, and it is the one to take seriously: the row's relation is a table **this stream captured**, and its rows now arrive under another schema — the shape of `ALTER TABLE … SET SCHEMA` on a synced table. The move itself writes a DDL marker that halts the stream before any post-move row is read, so this warning means that halt did not fire: the install's capture functions predate `captured_relid` (`STALE-CAPTURE-FUNCTION` will have said so at every open), or the halt was cleared without re-running setup. Every change to that table is being dropped and the target has been frozen for it since the move. Drain the stream, decide whether the table belongs in the sync under its new schema, re-run `sluice trigger setup` so the capture functions record `captured_relid`, then `sluice sync start --source-driver=... --source=... --target-driver=... --target=... --restart-from-scratch`. The reader tells the two warnings apart with one catalog read per relation — the relation's OID is either in the set it captured at stream open or it is not — and falls back to `CAPTURE-OUT-OF-SCOPE` with both causes listed if that read fails. (On an install that still grants the capture function to `PUBLIC`, a decoy that already existed when the stream opened is in that set too and is reported as moved; the `CAPTURE-FUNCTION-PUBLIC-EXECUTE` warning at open is what tells you that reading is possible.)

Since v0.153.x a `postgres-trigger` stream also **refuses to open** when the captured-relation OID set cannot be read from the source catalog, rather than warning and continuing without it: without that set the `SET SCHEMA` marker is discarded and the moved table's changes are dropped silently, so the read is load-bearing. The refusal names the catalog error; re-run `sluice sync start` once the source is readable.

### The first-touch schema boundary, and `TRIGGER-SOURCE-LIVE-DDL-COORDINATION`

Since the fix for KEY-COLLATION-TRIGGER-CDC-NO-HISTORY, a `postgres-trigger` stream reads each table's shape from the source catalog at the table's first change of every session and hands it to the target ahead of that change. That is what lets a MySQL target refuse (`KEY-COLLATION-MERGE`) a row the source keeps apart from another only by case, instead of overwriting it. The shape is also recorded in the target's schema history and in a backup's manifest, as a native Postgres stream's is. On the event-trigger tier the table's columns and keys are read once per schema per session (at the session's first change of any captured table in that schema) and each table's collations at its own first change. That tier records a marker, and halts the stream, for `ALTER TABLE`, `CREATE TABLE`, `CREATE INDEX` and a dropped table — so an added column, key or collation is never judged from an older read — but not for `DROP INDEX`, `ALTER TYPE … ADD VALUE` / `RENAME VALUE` or `ALTER DOMAIN`, which leave the session's read stale. A stale read cannot disarm the key-collation guard, which takes the keys it guards from the target's own catalog and only the column collations from the source, and a label added to an enum on the source reaches the target exactly as it did before this boundary existed. A `DROP INDEX` on the source is not safe, though, on this or any CDC source: the target keeps the key, so rows the source now allows under it — even byte-identical ones — meet on the target, where an upsert through that key can overwrite an existing row at exit 0. That hole is filed separately; until it is closed, drop the index on the target too, with the stream drained, before the source writes rows the old key forbade. On the `--allow-polled-fingerprint` tier, where no DDL leaves a marker, each table is read at its own first change instead; a change made after that is not seen until the next session.

Because the shape is read as the catalog stands, a schema change made while the stream was stopped can show in it before the stream reaches the change's own DDL marker. A trigger-CDC source therefore runs the same boundary check as `--schema-changes=refuse`, whatever that flag says: a table the target cannot hold stops the stream with `SCHEMA-CHANGE-REFUSED`, and the message carries this engine's recovery, the same as the observed-DDL refusal's: drain the stream, then re-run `sluice sync start --restart-from-scratch`. An operator restart drops and recreates the stream's tables on the target from the source's current schema and re-copies them, so it lands the change; `sluice migrate` cannot, since it refuses a populated target and never alters one. Under `--inject-shard-column` the consolidated table is shared and the restart does not drop it: apply the same change to it (the target table the source table lands in: under a table or schema rename that is the mapped name) and delete this shard's rows from it first, or rows the source deleted while the stream was stopped stay on the target. Under `--schema-already-applied` the restart drops and recreates nothing either: apply the change on the target and empty the stream's tables before restarting. With the DDL event triggers installed (the default tier), applying the change on the target and restarting at the same position is not enough: the reader reaches the change's DDL marker and refuses again. Under `--inject-shard-column` a `postgres-trigger` source must run with `--no-coordinate-live-ddl`: live cross-shard coordination would forward that shape to the consolidated target, so it refuses at start with `TRIGGER-SOURCE-LIVE-DDL-COORDINATION`. `sqlite-trigger` and `d1-trigger` emit no such shape and are not refused.

Downgrading after a stream has recorded such shapes: a release before this one refuses to warm-resume a `postgres-trigger` stream whose target holds `postgres-trigger` rows in `sluice_cdc_schema_history`, because it cannot order them. Delete those rows (`DELETE FROM sluice_cdc_schema_history WHERE source_engine = 'postgres-trigger'`) before starting the older binary, or restart from scratch.

### Dropping a synced table (and the `DROP-CAPTURE-ABSENT` warning)

Through v0.134.x, `DROP TABLE` on a synced source table was **invisible to capture**. The event trigger's tag list named `DROP TABLE`, but PostgreSQL reports dropped objects only through `pg_event_trigger_dropped_objects()` (a `sql_drop` event trigger) — never through the `pg_event_trigger_ddl_commands()` the DDL capture function reads — so the function found nothing to record. The stream kept running at exit 0 and the target kept the dropped table's last-synced rows forever.

From v0.136.0, `sluice trigger setup` installs a second event trigger (`sluice_capture_drop_trg`) on `sql_drop`. Dropping a table this install captures — directly, or via `DROP SCHEMA … CASCADE` / `DROP OWNED BY` — now refuses the stream at the next poll, naming the relation and telling you what to do about it. Two deliberate non-events: `DROP INDEX` on a synced table records nothing (sluice never forwards index DDL, so an index drop cannot change any row the applier writes), and a `DROP TABLE` elsewhere in the database records nothing at all — the capture is scoped to tables carrying this install's own `sluice_capture` trigger.

Note that the remedy is **not** `sluice migrate`: that reads the *source* schema, so it cannot land a drop. Drain the stream, decide the target's fate for that table (drop it to match the source, or keep it as a deliberate archive), re-run `sluice trigger setup` with the tables that still exist, remove the dropped table from the sync's `--tables`, then `sluice sync start --restart-from-scratch`.

**Existing installs need one re-run.** Upgrading the binary does not add an event trigger to a database. Every stream open on an install that predates the arm logs a `DROP-CAPTURE-ABSENT` warning naming the missing trigger; `sluice trigger setup --dsn=... --tables=...` installs it and preserves the change log, the resume watermark and the consumer registry. (This is the same re-run the security note below asks for, so one setup pass covers both.)

### Security: re-run `trigger setup` after upgrading past v0.134.0

Releases v0.85.0 through v0.134.0 installed the DDL capture function (`sluice_capture_ddl`) as `SECURITY DEFINER` **without** a pinned `search_path`. `CREATE EVENT TRIGGER` requires superuser, so that function is owned by one, and an unpinned definer resolves the built-ins it calls against the search_path of whichever session fires it — which is any user's DDL session. An unprivileged user who can create a function in a schema their search_path reaches (the default `PUBLIC` grant on `public` before PG 15, or any schema they own) could shadow one of those built-ins and have it execute with superuser privileges by running a single `CREATE TABLE`. This was reproduced end to end on PG 16.

The renderer is fixed, but **upgrading the sluice binary does not repair a database that already has the function installed** — only re-running setup does, because `CREATE OR REPLACE FUNCTION` is what rewrites the function's settings:

```
sluice trigger setup --dsn=<source-dsn> --tables=<same tables as before>
```

Add `--capture-replicated-writes` if that is your recorded posture. The re-run preserves the change log, its resume watermark and the consumer registry, so a running sync resumes where it left off; do it at your next convenient window. Until then every `postgres-trigger` stream open logs an `INSECURE-CAPTURE-FUNCTION` warning naming the affected function and this remedy. It is a warning rather than a refusal deliberately: the same check runs on every warm resume, so refusing would turn a binary upgrade into an outage on every running sync. Sources on the `--allow-polled-fingerprint` tier never had the DDL capture function installed and are not affected.

**`PARTITIONED-PARENT-CAPTURE` (warn, at `trigger setup`).** One of the tables you named is a declaratively **partitioned parent**. PostgreSQL clones the row trigger onto every partition, and a cloned trigger records the *partition's* name (`events_us`), not the parent's — because it fires on the partition and `TG_TABLE_NAME` is the relation it fired on. `sync start` and `migrate` refuse a partitioned source table at preflight, so this install is not usable for the parent as it stands, and that refusal names the recovery in full. The route that works is to exclude the parent (`--exclude-table`) and let the partitions copy as ordinary tables — and the clone names are exactly right for that, since the partitions are then what is in scope. Setup warns rather than refusing because preparing that route is legitimate; it is telling you at setup time what you would otherwise discover at `sync start`.

**`CAPTURE-FUNCTION-PUBLIC-EXECUTE` (warn, at every stream open) is
cleared by the same re-run.** It fires when the source's
`sluice_capture*` functions are still EXECUTable by `PUBLIC`, and names
which ones. Those functions are `SECURITY DEFINER`, so while PUBLIC can
call them, any source role that can create a table and a trigger could
attach one to a table of its own named after a synced table and have its
rows applied to your target. Re-running `sluice trigger setup` revokes
EXECUTE from PUBLIC and grants it back to the setup role. **A mitigation
is already in place, which is why this is a warning and not a
refusal:** the reader drops every captured row whose schema is not the
one this stream is synchronising, logging `CAPTURE-OUT-OF-SCOPE`, so
rows written that way are never applied. Treat the warning as
defence-in-depth worth closing at your next window, not as an active
breach. If the advisory's own catalog query fails, sluice logs at DEBUG
and says nothing further, so absence of this warning is not by itself
proof the grant was revoked; `\df+ sluice_capture*` in psql is.

**The same re-run is also what clears a `STALE-CAPTURE-FUNCTION` warning — and v0.154.0 is a release that will raise it on every existing install**, because it changes the capture bodies again: the `sql_drop` marker gained `captured_relid` (which is what lets the reader tell a moved captured table from an out-of-scope one, above), and `CREATE TABLE … PARTITION OF` / `… INHERITS` beneath a captured parent now record a DDL marker instead of passing silently. Until `sluice trigger setup` is re-run, an install keeps capturing through its old bodies and those two signals are simply absent. From v0.137 every stream open compares the capture functions the source actually has — their body, their `SET` pins and their `SECURITY DEFINER` flag, read from `pg_proc` — against the definitions this binary renders. An install made by an older sluice keeps capturing through its OLD function body until setup re-runs, and that is not cosmetic: before the `bytea_output` pin every captured bytea is corrupted on the way to a MySQL or SQLite target, and before the `extra_float_digits` pin every captured float is silently rounded when the writing application's session setting is lower. The warning names the functions and this remedy; it is a warning, not a refusal, for the same reason as the one above. Two shapes DO refuse, because no sluice version could have produced them: a capture function whose body no longer writes into the change log at all (it would capture nothing while every trigger still looks correct), and — on installs created from v0.137 onward, which record what setup installed — a definition that was changed after setup installed it. If you edit a `--dry-run` plan's function bodies by hand, expect that second refusal; re-running setup restores the shipped definition.

The same re-run also repairs a second defect found in the same audit, and it is worth knowing what it was. Releases v0.133.1 through v0.134.1 suppressed DDL capture for sluice's own `trigger setup` statements by setting a session variable, `sluice.setup_in_progress`, that the capture function checked. PostgreSQL puts **no privilege** on setting a variable with a dotted name, so any session on the source could set it and run schema changes that were never recorded — and because the trigger engine's `op='X'` markers are its only DDL-detection tier, nothing downstream noticed. From this release the suppression additionally requires evidence a session cannot fabricate (a one-shot record written into `sluice_change_log_meta`, a table setup grants to nobody, keyed to the running backend), so setting the variable by hand no longer suppresses anything.

**If you apply the `--dry-run` plan by hand, apply it whole, in one psql session.** It now begins with `BEGIN` and ends with `COMMIT`, and it uses `SET LOCAL`, so PostgreSQL reverts the suppression marker at both commit and rollback — which is the point: previously the marker was cleared by a `RESET` at the very end, and an operator whose paste stopped on an error (say, under `\set ON_ERROR_STOP on`) kept the suppression for the rest of that session, silently swallowing the `op='X'` marker for their own next `ALTER TABLE`. Stopping partway is now safe: roll back (or just disconnect) and the marker goes with it. Applying only part of the plan still leaves the engine partly installed, so re-run `sluice trigger setup` to converge either way.

## Stopping a PlanetScale or Vitess cold start during its copy means a re-copy (`VSTREAM-COPY-RESUME-WITHDRAWN`)

**A `planetscale` or `vitess` cold start stopped or killed while it is still copying cannot be resumed; re-run it with `--restart-from-scratch`.** Before v0.163.3 sluice saved the copy's position as it ran and continued from it on the next start, but a continued copy could not make the target match the source: Vitess copies the already-finished tables again rather than replaying their changes, and that second copy only adds and overwrites rows, so any row the source deleted while the stream was stopped stayed on the target, as did every old row of a table dropped and re-created under its name. Since v0.163.3 no position is saved until the copy finishes. A first cold start stopped during its copy leaves no position, so its re-run finds the copied rows and refuses (`SLUICE-E-COLDSTART-TARGET-NOT-EMPTY`); a re-copy of an existing stream stopped the same way refuses `COLD-START-INCOMPLETE`; and a mid-copy position saved by an earlier release is refused under `VSTREAM-COPY-RESUME-WITHDRAWN` when it carries a copy cursor, and under `VSTREAM-COPY-COMPLETION-UNPROVEN` (below) when it does not. Do not use `--force-cold-start` here: it copies by upsert over the rows already there and keeps the deleted ones. `--restart-from-scratch` clears the in-scope target tables and copies them again; with `--schema-already-applied` it cannot clear them (they are yours), so it refuses while they hold rows (`RESTART-FROM-SCRATCH-TARGET-NOT-CLEARED`): empty them, then re-run. A stream that has reached CDC resumes from its saved position as it always has.

**A position saved by v0.163.1 or earlier may carry no copy cursor at all, and then only the target can say whether the copy finished (`VSTREAM-COPY-COMPLETION-UNPROVEN`).** Those releases often froze the copy's position at its first save, a few thousand rows in, as a plain list of per-shard GTIDs: exactly what a finished copy leaves. v0.163.2 and v0.163.3 warm-resumed from it, logged `INCLUDE-TABLE-SCOPE-UNRECORDED`, and never copied the rest (Bug 327: 40,000 to 49,000 of 300,000 rows missing at exit 0 in the v0.163.3 regression cycle). So a `planetscale` or `vitess` warm resume now requires evidence on the target that the stream's copy finished, and refuses without it:

- The stream's `established_tables` record, which a cold start writes with its CDC anchor after the copy (since v0.163.0), is proof on its own.
- A `sync-<stream-id>` row in `sluice_migrate_state` at phase `complete` (written since v0.149.0) is not, because it can say `complete` about a target that does not hold the copy. It goes `complete` as soon as the bulk copy returns, before the VStream FLOAT re-read, the foreign-key check and the CDC anchor, so a stop there on v0.163.1 or earlier left it beside a mid-copy position. And `--restart-from-scratch` drops the target tables before it replaces that row (and never replaces it when the run could not record its progress), so an interrupted re-copy could leave an old `complete` row beside an emptied target. The row counts only when every in-scope table it records as having copied rows still holds rows on the target, and the stream's `sluice_cdc_state` row was written after it. A copied table that is now empty on the target is checked against the source with a one-row read: empty there too means the table was drained since (a queue, a replicated `TRUNCATE`), which is fine; holding rows there means the target lost the copy. The two timestamps are compared only on a Postgres target whose session time zone is at UTC all year (releases before v0.156.5 wrote the position's time in the session's local time, so `Europe/London`, for instance, does not qualify). On a MySQL-family target they are never compared, because `sluice_cdc_state.updated_at` there also moves on stop requests and live-add writes, so a `complete` row alone never proves the copy on MySQL and `--assert-copy-finished` (below) is the way through. A pass on the row records the stream's tables, so the next start passes on that record and the row is judged once.

A stream stopped during its copy has no such evidence. Neither does a stream whose last cold start finished on v0.148.x or earlier, or a later one whose progress recording was disabled or whose evidence does not hold up as above, so those are refused once too. The refusal is a codeless exit 1 carrying `INCLUDE-TABLE-SCOPE-DRIFT`, which the fleet supervisor does not restart. It has applied no change and changed no table in the stream's scope (reading the progress record may create the empty `sluice_migrate_state` control table on a target that never had one). A record, table or timestamp that cannot be read (the target unreachable, say) refuses as well rather than passing. A `sluice_migrate_state` this role cannot create or bring up to date (a role with DML only, or a PlanetScale branch with safe migrations) refuses naming the remedy for the statement that failed: on Postgres, the statements `sluice control-tables ddl --engine postgres` prints, applied by the table's owner; on a MySQL-family target, the failing statement itself (an `ALTER` for an out-of-date table, shipped with `sluice deploy-ddl` on a PlanetScale branch with safe migrations), because `sluice control-tables ddl` prints only `CREATE TABLE IF NOT EXISTS` there, which cannot fix a table that exists. The safe remedy is `--restart-from-scratch` (see its two exceptions above, and `--inject-shard-column`, which refuses until this shard's rows are deleted by hand). If you have compared the target's row count with the source's, table by table, and they match, re-run the same `sluice sync start` command once with `--assert-copy-finished`; that the stream has been streaming changes is no evidence, since every stream this refusal protects has. That resume logs `COPY-FINISHED-ASSERTED` and records every in-scope table that exists on the target and holds rows as copied, so later resumes pass without the flag; an absent or empty table is not recorded and is named, and the next start judges it as never copied. The flag is refused where the target shows the copy did not finish: a progress row short of `complete`, a `complete` one whose copied table is now empty while the source table holds rows, or a position written before it. On a `sluice sync run` leg, take the leg out of the fleet and run `sluice sync start` with the flag once; the fleet spec has no key for it. If the copy had in fact stopped midway in a way none of that shows, the rows it never reached stay missing, which is why it is a flag and not a default. A stream handed off from a backup chain with `--position-from-manifest` is not judged on that run, since its position is the chain's and its copy is the restore's. On a PlanetScale or Vitess source, once that handoff's change stream has opened, it records the chain's position as the stream's anchor and, as copied, the tables in the stream's current scope that the backup chain holds (its terminal manifest's table list) and that exist on the target, the same record a cold start writes, so its later restarts without the flag pass on that record. A stream that already has a record keeps it. A table in scope that the chain does not hold, or that the target does not have (a restore filtered with `restore --include-table`), is not recorded: it was never copied, so the next start judges it as never copied (`INCLUDE-TABLE-SCOPE-DRIFT`) and the handoff WARNs naming it; bring it in with `sluice schema add-table` or take it out of scope. If the chain's table list cannot be read, the write fails, or the target writes the anchor without the record (a control table this role cannot ALTER, `COLD-START-ANCHOR-UNRECORDED`), the handoff refuses with `MANIFEST-HANDOFF-UNRECORDED` and has applied no change: fix what the error names (for the last, add the record's columns to `sluice_cdc_state` with a role that can: on Postgres apply what `sluice control-tables ddl --engine postgres` prints; on a MySQL-family target the `ALTER` the `COLD-START-ANCHOR-UNRECORDED` warning names) and re-run the same command. A restored table that is empty on the target is recorded (an empty table in a backup is legitimate), unlike under `--assert-copy-finished`, which records only tables that hold rows. On every other source the handoff records nothing, as before.

## Stopping a cold start after the copy keeps the slot (`STOPPED-SLOT-KEPT`)

If you stop a `sync start` (Ctrl-C, SIGTERM) after the bulk copy has committed but before CDC begins — during the index build, say, which on a large table is where a stop most often lands — sluice **keeps** the source's replication slot instead of dropping it, and WARNs under `STOPPED-SLOT-KEPT`.

**Re-run `sluice sync start` with the same `--stream-id`. That is the whole remedy on a PostgreSQL source whose copy had finished** — and it is worth saying plainly, because two earlier releases said something else. v0.148.0 told you to re-run and the re-run did not work; v0.148.1 corrected this page to say the state could not be resumed at all, which was true of that release. From v0.149.0 the resume exists, and the re-run picks the copy up: it **skips the bulk copy**, finishes the remaining phases (indexes, constraints, views), takes the CDC anchor from the slot's own consistent point, and starts streaming. Every source change committed while you were stopped is still on the slot, so nothing between the snapshot and now is lost. The run announces it under `COLD-START-RESUMED`, naming what it skipped and what it finished; that line is how you tell a resume from a fresh copy.

**What the resume requires, in full, because it refuses rather than guessing.** The re-run either proves every one of these or does what it did before this release:

- **No CDC anchor yet.** A stream that reached CDC has a `sluice_cdc_state` row and warm-resumes as it always has; this path is only ever the window before that row exists, so an ordinary resume is never touched by it. `--reset-target-data` and `--restart-from-scratch` are handled earlier still and never reach the gate: an operator who asked for a fresh copy gets one.
- **A single namespace.** The proofs below are keyed by bare table name, so a schema spanning two namespaces — where `app.users` and `public.users` are different tables — stands the resume down rather than letting one inherit the other's evidence. A multi-schema sync takes a different lane, which records no anchor and never reaches here.
- **A PostgreSQL source.** A replication slot is what makes the anchor provable; every other source has no equivalent and still refuses. The engines that can resume are exactly those below, derived from the code rather than maintained here by hand:

  <!-- coldstart-resume-engines: postgres -->

- **A copy that finished.** Every in-scope table must be recorded complete — sluice reads the per-table progress it wrote, not merely which phase the run reached, so a stop *during* the copy re-runs exactly as before.
- **The same row-shaping flags.** `--where`, the table scope, `--type-override`, `--redact`, `--inject-shard-column` and `--target-schema` are fingerprinted when the copy starts, and a re-run whose flags differ is refused (`COLD-START-SHAPE-CHANGED`, below). `--skip-foreign-keys` and the view filter are fingerprinted too but only *warn*, because they change DDL the resume re-runs rather than rows it inherits.
- **The same tables.** Each table's engine id (`pg_class.oid`) is recorded when the copy starts, and the re-run compares it table by table. A table dropped and re-created under the same name (or swapped with another) while you were stopped has a new id, and the re-run refuses naming it (`COLD-START-SHAPE-CHANGED` with `TABLE-IDENTITY-CHANGED`): drop the stopped run's slot with `sluice slot drop`, then re-run with `--restart-from-scratch`. `VACUUM FULL`, `CLUSTER`, `TRUNCATE` and rewriting `ALTER`s keep the id, so they do not refuse (a source `TRUNCATE` made while stopped reaches the target through the slot, after the anchor). The same ids are checked again at the CDC anchor, after the remaining phases, and on every cold start's anchor: a table re-created between its copy and the anchor refuses the same way, and `schema add-table` refuses to record an add whose table was re-created during it. If either re-read fails (the source could not be queried), the anchor or the add refuses with `TABLE-IDENTITY-UNREAD` rather than taking the failure as a pass, and writes nothing. Once the source answers, re-copy as for `TABLE-IDENTITY-CHANGED` (for an add, empty the target table and run the add again). A copy recorded by v0.163.0 or earlier carries no ids, so its re-run does not resume and refuses on the existing slot instead, as before v0.149.0. From v0.149.0 through v0.163.0 a resume over a re-created table treated it as copied, silently.
- **The rows still on the target.** sluice asks the target itself whether the tables the copy filled still hold anything (`COLD-START-TARGET-EMPTIED`, below).
- **A slot that has not moved.** It must be unattached and sitting at exactly the recorded `confirmed_flush_lsn`, bound to the database this run connects to.

If any of those cannot be proven, the re-run behaves as it did before the resume existed: a loud refusal, or a refusal specific to what could not be proven. It never skips the copy on partial evidence.

**If your row-shaping flags changed, sluice refuses and names them (`COLD-START-SHAPE-CHANGED`).** The resume SKIPS the copy, so run 1's rows become run 2's data — and CDC only carries changes from the snapshot onward, so nothing backfills the difference. Widen or drop a `--where` and the excluded rows would be permanently absent; change `--redact` and half the target is redacted by provenance; change `--target-schema` and the rows are in the other namespace. Re-run with the flags the recorded copy used, or use `--reset-target-data` to copy again under the new ones. (This is the same drift check a warm resume gets from its `sluice_cdc_state` row — that row does not exist yet in this window, so the fingerprint rides the migrate-state row the cold start already writes.)

**Two settings change DDL rather than rows, and those only warn — under the same marker.** `--skip-foreign-keys` and the view filter shape the constraints and views phases, which the resume re-runs under your new settings, so the run proceeds. What the warning tells you is the part the re-run cannot fix: anything the stopped run had *already* created stays. Adding `--skip-foreign-keys` on the re-run does not remove foreign keys the stopped run created before you interrupted it, and dropping it does not remove the backing indexes that run synthesised for the keys it skipped. No copied row is affected either way. Refusing here would mean a full re-copy to correct a constraint, which is the wrong trade — but it is a real difference, so it is said out loud rather than left for you to find.

**If the target was emptied, sluice refuses (`COLD-START-TARGET-EMPTIED`).** A `TRUNCATE` on the target leaves every control row and every index intact, so nothing in sluice's own bookkeeping notices — which is why the resume asks the target directly: each table the copy recorded rows for must still hold at least one. `DROP` already failed loudly; this makes the less destructive operation fail loudly too. Note what this floor does *not* catch: a partial delete, where one surviving row is enough to pass.

**If something else consumed the slot, sluice refuses and shows you both positions (`COLD-START-ANCHOR-MOVED`).** A slot that has advanced past the recorded anchor has already discarded the changes in between, so resuming from it would silently skip them. sluice changes nothing, prints the recorded anchor and the slot's current `confirmed_flush_lsn`, and leaves the decision to you: find what moved the slot (another consumer, a manual `pg_logical_slot_get_changes`) and re-run once it is quiescent, or drop the slot and re-copy with `--reset-target-data`. The same refusal covers a slot that is currently **active** — an attached consumer may be advancing it as sluice looks, so "equal right now" would prove nothing — and a slot of the right name bound to a *different database*, which a logical slot's position says nothing about.

**A replaced source is caught too, from this release onward.** The snapshot's recorded position now carries the source's `system_identifier` and timeline from the moment the slot is created, so a resume whose `--source` has been repointed at a physical clone, a restored backup or a promoted standby is refused by the existing source-identity check rather than streaming from it. Since v0.154.0 that refusal is **terminal** — it is the `FOREIGN-LINEAGE-REFUSED` class below, so nothing on the target is touched and no automatic re-copy follows; if the replacement is what you meant, re-copy deliberately with `--restart-from-scratch` or `--reset-target-data`. Positions recorded by earlier releases carry no such pin — and they carry no copy-shape fingerprint either, so the resume declines them for that reason first.

**The kept slot pins WAL on the source, and that is not free.** PostgreSQL retains WAL from the slot's position until the slot advances or goes away, so an unattended slot on a busy source can fill the disk — resume promptly, or clear it:

- **To resume** — re-run `sluice sync start` with the same `--stream-id`, as above. The stream picks up from the slot and releases the retained WAL as it catches up. (A stop that landed *during* the anchor write, rather than before it, completes that write and warm-resumes instead; that path has worked since v0.116 and needs nothing from you either.)
- **If the re-run refuses** — because the source is not PostgreSQL, the copy had not finished, or the anchor moved — drop the slot, then re-run `sluice sync start` with `--reset-target-data` to copy again. sluice has first-class commands for the drop; you do not need psql:

  ```
  sluice slot list --source-driver postgres --source "$SLUICE_SOURCE"
  sluice slot drop --source-driver postgres --source "$SLUICE_SOURCE" sluice_slot --yes
  ```

  `slot list` shows each slot with what it is retaining, which is the number to watch on a busy source. `slot drop` requires `--yes` — it refuses loudly rather than prompting — and takes `--if-exists` if you are scripting it. Add `--force` only if a consumer is still attached.

  **The name `slot drop` takes is the LITERAL slot, not the `--slot-name` you passed to `sync start`.** Those differ: `--slot-name` is a *suffix* and sluice prepends `sluice_`, so `--slot-name prod` creates `sluice_prod`. Use the name exactly as the `NAME` column of `slot list` prints it — which is also the name the `STOPPED-SLOT-KEPT` warning gives you, already resolved. (If you do name the suffix by mistake, `slot drop` tells you what you probably meant rather than dropping something else.)

A cold start that fails for a real reason — a refused preflight, a foreign-key violation, an unreachable source — still drops its slot, because there the slot is debris rather than a resume point.

## A source that is not the one your position came from is refused, never re-copied (`FOREIGN-LINEAGE-REFUSED`)

A persisted position can stop being usable for two reasons that look the same from the outside. The **same** source may have moved past it — binlogs purged, `RESET MASTER`, a slot dropped — and there sluice's automatic recovery (ADR-0022/0093) is right: drop the in-scope target tables, re-copy, carry on. Or a **different** source may now be answering the DSN: an instance replaced or restored from the wrong backup, a load-balanced or DNS-failed-over endpoint, a keyspace that is simply another database. There the same recovery destroys a correct target and repopulates it from the wrong database, at exit 0, looking like success. The 2026-09-09 audit measured exactly that on the MySQL GTID path: four correct target rows replaced by the replacement instance's single row.

Since v0.148.2 every MySQL-family lane — binlog GTID, binlog file/pos (`@@server_uuid`), MariaDB (lineage anchor and domain), and VStream (a foreign keyspace) — treats a **different lineage** as terminal, and **since v0.154.0 Postgres does too**: its `(systemid, timeline)` pin ([ADR-0051](../adr/adr-0051-pg-cdc-source-identity-pinning.md)) used to route a diverged source into the automatic re-copy, which is how an *empty* target pointed at a PITR'd or promoted instance cold-started from it at exit 0 and streamed the wrong timeline forever. The refusal is `SLUICE-E-CDC-LINEAGE-MISMATCH` from the MySQL-family engines and, from the pipeline on every engine, a line marked `FOREIGN-LINEAGE-REFUSED` that says nothing on the target was touched.

**Which paths the door covers is engine-specific, and worth reading before you rely on it.** On the MySQL family it fires on both: a warm resume refuses before streaming, and the reactive path — a position that went invalid mid-stream — asks the source the same question before it drops anything. On **Postgres** the door is the resume open only: the pin is compared against the source's live `IDENTIFY_SYSTEM` every time the stream starts, which is what refuses a repointed `--source`, but the Postgres reader answers no mid-stream lineage question, so the reactive path has nothing to ask there. What is *not* foreign, and still recovers automatically: a purged position; a VStream errant GTID, whose remedy is on the source and which keeps its existing route; and, on MySQL, an **empty** `@@gtid_executed` — *provided the server's `@@server_uuid` is one the position names*, which is what makes it the same instance after a `RESET MASTER`. An empty or behind set on a server the position has never seen is the rebuilt-node shape — a restore followed by `RESET MASTER`, or one seeded through `gtid_purged` from an older backup — and is refused (the 2026-09-15 audit measured the automatic re-copy reducing a target to the rebuild's stale rows on that shape). The refusal names the uuid; if the server is a lagging replica behind a failover endpoint, waiting for it to catch up makes the position contained and the resume proceeds with the target intact. A set **behind** the position under the server's **own** uuid is refused too, with its own diagnosis (operator decision, 2026-09-15): the instance no longer holds transactions it issued — a primary rolled back past the position, or an in-place restore that seeded `gtid_purged` from an older backup — so the target is *ahead* of it, and the automatic re-copy would reduce the only copy still holding those rows. Nothing on the target is touched; point the sync at the instance that holds the position, or, if the rolled-back source is now the truth, re-copy from it deliberately with `--restart-from-scratch`. The uuid is a check of *identity*, not of safety, and one residual is stated plainly: an **in-place restore on the same server that seeds no `gtid_purged`** — `RESET MASTER`, then `mysql < dump.sql` on the same box with `auto.cnf` untouched — presents an empty set under the position's own uuid, which is indistinguishable from a routine `RESET MASTER` on a server whose data is intact, and STILL takes the automatic re-copy, reducing a target that was ahead of the restored source to the dump's rows. Refusing that shape would refuse every same-server reset, and the same decision chose not to. If you restore a source in place, stop the stream before the restore and decide afterwards, deliberately, whether the restored source or the target is the truth — the automatic path will not ask. **MariaDB has no instance identity**, so an empty `@@gtid_binlog_state` cannot say whether the server was reset in place or rebuilt; since the same 2026-09-15 decision it is refused, and the message names both — a server reset with its data intact takes `--restart-from-scratch`, a rebuilt or replaced one means pointing the sync at the instance that holds the position. One MariaDB gap stays open and is stated rather than implied closed: a byte-identical rebuilt node (the same image, `--server-id` and statements — what a containerised rebuild produces) reproduces the lineage anchor, has a non-empty binlog state, and passes both lineage checks (ADR-0170's residuals).

What to do when you see it: first confirm the DSN points at the database you mean — the three shapes above are indistinguishable from the position alone. If the replacement **is** intended, re-copy deliberately: `sluice sync start … --restart-from-scratch` (keeps the cdc-state row) or `--reset-target-data` (clears it too). Nothing happens until you say so.

## PostgreSQL sources: a slot acknowledged past the target's position is refused (`SLOT-ACKED-PAST-TARGET-POSITION`)

When a `sync` resumes, it starts from the position the target recorded in `sluice_cdc_state`. PostgreSQL decodes from the **later** of that position and the replication slot's `confirmed_flush_lsn`, so if the slot has been acknowledged past the target's position, every change committed in between is skipped and never reaches the target. Since v0.156.7 a warm resume compares the two first — on single-schema and multi-schema resumes, and on the resume that finishes a stopped cold start — and refuses with `SLOT-ACKED-PAST-TARGET-POSITION`, naming the slot, both LSNs and the remedy. The run exits non-zero and is not retried.

How a slot gets there:

- **A stop on v0.156.6 or earlier of a Postgres → MySQL-family sync** (MySQL, MariaDB, PlanetScale, Vitess). Those releases acknowledged the slot at the position the reader had *streamed*, ahead of the target's writes, so a Ctrl-C, crash, or apply error that ended the run while changes sat in an apply batch left the slot past them. A graceful `sync stop` that drained its batch did not. Postgres → Postgres was exposed the same way before v0.99.130.
- **A target restored from a backup, or failed over to a replica**, holding an older `sluice_cdc_state` row than the slot has been acknowledged to.
- **A slot dropped and recreated** after the stream wrote its position — for example a `--restart-from-scratch` (whose "slot already exists" refusal says to drop the slot) that was interrupted before its copy finished, leaving the old row next to a slot created at "now".

A stream written by this release never trips it: the slot is only ever released to the position the target has persisted, and that position never moves backward.

What to do: re-copy with `sluice sync start … --restart-from-scratch` (or re-copy the affected tables). If you have verified the target already holds every change up to the slot's position — for instance every change in the gap was to a table outside this stream's filter — start once with `--accept-slot-acked-past-position=<confirmed_flush_lsn>`, using the LSN the refusal prints. It is bound to that LSN, so a slot that has moved since refuses again, and it is a command-line flag only (not a `syncs.yaml` key), so it cannot pre-accept a later refusal. One legitimate upgrade shape can also trip the check: a Postgres → Postgres stream last written by an older release whose final persisted position was a mid-transaction schema-change anchor; its resume was lossless, and the acknowledgement is the right answer there.

**The same door on the other resume paths.** `sync start --position-from-manifest` resumes from the end position of the backup chain the target was restored from, and its refusal names that chain; the remedy is to restore from a fresh full backup and hand off from its chain, or to re-copy, and the acknowledgement above applies. `backup stream` and `backup incremental` resume from the end position of the chain's last committed manifest. Their chain preflight refuses a slot that is already past it before the stream opens, and the door is the backstop for a slot that moves after that check, and the only guard when `backup stream` reopens its pump after a transient error. There the refusal names the chain's end position and says no link of the chain holds the gap; the remedy is a new chain from a full backup (`backup full --chain-slot` anchors a slot at the backup's own position). There is no acknowledgement for a chain, by design: the chain preflight that refuses the same shape has none, and a chain that skipped the gap would restore without it on every restore that crossed it.

**Check after upgrading.** A stream that already resumed on v0.156.6 or earlier after such a stop was fast-forwarded past its gap at that resume, and this check cannot see it any more (the target has since persisted positions past the slot). For each Postgres → MySQL-family stream that was stopped by Ctrl-C, a crash, or an apply error on one of those releases, compare `pg_replication_slots.confirmed_flush_lsn` with the LSN in the target's `sluice_cdc_state.source_position` *before* its first resume on this release; if the slot is past it, re-copy. For a stream that has already resumed, compare row counts (or `sluice verify`) against the source.

## PostgreSQL sources: the slot follows the server's WAL while your tables are idle (`KEEPALIVE-BOUNDARY-PASSED-COMMIT`)

The slot is released only to a position the target has persisted, and through v0.156.7 a position was persisted only at a decoded commit on one of the stream's tables. Postgres 15 and later skip a transaction that touches no published table — including the `--source-heartbeat-interval` heartbeat's — so while your tables were idle the slot stayed at the last commit to them and the server retained every byte of WAL written since, however busy the rest of the server was (GC-41 (j)). Postgres 14 and earlier advanced only when something wrote in the stream's own database.

Since the fix, whenever none of the stream's source transactions is in flight, the reader takes the walsender's keepalive position as a transaction boundary: it emits an empty one there (at most one per 10 seconds) that every apply path persists like a commit, and the slot is released to it once the target holds it — the rule PostgreSQL's own subscriber follows. The slot then trails the server's WAL by tens of seconds while `sync` is connected (measured 10–21 s on PG 14 and PG 16, every apply path, Postgres and MySQL targets), with or without the heartbeat. A server that then goes fully quiet still keeps the WAL written since its last activity, because `restart_lsn` advances only when decoding reaches a running-transactions record; it adds nothing more. A `backup stream` / `backup incremental` chain on the same reader releases its slot at each committed window's end position, which these boundaries advance the same way. The acknowledgement rule itself is unchanged, so `SLOT-ACKED-PAST-TARGET-POSITION` above still holds. The heartbeat is no longer needed on Postgres to keep the slot moving.

Safety rests on one walsender behaviour, cited from the PostgreSQL source rather than measured: a keepalive never reports a position past the commit of a transaction the walsender sends afterwards. A logical walsender writes a transaction's output into its send buffer when it decodes the commit record, and advances its read position (`sentPtr`, what the keepalive reports) only after that record is processed (`XLogSendLogical` → `LogicalDecodingProcessRecord`); keepalives go through the same FIFO send buffer, so they cannot overtake output queued before them. PostgreSQL's own subscriber relies on the same ordering when it confirms a keepalive's position.

The reader also carries a tripwire for it, and the tripwire's reach is narrow. If a delivered transaction is seen to commit below a boundary already emitted, the reader logs `KEEPALIVE-BOUNDARY-PASSED-COMMIT` at ERROR, applies the transaction anyway (stopping there could skip it on resume), and stops emitting boundaries for the rest of that connection. It only observes an **uninterrupted** connection. In the window where a violation would actually lose data — the boundary persisted and the slot acknowledged to it, then a stop, crash or reconnect before the late commit arrives — the resumed stream starts past that commit and never delivers it, so the tripwire never fires. It is evidence that the premise broke, not protection from it. If you see it, verify the target against the source for changes committed near the two LSNs the line names, and report it.

## MySQL and MariaDB binlog sources: an idle stream persists its position at every binlog rotation

The target persists a position only at a source transaction's commit, and three kinds of binlog traffic carry none: a rotation, a heartbeat, and a standalone GTID group (a DDL, `CREATE USER` / `GRANT`, `OPTIMIZE TABLE` — implicit commits with no XID). Through v0.156.8, a connected stream that saw only those kept its persisted position in a binlog file the source then rotated past, though it had read every event and missed nothing (GC-43 (r)). Once binlog retention purged that file, the next `sync start` failed the resume check ("persisted position is no longer valid … purged", or MariaDB's error 1236), and the ADR-0093 auto-resnapshot dropped the target's tables and copied them again. In file/pos mode a fully idle source was enough; in GTID mode it took standalone groups as the last GTIDs before the purge. On MariaDB the lineage anchor also never moved past its purged file, so the restart could only proceed under `UNVERIFIED-INSTANCE-IDENTITY`. The drop-and-re-copy dates from v0.99.71; releases before that failed the same restart loudly. A source that kept committing transactions on any database was not affected, because an out-of-scope transaction still persists a position.

Since the fix, the binlog reader emits an empty transaction at each rotation it reads from the binlog, whenever no source transaction is open, and the consumer persists it like a commit: the next file's start in file/pos mode, the executed GTID set in GTID mode, and on MariaDB the re-anchored lineage. A file can only be purged after the server rotates past it, so a connected stream persists a position past it first, and a restart after the purge resumes. It is the same shape as the Postgres keepalive boundary above. The boundary is in the binlog reader itself, so every stream that reads a binlog source gets it, `sync` (including each database of a multi-database stream) and `backup stream` among them. VStream sources (`--source-driver planetscale` / `vitess`) use a different reader and are not covered.

Two shapes are unchanged, and both are named in the code:

- **A source server restart.** The server ends its file with a stop event, not a rotation, so no position is persisted at that crossing. What the dump thread sends there is UNVERIFIED. An idle stream whose source restarts, then purges the pre-restart file before the next rotation, still resumes from the purged file.
- **An `XA PREPARE` as the last group of a file**, on an otherwise idle GTID-mode MySQL source. sluice folds that group into the executed set only at the next group, so the rotation that follows it is skipped rather than persisted early.

For those two, `--source-heartbeat-interval` still helps on a MySQL-family source: each heartbeat commits a row on the source, which persists the position like any transaction. Outside them, a connected stream no longer needs the heartbeat to survive binlog retention. `--no-auto-resnapshot` turns any remaining drop into a loud refusal instead.

## A full backup that recorded no end position cannot root a chain (`POSITIONLESS-FULL-ROOT`)

Every `backup incremental` and `backup stream` resumes the source's change stream from the position its parent recorded. A full backup normally records one at the end of its row sweep — a Postgres LSN, a MySQL GTID set or file/position, a VStream vgtid — and that position is the only thing that makes the chain contiguous: the incremental covers everything from *there* forward, and the full covered everything up to it.

Three kinds of full carry **no** position: one taken FROM a PlanetScale Neki router (a Neki has no cluster-wide WAL position to give — the backup succeeds since v0.153.1 and says so at WARN), one taken from a MySQL server whose binary log was off, and one older than v0.17.2. Before v0.153.1 sluice extended such a full anyway, after a WARN, by starting the chain from the source's **current** position — which silently left out every change between the full's read and the moment the incremental opened. Since v0.153.1 the extension refuses instead, with a line marked `POSITIONLESS-FULL-ROOT` that names the parent and the remedy, before any replication connection is opened and before anything is written to the store.

What to do when you see it: take a fresh `backup full` on a source that records a position and start a new chain from it. A Neki full is a complete, restorable backup on its own; it just cannot be the root of an incremental chain. If the source is MySQL, confirm `log_bin` is ON before the full — a full taken with it off has nothing for the next link to resume from.

Trigger-CDC sources (`postgres-trigger`, `sqlite-trigger`, `d1-trigger`) were the one stated exemption through v0.153.2: they recorded no position on a full, so their chains started from the change log's **current** id after a WARN, and every write between the full's sweep and that moment was in no link of the chain — the v0.153.1 regression cycle measured it at 100 of 100 rows. Since v0.154.0 (roadmap item 163) a trigger full records the change log's anchor inside its own read — on `postgres-trigger` the same settled anchor `sync start` computes, taken in the backup's `REPEATABLE READ` snapshot; on `sqlite-trigger` and `d1-trigger` the log's `MAX(id)` read before the sweep, so a write that lands during the sweep is at worst replayed idempotently, never skipped (the D1 behaviour is derived from the SQLite proof, not measured live) — and `backup incremental` / `backup stream` resume the poller there. The exemption is gone: a trigger full with no position is one taken before v0.154.0, or one whose snapshot-anchored open refused (the WARN at backup time names the cause), and it is refused as a chain root exactly like the three kinds above. `--chain-slot` is refused on a trigger source — there is no slot, and none is needed.

What holds the change log for a chain on a trigger source: both extenders seat the chain in the source's change-log consumer registry (`sluice_change_log_consumers`, the same table every sync registers in) under `backup-chain:<root backup id>`, at the position they resume from, and move the seat to each committed link's end — so a peer sync's `--auto-prune-change-log`, or an operator `sluice trigger prune`, cuts no lower than the chain's next resume point, and a chain you stop taking incrementals from holds the log until you remove its row (the same posture as a stopped sync; the prune's staleness WARN names the row). **One window is not covered, stated rather than implied:** between the full and its first incremental the chain is not yet registered (the engine cannot name the chain at anchor time), so a peer that applies past the full's anchor and prunes in that window removes rows the first incremental needs, and the incremental exits 0 without them on every trigger engine — `postgres-trigger`'s poller reads the pruned range as aborted transactions and skips it with only an INFO line (`skipping a permanently-absent change-log id range`), and `sqlite-trigger` / `d1-trigger` never see the deleted ids at all. On a source with peer syncs, take the first incremental promptly after the full.

The refusal above lives in the binary doing the *reading*, so on a mixed fleet it protected nothing: a pre-v0.153.1 binary handed the same full still took the from-now branch. Since v0.154.0 the full itself carries it — a positionless full on a non-trigger source is written at manifest **format version 11** (see [backup-format-versioning.md](../backup-format-versioning.md)), which every older binary refuses at its own version ceiling (`format version 11 is newer than this build supports … upgrade sluice`) before it reads the position at all. The cost is stated plainly: such a full needs a v0.154.0+ binary to restore, verify or `export-as-parquet`. Nothing else moves — a full that records a position, every incremental, and every trigger-CDC full keep the version they had, so ordinary chains stay readable by whatever you were running.

## `sync`: a forwarded `ADD COLUMN` is backfilled from the source (`ADD-COLUMN-BACKFILL-INCOMPLETE`)

When `sync` forwards a source `ADD COLUMN`, the target fills every row it already holds with the column's DEFAULT as the forward carried it, and that DEFAULT is read from the source when the boundary reaches sluice. It is not what the source filled its own rows with whenever the DEFAULT was dropped or changed in between — Django's `AddField` emits `ADD COLUMN c … NOT NULL DEFAULT 'v'` and then `ALTER COLUMN c DROP DEFAULT` for every field with a default — or when a non-constant DEFAULT (`now()`, `CURRENT_TIMESTAMP`, `gen_random_uuid()`) was dropped or changed before the `ADD COLUMN` reached sluice, where the target would evaluate its own. (A non-constant DEFAULT the source still declares when the `ADD COLUMN` reaches sluice is refused, not backfilled — ADR-0058 §2a.) So after the ALTER lands, sluice reads the new column's value for every row from the source, paging by primary key, and writes it to the target. The backfill runs ahead of every change that follows the ALTER in the stream, so a row the source updates after the ALTER still ends at its updated value. It is on by default for Postgres, MySQL, MariaDB and PlanetScale/Vitess sources, on single-stream forwarding and on the Shape A fan-in (`--inject-shard-column`), where each shard's stream fills only its own shard's rows, from its own source. A `--where` filter applies to the backfill's read.

**The cost, and the stream waits for all of it.** The backfill is one pass over the table on the source — it reads only the primary key and the added columns, in pages of 5,000 rows — plus one `UPDATE` per row on the target, and every change behind the `ALTER` waits until it finishes. On a Postgres target those `UPDATE`s are pipelined. On a MySQL, MariaDB or PlanetScale target they are not batched: each is its own round trip, so a table of a million rows over a 100 ms link is on the order of a day of round trips (divided by `--apply-concurrency` lanes), during which the stream falls that far behind. Plan a large `AddField` on such a target accordingly, or pass `--no-backfill-added-column` for that migration and repair the column yourself. The source stream is kept alive while it waits: a Postgres reader keeps answering the server and a PlanetScale/Vitess reader no longer mistakes the wait for a hung stream. On a MySQL or MariaDB binlog source, a wait longer than the server's `net_write_timeout` (60 s by default) during a large source transaction makes the server drop the binlog connection. It is re-established automatically. On a GTID-mode source the server then re-sends that whole transaction, and sluice drops the events it had already delivered (a source on binlog file and offset resumes exactly where it stopped, with nothing repeated) — but the re-send costs a second transfer of the transaction, so raise `net_write_timeout` on the source if your backfills run long. It logs `forward-add-column: backfilling the added columns …` when it starts, `forward-add-column: backfill in progress` with the row count every 30 seconds, and `forward-add-column: backfill complete` with `rows_backfilled` at the end.

The table needs a primary key, and the backfill reads it from the source catalog rather than from the change stream: a Postgres change stream's key is the table's REPLICA IDENTITY, which under `REPLICA IDENTITY FULL` (required for a filtered `--where` sync) is every column, and a PlanetScale/Vitess field event does not carry the key's order. Without a primary key the backfill refuses and the run ends as described below. It also refuses when the source has moved on in a way that touches what it reads: if the added column is no longer on the source when the backfill runs (dropped or renamed since — the two cannot be told apart at that point, and a rename would leave the renamed column's existing rows unfilled), or if the primary key's columns have been renamed or dropped since. A later change to any other column does not affect it.

To skip it, pass `--no-backfill-added-column` (fleet `syncs.yaml` key `no-backfill-added-column: true`). The rows the target already held then keep the target's fill, and a WARN (`forward-add-column: backfill suppressed`) names every column so affected. `--backfill-added-column`, the old opt-in, is accepted and does nothing but log that the backfill is now the default.

**An interrupted backfill does not resume, so it stops the stream.** A restarted stream does not see the `ADD COLUMN` again, so the rows the backfill had not reached would keep the target's fill with nothing to report it. Instead, a run that ends before the backfill provably reached the target — a Ctrl-C or stop that interrupts it, a failed source read, an apply error — ends with `ADD-COLUMN-BACKFILL-INCOMPLETE`, naming the table and columns. It is recorded on the stream's control-table row exactly like `UNFORWARDED-SCHEMA-CHANGE` (below), so every restart refuses until you acknowledge it. To recover, copy the added column's values from the source to the target for the rows that predate the `ADD COLUMN`, then start once with `--accept-unforwarded-schema-change=<fingerprint>`, using the fingerprint the refused start prints — or re-copy instead, by passing `--restart-from-scratch` on that same acknowledged start. "Provably" is deliberately strict: sluice needs the target's persisted position to be strictly past both the last change before the backfill and the `ADD COLUMN` itself, which only a change after the backfill can supply, so a stop that lands in the moment between the backfill finishing and that checkpoint refuses too. On a PlanetScale/Vitess source that confirmation arrives with the next change whose position has advanced, so on an idle source a stop before one arrives refuses. A process killed without running its exit path (SIGKILL, an OOM kill, power loss) is covered too: before the `ALTER` reaches the target, sluice writes an `ADD-COLUMN-BACKFILL-INCOMPLETE` record to that same control-table row, and clears it only once the backfill is confirmed on the target (checked every 10 seconds while the stream runs, and again when it stops). A restart after a hard kill during the backfill therefore refuses in the same way. The record says the process ended without settling the backfill. The record is conservative, so it can also appear when nothing was lost:
- after a kill in the seconds between a backfill completing and being confirmed;
- after a kill between the record being written and the `ALTER`;
- after an `ALTER` that failed.

In each case, check the added column against the source before you acknowledge the refusal. If the target cannot store the record (for example, a role without `UPDATE` on `sluice_cdc_state`), the `ADD COLUMN` is refused rather than forwarded without it. Two cases remain uncovered. On the Shape A fan-in, another shard's `ALTER` fills this shard's rows before this shard's stream has seen its own `ADD COLUMN`, so a hard kill in that gap happens before anything is recorded. And a hard kill before sluice reaches the `ADD COLUMN` at all is outside what this record can cover. After a crash that follows a source schema change, compare the added column against the source (`sluice verify` compares real rows).

On a MySQL or MariaDB source, a `DROP DEFAULT` (or `SET DEFAULT`) that the binlog reader sees as a separate change to a column it has already recorded — typically because a write to the table landed between the `ADD COLUMN` and the `DROP DEFAULT` — stops the stream as `UNFORWARDED-SCHEMA-CHANGE` rather than forwarding, as any DEFAULT change on an existing column does.

## Backup chains: the values an `ADD COLUMN` filled (`ADD-COLUMN-FILL-NOT-REPRODUCIBLE`, `ADD-COLUMN-FILL-NOT-CAPTURED`)

When a source runs `ALTER TABLE t ADD COLUMN c … DEFAULT d` between two links of a chain, it fills every row it already holds — and that fill writes no row event, so the change stream carries no value of `c` for those rows. Chain restore and `sync from-backup` replay the recorded `ADD COLUMN`, whose DEFAULT is the one the source's catalog showed at the END of the window, and the target fills the same rows by evaluating it. That matches the source only when the window-end DEFAULT is a constant that was also the DEFAULT at the `ALTER`. It does not match for a DEFAULT dropped or changed later in the same window — `ADD COLUMN c … DEFAULT 'v'` then `ALTER COLUMN c DROP DEFAULT`, which is what Django emits for every `AddField` with a default — nor for one that depends on when or where it is evaluated (`now()`, `CURRENT_TIMESTAMP`, `clock_timestamp()`, `gen_random_uuid()`, `CURRENT_USER`, a sequence).

**Since v0.156.1, the capture records the fill.** When `backup incremental` or a `backup stream` rollover sees that its window added a column, it reads the column's actual values back from the source for every row, keyed by the primary key, and writes them into the same incremental as ordinary row updates that replay after every event of the window. The restored rows then hold exactly the source's values, whatever the DEFAULT was. The cost is one read of the key and the added columns per table, once per window that adds a column; it is logged (`recorded the ADD COLUMN fill`, with the row count and the read's duration). Nothing about the backup format changes: an older sluice restoring such a chain replays the same updates and gets the same rows.

Two edges, stated rather than implied. The values are read when the window closes, not at the window's end position, so a row changed after the window ends carries its newer value one link early; the next link replays that change anyway, so a restore of the whole chain is exact, and only a restore that stops at that very link sees it. And a table with no primary key cannot be addressed row by row: the capture logs `ADD-COLUMN-FILL-NOT-CAPTURED` naming the table and columns, and records the fill as skipped.

`ADD-COLUMN-FILL-NOT-REPRODUCIBLE` is the restore-side WARN for a column whose fill the chain does **not** carry. It fires for two kinds of chain. A chain captured by an older sluice (before the fix) records no fill, so the replay names every column added with a DEFAULT it cannot prove constant — and still cannot see a Django-style dropped DEFAULT, whose rows land NULL with no warning. A chain whose capture had to skip the fill names every added column of that table, whatever its DEFAULT. Either way the restore carries on: the true values are in no link, and refusing would throw away every later link of the chain for one column's pre-existing rows. To repair, copy that column's values for the rows that pre-date the `ALTER` from the source, or take a fresh full backup after the `ALTER` and restore from it.

Toward a MySQL target, sluice v0.156.0 and earlier also dropped a DEFAULT on a `TEXT`, `BLOB` or `JSON` column from the replayed `ADD COLUMN` (with its own WARN), so on a chain without a captured fill those rows landed NULL. A chain with a captured fill restores their values even on those releases — measured with v0.156.0.

## Backups refuse a text value that is not valid UTF-8 (`BACKUP-VALUE-NOT-UTF8`)

Every backup chunk — the rows of `backup full`, and the changes of `backup incremental` and `backup stream`, including before-images and the `ADD COLUMN` fill — is JSON. JSON cannot hold a byte that is not part of valid UTF-8, and Go's encoder writes each such byte as U+FFFD (`�`) without an error. Before this refusal existed that is what a backup did: the chunk sealed, `backup verify` rehashed it and agreed, and a restore landed `�` where the source held a value, at exit 0. Two ways in are known. A **source that holds bytes which are not valid text in a text column** — a SQLite `TEXT` value written from raw bytes (`CAST(x'636166e9' AS TEXT)`), a Postgres database with `SQL_ASCII` encoding, legacy invalid bytes in a MySQL `utf8mb4` column — reaches it on any backup, `backup full` included. And a **reader that did not convert a column from its character set**: MySQL, MariaDB and PlanetScale/Vitess change streams on legacy-charset columns (latin1, cp1250, sjis, …) did this before their decoder fix.

A backup now refuses such a value at capture: the run fails with `BACKUP-VALUE-NOT-UTF8`, naming the table, the column, which image of a change held it, and where inside a list, map or structured value it sits. (A JSON column that reaches the backup as raw bytes is carried as bytes and is not inspected.) `backup stream` stops on it rather than retrying — the refusal is not a transient error — and no manifest is committed for the refused window, so the chain still ends at the last good one. The source value is intact.

To fix it, repair the value at the source, or store it as a binary type (`BLOB` / `bytea`) if it really is binary. To back up everything else in the meantime: `backup full` can leave the table out with `--exclude-table`, or null the column with `--redact <table>.<column>=null`; `backup incremental` and `backup stream` have neither, so the value has to be repaired at the source before the chain can advance past it. **If you restored a chain captured before this refusal from such a source**, compare the affected text columns against the source: any `�` in them is a lost value, and so is any other character a legacy-charset value turned into.

## PostgreSQL sources: slot creation can block on a prepared transaction (`PREPARED-XACT-BLOCKS-SLOT-CREATE`)

`CREATE_REPLICATION_SLOT` builds a consistent point, and that builder waits for every prepared transaction (2PC) on the **cluster** — not just in your database — to be resolved. If one is orphaned because its coordinator died, the slot creation blocks indefinitely with no further output, which reads exactly like a hung connection.

The cross-database half is **measured, not inferred** (PostgreSQL 16, 2026-09-09): with a prepared transaction stranded in database `beta`, `CREATE_REPLICATION_SLOT` in database `alpha` blocked past a 40-second timeout; a `ROLLBACK PREPARED` on that transaction in `beta`, with nothing else changed, let the identical creation finish in **123 ms**. A prepared transaction you cannot see from your own database will stall your slot.

One operational detail from the same measurement, because it surprises people: **an interrupted creation leaves the slot behind.** The slot is registered first and the consistent point is built second, so killing a blocked `CREATE_REPLICATION_SLOT` leaves an inactive slot that is already pinning WAL. Check with `sluice slot list` before retrying, and drop the leftover if you are not going to use it.

Before creating the slot, sluice reads `pg_prepared_xacts` and warns under `PREPARED-XACT-BLOCKS-SLOT-CREATE` if anything is pending, listing each transaction's `gid`, database, owner and age. Resolve an orphan on the source with `COMMIT PREPARED '<gid>'` or `ROLLBACK PREPARED '<gid>'`; a transaction that belongs to a live coordinator will clear on its own and only needs waiting out.

The same marker also carries the probe's own failure — if sluice could not read `pg_prepared_xacts` (permissions, a timeout), it says so rather than implying the cluster is clear. A warning that could not rule the condition out is not the same as one that ruled it in, and the message distinguishes them.

## PostgreSQL and MySQL-family sources: a schema change the stream cannot carry ends it (`UNFORWARDED-SCHEMA-CHANGE`)

Logical replication (pgoutput) describes a table by its column names and types, nothing more. So these source-side changes cannot reach the target through the stream: `ADD`/`DROP CONSTRAINT` (primary key, `UNIQUE`, foreign key, `EXCLUDE`, `CHECK`), `ENABLE`/`FORCE ROW LEVEL SECURITY`, `CREATE`/`ALTER`/`DROP POLICY`, `SET`/`DROP NOT NULL`, `SET`/`DROP DEFAULT`, and identity changes. Before v0.156.0 each one was ignored silently, and the target stayed weaker than the source. The worst shape was one statement: `ALTER TABLE t ADD COLUMN x int, ADD CONSTRAINT fk FOREIGN KEY (x) REFERENCES p(id)` forwarded the column and dropped the foreign key.

MySQL and MariaDB binlog sources have the same gap for a different reason: sluice re-reads only a table's columns after a DDL. There the door covers primary key, `UNIQUE`, foreign key and `CHECK` changes (including `NOT ENFORCED` on MySQL), and `DEFAULT`, `EXTRA` or generation-expression changes on an existing column. Nullability is already carried by the column forward.

When the stream starts, sluice records these objects for every table (the baseline). On Postgres, each such DDL makes the server resend the table's description before the next change it decodes for that table. On MySQL, the DDL clears sluice's schema cache and the next row on the table rebuilds it. At that point sluice reads the table again and compares. On any difference, `sync` and `backup stream` end with `UNFORWARDED-SCHEMA-CHANGE`, naming each change. The refusal is never retried automatically. An automatic retry after some OTHER transient error (a dropped connection, say) keeps the baseline the stream started with, so a change made just before that error is still refused.

**The refusal is recorded and survives a restart.** `sync` records it on the stream's row of the target's `sluice_cdc_state` table (column `unforwarded_refusal`); `backup stream` records it in the destination's `stream_state.json`. Every later start of that stream reads the record before it opens a change stream and refuses again, quoting the recorded refusal, on every start path (warm resume, multi-database resume, `--restart-from-scratch`, `--reset-target-data`). This matters under a supervisor: a restarted reader would baseline the source catalog that already has the change, so without the record a `Restart=on-failure` unit, a pod restart or a fleet restart would accept the change silently.

The refusal carries no `SLUICE-E-*` code, so the process exits **1**, not 3, and a JSON log line or envelope has no `code` or `hint` to branch on. Match on the marker `UNFORWARDED-SCHEMA-CHANGE` in the message instead.

**The replayed refusal prints a fingerprint.** The refusal that stops the stream names the changes. The next start replays the recorded refusal and adds `fingerprint <12 hex digits>`, the first 12 hex digits of the SHA-256 of the recorded text, and the exact acknowledgement to pass (`--accept-unforwarded-schema-change=<fingerprint>`). So to get the fingerprint, start the stream once without the flag and read the refusal.

To continue:

1. Apply the same change to the target yourself. For `backup stream`, take a new full backup instead; a chain restored from the old full would lack the change.
2. Start once with the same `--stream-id` and `--accept-unforwarded-schema-change=<fingerprint>` (the same flag on `backup stream run`). It clears the record, logs a WARN naming what was accepted, and takes a fresh baseline.

**The acknowledgement is bound to one refusal.** Only the fingerprint of the refusal recorded now clears it. A value naming any other refusal is refused, with the message saying the acknowledgement "names a different refusal than the one recorded, so it was not applied". An empty value keeps refusing. Once the flag has cleared the record, the running process treats it as spent, so a later refusal in the same process is not pre-accepted. This is what makes a flag left behind in a systemd `ExecStart` line or a wrapper script harmless: it cannot clear the next, different refusal on the next automatic restart. Remove it from the command line anyway.

**The acknowledgement takes a fresh baseline, so passing it without step 1 accepts the difference permanently** and nothing reports it again.

**Fleet legs (`sync run`).** The supervisor does not restart a leg that stopped with `UNFORWARDED-SCHEMA-CHANGE`. It marks the leg `failed` and logs it at ERROR; other legs keep running. There is deliberately no `syncs.yaml` key for the acknowledgement, because standing config would pre-accept refusals. To acknowledge:

1. Apply the change to the target (the leg is already stopped).
2. Start that stream once outside the fleet: `sluice sync start --stream-id <id> … --accept-unforwarded-schema-change=<fingerprint>`, with the leg's own source, target and flags.
3. Stop it with `sluice sync stop --stream-id <id> … --wait`.
4. Restart the fleet process. On Linux and macOS a `SIGHUP` also works: a reload starts a failed leg that is still in `syncs.yaml`.

Every other leg failure is restarted on backoff, as before.

If sluice cannot write the record (the target is unreachable at that moment, say), it logs an ERROR saying a restart will NOT refuse again. Treat that line as "do not restart until the change is applied to the target". A target whose control table lacks the `unforwarded_refusal` column, where sluice cannot add it, never gets that far: every `sync start` first makes sure a refusal could be recorded, and fails before streaming when it could not. A Postgres role that does not own the table cannot add the column, and a PlanetScale safe-migrations branch refuses the ALTER. See [schema-change-runbook](../schema-change-runbook.md) and [managed-services](../managed-services.md) for adding it after an upgrade.

Changes sluice already forwards are not refused: adding, dropping or retyping a column (ADR-0091), including the attributes of a newly added column and a constraint that disappears because its column was dropped. A retype does not excuse a new DEFAULT *value*. The forwarded type change carries no DEFAULT on a Postgres target, so a retype that also changes the default value refuses. Only a re-spelling of the same value is exempt (MySQL renders `0` as `0.00` after a move to `DECIMAL`), plus, on Postgres, a generation expression re-rendered by the retype. A foreign key is compared by what it references, not its text, so renaming the table it points at is not a refusal. Constraint validity is not compared, so `ADD … NOT VALID` followed by `VALIDATE CONSTRAINT` does not refuse.

What this does not catch, stated so it is not read as broader:

- A change made while the stream was stopped, or during the cold-start copy, is already in the baseline. More precisely: anything made after the last position the target acknowledged and before the stream started, including a DDL a lagging stream had not reached yet when it stopped.
- Upgrading does not find an old gap. A change a pre-v0.156.0 stream ignored is in the first baseline the new release takes.
- `backup incremental` opens a fresh reader every run, so a change between two incrementals is in the next run's baseline.
- Postgres only: a non-key column's collation and policies or RLS on a partitioned root are not compared by this check. A key column's collation is a different door: it is judged at the first schema boundary (`KEY-COLLATION-CHANGED`) and on every upsert (`KEY-COLLATION-MERGE`), described under `DEFERRED-SCHEMA-CHANGE` below. A change to a constraint's storage (tablespace, fillfactor) changes its definition text, so it refuses rather than slipping through. A constraint rename refuses as a drop plus an add.
- A downgrade to an older binary ignores a recorded refusal, so a downgrade followed by a restart accepts the change silently.
- MySQL only: `DROP COLUMN b` shrinks a composite `UNIQUE (a, b)` to `UNIQUE (a)`, and sluice refuses that, because it cannot tell whether the target shrank the key the same way (Postgres drops the whole index instead). Apply the same drop on the target and acknowledge the refusal as above.
- PlanetScale and Vitess (VStream) sources are not covered yet.
- Detection needs a later write to the same table. A change on a table nobody writes to again is not seen until someone does.
- Plain (non-constraint) indexes are not compared. Index DDL is the documented not-forwarded case, and refusing on every source `CREATE INDEX` would end streams on routine tuning.

A unique key the source dropped while the stream was stopped, or on a source this door does not cover, is caught by the next section's check instead.

## `sync`: a target unique key the source does not enforce refuses (`SOURCE-UNIQUE-KEY-ABSENT`)

Every insert reaches a sluice target as an upsert (`INSERT … ON DUPLICATE KEY UPDATE` on a MySQL-family target, `INSERT … ON CONFLICT … DO UPDATE` on Postgres). On MySQL the upsert resolves a conflict through **any** unique key the table has; on Postgres through the table's ON CONFLICT key only (a conflict through another key raises an error). A target unique key the source does not enforce can therefore turn the source's next duplicate of it into an overwrite of a different row. The usual cause is a source `DROP INDEX` no stream saw: made while the stream was stopped (the door above baselines at start, so the drop is in its baseline), or on a `postgres-trigger`, `sqlite-trigger`, `d1-trigger`, PlanetScale or Vitess source, whose change streams carry no DDL at all. The apply-time check (`UNIQUE-KEY-CONFLICT-OTHER-ROW`) refuses most such merges at the first colliding row, but two shapes look exactly like a re-delivery of the same row to it: a table with no primary key and one unique key, and two rows that differ only in a NULL or partial-index column.

So every `sync start` compares, for each table the stream applies to, the target's unique keys (its primary key included) with the source's current ones, read from both catalogs after the change stream opens and before the first change is applied. That covers every start: cold start, warm resume, `--restart-from-scratch`, `--reset-target-data`, each namespace of a multi-database stream, and every `sync run` leg start. A target key passes when a source key implies it: the same columns, in any order, or a subset of them (rows distinct on `(a)` are distinct on `(a, b)`) — names compared without case, unless the table has two columns whose names differ only in case; a prefix `c(10)` implies `c(20)` and the whole column; the same expression or partial-index predicate read in the same SQL dialect; across dialects (a functional key from MySQL to Postgres), a key of the same name, as the target spells it (a Postgres target prefixes an index name with its table: `uniq_email` becomes `users_uniq_email`), and the same shape. On a Postgres side three facts the schema read does not carry come from the catalog: an index-level collation (`(k COLLATE x)`, which a target key may carry only if the source's does), NULLS NOT DISTINCT, and an index left invalid by a failed `CREATE UNIQUE INDEX CONCURRENTLY` (which enforces nothing, so it covers nothing); a partitioned table's keys, which the schema read does not list at all, come from the catalog the same way. A key column whose target collation equates values the source's keeps apart (case-, accent- or trailing-space-insensitive where the source's is not) does not count as implied, and the refusal names that column: an `ALTER` of it to a collation as strict as the source's clears it too. That is judged by direction rather than by collation name (MySQL-family by the `_ci` / `_ai` / `_bin` name tokens and the PAD attribute, with `CHAR` always ignoring trailing spaces; Postgres by whether the collation is deterministic, with `bpchar` always ignoring trailing spaces and `citext` folding case; an array takes its element's). A collation whose name does not state all its axes (a MariaDB `_w2` weight level, a kana-sensitive `_ks`) is compared by name instead, and a differing name counts as looser (the loud direction). It is judged by direction only for engines that can classify their collations <!-- collation-direction-engines: mariadb, mysql, planetscale, postgres, postgres-trigger, vitess -->(MariaDB, MySQL, PlanetScale, Postgres, `postgres-trigger` and Vitess), between two MySQL-family servers, between two Postgres servers, and from any of them into a Postgres-family target. A source that cannot classify its collations <!-- collation-narrow-rule-engines: d1-trigger, sqlite-trigger -->(`sqlite-trigger`, `d1-trigger`) into a Postgres-family target is judged narrowly instead: a target key column known to fold case or accents (`citext`, a nondeterministic collation) refuses, whatever the source column declares (a SQLite `COLLATE NOCASE` column folds ASCII case only, where `citext` and ICU collations fold Unicode case and accents); the default — a SQLite `TEXT` key onto a deterministic `text` column — passes. Into a MySQL-family target from such a source it is not judged (KEY-COLLATION-SQLITE-SOURCE-UNSTAMPED). From a Postgres or MySQL-family binlog source it is judged at a cold start only, since a collation change made while the stream was stopped is the key-collation check's (`KEY-COLLATION-MERGE`), which forwards it; from a PlanetScale, Vitess or trigger source, at every check. Keys sluice adds itself pass: a key copied from the source, the `--inject-shard-column` composite (it only adds the shard column), and a surrogate the target generates on every insert (`AUTO_INCREMENT`, an identity column, MySQL's invisible primary key).

The check also runs while the stream is running:

- **At a schema change that moves a table's columns, or loses a unique key with a column**, for that table, on every source, whether or not the change is forwarded: before the forward applies it when the change only adds columns and leaves every existing column as it was (so the target's keys cannot change), and after the forward otherwise. A Postgres source drops an index outright with a column it covers, while a forwarded `DROP COLUMN` narrows a MySQL-family key that included the column (`UNIQUE (a, b)` becomes `UNIQUE (a)`), and a `DROP COLUMN` at the first boundary after a cold start is not forwarded at all, so the target keeps the column, its default, and the key on it. Two Postgres shapes leave the change stream's column names unchanged: a dropped GENERATED column (logical replication carries no generated columns) and a column dropped and re-added under its name and type (only its attnum moves). The Postgres reader reports a unique key lost with a column from the catalog and compares attnums, so both are checked; a primed drop-and-re-add is usually refused first by the schema-forward check's own "now name a different column". A table's first schema change of a run is compared with the column list read at start, so one made before the table's first row change of the run is checked too. Nothing after the change is applied before the check, and a check that cannot read a catalog stops the stream at once with `SOURCE-UNIQUE-KEY-RECHECK-FAILED` (an ordinary failure a restart retries) rather than let the change through unjudged.
- **On a `postgres-trigger`, `sqlite-trigger`, `d1-trigger`, PlanetScale or Vitess source, every 15 seconds**, over the tables whose target has a unique key besides the primary key. When a re-check is due, the next transaction is held until it writes one of those tables (the re-check runs first) or commits without writing one (it goes on unchecked). An idle stream, or one that only writes other tables, costs nothing. Postgres (pgoutput) and MySQL-family binlog sources are not re-checked this way, because the door above already refuses a live `DROP INDEX` before the next row of the table.

The refusal names each key under its target table name (the renamed namespace on a multi-database stream, `--target-schema` when set). It carries no `SLUICE-E-*` code, so the process exits **1**; match on the marker. It is not retried, and a `sync run` leg that hits it is marked failed rather than restarted, because every start reads the same two catalogs and nothing is recorded. To recover:

- **The key was dropped while no stream was reading, or the target was built with it.** On a Postgres or MySQL-family source the message says nothing written after the drop has been applied. Drop that key on the target (`DROP INDEX`, or `ALTER TABLE … DROP CONSTRAINT` for a constraint, which the message names) and start again with the same `--stream-id`. The same applies to a refusal at a schema change.
- **Rows may already have merged.** This is the case when the mid-stream re-check found it, or when a source whose change stream carries no DDL dropped the key while a stream was running, or when a sluice v0.161.0 or earlier was streaming from a Postgres source when its plain unique index was dropped, or when a sluice v0.161.1 or earlier was streaming across a `DROP COLUMN` of a key column (no release through v0.161.1 checked the keys at a schema change). Dropping the key alone keeps the merged rows, so re-copy from a clean target: `sluice sync start --restart-from-scratch` or `--reset-target-data --yes`, with the same `--stream-id`. Both drop and re-create the stream's target tables from the source, the key and any merged row with them (destructive). From a Postgres (pgoutput) source, drop the stream's replication slot first (`sluice slot drop <slot> --source-driver=postgres --source <DSN> --yes`, the full name `sluice slot list` prints): the re-copy's fresh snapshot refuses to inherit it. **Under `--inject-shard-column` do not use `--reset-target-data`:** the target table is shared by every shard, and it drops that table with every shard's rows. Drop the key on the target and re-copy this shard with `--restart-from-scratch`, which there re-copies onto the shared table without clearing it (so it cannot remove a row a merge left behind; unmeasured).
- **The target is meant to have the key** because it was built with it on purpose. Accept it on every start with the value the refusal prints beside the key, `--accept-target-only-unique-key <table>.<key>=<fingerprint>` (repeatable; `<database>.<table>.<key>=<fingerprint>` on a multi-database stream, by the source or the target database name spelled exactly as the database is named (the refusal prints the target's), and `<schema>.<table>.<key>=<fingerprint>` with the `--target-schema` the refusal prints). The fingerprint is a short hash of the key's definition as the target engine itself reports it, together with the definition of every column the key depends on — on Postgres `pg_get_indexdef` (parts, expressions, per-part collation and operator class, NULLS NOT DISTINCT, the predicate with its literals verbatim) and, for each column the index or its expression or predicate reads, its attribute number, name, type with modifiers, a domain's base type, its collation by schema-qualified name (an array's is its element's) and whether it is deterministic, NOT NULL and a generated expression; on a MySQL-family target the database and table as the server reports them, the key's `SHOW CREATE TABLE` line and `information_schema.STATISTICS` rows, and for each column it depends on (every column of the table, for a functional key) its `information_schema.COLUMNS` row and `SHOW CREATE TABLE` line (comment included), plus a functional part's hidden column. Nothing is normalised. A functional key part on PlanetScale or Vitess cannot be fingerprinted — it compares under a hidden column's collation those servers do not expose, which can come from the session at `CREATE` time — so such a key cannot be accepted: the refusal says so, and dropping the key is the remedy. Only a MySQL-family or Postgres target reports a key's definition at all; on any other target (SQLite, D1) a target-only unique key cannot be accepted either, the refusal says the target engine has no definition surface, and dropping the key on the target is the remedy. **Not inputs**, named so the fingerprint is not read as broader than it is: the collation's provider and ICU version (a collation is bound only by its name, so a server whose ICU library changes what `und-u-ks-level2` folds keeps the same fingerprint); the body of a user function an expression or predicate calls (on Postgres a function redefined to fold differently surfaces at the write as a loud duplicate-key error, 23505); a Postgres column comment; and the columns behind a whole-row reference in a Postgres expression or predicate, which the catalog records as a dependency on the table rather than on a column. The accepted cost is that any change to an input refuses until re-accepted: a size-only widening, a rename, a MySQL column comment, and a server upgrade that respells a type or collation (MySQL 8.0.30's `utf8` → `utf8mb3`) included. A predicate holding a temporal literal is rendered by Postgres in the reading session's `TimeZone` / `DateStyle`, so two hosts with different session settings can disagree on the fingerprint of an unchanged key, which refuses an accepted one. All of these refusals are loud and print the new value; that is the trade. A key whose definition cannot be read refuses rather than passing. A value without a fingerprint, or with a malformed one, refuses at the start. The fleet spec key `accept-target-only-unique-key` takes the same list, and since the key stays on the target the acceptance is standing, not one-shot. The apply-time check still refuses a merge through an accepted key wherever it can tell the rows apart. An acceptance is honoured only while the key's definition still hashes to its fingerprint, at every check (the start, a schema change, the periodic re-check, `schema add-table`): a key a forwarded change later reshapes — a `DROP COLUMN` turning `UNIQUE (a, x)` into `UNIQUE (a)`, or a `MODIFY … COLLATE` making it case-insensitive, each of which merges rows the accepted key kept apart — refuses again, at that change and at every restart after it, naming the fingerprint that was accepted and printing the new value. A type- or collation-only change on a table carrying an accepted key is judged too. Passing the new value is accepting the new definition: do it only having checked that the key should be that way. On a multi-database stream a `<table>.<key>` acceptance that matches the key in more than one database refuses at the start; name the database (`<database>.<table>.<key>`). `sluice schema add-table` checks a pre-created target table the same way, before copying it — with the catalog facts above on both sides, and judging collation direction on the source table as read, before any `--type-override` — refuses if it cannot read either catalog, and takes the same flag.

A periodic re-check that cannot read a catalog logs a WARN containing `SOURCE-UNIQUE-KEY-RECHECK-FAILED`, and the next due check tries again; four failures in a row stop the stream with that marker (an ordinary failure a restart retries), because on the sources that carry no DDL the re-check is the only mid-stream protection.

What this does not catch, stated so it is not read as broader:

- Mid-stream on the sources that carry no DDL, the transactions applied between the source's drop and the next due re-check (up to 15 seconds of them). For the two shapes the apply-time check cannot see, a merge in that window is applied; the re-check then refuses and names a re-copy. The trigger engines refuse a table without a primary key at setup, so on them those shapes cannot occur; a PlanetScale or Vitess source can carry one.
- A mid-stream primary-key change on those sources: only tables with a unique key besides the primary key are re-checked. The next start catches it.
- A source key dropped, a duplicate written and removed, and the key re-created, all between the stream's last position and its start: the key looks unchanged at start. The apply-time check refuses the replayed duplicate where it is armed; on the two shapes above it is silent.
- A cross-dialect functional or partial key redefined under its old name passes (pinned as a known miss). One renamed on either side refuses; accept it by name.
- Column collation direction from a Postgres or SQLite source into a MySQL-family target: a Postgres text key is byte-exact and the column sluice creates for it takes the target's case-insensitive default, so judging it would refuse every such stream; `KEY-COLLATION-MERGE` refuses that merge at apply time for a unique key beside a primary key. A Postgres nondeterministic collation counts as folding both case and accents (which one it folds is not recorded), so a MySQL `_as_ci` key against a Postgres ICU `ks-level2` column refuses although only case folds there; accept it by name. Two collations with the same axes but different folding tables (MySQL `utf8mb4_general_ci` and `utf8mb4_0900_ai_ci`, which disagree on characters such as `ß`) count as equal; only an operator-built target can hold such a pair, since sluice copies or maps the source collation. On a PlanetScale or Vitess source the collation is judged at each start and, for a table whose target has a unique key besides its primary key, at each 15-second re-check, so a key column moved to a stricter collation mid-stream can merge up to one re-check interval of rows first (`KEY-COLLATION-MERGE` is unarmed on those sources).
- The source catalog is read when a check runs, so it can be ahead of the stream, and the check refuses any target key the source catalog does not enforce at that moment, at every start and every schema change. That includes a key the source will lose only through a `DROP COLUMN` the stream has not reached yet. The check cannot tell that apart from a key the source dropped on its own, earlier, with duplicates written before the column went, which is a real merge. Two cases refuse although replaying the stream would have forwarded the `DROP COLUMN` and dropped the key:
  - a `DROP COLUMN` of a unique-key column made while the stream was stopped, refused at the start;
  - one the source has already made while the stream lags behind it, refused at the earlier schema change.

  A plain restart refuses again at the start, because the stream never gets past the change it stopped before. Drop the named key on the target and start again with the same `--stream-id`. That converges, and any duplicate the source wrote then lands as its own row (measured for both cases, into Postgres and MySQL). Re-copying works too.
- On a PlanetScale or Vitess source, whose change stream carries column changes but not index changes, a due 15-second re-check can read the target while a forwarded `DROP COLUMN` is still being applied there, and refuse a key that `DROP` is about to remove. It is loud, a restart clears it, and it needs a due re-check to coincide with such a `DROP`. The trigger engines forward no schema change at all, so it cannot occur on them.
- Tables added with `schema add-table --no-drain` while the stream runs join the re-check at the next start.
- The check needs the target tables to exist, so on a cold start into a pre-created target an extra key refuses after the copy, not before it (the copy itself cannot merge through such a key).
- `sync from-backup run` and `sluice restore` do not run this check. A backup chain records a source `DROP INDEX` as a schema change of the window it falls in, and both apply it to the target before that window's rows, so the duplicate lands as its own row (measured for a MySQL source). A target pre-created with an extra unique key is not judged there.

## `sync`: a table the stream never brought in refuses a warm resume (`INCLUDE-TABLE-SCOPE-DRIFT`, `INCLUDE-TABLE-ADD-IN-PROGRESS`, `COLD-START-INCOMPLETE`, `VSTREAM-COPY-RESUME-WITHDRAWN`, `PENDING-ADD-SUPERSEDED`, `LIVE-ADDED-TABLE-EXCLUDED`, `TABLE-IDENTITY-CHANGED`)

A warm resume copies nothing: it continues the change stream from the persisted position. So a table that joins the stream's scope on a restart is never copied. On a Postgres pgoutput source a table outside the publication is not even streamed; a table the publication delivers anyway, or any table on a MySQL-family, VStream or trigger-CDC source whose target table exists, is streamed from the persisted position onto a target copy missing everything before it. Through v0.162.0 the stream came back green in every one of those shapes (Bug 321). A table joins a running stream through `sluice schema add-table`, never through the flags of a restart.

Each stream keeps three records on its `sluice_cdc_state` row:

- **`established_tables`:** the tables each cold start actually copied (every lane; each namespace of a multi-database stream; `--restart-from-scratch` rewrites it), plus every `schema add-table` that completed. A cold start leaves it untouched until its point of no return — immediately before the target drop of `--restart-from-scratch` or `--reset-target-data`, or, when nothing is dropped, immediately before the copy's first write to the target — and there marks it *cold start in progress*; the copied set replaces the mark when the cold start finishes. (`--reset-target-data` then deletes the control row, mark and all, so its anchor records the copy as a first cold start's does.) So a cold start refused before that point (the "slot already exists" refusal, a schema preflight) leaves the record convicting exactly as before, even though it may already have widened the publication, and one that stopped after it leaves a mark every warm resume refuses (`COLD-START-INCOMPLETE`, below). A stream that has a record never goes back to having none.
- **`dropped_tables`:** established tables a later restart's scope left out. Their changes are discarded from then on — on pgoutput the table stays in the publication and the stream drops its changes — so the target copy goes stale.
- **`pending_added_tables`:** each `schema add-table` in flight. It is written before the add changes anything, under a token unique to that add-table run; its heartbeat is refreshed every 30 seconds while it copies, and once the copy is handed to the stream the entry is removed and the table recorded as established in one transaction. Every write after the first compares the token, so an add whose entry was marked abandoned by `--abandon`, or taken over by another add-table of the same table, stops with `PENDING-ADD-SUPERSEDED` (a heartbeat that finds this cancels the copy) and records nothing; the target table may then hold a partial copy. A failed add marks its entry no longer running and, on a Postgres source, takes back the publication add it made. Heartbeats are stamped and compared in the control-table server's clock, never a host's; one more than a minute ahead of the server's clock counts as stale and is named in a WARN.

On every start — each `sync start`, and each start of a `sync run` leg, restarts included — before the reader opens, a warm resume refuses with a codeless exit-1 error containing `INCLUDE-TABLE-SCOPE-DRIFT`, naming each table and why, for:

- a table an `--include-table` entry names **literally** that the stream never copied. A literal entry has no `*`, `?`, `[` or `\` (a backslash makes an entry a glob), is compared case-sensitively, and a schema-qualified entry such as `app.t` names no table (it admits none either);
- a **dropped** table that any scope re-admits — literal, glob or unfiltered;
- a never-copied table admitted by a glob or an unfiltered stream whose changes **would be applied**: its publication delivers it (shared with another stream, FOR ALL TABLES, a multi-schema stream's spanning publication, or a missing publication the reader would recreate FOR ALL TABLES), or, on a source with no publication, its target table exists;
- an established table that a FOR TABLE publication **no longer lists** — dropped and recreated on the source, or removed from it — shared or not;
- an established table that is **no longer the same table** on the source (`TABLE-IDENTITY-CHANGED`): its engine id no longer matches the record. On a Postgres or `postgres-trigger` source any change of `pg_class.oid` under the same name counts — `VACUUM FULL`, `CLUSTER`, `TRUNCATE` and rewriting `ALTER`s keep the oid (only `relfilenode` changes), so a changed one means the table was dropped and re-created, or swapped with another, while the stream was stopped. On MySQL and MariaDB InnoDB gives a table a new `TABLE_ID` on `OPTIMIZE TABLE`, a copying or rebuilding `ALTER` and `TRUNCATE`, so a changed id alone is not refused there: the record takes the new id, and a WARN names the old and new id: a DROP and re-CREATE under the same name looks the same there (`TABLE-RECREATED-WHILE-STOPPED`, below). Both engines refuse a **swap** (`RENAME TABLE t8 TO tmp, t9 TO t8, tmp TO t9`, or the same in three `ALTER … RENAME`s), proved by one name's recorded id now belonging to another, and the message says which table each name now holds;
- an in-scope table whose add-table entry has gone **stale** (heartbeat older than five minutes: the add died);
- any stream whose record reads **cold start in progress**: a cold start passed its point of no return and did not finish, so the persisted position no longer describes the target. The message carries `COLD-START-INCOMPLETE`; re-run the cold start (`--restart-from-scratch`, or `--reset-target-data`, whichever was interrupted).
- a PlanetScale or Vitess stream whose persisted position is a **mid-copy cursor**, saved by v0.163.2 or earlier when a cold start was stopped during its copy. Resuming it would keep the rows the source deleted while the stream was stopped ([above](#stopping-a-planetscale-or-vitess-cold-start-during-its-copy-means-a-re-copy-vstream-copy-resume-withdrawn)), so the message carries `VSTREAM-COPY-RESUME-WITHDRAWN`; re-run with `--restart-from-scratch`.
- a PlanetScale or Vitess stream whose persisted position carries no copy cursor and whose target holds no evidence that its copy finished: no `established_tables` record, and no `sync-<stream-id>` row at phase `complete` in `sluice_migrate_state` that holds up (its copied tables still hold rows, and the position was written after it). It was cold-started before v0.149.0 (or by a later release that could not record its progress), or stopped during its copy on v0.163.1 or earlier ([above](#stopping-a-planetscale-or-vitess-cold-start-during-its-copy-means-a-re-copy-vstream-copy-resume-withdrawn)). The message carries `VSTREAM-COPY-COMPLETION-UNPROVEN`; re-run with `--restart-from-scratch`, or, once you have matched the target's row counts to the source's table by table, once with `--assert-copy-finished` (refused where the target shows the copy did not finish).

Nothing has been applied. Every restart repeats it and `sync run` does not restart the leg. A table whose add-table is **still running** (fresh heartbeat) is judged by that add alone: being never copied, or re-admitted after a drop, is exactly what the add's completion cures. When every refused table is such a table, the resume defers with `INCLUDE-TABLE-ADD-IN-PROGRESS`, which the fleet supervisor restarts, and once the add completes the stream resumes; a conviction on any other table — or an established table gone from the publication, which an add does not cure — keeps the terminal refusal.

A never-copied table whose changes are provably **not** applied — outside the publication, or with no target table (the applier already skips those loudly, `sluice_cdc_skipped_tables`, `sync health`) — does not refuse: it stays out until `schema add-table` brings it in, and every resume names such tables in an `INCLUDE-TABLE-NOT-ESTABLISHED` WARN. That is the whole cost of the rule: those tables are not replicated until you add them. A pending add for a table since dropped or renamed on the source is ignored with a WARN. Remedies, per named table:

1. With the stream stopped, empty the target table and run `sluice schema add-table <table>` with the stream's `--source-driver`, `--source`, `--target-driver`, `--target` and `--stream-id`, then the same `sync start` again. (Not on a multi-database stream: add-table cannot record a table there, and the refusal names only the re-copy.)
2. Take the table out of scope (`--include-table` / `--exclude-table`). For a table `schema add-table` brought in, neither flag does it — `--include-table` does not remove it and an `--exclude-table` naming it is refused — so run `sluice schema add-table --abandon <table> --yes`, then restart.
3. Re-copy every table with `--restart-from-scratch`. On a Postgres source that run first refuses because the stream's replication slot exists; drop it with `sluice slot drop`, then re-run. The re-copy rewrites the records and clears the pending entries of the tables it copied.

**`sync health`** reports a pending add-table that is still running as `pending_added_table: <t> in progress` with exit 0, so a cron probe does not page through every normal `--no-drain` add, and one whose heartbeat went stale as `ADD-TABLE INCOMPLETE` with exit 1; the text `sync status` lists both. For an entry no add-table can clear — its table was dropped on the source, or taken out of the stream's scope — run `sluice schema add-table --abandon <table> --yes` with the stream's driver, DSN and `--stream-id` flags. It refuses while the add is still running. Otherwise it takes the table out of a Postgres publication unless the stream established it or another sluice slot exists on the same database, drops the dead add's snapshot slot (`sluice_addtable_<table>`, or the `--slot-name` you pass) when it is inactive, and leaves the target table as it is, which may hold a partial copy. It does **not** remove the entry: it marks it abandoned, because a running stream may still be applying the table's changes onto that partial copy (the publication may still deliver it), and only a stream start judges the table. Until then `sync health` exits 1 with `ADD-TABLE ABANDONED: restart the stream`, and `--abandon` says the same. **Restart the stream.** A start that finds the table out of the stream's scope, gone from the source, or with changes provably not applied clears the entry; any other start refuses `INCLUDE-TABLE-SCOPE-DRIFT` naming the abandoned add, and the remedies above apply. A completed re-run of `schema add-table` for the table, or a cold start that copies it, also clears it.

**A stream cold-started by an earlier release** has no record until its next cold start; sluice does not seed one from the current scope, which would record a never-copied table as copied. Until then the check falls back to the stream's publication on a pgoutput source, for literal includes, and only when no other sluice replication slot exists on the same database (a slot on another database of the server cannot read the publication, so it does not count). Otherwise every resume logs `INCLUDE-TABLE-SCOPE-UNRECORDED` and there is no evidence, except on a PlanetScale or Vitess source, where since v0.163.4 a warm resume with no record refuses `VSTREAM-COPY-COMPLETION-UNPROVEN` unless the stream's `sluice_migrate_state` progress row proves the copy (Postgres targets only), and a pass, or `--assert-copy-finished`, writes the record. A first cold start that cannot bring the record's columns up to date (missing, or of a type sluice refuses, on a control table this role or branch cannot ALTER) logs `COLD-START-ANCHOR-UNRECORDED` at its anchor and `INCLUDE-TABLE-SCOPE-UNRECORDED` at its record write, and runs without the record. Those are the only ways to have no record.

**A table `schema add-table` brought in stays in the stream's scope.** The add records it in the stream's live-added set (`live_added_tables` on the control row), on every source and path — the mechanism MySQL's `--no-drain` path has used since v0.27.0. Every later start reads the set and admits its tables whatever `--include-table` says, so the staged-wave flow (an `--include-table 'orders,order_items'` stream, `sluice schema add-table` of `users`, then the same `sync start` command again) keeps streaming `users`. Through v0.162.0 only the MySQL `--no-drain` path recorded it, so on a Postgres source, or after any drained add, that restart dropped every change to `users` at the dispatch filter, silently. One thing takes an added table back out: `sluice schema add-table --abandon <table> --yes`, which for a completed add takes it out of the live-added set; the next start narrows it, below. A cold start — `--restart-from-scratch`, an interrupted copy's resume, or the re-snapshot after an invalid position — copies the live-added tables along with the ones the flags name: the copy covers exactly what the stream will apply. `--reset-target-data` is the exception, because it deletes the control row the set lives on: its copy and its stream cover only the flags' scope, and a WARN names each live-added table discarded, whose target table is left as it was and receives no further changes. Name such a table in `--include-table`, or `schema add-table` it again, to keep replicating it. On a MySQL-family target, `schema add-table` refuses at its preflight, before it changes anything, a table whose name contains a comma or begins or ends with whitespace (a codeless exit 1): the live-added set there is a comma list, trimmed on read, so the name would read back as other tables. To stream such a table, name it in `--include-table` with a glob that matches it (`?` for each comma or edge space, for example `foo?bar`) and re-copy with `--restart-from-scratch`, or rename the table. A warm start that finds a live-added entry the source catalog does not hold logs `LIVE-ADDED-TABLE-NOT-IN-CATALOG` naming the entries. Either the table was dropped on the source, or, on a MySQL target, the entries are fragments of a comma name an older release recorded, which no longer admit that table. Check each, and `sluice schema add-table <table> --abandon --yes` (with the stream's flags) any entry that should not be there.

**An `--exclude-table` that names an added table is refused (`LIVE-ADDED-TABLE-EXCLUDED`).** The add said the table is in the stream's scope, and the exclusion would apply none of its changes, so the target copy would go stale while the stream reported healthy. Every start refuses it before copying, dropping or applying anything (a codeless exit 1 carrying `INCLUDE-TABLE-SCOPE-DRIFT`, which the fleet supervisor does not restart), and so does a running stream: `schema add-table` cannot know the stream's flags, so a `--no-drain` add of a table the running stream excludes completes (or, if the stream sees it first, stops with `PENDING-ADD-SUPERSEDED`), and the stream stops when its live-added poll reads the add. Changes to the table that reached it between the add and that poll (at most one poll interval, 5 seconds — the window every live add has, ADR-0034) were dropped as excluded while other tables' changes moved the persisted position past them, so before stopping the stream writes that to its control row in one locked transaction: the table's add-table entry is marked abandoned (a still-running add stops and records nothing), the table moves to the dropped set, and it leaves the live-added set. From then on the table comes back only with a fresh copy — narrow `--exclude-table`, empty the target table and `schema add-table` it again, or `--restart-from-scratch` — and a restart that only narrows the exclusion refuses (`INCLUDE-TABLE-SCOPE-DRIFT`, dropped). Keeping the exclusion leaves the table out and the next start passes. If that control-row write fails — or commits but cannot record the table as dropped, because the stream has no established-table record (cold-started by an earlier release), keys a multi-database record, or is mid cold start — the stream still stops and logs it at ERROR; then nothing on record stops a restart that only narrows the exclusion, and the refusal says so — with the exclusion still in place every start keeps refusing. At a start (nothing streamed yet), decide which you meant: to keep the table, narrow `--exclude-table` so no pattern matches it; to take it out, `--abandon` it as above. Through v0.162.0 a MySQL `--no-drain` add silently won over the exclusion instead (ADR-0034's additive rule).

**A table renamed while the stream was stopped is followed, not refused.** The record keeps each established table's engine-stable id beside its name (Postgres and `postgres-trigger` sources: `pg_class.oid`; MySQL and MariaDB: InnoDB `TABLE_ID`). On a warm start, an established table whose name is gone from the source, whose id now belongs to a new in-scope name, is that table renamed: the record takes the new name and keeps the id, and nothing refuses — provided the target was renamed too: it holds the new name **and no longer holds the old one**, as the drained-model recovery leaves it ([schema-change-runbook](../schema-change-runbook.md)). Otherwise the start refuses saying the target was not renamed — including when the target holds a table under the new name beside the stream's copy under the old one: that new-named table is some other table, and following the rename would apply onto it and strand the real copy. Drop or rename such a table away first. A table dropped and re-created under a new name has a new id and refuses as never copied. Where no id proves a rename — a PlanetScale or Vitess source (vtgate does not expose the InnoDB dictionary), a table name InnoDB stores in its filename encoding, every table of a database whose name is so encoded (for example `my-db`, which leaves the whole stream without ids), a partitioned table, or a record written without ids — the refusal names `--accept-table-rename <old>=<new>` on `sync start`: a human's statement that the new table is the old one renamed, after renaming the target too; the record then follows it, under the same target rule (new name present, old name gone). sluice cannot check what the target table under the new name holds, so with the flag it is trusted as-is. A pair that matches no rename only WARNs, so the flag does nothing once the rename is followed. It has no `syncs.yaml` key: take the leg out of the fleet for the one start that needs it.

**A narrowing is logged and recorded, or the start refuses.** A start whose scope no longer holds an established table logs a WARN naming it — its changes are no longer applied, and bringing it back later refuses until it is copied again — and moves it to `dropped_tables` in one locked write. If that write cannot be made (the `dropped_tables` column missing on a control table this role cannot ALTER, a lost connection), the start refuses with `INCLUDE-TABLE-NARROWING-UNRECORDED` instead of going on, because a narrowing nobody recorded would let a later re-widen pass a table whose changes were discarded: restore the scope the stream had, or fix what the error names and start again. The three record columns are added together, in one first write, and a refusal for a missing one names the statement that brings them up to date, built from the columns the table has (on MySQL that includes `live_added_tables`, added if missing or widened to `LONGTEXT CHARACTER SET utf8mb4`); `sluice control-tables ddl` prints them (and `live_added_tables`) with the rest of the control table. A pre-existing record column of any type but `LONGTEXT` (MySQL family) or `TEXT` (Postgres) is refused with the `ALTER` that fixes it: a shorter type would cut a long record where nothing could tell.

**A record that does not decode** (hand-edited, truncated, corrupted) is never read as some other set. A start refuses `INCLUDE-TABLE-SCOPE-DRIFT` naming the column and the recovery. For `established_tables` or `dropped_tables` the recovery is a re-copy (`--restart-from-scratch`): the cold start overwrites the record without reading it (an ERROR line names the discarded value's length). The dropped set cannot be rebuilt from an unreadable value, so the cold start records as dropped every table the source catalog holds that the copy did not cover (any table that ever left the scope and still exists is among them); a later start then refuses each of those if a scope re-admits it, while a table created after the re-copy is judged like any never-copied one. Only when the cold start cannot read the catalog does it record the catch-all "every table this copy did not cover counts as dropped" (which refuses any table the stream does not hold, including one it would only have warned about), and the next cold start that can read the catalog replaces it. A pending add-table entry that does not decode is reported rather than failing the command: `sync health` exits 1 and prints its raw text, `sync status` lists it, and a start refuses the table it names; `sluice schema add-table --abandon <table> --yes` retires it. An entry with no readable table name, or a pending column that does not decode at all, is cleared with the SQL the message gives (`UPDATE sluice_cdc_state SET pending_added_tables = NULL WHERE stream_id = '…'`), after which the tables it named need `schema add-table` or a re-copy.

**`sync health --format json`** carries the pending record as `pending_added_tables` (one object per entry: `table`, `started_at`, `heartbeat_at`, `in_progress`, `abandoned`, `malformed` — the raw text of an entry that does not decode), `pending_added_tables_tripped` (any entry not in progress: exit 1) and `pending_added_tables_abandoned` (any entry `--abandon` retired: restart the stream).

What the check still cannot see:

- **a running stream.** The check runs when a stream starts, and apart from `LIVE-ADDED-TABLE-EXCLUDED` (above) nothing re-checks a stream that is already running. Everything else in this section that arises while a stream runs — an add-table killed mid-copy, an abandon of an add whose table the stream is still applying, the window below between a cold start's anchor write and its record write — is caught at the next start, not before. `sync health` is the running-stream signal (`ADD-TABLE INCOMPLETE`, `ADD-TABLE ABANDONED`); alert on it;
- a process killed in the middle of `schema add-table` cannot take back its publication add, so a running stream keeps applying into the partial copy until `sync health` reports the entry stale or the stream restarts and refuses. The add's snapshot slot is persistent and survives the kill too, until `--abandon` (or `sluice slot drop`) removes it;
- a table dropped and re-created under the same name while the stream was stopped (`TABLE-RECREATED-WHILE-STOPPED`), where the record carries no id for it: on Postgres that is a record written before ids were recorded (until the stream's next cold start or `schema add-table` of the table), under a `FOR ALL TABLES` or `FOR TABLES IN SCHEMA` publication — a `FOR TABLE` publication drops the table on `DROP TABLE`, which the check catches without an id. On MySQL and MariaDB it is every such table, because a changed `TABLE_ID` there is as likely a rebuild (above); the binlog the resume replays carries the `DROP`/`CREATE`, and whether anything in that replay catches it has not been measured. A swap is caught on both engines wherever ids are recorded. On MySQL that excludes the tables listed above as having no id (filename-encoded table or database names, partitioned tables), so a swap made there while the stream was stopped is not seen;
- a process killed between a later cold start's anchor write and its record write (`--restart-from-scratch`, an interrupted copy's resume, the re-snapshot after an invalid position) leaves the in-progress mark, so the next warm resume refuses `COLD-START-INCOMPLETE` although the cold start had finished — loud, and a re-copy clears it. A stream's first cold start has no control row until that anchor, and neither has a `--reset-target-data` cold start, which deletes the row (its in-progress mark with it) before copying, so the anchor write itself records the copied tables with their engine ids, in the same transaction, and a kill after it warm-resumes on that record (the dropped set follows it), so a table dropped and re-created while the stream was stopped still refuses `TABLE-IDENTITY-CHANGED` on a Postgres source. Without that, the new stream would be left with no record and judged like one an older release cold-started. This holds for the stopped-cold-start resume's anchor (`COLD-START-RESUMED`) and the multi-database stream's too. Where the control table's record columns cannot be brought up to date (missing, or a type sluice refuses, such as a MySQL `live_added_tables` that is `TEXT` or not `utf8mb4` and cannot be widened), the anchor is written alone, as before, and a WARN carrying `COLD-START-ANCHOR-UNRECORDED` names the error;
- on a multi-database stream, each database's cold-start refusals (a populated target, a pre-existing foreign key, the target-side preflights) run when that database's turn comes, after earlier databases were already copied — and, under `--restart-from-scratch` or `--reset-target-data`, dropped. A refusal there is loud and every re-run repeats it after re-copying the earlier databases; fix what it names. On a single-database stream every deterministic refusal runs before the record is marked and before anything is dropped;
- `sync status --format json` does not carry the pending record yet (`sync health --format json` does);
- an in-scope table with no capture trigger on a trigger-CDC source captures nothing, at cold start as well, which is a separate class.

## `sync`: a schema change the stream did not see is checked against the target (`RESUME-SCHEMA-DIVERGENCE`)

When `sync` starts on a stream that already ran — a warm resume, a restart, a `sync run` leg restart, an automatic retry after a transient error — it has no record of the schema change that may have happened since: the change was made while it was stopped, or after it restarted and before the table's next row. Since v0.156.10 each table's first schema boundary on such a start is compared with the target table itself (column names and types; the source's shape is rendered the way the cold start created the target, and a column named by `--type-override` is compared by presence only — its type is the operator's, so an override changed between runs is not seen here). Postgres and PlanetScale/Vitess sources produce that boundary at each table's first change; MySQL and MariaDB binlog sources do too since this release.

- **They match:** nothing happens.
- **The source has columns the target lacks:** they are added on the target, with their DEFAULT, and the rows the target already held are backfilled from the source — the same path, and the same `ADD-COLUMN-BACKFILL-INCOMPLETE` guarantee, as an `ADD COLUMN` seen live.
- **Exactly one column the source widened within its family** (a temporal precision, a decimal's integer digits and/or scale, a `CHAR`/`VARCHAR` length, `FLOAT` → `DOUBLE`, an integer width with the same sign): the change is applied, and the session-zone refusal still applies to a `TIMESTAMP` ⇄ `DATETIME` pair. An array column whose element the source widened (`numeric(10,2)[]` → `numeric(10,4)[]`) refuses instead: the element modifier is compared since v0.156.10's third review, but no first boundary alters an array column.
- **Exactly one column the source NARROWED while the target still holds the old type**, where the stream's retained schema history proves it — the history's version of the table held the type the target holds, the source's now cannot hold every value of it, and the boundary lies strictly after that version in the source's own position order (a MySQL or MariaDB binlog source; a Postgres source's history cannot prove this — its schema versions carry no usable position — so there the next bullet's WARN applies) (a temporal precision, a decimal on either axis, `DOUBLE` → `REAL`, a `NUMERIC` → integer, a shorter `VARCHAR`/`CHAR`, an `ENUM`/`SET` label removed): the narrowing is applied, as a live one would be, so the target's rows are converted the way the source's own `ALTER` converted them. The INFO line's `difference=` says `narrowed from`. If the target holds a type other than the history's (it was widened past the source on purpose), the stream refuses with `RESUME-SCHEMA-DIVERGENCE` instead. An array column's element is never narrowed here (it refuses).
- **Exactly one column the target already holds WIDER than the source, with no such proof:** a WARN (`the target column is WIDER than the source's`); the target keeps its type. Wider means within the family as above (an array compared through its element), or across families where the target's type holds every value the source's can send: `TEXT` for a `VARCHAR`, a `NUMERIC` with a non-negative scale and enough integer digits for an integer (10 for `INT`, 19 for `BIGINT`, 20 for `BIGINT UNSIGNED`), a wider signed integer for an unsigned one, a superset of an `ENUM`'s labels, and a superset of a `SET`'s labels in the same order (a `SET` renders a value in its own declaration order) — never `CHAR` across families (a Postgres source sends `bpchar` padded, while the target's rows hold the unpadded value, so key-scoped updates would match nothing), and never `jsonb` for `json`, which rewrites the document. For an array element only the first of those holds: a `text[]` target for a `varchar(n)[]` source is wider; `char(n)[]` against `text[]` refuses (padding again, element by element — GC-44 F25), and the other cross-family pairs are not extended to array elements. So a replay that meets a column the stream itself already forwarded to `text` resumes instead of refusing on every start. Without the history's proof a first boundary never narrows: a target an operator widened on purpose, and on a Postgres source the replay (after a crash in the middle of a transaction) of the shape from *before* an `ALTER` the target already took, both look like a source that narrowed the column. A boundary that does not lie strictly after the history's version may be such a replay and never counts as proof; one that does is proof whatever shape it shows, including a narrowing back to a shape the table held before. The WARN says the source may have narrowed it; if it did, the rows the target already holds kept values the source's `ALTER` converted — narrow the target or re-copy the table (the drained model).
- **The target has columns the source no longer has:** a WARN names them (`target_only_columns`); the target keeps them and they receive no values from here on.
- **Anything else** — columns added and removed together (a possible rename), more than one changed column, a change across families the target's type does not already hold (a source `VARCHAR` → `TEXT` made while stopped is refused, not forwarded), a decimal widened on one axis and narrowed on the other: the stream ends with `RESUME-SCHEMA-DIVERGENCE`, naming every differing column with its source and target type, before anything after the boundary is applied or recorded (rows read before the boundary may already have been applied).

The refusal carries no `SLUICE-E-*` code, so the process exits **1**; match on the marker. It is not retried automatically, and a `sync run` fleet leg that hits it is marked failed rather than restarted, because the check runs again at the table's first boundary on the next start: it records nothing, and a fresh run reads the same source and the same target. To recover, make the target table match the source (the drained model in the [schema-change runbook](../schema-change-runbook.md)), then start again with the same `--stream-id`. With `--inject-shard-column` (Shape A) a difference the check forwards goes through the shard-consolidation lease like any live boundary: the first shard to reach it applies it, the others observe the apply (or find the target already matching), so a change made on every shard's source while the fleet was stopped is applied once.

Through v0.156.9 that first boundary was accepted as the new baseline without being applied. A `DATETIME` → `DATETIME(6)`, `DECIMAL(10,2)` → `DECIMAL(12,4)`, `FLOAT` → `DOUBLE` or Postgres `numeric`/`timestamp` precision change made while the stream was stopped therefore never reached the target, and every following value was rounded into the old column at exit 0 (a `VARCHAR` widen or an `ADD COLUMN` failed loudly at the next row instead).

## `sync` streams that forward no schema change: `SCHEMA-CHANGE-REFUSED`

Four kinds of stream forward no source DDL: `--schema-changes=refuse`, a multi-database stream (`--all-databases`, `--include-database`, `--map-database`; forwarding is single-database only), `--inject-shard-column` with `--no-coordinate-live-ddl`, and a trigger-CDC source (`postgres-trigger`, `sqlite-trigger`, `d1-trigger`) whatever `--schema-changes` says — its reader refuses source DDL itself, and a `postgres-trigger` stream's first-touch boundaries go through this check rather than being forwarded (see [the first-touch schema boundary](#the-first-touch-schema-boundary-and-trigger-source-live-ddl-coordination)). Since v0.156.10 every schema boundary such a stream sees — a DDL while it runs, and each table's first change after it starts, which covers a change made while it was stopped — is compared with the target table, column names and types, the same comparison as `RESUME-SCHEMA-DIVERGENCE` above:

- **They match:** nothing happens.
- **The target's column is wider than the source's and holds every value the source can send** (a larger temporal precision with the same zone kind, at least as many decimal integer and fraction digits, a longer `VARCHAR` or `CHAR`, `DOUBLE` for `FLOAT`, a wider integer of the same sign, an array whose element is wider — or, across families, a type that holds every value of the source's: `TEXT` for `VARCHAR` (also as an array element: `text[]` for `varchar(n)[]`), a `NUMERIC` with a non-negative scale and enough integer digits for an integer, a wider signed integer for an unsigned one, a superset of `ENUM` labels, a superset of `SET` labels in the same order, but never `CHAR` across families (nor `char(n)[]` against `text[]`, GC-44 F25) and never `jsonb` for `json` — the same direction rule the forward path uses to never narrow a target), **and nothing says the source narrowed it**: a WARN, and the stream goes on. This is the target changed ahead of the source — the drained model. The WARN says the source may also have narrowed the column with no earlier shape on record to show it; if so, the target's existing rows kept values the source's own `ALTER` converted.
- **The source narrowed the column** — the stream's own earlier shape of the table (its last boundary in this run, or its retained schema history) held the type the source's column can no longer hold every value of, e.g. a live `numeric(14,4)` → `numeric(12,2)`, `timestamp(6)` → `timestamp(0)`, `double precision` → `real`, `numeric(12,2)` → `integer`, a shorter `VARCHAR`, an `ENUM`/`SET` label removed: `SCHEMA-CHANGE-REFUSED`, the source type marked `narrowed from …`. The source's `ALTER` converted the rows it stores; the target's copies were never converted, so accepting the boundary would leave them different at exit 0. A boundary that lies *after* that earlier shape in the source's own position order (a MySQL or MariaDB binlog source) is judged whatever shape it shows — including a narrowing **back** to a shape the table held before, e.g. `DECIMAL(10,2)` widened to `(12,4)` by the drained model and then narrowed back to `(10,2)`, live or after a restart. One that lies *before* it is a replay and is never read as a narrowing. Narrow the target the same way (or re-copy the table) and restart. On a Postgres source, where the position order says nothing, see **AMBIGUOUS** below.
- **AMBIGUOUS — a replay or a source change (`AMBIGUOUS-SCHEMA-BOUNDARY`).** A narrowing or a `DROP COLUMN` (next bullet) whose only evidence is the stream's earlier shape, at a boundary the source's position order cannot place after that shape, is one of two things, and sluice cannot tell which: **(1) a replay** — a transaction re-delivered from its start after a restart or a retried transient error (ADR-0038), presenting the table as it was *before* a change the target already holds; or **(2) a change made on the source** that this stream has not applied. On a Postgres source this is every such refusal: its schema boundaries are anchored at LSN `0/0` and its schema history keeps one shape per table (GC-44 F23), so a part-applied transaction that wrote, ran `ADD COLUMN` and wrote again, retried after the target's connection dropped, replays its pre-`ALTER` relation against a history that already holds the post-`ALTER` shape (a type change in such a transaction is refused by the reader first, below, unless a start under `--schema-changes=forward` recorded it). Accepting it would be silent loss in case (2), so it refuses — but the usual remedy, applied in case (1), would destroy data (drop a column the source still has, round a column the source never narrowed). The refusal names both readings. First **compare the source's current definition of the table** (`\d` in psql, or `SHOW CREATE TABLE`) **with the target's**: if the source's column is narrower than the target's, or gone, it is (2) — apply the same change to the target and restart. A match is *consistent* with a replay but does not prove one: a column narrowed and widened back, or dropped and added again (GC-44 F22), on the source while the stream was stopped also leaves the two definitions matching, with the source's values rounded or replaced. So also confirm that nobody ran DDL on that table on the source while the stream was stopped. If both hold it is (1): change nothing on the target and start once with `--accept-unforwarded-schema-change=<fingerprint>`, the fingerprint the refusal prints. If you cannot rule the DDL out, re-copy the table (or the column's values) from the source instead, which is safe either way. The fingerprint names that table, those columns **and the position the stream resumed from**, so it accepts only the replay re-delivered from that position: once the stream has applied past it, a later boundary of the identical shape — a genuine rollback narrowing, say, with the flag left in a unit file — prints a different fingerprint and refuses, and within one process the value is dropped as soon as a retry resumes from a later position. It is the same flag that acknowledges `UNFORWARDED-SCHEMA-CHANGE`; nothing is recorded for it, a restart from the same position without it refuses again with the same fingerprint, and a fingerprint of any other boundary is not applied. If the stream persisted progress before reaching the boundary, the next refusal prints a new fingerprint: acknowledge that one. It works on every stream shape, including multi-database / multi-schema and `--inject-shard-column` with `--no-coordinate-live-ddl`. The refusal does not offer `--schema-changes=forward` here: its first boundary cannot prove the change on such a source either and would keep the target with a WARN. A boundary that also names a column the target lacks (a replayed `RENAME COLUMN`) cannot be acknowledged; its recovery is the pre-`ALTER` replay wedge's, below. On a Postgres source, a replayed transaction that changes the table's type again after the acknowledged boundary then stops at the reader — the same wedge.
- **A column the source replaced under the same name** — a Postgres column whose `attnum` changed between two boundaries of this run (a `DROP` + `ADD` of the same name and type, or a same-type swap through renames, inside one relation message): `SCHEMA-CHANGE-REFUSED`. The target kept the old column and its old values. Drop and re-add it on the target, copy the source's values into it, and restart. Seen within one run only (GC-44 F22). On a MySQL/MariaDB binlog source the same replacement refuses `COLUMN-IDENTITY-CHANGED` instead, at the `ALTER` itself and also when a resume replays it (see the MySQL-family section below).
- **The target has columns the source does not:** where the stream's earlier shape of the table (its last boundary, or its retained schema history) shows the source had the column, the source dropped it while the target kept it — `SCHEMA-CHANGE-REFUSED` naming the `DROP COLUMN` (the likely `RENAME COLUMN` when a column the target lacks comes with it); drop (or rename) it on the target and restart — **unless the refusal says `AMBIGUOUS-SCHEMA-BOUNDARY`**, in which case compare the definitions first, as above: on a Postgres source the replay of an `ADD COLUMN` transaction reads exactly like this, and dropping the column then destroys its values. With no earlier shape on record, a WARN (`target_only_columns`); the target keeps them and they receive no values from this stream.
- **Anything else** — a column the source has and the target lacks, or a type the target's column cannot hold (`DATETIME` → `DATETIME(6)` against a `timestamp(0)` target, `numeric(10,2)` → `numeric(10,4)`, a longer `VARCHAR` or `CHAR`, a sign change at the same width, a change across families the target's type does not hold): the stream ends with `SCHEMA-CHANGE-REFUSED`, naming every column with its source and target type, before the boundary is recorded or any row after it is applied.

The refusal is codeless and exits **1**. A `sync run` fleet leg that hits it is marked failed rather than restarted (the fleet config has no acknowledgement key: start an AMBIGUOUS leg once outside the fleet). Nothing is recorded and — but for an AMBIGUOUS refusal's replay case — nothing needs acknowledging: the check reads the target again on every start, so the next start refuses again until the target can hold what the source sends. To recover, apply the same change to the target table (`sluice sync stop --wait` first if the stream is still running), then start again with the same `--stream-id`. A single-database stream under `--schema-changes=refuse` can instead switch to `--schema-changes=forward`, which applies such changes itself; a multi-database stream and `--inject-shard-column` have no forward path, and the refusal does not offer one. **For a column the target lacks, the drained model is not a backfill:** an `ADD COLUMN` you run on the target fills the rows it already holds with that ALTER's DEFAULT (or NULL), and only rows changed after the restart carry the source's values — copy the column's existing values across yourself if they matter. (`--schema-changes=forward` does backfill a forwarded `ADD COLUMN`.)

**A `--type-override` column** is not compared by type — the override, not the source, decided what the target holds — but it is judged on width where its two types are in one comparable family. A source type that outgrows the override (`DECIMAL(10,2)` → `DECIMAL(14,4)` under an override of `numeric(12,2)`) refuses with `SCHEMA-CHANGE-REFUSED`, the column marked `(--type-override)`; widen the target column and restart. An override across families (a `json` override on a text column) is the override's own decision and passes. A deliberately narrowing override (`numeric` → `numeric(18,4)`, `bigint` → `int`, `varchar(255)` → `varchar(64)`) passes as long as the source's type is what it was at the table's last accepted boundary, its retained schema history, or — on the first start, the cold start — the source table the copy read; a source narrowing under an override refuses like any other. A warm resume of a table with neither a boundary nor a history row (no change to it since the cold start) still refuses a narrowing override, because the check cannot tell it from a widen made while the stream was stopped (GC-44 F12, whose fix writes the cold start's shape as a history version).

**Where the target cannot be compared** — an engine pair with no storage-shape rendering, or a table the target does not hold — the boundary is compared with the table's last accepted shape (the stream's own, or its retained schema history, which never records a refused boundary, so a refusal there repeats on the next start) and any structural change refuses; a table with neither passes its first boundary with a WARN. A multi-database namespace whose target catalog cannot be read stops the stream with the read error (restartable, not the marker), as a single-database stream does.

**On a Postgres source the reader refuses first.** On all three stream shapes (and under Shape A's coordinated router) the pgoutput reader keeps its own gate, exactly as through v0.156.9: an `ALTER COLUMN TYPE`, `DROP COLUMN` or `RENAME COLUMN` on a table whose relation it has already seen in this session stops the stream with `incompatible schema change mid-stream` and the drained-model hint, before this check sees it. This check judges what the reader lets through — each table's first relation after a start (a change made while the stream was stopped) and `ADD COLUMN`. `RENAME TABLE`, `DROP` + `CREATE` and a projection-invisible typmod change are refused at the reader in every mode, as before.

**The pre-`ALTER` replay wedge (GC-44 F24), a loud residual of that gate.** A source transaction that writes a table, changes a column's type (or drops or renames it) and writes the table again, on one of these streams, is refused at the reader on its first delivery, at the post-`ALTER` relation: nothing the transaction wrote after the change reaches the target (what it wrote before may already have — a source transaction can span target transactions — and those are the source's committed values, re-applied by the recovery). The drained model does not get it past: every restart re-delivers the transaction from its start, the pre-`ALTER` relation is cached first, and the post-`ALTER` one is refused again, whatever the target holds. Nothing is lost; the stream simply cannot pass that transaction. The reader's refusal says so itself: when the refused relation's transaction had already written the table, the message carries `PRE-ALTER-REPLAY-WEDGE` after the drained-model hint. After the drained model, a `DROP COLUMN` or `RENAME COLUMN` wedge's restart may instead stop at the check above, as `SCHEMA-CHANGE-REFUSED` naming the column the target now lacks (the replay's pre-change relation); its hint points here, because adding the column back does not pass it either. Recovery, after applying the change to the target, by change and stream shape — each pinned end to end, rows read back exact and the stream resuming in its own mode afterwards:

- **A column type widening on a single-database stream** under `--schema-changes=refuse`: start **once** with `--schema-changes=forward` (its reader hands the post-`ALTER` relation to the forward path, which finds the target already holding the type and applies the transaction's rows), then return to `--schema-changes=refuse` (`TestStreamer_RefuseMidTransactionAlter_PostgresToPostgres`, `TestStreamer_RefuseCrashReplayWiden_PostgresToPostgres`). This is the only change the forward start passes: a `DROP COLUMN` fails it (the forward path reads the replayed pre-`DROP` relation as an `ADD COLUMN` and refuses on the source `DEFAULT` it cannot find — even with the column added back on the target), and a `RENAME COLUMN` stops with `RESUME-SCHEMA-DIVERGENCE`.
- **Every other change on a single-database stream, and any change on a multi-database or multi-schema stream:** a re-copy. Drop the stream's replication slot first (`sluice slot drop sluice_slot --source-driver postgres --source "$SLUICE_SOURCE" --yes` — the literal name `sluice slot list` prints; a Postgres snapshot refuses to inherit an existing slot), then start once with `--restart-from-scratch`, which re-copies every table in scope from a fresh snapshot past that transaction (on a single-database stream it clears the in-scope target tables first) (`TestStreamer_WedgeRecovery_{SingleDatabase,MultiSchema}_PostgresToPostgres` for `DROP` and `RENAME`, `TestStreamer_MultiSchemaMidTransactionAlter_PostgresToPostgres` for widenings).
- **`--inject-shard-column`:** the target table holds the sibling shards' rows too, so `--restart-from-scratch` does not clear it, and the shard preflight refuses the re-copy while it holds this shard's rows. Delete **this shard's** rows from every in-scope target table (`DELETE FROM <table> WHERE <shard column> = '<this shard's value>'`), drop the slot, then start once with `--restart-from-scratch`; the sibling shards' rows stay (`TestStreamer_WedgeRecovery_ShapeA_PostgresToPostgres`, widen, `DROP` and `RENAME`, under `--no-coordinate-live-ddl`; the coordinated default reaches the same cold start and preflight — by code reading, not pinned). Never `--reset-target-data` here: it drops the whole table, every shard's rows with it. The wedge needs a restart that re-delivers the table's pre-`ALTER` relation before the post-`ALTER` one in the same session, which a transaction writing the table on both sides of the change always does; an `ALTER` run in its own transaction followed by writes, the drained model's own shape, recovers with a plain restart (pinned by `TestStreamer_PGToPG_DrainedModelRecovery`). The GC-44 F5 review relaxed the reader's gate on these streams to remove the wedge; that let a narrowing made inside one session reach a check that could not prove it on a Postgres source, and the gate was restored before release (the relaxation never shipped).

These streams write an ADR-0049 schema-history row per table at its first change after every start (the binlog first-touch boundary), and on a Postgres multi-schema stream for every selected schema: the history-growth class filed as GC-44 F12.

Through v0.156.9 none of the three refused anything the target could not hold: a type widen within its family — `DATETIME` → `DATETIME(6)` on MySQL, `numeric(10,2)` → `numeric(10,4)` on Postgres, measured on both and on a MySQL multi-database stream — left the target's column in place, and every following value was rounded into it at exit 0. A Postgres multi-schema stream was wider still: its reader produced schema boundaries only for the schema the source DSN names, so in every other selected schema even a change made while the stream ran went unchecked unless that table had already written a row in the same run. It now produces them for every selected schema.

## `sync`: a change to a table's column order refuses until the target holds it (`COLUMN-ORDER-CHANGED`, `COLUMN-ORDER-RECORD-UNAVAILABLE`)

A column swap (`RENAME COLUMN b TO c, RENAME COLUMN c TO b`), a rotation of three or more names, and a MySQL/MariaDB reorder (`MODIFY c … AFTER id` / `FIRST`) produce the same schema boundary: every column keeps its name and its type, and only the order the source declares them in changes. A reorder needs nothing on the target. A swap leaves every row the target already holds under the wrong column names. Since v0.158.0 a boundary across which two of a table's columns changed order stops the stream with **`COLUMN-ORDER-CHANGED`**, before the boundary is recorded or any row after it is applied. The message names the columns that changed order.

The boundary is accepted once the target's own column order has **moved** from the order sluice recorded for that table to the source's new one, which is what applying the same change there does. A target that merely already declares the new order proves nothing: a forwarded `ADD COLUMN x … AFTER id` lands at the end of the target table, and a later swap of `x` with its neighbour would then match it. The record lives in the control table `sluice_cdc_column_order`, one row per stream and table, holding the source's and the target's column order. It is written at the cold start and in the transaction of every accepted boundary that changes the source's column list.

The check runs on the live forward path, at each table's first boundary after a restart (so a restart after the refusal refuses again), under `--schema-changes=refuse` and on multi-database streams (where the message is `SCHEMA-CHANGE-REFUSED` and also carries `COLUMN-ORDER-CHANGED`), and under `--inject-shard-column`. On a stream that forwards no DDL from a Postgres source, the reader refuses a mid-session rename itself first (above). The refusal is codeless and exits **1**; a `sync run` fleet leg that hits it is marked failed rather than restarted. The remedy depends on what sluice can prove, and the message names one:

- **Apply the same change on the target, then restart with the same `--stream-id`:** the same `RENAME COLUMN` statements for a swap or rotation, or the same `MODIFY … AFTER/FIRST` for a reorder on a target that can reorder in place (MySQL, PlanetScale, Vitess and MariaDB targets declare the `ReorderColumns` capability; MySQL rebuilds the table to do it). Do not update values instead: the check reads the target's column order.
- **Re-copy:** `sluice sync start --reset-target-data --yes` with the stream's other flags unchanged, which drops every table of the stream on the target and copies it again from a fresh snapshot. On a Postgres source, drop the stream's replication slot with `sluice slot drop` first. This is the remedy for a reorder on a target that cannot reorder in place (Postgres), and the only one offered when sluice cannot prove the target moved. That happens when the table has no record, as on a stream started before v0.158.0 that has not yet accepted a boundary changing that table's column list, or a target that cannot keep records. It also happens when the recorded target order already disagreed with the source. `schema add-table` is deliberately not offered: it re-copies one table but keeps the stream's position, so rows written before the change would be replayed onto it under the old names.

**`COLUMN-ORDER-RECORD-UNAVAILABLE`** is a WARN at start: the target cannot keep the records, typically a PlanetScale safe-migrations branch or a Postgres role that cannot create tables. The stream runs, but every column-order change on it refuses with the re-copy remedy, even after you apply it on the target. To enable the records, have a role that can create tables run the `sluice_cdc_column_order` statement `sluice control-tables ddl --engine <target engine>` prints (on a safe-migrations branch, ship it with `sluice deploy-ddl`).

Chain restore, `backup verify` and `sync from-backup` refuse an incremental whose schema delta changed a table's column order (`SLUICE-E-BACKUP-SCHEMA-DELTA-UNSUPPORTED`), before applying anything of it. A chain whose incremental recorded a MySQL/MariaDB reorder or swap cannot be restored past it; take a fresh `backup full`. An `ENUM` label reorder is not a column-order change.

**Affected releases and what to check.** Through v0.157.2 a swap reached the target as no change, at exit 0, on every release of `sync start`; under `--inject-shard-column` since v0.73.0; and on chain restore and `sync from-backup` in every release that replays a schema delta. Rows written after the swap landed correctly, and an UPDATE carrying the whole row rewrote that row correctly, so the damage is every pre-swap row the source never touched again. **Checking for it:** `sluice verify --depth=sample` from a release after v0.158.0 compares columns by name, so a swapped target mismatches on every sampled row that predates the swap; v0.158.0 and older hashed each side's columns in its own declared order and read a swapped target as clean (VERIFY-SAMPLE-COLUMN-ORDER). A sample samples: when the pre-swap rows are a small fraction of the table, raise `--sample-rows-per-table`, or compare the affected columns' values by primary key between source and target yourself. Re-copy the table where they differ.

## MySQL-family binlog sources: decoding rows behind the head (`DEFERRED-SCHEMA-CHANGE`, `SLUICE-E-CDC-BINLOG-LOOKAHEAD-SHORT`)

A binlog reader that is behind the head reads events recorded under an older shape of a table. That covers every `backup incremental` window, every `backup stream` start, a warm-resumed or lagging `sync start`, and the CDC phase after a cold copy. Through v0.157.2 the reader decoded those events against the table's current definition from `information_schema` (Bug 301, CRITICAL). A change that kept the column count and every column's type family decoded cleanly with values under the wrong column names, at exit 0. Examples are a reorder of two same-type columns, a column-name swap, a drop-and-add of the same type, and an `ENUM` label reorder. The silent mis-decode existed since v0.1.0. From v0.113.0, changes across type families or column counts refused loudly with `SLUICE-E-CDC-SCHEMA-REPLAY-MISMATCH`, and only same-family ones stayed silent. The same mis-decode happened at the head for a schema change issued from another default database (`USE other; ALTER TABLE app.t …`).

Since v0.158.0 each row event is decoded by the shape it was recorded under, or refused before any row of the table is decoded:

- **`binlog_row_metadata=FULL` (recommended).** Every event carries its column names and sluice decodes by them. Add, drop, reorder, rename, an `ENUM` label reorder and two changes close together decode exactly. Set it with `SET PERSIST binlog_row_metadata = 'FULL'` on MySQL. MariaDB has no `SET PERSIST`: use `SET GLOBAL binlog_row_metadata = 'FULL'` and put `binlog_row_metadata = FULL` under `[mariadbd]` in its option file so a restart keeps it. Binlog written before the setting cannot be decoded by name, so take a new `backup full` or re-snapshot the sync (`--restart-from-scratch`) after setting it. `FULL` still refuses in these cases:
  - **A column the binlog cannot describe on its own.** This means a dropped signed `TINYINT` (the binlog does not record whether it was `TINYINT(1)`), a spatial column (its SRID), or a binary column on MariaDB (native `UUID`/`INET` or not).
  - **A schema change between the stream and the head, on a table with a GENERATED column or a MariaDB `UUID`/`INET4`/`INET6` column.** sluice proves such a table's shape as it does without names.
  - **`DEFERRED-SCHEMA-CHANGE`.** A row whose recorded shape includes a column dropped or retyped later in the binlog never becomes a schema boundary, so a change it carries would reach the target only after its rows. sluice holds such a row to the table's previous shape. It refuses with `DEFERRED-SCHEMA-CHANGE` if a shared column's type changed, or if the stream has no typed shape of the table to compare with. It refuses with `COLUMN-ORDER-CHANGED` if two shared columns reversed order. A character column's collation is compared too: the binlog records it as an ID, which sluice names from the source's own collation table (an ID it cannot name refuses, since the change it may carry cannot be checked). A key column's collation or character-set change met as the first schema boundary after a start, or on a `--schema-changes=refuse` stream, is judged against the source's own earlier shape of the table: forwarded under `--schema-changes=forward`, refused under `refuse` or when no earlier shape is on record, each refusal marked `KEY-COLLATION-CHANGED` (apply the same change on the target and restart). Whatever a boundary does not show, the applier checks on every upsert: one whose key matched an existing target row equal to it under the target's collation but different under the source's current collation refuses with `KEY-COLLATION-MERGE` before anything is written. If the target cannot express the source's collation for that comparison (the collation or character set does not exist there), the stream refuses at its first write to the table with `KEY-COLLATION-GUARD-UNSUPPORTED` rather than apply unguarded; create the collation on the target, or align the key column's collation on both sides (a MySQL 8 `utf8mb4_0900_*` key on a MariaDB target is compared under MariaDB's NO PAD `uca1400` collations, which exist from MariaDB 10.10; the supported MariaDB floor is 10.11, and below 10.10 the refusal names both the source's collation and the comparison collation it lacks) (on a Postgres source the collation is read from the catalog at each Relation message, since the change stream carries none). On a MySQL-family target the same marker has a second cause, which no collation change fixes: a functional unique-key part (`UNIQUE ((lower(k)))`) whose columns sluice cannot resolve, so it cannot tell which columns the key compares. The refusal names each such key part with its cause and remedy: the expression names a column sluice cannot find in the table (a non-ASCII column name the catalog's text of the expression does not spell as the table does; recreate the key over columns named in ASCII), it holds a string literal sluice cannot scan to its end (write the literal plainly, or move the expression into a stored generated column and key that), or it reads generated columns built on generated columns more than eight deep (key a shallower expression). Excluding the table is the alternative in every case, and nothing of the table is written before the refusal. A VStream source carries no collation at all and is not covered (KEY-COLLATION-FIRST-BOUNDARY in `docs/dev/audit-backlog.md`). The copy phase carries the same check: a chunked or resumed copy, `schema add-table`, the VStream COPY and restore all write through an upsert that refuses `KEY-COLLATION-MERGE` (or `KEY-COLLATION-GUARD-UNSUPPORTED`) on the same keys, because the two refused rows are two rows of the source — give the target key the collation the message names and run the copy again, or exclude the table. On a MySQL target's plain bulk load, a batched INSERT retried after a transient that meets a duplicate key on such a table is re-sent as that guarded upsert: the batch's own rows, landed by the attempt whose acknowledgement was lost, converge, and a merge refuses `KEY-COLLATION-MERGE`. LOAD DATA has no upsert form, so a replayed segment that skipped rows on such a table refuses `KEY-COLLATION-REPLAY-AMBIGUOUS` instead of counting the skips as landed; run the copy again, and a genuine merge then surfaces as a duplicate key on the first attempt (KEY-COLLATION-ROWWRITER).
- **`MINIMAL` (MySQL's default) or `NO_LOG` (MariaDB's default).** sluice proves the catalog shape holds at the stream's position by reading the schema changes logged between the two with `SHOW BINLOG EVENTS`. It refuses a table one of them reshapes. **Behind the head, these now refuse where they used to decode:** any schema change of a streamed table other than an index, a table option, a `TRUNCATE` or an in-place redefinition. That includes an `ENUM`/`SET` label append via `MODIFY`, the `RENAME TABLE` cutover of gh-ost, pt-online-schema-change and LHM (even for an index-only migration), a no-op `CREATE TABLE IF NOT EXISTS` of a streamed table, and `CONVERT TO CHARACTER SET` on a table with `ENUM`/`SET` columns. An in-place `MODIFY` of a `YEAR` column refuses under `MINIMAL`, and a `VARCHAR` widen refuses under MariaDB's `NO_LOG`. The remedy for each is `FULL` metadata.

**`COLUMN-IDENTITY-CHANGED` (any metadata setting, at the head or behind it).** Some schema changes leave a column name in place holding a different column: `DROP COLUMN c, ADD COLUMN c` of the same type, `RENAME COLUMN c TO tmp, ADD COLUMN c`, `DROP COLUMN b, RENAME COLUMN c TO b`, or a rename swap followed by a `MODIFY … AFTER` that restores the old order before the table's next row. MySQL columns have no stable id, so no comparison of the table's shape can see these — not even under `FULL` — and the target's existing rows would keep the old column's values at exit 0. sluice reads the `ALTER TABLE` statements in the binlog and refuses at the statement itself, so a restart before the table's next row cannot skip it. A plain rename swap or rotation in one statement is left to `COLUMN-ORDER-CHANGED`, which the operator can satisfy by applying the same renames on the target; a swap spelled as three renames through a temporary name refuses here at its second statement. The remedy is a re-copy: `sync start --reset-target-data --yes` with the stream's other flags unchanged, or a fresh `backup full`. MariaDB's `IF EXISTS` / `IF NOT EXISTS` on a column clause is read as if the clause took effect, so a no-op `DROP COLUMN IF EXISTS c, ADD COLUMN c` refuses too. A statement sluice cannot parse at all (for example one adding a MariaDB `UUID` column) refuses, marked `COLUMN-IDENTITY-UNREAD`, when it spells `DROP`, `CHANGE` or `RENAME` or follows a statement that dropped or renamed a column of the same table; otherwise it is logged at WARN with that marker and the stream continues.

**A column's collation changed behind the head (MySQL and MariaDB binlog sources, `MINIMAL` or `FULL`).** A stream that reads a collation change after the fact — changed and changed back (`MODIFY k … COLLATE utf8mb4_bin`, a row `'A'` beside `'a'`, then `MODIFY k … COLLATE utf8mb4_0900_ai_ci`), or loosened (`_bin` → `_ci` after such a pair moved apart) — sees the catalog's current collation, but each row event's TABLE_MAP still records the collation the row was written under. sluice decodes and reports each row under that recorded collation, so the schema boundary at the change carries the shape the rows were written under: a sync forwards it before them (or refuses it under `--schema-changes=refuse`, marked `KEY-COLLATION-CHANGED`), and a backup records it. A backup chain records each schema version its window observed, and chain restore applies each just before the first change recorded at or after it, starting from the shape the previous backup recorded for any table whose key collation the window changes, so the rows are guarded under the collation they were written under and a merge refuses `KEY-COLLATION-MERGE` — whose message then leads with the remedy: take a fresh full backup after the key change and restore it into an empty target, because the incremental changes a key collation inside its own window and every restore of the chain re-applies the change ahead of the same rows (`sluice restore` does not resume, so altering the target key and re-running does not converge either). The same refusal, marked `KEY-COLLATION-DELTA-FAILED` and with the same remedy, replaces the target's raw error when the target refuses the key change itself: an incremental's schema change is applied ahead of its rows, so a key loosened in a later incremental than the `'A'` and `'a'` it equates, after a row of that incremental moved one of them away, meets both values on the target (MySQL's `Error 1062 Duplicate entry`; a scheduled `backup incremental` splits a change from its revert this way). Nothing is merged. A MySQL or MariaDB backup records its tables with no database name while its change rows name the database; the shape a window starts from takes the name its rows carry. A row naming no database at all — the `ADD COLUMN` fill a backup window records, one update per row by primary key, which names what the manifest names — neither sets nor contradicts it. A row of that table naming a different database than the shape was filed under refuses `KEY-COLLATION-VERSION-NAMESPACE` (the check on the premise that a single-database backup's rows name one database). A restore by v0.159.2 armed nothing when no row of the table followed the loosening inside the window and merged at exit 0 (Bug 306). And a chain records only what its capture saw: a key changed and changed back inside a window that `backup incremental` on v0.159.1 or earlier read after the revert left no trace of the intermediate collation, so no release can refuse it; check such a restore against the source and take a fresh full backup. Chain restore, `sync from-backup` and `backup verify` log a WARN marked `KEY-COLLATION-PRE0159-2-UNVERIFIABLE` for every MySQL-family incremental captured before v0.159.2 that records a character column in a primary or unique key, naming the table and columns, so the check is not left to memory: run `sluice verify` against the source for those tables. `sync from-backup` places no version between a window's changes and instead refuses any window that changes a key column's collation with `KEY-COLLATION-HISTORY-UNORDERED` (as does a restore that cannot order the versions against the changes, such as a `postgres-trigger` chain read by a binary older than v0.161.0, which gave that engine a position orderer). Neither restarting nor changing the target key converges; take a new full backup after the key change, then run `sluice sync from-backup run --reset-target-data --yes` against the new chain. A collation change the binlog carries no statement for (a DDL run with `sql_log_bin=0`) refuses `DEFERRED-SCHEMA-CHANGE`, marked `COLLATION-CHANGE-UNANNOUNCED` (compared from the first row of the table the stream itself decoded: where a backup window's first row of a table differs from the shape its parent recorded, which the parent read when its window closed, that row's shape becomes a schema version at the window's start instead), and a row whose collation ID cannot be named, on any character column, because `information_schema.COLLATIONS` could not be read or does not list the ID, refuses `COLLATION-NAMES-UNAVAILABLE`, which a restart retries. Not covered: VStream sources, whose events carry no collation, MariaDB's default `binlog_row_metadata=NO_LOG` (an in-place column change ahead of the stream refuses there instead), and the trigger-CDC sources.

**A key column's collation changed behind the head (Postgres sources).** pgoutput carries no collation, so the reader reads each column's collation from the catalog when it meets the table's relation message, which is the collation in force now, not necessarily the one the rows were written under. A key column's catalog row is rewritten when the column is altered. When that row is newer than the transaction being decoded, or was written by that same transaction (whose DDL may have run after its rows), and its collation is nondeterministic (an ICU case- or accent-insensitive collation), the reader records the collation as not established for those rows, and both appliers then compare that key byte for byte: an incoming row whose key matches a byte-different existing key refuses `KEY-COLLATION-MERGE` instead of merging onto it. A byte comparison is stricter than the collation's, so the cost is loud: a conflict the collation would have equated also refuses, and the same happens after any other change to that column (a rename, `SET NOT NULL`) made after the rows being replayed. A backup window keeps one schema version per table for a Postgres source, so a later not-established version makes the whole window compare that key byte for byte. `sync from-backup`, whose applier compares nothing from a window's versions, refuses such a window with `KEY-COLLATION-HISTORY-UNORDERED`. Not covered: a DDL whose transaction was assigned its id before the replayed one and committed after it, which reads as older, and a table or key column renamed or dropped after the replayed rows, which the catalog lookup misses (KEY-COLLATION-PG-LOOSENED-REPLAY in `docs/dev/audit-backlog.md`). A backup window (`backup stream` or `backup incremental`) that records two shapes of a table that disagree on a key column's collation is refused at capture with `KEY-COLLATION-SAME-ANCHOR`, because a Postgres change stream anchors every schema version at one position and the backup could keep only one of them: take a fresh full backup after the change and continue the chain from it. That includes a forward-only key collation change in a window that already holds a row of the table, unless the first shape the window recorded was already not established, which compares the key byte for byte and needs no refusal.

**Grants.** The look-ahead's `SHOW BINLOG EVENTS` needs `REPLICATION SLAVE` on MySQL, which a CDC account already holds. On MariaDB 10.5+ it needs `BINLOG MONITOR`, which `REPLICATION CLIENT` includes there. An account without it is refused with `SLUICE-E-CDC-REPLICATION-PERMISSION`, naming `GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO <account>`. Managed providers are expected to allow it for an account that can stream: **UNVERIFIED PREMISE** — no measurement on RDS, Aurora, Cloud SQL or Azure is recorded.

**`SLUICE-E-CDC-BINLOG-LOOKAHEAD-SHORT`.** The look-ahead could not read the binlog up to the position the source reported with its catalog read for about ten seconds. It never marks binlog it did not read as checked. Retry; if it recurs, check the source's `sync_binlog` and `binlog_group_commit_sync_delay`.

**Cost.** The look-ahead reads the binlog between the stream and the head at most once per window, and nothing for a stream at the head. Under `FULL` a rows event needs no scan, except for the tables named above.

**What sluice cannot check.** A MySQL-family backup chain or sync target captured by an affected release may hold earlier rows with values under the wrong columns or labels. This applies across a column reorder, a column-name swap or an `ENUM` label reorder made while the reader was behind the head, or at the head when the change came from a different default database. `backup verify` (both depths) and restore cannot detect it, because the chain is internally consistent. `sluice verify --depth=sample` hashes a sample of rows per table, and Bug 301 alters only rows written before the schema change, typically far fewer than a sample catches. Rebuild such a chain from a new `backup full`, and re-snapshot such a target.

## MySQL-family sources: resume signals (`POSITION-MODE`, `UNVERIFIED-INSTANCE-IDENTITY`, `SOURCE-INSTANCE-IDENTITY-CHANGED`)

A warm resume — `sync start` with an existing `--stream-id`, `backup incremental`, chain replay, the backup→CDC handoff — asks the source two questions before it opens the stream: *has the source purged anything this position still needs?* (the retention check; a "no" is the position-invalid refusal that takes the auto-resnapshot route, or a hard stop under `--no-auto-resnapshot`) and, since v0.137.2/v0.138.0, *did this source ever produce this position at all?* (the identity/lineage check — a refusal, but **not** always the same route: a verdict of *different lineage* is TERMINAL and does not auto-resnapshot — since v0.146.0 for the MySQL file/pos `@@server_uuid` mismatch, since v0.148.2 for the GTID, MariaDB and VStream arms (the `FOREIGN-LINEAGE-REFUSED` section above) — because a different lineage means a different server rather than the same server having advanced; only a verdict of *this same server has moved past the position* still takes the auto-resnapshot route). The second question exists because a replaced, restored, reset or rebuilt instance answers the first one with "nothing purged" and then streams its own unrelated history as the continuation, at exit 0. How it is asked depends on the position's mode, and two grep-stable log markers tell you which check a resume is running without.

Which arm a position uses is decided by the source, not by the command: since v0.139.0 EVERY capture door — the backup doors, the from-now open, and both `sync` cold-start snapshot openers — records a **GTID** position when the source has `gtid_mode=ON`, and a file/offset one (stamped with the server's `server_uuid`) when it does not. Before v0.139.0 the two sync openers always recorded file/offset, so a `sync` chain on a GTID-mode source could not follow a failover to a promoted replica: the identity check refused the new server and the stream fell through to a fresh cold start. Positions written by earlier releases keep resuming on the arm they were written with, so an upgrade needs nothing; the change takes effect at the next cold start.

- **`POSITION-MODE`** (INFO, vanilla `mysql` binlog sources only — MariaDB is always in GTID mode and the `planetscale`/`vitess` flavors resume on VStream positions, so neither has a choice to advise about). Logged when the source has `gtid_mode=OFF`, MySQL 8's shipped default: sluice then resumes from a binlog **file and offset**. That is supported and correct, and it is the weaker of the two resume modes — binlog filenames are instance-local, so if the source is ever replaced, rebuilt or failed over onto a different server, the position's meaning does not carry over. sluice stamps the source's `@@server_uuid` onto such positions and refuses a mismatch, whereas a GTID set is instance-bound by construction and needs no stamp. It is an INFO line rather than a WARN because nothing is wrong with the configuration; it exists so an operator can *know* which arm they are on. Enabling GTID mode on the source is the stronger configuration if you have the choice (PlanetScale imports require it anyway).
- **`UNVERIFIED-INSTANCE-IDENTITY`** (WARN). The resume is proceeding **without** the identity/lineage check, so a replaced or rebuilt source would not be caught on this resume. It has five sources, and each names its own remedy:
  - a MySQL file/pos position with no `server_uuid` — captured before v0.137.2 stamped it, or its capture could not read the value. The resume falls back to the filename check alone. One fresh full backup (or cold start) moves the chain onto the identity check; that population cannot grow, since every capture door now stamps.
  - a MySQL file/pos position that *has* a `server_uuid`, but the source's `@@server_uuid` could not be read on this resume. That is a probe failure on a refusal-gating check, allowed through so a transient read does not force a full re-snapshot; if it persists, treat it as a real finding.
  - a MariaDB position with no lineage anchor (persisted by v0.137.4 or earlier). MariaDB GTIDs carry no instance identity, so a rebuilt source whose history reads the same GTIDs would not be caught; the domain check (every domain in the resume set must appear in `@@gtid_binlog_state`) still runs. One fresh full backup or cold start moves the chain onto the anchor check.
  - a MariaDB position whose lineage anchor's binlog file has been purged by retention. The oldest retained file above the anchor starts at a state that covers the anchor's set, which is what a purge on the same lineage looks like, and also what a rebuilt instance whose numbering rotated past the anchor and whose GTIDs collide at exactly that state looks like; MariaDB has no second witness to tell them apart, so sluice proceeds and says so (v0.138.0 logged this as INFO "lineage confirmed", which overclaimed — Bug 261). If the source was rebuilt or replaced, stop and take a fresh full backup or cold start.
  - a PlanetScale/Vitess resume whose per-shard lineage probe (`GTID_SUBSET(<resume>, @@global.gtid_executed)`) failed. The pre-flight proceeds to the retention check; a replaced keyspace would not be caught on this resume, and a persistent failure is a real finding.

**What refuses TERMINALLY, with the `SOURCE-INSTANCE-IDENTITY-CHANGED` marker, and does NOT auto-resnapshot** (v0.146.0): a MySQL file/pos `@@server_uuid` mismatch. The instance answering the DSN is not the one the position was captured from, and unlike a purge that is a *different server* — one sluice cannot tell apart from a stale connection string, a load-balanced or DNS-failover endpoint, or a node restored from the wrong backup. Auto-recovering would drop the target's tables and re-copy from it. The remedy depends on which command you ran, and the refusal spells all three out: a warm `sync start` takes `--restart-from-scratch`; `sync start --position-from-manifest` needs a manifest captured from *this* instance, or a fresh `backup full` to make one (`--restart-from-scratch` is rejected alongside `--position-from-manifest`, so it is not the answer there); `backup incremental` needs a fresh `backup full`.

What refuses, with no marker, and takes the position-invalid (auto-resnapshot) route — the verdicts that mean *the same source has moved past the position*: a MySQL GTID resume set not contained in the source's `@@global.gtid_executed` because the executed set is *empty* (a `RESET MASTER`), **only when the server's `@@server_uuid` is one the resume set names** (since v0.153.2 — and this is an identity check, not a safety one: an in-place same-server restore that seeds no `gtid_purged`, `RESET MASTER` then the dump loaded on the same box, presents exactly this shape and still re-copies, see the `FOREIGN-LINEAGE-REFUSED` section); a VStream errant GTID (the position shares UUIDs with the shard and names one it never executed — the remedy is on the source, and it stays on this route). What refuses TERMINALLY as a *different lineage* — `SLUICE-E-CDC-LINEAGE-MISMATCH` from the engine, `FOREIGN-LINEAGE-REFUSED` from the pipeline, since v0.148.2: a MySQL GTID resume set sharing no source UUID with the executed set, and, since v0.153.2, an empty or behind executed set on a server whose `@@server_uuid` the position has never named (the rebuilt-node shape — a restore followed by `RESET MASTER`, or a `gtid_purged` seeded from an older backup; if it is a lagging replica behind a failover endpoint instead, wait for it to catch up and retry); since the 2026-09-15 operator decision, an executed set *behind* the resume set under the server's **own** `@@server_uuid` (every source UUID present, sequence numbers lower — a primary rolled back past the position, an in-place restore seeding `gtid_purged` from an older backup, or a hole in its set: the target is ahead of the source, and the message says so); a MariaDB anchor that answers a different GTID state, or no event at the anchor with no retained file above it that could have purged it on the same lineage, and a resume domain absent from a `@@gtid_binlog_state` — non-empty, or, since the same decision, *empty* (a same-server reset and a rebuilt node are indistinguishable there, and the message names both); a VStream shard sharing no source UUID with the position (a shard that is merely behind is replica lag, logged at INFO, and left to vtgate's tablet picker). Lineage is checked before retention on every arm, so a foreign source that has also purged binlogs is diagnosed as foreign rather than with a recovery hint that does not apply. The markers above are MySQL-family; **Postgres reaches the same terminal verdict by its own route** — the `(systemid, timeline)` pin of [ADR-0051](../adr/adr-0051-pg-cdc-source-identity-pinning.md), compared against `IDENTIFY_SYSTEM` at every resume, which since v0.154.0 refuses under `FOREIGN-LINEAGE-REFUSED` instead of falling through to the automatic re-copy. It is a different mechanism, not a different policy.

## MySQL binlog sources: writes that never enter the binlog

sluice's MySQL/MariaDB CDC **is** the binlog — a write the server never logs cannot reach the target, and nothing errors, because there is no event to mis-handle. Most members of this class are refused loudly at CDC start: `binlog_format` ≠ ROW and partial row images (`SLUICE-E-CDC-BINLOG-FORMAT-NOT-ROW`, `SLUICE-E-CDC-ROW-IMAGE-PARTIAL`), a source that is itself a replica with `log_replica_updates=OFF` and a replication channel that is running or connecting (`SLUICE-E-CDC-REPLICA-NO-LOG-UPDATES` — a server whose every channel has both its IO and SQL threads stopped, the state of a primary promoted after a failover, is accepted with an INFO marked `REPLICA-CHANNELS-STOPPED`; replication started on it after the stream opens is not seen until the next CDC open re-runs the check), server-side `--binlog-ignore-db`/`--binlog-do-db` filters covering a synced database (`SLUICE-E-CDC-BINLOG-DB-FILTERED`), and a session-level `binlog_format=STATEMENT` override's DML is stopped mid-stream by a dispatch belt (`SLUICE-E-CDC-STATEMENT-DML`). Two shapes remain that sluice **cannot detect at all**, and they are documented here rather than implied covered:

- **`SET SESSION sql_log_bin=0`.** A session holding `SUPER`/`SYSTEM_VARIABLES_ADMIN` can opt its own writes out of the binlog entirely — DBA hotfixes, ops scripts, `mysqldump --set-gtid-purged` restores. Ground-truthed on real `mysql:8.0.46` (2026-08-26): the rows are SQL-visible on the source, the binlog position does not move, **no GTID is allocated**, and afterwards there is zero server-side trace — no event, no counter, no position delta — so no preflight, belt, or resume check can ever see it. Writes that landed before the cold-copy snapshot are carried (they are SQL-visible); anything written this way during the live tail is silently absent from the target. The only *point-in-time* probe is a currently-connected session's variable (`SELECT t.PROCESSLIST_ID, v.VARIABLE_VALUE FROM performance_schema.variables_by_thread v JOIN performance_schema.threads t USING (THREAD_ID) WHERE v.VARIABLE_NAME='sql_log_bin'`), which cannot see past or future sessions. That lookup works on **MySQL only** (where it requires `performance_schema=ON`, the default). On **MariaDB the query hard-errors regardless of the setting** — `variables_by_thread` is not in MariaDB's performance_schema table set at all (verified live on 11.4: error 1146 with the setting ON and OFF alike), so enabling `performance_schema` cannot fix it; on MariaDB find the writer by interrogating candidate sessions from `SHOW PROCESSLIST` (the same precondition applies to `SLUICE-E-CDC-STATEMENT-DML`'s session-hunt remedy, which uses the same tables). **`sluice verify` is the only independent after-the-fact catch** — it compares real rows, not binlog state. If your operational practice includes `sql_log_bin=0` sessions on the source, schedule `verify` runs and treat the source's primary as the write path during a sync.
- **Vitess/PlanetScale: tablet-side writes with binlogs disabled.** On **self-hosted** Vitess the same class is reachable via `vtctldclient ExecuteFetchAsDBA --disable-binlogs` (the flag wraps the statement in `SET sql_log_bin = OFF` on the tablet) or any direct-mysqld session. Reproduced on a real Vitess v24 cluster (2026-08-26): the row lands on the primary, VStream — which re-serves the tablet's binlog — never carries it, and the stream stays healthy around the hole. Worse, MySQL replication inside the shard rides the same binlog, so the hidden write also splits primary/replica state — a later cold copy or re-snapshot from a REPLICA tablet (sluice's default) misses the row even in SQL, and `verify` must read `@primary` to see it on the source at all. PlanetScale customers have neither `vtctld` nor mysqld access, so on the managed flavor this class is unreachable by customers. As with `sql_log_bin=0`, there is no after-the-fact server-side trace; `sluice verify` (against the primary) is the independent catch.

One further member of this class **is** detected, because the evidence lives in the schema rather than in a session: **foreign keys with referential actions** (`ON DELETE CASCADE`, `ON UPDATE CASCADE`, `ON DELETE SET NULL`, `SET DEFAULT`). When a parent-key `DELETE`/`UPDATE` cascades, MySQL writes only the **parent table's** events to the binlog and expects the replica to re-run the cascade locally through its own FK definitions — and sluice's applier deliberately suppresses exactly that re-cascade (target-side FK enforcement is disabled so out-of-order apply cannot poison-pill, the Bug 164 fix), so the target's child rows silently survive or keep stale FK values while the sync exits 0. This applies to **both** MySQL lanes (binlog and VStream — the vstreamer re-serves the tablet's binlog, where the cascaded rows are equally absent) and to every target except an unprivileged Postgres, where enforcement stays on and the translated FK re-runs the cascade itself. Because the FK declarations are visible in `information_schema`, every CDC open censuses the in-scope tables and logs a `FK-REFERENTIAL-ACTION-CAPTURE-GAP` warning naming each affected constraint. Plain FKs and `RESTRICT`/`NO ACTION` actions cause no invisible writes and never trigger it. If the warning names your schema: run `sluice verify` after parent-key deletes/updates, or replace the referential actions with application-level deletes for the sync's duration. Re-enabling target-side FK enforcement is **not** the remedy — it re-opens the ordering failures the suppression exists to prevent.

## A tuning flag the run cannot use is named, not dropped (`INERT-FLAG`)

Many of sluice's tuning flags govern one engine family's path and say so in their `--help` ("PG source only", "Inert on MySQL/VStream sources", "MySQL/PlanetScale/Vitess target only"). Passing such a flag on a run whose engines never read it used to be accepted silently: the flag parsed, nothing consumed it, and the operator who set `--bulk-parallelism=8` to speed up a Vitess cold copy got a serial copy and no signal. Since ADR-0118 (and its GC-19 generalization) every such case logs one WARN carrying the **`INERT-FLAG`** marker, naming the flag, the command, the engine it is inert on and why — with the knob that applies instead where one exists:

```
INERT-FLAG: --bulk-parallelism has no effect on `sync start` with a vitess source — it governs the ADR-0079 FAST cold-start, which needs a source that can mint snapshot-pinned readers (postgres); this source's cold-copy is engine-internal — use --copy-fanout-degree / --vstream-copy-table-parallelism / --copy-table-parallelism to tune it
```

The WARN fires on the flag's **spelling** — an explicitly passed flag at its default value still warns, an unset one never does — and the decision is derived from the engine's declared capabilities rather than its name, so the trigger-CDC (`postgres-trigger` / `sqlite-trigger` / `d1-trigger`), `mydumper` and flat-file sources are covered exactly like the MySQL family. Nothing about the run changes: the flag stays inert, the WARN is the loud version of what was already happening. The covered flags are the ADR-0079 fast-cold-start knobs on `sync start` (`--bulk-parallelism`, `--table-parallelism`, `--bulk-parallel-min-rows`, `--bulk-batch-size`, `--raw-copy-format`), the native-MySQL read axis (`--copy-table-parallelism`, `--no-intra-table-stealing`), the VStream knobs (`--vstream-copy-table-parallelism`, `--vstream-preserve-skew`, `--strict-float`, `--no-float-exact-reread`, and `backup full`'s `--float-reread-max-rows`), `--auto-prune-change-log` off a trigger-CDC source, the target-side `--index-build-mem` / `--index-build-parallelism` / `--max-target-connections` / `--reap-stale-backends` on `migrate` and `sync start`, `--control-keyspace` on every command that takes it (including a fleet `control-keyspace:` key under `sync run`), `sync health`'s and `diagnose`'s Postgres-slot flags, `cutover --target-schema`, and the `trigger` commands' `--schema`. A flag that already refuses loudly on the wrong engine (`--infer-types`, `--target-schema` on a flat-namespace target, `--planetscale-raise-query-timeout`) keeps its refusal and does not additionally warn.

## Re-copying onto a target that already holds data

`sync start --restart-from-scratch` and the automatic re-snapshot (which fires
when a stream's persisted position has aged out of the source's retention
window) both re-copy onto a target that already holds the previous copy. What
happens to the rows already there depends on whether the source's snapshot
reader is **idempotent**:

- A **non-idempotent** reader's copy is a plain `INSERT`, so the in-scope
  target tables are cleared first — they always were, or the copy would
  dup-key. This is every source except the one below.
- The **idempotent** reader — the VStream snapshot, which backs the
  **PlanetScale** and **Vitess** flavors — upserts, so its target used to be
  left in place. From v0.109.0 an explicit `--restart-from-scratch` clears it
  there too, because an upsert converges on rows that still exist at the source
  and cannot remove one the source deleted. The **automatic** re-snapshot still
  merges, by design, and warns about exactly that.

A native MySQL binlog snapshot is **not** idempotent, so a plain `mysql` source
is on the cleared side even though it lives in the same engine package as the
VStream reader.

## A crash in the middle of a source transaction: exactly-once apply marks (`APPLY-MARK-MISMATCH`, `APPLY-MARKS-UNAVAILABLE`, `APPLY-MARK-UNTRUSTED`)

A restart re-delivers everything after the stream's persisted position, and the position only ever advances at a source transaction's commit. When a process dies partway through applying a source transaction, the target already holds part of that transaction, and the restart replays the whole transaction on top of it. Most changes replay harmlessly (sluice's apply is an idempotent upsert), but a transaction that frees a unique value and reuses it, swaps one through a temporary, or changes a primary key does not: before ADR-0190 the replay collided (`23505` / `Error 1062`) and every restart stopped on the same collision, recoverable only with `--restart-from-scratch`.

sluice now writes an **apply mark** for every change whose replay is not idempotent — except, by default, the changes the concurrent lanes apply to a table with a secondary unique index, which need `--exactly-once-lanes` (see "Which apply paths" below) — in the SAME target transaction as the change's own row, into the control table `sluice_cdc_apply_marks`. A mark names the source transaction and the change's position within it. On a restart, every change of an interrupted transaction first consults the marks for its keys, and a change a mark proves already landed is skipped — so the restart converges exactly and the position moves on. On a target that commits a transaction atomically, a mark and the row it vouches for commit together or not at all, so the target can never hold one without the other. A PlanetScale or Vitess target whose control tables live in a sidecar keyspace (`--control-keyspace`, or the unsharded keyspace sluice auto-detects on a sharded target) does not: vtgate commits the rows' shard and the control keyspace separately, with no two-phase commit. sluice sends every row before any control-table write, so a torn commit leaves rows without their marks and the position behind them, never marks or a position past rows that did not land. The restart then re-applies those rows with no mark to skip them, so there the marked classes are at-least-once or loud: a unique collision stops the stream, and a keyless table can gain a duplicate row. A change is never skipped silently (ADR-0190, GC-41 (c) note).

**Which changes write a mark.** A change to a table with a UNIQUE index or constraint besides its primary key; a change that alters a primary key (it marks the old key and the new one); and every change to a table with no key at all. A table with only a primary key writes no marks — its changes replay idempotently — so an ordinary primary-key workload pays nothing. Keyless tables are the one place this changes what you can expect beyond the collision: a keyless table's rows used to duplicate when a transaction was replayed after a crash (at-least-once, ADR-0089); on the covered sources, and on a target that commits atomically, they now land exactly once. With a sidecar control keyspace they remain at-least-once across a torn commit (see above).

**Which sources are covered.** The marks rely on the source's reader giving every change a stable identity that a re-delivery reproduces exactly. The MySQL and MariaDB binlog readers do (the transaction's own GTID, or in file/position mode the server's `server_uuid`, binlog file and the transaction's start offset), and so does the Postgres logical-replication reader (the transaction's commit LSN). The PlanetScale and Vitess VStream reader does too: each shard's transaction is named by its keyspace, its shard and that shard's GTID before the transaction — which vtgate re-delivers identically on a resume, verified against a real multi-shard Vitess — and the reader now passes each shard transaction's boundaries to the applier, so a VStream stream also saves its position at transaction commits. Rows VStream sends while it copies a table (its COPY phase) carry no identity, and neither do the rows of two shard transactions that arrive interleaved (vtgate has not been seen to do this; sluice WARNs once if it does, and those rows replay as they did before ADR-0190). **On a sharded keyspace, exactly-once across a crash is best-effort:** a restart resumes every shard at once and may deliver another shard's transaction before the interrupted one, and marks are trusted only for the first transaction a restart delivers, so the interrupted transaction's marks are then set aside with `APPLY-MARK-UNTRUSTED` and it replays as before ADR-0190 — a loud collision at worst, never a silent skip. An unsharded (single-shard) keyspace is not affected: its restart has only one shard to deliver from. The trigger-CDC sources (`postgres-trigger`, `sqlite-trigger`, `d1-trigger`) name every change by its change-log id, stamped with a value the change log stores with the row and a later capture cannot repeat — the capturing transaction's id on `postgres-trigger`, the row's `captured_at` on `sqlite-trigger` / `d1-trigger` — so a change-log id sequence that is reset or restarted cannot re-issue a name an old mark still holds. The change log records no transaction boundaries sluice can use, so each change is its own transaction. On the serial paths a trigger stream saves its position with every batch, so a restart never replays an applied change and no mark is needed; on the lane path the marks cover the changes a lane committed ahead of the position save.

<!-- apply-identity-engine-packages: mysql, pgtrigger, postgres, sqlite-trigger -->

The marker above lists the engine PACKAGES whose readers stamp an identity, and `internal/docsync` holds it to the code — together with a roster of the files allowed to stamp one. The `mysql` package holds the binlog reader and the VStream reader; `sqlite-trigger` also serves the `d1-trigger` engine.

**Which apply paths — and `--exactly-once-lanes`.** By default: the per-change path (`--apply-batch-size 1`), the serial batched path (`--apply-concurrency 1`), and the concurrent lane path's BARRIER — the changes the lanes hand to the coordinator one at a time: every change to a table with no key, and every primary-key change. The changes the lanes themselves apply to a table with a secondary unique index are marked only with **`sync start --exactly-once-lanes`** (fleet key `exactly-once-lanes: true`), because marking them safely needs one extra step: before the first such change of a source transaction reaches a lane, sluice drains the lanes and saves the position at the start of that transaction, so a lane never writes a transaction's marks while an earlier transaction's position save is still pending (ADR-0190 amendment A). Since v0.156.8 (ADR-0190 amendment D), that position is written inside the lane's own target transaction — the one that commits the transaction's first marked change and its mark — rather than as a separate synchronous write, so the cost is one lane drain per source transaction touching such a table, and the marks and the position become durable in one commit. The drain still serialises those transactions at their start, so on a workload made of them the flag runs at roughly `--apply-concurrency 1`'s rate rather than the lanes' (§D.9 of ADR-0190 has the measurement), and it stays off by default (ADR-0190 amendments C and D). **Without the flag**, a crash in the middle of a source transaction that touches a secondary-unique table on the lane path can still stop every restart on the unique collision, exactly as before v0.156.5 — loud, never silent — and recovery is a re-copy (`--restart-from-scratch`); run with `--exactly-once-lanes`, or apply serially with `--apply-concurrency 1` (whose marks cost next to nothing, since it already commits once per source transaction), if that matters more than the lanes' throughput. Primary-key-only tables are unaffected either way, and every change on every path still CHECKS the marks that exist, so a lane never re-applies a change a barrier or serial mark proves already landed. On a trigger-CDC source every change is its own transaction, so with the flag on the cost is one drain per CHANGE to a table with a secondary unique index (its position rides that change's lane commit).

With the flag on, a lane commit that also carries the position can fail at the COMMIT itself in a way that leaves its outcome unknown (a commit that outlived the apply's statement timeout, or a connection lost during the COMMIT). sluice does not retry that batch in place — had it actually committed, a retry would count its rows twice — and instead stops the apply attempt, which the retry loop re-enters from the position and marks the target actually holds; the error names the transaction and says "unknown outcome". **`FOLD-TICKET-DUPLICATE`** is an internal-consistency refusal: one lane batch was handed two such positions, which the coordinator must never do. The run stops without applying the batch; please report it with the log around it.

**The barrier's position, flag or not.** Since ADR-0190 amendment E, a lane barrier — a change to a table with no key, a primary-key change, a schema snapshot, and on a Postgres target a `TRUNCATE` — writes the position at the start of its source transaction in its OWN target transaction, after its row and its mark, instead of in a separate synchronous write just before it: one commit per barrier instead of two, with nothing to configure. A `TRUNCATE` on a MySQL, Vitess or PlanetScale target keeps the separate write, because MySQL commits a `TRUNCATE` implicitly and nothing after it would share its transaction. **`BARRIER-FOLD-NOT-TRANSACTIONAL`** is the internal-consistency refusal for that case: the coordinator handed such a `TRUNCATE` a position to write anyway. The run stops before writing anything; please report it with the log around it.

**Clean-up.** A transaction's marks are deleted by the same target transaction that persists a position past it, so the table holds only the marks of transactions the persisted position has not passed yet — normally none, and after a crash those of the one interrupted transaction. Every cold start (`--restart-from-scratch`, `--reset-target-data`, the automatic re-snapshot) deletes the stream's marks before it copies anything.

**`APPLY-MARK-MISMATCH`** (terminal) means a replayed change and the mark that should vouch for it disagree: the mark names the same position in the same transaction but a different change, or it was written under a different `--where` row filter than the one the stream runs with now. sluice refuses rather than skipping, because a skip on doubtful evidence could drop a change the target never received. For a changed `--where`, re-run with the filter the stream was established with; otherwise re-copy with `sync start --restart-from-scratch`, which also clears the stream's marks.

**`APPLY-MARKS-UNAVAILABLE`** (a WARN at the start of an apply run) means the mark table cannot be used: it could not be created (a PlanetScale branch with safe migrations enabled, a role without `CREATE`), it is absent on a `--schema-already-applied` target, or the role lacks `SELECT`, `INSERT`, `UPDATE` or `DELETE` on it. The stream then runs exactly as it did before ADR-0190: a restart after a crash mid-transaction replays the interrupted transaction, which may stop loudly on a unique collision, and a table with no usable unique key may gain a duplicate of a replayed row. A probe of the mark table that fails with a transient error (a dropped connection, a timeout) does not produce this WARN: the apply retry loop retries it, and only a definite answer that the table cannot be used disables the marks. To enable the marks, let sluice create the table (or have a role that may create it run the statements `sluice control-tables ddl --engine <target engine>` prints) and grant the apply role those four privileges.

On a **Postgres** target, v0.156.5 and earlier reached this WARN only in the `--schema-already-applied`-without-the-table case: every start ran `CREATE TABLE IF NOT EXISTS` and `ALTER TABLE … ADD COLUMN IF NOT EXISTS` against every control table, and PostgreSQL checks `CREATE` on the schema and table ownership before it looks at `IF NOT EXISTS`, so a role without `CREATE`, or one that did not own `sluice_cdc_state`, stopped the start loudly first (Bug 291). From the release after v0.156.5 (GC-40 (a)), each Postgres control-table ensure reads the catalog first and runs only the DDL whose table, column or index is actually missing, so a role holding only `SELECT`, `INSERT`, `UPDATE` and `DELETE` on control tables another role created starts and streams, and the role causes above reach this WARN as they do on MySQL. DDL that is genuinely needed and that the role cannot run still stops the start, now with **`CONTROL-TABLE-DDL-REQUIRED`** naming the missing table or column and the exact statement to run as the owner. `sluice control-tables ddl --engine postgres` prints the whole set: each table's `CREATE` followed by the `ADD COLUMN` statements later releases added, all idempotent, in schema `public` (use your DSN's `schema` if it names another). One exception does not degrade: on a PlanetScale Neki target, if the table is created but cannot be placed in an unsharded shard group, the start refuses with `SLUICE-E-TARGET-CONTROL-TABLE-PLACEMENT`, exactly as every other sluice control table does there — a mark table spread across shards would be read and written inconsistently, which is worse than no marks.

**`APPLY-MARK-UNTRUSTED`** (a WARN, at most once per apply run) means a restart met a mark of a transaction that was not the first one it re-delivered. Marks only ever exist for the first transaction after the persisted position, so this means the position had moved behind them; sluice then treats the mark as no evidence and APPLIES the change rather than skipping it. Nothing is skipped silently, but the re-apply is not always loud: a unique collision stops the stream, while on a keyless table it can add a duplicate row (keyless apply is at-least-once, ADR-0089), so compare that table against the source. On a SHARDED Vitess / PlanetScale keyspace it is expected after a crash, not a defect: a restart may deliver another shard's transaction first (see "Which sources are covered" above). On every other source it is a safety net: every known way for the position to move behind the marks is fixed (a schema change reaching a table inside a transaction used to persist the schema event's own, earlier, position on the serial batched path), so please report it with the log around it.

An older sluice binary ignores the table entirely and replays as it always has.

## Backup-chain replay resumes inside an incremental, exactly-once where the chain records identities (`BROKER-INCREMENTAL-PARTIAL`, `SLUICE-E-BROKER-KEYLESS-TABLE`, `SLUICE-E-BROKER-INCREMENTAL-REWRITTEN`, `SLUICE-E-RESTORE-KEYLESS-TABLE-NOT-EMPTY`)

Since ADR-0191 the apply marks above cover backup-chain replay too, for a chain that records them. `backup stream` and `backup incremental` store each change's apply identity — the source's own transaction id and the change's ordinal in it — next to the change (the manifest says so with `apply_identity`), and the `sync from-backup` broker hands it to the applier exactly as `sync start` would. The broker's position can also stand **inside** an incremental: it advances, in the same target transaction as the work, to the last source-transaction boundary whose effects are durable, and records the incremental's id and a digest of its chunk list. So when a broker run is interrupted partway through an incremental — an apply error, a crash, a SIGINT or SIGTERM — the next run re-reads that incremental, skips what is already applied and re-delivers from the first source transaction not durably applied — the one in flight, or on the lane apply mode the transactions whose lanes had not all committed; the marks then skip the re-delivered changes which already landed, key changes and tables without a key included. A change the source reader could not name (a VStream COPY row or interleaved shard group, a MySQL transaction without a GTID or server identity, a row the capture synthesized such as an ADD COLUMN fill) is recorded without an identity: on a keyed table it re-applies without marks and converges by its key, except for a key moved onto another row inside the interrupted transaction, and the broker logs **`BROKER-UNIDENTIFIED-CHANGES`** once for each incremental that carries any; on a keyless table it is refused (below). If the incremental was rewritten between the two runs (smart compaction), the skip would be counted over a different stream, so the broker refuses with **`SLUICE-E-BROKER-INCREMENTAL-REWRITTEN`** (exit 3) instead; recover with `--reset-target-data`.

**Restarting over an existing position.** `--reset-target-data` is honoured whether or not the target already holds this stream's broker position: it clears that row and the stream's apply marks, then drops and restores as on a fresh target. `--at-chain-id` asserts what a target with **no** position holds; over an existing one it is accepted only when it names the link the position records as last fully applied with nothing in progress, and otherwise refuses with **`BROKER-AT-CHAIN-ID-CONFLICT`** before anything is applied (through v0.156.12 it was ignored and the broker resumed from the recorded position). If you restored the target to that link yourself, delete the stream's row from `sluice_cdc_state` and its rows from `sluice_cdc_apply_marks` first. A row is the broker's when its `_engine` marker says so (`backup-broker-v2`, or the classic `backup-broker`), whether or not the rest of it decodes: a broker row damaged from outside (a hand edit, a bad restore of the control table) refuses a plain run with **`BROKER-POSITION-CORRUPT`** and is discarded by `--reset-target-data` (through v0.157.0 it was reported as owned by a non-broker writer and the flag was refused). A row with no broker marker belongs to another writer, such as a `sync start` stream, and is refused with or without the flag.

**Downgrading below this release.** v0.156.12 and older read this release's position token as owned by a non-broker writer and refuse before they look at `--at-chain-id`. Delete the stream's row from `sluice_cdc_state` and its rows from `sluice_cdc_apply_marks` (or choose a new `--stream-id`), then start the older binary with `--at-chain-id=<the row's last_applied_backup_id>`; it re-applies any incremental the newer one was inside without marks, as it always did.

A chain written by an older sluice, and any incremental smart compaction rewrote (it collapses changes across transactions, so it drops their identities and clears `apply_identity`), records none. There the in-flight transaction is re-applied without marks: a table the applier upserts into on a key whose columns the replayed rows carry (a PRIMARY KEY, or a UNIQUE index whose every column is NOT NULL) converges for inserts, and for updates and deletes that keep each row's key; a transaction that changed a key value does not, and the `BROKER-INCREMENTAL-PARTIAL` paragraph below says what happens instead. A table with neither key falls back to a plain INSERT and would gain a duplicate of every row of that transaction the interrupted run had already committed (audit F-E1; measured, when the broker still re-applied whole incrementals, on Postgres at 2,001 target rows for 1,001 source rows, in both the serial and the lane apply modes). So would a target table whose only key is one the rows do not supply — re-keyed on a `bigserial`, a `GENERATED BY DEFAULT AS IDENTITY` column, a `DEFAULT gen_random_uuid()` column or a MySQL `AUTO_INCREMENT` surrogate — because every re-applied row draws a fresh key value: the applier still names that key in its `ON CONFLICT`, and nothing collides (measured at 2,000 target rows for 1,001). Apply marks cannot help that last shape even on a chain with identities, because a mark is keyed by the target key the rows do not carry.

**`SLUICE-E-BROKER-KEYLESS-TABLE`** (exit 3). `sync from-backup run` refuses an incremental before it applies anything of it — and at start for the incremental a broker is inside or about to start, so a restart learns of a refusal before anything is written — when a table that incremental touches has no such key AND its replay cannot be made exactly-once: the incremental records no identities, a change to the table inside it carries none (`BROKER-KEYLESS-NO-IDENTITY`: a VStream COPY row or an interleaved shard group), or the target's apply marks cannot cover the table (unusable by the role, `APPLY-MARKS-UNAVAILABLE`; a PlanetScale Neki target, whose cross-shard-group atomicity is unverified; a target engine without apply marks, such as SQLite; or a target keyed only on a column the rows do not carry). A table keyless on the target is covered by table-wide marks. One more incremental is refused this way after an upgrade: when the broker resumes from a position written by v0.156.12 or older (a classic `backup-broker` token, which kept no apply marks), the next incremental the chain already held may have been partly applied by that run with nothing to skip it, so it refuses with **`BROKER-CLASSIC-RESUME`** in the reason, as v0.156.12 did; the incrementals after it are judged normally. A `--reset-target-data` cold start runs the target half of that check before it drops anything. Each table's key is judged twice and the message says which judgment failed. The chain's **recorded** schema is judged by the same predicate the backup orchestrator uses for its own replay-overlap refusal; the **target** table is judged from its live catalog by the target engine's own collision rule, and its key must be made of columns the chain's rows carry (a non-generated column of the recorded table, not generated on the target). On Postgres the key judged is the one the applier names in its `ON CONFLICT` — the very function it calls to pick that arbiter, so a partial, expression or nullable UNIQUE index does not count, and a supplied UNIQUE index beside an unsupplied primary key does not count either, because the re-applied INSERT would then fail on it. On MySQL any PRIMARY KEY or UNIQUE index counts, because `ON DUPLICATE KEY UPDATE` collides on every one of them, but only when every key part is a NOT NULL plain column (it does not collide on a NULL). The two judgments cover each other's blind spots: the recorded schema cannot see a target that lost the key, and the target cannot see that a keyless source may hold duplicate rows, which the recorded judgment refuses outright. Neither sees a target key that is coarser than a keyed source's identity — a MySQL prefix UNIQUE index, or a case-insensitive collation over a case-sensitive source column: such a key collides as designed and merges distinct source rows on the first apply, not only on a replay, so a pre-created target's unique keys must be at least as fine as the source's. The broker has no table filter, so every table in the chain is in scope. The remedy depends on the reason the message gives: for an incremental without identities, `--reset-target-data` restores the chain through its tail and the broker then judges only the incrementals that follow (which this sluice writes with identities); for the target's marks, make them usable; otherwise a key on the source and a new full backup, or `sluice sync start` for those tables. For **`BROKER-CLASSIC-RESUME`** none of those applies — the chain may already be one this sluice wrote, and re-running the same command refuses again, because the old position is replaced only by applying the incremental it refuses. Recover with `--reset-target-data`. When the classic position is the only reason the incremental is refused, the hint also offers an operator's assertion: only if you know that no broker run started applying the named incremental after that position was written, delete the stream's row from `sluice_cdc_state` and run again with `--at-chain-id=<the row's last_applied_backup_id>`. A later run that refused the incremental — a v0.156.11 or v0.156.12 broker, say — is no evidence: an earlier, older run may have been interrupted inside it and left the same position. If the assertion is wrong, the rows that run committed are duplicated, silently. When the incremental also records no identities, or the target's marks cannot cover the table, that route would only refuse again, and the hint does not offer it. A key added to the target table is not a recovery here: a table keyless on the source may hold duplicate rows, which the key would merge. v0.156.11 and v0.156.12 refused every keyless table in the chain, whatever the incremental.

**`BROKER-INCREMENTAL-PARTIAL`** (exit 1). A cancel that lands while the broker is applying an incremental is no longer a clean exit. The rule is mechanical: if the context is cancelled while the broker is inside an incremental — its schema deltas, its change chunks, or the final position write — part of it may be committed beyond the position, so the run returns an error carrying this marker and the incremental's backup id, and states that the next run re-applies the source transaction that was in flight — exactly-once when the incremental records identities, in which case re-running the same command is the whole recovery, whatever the transaction did. A cancel observed anywhere else (between incrementals, between ticks, during the chain walk or the integrity checks) has applied nothing of an unadvanced incremental and still exits 0. `sluice sync from-backup stop` is observed only between ticks, so it always exits 0; use it to stop a broker deliberately. On the live panel, `q`/ctrl+c is the same cancel as SIGINT, and the panel reports this error rather than "stopped." On an incremental without identities, re-running the same command is the recovery when the in-flight transaction did not change any row's key value: every table that incremental touches was judged to have a key the replayed rows carry and collide on, so re-applied inserts, and updates and deletes that keep each row's key, converge. A transaction that changed a key value is different. The re-run re-inserts a row the interrupted run had already moved, and the move then collides with the moved copy, so the re-run fails on a duplicate key (MySQL 1062 / Postgres 23505) on every attempt; in the lane apply mode a failed re-run can also have committed part of it first. Worse, when a key value was moved off one row and onto another inside that transaction, the re-run can apply a change to the wrong row with no error at all (measured on both engines: re-applying "move 1 to 2, delete 2, move 3 to 1" onto the source's end state deletes the row now at 1). If the source changes key values inside a transaction, recover such an incremental with `--reset-target-data` instead of re-running. Both shapes converge on an incremental with identities (audit F-E1-KEY-REUSE-REPLAY, pinned on Postgres and MySQL at every statement of both shapes). A cancel during a `--reset-target-data` cold start, after it has begun dropping the target's tables and before it records a position, returns **`BROKER-COLD-START-PARTIAL`** (exit 1) for the same reason: the target holds a partial restore and no position. Re-run with `--reset-target-data`; never start that target with `--at-chain-id`.

**`SLUICE-E-RESTORE-KEYLESS-TABLE-NOT-EMPTY`** (exit 3). `restore` — a single full or a whole chain — has the same exposure on a re-run: the full's bulk load appends, and an incremental's INSERTs upsert only where the target has a key, so re-running a restore that failed partway onto the same target writes everything the earlier attempt wrote a second time. A keyed table then fails loudly on its key, on every target engine: Postgres `COPY`, SQLite's `INSERT` and MySQL's batched `INSERT` fail on it, and when MySQL's `LOAD DATA LOCAL` path skips the duplicate row with a warning instead, sluice refuses that skip as `LOAD-DATA-ROWS-SKIPPED`. The door refuses the duplicating remainder: an in-scope table (after `--include-table` / `--exclude-table`) that is keyless on either judgment above **and already holds rows on the target**. An empty keyless table — a fresh target, or tables the operator pre-created empty — restores normally, and tables outside the restore's scope are never examined, so restoring into a database that holds other data is unaffected. `restore` has no `--reset-target-data`: after a restore that failed partway, empty (`TRUNCATE`) or drop **every** table it loaded — not only the named ones, since a keyed table it loaded fails the re-run on its key — and re-run; or exclude the named tables. If those rows were loaded deliberately, decide first whether the restore should add to them; nothing in the target can tell them apart from an earlier attempt's. The `sync from-backup run --reset-target-data` cold start drops its tables before its restore and does not reach this refusal. The door applies to every target engine with a row writer — Postgres, the MySQL family and SQLite — and refuses, rather than skips, a writer that cannot answer either judgment.

**Severed transactions in the chain itself (`SLUICE-E-BACKUP-CHAIN-SEVERED-TRANSACTION`, `CHAIN-APPLIED-SEVERED-TRANSACTION`).** Separately from re-applying an interrupted incremental, a chain an older `backup stream` wrote can carry one source transaction across two incrementals — a window that ended inside a source transaction, or, on Postgres chains written before v0.138.0, a resume that re-delivered the previous window's last transaction — or an incremental whose `EndPosition` is past its last stored change (the old cancel-drain loss). On every tick with new incrementals, before applying them, the broker runs the same severed-transaction check chain restore runs, over the whole chain. A finding that lands on a link it has **not** applied yet refuses (exit 3, with `SLUICE-E-BACKUP-CHAIN-SEVERED-TRANSACTION`, or `SLUICE-E-BACKUP-INCOMPLETE` for the `EndPosition` shape), before anything of that tick is applied; the remedy is a new full backup and a new chain. A finding on a link the broker **already** applied — by an older binary, or a pre-v0.138.0 Postgres resume — cannot be undone by refusing, so it is logged once per run as the WARN `CHAIN-APPLIED-SEVERED-TRANSACTION` and the broker continues; compare the tables those links touched against the source, or rebuild the target from a new full backup. The re-delivered-transaction shape is judged only when replaying into Postgres. See the [error-code table](error-codes.md) for both codes.

**Who should check, and how.** Any keyless table — or any target table keyed only on a serial, identity or defaulted surrogate the chain's rows do not carry — that a `sync from-backup` broker on v0.99.222 through v0.156.10 replayed into, if that broker was ever interrupted — an error mid-incremental, a crash, a SIGINT/SIGTERM, a supervisor restart — may hold duplicate rows; compare it with the source (a per-table row count shows it — `sluice verify --depth count`, or `SELECT count(*)` on both sides). Brokers on v0.20.0 through v0.99.221 had the opposite failure: the same interruption skipped the rest of the incremental, so a keyed or keyless table could be missing rows. And re-running a `restore` (a single full or a chain) onto the target an earlier, failed attempt had written duplicated every such table's rows in every release through v0.156.10; if you ever did that, compare those tables too.

## A stream row dated in the future is unknown, not fresh (`CONTROL-TIMESTAMP-IN-FUTURE`)

`sync health`, `sync status` (and the `sync status --all` fleet view), `sluice_seconds_since_last_apply` and the live panel all age a stream by its `sluice_cdc_state.updated_at` against the clock of the host they run on. A row that reads more than 60 s in the future says nothing about how recently the stream applied, and a negative age is below every staleness threshold, so it is reported as unknown under **`CONTROL-TIMESTAMP-IN-FUTURE`** rather than as fresh: `sync health` exits 1 whatever `--max-stale-seconds` says (state `UNKNOWN`, JSON `control_timestamp_in_future: true`), `sync status` shows the marker in the AGE column and `control_timestamp_in_future` in its JSON, the metric reads `+Inf` so a `> N` alert fires, and the live panel shows the freshness as unknown. Up to 60 s is treated as clock skew and aged normally.

Two things produce such a row. A sluice older than v0.156.5 wrote `updated_at` in the database's local time on a Postgres target whose zone is east of UTC (hours in the future, e.g. 9 h on `Asia/Tokyo`); and the target's clock can run more than 60 s ahead of the host reading it. The stream's next position write corrects the row, so a running stream clears it at its next checkpoint — but a stream that is stalled or stopped never writes one, which is exactly the stream the probe exists to catch: restart it with `sluice sync start` and check again, and check NTP on both hosts.

## Identity columns: `IDENTITY-ALWAYS-DOWNGRADED`, `IDENTITY-ALWAYS-RESTORED`, `IDENTITY-OPTIONS-NOT-CARRIED`

A Postgres `GENERATED ALWAYS AS IDENTITY` column refuses application-supplied ids (SQLSTATE 428C9). sluice creates every identity column on a Postgres target as `GENERATED BY DEFAULT AS IDENTITY` so the bulk copy can land the source's ids, and says so **once per run** in a WARN marked `IDENTITY-ALWAYS-DOWNGRADED` that names every affected `table.column`. What happens next depends on the command:

- **`migrate`** restores `ALWAYS` after the copy and the constraints phase and logs `IDENTITY-ALWAYS-RESTORED`. Two migrate shapes are not the last bulk load into the table and keep `BY DEFAULT` with the WARN instead: a shard-consolidation run (`--inject-shard-column`) and `--force-cold-start`.
- **`sync` cold start, `restore`, chain restore** keep `BY DEFAULT`: their change appliers write explicit ids (CDC rows, incremental links, a `sync` resumed from a restored position), which an `ALWAYS` column would refuse mid-stream. Until you re-apply `ALTER TABLE … ALTER COLUMN … SET GENERATED ALWAYS` after the last such write, the target accepts application-supplied ids the source rejected.

The identity's sequence options (`START` / `INCREMENT` / `MINVALUE` / `MAXVALUE` / `CACHE` / `CYCLE`) are carried exactly on every Postgres-target path. Toward MySQL or SQLite neither the `ALWAYS` mode nor the options exist; the writer WARNs per column with `IDENTITY-OPTIONS-NOT-CARRIED` and the column lands as a plain `AUTO_INCREMENT` / rowid alias that accepts explicit values and steps by one (MySQL: by the server's `auto_increment_increment`).

## DEFAULTs on TEXT / BLOB / JSON / GEOMETRY columns: `LOB-DEFAULT-NOT-CARRIED`

MySQL rejects a plain literal `DEFAULT` on a TEXT, BLOB, JSON or GEOMETRY column and, before 8.0.13, rejected every DEFAULT there. On a MySQL 8.0.13+ target (PlanetScale and Vitess included) and on MariaDB, sluice carries such a column's DEFAULT in the parenthesised form both accept — `DEFAULT ('txt')`, `DEFAULT (X'00AB00')`, `DEFAULT ('{"a": 1}')` — translated per family: a Postgres `bytea` default as its bytes, `jsonb` as its document, a one-dimensional `text[]` / `integer[]` / `boolean[]` default as the JSON array the column's rows are stored as. The target's version comes from `SELECT VERSION()` when the writer opens.

A DEFAULT sluice cannot carry faithfully — any such DEFAULT on a MySQL target older than 8.0.13 or whose version could not be read, a geometry literal, an array of another element type, a bytes literal whose encoding is ambiguous — is handled by where it appears:

- **`CREATE TABLE`** (`migrate`, a `sync` cold start, `restore`) creates the column without it and WARNs `LOB-DEFAULT-NOT-CARRIED`, naming the table, column and reason. The copied rows carry their own values; only later inserts that omit the column are affected (and fail outright on a NOT NULL column). Re-create the DEFAULT on the target if your application relies on it.
- **A forwarded `ADD COLUMN`** is refused (`SLUICE-E-VALUE-UNREPRESENTABLE`, the same marker) before the target ALTER runs. The target fills every row it already holds with the column's DEFAULT, and the source's own fill emits no change event, so adding the column without it would leave those rows NULL where the source holds the default. Add the column on the target yourself with the right value for the existing rows, then resume.
