**CORRECTION (2026-10-13).** Two statements in these notes are wrong. First, the KEY-COLLATION-LOOSENED-WINDOW fix is inert when no row of the table follows the loosening `ALTER` inside the window: chain restore by v0.159.2 still merges two source rows into one at exit 0 there, on both the `backup incremental` and `backup stream` lanes, with `backup verify` passing (Bug 306, HIGH, fixed in v0.159.3). Second, "Anyone holding a chain that spans such a window: v0.159.2's restore of it now refuses `KEY-COLLATION-MERGE`" is false for a window that changed a key's collation and changed it back when the chain was written by `backup incremental` on v0.159.1 or earlier: that chain recorded only the reverted shape, so no release can see that the key was ever stricter, and v0.159.2 restores it, or replays it through `sync from-backup`, with the rows merged at exit 0 (Bug 307). The same is true of a `backup stream` window whose reader was behind the source when it read past the revert, and of any collation change made with `sql_log_bin=0` before v0.159.2. A `backup stream` window captured live, and a loosened window written by v0.159.0 or v0.159.1, do carry the evidence; v0.159.3 refuses both. If you restored, or will restore, a MySQL or MariaDB chain across a window in which a key column's collation changed, check each such table against the source (`sluice verify`, or `SELECT k COLLATE <the target key's collation> AS kk, COUNT(*) FROM t GROUP BY kk HAVING COUNT(*) > 1` on the source) and re-copy it on a mismatch, and take a fresh `backup full` to restore from in future.
